## 摘要
AI智能体可以通过将单个自然语言请求转化为跨越工具、文件和应用程序的多步骤过程来自动化任务。用户往往只能根据碎片化的执行信息和最终输出来判断该过程。为使已完成的过程更易于理解、验证和复用，我们研究了任务后工作流：对智能体已完成执行的可编辑、基于图的表示。我们首先分析了来自 n8n 的 10,803 个公开工作流模板，以刻画真实世界的自动化实践，然后开发了 Trace2Flow，一个研究探针，用于将智能体执行轨迹转化为可交互的任务后工作流。在一项研究中，参与者（N = 20）审查了包含提示或智能体错误的智能体执行。我们发现，与仅提示条件相比，任务后工作流提升了他们的理解和错误检测能力，并且验证主要是在用户跨多个证据来源进行交叉核对时取得成功。对于后续任务，调整工作流在成功率、时间和难度上与调整先前提示相当，并且往往更受偏好。

## Abstract
AI agents can automate tasks by turning a single natural-language request into a multi-step process spanning tools, files, and applications. Users are often left to judge that process from fragmented execution information and the final output. To make the completed process easier to understand, validate, and reuse, we investigate post-task workflows: editable, graph-based representations of an agent's completed execution. We first analyzed 10,803 public workflow templates from n8n to characterize real-world automation practice, then developed Trace2Flow, a research probe that translates agent execution traces into interactive post-task workflows. In a study, participants (N = 20) reviewed agent executions with prompt or agent errors. We found that post-task workflows improved their understanding and error detection over a prompt-only condition, and that validation succeeded mainly when users cross-checked across multiple evidence sources. For follow-up tasks, adapting the workflow matched adapting the prior prompt in success, time, and difficulty, and was often preferred.

## 1. 核心问题与研究动机

- **背景**：随着 LLM 发展，AI Agent 可将一句自然语言请求转化为跨工具、文件与应用的多步骤执行过程。高层提示（prompt）虽使任务委派更便捷，却把"监督负担"转移给了用户——用户需要理解 Agent 如何解释意图、验证其动作与输出、并定位潜在错误。
- **核心痛点**：现有 Agent 界面只暴露碎片化执行产物（动作轨迹、工具调用、中间输出、最终结果）。理解任务如何完成，仍需用户自行把分散在众多动作、工具和输出中的信息"拼接"起来。原始执行日志冗长、难以用于诊断（如 DiLLS 的发现）。
- **研究空白**：已有工作多聚焦于让"单个决策或输出"可解释，而**如何表示 Agent 端到端执行的结构以支持人类监督**尚不清楚；且已有从执行轨迹生成工作流的工作多将其作为"规范性（prescriptive）规格"约束后续执行，限制了开放式提示的灵活性。
- **核心主张**：提出**任务后工作流（post-task workflow）**——在任务完成后生成的、描述性（descriptive）而非规范性的、可编辑的图结构表示。它既"向后看"（理解、验证、定位错误），也"向前看"（复用、改编以完成相关任务），且不牺牲自然语言委派的灵活性。
- **研究问题**：
  - **RQ1**：任务后工作流如何帮助用户理解 Agent 做了什么、验证任务结果、识别执行错误？
  - **RQ2**：对于相关后续任务，用户更偏好复用/改编已生成的工作流，还是重新通过提示委派给 Agent？

## 2. 方法论

### 2.1 整体研究路径
- **三步走**：① 分析 10,803 个 n8n 公开工作流模板刻画真实实践 → ② 形成性调研（42 名 AI Agent 用户 + 39 名工作流自动化用户）→ ③ 开发研究探针 **Trace2Flow** 并开展用户研究。

### 2.2 真实工作流实践刻画（设计空间来源）
- **任务域分类**：人工审阅 100 个模板归纳出 4 类（客户运营、内容生产、数据分析、个人助理）+ Other，再用 **gpt-5.6** 对全部 10,803 个模板分类。
- **复杂度度量**：规模（节点数、边数、最长路径）与结构（平均节点度、环数）。
- **节点功能分类**：基于 n8n 官方 195 个节点及其支持操作，划分四类功能——**任务动作 / 数据处理 / AI 支持操作 / 工作流控制**，再由 **gpt-5.6** 结合节点类型、配置操作与工作流上下文分类。

### 2.3 Trace2Flow 系统设计
- **设计目标**（由透明度文献三原则 + 形成性调研推导）：
  - **DG1**：让执行过程可见可追溯（单一图中呈现动作、步骤、工具调用，可查看每步输入/输出，可重跑单步）。
  - **DG2**：支持基于工作流的改编与复用（只改必要输入/步骤/工具，保留其余流程）。
  - **DG3**：补充而非替代自然语言委派（提示与工作流无缝衔接）。
- **双界面**：
  - **聊天界面**：自然语言委派 + 轻量进度可见性（进度面板、当前活动指示器、任务完成后的 "Workflow" 入口按钮）。
  - **工作流画布**：节点=任务操作，连边=依赖关系；可选中节点查看/编辑输入、输出、参数；可增删节点、改连接、重跑整条工作流。
- **核心技术流程：Trace-to-Workflow 三阶段翻译**（借鉴 InstructPipe 思路）
  1. **Grounding（接地）**：检查 Agent 执行轨迹，将任务相关工具执行匹配到候选工作流节点规格；为每个操作保留期望输入/输出及轨迹中观测到的一个示例输出，形成**任务特定的节点目录**，约束后续生成并提供数据证据。
  2. **Generation（生成）**：LLM 接收原始用户提示、执行轨迹、接地后的节点规格，重构为**紧凑中间表示（IR）**；IR 同时表达单个操作及其数据依赖（如 `list_1.files` 表示下游节点消费 `list_1` 的 files 输出）。
  3. **Compilation（编译）**：将 IR 转为画布所需结构——实例化节点、把符号引用转为显式输入绑定与图边、校验被引用节点存在且输出与下游输入兼容；若校验失败，将 IR、编译结果与检测到的错误反馈给 LLM，允许**一次额外的重生成尝试**。
- **研究探针定位**：Trace2Flow 是用于研究"任务后工作流对终端用户作用"的探针，而非通用 trace-to-workflow 翻译方法。

## 3. 实验设计

### 3.1 数据集 / 场景
- **工作流模板语料**：n8n 公开模板 **10,803 个**（截至 2026 年 7 月）。
- **用户研究任务集**：**5 组任务对（T0–T4）**，改编自真实 n8n 工作流，覆盖 3 个任务域：
  - 数据分析：T0（生成模拟用户数据并统计订阅）、T3（图书信息采集、流派推断、按价格排序）
  - 客户运营：T1（简历筛选）、T4（客户评论处理）
  - 内容生产：T2（RSS 新闻文章处理与分发）
  - 参考工作流最长路径 5–10 步，含顺序、分支/合并、循环等结构（T0 含循环，T2 含分支）。
  - 每个 review 任务构造 3–5 个提示，选取 1 个执行案例作为研究对象。

### 3.2 错误案例构造（benchmark 性质）
- 每个 review 任务选取一个含错误案例：**2 个提示错误**（T2、T3）+ **3 个 Agent 错误**（T0、T1、T4）。
  - T0：Agent 把后两组用户合并处理（应分三组）。
  - T1：Agent 把 CV 中虚构地点误判为欧洲地点。
  - T2：提示把"相关内容发 Slack / 非相关内容写 Google Sheets"搞反。
  - T3：提示遗漏"非虚构写入 Sheet 3"及"按价格排序"要求。
  - T4：Agent 未利用已有评论过滤旧评论，直接全部写入。

### 3.3 对比条件与设计
- **被试内设计**，两条件：
  - **Chat 条件**：仅通过聊天界面审查执行，并**编写新提示**完成后续任务（可参考原提示）。
  - **Workflow 条件**：可额外访问任务后工作流进行审查，并通过**改编+重跑工作流**完成后续任务。
- 条件顺序与任务对分配**跨被试平衡（counterbalanced）**。
- 使用 **Wizard-of-Oz** 复现同一执行轨迹与输出，保证同一任务的被试观察到相同执行与错误。
- 流程：T0 任务对做教程 → 2–3 个正式 session（从前两 session 起每位被试经历两种条件）→ 半结构化访谈。

### 3.4 被试
- 招募 22 人，**20 人完成并纳入分析**（12 男 8 女，18–32 岁）；**7 人有近期工作流自动化经验，13 人无**；补偿 €15 礼品卡；经伦理审查批准。
- 纳入标准：至少每周使用 AI Agent 工具（ChatGPT Agent、Claude Cowork、Copilot 等）。

### 3.5 测量指标与统计方法
- **RQ1**：步骤精确率/召回率、工具精确率/召回率、流程理解准确率、自评理解（5 点）、验证成功（二值）；辅以屏幕录像编码（output check / workflow check / cross-check）与访谈。
- **RQ2**：任务成功（二值）、完成时间、感知难度（5 点）。
- **统计**：非二值指标按被试-条件聚合后用**双侧 Wilcoxon 符号秩检验**；二值结果保留 session 级观测（N=46），用**逻辑混合效应模型**：`Success ~ Condition + TID + Session Number + (1|Participant ID)`。

## 6. 主要结论与发现

- **RQ1（审查与验证）**：
  - 工作流条件显著提升**步骤召回**（M=.94 vs .78, p<.01）与**工具召回**（M=.84 vs .66, p<.05）；精确率两条件均高且无显著差异（说明并非"记得更多但更错"）。
  - **流程理解准确率**显著更高（M=.82 vs .57, p<.05），**自评理解**更高（M=4.47 vs 3.88, p<.05）。
  - **验证成功率**：工作流 15/23（65%）vs chat 7/23（30%），条件效应显著（β=2.62, SE=1.04, p<.05）；任务主效应显著（χ²(3)=8.66, p=.034），T3 显著高于 T4（OR=85, p=.019）；session 序号不显著。
  - **审查模式**（表 4）：仅做输出检查成功率极低（1/10, 10%）；仅做工作流检查 0/2；输出+工作流分别检查 4/8（50%）；**跨来源交叉核对达 17/23（74%）**，工作流条件下"输出+工作流+交叉核对"高达 11/13（85%）。
  - **工作流的边界**：当错误反映在**执行结构**中（T2 路由错误、T3 缺失分支、T4 缺失依赖）时工作流帮助最大；当错误取决于**对具体内容的正确性判断**（T1 虚构地点）时帮助有限。即便有工作流，仍有 8/23（35%）判断错误。
  - **质性**：20 人中 17 人认为工作流有帮助，14 人认为其价值在于"让过程透明"，7 人重视可打开单步查看输入/输出/参数/工具调用结果；2 人认为价值有限，1 人觉得图更令人困惑。
- **RQ2（后续任务复用）**：
  - **成功率**：工作流 17/23（74%）vs chat 13/23（57%），但**无统计显著差异**（p≥.05），任务与 session 序号亦不显著。
  - **完成时间**：工作流略长（6 分 12 秒 vs 5 分 24 秒），**不显著**。
  - **感知难度**：相近（1.77 vs 1.48），**不显著**。
  - **偏好分布**：9 人偏好工作流、6 人偏好改提示、5 人视情况而定。偏好工作流的理由：易于定位改动位置、任务已分解为显式步骤、可先测试单步再整体重跑、过程更"具体可控"（如"工具箱"）。偏好提示的理由：学习成本高、改动多时编辑繁琐。
  - **关键发现**：偏好提示**高度依赖"旧提示可用"**——当被问及若需从零写提示是否仍偏好提示时，6 人中仅 1 人（P15）坚持。说明提示复用的价值绑定于提示可获取性，而工作流作为**持久化制品**更具优势。
  - **偏好与经验相关**：7 名有工作流经验者中 6 人偏好工作流；13 名无经验者中仅 3 人偏好工作流、6 人偏好提示、4 人视情况而定（探索性观察）。

## 7. 优点

- **概念创新清晰**：提出"任务后工作流"这一**描述性而非规范性**的定位，明确区别于"用工作流规格约束执行"的既有路线，从而在保留提示灵活性的同时提供结构化监督对象。
- **研究链条完整**：真实数据刻画（10,803 模板）→ 形成性调研 → 系统实现 → 受控用户研究 → 访谈与录像编码，问题定义有实证基础，任务设计也源自真实 n8n 工作流。
- **设计目标与文献原则对齐**：DG1–DG3 直接由过程透明度的三条原则（结构化概览+步骤级可追溯+选择性介入）推导，设计有理据。
- **实验控制严谨**：被试内 + 平衡 + Wizard-of-Oz 复现同一执行与错误，有效隔离了"界面表示"这一自变量；对二值结果使用混合效应模型而非简单聚合，统计处理较细致。
- **混合方法互补**：量化指标（召回/精确率、验证成功率）+ 行为编码（output/workflow/cross-check 三种审查模式）+ 访谈，能解释"为什么成功/失败"，而非只报告显著性。
- **诚实的边界刻画**：明确指出工作流对"内容正确性类错误"帮助有限（T1、T4），并提出"应将每步链接到其消费/产出的确切数据与制品"的设计改进方向。
- **可迁移的设计启示**：验证成功的关键是**跨来源交叉核对**而非"展示更多信息"，这一发现对一般性的 Agent 监督界面设计具有指导意义。

## 8. 不足与局限

- **样本与经验分布**：N=20、仅 7 人有工作流经验，"经验降低复用门槛"的结论作者自认为探索性；子组样本过小，无法检验交互效应。
- **任务覆盖有限**：任务规模与结构复杂度受控（最长路径 5–10 步），后续任务刻意"最小改动"，无法外推到大型工作流或需大幅重构的任务；作者建议未来系统性变化改编范围。
- **错误类型覆盖窄**：仅 5 个错误案例（2 提示错误 + 3 Agent 错误），每任务每条件 5–6 个 session，单元格样本小、统计功效有限，任务间差异（如 T3 vs T4）可能受任务难度而非机制驱动。
- **翻译方法未泛化验证**：Trace2Flow 定位为研究探针，trace-to-workflow 翻译仅在研究任务集上验证，跨任务、工具、Agent 的泛化性未知。
- **条件混淆风险**：工作流条件同时提供"审查用的结构视图"与"可执行复用的制品"，两个作用难以完全分离；此外后续任务中 chat 条件可参考原提示，虽提升了公平性，但也可能使 chat 条件偏强，从而"稀释"工作流的相对优势。
- **生态效度**：研究在受控实验环境（含 Teams 远程控制、Wizard-of-Oz）中进行，非真实长期使用；作者指出**长期学习成本**是否随熟悉度下降尚不清楚。
- **激励与利害关系**：被试对任务无个人利害关系，也未涉及法律或企业合规要求下的人类监督场景，可能低估用户在真实高风险场景中的审查动机与偏好差异。
- **算力与复现透明度不足**：未报告模型推理成本、延迟、token 开销等，也未给出翻译成功率/失败率的量化评估，影响可复现性与工程可行性判断。
- **潜在偏差**：模板分类与节点分类均依赖单一 LLM（gpt-5.6）自动标注，虽有人工抽样校准，但可能存在系统性标注偏差；工作流模板来自 n8n 单一平台社区，代表性受平台生态限制。
