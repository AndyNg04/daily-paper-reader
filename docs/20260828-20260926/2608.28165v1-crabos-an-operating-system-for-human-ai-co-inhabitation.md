## 摘要
AI 智能体正在演变为能够调用工具、维护记忆并跨应用完成复杂任务的长期运行计算实体。在现实场景中，完成一项任务通常需要人类与 AI 轮流主导其执行。这种交替依赖于任务工作状态在人类与 AI 之间的无缝交接。然而，现有智能体系统为人类与 AI 提供了彼此分离的工作环境。因此，AI 智能体必须依赖额外的桥梁才能继续工作：要么由开发者构建特定任务的接口来访问工作状态，要么由用户通过截图或文本描述手动转移其中的相关部分。这两种方法都使交接成本高昂且难以扩展。我们提出人机共居（Human-AI Co-inhabitation），一种使人类与 AI 能够无缝轮流继续同一任务工作的工作环境，并设计实现了 CrabOS 来落实这一概念。CrabOS 将工作状态表示为人类与 AI 共享的、自然语言可读的文本对象，使双方无需桥梁即可通过同一可审计接口直接访问和操作它。案例研究表明，CrabOS 将对人类与 AI 交替主导的复杂任务的支持，从依赖桥梁的应用层解决方案提升为原生操作系统能力，为开发和运行 AI 智能体提供了新的基础。

## Abstract
AI agents are evolving into long-running computational entities that can invoke tools, maintain memory, and complete complex tasks across applications. In real-world settings, completing a task often requires humans and AI to take turns leading its execution. Such alternation depends on the seamless handoff of the work state of the task between humans and AI. Existing agent systems, however, provide humans and AI with separate work environments. AI agents must therefore rely on additional bridges to continue work: either developers build task-specific interfaces to access the work state, or users manually transfer relevant parts of it through screenshots or textual descriptions. Both approaches make handoffs costly and scale poorly.   We propose Human-AI Co-inhabitation, a type of work environment that enables humans and AI to seamlessly take turns continuing work on the same task, and design and implement CrabOS to realize this concept. CrabOS represents the work state as natural-language-readable text objects shared by humans and AI, allowing both to access and manipulate it directly through the same auditable interface without bridges. Case studies show that CrabOS elevates support for complex tasks with alternating human and AI leadership from bridge-dependent application-level solutions to native operating-system capabilities, which provide a new foundation for developing and running AI agents.

## 1. 核心问题与研究动机

- **背景趋势**：随着大语言模型能力提升，AI 智能体正从被动应答的对话工具，演变为可自主调用工具、维护记忆、长时间推进复杂任务的"计算实体"，与人类一样成为任务的独立执行者。

- **核心问题**：现有智能体系统为人类与 AI 提供的是**彼此分离的工作环境**，二者不共享工作状态，因此交接必须依赖额外"桥梁"：
  - 开发者需为每个场景定制专用接口来暴露状态；

- **两大成因**：
  1. 人类主要通过图形界面推进工作，AI 依赖自身运行时的对话上下文与记忆，状态以不同形式存储，无法互相复用；
  2. AI 只能看到宿主应用暴露的狭窄接口，而非人类实际所处的完整工作环境。
- **后果**：任务阶段越多，桥接负担越重、可扩展性越差；这是应用层方案的结构性缺陷。

## 2. 方法论

### 2.1 核心思想

一个工作环境由**工作状态**与**访问接口**构成，工作状态又包含**工作数据（work data）**与**工作对象（work objects）**。人机共居要求二者同时满足三个条件：统一访问工作数据、共同指称工作对象、统一可用的访问接口。由此导出三条设计原则：

- **原则 1：工作数据文本化（Textualize Work Data）**
  - 工作数据须以**自然语言可读、结构稳定的文本对象**持久化，人类可直接读懂修改，AI 可直接解析续用，读写与订阅即普通文件系统操作，无需为每个协作场景设计专用 API。
  - 论文指出数据库方案的隐性代价：状态一旦进入数据库，唯一合法通路就是 API，能力只能"预先枚举"，未实现的能力等于不存在。
- **原则 2：共享工作对象（Share Work Objects）**
  - 人类与 AI 须直接操作**同一组可指称的工作对象**。工作对象既包括文件、任务、页面等已持久化实体，也包括当前窗口、选区、焦点位置等**尚未持久化的活跃操作状态**。
  - 若仅靠截图，AI 必须重新识别页面、选区与焦点，截图/粘贴/复述成为每次交接都要支付的桥接成本。
- **原则 3：统一能力入口（A Unified Capability Entry）**
  - 取消专为 AI 构建的私有工具封装层，所有执行者（人、AI、应用）通过**同一可审计入口**调用系统能力。
  - 动机：AI 与人共享环境后不能默认拥有与人类同等的信任级别，系统必须在调用时刻识别调用主体、解析目标并施加授权与约束。

### 2.2 系统架构（四层）

- **L0 对象层（Object Layer）**
  - 所有状态物化为文本对象，文件系统仅作为天然可寻址的通用 I/O 载体，内存只作缓存。
  - 八类对象，缺一即破坏访问契约：
    - 人类写入：`File`（供人读）、`Handbook`（供 AI 读，推理前主动注入上下文）；
    - AI 执行写入：`Chat`（交互驱动，逐步等待人类消息）、`Task`（入队后自主执行至完成）、`Memory`（跨会话蒸馏，作用域超出单次交互）——三者在索引策略、执行模型、权限边界上不同；
    - CrabOS 写入：`App`（安装信息）、`Config`（行为权威来源，系统运行必需）、`System`（运行时派生的次要数据，可删除并自动重建，不可与 append-only 的 Log 混淆）。
  - **关键机制**：许多能力无需在系统层实现，而是从可寻址文本对象中"涌现"——hook 即对某路径变更的订阅；子智能体即创建 Task 对象并等待完成；跨智能体共享上下文即读取另一智能体的 Memory。所需原语仅为 `WaitPathChange`、`ReadFile`、`WriteFile`。
- **L1 系统服务层**
  - 三层结构：顶部 **Kernel Interface**（统一入口）→ 中部各服务 → 底部 **Object Manager**（统一对象 I/O、集中 schema 校验与写入优化）。
  - **Kernel Interface 五阶段强制流水线**：Subject Binding（主体绑定，身份在传输层强制而非自报）→ Contract Resolution（契约解析，确定能力类型与边界）→ Policy Enforcement（策略执行，越界即拒）→ Authorization Gate（需显式授权的操作挂起等待确认）→ Capability Dispatch（派发到对应服务）。
  - 服务包括：**Agent Runtime**（Chat/Task 两种模式；智能体行为由 system prompt + 状态信息槽位 + 工具集构成的模板决定，故不同交互形态只是模板配置，Claude Code 的 plan 模式、Codex 的只读模式均可由此表达）、**App Runtime**（应用发现与验证，把聚焦窗口呈现为用户工作区）、**Index Service**（全对象空间索引与语义检索）、**Network Service**（统一管控网页浏览、外网访问、远程命令执行）、**Object Manager**。
- **L2 Shell 层**
  - 定位：既是人类操作界面，也是 **AI 感知人类工作状态的层**——当前运行应用、聚焦窗口及其内容需有唯一权威来源，该来源不能位于 L3（与其管理的应用同级，破坏分层）也不能位于 L1（无头计算层不应渲染 UI）。
  - 刻意克制设计：**最小内置面 + 最大扩展空间**，只有两个不可替代模块——`GUI Shell`（Dock、应用启动与窗口托管）与 `Text Shell`（与系统 AI 智能体对话的终端，必须先于一切应用存在）。
- **L3 应用层**
  - **最区别于现有智能体系统之处**：应用与系统 AI 智能体地位对等，通过 SDK 拥有与 AI 智能体相同的系统 API 调用能力，因而可自行实现智能体逻辑、成为 AI 智能体。
  - 预装 Memory Manager、Image Preview、Task Manager、File Manager、Text Editor、App Manager、Settings，但**全部是 L3 应用且可任意卸载**，无任何应用被硬编码进系统。

### 2.3 实现要点

- 基于 **Electron** 与 Web 技术构建，原生跨平台；L2 GUI Shell 与 L3 应用共享同一渲染环境，无需桥接原生 UI 与 Web 层。
- L3 应用以 **iframe** 为运行时，复用浏览器安全模型；浏览器文件 I/O 能力有限，由 L1 的 **App SDK** 补齐，应用与 AI 智能体走同一统一入口，无法绕过 Kernel Interface；iframe 支持 WebAssembly 与 WebGPU，可承载计算密集任务。
- **原生应用三条接入路径**（集成深度递增）：① 完全重写为 L3 应用；② 仅重写 L3 GUI、保留原生后端 API 并在沙箱中运行；③ GUI 适配器——实现 L3 界面，把界面操作映射为 UI 控件再映射为控件坐标驱动原生应用；对人与 AI 而言入口是同一个 L3 应用。
- **开箱即用 / 零依赖**：Index Service 在本地执行嵌入，通过 Transformers.js 加载 ONNX 模型并在 Node.js 进程内推理，不依赖云端嵌入 API，向量索引完全离线。

## 6. 主要结论与发现

- 复杂任务的交替主导能否**无缝**，取决于上一阶段的工作状态能否被下一阶段直接使用；这本质上取决于人与 AI 的工作环境是否共享所需状态。
- 现有系统（人类中心式 AI 辅助、自主智能体系统、已有 Agent OS）分别只服务单一执行者，或其关注点在"更强的执行平面与更细粒度治理"，而非"让人与 AI 在同一工作环境中共居"，因此状态与接口被封闭在各自边界内，无缝续接必须依赖桥梁。
- 通过三条设计原则（文本化工作数据、共享可指称工作对象、统一可审计能力入口），CrabOS 把记忆管理、跨应用上下文延续、多智能体编排、操作轨迹等能力变为可由操作系统原语**组合涌现**的能力，而无需额外桥接。
- 结论：当 AI 成为长期运行的执行者，基于人机共居三原则构建的操作系统有望成为未来智能体系统的基础设施。

- **实证证据缺失是最大短板**。核心主张是"桥接成本下降、交接无缝"，但全文没有给出任何可测量的桥接成本定义，也没有交接成功率、状态重建耗时、token 消耗、人工干预次数等指标。案例研究只能证明"架构上可以这样表达"，不能证明"这样做确实更省成本"。
- **文本作为权威状态载体的工程风险未被讨论**：
  - **并发与原子性**：以文件系统取代数据库，意味着放弃事务、锁与一致性保证。当人、多个 AI 智能体、多个 L3 应用同时读写同一对象时，冲突解决、写丢失、部分写入等问题的处理策略论文未展开。
  - **规模可扩展性**：全对象空间索引 + 语义检索在对象数量、更新频率增长后的性能表现（索引重建成本、增量更新策略）没有任何数据支撑。
  - **schema 漂移与解析脆弱性**：文本对象"自然语言可读"的优点是双刃剑，AI 解析依赖约定而非形式化约束，一旦写入格式偏离预期，下游消费者可能静默失败。
- **安全模型讨论偏概念化**：五阶段流水线设计合理，但论文未说明策略（Policy）如何表达与组合、授权请求如何避免疲劳式弹窗、恶意或提示注入的 L3 应用能否借助"与应用同权"的智能体能力绕过约束。Subject Binding 在传输层强制是优点，但主体粒度（进程级？应用级？会话级？）与权限继承规则未明确。
- **实现细节与可复现性不足**：未报告代码规模、模块划分粒度、Kernel Interface 的实际调用开销、iframe + App SDK 组合在复杂应用（如大文档编辑器、IDE）中的实际可用性；第三条原生应用接入路径（坐标驱动）在论文自身也隐含承认其脆弱，但未评估其鲁棒性。
- **技术栈选择的隐性代价**：以 Electron 与 Web 技术为基础虽带来跨平台与统一渲染的好处，但也引入了内存占用、启动延迟、原生体验妥协等已知问题，论文对此未作权衡讨论，而这恰恰是"操作系统"定位下用户敏感的部分。
- **场景覆盖有限**：案例集中在单用户、桌面、文本/文档密集型任务；多用户协作、移动端、实时多媒体编辑、强交互图形应用等场景下三原则是否依然成立，未被触及。
- **对比的公平性**：对 OpenClaw、Hermes、Codex、Claude Code 等的描述以架构概览为主，未在其真实运行中执行同一任务，也未承认这些系统在作者所批评维度之外（如开箱可用性、生态成熟度、模型协同深度）的优势，存在叙述性偏差。

## 9. 启示与可延展方向

- **把"工作状态共享"当作一等系统问题**，而非每个应用的集成任务，这一视角迁移性强：即便不采纳 CrabOS 的全部设计，其"状态可寻址 + 对象可指称 + 入口可审计"的三元要求也可作为评估任何 agent 平台的检查清单。
- **"能力涌现"优于"能力枚举"**的工程哲学值得借鉴：用少量通用原语（读、写、等待路径变更）组合出 hook、子智能体、跨智能体共享上下文，能显著降低系统层的设计负债，这一思路同样适用于工具生态与插件体系设计。
- **操作轨迹的副产品价值**：把工具门控与主体绑定结合起来，使语义级操作日志成为系统自然产物，这为 AI 接管、审计以及大模型后训练数据获取提供了低成本通道，可能是本文最具长期价值的设计之一。
- **待验证的关键问题**：文本状态在真实并发负载下的可行性、统一入口的安全边界、以及"人机共居"对用户认知负担的实际影响（是否会因 AI 可见全部工作状态而带来隐私与心理压力），都需要后续的定量实验与用户研究来回答。
