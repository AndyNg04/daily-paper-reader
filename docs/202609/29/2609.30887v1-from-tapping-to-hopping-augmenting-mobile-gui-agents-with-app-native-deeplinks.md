## 摘要
移动 GUI 智能体通过点击、滑动等 GUI 操作完成任务。这些操作广泛适用于各类应用，但到达目标界面往往需要逐屏导航。一次深度链接调用即可替代一连串逐屏执行的 GUI 操作。因此，我们提出混合交互方式：使用深度链接直接导航，并使用 GUI 操作完成其他屏幕操作或在深度链接不可用时作为备用方案。为实现这一方式，我们通过静态分析发现候选深度链接，在真实设备上验证其有效性，并描述实际到达的页面。该过程构建了一个经过验证、具有实际页面依据的深度链接目录，将每个可用的深度链接与其目标页面描述配对。基于这一目录，我们提出 GUI-Hopper。它提高了真实设备上商业应用中的任务成功率，进一步证明了混合交互的优势。

## Abstract
Mobile GUI agents complete tasks using GUI actions like taps and swipes. These actions are broadly applicable across applications, but reaching a navigation interface. A single deeplink call can replace a sequence of screen-by-screen GUI actions. We therefore introduce hybrid interaction, using deeplinks for direct navigation and GUI actions for other on-screen operations and fallback. To enable this, we discover candidate deeplinks through static analysis, validate them on real devices, and describe their observed landing screens. This process creates a verified and grounded deeplink catalog that pairs each working deeplink with a description of its landing screen. Using this catalog, we introduce GUI-Hopper, a improves task success in commercial applications on real devices, further demonstrating the benefits of hybrid interaction.

## 1. 核心问题与整体含义

- **研究问题**：移动 GUI 智能体通常只能通过点击、滑动等操作逐屏导航。目标页面越深、任务涉及的应用越多，操作链就越长，出错机会也越多。
- **核心洞见**：部分 Android 应用原本就提供可直达应用内部页面的**深度链接（deeplink）**。论文主张将其用作高层导航动作，同时保留 GUI 操作来读取信息、填写或提交内容，以及在跳转失败时继续任务。
- 因此，论文研究的不是用深度链接取代 GUI，而是让智能体学会**何时“跳转”，何时“点击”**。

## 2. 方法论：GUI-Hopper 如何工作

- **构建经过验证的链接目录**：先从应用安装包的清单和快捷方式定义中静态提取候选链接，过滤无法被外部调用或无法解析的条目；再在真实设备上尝试调用、测试参数、剔除无效或重复条目。保留的目录项包括落地页面描述、参数格式与示例，以及供执行和校验使用的调用模板、预期 Activity。真实应用目录最终有 **1,251 个条目**，其中 **246 个带输入参数**。
- **训练混合动作策略**：智能体可选择 GUI 动作，或调用带具体参数的深度链接。训练轨迹既包含多次跳转与后续 GUI 操作，也包含两类反例：*链接缺失或仅有无关链接*，用于学习改走 GUI；*故意调用错误链接*，用于学习识别和恢复。
- **在线强化学习**：在任务成功的前提下，奖励正确到达预期页面的相关链接调用，以及短于参考长度的轨迹。论文的奖励可概括为  
  `任务成功 ×（1＋链接调用奖励＋轨迹效率奖励）`；任务失败时总奖励为零。策略更新采用 GRPO。
- **推理时的执行闭环**：系统先将任务拆成导航目标，结合语义匹配与 BM25 检索，提供**最多 10 个**候选链接。调用后不仅检查命令是否执行，还检查实际前台 Activity 是否与目录记录相符；失败则向智能体反馈，以便使用 GUI 恢复。**到达预期 Activity 不等于任务完成**，保存、发送及结果确认仍可能需要 GUI 操作。

## 3. 实验设计与对比

- **MobileWorld**：模拟 Android 环境，含 13 个内置应用、117 个任务；每种设置每个任务运行 3 次，共 **351 次任务执行**。对应目录有 34 个链接。
- **MobileWorld-Real**：在实体设备上的商业应用场景，从中选取 **26 个应用、119 个任务**，使用上述 1,251 条链接目录；文中未像 MobileWorld 一样明确说明各设置的重复次数。
- **指标**：任务成功率、成功轨迹的平均交互步数，以及所有轨迹的平均交互步数；附录还报告了部分执行耗时。
- **主要对比**：在 Qwen3.5 的 4B、9B、35B-A3B 三种规模下，比较原始模型、仅用 GUI 训练的模型与混合训练的 GUI-Hopper；另列出多种通用视觉语言模型和专用 GUI 模型作为参考。论文还测试了不提供链接、提供任务匹配链接、检索前 10 条及提供完整目录等条件。

## 4. 资源与算力

- 论文给出了部分**训练配置**：监督微调 6 个 epoch、上下文长度 28,672 token；在线强化学习每组采样 8 条轨迹，轨迹上限为 50 个交互步骤等。
- **未明确报告 GPU 型号、GPU 数量、总训练时长或总 GPU 小时数**，因此无法据此评估完整训练算力成本。链接挖掘与真实设备验证的总耗时也未给出。

## 5. 实验数量、充分性与公平性

- 实验覆盖**两个 benchmark、三个模型规模**，并包含训练阶段消融、链接供给条件、单应用与跨应用任务分析、执行时间分析及成功和失败案例。覆盖面较好，不只依赖单一模型或单一场景。
- 同规模的 GUI-only 与混合训练模型使用配对任务轨迹和相同的基本训练配置，这是较有说服力的受控比较；MobileWorld 上还测试了 GUI-Hopper **在推理时不给链接**的表现。
- 但需区分两种效应：主结果同时改变了**训练方式和推理时可用的动作**，不能把全部提升都归因于某一个环节。真实设备实验选取的是 benchmark 中的部分应用与任务；论文也未报告统计置信区间。此外，“所有轨迹平均步数”会受到失败轨迹提前结束的影响，应结合成功率和成功轨迹长度一起解读。

## 6. 主要结论与发现

- 在 **MobileWorld** 上，GUI-Hopper 相对同规模 GUI-only 模型，三种规模的成功率分别由 **52.7%→60.1%**、**54.4%→63.5%**、**57.8%→64.1%**；所有轨迹的平均步数也均下降。
- 在 **MobileWorld-Real** 上，相应成功率由 **70.2%→84.0%**、**77.1%→86.6%**、**79.2%→89.1%**，同时平均步数下降。
- 在 MobileWorld **不给深度链接**的评估中，混合训练模型的成功率仍略高于 GUI-only 模型，说明收益并非完全来自即时跳转；但“混合训练改善了任务规划”仍是论文提出的可能解释，而非已被严格证明的机制。
- 链接供给实验显示，未经专门训练的模型面对更大的候选目录时成功率可能下降；GUI-Hopper 对无关候选更稳健。

## 7. 优点

- **利用应用原生入口**，无需为每个应用另行开发智能体专用 API，同时与通用 GUI 控制互补。
- **把静态发现、真实设备验证、页面描述和执行后校验连成完整流程**，比直接把原始 URI 交给模型更可靠、可解释。
- **显式训练“不调用”和“调用失败后恢复”**，关注了实际部署中链接缺失、检索噪声和运行时失败等问题。
- 除成功率外还考察步骤数、候选目录规模及真实设备表现，使效率主张有多角度证据。

## 8. 不足与局限

- **覆盖受应用开放程度限制**：没有外部可调用入口的页面无法通过此方法直达；当前研究仅针对 Android。
- **Activity 校验较粗**：到达预期 Activity 仍可能填入错误日期或打开错误内容。论文案例中，智能体曾错误创建日历事件，随后才通过 GUI 补建正确事件；轨迹也未展示删除错误事件。这说明落地校验不能替代内容核对和副作用处理。
- **目录可能存在分布偏差与维护成本**：1,251 条链接在应用间分布不均；应用版本、登录状态、地区或动态参数变化可能影响已验证链接的持续有效性。
- **部署问题尚未充分量化**：论文没有完整报告挖掘成本、算力成本及长期维护成本。运行中捕获用户相关参数虽可能提升可用性，也需要进一步明确隐私保护、权限与数据保留策略。
