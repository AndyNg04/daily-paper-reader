1 Introduction 

Consider postponing a project briefing by one day. The calendar entry and the team announcement must change, while a settled flight booking must remain untouched, and a collaborator may request a different date midway through execution. A revised plan does not, by itself, say which updates have already taken effect, which records must stay protected, and which effects can no longer be undone. As Figure 1 illustrates, users ultimately live with changes to the world, not with changes to an agent’s plan. Computer-use agents (CUAs) have made this delegation techni-cally plausible at scale. Modern agents parse complex layouts, syn-thesize input gestures, and execute extended operational sequences across unfamiliar interfaces [11, 13, 24, 46, 50, 55, 75]. Interaction research has responded by opening execution up for oversight: co-planning surfaces let users revise procedural steps, ambient displays communicate agent status, and malleable or generative interfaces re-organize the workspace around the task [8, 10, 17, 31, 33, 35, 64, 72]. These designs make the agent’s procedure the object of interaction: what the user inspects and edits is what the agent will attempt next. Two gaps persist in this procedure-centric stance. First, editing a step changes what the agent will attempt, but it cannot express what the world must keep: boundaries on side effects, records that must remain untouched, and facts that should outlive the current plan have no representation in a list of actions. Second, completion and recovery rest on the agent’s own account. When the execu-tor’s report is the only evidence, users cannot verify what actually changed, and undo is offered without a model of which effects can be restored, inviting the over-reliance that supervisory control re-search has long documented [3, 42, 51, 52]. Both gaps follow from one representational choice: the task is modeled as a sequence of actions, so the obligations attached to its outcome have nowhere to live. Our stance extends a lineage of work that treats the object, not the procedure, as the unit of interaction. Direct manipulation es-tablished that users reason about visible objects of interest [32, 59]; undo research made recovery a first-class design concern [1, 49]; and accountability research argued that systems should expose what they did so that people can judge it [5, 60]. We extend this lineage from artifacts the user operates to agents that operate on the user’s behalf. We call the resulting stance task-state governance: a task is represented as an editable contract among three state com-ponents, not as a procedure alone. The desired state holds the target values the user authorizes the agent to establish. The preser-vation scope pins application facts that must remain undisturbed. The observed state captures what running applications currently display. When the three are represented together, an edit becomes a checkable commitment: the system knows what it must establish, what it must not disturb, and what evidence will count as done. The plan remains useful, but as one revisable realization of the contract rather than as the task itself. We call the runtime that maintains this contract a Task Virtual Machine , and the name is deliberate about scope. It is not an operating-system virtual machine: it owns neither the full state of third-party applications nor the power to roll them back atomically. What it owns is the task’s obligation state and an honest account of evidence. Four commitments make the abstraction tangible. Editing a desired value does not assert that the world changed; desired and observed values sit side by side until fresh observation closes the gap. Marking a record as preserved lifts that constraint out of the agent’s plan and into independent verification. An executor’s completion report does not close a task; a separate verifier checks fresh screen evidence first. And a checkpoint is not time travel; recovery is expressed as the operations the environment actually supports. We realize this stance in TaskVM , a prototype that places the observed state of live applications beside editable task controls. The runtime compiles user edits into genuine interface gestures, so authority flows through the same rendered interface a human would use. An independent visual verifier , architecturally sep-arated from the executor, checks fresh observations against the contract, and the interface distinguishes reversible, compensatable, and irreversible actions so that recovery is described as supported operations rather than a blanket promise. As the Java Virtual Ma-chine (JVM) exposes one bytecode interface across operating sys-tems, the task virtual machine exposes one obligation model across software stacks; substrate independence is the extent of the analogy we intend. We evaluate the paradigm through three complementary lenses, asking three research questions (RQ): 

• RQ1: Does representing tasks as state contracts improve machine-level satisfaction of governance obligations com-pared with procedural agent baselines, and at what execu-tion cost? 

• RQ2: When execution outcomes are held constant, does governing state change how well users understand, control, and trust the agent? 

• RQ3: Does the paradigm remain usable and welcome when a live model executes tasks that participants author them-selves? An automated benchmark over 36 task instances drawn from a suite of productivity, social, and content applications measured contract satisfaction and its costs. A controlled within-subject study with 37 participants compared TaskVM against a conversational Task-State Governance: A Virtual Machine for Verifiable and Recoverable GUI Agent Execution 

agent interface under replayed execution, isolating perception from execution variance. An exploratory follow-up with 14 returning participants observed live-model use on self-authored tasks. Across these lenses, TaskVM improved contract compliance at higher ma-chine cost, significantly increased perceived recovery control and trust while execution outcomes were held constant, and remained usable in open-ended use, where participants exercised recovery operations and asked for more. In summary, this paper contributes: 

• Task-state governance , an interaction model that repre-sents a task as an editable contract over desired outcomes, preservation constraints, and observed state, together with an explicit taxonomy of recovery. 

• TaskVM , a prototype that instantiates the model through live state projection, GUI-grounded bidirectional execution, independent verification, and honestly bounded recovery, running across web, mobile, and desktop substrates. 

• A multi-tier evaluation combining an automated contract benchmark, a controlled user study, and an open live-model exploration, together with design implications for agent interfaces that users can govern rather than merely watch. 

2 Related Work 

Our research intersects four traditions: autonomous graphical user interface agents, interfaces that project agent execution, bidirec-tional and malleable data abstractions, and human-agent gover-nance and awareness. Appendix Table 7 maps this landscape along the object each interface asks the user to govern, tracing what an edit commits each system to, what counts as completion, and what recovery can mean. 

2.1 GUI Agents: From Autonomous Execution to Interaction 

Autonomous graphical user interface agents have transitioned from scripted web automation to multimodal models operating across web [13, 37, 76], desktop [30, 70], and mobile operating systems [55, 66, 74]. Modern systems specialize in coordinate-level display grounding [11, 22, 46, 54, 71], supported by structured reasoning loops [24, 73, 75]. However, benchmark success on autonomous execution does not resolve the human interaction problem. Au-tonomous traces remain opaque, self-reported completion often diverges from application reality, and single-pass metrics ignore the interactive cost of correcting intermediate errors. Rather than proposing another grounding model, we investigate how agents operate within an architecture that enforces state transparency, non-interference, and verifiable outcomes. 

2.2 Projecting Agent Execution: Plans, Interfaces, and Malleable Views 

To support human oversight, prior research has explored diverse representations of agent operations. Interactive scaffolding demon-strated the value of structured prompt chains for inspectable sub-steps [68]. Plan-centric systems externalize reasoning into sequen-tial steps, decision forks, and progress indicators [17, 31, 48]. Plover represents the closest point of comparison: it surfaces structured plans that users can locally revise, keeps executed plan steps as immutable history, attaches derived constraints and visual checks to actions, and runs a cross-platform executor across desktop envi-ronments [64]. Beyond a six-person formative study, its evaluation includes an expert benchmark-repair analysis in which the first author intervened on 26 autonomous failures and improved 23, pre-sented by the authors as an upper bound on recoverability rather than typical user performance. Our comparison concerns the object of interaction and the re-sponsibilities attached to an edit. In plan-centric designs, the pro-tected object is the plan’s executed history, whereas the obligations we study protect facts inside external applications. The evidence of completion also differs in scope: plan-centric systems inspect plan state and screens for execution continuity, whereas our ver-ifier certifies explicit contract obligations (target satisfaction and non-interference over protected facts) from fresh, independently ob-tained observations of application state. And the evaluative claims attach to different populations: expert-assisted recoverability in a formative setting, versus unaided use by ordinary participants un-der controlled replay. We read these framings as protecting different assets, and the two objects can compose within one system. Complementary work explores malleable views and genera-tive interfaces. Morae pauses browser workflows to preserve crit-ical user choices [53]. Sidekick visualizes multi-task status [10], while AgentLens adaptively renders mobile interfaces [35]. In web mashups, Orca extracts components with bidirectional DOM syn-chronization [33], and A-mash combines mobile features into task mashups [43]. Generative UI frameworks synthesize on-demand task cards [8, 38, 63, 69, 72]. Systems such as DynaVis, which com-poses widgets on demand [63], and Orca, which organizes web components across pages [33], anchor their evidence loops inside the browser they render; cross-application compensation and fresh-observation checks of protected state lie outside the problems these systems set out to solve. 

2.3 Editable and Bidirectional Interfaces: Lenses, Sagas, and Views 

Decoupling physical storage from logical views originates in rela-tional databases [12] and declarative querying [9]. Translating edits on projected views back into source structures is formalized as the view-update problem, addressed by Foster et al. through bidirec-tional lenses with round-trip fidelity [18]. In distributed computing, managing multi-step mutations led Garcia-Molina and Salem to formulate Saga transactions with compensating steps [20, 23, 26]. In HCI, declarative generation decouples task specifications from widget layouts, as demonstrated by SUPPLE [19]. Recent declarative systems like DMI [65] and VeriSafe [41] compile state targets and safety constraints into accessibility gestures. Generative UI proto-cols such as A2UI [21] and GenUI [44] define standards for stream-ing components, while UICoder [67] and Cells [36] present meth-ods for interactive UI code generation and structured interfaces. TaskVM adapts these principles to computer-use agents, treating heterogeneous interfaces as a distributed database and compiling user edits into verified, compensatable actions across applications. 2.4 Governance, Trust, and Awareness in Human-Agent Collaboration 

Designing effective oversight requires mitigating automation com-placency. Human supervisory performance degrades during passive monitoring [3], fostering automation bias when agents exhibit high but imperfect competence [51, 52]. Mixed-initiative frameworks ad-vocate dynamic responsibility allocation [29, 47]. Human-AI guide-lines emphasize communicating system actions, supporting effi-cient error correction, and conveying operational boundaries [2]. Furthermore, mitigating over-reliance requires cognitive forcing functions that prompt deliberate verification [7, 28, 42]. Human agency is further supported by malleable, reversible in-teraction. HCI inquiries show that users continuously appropriate software to fit evolving practices [14, 15, 61]. Reversibility under-pins direct manipulation through rapid, reversible operations with visible impact [32, 59], formalized in command trees, selective undo, and side views [1, 49, 62]. Across multi-device and task-centric computing, systems maintain continuity across fragmented tools [4, 6, 27, 34, 40, 56, 57]. Finally, collaborative awareness requires visible artifacts that expose system capabilities and boundaries [5, 16, 25, 39, 58, 60]. TaskVM synthesizes these insights by replac-ing passive trajectory tracking with an editable, live projection of verified application state. 

3 A Task-State Governance Interaction Model 

To bridge human intent and autonomous software execution, we formulate a task-state governance model elevating application state into the primary interactive medium: humans govern tasks, while agents operate applications. 

3.1 State Intent versus Plan Intent 

Current interactive agents structure human intervention around plan intent, presenting upcoming procedural steps, tool invocations, or sub-goal trees [17, 64]. When a user intervenes, the operation modifies an upcoming action, such as replacing a query or deleting a click. While offering procedural steerability, this conflates what the agent attempts with what the user requires the world to become: a step can execute without error yet fail to achieve the intended outcome, or inadvertently corrupt adjacent records [2, 3]. In contrast, our interaction model formalizes user intent as state intent, specifying invariant properties that must hold true once execution concludes. Instead of dictating navigation paths, the user specifies what application facts must change and what histor-ical context must remain undisturbed. As defined in our domain schema, an ActionContract encapsulates these state obligations independently of platform execution paths. This distinction decou-ples human governance from low-level software idiosyncrasies: just as programming runtimes allow developers to declare invariants while delegating memory management, our model enables users to express task invariants while delegating mouse coordinates and Document Object Model (DOM) traversals to autonomous execu-tors. As mapped across the top band of Figure 3, a governed round trip traverses eight semantic stages from Observe and Abstract through Reconcile to close a single episode. 

3.2 The Executable View: Bottom-Up Live Projection 

To make state intent manipulable without exposing raw complexity, our model compiles live software state into an executable view, com-pressing distributed fields into a unified, low-cognitive-load surface. Figure 2 shows the governance interface that realizes this view, or-ganized into three zones that mirror the state representations of our model. Zone C (Editable Task State and Live World) presents the de-sired, preserve, and observed fields of each task variable side by side with the live application window. The observed column is a read-only faithful projection of current software reality, grounded in visual evidence parsed directly from rendered screens [60]; the desired column is editable, and the preserve column pins facts that must remain undisturbed. Zone A (Task Intent and Global Governance) hosts the mission contract and lifecycle controls, and Zone B (Execution Progress and Local Governance) exposes exe-cution progress, the live status of each model-invoking role, and the model call chain. Maintaining fidelity between the projection and external soft-ware requires continuous bidirectional synchronization. The pro-jection streams dynamic live deltas through server-sent events, updating the interface as the external world changes. When con-current external modifications occur, such as a colleague editing a shared document, the system triggers reconciliation mechanisms. Rather than silently overwriting external modifications or crashing the pipeline, TaskVM surfaces external changes as explicit conflict markers in Zone C , inviting the user to reconcile divergent values through deliberate interaction [7, 16].

3.4 Verification Semantics: Independent Witnessing and Non-Interference 

A core tenet of our governance model is that execution completion must never be self-certified by the executing agent. Autonomous agents frequently report success prematurely, mistaking the emis-sion of a completion token for actual state alteration [24, 75]. Our model delegates verification to an independent visual verifier eval-uating rendered application screens. The verification engine enforces two complementary properties: target satisfaction and non-interference. To verify target satisfac-tion, the verifier requires visible witness predicates, demanding explicit evidence that an intended modification was actively en-acted to eliminate the no-op loophole where an agent claims success on a pre-existing state. To enforce non-interference, the verifier evaluates negative predicates over specified, observable entities in 

𝑆 preserve , confirming that protected fields display the same values in fresh screenshots. Crucially, the independent verifier operates with strict contextual and architectural isolation from the executing agent, sharing no internal reasoning buffers or prompt scaffold-ing; in the interface it appears as a first-class role awaiting fresh observation (Zone B of Figure 2). Evaluating fresh visual obser-vations against formal predicates provides an objective, falsifiable gate before any task is marked complete in the user interface [5]. 

3.5 Recovery Semantics: Reversible, Compensatable, and Irreversible Actions 

Real-world software interactions require robust mechanisms for error correction, interruption, and recovery. In traditional direct manipulation interfaces, undo operations revert local memory struc-tures [1, 59]. However, in multi-application environments, software changes induce persistent external side effects that cannot be un-done by simple state restoration [20, 23]. Our model establishes a taxonomy of operational reversibility, codified in our implementation as Reversibility :

• Reversible Actions: Operations whose effects can be com-pletely and symmetrically undone through standard graph-ical gestures without residual impact, such as toggling an unsubmitted checkbox or clearing a draft text field. Wenkui Yang, Yiming Hao, Kai Zhou, Chengyu Pu, Yuzhe Zhang, Jie Cao, Jin Huang, Shuai Ma, and Feng Tian 

• Compensatable Actions: Operations that induce persis-tent external effects but can be semantically counterbal-anced through secondary compensation actions, such as sending a cancellation message to follow an erroneous no-tification [20, 26]. 

• Irreversible Actions: Operations that permanently modify external systems or invoke physical effects that cannot be restored, such as deleting account archives or completing financial settlements. When a user initiates a rollback or edits a historical checkpoint, TaskVM derives a compensation plan exclusively from its commit-ted action history (CompensationPatch). Reversible and compensa-table actions execute compensating GUI gestures across affected applications. Conversely, when an action crosses an irreversible boundary, the interaction model prohibits deceptive representations of undo: the global rollback dialog in Zone A (Figure 2) previews which committed steps would be replayed or restored, explicitly marks effects that are not auto-compensable, and locks irreversible entities with transparent status badges, preventing the dangerous il-lusion of complete reversibility and supporting appropriate reliance [7, 42]. 

4 The TaskVM Prototype 

We implement the task-state governance model in TaskVM, an interactive system governing multi-application workflows across web, mobile, and desktop software. This section details the data flow, privacy boundaries, bidirectional bindings, governance primitives, and substrate abstractions that realize our conceptual framework. 

4.1 System Architecture and Separation of Concerns 

As mapped in Figure 3, TaskVM is organized around a hub-and-spoke data flow centered on the Task-state VM (Kernel). The Kernel serves as the sole owner of task state, maintaining TaskState (intent, variables), workflow graphs, append-only event logs, and epoch checkpoints. By enforcing a defensive read path, the system pre-vents low-level drivers or downstream consumers from polluting central task semantics. Rather than relying on a single vision-language model, TaskVM distributes responsibilities across specialized roles that exchange typed objects with the Kernel. The GUI Agent functions as an En-coder, observing live software displays via dedicated observation structures and channeling them into the State Compiler (F2). The Compiler converts visual candidates into standardized task vari-ables (F2, F2’) and forwards them to the Task Architect. A separate generative interface model functions as a Decoder (F3), translat-ing intent into interactive A2UI components projected to the user interface (F3’). These roles execute through independent model invocations marked by amber indicators, preventing their conversa-tional histories from being shared directly. All experiments reported in this paper instantiate every model-invoking role with the same production model, OpenAI’s GPT-5.6-sol (per-condition configu-ration in Section 5 and Appendix L). While this separation limits direct context leakage, it does not eliminate extraction errors or correlated failures, so the generated representation is not treated as evidence of its own correctness. 

4.2 GUI-Only Purity and the No-Internal-ID Rule 

A pervasive vulnerability in automated GUI systems is reliance on internal implementation identifiers, such as private DOM IDs, database keys, or synthetic accessibility tags. While internal identi-fiers facilitate automated testing, they break down in open-world environments where dynamic layouts alter internal structures with-out changing visual appearances. Furthermore, relying on internal identifiers creates backdoors that bypass rendered interfaces, giving automated agents privileges unavailable to human operators. To maintain operational integrity, TaskVM enforces the GUI-only purity standard. Every piece of data entering the model pipeline must satisfy the one-question test: could a real human user see this exact string on the rendered screen? If an attribute cannot be visually perceived by a human looking at the monitor, it is strictly prohibited from entering any model prompt. The compi-lation pipeline incorporates an explicit verification module that intercepts candidate records and strips internal database keys, ac-cessibility labels, operator jargon, and deep-link URLs via dedicated hidden-ID scrubbers and architectural no-leak filters. Every task variable in the governance console must link directly to verbatim visual evidence parsed from the display. Moreover, all write op-erations must traverse authentic graphical gestures (GuiAction), including coordinate-targeted mouse clicks, keystrokes, and scroll events. Any state alteration that does not require a rendered display and simulated user input is classified as an unauthorized backdoor and rejected by the runtime kernel. 

4.3 Bidirectional Executable Binding and Multi-App Action Contracts 

TaskVM achieves bidirectional interaction through executable se-mantic bindings that connect high-level virtual machine variables to low-level application gestures. We conceptualize this mechanism as an analog to the Java Virtual Machine. Just as a Java program-mer modifies an abstract object variable and relies on the virtual machine to translate the assignment into platform-specific memory offsets, a TaskVM user edits an abstract task variable in the gov-ernance console and relies on TaskVM to synthesize coordinated writes across heterogeneous software. When a user alters a variable in the governance console, the sys-tem instantiates a semantic ActionContract in our domain schema. The contract specifies what condition must become true in the tar-get application, rather than hardcoding how the application must be navigated. Target entities are identified through robust visual anchors, such as surrounding label text, relative geometric offsets, and icon visual embeddings, rather than brittle pixel coordinates. When a single conceptual edit requires modifications across multi-ple applications, such as synchronizing a deadline across a project management board and a team chat client, the runtime orches-trates a fan-out execution plan. The execution engine sequences operations across application windows, monitors UI transitions, and commits state updates only after verifying structured action outcomes (ActionReceipt). 4.4 Hot Governance: Pausing, Patches, Epochs, and Recovery 

Real-world human governance requires the ability to intervene while execution is actively underway. TaskVM provides four foun-dational hot governance primitives: pause, local patch, goal patch, and rollback. At any point during autonomous execution, the user can trigger a pause control in the governance console. The Gover-nance Service immediately issues a halt signal to the active runtime, freezing the execution harness at the current step boundary. To manage race conditions during mid-execution interventions, TaskVM introduces epoch-based governance gating in the kernel. Every task execution belongs to a monotonically increasing integer epoch. When a user pauses the system and applies a local patch or revises the overarching goal, the governance engine increments the epoch counter. If the autonomous agent was in the process of generating an action from the preceding epoch, the kernel gate intercepts the returning proposal and discards it before dispatch. This prevents stale proposals from being newly dispatched after a revision, without claiming to reverse effects of actions already dispatched. When a user modifies a goal, the system retains valid, commit-ted action history and recomposes only the affected future trajec-tory, avoiding redundant re-execution of unaffected milestones. When a rollback is requested, the compensation engine analyzes the committed action registry. For reversible operations, the run-time synthesizes inverse graphical gestures, such as untoggling checkboxes or clearing input forms. For compensatable operations, the runtime executes compensating GUI actions, such as dispatch-ing cancellation notes; these counteract the intended effect but do not assure atomic rollback [20]. Finally, when an operation crosses an irreversible threshold, such as a finalized monetary payment, the system prevents misleading undo representations by raising an explicit irreversible signal. Irreversible entities are locked in the interface with transparent explanatory badges, clarifying the limits of automated recovery.

Table 1 reports the primary comparison across the 36 task instances, visualized in Figure 4. On the skills-OFF main comparison, TaskVM obtained 21/36 strict passes (rate: 0.583) and an atomic predicate mean of 0.870, compared with 18/36 (0.500) and 0.761 for Direct-CUA, and 17/36 (0.472) and 0.737 for Planner-CUA. 5.5 Skills Injection and Non-Inferiority Analysis 

We examine whether procedural skills injection harms TaskVM’s contract faithfulness and whether TaskVM remains non-inferior to its strongest baseline once skills are enabled (Table 3). Paired across 21 instances between the two waves, skills injection flipped four instances in TaskVM’s favor and three against it, a modest net gain of +1; neither CUA baseline showed any net change. Because the skills-OFF and skills-ON waves differ in coverage, we addi-tionally evaluate non-inferiority within the same skills-ON wave on contract-faithful execution (CFE), a per-instance correctness measure derived from the task boundary semantics of each family. The two analysis collections are explicitly distinct: the strict-COV index retains only fully measured cells (23 of 36 for TaskVM un-der skills-ON), whereas the CFE comparison additionally admits the protocol’s per-family fallback judgments (e.g., boundary arcs judged from pre-boundary oracle segments), yielding 35 compa-rable instance clusters paired between TaskVM and Direct-CUA; the 35 are instance-level clusters, not a third task set. A cluster bootstrap over these 35 paired clusters (10,000 resamples, fixed seed) yields a point estimate of the TaskVM minus Direct-CUA difference of +0.0571, with a one-sided 95% lower bound of −0.0857. This lower bound clears the margin of 10 percentage points speci-fied in our evaluation protocol, establishing non-inferiority at that margin; sensitivity analyses at 5 and 7.5 points remain inconclusive, and the verdict also holds at 15 points. Among the eight discor-dant clusters, TaskVM alone succeeded on five instances concen-trated in drift-robust rescheduling and sequential contract chains (drv-01 , drv-03 , sqv-01 through sqv-03 ), while Direct-CUA alone succeeded on three instances involving confusable references and retargeting ( gpv-03 , lpv-03 , pfv-03 ). Skills injection therefore does not degrade TaskVM below its strongest baseline on contract-faithful execution, though the inconclusive stricter margins call for larger paired samples. This result supersedes an earlier cross-wave draft analysis that was inconclusive; the final protocol and its sensitivity margins are documented in Appendix B. 

5.6 Stress-Tier Robustness 

Beyond the frozen benchmark waves, a development-era stress tier probed governance durability under adversarial goal mutations with skills enabled throughout. The tier comprises 18 variants at dif-ficulty levels L3 and L4, covering conflict injection, goal repair, and cross-session intervention, adjudicated under a majority criterion in which a frozen pass verdict is never reversed. Eleven of 12 L3 variants and all 6 L4 variants passed. The single L3 failure is rbvl3 ,a rollback-compensation family blocked by a signing-window race condition that remains an open, documented defect. The placement of the sole failure is nonetheless informative: rollback is simultaneously the hardest capability to make reliable and, as the next two sections show, the capability human participants used and requested the most (Sections 6 and 7); we return to this tension in the Discussion.

6.2 Participants and Ethics 

We recruited 37 participants through a public research-volunteer group maintained by our laboratory; membership in the group is open to anyone, although in practice it skews toward university students and researchers (Appendix M). 19 participants were as-signed to the TaskVM-first order and 18 to the Conversational-first order. All participants completed both conditions and enter the analysis as a within-subject sample. Self-reported demographics and agent-related background, collected post-study through volun-tary channels, are detailed in Appendix M. Of the 37 completers, 36 disclosed gender, age, and affiliation (15 female, 21 male; ages 18–42, 𝑀 =24 .7) and 35 completed the background questionnaire. The sample was technically literate but predominantly novice with respect to GUI agents: only 2/35 reported direct computer-use/GUI-agent professional background, and 14/35 had never used a GUI agent or had tried one only once or twice. This study was conducted in accordance with the ethical guide-lines of the local ethics committee. Prior to participation, all subjects provided informed consent, and their confidentiality and anonymity were strictly maintained throughout the study. The study employed a counterbalanced within-subject design. Each participant completed multi-application workflows under two con-ditions, illustrated in Appendix Figures 6 and 7: 

• Conversational CUA (Baseline): Participants supervise an agent through an application screencast accompanied by an interactive chat drawer, receiving conversational progress updates and issuing natural language steering directives. 

• TaskVM (Ours): Participants govern execution through the governance cockpit (Figure 2): the editable task-state zone displays desired, preserve, and observed fields beside Wenkui Yang, Yiming Hao, Kai Zhou, Chengyu Pu, Yuzhe Zhang, Jie Cao, Jin Huang, Shuai Ma, and Feng Tian 

the live application, the progress zone exposes role status and verification reports, and the global governance zone provides lifecycle controls, checkpoints, and rollback. Participants performed eight representative task scenarios span-ning collaborative office productivity, event scheduling, customer support record updates, and social communication. Each scenario encompassed three distinct phases: an initial autonomous execu-tion phase across multiple applications, an injected environmental perturbation such as dynamic UI drift or an unexpected record conflict introduced by a simulated collaborator, and a required user intervention prompting selective modification of target fields while preserving existing records. 6.4 Procedure 

Each condition began with its own onboarding sequence containing an unscored training task ( r8-train ) so that participants practiced both interfaces to the same degree, followed by a six-minute think-aloud free-exploration period. In the formal battery each participant completed three of the eight tasks per condition (Table 9); task– condition–order assignments followed the Latin-square schedule, and read/write probe slots were allocated deterministically per task slot in a balanced rotation, so probe exposure was independent of performance. The condition-end questionnaire (all subjective scales described below) was administered once at the end of each condition; there were no per-task questionnaires. The experimenter intervened only at scripted perturbation points and through a fall-back prompt (e.g., asking the participant to verify the selected item when the scripted model error did not occur), applied identically in both conditions; a logged help channel gave direct guidance on request, and such help was recorded as help usage. Participant inputs that did not match a scripted replay branch were steered back onto the canonical path by the operator, and these mismatch and resume events are annotated in the session records. Sessions were run individually. To isolate the effect of interaction representations on human perception and behavior, the study executed on a high-fidelity Wizard-of-Oz replay rig. Underlying application screens and event streams were pre-recorded from authentic runs on a simulated application suite, with every frame undergoing automated semantic verification to ensure visible text, status bar timestamps, and pixel evidence aligned with the experimental script. When participants intervened, the platform matched the input against a canonical script of branching paths, substituting the runtime engine without altering the study runner ( ConditionRuntime , StudyRunner ). The replay protocol fixes three things identically across arms: the environment’s event sequence, the agent’s recorded steps, and the timing and manifestation of errors. It deliberately fixes nothing about the participant’s own intervention: the write-probe score evaluates what the participant did at the intervention point, so paired outcomes legitimately diverge across conditions. Consistent with this design, marginal pass rates are identical (34.3%, 12 of 35 scored probes per arm at the boundary; 51.4%, 18 of 35 at trial end) while the paired record is fully discordant (Section 6.6): every pass was earned by different participants in the two arms. We therefore read the identical margins strictly as evidence that neither arm offered systematically easier intervention opportunities, not as evidence that participants experienced identical outcomes, and not as evidence that the two interfaces would execute with equivalent competence outside the rig. 

6.5 Measures and Analysis 

Subjective scales were collected once per condition through the condition-end instrument (verbatim item texts, sources, and com-posite rules in Table 12). The NASA Task Load Index (NASA-TLX) was administered as six 0–100 sliders and scored as the unweighted mean (RTLX); the performance slider runs from Perfect (0) to Fail-ure (100), so all six dimensions share the same demand direction with no post-hoc inversion. UMUX-Lite, the two-item short form of the Usability Metric for User Experience, is rescaled to 0–100 by mean (items − 1)/ 6 × 100. Recovery control is a study-specific composite of four items (influence, stop/redirect, correct, overall). Trust is a two-item composite (trust, rely) adapted from the Trust in Automation instrument; perceived transparency is a three-item pre-dictability subset of the same instrument with one reverse-scored item. Support satisfaction adapts the three After-Scenario Ques-tionnaire items to the condition block. Read probes (three questions each on committed effects, effective goals, and governance facts) were embedded in drift-triggered trials and preceded by a single confidence rating (0–100) for the whole probe; write probes score the participant’s own intervention at the scripting boundary and at trial end against the frozen expectation. All inferential analyses use the participant as the unit: two-sided paired Wilcoxon signed-rank tests for scalar measures and exact McNemar tests for paired binary outcomes (scipy, version pinned in the analysis environment). Paired differences are summarized by 𝑑 𝑧 = mean (𝑑 𝑖 )/ sd (𝑑 𝑖 ); reported confidence intervals are 𝑡 -based intervals of the mean paired difference. Missing responses per mea-sure are reported in the table (valid pairs range from 34 to 37 for write probes and 8 for read-probe pairing); zero differences are handled by the implementation’s defaults. We report the complete set of planned comparisons without selective omission, with un-adjusted 𝑝 -values interpreted alongside effect sizes, and we do not retroactively designate a subset as the sole primary endpoints. All numbers are reproducible from the consolidated archive’s analysis scripts.

Two properties of the study environment shaped what partic-ipants could attempt, and we disclose both because they delimit the generality of the Stage 3 material. First, the substrate is a static, offline world: every searchable object exists only because it was injected during setup, so open-ended search tasks could hit cover-age gaps. The qualitative material consists of responses to two open-ended questions, not interviews. We grouped responses into themes, with the individual response as the coding unit; a single participant could contribute to more than one theme, and theme counts below refer to distinct participants. On the supportive side, four participants (P21, P37, P27, P25) described faithful execution and precise intent recognition under open-ended tasks. P27 wrote that the system recognized the in-tended edit and completed the keyword changes without over-guessing what they wanted to do [translated], and P21 described watching the planned decomposition land step by step as reas-suring [translated]. One participant’s account constitutes logged governance use: P30 inserted a new instruction midway through execution, asking the agent to additionally ask a specific colleague about overtime availability, and reported that the agent completed the original task and then correctly located the colleague and de-livered the inquiry, describing the outcome as deeply satisfying [translated]; this insertion also appears in the session record, so it reflects logged use rather than praise alone. Separately, P35 praised the topology view of task structure as something they really liked [translated]; we count this as appreciation of the interface, not as use of a governance operation. Two participants (P30, P27) indepen-dently requested stronger governance automation, asking that the system place checkpoints automatically at nodes where failures are likely [translated]. We read these requests as demand-side evidence that the checkpoint concept had been absorbed and extended by users, not as reports of a system defect. On the critical side, three themes emerged, ordered by severity. First, three participants (P35, P06, P13) were frustrated when open-ended search queries missed the simulated platform’s injected data. One searched for several popular videos and found none of them [translated]; another searched for their own uploaded videos and felt discouraged when nothing came back [translated]. Second, four participants (P10, P20, P13, P22) traced failures to live-model ex-ecution problems such as retry loops, repeated actions, and lost task continuation. These failures originate in the executor (model) layer and would be inherited by any interface paradigm; what differs across interfaces is how such failures are surfaced, contained, and recovered from, which is precisely where the governance features are exercised. 7.4 Cross-Substrate Capability and Boundaries 

A central objective of TaskVM is substrate independence: ensuring that task-state governance operates across diverse software stacks without requiring application-specific programming interfaces. As mapped in the substrate port of Figure 3, TaskVM abstracts external software through a unified port interface that renders pixels into observations and dispatches standard hardware inputs, and we maintain adapters for modern single-page web applications, mobile environments hosted through MobileGym [66], and Linux desktop applications within OSWorld [70]. Across these environments, the runtime compiles the same state-level intents into substrate-specific gestures, and the independent visual verifier confirms terminal states from raw screen pixels, so a unified task contract survives platform changes. Our cross-substrate investigations also expose clear operational boundaries where the abstraction encounters friction: 

• Canvas-Rendered Interfaces: Applications rendered en-tirely through low-level graphical canvases lack discrete visual text and standard widget affordances, challenging the visual entity extraction pipeline. 

• Transient Dynamic Popups: Short-lived visual notifica-tions that appear and fade within sub-second intervals can elude periodic screenshot polling, occasionally delaying conflict detection. 

• Defensive Anti-Automation Gates: Web platforms de-ploying CAPTCHA challenges, biometric verification, or aggressive bot-detection scripts intentionally resist auto-mated inputs, representing an absolute boundary requiring direct human handoff. 

• Desktop Window Occlusion: Overlapping application windows on multi-tasking desktops can temporarily ob-scure visual evidence, requiring the runtime to synthesize window-focus management gestures before polling visual artifacts. Documenting these boundaries clarifies that task-state governance is designed for structured productivity workflows, establishing transparent expectations for open-world deployment. 

8 Discussion 

The core question raised by TaskVM is not merely how agents execute software, but how users interact with, verify, and recover from software state changes with bounded cognitive effort. Here we discuss four critical interaction design choices emerging from the TaskVM paradigm, its technical evaluations, and its associated operational costs. 

8.1 Defining Preservation Constraints versus Monitoring Actions 

In traditional conversational agents, users are placed in an unnatu-ral supervisory role: watching an automated cursor move across windows and reading lengthy logs to verify execution. This intro-duces passive monitoring costs and opportunities for automation bias [3, 51]. TaskVM replaces this monitoring with explicit contract defini-tion. The user specifies both a desired state and a preservation scope, effectively transferring the effort from watching cursor clicks to writing state constraints. While this shifts human attention from procedural navigation to declarative intent, it does not entirely remove cognitive effort. Determining which fields may change and which must remain protected is its own conceptual workload. We argue that when dealing with multi-application environments, defining bounded state invariants is more tractable than mentally synthesizing low-level execution traces across isolated application silos. 

8.2 The Latency and Cost of Verification 

The properties provided by TaskVM do not come without overhead. In conventional computer-use agents, execution progresses through an unconstrained forward loop, generating actions until the model emits a stop token. TaskVM, by contrast, introduces structured overhead at multiple stages: compiling initial state, projecting the interface through a secondary model, filtering internal identifiers, and polling rendered screens. Our automated benchmarks highlight this trade-off. TaskVM con-sumed 19,960 seconds of total wall time and 1,126 model calls across 36 task trials, compared to 9,010 seconds / 1,361 calls for Direct-CUA, and 6,695 seconds / 1,031 calls for Planner-CUA (Table 1). This cost distribution cannot be attributed solely to verification: state compilation, dynamic re-projection, and structured execution boundaries all contribute to the measured wall-time gap. However, if an interface treats an external task merely as an asynchronous background job, the cost of an unverified error in high-stakes en-terprise software vastly outweighs the latency of checking. An observed trade-off also emerged in our user study: participants exhibited a median intervention latency 19.6 seconds higher under TaskVM (Table 4), a pattern characterized by substantial variance across users without a statistically reliable condition effect. Neither of our human studies decomposes this runtime overhead into ma-chine and human shares. The replay study estimates interaction latency in a controlled setting and cannot establish whether verifi-cation delays surface for users under live execution; the exploratory follow-up offers workload descriptions rather than a controlled cost comparison. A design implication is therefore to make verification effort and its products visible at the points where users must judge or intervene, while explicitly evaluating how evidence presentation, waiting time, and recovery demands interact under live execution. 

8.3 What Can Visible Observations Certify? 

A recurring theme in TaskVM is that interfaces cannot simply trust self-reported execution successes. We rely on independent visual verification against observable fields to certify task state. However, this relies on an important boundary: visible observations can prove Task-State Governance: A Virtual Machine for Verifiable and Recoverable GUI Agent Execution 

what is rendered on the display, but they cannot strictly prove hidden backend states or atomic transactional assurances across third-party platforms. For example, a verified booking screen shows that the UI reflects a date change, but does not inherently prove that airline system databases successfully processed a refund or cancellation ticket. TaskVM’s live state projection surfaces exactly what the system can observe, flagging when visual evidence is insufficient rather than silently assuming consistency. This transparency highlights that interface trust should be grounded in explicit model boundaries, not in exaggerated claims of system-wide correctness. 

8.4 Designing for Bounded Recovery and Irreversibility 

A prevalent tendency in automated agent design is the masking of failures through optimistic self-reporting. When an agent makes an irreversible error, such as deleting a contact record, conversa-tional interfaces often provide vague reassurances, misleading users into believing the action can be undone. TaskVM implements a tri-partite taxonomy of reversibility. Reversible and compensatable actions are tracked and counteracted through inverse GUI gestures, while irreversible operations are explicitly locked to prevent de-ceptive undo representations. Empirically, participants exercised goal interventions in every task by design, and 11 of 37 additionally invoked rollback a total of 17 times under TaskVM (baseline: 2 participants, 4 times), with 13 of those 17 events occurring outside the two tasks that scripted an undo request, demonstrating that participants reached for the exposed recovery control even when not asked to. We note that compensating actions, such as sending a cancella-tion message, do not equate to true atomic rollbacks. They introduce secondary effects and may leave behind specific audit trails in third-party systems. By forcing the interface to distinguish between these recovery modes, TaskVM shifts user trust away from fictional com-prehensive undo capabilities toward calibrated expectations about what can, and cannot, be reversed. Our evidence also reveals a productive tension: rollback is si-multaneously the most demanded governance capability and the hardest to make reliable. Rollback was the operation our baselines lacked entirely, the function 11 of 37 study participants invoked (17 events) beyond scripted requests, and the automation Stage 3 participants requested in stronger form, asking for checkpoints placed automatically at failure-prone nodes. Yet the one unresolved failure in our stress tier is precisely a rollback-compensation family, blocked by a race between a signing window and the confirmation gesture. We read this convergence not as a defect to be excused but as the clearest roadmap the paradigm offers: honest vocabu-lary about recovery creates demand for reliable recovery, and the engineering agenda should follow the demand. 

9 Limitations and Future Work 

Our results are bounded in several ways. Stage 2 holds the envi-ronment and the replayed agent trajectory constant, which isolates perception but cannot evidence live-model execution success or real recovery capability; its read probes reached only a subset of trials (𝑛 = 8 matched pairs), so probe accuracy is directional evidence rather than an established gain in understanding. Stage 3 restores a live model and participant-authored tasks but removes the control arm, so its lower workload is descriptive and confounded with task freedom and practice, and its sample is self-selected: the 14 return-ing participants had shown a substantially larger Stage 2 workload advantage than the 23 who did not return ( −24 .70 versus +0.14 NASA-TLX points). Participants were recruited from a single labo-ratory research-volunteer pool skewing toward university students and researchers. All stages ran on an offline simulated application suite with finite injected data, so open-ended search occasionally missed the corpus, adding noise without affecting the governance mechanism; cross-platform deployment is engineering-supported through our substrate adapters but not empirically demonstrated here; live-model execution failures such as retry loops originate in the executor layer, yet their consequences still require an interface that can surface and govern them. On the system side, our com-piled schemas express structured productivity workflows whose state maps to discrete variables and invariant predicates; contin-uous creative workflows (video editing, 3D modeling, freehand illustration) resist this decomposition, and our purely visual polling can miss sub-second transient UI states, complicating fine-grained causal diagnosis. Finally, TaskVM deliberately does not circumvent defensive gates such as CAPTCHAs; graceful human handoff at such boundaries, broader and more diverse samples, production substrates, and equivalence-controlled live-model comparisons are the natural next steps. 

10 Conclusion 

As autonomous agents gain the ability to execute complex work-flows, the object users must govern is not the agent’s procedure but the state of the world the agent touches. We present task-state gov-ernance, an interaction model that frames a cross-application task as an editable relationship among desired outcomes, protected facts, and observed application state. TaskVM instantiates this relation-ship through task-level controls, separately checked observations, and explicitly bounded recovery. Our evaluation characterizes three distinct questions with three distinct designs: technical capability and cost on a fixed bench-mark suite, subjective experience under controlled replay, and exploratory use by returning participants on self-authored tasks. These are complementary forms of evidence rather than three con-firmations of one mechanism, and each carries the boundaries reg-istered in the preceding section. Together they show that the obli-gations and limits of agent-mediated change can be made explicit objects of interaction, verifiable in principle and inspectable in use, while live-execution effectiveness and broader generalization re-main open to further study. By shifting the unit of interaction from procedural plans to verifiable state contracts, TaskVM suggests how users can govern autonomous agents with clarity and calibrated trust: humans govern tasks, while agents operate applications.

This appendix defines the ten Contract-Outcome Verification (COV) predicates used to adjudicate every Stage 1 trial. Each trial is scored on every applicable predicate; a strict pass requires all applicable predicates to pass.

> The target fields specified by the task end in the desired state.

B Stage 1 Data Quality Notes 

We document the exclusion and correction decisions behind the Stage 1 numbers so the reported tables can be audited cell by cell. Five trials in the first wave failed at the infrastructure level rather than at task execution (two vendor server errors and three setup timeouts); these were re-run cleanly, and their invalidated records were removed from all denominators. Two further trials misclassified by the fail-loud grading gate (one true pass and one valid failure) were vindicated in a subsequent envelope audit and counted correctly. Frozen pass verdicts are regression-locked and can never be reversed by later waves. In the skills-ON wave, TaskVM has valid cells for 23 of 36 instances; the remaining cells are recorded as missing rather than scored as failures, and a cell-level index cross-validation across all 108 cells reported zero mismatches. The skills-ON wave initially produced a misleading side artifact: a cell-level index in which all baseline cells were marked as failures due to a residual obsolete progress gate. The authoritative rollup supersedes that index (Direct-CUA 19/36, Planner-CUA 18/36); any aggregation from the raw cells would reproduce the obsolete gate and is excluded by an on-record erratum. Finally, the non-inferiority analysis reported in Table 3 is the cor-rected protocol version computed after adjudication of the frozen waves. An earlier draft compared the skills-ON and skills-OFF waves against each other and was inconclusive; the corrected anal-ysis follows the evaluation protocol in comparing TaskVM against its strongest baseline within a single wave on contract-faithful exe-cution, pairing 35 task clusters and resampling 10,000 times with a fixed seed. At the 10 percentage-point margin specified in our evaluation protocol the one-sided 95 percent lower bound ( −0.0857) clears the margin, establishing non-inferiority; sensitivity analyses at 5 and 7.5 points remain inconclusive, and the verdict also holds at 15 points. The 23-of-36 valid strict-COV cells and the 35 CFE clus-ters are explicitly different analysis collections: the former retains only fully measured cells, whereas the latter additionally admits the protocol’s per-family fallback judgments, so the larger CFE count does not contradict the smaller COV count, and the 35 clusters are instance-level pairings between TaskVM and Direct-CUA, not a separate task set.

H Stage 3 Usage in Aggregate 

To protect participant privacy, the anonymized archive retains per-episode runtime counters (goal formulation, status, model-call count) rather than complete GUI interaction traces, and some open-ended search terms typed by participants are withheld entirely. We therefore report Stage 3 usage in aggregate (Table 10) instead of as per-task transcripts, and point readers to the open-ended responses (Table 11) for what participants themselves chose to disclose about their tasks. Per-episode success is not adjudicated (Stage 3 embed-ded no probes and no per-task ground truth). Model calls are the LLM invocations attributed to an episode by the runtime ledger; application and contact names appearing anywhere in the study are fictional entities of the offline simulator. Diversity is visible at the aggregate level. The fourteen partic-ipants differ markedly in how they used the open session: total model calls span 3 to 149 per participant (median 52.5), episodes span 1 to 4 (median 3), and tasks touched five distinct application surfaces across the cohort (messaging: 11 participants; social feed: 7; video platform: 4; music: 3; content community: 2). An inde-pendence audit confirmed that no two participants produced an identical episode sequence: even where two participants issued a textually identical goal, the runs differ in status, timing, and model-call counts (e.g., 3, 41, 46, 50, 63, and 73 calls on six runs of one shared formulation).

L Evaluation Configuration 

In all stages the user-facing runtime observes only rendered pixels and emits standard GUI gestures; oracle-only capabilities (state resets, internal-state reads, deterministic event injection) are con-fined to an isolated evaluation harness and are never exposed to the interactive session, as detailed in the prototype section. Per-trial manifests record model identity, per-role call counts, and wall time; frozen artifacts per instance are retained in the consolidated archive cited in Section 5.
