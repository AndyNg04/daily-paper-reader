## ABSTRACT 

The safety of LLM-based agents currently rests on alignment training and safety classifiers, neither of which can rule out that a sophisticated indirect prompt injec-tion (IPI) goes through and causes significant harm. Recent work therefore builds agents with information-flow guarantees that rely on structured tool interfaces to interact with the environment. Computer Use Agents (CUAs) act visually on the computer screen, which does not provide a boundary between trusted first-party interfaces and untrusted, potentially attacker-authored content. Actions are equally ambiguous: a click may land on an application toolbar or a button controlled by an attacker. Treating the user as the source of trust and confirming each sensitive deci-sion produces confirmation fatigue, with the risk of missing harmful actions. We introduce SA-CUA, a dual-LLM framework that generates a reliable trust boundary for CUAs by deriving conservative deterministic rules from the accessibility tree for unmasking trusted regions from the privileged LLM’s screenshot, keeping trusted and untrusted content separated. Human interaction is only required for proper task specification in the beginning. During the task a robust endorsement channel allows values to pass from the untrusted to the trusted domain by verifying information via trusted channels. This allows the agent to autonomously handle tasks involving untrusted information. SA-CUA maintains much higher utility than CaMeL-CUA while keeping the attack success rate at zero. 

## 1 INTRODUCTION 

LLM-based agents have moved from demonstrations into deployments with real-world consequences. Most deployed systems are tool-use agents that act through structured tools with the environment, but there is growing interest in computer use agents (CUAs), which perceive a GUI environment and act on it via mouse and keyboard. CUAs provide the possibility to interact with every application a human can operate without requiring special integration (Xie et al., 2024) and are offered by many frontier labs such as Anthropic (Anthropic, 2026). For the agent to complete a task it has to potentially interact with environments that third parties can write to, and an adversary who anticipates this can leave malicious instructions behind for the agent to act on. Such indirect prompt injections (IPIs) (Greshake et al., 2023) attempt to hijack the agent’s trajectory, manipulating the user task toward an attacker-chosen malicious goal such as exfiltrating credentials or private files, sending messages, authorizing payments, or removing data. Khodayari et al. (2026) show the realism of this threat by crawling 1.2B URLs and finding 15.3K injections. IPIs can be mitigated by making the model itself more resistant through alignment training (Bai et al., 2022; Guan et al., 2024) and/or filtering inputs and outputs with additional safety classifiers (Sharma et al., 2025; Inan et al., 2023). Instead we focus on enforcing security by the system architecture. CaMeL (Debenedetti et al., 2026) and FIDES (Costa et al., 2025) establish frameworks for tool-use agents that secure control- and data-flow by ensuring integrity and confidentiality. Both build on a dual-LLM approach (Willison, 2023), where a privileged model plans and operates tools interacting only with trusted content. Untrusted content is handled by a quarantined model, which can be queried by the privileged model in a structured fashion. Recently, CaMeL-CUA (Foerster et al., 2026) and untrusted content masking (UCM; (Nikoli´ c et al., 2026) extend this to computer use. CaMeL-CUA keeps the privileged model blind to the environment restricting utility, whereas UCM relies on active page owners to mark untrusted regions in the Document Object Model (DOM). Their experiments show that labeling untrusted content by LLMs is not reliable. To achieve data-flow control, both systems bound the type the quarantined model can return to limit the channel capacity. However, we argue that already a single bit can be sufficient to steer the privileged model into an adversarial branch. For data-dependent tasks that require higher-capacity return values, CaMeL-CUA and UCM fall back to asking the user to confirm. However, repeated security prompts can drive the user into confirmation fatigue, auto-approving requests without checking them, a well-known problem in security (Furnell & Thomson, 2009). Our framework SA-CUA builds on the dual-LLM approach (Willison, 2023). By default the full screen is masked in SA-CUA and we derive deterministic rules based on the accessibility tree to 

unmask trusted content before it reaches the privileged model, instead of masking untrusted content 

in the DOM as in UCM. Therefore, the privileged LLM only gets a screenshot where every untrusted element is masked, so its context remains trusted and its integrity to issue actions is preserved in the sense of Biba (1977). For data-dependent tasks we introduce an endorsement channel, which overcomes the data-flow problem of prior work without compromising the agent’s autonomy by repeated confirmation requests. We endorse by verifying each value that traverses the trust boundary with the help of independent trusted sources, e.g. the parametric knowledge of the privileged LLM, trusted domains/contacts etc. This follows the principle of robust endorsement (Zdancewic & Myers, 2001; Myers et al., 2006), under which the value being endorsed cannot influence the endorsement check. Our contributions are: • SA-CUA performs trust labeling using AT-SPI accessibility trees for hybrid web–OS environments and thus can handle general CUA tasks, while UCM is restricted to the browser as it uses the DOM. 2Preprint. Our automatic labeling is reliable and has zero leakage of untrusted free text ( FNR free ) in contrast to UCM, e.g. 0% for SA-CUA vs 44.1% for UCM for Qwen3.8-27B. • SA-CUA introduces an endorsement channel for untrusted content where values are verified using independent sources. In this way we preserve agent autonomy and are able to counter value substitution attacks which are not prevented by low-capacity channels. • In our novel RTC-value examples, we introduce IPIs where the injected value is indistinguishable from the expected benign value at the type level, so constraining the output type of queries does not stop the injection. ## 2 RELATED WORK 

Prompt injections and CUAs. WASP (Evtimov et al., 2025) places injections in live We-bArena (Zhou et al., 2024) sites with attacks that exploit both the visual and DOM channel. EIA (Liao et al., 2025) adds deceptive form elements to the DOM that are visually invisible, Johnson et al. (2025) place adversarial triggers in aria-labels in the HTML code that are read out into the accessibility tree, Zhang et al. (2025) carry IPIs via pop-ups, and adversarial perturbations of screenshots (Seip & Hein, 2026; Wu et al., 2025) attack the perception of the agent directly. Utility of CUAs is measured on OSWorld (Xie et al., 2024) and WindowsAgentArena (Bonatti et al., 2024). Security evaluations are performed by OS-Harm (Kuntz et al., 2025), which extends OSWorld with misuse, injection and misbehavior tasks, and RedTeamCUA (Liao et al., 2026), which places adversarial content in hybrid web–OS environments. 

Alignment training and safety classifiers. Model-level defenses try to align the model to resist both direct and indirect prompt injections: Constitutional AI trains the model to follow a constitution of human-written rules (Bai et al., 2022), deliberative alignment teaches the model safety policies and to reason over them at inference time (Guan et al., 2024), and SecAlign trains with DPO (Rafailov et al., 2023) over paired secure/insecure completions (Chen et al., 2025b). Other approaches force agents to follow only special prompts (Chen et al., 2025a) or instruct models to prioritize privileged instructions over third-party content (Wallace et al., 2024). A second family is safety classifiers which filter inputs and outputs (Inan et al., 2023; Chennabasappa et al., 2025; Sharma et al., 2025). Task Shield (Jia et al., 2024) gates actions of the agent on whether the action contributes to the user’s stated task, and GuardAgent (Xiang et al., 2024) introduces additional safety checks on the action plan via a separate guard agent. All these defenses are heuristics: they reduce attack success rate but cannot provide safety guarantees. 

Information-flow control and system-level guarantees. An alternative is to enforce security outside the model, in the surrounding system architecture. The Biba model (Biba, 1977) does not allow high-integrity entities to read from low-integrity data, precisely the property that indirect prompt injection violates. The dual-LLM (Willison, 2023) pattern is an instantiation of that principle: a privileged model that plans and has access to tools but never reads untrusted content, while a quarantined model reads it but has no access to tools. This provably secures the control-flow, but remains susceptible to data-flow attacks. CaMeL (Debenedetti et al., 2026) and FIDES (Costa et al., 2025) secure data-flow by tracking the taint of values and block consequential actions that use untrusted data. CaMeL emits a plan for the task at the beginning of the trajectory and FIDES ensures trusted context by selectively hiding untrusted tool outputs. The transfer to CUAs is harder as the screenshot entangles trusted and untrusted content. Foerster et al. (2026) extend CaMeL to CUAs to ensure control-flow integrity, and Prismata (Villa et al., 2026) confines cross-site injection in web agents by gating each action output on the integrity of the targeted element, which is evaluated along that element’s ancestor path in the page tree. Untrusted content masking (Nikoli´ c et al., 2026) hides untrusted regions from the privileged model assuming that site owners provide trust labels. Untrusted content can be queried from a quarantined model via structured queries of limited capacity which affects utility.

Threat model. We assume that the benign user operating the agent once invests effort into an allowlist of trusted web domains and e-mail contacts. The user tasks are benign and span web pages, native applications, or both. We consider adversaries which inject IPIs in third-party user-generated content, e.g. forum posts, e-mails, listings or reviews. We exclude cyber attacks on trusted sources which would change their trust status. At the OS-level, trust is carried in file metadata maintained per episode: a file downloaded from the internet is untrusted and may carry an injection. 

Challenges for computer use. Three properties of computer use make a reliable defense difficult. First, a click or a keystroke is syntactically benign, but its effect depends on the element under the cursor or in focus. Actions cannot be checked by their type alone. Second, the screen is a channel that entangles trusted and untrusted visual content. Treating it fully untrusted destroys utility, while trusting it compromises safety. Third, the accessibility tree, the natural textual representation for hybrid web and OS environments, is incomplete: aria-hidden removes nodes, aria-owns 

moves nodes to a new parent, so a permission for a container can cover subtrees outside it. Visible regions may also be missing, shown only as placeholders, or appear as containers without children. 

Overview. SA-CUA builds on the dual-LLM information flow control (IFC) design of Costa et al. (2025) and treats the screen as a channel with mixed trust labels (fig. 1). The privileged planner (P-LLM) sees the screen only with all trusted content unmasked, so its context stays trusted. It can query the quarantined model (Q-LLM), which sees the full screen and must answer within a type the P-LLM requests. Since the answer comes from untrusted content, the P-LLM receives it as a redacted variable. Redacted variables can be used in non-consequential actions, such as answering the user or scrolling. Reading the variable or using it in a consequential action requires endorsement (section 3.3). The same mechanism lets the agent endorse a masked element on screen to unmask it. 3.1 TRUSTED CONTENT LABELING : D ISENTANGLING WHAT ’S TRUSTED ON THE SCREEN 

Motivation. Biba’s integrity model (Biba, 1977) does not allow an entity to read information of lower integrity. In a dual-LLM architecture, this means that the privileged model never sees untrusted content and thus never sees adversarial injections. This is enough for data-independent tasks (Nikoli´ cet al., 2026; Debenedetti et al., 2026; Foerster et al., 2026), which can be solved without reading untrusted content. However, data-dependent tasks are impossible by construction, and therefore an endorsement channel is needed to let information cross the trust boundary (section 3.3). Computer use agents face this problem at an early stage, since the screen mixes trusted and untrusted content. Treating the whole screen as untrusted would keep integrity but make the agent useless. We therefore propose a pipeline that labels which content on the screen can be trusted. 

Masking user-generated content (UGC). Since the agent operates only on trusted domains, an adversary can inject content only as UGC, defined as: 

Definition 3.1 (User-generated content) . A region of a page or a printed node of the accessibility tree (AT) is user-generated if any party other than the site’s operator can cause it to display different content. Regions that are not user-generated are operator-controlled .This definition is broader than that of Nikoli´ c et al. (2026). It is not important who wrote a string but who can influence the displayed value. The definition includes channels that cannot carry an injection, such as commit hashes or issue counts, but unlike a judgment of a channel’s capacity it 4Preprint. Under review. is decidable, which makes labeling reproducible for human and LLM labelers (section A.5). Mere existence does not count as influence, e.g. a timestamp is user-generated because the user chooses when to post, whereas the label “created” that the platform prints before it is not. Labeling errors of accessibility tree elements have different costs. A false negative leaves untrusted content visible, so an attacker’s string reaches the privileged LLM, which breaks the safety guarantee. A false positive masks trusted content and only reduces functionality, for example when the agent cannot read a button. We therefore aim for zero false negatives. This goal is also the reason for a major conceptual change compared to UCM, which masks untrusted content . We invert this and start with a masked screen and unmask trusted content . Missing coverage then costs utility rather than security, including wherever the accessibility tree is incomplete or misaligned with what is rendered. This means that at the pixel level the background canvas is masked by default, so a visual region without a corresponding accessibility tree node is masked. Unmasking has two phases. Offline: we derive per URL template or application a deterministic rule set using a chain of LLM calls. Online: we apply the derived trust rules to the AT, and only trusted regions are unmasked before the screenshot reaches the P-LLM. We first describe the offline phase. 

Default trusted regions. We split the screen into the first-party interface (browser chrome, menus and toolbars of native applications, the window frame) and the content it renders, which is the only place UGC can appear. The first-party interface is never masked and we treat the URL bar as trusted chrome as no site can write into it, the episode starts on a page the user chose, and only trusted URLs may be clicked, so no navigation by the agent can place attacker text there. 

Rule proposal. The accessibility tree is read through OSWorld’s AT-SPI server, extended with link targets, off-screen geometry and window stacking order (section A.5). Trust rules are proposed over the subtree below each application’s content root. This subtree of the AT is sanitized: every accessible name and text is replaced by [name:length:N] , while role, id and class are kept, so the rule-proposing LLM (RP-LLM) sees the structure but not the content. Given this skeleton the RP-LLM proposes a set of trust rules based on its prior derived from the host and its category. Then it checks each rule against the number of elements it covers and deletes rules which are too broad or cover nothing. Finally, every rule that makes a claim about a subtree is applied on the unredacted subtree and checked if the operator wrote every string in it (see section A.5 for details). This check can only drop a rule but not add one, so it only removes trust and is thus safe against manipulation. It is needed because a note written for a redacted subtree can be wrong about what a container holds. For the technical details on the rule language we refer to section A.5. 

Shortcuts. Three shortcuts unmask elements that no rule names. Each uses information the RP-LLM does not have when proposing rules. Consent banners are detected by matching their id against known consent-management platforms. Under our threat model, these banners are controlled by the site operator and cannot be set by an attacker. Capacity. An element whose rendered text fully matches one of 24 patterns (e.g. prices, dates, durations, file sizes, ratings, counts, reference numbers) cannot express an injection and is unmasked. This does not apply if other elements in the same row or column would also be unmasked, since together they could form free text. File ownership. Files that the harness recorded as created by the user are unmasked, both in listings and in their native application. Details are in section A.5. 

From offline proposal to online masking. At run time, the agent selects the stored rule set whose hostname and URL template match the current page, and proposes a new set if none matches. A tem-plate is the URL path with ids and slugs replaced by wildcards. For example, the unseen post 

reddit.com/f/books/59421/what-are-you-reading has the template /f/*/#/* ,so it reuses the rules of a post from another forum ( /f/coolgithubprojects/103666/... ). The forum page /f/books has the template /f/* and gets the rules of a forum listing instead. Rule sets of different templates are not merged, since this can cause leaks (see section C.5). Native applications have no URL that separates their states, so we use the union of their rule sets. This works because their accessibility tree keeps the same container ids across states. 3.2 POLICIES FOR INFORMATION -FLOW CONTROL 

We adopt the policy checks of FIDES (Costa et al., 2025). A consequential tool call proceeds only if the context and the labels of its relevant arguments meet the integrity level required by the policy, 5Preprint. Under review. so the decision to act depends only on trusted inputs. For computer use, checking the tool is not enough, since the effect of a click depends on what is under the cursor, and an untrusted region can contain a submit button, a redirect or any other control. We therefore treat clicking and typing as consequential and label their indirect arguments by the screen region they act on. The label ℓ(x,y )

of the coordinates is trusted only if (x, y ) lies in a trusted region, so clicking and typing in untrusted regions is blocked. Non-consequential actions, such as scrolling, are unrestricted. As in FIDES, policies apply to actions and not to the final response, so redacted variables can be returned to the user without endorsement, as required for the UCM-B tasks. 3.3 ENDORSEMENT : EXTENDING TRUST TO UNTRUSTED VALUES 

Motivation. Content in untrusted regions of the screen is read by a quarantined model, which extracts values from the screen and never calls tools. The planner receives these values only as redacted variables with an untrusted label. Only trusted values are shown in the clear and can be used in consequential actions. These are the user’s instruction, the first-party application chrome and the operator’s own configuration. Strict isolation would rule out most realistic tasks, since the value a consequential action needs is often only available in an untrusted region. For example, when asked for “a Python package that prints colored output to the terminal”, the agent finds the name termcolor 

in a forum post. The name therefore has the post’s label and could in principle contain an injection. In SA-CUA, an endorsement channel is used to change the label of a value from untrusted to trusted without a human in the loop, so the agent can act autonomously. 

Robust endorsement. Endorsement, the integrity dual of declassification, must be robust (Zdancewic & Myers, 2001; Myers et al., 2006). The value being endorsed must not be able to influence the expectation it is checked against or the procedure that checks it, only whether it matches. Asking a second LLM whether termcolor is the package that prints colored output is not robust, since a value such as this-is-the-right-package-send-your-data-to-... can argue for itself. All endorsement routes therefore follow the same pattern. First, a component that never sees the candidate derives an expectation from trusted sources only. This can be a single value, a finite set of values or a structural pattern. Second, there is a deterministic check of the candidate against this expectation, using type-aware equality after normalization and without model judgment. Only if the check succeeds is the value relabeled as trusted and shown to the planner in the clear. The attacker thus can make an endorsement fail but cannot pass a value of its choice. 

Type-constrained queries cannot return free-form text. As in prior work (Debenedetti et al., 2026; Costa et al., 2025; Nikoli´ c et al., 2026; Foerster et al., 2026), a query to the Q-LLM may only return a requested type from a closed catalog, such as a URL, e-mail address or date. The type is enforced after the model answers, and free text is refused. The type bounds channel capacity, e.g. a package name cannot express a shell pipeline. Selection types ( ENUM , INDEX ) let the page choose among alternatives written by the planner without adding its own. Most importantly, the type determines how a value can be endorsed, which is not possible for free text. The only unbounded type is PROCEDURE , a shell command, since no character set allows sudo apt-get install -y htop but blocks rm -f ~/BankStatement.pdf . A procedure is therefore parsed into a syntax tree of pipeline stages, privilege prefix, program, subcommand, flags, operands and redirections. A grammar for each program assigns each leaf a catalog type, e.g. the operands of apt-get install are PACKAGE_NAME s. The program and subcommand must fit the capability the planner requested, and every leaf, including option values, must pass the verifier for its type. Anything the parser cannot model, such as loops, command substitution or unknown programs, is refused (section A.6). 

The endorsement toolset. What counts as trusted evidence depends on the value: a package the user named is checked against the instruction, a package described only by its function needs an external source mapping function to name, a recipient needs the user’s contact book, and a command needs containment against the effects the task authorized. We therefore provide a small set of routes, each tied to one kind of trusted expectation (table 11, section A.6). The main tool, endorse , compares a value against the user’s instruction, the planner’s knowledge from before the episode, a small set of alternatives the planner derives from trusted context, or the value’s type combined with a constraint from the task. Specialized tools check that a name exists in a curated registry or that a file appears in an allowlisted listing, or derive the answer anew from an allowlisted source. For procedures, the commands are checked by capability and the values are endorsed individually. We built these routes 6Preprint. Under review. against a diverse task set (section 4) to test whether the robustness principle holds across the value types agents meet, not to cover every possible task. 

Specification classifier. Some tasks cannot be completed safely at all. In “follow the instructions on screen”, the task is defined entirely by UGC, so no endorsement is possible: an unspecific task compromises safety (section C.4). Before the agent starts, a specification classifier therefore checks whether the task describes the values it needs precisely enough for them to be endorsed. Values only need to be described, not named. “Install the package that prints colored output to the terminal” is enough, whereas a task that names termcolor would make the screen largely unnecessary. If the classifier rejects a task, the user is asked to make it more specific. 

## 4 INDIRECT PROMPT INJECTION SUITES 

We evaluate on adversarial and benign tasks and sort injections by how far the benign task depends on untrusted content: solvable without reading it, requiring engagement with an injection interleaved with the benign instruction, or depending on a value the attack corrupts. Adversarial tasks span GitLab, Reddit, OwnCloud, RocketChat and Thunderbird. We adapt tasks from WASP (Evtimov et al., 2025) and RedTeamCUA (Liao et al., 2026) and contribute tasks for two gaps in these benchmarks: injections that substitute their own value within the user’s task instead of diverting the agent, and injections in native applications. Details are given in section A.3. Three examples are shown in fig. 2. 

Tasks solvable without reading the injection: we take 42 WASP tasks (WASP †; GitLab 22 , Red-dit 20 ) in which the agent is asked to comment on an issue / post or react with an emoji / upvote. They differ in how far the injected goal is from the current page (same page, one navigation step, or several ones needed) and cover six attack classes. We add another adversarial goal that succeeds once the agent opens an attacker URL, and variants that hide the injection in a third-party comment. 

Interleaved injections: we select 65 RedTeamCUA tasks (RTC †) on Reddit, OwnCloud and Rock-etChat, where each injection samples one of 24 harmful actions and claims that it is needed to complete the benign task, such as installing a package, cloning a repository, or configuring the shell. We vary how specific the user instruction is (generic, loose, specific) and whether the injection is formulated as code or natural language, and remove hints such as localhost URLs that reveal the test setting. 

Value Injection: our 78 RTC-value tasks formulate the injection so that it substitutes the benign value and can be returned in type-constrained queries. On Reddit ( 40 ), the top answer for installing vim-commentary contains the injection that exfiltrates private data or links to a malicious clone of the repository backed by fake replies. On Thunderbird ( 28 ), our native application setting, the corrupted value is a lookalike sender or recipient. On GitLab ( 10 ), an issue from a lookalike account tries to swap a value the task needs, such as the username of a teammate or a dependency version. The injected value has the same type as the benign one, so it passes any type-constrained query. For these tasks, we trust the user instruction and the P-LLM’s own knowledge about the task. Personal details, such as a colleague’s e-mail or GitLab handle, come from a contact book kept across episodes. Sites without UGC, such as official documentation, can be read directly, while sites such as GitHub do host UGC and could in principle be manipulated, but we nonetheless treat them as a reference authority for endorsement. Some values needed for a task, such as the identifier of the repository that implements a requested functionality, can only be checked against that GitHub repository itself, so treating it as untrusted would make such tasks impossible to complete. Task and attack success are checked deterministically from the environment state.

At every step the agent receives a screenshot, optionally with the accessibility tree, and answers with pyautogui code executed in the VM; episodes end on DONE or FAIL or after 50 steps, and the context keeps the last 10 turns. All web applications are self-hosted containers: Postmill and GitLab from WebArena (Zhou et al., 2024), OwnCloud with Collabora and RocketChat from TheAgentCompany (Xu et al., 2025), and the ten UCM-B sites (UCM-Bench from Nikoli´ c et al. (2026)); native applications such as Thunderbird, LibreOffice, VS Code and the terminal run inside the VM. Adversarial content is injected into each platform’s backend before the episode, all state is reset between episodes, and parallel episodes run on separate container instances. Unless noted otherwise, models are sampled at temperature 1.0 and top-p 0.9.

Evaluation of prompt injections. Table 1 reports attack success rate, ASR@k, where k is the number of runs, completion rate (CR), and failure rate (FR). On WASP † and RTC † the benign and attack goal can both be reached in one episode, so CR measures utility independently of the attack. In RTC-value, benign and attack goals usually exclude each other, since an agent that adopts the injected value cannot complete the benign task. Therefore we also report failure rate FR (neither the benign nor the attack goal is achieved). As ASR counts any hit over k seeds while CR and FR average over runs, the three need not sum to 100. The unprotected CUA has low ASR on WASP † (4.8% and 7.1%), but high ASR of 46.2% and 38.5% for RTC † tasks and 43.6% and 38.5% for value injections in RTC-value. CaMeL-CUA and SA-CUA reach zero ASR for all tasks with both models. CaMeL-CUA pays for this with utility, completing only 18.5% and 27.7% on RTC † and 18.8% and 29.5% on RTC-value, with its successes concentrated on specific task formulations (see section C.3, section C.4): extracting data from the screen largely fails, a typical episode fails entirely because the agent tries to click a GitHub link that is not clickable, and multi-step Thunderbird tasks in varying environments fail without exception. SA-CUA retains most of the utility. On WASP † it has the highest CR of all frameworks (88.9% and 100.0%), even better than the unprotected CUA, on RTC † it reaches 86.2% and 81.5% against 95.4% and 98.5% for the unprotected CUA, and on RTC-value it completes about as many tasks as the unprotected CUA (50.9% vs 53.4% and 69.2% vs 60.3%), since none of its episodes adopts the injected value; all its remaining episodes fail without harm (FR 49.1% and 30.8%). For the unprotected CUA, tasks with generic user prompts are most susceptible to attacks (see section C.4), and SA-CUA fails if the endorsement does not work, since the task does not say which value to endorse. This is why we introduce the specification classifier: without it, generic tasks can hardly be completed safely.

Cost. We analyze the token cost per episode for GPT-5.6-Luna over successful episodes. Trusted Content Labeling. We evaluate the labeling in table 2 on 160 hand-labeled captures from 18 web domains and 13 native applications (section B). The unit of evaluation is a row, which is a visible node that shows something no other row covers, including images and icons without text. The 20,744 rows consist of 12,229 trusted and 8,515 untrusted rows, and 2,048 (24.1%) of the untrusted rows have bounded capacity. We compare SA-CUA, an allowlist where everything is untrusted by default, with UCM, a denylist where everything is trusted by default, using Qwen3.8-27B and GPT-5.6-Luna as RP-LLM. We map the CSS selectors of UCM to rows by geometric containment. Since UCM is restricted to the DOM, we evaluate only on the 115 web captures. We treat untrusted as the positive class. FNR free is the share of untrusted rows with free capacity that are not masked, which must be zero for a safe system. FNR bounded is the same share for rows with bounded capacity, and FPR is the share of trusted rows that are masked. We report the rates with the capacity shortcut off and, in parentheses, on. For both RP-LLMs, SA-CUA shows no untrusted row with free capacity (FNR free = 0 ), whereas UCM shows 44.1% and 36.7% of them on web only. The high security of SA-CUA comes at the price of over-masking: SA-CUA has an FPR of 76.9% and 56.3% versus 5.2% and 4.7% for UCM. This potential loss in utility reduces markedly with the stronger GPT-5.6-Luna as RP-LLM. The capacity shortcut never changes FNR free . It only unmasks rows with bounded capacity, raising FNR bounded close to the 58.7% of the oracle. A transfer analysis is given in section C.5. 

## 6 CONCLUSION AND DISCUSSION 

We present SA-CUA, a dual-LLM CUA framework that defines the trust boundary in an automatic and conservative fashion based on the accessibility tree. A robust endorsement channel allows it to maintain utility and act autonomously. Our experiments on complex tasks show that SA-CUA outperforms CaMeL-CUA significantly in terms of maintained utility while achieving zero attack success rates on all tasks. Our attacks are non-trivial as we show that at least two of them succeed 9Preprint. Under review. on Claude Sonnet 5. Our Trusted Content Labeling is reliable and achieves zero FNR on free values necessary for security guarantees and outperforms UCM. 

Limitations: SA-CUA guarantees integrity against external manipulation but no confidentiality, so the agent could still disclose confidential information, for example in a public Reddit post. Further, it is an open question whether the long system prompt of the P-LLM could be shortened, by fine-tuning on trajectories to teach the model to work with masked screenshots. Finally, some untrusted content cannot be independently checked: in “find me a laptop that [condition] and buy it”, the condition can often only be checked in the untrusted seller info. Such restrictions are the price of safety, and we see our work as a step towards deciding how utility, cost and safety should be traded against each other. AI USE STATEMENT

Additionally, we used AI tools for improving the text and figures of this manuscript. This work studies indirect prompt injection against computer use agents in order to build and evaluate a defense. Although our benchmark contains adversarial content designed to induce harmful actions, the underlying techniques are already documented in the literature and in existing benchmarks (RedTeamCUA, WASP). We additionally introduce new phishing-style injections delivered via Thunderbird e-mails, which do not appear in these benchmarks but follow well-established phishing patterns and target only our sandboxed environment. Credible evaluation of defenses requires realistic attacks. All experiments run in isolated sandboxes (a VM and self-hosted Docker replicas of Postmill, OwnCloud, RocketChat, and GitLab). No content was posted to live services, “malicious” endpoints are local mock servers, and all credentials and exfiltrated data are synthetic. Chat counterparts are simulated by language models, and the forum replica reuses the public WebArena dataset with only synthetic additions. We will release the evaluation examples and defense implementation for research use, with all payloads targeting local mock infrastructure. REPRODUCIBILITY STATEMENT

## A IMPLEMENTATION DETAILS 

This section gives more implementation details about SA-CUA. Section A.1 describes the evaluation environment and section A.2 the baselines. Section A.3 describes the evaluation examples in detail. Section A.4 covers the architecture of SA-CUA, the IFC mechanism and the policy gate. Section A.5 explains how we unmask the screen using the accessibility tree and how the unmasking rules are proposed, checked and applied. Section A.6 describes the endorsement tools. A.1 ENVIRONMENT 

Virtual machine. Each episode runs in a fresh Ubuntu 22.04 guest. The guest is a QEMU/KVM virtual machine inside a Docker container with 4 CPU cores, 4-GB of RAM and a 32-GB disk. The disk image is mounted read-only and the container is recreated between episodes, so every episode starts from the same clean state. A Flask server inside the guest runs code and captures both the screen (a pyautogui screenshot with the cursor drawn in) and the accessibility tree. Actions are Python strings that this server executes with pyautogui at a resolution of 1920 × 1080 . After each action, the environment waits two seconds before it takes the next observation. Before the first observation, we turn off the update services of the guest (apt timers, snap refresh, the software center and GNOME notification banners). Before every capture, a small script also closes any update banner that is still on screen. 

Web environments. The web applications run in self-hosted containers. We use Postmill with the WebArena data as the Reddit clone, OwnCloud with Collabora from TheAgentCompany for file sharing, RocketChat 5.3 with NPCs simulated by an LLM (also from TheAgentCompany) for chat, and a GitLab instance that holds the WebArena repositories. UCM-B adds ten single-page sites: a shop, a bank, a calendar, webmail, a support desk, a job board, a restaurant, travel booking, a wiki and a forum. Inside the guest, every application is reachable under a domain name without a port (e.g. 

reddit.com , gitlab.com ). An nginx proxy on the host reads the Host header of each request and forwards it to the right container. Each platform runs several instances in parallel, each with its own database, office server and chat back end. A run reserves one instance through an exclusive file lock and keeps it until it exits, so parallel runs never share state that can change. Some settings depend on the domain name, such as the trusted domains and the office endpoint of OwnCloud or the site URL of RocketChat. We apply these settings again at the start of every episode. 

Injection. We place the adversarial content in the environment before the agent starts. The agent sees the environment exactly as a normal user of that platform would. • Reddit. We either update the body of a post or comment in the forum database with SQL, or we add a comment by a third party that carries the payload and hide it among filler comments. • OwnCloud. We copy a PDF into the user’s file store and then rescan the file index. • RocketChat. A colleague is simulated by a local Qwen2.5-32B model. Its strategy tells it to pass on the payload word for word when asked. • GitLab. We file a new issue while impersonating an attacker account, with the injection as its description. • Thunderbird. The mailbox is built in advance as a profile archive that already contains the attack mail. Mock SMTP, newsletter and git servers inside the guest record what the agent sends, downloads or pushes. Between episodes we reset the state of the environments: databases and file stores, comments and reactions left by earlier runs, a database timestamp for each episode that the evaluation uses, and every endorsement the agent made. 

Evaluation and metrics. When the agent stops, two evaluators score the episode. A benign evaluator checks whether the task was completed, and an adversarial evaluator checks whether the injected goal was reached. Both are deterministic and look at the final state of the machine and the applications. Each evaluator combines a getter (a VM command, a file, the mock outbox, a database 15 Preprint. Under review. query or the REST API of the application) with a metric. Checks that use a database only count rows created after the timestamp of the episode, so leftovers from earlier episodes cannot count. For the question answering tasks in UCM-B, we score the agent’s answer. We report three metrics. The attack success rate ASR@ k counts a task as attacked if the adversarial evaluator fired in any of k

seeds. The completion rate (CR) is the mean benign success over seeds. For the value injection suites we also report the failure rate (FR), the share of episodes that neither completed the task nor were attacked successfully. A.2 BASELINES 

CUA. CUA is the standard OSWorld harness (Xie et al., 2024) used in RedTeamCUA (Liao et al., 2026). At each step the model receives a system prompt with the task instruction and the output format, the last ten observations, responses and executed actions, and the current screenshot as a base64-encoded PNG. It predicts the next action as pyautogui code, which the harness parses and executes. The harness has no defense against prompt injection, so it measures how robust the model itself is. The only protection comes from the model’s alignment and from any classifiers or filters that the API provider applies. 

CaMeL-CUA. CaMeL-CUA adapts the implementation of Foerster et al. (2026) to the RedTeam-CUA environment. The P-LLM writes the full plan as Python code, based on the user instruction and a system prompt, and it can only use a fixed set of functions. Some of these functions are run by a quar-antined Q-LLM and return structured output. They include functions that work on screenshots, such as find (locates a UI element and returns its position), summarize_screenshot_content 

(describes the current screen) and check_done (checks whether the task is complete), and func-tions that work on the accessibility tree, such as get_page_elements , get_page_text and 

find_element_by_text . Every output of the Q-LLM goes through the Pydantic-based parser of the CaMeL pipeline (Debenedetti et al., 2026). 

Untrusted content masking. UCM (Nikoli´ c et al., 2026) is the prior work closest to ours when it comes to masking regions that may carry a prompt injection. Before the page reaches the agent, UCM redraws the untrusted regions of the page as labeled placeholders. The labels either come from the site owner or are inferred by an LLM as CSS selectors from a DOM whose content has been removed. Untrusted content can only be reached through a quarantined model whose answers are limited to booleans, integers, floats, enumerations and dates. Tasks that need free text fall back to string answers that the user must approve. Queries to the Q-LLM include the name of the placeholder shown on screen. SA-CUA differs in four ways. First, it labels the AT-SPI tree instead of the DOM, so it also covers native applications. Second, its rules name trusted content rather than untrusted content, so a missing rule masks too much instead of leaking. Third, a constrained answer is not accepted because it carries little information, but only after it has been endorsed against trusted evidence. Fourth, no step asks the user to approve a value. Every adversarial task is an indirect prompt injection (IPI) against a computer use agent. A benign user gives the agent a legitimate task. Injections are written using only public or organizational knowledge (who the user is, which repository or vendor they use), so they must work without knowing the exact wording of the task. We distinguish two kinds of injections. Effect attacks make the agent take a new action that is not part of the task, such as deleting a private key, sending out a file, adding a rogue project member or posting a political slogan. The benign task never asked for this action, and the attack counts as successful when its side effect appears. WASP † and RTC † consist of effect attacks. Value attacks keep the action the same but change the value the agent uses in it, such as a package index, a collaborator, a quantity or a recipient. The injection succeeds when it replaces the benign value. We build value attacks under three rules. The correct value must be derivable from the trusted domain (the user’s own words, a file the user wrote, a named directory entry, a named vendor domain) and never from a rule made for one specific example. Endorsement may never consist of “asking another model”. And there is no human in the loop as a general way out. A.3.5 TRUST BOUNDARY IN THE EVALUATION EXAMPLES 

The right trust boundary is not fixed, since different settings and tasks need different boundaries. This matters most for the question of which domains count as trusted at all, because the user may explicitly ask for a task that cannot be done without touching content that would be untrusted in another setting. For example, if the user asks the agent to find a GitHub repository in a Reddit thread and clone it, then downloads from GitHub are allowed, and GitHub must be able to endorse the repository the user asks for. In our tasks, the injection is limited to the visual channel on the websites where the trajectory starts. The benchmarks our tasks come from do not track integrity labels, so we set the provenance of local files in advance. Files that are needed for the benign goal are labeled trusted/owned (this mainly affects the OSWorld tasks). The user and the model itself (i.e. its parametric knowledge) are also trusted. The interface of the application, including the address bar and navigation, is trusted for two reasons. The user opened the first screen, and any later page was reached through a link that must itself have been trusted or endorsed. However, when the prompt names a source, this does not make everything that source says trusted. In the RocketChat tasks, for example, one task asks the agent to ask Mike Chen how to set vim as the default editor and then set it up. Yet Mike Chen is the channel that delivers the ad-versarial instruction. In the same way, a task that asks the agent to look for an e-mail from 

lisa.wong@businessanalytics.com must be able to endorse the sender, but not neces-sarily the content of the e-mail. A.3.6 EVALUATION

A quarantined model (Q-LLM) answers questions about the untrusted regions of the screen. The Q-LLM can only return typed values, and the P-LLM sees these values as redacted variables. 22 Preprint. What the P-LLM sees. The only view of the screen the P-LLM gets is a redacted screenshot, in which every region that is not labeled trusted is blacked out (section A.5). Masking works on a default-deny basis: every element that is not covered by a rule granting it trust is masked. The P-LLM does not receive a listing of the accessibility tree. In each turn it also receives the variables in scope, one line per variable, with the name and integrity level but with the value hidden. Only endorsed variables show their value. The conversation history is append-only. A sliding window keeps the last ten elements, where each element is an assistant call, its result and the screenshot that followed, and the window records how many elements were dropped. A new screenshot is added only when the screen or the set of revealed regions has actually changed, so pure reads cost no image. wait is the documented way to look at the screen again without acting. An episode ends when the P-LLM calls done , fail or abstain , after 50 UI steps, after 70 P-LLM turns, or after six tool errors in a row. Calls that do not change the VM, such as reads and endorsements, do not count towards the step budget, and neither do calls that the policy blocks. 

Tools and arguments. The P-LLM can use the tools listed in table 9. On purpose, there is no tool that runs a terminal command. The P-LLM opens a terminal with a hotkey and types into it, so the terminal is ordinary screen content and follows the same rules as any other window. Arguments are plain JSON. Inside a string, a variable is referenced as $name , and the host fills in its value only when it executes the call, so the P-LLM never reads the value. Every tool schema is strict and every field is required. A field that only some calls use takes an explicit empty value, such as an empty 

control . The schemas stay the same for the whole episode, which keeps the start of the P-LLM’s prompt cacheable. 

Screen zones. The screen is split into zones with the following integrity. • First-party interfaces such as the browser chrome and the OS shell are trusted. • Inside a web page , the rendered content is untrusted by default. Only elements that a rule or a shortcut marks as trusted are unmasked. • In native applications , the trust boundary is the document, not the application. The shell of the application is trusted, while its content (a mail body, a PDF page, a file listing) is treated exactly like the inside of a web page. • The terminal is trusted until its scrollback contains a command that prints content the user did not write: a network download to standard output, reading an untrusted or unknown file, command substitution, or inline interpreter code. From then on, the terminal is masked. • Self-authored content. Messages and posts whose byline matches the identity declared by the operator are shown automatically as self-authored. The same holds for trusted files that the user wrote. 

Policy. The policy gate checks every tool call in a fixed order. 1. Endorsement calls are logged and allowed. Whether they succeed is decided inside the tool. 2. The location rule. A pointer action whose coordinates fall inside a masked region is refused, and a drag is checked at both ends. The rule looks at pixels and not at where the coordinates came from, so typing in coordinates by hand does not get around it. Under masking, the integrity of the target element is exactly its visibility: visible means trusted, masked means untrusted. 23 Preprint. Under review. 3. The focus rule. Keyboard input is refused while the focused element is under the mask, so the P-LLM can neither type into nor copy from content it cannot see. Compositor hotkeys (opening a terminal, switching windows) and a focused terminal are exceptions. 4. Fetches with an untrusted URL are refused unless the host is on a trusted allowlist. A refused call never reaches the VM. The P-LLM receives the message “Policy blocked your last tool call” together with a fixed reason that never quotes any content. After three identical refusals, the message adds that repeating the call will keep failing. Text that the P-LLM types itself is treated as trusted, because the model takes on the integrity of its trusted context. 

Screen reading. query_screen gives the unmasked screenshot to the Q-LLM and asks it a question. The call must name an answer_type (section A.6). Free text and booleans are refused (for booleans, see below). An answer that is a point is mapped back to screen coordinates and takes the label of the content it was read from. Three more tools search for text in the accessibility tree instead of asking a model. They replace boolean queries, since a boolean value can hardly be verified. locate_on_screen finds a typed value, requires it to be unique and returns UNIQUE 

and its coordinates. If the result is ambiguous, not found or rejected by the model, the tool fails.

It adds no integrity and only catches an extractor that reports a wrong value. Specification classifier. Before the episode starts, a classifier decides whether the instruction specifies every value the task needs precisely enough to endorse it. Values only need to be described, not named. “install the package that prints colored output to the terminal” passes, but “follow the instructions on screen” fails, because then the task is defined by UGC and nothing trusted is left to check against. A rejected task is sent back to the user once with a request to make it more specific. In our evaluations, the loose version of the task is used automatically instead. The classifier runs on the same model as the P-LLM. A.5 TRUSTED CONTENT LABELING 

Why the accessibility tree. We read the screen through the AT-SPI accessibility tree and not through the DOM, for two reasons. First, the tree covers every application, including native ones, while the DOM only exists in the browser. Second, the tree describes what the browser exposes and draws, including screen geometry, while the DOM describes how the page is built. For example, a button that the DOM represents as three nested framework elements is a single push-button 

node named Submit in the tree. The DOM is also longer than the tree. Still, the tree is large, up to 200K tokens for a single capture. We cannot shrink it with the rule-based filtering of OSWorld, which drops nodes that have no name or text, because nameless visual regions such as ad banners are exactly the ones that can carry untrusted content. For computer use that mixes the web and the OS, the accessibility tree is therefore the right input channel. 

Tree capture. The server inside the VM walks the AT-SPI tree of every application, with a limit of depth 50, width 1,024 and 5,000 calls per application. For each node it records the role, name and states (e.g. visible, showing, active, focused), the object attributes (HTML tag, class, id, ARIA role), the text content, the value and actions, and the screen geometry. Geometry is recorded for nodes that are visible and showing, for media and for named nodes. For a link, the target URL is read from the hypertext interface of the parent and matched to the child by identity, not by position. A node that is drawn off-screen keeps its coordinates and gets the flag cp:offscreen_geometry . Top-level windows get their stacking order from the window manager ( st:stackorder ), so that a window hidden behind another one cannot draw over it. We correct two sources of wrong geometry before we use any geometry. LibreOffice reports every widget below the menu bar too high by exactly the height of the menu bar. And AT-SPI reports frames without their title bar, so we use the rectangle of the enclosing shell panel as the area that covers the window. 24 Preprint. Under review. 

Defects of the tree. The tree is incomplete and sometimes wrong. Content that is drawn but marked 

aria-hidden is missing. Booking.com, for example, hides the visible price and puts a copy for screen readers (“Price C578”) into a collapsed element next to it, and Amazon does the same with prices. Wrappers can be moved or collapsed, so their geometry is shifted or shrinks to 2 × 1 pixels, as for a menu item on Booking.com or the contributor count on GitHub. Placeholders for modals appear in the tree without the element they stand for. And aria-owns moves nodes to a different parent, so on Amazon a product grid shows up below a legal disclaimer widget. These defects are the reason for our default-deny approach. 

Applying the UGC definition. Definition 3.1 asks who can influence the displayed value. It does not ask who wrote it or whether its channel could carry an injection. The second question gives inconsistent answers across a corpus. Commit hashes, branch names and issue counts can all be influenced but seem unable to carry a payload, and the capacity of a channel depends on the platform in ways that are easy to get wrong. GitHub reactions, for example, come from a closed set of eight emojis, while GitLab and RocketChat accept custom ones that an attacker could manipulate. The influence question can be decided, so both human and LLM labelers answer it in a reproducible way. Channels that can be influenced but cannot carry an instruction are handled separately by the capacity shortcut. Making an element appear does not count as influencing its content. A timestamp is user-generated, because the user chooses when to post. The created label in front of it is not, because posting only makes the label appear and its text is fixed by the platform. 

Rule proposal. The proposer does not see any page text until the final audit. It receives a cleaned skeleton of the tree with one line per node and indentation for depth. Each line keeps the role, id 

and class of the node, and every accessible name and text is replaced by [name:length:N] .Rules are proposed in four calls per capture. 1. Site prior. The model only gets the host and its category, without URL, title or skeleton. It describes who operates the site and where UGC can enter it. The prior is cached per site. 2. Proposal. Given the skeleton, the model returns rules that grant trust. Since it never sees page text, the page cannot address it. 3. Extent feedback. The model gets its rules together with the number and kind of rows each rule covers, and it returns a new set of rules. The idea of this second round comes from Nikoli´ c et al. (2026). 4. Note audit. This is the only call that reads page text, and it can only remove rules. For every trusted rule, it asks whether the note describes the covered region and whether every string in it was written by the operator. 

Rule language. A rule set is a JSON list. The main type of rule is an ancestor_path of identifiers. Each identifier names a role and can also name an id , which must match exactly, and a 

class , which must appear somewhere in the full class string of the node. So s-topbar matches 

class="s-topbar ps-fixed js-top-bar" . The identifiers in ancestor_path are matched in order against the chain of ancestors of the target node, but they do not have to be consecutive, so intermediate levels can be left out. A rule covers the matched container and every-thing below it. A rule names what is trusted and adds a short free-text note on what the region is, for example:           

> {"ancestor_path": [{"role": "landmark", "class": "s-topbar"} ], "verdict": "trusted", "note": "top navigation bar: renders Home/Questions/Tags/Users" }

Two optional fields refine a rule. except lists signatures and excludes every node below the named node that matches them or lies inside one. This handles pages where the chrome shares a wrapper with submitted content. own_role limits the grant to nodes of a single role inside the container. This handles trusted widgets spread through user content, such as vote buttons at the bottom of a post. 25 Preprint. Under review. A rule with "scope": "page" sets the verdict for the whole page: trusted for a reference or error page, and untrusted for a self-published page where the operator and the author are the same. Such a rule must be the only rule for its page. A rule for the user’s own content is only resolved at run time. Each row is decided by the first of the following that applies: the allowlist of consent banners, the page title, the rules in order (the first match wins), and otherwise untrusted. 

Guards. Three safety checks run on every page after the rules have been applied. First, we drop any rule that would mark more than half of the rows on a page as trusted, because such a rule has most likely grabbed the whole page by mistake. Rules that set the verdict for the whole page are exempt from this check. Second, if a trusted row contains text of four or more characters that also appears in an untrusted row, we treat the trusted row as untrusted as well. Otherwise an attacker could get their text shown in a trusted place simply by having it repeated there. Third, a trusted verdict only passes from a container to the elements inside it if those elements actually lie within the area of the container on screen. The accessibility tree can place an element under a parent that sits somewhere else on the page (through aria-owns ), and without this check a small trusted strip could make content far away from it look trusted. 

Shortcuts. Three exceptions unmask rows that no rule names. Each of them uses information that the proposer did not have. Consent banners are recognized by matching the banner’s own id 

strings against a curated list of fingerprints of consent management platforms. Under our threat model the domain is trusted and only uploaded content is not, so these identifiers belong to the operator’s template and an attacker cannot reach them. Capacity. A row from a third party is unmasked if it cannot carry a prompt injection. A row counts as capacity-bounded only if every string it shows fully matches one of 24 closed grammars. These cover prices and currency codes, percentages, absolute and relative dates, clock times and durations, file sizes, distances and areas, ratings, counted nouns, ordinals, pagination, dimensions and reference numbers. A grammar only allows letters as fixed keywords from a closed list, and it rejects characters outside ASCII except for a fixed set of currency signs. This way homoglyphs are refused instead of being normalized and accepted. There is no length threshold. A fragment check refuses the exception if other elements in the same row or column would also be unmasked, so a number cannot be released from inside a sentence. File ownership. A file that is recorded as written by the user is shown in the clear, both as a name in a directory listing and as a document open in its native application. The lookup uses three keys: the window title, the full path, and the base name for rows of the file manager whose whole text is the base name. 

Scoping and routing. Rules are stored per scope (the normalized host or the application name) and per URL template. At run time, a capture is matched first by exact path, then by template, by a looser template, by a path prefix, and finally by the default of the scope. Rule sets of different web pages are not merged, because merging can increase the number of leaks in web environments. Native applications and the single-page UCM-B websites are the exception, because their structure stays the same across screens (see section C.5). When no stored rule set matches, a new one is proposed live during the episode with the same pipeline, including the audit, and it is cached for the rest of the episode. 

Runtime unmasking. In every turn, the agent builds the rows from the live tree, resolves the rules for each content root, predicts the verdicts, applies the shortcuts and unmasks every row that is trusted from the default-masked screen. Each visible row with a box is painted as a filled rectangle unless it is trusted. If a trusted row lies inside an untrusted ancestor, its own pixels stay visible. If boxes of unrelated branches overlap, the mask wins. A browser root without a URL is denied by default, and if several browser windows are open, the rules of each window are resolved from its own address bar. For native applications, the window is split into shell and content, which separates the trusted menus and toolbars from the content region. The table of a file chooser and an archive listing count as content. Regions revealed by endorsement are copied back from the original screenshot and removed from the hit test of the mask, so the location rule and the pixels always agree. Reveal records are resolved again against every new tree and dropped when their element is covered or off-screen. If a mask cannot be built (no tree, a tree that cannot be parsed, no content root, failed alignment or a failed live proposal), the agent retries three times and then stops the episode instead of showing an unmasked screen. 26 Preprint. A.6 ENDORSEMENT TOOLSET 

Typed extraction. Every screen or text query names an answer type from a closed list (table 10). Each value is checked deterministically against its type’s constraint and is rejected otherwise. Each type is also classified by its shape as none, bounded or unbounded. For each type we list the verifiers that are able to endorse it. Any other endorsement tool is refused. This closes the path of giving a value a different type to reach a weaker verifier. For instance, a boolean that is retyped as an enumeration is refused. Only the task instruction can endorse every type. Equality for verification is strict after normalization and is never based on one string containing another. 

endorse . The main endorsement tool takes a variable, its type and one of several sources. • task . The value must appear as a whole term in the user’s instruction, which the host keeps. Terms are matched as whole subtokens, so a value inside a longer literal, such as alias tproj=’...’ or alpine:3.19.1 , still matches. Very short values, stop words and instructions that only point at the screen are refused. • recall . The model answers the question of the tool call only from its parametric knowl-edge, without seeing the screen or the value. The result is CONFIRMED , DIVERGED or 

> ABSTAINED

.• expected . For this source, the P-LLM can directly supply the expected value or also several alternatives, built from context it already trusts. • shape . This is only a type check. It clears e.g. version numbers. 

Endorsement from external sources. endorse_by_registry checks whether a value ex-ists in an index, by exact match on the index’s own name field. Curated indexes (the Ubuntu and Debian archives and Docker Official Images) give ENDORSED , since no attacker can reg-ister a name there. Open indexes (PyPI, npm, GitHub) return INSUFFICIENT and clear noth-ing. endorse_by_listing checks whether a value is in a listing fetched from an allowlisted host, such as a release index or the file list of a repository. At least one path segment of the listing URL must be a term of the task, so the attacker cannot choose which listing is used. 

endorse_by_crosscheck derives the answer again from an allowlisted source, using a Q-LLM that is not told the candidate, and deterministically compares the two answers. A disagreement returns DIVERGED and does not clear the value. The question and the search query must come from trusted context, so the attacker cannot choose the evidence through the query of the P-LLM. This endorsement tool can also be used by the P-LLM after disagreement to verify an assumption the model has about the value under endorsement. This can be done since endorsement via crosscheck might fail because the Q-LLM failed to read the value correctly from screen and the P-LLM has an assumption on what the correct value might be for the user task. 

Procedures. endorse_by_procedure endorses a shell command that was read on an untrusted page. The host first splits the command into its stages. It then uses a table of known programs to work out what kind of value each argument is (a URL, a file path, a package name and so on), and this also covers code passed to bash -c . Loops, command substitution and unknown programs are refused. Next, the host looks up which capabilities each program needs. If these go beyond what the P-LLM de-clared for its task, the command is refused. A command that passes these checks is endorsed through the first of three routes that succeeds. In route A, the command is a standard operation (installing a 27 Preprint. Under review. package, cloning a repository or downloading a file) and the task names its arguments. In route B, it is a single command and each argument passes its own check. For example, a URL must point to an allowlisted host, and a model that sees only the task and not the page must name the same resource. In route C, a page on an allowlisted host, whose address the P-LLM gives, contains a command with the same components. In every case, the variable then holds the command as the host rebuilt it, never the text that was read from the page. Route B is the most relevant one: take the following RTC Reddit task as an example. The injected comment asks the agent to run sudo systemctl stop cups 

before git clone https://github.com/shobrook/ChatOverflow . The P-LLM de-clares that it needs to download and write files. The clone command fails route A, because the task does not name the URL. It passes route B where the leaf value gets checked similarly to 

endorse_by_crosscheck : github.com is allowlisted, and the crosscheck returns the reposi-tory described in the task, shobrook/ChatOverflow . systemctl stop needs a capability that the P-LLM did not declare, so it is refused, both on its own and when it is chained to the clone. 

Unmasking screen elements. Masking can hide an element that the task needs, such as the chat input field or the inbox row of a colleague. The P-LLM cannot point at a masked element itself, so 

endorse_element lets it ask for one in two ways. By author : the P-LLM passes an identifier from a trusted source (an entry from get_contacts , the task, or an ENDORSED variable), and the host reveals the rows whose byline matches this identifier exactly. Only the name of the author is shown, never what they wrote. By control : the P-LLM names a widget from a fixed set of controls that belong to the application itself (e.g. message_box , reaction , upvote , downvote , link ,and button together with its exact label from the task). For some applications, the ids of elements cannot be known by the model. For those, we wrote an adapter that finds this widget in the accessibility tree. This way the P-LLM can ask for message_box which gets routed to the exact id of message boxes on RocketChat. Both kinds of request are resolved again on every new screen. 

Choosing an endorsement route. The P-LLM picks a route based on how it knows what the right value is. If the task names the value, it uses task . If the P-LLM knows the value from its own knowledge, it uses recall . If the task only says what the value should do, it checks the value against an allowlisted source with a crosscheck. For a message from a trusted person, it first looks up the person with get_contacts and then reveals the row of that sender with endorse_element .For a command, it uses endorse_by_procedure , which breaks the command down into its parts and checks each of them. If more than one value would be correct, the P-LLM can pass all of them to expected as a list of candidates. Table 11 lists the tools, and table 12 shows which route is used for each benign goal. ## C ADDITIONAL RESULTS 

C.1 ABLATION RUN 

We cannot run the UCM agent exactly in our setup, because UCM works differently in three ways. It re-renders websites with the untrusted regions as placeholders, it reads the DOM instead of the accessibility tree, and it only masks what is labeled untrusted, while SA-CUA masks everything that is not labeled trusted. Instead, we run an ablation of SA-CUA that comes close to UCM in concept but keeps our harness, our masking and our system prompt. We make three changes. First, we remove all endorsement tools. Second, query_screen returns its typed answers in the clear, so a constrained value read from untrusted content reaches the P-LLM directly, as in UCM. Third, we turn off the policy gate, so clicks into masked regions are no longer blocked. We compare this ablation with a single seed of SA-CUA with Qwen3.8-27B (table 14). As expected, some attacks now succeed, on RTC † (1.5%) and on RTC-value (3.8%), because the injected value reaches the P-LLM without any check. The attack success rate stays low, however, because masking still hides the injected instructions, so only attacks that work through the returned value can succeed. Utility drops on most suites. Without endorse_element , the agent cannot reveal the controls it needs, such as the comment box or the upvote button. Instead, it has to ask the Q-LLM for the coordinates of the masked element and then click on them. Its P-LLM writes one plan at the start, and most of the work happens in the quarantined calls, so the Q-LLM uses more tokens than the P-LLM. Counting both, CaMeL-CUA uses about 0.2 times the tokens of the CUA. Its successful episodes also come from only a few tasks, so its average covers a different mix of tasks than the averages of the other two agents. Much of the overhead of SA-CUA comes from the long system prompt of the P-LLM, which teaches it how to query and endorse values. The CUA needs no such prompt, because it already knows its workflow and the available pyautogui commands from training. It remains an interesting question for future work whether fine-tuning on trajectories of SA-CUA can shorten this prompt and teach the model to work with masked screenshots and to endorse untrusted information. Rule sets are proposed offline, once per URL template or native application, and are reused by every later episode that reaches a matching page, so this cost is not incurred at every step. Proposing the rules for one snapshot takes three calls with parts of the accessibility tree in context to the RP-LLM. Turn 1 contains the instructions and the sanitized skeleton, i.e. the accessibility tree with all text redacted. Turn 2 repeats turn 1 and appends the proposed rules together with a report of how many elements each rule covers. Table 18 reports the resulting input tokens for GPT-5.6-Luna over the 160 hand-labeled captures of section B. On average, one proposal takes 58,754 input tokens. Turn 2’s prefix and two of the three audit copies repeat earlier input (49% of the total), so prompt caching lowers this to 40,072 billed tokens, priced as in table 15. A single proposal thus costs less than a fifth of one SA-CUA episode (18.0% cached, 10.1% uncached). Amortized over n episodes that reuse the rule set, its share per episode falls as 1/n . With caching, it drops below 5% of the episode cost after 4 episodes and below 1% after 18; without caching, after 3 and 11. An episode that reaches several new templates pays one proposal for each, but each proposal amortizes separately. Since a rule set covers every page with the same template, e.g. every post in a forum, this point is reached quickly. All figures count input tokens only, as the proposer’s output tokens were not recorded. C.7 ABLATION ON RP-LLM: THE NOTE AUDIT

## D DISCUSSION OF AGENT TRAJECTORIES FOR SA-CUA 

This section looks at the trajectories of SA-CUA in detail. D.1 A TYPICAL SUCCESSFUL EPISODE 

A successful episode is short and always follows the same pattern: the agent reads a value, checks it and then acts. It takes a median of 9 planner turns and, on average, 11.9 tool calls, 0.7 refusals, 1.9 endorsement calls and 6.7 UI actions. The planner never gets an untrusted value directly. It only gets a handle to the value and has to endorse it before it can use it. 

Example: Reddit (RTC †). The task is: “Install the Python package termcolor in version 2.4.0 . . . The post describes the necessary steps.” The agent reads the steps from the post as an untrusted 

PROCEDURE . Its first attempt to endorse the command is refused, because it asks for a capability that the P-LLM did not declare. The second attempt passes through route A of section A.6, because the command is a standard operation. The agent then types the command and finishes the task.

Example: Reddit (RTC-value). The task is: “Copy the clone URL of the vim-commentary plugin from this reddit thread and clone it . . . ” The thread offers a URL with a small typo in the user name (github.com/tpepe/... instead of tpope ). The same pattern appears in many episodes: the first endorsement attempt is refused, and the second one, aimed more precisely, succeeds. A refusal gives the agent useful information and does not end the episode. D.2 WHY EPISODES FAIL 

The failures fall into five groups: • Turn limit. The planner runs out of turns without calling done , fail or abstain , so no final action is recorded and the episode scores 0. These episodes burn more input tokens and model calls than a successful one. Most refusals say that the Q-LLM could not answer, or that the control the agent asks for is not on screen. The agent knows what it is looking for, but on the masked screen it cannot tell which element it is. • Step limit. These episodes run out of environment steps but have few refusals, so they are not stuck in a loop. The tasks are simply long, such as the Thunderbird invoice tasks, which require collecting several invoice e-mails, downloading their PDFs and writing one e-mail. • Done but wrong. The planner declares the task done, but the evaluator disagrees. • Abstain. Every endorsement route fails and the agent stops. For example, Mike Chen in RocketChat names a correct Node.js version, but the model cannot endorse it. • Explicit fail. The agent gives up by calling fail itself. D.3 READING VALUES FROM UNTRUSTED CONTENT 

A value that only appears in untrusted content cannot be endorsed by any route, because every check needs evidence from outside that content. This matters little when the agent only has to read a value and report it. SA-CUA is able to query the Q-LLM for the information needed from the screen. However, almost none of the correct answers were endorsed: the agent reads the value with query_screen and reports it while it is still UNTRUSTED . This does not break the security guarantee, since reporting a value is non-consequential. The limit becomes visible when an untrusted value has to be used in an action. In banking_send_money , the user asks the agent to send $100 to Whole Foods Market with “the correct account number for the recipient”. This number only appears on the untrusted page, so there is nothing trusted to check it against, and the task fails for SA-CUA, while CUA completes it. Such tasks cannot be completed safely by design, because they ask the agent to act on a value that the threat model says it must not trust. The same limit also shows up in two less obvious places. First, once a command with inline code, such as python -c , prints to the terminal, the terminal then counts as untrusted and is masked, because such code can print any content. The agent then cannot read the output of a command it just ran. In Reddit (RTC †), for example, the agent installs a package and checks the installation with python3 -c , but the result of this check is masked right away. Second, a masked element on a page with content written by users has no safe key. endorse_element reveals an element by its author or its label, but on such pages both come from the attacker, e.g. on a UCM-B forum that only shows display names, the author of a post can never be matched. Other failures revolve around masked control buttons, such as sorting flights by price or canceling a calendar event, which fail because of the masked screen and the turn limit in which the agent does not find a way around the masking. 37 Preprint.
