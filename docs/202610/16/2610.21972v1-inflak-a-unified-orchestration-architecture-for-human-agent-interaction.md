## 摘要
由大语言模型驱动的智能体日益广泛地支持开放式活动，但如何编排智能体何时以及如何与人类交互，仍然颇具挑战。现有方法通常将交互机制绑定于特定任务或执行模式，缺乏能够满足多样且不断演变的交互需求的统一架构。我们提出 Inflak，这是一种用于人机交互编排的四层统一架构，将状态重构与路由、交互与执行规划、交互设计以及界面渲染分离。其分层设计与渐进式细化机制使其具备广泛适用性、运行时灵活性、模块可组合性以及编排可维护性。我们在通用智能体框架中将 Inflak 实现为智能体原生的、基于技能的插件，并通过涵盖多种应用场景与交互范式的案例集、技术性能测试以及对比实现案例研究进行评估。评估结果表明，Inflak 可作为编排多样化人机交互流程的通用且可扩展的基础架构。

## Abstract
LLM-powered agents increasingly support open-ended activities, yet orchestrating when and how agents interact with humans remains challenging. Existing approaches often provide interaction mechanisms tied to particular tasks or execution patterns, lacking a unified architecture for diverse and evolving interaction needs. We introduce Inflak, a unified four-layer architecture for human-agent interaction orchestration that separates state reconstruction and routing, interaction and execution planning, interaction design, and interface rendering. Its layered design with progressive resolution enables general applicability, runtime flexibility, module composability, and orchestration maintainability. We implement Inflak as agent-native, skill-based plugins within a general-purpose agent framework and evaluate it through a gallery of various application scenarios and interaction paradigms, technical performance testing, and a comparative implementation case study. The evaluations show that Inflak can serve as a general and extensible foundation for orchestrating diverse human-agent interaction flows.

### 1.1 论文研究什么问题？

这里的“编排”不仅是生成界面，更涉及**任务状态理解、控制权转移、交互机制选择和执行结果回流**。

| 现有方法 | 主要优势 | 主要局限 |
|---|---|---|
| 应用代码中预定义工作流和界面 | 交互丰富、行为可控 | 交互时机与形式较固定，跨任务适应性不足 |
| 根据上下文动态生成控件 | 能适应具体任务状态 | 生成逻辑通常绑定单一应用，难复用和维护 |
| 智能体调用询问、选择或审批工具 | 可跨任务主动请求输入 | 通常只有少量通用交互原语，表达能力有限 |

因此，论文提出四个设计目标：**通用适用性、运行时灵活性、模块可组合性和可维护性**。

**整体意义**：把分散在提示词、任务技能和前端代码中的交互逻辑，组织为可复用、可追踪的运行时结构，而不是为每个应用重新设计完整流程。

## 2. 方法论：核心思想与技术细节

### 2.1 核心思想：四层分工、渐进式细化

Inflak 将“接下来做什么交互”拆分为四层，逐步从抽象任务状态细化到具体界面：

| 层级 | 核心问题 | 主要职责 |
|---|---|---|
| **L1 Router：路由层** | 当前是什么状态，交给谁处理？ | 重建状态，选择任务规划器，返回宿主智能体或结束流程 |
| **L2 Planner：规划层** | 还缺什么，下一步做什么？ | 诊断任务缺口，决定请求交互还是直接执行 |
| **L3 Designer：设计层** | 用什么交互来解决缺口？ | 定义展示内容、操作控件及预期返回，形成语义控件契约 |
| **L4 Renderer：渲染层** | 如何实现界面并收回结果？ | 生成、渲染界面，校验返回结构，再交回 L1 |

关键在于：**不提前把任务需求绑定到固定界面，也不让界面生成模块同时承担任务规划职责。**

### 2.2 理论基础：IAI 交互图

论文以已有的 **Interaction-Augmented Instruction（IAI）模型**为基础，将交互表示为实体与关系构成的图：

- 实体包括人类、交互、文本提示、产物、增强指令和生成式模型。
- 关系包括人执行交互、交互操作产物、传达意图、调用模型等。
- 不同关系组合形成不同交互范式。

Inflak 的主要贡献不是提出新的交互分类，而是**将描述性的 IAI 模型转化为可运行的编排机制**：识别当前状态、判断下一步需要激活的关系，再绑定具体交互能力。

### 2.3 关键机制

- **任务缺口诊断**：L2 根据任务特定策略，判断是否存在值得请求用户参与的缺口，例如意图不明确、对象指代未解决或空间布局缺失。论文没有给出统一的数值优化目标，主要依赖技能中的策略和模型推理。
- **显式交接契约**：相邻层通过结构化 handoff 传递状态、交互目标、上下文和预期返回，避免仅依靠自由文本推理轨迹衔接。
- **能力注册表**：
  - `planners.json`：登记任务规划器及适用条件。
  - `widgets.json`：登记交互能力及兼容约束。
  - `tools.json`：登记执行工具元数据。
- **技能化实现**：以 GitHub Copilot Agent 的技能插件承载各层实例，不修改宿主智能体核心执行逻辑。
- **语义设计与实现分离**：L3 定义“交互应做什么”，L4 决定如何用 HTML、CSS、JavaScript 等实现，也可以使用预定义模板。

### 2.4 算法流程与运行路径

论文没有提出训练算法，核心是以下运行时循环：

1. L1 汇总用户请求、当前产物、交互历史和执行结果。
2. 根据注册表选择 L2 任务规划器。
3. L2 判断任务是否存在需要人类解决的缺口。
4. 根据判断选择路径：
   - **交互路径**：`L1 → L2 → L3 → L4 → 用户返回 → L1`
   - **执行路径**：`L1 → L2 → 执行工具 → L1`
   - **宿主返回**：无适用规划器时返回宿主智能体。
   - **完成路径**：当前目标已满足时结束流程。

例如，生成咖啡馆场景时，系统先请求用户绘制布局草图；草图返回后，L2 将其与文本要求组合，直接调用图像生成工具，跳过 L3、L4。

## 3. 实验设计：数据、场景、Benchmark 与对比方法

### 3.1 应用案例集

作者实现了 **13 种交互范式**，对应 IAI 的 12 种原子范式及其作者另外识别的一种范式，覆盖：

- 提示词选择、组织、分解和属性调节。
- 草图作为指令、参考图像与区域标注。
- 产物直接操控、对象绑定、局部修改。
- 根据上下文主动发起交互。

产物包括文本、草图、位图、CSV 数据和 SVG；操作包括选择、拖拽、绘制、标注、切换和直接操控。

随后构建两个组合应用：

1. **多模态共创**：从儿童故事写作转向封面设计，复用表单等控件，并按任务切换规划器。
2. **SVG 拼贴创作**：围绕持久产物组合初始创作、分析、比较、修改和增量添加等交互。

这些案例主要检验架构的表达和组合能力，**不是有独立用户参与的效果实验**。

### 3.2 技术 Benchmark

论文使用**自建测试集，而非公开标准 Benchmark**：

- 2 个插件。
- 每个插件覆盖 4 类运行路径。
- 每类路径 5 个测试用例。
- 合计 **40 个用例**。
- 每个用例重复 10 次。
- 在文中报告的 GPT-5.5、GPT-5.6 Sol 两种宿主模型上测试。

用例由 GPT-5.6 Sol 生成，包含输入提示、必要资产、模拟用户响应，以及预期观察边界和判断标准。

主要指标：

- **分层遵循率**：是否按架构规定的层级顺序运行。
- **延迟**：端到端及各层的中位数、P95 耗时。

**未评估**最终界面质量、产物质量、交互选择是否最优或真实用户满意度。

### 3.3 对比实现案例

比较两种具备相似用户功能的系统：

- **Inflak 插件**。
- **技能化 vibe-coded 插件（VC）**：从相同的最小 Copilot SDK 聊天应用独立构建，但不采用 Inflak 四层结构。

共同任务是新增可复用的 **Compare Viewer**，并接入写作修订和图像编辑流程。分析重点是：

- 哪些文件负责交互实现、调用策略和能力暴露。
- 新能力引入后，需要修改哪些依赖组件。
- 职责是否混合，依赖路径是否一致。

这属于**定性软件结构比较**，不是开发时间或维护成本的统计实验。

### 5.2 是否充分、客观、公平？

- **支持可行性较充分**：多范式、多产物、两种界面环境和重复测试，能说明架构并非仅适用于单个演示。
- **支持优势结论仍有限**：没有与其他完整编排架构进行定量对比，也没有证明四层结构优于三层、合并层或端到端实现。
- **重复次数不等于场景广度**：大量重复能测稳定性，但独立用例仍只有 40 个。
- **基线有一定可比性**：两种实现共享基础应用，功能要求相近，VC 也采用模块化技能，而非刻意使用完全无结构的实现。
- **仍有偏差风险**：用例由模型生成且围绕现有插件设计；VC 由研究者构建，质量可能受提示词和实现过程影响；排除插件未被调用的运行，使结果主要反映“成功进入插件后的遵循情况”。

## 6. 主要结论与发现

### 6.1 运行稳定性

| 路径 | GPT-5.5 | GPT-5.6 Sol |
|---|---:|---:|
| 交互路径 | 94/100，94% | 100/100，100% |
| 执行路径 | 100% | 100% |
| 返回宿主智能体 | 99/99，100% | 100/100，100% |
| 完成路径 | 100% | 100% |

GPT-5.5 的 6 次违规均出现在拼贴场景：5 次跳过 L2，1 次从 L3 回退到 L2。

**这些结果说明分层协议通常能被模型遵循，但不能等同于任务成功率或交互质量。**

### 6.2 延迟与瓶颈

- 交互路径中位延迟约 **30.1–30.9 秒**。
- 执行路径约 **48.8–50.8 秒**，包含外部任务执行开销。
- 返回宿主或完成路径约 **3.1–4.4 秒**。
- L4 中位延迟约 **15.7–16.2 秒**，是界面交互路径中的主要耗时环节。

作者认为延迟可管理，但是否可接受仍取决于使用情境；对于高频、即时操控，约 30 秒的界面准备时间可能较明显。

### 6.3 扩展与维护

新增 Compare Viewer 时，Inflak 的变更主要局限于：

- 新增 L3 技能。
- 更新注册表。
- 修改相关 L2 规划器的调用策略。

VC 也可实现复用，但交互设计、调用时机和返回协议更容易混在同一文件中，并形成直接、间接并存的依赖路径。

## 7. 优点与亮点

- **问题定位准确**：将“生成界面”提升为“协调人类参与和自主执行”，覆盖交互前后完整流程。
- **职责边界清晰**：路由、任务推理、交互语义和界面实现分离，有助于定位问题和局部修改。
- **复用粒度合理**：不同任务可共享交互能力，同一任务也能随状态变化选择不同控件。
- **状态回流机制统一**：用户输入和执行结果都重新进入 L1，支持跨轮次、跨任务调整。
- **实现较轻量**：技能文件、注册表和交接契约便于与现有智能体集成，并提供公开代码和案例。
- **覆盖面较广**：不仅展示问答和审批，还覆盖草图、对象绑定、局部操控和持久 SVG 产物。
- **明确限定技术指标范围**：作者没有将分层遵循率直接作为界面或产物质量指标。

## 8. 不足与局限

### 8.1 实验与证据边界

- **缺少真实用户研究**：无法判断是否减少用户负担、改善控制感或提高任务效率。
- **缺少开发者研究和量化维护指标**：没有开发耗时、错误率、回归缺陷或长期维护数据。
- **没有结构消融**：四层是合理的设计选择，但尚未证明是效率与组合性的最佳平衡。
- **跨框架泛化尚未验证**：实际测试集中在 Copilot 和两个同系列宿主模型上。
- **没有比较运行成本**：不能据此断言优于普通工作流或其他编排框架。

### 8.2 方法与应用限制

- **缺口判断依赖人工策略和模型推理**：没有充分验证请求交互的必要性，可能过度询问，也可能漏掉关键确认。
- **契约不是硬性正确性保证**：GPT-5.5 已出现跳层；返回结构合法也不代表内容语义正确。
- **主要面向下一步决策**：多个并存缺口、复杂依赖、多步前瞻、并行或嵌套交互仍是未来工作。
- **效率仍需优化**：运行时生成界面耗时较高，模板复用、缓存和异步执行的收益尚未实测。
- **安全与长期运行讨论不足**：虽然提到沙箱和返回校验，但缺少提示注入、恶意产物、权限边界、状态膨胀和注册冲突等系统性评估。

**总体评价**：Inflak 的核心贡献是一套具有实践价值的交互编排架构，而非新的模型算法。现有证据较好支持其**可实现性、范式覆盖和模块化扩展潜力**；对于真实用户收益、长期维护优势、跨框架泛化和成本效率，仍需要更严格的比较实验。
