LLM-powered agents increasingly support open-ended activities, yet orchestrating when and how agents interact with humans
remains challenging. Existing approaches often provide interaction mechanisms tied to particular tasks or execution patterns, lacking a
unified architecture for diverse and evolving interaction needs. We introduce Inflak, a unified four-layer architecture for human–agent
interaction orchestration that separates state reconstruction and routing, interaction and execution planning, interaction design,
and interface rendering. Its layered design with progressive resolution enables general applicability, runtime flexibility, module
composability, and orchestration maintainability. We implement Inflak as agent-native, skill-based plugins within a general-purpose
agent framework and evaluate it through a gallery of various application scenarios and interaction paradigms, technical performance
testing, and a comparative implementation case study. The evaluations show that Inflak can serve as a general and extensible foundation
for orchestrating diverse human-agent interaction flows.

Introduction
Large language model (LLM)-powered agents are increasingly supporting a wide range of open-ended activities [25].
Along with the increasing capability and applicability, researchers and designers have explored various ways for humans
and AI models or agents to interact with each other in efficient and effective ways. For example, Dreamsheets [1]
provides a spreadsheet-like interface for users to expand instructions along given dimensions conveniently, such as
style and color usage, before task execution. DynaVis [36] applies synthesized widgets to enable users to manipulate
generated artifacts in a targeted manner. A recent work proposed Interaction-Augmented Instruction (IAI) [34] model
to systematically characterize these interaction paradigms. It identified twelve paradigms depend on the interaction
timings, such as before and after invoking AI models, and targets, including prompts, generated artifacts, or non-verbal
information to supplement prompts. These observations suggest that no single interaction form is suitable for every
situation. Interaction is often embedded directly in an ongoing activity and grounded in the immediate task state, while
the form of interaction can vary substantially and adapt to different task types, user needs, and stages of execution.
Therefore, as the task state evolves, an agent must determine when human interaction is needed and how it should
be carried out, while coordinating interactions with autonomous execution. We refer to this runtime problem as
human-agent interaction orchestration.
Orchestrating human-agent interaction is non-trivial, since the interactions are highly in-situ and dynamic [16].
Also, the agent users and developers may have their special requirements, such as dedicated interaction design to
facilitate existing workflow, to be supported by agents at runtime. These features requires designing and implementing
orchestration to meet four key pillars: general applicability across tasks and runtime capabilities, flexibility to initiate
and resolve interaction according to evolving task state, composability to combine and extend heterogeneous interaction
and execution capabilities, and maintainability through explicit and separable orchestration responsibilities. However,
these needs are hard to be met in existing systems, which progressively make interaction decisions from application
design toward runtime control. A common strategy is to encode workflows in application code and provide predefined
interfaces for rich forms of interaction [6, 38]. While effective within their intended tasks, both the available interaction
forms and when they are used are largely determined at design time, limiting adaptation to changing tasks and states
(insufficient applicability). More recent systems combine code templates with prompt-based generation to synthesize

task-specific interaction widgets at runtime [36, 43]. This moves interaction realization into runtime and enables greater
in-situ flexibility, but the generation logic and interaction conventions remain tied to individual applications, making
them difficult to compose, reuse, or extend across tasks (insufficient composability and maintainability). More agentic
approaches further move interaction control into the agent itself, allowing prompts or agents [21] to decide when user
input should be invoked through mechanisms such as ask-user-question tools [2]. Although broadly applicable across
tasks, these approaches typically achieve such generality through a small set of generic interaction primitives, such as
structured questions or multiple-choice input, limiting the range of interaction semantics and realizations that can be
orchestrated (insufficient flexibility in interaction methods). Taken together, existing approaches separately provide rich
predefined interaction, dynamically generated task-specific interaction, or general agent-triggered interaction, but do
not jointly support the requirements of increasingly diverse human-agent interaction.
To fill the gap of existing orchestration methods and meet the four requirements, we introduce Inflak, a unified
orchestration architecture for human-agent interaction. The architecture contains four layers (Router, Planner, Designer,
and Renderer) and each layer has multiple instances that can be designed and added by agent developers. The previous
layer progressively decide which instance in the next layer should be routed to at runtime. Specifically, based on the
comprehensive IAI model, Inflak dynamically construct the current interaction state as a graph with entities what
has been involved in the interaction (e.g., human users, prompt instructions, and artifacts) and links what has been
activated (e.g., a prompt was sent to the agent) in the Router layer. Then, it will pass the state to the corresponding
next Planner to decide whether there is a gap between the current state and an optimal state for agent execution (e.g.,
ambiguous intent) and then what next link and the end entity of the link should be activated (e.g., to ask human to
detail image layout with sketching or to generate the image directly). If a specific interaction is needed to fill the gap,
the Planner will pass necessary information, such as the detailed task and gap needs, to the selected Designer, which
designs a specific interaction method to address the gap, such as a sketchboard or a composed form with multiple
fields. The Designer will assemble the information from the Planner layer into the interaction specification and pass
it to the final corresponding Renderer layer. The Renderer produces the interaction interface code based on needs,
such as HTML, JavaScript, and CSS code for a web-based app, and validates its return to the runtime for Router to
plan the following round. Each instance of one layer is defined with a unified structure with key function introduction,
the approach to interpret information from the previous layer, criteria to route to the next layer, and handoff package
design to the instances in the next layer. The layered design enables a dynamic routing across multiple instances of one
layer so that different interactions can be initiated for various contexts at runtime (flexibility). It also facilitates adding a
new instance, removing one, or modifying one by developers, while keeping the others not affected (composability and
maintainability). At the same time, rooted in the IAI model, the unified four-layer structure and the consistent structure
of information inside each layer instance are disentangled from detailed contexts and specific interaction design. It
allows that various interactions and tasks can be included and resolved consistently, achieving broader applicability.
We instantiate this architecture as plugins to GitHub Copilot1, a widely applied agent, in which the instances
of four layers are implemented as the agent’s skill files. To demonstrate Inflak can meet the four requirements, we
evaluate its applicability through implementing all 13 interaction paradigms reviewed by Shen et al. [34] as plugins
and testing the implementation’s speed and success rate in providing proper interactions. Then, we merge ten plugins
representing different interaction paradigms into two plugins, multi-modal co-creation through a chat-based interface
and visual collage authoring through a canvas-based interface, demonstrating the composability and the flexibility

• We introduce Inflak, a unified four-layer orchestration architecture for human-agent interaction that separates and

Related Work
We reviewed existing work to summarize the characteristics of human-agent interaction to understand the necessity
of orchestration mechanism (Sec. 2.1). We also identified how the orchestration is performed in existing work and
discussed why they are insufficient to fulfill the requirements led by the characteristics of human-agent interaction
(Sec. 2.2). We note that some interaction design work targets at interactions with general GenAI models instead of
strictly defined LLM-powered agents [20], such as work on prompt preparation [38, 43]. However, their interaction
and orchestration methods are mostly transferrable to LLM-powered agents. As a result, we also included them in our
related work. Similarly, we also reviewed a broader scope of human-AI interaction models in Sec. 2.3 to examine how
their characterization can facilitate our design of human-agent interaction orchestration architecture.
2.1
Characteristics of Human-Agent Interaction
The growing capabilities of agents are reshaping how human participation is integrated into interactive tasks [32, 47].
Human–agent interaction is increasingly embedded across different stages of extended activities such as writing [29, 43],
data analysis [37], and visual creation [27]. For example, DreamSheets [1] and TaleBrush [6] support intent refinement
before generation through structured controls and sketch input. WaitGPT [40] exposes an agent’s ongoing data-analysis
process so that users can inspect and modify intermediate steps during execution. After generation, systems such as
DynaVis [36] and AI-Instruments [31] further support continued refinement of existing artifacts. Other systems involve
agents throughout broader task processes, spanning planning, execution, inspection, and revision [7, 21]. Collectively,
these works show that human–agent interaction can occur at multiple points throughout a task rather than at a single,
fixed interaction point.
These systems also demonstrate that interaction varies not only in when it occurs, but also in how it is realized to
accommodate different task states and artifact types. For example, Intent Tagging [9] introduces interactions tailored to
visual and semantic assets. Coladder [42] supports exploratory coding through a node-based interface for code and
natural-language prompts. Such systems often design specialized interaction mechanisms around the particular artifact
being manipulated. More recent work further explores interfaces that need not be predefined for each artifact or task
type, but can instead be adapted at runtime [13, 41].
Human–agent interaction is therefore increasingly characterized by both interaction diversity and in-situ adaptivity.
As runtime state evolves, systems should determine whether interaction is needed, what it should achieve, and how it

2.2
Orchestration of Human-Agent Interaction
Human-agent interaction orchestration determines when human participation is needed, what interaction should
be initiated, and how it is coordinated with agent execution [47]. Existing systems implement such orchestration
through different mechanisms, ranging from application-defined workflows to dynamically generated interfaces and
agent-integrated interaction tools [18, 21].
One common approach is to encode orchestration in application-level workflows and program logic. Such systems
organize user interactions, agent operations, and their transitions through predefined application structures. For example,
PromptCharm [38] implements multimodal prompt refinement through a task-specific workflow. Cocoa [7] supports
human-agent co-planning and co-execution within an explicitly designed collaborative process. These systems enable
rich task-specific interaction, but when and how interaction occurs is largely predetermined, limiting the flexibility in
deciding interactions at runtime.
Another approach uses templates and generative mechanisms to realize interactions dynamically. Rather than
implementing every interface in advance, these systems leverage runtime context to synthesize or adapt interaction
components. For example, DynaVis [36] synthesizes widgets for targeted visualization editing. Malleable Prompting [44]
transforms preference expressions in natural-language prompts into manipulable GUI controls, enabling users to steer
LLM generation and inspect the effects of individual preferences on the output. Related systems similarly use runtime
task context [41, 46], user goals [13], or evolving artifact state [4] to generate or adapt task-specific interfaces, providing
greater situated flexibility than fully predefined interaction. Though more flexible, these methods are still heavily
depend on the detailed tool-specific implementation, which can hardly be generalized to other applications.
More recently, agent frameworks and runtimes have incorporated human interaction as part of agent execution. For
example, Claude Agent SDK’s AskUserQuestion [2] provides a callable mechanism for agents to request structured
user input. AutoGen [39] integrates humans into multi-agent conversations through configurable user-proxy agents
that collect feedback and relay it to other agents. By integrating interaction mechanisms into the agent runtime, these
approaches allow agents to request human input without prescribing every interaction point in application code.
However, their built-in interaction mechanisms commonly emphasize generic and rigid interaction methods, such as
questions, choices, or approvals, rather than supporting a broad range of interaction forms for flexible and diverse tasks.
Overall, these methods can hardly achieve both general applicability and flexibility in delivering diverse and in-situ
interactions. Furthermore, their implementation often distributed the entire orchestration of human-agent interaction
across application workflows, interface generation, and agent execution. This fragmentation makes it difficult to
coordinate and compose diverse interaction mechanisms within a shared runtime structure for easy maintenance
and reuse. Inflak addresses these issues by resolving interaction needs from the evolving task state at runtime and
further separates interaction planning from capability binding and interface realization, allowing different interaction
mechanisms to be selected and instantiated within the same orchestration structure.
2.3
Models for Understanding and Characterizing Human-AI Interaction
Prior work has modeled human-agent interaction from different perspectives. Early work examined how control and
initiative are distributed between humans and intelligent systems, establishing conceptual foundations for different levels
of automation and mixed-initiative collaboration [11, 26]. More recent studies extend these perspectives to dynamic

human-AI collaboration. Muller and Weisz [22] examine how collaboration changes across different configurations
of human and AI initiative, incorporating dynamism and sociality into existing collaboration frameworks. Building
on the concept of agency, Zhang et al. [45] synthesize collaboration patterns and strategies in human-AI co-creation.
Complementing these perspectives, Chappidi et al. [5] identify recurring archetypes of roles assigned to LLMs in
collaborative decision-making, illustrating how AI can contribute to human decisions in different capacities. Together,
these studies provide a high-level understanding of how humans and AI share responsibilities, exercise control, and
organize collaboration.
Other studies examine human-AI interaction more closely through the ways users communicate with and manipulate
AI systems. Moving beyond conversational prompting, researchers have investigated how interface affordances, input
modalities, and interaction techniques shape users’ ability to express and refine their intentions [14, 18]. These
investigations have led to frameworks that organize recurring interaction practices across tasks and contexts. For
instance, COFI [30] describes co-creative interaction in terms of how participants contribute, communicate, and
manipulate shared products. Other work provides taxonomies of human-LLM and creative GenAI interaction to
characterize recurring communication modes and design patterns [8, 12]. Related work further explores how GUI
operations can complement text prompts to express fine-grained intent [31, 33]. Among these work, Shen et al. [33]
characterize who, how, why, when, and what interactions are used to enhance text prompts. AI-Instruments [31]
demonstrate how prompts can be embodied as reusable, directly manipulable interface instruments. These studies
offer concrete design knowledge or guidelines for understanding and developing diverse interaction mechanisms,
while providing limited structured and operationalizable characterization of human-AI interactions to guide detailed
interaction design and implementation.
To represent such diverse interactions within a common structure, researchers have further explored how interaction
patterns can be constructed from fundamental elements and their relationships. Tsiakas and Murray-Rust [35] develop
a semi-formal representation of information exchange between humans and traditional AI systems powered by deep
learning techniques, such as recurrent neural networks or interactive reinforcement learning, in which interaction
primitives can be composed into recurring patterns. However, their method provides limited characterization for
systems or agents powered by generative AI models that can be instructed with natural language prompts and
other GUI interaction techniques, limiting its applicability in our goal to orchestrate human-agent interaction. More
recently, Interaction-Augmented Instruction (IAI) [34] formalizes human-GenAI interaction as an entity-relation graph
connecting humans, interactions, prompts, artifacts, and GenAI. By combining these relationships, IAI systematically
characterizes diverse interaction paradigms and further supports their composition into more complex forms. Unlike
broader taxonomies and design spaces, this representation makes the dependencies among interaction components
explicit and provides structures that can be instantiated within an execution process, making IAI a suitable basis for
studying a unified orchestration mechanism in human-agent interaction. However, IAI itself does not specify how
these structures should be operationalized as an evolving agent runtime: the current task state must be interpreted to
determine which interaction or execution is needed, abstract relations must be bound to available capabilities, and
subsequent execution must be coordinated as state changes. Inflak builds on this representation to provide these runtime
orchestration mechanisms.

Inflak: A Four-Layered Architecture to Unify Human-Agent Interaction Orchestration
As discussed in Sec. 1, human-agent interactions are dynamic and in-situ, and thus orchestrating these interactions is
non-trivial. This section introduces how we design Inflak to tackle the challenge with a unified four-layer architecture

3.1
Design Goals
To better accommodate the complexity of human-agent interaction across diverse runtime states, we derive four design
goals to guide our orchestration structure design.
G1. Applicability. A human-agent interaction orchestration architecture should provide a common organization
for coordinating heterogeneous runtime participants, including interactions, users, generated artifacts, and agents.
This organization should remain applicable across different tasks, interaction paradigms, artifact types, and modalities,
rather than requiring a task-specific orchestration structure for each application.
G2. Flexibility. An orchestration architecture should allow interaction and execution decisions to be resolved in situ
from the evolving runtime state. Human responses, artifact changes, tool results, and intermediate execution outcomes
should be able to change whether interaction is needed, what interaction should be initiated, how the interaction results
are interpreted, and what the next operation should be.
G3. Composability. Orchestration capabilities should be independently addable, replaceable, reusable, and combinable.
Introducing a new task-specific planner, interaction mechanism, agent, tool, or subworkflow by agent developers should
require localized extension rather than reconstruction of an end to end workflow, while existing capabilities should
remain reusable across different orchestration contexts.
G4. Maintainability. The architecture should make different classes of orchestration decisions explicit and identifi-
able, so that developers can understand how control, interaction, and execution decisions are made. Changes to an
orchestration capability should remain localized enough that it can be added, modified, removed, or debugged without
tracing or reconstructing the complete workflow.
3.2
Formulating the Orchestration Workflow
To achieve the four goals with Inflak, the foundation is a model of human-agent interaction with descriptive power to
characterize various interaction paradigms, discriminative power to differentiate those paradigms’ usage, and generative
power to accommodate potential new paradigms [3, 17]. Only after defining interactions between humans and agents
in a universal way, it is possible to design a unified orchestration mechanism to scaffold agents in deciding when they
should interact with humans and how the interaction would be conducted. A model with the three powers ensures that
Inflak can be generally applicable to existing and also future human-agent interaction (G1).
Based on our survey of human-agent interaction or broadly human-GenAI interaction models (Sec. 2.3), we identified
Interaction-Augmented Instruction (IAI) model as an appropriate starting point, as it captures a broad range of recurring
and composable interaction patterns and provides a structured representation amenable to runtime execution. IAI
model defines a graph consisting of entities and relations to show how information flows among them in human-GenAI
interactions (Figure 2). The entities define what participants are in the current interaction, including human, interaction,
prompt, interaction-augmented instructions (i.e., a combination of both verbal and non-verbal information produced by
interactions as input to GenAI), artifacts, and GenAI. The relations specify who conducts the interaction and what
the interaction targets. For example, linking a human user node, an interaction node, and an artifact node means that
the user conduct interactions on the artifact. With the design, interaction paradigms for various scenarios and goals

can be derived by combining multiple relations, such as one paradigm to show how interactions on artifacts can be

With the IAI model and its derived interaction paradigms, we abstract and divide our orchestration problem into three
sub-problems which need to be solved sequentially:
Build contextual interpretation of IAI entities and relations for decisions. IAI paradigms describe the entities involved
in an interaction, how these entities are connected, and how interaction is organized in relation to other elements
of the paradigm. In a runtime setting, however, these descriptive structures must be interpreted against a concrete
and continuously evolving task state. The system first needs to collect interaction relevant information from sources
such as user prompt, artifacts, prior interaction results, and execution outcomes, and use this information to determine
how the current runtime state instantiates an abstract interaction structure in the next step. This motivates a runtime
orchestration flow that first establishes the current context and routes control accordingly (Fig. 2(A)), before identifying
the next operation needed to advance the task.
Decide IAI paradigm application and task execution through stateful runtime coordination. IAI identifies twelve atomic
interaction paradigms and demonstrates how the conceptual model can support the derivation of additional paradigms
and the composition of multiple paradigms into richer interaction workflows. In an agent runtime, however, composition
alone does not determine how such a workflow should unfold over time. Runtime execution introduces stateful dynamics
and lifecycle management concerns. The system must determine which interaction paradigm or execution step is
currently applicable and then reason over the corresponding entities and relations to determine what information or
state change is expected before the task can progress. It includes deciding whether human interaction is currently
needed to address issues such as underspecified intent or unresolved artifact references (Fig. 2(B1)). If needed, it should
also select the appropriate interaction paradigm to proceed with, such as asking the user to mark their intent on artifacts.
If no interaction is needed, it should hand over the task to executors, such as a GenAI model (Fig. 2(B2)). Therefore,
composing interaction paradigms at the conceptual level must be extended into a stateful coordination process that
continuously and progressively maintains and updates the task context throughout runtime execution (G2 and G3).
Detail next-step interaction represented with abstract IAI entities and relations to concrete interaction designs. IAI
intentionally represents entities and relations at an abstract level, which enables recurring interaction paradigms to be
identified and compared independently of particular implementations. Runtime orchestration, however, must translate
these abstract roles into concrete capabilities that can actually be invoked in the current environment. Specifically, the
interaction entity 𝐼captures the functional role of human interaction without prescribing how that interaction should
be performed. Its concrete realization may vary according to the task, modality, artifact, and intended information
return, such as selecting among recommended options, providing textual input, sketching over a visual artifact, or
directly manipulating an object. Runtime orchestration therefore requires a further resolution step that binds abstract
interaction roles to appropriate interaction designs and also implement designs as executable interfaces (Fig 2(C)).

3.3.1
Overview. We design Inflak as a four-layer architecture to progressively resolve the three problems through L1
Router, L2 Planner, L3 Designer, and L4 Renderer. Besides L1 Router, each layer can have multiple instances to handle
various situations. Each instance will have the identical structure of input, output, and other detailed information to
state a modular function. For example, a L3 Designer instance defines how multi-field forms should be designed, while
another instance states how sketchboards will look like. The previous layer will decide and invoke a specific instance of
the next layer with sending the instance an identical handoff package.
Specifically, L1 Router tackles the first sub-problem through collecting context information and pass it to an instance
of the Planner layer based on the current task nature. The Planner layer resolves the context information and then
determine whether interaction to fill in information gaps between humans and agents or direct task execution is needed,
tackling the second sub-problem. When interaction is needed, an instance of L3 Designer will be invoked to compile
the detailed interaction design based on design knowledge and Planner’s identified gaps. This layer addresses the third
problem jointly with L4. L4 Renderer implements the interaction design based on the technical environment where the
interaction happens, such as a chat-based web interface.
With the progressive resolution process, Inflak can accommodate various context and interaction needs dynamically
(G2). Also, separating functions across layers and defining multiple instances for one layer ensures that various
interaction paradigms can be easily added to Inflak by reusing other layers and instances (G3). Updating or removing a
specific layer instance will only require minimum changes in the previous layer and will not affect other instances in
the same or downstream layers (G4).

3.3.4
L3 Designer: Interaction Specification. L3 designs the concrete interaction required by the plan from L2. Given an
interaction requirement and its task context, it specializes the intended interaction into a semantic widget contract.

the supported interactive controls, and defines the expected return. L3 determines the interaction design without
implementing the concrete interface.

widget specification: the scene request and relevant entities are presented as context, a drawing canvas and appropriate
sketching controls support spatial input, and the completed sketch is defined as the expected return. The resulting
widget contract is then passed to L4 for concrete interface implementation.
3.3.5
L4 Renderer: Interface Realization and Return Validation. L4 compiles the renderer-independent widget contract
into an executable and sandboxed interface instance, and binds submission behavior to return collection. When an
interaction requires a particular presentation style or complex interface behavior, L4 may incorporate reference HTML,
CSS, or JavaScript assets while preserving the semantic contract defined at L3. L4 also validates returns against the
expected-return schema and routed back to L1. In Fig. 3, L4 realizes the sketch contract as a sandboxed canvas with the
required task context, drawing controls, and submission actions. Once submitted, the sketch is exported as a layout
artifact and returned in the contract-defined structure after validation. The validated return then re-enters L1 for state
reconstruction and further routing.

the current orchestration state is resolved through different runtime pathways depending on whether further human
interaction is required, autonomous execution is ready, or no further Inflak processing is needed. Each interaction or
execution result subsequently re-enters L1, where the updated state is reconstructed and a new pathway is determined.

Implementing Inflak as Agent Plugins
We implement Inflak as skill-based agent plugins to GitHub Copilot, a widely applied agent. In a plugin, each layer
defines a fixed runtime responsibility and layer instances define concrete capabilities through skills and shared handoff
contracts. Through integrating the plugin with Copilot SDK2 as backend, the agent can leverage Inflak to dynamically
interact with human users through a web-based interface. We choose skills as the implementation unit because they
provide a lightweight and agent-native mechanism. It allows modular behavior without modifying the host agent’s core
execution logic. Each skill can independently encode a layer-specific capability, its applicability, and its expected inputs
and outputs in a readable specification, while remaining dynamically invocable by the host agent at runtime. This
modular structure maps naturally to Inflak’s layered design, allowing individual layer capabilities to be implemented
and extended independently while coordinating through shared handoff contracts. In the following, we describe how
the four-layer architecture is implemented and present the resulting plugins in Sec. 5. Our implementation is available
at https://github.com/Inflak-orchestration/Inflak-demo.

4.2
Developing a Plugin
Inflak provides shared contracts that specify the expected responsibility, required content, and handoff structure of
each layer instance. These contracts serve as authoring guidance for translating task and interaction descriptions into
framework-compatible skill files. Besides manually authoring them by following guidance, it is possible to define a new
L2 Planner skill in natural language and ask coding agents, such as GitHub Copilot, to implement it. For example, a task
such as “select relevant HCI papers every day and produce a daily paper report” can be translated into an L2 Planner
that applies the IAI model to identify task states in which missing information or unresolved decisions constitute an
interaction gap. L3 Designer instances allow similar flexibility that developers can describe an intended interaction
profile in natural language or provide reference implementation code as a template. Therefore, a basic Inflak plugin can
be authored largely through natural-language interaction with coding agents, based on the contracts constraining the
resulting skills into the expected four-layer structure.
We also developed an Inflak authoring plugin based on Inflak’s four-layer structure. It can help new developers to get
familiar with what information should be provided for a basic Inflak-based plugin by dynamically scaffolding developers
with Inflak-orchestrated interactions. During authoring, the plugin continuously reasons about what information is
still missing, when user input is needed, and which interaction mechanism is appropriate for eliciting or aligning
that information. It can therefore decide, for example, when to ask the user to clarify a task boundary, select among
candidate workflow stages, or compare alternative widget designs, rather than following a fixed authoring wizard.
For the daily-paper example (Fig. 5), the authoring plugin may progressively decompose the task into stages such as
confirming the date range, specifying research topics, and filtering candidate papers. At each stage, Inflak determines
whether an interaction gap exists and, if so, selects an appropriate interaction form, such as a date selector, keyword
selection, or paper-filtering cards, to align the emerging plugin design with the user’s intent. Once the task logic and
interaction designs are sufficiently specified and confirmed, the accumulated intent is represented as a plugin blueprint.
This blueprint is then translated, according to the shared contracts, into concrete L1-L4 instances and corresponding
registry files. In this sense, the authoring plugin makes Inflak self-applicable: the same orchestration structure used by
downstream plugins is also used to coordinate how those plugins are authored.

4.3
Extending a Plugin
The plugin organization provides explicit extension points for adding new task and interaction capabilities. As illustrated
by the dashed nodes in Fig. 4, adding a new task-specific planning capability primarily requires introducing a new L2
Planner skill and registering it in planners.json. Its task scope and eligibility conditions make the new capability
visible to the shared L1 Router, which can then route appropriate runtime states to it without introducing a new
end-to-end workflow or modifying existing planners. Similarly, a new interaction mechanism can be added as an L3
Designer skill and registered in widgets.json. Once registered, existing L2 Planners can reuse the new interaction
capability when its interaction goals, artifact constraints, return schema, and runtime requirements are compatible.
This organization also supports composition across task capabilities. Multiple task-specific L2 Planners can coexist
in the same registry and operate over a shared runtime state containing user input, artifact state, interaction history,
prior returns, and execution outcomes. As the task evolves, the L1 Router can route different states to different eligible
planners within the same plugin. Meanwhile, L3 interaction capabilities and the shared L4 Renderer remain reusable
across these planners. Thus, extending a plugin primarily adds or registers localized layer instances, while shared
orchestration and interaction capabilities can continue to be composed across tasks without duplication.

artifact and workflow. The runtime can therefore route changing user intent and artifact state to the appropriate task
planner and interaction mechanism without requiring an entirely separate interaction stack for each task.

Technical Evaluation
We further evaluate Inflak as a plugin across different host agent models to examine the stability and latency of executing
its orchestration process during inference. This section reports the experimental setup and results.
6.1
Experiment Settings
Dataset. We constructed a dataset using the two Inflak plugins in Secs. 5.2 and Sec. 5.3. We tested the two plugins
as (1) they include various tasks ranging from writing to image editing; (2) they are composed of multiple different
interaction paradigms; and (3) they work in both chat-based and canvas-based interfaces. For each plugin, we tested
four resolution pathways mentioned in Sec. 3.3.6, with five cases per pass type. The coverage allows us to examine
the stability and the latency comprehensively. We used GPT-5.6 Sol [24] to generate cases grounded in the plugin
workflows with explicit preconditions. Each case specifies an input prompt, any required assets (e.g., a reference image
for a poster), a simulated user response when interaction is needed (e.g., selecting a balanced stance), and the expected
observable boundary with its evaluation criteria. For example, one case pairs a fixed cafe photograph containing a
bicycle and a chalkboard with a prompt asking the agent to let the user identify which object to remove before editing.
The simulated response selects the chalkboard using a predefined bounding box; the evaluation records whether a
selection interface is rendered and whether control subsequently returns to L1 router after submission. Each case was
repeated ten times with the same prompt, assets, and user response to assess run-to-run stability.

and GPT-5.6 Sol [24], to examine whether Inflak can be executed consistently across different host agent models. The

prescribed by the architecture. For latency, we measured both per-layer and end-to-end values when executing resolution
pathways with different models. Intentionally, we did not measure the quality of finally generated interaction widgets
or execution results, as they depend on the quality of the detailed widget design instructions in skills and the execution

6.2
Results
Overall, the results suggest that, as an agent extension, Inflak operates with manageable runtime latency and stable
execution reliability across the two host agent models. We report pathway-level compliance and end-to-end latency in
Table 1, and further decompose runtime cost by architectural layer in Table 2.
Regarding layer compliance, Host-Agent Return, Completion, and the Execution Pathway achieved 100% compliance
for both models, as shown in Table 1. The Interaction Pathway achieved 94% compliance for GPT-5.5 and 100% for
GPT-5.6 Sol. The six noncompliant GPT-5.5 runs all occurred in visual collage authoring cases, with five skipping
the L2 by transitioning directly from L1 to L3, while one transitioned backward from L3 to L2. Overall, these results
indicate that Inflak’s prescribed layer progression can be followed reliably across the tested GPT host agents, including
multi-layer execution and interaction pathways.
Among all pathways, Host-Agent Return and Completion had the shortest median end-to-end latencies of 3.06-4.39
seconds across the two models, as they only require running L1. In comparison, the Interaction Pathway required
median latencies of 30.12-30.87 seconds, while the Execution Pathway required 48.78-50.75 seconds. The per-layer
results in Table 2 explain the observation. Most layers other than the implementation one (L4) remained lightweight.
Across the two models, median latency was 3.86-3.92 seconds for L1, 6.58-7.08 seconds for L2, and 3.87-4.33 seconds for
L3, showing an overall manageable time cost for the first three layers. L4 was comparatively more expensive, with
median latency ranging from 15.74 to 16.21 seconds. This concentration of latency at L4 suggests that the additional
cost of interaction-oriented pathways primarily arises during concrete interaction implementation rather than being
uniformly distributed across the orchestration pipeline. Similarly, execution pathways’ latency mostly depends on the
additional tools or model calls to execute tasks.

7.1
Case Scenario and Study Setup
Scenario and requirements. Our case builds on the writing-revision and image-editing workflows in the existing
application. Both workflows can produce concrete artifact states or alternative outputs, but the original implementation
does not provide a dedicated interaction for reviewing complete candidates side by side before deciding which one
to retain. We therefore extend the system with a Compare Viewer, which presents multiple completed artifact states,
preserves their identities, and allows users to select a preferred result with optional feedback. We guided both systems
with natural-language prompts addressing equivalent functional requirements, such as “add a viewer for comparing
and selecting completed candidates” and, during iterative testing, “fix the viewer not restoring the saved selection
after reopening.” We formulate two requirements. R1: Adding a new interaction capability introduces the Compare
Viewer as a reusable interaction for reviewing and selecting among completed artifact states. R2: Integrating the
capability into task workflows allows the writing-revision and image-editing workflows to invoke the Compare
Viewer when multiple completed candidates, or an original and edited result, should be compared before proceeding.
Together, they represent two common forms of interaction-flow evolution: introducing a new interaction capability and
incorporating it into existing task workflows.
Compared systems and analysis method. We implement the above requirements in the Inflak-based plugin and the
vibe-coded plugin. We constructed the baseline vibe-coded plugin independently from a minimal GitHub Copilot SDK
chat application, which is also used by the Inflak-based plugin. Following a conventional vibe-coding workflow, we
asked the agent to implement the same user-facing multimodal co-creation capabilities as the Inflak-based plugin.
Both systems are modular and skill-based: Inflak realizes the four-layer orchestration architecture through extensible
plugins, while the vibe-coded plugin organizes interaction behavior through task-oriented skills and shared resources.
To compare how the two systems accommodate capability extension and task integration, we distinguish between
primary (P) and dependent (D) changes. Primary changes directly define the requested interaction capability (R1) or the
policy for invoking it in a task workflow (R2), whereas dependent changes adapt supporting or consuming components
so that the new capability can be exposed and used.

R1. Adding a New Interaction Capability. In Inflak, R1 is fulfilled with a new L3 Compare Viewer skill. The

7.2.2
R2. Integrating the Capability into Task Workflows. After R1, the Compare Viewer is available as an interaction ca-
pability. R2 concerns when existing task workflows should invoke it. In Inflak, this decision is owned by the two relevant
L2 planners. The writing-revision planner routes to the Compare Viewer when multiple complete revision candidates
should be inspected before one is selected. Similarly, the image-editing planner invokes it when multiple completed edits,
or an original and edited artifact, should be compared. The widget registry records the capability and its planner eligibil-
ity, allowing these planners to route to the new L3 interaction without changing its implementation or any other L3 skills.
In VC, the invocation policy is defined together with the interaction specification in compare-viewer.md. The resulting
dependency path is less uniform. The shared web-interaction/SKILL.md reads the Compare Viewer reference to de-
termine and generate the interaction. At the same time, writing-revision/SKILL.md and image-edit/SKILL.md also
directly reference the same Compare Viewer protocol (web-interaction/references/compare-viewer.md) while
still using web-interaction at the same time. Consequently, the task workflows depend on the capability through
both a shared interaction skill and the underlying specification itself. These paths are individually explicit, but the same
capability is reached through different levels of abstraction, making its dependency structure less consistent.
7.3
Findings
The case highlights three differences in how the two skill-based systems accommodate interaction-flow evolution.
Clear and stable responsibilities make the implementation easier to inspect. In Inflak, the mapping from the two
requirements to implementation files is relatively direct. R1 corresponds to one newly introduced L3 skill that owns the
Compare Viewer realization, while R2 is handled by the two L2 planners that decide when the capability should be
invoked. The registry only exposes the capability and its eligibility. This separation makes the implementation relatively
intuitive to inspect. Interaction design, task-specific invocation, and capability registration each have a focused location,
and adding the new capability does not require modifying any existing interaction implementation. VC also retains a
modular skill-oriented file structure, but the extension introduces mixed responsibilities within compare-viewer.md.
As shown in Fig. 9, compare-viewer.md contains the interaction design, the timing to use the interaction, and the
return contract. As a result, developers need to identify and understand intertwined functions from one single file.

Directional dependencies make change propagation easier to trace and contain. The two implementations also differ in
how a newly introduced capability is linked to others. In Inflak, the change follows a relatively explicit path: the new
interaction capability is defined at L3, registered as an available capability, and consumed by the relevant L2 planners.
This provides a direct trace from introducing the capability to the task workflows affected by it. In VC, the Compare

while also directly reading the underlying compare-viewer.md protocol. A change to the shared specification may
therefore affect components that consume it directly as well as components that interpret it through web-interaction.
These dependencies remain traceable, but determining the propagation of a change requires understanding which parts
of the specification are consumed through each path rather than following a single dependency chain.
Modularity with stable responsibility boundary and clear dependency definition facilitate later maintenance and reuse.
The two features introduced above not only benefit developers’ understanding but also make future change or reuse
easier. Both systems begin with modular, skill-oriented file structures, but the case illustrates how those boundaries
evolve when a new cross-task interaction is introduced. In Inflak, the Compare Viewer remains an independent
L3 capability, while existing L3 interactions remain unchanged. Subsequently, new planners can reuse it through
registration and routing without modifying its implementation. Its interaction logic can therefore evolve separately
from the task-specific conditions under which it is invoked. In VC, reuse is also possible, but the mixed responsibility of
compare-viewer.md and the coexistence of direct and mediated dependencies create additional coordination points. For
example, introducing the Compare Viewer into another workflow may require deciding whether the new task should
directly adopt the shared protocol, rely on web-interaction, or both. Updating the criteria to invoke the skill may
also modify a file that defines interaction design and return behavior. It therefore suggests that explicit responsibility
boundaries and well-defined dependencies can help keep a single module more focused and independent for subsequent
modification and reuse.
8
Discussion
We further reflect on the design choices and practical use of Inflak, and discuss opportunities for extending its
orchestration capabilities in future human-agent systems.
8.1
Reflection on Designing Inflak
The key idea behind Inflak is to treat orchestrating interaction as a progressive resolution process with four layers.
This design facilitates the dynamic and in-situ characteristics of human-agent interaction through disentangling multiple
factors to consider for initiating interactions. As illustrated in Sec. 3.2, based on a well-designed interaction model,
we decompose the orchestration problem into three sub-problems: collecting contextual information to decide the
current task, deciding whether to interact and what the interaction target is, and designing detailed interaction forms.
Through decomposing them, agents can have greater flexibility to decide what the final interaction would be, without
prematurely binding to a specific interaction format at the design time. For example, under both image editing and
generation tasks, the agent can dynamically select and apply sketch pads or canvas editors according to the specific
scenario (Sec. 7). The flexibility is hard to be achieved by specifying all combinations following an end-to-end manner,
as the number of combinations can reach the multiplication of agent tasks, interaction needs, and specific interaction
formats. Another benefit led by the progressive resolution is to lower the burden for developers to maintain. In our
structure, agents are scaffolded to make decisions step-by-step. As a result, it is easier to monitor and diagnose which
Manuscript submitted to ACM


24
Lin Gao, Li Chen, Jianxun Lian, Ji Li, and Haotian Li
layer can be problematic. And the fix can be applied only to a specific instance of the layer, without touching other
instances. The diagnosis and fix can be more challenging when an end-to-end interaction is triggered.
After deciding the usage of progressive orchestration approach with a layered structure, it is crucial to decide
how many layers and what layers are responsible for. Our final four-layer structure reflects a trade-off between
efficiency and composability. Fewer layers can simplify the structure and reduce the time to finish one pathway, but
also making it difficult to distinguish where routing, task reasoning, interaction design, and realization decisions
originate, leading to low composability. Conversely, decomposing orchestration into many small stages would make
individual responsibilities precise at the cost of greater coordination overhead. Based on these considerations, we finally
decided to adopt the four-layer structure as a balance point. It allows us to separate collecting context information and
deciding tasks (L1 Router), identifying interaction targets and goals (L2 Planner), making detailed interaction design
(L3 Designer), and interaction widget implementation (L4 Renderer) into composable instances in layers. L1 and L2
distinguishes responsibility of information gathering, task decision, and interaction need judgment. If merging L1 and
L2, adding a new task would require re-implementing the entire L1’s information collection function. Furthermore, task
selection will be left to the main agent without clear guidance. L2 and L3 separates interaction goals and targets from
the detailed formats. If merging L2 and L3, the entanglement will lead to less flexibility to re-use interaction formats for
different tasks. L3 and L4 provide a clear boundary between design and implementation for maintainability. If merging
L3 and L4, transferring one Inflak plugin to another environment, such as switching from pure JavaScript-based to
Vue-based web applications, would require significant changes in all L3 instances. Our gallery in Sec. 5 verifies that
the four-layer structure is generally applicable and facilitates composing different interactions together. Our technical
evaluation (Sec. 6) shows that our layers can be processed at a reasonable time cost, which can be reduced through
further optimization (see more discussion in Sec. 8.3).
8.2
Usage of Inflak
We envision Inflak primarily for agent developers and interaction designers who need to explicitly organize human
participation within agent systems. It can be used when orchestrating human-agent interaction for a new task, such as
the case in Sec. 4.2. It is also possible to extend an existing agent with richer and more context-sensitive interactive
capabilities (see Sec. 7). We also envision that it provides a general solution to restructuring an existing agent workflow
whose interaction logic has gradually become distributed across prompts, skills, and interface components for easier
modification and extension. Our examples in Sec. 5 demonstrate this potential. We implemented interaction paradigms,
which were originally created by different author teams, with Inflak universally. Other than developers, Inflak can
possibly serve as a common infrastructure for studying and testing new interaction design between humans and agents,
as it requires little programming knowledge and low cost to update designs iteratively. Furthermore, end users can use
Inflak to achieve transferable interaction orchestration between different agents for the same interactive experience.
Our current implementation implements Inflak as a skill-based agent extension. One benefit of this representation is
that layer ownership does not impose a fixed granularity on individual instances. An L2 skill may cover a complete task
such as image generation, or be decomposed into narrower planners for layout, style, or other concerns. Similarly, an
L3 skill may represent an atomic interaction or a richer composition of related interaction mechanisms. These choices
shift where orchestration complexity is managed. Broader instances keep more related knowledge and coordination
locally within one skill, whereas finer instances expose capabilities more independently for modification and reuse,
while requiring more coordination across skills. Natural-language skills accommodate both forms because they can
flexibly package different amounts of task knowledge, policies, and constraints. Their self-contained form also allows

Inflak to be packaged as an agent extension without modifying the host agent’s core logic, suggesting opportunities for
relatively lightweight reuse across compatible agent systems.
Beyond the granularity of each layer, agents’ autonomy of implementing interaction designs can also be controlled
when using Inflak. Our current implementation primarily generates UI with L4 Renderer based on natural-language
interaction specifications and structured contracts produced by L3 Designer. We aim to preserve some visual design
choices to be made by agents to enhance flexibility, leveraging their UI generation capability [4, 10, 15]. However,
this is not the only choice provided by Inflak. When widget consistency and reliability are prioritized, a predefined
HTML/JavaScript/CSS template can be defined with L3 to fill in and L4 to render. A descriptive specification, like most
of our L3 instances (see Fig. 4 for example), can leave visual and interaction details to runtime generation. Minimal
specification with no specific design constraints can give the agent broader freedom for unforeseen interaction needs.
This suggests that our method can be adapted to suit different scenarios with adjusting the autonomy level of agents.
Finally, other than skill-based plugins, layer responsibilities could also be implemented through other methods. For
example, each layer could be assigned to a specialized agent, with information passed between these agents through
explicit handoffs [28]. In this design, the modular unit would shift from an individual skill specification to an independent
agent responsible for a particular layer. Each agent could maintain its own context and reasoning process to take the
corresponding responsibility.
8.3
Future Work
Inflak currently resolves orchestration primarily around the next interaction or execution requirement. More complex
tasks may expose several gaps simultaneously or require multiple steps to be anticipated before execution can proceed.
Supporting such cases would require L2 Planner to reason not only about the next gap, but also about the dependencies
among multiple gaps and the sub-workflows needed to resolve them. This in turn raises a corresponding interaction-
design problem at L3: multiple interaction requirements may need to be presented sequentially, in parallel, or through
nested or composite widgets within a single generation. Different compositions can substantially change what users see
at once, the order in which they provide information, and how one interaction constrains or reveals the next. Extending
Inflak toward such multi-step orchestration therefore requires jointly reasoning about workflow structure and the
composition of the interactions through which that workflow is exposed to users.
As orchestration accumulates across more tasks and interaction episodes, the resulting traces may also become a
source of reusable orchestration knowledge. Inflak currently carries prior interaction and execution history forward as
part of the runtime context, but does not explicitly abstract recurring patterns from this experience. Such traces could be
used to derive lightweight user preferences when useful, but more importantly, they may reveal recurring relationships
between task states, interaction needs, selected interaction mechanisms, and subsequent outcomes. Distilling these
regularities into reusable knowledge could allow planners and interaction designers to draw on patterns learned from
prior orchestration rather than relying entirely on manually authored policies. Over time, this may support a more
evolving form of Inflak in which successful interaction patterns can be identified, generalized, and incorporated into
future orchestration. This raises broader questions about how interaction traces should be abstracted into knowledge,
how such knowledge should be represented and retrieved, and when newly distilled patterns should be incorporated
into existing planning and interaction capabilities.
These extensions also make the efficiency of orchestration an important practical consideration. Our technical
evaluation shows that latency varies across host models and resolution pathways, with L4 contributing a substantial
portion of the overall runtime. Overall, however, the observed cost remains acceptable for the orchestration process

previously established interaction structures, or executing Inflak asynchronously with a sub-agent.
9
Conclusion
Dynamic and in-situ interaction facilitates smooth and productive collaboration between humans and AI agents. This
paper presents Inflak, a unified orchestration architecture to coordinate human-agent interaction with general applica-
bility, runtime flexibility, module composability, and maintainability. It applies a progressive resolution mechanism to
decide when and how agents should interact with humans through instances of four different layers: router, planner,
designer, and renderer. We implement the Inflak architecture as skill-based plugins to agents since they are both
agent-native and composable. Inflak is evaluated through application galleries, technical measurement of latency and
layer compliance, and a case study comparing adding new interactions to an Inflak-based plugin and a loosely structured
plugin. These evaluation results demonstrate Inflak can effectively meet the four requirements. Looking ahead, Inflak
can be further augmented by introducing multi-step planning, adapting to user preferences through self-evolving skills,
and improving its runtime efficiency with caching and reusing.
