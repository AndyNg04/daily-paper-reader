## Abstract 

Modern conversational information access systems continuously ex-tract user information from conversations to build user profiles for personalized retrieval. As user profiles accumulate over time, they inevitably become noisy, making effective user profile denoising a fundamental challenge. Existing personalized conversational query reformulation methods rely on the black-box reasoning capability of LLMs to expand the original query with relevant user profile phrases, producing a verbose query for retrieval. Such rewrite-then-retrieve pipelines reduce user profile denoising to the explicit selection of profile phrases in the sparse token space, separating per-sonalization from downstream relevance modeling. Consequently, they often fail to identify user information that is truly beneficial for retrieval. To enable retrieval-aware user profile denoising, we propose Personalized Conversational Dense Retrieval (PCDR), which learns to jointly project the conversation history and user profile into a latent embedding space dedicated to retrieval. By inheriting the context denoising capability from conversational dense retrievers, PCDR requires only a handful of personalized relevance annotations for training. We evaluate PCDR on the iKAT 2026 tasks, where it serves as the core retrieval component of a conversational AI agent assisting users with complex information needs.

## 1 Introduction 

Conversational Search systems resolve a user’s information need through multiple turns of natural-language interaction [17, 63]. Personalized Conversational Search systems additionally condition conversational retrieval on a profile of persistent facts about the user. The TREC Interactive Knowledge Assistance Track (iKAT) [5] targets this problem by providing human-curated information-seeking conversations accompanied by user profiles consisting of natural-language statements. This year, iKAT 2026 introduced an interactive task that requires the participating retrieval system to interact with the same simu-lated user [51] across multiple conversation sessions. Submitted systems should continuously extract new persistent user facts and append them to the profile throughout these sequential interactions. The profile therefore grows monotonically as the dialogue unfolds. This accumulation comes at a cost. Long-term memory mecha-nisms for conversational agents are typically designed to add new information more readily than they consolidate or remove it [52, 66]. Over extended interactions, the profile becomes long and accumu-lates statements that are only loosely related to any individual arXiv:2610.17673v1 [cs.IR] 13 Oct 2026 Hui et al. 

question. The resulting profile is informative but noisy: informa-tion that is decisive for one question may distract retrieval for the next, and the relevant profile statements cannot be determined in advance. This problem is amplified by the prevailing approach for exploit-ing user profiles: Personalized Conversational Query Reformulation (PCQR) [14, 15, 20, 30, 40, 48]. Given the full conversation history and the user profile, PCQR employs Large Language Models (LLMs) to generate a personalized and de-contextualized self-contained query to submit to off-the-shelf ad-hoc retrievers. However, pre-vious studies [20, 40] showed that this process can cause over-personalization query drift, where LLMs incorporate weakly related profile phrases into the rewritten query. As profiles grow through continued interaction, this problem becomes increasingly severe. We argue that this limitation arises from the intermediate rewrit-ten query. First, personalization must be verbalized through explicit profile phrase injection in the discrete token space, which cannot fully express implicit, retrieval-relevant meanings. For example, a user’s interest in technology may imply science fiction when search-ing for books or futuristic when searching for clothing. Second, queries generated by zero-shot LLMs are not directly optimized for retrieval. Even when the selected profile phrases are relevant, inserting them into the query does not necessarily produce a good search query. To overcome these limitations, we propose Personalized Con-versational Dense Retrieval (PCDR) , which performs retrieval-aware user profile denoising directly in the dense retriever’s latent embedding space. PCDR jointly encodes the conversation history and user profile into a single query embedding, allowing implicit personal information to influence retrieval without being explicitly verbalized in a rewritten query. Trained with a small number of per-sonalized relevance judgments from the iKAT 2023–2025 datasets, PCDR learns to condition the encoding of the contextual dense embedding only on the relevant parts of the user profile that are also useful for search. This can be viewed as an implicit user profile denoising process that is optimized directly for the retrieval task. We further distill knowledge from personalized human rewrites to stabilize training. Figure 2 illustrates the two-stage continual train-ing that produces PCDR from a base Qwen3 0.6B embedding model. Visualization analysis illustrates that PCDR focuses on fewer but more essential profile signals than explicit profile phrase selection. We evaluate PCDR by incorporating it in a search system par-ticipating in the online interactive track of iKAT 2026. The results show that for complex real-world information needs, PCDR alone produces effective personalized retrieval results, while combining it with heterogeneous retrievers provides further improvements. 

## 2 Related Work 

Conversational Dense Retrieval. Conversational search aims at resolving context-dependent utterances against a long and noisy dialogue history [41]. Instead of rewriting the utterance into a self-contained query [34, 39, 42], conversational dense retrieval (CDR) encodes the whole session into a single query embedding, learning to denoise the conversation in latent space and to keep only the context that reveals the current search intent [29, 53, 62]. PCDR is continually fine-tuned from a CDR checkpoint, so that it inherits the ability to denoise a long conversational context and can apply it to the user profile, preventing the profile from overloading the search intent with irrelevant information. 

Personalized Dense Retrieval. A similar idea is widely used in personalized dense retrieval, where various forms of user informa-tion are jointly encoded with the query: latent or ID-based user em-beddings [3, 4, 7, 10], categorical profile features [19, 65], behavioral histories such as past queries, clicks, and purchases [8, 21, 22, 28, 64], and structured textual constraints [59]. The retrieval targets range from products and videos to agent skills. Instruction-following re-trievers have also been studied with long-form personalized instruc-tions [49, 60]. In these tasks, although complicated, the information need is still clearly stated by the instructions, not demanding as much reasoning effort as inferring the search intent implied by a stand-alone user profile. None of these works conditions large-scale web passage retrieval on a persistent, unstructured natural-language profile of a specific user together with that user’s conversational history. Such natural human–agent interactions are noisier, and their personal intents are often only implied by the interactions of phrasing nuances in both profiles and dialogues, which makes dense retrieval considerably harder. 

Personalized Conversational Information Retrieval. Person-alized conversational information retrieval (PCIR) studies exactly this setting [1, 5]. Existing systems mostly follow the Personal-ized Conversational Query Reformulation (PCQR) paradigm: they rely on the implicit incorporation of profile statements based on the parametric knowledge of LLMs to produce a plausibly per-sonalized search query, then pass it to off-the-shelf retrievers and rerankers [14, 15, 20, 30, 40, 48]. Since such LLM-based user profile denoising that is not trained in favor of retrieval can be imper-fect [14], PCDR instead trains a retrieval model to denoise the user profile directly. ## 3 Task Formulation 

We address personalized conversational search over a fixed passage corpus C. A conversation proceeds over turns 𝑡 = 1, 2, . . . ; at turn 𝑡 

the user issues an utterance 𝑢 𝑡 whose information need may depend on the dialogue history 𝐻 𝑡 = (𝑢 1, 𝑟 1, . . . , 𝑢 𝑡 −1, 𝑟 𝑡 −1), where 𝑟 𝑖 is the system response at turn 𝑖 . The user is characterized by a profile 

𝑃 𝑡 = {𝑝 1, . . . , 𝑝 𝑚 𝑡 }, a set of natural-language statements about the user, for instance “ I am vegetarian ”. Appendix A shows an example of a conversation and its user profile. Given (𝑢 𝑡 , 𝐻 𝑡 , 𝑃 𝑡 ), the system returns a ranking of passages from C that satisfy the information need behind 𝑢 𝑡 and are consistent with the profile 𝑃 𝑡 , and then generates a response 𝑟 𝑡 grounded in the top-ranked passages. The profile is dynamic in the interactive setting: it is not supplied in advance but accumulated online. After turn 𝑡 , new durable facts inferred from (𝑢 𝑡 , 𝑟 𝑡 ) are appended, so 𝑃 𝑡 ⊆ 𝑃 𝑡 +1 and |𝑃 𝑡 | grows monotonically across turns and across a user’s successive sessions. In the offline training and validation setting of Sections 4 and 5, the profile is instead the fixed, human-annotated user profile of the conversation. 

## 4 Method 4.1 Overview 

Following existing practice in CDR [29, 35, 44, 45, 62], only the query side of the PCDR dual encoder is fine-tuned, while the docu-ment encoder is kept frozen. More specifically, a query encoder 𝑓 𝜃 

encodes the current utterance together with the dialogue history and the user profile into a single vector 𝑞 = 𝑓 𝜃 (𝑢 𝑡 , 𝐻 𝑡 , 𝑃 𝑡 ), and pas-sages are ranked by the cosine similarity cos (𝑞, 𝑑 ) between 𝑞 and their frozen embeddings; only 𝜃 is trained. Unlike the reformulate-then-retrieve pipelines of our previous systems [20, 40], PCDR forms no intermediate rewritten query and consumes the conver-sation and the user profile directly. We initialize 𝑓 𝜃 from a conver-sational backbone, conv-Qwen3, which is described in Section 4.3. Section 4.4 describes how the query is constructed from the conver-sation and the user profile, and Section 4.5 presents the composite training objective, which distills a personalized human rewrite into the conversational query. The encoder produced by this recipe is PCDR. This section and Section 5 concern training and offline eval-uation, where the profile is fixed and human-annotated; Section 6 describes how PCDR is deployed in the interactive task, where the profile is accumulated turn by turn. 

## 4.2 Training Data 

Having outlined the model, we now describe the data it is trained and evaluated on. PCDR is trained and validated entirely on 

previous-year iKAT data and tested online on the iKAT 2026 simulated users, as reported in Section 7; no 2026 relevance labels are used in training. 

iKAT 2023–2025. We use the graded relevance judgments of the TREC Interactive Knowledge Assistance Track (iKAT) [5] 2023– 2025, a personalized conversational benchmark over the ClueWeb22-B web corpus [50]. Each conversation is paired with a user profile as defined in Section 3. Each turn provides the context-dependent utterance 𝑢 𝑡 , a human oracle rewrite that resolves it into a self-contained query and is used only as a distillation teacher in Sec-tion 4.5, and, for the relevant turns, human annotations of which profile statements are relevant. Passage relevance is graded on a 0–4 scale. We use all 324 turns that have relevance judgments: 176 from 2023, 103 from 2024, and 45 from 2025. 

TopiOCQA. To obtain a conversational backbone we fine-tune on TopiOCQA [2], an open-domain conversational passage-retrieval dataset over Wikipedia with topic shifts, which contains about 45K history-aware query–passage pairs. 

Splits. We split the iKAT judged turns by conversation with a 9:1 ratio, stratified by year, into 280 training and 44 held-out turns, and report NDCG@3 on the held-out turns under full-corpus retrieval over the 116M-passage ClueWeb22-B index. Each training turn carries on average ∼177 graded candidate passages. 

## 4.3 Conversational Backbone: conv-Qwen3 

We first fine-tune base-Qwen3-Embedding [54], a 0 .6B general-purpose embedding model, on TopiOCQA to obtain a CDR model, conv-Qwen3, which serves both as a strong zero-shot baseline and as the initialization for personalized fine-tuning. The fine-tuning recipe and the criterion for selecting the backbone checkpoint are given in Section 4.6. 

## 4.4 Query Construction 

Following the Qwen3-Embedding protocol [54], a query is an instruction-prefixed string. The instruction is placed on the query side only, and documents are encoded without instruction. We consider three forms: 

• full-profile : the instruction “ Given a conversation between a user and an AI assistant and the user’s profile, retrieve pas-sages that answer the user’s last question in a way consistent with the user’s profile ”, followed by the entire profile and the conversation history ending in the current question. 

• relevant-profile : identical, but the profile contains only the human-annotated relevant profile statements, an oracle profile selection. 

• oracle rewrite , used only as the teacher: the ad-hoc instruc-tion “ Given a web search query, retrieve relevant passages that answer the query ” followed by the human oracle rewrite.

## 4.6 Implementation Details 

conv-Qwen3 fine-tuning. We fine-tune base-Qwen3-Embedding on TopiOCQA with an InfoNCE [58] contrastive loss with a tempera-ture of 0 .01, cross-GPU in-batch negatives, and false-negative mask-ing, a batch size of 480 over four GPUs, a constant learning rate 1e −5with 6% warmup, 20 epochs, and fp32 master weights. Checkpoint se-lection: we evaluate every epoch on the out-of-domain QReCC con-versational benchmark and select the peak epoch, epoch 1, whose NDCG@10 of 54 .6 exceeds the 52 .5 of the zero-shot base model; later epochs monotonically forget, so the backbone is early-stopped at its conversational peak. 

Personalized fine-tuning. We train the query encoder with the objective of Section 4.5 for up to 30 epochs, batch size 16, constant learning rate 5e −6, bf16 with fp32 master weights, keeping all judged grade-0 docs as negatives plus 𝐾 =2048 global negatives; default weights 𝑤 𝑔 =1, 𝑤 𝑘 =2, 𝑤 𝑎 =1. Whether to use LoRA [18] or full fine-tuning is decided empirically in Section 4.7.

## 6 Submitted Runs 

The interactive task evaluates a complete conversational system on-line, through the iKAT user-simulation API (Sim.API): at each turn the system receives the simulated user’s utterance, ranks passages from ClueWeb22-B, and returns a generated response. A retriever alone is therefore not enough, and, unlike the offline evaluation of Section 5, the profile is not given but accumulated on the fly. Each run wraps PCDR in a common per-turn pipeline: a gpt-5-mini model at low reasoning effort extracts new durable facts about the user from the latest exchange and adds them to the running profile that PCDR encodes; PCDR ranks passages, optionally fused with a second retriever by Reciprocal Rank Fusion (RRF) [13] and optionally reranked; and the same model generates the response from the top five passages. Run 5: fusion with a learned sparse retriever. We fuse PCDR with SPLADE-v3 [27], a learned sparse retriever, by RRF and with-out reranking. SPLADE-v3 is driven by a de-contextualized, non-personalized reformulation of the current question, contributing profile-free lexical evidence that complements the personalized dense ranking. As in the preceding runs, we omit reranking here: when the fused pool is already strong, our 2024 experience [20] indicates that a reranker brings little benefit and can even harm the ordering. 

Run 4: fusion with a lexical retriever and reranking. We fuse PCDR with BM25 [55] by RRF and rerank the top 50 fused passages with RankLLaMA [32]; BM25 is given a personalized reformulation of the question. As the lexical retriever is the weakest of the three fusion partners, we reinstate a reranking stage to consolidate the final ranking.

An end-to-end, rewrite-free configuration. The PCDR + CDR run is fully rewrite-free: both legs are dense and encode the conver-sation and profile directly, so the entire pipeline consumes only the full conversation and the user profile, with no LLM query rewriting anywhere. It is the most genuinely end-to-end of the four runs and removes the latency and cost of an LLM rewriting step, and it remains competitive on all three families of metrics. This shows that the reformulate-then-retrieve stage can be dropped entirely without collapsing quality. 

Response quality is decoupled from retrieval. The response-quality scores do not track the retrieval scores. PCDR alone has the lowest retrieval score yet obtains the highest response quality at both the per-turn and the dialogue level, while the fused runs with stronger retrieval score lower on both. Since every run generates its response from the same top passages with the same model, a better passage ranking does not translate into a better judged response here. We do not have an explanation for this inversion and leave it to future work. 

Mixed initiative. Mixed-initiative strategies are our weakest di-alogue dimension. This is expected, as our pipeline answers each question directly and we did not build an explicit mixed-initiative mechanism such as asking clarifying questions or proactively sug-gesting follow-ups [6]. The low scores reflect the absence of that mechanism rather than a retrieval deficiency. 

What we cannot yet conclude. Three factors limit the analysis. First, other teams’ submissions were not made available to us, so we can read only within-system contrasts and cannot place our results against the field. Second, a per-user-type analysis is not meaningful here, because the variants cover different and unequal subsets of the conversations, so averages per variant are confounded with topic difficulty; only six conversations are run with all four variants, which is too few for a controlled comparison. Third, the organizers do not disclose which user characteristics the four variants are meant to distinguish, which further prevents us from interpreting robustness across variants as intended. ## 8 Visualization: What the Dense Encoder Attends To 

To make concrete the claim that PCDR denoises a long profile in-side the representation, we visualize which input tokens most influ-ence its query embedding. We use the generic attention-relevancy method of Chefer et al. [11], which attributes a model output back to input tokens by aggregating attention maps weighted by their gra-dients across layers; a higher relevancy means a token contributes more to the retrieval embedding. Figure 3 applies it to a representa-tive personalized turn from iKAT 2024. The input consists of the instruction, a 13-statement user profile, and a one-turn conversa-tion ending in the question “ Is it suitable for me? ”. Only profile statements 1, about makeup, and 5, about dry skin, are annotated as relevant; they are marked with ⊲ in the figure, and the antecedent of the pronoun is boxed. The figure shows two behaviours that a dense encoder can per-form but a bag-of-words query cannot. It attenuates the irrelevant part of the profile: of the thirteen statements, relevancy concen-trates on the skin-related ones and on the current question, namely the discriminative tokens dry skin and the topically related Mac primer , Clinique , and CeraVe , while statements about travel, work, or water intake receive little. And it resolves conversational con-text, linking the pronoun “ it ” in the question to “ double cleansing ”introduced one turn earlier, without an explicit rewriting step. The contrast with query reformulation is instructive. For the same turn, the personalized LLM rewrite our pipeline produces is 

“Is double cleansing suitable for someone who wears makeup regularly and is looking for dry skin solu-tions?” 

To personalize, the rewrite must verbalize the selected profile facts as additional query text, which lengthens the query and, when the profile is long, dilutes the discriminative terms among many others [9, 26]. PCDR instead keeps the entire profile as input but internally attends to only the few relevant tokens shown in Figure 3, performing the same selection inside the representation rather than by editing text. The denoising happens in embedding space, which is exactly where dense retrieval is robust to verbosity and where reformulation is not. 

## 9 Conclusion 

In this paper, we tackle the problem of over-personalization caused by the excessive integration of user profile terms in existing person-alized conversational query reformulation. We propose to perform user profile denoising in a latent semantic space, optimized di-rectly for retrieval performance. In this way, more precise user information is integrated into the latent representation of the con-versational information need to enhance search. Specifically, we train PCDR, which performs retrieval-aware user profile denoising directly in the dense retriever’s embedding space. Initialized from a conversational dense retriever, PCDR requires only a small set of previous-year iKAT relevance judgments, augmented by light distillation from personalized human-rewrite embeddings. Online evaluation on the iKAT 2026 interactive runs shows that PCDR alone can produce satisfying tailored search results, and combining it with heterogeneous retrievers yields further improvements. Our visualization analysis further illustrates that the profile denoising goes beyond shallow semantic relevance. Future work includes removing the reliance on distillation from human query rewrites, so that PCDR is trained from relevance signals alone and no longer needs rewritten queries at any stage. It also includes scaling training with synthesized end-to-end personalized conversational retrieval datasets and studying continual adaptation from ad-hoc search to conversational search and ultimately personalized conversational search.

## A Sample Conversation and User Profile 

Figure 4 shows a judged training turn from iKAT 2024, the sec-ond turn of the conversation “Traveling to Egypt”. The user profile contains 21 statements, of which the annotators mark only state-ment 12 as relevant to the current question. The question “ Oh, do I need a visa? ” depends on both sources of context. The dialogue history establishes that the visa is for Egypt, and the profile implies, without stating it, that the user is an American citizen, which deter-mines whether a visa is required. The human oracle rewrite makes both pieces of information explicit. PCDR receives the instruction, the full profile, and the conversation as a single string, as described in Section 4.4, and the oracle rewrite is used only as the distillation teacher of Section 4.5. 

## B Is PCDR Better than PCQR? An Inconclusive Study 

Our motivation for PCDR is that dense encoding should be more robust than Personalized Conversational Query Reformulation (PCQR). We ran a controlled experiment to test this directly, but the held-out set turned out to be too small to draw a statistically reli-able conclusion. We report it here for completeness and to motivate future work. 

Setup. We fix the retriever to the raw, un-fine-tuned base-Qwen3-Embedding index and vary only how the query is built. For PCQR, a rewriter reads the full conversation and the full user profile and pro-duces a self-contained personalized query, which is then encoded with the same ad-hoc instruction template as our other Qwen3 rows; we use the minimal MQ4CS prompt listed in Appendix C at temperature 0. We sweep the rewriter across the open-weight Qwen3 model sizes of 0 .6B, 1 .7B, 4B, and 32B, the frontier model gpt-4o, and the human oracle rewrite. PCDR instead encodes the conversation and the full user profile directly, with no generative call. All rows are evaluated on the same 44 held-out turns with full-corpus retrieval and NDCG@3. To score all rewrites in a sin-gle pass over the corpus, the rewriter rows use exact search over int8-quantized document embeddings, whereas PCDR is evaluated with the full-precision index of Section 5. The quantization changes scores only slightly: the human oracle rewrite obtains 36 .7 on the int8 index and 36 .3 on the full-precision index, the latter being the upper bound reported in Table 3. 

Significance testing. For each rewriter we compare its per-turn NDCG@3 against PCDR with a paired Wilcoxon signed-rank test over the 44 turns, and apply a Bonferroni correction for the six comparisons, giving a threshold of 𝛼 = 0.05 /6 ≈ 0.0083.

For reference, the same raw encoder scores 12 .9 on the direct full-profile query and 29 .0 after conversa-tional fine-tuning. Only the same-size 0 .6B rewriter is significantly worse than PCDR. In other words, on this data we can neither conclude that PCDR beats PCQR nor the re-verse: PCDR is statistically indistinguishable from strong rewriters and from the human oracle, while a rewriter of the same size as the PCDR encoder is clearly worse. The point estimates suggest the reformulate-then-retrieve pipeline needs a rewriter roughly an order of magnitude larger to match direct encoding, and pays an extra generative call per turn, but with 44 queries the test is underpowered and we do not claim this as a finding. 

Future work. A conclusive comparison needs far more personal-ized relevance judgments than the iKAT held-out split provides. A promising direction is to train PCDR on a larger synthesized per-sonalized dataset and then compare PCDR against PCQR across all iKAT test collections from 2023 to 2025 at once, where the combined query set would give the statistical power this appendix lacks.

## C.4 Response generation 

The retrieval-augmented response is generated from the top-ranked passages with the following prompt. 

# Task Description: You are a helpful, knowledgeable assistant talking with the user in an ongoing conversation. You are given the user's profile (PTKB) and your Search Results for their last question. Write a reply to the user's last question that, above all, SOUNDS NATURAL -- like a real person speaking, not a report, a database export, or a list. Follow ALL of these: a. Natural, conversational tone (THE MOST IMPORTANT CRITERION): Write in flowing, warm, human prose. Lead with a direct, helpful answer, then weave the relevant details into sentences. Do NOT produce long structured checklists, multi-section plans, day-by-day schedules, printable templates, or exhaustive bulleted/grocery lists -- EVEN IF the user explicitly asks for one, answer conversationally with the couple of most useful points (a concrete example or two is fine) and keep it brief. It must read like a knowledgeable friend chatting, NOT a document, a template, or a search engine. Answer DIRECTLY, as if you simply know the information -- do NOT keep announcing where it came from. An occasional light "from what I found" is fine, but do NOT overuse it, and NEVER say things like "the search results recommend", "the material I reviewed", " the sources say", "ideas found:", "I found them on Amazon", or "the trail picks I saw", and never use the words "passage", "passages", "reference passage(s)", or "the provided passages/documents/sources". Do not number or cite sources inline, and do not copy text verbatim. b. Grounded: Base your answer ONLY on the information in your search results -- no outside knowledge, no invented or assumed facts. If your search didn't cover something the user asked, just say so briefly and naturally rather than guessing. c. Answer the actual question: Directly answer what the user LITERALLY asked -- if they ask for specific things (a particular sport, a product name, a number, a recommendation), give concrete specifics rather than only offering to find them. Include the key relevant facts. But do NOT repeat what you already said in earlier turns -- build on it or add something new; if the user re-asks or the conversation circles back, briefly acknowledge what you covered and add new information rather than restating it. d. Personalized: Tailor the answer using ONLY the profile facts relevant to this question; ignore the irrelevant ones and never force-fit the profile. e. Length: Keep it brief and conversational -- usually ~120-180 words ( a short chat reply), and never exceeding ~250 words. A concise, on-point answer is better than a long one. ===TAIL_INSTRUCTION=== Now, please reply to the user's **Last Question** under the **Dialog Context**, considering the **User Profile** and using your **Search Results**. The output format should always be: Response: $Response Go ahead!
