## 摘要
图形用户界面（GUI）智能体如今能够在真实应用程序中执行工作流，但当执行过程偏离预期时，用户必须判断哪些内容发生了变化、哪些内容本应保持不变，以及哪些内容仍可恢复。以计划为中心的界面让用户监督操作流程，但用户真正需要应对的是应用程序状态的变化。我们提出任务状态治理这一交互范式，将任务表示为一份可编辑的契约，其中关联了期望结果、必须保留的事实以及观测到的应用程序状态。我们在 TaskVM 中实现了这一范式：它将实时状态映射为可编辑的任务控件，将用户编辑作为真实的界面操作执行，通过独立观测验证结果，并将每项操作标记为可逆、可补偿或不可逆。在自动化契约基准测试、受控用户研究和开放式实时模型探索中，该范式提升了契约遵循度，以及用户对恢复过程的控制感和信任度，同时保持执行结果不变。任务契约为可治理的智能体界面开辟了新的设计空间。

## Abstract
Graphical user interface (GUI) agents now execute workflows across real applications, but when execution drifts, users must determine what changed, what should have remained untouched, and what can still be recovered. Plan-centric interfaces leave users supervising procedure, but users live with changes to application state. We introduce task-state governance, an interaction paradigm that represents a task as an editable contract linking desired outcomes, facts that must be preserved, and observed application state. We instantiate this paradigm in TaskVM, which projects live state into editable task controls, executes user edits as genuine interface actions, verifies outcomes through independent observation, and marks each action as reversible, compensatable, or irreversible. Across an automated contract benchmark, a controlled user study, and an open live-model exploration, the paradigm strengthened contract compliance and users' recovery control and trust, while execution outcomes were held constant. Task contracts open a design space for governable agent interfaces.

## 1. 核心问题与整体含义

### 研究背景与动机
GUI 智能体已经能够跨应用执行点击、输入、编辑、发送消息等操作，但当任务发生偏离时，用户仍难以回答三个问题：

- **哪些变化已经真正发生？**
- **哪些记录或字段本应保持不变？**
- **出错后哪些影响能够撤销，哪些只能补偿，哪些无法恢复？**

现有的对话式或计划式监督界面主要展示“智能体准备做什么、执行到了哪一步”。但**操作步骤执行成功，不等于任务目标已经实现，也不等于没有误改其他数据**。此外，若任务完成与否完全依赖执行智能体的自述，用户容易过度信任系统。

### 核心主张
论文提出 **任务状态治理（Task-State Governance）**：将用户监督的对象从“执行计划”转向“应用状态及其约束”。

一个任务应明确包含：

1. **期望状态**：用户授权系统建立什么结果；
2. **保留范围**：哪些事实或数据不得受到干扰；
3. **观测状态**：应用界面当前实际显示什么。

例如，推迟项目会议时，不仅要更新日历与团队通知，还应明确保护已经确定的机票订单。

**整体意义**：论文不是提出更强的 GUI 操作模型，而是为现有智能体增加一层可检查、可干预、恢复边界明确的治理机制。

## 2. 方法论：核心思想、技术细节与流程

### 2.1 用状态契约描述任务
论文将任务表示为：

\[
T=\langle S_{\text{desired}},S_{\text{preserve}},S_{\text{observed}}\rangle
\]

其中：

- \(S_{\text{desired}}\)：目标字段及其期望值；
- \(S_{\text{preserve}}\)：受保护实体上的不变约束；
- \(S_{\text{observed}}\)：从当前应用界面提取的可见事实。

任务有效完成的条件为：

\[
\mathrm{Valid}(T)
\iff
(S_{\text{observed}}\models S_{\text{desired}})
\land
(S_{\text{observed}}\models S_{\text{preserve}})
\]

即：**目标满足与保护约束满足必须同时成立**。这些公式定义的是完成判定条件，并不意味着系统能够形式化证明整个第三方应用正确。

### 2.2 TaskVM：管理任务义务，而非虚拟化整个应用
TaskVM 是该交互模型的运行时实现。它不是操作系统虚拟机，也不拥有第三方应用的完整状态，更不能保证跨应用原子回滚。

其核心架构包括：

- **状态编译器**：将可见界面信息转为结构化任务变量；
- **任务架构器**：根据用户意图与状态变量生成工作流和动作契约；
- **GUI 执行器**：通过真实界面操作改变外部应用；
- **独立验证器**：根据新获取的界面证据判断目标与保护约束是否满足；
- **内核**：集中维护任务状态、工作流、追加式事件日志、检查点与执行版本；
- **界面投影层**：并列展示“期望—保留—观测”，让用户直接编辑任务目标。

期望状态只能通过治理入口修改，观测状态只能通过同步入口更新，避免把“用户想要的结果”误显示为“已经发生的事实”。

### 2.3 GUI-only 执行与双向绑定
TaskVM 将用户对任务变量的修改编译成语义化的 `ActionContract`，再生成点击、输入、滚动等真实 GUI 动作。

系统强调：

- 模型只能接收用户能在屏幕上看到的信息；
- 禁止使用隐藏数据库键、私有 DOM ID 等内部标识；
- 写操作不能通过后台 API 或数据库修改绕过界面；
- 评测所需的状态读取、环境重置等特权能力与运行时隔离。

一个高层修改可以对应多个应用的联动，例如同时调整任务看板截止日期和聊天通知。

### 2.4 独立验证与非干扰检查
执行器报告“完成”后，任务不会立即结束。验证器需要重新获取可见证据，检查：

- **目标满足**：目标字段是否达到指定值；
- **见证条件**：是否出现了任务要求的执行证据，而非仅凭口头声明；
- **非干扰**：受保护字段是否仍保持原值。

验证器与执行器采用独立调用，不共享内部推理上下文。但它们使用同一基础模型，**架构隔离不等于错误在统计上独立**。

### 2.5 执行中治理与恢复
系统支持暂停、局部修改、整体目标修改、检查点和回滚。

为防止目标修改后旧动作继续执行，TaskVM 使用递增的 **epoch**：

- 用户修改任务后，内核提升 epoch；
- 旧 epoch 生成、尚未派发的动作会被丢弃；
- 已经派发或已经发生的外部影响不会因此自动消失。

恢复能力分为三类：

| 类型 | 含义 | 示例 |
|---|---|---|
| 可逆 | 能通过逆向 GUI 操作恢复 | 撤销勾选、清空未提交草稿 |
| 可补偿 | 不能消除原影响，但可通过后续操作抵消 | 发送更正或取消通知 |
| 不可逆 | 无法可靠恢复原状 | 某些永久删除、已完成结算 |

回滚根据已提交历史生成补偿计划，并预先说明残留影响，而不是承诺虚假的“一键恢复”。

### 2.6 完整流程
一次治理闭环为：

**观察界面 → 抽象状态 → 投影控件 → 用户编辑 → 重组工作流 → GUI 执行 → 独立验证 → 状态协调。**

## 3. 实验设计：场景、基准与对比方法

论文采用三阶段评估，分别考察机器能力、人类交互体验和开放使用。

### 3.1 阶段一：自动化契约基准

#### 场景与 benchmark
作者构建了一个冻结的离线模拟应用基准：

- **12 类任务结构，每类 3 个变体，共 36 个任务实例**；
- 场景涉及办公协作、日历、社交内容、消息传递等；
- 结构包括顺序执行、循环、扇出、部分失败、跨应用、冲突、界面漂移、中断、局部修改、目标修改、不可逆操作和回滚。

主要指标是 **契约结果验证（COV）**，包含 10 类机器可判定谓词，例如：

- 最终目标状态；
- 保护范围不受干扰；
- 所需见证轨迹；
- 最新意图生效、旧意图受到抑制；
- 暂停/停止边界；
- 外部对象所有权保护；
- 可逆恢复；
- 不可逆影响如实保留；
- 不使用隐藏评测器重置掩盖失败。

报告两种汇总指标：

- **严格通过率**：所有适用谓词均通过；
- **原子谓词平均通过率**：适用谓词的平均满足程度。

#### 对比方法
- **TaskVM**：状态契约、多角色调用、独立验证与恢复机制；
- **Direct-CUA**：直接根据截图操作，通过自然语言接收干预；
- **Planner-CUA**：先生成层次化计划，再执行；
- **Template Control**：脚本式检查工具，但存在严重实现缺陷，不能视为有效基线。

各模型条件使用相同基础模型、环境种子与隐藏评测契约。

此外，论文还开展了：

- 程序性技能注入开/关比较；
- 技能开启条件下的非劣效分析；
- **18 个开发期压力变体**，覆盖更复杂的冲突和目标修改。

### 3.2 阶段二：受控用户研究
- **37 名参与者**，被试内、顺序平衡设计；
- 对比 TaskVM 与“应用画面＋对话抽屉”的监督界面；
- 任务库包含 **8 个场景**，每人每种界面完成 3 个任务；
- 场景包括目标切换、混合回滚、外部漂移和跨应用内容变化。

关键设计是采用 **Wizard-of-Oz 分支回放**：

- 两组使用相同的环境事件、智能体轨迹和错误表现；
- 用户自身的干预行为可以不同；
- 因而适合研究界面带来的控制感、信任和交互行为差异，**不能用来证明实时执行能力或真实恢复能力更强**。

测量涵盖恢复控制感、信任、满意度、可用性、NASA-TLX、状态理解、干预成功率、延迟与回滚使用次数。

### 3.3 阶段三：实时模型开放探索
- **14 名回访参与者**；
- 自拟任务、实时模型执行，无对照组；
- 共 **39 个执行 episode、905 次模型调用**；
- 涉及消息、社交动态、视频、音乐、内容社区等 5 类应用界面。

这一阶段没有逐任务标准答案或成功率裁定，主要用于描述实际使用、执行故障与改进需求。

## 6. 主要结论与发现

### 6.1 契约遵循有所改善，但绝对成功率仍有限

| 方法 | 严格通过率 | 原子谓词平均通过率 |
|---|---:|---:|
| TaskVM | **58.3%（21/36）** | **87.0%** |
| Direct-CUA | 50.0%（18/36） | 76.1% |
| Planner-CUA | 47.2%（17/36） | 73.7% |

TaskVM 的严格通过率分别领先 **8.3、11.1 个百分点**。但仍有 15/36 个任务未完全通过；跨应用和不可逆任务族中，所有方法均未取得严格通过。

### 6.2 恢复机制有价值，但可靠性尚未解决
- 可逆恢复谓词：TaskVM **4/6**，两个基线分别为 **0/3、0/5**；
- TaskVM 暂停/停止边界为 **36/36**；
- 压力测试通过 **17/18**，唯一失败仍发生在回滚补偿相关的竞态条件。

说明恢复是重要增益，也是系统最薄弱的环节之一。

### 6.3 用户控制感和信任提升
在受控回放条件下：

- 信任：**5.54 vs 4.36**，\(p=.0030\)；
- 恢复控制感：**5.56 vs 4.63**，\(p=.0050\)；
- 支持满意度：**5.66 vs 4.95**，\(p=.0222\)；
- 回滚使用：TaskVM 中 11 人、17 次；基线中 2 人、4 次。

这些结果支持**用户更愿意使用、也更清楚如何使用恢复控制**，但不等于真实环境中的恢复一定成功。

### 6.4 理解、工作负荷与延迟尚无确定改善
- 过度自信差距从 **25.8 降至 13.2 个百分点**，仅为描述性结果；
- 状态理解探测仅有 8 个有效配对，差异不显著；
- 总工作负荷、可用性、透明度均未达到统计显著；
- 干预延迟中位数为 **85.3 vs 65.7 秒**，差异同样不显著。

### 6.5 非劣效结论需要限定解释
技能开启条件下，TaskVM 相对 Direct-CUA 的 CFE 差异点估计为 **+5.71 个百分点**，单侧 95% 下界为 **−8.57 个百分点**。

这只支持在预设 **10 个百分点容忍界限**下的非劣效，不证明两者等效或 TaskVM 更优；5 和 7.5 个百分点的更严格界限均无定论。

## 7. 优点与亮点

- **交互对象转变明确**：从监督操作过程，转向治理目标、保护范围与真实状态。
- **显式建模副作用边界**：将“不得误改什么”纳入成功标准，而非只看目标完成。
- **分离意图与事实**：编辑期望值不会被错误显示为世界已经改变。
- **验证证据独立获取**：减少执行器自证完成、过早结束的问题。
- **恢复语义诚实**：区分撤销、补偿与不可逆残留，避免虚假安全感。
- **并发治理设计具体**：epoch 机制能阻止目标修改后的陈旧动作继续派发。
- **评测维度较全面**：不仅看最终状态，也检查暂停、意图替换、外部所有权和恢复。
- **证据边界披露较充分**：作者明确区分受控回放、开放探索和真实部署能力，没有将三类证据混为同一种效果证明。

---

## 8. 不足与局限

### 8.1 视觉验证不等于完整系统正确性
- 截图只能确认界面显示，无法严格证明后台持久化、结算完成或跨系统一致性；
- 轮询可能漏掉瞬时变化，因此“前后值相同”不必然证明中间从未被修改；
- 同一模型承担多个角色，仍可能出现相关性误判。

### 8.2 真实部署证据不足
- 实验主要运行于离线模拟应用，数据有限、联系人预设；
- 虽实现 Web、MobileGym、OSWorld 适配器，但没有充分的跨真实平台实证；
- 对生产应用中的权限、网络故障、复杂并发等覆盖有限；
- CAPTCHA、生物识别、窗口遮挡、Canvas 界面和短暂弹窗仍构成障碍。

### 8.3 用户研究存在外推与偏差风险
- 参与者来自单一研究志愿者池，偏年轻、学术背景强、技术素养较高；
- 阶段二的非脚本输入由实验人员引导回规范路径，限制自然使用；
- 两组写入探测的边际通过率相同，但成功者完全不重叠，这一特殊配对结构值得进一步审计，不能仅凭边际相同认定所有交互机会都已等价；
- 阶段三回访者恰好是此前更受益于 TaskVM 的人，存在明显自选择偏差；
- 阶段三没有对照组和任务成功率，不能据此证明工作负荷降低或实时成功率提高。

### 8.4 基准与报告仍有改进空间
- 缺少与强交互式、计划式系统的直接实现比较；
- 技能开启实验缺失较多，不同指标使用不同分析集合；
- 正文与表格中的部分任务分区说明不一致；
- “冻结通过结果不再反转”等规则可能影响稳健性解释，需要完整日志与预先固定的裁定流程支持。

### 8.5 成本与适用范围有限
- 自动化总耗时增加约 2.2～3 倍，尚缺少成本—风险收益分析；
- 用户仍需要判断并表达保护约束，这本身具有认知负担；
- 更适合字段明确、状态离散的生产力任务，不易直接推广到视频编辑、绘画、三维建模等连续创作任务；
- 补偿操作可能留下审计记录、已读消息等残留，不能等同于恢复原世界。

**综合评价**：论文最有价值的贡献，是把“目标、保护边界、证据与恢复限制”变成用户可操作的对象。现有结果支持这一设计方向，并显示控制感与信任收益；但其真实环境可靠性、恢复成功率、成本效益及更广泛人群适用性，仍需要更大规模、对等功能、实时执行的研究验证。

（完）
