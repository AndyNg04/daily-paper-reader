Abstract 

AI coding agents increasingly work inside a harness: rule files such as AGENTS.md , on-demand skills, runtime hooks and automated checks. Most studies of harnesses look at a single point in time or at short benchmark runs. I report a six-week case study of my personal system of record, a plain-markdown repository that three AI agent tools edited daily under one shared rule set. I built a ledger of 118 agent failures, their fixes and whether they came back. I also tested the system’s monthly LLM documentation audit against 47 known stale statements and 20 planted errors. Finally, I replayed five past failures in isolated git clones, with and without their fixes. All results come from one repository with three runs per condition, so I report them as exploratory. Stale documentation ( drift ) was the largest failure class (48 of 118), although 35 of those were found on one audit day. A single audit run found about half of the known drift (Claude Sonnet 5.5 mean: 50 %), and at least 93 % of its findings were correct. On Sonnet 5.5, the agent finished four of the five replayed tasks. In three of those four, the failure did not happen, with or without its fix. Only the stale-count failure came back without its check, and the check stopped it in every run. On older models, an agent drafted an em-dash once while the em-dash lint check was active, and the check rejected it. A written rule on run-time estimates did not change Sonnet 4.5’s overestimates. These results suggest that harness lessons can outlive the failures they were written to fix, while drift persists and still needs mechanical checks. Tools that evolve a harness add lessons faster than they retire them, so they should re-test their rules from time to time and retire the obsolete ones. 

# 1 Introduction 

An AI coding agent does not act on its language model alone. It works inside a harness : the instructions it loads at session start, the skills it loads on demand, the hooks that run around its tool calls, and the checks that run before a commit is accepted [12, 43, 46]. Rule files in the repository, such as AGENTS.md and CLAUDE.md , have become the standard way to give these instructions [1, 26]. Recent studies describe what these files contain [8, 9, 18], how they grow over time [4, 6], and how they affect task cost and completion [13, 24, 48]. Two gaps remain. First, almost all existing studies are cross-sectional: they mine snapshots of open-source repositories or measure single-turn benchmark runs. Galster et al. call for longitudinal and experimental studies of harnesses in daily use [12]. Second, people who maintain a harness respond to agent failures by adding lessons . A lesson is either a prose rule that the model reads or an executable check that the runtime enforces. Recent frameworks automate this loop: Harness 2

keeps a growing library of lessons across tasks [45], and Harness-R1 writes executable harness patches from failure traces [34]. Yet little is known about what happens to a lesson after it enters the harness. Does the failure come back? Is the lesson still needed after the model is upgraded? To answer these questions, I studied one harness in daily use for six weeks. The system is my personal system of record: one git repository of plain markdown files and Python scripts that 1arXiv:2610.32578v1 [cs.SE] 23 Oct 2026 holds my job search, my language learning and my life administration. Three agent runtimes (three different AI agent tools) edit this repository daily under one shared rule set. From the start of the study period, I enforced a logging policy: every repeatable agent failure and its fix had to be recorded with the reason. The commit history and change logs therefore record every harness change made through a commit or a log entry. I investigate three research questions: 

RQ1 Which agent failures occur, which come back after a fix, and what side effects do the fixes have? 

RQ2 How much stale documentation ( drift ) does an automated LLM audit find? 

RQ3 Does a past fix still change agent behaviour when the original failure is replayed, and does this depend on the model version? The paper makes three contributions. First, a ledger of 118 agent failures, coded in two LLM passes whose disagreements I resolved, with daily measurements of how much rule text the harness holds (Section 4). Second, a test of how much drift an LLM documentation audit finds, against an answer key of 47 real stale statements and 20 planted errors. Third, a replay of five past failures in throwaway git clones, with and without their fixes, on several model versions (a 

counterfactual replay ). The results (Section 5) point to one main conclusion: lessons can outlive their failures . A behavioural failure is a mistake in what the agent does, such as quoting an outdated decision. On the current model, I could replay one behavioural failure with its written rule removed, and it did not recur. Two other failures did not occur even without their fixes. Documentation drift, by contrast, comes from how the repository changes, not from how the agent behaves. It came back again and again as the repository changed, a single LLM audit pass caught only half of it, and code checks were still needed to block it. 

# 2 Background and related work 

Rule files and harness configuration. Mining studies of CLAUDE.md , AGENTS.md and Cursor rules show that these files mostly specify build commands, coding conventions and architecture summaries, with relatively few security or safety rules [8, 9, 18]. Galster et al. identify eight configuration mechanisms across agentic coding tools. They find that static context files dominate practice, while modular skills and subagents are underused [12]. Context files grow through small additions [9]. Across 1,867 repositories, Chakrabarti finds that a file grows by 226 % on average over its lifetime, and that older instructions are less likely to be deleted [6]. In a survey of 99 practitioners, Cai et al. found that 78 % of developers reported modifying rules to correct AI errors, most often by appending prohibitions [4]. Dos Santos et al. catalogue the resulting configuration smells, such as rule bloat and contradictory directives [11]. Vendor guides stress that prompt files give advisory context, not guaranteed enforcement. They recommend runtime hooks for hard constraints [2, 3] and on-demand skills to keep always-loaded context small [31, 44, 47]. Yet a factorial experiment across 1,650 sessions found no statistically significant effect of context file length, ordering or conflicting instructions on how well agents follow instructions [25]. 

Do rules work? Evidence on the effectiveness of prose rules is mixed. Lulla et al. report reduced execution time and token consumption when an AGENTS.md file is present [24]. Conversely, Gloaguen et al. find that repository context files do not consistently improve task resolution rates while increasing token costs by more than 20 % [13]. Zhang et al. observe that the only standalone rules that improved performance were explicit prohibitions, and that randomly sampled rules performed comparably to human-curated ones [48]. Converting natural-language instructions into executable verification checks increases compliance from 67.0 % to 88.3 % in ContextCov [36], while runtime policy enforcement in AgentSpec prevents the vast majority of unsafe tool 2invocations [41]. My counterfactual replay examines this same contrast between prose rules and executable code checks inside a lived production repository. 

Automated harness evolution. Several recent systems automate the refinement of harnesses. Harness 2 iteratively adapts harness configurations per task and accumulates a persistent library of lessons for future runs [45]. Lin et al. demonstrate in Agentic Harness Engineering that performance gains stem primarily from tool design, middleware, and memory rather than system-prompt edits [22]. Kang et al. identify harness-level forgetting , in which a new harness modification degrades previously working behaviour, and guard each update with a regression check [19]. Wang et al. further show that automated harness evolution frequently overfits to training benchmarks and fails to outperform simple baselines on held-out tasks [42]. Existing automated harness systems add lessons or patches and check them against earlier behaviour under a fixed model. To my knowledge, none evaluates whether accumulated lessons remain necessary after the underlying language model is updated. 

Agent memory and documentation staleness. Agent memory architectures store past episodes as retrievable text [15, 29, 30, 38], yet Chao et al. demonstrate that LLM agents struggle to recognise when stored facts have become outdated [7]. In software engineering, detecting outdated code element references [39], stale comments [16], and code-documentation inconsistencies [20] is a long-standing problem. Because an agent treats its harness and repository documentation as ground-truth instructions, documentation drift can directly induce agent errors. 

Agent failures and the closest study. Prior work has established failure taxonomies for multi-agent pipelines [5] and evaluated destructive tool actions or false completion reports in red-team sandboxes [32, 35, 49]. Interactive permission prompts carry their own human factors cost: users approve 93 % of prompts, and automated classifiers still miss some over-eager edits [17]. Field studies indicate that coding agents increase short-term commit velocity [14, 27], while Cursor adoption also brings persistent increases in static-analysis warnings and code complexity [14]. The closest study to mine is Vasilopoulos [40], who describes building a codified context infrastructure with an always-loaded constitution, retrieval hooks, and on-demand specifications across 283 sessions in a single-developer codebase. Vasilopoulos reports that this infrastructure prevented repeated failures in four case studies. The present study differs by tracking failure recurrence by fix type, evaluating automated drift detection against a ground-truth answer key, and replaying historical failures across model versions. 

# 3 The system I studied 

The system under study is a private git repository of plain markdown documents and small Python scripts. It is my single system of record for job applications, CV generation, language study and administrative deadlines. Three agent runtimes work on the repository: Claude Code and Antigravity interactively on a laptop, and a headless server agent, one that runs without a chat window, for scheduled background jobs. Git is the only synchronisation layer between the laptop and the server, with a local systemd timer pulling and pushing changes every few minutes. The repository was created on 28 July 2026 and had 929 commits by 15 October 2026, of which 336 were automated sync commits. The first weeks had little activity: 17 commits between 28 July and 8 August, then a four-week pause. So I study the six weeks from 4 September, when I introduced AGENTS.md , to 15 October 2026. This window contains 912 commits and 115 of the 118 recorded failures. Two incidents predate it, and one was first seen on 19 October during second-pass coding. 

# 4 Method 

I use an autobiographical, single-case design that follows one system over time [23, 28, 33, 37]. It combines three studies, one for each of RQ1 to RQ3. 44.1 The failure ledger and rule growth (RQ1) 

To build the failure ledger, a table with one row per failure, I searched the git commit log, the area change logs, two documentation audit reports and my daily diary up to 15 October 2026. A keyword filter and a first structured extraction pass with Claude Sonnet 5.5 identified the candidate incidents. For each incident, the ledger records the date it was first seen, its failure category, how it was detected, the fix, the fix type ( rule , hook , lint check , script , configuration or 

none ), and whether a failure of the same kind recurred before 15 October 2026. I marked an incident as not recurring (“Did not”) only if at least seven days had passed since its fix. If fewer than seven days had passed, or if the records gave no evidence either way, I marked it Unknown .To check how reliable this coding was, I wrote a codebook with ten categories, that is, written rules for assigning each incident to a class. A blind second coding pass (Claude Opus 5.5) then coded all incidents again. It saw only the incident summaries written in the first pass and the fix descriptions, not the first labels. The second pass also judged recurrence for a seeded random sample of 30 incidents, working directly from the git history and logs. The two passes disagreed on 49 fields: 32 on category, 9 on fix type and 8 on recurrence. I resolved each one with the codebook rules. Then I checked a random sample of 30 resolved entries by hand against plain-English incident descriptions. Finally, I wrote a script that counts the words in AGENTS.md 

and in all rule text combined ( AGENTS.md , nested rule files and on-demand skills) at the end of each day in the git history. 

4.2 How much drift an LLM audit finds (RQ2) 

The repository’s monthly documentation audit runs a headless agent with a fixed prompt and read-only file and git tools. I measured its recall , the share of known stale statements it finds, and its precision , the share of its findings that are correct. For this, I made an isolated clone of the repository at commit 769dc91 on 14 October 2026, just before three commits that fixed a batch of stale documentation. The answer key holds 47 real stale statements. Each was in the audit’s scope, already existed at the snapshot, and was corrected by one of those three commits. Eleven of the 47 are borderline. One of the three commits fixed what the first monthly audit had found, so an earlier LLM audit had already found 22 of the 47 items. This favours drift that an LLM audit can detect. I also planted 20 synthetic drift errors of seven kinds: cron schedules (3), dead file paths (6), item counts (4), renamed identifiers (3), a modified governance rule (1), a deadline date (1) and described script behaviour (2). Each planted error contradicted another document, the directory tree or the git history. Git could have shown the agents which files I had changed. To hide this, I marked those files with git update-index --skip-worktree . Then git status 

and git diff showed a clean working tree. I ran the audit three times on each of three models: Claude Haiku 5.5, Claude Sonnet 5.5 and Claude Opus 5.5. Opus handed its file reading to Haiku subagents , smaller helper agents that it starts itself. An Opus evaluation pass scored each audit report against the 67-item key. As a spot check, five key items and six match scores were verified against the snapshot. Then I reviewed the key, the match scores and the extra findings before computing precision. A finding counts as correct if it matches a key item, a planted error, or a true stale statement outside the key. Precision is the number of correct findings divided by all findings. 

4.3 Replaying past failures with and without their fixes (RQ3) 

To test whether past fixes still change agent behaviour on current and older models, I chose five past failures. Each had a clear task that triggered it and a self-contained fix commit: 1. Stale skill counts: forgetting to update hardcoded skill counts in documentation after creating a new skill (fix: pre-commit lint Check 12). 52. Superseded decision: quoting an outdated architectural verdict from an earlier log entry when a newer entry reversed it (fix: a prompt rule requiring agents to check the newest log entry first). 3. Forbidden punctuation: writing an em-dash in a drafted cover letter despite a prompt prohibition (fix: pre-commit lint Check 9 blocking em-dashes in letters). 4. Destructive git reset: running git reset --hard after a stopped rebase and wiping uncom-mitted notes (fix: the guard.py pre-tool hook). 5. Run-time overestimation: giving inflated multi-hour estimates for fast mechanical tasks (fix: a prompt rule that sets 1 to 5 minutes as the normal run-time estimate and asks for the real time when an estimate is off by 2 × or more). For each failure, I built two throwaway git clones with no network remote. Condition A is the exact repository state just before the fix. Condition B is the same state with only that fix added ( cherry-picked , in git terms). Both clones got the same neutral commit message, so the git log could not reveal the condition. I ran each original task headless three times per condition on Claude Sonnet 5.5 (30 runs). To test whether model upgrades explain why failures did not recur, I repeated the em-dash and run-time estimate scenarios (three runs per cell) on two older models, Claude Sonnet 4.5 and Claude Sonnet 5, and on a second vendor’s runtime, Gemini 3.8 Flash in Antigravity. 

4.4 Guardrail counts from session logs 

To measure how often the runtime guardrails fired in normal work, I parsed 74 local Claude Code session transcripts recorded between 20 September and 14 October 2026. These transcripts contain personal data, so I extracted only counts of hook runs and blocked shell commands. No transcript text is quoted or released.

5.2 How much drift an LLM audit finds (RQ2) 

Figure 4 shows the recall of the read-only LLM audit on the 14 October snapshot. Claude Sonnet 5.5 did best. A single Sonnet 5.5 audit found 49.6 % of the 47 real drift items on average (22 to 25 items per run). Together, the three Sonnet 5.5 runs found 63.8 % (30 of 47 items). Claude Haiku 5.5 averaged 26.2 % and varied widely (7 to 18 items). Claude Opus 5.5 averaged 41.1 % (16 to 21 items). In these runs, Opus handed file reading to Haiku subagents. This may explain why Opus scored below Sonnet 5.5, but I did not test it. All nine runs, on all three models, missed 12 of the 47 real drift statements. Over all nine runs together, the audits found 30 of the 37 drift items that contradicted another current file in the repository, 2 of the 5 items that only git history could show, and 3 of the 5 items visible from both sources. The planted errors were much easier to find. Mean recall was 65.0 % on Haiku 5.5, 80.0 % on Sonnet 5.5 and 83.3 % on Opus 5.5. Pooled over all nine runs (180 item checks), detection depended strongly on the kind of error: • Structural and cross-file mismatches: mismatched cron schedules (27 of 27, 100 %), renamed identifiers (25 of 27, 93 %), dead file paths (43 of 54, 80 %), modified rule text (7 of 9, 78 %), and wrong item counts (26 of 36, 72 %) were detected reliably because a directory listing or paired table directly contradicted them. • Semantic and temporal drift: inaccurate descriptions of script behaviour (6 of 18, 33 %) and an outdated deadline date (3 of 9, 33 %) were missed in two-thirds of runs. Precision was high in every run. Across all nine runs, the audits raised only 8 false alarms (precision 0.93 to 1.00 per run). They also found 9 genuine stale statements that my answer key had missed.

In all 6 runs, the model ran git status and git diff , saved the uncommitted changes to a patch file and resolved the repository cleanly, so guard.py never had to fire. No run reached the destructive command, so this scenario does not test whether the guard is still needed. The fifth scenario was run-time estimation. The agent read the date from the host clock (19 October 2026), so the deadlines in the snapshot’s DEADLINES.md looked imminent. Sonnet 5.5 started the repository’s focus-guard skill and declined the task in all 6 runs. This scenario therefore gives no measurement of the estimation rule on Sonnet 5.5. Table 4 shows the em-dash and run-time estimation scenarios replayed on older Claude models and on Gemini 3.8 Flash. The older Sonnet models (Sonnet 4.5 and Sonnet 5) still wrote em-dashes in 2 of 12 cover letter drafts. One was in Condition A on Sonnet 4.5, and it was committed. The other was in Condition B on Sonnet 5, where the pre-commit lint check rejected it and the agent fixed it. Sonnet 5.5 and Gemini 3.8 Flash together wrote no em-dash in 12 drafts. For run-time estimation, Sonnet 4.5 did the task instead of declining it. It overestimated the run time by at least 2 × in 2 of 3 runs in Condition A and in 2 of 3 runs in Condition B, so the prompt rule made no difference. Gemini 3.8 Flash declined 3 of the 6 estimation runs under the same focus rule. In the 3 runs it did, no estimate exceeded twice the actual time (1 to 3 minutes estimated against 1.5 to 6 minutes actual). On the older models, then, the lint check stopped the one em-dash that reached a commit attempt (Sonnet 5). The prose rule did not change the estimates on Sonnet 4.5, the only older model that did the estimation task. 10 6 Discussion 

Lessons may outlive the model failures that motivated them. On the current model, three of the four finished failures did not occur in my replay, with or without their fixes. Three runs per condition cannot show that a failure is gone, only that it did not occur in those runs. And as Section 5 notes, the em-dash and reset scenarios do not test whether their lessons are still needed. Only the superseded-decision scenario removed a prose rule and reached its trigger. The harness may carry prose rules and hooks against mistakes that newer models avoid on their own in this setup. This complements the continuous rule growth that Chakrabarti documents [6] and that Figure 3 shows. Lessons are cheap to add after an incident, but nothing signals when a model upgrade has made them obsolete. Harness rules should therefore record the model version that motivated them and carry a date for a re-test. Counterfactual git replay is a cheap retirement test: 30 headless sessions across five scenarios took 10 minutes and cost about $3.55 in API-equivalent tokens. 

Drift comes from how the repository changes. In the one drift scenario I replayed, the stale-count failure recurred in all three unguarded runs on Sonnet 5.5. I did not replay drift on other models. Drift is also the largest class in the ledger (40.7 %), and a single LLM audit pass misses half of it. A formatting quirk or a rash shell command is a matter of agent behaviour, whereas drift follows from keeping natural-language documentation next to files that keep changing. Every added skill, renamed script or updated policy silently makes statements in other files wrong. Agents struggle to notice when stored context has become stale [7], and LLM audits miss most drift that only git history shows. An invariant is a fact that must always hold, such as a count that matches the files on disk. For any invariant that can be written in code, a deterministic pre-commit check therefore remains the only reliable defence. 

Code checks worked where a written rule did not. Three runs per cell give an exploratory signal, not a high-powered statistical comparison. Still, the cross-model replay agrees with larger benchmark studies in which executable checks beat prompt guidance [22, 36]. Whenever a check was active and an agent produced an out-of-date skill count (Sonnet 5.5) or a forbidden em-dash (Sonnet 5), the pre-commit linter rejected the commit with a specific error message. The agent then fixed the violation at once. By contrast, the prompt rule on time estimates did not reduce overestimation on Sonnet 4.5. 

What this means for tools that update rules automatically. Self-evolving harness frameworks such as Harness 2 and Harness-R1 automate the adding of lessons [34, 45]. My findings point to two additions for such systems: 1. Automated lesson retirement: when a base model is upgraded, the harness should replay the stored trigger task for each lesson without that lesson active, archiving prompt rules that no longer change outcomes. 2. Checks before a new lesson goes live: fixes can cause false positives or interfere with operations (such as the 197 background autostash runs that interfered with active sessions). A candidate harness edit should therefore pass both human approval and a regression check, a test that earlier behaviour still works [19], before it is deployed. 

The same rules with a second vendor’s model. Although the harness was written mainly in Claude Code sessions, Gemini 3.8 Flash in Antigravity followed the same AGENTS.md rules and on-demand skills without changes in the two scenarios I replayed on it, including the deadline focus skill. This suggests, but does not establish, that a markdown harness can govern agents across model providers and client runtimes. 11 7 Threats to validity 

Single-user system. All data come from one repository that I designed, maintained and studied myself [28, 37]. A written codebook and a blind second coding pass support consistent classification ( κ = 0 .65 and 0 .89). They do not remove the selection bias of studying one system, and the findings cannot be generalised statistically to software repositories with many developers. 

Researcher roles. I designed the logging policy, wrote most fixes, chose the replay scenarios, approved the answer key and resolved every coding disagreement. The blind second coding pass and the planted errors reduce, but do not remove, the risk that my expectations shaped these data. I did not measure the recall of the keyword search that seeded the ledger. 

Under-reporting in the ledger. I constructed the failure ledger from git commits, change logs, and audit reports recorded during daily work. Minor agent mistakes that I corrected conversationally in chat without creating a log entry or commit are absent from the dataset. 

Short observation window and one heavy audit day. The study covers six weeks. Incidents fixed in the final week therefore had fewer than seven days to recur. I marked them Unknown , as I did incidents with no evidence either way. Recorded failure counts also depend on how hard I looked. The two full-repository LLM audits on 14 October found 38 stale statements on a single day, which I recorded as 35 drift incidents (Figure 2). Without that day, drift accounts for 13 of 83 incidents. 

Few runs, and LLMs as measuring tools. The audit benchmark and the replay both use three runs per cell. LLMs also play several roles in this study: coding assistants, audit scorers and replayed agents. In Table 3, 3 of 3 failures against 0 of 2 gives a one-sided Fisher’s exact 

p = 0 .10. That is a directional signal, short of statistical significance. 

Other explanations for the replay results. When a past failure does not reproduce in replay, I cannot fully separate two causes: a newer model, or a reconstructed prompt that missed a subtle trigger from the original session. Also, the original incidents happened on Claude Opus models and in Antigravity, while the main replay used Claude Sonnet and Gemini Flash. Finally, each replay clone checked out a past commit, but the agent runtime read the host system clock (19 October 2026). This made past deadlines in DEADLINES.md look imminent. The focus-guard skill then declined non-essential tooling work in 7 of the 30 Sonnet 5.5 replay runs (3 in Condition A, 4 in Condition B), in all 6 Sonnet 5 estimation runs and in 3 of 6 Gemini estimation runs. Future replays should run under a faked system clock (for example 

libfaketime ) to remove this problem. 

Ground-truth key completeness. The 47-item audit answer key was defined by the stale statements corrected on 14 October. It therefore under-counts true repository drift by at least the 9 additional valid stale statements that the nine audit runs uncovered. 

# 8 Conclusion 

For six weeks of daily use, I studied my personal system of record. A shared rule file, on-demand skills, runtime hooks and pre-commit checks governed it. In that time I recorded 118 agent failures. Documentation drift was the largest failure class (40.7 %, most of it found on one audit day). It came back after each new check, and single LLM audit passes missed about half of it. I replayed five past failures in isolated git clones on a current model. The agent finished four of the tasks. In three of them, the failure did not reproduce in three runs per condition, with 12 or without the fix. The one drift scenario recurred in every unguarded run, and its pre-commit lint check stopped it every time. As language models improve, harnesses may accumulate rules against mistakes the models no longer make, while structural drift continues. People and tools that maintain harnesses should therefore record which model version required each lesson, enforce structural invariants in executable code, and regularly replay and retire obsolete prompt rules.
