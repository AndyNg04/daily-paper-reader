Abstract —AI assistants are increasingly embedded in com-putational notebooks, scientific workflows, software engineering tools, and learning systems, yet human–AI interactions are often treated as transient prompt–response exchanges rather than durable data products, hindering reproducibility, explainabil-ity, replay, behavioral analysis, and adaptive AI support. We argue that these interactions form a new data class requiring formal representation and introduce the Human–AI Interaction Description Language (HAIDL), a formal interaction model with a Backus–Naur Form-inspired concrete syntax. HAIDL encodes each interaction as a structured object capturing computational context, user request, prompt payload, AI response, feedback, problem context, provenance, and model metadata. We integrate this vision into HAIDL-X, a middleware for JupyterLab that instantiates HAIDL by capturing user-bot state, building con-textualized prompts, interfacing with AI providers, collecting feedback, and storing interactions in a repository. We add a learning layer over HAIDL that maps interaction objects and notebook execution traces into reproducible measures of user behavior, including engagement, performance, help-seeking, error-oriented use, and learning personas. HAIDL-X provides a foundation for treating human–AI collaboration as structured, queryable, replayable, analyzable data. 

Index Terms —Human-AI interaction, interaction data, AI middleware, provenance, learning analytics, JupyterLab, large language models, Big Data infrastructure 

I. I NTRODUCTION 

Foundation models are being woven into computational work at every scale: they draft and debug code in compu-tational notebooks, steer data analyses, configure scientific workflows [1], and act as agents in campaigns spanning edge, cloud, and HPC systems [2]. Computational results are therefore no longer produced by humans or machines alone but through sustained human–AI exchanges, which now shape what gets computed, how errors are resolved, and which conclusions are drawn. Consider an AI assistant embedded in a computational notebook. A user who never invokes it looks, in the AI logs, like a failure of adoption—but zero interactions are ambiguous: the user may be progressing independently, or stuck and never seeking help, and the logs cannot tell these apart though they call for opposite responses. Heavy use is just as ambiguous: two users may each invoke the assistant a dozen times with nearly identical transcripts, where one is debugging—each request follows a runtime error, each response followed by a code change and a successful re-execution—while the other extracts answers, pasting responses forward without attempts in between. Counted as prompts, these users are identical; as collaborations, they could not be more different. Human–AI collaboration is not explainable :when AI assistance fails, misleads, or simply goes unused, we cannot reconstruct why. This is not for lack of logging— emerging telemetry standards record, in structured form, what the model saw and said: prompts, responses, token counts, tool calls, and latencies [3]—but such records cannot answer what an explanation requires: (1) what computational state led a user to request assistance; (2) what role that assistance played (error recovery, a next step, a concept, validation); (3) across a community of users, who is helped, who over-relies, and who struggles in silence. Nor can such records support auditing or reproducing AI-assisted portions of aresult after the fact. Answering these requires recording the 

human side of each exchange—the computational state that motivated it and the actions that followed; today’s logs do neither. Existing approaches each capture one side of this coupling (Section IX surveys these in detail): observability conventions such as OpenTelemetry GenAI [3] instrument the model side but omit user context and downstream ac-tions; provenance models, from W3C PROV [4] to PROV-AGENT [2] and LLMography [5], trace agent actions within workflows but do not treat the request–response–assessment cycle as a first-class unit; and programming-process formats such as ProgSnap2 [6] standardize the human side but predate AI assistance, while transcript-only studies [7] lack the com-arXiv:2610.40006v1 [cs.AI] 29 Oct 2026 putational state needed to ground inferred intent. No existing representation couples both sides of a human–AI exchange or defines semantics for deriving knowledge from it. We provide that representation: the Human–AI Interaction Description Language (HAIDL) , a formal language that models each human–AI exchange as a single structured object spanning the computational state that motivated the request, the con-textualized prompt, the AI response, the user’s assessment, and full provenance. HAIDL pairs this grammar with an explicit derivation relation ( ⇒K ) that turns stored interactions into inspectable knowledge—for example, resolving whether a user with zero interactions was progressing independently or was stuck and never sought help. We instantiate HAIDL in HAIDL-X, a human–AI middleware for JupyterLab, and validate it through a semester-long capture of interactions in a university computing course: 35 students, four programming assignments, ≈800 recorded interactions, and 140 student– assignment pairs, reproducing the ambiguities above in real data. This paper makes four contributions:  

> •

The HAIDL representation. A formal model of human– AI interactions as first-class, self-contained data objects, defined by a BNF-inspired grammar over seven semantic components—computational context, request, prompt, re-sponse, feedback, problem context, and model provenance— with a derivation relation separating observed data from inferred knowledge (Section III).  

> •

A human–AI middleware for runtime capture. HAIDL-X instantiates HAIDL during live computational work: captur-ing notebook state per request, constructing contextualized prompts, communicating with interchangeable AI providers, collecting feedback, and persisting interaction objects in a queryable repository (Section IV).  

> •

Knowledge extraction, demonstrated in a case study. 

We define derivation rules composing HAIDL objects with observed execution evidence to recover the role each re-quest played, the trajectory of use over an assignment, and the collaboration patterns behind it—resolving the opening ambiguities: among 37 student–assignment pairs with no recorded interactions, distinguishing students progressing alone from those stuck and never asking (Sections VI–VII).  

> •

Empirical quantification of system cost. We measure the latency, storage, and retrieval overhead HAIDL-X adds to an AI exchange, showing the cost of turning a transient conver-sation into a persistent, explainable record (Section VIII). II. H UMAN –AI I NTERACTIONS AS FIRST -C LASS DATA 

Human–AI collaboration is often seen as a series of prompt– response exchanges, but this view is incomplete. Each interac-tion is a state-changing event in which a user, an AI system, and a computational environment jointly solve problems: it starts from a computational state that motivates the request and ends in a new state shaped by the user’s actions after interpreting the AI’s guidance. We model an interaction as a state transition:

Unlike traditional chat logs, this explicitly models how interactions transform computation rather than recording exchanged messages. A sequence of interactions forms an interaction trajectory, 

T = ⟨I1, I 2, . . . , I n⟩, (2) describing the evolution of a collaborative problem-solving session and supporting analysis of interaction strategies, learn-ing behaviors, and AI effectiveness over time. This is the data problem raised in Section I: interactions become structured entities to be represented, stored, queried, replayed, and ana-lyzed, like database records or provenance objects in scientific workflows. Figure 1 illustrates this lifecycle. Every interaction consists of three conceptual stages.  

> •

User Request. A user in a computational environment submits a request based on the current state (source code, outputs, errors, and problem description), informing both the immediate question and the broader task.  

> •

AI Response. Using this context, the AI constructs a contex-tualized prompt and returns guidance—explanations, debug-ging help, code suggestions, or conceptual clarification— emphasizing collaborative reasoning rather than mere text.  

> •

Interaction Assessment. The user evaluates the response explicitly (feedback) or implicitly (editing code, running cells, follow-ups, or abandoning the solution). This assess-ment defines the next computational state and the starting point for the next interaction. III. H UMAN –AI I NTERACTION DESCRIPTION LANGUAGE 

We present the Human–AI Interaction Description Lan-guage (HAIDL), a formal language for representing human– AI collaboration as structured data and composing those rep-resentations into higher-level interaction knowledge. HAIDL is independent of any AI provider, application, or runtime; its concrete syntax is a grammar inspired by Backus–Naur Form (BNF), while its semantics define how interaction constructs relate to computational state and to one another. The lower part of Figure 1 shows the basic abstraction. Rather than repre-senting the stages of human–AI collaboration as disconnected events, HAIDL groups them into a single interaction object— a self-contained representation of a collaborative episode that can be stored, shared, queried, replayed, and analyzed inde-pendently of its original runtime. 

A. Design Principles 

HAIDL builds on five principles: 1) Completeness : capture the full lifecycle of an interaction, not only the prompt and response. 2) Modularity : represent interactions through reusable se-mantic components. 3) Explainability : associate each construct and derived ex-pression with an explicit interpretation. 4) Extensibility : allow new AI models, applications, and metadata without changing the overall language structure. Fig. 1: Lifecycle of a human–AI interaction. A user request arises from a computational state, the AI returns guidance, and the user evaluates or acts on it. HAIDL represents the full lifecycle as a structured artifact whose outcome seeds the next interaction. 5) Composability : allow interaction objects and computa-tional states to be related across time so higher-level knowledge can be expressed and derived. 

B. Interaction Objects 

At the highest level, HAIDL represents each interaction as a structured object: 

I = ⟨M, R, P, A, F, C, L ⟩, (3) where M is record metadata, R the user request, P the prompt payload, A the AI response, F feedback or assessment, C

the problem context, and L model metadata. Figure 2 shows this organization: rather than storing prompts and responses separately, HAIDL models each collaborative episode as a single object spanning the computational state that led to the request, the contextualized prompt, the AI response, the user’s assessment, and the provenance needed to interpret the interaction—the atomic unit from which more complex HAIDL expressions are built. The interaction is:         

> Interaction ::= <RecordMetadata, UserRequest, PromptPayload ,LLMResponse, Feedback, ProblemContext, ModelMetadata >

The ProblemContext component links an interaction to the motivating task or scientific problem, which is essential because the same observable interaction can mean different things depending on the problem being solved. 

C. Recursive Grammar 

HAIDL recursively decomposes an interaction into seman-tically meaningful components. For example, UserRequest 

records the computational context that motivates assistance:             

> UserRequest ::= <request_id, user_id, cell_id, Time, code, UserCodeOutputs >UserCodeOutputs ::= StreamOutput |ErrorOutput

Fig. 2: Conceptual organization of a HAIDL interaction object: a single structured object with seven semantic components, forming the atomic unit of human–AI collaboration and the root production of the HAIDL grammar.            

> StreamOutput ::= <output_type, traceback, text > ErrorOutput ::= <output_type, traceback, error_type, error_value >

Prompt construction, AI response, feedback, problem context, and model metadata are represented separately:                                      

> PromptPayload ::= <prompt, Time >LLMResponse ::= <request_id, user_id, response, Time, llm_latency, server_latency >Feedback ::= <request_id, user_id, cell_id, FeedbackValue, Time, problem_label, latency_ms, ts_ms >FeedbackValue ::= "Yes" |"No" |"Somewhat" ProblemContext ::= <assignment_name, problem_label > ModelMetadata ::= <provider, model >

This decomposition separates information typical chat his-tories conflate or omit: the computational state motivating assistance, the contextualized prompt sent to the model, the AI response, the user’s assessment, the problem context, and runtime and model provenance. Because each component has explicit semantics, they can be queried independently and then recomposed. 

D. From Interaction Objects to Interaction Expressions 

The grammar above defines the structure of a single in-teraction, but human–AI collaboration rarely involves just one exchange. As introduced in Section II (Eqs. 1–2), an interaction changes computational state and a sequence of interactions forms a trajectory T = ⟨I1, . . . , I n⟩. HAIDL sup-ports two composition levels: structural composition combines fields into interaction objects per the grammar, while temporal composition relates objects via their states, timestamps, users, and problem contexts, expressed at the language level as:      

> InteractionTrajectory ::= Interaction* InteractionData ::= Interaction |InteractionTrajectory |ExecutionState

An Interaction is a single collaborative episode, an 

InteractionTrajectory is an ordered sequence of such episodes, and ExecutionState provides observable com-putational links between them. Together, these form the sub-strate for expressing higher-level interaction knowledge. 

E. From Syntax to Knowledge 

The distinction between representation and knowledge derivation is central to HAIDL. The BNF-inspired production operator ::= defines valid language constructs and their structure but does not infer the meaning of observed behavior. We introduce a separate knowledge-derivation relation, 

O1, . . . , O n ⇒K K (4) where O1, . . . , O n are HAIDL interaction-data expressions and K is knowledge derived from their relationships; ⇒K

explicitly links observable data to a higher-level interpre-tation. For example, ErrorOutput appears directly in a 

UserRequest , so it is interaction data, not inferred knowl-edge. When that error occurs in the computational state prompting an AI interaction, however, it can support a higher-level interaction expression: 

ErrorOutput (Si), I i ⇒K ErrorRecovery (Ii) (5) Similarly, knowledge can be derived from relationships across multiple interactions and computational states: 

Ii, S i+1 , I i+1 ⇒K Ki:i+1 (6) The exact meaning of Ki:i+1 depends on the derivation rule and domain—repeated help seeking, validation of AI guidance, progress following assistance, or another domain-specific pat-tern. This separation gives HAIDL two complementary roles: (1) a language for representing and composing interaction data, and (2) rules for deriving higher-level knowledge from those representations, turning relationships among interactions into inspectable knowledge. In HAIDL, interactions are therefore not only queryable, replayable, and analyzable data objects, but the primitives of a compositional language for human– AI collaboration: its grammar defines syntax, its derivation relation defines semantics, and HAIDL-X provides the runtime that instantiates it from real interactions (Section VI). IV. HAIDL-X: A N AI MW FOR SCIENTIFIC COMPUTING 

HAIDL specifies how human–AI interactions are repre-sented; HAIDL-X is the runtime that realizes this represen-tation as first-class data during execution: a human–AI mid-dleware that augments computational notebooks with context-aware assistance while capturing every interaction as a struc-tured, persistent record. We target JupyterLab [8], the inter-active computing environment now standard in data science. Rather than a monolithic assistant, HAIDL-X is a layered middleware separating user interaction, interaction capture, AI communication, interaction representation, and persistent stor-age, letting each layer evolve independently while preserving one common interaction model. 

A. Software Architecture 

HAIDL-X comprises six cooperating layers.  

> •

JupyterLab Extension. Integrates HAIDL-X into Jupyter-Lab, letting users request assistance and receive responses without leaving the notebook.  

> •

Frontend Client. Captures the computational context for each request—source code, executed cells, outputs, errors, timestamps, notebook metadata—packaging it into struc-tured interaction requests.  

> •

Backend Server. Validates requests, enriches them with context, builds contextualized prompts, invokes external AI providers, and records runtime metadata.  

> •

HAIDL Interaction Layer. Gives the middleware a com-mon representation independent of AI provider or notebook environment; components exchange structured HAIDL ob-jects rather than provider-specific messages.  

> •

Provider Abstraction Layer. Decouples provider-specific APIs from the interaction model, so new foundation models can be integrated without changing HAIDL or the middle-ware itself.  

> •

Interaction Repository. Persists completed interactions as HAIDL objects in a MongoDB repository, including prove-nance, timestamps, user assessments, and model informa-tion, supporting replay, querying, and behavioral analytics. 

B. Capture Pipeline, Repository, and Provider Independence 

These six layers execute in sequence for each request: the frontend captures computational state and packages it into a structured request; the backend builds a contextualized prompt and invokes the selected provider through the abstraction layer; the response and context are combined into a HAIDL object with explicit feedback when available; and the completed ob-ject is persisted to the repository. This pipeline is what makes human–AI interaction first-class data in practice: instead of ephemeral, implementation-specific chat logs, every inter-action becomes a computational artifact—indexed, queried, replayed, and analyzed across sessions, users, assignments, and providers. Because interaction representation is decoupled from model execution, the same HAIDL object results across different AI models. V. D EPLOYMENT AND DATA COLLECTION 

We deployed HAIDL-X in a university Data Engineering course to evaluate HAIDL with interactions from authentic computational work, yielding two complementary views of student activity: HAIDL-based records captured when students interacted with HAIDL-X, and execution evidence preserved in submitted Jupyter notebooks. This section describes the de-ployment and data preparation; interaction-knowledge deriva-tion is presented in Section VI. 

A. Classroom Deployment 

HAIDL-X was integrated directly into the JupyterLab en-vironment used by students for programming assignments. When assistance was requested, HAIDL-X captured the active cell code and its available execution output, constructed a context-aware request, routed it to the AI provider, returned the response in the notebook, and persisted the interaction through the HAIDL capture pipeline. The deployment involved 35 students and four programming assignments, yielding 140 student–assignment pairs. The assignments spanned different tasks and complexity: Assignment 03 focused on mathematical and algorithmic problem solving, Assignment 04 on text processing and exploratory analysis, and Assignments 07 and 08 introduced distributed data-processing tasks using PySpark (distributed k-means and a machine-learning pipeline, respectively). HAIDL-X was used during regular assignments, capturing interactions as students wrote, executed, debugged, and inspected notebook code. 

B. Experimental Design 

The classroom deployment used a crossover design. Group A had access to HAIDL-X for Assignments 03 and 07, while Group B had access for Assignments 04 and 08. Each group served as the no-access condition for the other assignments, enabling comparisons based on HAIDL-X avail-ability. Assigned access and observed use are not equivalent, however–some students with access never invoked HAIDL-X, while others used it outside the assigned-access condition– so we retain these cases rather than discard them, since the distinction between access and actual use is itself relevant context. The analysis therefore treats the student–assignment pair, not the student alone, as its primary unit. 

C. Data Sources 

The deployment produced two complementary data sources: 

a) HAIDL interaction data: HAIDL-X persisted each observed AI interaction as structured interaction data. De-pending on the available context, records include the student identifier, assignment and notebook-cell identifiers, source code, execution outputs or errors, contextualized prompt, AI response, timestamps, model information, latency metadata, and explicit user feedback. These records provide evidence for AI-use measures and semantic interaction events in Section VI. 

b) Notebook execution data: Submitted Jupyter note-books provide an independent record of computational ac-tivity. We analyze notebook cells implementing assignment logic, excluding markdown and timing-only cells. A cell is 

touched when the notebook shows evidence it was executed; among touched cells, one that completes without a Jupyter execution error is successfully executed, one producing an error is unsuccessful, and cells without execution evidence are not executed. These execution-based proxies do not imply a logically correct solution, but provide observable evidence of how far students progressed and how extensively they interacted with an assignment’s code cells. The two sources capture different aspects of the same activity: notebook traces describe what happened during computation, including activity where HAIDL-X was never invoked, while HAIDL objects describe what happened when AI assistance was requested. Neither source alone provides the combined view used in our knowledge derivations. 

D. Data Preparation and Alignment 

We aligned the two data sources around the student– assignment pair: notebook execution records were reduced to the assignment-relevant code cells described above, and HAIDL-X interaction records were grouped by student and assignment and, when a cell identifier was available, linked to the corresponding notebook cell. Within each pair, interactions were ordered by timestamp, preserving the temporal structure HAIDL requires and allowing multiple requests to be repre-sented as a trajectory. The resulting analysis record connects three forms of evidence: 

Du,a = ⟨Nu,a , H u,a , X u,a ⟩ (7) where Nu,a denotes notebook execution evidence for student u

on assignment a, Hu,a the corresponding HAIDL interaction objects, and Xu,a the assigned HAIDL-X access condition. We preserve these sources separately rather than collapsing them during preprocessing, so that execution behavior, AI interaction behavior, and experimental context remain inde-pendently inspectable and are composed only through the explicit derivation rules of Section VI. VI. F ROM INTERACTION DATA TO KNOWLEDGE 

Representing human–AI interactions as first-class data is useful only if the representation supports reasoning beyond individual records. HAIDL is both a grammar for describing interaction objects and a language for deriving higher-level knowledge; its core idea is composition: observable fields describe individual events, relationships among events describe behavior, and sequences of behaviors reveal higher-level pat-terns. We illustrate this in a learning scenario—not to recast HAIDL as a language dedicated to learning tasks, but to show how the interaction primitives of Section III combine with domain-specific observations to infer knowledge not explicitly contained in any single interaction record. 

A. From Observations to Derived Knowledge 

HAIDL distinguishes three levels of representation: Observation ::= Interaction | ExecutionState InteractionKnowledge ::= InteractionEvent | InteractionTrajectory | BehavioralState 

An Observation is directly captured data. An Interaction is a HAIDL object I =

⟨M, R, P, A, F, C, L ⟩, and an ExecutionState is the observable notebook state for that interaction (e.g., executed code, outputs, or errors). InteractionKnowledge , in contrast, is derived by relating observations. For instance, an 

ErrorOutput is an observation, while using AI assistance in response to that error is an ErrorRecovery event. Likewise, multiple interactions showing persistent lack of progress can form RepeatedHelp . These higher-level constructs are reproducible expressions over HAIDL fields and computational observations, not extra labels stored apart from the interaction data. We use the derivation operator ⇒K to distinguish knowledge derived from HAIDL observations from the BNF productions that define their concrete representation: 

O1, . . . , O n ⇒K K

where Oi are observable interaction or execution objects and 

K is a derived knowledge construct. 

B. Deriving Interaction Events 

The first level of knowledge describes the apparent role of an AI interaction in the user’s computational activity:     

> InteractionEvent ::= ErrorRecovery |StuckNextStep |ConceptualHelp |Validation

These events are not independent fields in the interaction repository; they are derived from combinations of HAIDL components and notebook state, with intent inferred from the source cell, execution outputs, errors, and the request–response pair. For example, an error in the computational state for an interaction indicates a need for error-oriented help: 

ErrorOutput (Si), I i ⇒K ErrorRecovery (Ii)

An interaction associated with incomplete code or an unfin-ished computational step provides evidence for: 

IncompleteState (Si), I i ⇒K StuckNextStep (Ii)

Requests for explanations or clarification are labeled 

ConceptualHelp , while requests to inspect or check ongo-ing work are labeled Validation . These categories describe HAIDL-X ’s observable role in the workflow rather than the user’s underlying intent. Their value lies in being derivable, inspectable, and reproducible from interaction data. 

C. Composing Events into Interaction Trajectories 

Individual events show how AI is used at one moment. HAIDL’s state-transition model also allows composing events over time. For a learner u and assignment a, we define: 

Tu,a = ⟨I1, I 2, . . . , I n⟩

where interactions are ordered by their timestamps.   

> InteractionTrajectory ::= InteractionEvent*

The trajectory permits knowledge to be expressed over re-lationships among interactions and subsequent computational states. Two useful derived constructs are:   

> TrajectoryEvent ::= RepeatedHelp |NoProgress

Conceptually, repeated help seeking consists of an interaction event followed by a no-progress state and another interaction:      

> InteractionEvent →NoProgress →InteractionEvent
> ⇒KRepeatedHelp

Likewise, an interaction followed by execution with no observ-able progress is NoProgress . These constructs highlight a key property of HAIDL: knowledge can be expressed not only over fields within an interaction object, but over relationships among objects and the computational states connecting them. 

D. Composing Interaction and Domain Knowledge 

The previous constructs are domain-independent descrip-tions of interaction behavior; applications can combine them with domain-specific observations to derive richer knowledge. In our classroom deployment, notebook execution provides evidence about student performance and engagement, so for each student u and assignment a, we define:    

> P erf ormance (u, a ) = correctly solved cells (u,a )
> total code cells (u,a ),Engagement (u, a ) = touched cells (u,a )
> total code cells (u,a )

Here, successful execution is used as a performance proxy rather than proof of semantic correctness. These measures produce four relative learning profiles:                     

> LearningProfile ::= HPHE |HPLE |LPHE |LPLE HPHE ::= HighPerformance +HighEngagement HPLE ::= HighPerformance +LowEngagement LPHE ::= LowPerformance +HighEngagement LPLE ::= LowPerformance +LowEngagement

Interaction objects provide complementary measures, with

> BotIntensity (u, a ) = N(u, a );
> ErrorU se (u, a ) = |{ Ii:ErrorOutput ∈U serRequest (Ii)}|

These measures remain traceable to notebook observations or HAIDL components. 

E. Deriving Behavioral States 

The classroom deployment provides an additional con-textual observation: whether HAIDL-X was expected to be available for a given student–assignment pair, encoded as:     

> ExposureStatus ::= ExpectedUser |ExpectedNonUser |Control |CrossConditionUser

An ExpectedUser had assigned access and used HAIDL-X; an ExpectedNonUser had assigned access but did not use it; a Control had no assigned access and did not use the system; and a CrossConditionUser used it despite not having assigned access. Thus, learning profile, exposure status, and interaction knowledge can now be combined. LearningTrace ::= Learner | Assignment | ExposureStatus | LearningProfile | InteractionTrajectory | BehavioralState BehavioralState ::= SelfSufficient | ExploratoryOverUser | DisengagedStruggler | ScaffoldedLearner | CrossConditionUser 

For example, the analysis interprets an expected non-user with high performance as self-sufficient, whereas an expected non-user with low performance is interpreted as a disengaged struggler:         

> ExpectedNonUser +HighPerformance ⇒KSelfSufficient ;
> ExpectedNonUser +LowPerformance ⇒KDisengagedStruggler

For students expected to use HAIDL-X, interaction patterns further refine interpretation. Low performance paired with productive help-seeking—long studied in intelligent tutoring systems [9]—or sustained engagement indicates a scaffolded learner, where ProductiveHelp aggregates error-recovery, next-step, and conceptual-help interactions:       

> ExpectedUser +LowPerformance +(ProductiveHelp ∨HighEngagement )⇒KScaffoldedLearner

High performance together with comparatively high AI use dominated by validation-oriented interactions evidences ex-ploratory over-use, while cross-condition use is retained ex-plicitly rather than interpreted as a normal help-seeking per-sona:          

> ExpectedUser +HighPerformance +HighBotUse +ValidationDominant
> ⇒KExploratoryOverUser ;
> CrossConditionUse ⇒KCrossConditionUser

These behavioral states are not diagnoses or intrinsic student traits. They are reproducible interpretations of observable behavior for a particular student–assignment pair. 

F. What the Language Reveals 

The resulting hierarchy is:         

> Observations →Interactions →Events →Trajectories →Behavioral Knowledge

capturing the distinction between storing interaction data and reasoning over it: a runtime error is an observation; an AI re-quest made in that context is error-recovery behavior; multiple such events form a trajectory; and combined with execution-derived performance, engagement, and experimental context, a trajectory supports a behavioral interpretation. Conventional chat histories preserve text exchanges but lack a common semantic representation connecting the request to computa-tional state, errors, task context, feedback, and subsequent interactions; HAIDL makes these relationships explicit and derivable through inspectable rules. The classroom deploy-ment demonstrates this capability, but the mechanism is not inherently educational—the same domain-specific state and derivation rules could instead express interaction knowledge about scientific workflows, software debugging, or other forms of human–AI collaboration. HAIDL’s contribution is thus a compositional language, not a fixed taxonomy of learning behaviors. VII. C ASE STUDY : D ERIVING INTERACTION KNOWLEDGE 

We apply the Section VI framework to the classroom deployment in Section V, covering 140 student–assignment pairs from 35 students across four assignments and combining notebook execution data, HAIDL-X interaction logs, and ac-cess conditions. Our goal is not to estimate HAIDL-X’s causal effect on performance, but to test whether first-class interaction data let us distinguish forms of human–AI behavior that are ambiguous from notebook traces or AI logs alone. 

A. Interaction Behavior and Learning Profiles 

We first examine interaction events derived from HAIDL-X records, classifying each event’s role (Section VI-B) from the source cell, execution state, errors, and request–response pair; we then examine notebook-derived learning profiles from performance and engagement proxies. Table I reports both distributions by assignment. Interaction events varied substantially across assignments. Assignment 03 (algorithmic problem solving) generated the most stuck/next-step, error-recovery, and validation requests. Assignment 04 shifted to-ward conceptual help and error recovery, while PySpark As-signments 07 ( k-means) and 08 (a multi-stage MLlib pipeline) were dominated by error recovery, with Assignment 08 also generating substantial conceptual help. Thus, a simple “num-ber of prompts” metric obscures important differences: the same HAIDL-X call can serve different roles depending on the task and execution state. HAIDL captures these differences by linking each request to its execution context. The learning profiles add important nuance. The first two assignments are dominated by High-Performance/High-Engagement (HPHE) and Low-Performance/Low-Engagement (LPLE), while the Spark assignments introduce Low-Performance/High-Engagement (LPHE) students (8 pairs in Assignment 07 and 6 in Assignment 08), with no HPLE cases. LPHE captures engaged struggle : students who touched many cells but completed few. In contrast, LPLE combines low performance with low activity. Interaction counts alone reveal little about outcomes: across all 140 pairs, interaction count has only weak correlations with successfully executed cells (r = 0 .12 ) and touched cells ( r = 0 .12 ). Thus, frequency alone does not indicate whether HAIDL-X helped or hindered performance; events and learning profiles instead provide complementary views of how AI was used.

C. What the Derived Knowledge Reveals 

Analyzing interaction data and notebook execution evidence separately, then combining them, is more informative than either alone, in four ways. Interaction counts conceal how AI is used : HAIDL-X’s role shifts with the task—next-step help and validation for Assignment 03, error recovery for Assign-ment 07, conceptual and error recovery for Assignments 04 and 08—a distinction simple request counts cannot reveal. 

Notebook traces distinguish forms of struggle : the Spark assignments surface LPHE students who keep attempting cells despite limited success, an engaged-struggle state distinct from LPLE, with HAIDL records showing whether they seek debug-ging, conceptual, or next-step help. Zero AI interactions are ambiguous : a non-user with strong performance suggests self-sufficiency, a non-user with weak performance a disengaged struggler—identical states in the AI log alone. Observed use and experimental exposure are not equivalent : the 26 cross-condition cases show a simple used/did-not-use variable can-not capture real deployment, since HAIDL records observed behavior while the access schedule supplies context to interpret it. These results do not show that HAIDL-X improves learning, nor is that their purpose; they support this paper’s central claim that structured interaction data, combined with computational and experimental evidence, yields knowledge none of these sources provides alone—every behavioral state traces back to specific HAIDL fields, notebook observations, and derivation rules, the practical value of treating human–AI interactions as first-class data. D. Discussion 

The key systems question is not whether HAIDL-X out-performs an AI provider or database, but whether preserving full interaction context is practical for interactive use. These measurements quantify that cost against the benefit shown in Section VII: preserving computational state, context, prove-nance, and temporal structure enables knowledge otherwise hard to reconstruct. B. Provenance and AI Observability 

Provenance systems record processes, dependencies, and execution states for reproducibility [1], [21], [22], built on the W3C PROV model [4] and extended by ProvONE [23], notebook-provenance systems [24], and Workflow Run RO-Crate [25]. This fam-ily keys to the model invocation or agent actions, not the user’s computational state or assessment (Table IV); HAIDL contributes the human-side coupling and derivation semantics (⇒K ) these models omit. 

C. Interaction Data Standards and Formal Models 

Interoperable activity standards—ProgSnap2 for programming-process data [6], the Experience API [27], and profile-based event models [28]—predate AI assistance and provide no rules for deriving higher-level constructs from recorded events; such analyses are re-implemented per study. Grammar-based formalisms have separately been applied to constrained generation [29] and workflow resource-allocation [30]. HAIDL applies the same principle, pairing a BNF-inspired grammar with an explicit derivation relation these standards lack (Section VI). X. C ONCLUSION 

Human–AI interactions are central to computational and scientific workflows, yet they are still logged only as transient prompts and responses, discarding the computational state, task context, feedback, provenance, and timing needed to understand the collaboration. This paper introduces the Hu-man–AI Interaction Description Language (HAIDL), a formal language that treats each interaction as first-class data: a struc-tured object with composition and derivation semantics relat-ing these objects across states and over time. HAIDL-X instan-tiates HAIDL in JupyterLab, capturing interaction context, AI responses, feedback, and provenance during live computational work. A classroom deployment demonstrates the value of this representation. HAIDL objects compose into semantic inter-action events—error recovery, next-step assistance, conceptual help, validation—and, combined with notebook execution and experimental context, into higher-level behaviors distinguish-ing independent progress, scaffolded AI use, and disengaged struggle: patterns invisible from interaction counts or notebook traces alone. These results are not a causal claim about AI’s effect on learning; they show structured interaction data supports reproducible, evidence-traceable interpretation. The broader contribution is not a classroom taxonomy but a data model and language for preserving human–AI collaboration in queryable, composable form. The same primitives extend to scientific workflows, software development, and AI-assisted experimentation wherever understanding an AI collaborator’s role requires more than logging what was said—it requires preserving the state, provenance, and consequences of each exchange. Treating interactions as first-class data is what makes human–AI collaboration inspectable, reproducible, and ultimately explainable. ACKNOWLEDGMENTS
