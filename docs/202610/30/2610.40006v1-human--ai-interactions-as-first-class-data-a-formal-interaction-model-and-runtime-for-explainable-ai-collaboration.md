## 摘要
人工智能助手正日益嵌入计算笔记本、科学工作流、软件工程工具和学习系统中，但人机交互往往被视为短暂的提示—响应交流，而非持久的数据产品，这妨碍了可复现性、可解释性、回放、行为分析和自适应人工智能支持。我们认为，这些交互构成了一种需要形式化表示的新型数据类别，并提出人机交互描述语言（Human-AI Interaction Description Language，HAIDL）。HAIDL 是一种形式化交互模型，采用受巴科斯—诺尔范式（Backus-Naur Form）启发的具体语法。HAIDL 将每次交互编码为结构化对象，涵盖计算上下文、用户请求、提示载荷、人工智能响应、反馈、问题上下文、来源信息和模型元数据。我们将这一理念融入 HAIDL-X——一种面向 JupyterLab 的中间件。HAIDL-X 通过捕获用户与机器人状态、构建上下文化提示、连接人工智能服务提供方、收集反馈并将交互存储至存储库，实现了 HAIDL。我们还在 HAIDL 之上增加了一个学习层，将交互对象和笔记本执行轨迹映射为可复现的用户行为度量，包括参与度、表现、求助行为、以错误为导向的使用方式以及学习者画像。HAIDL-X 为将人机协作视为结构化、可查询、可回放、可分析的数据奠定了基础。

## Abstract
AI assistants are increasingly embedded in computational notebooks, scientific workflows, software engineering tools, and learning systems, yet human-AI interactions are often treated as transient prompt-response exchanges rather than durable data products, hindering reproducibility, explainability, replay, behavioral analysis, and adaptive AI support. We argue that these interactions form a new data class requiring formal representation and introduce the Human-AI Interaction Description Language (HAIDL), a formal interaction model with a Backus-Naur Form-inspired concrete syntax. HAIDL encodes each interaction as a structured object capturing computational context, user request, prompt payload, AI response, feedback, problem context, provenance, and model metadata. We integrate this vision into HAIDL-X, a middleware for JupyterLab that instantiates HAIDL by capturing user-bot state, building contextualized prompts, interfacing with AI providers, collecting feedback, and storing interactions in a repository. We add a learning layer over HAIDL that maps interaction objects and notebook execution traces into reproducible measures of user behavior, including engagement, performance, help-seeking, error-oriented use, and learning personas. HAIDL-X provides a foundation for treating human-AI collaboration as structured, queryable, replayable, analyzable data.

# 论文总结：将人机交互作为一等数据

## 1. 核心问题与研究背景

### 1.1 论文试图解决什么问题？

论文关注的不是“如何让大模型回答得更好”，而是：**如何保存、重建并解释人类与 AI 共同完成计算任务的过程。**

现有系统通常记录提示词、回答、模型名称、Token 数量和调用延迟，却较少同时记录：

- 用户是在什么代码、输出或错误状态下寻求帮助；
- AI 回答承担的是调试、概念解释、下一步指导还是结果验证；
- 用户采纳回答后，是否修改代码、重新执行并取得进展；
- 没有使用 AI 的用户，是能够独立完成任务，还是遇到困难却没有求助。

因此，**相同的调用次数或相似的聊天记录，可能对应完全不同的协作过程**。单纯保存对话，难以支撑协作过程审计、结果复现和行为分析。

### 1.2 整体含义

论文主张将人机交互视为“一等数据”：像数据库记录或科学工作流溯源对象一样，具有明确结构、上下文、来源和时间关系，能够被持久保存、独立查询、组合分析及重建。

其贡献分为三层：

1. **表示层：**提出交互描述语言 HAIDL。
2. **系统层：**实现 JupyterLab 中间件 HAIDL-X。
3. **分析层：**通过显式规则，将交互记录与执行证据组合为可追溯的行为解释。

这里的“可解释性”主要指**解释人机协作过程**，并非解释模型内部的推理机制。

## 2. 方法论：核心思想、关键技术与流程

### 2.1 将交互建模为计算状态转换

论文将一次交互表示为：用户从某个计算状态出发，提交请求，获得 AI 回答并进行评价或采取行动，最终进入新的计算状态。

- 交互前状态包括代码、运行输出、错误等。
- 交互内容包括请求、回答和用户反馈。
- 多次交互按时间排列，形成“交互轨迹”。

这种建模强调：**交互不仅是文本交换，也是嵌入计算过程的事件。**不过，状态变化与 AI 建议之间是否存在因果关系，仍需要额外证据判断。

### 2.2 HAIDL：统一的交互对象

HAIDL 使用受 BNF 启发的语法，将一次交互组织为七个组成部分：

| 组成部分 | 主要内容 |
|---|---|
| 记录元数据 | 记录标识及相关来源信息 |
| 用户请求 | 用户、单元格、时间、源代码、执行输出或错误 |
| 提示载荷 | 实际发送给模型的上下文化提示及时间 |
| AI 响应 | 回答、关联请求、时间和调用延迟 |
| 用户反馈 | Yes／No／Somewhat、关联任务及时间等 |
| 问题上下文 | 作业名称、具体问题标签 |
| 模型元数据 | 服务提供方、模型名称 |

重要设计是区分**用户提出的请求**与**系统实际构造的提示词**，以便追踪上下文包装如何影响模型输入。

### 2.3 区分“观测事实”与“推导知识”

论文使用独立的知识推导关系，将原始数据映射为更高层解释：

- **观测事实：**某个单元格出现运行错误。
- **事件解释：**用户在该错误状态下调用 AI，可解释为错误恢复类求助。
- **轨迹解释：**一次求助后没有可观察进展，随后再次求助，可形成重复求助模式。
- **行为解释：**结合执行表现、参与度和访问权限，形成特定学生—作业对的行为状态。

交互事件分为四类：

- 错误恢复；
- 卡住／下一步指导；
- 概念帮助；
- 验证已有工作。

**这些类别反映系统在可观察工作流中的作用，不等同于准确识别用户的真实心理意图。**

### 2.4 学习行为度量与规则

论文结合笔记本执行证据计算：

- **表现：**成功执行的任务代码单元格占比。虽然公式使用“正确解决”的措辞，实际采用的是无执行错误这一代理指标，并不验证语义正确性。
- **参与度：**有执行证据的代码单元格占比。
- **AI 使用强度：**交互次数。
- **错误导向使用比例：**带有错误输出的请求占比。
- **反馈率：**有显式反馈的交互占比。

随后将高／低表现与高／低参与度组合成四类相对画像，并结合访问条件推导行为状态。例如：

- 有访问权限、未使用 AI、表现较高 → 独立完成型；
- 有访问权限、未使用 AI、表现较低 → 论文称为“低参与挣扎型”；
- 使用 AI、表现较低，但持续参与或进行支持性求助 → 支架支持型学习者。

这些标签针对具体作业情境，不应被视为学生的固定特质。

### 2.5 HAIDL-X 的运行流程

系统包括 JupyterLab 扩展、前端客户端、后端服务器、HAIDL 表示层、模型提供方抽象层和 MongoDB 存储库。

每次调用的流程为：

1. 捕获当前代码、输出、错误及相关元数据；
2. 后端校验请求并构造上下文化提示；
3. 通过统一接口调用 AI 提供方；
4. 整合回答、延迟、上下文和可用反馈；
5. 持久化交互对象；
6. 按用户、任务、错误类型和时间顺序查询分析。

## 6. 主要结论与发现

### 6.1 行为分析发现

- **调用次数无法充分表征协作质量。**交互次数与成功执行单元格数、执行过的单元格数的相关系数均约为 **0.12**，仅呈弱相关。
- **任务影响求助类型。**算法任务中下一步指导较突出；PySpark 任务中错误恢复更突出，部分任务还有大量概念性求助。
- **高参与不等于高表现。**两次 Spark 作业分别出现 **8 个和 6 个**低表现、高参与的学生—作业对，表明“持续尝试但进展有限”不同于低活动状态。
- **零交互具有歧义。**有访问权限但没有交互的 **37 个学生—作业对**，需要结合执行表现才能进一步区分。
- **实际使用不等于实验分配。**共有 **26 个跨条件使用对**。
- 规则分析识别出 **29 个支架支持型学习者对**，探索性过度使用仅出现一次；但这些是规则下的行为解释，不是对学习改善或依赖程度的独立测量。

### 6.2 系统性能发现

| 指标 | 中位数 | P95 |
|---|---:|---:|
| HAIDL 对象大小 | 4.53 KB | 61.79 KB |
| 持久化延迟 | 1.40 ms | 1.97 ms |
| 学生—作业查询 | 0.399 ms | 0.581 ms |
| 含错误交互查询 | 0.399 ms | 0.711 ms |
| 有序轨迹查询 | 0.401 ms | 0.652 ms |

作者报告，在测试的提供方与并发配置下，服务器总延迟减去模型调用延迟所得的额外开销均保持在 **25 ms 以内**。

这些结果支持“在所测环境中采集成本较低”，但不能直接外推到大规模长期部署。

### 6.3 总体结论

论文最有力的结论是：

> 将交互上下文、AI 回答、执行证据和访问条件统一关联，能够支持比单独聊天记录或单独笔记本更丰富、可追溯的协作解释。

论文并未证明 HAIDL-X 提高了学习成绩，也未证明其行为标签准确反映用户真实意图。

## 7. 优点与亮点

- **问题定位清晰：**从“模型说了什么”推进到“AI 在实际任务中起了什么作用”。
- **表示与推断分离：**明确区分原始事实和规则解释，便于审计与修正规则。
- **上下文关联有价值：**将请求与代码、错误、任务、反馈及执行结果联系起来。
- **系统实现完整：**覆盖前端采集、模型调用、对象组装、持久化和查询。
- **提供方解耦：**统一表示不依赖某一家模型 API，便于替换模型。
- **真实场景验证：**保留非使用和跨条件使用，呈现了课堂部署的复杂性。
- **结论边界相对克制：**没有将描述性行为模式误当成学习效果的因果证明。

## 8. 不足与局限

### 8.1 形式化与规则仍不充分

- BNF 风格语法和推导关系提供了清晰框架，但未完整定义类型约束、缺失值处理、规则冲突、时间对齐及不确定性传播。
- 高／低表现、高使用强度、验证主导和“无进展”等判断的具体操作细节不够充分。
- 交互事件和画像缺少人工标注一致性、分类准确率及外部效度验证。

因此，其“形式化”更接近**结构化表示与规则推导框架**，尚非完整、严格验证的形式系统。

### 8.2 行为标签可能过度解释

- 无执行错误不代表代码逻辑正确或学生真正理解。
- 执行单元格较少不一定表示低参与，也可能是高效完成或在其他环境工作。
- 有错误时调用 AI，只能支持“错误相关求助”，不能证明错误最终被解决。
- 高表现且未使用 HAIDL-X，不排除使用外部工具。
- “低参与挣扎”“过度使用”等标签需要访谈或更丰富行为证据佐证，不宜直接用于评价学生。

### 8.3 连续状态与回放能力验证有限

- 提交的笔记本主要保留最终执行状态，可能遗漏被修复错误、撤销编辑和中间尝试。
- 系统未充分展示连续捕获所有后续操作的能力。
- 保存交互不等于能够确定性重现计算结果；还需要依赖版本、数据快照、随机种子、运行环境和模型版本等信息。

因此，论文支持的是**协作记录的重建基础**，而不是已经充分验证的端到端精确回放。

### 8.4 实验覆盖与系统评测有限

- 单课程、小样本，缺少软件工程、科研工作流等领域验证。
- 140 个分析对来自35名重复参与的学生，不能视为140个完全独立个体。
- 缺少消融、强基线和大规模数据库测试。
- 延迟差值未必覆盖前端、网络及异步反馈的完整端到端成本。
- 未充分说明测试硬件、数据库规模、索引、缓存和重复测量设置。

### 8.5 隐私与治理问题

系统可能保存学生身份、源代码、输出、错误和完整提示内容，因而需要：

- 知情同意与数据最小化；
- 去标识化和访问控制；
- 敏感代码及凭据脱敏；
- 数据保留、删除和审计机制。

论文对此讨论有限，而这些问题是大规模实际部署的重要前提。

**综合评价：**这是一项以数据模型和运行时基础设施为核心的研究。其主要价值是为人机协作建立可关联、可查询、可追溯的数据底座；现有证据足以支持原型可行性，但对行为推断准确性、跨领域泛化和完整复现能力的验证仍有明显提升空间。
