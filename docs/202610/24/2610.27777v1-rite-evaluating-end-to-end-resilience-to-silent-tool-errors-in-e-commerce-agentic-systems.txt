## ABSTRACT 

Tool-using LLM agents increasingly answer e-commerce queries through multi-step tool interactions. The expected output of a tool call can shift between agent development and execution, allowing a plausible but incorrect value to be returned without an explicit failure signal. These silent errors may propagate through sub-sequent decisions into final answers. To study agents’ resilience across this end-to-end process, we formulate Silent-error Resilience Task, an interactive task that evaluates whether they complete the original query after a silent error corrupts an intermediate state. We introduce RITE, a benchmark built from human-authored industrial workflows and production-log-derived inputs. To enable controlled and reproducible evaluation, we use a semantic error taxonomy to inject errors into fixed workflow prefixes, freeze recorded tool behavior, and let agents continue freely. It contains 167 matched units across nine e-commerce workflows, yield-ing 501 silent-error, correct-value, and explicit-failure instances. Across 10 recent LLMs, silent errors roughly halve task success and are consistently harder than explicit failures. Recognition, use of an available verification path, and integra-tion of the resulting evidence form successive bottlenecks. We also propose a light State Checker as an intervention to test whether resilience can be improved. 

## 1 INTRODUCTION 

Agentic LLM systems increasingly complete e-commerce tasks through multi-step workflows that invoke multiple external tools and pass their outputs from one step to the next. In industrial deploy-ments, a tool’s runtime output may differ from what the agent was built to expect because underlying business data, tool implementations, or deployed versions can change between development and ex-ecution. This build-time–runtime mismatch can remain hidden: a call may complete and conform to the expected API schema while returning a plausible value that is incorrect for the current task. We refer to such plausible-but-wrong intermediate values without an explicit failure signal as silent errors . For example, suppose a user mainly watches local football videos, one of which mentions blockchain-based fan tokens. During agent development, the profile tool returns “local sports”; af-ter an update that overweights “blockchain,” it returns “blockchain” at execution. The new label remains plausible and schema-valid, so no failure is signaled. The absence of an explicit failure signal makes silent errors particularly severe: an agent may have no immediate basis for detecting that the value is incorrect. It may therefore propagate the corrupted value through subsequent tool calls, allowing a single intermediate error to directly alter the final user-facing output. Existing benchmarks evaluate tool use in nominal settings (Qin et al., 2024; Trivedi et al., 2024; Ma et al., 2024), recovery from explicit or implicit faults injected while agents run (Zhu et al., 2026; Tian et al., 2026; Chen et al., 2026), silent-error detection (Sun et al., 2024; Mazumder & jahan Lia, 2026), or how corrupted intermediate values affect later outputs (Gurram, 2026). In these fault-based settings, each agent runs freely and meets a fault only if and when its own trajectory reaches the perturbed call, so different agents face silent errors at different points and with different histories. 1arXiv:2610.27777v1 [cs.AI] 20 Oct 2026 Published as a conference paper at ICLR 2027 They therefore cannot compare different agents on the same silent error at the same decision point, nor pair that error with correct-value and explicit-failure counterparts at that point. To address this gap, we formulate Silent-error Resilience Task, in which a plausible but incorrect tool result enters an agent’s execution history without an explicit failure signal. Given the query and toolbox, the agent operates in an agentic loop, repeatedly reasoning, calling tools that may return silent errors, and incorporating their outputs until it produces a final answer. The task asks whether the agent can recognize the error, reacquire reliable evidence, and complete the original query instead of propagating the error into its final answer. To evaluate this task under controlled conditions, we introduce RITE (Resilience to Incorrect Tool Evidence). Each human-authored workflow specifies a pre-orchestrated agentic process, and its execution log records tool calls and observations in the same format as an agent trajectory. We use this log as a fixed trajectory, allowing us to control where a silent error is introduced. We select a semantically important slot in the log and inject a silent error at that point. The trajectory up to and including this slot is provided as the agent’s prefix, while the workflow’s tools and their recorded input–output behavior are frozen to form the evaluation world, so that recorded calls return identical outputs across models and conditions. The agent then continues in an agentic loop, allowing us to compare its behavior while controlling for error type, slot, and environment. Following this protocol, we first construct a semantic taxonomy covering errors in object or category selection and in attributes or values. We sample inputs from the production logs of one internal platform and use them to run workflows deployed on a separate internal platform. From the resulting traces, we select task-relevant checkpoints and instantiate taxonomy-guided plausible but incorrect values. Each resulting unit contains matched prefixes for the silent-error, correct-value, and explicit-failure conditions, all paired with the same evaluation world. RITE contains 167 matched units from nine e-commerce workflows, yielding 501 instances. We evaluate 10 recent closed and open-weight LLMs on RITE. Across all models, silent errors reduce task success to roughly half of correct-condition performance and are consistently harder to handle than matched explicit failures. Our analysis traces this weakness through a three-stage chain: agents often fail to recognize that an inherited value may be wrong; recognition does not reliably lead them to refetch its source; and refetching does not guarantee that the corrected value is carried through to final recovery . We further find that most benchmark corruptions would change the downstream e-commerce task output, with damage varying substantially by error type and workflow position. Finally, a lightweight State Checker makes agents notice and refetch more often but yields only limited improvement in final task success. Making agents look is therefore easier than making them repair what they find. In summary, our contributions are: • Task formulation. We formulate Silent-error Resilience Task as an interactive agentic task for studying resilience to silent errors throughout the query-to-answer process. It evaluates whether an agent can recognize an unreliable tool result, reacquire trustworthy evidence, and still produce a correct final answer rather than propagate the error downstream. • Benchmark construction. We introduce RITE, which replays a human-authored workflow execution up to a selected point, returns a correct, silently incorrect, or explicitly failed result there, and lets the agent continue freely. Using inputs sampled from one internal platform’s production logs, workflows deployed on another, and a semantic error taxonomy, we construct 167 matched units across nine e-commerce workflows, comprising 501 silent-error, correct-value, and explicit-failure instances. • Empirical analysis. Across 10 LLMs, silent errors roughly halve task success. We identify recognition, producer refetch, and recovery as successive failure points, characterize effects by error type and position, and propose a lightweight State Checker as an intervention to test whether resilience can be improved. 

## 2 RELATED WORK 

Tool-use and agent evaluation. Agent evaluation spans three levels. At the tool-call level, Meta-Tool (Huang et al., 2024b) asks whether a tool is needed and which one to select, while ToolBench, BFCL, and API-Bank (Qin et al., 2024; Patil et al., 2025; Li et al., 2023) evaluate call construc-tion and extend to multi-tool, dependent, and stateful multi-turn interactions; ToolACE (Liu et al., 2Published as a conference paper at ICLR 2027 2025) provides synthesized data for improving these abilities. At the task-outcome level, AppWorld, GAIA, and WebArena (Trivedi et al., 2024; Mialon et al., 2024; Zhou et al., 2024) judge a complete rollout by its final answer or by the state it leaves in the environment, while allowing different valid action paths. At the process level, AgentBoard (Ma et al., 2024) tracks task progress, WorFBench (Qiao et al., 2025) evaluates generated workflow structure, ToolScan (Kokane et al., 2025) diagnoses call-level errors, and process-mining methods (van der Aalst, 2016) compare executed and expected flows. Across these levels, the benchmarks above vary task difficulty and agent behavior but do not systematically manipulate the semantic correctness of intermediate tool values. We instead vary the intermediate business value and ask whether an agent can still complete the task correctly when that value is wrong. To keep the test controlled and reproducible, we provide the recorded workflow execution up to the selected checkpoint as the agent’s initial history, then let it continue freely. 

Tool-failure recovery, silent-error detection, and error propagation. Work on unreliable tools can be separated by the stage of the error-handling chain that it evaluates. One line studies recovery from tool failures: agents resume from the environment left by a failed attempt (Tan et al., 2025), rewind to an earlier checkpoint (Zhuang et al., 2026), recover from explicit or implicit faults injected into tool responses while the agent runs (Zhu et al., 2026; Tian et al., 2026; Chen et al., 2026), or diagnose failed trajectories and characterize recovery cost (Vuddanti & Chittiprolu, 2026; Zhu et al., 2025; Zhang et al., 2026). Resumption settings start from uncontrolled natural failures, while injection settings expose an agent to a fault only if and when its own trajectory reaches the perturbed call. A second line studies silent-error detection, asking whether agents identify faulty outputs that trigger no exception (Sun et al., 2024) or silent data-quality faults introduced during controlled replay (Mazumder & jahan Lia, 2026). In both, the faulty response is delivered when the agent’s own run issues the corresponding call. A third line studies error propagation, tracing a schema-valid but semantically wrong argument to the final answer (Gurram, 2026) and measuring how perturbed requests or tool responses alter later calls and task outcomes (Xiong et al., 2025; Wang et al., 2026b). To our knowledge, RITE is the first benchmark to evaluate business-semantic silent errors at controlled decision points: every agent encounters the same plausible but incorrect value after the same recorded execution history, the same point is also instantiated with the correct value and with an explicit failure, and the agent then continues freely to a final answer. 

E-commerce and business-domain agents. Work in this domain spans three forms of capability. Domain models test whether a model understands products and users well enough to answer ques-tions (Peng et al., 2024), while recommender agents use that understanding to retrieve, rank, and rec-ommend products (Gao et al., 2023; Huang et al., 2024a). Shopping benchmarks place agents in in-teractive stores, where they must search, compare, and purchase while satisfying constraints on prod-ucts, vouchers, budgets, and sellers (Yao et al., 2023; Wang et al., 2026a). Business-service bench-marks require agents to interact with users over multiple turns, operate on business records through tools, and comply with domain policies (Yao et al., 2025; Wang et al., 2025), while CRMArena-Pro additionally tests confidentiality in enterprise workflows (Huang et al., 2026). These benchmarks do not systematically test what happens when a task-critical business value is silently corrupted. Grounded in production execution logs and human-authored industrial e-commerce workflows, our benchmark instead examines this reliability risk involving tools developed and maintained by mul-tiple parties: a call may complete while an intermediate business value is silently wrong. 

## 3 PROBLEM FORMULATION 

We study whether an agent can remain reliable when a tool silently returns an incorrect result and still complete the original task. We first formulate this end-to-end resilience as Silent-error Re-silience Task, then define how RITE evaluates it in this section. 

Silent-error Resilience Task. In a standard agentic task, an agent A receives a task query q and repeatedly selects and executes tool calls from a tool set T provided by an environment E. The interaction begins without a preloaded execution history, i.e., hstd 0 = ∅. At each step t, the agent observes the current history ht and selects an action at. The environment executes the action and returns an observation ot, which is appended to the history:

In de-ployed systems, changes to business data, tool implementations, or deployed ver-sions can cause runtime results to diverge from the expectations under which the agent was built. A call may still complete and conform to its API contract while re-turning a result that is incorrect for q. At a tool-call step j, let o⋆j denote the task-correct result and ˜oj the result actually returned by the tool. A silent error occurs when ˜oj differs from o⋆j in task-relevant meaning but remains plausible, schema-valid, and free of an explicit failure signal. Because the ordinary update rule still appends (aj , ˜oj ) to the history, subsequent actions condition on unreliable evidence and may propagate it into the final answer. The Silent-error Resilience Task measures whether the agent can still complete q after such a result has entered its execution history. Process measures track whether the agent recognizes the unreliable result, reacquires trustworthy evidence, and integrates that evidence into a correct final answer. The agent retains A0 and may reason from the current state, revisit or reissue an earlier tool call, seek corroborating evidence, or pursue another continuation.

## 4 BENCHMARK CONSTRUCTION AND EVALUATION ENVIRONMENT 

Each human-authored workflow specifies a pre-orchestrated agentic process. Its execution produces a controlled trace of tool calls and observations in the same format as an agent rollout. We use this trace to construct matched prefixes that share the preceding history and differ only in selected intermediate evidence; all prefixes are paired with the same continuation environment. Taxonomy definition. We constructed the silent-error taxonomy through a targeted, literature-grounded synthesis of adjacent error and failure taxonomies. We selected studies whose source cat-egories could clarify the boundary of a silent state corruption or be operationalized as schema-valid, plausible-but-wrong workflow values. For each relevant source category, two authors independently assessed its observable error signal, workflow locus, and suitability for conversion into a single-slot implicit perturbation. They then reconciled overlapping categories and clarified the resulting bound-aries. The final taxonomy contains seven leaf types organized into two semantic groups. Object or category selection errors cover substitution with a same-level category (category sibling drift), an ancestor or descendant (category granularity mismatch), or a similar but incorrect real entity (en-tity near-duplicate). Attribute or value errors cover changes to an entity’s attribute (profile attribute drift), movement to a neighboring valid numeric range (numeric bucket shift), superficially similar text with a different business meaning (semantic synonym drift), and reuse of a formerly valid but outdated value (temporal staleness). The benchmark instantiates every leaf type except temporal staleness. Although a stale value can be schema-valid and lead to an incorrect answer, recognizing that it is stale requires prior or time-indexed evidence that the agent does not observe. Appendix B provides the complete definitions, category boundaries, and literature grounding. 4.2 BENCHMARK INFRASTRUCTURE CONSTRUCTION

The data branch constructs the paired prefixes initializing an agent, whereas the environment branch independently constructs the world where the agent continues acting (Fig. 2). 

Workflow trace reconstruction. To avoid polluting the internal platform data, which may record the workflow execution result, we first post-process every selected workflow into a deployable replica by mocking out reporting and other side-effecting nodes and deploy the modified workflow back onto the platform. Then, a local central controller connects the log and workflow to provide an execution trace. It initially maps the production log record to the start schema of the deployed replica, producing the input xi. It then invokes the deployed workflow through the platform API with xi and retrieves the full execution trace of that run, which records every executed node with its arguments, outputs, status, and data dependencies. We retain only executions that complete suc-cessfully and contain full information needed to reconstruct the workflow state. The retained τi is therefore the clean execution record shared by the two downstream branches. 

Paired prefix construction. Slot selection. We align the workflow graph with τi and obtain an execution graph whose edges carry the values propagated between nodes. We then search this graph along producer → si → consumer → downstream result: an intermediate slot si qualifies when it 5Published as a conference paper at ICLR 2027 carries business-relevant content, is consumed downstream, and plausibly affects the task outcome. For each retained slot, we record its producer and consumer and determine the locus at which the intervention is realized, either in the producer observation ( tool output ) or in a downstream tool argument ( tool input ). A single execution yields multiple such slots, and each retained slot defines one task through the prefix built around it.

Verification. Before delivery, each candidate must preserve prefix executability and structural com-patibility. Four additional gates then check the intervention itself. (1) Plausibility. The explicit condition must expose an un-ambiguous failure signal. (3) Non-leakage. Neither the query nor the prefix may reveal that an intervention was applied. (4) Discriminability. The query remains solvable, and answers grounded in the gold value and in the polluted value must remain distinguishable under ci. The surviving artifacts are delivered in the formulation’s schema Dki = ( qi, p ki , c i), with all three conditions shar-ing the same query and result constraint. Providing every model with the same recorded execution before the affected value deliberately reduces variation in reaching that point, so the matched con-ditions focus on how agents handle the evidence they receive there.

## 5 EXPERIMENTS 

We evaluate 10 recent LLMs in three groups: two closed frontier models (Claude-Opus-4.8 and GPT-5.5), five open-weight frontier models (GLM-5.2, Kimi-K3, DeepSeek-V4-Pro, Hy3, and Qwen3.5-397B), and three smaller open-weight models (Qwen3.6-35B, Qwen3.5-35B, and Qwen3.5-122B). Each model runs all 501 instances at temperature 0 with a 25-step budget. Roll-outs invalidated by environment-side tool anomalies are excluded. F3: Producer refetch does not ensure recovery. To test whether producer refetch restores the correct evidence, the state judge compares the latest valid producer observation with the gold and polluted values. Among the 147 implicit-condition rollouts with a producer refetch, 87 (59.2%) match the gold value and 60 (40.8%) match neither value; none match the polluted value. Of the 87 matches, 85 are obtained in one re-query and the remaining two require multiple rounds. Among Noticed rollouts with a producer refetch, about one third still fail the task (RSR 0.655; F2). To understand why refetching does not ensure recovery, we manually inspect the 60 trajectories that did not match value, focusing on unsolved rollouts in which the re-query nonetheless returns usable evidence. After usable evidence is acquired, we identify three recurring patterns. First, reasoning overwrite occurs when a model initially uses recovered evidence but later replaces it with a self-imposed heuristic. In one trajectory, an agent reconstructs the correct timestamps and uses them in the next RPC call, but then redefines the “opening warm-up” boundary and selects the wrong final comment. Second, lossy selection occurs when a model alters recovered candidates while choosing among them. One agent merges two recovered topic clusters despite an instruction to select one, while another replaces the retrieved topic with a plausible but unsupported reformulation. Third, 

unsupported synthesis occurs when a model uses corrected evidence but adds claims absent from it. Agents incorporate corrected profile or interest labels but add unsupported viewing-duration, inter-action, or presentation claims. Across these patterns, usable evidence is obtained, but the correction does not carry through to the final answer. 

## 6 DISCUSSION 

The main results separate silent-error handling into recognition, use of an available verification path, and integration of the resulting evidence into final recovery. This section asks three follow-up questions: whether the resulting performance loss corresponds to changed e-commerce task outputs (D1), where the vulnerability concentrates (D2), and how far a light check can go (D3).

The gold and polluted values are judged to lead to different task outputs for 146 of 167 slots (87.4%). The change rate is at least 82.6% for every non-numeric error type and 65.6% for numeric bucket shifts. Restricting evaluation to the 146 output-changing slots changes mean Retention only from 0.416 to 0.408. ## 7 CONCLUSION 

We study silent errors in agentic tasks, where a plausible but incorrect tool result enters the execution history without an explicit failure signal and propagates through subsequent steps. We formulate a task that measures whether an agent can tolerate this corrupted state and still complete the origi-nal task, and introduce RITE, a benchmark built from 167 corruption slots across nine industrial e-commerce workflows grounded in real service logs. Across 10 recent LLMs, silent errors roughly halve task success and usually remain unnoticed; recovery remains incomplete even when models 9Published as a conference paper at ICLR 2027 question the affected evidence and re-query its producer. Further analysis shows that these errors of-ten alter downstream e-commerce outputs, with category errors and early-stage corruptions causing the greatest damage. Beyond the benchmark, we provide a simple reliability check that increases error detection and producer refetching more than final task success. 10 Published as a conference paper at ICLR 2027

## A WORKFLOW AND LOG DATA SOURCES 

This appendix documents two data-source stages: selecting the workflow collection W and mapping production logs to workflow inputs that yield eligible traces. It also records the resulting golden workflows. Workflow identifiers are anonymized and stable across the released artifacts. 

Workflow selection: structural validity. We inspected e-commerce applications at the DSL level and retained complete deterministic DAGs with explicit control flow. We excluded graphs contain-ing autonomous agentic nodes, atomic retrieval wrappers, short utility graphs, AB-test fragments, dangling references, or incomplete subgraphs. Fixed tool calls, read-only requests, code and LLM transformations, and explicit branch or loop nodes remained eligible. 

Workflow selection: task diversity. Because the application library contains multiple versions of many task families, we deduplicated each family, selected a representative complete version, and formed a set spanning different business stages, task objectives, and data dependencies. These two workflow checks yielded nine golden workflows. 

Log selection and trace retention. For each selected workflow, we mapped each candidate production-log record to the required start inputs and executed it on a structure-preserving replica. We selected a log only when its execution yielded a complete node-level trace with sufficient pro-cess depth and at least one business-semantic intermediate state that was produced upstream, con-sumed downstream, and locatable at a producer or consumer checkpoint. The corresponding trace was retained with the selected log. For safe trace collection, the replicas retained node identities, graph edges, data references, read-only retrieval, deterministic computation, and model-inference nodes, while writes, reporting calls, locks, memory updates, and external sends were neutralized or guarded. ## B SILENT -E RROR TAXONOMY AND LITERATURE EVIDENCE 

We synthesize 15 papers spanning agent and tool failures, data quality, and factuality. Two authors independently coded the error phenomena and boundaries described by each source, mapped over-lapping concepts to a common vocabulary, and reconciled the mappings. The resulting taxonomy describes the semantic form of a plausible but incorrect intermediate value. Injection location is recorded separately. B.1 OPERATIONAL DEFINITIONS 

The main taxonomy contains two semantic groups and seven leaves (Table 6). The first group changes which object or category is referenced; the second preserves the object while changing one of its attributes or values. Each leaf requires a schema-valid value whose task-relevant meaning differs from the recorded value. Table 6: Operational definitions and boundaries of the seven silent-error leaves.                 

> ID Leaf Operational definition Primary boundary L1.1 category sibling drift Replace a category with a nearby category at the same hierarchy level. Parent–child substitutions belong to L1.2. L1.2 category granularity mismatch
> Replace a category with an ancestor or descendant, making its scope too broad or too narrow. Same-level substitutions belong to L1.1. L1.3 entity near duplicate Replace the intended entity with another real, similar entity from the candidate domain. If entity identity is preserved and only an attribute changes, use L2.1. L2.1 profile attribute drift Preserve entity identity but replace a profile, preference, label, or other attribute with another valid value. Whole-entity replacement belongs to L1.3. L2.2 numeric bucket shift Move a numeric value or interval to a neighboring valid range. Malformed, impossible, or plainly out-of-range values are explicit failures. L2.3 semantic synonym drift Substitute text that appears semantically close but changes the business interpretation used downstream. Meaning-preserving paraphrases are not errors. L2.4 temporal staleness Reuse a value that was valid previously but is no longer correct at the task time. A contemporaneous neighboring numeric value belongs to L2.2.

The injection locus is annotated independently of the semantic leaf and takes one of two values: 

tool output , where the substitute is written into the producer observation, or tool input ,where it is written into a downstream tool argument. B.2 LITERATURE GROUNDING 

Silentness and exclusion boundaries. Tools Fail (Sun et al., 2024) establishes the central oper-ational criterion: a tool output may be schema-valid and wrong without raising an exception. The 

Tool-Augmented LLM Failure Taxonomy (Winston & Just, 2025) reinforces the distinction between explicit and silent failures. The LLM Hallucination Survey (Huang et al., 2025) and Where LLM Agents Fail (Zhu et al., 2025) further separate entity, context, profile, memory, and parameter er-rors, motivating value-level interventions while excluding failures that arise only from the agent’s internal reasoning or memory. Other taxonomies delimit the scope from adjacent phenomena: the 

Multi-Agent Failure Taxonomy (Cemri et al., 2025) covers behavioral and system failures, τ -bench (Yao et al., 2025) emphasizes domain-policy compliance, CRMArena-Pro (Huang et al., 2026) adds confidentiality failures, and Reasoning Error Localization (Tyen et al., 2024) distinguishes recog-nizing an error from correcting its downstream effects. Together, these sources define silent error 16 Published as a conference paper at ICLR 2027 as an incorrect intermediate value rather than a planning, collaboration, policy, confidentiality, or reasoning failure. 

Semantic distinctions. Data-quality and factuality research supplies the distinctions used to orga-nize the seven leaves. The Dirty Data Taxonomy (Kim et al., 2003) separates category, value, re-lation, and stale-data errors, supporting category-level substitutions, attribute and numeric changes, and temporal staleness. Faithfulness versus Factuality (Maynez et al., 2020) frames an error as a contradiction with its source evidence, providing a common criterion across all leaves. The taxon-omy of Factual Errors in Summarization (Tang et al., 2023) distinguishes entity, attribute, numeric, and temporal errors, which map naturally to entity near-duplicates, profile-attribute drift, numeric-bucket shifts, and temporal staleness. 

Specialized leaves and loci. Several sources refine particular boundaries. Butterfly Effects in Toolchains (Xiong et al., 2025) shows how incorrect tool arguments propagate downstream, mo-tivating tool input as an intervention locus in addition to tool output . Work on Duplicate Record Detection (Elmagarmid et al., 2007) motivates the distinction between real near-duplicate entities and superficially similar text. FreshLLMs (Vu et al., 2024) grounds temporal staleness in an-swers that change over time. Finally, LM-Emulated Sandbox Risks (Ruan et al., 2024) helps exclude system and safety failures from the semantic taxonomy. Taken together, the agent and tool literature defines when an error is silent and what lies outside scope, while the data-quality and factuality literature supplies the semantic forms of the corrupted value. We adapt these distinctions into schema-valid, single-slot workflow interventions; the seman-tic leaf describes what changed, and the locus records where that change enters the trajectory.

## D HUMAN VALIDATION OF RESULT AND NOTICED LABELS 

This appendix reports an independent human validation of two automatically produced evaluation labels: the LLM-based Result judgment that defines RSR and the trajectory-derived Noticed label. 

Recruitment and assignment. We recruited six university participants through a campus forum. The recruitment post described an approximately 50-minute annotation task, and each participant re-ceived RMB 50 upon completion. We selected 100 rollouts using stratified sampling: 28 were from the correct condition, 35 from the explicit-error condition, and 37 from the implicit-error condition, with 10 rollouts from each evaluated model. Within each stratum defined by model and condition, rollouts were drawn uniformly at random. Each rollout was independently assigned to three partic-ipants, and each participant annotated 50 rollouts, yielding 300 participant–rollout judgments. To balance overlap, each of the 20 possible three-person annotator groups was assigned five rollouts. Participants were instructed to work independently and not discuss individual cases. 

Two-stage annotation protocol. For each rollout, the interface presented the user task, the correct reference evidence, the complete agent trajectory, any new tool observations, and the final answer. Annotation then proceeded in two stages. In the blind stage, participants answered two binary questions: (i) whether the final answer solved the user task (Result), and (ii) whether the agent explicitly noticed a data anomaly and subsequently invoked a tool to verify it (Noticed). A Noticed label therefore required both an explicit recognition signal in the reasoning and a later verification action. Once submitted, these labels were locked. In the review stage, the interface revealed the two automatic evaluation labels and their rationales. Participants marked each label as agree , disagree ,or unsure , with an optional comment. Figure 4 illustrates the two stages. Because the second-stage responses may be influenced by the revealed rationales, we treat the blind-stage comparison as the primary validation and report review-stage agreement only as complementary evidence.

## G LIMITATIONS 

Several limitations qualify our findings. First, each silent-error instance contains a single corrupted value, and re-querying its producer returns the unpolluted response; RITE therefore measures recov-ery when a trustworthy verification path is available, and faults that persist across re-queries are left to future work. Second, recorded calls are replayed, whereas valid calls absent from the recordings are served by read-only live tools, so continuations that leave the recorded paths may observe cur-rent tool behavior. Third, temporal staleness is defined in the taxonomy but not instantiated. Finally, RSR relies on an LLM judge, whose errors may affect absolute scores. 24
