## 摘要
编码助手被普遍认为能够加快代码产出，但大多数相关论述止步于此。本文报告了一个合规要求严格、有人参与的考试评分系统从构建到部署的全过程。该系统由一名开发者独立构建，其间未手动编写任何代码；从利益相关者画像到行为审计，整个过程均由设有门控机制的流程加以保障。初始系统在三个工作日内完成构建，并已能够为真实考生群体评分。基于这段经历，我们提出一个观点：AI 对软件工程的影响，与其说是让编程更快，不如说是改变了稀缺资源的所在。代码编写变得充裕，而可靠评估——即判断结果是否正确、是否满足实际需求——在每次迭代中仍不可或缺，并成为制约进展的关键因素。工程判断力仍是另一项稀缺资源。若干缺陷通过了测试套件：它们出现在测试中被模拟的边界处，即浏览器与语言模型 API 的交互处，或仅在真实使用中才会显现。部署过程暴露了本地测试未能发现的假设。此外，AI 助手跨多个步骤执行任务时绕过了流程检查点，直到我们将其设为不可绕过的门控环节。这些观察均来自一个三重角色合一的案例：开发者同时也是最终用户和领域专家，因此专家判断能够即时获得，评估成本也低至极限。这种情形有利于体现迭代效率的提升；若评估需要更多人员或专业知识，这种提升可能会减弱。但这也使该案例成为检验评估稀缺性的严苛试验：评估仍然制约着进展。我们总结出五点经验：采用设有门控且可追溯的构建流程；明确哪些内容可以预先确定，并通过运行中的原型探索其余内容；在真实环境中进行验证；对助手本身设置门控，而不只是对其产出设置门控；记录决策及其假设，以及助手容易遗忘的流程状态。另一个项目也呈现出类似模式；一项由独立领域专家单独开展的案例进一步印证了这一转变。

## Abstract
Coding assistants are widely reported to speed up code production; most accounts stop there. We report the end-to-end construction and deployment of a compliance-critical, human-in-the-loop exam-grading system, built by a single developer who wrote no code by hand, protected by a gated process from stakeholder persona to audited behavior. The initial system was built in three working days and could grade a real cohort. We draw one claim from this experience: AI changes software engineering less by making programming faster than by changing what is scarce. Writing code becomes abundant. Reliable evaluation-knowing whether a result is correct and meets the actual need-remains necessary at every iteration and becomes the binding constraint. Engineering judgment remains a second scarcity. Several defects passed the test suite: they sat at the boundaries the tests had mocked, the browser and the language-model API, or appeared only in real use. Deployment exposed assumptions that local tests had missed. Moreover, an AI assistant acting across many steps bypassed process checkpoints until we made them enforceable gates. All of this was observed in a triple union: the developer was also the end user and domain expert, making expert judgment immediately available and evaluation as cheap as it can be. This favors the iteration gains, which may shrink where evaluation requires additional people or expertise, but makes the case a hard test for evaluation scarcity: evaluation still constrained progress. We draw five lessons: run a gated, traceable construction process; specify what is knowable and discover the rest against a running prototype; validate in the real environment; gate the assistant, not only the work; record decisions with their assumptions and the process state the assistant forgets. A second project showed similar patterns; an independent single-expert case corroborates the shift.
