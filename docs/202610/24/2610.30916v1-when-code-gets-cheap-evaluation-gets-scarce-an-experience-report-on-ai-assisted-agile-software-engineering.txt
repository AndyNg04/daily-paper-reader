# When Code Gets Cheap, Evaluation Gets Scarce: An Experience Report on AI-Assisted Agile Software Engineering 

Barbara Weber, Olaf Zimmermann, Marco Franceschetti 

University of St.Gallen 

St.Gallen, Switzerland {barbara.weber, olaf.zimmermann, marco.franceschetti}@unisg.ch 

Abstract —Coding assistants are widely reported to speed up code production; most accounts stop there. We report the end-to-end construction and deployment of a compliance-critical, human-in-the-loop exam-grading system, built by a single devel-oper who wrote no code by hand, protected by a gated process from stakeholder persona to audited behavior. The initial system was built in three working days and could grade a real cohort. We draw one claim from this experience: AI changes software engineering less by making programming faster than by chang-ing what is scarce. Writing code becomes abundant. Reliable evaluation—knowing whether a result is correct and meets the actual need—remains necessary at every iteration and becomes the binding constraint. Engineering judgment remains a second scarcity. Several defects passed the test suite: they sat at the boundaries the tests had mocked, the browser and the language-model API, or appeared only in real use. Deployment exposed assumptions that local tests had missed. Moreover, an AI assistant acting across many steps bypassed process checkpoints until we made them enforceable gates. All of this was observed in a triple union : the developer was also the end user and domain expert, making expert judgment immediately available and evaluation as cheap as it can be. This favors the iteration gains, which may shrink where evaluation requires additional people or expertise, but makes the case a hard test for evaluation scarcity: evaluation still constrained progress. We draw five lessons: 1) run a gated, traceable construction process; 2) specify what is knowable and discover the rest against a running prototype; 3) validate in the real environment; 4) gate the assistant, not only the work; 5) record decisions with their assumptions and the process state the assistant forgets. A second project by the same developer and assistant showed similar patterns, and an independent single-expert case corroborates the shift. 

Index Terms —AI-assisted software engineering; agentic coding assistants; software-engineering economics; test oracle problem; human-in-the-loop systems; agile software development. 

1. I NTRODUCTION 

Software engineering has traditionally treated implementa-tion as a substantial cost. Specifications, design reviews, and the division of labor help manage that cost. Large language model (LLM) coding assistants are now credited with large productivity gains [1]. But faster implementation raises a different question: what becomes costly when producing code is no longer the main constraint? Most accounts of assistants look at a narrow slice of the lifecycle, the generation and correctness of code [2]. They say little about requirements, testing, deployment, operation, or the changing role of the human. The shift toward judgment and evaluation as potential bottlenecks has been anticipated [3], but rarely documented across the development lifecycle. We examine it by reporting on the construction and deployment of a real-world system, including its failures: a human-in-the-loop exam-grading application that graded a real cohort under data-protection constraints. An LLM proposes a score and a rationale for each student answer against a rubric; the instructor reviews, accepts, or overrides every score, and every decision is recorded. The first author, who has a software-engineering background, built the application with an LLM coding assistant without writing any source code by hand; the paper refers to her as the developer. The grading application has since gone into institutional use in a university pilot, and the same process built a second application, also in use; the lessons held on both. Our experience suggests that the main effect of AI-assisted development is not simply faster implementation, but a shift in what limits progress. Code became cheap to produce, while evaluating whether it was correct and met the actual need re-mained necessary at every iteration. These human evaluations became the binding constraint. Furthermore, several defects escaped automated tests and appeared only in real use or deployment. Human engineering judgment remained essential for diagnosing failures and making technical decisions. Our setting was unusually favorable: the developer was also the user and domain expert, a combination we call the 

triple union . This made evaluation cheap, which limits how far the iteration gains generalize, yet makes the reported case a hard test for evaluation scarcity. We document the shift in what limits progress through the experience gained when building and deploying the human-in-the-loop exam-grading application outlined above. We draw five lessons from its recorded failures: 1) Run a gated, traceable construction process. Make each step, from stakeholder persona to audited behavior, pass a human or an automated gate. 2) Specify the knowable, discover the discoverable. Lock in requirements that can be stated in advance with speci-fications and tests; find those that only show themselves in use by building a candidate and reacting to it. 3) Validate in the real environment. Do not trust mocked arXiv:2610.30916v1 [cs.SE] 22 Oct 2026 tests alone: the costly defects passed them and surfaced only in the browser, at the model boundary, and on deployment. 4) Enforce oversight, do not assume it. An agentic assis-tant bypasses checkpoints that exist only as conventions; turn them into gates the process forces it to stop at. 5) Record what the assistant cannot hold. Let tests preserve correctness expectations, hand-off notes carry process state across sessions, and decision records keep each assumption with a revisit trigger. Sect. 2 reviews related work; Sects. 3 and 4 describe the system and construction process; Sect. 5 reports observations. Sect. 6 discusses the implications of these observations; Sect. 7 generalizes and gives recommendations. Sect. 8 examines limitations and Sect. 9 concludes the paper. 2. B ACKGROUND AND RELATED WORK 

Reducing the cost of implementation changes the balance of software-development work. It never becomes free, since tokens, subscriptions, and latency still cost, but it can become cheap enough to change how effort is allocated. Two ideas help explain this. Amdahl’s law [4] suggests that accelerating code generation has diminishing benefits when other activities remain unchanged. As generation gets cheaper, requirements, evaluation, and engineering judgment account for more of the effort. Cynefin’s distinction between complicated and complex situations [5] offers a related perspective: some requirements can be analyzed and specified in advance, while others require experimentation with working software. Cheaper implementa-tion makes the latter more practical. Evidence on coding assistants is mixed, and generation speed alone does not explain why. Field experiments report faster task completion [1] and a quarter more tasks finished [6]. A randomized trial with experienced developers in mature repositories found them 19% slower, while they believed themselves 20% faster [7]. Developers accept suggestions selectively [8], spend more of a session verifying them than on anything else [9], and write less secure code while trusting it more [10]. At enterprise scale, output doubled under a produc-tivity mandate, reviewer load doubled with it, and automated review overtook human review [11]. Despite differing tasks and settings, these studies suggest that gains appear where checking is cheap and losses where it is expensive; our case examines this observation across the development lifecycle. Closest to this paper are three bodies of work. The agentic software-engineering roadmap names the shift to software engineering for agents [12], and human-in-the-loop agent frameworks are already in production [13]. An independent single-expert case has the same shape as ours: velocity exposes failures, failures become durable controls, and judgment is the scarce input [14]. Our case differs in one respect: the developer was also the user and domain expert, making evalu-ation unusually cheap. The other relied more on deterministic controls. Comparing the two separates the cost of a trustworthy verdict from judgment in general. The harness literature treats an agent’s gates and checks as engineering work in its own right [15]–[18]. This paper offers an economic reading of why such controls become necessary, and reports experience from one concrete case where these controls changed after failures. Established ideas help interpret particular observations. The agile [19] and Lean Startup [20] traditions supply the short build–measure–learn loops we revisit, and set-based concurrent engineering [21] keeps several candidates open and decides late, an approach historically constrained by implementation cost [22]. Polanyi’s “we know more than we can tell” [23] motivates discovering tacit requirements by reacting to a prototype. The testing literature calls the constraint we meet the oracle problem [24], and language-model test generation inherits it [25], [26]. Transaction-cost economics [27] explains why cheaper construction changes what is worth delegating, and distributed cognition [28] why state must live outside a session that forgets. Bainbridge’s ironies of automation [29], revisited for generative AI [30], anticipate the out-of-the-loop problem this paper meets once the assistant acts across many steps. The software-architecture community’s “big questions” re-port [31] asks how human and machine should work together; a practitioner focus group at EuroPLoP 2026 has since col-lected answers [18]. Generated code must be checked [2], [26], [9]; new here is that evaluation can bind even when expert judgment is nearly free, because checks go uninvoked or exercise the wrong behavior, and that agentic generation removes the oversight passive autocomplete gave implicitly. 3. S YSTEM AND STUDY CONTEXT 

The system under study is the exam-grading application outlined in Sect. 1. It grades written exams against a rubric, and in principle any artifact a rubric can describe. Fig. 1 shows that AI has two distinct roles in it. At build time

At run time it is a component of the solution: it takes submissions as photographed handwritten exams, PDFs, or computational notebooks, transcribes the handwritten ones, and proposes rubric-anchored grades, which the teacher ac-cepts, overrides, or revises per question. Feature development followed a repeatable cycle of AI-assisted agile software engineering , refined after the first three days: (1) A user story fixed the acceptance criteria and the non-negotiable constraints. (2) A prompt specification captured what to build, why, how it fit the architecture, and what the tests must verify. (3) Work proceeded on a feature branch, test-first, red then green. (4) Validation ran on real data within minutes; the change then went through a pull request, with continuous integration and the developer’s validation as the merge gate, and no line-by-line code review. Fig. 2 shows the loop and its gates, with the artifact each step produces beneath it. The loop closes only at step (4), once the developer has confirmed the running behavior. One gate was not in the original design. The branch-and-pull-request step, with continuous integration, arrived on day five; it could still be bypassed, and on that same day the assistant did (Sect. 5.8). On day six a guard made the main branch unwritable for the assistant, and the step became a gate that cannot be skipped. A gate that had been a habit was rebuilt as structure. Its head stands still: the persona, a stakeholder written down once on day one, here a lecturer who must grade defensibly, whose obligations enter as non-negotiable constraints. Its tail is produced anew on every pass. A non-negotiable is met by a story’s acceptance criterion, which the prompt turns into a test obligation, which becomes an executable assertion, in practice almost verbatim, checking the specified behavior. One instance shows the traceability chain end to end. The persona is a lecturer who must grade defensibly; among her non-negotiables, written on day one: the tool must never auto-accept an AI-suggested score; every score requires an explicit teacher action . Story US-07 discharges it as an acceptance criterion: given no explicit action has been taken, no score is recorded and the question remains pending ; its sibling US-10 adds that every accept and override is logged with the AI score, the teacher score, a comment, and a timestamp, earlier decisions preserved in order. The prompt specification for the review screen restates both as test obligations: no score recorded until explicit action taken; multiple decisions on the same question all preserved . The suite holds them as assertions on the decision store, present since the initial commit: no decision exists before an action, a saved decision carries its type and timestamp, and a second decision appends rather than replaces. The audited behavior is the per-question decision list in the local record, the append-only trail of Sect. 3. Identifiers inside submitted artifacts lie beyond any asser-tion’s reach. Every artifact of this instance, the persona, the stories, the prompt specification, the tests, and an example record produced on the demo data, is in the artifact package (DOI: 10.5281/zenodo.23337589), together with Appendices A–D, the files of the harness described in Appendix D, and a dated commit log for every incident cited in Appendix A; the application source is in institutional use and available to reviewers on request. 5. O BSERVATIONS IN THE CASE 

This section reports eight observations, drawn from recorded incidents of construction, deployment, or mainte-nance of the grading system. We selected all incidents in the commit record and development notes that either changed the process or produced a defect that escaped the test suite and surfaced only when using the application. Appendix A links each observation to its incident, anchoring it in the record. 

5.1. Two regimes: the knowable and the discoverable 

The first incident occurred on day three, from a feature built exactly to its specification. A student-facing report for grade-review meetings passed its tests and was still wrong. Its acceptance criteria had specified a mechanism, per-criterion checkboxes, rather than the real need, readable feedback. The fix took two revisions, from per-criterion scores to AI-drafted readable explanations. The feature met its specification, but the specification missed the actual need: the requirement was tacit and became clear only through use. Not every requirement can be pinned down before code is written. Some are settled in advance; others surface only as the software runs. We call these types of requirements two regimes , in the economist’s neutral sense of a prevailing set of conditions, and read them as an economic take on Cynefin’s complicated and complex domains [5]. Knowable requirements, such as compliance, the data model, and the grading pipeline, are specified upfront and locked in by test-driven development (TDD). For discoverable requirements the running candidate helps establish the specification. The split is a continuum, not a clean binary: the compliance pipeline was knowable at its core yet carried discoverable interface work around it. The two regimes name the ends of a spectrum. The discoverable regime is common in product develop-ment. Contract work often begins with a client who holds requirements to elicit; in product development, more of them are found by building. Our setting is the extreme: a triple union in which developer, user, and domain expert are one person. The union collapses the classical separation of analyst, developer, and customer (end user) into a single judgment. 

5.2. The economics of iteration invert 

The student-facing report of Sect. 5.1 had been expensive to specify and cheap to rebuild: one iteration took minutes. That is the inversion: specifying a tacit requirement in advance now costs more than building a candidate and reacting to it, so building became the cheaper way to find the specification. The same held wherever a requirement was tacit. The candidate was critiqued and regenerated until it converged, and conver-gence stayed cheap only because the judge, the developer as domain expert, was at the screen due to the triple union. 

5.3. Mocked tests verify wiring, not reality 

Four features passed the full suite and an automated head-less smoke test, yet failed in use. An inline document preview rendered as a security error: the browser blocks data: URLs in iframes, which only a real browser shows. A generation feature silently produced empty output: the token budget truncated the response, which the tests could not see because they mock the language model. An overwrite was destructive only on an empty response from the language model, and a notebook plot was too large for the real API. All four incidents arose where the mocks end: at the browser, the language-model API, and the SDK boundary. They were found by running the system in its real envi-ronment, which no document or mock could replace. We learned that a green mock-based suite does not imply aworking system, the classicist argument against doubles at the seams [33], [34]. These failures differ in kind from the tacit requirement of Sect. 5.1: there the specification missed the need; here it captured the need, but the tests did not exercise the real environment, and a different oracle caught them. The most severe incident was a data-isolation defect: one exam’s edits surfaced in another. A hidden assumption about question identifiers caused it, not a mocked boundary. The defect survived several hundred passing tests and an automated interface harness. A human at the screen found and fixed it. 

5.4. Deployment surfaces hidden assumptions 

Moving from “runs locally” to “runs on a server” exposed issues our local tests had not predicted. The stack was modest: one application container that publishes no ports, behind a reverse proxy for HTTPS and basic authentication, on a com-mercial EU cloud host. Still, the first deployment ran into four issues. (1) A secret was mangled by variable interpolation: the container tooling ate the dollar signs in a password hash, and the proxy rejected the credential until every dollar was doubled and production read its secrets from a file. (2) A dependency that worked locally was missing from the manifest, and the export screen failed the first time it was opened on the server. (3) The private repository would not clone until a read-only deploy key was installed. (4) The hosting region had to be weighed against the data-protection requirement: EU hosting suits the demo with synthetic data, but real exam data carries a Swiss-residency requirement, so a Swiss host was needed before any deployment with real submissions. Each issue was minor, but together they made up much of the deployment work. All four came from infrastructure set up for the first time: a proxy, a server, a key, and a host. The fixes were captured in a runbook; with it, a first deployment takes about thirty minutes and a redeploy about five. Three tasks remained with the engineer: running the steps that required credentials, diagnosing failures as they occurred, and deciding where real data may be stored. 

5.5. Engineering judgment remains load-bearing 

In the build phase a clean division of labor held: the expert decides what, the assistant handles how. Deployment complicated it. The assistant generated the infrastructure and deployment configuration, firewall rules, the TLS reverse proxy, deploy keys, container and environment variables, and explained each step. The developer directed and executed an interactive, top-to-bottom deployment rather than authoring those configurations. The developer retained the decisions encoded in those configurations, such as the firewall posture and whether data may leave the machine, and the diagnosis when things failed: the deployment problems of Sect. 5.4, and two of the defects of Sect. 5.3, which took recognizing a browser restriction and a truncated response. The assistant’s output was confident and plausible even when wrong. These decisions and this diagnosis were the hard part, and they are engineering rather than domain work; the authoring of configuration text was not. A domain expert without that background might have been blocked, or might have shipped something broken or insecure. So the honest refinement of “zero lines of code” is that zero code is not zero technical skill. The assistant lowered the cost of writing software. It did not lower the cost of deciding, of diagnosing across mock boundaries, or of knowing when to distrust it. That is the clearest evidence for scoping the paper’s central claim: evaluation is not the sole scarcity that survives the assistant. Supervisory engineering judgment, the capacity to make these decisions and to diagnose when they fail, survives with it. 5.6. Refactoring across sessions: externalizing process state 

Maintenance was a third activity, beyond build and de-ployment. In five phases, a 2,434-line user-interface file was split into a package of seven modules, leaving 95 lines of wiring. The split followed domain-driven design but stayed deliberately partial, scaled to a single bounded context. An architecture test now guards the layering: it counts the places where the interface still depends directly on infrastructure, fails if a change adds one, and lowers its ceiling whenever one is removed, so the count can only go down. Refactoring is the knowable regime in its clearest form: the requirement, preserve behavior, is known in advance, and a regression suite of 492 tests, including 13 interface smoke tests, checked it. That made the work safe to spread over several sessions. A session is one conversation with the coding assistant; the next starts with no memory of it, only with what was written down. Two artifacts carried the work across that gap. The tests carried correctness: a resuming session did not have to trust the previous one’s claims, it re-ran them. A hand-off note carried the process state: what was done, the exact next step, the open decisions, and the constraints that must not be violated. Updated at the end of each session, it let the next one start where the last had stopped, a deliberate form of distributed cognition [28]. Tests and hand-off note differed in kind. The tests were non-negotiable; the note kept the work coherent. Without it, we think, the five phases would have become five ad-hoc cuts instead of one plan. A session boundary erases two things the code does not hold: why it was built this way, and what comes next. The note carried the second; the first lived in the developer’s head and in a session that no longer existed. Architectural decision records, adopted later, now capture it. 

5.7. Assistant advice produced technical debt 

When the code was modularized (Sect. 5.6), the developer asked the assistant to go one step further and move the scoring rules into a domain model of their own. The assistant advised against it: for a single bounded context, full domain-driven design would be over-engineering. The approved specification followed that advice, so the layers of Sect. 3 stayed as they were and the scoring rules stayed where they were, repeated inside each screen. The same afternoon a second grading paradigm was added. Every screen now needed the new rules, the copies drifted apart, and about fifteen screens showed silently wrong or empty results. That night the scattered rules were consolidated into one domain module, with the regression suite guarding the change. 

5.8. The assistant ran past the gates 

While the screens were being repaired, the assistant ran past the checkpoints the process intended: the branch-and-pull-request step was new that day, and nothing yet enforced it. Proposing, editing, and committing across many steps in one turn, it produced a run of implementation commits without a specification or a test, and nothing in the tooling stopped it. That day, five of 39 code commits carried a prompt specifica-tion, and eight user-interface iterations shipped without a test. Afterwards the deviation was plain in the commit record; while it happened, nobody could see it. From the next day on, every code commit reached the main branch through a pull request (cf. Fig. 2), and once a guard made the main branch unwritable for the assistant, 26 of 27 code changes carried a test and 22 a prompt specification. The recovery had setbacks, and a single developer’s before-and-after is anecdotal evidence. 6. I NTERPRETATION OF THE OBSERVATIONS

6.1. The shift in scarcity, and what it overturns 

Many classical software-engineering disciplines exist be-cause construction was expensive. When generation makes it cheap, their reasons weaken or turn around. Below we take five of them in turn, upfront specification and design, reuse over rewrite, low-fidelity prototyping, the division of labor, and delegation, and ask the same question of each: what did it save, and what of it survives when building costs little? A sixth paragraph covers the exception, latent assumptions, which cheap generation makes worse. 

Upfront specification and design paid off in the past because change was costly [35]. With cheap generation, foresight yields to discovery wherever requirements only show them-selves in use, the second regime of Sect. 5.1. The cost-of-change curve can flatten for behavior-preserving changes when a strong regression suite is cheap to maintain (Sect. 5.6). What survives is specification as a forcing function for thinking, and tests as the check that convergence needs. 

Reuse over rewrite often has amortized the cost of building [36]. A disposable rewrite now competes with reuse on cost. What survives is reuse of what was expensive to validate, not of what was expensive to write. 

Low-fidelity prototyping reduced risk before commitment, and sketches invited bolder critique than polished prototypes, because polish signalled that the design was settled [41], [42]. Functional prototypes are now as cheap as sketches, so fidelity becomes a communication choice rather than a cost constraint: a team can build the real thing and still mark it as provisional. Faking the hard part can cost more than building it. Staging convincing per-answer scores just to exercise the review workflow would have cost more than wiring the real grading call. Cheap building also admits set-based concurrent engineering [21], historically too costly for software [22]. And it moves the Lean Startup threshold [20]: when building a little more costs nothing real and evaluation binds, the minimum viable product shifts toward a more mature prototype. 

The division of labor has two classical rationales: special-ization [43], [44], and the cost of handoffs, which require explanation and waiting. Cheap generation weakens the second rationale where one person holds the domain knowledge and can take on the technical side through the assistant: analyst, developer, and customer collapse into that person, the triple union of Sect. 3. Where domain and technical expertise cannot sit in one head, the division stays. 

Delegation is the boundary case of the division of labor. It weighed communication cost against building cost [27]. When the expert with an assistant builds faster than a specification could be handed over, “faster to do it myself” becomes an economic prediction. In Brooks’s terms, generation drives ac-cidental complexity toward zero and leaves the essential [44]; judgment stays with the engineer (Sect. 5.5). 

Latent assumptions are where the pattern reverses. The discipline here, recording assumptions and revisiting them, does not weaken under cheap generation; it becomes more necessary, because an old failure becomes more likely. As-sumptions decay as requirements grow, and they are now easier to introduce and harder to notice. Such design erosion [45] can be avoided with evolutionary architecture and its fitness functions [46]. Generation adds a new twist, because it reasons locally. Each diff looks right on its own, so a choice that was sound under one requirement is silently invalidated by a later one. The data-isolation defect reported in Sect. 5.3 exemplifies the amplification of design erosion. 

6.2. Evaluation: the binding constraint 

Knowing whether a generated result is right is the costly step. Testing research calls it the oracle problem [24]. And 

right has two senses, matching the two regimes of Sect. 5.1: when we know what to build, the question is whether it is built correctly, verification; when we must discover what to build, whether it is the right thing, validation. In our case the two checks nearly fuse. Automated tests carry the mechanical part of verification. On top of them, the developer-user, who is also the domain expert, looks once at the running system on real data and confirms both that it works and that it is what was wanted — the step-4 gate shown in Fig. 2. The triple union brings this fusion. A trustworthy verdict can be scarce in two ways: it can be costly, or it can be neglected. Cost comes as latency or money per check, or as the realism that mocked tests lack when the only reliable judge is a user study. Cheap generation widens that realism gap while making it feel narrower. When a test costs about as much as the code it checks, coverage grows fastest where tests are trivial to write, in pure domain logic, and stays thin at the integration, framework, and SDK boundaries. The suite then comes back green where testing is easy and stays silent where the costly defects live, as Sect. 5.3 observed. Generated tests detected under a tenth of benchmark defects [26]; mutation-guided generation can steer them toward the hard cases [25], but only if chosen. Neglect is the other way: the verdict is cheap, yet it goes unconsulted. Our case is mainly one of neglect: expert judgment was near-free; what bound progress was whether it was invoked and what the check exercised. These two ways pose two ordered questions. First: is a cheap, trustworthy answer available? Only then: are the process’s gates hard enough that the assistant must stop at them? Where no affordable answer exists, there is nothing trustworthy to gate on. Our interpretation is that the second question only arises once the first is answered; conditioning method weight on system type is old [47], [48], this pair and its ordering are new. In our project the evaluator was cheap, so the second question became decisive. While the gates were soft, the check was there and went unasked, the lapse of Sect. 5.8, until the guard made the pull-request gate enforceable. Once the gates were hard, the inversions of Sect. 6.1 followed. Appendix C places a project on the two questions and reads off which disciplines will invert for it and which will hold. 

6.3. Where the cost migrates, and technical debt 

When construction becomes cheap, its cost migrates to whatever did not become cheap, an Amdahl’s-law effect [4]. The largest of those costs is evaluation; two others surface here. One is being wrong in production — a feature that is free to build is not free to ship, secure, and support (Sect. 5.4). The other is coherence. Adding one more function is trivial; keeping the growing set consistent, with no duplicated logic and a single source of truth, is not. This cost is hidden because each generation looks free on its own and the bill arrives only as the pieces drift apart. A missing abstraction, copied across many call sites, is technical debt [37], and near-free generation changes its economics: incurring the debt became cheap, servicing it did not. In Sect. 5.7, the principal was the domain model nobody built; the interest was every change touching every copy, invisible while only one grading paradigm existed. Separating concerns, a routine practice, would have prevented the debt; cheap duplication tempts one to skip the practice. The assistant did not only tolerate the debt; it argued for it. When the developer proposed a domain model for the scoring rules, the assistant advised against it as over-engineering. Sect. 6.2 named two ways a check can fail: it is too costly, or it is never asked. This episode shows a third. The check was cheap and it was asked; the developer received an answer and let it override her own judgment. In the lapse of Sect. 5.8 the assistant bypassed the human; here it persuaded her. 

6.4. The oversight inversion: the assistant can leave the loop 

The lapse of Sect. 5.8 shows a mechanism we call the over-sight inversion . With a passive autocomplete, the developer saw every change, because each one passed through her hands before it existed. Oversight needed no effort and could not be skipped. Agentic generation removes that guarantee: oversight stops being a property of the tool and becomes a discipline someone has to enforce. The phenomenon is old, the out-of-the-loop problem of human factors [29]; what is new is its cause, near-free generation pulling the human out. We claim this narrowly, for assistants that commit across many steps without each change passing through the developer’s hands. What fails is the human’s ability to intervene in time. An agentic assistant can finish and commit a divergent cascade before the intended checkpoint arrives; no single step reads as the violation, so a rule held only as a preference loses ground step by step. The defense is a hard gate the assistant must stop at; the gates presented in Sect. 4 were hardened this way. The irony is first-hand. The built grading system enforces that a human accept or override every AI grade; the process that built it left the equivalent gate as a preference, and the same class of assistant walked past it. 

6.5. Reasserting the gate: review and decision records 

In the lapse of Sect. 5.8, the oversight inversion, the human could not re-impose a gate while the assistant was running; in the debt episode of Sect. 5.7, a domain model stayed unbuilt because the assistant advised against it. Two defenses address them: the pull-request gate, continuous integration plus validation on real data, enforces the per-change check, and periodic whole-system review [38] finds accumulated debt. Whole-system review is neither the only defense nor the first. Hard gates stop the assistant before it diverges, the test suite holds the specified floor, and validation in the real environment remains the last check (Sect. 5.4). Review adds a scheduled look at the whole that no other layer provides: it catches the structural debt that accumulates quietly and the process drift the assistant will not report. In our case it surfaced the remaining scoring debt of Sect. 5.7 and drove its consolidation. This is the discipline cheap generation erodes, and a human has to reinstate it on purpose. Similarly, Davis et al. [14] report a single-expert case that inspected almost no generated code and moved every check expressible as a rule into deterministic controls. There, too, users found a defect the controls had missed: even a fully automated harness did not replace a human look at the running system. A second scheduled defense has since joined review: deci-sions recorded with their assumptions and an explicit revisit trigger, checked against each new requirement. These Archi-tectural Decision Records (ADRs) [39], with a definition of 

done [49], make the before-and-after visible: the assumption behind the data-isolation defect (Sect. 5.3) had no such record and decayed silently; an assumption we had recorded surfaced as anticipated when a later change strained it. Each gate was added after the failure that called for it. 

6.6. AI-assisted agile: reading the regime first 

Agile methods require disciplined practices but are rou-tinely mistaken for the absence of process. Vibe coding— accepting generated output without specifications, tests, or real validation—is such an absence: it keeps the speed of cheap generation and discards the feedback discipline, so it diverges instead of converging. What we report is the opposite: agile’s disciplines kept, the assistant used only to lower the cost of building. Fast iteration (Sect. 5.2) needs reliable evaluation to converge (Sect. 6.2); agile supplies mechanisms for it: tests for correctness [50] and acceptance criteria for fitness [32]. Cheap generation makes that discipline easier to abandon and therefore more necessary to enforce. It also shows the limits of the two extremes. Specification-driven development ignores the two regimes of Sect. 5.1 and specifies everything; vibe coding specifies nothing. Our practice decides first, for each requirement, whether it is knowable or discoverable: knowable requirements are specified and locked in by tests, discoverable ones are found by building a candidate and reacting to it. Our approach to AI-assisted agile software engineering needs an evaluator who answers fast enough to gate a loop of minutes and cheaply enough to be asked on every iteration; in our case, the domain expert. In such a loop, we expect speed to bind more than price: the evaluator must keep pace with generation or the loop stalls. Extreme programming’s on-site customer [40] addressed the same problem by co-locating the expert; the strongest configuration unites developer, user, and domain expert in one person, removing the handoff altogether. Pair programming is the practical fallback when that union is not available: the developer drives the assistant, paired with the domain expert or a user standing in for domain judgment, so evaluation stays present and quick instead of deferred. Whether pairing recovers what the triple union achieves is future work. The discussion in this section contains predictions; where the grading case supports them, the paragraphs point to the observations of Sect. 5. Two caveats apply. Generation is cheap, not free (Sect. 2). And one cost does not fall at all, the wait for an evaluator who is not the builder; it drives the last two predictions. 7. B EYOND THE CASE : T RANSFER AND 

RECOMMENDATIONS 

7.1. What transferred, what remains conjecture 

We built a second application, a co-creation review tool, following the construction process presented in Sect. 4, with the day-5 gates and the decision records in place from the beginning. This paper was first reviewed and revised in this tool, then edited further in Overleaf. The economics were similar in this second case: 19 user stories and 147 tests, deployed with a live human-and-AI review panel, were built in roughly two working days. Mid-course, the entire user-interface layer was rebuilt on a different stack in a few hours; the old interface had cost little to build. We did not observe the first project’s failure modes recurring. The review tool also contains the human gate of the construction cycle (Sect. 4, Fig. 2): every contribution the assistant makes stops at a human accept gate, and the record of these decisions is this paper’s own review history. All of this is corroboration: same developer, same assistant, same revised method. One case by other authors has since reported the same dy-namic, velocity exposing failures and failures becoming con-trols, and our observations in Sect. 5 are consistent with each of its testable propositions [14]. This provides cross-person corroboration absent from our study, though not methodolog-ical independence: both cases used assistants from the same model family and started from scratch. Four conjectures result. 

Teams. Several developers generating in parallel multiply divergence, so we expect coordination to dominate: required CI and code review, branch protection, a shared working agreement for the assistant, interface ownership turning from optional to essential. Code review would become the binding constraint; one practitioner’s agent-team experiment already reports that, with tickets cleared faster than humans could review or replenish them [3]. 

Adoption. The agile coach’s onboarding role persists but turns AI-aware, carrying the collaboration discipline and the distinction of Sect. 6.6. 

Apprenticeship reaches into teaching. Cheap generation absorbs Brooks’s accidental complexity and shifts the weight toward the essential [44]: design, requirements, and the evalu-ation judgment this paper finds decisive, a grounded response to the skills question the software-architecture community has posed for the generative-AI era [51]. Supervisory judgment was historically acquired through lower-level work now ab-sorbed by assistants, so classrooms may have to provide the experience practice no longer supplies. How teams and cur-ricula sustain apprenticeship under this inversion is a distinct question and warrants future investigation. 

The human’s own rhythm is a fourth conjecture. Dis-patching construction to the assistant makes the work event-driven: framing a task, waiting on it, then judging what returns. Whether that fragments attention, or erodes the concentration deep design needs, our experience surfaced but did not mea-sure; we recorded artifacts and economics, not the developer’s flow. It is a natural next measurement, and perhaps a design target: the artifacts that externalize correctness and process state might also protect the human’s attention. Our observations and their generalization are in line with what a focus group at EuroPLoP 2026 reported [18]. Its partic-ipants agreed that architectural decision-making, accountabil-ity, and the authoring of guardrails remain human tasks. They named harness engineering , the discipline of building what governs AI-assisted construction, as the emergent concept; proposed criticality, uncertainty combined with cost of change, as the criterion for calibrating human oversight; and warned of 

cognitive debt , the erosion of understanding when AI-assisted decisions are accepted without engagement. These findings parallel ours: the judgment that stayed load-bearing (Sect. 5.5), the harness of Appendix D, the stakes-dependent verdict (Sect. 6.2), and the debt the assistant defended (Sect. 6.3). 

7.2. Recommendations for Practitioners 

The observations of Sect. 5, their interpretation in Sect. 6, and the second case of Sect. 7.1 yield 13 recommendations, grouped by where the constraint now binds: specification, evaluation, and oversight. 

Specification. a) Keep agile’s disciplines , specifications, tests, real validation: cheap generation makes them easier to drop and more essential. b) Match the artifact to the regime :specify the knowable, prototype to discover the tacit, and avoid the two regime-blind failures, never specifying (“vibe coding”) and always specifying (“big design upfront”). c) Encode testable non-negotiables as assertions, not only prose ,so compliance and safety obligations can fail visibly in the suite. d) Record design decisions with their assumptions and a revisit trigger , for example as Y-statement records [39] or MADR [52], with a definition of done [49], and check them against every new requirement, to catch assumption decay before the next review. 

Evaluation. a) Validate in the real environment, not only against mocks : the browser, the language model, and integra-tion boundaries are where the costly defects hide, so budget deployment and operation as first-class work. b) Keep expert judgment in the loop at low cost , ideally by uniting developer, user, and domain expert in one person; test on realistic cases. 

c) Where no such union exists, try a surrogate : pair developer and domain expert on the tacit-requirement work, or rotate an on-site-customer role, and treat the expert’s feedback latency as the binding parameter it then becomes (Sect. 6.6). d) Spend freed capacity on signal, not on more building : prototype at high fidelity early, and drop to lower fidelity as a deliberate signal that a design is provisional. e) Externalize state, not just the check : tests carry correctness checks across sessions; a hand-off note preserves state for an amnesiac collaborator. 

Oversight. The assistant works inside a harness of gates, permissions, and checks, an engineering artifact in its own right and where the freed capacity goes; a) to c) concern the harness, d) the people. a) Gate the assistant, not only the work : a human stays in the loop automatically only while the assistant is passive, so make approval before construction and validation after it hard checkpoints the assistant must stop at (Sect. 6.4). b) Review periodically : schedule whole-system review as a ritual, not a reaction; it finds process drift and structural debt that per-change gates may miss (Sect. 6.5). c) Make the gate measurable : per-change specification-and-test presence and a ratcheted architecture ceiling turn “are the dis-ciplines holding?” into numbers. d) Count the apprenticeship cost , which no harness covers: when building is faster than delegating, juniors may lose chances to learn by doing; protect that path deliberately. 8. T HREATS TO VALIDITY 

Construct validity. This is a single-case, single-developer, self-reported study. As builder and evaluator, the same person produces and interprets the reported incidents. We mitigate this by linking observations to recorded artifacts: commits, the append-only audit trail, and the claim-to-incident map of Appendix A. We follow the LLM-study guidelines of [53]; the compliance record is in the artifact package. We report observations and mechanisms, not controlled measurements; hence, the numbers are descriptive. 

Internal validity. Two threats materialized inside the study. The assistant ran past the intended approval and validation gates on its own initiative: first-hand evidence of the oversight inversion, but also a study whose process was not always the process as designed (Sect. 5.8). A high-severity data-isolation defect, caused by question identifiers reused across exams, then passed several hundred green tests and an automated interface harness, and only use of the running system caught it (Sect. 5.3). That one cuts deeper: the suite this study uses as a correctness check can pass leaving a serious defect undetected. 

External validity. The case has one particular advantage: the developer is also the user and domain expert, making ex-pert evaluation available at negligible handoff cost. Hence, the boundary is the cost and availability of trustworthy evaluation. Work evaluated by external users may not share this advantage; internal tools with users as domain experts may come closer. The independent single-expert case sits on the far side of that boundary: its developer was neither user nor domain expert [14]. The triple union affects our findings differently. For the iteration gains it is the best case: evaluation was as cheap as it gets, so the size of those gains will not transfer. For evaluation scarcity it is the hardest case: evaluation bound progress even though the evaluator was nearly free, which shows that the scarcity lies in whether a check is invoked and what it exercises, and only secondarily in its price. Three further factors limit generalization. First, all results come from one model family, Anthropic’s Claude, in three successive versions during the study period. Second, the developer’s software-engineering training is what Sect. 5.5 found decisive, so domain experts without it may not get the same results. Third, the second project had the same developer, assistant, and revised method: it supports the findings within one developer but does not replicate them (Sect. 7.1). 9. S UMMARY AND CONCLUSIONS 

This experience report presented and reflected on the agile, AI-assisted development of a real-world academic grading system. The system graded a real cohort and remains in use and development, with further roll-out planned. The workflow is traceable through commits, prompt specifications, the appli-cation’s audit trail, and this paper’s own review record. The observations can be traced through the artifact package and, on request, the repositories, although independent reproduction is not possible. The threats discussed in Sect. 8 limit gener-alizability without invalidating the observed mechanisms and failure modes. Generation made construction nearly free; the scarce re-source became a trustworthy verdict on what was built. Requirements split into the knowable, to be specified, and the discoverable, to be found against a running prototype. Boundary defects escaped mocked tests; latent assumptions surfaced in real use. An assistant acting across many steps ran past soft gates until they were rebuilt as hard ones. And judgment stayed with the engineer: what to build, what to trust, and when to stop. Five lessons follow: 1) run a gated, traceable construction process; 2) specify what is knowable and discover the rest against a running prototype; 3) validate in the real environment; 4) gate the assistant, not only the work; 5) record decisions with their assumptions and the process state the assistant forgets. The reported case benefited from a triple union of developer, user, and domain expert in one person, which made expert evaluation nearly instant. Read together, the observations suggest that cheap gener-ation does not abolish software-engineering disciplines but changes why they are needed. Disciplines that saved con-struction cost lose that rationale; those that protect evaluation and coherence gain weight (Sect. 6.1). Whether a project benefits depends on whether a cheap, trustworthy verdict is available and whether the gates force the assistant to stop for it (Sect. 6.2). Once the assistant acts across many steps, the process, not the tool, must enforce oversight (Sect. 6.4). Zero hand-written code proved not to be zero technical skill. Open questions remain: whether pairing can stand in for the triple union, whether review becomes the bottleneck in teams, and how newcomers will acquire the supervisory judgment that lower-level work used to teach (Sect. 7.1). Software engineering has always optimized around what is scarce. AI changes the scarcity. The discipline must adapt. ACKNOWLEDGMENTS AND DECLARATION OF
