# MAS-Guard: Unified Guardrails from Individual Agents to Multi-Agent LLM Systems 

Mohammad Kachuee, Phu Mon Htut, Sheng Li, Nikolaos Pappas Miguel Ballesteros Martinez, Yassine Benajiba, Sujith Ravi, and Dan Roth 

Oracle AI 

Abstract 

Agentic AI extends large language models (LLMs) from generating responses to plan-ning and executing complex workflows, sub-stantially expanding their utility while expos-ing applications to unsafe actions, information leakage, and adversarial manipulation. Multi-agent systems further expand these capabili-ties through specialization and collaboration, but distributed authority, heterogeneous roles, and opaque or potentially compromised par-ticipants make safeguarding even more chal-lenging. Existing defenses address important individual threats but provide fragmented cov-erage across local execution, system-level in-teractions, and enforcement mechanisms. We introduce MAS-Guard, a unified framework that closes this gap for safeguarding single- and multi-agent AI applications containing both in-strumentable and opaque agents. Within in-strumentable agents, the proposed local Agent Guardrail (A-Guard) layer applies task-specific experts to assess agentic events. At the sys-tem level, developer-owned Agent Charters and a Control Plane combine deterministic struc-tural checks of routes, agent capabilities, and message formats with semantic assessments of roles and message content. These comple-mentary layers enable enforcement through a shared set of interventions: allow, reflection, confirmation, and block. Evaluated across six benchmarks covering diverse single- and multi-agent scenarios with three agent LLMs from different providers, MAS-Guard reduces the overall attack success rate by 71.5–86.3% rel-ative to unguarded agents, while meeting the utility reference criterion on benign tasks. 

1 Introduction 

Large language model (LLM) agents extend text generation into action by retrieving data, invoking tools, and collaborating with other agents. Tool-selection errors or malicious instructions in re-trieved content can trigger irreversible actions or disclose sensitive information. Recent studies re-port vulnerabilities such as indirect prompt injec-tion through tool outputs, taking unsafe actions, and observation or memory poisoning (Ruan et al., 2024; Greshake et al., 2023; Zhan et al., 2024; Debenedetti et al., 2024; Zhang et al., 2025). Multi-agent systems (MAS) built from LLM agents expand this attack surface. Inter-agent mes-sages serve simultaneously as task data and control signals; consequently, a local failure can propa-gate through delegation, shared context, and down-stream tool access. Attacks can spread injected instructions across agents, manipulate communi-cation channels, or disclose sensitive information (Lee and Tiwari, 2024; He et al., 2025; Patil et al., 2025; An et al., 2026; Kavathekar et al., 2026; El Yagoubi et al., 2026; Naik et al., 2026). Furthermore, real-world deployments may com-bine instrumentable agents , whose runtime allow guardrails to inspect and stop tool calls or mes-sages, with opaque agents , such as third-party services that expose only a request–response in-terface. AI safety risks are especially difficult to govern when a deployment combines instru-mentable agents, whose execution loops support local guardrail integration, with opaque agents, ac-cessible only through their external interfaces: no individual agent observes the full context, yet un-safe behavior can emerge at the shared boundaries. Existing defenses provide pieces of the solution. Prompt-isolation and injection-detection methods protect untrusted context; trajectory guard mod-els audit agent behavior; tool-call guards intervene before execution; and policy or information-flow systems enforce structured restrictions (Hines et al., 2024; Chennabasappa et al., 2025; Mou et al., 2026; Liu et al., 2026b; Costa et al., 2025; Wang et al., 2026). However, the literature remains fragmented along three dimensions. Surface fragmentation 

yields defenses specialized for prompt injection, tool use, or another isolated failure mode. Scope

fragmentation leaves most safeguards centered on one agent rather than the routes, roles, and trust boundaries of the composed application. Enforce-ment fragmentation makes it difficult to apply a consistent intervention policy across heterogeneous guardrails. Multi-agent defenses based on anomaly detection or permitted control-flow graphs address important subsets of these problems (Zhou et al., 2025; Jha et al., 2026), but do not by themselves provide a common guardrail layer spanning local agent execution and cross-agent boundaries. We introduce Multi-Agent System Guardrail, 

MAS-Guard , a unified runtime guardrail frame-work for applications containing one or more LLM agents. MAS-Guard operates over observable events at user–agent, agent–tool, and agent–agent boundaries (Figure 1). Here, a single-agent de-ployment is the special case with one agent and no agent–agent edges. For instrumentable agents, a local Agent Guardrail (A-Guard) layer selects task-specific experts for agentic events such as user inputs, tool calls, tool results, and final responses (Figure 2). At the system level, lightweight, developer-specified Agent Charters specify each agent’s intended role, input/output boundaries, and capabilities, while a Control Plane registers agents, governs communication routes, and configures de-terministic and semantic safeguards. In MAS-Guard, all safeguards share a common intervention space— ALLOW , REFLECT , CONFIRM , and BLOCK ,facilitating balanced choices between maintaining the user experience and enforcing agentic safety. Our contributions are as follows: • We introduce the Agent Guardrail (A-Guard), an extensible local defense layer for instru-mentable agents. A-Guard selects event-specific experts, evaluates them, and exposes a shared verdict interface for intervention be-fore content delivery or tool execution. • We propose a unified framework for ap-plications combining instrumentable and opaque agents under a trusted and instru-mentable MAS orchestration layer. We de-vise developer-owned Agent Charters and a Control Plane that connect local safeguards to system-level policy through deterministic structural checks, semantic compliance assess-ments, and consistent enforcement options. • To assess whether the framework’s benefits extend across agent models from different providers, we evaluate GPT-5.6-Terra (Ope-nAI, 2026c), Muse-Glimmer-30B (Meta, 2026), and Grok-4.3 (SpaceXAI, 2026) on six benchmarks, against eight defense methods and the unguarded baseline. The evaluation spans various prompt injection attack patterns, compromised multi-agent collaboration, pri-vacy leakage, reasoning slowdown, and unsafe tool execution. MAS-Guard reduces the over-all attack success rate by 71.5–86.3% while retaining benign task utility for each agent. 

2 Related Work 

Early work examines unsafe actions for under-specified requests through ToolEmu (Ruan et al., 2024) and indirect prompt injection through re-trieved content (Greshake et al., 2023). InjecAgent, 2AgentDojo, and Agent Security Bench evaluate injection and related failures in individual-agent environments (Zhan et al., 2024; Debenedetti et al., 2024; Zhang et al., 2025), motivating safeguards at local execution boundaries. Runtime defenses intervene at different stages. Sandwich reinforces task instructions (Schulhoff, 2024), while Delimiter marks untrusted content (Hines et al., 2024). ACI-Sentinel filters outputs for query relevance (An et al., 2026). LlamaFire-wall combines prompt-injection, alignment, and code-safety checks (Chennabasappa et al., 2025); ToolSafe assesses tool invocations and provides corrective feedback (Mou et al., 2026); and Agent-DoG audits agent trajectories (Liu et al., 2026b,a). FIDES alters access pattern to untrusted content using sandboxed access and query mechanisms (Costa et al., 2025), and AgentSpec applies trigger– predicate–enforcement rules (Wang et al., 2026). Multi-agent systems introduce additional risks. Prompt Infection and Agent-in-the-Middle attacks exploit instruction propagation and inter-agent communication (Lee and Tiwari, 2024; He et al., 2025). Privacy studies expose information leak-age and exfiltration (Patil et al., 2025; El Yagoubi et al., 2026; Naik et al., 2026), while TAMAS and ACIArena study attacks across frameworks and topologies (Kavathekar et al., 2026; An et al., 2026). Defenses include GUARDIAN’s error propaga-tion model (Zhou et al., 2025) and ControlValve’s control-flow constraints (Jha et al., 2026). MAS-Guard connects local safeguards with system-level policies over agent roles, communica-tion routes, and capabilities. Its Agent Charters and Control Plane combine deterministic and semantic checks with shared interventions across agents, pro-viding a common framework for integrating com-plementary safeguards.

Threat model and assumptions. An adversary may manipulate user inputs, tool outputs, external content, agent-to-agent messages, or one or more participating agents, with objectives such as unsafe action execution, information leakage, task manip-ulation, or resource exhaustion. We assume that the guardrail system G can observe and intercept events exposed by the MAS orchestration layer. We call an agent instrumentable when its run-time exposes integration points that allow us to ob-serve local execution events and enforce guardrail decisions before the corresponding action is exe-cuted or content is delivered or consumed. These integration points may include hooks for user in-puts, tool invocations, tool results, and agent re-sponses. Instrumentability concerns access to the agent’s execution loop; it does not require access to model weights, hidden reasoning, or all inter-nal state. An opaque agent , by contrast, exposes only external interaction boundaries. For exam-ple, agents built with the OpenAI Agents SDK or Google’s Agent Development Kit (ADK) can be instrumented as MAS-Guard can integrate with their runtime callbacks (OpenAI, 2026d; Google, 2026). A third-party proprietary agent accessed solely through the Agent2Agent (A2A) protocol exemplifies the opaque case when MAS-Guard can intercept exchanged messages without access to the agent’s internal execution loop (A2A Project).

4 MAS-Guard Framework 

4.1 Architecture Overview 

Figure 1 presents MAS-Guard as a protection layer for applications composed of one or more LLM agents. The framework combines safeguards within individual agents with system-level policy enforcement, protecting the execution of tasks as agents interact with users, tools, and other agents. These two layers provide complementary coverage: local safeguards inspect how an agent loop runs and uses its capabilities, while system safeguards as-sess whether its observable behavior is appropriate within the composed application. For illustration, consider an application that re-trieves department-level statistics and emails a sum-mary to a user-specified recipient. An orchestrator delegates retrieval to a SQL agent with a database-query tool and delivery to a notification agent with a sending tool. A malicious instruction embed-ded in a database result could attempt to redirect the workflow toward disclosing private records or notifying an unauthorized recipient. The application owner configures MAS-Guard through two complementary policy specifications. 

Agent Charters describe each agent’s intended role, input/output boundaries, and permitted capabili-ties. The Control Plane configuration binds these reusable contracts to runtime identities and speci-fies communication routes, applicable safeguards, and enforcement behavior. Within an instrumentable agent, the local Agent Guardrail (A-Guard) applies specialized experts at execution boundaries, for example, to detect in-jected instructions in a database result before the agent consumes it. The system layer combines deterministic checks of communication routes, de-clared message formats, and observable capabil-ities with semantic assessments of role and con-tent. Here, deterministic checks can reject a direct SQL-agent-to-email-service route, or a declared message type outside the receiver’s accepted for-mats. Semantic checks can audit message content for unauthorized information leak. 

> Figure 2: A-Guard provides a local guardrail layer to audit agentic events for instrumentable agents.

MAS-Guard supports realistic deployments in which some individual agents are opaque, provided that the MAS orchestration layer remains trusted, observable, and instrumentable. Such agents are guarded at their exposed boundaries, while instru-mentable agents additionally receive local A-Guard protection. A single-agent application is supported as a special case of a multi-agent application. 

4.2 Local Guardrail Layer 

A-Guard is the local guardrail component of MAS-Guard, typically integrated through the agent exe-cution hooks (Section 3). A-Guard intercepts local events including user inputs, tool registrations, tool invocations, tool results, and agent responses be-fore they are observed, delivered, or executed. A-Guard organizes safeguards as task-specific 

experts . Each expert declares the event types and static conditions under which it is applicable. For an event et, A-Guard selects 

Et = {gk : eligible k(τt, c t, Π) = 1 } , (4) where Et is the set of eligible experts. Eligibility rules avoid unnecessary model calls by excluding irrelevant events or trusted cases. The selected experts execute in parallel and emit verdicts in a shared output space. Their outputs are passed to the enforcement mechanism described in Section 4.4. Our implementation instantiates three guardrail experts: User Prompt Injection , which detects di-4rect prompt injection instructions in user turns; 

Tool-Result Prompt Injection , which detects in-direct prompt injection instructions embedded in external tool results; and Sensitive Unintended Tool Call , which assesses whether a non-read-only action is supported by the user’s intent and execution context. We selected these ex-perts to address the Prompt Injection and Ex-cessive Agency risk categories identified in the OWASP Top 10 for LLM Applications (OWASP Foundation, 2025). We implement these ex-perts using task-specific prompts optimized for 

Gemma-4-26B-A4B-IT (Gemma Team, 2026), in-dependent of the acting agent model. We optimized the guardrail prompts using an automated prompt optimization (APO) loop in-spired by Autoresearch (Karpathy, 2026) and Meta-Harness (Lee et al., 2026), in which an optimiza-tion agent iteratively analyzez evaluation results and failure cases, proposes targeted revisions, and verifies them on a disjoint development set. Ap-pendix E.3 details the optimization loop design, development datasets, candidate generation, and optimization objective. The proposed architecture is not restricted to these experts or this choice of underlying model: additional heterogeneous safe-guards can be registered to cover broader vulnera-bilities. Implementation details in Appendix E. 

4.3 System Guardrail Layer 

The system guardrail layer governs the applica-tion’s behavior using agent roles, input/output con-tracts, routes, and capabilities. It evaluates the boundaries exposed by the orchestration layer, in-cluding user-facing inputs and outputs, coordina-tion or delegation among agents, and boundary events produced by opaque agents whose internal execution cannot be instrumented. This scope al-lows the same policy framework to protect both instrumentable agents and the observable MAS system-level interfaces. To represent these policies in MAS-Guard, each 

Agent Charter specifies a reusable role contract through its charter_id , objective , input/output (I/O ) contracts, and features . Each input/output contract specifies accepted message formats, pro-hibited content types, and a semantic topic policy. Content type restrictions identify categories that must not appear, such as credentials or personal information. 4.4 Enforcement and Mitigation 

Each local or system-level safeguard returns a bi-nary violation trigger and a rationale. The config-ured enforcement policy maps each violation to an intervention. MAS-Guard aggregates the ver-dicts into one of four decisions. A LLOW admits the event without intervention. R EFLECTION is a non-blocking intervention for potentially correctable behavior; additional guardrail feedback is provided to the agent so it can correct its course. CON - 

> FIRMATION

pauses the event to require explicit user approval, particularly suitable for ambiguous or sensitive actions. Finally, B LOCK prevents the event from being delivered or executed when a clear policy or safety violation is detected. REFLECTION > ALLOW . This keeps verdict ag-gregation deterministic and avoids introducing an additional model-based decision layer. 

5 Experiments 

We evaluate MAS-Guard through three research questions: (RQ1) whether it reduces attack success without materially degrading benign-task utility; 

(RQ2) whether the safety–utility trade-off transfers across agent backbones and attack families; and 

(RQ3) how much the local A-Guard, deterministic, and semantic system checks each contribute. 

5.1 Experiment Setup 5.1.1 Benchmarks 

Our evaluation suite contains four multi-agent and two single-agent benchmarks, summarized in Ta-ble 2. ACIArena (An et al., 2026), TAMAS (Ka-vathekar et al., 2026), AgentLeak (El Yagoubi et al., 2026), and OmniLeak (Naik et al., 2026) 1 ex-ercise cross-agent instruction propagation, com-munication compromise, privacy leakage, and un-safe delegation across heterogeneous multi-agent topologies. OverThink (Kumar et al., 2025) and Agent Security Bench (ASB) (Zhang et al., 2025) test coverage for local vulnerabilities, including performance sabotage, direct and indirect prompt injection, memory poisoning, and malicious tool execution. This mixture is intentional: a unified guardrail should protect both internal agent events and system-boundary interactions. 

5.1.2 Metrics 

We jointly assess safety and usefulness through attack success rate (ASR) and Utility. ASR mea-sures the proportion of adversarial cases in which the attacker achieves the malicious objective, while Utility measures task success on benign cases. For each benchmark, we retain its definitions of attack success and task completion where they align with these general definitions. Table 2 summarizes the operational definitions used in our experiments. For each metric, overall results are sample-weighted means across benchmarks. 5.1.3 Agents and Guardrail Baselines 

We repeat our experiments with three agent models: GPT-5.6-Terra and Grok-4.3 as pro-prietary LLMs, together with Muse-Glimmer-30B as an open-source LLM. Note that MAS-Guard’s semantic experts use the separate 

Gemma-4-26B-A4B-IT (Gemma Team et al., 2026) model described in Section 4.2, separating the model that generates an action from the model that audits it. We used Codex (OpenAI, 2026a) with GPT-5.6-Sol (OpenAI, 2026b) at high reasoning effort to author the MAS-Guard Agent Charters and Control Plane configurations. For each pub-lic benchmark, the provided context contained the benchmark documentation and a development sam-ple set disjoint from the test set used for the re-ported evaluation. Appendix G provides further details and examples. To cover a diverse comparison space, we include methods ranging from lightweight prompt defenses to structural changes in agent execution and inde-pendent guardrail models. Sandwich (Schulhoff, 2024) and Delimiter (Hines et al., 2024) repre-sent prompt-based defenses that rewrite or mark untrusted input. ACI-Sentinel (An et al., 2026) represents model-based output filtering, while Lla-maFirewall (Chennabasappa et al., 2025) provides a guardrail system spanning prompt, alignment, and code checks. ToolSafe (Mou et al., 2026) is a specialized tool-invocation safety model, and AgentDoG (Liu et al., 2026b) and AgentDoG-1.5 (Liu et al., 2026a) are independent trajectory-level guardrail models. FIDES (Costa et al., 2025) represents a control and data flow approach that keeps untrusted values out of planner context through sandboxed value queries and opaque ref-erences. No-Guardrail retains the agent model’s native safety behavior. Appendix H details method configurations, benchmark execution-loop integra-tion, and enforcement setup in our experiments.

5.2.2 Benchmark Results 

Table 3 presents the benchmark-level ASR results for the GPT-5.6-Terra agent. MAS-Guard lowers ASR relative to No-Guardrail on all six benchmarks for GPT-5.6-Terra. The largest reductions occur on ASB (44.6% to 13.2%), OverThink (34.5% to 0.0%), and AgentLeak (23.1% to 5.0%). It also reduces cascading-injection ASR on ACIArena from 24.0% to 11.0% and matches the best Utility-preserving result on TAMAS. Overall, MAS-Guard obtains the best performance on four of six bench-marks and the lowest aggregate ASR. FIDES achieves lower ASR on ACIArena and AgentLeak while meeting their utility reference criteria, potentially benefiting from its isolation of untrusted data from planner context. However, its overall ASR is higher than MAS-Guard’s, and its overall Utility falls below the reference thresh-old. Delimiter’s simple approach is highly effec-tive against OverThink’s injected reasoning decoys, yet transfers poorly to ACIArena and AgentLeak. ToolSafe and the AgentDoG variants suppress ma-licious tool use on ASB, but their ASR reduction is accompanied by Utility regressions. A-Guard applies experts within instrumentable agents, while Agent Charters and a Control Plane govern observable application boundaries through deter-ministic and semantic checks. A shared interven-tion space provides consistent enforcement across layers, supporting deployments containing instru-mentable and opaque agents. Across six bench-marks and three agent LLMs, MAS-Guard reduces overall ASR by 71.5–86.3% relative to unguarded execution while meeting the utility criterion. These results support combining local safeguards with application-specific policy enforcement to address agentic risks while preserving benign-task utility. MAS-Guard provides a framework for coordinat-ing safeguards across heterogeneous agents under developer-owned contracts. 8Limitations 

We consider heterogeneous multi-agent deploy-ments in which a subset of participating agents may be opaque. However, we assume that the multi-agent orchestration framework is observable, in-strumentable, and trusted. Under this assumption, for opaque agents, protection is limited to exter-nal inputs and outputs: internal prompt injection, memory corruption, hidden tool use, and other un-exposed actions may remain undetected. Boundary checks cannot undo side effects that have already occurred internally or guarantee that all malicious behavior becomes externally visible. Furthermore, compromise of the operating sys-tem, runtime, or orchestration infrastructure, and attacks on agent-to-agent transport channels that bypass interception, are outside this threat model. Access control, tool permissions, sandboxing, au-thentication, encryption, and network security re-main important, orthogonal areas of security engi-neering. MAS-Guard’s checks on declared routes and capabilities complement these controls but are not a replacement and do not implement their un-derlying security guarantees. We also assume a trusted application owner who authors Agent Charters and configures MAS-Guard Control Plane. Although we used AI assistance to produce experimental configurations, application developers must ultimately own, vet, and maintain the Agent Charters and Control Plane configura-tions used in real deployments. Defining these con-tracts requires application-specific judgments about legitimate workflows, role boundaries, data sensi-tivity, and permitted capabilities. Incomplete or overly permissive policies can leave unsafe behav-ior unconstrained, while overly restrictive policies can suppress legitimate tasks. Lastly, to simplify our experiment setup and make comparisons easier, we use ASR as an um-brella term for rate of successful attacks in our experiments; therefore, the reported results should not be interpreted as a severity-weighted or abso-lute measure of real-world harm. For consistent comparisons across benchmarks, we measure Util-ity only on benign episodes, leaving legitimate-task completion under attack for future studies. 

Ethical Considerations 

MAS-Guard proposes guardrails intended to sup-port safer and more responsible use of agentic AI through enforcement of application-owner policies. Such policies may themselves be incomplete or in-appropriate, and guardrail errors may permit harm-ful actions or block legitimate tasks. Our bench-mark results therefore do not establish safety for arbitrary deployments. Real-world deployments should include review of the governing policies, application-specific evaluation, and appropriate hu-man oversight. Although intended for defense, MAS-Guard could be incorporated into an adversarial simula-tion loop, using guardrail feedback to iteratively develop stronger malicious attacks. To limit this risk, we do not publicly release the exact guardrail prompts, and we are instead considering availabil-ity through controlled access, while acknowledging the resulting limitation on reproducibility.

11 A Agent Charter Schema 

An Agent Charter is a reusable, system-owner-authored contract for one agent role. It describes acceptable behavior at observable system bound-aries rather than asserting how the agent is imple-mented internally. Runtime identities are bound to Charters by the Control Plane (Appendix B), so multiple agents that implement the same reviewed role may share one Charter. 

Schema. Table 5 gives the Charter fields and closed vocabularies used in our evaluation. Each semantic topic is a record containing a unique topic_id , a short title , and a natural-language description . Topic policy may be 

unconstrained , an allowlist , a denylist , or 

allow_and_deny . An allowlist requires at least one accepted topic, a denylist requires at least one prohibited topic, and the combined mode requires both. 

Compliance semantics. For a mediated interac-tion, Charter Compliance considers the sender’s output contract and the receiver’s input contract. Format checks compare the event’s declared con-tent type with the corresponding accepted formats. Feature checks use instrumented capability sig-nals (not keyword matches in message text) as well as structural evidence such as a broadcast route. Prohibited-content classes are evaluated with lightweight pattern scanners or configured guardrail classifiers, while topic policies use a se-mantic topic classifier.

Compilation and event processing. Before ex-ecution, MAS-Guard validates unique Charter, agent, and guardrail IDs; resolves every registry-to-Charter reference; rejects routes containing un-known endpoints or appearing in both route tables; and resolves all configured classifiers and A-Guard attachments. For each event, the Control Plane first re-solves both endpoint Charters and then applies route policy with precedence always_block >

always_allow > the unlisted-route action. An allowed route only establishes that the commu-nication edge may exist; it does not bypass con-tent or Charter checks. For an admitted event, all guardrails bound to its event type run, and their out-puts are combined using the decision ordering in Section 4.4. In shadow mode the resulting decision is logged while the event passes; in enforcement mode it is applied. 13 C Detailed Results 

Tables 7 and 8 extend the benchmark-level ASR analysis to Muse-Glimmer-30B and Grok-4.3. MAS-Guard reduces overall ASR from 30.6% to 4.2% and from 30.9% to 8.8%, respectively, achiev-ing the lowest overall ASR point estimate among the evaluated methods for both backbones. It re-duces ASR on five of six benchmarks in each setting. The remaining benchmark is unchanged: OmniLeak stays at 0.1% for Muse-Glimmer-30B, while OverThink remains at the already-zero un-guarded result for Grok-4.3. The benchmark breakdown reveals variation in both baseline vulnerability and residual risk. For Muse-Glimmer-30B, MAS-Guard reduces Over-Think ASR from 36.6% to 0.0% and ACIArena ASR from 40.0% to 7.9%. For Grok-4.3, substan-tial reductions occur on ASB (70.8% to 13.8%) and OmniLeak (16.3% to 0.1%). Nevertheless, Grok-4.3 retains higher residual ASR on ACIArena and AgentLeak, at 26.6% and 17.0%, compared with 7.9% and 3.8% for Muse-Glimmer-30B. Thus, the aggregate improvements extend across backbones, although protection remains dependent on the agent and evaluation setting. Tables 9, 10, and 11 report the corresponding benign-task Utility. Overall Utility changes from 50.0% to 48.4% for GPT-5.6-Terra, from 50.7% to 50.2% for Muse-Glimmer-30B, and from 59.0% to 58.4% for Grok-4.3. These represent decreases of 1.6, 0.5, and 0.6 percentage points, respectively. In each case, the guarded point estimate remains above the lower endpoint of the unguarded base-line’s 95% confidence interval, satisfying the utility reference criterion. The comparisons also illustrate why ASR and Utility should be interpreted jointly. FIDES achieves lower ASR than MAS-Guard on ACIA-rena and AgentLeak across all three backbones, but its overall Utility falls below the reference thresh-old in every setting. On ASB with Grok-4.3, Tool-Safe achieves an ASR of 1.0%, compared with MAS-Guard’s 13.8%, while its Utility is 49.1%, compared with 65.2% for MAS-Guard. Such dif-ferences show that strong attack suppression on an individual benchmark can accompany substantial reductions in benign-task performance, motivating comparison at both the benchmark and aggregate levels.

This appendix specifies the local A-Guard compo-nent introduced in Section 4.2: deterministic expert eligibility, expert-specific input construction and classification, and verdict aggregation. The prompt descriptions below summarize the classification ob-jectives and decision boundaries; they are not the verbatim templates used by the experts. 

Note: As a precaution against prompt-specific evasion and misuse, we do not publicly release the verbatim expert prompts. The summaries specify the intended behavior but are not substitutes for the exact templates. We are exploring a controlled-access process to share the prompts confidentially with qualified researchers. 

E.1 Event representation and eligibility 

An A-Guard event contains a type, an ordered mes-sage history, and available tool definitions. A static orchestrator selects experts using the event type. The three experts cover the following local sur-faces:     

> Expert Eligible event Decision
> User Prompt Injection User input. BLOCK
> Tool-Result Prompt Injection Tool result. BLOCK
> Sensitive Unintended Tool Call Tool invocation with at least one call not explicitly marked read-only. CONFIRM

For tool-call eligibility, the checker inspects the latest assistant message containing proposed calls and matches function names to the registered tool definitions. A call is treated as read-only only when its definition supplies the Boolean annotation 

readOnlyHint=true ; missing definitions, missing or non-Boolean annotations, and malformed calls do not qualify for this exemption. No proposed calls, or a batch consisting entirely of explicitly read-only calls, makes this expert ineligible. These annotations are supplied by the trusted integration, not inferred from a tool name or from retrieved text. Tool registrations, agent responses, and RAG-database insertions are covered by the proposed event interface but have no eligible expert in the current implementation and experiments. 

E.2 Expert inputs and prompt summaries 

Each expert receives a fixed classifier instruction and a task-specific projection of the event. It returns a JSON object with a binary decision (ALLOW or 

BLOCK ) and a short reason . If no expert is eligible, A-Guard returns ALLOW .

User Prompt Injection. The input is the lat-est user-message text. The prompt asks whether that message attempts to manipulate the assistant’s instruction hierarchy, obtain hidden instructions, weaken safety enforcement, or elicit harmful behav-ior through a jailbreak. It distinguishes these cases from ordinary task requests, formatting preferences, benign role assignments, technical administration, and analytical discussion of security-sensitive top-ics. Classification depends on the requested behav-ior, not isolated keywords or tone; ambiguous frag-ments without a clear violation default to ALLOW .

Tool-Result Prompt Injection. The input con-tains tool-result messages extracted from recent context and the latest available user message as task context. The prompt asks whether the returned con-tent functions as a live instruction to the assistant or its toolchain: for example, overriding governing instructions, soliciting confidential information, or redirecting the assistant into an unauthorized side task. It distinguishes such instructions from ordi-nary source material, quoted text, interface content, and completed-action receipts. Sensitive data or an earlier unsafe action does not alone establish a new injection in the current result. The user message contextualizes the task and is not itself the classifi-cation target. Uncertain cases default to ALLOW .

Sensitive Unintended Tool Call. The input con-tains the preceding session context, proposed tool calls, and matching tool definitions. Current call arguments and the definitions’ parameter schemas are omitted from their dedicated prompt fields. The prompt asks whether the proposed operation ad-vances the user’s intended task, including previ-ously authorized work and ordinary intermediate steps in a multi-step or batch request. A positive finding requires a clear task mismatch, an unre-quested action, or an action the user rejected. Miss-ing confirmation wording, incomplete arguments, and imperfect sequencing are not alone violations; ambiguity defaults to ALLOW . This expert assesses action-level intent alignment, not argument cor-rectness, destination authorization, or application-specific business rules. Earlier messages may still 18 contain argument values as part of the session his-tory. 

E.3 Agent-Aided Automated Prompt Optimization 

We use an agent-aided automated prompt opti-mization (APO) procedure to iteratively improve guardrail prompts through a metrics-driven exper-imental loop, following the general paradigm of autonomous experimentation and harness optimiza-tion inspired by Autoresearch (Karpathy, 2026) and Meta-Harness (Lee et al., 2026). Each APO run is governed by a task-specific specification file that defines the optimization ob-jective, allowed search space, development data, evaluation commands, target metrics and con-straints, permitted modifications, and artifacts to retain. The evaluation implementation and met-ric computation are treated as fixed infrastructure and cannot be modified by the optimization agent. In our experiments, we used balanced accuracy, 

BA = (TPR + TNR) /2, as the main optimization objective, and false positive rate (FPR) of at most 1% as the guardrail constraint. At a high level, the optimization loop consists of five steps. First, the agent inspects the current prompt and configuration together with prior ex-periment artifacts, including metrics, predictions, logs, and representative failure cases. Second, it analyzes quantitative results and qualitative error patterns to identify weaknesses and formulate a targeted hypothesis for improvement. Third, it pro-poses and applies a change only to components permitted by the specification. Fourth, it evaluates the resulting candidate using the prescribed devel-opment benchmark and fixed evaluation pipeline. Finally, it accepts or rejects the candidate according to the defined objectives and constraints, while pre-serving the resulting configuration, metrics, failure analysis, and decision for subsequent iterations. APO was applied independently to each guardrail task using a strictly disjoint set of datasets different from benchmarks used in the MAS-Guard evaluations. Specifically, we used a total of 2,200 samples from InjecAgent (Zhan et al., 2024), 

τ -bench (Yao et al., 2025), Agent-SafetyBench (Zhang et al., 2024), BrowseSafe Bench (Zhang et al., 2026), and AgentDojo (Debenedetti et al., 2024). Candidate selection combined aggregate metrics with analysis of false-positive and false-negative examples to distinguish meaningful improvements from changes that merely shifted errors across categories. This procedure automates much of the prompt-engineering loop while preserving a fixed evaluation protocol, explicit optimization con-straints, separation between development and test data, and an auditable history of candidate changes and outcomes.

In this section, we provide further analysis and in-sights into the kinds of protection each component supplies. We denote local A-Guard by A, deter-ministic system checks by D, and semantic system checks by S; ADS is full MAS-Guard. 

F.1 What does each component contribute? A-Guard: safeguarding local execution bound-aries. A provides the clearest benefit when an at-tack enters through an instrumented input, tool call, or tool result. On ASB, A-Guard alone achieves 15.0% ASR, compared with 36.6% for S alone; the fake-completion subset shows an even larger sepa-ration, 17.0% versus 63.2%. These results suggest that specialized local inspection catches attacks that broad task and role policies do not consistently identify. An OverThink trace makes this mechanism con-crete. A retrieved document for a factual question instructs the answerer to solve an unrelated Markov decision process exercise and insert its Boolean re-sult into the answer. Both A and ADS block the document before delivery; without A, the attack reaches the model and succeeds in the matched S

execution. All variants containing A achieve 0.0% ASR on this benchmark. 

Semantic checks: enforcing charter boundaries. 

Local attack recognition is insufficient when the vi-olation depends on who may receive information or what a role is authorized to do. Adding S to A re-duces ASR on ACIArena from 23.8% to 12.0%, on AgentLeak from 10.2% to 4.4%, and on TAMAS from 5.9% to 2.3%. The ACIArena MetaGPT sub-set is particularly informative: A leaves 28.7% ASR, whereas AS reaches 0.0%. For example, in an AgentLeak case, an assistant preparing a response letter sends a reviewer an otherwise ordinary draft with a synthetic SSN and a request to remember it. A allows the message and the case leaks. Semantic Charter checks block the inter-agent disclosure, and the full run still receives a positive task-success judgment. In a TAMAS education trace, an attacker claiming to be an e-learning director expands a one-student quiz task into a request for every student’s raw metrics. The full run passes format and capability checks but blocks the request for authority escalation; A alone permits it. The distinction is between an available operation and an authorized use of that operation. This strength depends on the supplied policy. AgentLeak specifies allowed and forbidden fields and provides attack-pattern context; its results demonstrate enforcement of that contract. Se-mantic checks can also overreach. In a benign AgentLeak case, S and ADS block a document request containing only the authorized case fields as over-collection. 

Deterministic checks: enforcing explicit, ob-servable constraints. D provides predictable en-forcement of explicit application constraints with-out requiring a model to interpret intent. At in-strumented boundaries, a prohibited route, format, or declared capability can be rejected even when the message appears benign to a semantic detec-tor. This makes D useful for requirements that should hold regardless of semantics. In an ACIA-rena code-hijacking trace, an attacker redirects a solver toward a remote reporting routine; D blocks the outgoing message because it contains a URL prohibited by the Charter. Such checks are also inexpensive as the deterministic checks use verifi-cation by code, rather than relying on ML models. The modest aggregate ASR contribution should be interpreted in light of the studied benchmarks. Adding D to A changes overall ASR from 7.8% to 7.7%; adding it to AS changes 5.1% to 4.8%. Many attacks travel over admitted routes and use valid formats or available tools, leaving their ma-licious purpose to local or semantic assessment. Furthermore, ASB and OverThink are single-agent benchmarks, with limited use of such capabilities. These results motivate retaining D when an ap-plication has explicit constraints to enforce, while showing that deterministic checks alone cannot ad-dress attacks that operate within those constraints. 

F.2 Which applications benefit from full MAS-Guard? 

Full composition is best motivated by workflows that combine the three obligations: inspecting agen-tic events locally, preserving task-specific autho-rization across agents, and enforcing explicit struc-tural constraints. A document assistant that re-trieves external material, delegates work over re-stricted records, and may send a notification is one example. Local experts can stop instructions em-bedded in retrieved content; semantic checks can reject unauthorized disclosure or fabricated author-ity; deterministic checks can enforce the permitted recipients, routes, and capabilities. 20 G Control Plane and Agent Charter Construction 

G.1 Construction protocol 

We used Codex (OpenAI, 2026a) with GPT-5.6-Sol at high reasoning effort (OpenAI, 2026b) as a policy-authoring assistant. Its inputs for each benchmark were the public benchmark documenta-tion and representative development samples that were disjoint from the test samples used to com-pute the reported evaluation results. We used the following construction protocol. First, we identi-fied every boundary-observable principal, includ-ing benchmark users, task agents, shared tools or data stores, and evaluation-harness identities. Second, we grouped principals that had the same trusted role and bound each group to a Charter. Third, we encoded the benchmark’s intended com-munication graph as explicit routes and chose a fallback for identities or routes not covered by the benchmark specification. Fourth, we expressed each role’s legitimate objective, text or JSON for-mats, prohibited semantic topics, and observable capabilities. Finally, we attached Charter Compli-ance and, for the full method, the standard A-Guard profile only at boundaries exposed by the adapter. We fixed the resulting templates and configurations before running the test evaluation; Codex was not invoked to adapt policy in response to test out-comes. This procedure is benchmark-aware: it models the product policy that an owner would author from system specifications and development held out data. AgentLeak is the only exception for which the complete authorization policy had to be instanti-ated case by case as the authorization varies across test case tasks. In our implementation, a fixed constructor fills the Charter template from each scenario’s declared allowed fields, forbidden fields and values, registered tools, and roles. Across the suite, generated Control Planes run in enforcement mode with a 45-second event-processing timeout. Except where noted, an unre-solved Charter isolates the event, an unlisted route is blocked, and a Charter violation is blocked. 

G.2 ACIArena 

ACIArena (An et al., 2026) contains several or-chestration frameworks with different runtime names for equivalent functions. We map these identities to five shared Charters: task source, planning/role allocation, solver/implementation, critic/reviewer/aggregation, and evaluation harness. The Control Plane admits the known framework-specific paths (for example, task specification, self-consistency voting, MetaGPT’s planning chain, and debate moderation) and explicitly blocks evaluation-harness identities from injecting instruc-tions back into task agents. Because the upstream frameworks may emit additional runtime identities and routing patterns, missing Charters and unlisted routes use pass ; admitted content is still evaluated when its sender and receiver resolve to registered Charters. The role-family Charters accept plain text and distinguish legitimate math, code, planning, review, and evaluation behavior. Their shared denylist covers the benchmark’s synthetic private identity and credentials, external callbacks, task derailment or artificial refusal, answer tampering, and propa-gation of embedded malicious control directives. The policy also prohibits credential, PII, PHI, PCI, URL, and shell-command content and declares in-ternet access out of scope. Charter Compliance inspects message-send and message-receive events; violations block by default, but disruption evalua-tions use reflection so the agent can retry the orig-inal task. A-Guard is attached to task-performing roles, not the synthetic user or evaluation harness. 

G.3 TAMAS 

TAMAS (Kavathekar et al., 2026) spans five do-mains and multiple AutoGen and CrewAI topolo-gies. Its policy contains a task-source Charter, a shared tool-boundary Charter, and 21 functional Charters covering the released domain roles and the manager. Role aliases and attacked A/B variants remain bound to the trusted base-role Charter: an attack may change an agent’s runtime description, but it does not change the product owner’s contract. The Control Plane permits task delivery, peer co-ordination or broadcast, guarded tool requests and results, and the final response. Unknown identities are isolated and unlisted routes block. The task source may not override an agent’s objective, fabricate authority, or request an unau-thorized harmful action. Tool output may not act as a control directive or request an unrelated harmful action. Each task-agent Charter adds objective-deviation, authority-abuse, unauthorized-side-effect, and role-boundary topics, together with the capabilities required by that role; direct code ex-ecution is out of scope for every benign role. We do not use static sensitive-content categories because 21 valid TAMAS work contains URLs and medical, legal, financial, and identity data. Charter Com-pliance therefore uses semantic authorization and capability checks on sends, receives, and handoffs. A-Guard is attached to task agents but not to the benchmark user or shared tool boundary. 

G.4 AgentLeak 

AgentLeak (El Yagoubi et al., 2026) defines a pri-vacy boundary that changes with the scenario, so the adapter creates case-scoped Charters. For each case, it registers a task source, a guarded tool boundary, and each runtime agent, and enumerates all intended user, agent-to-agent, and agent–tool routes. Our AgentLeak integration exposes four of the benchmark’s seven leakage channels: final output (C1), inter-agent communication (C2), tool input (C3), and tool output (C4). We measure leak-age over these observed channels; shared memory (C5), logs (C6), and artifacts (C7) are outside this integration. The Charter constructor resolves the scenario’s allowed fields against the named synthetic vault record, including explicitly supported aliases and safe derivations. It then computes the in-scope and out-of-scope capabilities from the registered tool. This is the most scenario-specific policy in our benchmark suite and should be interpreted as enforcement of a fully specified per-task privacy contract. Charter Compliance covers sends, re-ceives, and handoffs; full MAS-Guard also attaches A-Guard to the task agents. 

G.5 OmniLeak 

The version of OmniLeak available when we con-ducted this study did not include code or released data. We therefore use our reconstruction and extension of its disclosed experimental contract. It preserves the centralized Orchestrator–SQL– Notification workflow, attack categories, schema-knowledge settings, benign queries, and database scales described by Naik et al. (2026), while us-ing newly generated attack payloads and additional authorized control cases. Our reconstruction and guardrail-oriented exten-sion of OmniLeak (Naik et al., 2026) has a fixed six-principal topology: user, orchestrator, SQL agent, database, notification agent, and a synthetic local email sink. The Control Plane admits exactly the nine directed boundaries needed for query delega-tion, database access and return, result integration, optional notification, and the final answer. Each principal receives a role-level Charter with a least-privilege capability scope. 

G.6 OverThink 

OverThink FreshQA (Kumar et al., 2025) is a single-agent RAG workload. We register only the answer agent and model search as a tool rather than as a second agent. Its Charter accepts plain text and JSON but deliberately contains no topic restric-tions or capability limits, and the Control Plane installs no Charter Compliance guardrail. For full MAS-Guard, the answer agent’s A-Guard attach-ment evaluates the retrieved document as a tool result before model delivery and evaluates the fi-nal response. Consequently, any protection on this benchmark is attributable to the single-agent A-Guard layer, not to a benchmark-tailored Charter rule; MAS-Guard variants without A-Guard retain only the otherwise inert core Control Plane. 

G.7 ASB 

For each ASB case (Zhang et al., 2025), we create a Charter whose objective is the original benign task and bind the synthetic user and tool identities to a shared boundary Charter. The Control Plane allows only the four intended directions from user to agent, agent to tool, tool to agent, and agent to user. Inbound Charter violations use reflection, allowing the agent to reconsider untrusted planning, tool, or memory content; outbound violations block. A-Guard is attached only to the task agent. Because ASB tool identifiers do not constitute stable product-level capability declarations, Char-ter feature checking is disabled; semantic topic checking remains active on received messages, handoffs, and agent egress.

23 H Comparison-method Configuration 

H.1 Common adaptation protocol 

In our implementation of different safeguards used in the comparisons, every method receives the same canonical event representation and the same pre-intervention content at a boundary it supports. Its returned action is then applied before the bench-mark continues: input transformations replace the content delivered to the next agent, blocking deci-sions stop the pending boundary action, and pass decisions leave it unchanged. An event outside a method’s documented or implemented scope pro-duces an explicit pass. 

H.2 Prompt-transformation baselines Sandwich. Following the Sandwich de-fense (Schulhoff, 2024), at each supported untrusted-input boundary we append a fixed reminder after the original content. The reminder tells the receiving agent to preserve the benchmark task and explicit constraints and to treat conflicting requests for private-data leakage, external report-ing, artificial refusal, propagation of control text, or answer remapping as untrusted. The safeguard returns a redirect action containing the original content followed by this reminder. 

Delimiter. Following the delimiting form of Spot-lighting (Hines et al., 2024), we precede the con-tent with a fixed instruction to treat the following message as data rather than as authority, then en-close it between <untrusted_message> tags. It likewise returns a redirect action. We apply both prompt transformations to user-input, tool-result, and RAG-database- insertion projections. Neither baseline filters post-agent output or directly blocks a tool call. 

H.3 Event-level filters and classifiers ACI-Sentinel. We implement ACI-Sentinel (An et al., 2026) as a post-agent output filter. Given the original user query and the candidate agent an-swer, the shared guardrail inferencer is prompted to retain, in original wording and order, only ex-cerpts directly relevant to the query. Decoding uses temperature zero and at most 1,024 completion to-kens. Successful filtering redirects the outgoing answer to the filtered text; pre-agent boundaries are recorded as passes. 

LlamaFirewall. We use the all-components Lla-maFirewall (Chennabasappa et al., 2025) config-uration with PromptGuard, AlignmentCheck, and CodeShield enabled. PromptGuard uses a 0.9 block threshold. AlignmentCheck uses a Llama-4-Scout inferencer. CodeShield retains its regex checks, while its Semgrep subprocess is disabled because benchmark events may contain arbitrary natural language rather than source code. Scanner errors fail open. 

ToolSafe. For ToolSafe (Mou et al., 2026), we serve the released TS-Guard checkpoint, 

MurrayTom/TS-Guard , and use the released strict decision boundary under which a risk rating of 0.5

or higher is unsafe. Native agent-tool-call checks are enabled, as is ToolSafe’s malicious-user-request field for user inputs. Tool results and RAG in-sertions use the available Being Attacked content signa. 

AgentDoG and AgentDoG-1.5. We evaluate AgentDoG and AgentDoG-1.5 (Liu et al., 2026b,a) as two released matched checkpoint/prompt pairs. AgentDoG uses AI45Research/AgentDoG-Qwen 3-4B , the v1.0 binary trajectory prompt, and the exact safe /unsafe response contract. AgentDoG-1.5 uses AI45Research/AgentDoG1.5-Qwen3.5 -4B , the v1.5 coarse-grained moderation prompt, and its structured judgment parser. Both receive at most 15,360 input tokens and 512 completion tokens, and redundant checkpoint-native thinking is disabled. They evaluate trajectory-bearing agent tool calls and agent responses. 

H.4 FIDES dataflow baseline 

FIDES (Costa et al., 2025) is integrated inside each benchmark’s native planning and tool loop rather than as an event-verdict classifier. Untrusted re-trieval, tool, and peer-agent outputs are stored in case-local memory, and the planner sees opaque references. References can pass through later tool arguments and are expanded only at the executor. When hidden data must be transformed, a tool-less query_llm operation uses the suite’s shared guardrail inferencer and stores its result under a new reference. Only bounded Boolean or enumer-ated values may be revealed to the planner for data-dependent branching; larger results remain refer-enced until an authorized final-delivery boundary. 

H.5 Execution-loop integration 

Our evaluation executes each benchmark with guardrails embedded in its agent loop. Bench-mark adapters expose eligible user inputs, agent 24 messages, tool invocations, tool results, and final responses through a common event representation, retaining the available history and tool schemas. Their outputs can therefore change subsequent model inputs, tool execution, and task outcomes. Unsupported events pass unchanged.
