# From Interaction to Capability: Task Advancement as State and Supervision for GUI Agents 

Ziyang Chen 1 Qian Li 2 Chengwei Qin 1

1The Hong Kong University of Science and Technology (Guangzhou) 

2Joint SDU-NTU Centre for Artificial Intelligence Research (C-FAIR), Shandong University 

Abstract 

GUI memory should preserve the results of past actions and learn reusable operations. This is difficult in long-horizon workflows, where agents must use information across applica-tions and useful operations are interleaved with failed attempts. We introduce Task Advance-ment Memory (TAM), which defines task advancement as verified task progress, and supports ongoing task execution and learns reusable operations. During execution, Task Advancement State represents how verified task progress changes the remaining goals, allow-ing the agent to build on earlier achievements across applications. After each task, advance-ment supervision identifies and abstracts the in-teractions that produced a verified local result. The learned operations preserve the relation between required inputs, expected outcomes, and verification conditions. This retains locally successful operations from both successful and failed tasks. On MobileWorld GUI-only tasks, Advancement State alone raises success from 12.0% to 28.2%. Full TAM achieves a 17.6% relative gain in task success over the strongest evaluated baseline and reduces lifecycle tokens per solved task by 38.7%. On SPA-Bench, TAM achieves state-of-the-art task success in the single-app English Level 3 setting.

Recent methods improve the information avail-able to the agent through context management, program-guided execution, and verified task state (Yang et al., 2025; Tian et al., 2026; Liu et al., 2026a; Zheng et al., 2026; Wu et al., 2026; Liu et al., 2026b). Trajectory exemplars, induced workflows, and experience memories also trans-fer knowledge to later tasks (Zheng et al., 2024b; Wang et al., 2025b,a; Xiao et al., 2026; Ouyang et al., 2026). These approaches address how mem-ory can help an agent complete remaining goals and 1arXiv:2610.37482v1 [cs.AI] 27 Oct 2026 how successful interactions can become reusable operations. However, agents still struggle to ap-ply correctly acquired information to later goals across applications. Workflow memories tied to historical action sequences also leave the agent to adapt past routes when the interface changes. A task’s final outcome also gives incomplete feed-back about intermediate operations, a failed task can contain useful successes, while a successful task can include ineffective attempts. We propose Task Advancement Memory (TAM), a memory framework that uses task progress to guide execution and learning. A task advancement 

occurs when GUI observations confirm that a pre-viously unresolved requirement is satisfied, either by obtaining required information or by achiev-ing a requested outcome. Each advancement re-duces what the agent still needs to determine or accomplish. We call this task reduction . For online execution, Task Advancement State makes earlier advancements usable by later goals. It shows what information is available for each remaining goal and which goals are ready to pursue. TAM uses each advancement to supervise the selection and abstraction of productive interactions. The learned operations specify the inputs needed at entry, the result to achieve, and how to verify it. This re-tains useful capabilities from productive portions of both successful and failed workflows. Figure 1 illustrates these two uses of task advancement. We evaluate TAM on the GUI-only subset of MobileWorld (Kong et al., 2026) and the Level-3 English subset of SPA-Bench (Chen et al., 2025). With Qwen3-VL-32B-Instruct used by every listed MobileWorld method, TAM improves success from 29.1% for the strongest evaluated memory baseline to 34.2%. With GPT-4o in the SPA-Bench English Level 3 setting, it reaches 57.0%, the high-est success rate in the reported comparison. Our contributions are as follows: • We introduce Task Advancement State within TAM to guide execution across applications. It represents the remaining task in terms of satisfied requirements, available inputs, and unresolved dependencies. This lets the agent build on earlier advancements when choosing its next action. • We propose advancement supervision , which converts partial task success into capabilities that can be reused in subsequent tasks. Each learned operation specifies what it needs, what it should achieve, and how to verify the outcome. • We show that TAM outperforms the evaluated memory baselines in task success on Mobile-World and SPA-Bench. Cross-benchmark com-parisons, component ablations, and cost analyses establish the value of task-state memory and the additional benefit of persistent operators. 

2 Related Work 

Task state and verified execution. Explicit task representations preserve information and unfin-ished work across interface changes. AgentProg represents task variables and control flow; ATMem maintains task-driving information and execution status; TSR separates durable task information from transient observations; and StructAgent com-bines requirements, values, evidence, and verified transitions (Tian et al., 2026; Liu et al., 2026a; Zheng et al., 2026; Wu et al., 2026). MGA also or-ganizes interaction around validated state changes (Cheng et al., 2025). These methods preserve ex-plicit task information and distinguish intended actions from observed outcomes. TAM links task results to the remaining requirements they support. These dependencies guide execution and define the inputs and outcomes of reusable operations. 

Trajectory, workflow, and skill memory. Per-sistent experience can guide later tasks through demonstrations, trajectories, workflows, or skills. Synapse retrieves abstracted trajectories as in-context exemplars; AWM induces workflows from offline or online experience; and ReasoningBank distills reusable reasoning strategies (Zheng et al., 2024b; Wang et al., 2025b; Ouyang et al., 2026). Mobile-Agent-E stores tips and shortcuts, UI-Mem organizes workflows, subtask skills, and failure patterns, and SkillGen synthesizes and validates skills from successful and unsuccessful trajectories (Wang et al., 2025a; Xiao et al., 2026; Ma et al., 2026). These systems reuse experience at different granularities. They adopt different rules for locat-ing a reusable segment, assigning local credit, and verifying the result that the segment is expected to achieve. TAM selects interactions by the local re-quirement they satisfy and carries that requirement into the learned operation’s expected outcome and verification condition.

3 Method 

TAM uses task advancement in two ways. Task Advancement State represents what remains to be done using the information already obtained. Ad-vancement supervision learns reusable operations from interactions that satisfy a task requirement. These memories guide a fixed base policy, which chooses primitive actions from the live interface (Figure 2). Appendix A gives the execution proce-dure, update rules, and learning details. 

3.1 Task Advancement as a Shared Memory Unit 

At step t, a base policy πθ receives the instruction g,current GUI observation ot, bounded recent history 

Ht, and TAM’s bounded memory context Ct. It emits a primitive action in the original environment action space. TAM changes the supplied memory, without retraining the policy. A separate episode record T retains evidence for task-end review. On-line state acceptance guides the current task, retro-spective review evaluates which interactions should enter persistent memory. At task initialization, an LLM-based task com-piler identifies the information to acquire and the outcomes to establish from the instruction. It repre-sents them in a graph Q = ( V, E Q), whose nodes 

V are requirements and whose edges EQ encode their dependencies. For each requirement q, its de-pendencies Rq identify the requirements that sup-ply its inputs, and an evidence rule Vq specifies how its result is recognized. An optional branch condition γq specifies when the instruction requires 

q. These dependencies concern task results rather than a prescribed sequence of GUI actions. The task-local state St records each requirement’s sta-tus, known values, and supporting evidence at step 

t. Object bindings associate a value or outcome with its task entity, such as the event to which a meeting time belongs. 3.2 Advancement as State: Online Task Reduction 

Task Advancement State turns verified progress into an explicit representation of the remaining problem. Information already obtained is bound to the requirements that need it, and satisfied re-quirements are removed from the remaining work. We call this task reduction . We call the unfinished requirements with their available inputs the resid-ual task . Completed requirements leave this view, while their results remain in St for later use. For ex-ample, Figure 2 assumes a departure time of 5 PM. Reading a driving duration of 3 h 18 min supplies the missing value for calculating arrival at 8:18 PM. The remaining goal is to send Susan that time. TAM thus carries the result of the route query into the messaging goal across the application change. 

Reason from the reduced task. Among the re-maining requirements, TAM identifies those whose inputs are already available and whose branch con-ditions hold. This set is the Advancement Fron-tier . Using the observation returned by the environment, TAM dis-tinguishes three cases: text entered into a form is a draft, clicking Save is an attempt, and an appro-priate confirmation supports a saved result. The ac-cepted result then becomes available to dependent requirements. This keeps progress tied to observed effects while leaving action selection with the base policy. 

Retain visual evidence when text is insufficient. 

A task-local Evidence Cache E stores source im-ages or crops linked to task information and its object bindings. When a requirement needs infor-mation whose source screen has left recent context, recalled evidence can restore its value or clarify which object it describes. Recalled images are identified as historical evidence. Current controls and coordinates come from the live screen. 

3.3 Advancement as Supervision: Learning Reusable Operations 

Advancement supervision learns reusable opera-tions from verified local results, including those 4within failed workflows. The challenge is both tem-poral and semantic: identify the productive interac-tion, then determine what it required and achieved. 

Learning from local results. Each advancement identifies a local result and a candidate segment of preceding interactions. When terminal evalu-ation nominates an outcome, it enters the same retrospective review. At task termination, an LLM-based reviewer examines the result and recorded actions and observations, including later evidence of confirmation or contradiction. It retains sup-ported operations and selects the steps contributing to their navigation and information acquisition. Re-view evaluates each operation against the evidence for its local result, including when the larger task fails. TAM separates inputs needed before the re-tained interaction from information acquired within it. Only the former become the operation’s entry requirements. For example, a route query requires an origin and destination; the driving duration is acquired by the operation itself. This makes the learned query applicable to new routes whose dura-tion the agent still needs to find. 

Abstract task values while preserving object identity. A supported segment yields an Advance-ment Operator 

κ = ⟨Rκ, ∆κ, V κ, B κ, Γκ, Aκ⟩. (4) Its components are entry requirements Rκ, ex-pected advancement ∆κ, verification condition Vκ,object roles Bκ, optional applicability conditions 

Γκ, and reviewed GUI realizations Aκ: recorded action sequences together with the interface condi-tions under which they were observed. Abstraction replaces instance-specific values with roles shared across the inputs, result, and verification target. For example, event details and the creation confirma-tion must refer to the same event. Concrete GUI entry conditions and action details belong to indi-vidual realizations. The persistent Advancement Operator Graph G links each operator to its ob-served GUI realizations. This lets TAM reuse the same operation while checking each route against the current interface. To consolidate a new sam-ple, TAM compares its input–result relation with the stored operators: compatible samples refine a shared description while retaining distinct GUI re-alizations. Otherwise, the sample forms a separate operator. 

3.4 Operator Reuse: Task Meaning and GUI Realization 

An operation can remain useful across changes in its GUI implementation. TAM separates two ques-tions: whether the operation supplies a needed re-sult from available inputs, and whether the current interface supports a recorded route. TAM retrieves operators whose expected results and input roles match a frontier requirement. Among supported candidates, it considers both coverage of remain-ing requirements and the applicability and relia-bility of the stored GUI route. Selection retains a bounded set of alternatives across these two criteria, favoring additional requirement coverage. Appen-dices A.6 and A.10 specify matching, compatibility checks, and selection rules. When the required in-puts are available and a stored GUI route passes the interface and reliability checks, the readout in-cludes that route. Otherwise, a supported operator can still supply its required inputs, expected result, and verification cue, with missing inputs explicitly marked. Task knowledge therefore remains useful when a stored route needs adaptation. The actor uses this guidance to choose primitive actions from the current interface. Historical success guides the attempt; current observations determine whether the expected advancement is accepted. If no opera-tor is relevant, ordinary execution continues with the task state and recent context.

4.2 Main Results 

On MobileWorld, TAM achieves 34.2% success, improving on the strongest evaluated baseline by 5.1 percentage points (Table 1). Relative to the memory-free backbone, the gain is 22.2 points. Across all three app-count groups, TAM outper-forms all four compared baselines (Table 3). Its ad-vantage over ConAct is larger on the 62 multi-app tasks, where success reaches 32.3% versus 24.2% (+8.1 points), than on single-app tasks (+1.8 points). The larger multi-app gain supports TAM’s focus on sustaining execution across application bound-aries. TAM also attains the highest EQA@50, 29.2%, and uses 20.6 controller rounds on aver-age, showing that the advantage also holds when successful completion is rewarded for taking fewer rounds. TAM uses 0.771M lifecycle tokens per solved task, 38.7% below ConAct’s 1.257M. AWM is slightly cheaper at 0.720M, but completes 13.7% of tasks versus TAM’s 34.2%. TAM offers the strongest completion rate in this comparison at a lifecycle cost close to the cheapest evaluated memory method. This supports the practical value of organizing memory around established task re-sults rather than increasing the interaction bud-get. On SPA-Bench English Level 3, TAM reaches 57.0% success, 3.3 percentage points above GUI-explorer’s reported 53.7% (Table 2). This is the highest result in the reported comparison. Together, the two benchmarks show that TAM’s benefits oc-cur both in cross-app workflows with an open-source backbone and in difficult single-app tasks with GPT-4o. 

4.3 Component Ablations 

Table 4 shows that Task Advancement State pro-vides the largest gain, raising success from 12.0% to 28.2%. This gain establishes the value of ad-vancement state for online execution before persis-tent experience is added. Adding the Advancement Operator Graph to State yields 32.5%, while aver-age steps fall from 23.4 to 20.9. With the Evidence Cache enabled, the Operator Graph adds 5.1 points (29.1% to 34.2%). The Operator Graph improves completion in both cache settings. Online state provides the main gain by making earlier results available to unfinished work, persistent operators add experience about how to obtain the next needed result. 

4.4 Mechanism Analysis Identifying and using task information. To ex-amine whether acquired information remains us-able, we audit archived runs of tasks that require obtaining a value from the environment and using it in a later operation. The comparison covers the same 52 required values across 21 tasks for all five methods. Within each task, identification coverage 

is the fraction of required values explicitly and cor-rectly stated in online outputs; target-use coverage 

is the fraction correctly used in their intended fields or objects. Averaging these rates equally across tasks, TAM achieves the highest observed coverage for both identification and target use (Figure 3(a)). 

State availability and use. We use a flat-state control to test the value of relating stored facts to pending requirements. The control retains fact stor-age and open requirements while removing prereq-uisite links and their action guidance. To compare the use of available information, we include all tar-get fields in the paired runs whose required source inputs were visible to both agents. The nine eligible fields from five tasks are each assessed under two paired implementation revisions, giving 18 field instances. Over these instances, state availability 

measures the fraction with the correct value explic-itly recorded in the actor’s state. TAM achieves 77.8% versus 55.6% for flat state, while correct tar-get use reaches 77.8% versus 66.7% (Figure 3(b)). 

Localizing supervision for operator learning. 

For supported advancements written to operator memory, we compare candidate segments with the steps retained after retrospective review. Fig-ure 3(c) shows the 10th–90th percentile profiles, normalized by source-trajectory length. Review reduces the median retained segment length from 20% to 7.7% of the source trajectory. Therefore, the retained supervision is concentrated on local operations rather than the full interaction history.

5 Conclusion 

Task Advancement Memory makes established re-sults useful at two timescales. During execution, 

task reduction supplies acquired information to pending requirements and removes completed re-quirements. During learning, the interactions yield reusable operations whose entry inputs, outcome, and verification target remain aligned after abstrac-tion. Across MobileWorld and SPA-Bench, TAM improves task completion, with ablations establish-ing the independent value of Advancement State and further gains from persistent operators. These findings support a task-centered foundation for GUI memory: accumulated progress makes the current problem more concrete, while productive interaction builds capabilities for future workflows. 8Limitations 

TAM builds task state and reusable operators from observed results. The accuracy of this process de-pends on model-based interpretation of task re-quirements and GUI evidence, especially when outcome cues are ambiguous. Improving visual grounding and outcome verification can strengthen both online execution and experience learning. Our evaluation focuses on MobileWorld GUI-only tasks and the English Level 3 subset of SPA-Bench, covering cross-application workflows and difficult single-application tasks on mobile devices. Extending this evaluation to web and desktop work-flows would assess transfer across interface types. TAM’s persistent operators accumulate across the benchmark task sequences studied here. Longer task streams and repeated application updates intro-duce further requirements for maintaining relevant experience. The separation between an operation’s intended result and its GUI realizations provides a basis for studying adaptation as interfaces change. Future work can examine operator revision and retirement, together with their effects on retrieval quality and memory-maintenance cost.

A Method and Implementation Details 

This appendix describes how TAM connects the requirements of a task to observed progress and reusable operations. We follow the execution order in Algorithm 1: compile the requirements, maintain task advancement state, retrieve relevant evidence and operators, and review supported local opera-tions for reuse. The same requirement and object identifiers connect these stages. 10 A.1 Requirements and memory records 

A requirement in Q describes either information to acquire or an outcome to achieve. Its record contains a relation name, value type, object roles, prerequisite requirements Rq, and a verification condition Vq. Structured values also specify their required fields. An optional condition γq identi-fies the branch in which the requirement applies. For example, an event record can contain its title, date, and time, while a notification requirement depends on that record and the recipient’s contact information. Dependencies describe the informa-tion consumed by an operation; the GUI route is chosen during execution. The state St associates each requirement with its status, current bindings, and evidence references, as described in Section 3.1. Bindings preserve the relation between a value and its object: an event time belongs to the specified event, and an address belongs to the specified recipient. Evidence ref-erences identify the observation step and saved source artifact. The implementation also records artifact digests so that a reused image retains its original identity. The Evidence Cache E stores visual support for task-local facts. The persistent graph G stores op-erators and their GUI realizations. An operator records its entry inputs, expected advancement, ver-ification condition, object roles, and applicability conditions. Its realizations retain the corresponding action sequences and interface contexts. This sepa-rates the result an operation provides from the route used to obtain it. Task state and cached evidence re-set at the task boundary; reviewed operators remain available to subsequent tasks. 

A.2 Compiling the task requirements 

At task start, the LLM-based compiler receives the natural-language instruction and proposes informa-tion and outcome requirements in JSON. It assigns types, names the necessary fields, and specifies which requirements supply inputs to each outcome. For a conditional request, it also represents the condition and its dependent requirement. Compila-tion operates on the instruction; it does not require advance access to the applications or their task-specific contents. The implementation combines the proposal with schema normalization. This resolves requirement references, checks field types, and preserves pre-requisite relations when bounding the graph size. The default target is 12 requirements; dependen-cies needed by a retained requirement are preserved. Explicit instruction values, such as a requested re-cipient, subject, or message, are kept as constraints on the corresponding outcome. They specify what the agent must achieve and are kept separate from observations of what it has achieved. Consider the request to read an event’s details and notify a contact. The compiler separates the event information, the contact endpoint, and the notification outcome. If the task also asks for an independent numerical answer, that calculation is connected only to the outputs that use it. The result-ing graph therefore preserves independent branches of the request instead of requiring every intermedi-ate result before any outcome can be pursued. 

A.3 Updating and reading task advancement state 

The actor reports task-relevant observations along-side its action. Each observation update identifies a requirement, a value or structured fields, and the evidence that supports it. The update format distin-guishes source information, derived values, visible drafts, collection coverage, and observed effects. These roles retain the difference between reading an event’s time, entering that time into a form, and observing a saved event. The runtime associates the proposed update with its requirement and source observation, checks the field structure, and updates the corresponding binding. Model-based extrac-tion interprets the observed content; reference and schema checks preserve its association with the task and artifact. Source information can be established from the current observation. Relevant outcomes are as-sessed from the observation returned after an ac-tion, using the requirement’s verification condition. For instance, text visible in a message composer describes a draft; the sent-message view provides evidence about the resulting message. Both the content and its recipient matter when the task spec-ifies them. The two updates in Eq. 3 thus use the observations already produced by the interaction loop. Structured requirements retain missing fields until they are supplied. Collections preserve ob-served members separately from evidence that the requested scope has been covered. Similarly, an ab-sence claim refers to a particular source and search scope. Contradictory observations leave the af-fected requirement conflicted until further evidence 11 resolves it. This keeps later inputs tied to the infor-mation that has been established. 

Presenting the remaining work. The actor re-ceives the established bindings and a requirement readout that distinguishes available inputs from missing inputs. An input shared by several require-ments is referenced from the same state record. This is the implementation of the residual-task rep-resentation described in Section 3.2: completed requirements no longer constitute pending work, while their values remain available to their con-sumers. The frontier Ft identifies unresolved re-quirements whose dependencies and branch condi-tions are satisfied. In the event example, reading the event details supplies the notification’s content. After the con-tact endpoint is established, the notification has its required inputs. The actor can proceed using those values even after leaving the source applications. The readout organizes the next decision; it does not issue an action or replace the original task in-struction. TAM’s full-method configuration leaves primitive action selection to the base policy. 

A.4 Recalling visual evidence 

A cache entry links a saved screenshot or crop to the accepted relation, object binding, and source step. The cache is queried when a current require-ment needs information whose source is no longer represented in the actor’s recent visual context. Se-lection follows the requirement’s input dependen-cies and matches the corresponding bindings. If several facts come from the same image, that image is attached once. The implementation forms a packet covering the required source evidence within a limit of three recalled images. Evidence already present in the actor context contributes to that coverage. Each recalled image is marked as a past observation and supplied with a reference identifier. When the ac-tor reads a value from it, the observation update cites that identifier. The resulting value follows the ordinary state-update path. Current control lo-cations and coordinates are grounded in the live observation. Cache selection does not invoke another model. The selected images enter the ordinary actor call, where their visual tokens are included in the cost. If no matching packet is available, execution proceeds with the current observation, recent history, and task state. 

A.5 Reviewing local operations and abstracting their inputs 

An accepted advancement records the affected re-quirement, its bindings, supporting evidence, and the preceding interaction segment. This initial seg-ment retains context before the use of relevant in-puts. It is a candidate for review: some of its in-teractions may be navigation, repeated attempts, or work unrelated to the established result. At task end, the reviewer receives the candidates, their recorded actions, the result observations, and available later evidence. It decides whether each local result is supported, selects the steps to retain, and cites the supporting artifacts. Later observa-tions can confirm the result or reveal a reversal or object mismatch. Terminal success can nomi-nate an outcome candidate for review, it does not replace the local evidence judgment. The indepen-dent outcome-quality audit excludes such evaluator-nominated candidates (Appendix D.5). Correctly reading an event remains a useful operation when a later notification fails; a successful task can like-wise contain unproductive attempts that need not enter its reusable operation. 

Identifying the entry inputs. TAM saves the ac-cepted task facts available before each step. Once the reviewer selects a segment, the snapshot at its retained start identifies which inputs were already available. Changes within the segment identify in-formation acquired by the operation itself. This distinction determines Rκ: a value first obtained in-side the retained segment is an internal result, rather than an input required before the operation starts. If review chooses a later start, the corresponding later snapshot supplies its entry state. The implemen-tation preserves the navigation and information-acquisition steps needed to support the selected local result. For example, a segment that opens a calendar and reads an event can learn an operation for ac-quiring event details. A subsequent segment that starts with those details and sends a notification can learn an operation that consumes them. The second operation’s inputs should not be assigned to the first merely because both appear in the same com-pleted workflow. Conversely, reviewing a segment from a later starting point must use the information available at that point, rather than the task’s final state. 12 Consolidating an operation. For a supported segment, the reviewer provides a short descrip-tion of the entry inputs, local result, and reusable method. It replaces task-specific values with ob-ject roles and compares the input–result relation with nearby stored operators. Compatible samples refine one operator while preserving their individ-ual GUI realizations. Materially different inputs or outcomes produce separate operators. Differ-ent names, dates, or layouts alone do not require a separate semantic operation. For the route query in Figure 2, the entry snap-shot contains Orlando and Miami as the origin and destination. The driving duration is absent at en-try and is obtained from the route-result screen. Abstraction replaces the two locations with origin and destination roles. The operator requires those roles, returns their driving duration, and checks that the displayed route uses the requested trans-portation type. Its recorded realization is Maps

The stored record links this description to the re-tained steps and evidence. The expected result and verification condition refer to the same object roles as the inputs. The graph can therefore preserve an operation such as creating an event from given details while retaining different observed routes through the calendar interface. New evidence re-fines the shared description while preserving each observed route. 

A.6 Retrieval and actor readout

The readout includes the operation’s required inputs, expected advancement, and verification cue. When a realization fits the live interface, it also includes the corresponding route. Otherwise, the semantic operation still describes a useful result and how to recognize it, while the actor chooses a route from the current screen. A.9 Candidate boundaries and retained interactions 

An accepted local result supplies the candidate end-point e. For resource alignment, the implementa-tion ranks recorded transitions up to the detected endpoint by Hi = 4 xi + 3 ni + 2 max(0 , z i − yi).Here xi, y i, z i are the fractions of claim tokens ap-pearing in the action target, pre-action UI, and post-action UI, respectively; ni is the fraction newly visible after the action. Claim tokens come from the proposed values, fields, and evidence text, with generic stop words removed. The highest-scoring transition is used, with later steps breaking ties, only if Hi ≥ 0.35 ; backdating additionally requires an exact claimed value in that transition’s visible post-action UI. Otherwise the detected endpoint is retained. Let r be the earliest recorded availabil-ity step, before e, among the candidate’s required 14 inputs, and let p be the previous captured advance-ment step strictly before e. If a backdated endpoint is at or before the most recent advancement, that advancement does not constrain the start. The ini-tial start is max( r, p +1) when both exist, r or p+1 

when only one exists, and the episode start other-wise. The candidate contains the bounded suffix of this interval through e; the default setting retains at most eight steps. An empty recorded slice falls back to the detected transition as a single-step can-didate. Thus the reviewer receives a local candidate rather than choosing an unrestricted interval from the full episode. The reviewer chooses a nonempty subset of sup-plied step identifiers that includes e, and cites ev-idence identifiers from the supplied packet. The host validates both sets. It then closes the selection over observed input support: input-entry steps not marked as making no progress, or selections of a result or recipient bound to a required input, iden-tify the earliest supporting step. The retained route includes the nonempty, non-wait actions from there through e. For acquisition without entry inputs, it also retains the navigation/read prefix from the lat-est recorded app opening, or the bounded prefix if no app opening is present. If required inputs have no identified support step, the validated reviewer selection is retained. Entry inputs are determined after this closure. The snapshot immediately before the retained start supplies the available facts; subsequent snapshots through the endpoint identify acquired or updated facts. An input requirement is removed only if it was first acquired inside the retained interaction and was absent at entry. A later retained start there-fore uses its own earlier-state snapshot. Missing history remains unknown. When its application and activity are recorded, the GUI realization’s entry condition is taken from the first retained step’s ob-served pre-state; otherwise the original entry scope is retained. 

A.10 Operator identity, matching, and GUI readout 

Retrieval compares operators learned from re-viewed interactions with requirements compiled from the current instruction. It checks the required result and input roles before considering a recorded GUI route. Our MobileWorld and SPA-Bench con-figurations share the reference settings specified below. Task bindings and GUI context are recom-puted for each retrieval; execution evidence updates the reliability of each operation and route. The stored semantic record names its 

operator_kind and operator_family , en-try requires , expected effects , and verifies .Its input profiles bind requirement schemas to parameter roles; guard variants preserve optional conditions. The verification_contract names the result schema, the required result fields, and the evidence relation. Separate GUI records link to this semantic identifier and retain the entry context, typed route, retained source steps, required/capability roles, and evidence provenance. 

Consolidation. The reviewer compares the re-tained operation’s input-to-result relation with the supplied nearby operators. It proposes an existing identifier only when that relation is compatible; oth-erwise it returns null. The host accepts a proposed merge only if the identifier occurs among the sup-plied operators, the description is nonempty, and the result’s canonical family matches. Otherwise it stores the supported sample separately. A merge updates the description and retains observed input profiles, guards, and individual GUI realizations. The host does not average their action sequences. 

Schema canonicalization. Compiler names are lowercased and normalized with underscores. Marker-based alias maps assign canonical result families and input roles. Effect families en-code domain and operation; resource families re-tain recognized role/domain and positional qual-ifiers. Thus SMS-Sent and text_message_sent 

map to text_send , while meeting_time and 

event_time map to resource:event_time . In-put profiles additionally normalize declared roles, such as render to content . Unrecognized ef-fects use predicate:<schema> ; resources lack-ing a recognized role retain resource:<schema> .In fallback schema comparison, qualifier conflicts mean opposing marker groups (e.g., start/end, source/destination, departure/arrival) or aggregate versus nonaggregate markers; these receive zero similarity. 

Semantic matching. Semantic matching tests whether an operator can supply the result of a pend-ing requirement. Result types and input roles con-strain eligibility; normalized schema comparison supports records with incomplete type metadata. An explicitly typed source must match the target’s resource-acquisition or effect-realization kind and canonical result family. For records without an ex-15 plicit family, TAM first derives a canonical family from the schema name. Agreement with the target family gives a match score of 1. Otherwise, nor-malized schema comparison checks exact identity, qualifier conflicts, effect-family or resource-role agreement, and finally substring or token overlap. The corresponding reference scores are 1 for exact identity, 0 for qualifier conflicts, 0.94 for a shared effect family, 0.86 for a shared resource role, 0.82 

for a substring match, and token Jaccard otherwise. The reference fallback threshold is τm, 0 = 0 .80 . In-compatible effect families and effect–resource pairs are capped at 0.59 and excluded from feedback-calibrated matching, so name overlap cannot over-ride a type conflict. Compatible input profiles must agree on whether the operation consumes inputs. When both profiles have role metadata, the source profile must cover the target’s required roles. The matched operation is rebound to the current require-ment and its inputs. Reuse preserves the input– result relation while substituting the new task val-ues; historical values remain provenance. Profiles lacking role metadata retain the coarser check on whether inputs are consumed. 

GUI compatibility and reliability. GUI compat-ibility tests a recorded route against the live inter-face. B Experimental Setup 

B.1 Benchmarks and Observations MobileWorld. We evaluate the GUI-only parti-tion of MobileWorld (Kong et al., 2026). Based on the released task metadata (Tongyi-MAI, 2025), this partition contains 117 tasks across 15 GUI ap-plications, with 105 English and 12 Chinese instruc-tions. The application counts in the task metadata divide these tasks into 55 single-app, 48 two-app, and 14 three-app workflows. Tasks include com-munication, scheduling, document handling, file management, and shopping. The GUI-only setting 17 uses touch, text entry, scrolling, navigation, appli-cation launch, waiting, and termination. It excludes MCP tools and simulated-user clarification. The observation interface supplies the current screenshot and the available Android UI tree. Each method constructs its own history and memory con-text from these observations. MobileWorld ini-tializes the device and application data for each task. Its native evaluators check the requested re-sult through task-specific answer checks, backend state, device-local files, or application callbacks. Evaluation data are kept separate from actor obser-vations. 

SPA-Bench. We use the English single-app Level 3 setting of SPA-Bench (Chen et al., 2025). Based on the released task metadata (AI Agents 2030, 2024), this split contains 50 tasks across 36 applications, with reference human trajecto-ries comprising 9–18 annotated actions. These multi-stage single-app workflows complement the cross-app demands of MobileWorld. The split is identified by the English single-app task file and its Level 3 difficulty annotations; task instructions are used as released. As specified in Section 4.1, TAM uses GPT-4o with Set-of-Mark observations. Appendix B.3 describes initialization, action exe-cution, final evaluation, and memory continuity for this setting.

B.3 SPA-Bench Implementation and Evaluation Environment and action interface. SPA-Bench tasks run in an Android emulator controlled through Android Debug Bridge (ADB). Execution ends when the policy terminates or the budget is ex-hausted. An agent’s completion declaration closes the trajectory but does not establish benchmark success. 

Official evaluation. We use SPA-Bench’s single-app evaluator with its result_only reasoning mode and with_action trajectory representation (AI Agents 2030, 2024). C Baseline Adaptations 

All MobileWorld methods use the evaluation and stopping protocol in Appendix B.2. The inte-grations retain each method’s memory represen-tation, update procedure, and internal model roles. Adapters translate their actions to the common mobile interface and expose the current screen-shot, available UI-tree information, and application-launch operation. Internal calls contribute to the lifecycle accounting in Appendix B.5. 

AWM (Wang et al., 2025b). AWM induces workflow descriptions from successful trajectories and replaces task-specific arguments with variables. The online adapter updates the workflow library at task boundaries and includes its text in the actor prompt in source order, up to 12,000 characters. Induction requires at least two actionable steps and has a 2,048-token output limit. The actor retains the task’s previous action history and uses a 1,024-token output limit. Workflow descriptions preserve application and affordance names while abstracting instance values and omitting absolute coordinates. 

Mobile-Agent-E (Wang et al., 2025a). The in-tegration retains the Manager, Operator, Action Reflector, Notetaker, and the experience reflectors for tips and shortcuts. Its perception pipeline com-bines OCR and icon descriptions with available UI-tree controls. After an action, the agent ob-serves the result, reflects on the action, and updates its notes. In the evolution setting, tips and shortcuts persist across tasks, while working notes reset. The optional experience selector is disabled, so avail-able tips and shortcuts are supplied directly. Role responses have a 2,048-token limit. Shortcut ex-pansion is preserved, with its atomic actions logged separately from the controller decision. 

StructAgent (Wu et al., 2026). The adapter re-tains structured task state, planning, perception, milestone verification, completion auditing, and recovery. It uses the released fixed experience bank with up to ten retrieved items and at most five plan-ner images. The action adapter translates supported operations to Android interactions; desktop shell, browser-control, and office tools are unavailable in the GUI-only environment. The default role output limit is 1,500 tokens, with role-specific requests capped at 8,192. The original experience bank re-mains fixed during the task sequence. 

GUI-explorer (Xie et al., 2025). The adapter preserves exploration-derived knowledge, multi-modal retrieval, model-based ranking, action se-lection, and step summarization. The live screen queries the knowledge base through its embedding and FAISS pipeline. Retrieval requests one candi-date per image query at a similarity threshold of 0.9. The ranker selects knowledge relevant to the current instruction, and step summaries retain exe-cution history. Action selection and summarization use a 1,000-token response limit. The Device inter-face maps selected actions to MobileWorld while retaining this retrieval and execution loop. 

MemGUI-Agent (ConAct) (Liu et al., 2026b). 

We adapt the MemGUI-Agent implementation re-leased with MobileWorld. It retains the five-part tagged response format, structured context, history folding, and explicit context-management opera-tions. The actor receives one current screenshot with the shared UI-tree and application-launch ex-tensions; its own context operations manage earlier information. A context-management operation ex-ecutes a wait and consumes one controller round. Context resets at each task boundary. The response limit is 8,192 tokens to accommodate the tagged sections and rewritten context. Parsing permits up to three attempts on unchanged messages; these attempts are distinct from transport retries and do not introduce extra environment actions. 

D Additional Results and Analysis 

The following analyses examine information reten-tion, input preparation, operator learning and reuse, 21 and resource allocation. They draw on benchmark metadata, historical execution archives, paired state controls, and readout tests at fixed checkpoints. The benchmark comparisons measure end-to-end completion, these diagnostics examine the specific behaviors that task advancement is designed to sup-port. 

D.1 Benchmark Coverage of the Diagnostics 

Field-level diagnostics require both an acquired value and an identifiable destination for its later use. We classify all 117 MobileWorld GUI-only tasks by the principal information requirement in their instructions and official definitions (Figure 4). The classification identifies which tasks support this diagnostic. The census identifies 52 tasks whose principal requirement is to transfer acquired text or numer-ical content to a later GUI operation, comprising 47 multi-app tasks and five single-app tasks. Tasks involving final answers, decisions based on source information, file transfers, or navigation require dif-ferent evaluation criteria. A source-to-target field test therefore applies to a particular information requirement, rather than to every multi-app task. These 52 tasks define the benchmark scope of source-to-target field scoring. The main-text audit uses a reference catalogue covering 21 of them, comprising 14 fixed-role and seven collection tasks. Its 52 shared values provide identical field refer-ences across the five methods. The catalogue cov-ers a subset of the applicable tasks. 

D.2 Preserving Information beyond Its Source 

We measure retention after information has entered state. This requires an identifiable acquisition fol-lowed by an opportunity to retain the value. We therefore track values that match both their cited read-only UI source and the state supplied to the ac-tor. Instruction constants and echoes of the agent’s own input are excluded. This defines a diagnostic of acquired information with a verifiable textual source. Scanning all 756 valid archived TAM-family episodes yields 202 bindings across 32 tasks, where a binding associates a task role with a value. These 32 tasks contribute every acquisition satisfying the above rule. The 198 bindings with subsequent de-cisions yield 3,751 value–decision pairs. Every later decision is scored, including those where the value has disappeared, regardless of episode suc-cess. Availability is the fraction of these pairs in which the value remains in state, averaged equally across tasks. It reaches 92.3% overall, 93.1% in an application different from the source, and 89.6% when the value is absent from both current XML and recent text (Figure 5). For the temporal comparison, we require ten subsequent recorded decisions per binding so that every point follows the same values. Otherwise, episodes ending earlier would change the compo-sition of the curve. All 106 bindings meeting this duration requirement enter the analysis, covering 24 tasks. Values remain in the denominator even when they disappear. After ten steps, 95.1% remain in state, compared with 57.6% present in current XML or recent text (Figure 6). These results show that TAM preserves acquired information across application changes and extended action sequences. Advancement State keeps earlier results available to later decisions even when they are absent from the current XML and recent text. Scores measure literal retention in primary state, excluding quoted evidence. Observation ends with the episode. A value may disappear after replace-ment or completed work. The shared protocol spec-ifies matching rules and longer follow-up windows.

D.5 Quality of Local Learning Signals 

We apply three policies to the same recorded candi-date pools, retaining all candidates, retaining only candidates from successful episodes, or follow-ing TAM’s storage decisions. A candidate pairs a claimed local result with its interaction evidence. Tasks contribute through the learning candidates they produce. Each test includes all candidates meeting its reference conditions below. Correct-ness measures the quality of retained material, while coverage measures how much correct ma-terial is retained. 

Local outcomes. To assess local outcome judg-ments independently of terminal success, we in-clude all 20 admitted proposals made without ter-minal evaluator feedback. Proposals nominated by the evaluator already use the terminal signal being compared and are accounted for separately. TAM’s retained outcomes are 100% supported and cover 83.3% of the supported pool (Figure 9(a)). Success-only selection gives 85.7% correctness. It admits premature completion claims from a workflow that succeeds later. TAM excludes these contradicted claims. Missing supported outcomes result from review-output processing failures, which remain included in the coverage calculation. Local veri-fication thus improves the reliability of outcome evidence selected for operator learning. 

Acquired values. Value-level scoring compares a specified resource field with an external refer-ence. Within the source-reference catalogue, we include every admitted field with a complete, un-ambiguous value claim and a determinate reference in benchmark fixtures, injected messages, or source documents. This yields 234 fields across 20 tasks, including correct and incorrect values. Incomplete claims and roles without resolved references re-main in the full candidate accounting (Table 13). To prevent candidate-rich tasks from dominating the comparison, we fix weights before selection so that each task contributes equally to the com-mon pool. TAM retains 88.3% of correct material, compared with 64.3% for success-only selection. Correctness among retained values is 93.8% and 99.4%, respectively (Figure 9(b)). TAM combines higher retained-value correctness than keeping all candidates with broader coverage of correct mate-rial than success-only selection. This expands the evidence available for operator learning, including supported progress from unsuccessful workflows. 

Sensitivity to repeated values. Table 10 also gives equal weight to reference groups defined by task, resource role, and reference value. Correct-ness and coverage are ratios of weighted counts. Supported values remain in the coverage denomi-nator even when their group retains none. TAM’s coverage advantage persists under both weightings, showing that the gain holds when either tasks or repeated source values receive equal weight. The shared protocol also reports the unweighted com-parison.
