# EREBOTS 4.0: A framework for conversational assistants with A2A agents and MCP tools 

Elia Pacioni a,b, ∗, Davide Calvaresi a, Andrei C. Coman a, Ismael Jaggi a,Valerio Crocetti a, Gaetano Manzo a, Michael Schumacher a

> aHES-SO Valais-Wallis, Rue de Technopôle 10, 3960 Sierre, Switzerland
> bUniversity of Extremadura, 06800, Mérida, Spain

Abstract 

In recent years, multi-agent systems have shifted from rule-based, symbolic agents to sub-symbolic agents built on language models. However, several limitations remain unresolved. The new frontier is neuro-symbolic agents, which pair language models with deterministic tools and explicit protocols. Without a common framework to standardize and compose them, each study rebuilds the same infrastructure, and results are hard to replicate. This paper presents EREBOTS 4.0, an open-source, hybrid-AI, multi-agent framework that fills this gap for conversational assistants. Language-model agents plan and route requests, while deterministic tools compute exact results over the Model Context Protocol (MCP). An orchestrator selects one or more spe-cialist agents per turn and calls them over the Agent2Agent protocol (A2A). A new agent, local or remote, is added by listing its URL in a configuration file. The framework also manages identity, user context with consent flags, task states and traces. Its A2A server passed 97 tracked requirements in the official A2A Technology Compatibility Kit, with no failures. 

Keywords: multi-agent systems, agent interoperability, Agent2Agent protocol, Model Context Protocol, conversational assistants, agentic AI

1. Motivation and significance 

The building blocks of a multi-agent system have changed. Most multi-agent research built its agents from deliberative components that exchanged explicit communication acts, coordinating or competing over goals that were their own or partly shared [1]. A current wave builds them from language models that plan, call tools, and delegate in natural language, and the surveys of that shift already run to hundreds of primary studies [2, 3]. One reading of this wave is that it renames the earlier concepts [4]. The engineering problem moved with that shift, from building an agent to composing several. An agent is now assembled from parts that each hold a model, a prompt, and a set of executable operations, and those parts are often written by different groups on different hosts. Research on such systems needs a platform, for the same reason earlier multi-2agent research needed one. Comparing routing strategies, delegation policies, or the right granularity for a specialist means holding everything else fixed: discovery, transport, task lifecycle, streaming, identity, conversation state. A researcher who rebuilds that substrate for each study spends the effort there, and the result is hard for anyone else to replicate. A platform that holds it fixed turns those questions into things a researcher can change one at a time and measure, and into claims others can test on the same substrate. The challenge itself is not new. JADE [5] and SPADE [6] gave multi-agent research platforms where agents met over a specification, FIPA-ACL [7] in one case and XMPP [8] in the other, so researchers could compose each other’s agents and replicate an experiment elsewhere. Rasa played a compa-rable role for open conversational systems [9], and PEAK still builds agent communities on SPADE today [10]. Two specifications now do that job for language-model agents. A2A defines agent cards, messages, artifacts, and task operations [11], and MCP defines tool discovery and invocation [12]. Both have been taken up by the frame-works in common use. LangGraph [13], CrewAI [14], AutoGen [15], Microsoft Agent Framework [16] and Google ADK [17] are toolkits for building and orchestrating agents. They provide stores for conversation history and memory, and leave it to the ap-plication to authenticate the user and tie each request to that user. All are permissively licensed, four under MIT terms and ADK under Apache 2.0. Several of them now speak A2A. CrewAI delegates to a remote agent from its card URL, and Google ADK and Microsoft Agent Framework wrap one the same way. A LangGraph assistant serves a card of its own once deployed on LangChain’s hosted server [18]. In all of them the peer is reached from application code, so adding a peer or moving it to another host means chang-ing that code. CrewAI and LangChain develop their open core alongside a commercial managed platform. AutoGen began as a research artifact, and its repository now describes it as in maintenance mode, with no new features and under community management. EREBOTS 4.0 is a new generation of the EREBOTS platform for personal-ized health chatbots [19], which supported work on nutritional coaching [20] and explainable assistants [21]. This implementation introduces LLM-driven routing and specialists behind protocol endpoints. EREBOTS 4.0 is built for one kind of system, an assistant a person talks to. That narrowing is what lets the framework take over what those toolkits leave to the application, since every assistant needs it. The orchestrator takes the identity from the login, loads the context stored for that user, and passes both to every specialist it calls, local or remote, in A2A metadata. The examples use personal-data management and a deterministic calculation, which explain delegation, tool 3execution, and conversational state. It declares its routable specialists as A2A endpoints (URL) in a configuration file, and the orchestrator discovers what each offers from its agent card without application code constructing a wrapper for it. Writing an agent here means subclassing a single class and naming the MCP servers that hold its tools. A researcher uses the framework by writing a configuration file that lists agent endpoints, registering any specialist hosted in their own application, pointing each agent at a model endpoint, and starting the application with a GUI or CLI. This paper presents three main contributions (C): • C1. a framework that composes specialists over A2A and MCP, so they run in one process or on separate hosts with no code change; • C2. the application layer a deployed study needs beyond an agent library, with OpenID Connect (OIDC) login, user-context persistence, execution traces, and one conversation service every frontend shares; • C3. a measured conformance result against the official A2A Technology Compatibility Kit, reported with the requirements it leaves untested and the two a2a-sdk deviations the measurement exposed. 

2. Software description 

The repository separates the installable erebots package from application composition, specialist implementations, and frontend examples. Application code constructs agents, configures persistence and credentials, and mounts their endpoints. The core can also serve an orchestrator with no registered specialists. The examples in this paper use two specialists: PersonalAgent 

manages a user’s own data, and ConversionAgent converts between units.

The application lists routable endpoints in agents.yaml . The path can be passed in, and otherwise resolves from the working directory, without requir-ing a source checkout. The orchestrator then fetches each agent card and reads the name, description, skills, and endpoint it advertises. A routing prompt presents these capabilities to the orchestrator’s LLM, together with recent conversation turns for follow-up messages. The selected names are checked against the registry and bounded by a configured maximum. An empty selection produces a direct response from the orchestrator. What the orchestrator does next depends on how many specialists it selected. For one selected specialist, the orchestrator relays its streamed answer. For several, it starts concurrent A2A calls and tags each contribution with its agent name on a separate channel. Each specialist receives the request and a description of the responsibilities assigned to the others. The orchestrator then synthe-sizes the contributions with an additional LLM call, or concatenates them into sections. Concurrent calls change what a failure costs. A failing call removes one contribution and leaves the rest available. The trace records it and the answer 5omits it, unless every call fails and the turn ends in an error naming each. Concurrent specialists all receive the context prepared at the start of the turn, so an update made by one is not visible to calls already in progress. Specialists do not call one another. The orchestrator holds the only A2A client, and the interaction graph is a star. Specialists written inside the framework inherit BaseSpecialist , which im-plements MCP discovery and a bounded cycle of model calls, tool invocations, and tool results. Its A2A skills say what it can be asked for, and its MCP tool schemas say what it can execute. A tool that runs and reports failure is distinct from a server that cannot be reached, and the trace records each as its own step. A specialist does not always have what it needs to answer. The built-in 

ask_user control ends a streaming iteration with a request for missing in-formation, and the A2A executor marks the task input-required . A client resumes by sending the answer and the task identifier. The server recon-structs the exchange from the message that opened the task, so the specialist sees the question it asked and the context that preceded it. The orchestrator then bypasses routing, after checking ownership against the requesting iden-tity and checking expiry. The mechanism preserves task identity and does not checkpoint the internal LLM tool loop. A resumed specialist no longer knows which tools it already called, so any tool it might reach before asking the question has to be safe to run twice. A turn that crosses the orchestrator, a specialist, and a tool server cannot be reconstructed from any one of them. Traces record routing decisions, del-egations, tool calls, tool results, and tool failures. The failure taxonomy for multi-agent LLM systems was built from more than 1600 such traces, an-notated across seven frameworks [22]. Step identifiers and parent identifiers associate a specialist’s trace with the A2A call that produced it. Durations and token counts are attached where collected. These records describe ob-servable execution events and do not establish the causal reasoning behind a model’s choice. Context propagation and trace payloads travel inside A2A messages and artifacts as EREBOTS 4.0 metadata conventions. 

2.2. Software functionalities 

The A2A server layer uses the official a2a-sdk and exposes JSON-RPC and HTTP+JSON routes from one request handler, with streaming, task oper-ations, and push notifications. An extended agent card is advertised when one is configured. Push delivery validates the webhook address at registra-tion and again at delivery, then pins the connection to the validated address. The default task store is in memory, and the application can select database-backed task and push-configuration stores. A parked task then survives a 6restart, verified by recreating the server, the executor, and the store and resuming from the task identifier alone. An identity enters through Keycloak [23], which provides OIDC login over cookies or bearer tokens. The application derives it from the authenti-cated session and hands it to the specialist. There BaseSpecialist ex-poses a prepare_tool_args hook for pinning server-side arguments, and the PersonalAgent uses it to overwrite the user_id of every tool call before the call runs, so a model cannot address another user’s record. Internal traffic carries its own credentials. A2A and MCP routes accept service-account tokens obtained through client_credentials , and check which client each token was issued to. Every request below /tools/ carries that bearer, including reads from the loopback interface. An application can opt into one exception, which exists for a single UI library and defaults to off. Two gaps remain in that chain. Internal services are trusted to propagate the identity correctly, and the command-line client selects one with –user 

without authenticating it, which makes it a development tool. The PersonalAgent exposes profile updates, consent updates, and context retrieval through MCP, over a SQLAlchemy store. It keeps consent flags there and serves them to the application, which decides what to do with them. The same store holds the transcript, reached through a conversation-service inter-face that every frontend shares. That interface owns the transcript when an identity and a store are both present, and reports that it does not when either is missing. Appending a turn is a single transaction whose first statement is a write, which serializes two clients answering at once and loses neither turn. The suite exercises that path on SQLite. Local agents are registered in specialists/registry.py . A specialist sup-plies a prompt, a description, skills, and the addresses of the MCP servers holding its tools. The registry returns it under a name, and bootstrap mounts its A2A application at the matching path. That path is what agents.yaml 

lists: 

agents: - http://localhost:7860/a2a/personal 

The example application mounts every specialist and every tool server in one Asynchronous Server Gateway Interface (ASGI) application, so one port serves the whole assistant on a laptop, while the conformance fixtures run in their own process with their own dependency set. An independently hosted specialist supplies its own implementation and end-point, and the orchestrator needs no domain import for it. Connectivity, authentication, supported message forms, and any shared metadata conven-tions must still match. Model endpoints are configured per agent, tool-using 7agents require tool-call support, and image inputs require a multimodal de-ployment. For in-process testing, the orchestrator accepts an injected A2A client, so a consumer can point it at an ASGI application without opening a socket. 

2.3. Verification 

We measured EREBOTS4.0, release 1.0.0, with an automated suite and a conformance run, under Python 3.13 [24] with a2a-sdk 1.1.2, mcp 1.29.1, and openai 2.54.0. The suite passes 567 tests covering routing and fan-out with stubbed model calls, A2A round-trips through the SDK, task parking and resume across a recreated store, MCP discovery and tool-error handling, authentication, persistence under concurrent writes, and frontend event han-dling. The A2A Technology Compatibility Kit (TCK) grades a server against the capabilities its own agent card declares. Run against the fixture endpoints of version 1.0.0, built on a2a-sdk 1.1.2 and serving A2A v1.0, it reports no failures at MUST, SHOULD, or MAY level [25]. The fixtures answer from canned payloads with no model in the loop. One endpoint declares every optional capability. /a2a/tck-minimal serves the same scenarios behind a card that declares those capabilities absent. Only there can the suite reach

3. Illustrative examples 

We ship a demonstrator that starts PersonalAgent together with a

ConversionAgent whose single MCP tool converts quantities between units of mass, length, energy, and volume by exact factors. The following two scenarios distinguish framework mechanics from model decisions. Routing dispatch, the A2A call, the tool invocation, the stored value, and the task lifecycle are pinned by the automated suite with stubbed model replies, so they do not depend on which model is deployed. The choice of specialist and the decision to ask the user depend on the model. A user writes “Hello, my preferred language is Italian.” The intended route is PersonalAgent , which calls the profile-update tool, and reading the value back with the context-retrieval operation is what establishes success, since a generated confirmation does not establish that the profile changed. The user then writes “I made a mistake. Update my preferred language.” The specialist calls ask_user , the task becomes input-required , and the user answers “My preferred language is Spanish.” The reply carries the task identifier and no transcript, and the profile changes on that second turn. No system prompt 9names ask_user , and the framework exposes no tool_choice setting, so the tool description is the only instruction the model receives about it. A parked task resumes after the server and its store are recreated, the same resume is refused to a different identity, and it is refused once the task has expired. gemma-4-E4B-it [28] over an OpenAI-compatible [29] endpoint. The automated suite exercises the same mechanism with stubbed replies, and these figures show it under a model.

A user writes “Remember Italian as my preferred language and convert 12 miles to kilometres.” The two operations are independent, and routing selects both agents. The conversion returns 19.312128 kilometres from the exact factor 1 mile = 1.609344 kilometres, the trace identifies both A2A calls, and the composed answer keeps the numerical result alongside the outcome of the profile operation. With the conversion endpoint unreachable, the profile operation and its answer survive. The suite covers that fan-out path. The demonstrator itself starts with authentication disabled and tasks in memory, which leaves the transcript with the client. Reproducing the persisted outcomes needs Keycloak enabled and a2a_persistent_tasks 

set. Measuring the model-dependent half would need a pinned model, fixed prompts, and a decided repetition count, which makes it a study of model behavior. Routing reaches any endpoint that serves a conforming agent card, so an agent written in another language or on another stack is routable once its card validates. The conformance suite is itself an independent client, built on plain HTTP and JSON Schema with no dependency on a2a-sdk . The direction we have not measured is the reverse, our client against a server 11 built on something other than a2a-sdk .

4. Impact 

In EREBOTS 4.0, a single answer from the assistant can entail the work of several agents, local or remote. Adding an agent means listing its URL in a configuration file. That puts questions about routing strategy, delegation policy, and specialist granularity within reach of a researcher unwilling to reimplement discovery, streaming, task lifecycle, and authentication first. Since the framework’s mechanics are verified with stubbed model replies, two configurations differ only in the component under study and in the model. Moving an agent to another host takes a different URL, so where a specialist runs becomes a configuration choice. Conformance pushes EREBOTS beyond custom and possibly unverified agents. The server is measured against the official A2A Technology Com-patibility Kit, and the result is reported with the requirements the suite leaves untested. Two research groups that both meet the specification can compose each other’s agents with no shared codebase, and the fixtures we ship let either of them run the same check against its own server. The framework is self-contained and needs only an OpenAI-compatible end-point for the model, which a local inference server can serve, and identity and storage run beside it. Given that the composition happens over the wire, a specialist can run where its data and its tools already are, inside the network segment that holds them, while the orchestrator reaches it from outside. The operator therefore decides where the data sits and under which jurisdiction, which is what makes a deployment possible in a regulated domain at all. Beyond composition, conformance, and self-hosting, the framework has six more advantages: (i) user identity comes from the login and is propagated, with the user’s context, to every specialist, while server-side pinning of 

user_id prevents a model from reaching another user’s data; (ii) exact re-sults come from deterministic MCP tools, not from the model; (iii) a failing specialist removes only its own contribution to the answer; (iv) clarification requests are A2A tasks in the input-required state, resumable only by their owner, before expiry, and across restarts when persisted; (v) traces link every tool call, result, and failure to the delegation that produced it, supporting failure analysis [22]; (vi) all frontends share one per-user transcript, which stays consistent under concurrent writes. These properties are enforced by code and do not depend on the model. However, the framework acknowledges five limitations: (i) it offers only one queued waiting task, so a second clarification in a fan-out waits until it expires; (ii) consent flags are stored but not enforced; (iii) persisted tasks 12 survive restarts of a single instance, but replicas are not coordinated; (iv) specialists do not negotiate; (v) routing and the decision to ask the user depend on the model, and their success rates are not yet measured. Two lines of work are underway in the group. A nutritional-coaching assis-tant under the HARRISON [3, 31, 32] project continues the earlier ERE-BOTS work [20] as a research prototype, and a second explores industrial use, an assistant for maintaining pharmaceutical manufacturing equipment, with different tools and different specialists. 

5. Conclusions 

In EREBOTS 4.0, the user agent is an endpoint that serves an agent card. The orchestrator uses specialist agents over A2A, routes each request to the matching advertised MCP’s kills, and composes their responses. Login, user context, execution traces, and one shared transcript come with the frame-work. The framework passes 97 requirements of the official A2A conformance suite with no failures. EREBOTS 4.0 stores consent flags and serves them to the application. No code path refuses an operation when a consent is absent. Enforcing them is harder than in a single-agent assistant, because a consent could cover one operation or a whole specialist, and the check could sit in the orchestrator or in each specialist. For a specialist hosted elsewhere, the decision has to travel with the request, and A2A has no field for it. Letting one specialist call another is a small change, since each is already an A2A server. Loop detection and a hop limit carried in message meta-data would bound the exchanges. The open question is which interaction protocol they should follow. In a contract net [33], agents bid on a task based on their suitability. With LLM-based agents, however, each bid costs a model call, and the reported suitability is itself a model output that may be wrong. Future work will address whether agents’ negotiation outperforms orchestrators’ routing.
