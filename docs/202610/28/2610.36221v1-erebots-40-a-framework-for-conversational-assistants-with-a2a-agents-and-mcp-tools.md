## 摘要
近年来，多智能体系统已从基于规则的符号智能体转向基于语言模型的亚符号智能体。然而，仍有若干局限尚未解决。神经符号智能体是一个新兴方向，它将语言模型与确定性工具及显式协议相结合。由于缺乏用于标准化和组合这些组件的通用框架，每项研究都需要重新构建相同的基础设施，研究结果也难以复现。本文提出 EREBOTS 4.0，这是一种开源的混合人工智能多智能体框架，旨在弥补对话助手领域的这一空缺。语言模型智能体负责规划请求并进行路由，确定性工具则通过模型上下文协议（MCP）计算精确结果。编排器会在每轮交互中选择一个或多个专业智能体，并通过智能体间协议（A2A）调用它们。只需在配置文件中列出新智能体的 URL，即可添加本地或远程智能体。该框架还负责管理身份、带有同意标记的用户上下文、任务状态及跟踪记录。其 A2A 服务器通过了官方 A2A 技术兼容性套件中跟踪的 97 项要求，且未出现失败。

## Abstract
In recent years, multi-agent systems have shifted from rule-based, symbolic agents to sub-symbolic agents built on language models. However, several limitations remain unresolved. The new frontier is neuro-symbolic agents, which pair language models with deterministic tools and explicit protocols. Without a common framework to standardize and compose them, each study rebuilds the same infrastructure, and results are hard to replicate. This paper presents EREBOTS 4.0, an open-source, hybrid-AI, multi-agent framework that fills this gap for conversational assistants. Language-model agents plan and route requests, while deterministic tools compute exact results over the Model Context Protocol (MCP). An orchestrator selects one or more specialist agents per turn and calls them over the Agent2Agent protocol (A2A). A new agent, local or remote, is added by listing its URL in a configuration file. The framework also manages identity, user context with consent flags, task states and traces. Its A2A server passed 97 tracked requirements in the official A2A Technology Compatibility Kit, with no failures.

## 1. 核心问题与整体含义

### 研究背景与动机
- 语言模型智能体可以规划、调用工具和委派任务，但将多个智能体组合成可部署的对话助手，仍需要实现大量基础设施：
  - 智能体发现、通信和流式输出；
  - 身份认证、用户上下文与会话历史；
  - 任务状态、澄清交互与任务恢复；
  - 工具调用、错误处理和执行追踪。
- 如果每项研究都重新实现这些功能，不仅开发成本高，也难以保证不同实验之间的可比性和可复现性。
- 作者认为，现有通用智能体工具包虽然提供编排能力，但身份认证、用户绑定和部分远程智能体接入工作仍由应用开发者承担。

### 核心目标与意义
EREBOTS 4.0 希望提供一个固定的研究与部署基础层，使研究者能够主要改变路由策略、委派策略或专家划分，而不必重建整套系统。

其基本分工是：
- **语言模型**负责理解请求、选择专家和组织回答；
- **专家智能体**负责特定领域任务；
- **确定性工具**负责实际的数据操作或精确计算；
- **显式协议**负责跨进程、跨主机的组件连接。

因此，论文的价值主要在于**标准化组合和工程可靠性**，而不是已经验证了更高的任务完成率或更好的用户体验。

## 2. 方法论：核心思想、技术细节与执行流程

### 2.1 总体架构：A2A 连接智能体，MCP 连接工具

框架采用分层设计：

| 层次 | 主要职责 |
|---|---|
| 前端 | 接收用户消息，展示流式回答、状态和执行追踪 |
| 编排器 | 加载上下文、选择专家、委派任务、汇总回答 |
| 专家智能体 | 执行领域任务，进行模型—工具循环，必要时向用户提问 |
| MCP 工具服务器 | 提供工具发现、确定性计算和数据访问 |
| 身份与持久化服务 | 管理认证、用户资料、同意标记、历史和任务 |

- **A2A（Agent2Agent）**用于智能体发现、消息交换、任务操作和流式通信。
- **MCP（Model Context Protocol）**用于工具发现和调用。
- 模型通过 **OpenAI 兼容接口**接入，可为不同智能体分别配置；使用工具的专家需要模型支持工具调用。

### 2.2 配置驱动的专家发现与路由

- 在 `agents.yaml` 中列出专家的 A2A URL。
- 编排器获取各专家的 **Agent Card**，读取名称、描述、技能和端点。
- 将专家能力与近期对话提供给路由模型。
- 对模型输出的专家名称进行注册表检查，并限制最多选择的专家数量。

不同路由结果对应不同流程：
- **未选择专家**：编排器直接回答。
- **选择一个专家**：转发该专家的流式回答。
- **选择多个专家**：并发调用，再通过额外的模型调用综合结果，或按章节直接拼接。

需要注意：新增已符合接入条件的远程专家可以只修改 URL 配置；自行开发和托管本地专家仍需实现、注册并挂载端点。

### 2.3 专家执行与工具调用

框架内的专家继承 `BaseSpecialist`，复用：
- MCP 工具发现；
- 有次数上限的模型调用—工具执行—结果反馈循环；
- 工具执行错误与服务器不可达的分类处理；
- 向用户请求补充信息的 `ask_user` 控制机制。

论文中的两个示例专家为：
- **PersonalAgent**：管理用户资料、同意标记和上下文；
- **ConversionAgent**：通过确定性工具执行单位换算。

这里的“神经符号”主要体现为语言模型与显式协议、确定性工具的结合，并非提出新的符号推理算法。

### 2.4 澄清与任务恢复

当信息不足时：
1. 专家调用 `ask_user`；
2. A2A 任务进入 `input-required` 状态；
3. 用户携带任务 ID 提交补充信息；
4. 系统检查任务归属和有效期；
5. 绕过重新路由，恢复到原专家。

**关键限制**：恢复机制重建的是对话上下文，而不是完整的模型工具循环检查点。因此，恢复后可能重复调用先前工具，相关操作需要具备幂等性或可安全重复执行。

### 2.5 身份、安全、状态与追踪

- 使用 **Keycloak + OIDC** 认证用户，内部服务使用服务账户令牌。
- 用户身份和上下文通过 A2A 元数据传递。
- `PersonalAgent` 在服务器端强制覆盖工具参数中的 `user_id`，防止模型指定其他用户的记录。
- 使用 SQLAlchemy 管理用户资料、历史和任务；启用数据库任务存储后，可跨服务重启恢复任务。
- 追踪记录路由、委派、工具调用、结果、错误，以及部分时长和 token 数。

这些追踪说明的是**可观察执行过程**，不能直接视为模型内部推理的因果解释。

## 6. 主要结论与发现

- **实现了配置驱动的智能体组合**：满足协议、认证和元数据约定后，本地与远程专家可使用统一接入方式。
- **整合了对话助手所需的应用层能力**：身份、用户上下文、共享历史、任务生命周期和追踪不再完全由应用自行搭建。
- **协议测试合并通过 97 项要求，零失败**，但仍存在未测试和不适用的要求。
- **测试暴露并修复了依赖库问题**：
  - SDK 对不可取消任务返回了不符合规范的 HTTP 状态码；
  - 对终态任务的订阅返回了错误类型不符的异常。
- **仓库外安装验证发现了额外缺陷**：MCP 客户端曾忽略 `isError`，将工具错误文本当作正常结果；报告版本改为抛出 `MCPToolError`。
- **模型行为仍未得到量化验证**：路由是否正确、何时应向用户提问，仍依赖模型。

## 7. 优点与亮点

- **问题定位清晰**：针对对话助手，而不是试图覆盖所有多智能体应用。
- **职责划分合理**：语言模型负责决策，工具负责执行，协议负责通信，便于替换和独立验证。
- **工程测试与模型评测分离**：使用桩回复验证框架，避免把模型偶然成功误认为机制可靠。
- **验证结果表述审慎**：明确区分测试用例、协议要求、跳过项和未覆盖项。
- **重视真实交付环节**：不仅测试源码，还验证构建后的 wheel 能否在仓库外使用。
- **考虑异常与安全路径**：包括任务归属、过期拒绝、服务认证、服务器端身份参数固定及部分失败隔离。
- **有利于自托管和后续研究**：MIT 开源，并提供模型接口、配置和部署支持；但“更易复现”尚未由跨团队复现实验直接证明。

## 8. 不足与局限

### 8.1 实验覆盖与偏差风险
- 示例仅涉及资料管理和单位换算，任务简单，不能代表复杂规划、长链工具使用或真实业务。
- 路由准确率、澄清成功率、端到端完成率和幻觉率均未量化。
- 没有人类受试者研究，无法评估澄清负担、信任或可用性。
- 没有基线对比、消融、成本和延迟评测。
- 独立 TCK 客户端验证了其服务器，但框架自身客户端对非 `a2a-sdk` 服务器的反向互操作尚未测量。

### 8.2 架构与状态限制
- **交互拓扑是星形结构**：专家不能直接协商或调用彼此。
- **并发专家读取轮次开始时的上下文快照**，看不到其他并发专家刚完成的更新。
- **仅支持一个排队等待的澄清任务**，多专家同时需要澄清时存在处理限制。
- **恢复不保存完整工具执行检查点**，非幂等操作存在重复执行风险。
- **持久化仅验证单实例重启恢复**，没有解决多副本协调。

### 8.3 隐私、安全与应用限制
- **同意标记只存储、不强制执行**，不能据此认为框架已经完成隐私合规。
- 内部服务被信任为正确传播身份，尚非完整的端到端身份保证。
- CLI 可以通过 `--user` 选择身份而不认证，应视为开发工具。
- 默认演示关闭认证且任务存于内存，不能直接等同于安全、持久化的生产部署。
- EREBOTS 特定上下文和追踪元数据不一定被所有 A2A 实现理解；协议符合性并不自动保证业务语义兼容。
- 确定性工具只能保证既定输入下的执行规则，无法保证模型选对工具、填对参数或正确解释结果。

**总体评价**：EREBOTS 4.0 是一项具有明确工程价值的框架贡献，证据最强的部分是基础设施实现、异常处理和所测范围内的协议符合性。其多智能体任务收益、真实用户价值和大规模部署能力，仍需更系统的对比实验与场景验证。
