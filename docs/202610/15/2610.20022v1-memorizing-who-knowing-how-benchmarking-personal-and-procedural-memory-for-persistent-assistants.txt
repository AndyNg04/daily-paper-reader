## ABSTRACT 

Memory systems for persistent personal agents must move beyond isolated mem-ories, maintaining both personal memory about whom they serve and procedural memory about how to act. Crucially, in harness-based personal assistance, pro-cedures or skills are inherently user-conditioned : personal context determines which procedures apply, how they are instantiated, and when they should change. Existing benchmarks typically emphasize either personal or procedural memory, leaving their interaction underexplored. We introduce P RAXIS MEM BENCH , a harness-based benchmark for persistent personal assistance across daily-life and work trajectories, where personal and procedural memory evolve together and later tasks depend on both. Experiments show that maintaining two memory types separately is insufficient, with completion dropping from single-type to interde-pendent dependencies ( 84.6% →77.9% ). More broadly, across existing methods, relation-related failures increase from early to late sessions as interaction history grows ( 59.8% →72.9% ), revealing a continual-maintenance challenge: writing correct memories is not enough if their evolving content and organization can-not be preserved for later retrieval. To address this, we propose P RAXIS MEM ,which uses privileged joint-state supervision to internalize the ability to maintain memory content and organization into the memory manager, with location-aware GRPO and dynamic residual-routed OPSD. P RAXIS MEM reaches 40.78% overall Session Success Rate, compared with 20.60% for Claude Code’s native memory. 

## 1 INTRODUCTION 

Agent harnesses such as OpenClaw and Claude Code enable language models to operate applica-tions, invoke tools, and execute multi-step tasks across practical domains (Zhu et al., 2026; Cai et al., 2026; Ji et al., 2026). Beyond task-level capability, a broader goal is persistent personal assistance ,in which the same agent supports one user across a continuing stream of everyday life and work. In this longer-term setting, memory is a key mechanism for such persistence, allowing accumulated in-teraction history to shape later understanding and action (Packer et al., 2023; Chhikara et al., 2025; Xu et al., 2025). Personal memory maintains evolving user-specific states and preferences, while 

procedural memory preserves reusable ways of acting across applications. Crucially, procedures are inherently user-conditioned : personal context shapes which procedures apply, how they are instantiated, and when they should change. Existing memory benchmarks capture two complementary but incomplete sides of persistent per-sonal assistance. Long-term memory benchmarks ask whether models can recover information from dialogue or histories. Many emphasize personal memory like facts, preferences, and their evolution (Maharana et al., 2024; Wu et al., 2025; Chen et al., 2026). However, recall alone does not show whether such personal context can govern consequential actions in external appli-cations. Yet without persistent user context, they cannot determine whether a procedure is appropri-ate for a particular user or how it should adapt as that user changes. Together, these lines leave how personal and procedural memory interact in persistent personal assistance underexplored. As illustrated in Figure 1, the central challenge in persistent personal assistance is that procedures are user-conditioned : personal memory determines which procedures apply, how they should be instantiated, and when they should change. This coupling is often triggered by underspecified re-quests, since users rarely restate the relevant personal constraints or previously established proce-dures (Chen et al., 2026; Zhu et al., 2026). Executable session instantiation. In order to instantiate these joint dependencies, the annota-tor selects relevant personal memories, applicable procedural memories, an application, and an application-specific SOP from Ω⋆n. Following Eq. 2, these ingredients are instantiated through a current event or preference change, a natural user request, and execution in the selected application. By construction, the task requires personal memory (e.g., Maya’s updated meal preference) and

Their association I⋆n is instantiated when personal context constrains the candidate space, selects among procedural outcomes, or changes how a procedure should be applied. When a memory is first established, the user states the relevant personal information or procedure natu-rally but explicitly. Crucially, in later dependent sessions, these details are omitted from the public request, so the evaluated memory method must select the related personal and procedural memo-ries relevant to the current request and user state. The resulting session Xn contains the application fixture, reference execution, and evaluation checks. As detailed in Appendix C.2, only indepen-dently validated sessions advance the canonical state in Eq. 2; their outcomes and new memories may then shape subsequent sessions. 2.3 EVALUATION 

Persistent agent lifecycle. To realize the persistent transition in Eq. 1, PraxisMemBench evaluates each memory method f within the agent–harness–environment loop shown in Figure 3. In session 

n, the user issues qn; memory is accessed according to the evaluation setting, and the task agent interacts with the applications to produce trace Hn and state Sn+1 . After each session, the resulting interaction updates Mn+1 before the next request arrives. Both Mn+1 and Sn+1 are propagated to the next session without canonical-state correction. Thus, persistent evaluation requires continuously 

maintaining personal and procedural memory together with their evolving associations , so that user-conditioned procedures remain current, organized, and retrievable over the trajectory. 

Diagnostic evaluation design. To capture both memory-conditioned action and diagnostic mem-ory quality, PraxisMemBench evaluates three session families. Tool and Artifact tasks report personal-memory, procedural-memory, and execution-level scores (Tool Step SR or Artifact As-sert), while Memory QA isolates retrieval quality through Precision, Recall, and F1. All three fami-lies additionally report Session SR. Semantic requirements are judged by an LLM, whereas tool and artifact outcomes are checked programmatically. ## 3 PRAXIS MEM : L EARNING A PERSISTENT MEMORY MANAGER 

Notably, outcome-driven memory managers typically learn from final task rewards. However, such scalar supervision provides little indication of which part of the joint personal–procedural memory state is incorrect. Addressing this ambiguity requires the memory manager to understand, during each update, how user context and procedural knowledge should jointly shape the desired mem-ory state. Fortunately, during training, the canonical structured memory—including user and event states, reusable skills, and their associations—provides exactly this information. The key is therefore to internalize this supervision into the manager without requiring it at deployment. Hence, we propose P RAXIS MEM , which converts the canonical user–procedure state into privileged information (Zhao et al., 2026) by computing a dynamic residual that reveals what is missing or incorrect, where it belongs, and when the defect persists along the update trajectory. Specifically, 

location-aware GRPO learns what information should be maintained and where it should be orga-nized, while dynamic residual-routed OPSD identifies when unresolved defects persist along the update trajectory and provides targeted guidance only at those chunks. Together, the two objectives train the manager to maintain personal memory, procedural memory, and their evolving associations within a unified memory state. We focus on Update below because its state changes persist and shape later memory use. 3.1 PRIVILEGED JOINT -S TATE SUPERVISION

Memory systems. We compare five groups of methods. (1) PraxisMemBench remains challenging even for strong memory-augmented agents: component-level scores are consistently higher than session success, showing that recalling individual memories or satisfying isolated ex-ecution requirements does not guarantee complete task success. (2) Among harness-native sys-tems, Hermes gives the strongest overall Session SR, while Claude Code performs best on Memory QA. (3) Advanced memory systems remain uneven across task families: For Session SR, MemOS performs best on Tool and Artifact tasks, whereas A-Mem leads on Memory QA, suggesting that stronger performance on one form of memory use does not reliably transfer to others. (4) P RAXIS -MEM performs strongly across all three task families and achieves the best overall results. 4.3 ANALYSIS AND FINDINGS 

Finding 1: Joint dependencies take coordinated and interdependent forms. We distinguish two forms of joint dependency, both reflecting how procedures in persistent personal assistance are conditioned on user context. In Coordinated tasks, personal and procedural memory must be used together to determine the task outcome. This includes Field Coordination , where both memories jointly determine the same field; Output Coordination , where they jointly shape different parts of an output; and Workflow Coordination , where they jointly govern different actions or steps. In Interde-pendent tasks, this conditioning is stronger: personal context changes how procedural knowledge can be applied. Action Feasibility determines which actions remain valid, Action Selection deter-mines which candidate action or object should be chosen, and Plan Formation changes how the overall procedure or plan should be composed. Among audited joint tasks, 59.7% are Coordinated and 40.3% are Interdependent. The right panel of Figure 4 summarizes this distribution. 

Finding 2: Separate maintenance struggles with stronger interdependence. To test whether maintaining personal and procedural memory independently is sufficient, we implement DualMem ,which uses separate stores for the two memory types and combines their retrieved contents only before task execution. However, in general, its performance remains limited, motivating a closer analysis by dependency type. We combine Tool Step SR and Artifact Assertion into a single diag-nostic metric, Combined Completion . As shown in the left panel of Figure 6, DualMem performs progressively worse from personal-only (84.7%) and procedural-only (84.5%) tasks to Coordinated tasks (80.1%), and drops further on Interdependent tasks (77.9%). This suggests that Coordinated tasks already require compatible personal and procedural evidence to be maintained together, while Interdependent tasks are harder because the relevant procedural memory depends on the cur-

## A RELATED WORK 

A.1 LONG -T ERM MEMORY AND AGENT BENCHMARKS 

Long-term memory benchmarks have progressed from question answering over fixed interac-tion histories to memory-conditioned agent execution. LoCoMo and LongMemEval test retrieval and reasoning over multi-session conversations (Maharana et al., 2024; Wu et al., 2025), while Mem2ActBench adds task-oriented interaction traces (Shen et al., 2026). More recent benchmarks place memory inside executable loops: MemoryArena constructs causally dependent tasks across sessions, and VitaBench 2.0 evaluates how long-term user information affects tool-mediated deci-sions (He et al., 2026; Chen et al., 2026). These settings move beyond post-hoc recall, but vary in whether they use a general agent harness, natural requests, and agent-created state as an explicit dependency of later tasks. 13 Preprint A complementary distinction concerns what the agent must remember. Personalization benchmarks emphasize user facts, preferences, and their evolution, whereas procedural evaluations represent reusable ways of acting as workflows or skills (Chen et al., 2026; Wang et al., 2025; Li et al., 2026). Harness benchmarks such as ClawArena and WorkBuddy Bench broaden executable cov-erage across evolving environments and application domains (Ji et al., 2026; Cai et al., 2026), yet do not systematically test both memory forms. For persistent personal agents, however, the chal-lenge is to continuously maintain personal and procedural memory together over long-running interaction in a real harness , where both evolve and must remain usable for later tasks. A.2 MEMORY SYSTEMS AND LEARNING -B ASED MANAGEMENT 

Training-free memory systems externalize long histories through context management, retrieval, and structured updates. MemGPT introduces explicit movement between in-context and external memory, while Mem0 extracts compact memories and retrieves relevant entries for later interactions (Packer et al., 2023; Chhikara et al., 2025). Procedural knowledge is commonly stored separately as induced workflows or portable skill packages (Wang et al., 2025; Li et al., 2026). This division provides practical interfaces for user-specific knowledge and reusable action patterns, but gives lim-ited support for their joint formation and revision when a user’s changing constraints alter how a procedure should be executed. Recent work learns memory-management policies with reinforcement learning. Memory-R1 opti-mizes memory operations and answer-time memory use from downstream QA rewards (Yan et al., 2026b); DeltaMem learns end-to-end memory state transitions with state-level rewards (Zhang et al., 2026); and Memory-R2 introduces global–local optimization to improve credit assignment across long session sequences (Yan et al., 2026a). Their rewards primarily encourage correct memory writ-ing and retrieval, but provide little supervision for maintaining a well-organized store over long trajectories . Our P RAXIS MEM addresses this maintenance problem with location-aware GRPO and dynamic residual distillation against a well-organized target memory, selectively providing token-level guidance to the memory chunks responsible for unmet criteria. 

## B ADDITIONAL DETAILS OF PRAXIS MEM 

Persistent memory management requires more than writing correct information once. As interaction history accumulates, the manager must continuously revise memory so that relevant information remains organized and retrievable over long trajectories. PRAXIS MEM therefore uses location-aware GRPO as its primary outcome objective, rewarding not only whether required content is written, but also whether it is maintained in the appropriate part of the persistent store. GRPO alone provides limited learning signal when every rollout in a group misses the same re-quirement. We use OPSD to recover this group-level exploration failure. P RAXIS MEM constructs a dynamic semantic residual from the student’s realized memory state and the contemporaneous tar-get state. This gives the privileged teacher information about what the current rollout still needs to add, revise, move, or remove . The residual is routed at both the criterion and chunk levels: supervision is applied only to unresolved criteria and only where the corresponding defect persists. SFT would require complete, high-quality edit trajectories from each current store to its target state. Automatically deriving such trajectories from target states cannot ensure reliable operation-level supervision, while expert annotation at this scale is costly. Multiple add, update, and delete se-quences can also yield the same valid target state, so selecting a single canonical trajectory imposes one teacher’s action choices. SFT on such trajectories conditions later actions on gold intermedi-ate states. In contrast, P RAXIS MEM trains on the states reached by its own rollouts: the dynamic residual identifies missing, misplaced, outdated, conflicting, or redundant information and guides the operations that can repair it after earlier updates were incomplete or incorrect. ## C BENCHMARK CONSTRUCTION DETAILS 

C.1 TOOL DOMAINS AND SOP G ROUNDING 

Before constructing user trajectories, we select application domains that reflect recurring work and daily-life activities in persistent personal assistance and can be naturally mediated through a general-purpose harness . Candidate domains include communication, scheduling, shopping, travel, health, and personal finance. We retain a domain only when it supports (i) persistent applica-tion objects, (ii) both information-seeking and state-changing actions, and (iii) arguments, outputs, or application states through which personal and procedural memory can affect execution . The held-out domains adapt tool families from existing executable-agent environments to a determinis-tic offline setting. We separately author the training domains around analogous high-level activities while using distinct domain names, tool interfaces, fixture schemas, and workflows. For each selected domain, we implement a stateful mock application . Its data model specifies the application objects and valid state transitions; typed tool interfaces expose search or read operations together with actions such as creating, updating, sending, booking, or recording; and fixture files initialize the state for reproducible sessions. Every state-changing action must be observable through a subsequent read or final-state export, which allows the same environment to support both task execution and programmatic evaluation. A domain is admitted only if its fixtures load correctly, the exposed tool schemas match their implementations, read and write calls succeed through the MCP interface, writes produce the expected state transition, invalid tool calls fail explicitly, and independent runs do not share mutable state. These applications are implemented by experienced engineers, with coding agents used to assist development and testing. For each validated domain, we use a three-stage pipeline to construct reusable SOPs before intro-ducing a specific persona. An SOP specifies a common task goal, the action dependencies required to complete it, and the expected application state or artifact, while leaving all user-specific values uninstantiated. First, a proposal annotator inspects the domain’s objects and exposed tools and pro-poses three to five tasks that a user would naturally perform in that application. We reject goals that collapse to a single tool call or require an artificial sequence added only to increase task length. For every retained proposal, the annotator also marks which tool arguments, output fields, or artifact slots could later carry personal memory. Second, a tool engineer makes each proposal executable. The engineer creates a fixture containing the prerequisite objects, target objects, and distractors; runs a reference sequence against the appli-cation; and records the required tool calls, returned object identifiers, and resulting state changes. For an artifact workflow, this stage also fixes the artifact location and defines deterministic checks for its existence and structure together with semantic requirements for manual review. Third, an independent tester receives only the task goal and exposed tool schemas, without the reference se-quence, fixture contents, or evaluation checks. The tester completes the task and exports its tool trace and final application state. A tool-use SOP is accepted only when this blind execution reaches the intended state and covers the required calls; an artifact SOP must additionally pass its deterministic and semantic checks. We maintain disjoint domain pools for training and held-out testing. Each split contains 20 domains; the training pool contains 120 accepted SOPs and the test pool contains 140. The pools share no domain names, and training domains use separate capability names, tool surfaces, fixture schemas, and SOP identifiers. To model an evolving user rather than a fixed persona, the event generator then synthesizes a con-crete change for each selected mutable field using the prompt in Figure 21. It receives the field’s current value, the complete persona snapshot, earlier events, the session time, and, for executable tasks, the selected domain and SOP. We require the old and new values to differ substantively, the event to remain consistent with the current profile and history, and its wording not to copy entire persona values or explicitly expose a name, age, gender, or occupation. Invalid events are repaired or resampled before the session is instantiated. 

Memory disclosure and dependency construction. Beyond constructing the executable task it-self, each session must also establish the conversational history from which later memory depen-dencies arise. Because user-specific information in persistent assistance is typically revealed inci-dentally across everyday interactions rather than restated at task time, we construct preceding user turns that naturally disclose new personal events and procedural rules before they are needed. 

Personal updates describe changes in the user’s state, while procedural updates introduce reusable, domain-specific requirements for how an application action should be performed or an output should be formatted. New procedural rules are stated explicitly when first introduced; later sessions may reuse them without restating their exact content. In this way, both personal and procedural memory are accumulated through natural interaction rather than exposed directly as task specifications. Given this accumulated history, we then select previously disclosed personal facts together with pro-cedural memories that remain applicable in the current domain and user state. Recent information introduced immediately before the task is normally excluded from the historical target set, since it does not require long-term retrieval. The selected memories are instantiated into measurable task dependencies, such as query constraints, object selection, workflow decisions, output requirements, or final-state conditions. In joint tasks, personal context can further affect which procedural requirement applies or how it should be instantiated . The public request preserves the task goal and necessary non-memory details while omitting the historical personal and procedural informa-tion that the memory method must recover. With these dependencies established, the next stage instantiates the concrete task and its corresponding gold checks.

For Memory QA , the session asks about previously disclosed attribute histories. Independent validation and acceptance. Before an executable session is accepted, an indepen-dent tester receives the public request, only the personal and procedural memories required for that task, and the exposed application tool schemas. The tester can run the same application interface but cannot inspect the fixture, reference tool sequence, gold artifact requirements, or grading code. We compare its resulting trace, state, and artifact with the recorded execution and the same pro-grammatic and rubric-based checks used in evaluation. Tool tasks must cover the required reference steps, reach the intended state, and demonstrably use a targeted personal memory point; artifact tasks must pass their programmatic, semantic-memory, and procedural checks. Memory QA ques-tions undergo gold-answer consistency and answer-leakage checks. Failed sessions are repaired and retested or resampled. Only after acceptance do the disclosed user changes, procedural updates, and application outcome enter the state replayed for the next session. C.3 BENCHMARK SCALE 

Session count alone does not determine the volume or difficulty of persistent history. Existing memory benchmarks therefore report complementary measures such as sessions, turns, interaction periods, and history tokens. As summarized in Table 10, LongMemEval, MemBench, PersonaMem-v2, and AMemGym explicitly evaluate multiple history-length settings (Wu et al., 2025; Tan et al., 2025; Jiang et al., 2025; Jiayang et al., 2026). MemoryArena further shows that executable traces can reach 122.4K tokens with only 2–16 sessions because each session contains multi-step actions and observations (He et al., 2026). Motivated by the multi-session evaluation designs in Table 10, PraxisMemBench uses 25 tempo-rally ordered sessions per trajectory. This length provides repeated opportunities for personal state changes to affect which procedures apply and how they are executed, while keeping the construc-tion, independent validation, and full evaluation of executable sessions tractable. Across the com-24 Preprint plete OpenClaw, Claude Code, and Hermes runs, the observable user, assistant, tool-call, and tool-observation history averages an estimated 663.6K tokens per trajectory (606.7K–742.7K). This scale supports persistent-memory evaluation, although the benchmark’s primary focus is user-conditioned procedural use. Upon acceptance, we will release the benchmark and construction tools so that fu-ture evaluations can extend trajectories with additional sessions. C.4 BENCHMARK EXAMPLES

## D EVALUATION DETAILS 

Evaluation protocol. Each memory method is evaluated over a complete trajectory in chronolog-ical order. Within each session, a user script specifies the sequence of disclosures and requests. A fixed user message is sent directly when provided; otherwise the user simulator generates the next public message from the current and previous turn strategies and recent dialogue, using the prompt in Figure 22. It either continues an unmet request or advances to the next turn, without seeing fu-ture turn strategies. The task agent then responds through its harness. In OpenClaw-based runs, it receives the current session dialogue, available memory context, and application tools exposed through MCP. In the Scheduled setting, controlled methods retrieve at predefined task or targeted-question turns, using the current public user request as the query, and append the returned context to that turn. In the Autonomous setting, requests are less specified; the task agent decides when to call its available memory operation and supplies a query when that operation accepts one. Controlled OpenClaw runs disable its native memory tools and instruct the agent not to use workspace files as an alternate memory store; native-memory methods retain their built-in interface. At session end, controlled methods ingest the public dialogue and observed tool events through their update interface; native methods maintain memory through their agent behavior. The resulting memory store and application state are both carried into the next session. Evaluation is free-running with respect to these states: session-specific fixtures define or introduce the objects scheduled for the current session, but do not restore earlier application state to its canonical construction snapshot. The runner neither resets nor repairs application state after a failed execution. Consequently, earlier errors may cause state drift, including modified, missing, or already-consumed objects, and any re-sulting downstream failure remains part of the persistent evaluation. Canonical states and reference executions are used only for benchmark construction, validation, and grading; they are not used to overwrite the evaluated trajectory. OpenClaw assigns a distinct conversation key to each session, so prior session dialogue is not directly carried into the next task conversation. 

Task-family grading. For Tool tasks, we compare the observed tool trace and final application state with the required steps and procedural checks. Structured memory-bearing arguments are checked against gold values; open-text arguments are scored by the LLM judge for semantic cover-age of the required personal facts using the prompt in Figure 25. Tool Memory Slot averages these argument scores, Tool Procedural measures passed procedural checks, and Tool Step SR measures required-step completion. For Memory QA, the judge compares the answer with atomic gold facts: Recall is the fraction of fully recovered facts using Figure 27, Precision measures the accuracy of an-swer claims against the gold facts using Figure 28, and F1 is their harmonic mean. For Artifact tasks, programmatic verifiers check the artifact’s existence, structure, and procedural requirements, while the judge scores whether its semantic slots reflect the required personal facts using Figure 26. Arti-fact Memory Slot averages the slot scores, Artifact Procedural measures passed procedural checks, and Artifact Assert measures passed non-procedural assertions.

E.1 BENCHMARK CONSTRUCTION AND EVALUATION 

Construction setup. Application SOPs and individual sessions were constructed by software en-gineers working with coding agents and independently validated by a separate group of engineers. We use the GPT-5.5 API to expand PersonaHub seeds into structured profiles and to synthesize personal change events. 

Models and evaluation. Qwen3.7-Plus serves as the task agent, while GLM-5 serves as both the user simulator and the LLM judge. LLM-based memory baselines use Qwen3.5-9B for memory management where applicable, and P RAXIS MEM is trained from the same Qwen3.5-9B base model. The user simulator, LLM judge, and memory LLM run with temperature 0 and reasoning disabled. Programmatic verifiers evaluate required tool steps, procedural requirements, artifact assertions, and observable application state, while the GLM-5 judge scores semantic personal-memory require-ments and Memory QA responses against the gold annotations. 

System implementations. OpenClaw 2026.4.15 provides the task harness for controlled memory methods and the OpenClaw native-memory baseline, with the latter retaining its built-in memory operations. The other native-memory baselines use Claude Code 2.1.153 with Agent SDK 0.2.128 and Hermes v0.20.0, respectively. In native-memory systems, the task LLM performs memory retrieval and maintenance within the agent loop rather than relying on a separate memory LLM. All controlled memory methods use a 4,096-token final memory-injection budget. DualMem com-bines retrieval from its personal and procedural stores within this same budget. Long Context instead uses a 128,000-token total task context; when the accumulated history exceeds this limit, the oldest history is truncated first while preserving the current-session context and system instructions. We report one complete-test-split inference run per method. E.2 DUAL MEM BASELINE 

Memory representation. DualMem is a dual-store baseline inspired by Mem0 (Chhikara et al., 2025). It instantiates two isolated memory stores with the same Qwen3.5-9B memory model and Qwen3-Embedding-0.6B embedder. Each store has its own local Qdrant vector collection, entity index, history database, and user scope. The Personal store retains user identity, relationships, pref-erences, goals, constraints, resources, commitments, and evolving state. The Procedural store re-tains reusable steps, preconditions, branches, tool-use rules, output conventions, verification checks, and recovery procedures. Personal extraction follows the Mem0 extraction pipeline with a personal-information scope, while procedural extraction uses a dedicated, domain-general procedural instruc-tion. No record or entity link is shared between the two stores. 

Memory update. At the end of each session, both stores receive the same user–assistant inter-action and visible tool evidence. DualMem updates them serially in the fixed order Personal then Procedural. Within each store, the memory manager may add, update, or delete memory records, while the entity-linking stage updates the corresponding entity-index relations. Deduplication and conflict handling remain local to that store: the Procedural updater cannot read the Personal store or condition its decisions on a personal update, and the Personal updater cannot link its records to a procedure. Thus, the two updates separate what is remembered about the user from what is remembered about how to act. 

Retrieval and injection. At each scheduled retrieval point, the same query is issued first to the Personal store and then to the Procedural store. Each side returns up to 20 items in its own similarity order; DualMem performs no cross-store score normalization, reranking, linking, or conflict resolution. The two result lists are serialized under separate personal memory and 

procedural memory sections and concatenated within the shared 4,096-token memory budget. Unused capacity from a shorter side is assigned to the other side, while truncation preserves com-plete memory items whenever possible. The resulting block is supplied directly to the task agent, which must determine how the two sets of memories apply to the current task. In the Autonomous setting, one agent-issued memory search(query) call triggers the same sequential two-store retrieval and merged return. E.3 PRAXIS MEM TRAINING

Oracle conditions in memory benchmarks typically isolate memory access while leaving evidence integration, reasoning, and task execution to the same reader or task agent. Consequently, providing gold memory does not necessarily yield perfect performance. To further diagnose this gap in P RAXIS MEM BENCH , we compare two Oracle conditions. Oracle 

provides the exact personal and procedural memories required by the current task, while leaving the task agent to determine how they should be grounded to tool arguments, artifact fields, action order, and application state. Oracle-Action additionally provides an action scaffold: the required tools and their order, together with the source of task-relevant arguments, such as personal memory, procedural memory, the user request, or a previous tool result. It does not reveal runtime object identifiers, unseen tool outputs, complete gold tool calls, final answers, or finished artifacts; the agent must still interact with the application and execute the task. As shown in Table 13, action-level guidance substantially narrows the remaining gap on executable tasks. Tool Session SR rises from 83.90% to 94.10%, while Artifact Session SR increases from 77.42% to 95.65%. Memory QA, by contrast, is already nearly saturated under the standard Oracle and reaches 100% with Oracle-Action. The larger gains on Tool and Artifact tasks indicate that a substantial portion of the residual Oracle error comes after memory access: the agent must still 

combine personal and procedural requirements, ground them to concrete parameters and ap-plication objects , resolve runtime tool outputs, and verify execution. Even Oracle-Action remains below perfect end-to-end performance because these runtime decisions and outcomes are not di-rectly revealed. We therefore interpret Oracle as an upper bound on memory supply under a fixed task agent, rather than as a programmatically perfect solver. F.2 AUTONOMOUS -S ETTING RESULTS 

Table 14 reports results in the Autonomous setting, where requests are less specified and the task agent must decide whether, when, and with what query to access memory. Compared with the Scheduled results in Table 2, Autonomous interaction reduces task success for most methods, particularly on Tool and Memory QA sessions. Hermes falls from 26.34% to 10.42% Tool Session SR and from 10.71% to 2.86% Memory QA Session SR; MemOS falls from 19.12% to 8.33% and from 3.57% to 0%, respectively. Component-level execution remains considerably higher: Hermes and MemOS still reach 62.58% and 62.80% Tool Step SR, yet complete few ses-sions. Under less specified requests, an agent therefore makes partial progress while failing to recover the user state and procedural knowledge that jointly determine the correct target, action, or execution path. Autonomous performance also depends on whether the task agent invokes memory. We define the retrieval-call rate as the fraction of sessions in which the agent makes at least one memory search 

call. The advanced memory systems have an average retrieval-call rate of 57.3%. To examine whether the benchmark conclusions depend on the task-agent backbone, we rerun the Scheduled setting on the first eight test trajectories with three task LLMs: Qwen3.7-Plus, GLM-5.2, and DeepSeek-V4-Pro. F.7 RUNTIME AND TOKEN EFFICIENCY 

Persistent personal assistants operate inside general-purpose harnesses over repeated sessions, mak-ing both monetary cost and memory-maintenance latency practical constraints. Task-agent infer-ence accumulates API charges throughout the trajectory, while constructing and updating memory consumes additional compute and determines how quickly newly disclosed information becomes available to later tasks. We therefore evaluate cost and latency alongside Session SR. We record task-agent calls, input and output tokens, and wall-clock time for each executed session. Task-LLM API cost uses the standard international real-time Qwen3.7-Plus rates of USD 0.40 per million input tokens and USD 1.60 per million output tokens (Alibaba Cloud, 2026).
