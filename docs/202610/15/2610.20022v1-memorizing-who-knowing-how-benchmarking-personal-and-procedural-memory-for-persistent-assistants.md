## 摘要
持久化个人智能体的记忆系统不能局限于孤立的记忆，而必须同时维护关于服务对象的个人记忆，以及关于如何采取行动的程序性记忆。尤为重要的是，在基于 harness 的个人助理场景中，程序或技能天然受用户条件影响：个人背景决定哪些程序适用、如何具体执行，以及何时需要调整。现有基准通常侧重于个人记忆或程序性记忆，较少探究二者之间的交互。我们提出 PraxisMemBench，这是一个面向持久化个人助理的基于 harness 的基准，涵盖日常生活与工作轨迹；在其中，个人记忆与程序性记忆共同演进，后续任务依赖于二者。实验表明，分别维护两类记忆并不足够：当依赖关系从单一类型转为相互依赖时，任务完成率从 84.6% 降至 77.9%。更广泛地说，在现有方法中，随着交互历史增长，关系相关的失败率从早期会话到后期会话由 59.8% 升至 72.9%，揭示出持续维护方面的挑战：仅写入正确记忆并不足够，若无法保留其不断演进的内容与组织方式，以供后续检索，仍然难以奏效。为此，我们提出 PraxisMem，利用特权联合状态监督，将维护记忆内容与组织方式的能力内化到记忆管理器中，并采用位置感知的 GRPO 与动态残差路由 OPSD。PraxisMem 的整体会话成功率达到 40.78%，而 Claude Code 的原生记忆为 20.60%。

## Abstract
Memory systems for persistent personal agents must move beyond isolated memories, maintaining both personal memory about whom they serve and procedural memory about how to act. Crucially, in harness-based personal assistance, procedures or skills are inherently user-conditioned: personal context determines which procedures apply, how they are instantiated, and when they should change. Existing benchmarks typically emphasize either personal or procedural memory, leaving their interaction underexplored. We introduce PraxisMemBench, a harness-based benchmark for persistent personal assistance across daily-life and work trajectories, where personal and procedural memory evolve together and later tasks depend on both. Experiments show that maintaining two memory types separately is insufficient, with completion dropping from single-type to interdependent dependencies (84.6% to 77.9%). More broadly, across existing methods, relation-related failures increase from early to late sessions as interaction history grows (59.8% to 72.9%), revealing a continual-maintenance challenge: writing correct memories is not enough if their evolving content and organization cannot be preserved for later retrieval. To address this, we propose PraxisMem, which uses privileged joint-state supervision to internalize the ability to maintain memory content and organization into the memory manager, with location-aware GRPO and dynamic residual-routed OPSD. PraxisMem reaches 40.78% overall Session Success Rate, compared with 20.60% for Claude Code's native memory.

## 1. 核心问题与整体含义

### 1.1 研究背景与动机
长期服务同一用户的个人助手，需要同时维护两类记忆：

- **个人记忆（Personal Memory）**：用户的身份、关系、偏好、约束及其变化。
- **程序性记忆（Procedural Memory）**：可复用的工作流程、工具使用规则、输出格式和验证步骤。

现有评测通常分别考察“记住用户信息”或“复用操作流程”，但实际个人助手中的流程往往是**受用户情境约束的**：用户背景不仅决定流程中的参数，还可能决定哪些行动有效、应该选择哪个对象，以及整个计划如何组织。

例如，“按之前的方式退货”要求助手既记住退货步骤，也知道当前家庭关系对应哪件商品、退款应使用哪种支付方式。

### 1.2 核心研究问题
论文关注的不是简单的“能否存下、检索出两类信息”，而是：

> **随着用户状态和交互历史持续变化，助手能否维护个人记忆与程序性记忆之间的有效关联，并将其用于后续行动？**

作者将这一问题概括为**持续维护挑战**：某次更新写入了正确内容，并不意味着这些内容在长期积累后仍然组织合理、关系完整、可以正确调用。

论文提供两项主要贡献：

1. **PraxisMemBench**：联合评测两类记忆及其长期演化的可执行基准。
2. **PraxisMem**：利用训练期特权状态监督，学习维护记忆内容和组织结构的记忆管理器。

## 2. 方法论：核心思想、技术细节与算法流程

### 2.1 联合记忆状态建模
论文将记忆状态表示为三个部分：

- 个人记忆；
- 程序性记忆；
- 两者之间随时间变化的关联结构。

每轮会话不仅更新记忆，也会改变外部应用状态，例如订单、日程、工单或文档。后续任务同时依赖历史记忆和先前行动留下的状态。

**关键思想**是：记忆管理器不仅要学习“写什么”，还要学习“写在哪里，以及如何保持其关联可恢复”。

### 2.2 结构化 Markdown 记忆存储
PraxisMem 使用共享目录维护记忆：

| 存储位置 | 内容 |
|---|---|
| `USER.md` | 当前用户属性、偏好与约束 |
| `MEMORY.md` | 连接当前状态与历史事件的主题索引 |
| `events/*.md` | 带时间的变化记录，可包含任务和技能关联 |
| `skills/<domain>/SKILL.md` | 领域规则与可复用流程 |
| 原始交互归档 | 供定向搜索和检查的源证据 |

需要注意：

- 两类内容仍然分文件存储，但由**同一管理器联合维护**。
- 个人状态通过“索引—事件—技能”的路径与流程建立间接关联。
- `MEMORY.md` 本身不直接存放技能链接。
- 这一存储结构属于 **PraxisMem 的实现选择**，不是基准对所有方法的强制要求。

管理器同时学习两项任务：

- **Update**：读取新交互，新增、修改、合并或删除记忆。
- **Retrieval**：使用只读工具，输出当前任务所需的简洁记忆要点。

### 2.3 位置感知 GRPO：同时奖励内容和组织位置
普通结果奖励难以区分“内容正确但放错位置”与“内容及组织均正确”。作者因此引入位置感知奖励：

1. 比较管理器产生的记忆变化与参考变化。
2. 先依据类型兼容性和语义相似度建立候选匹配。
3. 进行一对一匹配，依次优先考虑：
   - 位置是否正确；
   - 匹配覆盖数量；
   - 语义相似度。
4. 计算位置加权的精确率、召回率和 F1。
5. 额外奖励有效操作，并惩罚过多调用和不必要的存储膨胀。

具体设置包括：

- 语义匹配阈值：**0.7**。
- 内容匹配但位置错误时，匹配权重降为 **0.2**。
- Update 总奖励由 **80% 状态匹配、10% 格式、10% 效率**组成。

之后使用 GRPO，在同一输入的多条候选轨迹之间计算相对优势，优化整个管理轨迹。

### 2.4 动态残差路由 OPSD：补充组内共同失败的监督
GRPO 的局限是：**如果所有候选轨迹都遗漏同一要求，组内相对奖励难以提供该要求的成功示范。**

论文引入两级监督路由：

- **要求级路由**：只有当全部候选都未满足某项记忆要求时，才激活其蒸馏监督。
- **交互块级路由**：逐块比较实际记忆与对应参考状态，只在该缺陷仍然存在的块上提供监督。

动态残差包括：

- 缺失内容；
- 不完整、过时、冲突或放错位置的内容；
- 冗余内容。

教师与学生使用同一冻结策略快照，但教师额外看到训练期残差信息。教师**不生成替代操作轨迹**，而是对学生已经采样的 token 重新评分，通过反向 KL 形式的在策略自蒸馏提供指导。

最终训练目标结合：

- 覆盖完整轨迹的 GRPO；
- 仅覆盖激活片段的 OPSD；
- 相对参考模型的 KL 正则。

**部署时不需要参考状态或残差信息。**

## 3. 实验设计：数据、场景、基准与对比方法

### 3.1 PraxisMemBench 的规模
该基准由虚构人物和合成交互轨迹构成：

| 项目 | 规模 |
|---|---|
| 训练集 | 20 名用户、500 个会话 |
| 测试集 | 20 名用户、500 个会话 |
| 每条轨迹 | 25 个按时间排序的会话 |
| 应用领域 | 训练、测试各 20 个，共 40 个 |
| SOP | 训练 120 个、测试 140 个 |
| 测试记忆依赖 | 2,185 个 |
| 可执行任务 | 360 个，其中 303 个需要两类记忆，占 84.2% |

场景覆盖旅行、购物、健康、饮食、金融、邮件、日程、团队沟通、工单和文档等。

训练和测试的应用名称、工具接口、数据结构与 SOP 标识相互分离，但仍包含相近的高层活动，因此更适合解释为**跨应用实现的迁移评测**。

代表性原生系统运行中，每条轨迹平均产生约 **66.36 万 token** 的可观察交互历史，部分记忆依赖跨越数月。

### 3.2 三类任务与两种设置
**任务类型：**

- **Tool**：执行工具调用并改变应用状态。
- **Artifact**：生成文档、报告或应用内文本成果。
- **Memory QA**：回忆用户属性、历史状态与变化事件。

**评测设置：**

- **Scheduled**：在预定义位置触发记忆检索，控制调用时机。
- **Autonomous**：请求更加欠明确，由助手自行决定是否检索、何时检索和如何构造查询。

评测按完整时间轨迹运行，**不会在失败后恢复记忆或应用状态**，因此早期错误可以传播到后续任务。

### 3.3 对比方法
主实验共报告 **15 种方法或诊断条件**，包括：

- **诊断条件**：Oracle、Long Context、DualMem。
- **基础检索**：BM25、Embedding RAG。
- **原生记忆系统**：OpenClaw、Hermes、Claude Code。
- **高级记忆系统**：Mem0、Zep、A-Mem、ReMe、MemOS。
- **学习型管理器**：Memory-R2、PraxisMem。

其中，DualMem 将个人记忆与程序性记忆分别维护，仅在任务执行前拼接检索结果，用于检验“独立维护是否足够”。

### 3.4 评测指标的重要边界
论文同时报告记忆分数、工具步骤完成率、成果断言分数和 Session SR。

**主文中的 Session SR 是“记忆条件化会话成功率”，不是严格端到端任务成功率：**

- Tool／Artifact：适用的个人、程序性记忆维度均达到 **0.75**。
- Memory QA：F1 ≥ **0.75**，且精确率、召回率均 ≥ **0.60**。
- 严格端到端成功还需满足全部执行与结果要求，但不是这里 headline 数字的定义。

整体 SR 按有效会话汇总计算，而非简单平均三类任务分数；少量会话经最终人工验证后被排除。

## 4. 资源与算力

### 4.1 模型配置
- 任务智能体：**Qwen3.7-Plus**。
- 用户模拟器与语义裁判：**GLM-5**。
- 记忆管理基础模型：**Qwen3.5-9B**。
- 向量模型：**Qwen3-Embedding-0.6B**。
- Memory-R2 也从相同的 Qwen3.5-9B 基础模型重新训练。

### 4.2 训练配置
论文明确报告：

- **单节点、8 张 NVIDIA A100 GPU**。
- 全参数训练，使用 **FSDP2**。
- 训练样本 **1,921 个**：
  - Update：481 个；
  - Retrieval：1,440 个。
- 每个样本采样 **8 条 rollout**。
- 训练 **1 个 epoch**，训练分析覆盖 **160 个步骤**。
- Batch size：8；学习率：\(10^{-6}\)。
- 最大输入／输出长度：24,576／4,096 token。

**未明确报告完整训练的实际耗时、GPU 总小时数及训练成本。**

### 4.3 推理与记忆维护开销
PraxisMem 的平均单会话资源包括：

- 任务模型调用约 **7.47 次**。
- 任务侧输入约 **24.89 万 token**，输出约 **5,160 token**。
- 记忆侧调用约 **35.82 次**，更新／构建耗时约 **276.62 秒**。
- 返回任务模型的记忆上下文平均约 **340 token**。

按文中的 API 与 GPU 计价口径，完成 500 个测试会话约需 **115 美元**。这一数字**不代表包含训练、数据构建和全部基础设施开销的总成本**。

## 5. 实验数量与充分性

### 5.1 大致实验规模
不将每项指标单独计算，实验至少包含：

- **2 套主评测**：Scheduled 和 Autonomous，各报告 15 种方法／条件。
- **4 个消融变体**：在固定 8 条测试轨迹上比较。
- **2 个 Oracle 条件**：Oracle 与 Oracle-Action。
- **3 种任务模型 × 3 种记忆方法**：固定 8 条轨迹上的骨干敏感性实验。
- 多项诊断分析：
  - 单类型、协调型、相互依赖型任务；
  - 证据时间距离；
  - 早、中、晚阶段失败组成；
  - DualMem 检索覆盖与失败归因；
  - 训练动态、监督路由、成本和延迟。
- **语义裁判审计**：120 个评分点，2 名专家和4种模型裁判。

部分设置复用同一主实验结果，**不能简单相加为完全独立的实验次数**。

### 5.2 充分性与公平性评价
**较充分的方面：**

- 不仅比较最终指标，还分析检索、关联、长期退化及训练机制。
- 多数受控方法共享任务模型和 **4,096-token** 记忆注入上限。
- 消融共享数据、基础模型、存储格式和评测协议。
- 使用程序验证与语义裁判结合，并进行人工一致性审计。

**仍需谨慎的方面：**

- 每种方法仅报告 **一次完整测试运行**，没有多随机种子、置信区间或显著性检验。
- 消融和骨干实验仅覆盖 **8／20 条测试轨迹**。
- 原生记忆系统由任务模型自行管理记忆，受控方法则使用独立记忆模型；比较反映系统整体能力，但不能完全隔离单一算法因素。
- Long Context 上限为 128K，而完整历史平均约 664K token，因此它不是无限上下文对照。
- DualMem 缺少跨库重排、关联与冲突处理，其结果不足以证明所有双库架构都不可行。
- 不同结果表的有效会话分母应进一步明确，以便精确复现汇总指标。

## 6. 主要结论与发现

### 6.1 两类记忆独立有效，不等于联合有效
DualMem 的完成分数随依赖增强而下降：

- 个人记忆单独依赖：**84.7%**。
- 程序性记忆单独依赖：**84.5%**。
- 协调型联合依赖：**80.1%**。
- 相互依赖：**77.9%**。

其中，“相互依赖”意味着个人情境会改变行动可行性、对象选择或计划形成，而非仅提供独立补充信息。

### 6.2 长期交互使失败重心转向关系维护
在所审计的 MemOS、Hermes、PraxisMem 失败案例中：

- 访问失败占比由早期 **40.2%** 降至后期 **27.1%**。
- 关系相关失败占比由 **59.8%** 升至 **72.9%**。

这里是**失败组成占比**，不是所有任务上的绝对失败率。它支持“后期更需要处理关系碎片化和竞争记忆”的判断。

### 6.3 PraxisMem 显著改善记忆条件化成功率
Scheduled 设置下：

| 方法 | Tool SR | Memory QA SR | Artifact SR | 整体 SR |
|---|---:|---:|---:|---:|
| Claude Code | 22.44% | 15.71% | 22.58% | 20.60% |
| Hermes | 26.34% | 10.71% | 23.23% | 21.00% |
| PraxisMem | **37.88%** | **55.00%** | **31.33%** | **40.78%** |

相对 Claude Code，整体提升 **20.18 个百分点**，但距离 Oracle 的 **86.20%** 仍有明显差距。

### 6.4 组织位置与精细监督均有贡献
固定 8 条轨迹的消融结果：

| 训练变体 | 综合完成分数 | 相互依赖完成分数 | 平均 SR |
|---|---:|---:|---:|
| 仅内容 GRPO | 66.2% | 54.9% | 23.5% |
| 加位置感知奖励 | 73.6% | 66.5% | 29.0% |
| 再加要求级 OPSD | 76.9% | 72.1% | 32.7% |
| 完整 PraxisMem | **83.4%** | **82.1%** | **43.1%** |

完整路由将平均蒸馏激活 token 比例从 **62.0%** 降至 **33.2%**，同时提高表现，说明更精确的监督比更广泛的监督更有效。

### 6.5 自主调用和检索后的行动仍是瓶颈
- Autonomous 中，PraxisMem 的 Tool、QA、Artifact SR 分别为 **23.00%、22.22%、31.64%**，仍是最强非 Oracle 方法，但多数任务类型明显低于 Scheduled。
- 高级记忆系统平均只有 **57.3%** 的会话调用过检索。
- Oracle 提供正确记忆后仍不能完全成功；增加行动骨架后，Tool SR 从 **83.90%** 升至 **94.10%**。

因此，瓶颈还包括**意识到需要记忆，以及将正确记忆转化为工具参数和行动顺序**。

## 7. 优点与亮点

- **问题定位明确**：将研究重点从事实召回推进到“用户情境如何约束流程”。
- **评测具有持续性**：记忆和应用状态自由演化，能够暴露错误积累与长期维护问题。
- **依赖可验证**：记忆要求映射到工具参数、对象选择、输出字段或最终状态，而非只看回答是否提及某事实。
- **构建验证较严谨**：独立测试者在不查看参考执行和评分代码的情况下验证任务可执行性。
- **训练机制互补**：位置奖励解决组织问题，残差蒸馏补充组内共同失败的学习信号。
- **不依赖唯一编辑轨迹**：以最终状态而非固定操作序列监督，允许多种有效修复路径。
- **关注实际部署开销**：同时报告效果、上下文长度、成本和维护延迟。

## 8. 不足与局限

### 8.1 合成数据与真实世界差距
- 人物、事件及部分交互由模型生成，可能带有文化、职业和行为偏差。
- 任务有意强化可测量的联合依赖，不一定反映真实用户请求分布。
- 应用为隔离的离线模拟系统，未覆盖真实 API 故障、权限变化、并发和外部副作用。

### 8.2 特权监督构建成本较高
- 需要会话级乃至交互块级参考状态、目标位置和内容要求。
- 这些标注的构建、审核与维护成本可能较高。
- 尚未验证能否在缺少精细参考状态的真实交互上低成本扩展。

### 8.3 组织监督可能绑定特定表示
位置正确性依赖文件、标题和技能路径。虽然作者允许替代结构，但尚缺少跨存储格式验证，不能确定收益有多少来自通用关联维护能力，有多少来自对指定模式的适配。

### 8.4 统计与因果证据仍有限
- 单次运行难以评估方差。
- 8 条轨迹的消融样本较小。
- 证据年龄与性能下降存在关联，但也可能混入任务难度、更新次数和应用状态漂移。
- 关系失败分类具有人工判断成分，且阶段分析仅涉及部分方法。

### 8.5 核心指标不能直接解释为部署可靠性
**40.78% 不是严格端到端成功率**。仍需补充严格执行成功率、错误行动严重性及安全约束等指标。

此外，语义裁判审计仅覆盖 120 个评分点；GLM-5 与人工参考总体 QWK 为 **0.793**，仍存在评分误差。

### 8.6 自主性、安全与隐私尚未解决
- 实际部署中，助手必须自行识别记忆需求，而 Autonomous 结果说明这一能力仍较弱。
- 论文没有系统评估记忆投毒、提示注入、敏感信息泄露、删除与遗忘。
- 平均数分钟的记忆维护耗时，对实时更新场景仍可能构成限制。

**总体评价：**论文最重要的价值，是将长期助手记忆明确表述为“内容与关联结构的持续维护问题”，并提供了可执行基准和有针对性的训练方法。结果具有说服力，但其优势目前主要成立于合成、受控环境及记忆条件化指标下，距离真实世界的长期可靠助手仍有较大空间。
