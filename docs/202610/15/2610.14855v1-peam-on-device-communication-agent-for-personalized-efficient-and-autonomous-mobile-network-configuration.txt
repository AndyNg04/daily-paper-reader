Abstract 

The growing deployment of compact large language models on smartphones is enabling autonomous on-device decision-making, such as emerging mobile GUI agents. However, many mobile decisions, such as network configuration when users switch apps or connectivity conditions change, must satisfy stringent latency constraints to preserve user experience. In this paper, we propose PEAM, an on-device LLM-based com-munication agent that autonomously generates personalized network-configuration rules executable within milliseconds. Specifically, PEAM first fine-tune the on-device LLM with a dataset constructed from manually annotated real-user data to integrate the communication knowledge into the local model. PEAM then operates in two phases. In the rule-generation phase, which is performed when the device is idle, such as overnight, PEAM analyzes historical network-configuration records in batches and reflects across batches to consolidate consistent evidence, reduce local bias, and derive robust con-figuration rules. To enable more accurate and stable rule gener-ation over time, PEAM further constructs a user profile from high-confidence rules to capture the user’s network prefer-ences and incorporates this profile into each rule-generation cycle. In the rule-execution phase, PEAM is invoked when the communication context changes, such as when users switch apps or connectivity conditions change, and searches the rule library to identify and execute the appropriate rule. Exper-iments demonstrate that PEAM, based on a fine-tuned 4B model, achieves 99.13% correct network configuration de-cisions, while 92.50% of the rules generated by PEAM are valid, outperforming the traditional expert-rule based method by 4.41% and 84.50%, respectively. 

Introduction 

Recent advances in large language models (LLMs) have significantly improved their reasoning, planning, and au-tonomous decision-making capabilities. One repre-sentative task is mobile network configuration, which dy-namically selects and adjusts communication resources and settings, such as access networks, WiFi access points, and SIM cards, according to application requirements, network conditions, device states, and user contexts. Unlike many of-fline decision-making tasks, mobile network configuration directly affects user experience and often lies on a latency-critical execution path. A practical solution should therefore be personalized , because different users may prefer differ-ent configurations under similar communication conditions; 

efficient , because configuration decisions must often be com-pleted within stringent latency constraints; and autonomous ,because the device should learn and apply user preferences without repeated manual intervention. Existing network-configuration methods mainly fall into three categories: expert-rule (ER)-based, supervised-learning (SL)-based, and reinforcement-learning (RL)-based methods. ER-based methods remain widely used in practi-cal systems. They encode communication knowledge into hand-crafted constraints over metrics such as signal strength, uplink/downlink latency, and quality of service (QoS), and then map such conditions to switching actions(Sunita, Soni, and Baghla 2015; Miyim, Umar, and Kiyawa 2021; Wu et al. 1arXiv:2610.14855v1 [cs.AI] 10 Oct 2026 2022). Although ER-based methods are efficient at runtime, their strategies are primarily determined by expert-designed heuristics, making them difficult to personalize according to individual user behavior. To improve adaptability, recent studies have explored SL-based and RL-based methods. SL-based methods learn correlations between communication observations and user actions from labeled data(Masi and Wac 2020; Paropkari, Thantharate, and Beard 2022; Peng et al. 2023), whereas RL-based methods formulate network switching as a sequential decision process and optimize poli-cies through reward-driven interaction(Tan et al. 2010; Wang et al. 2024; Xie, Zhu, and Li 2023; Lu et al. 2025; Wu et al. 2024; He et al. 2023). However, in these methods, user pref-erences are still implicitly encoded in hand-crafted rules, training labels, reward functions, or model parameters. As a result, they are difficult to interpret, update, and continually adapt as user behavior evolves. More recently, researchers have begun to apply LLMs to network-configuration tasks. Existing studies have ex-plored LLM-based solutions for WiFi roaming(Lee, Lu, and Doppler 2025; Nagai et al. 2026) and cellular handover(Li et al. 2026; Jeong et al. 2026), demonstrating the potential of LLMs to interpret heterogeneous communication observa-tions and generate corresponding decisions. However, these approaches largely employ LLMs as reactive decision en-gines that directly map current observations to configuration actions. They do not systematically distill long-term user be-havior into persistent, interpretable configuration rules, and they still rely on LLM inference during the decision-making path. Consequently, existing LLM-based methods struggle to simultaneously achieve personalization, efficiency, and au-tonomy for on-device mobile network configuration. To address these limitations, we propose PEAM, an on-device LLM-based communication agent for personalized, efficient, and autonomous mobile network configuration. The key idea of PEAM is to decouple complex LLM reasoning from latency-critical execution. Instead of invoking the LLM for every online configuration decision, PEAM performs LLM-based reasoning offline when the device is idle, dis-tills historical user behavior into persistent condition–action rules, and executes these rules online through lightweight retrieval. As illustrated in Figure 1, PEAM models personal-ized network configuration as two coupled problems: under-standing why a user prefers a particular configuration from historical records and determining what configuration action should be executed under the current communication context. This design introduces two key challenges on resource-constrained devices. First, how can a compact on-device LLM reliably infer user intents and generate con-figuration rules from long and heterogeneous histori-cal records? General-purpose LLMs lack communication-specific knowledge. Moreover, on-device compact models usually have limited context capacity. PEAM addresses this challenge by constructing a task-specific dataset from manu-ally annotated real-user network-switching records and per-forming supervised fine-tuning to integrate communication knowledge into the local model. PEAM then partitions long histories into coherent batches, analyzes each batch indepen-dently, and performs cross-batch reflection over the inter-mediate outputs. This divide-and-consolidate process keeps each inference within the model’s context window while in-tegrating distributed evidence, reducing locally biased con-clusions, and producing more reliable configuration rules. Second, how can we continually capture evolving user preferences and improve the accuracy and stability of rule generation over time? Static rules cannot adequately represent preferences that change with user behavior. PEAM therefore updates rule confidence according to whether the user accepts or rejects the configuration proposed by the retrieved rule, and discards rules whose confidence falls be-low a predefined threshold. Beyond maintaining individual rules, PEAM constructs a semantic user profile from high-confidence rules. This profile summarizes both scenario-specific preferences, such as preferred configurations under particular applications, times, locations, and network condi-tions, and broader behavioral tendencies, such as sensitivity to data usage and preference for connection quality. Rather than directly inheriting the previous profile, PEAM periodi-cally regenerates the profile from the latest reliable rules and incorporates it into the next rule-generation cycle, providing an up-to-date preference context for more accurate and stable personalization. The main contributions of this paper are summarized as follows: 

• We propose PEAM, an on-device communication agent that distills offline LLM reasoning into persis-tent condition–action rules and executes them through lightweight online retrieval. This design decouples com-plex deliberation from latency-critical execution, pro-viding a practical architecture for LLM-based decision-making on resource-constrained devices. 

• We design a divide-and-consolidate reasoning mecha-nism that decomposes long, heterogeneous interaction histories into coherent batches and consolidates dis-tributed evidence across batches, enabling compact on-device LLMs to generate personalized rules beyond a single context window. 

• We develop a rule-based hybrid memory that combines executable rule memory with semantic preference mem-ory. By reconstructing user profiles from high-confidence rules and feeding them into subsequent reasoning cycles, PEAM supports interpretable and behavior-based person-alization over time. 

• We construct benchmarks based on real-user and simulated-user records for comprehensive evaluation. Ex-tensive results, together with a smartphone deployment of a quantized 4B model, demonstrate PEAM’s effectiveness and practical on-device feasibility.

Methodology 

As illustrated in Figure 2, PEAM consists of four mod-ules: Record Acquisition, Periodic Update, User-Level Local Memory, and Real-Time Execution. We consider personal-ized mobile network configuration over a sequence of update periods indexed by t. In each period, PEAM first collects user-initiated configuration records, then performs offline LLM-based rule generation when the device is idle, updates the local rule and profile memories, and finally executes matched rules online without invoking the LLM. 

Record Acquisition 

The Record Acquisition module runs continuously in the background and monitors user-initiated network-configuration operations. Once an operation is detected, PEAM records the communication context immediately be-fore the operation, the configuration action selected by the user, and the resulting context after the operation. Reflection Clustering cannot guarantee that all records as-sociated with the same underlying intent fall into a single batch. As a result, batch-level outputs may contain incom-plete intents, redundant rules, or conflicting actions caused by limited local evidence. User-Level Local Memory 

PEAM maintains a user-level local memory consisting of a personalized rule base and a semantic user profile. Each rule 

r contains a condition–action pair and a confidence score qr .When a rule is retrieved for execution, PEAM asks the user whether to accept the proposed configuration. Acceptance increases the rule confidence, whereas rejection decreases it. Rules whose confidence falls below a predefined threshold are discarded. This feedback mechanism allows PEAM to retain reliable strategies while removing rules that no longer match the user’s preferences. Detailed rule states and transi-tion mechanisms are provided in the Appendix. To summarize user preferences beyond individual condition-specific rules, PEAM periodically constructs a se-mantic user profile from high-confidence rules. The pro-file captures both scenario-specific preferences, such as pre-ferred configurations under particular applications, times, locations, and network conditions, and broader behavioral tendencies, such as sensitivity to data usage and preference for connection quality. Real-Time Execution 

When the communication context changes, PEAM cap-tures the current application, temporal, spatial, device-configuration, and network conditions, and retrieves applica-ble active rules from the local rule base. Since these rules are generated in advance during periodic updates, the real-time execution path does not invoke the LLM. Instead, PEAM directly compares the current context with the conditions specified by each rule and retrieves the rules whose condi-tions are satisfied. If multiple rules match, PEAM resolves the conflict using a two-level priority scheme. It first selects the rule with the largest number of matched condition pred-icates, since this rule provides the more specific description of the current context. If multiple rules contain the same number of matched conditions, the rule with the highest con-fidence is selected. Finally, PEAM applies the action associ-ated with the selected rule to the device. This retrieval-based design avoids costly real-time model inference and enables millisecond-level online decision-making. 

Evaluation 

Datasets 

We construct three mutually disjoint datasets for model train-ing and evaluation: a simulated-user dataset, a real-user dataset, and a task-level dataset. 

Simulated-User Dataset We first collected one month of network-configuration records from 51 real users, together with additional records obtained in controlled laboratory set-tings. These records are manually annotated to identify 20 high-frequency communication intents and their correspond-ing configuration templates. Based on these annotations, we generate 300 simulated users with diverse spatiotemporal contexts, applications, device configurations, and network conditions, and use DeepSeek-V3.2(Liu et al. 2025) to an-notate the simulated data. Among these users, 200 are used exclusively to optimize the feature weights and HDBSCAN hyperparameters, while the remaining 100 are reserved for end-to-end evaluation. 

Real-User Dataset We further collect approximately two months of network-configuration records from 82 held-out real users. For each user, the records are chronologically divided into two periods. The first period is used to gener-ate personalized rules, while the second is used to evaluate whether these rules correctly predict subsequent user deci-sions. 

Task-Level Dataset We construct a dialogue dataset cover-ing Record Analysis, Cross-Batch Reflection, and User Pro-filing. The training set contains 5,000 samples, including 2,000 for Record Analysis, 2,000 for Cross-Batch Reflec-tion, and 1,000 for User Profiling. The test set contains 300 held-out samples, with 100 samples for each task.

Evaluation Metrics 

We evaluate different methods from three perspectives: rule effectiveness, generation quality, and efficiency. 

Rule Effectiveness We use three metrics to evaluate the effectiveness of rules generated from historical records. Rule Execution Accuracy (REA) measures the proportion of cor-rect actions among all triggered rule executions. Rule Cov-erage Ratio (RCR) measures the proportion of subsequent-period records that trigger at least one generated rule, reflect-ing the behavioral coverage of the rule set. Triggered Rule Ratio (TRR) measures the proportion of generated rules that are triggered by at least one record in the subsequent evalua-tion period, indicating whether a method produces excessive inactive rules. 

Generation Quality We use Semantic Similarity (SS) and Judge Model Score (JMS) to measure the discrepancy be-tween generated outputs and their reference labels, where higher scores indicate better generation quality. SS eval-uates embedding-level semantic similarity using Qwen3-Embedding-0.6B (Zhang et al. 2025a), while JMS uses DeepSeek-V3.2 to assign a score from 0 to 100 based on their overall consistency. The evaluation criteria for these tasks are summarized in the Appendix. 

Efficiency Inference Time (IT) measures the time required to complete a single inference for a given task. For cloud-based LLM baselines, we also report the input and output prices per million tokens. Since PEAM performs inference locally, it incurs no external API cost.

This result directly validates effec-tiveness of PEAM’s separation of offline LLM deliberation and online rule execution in real-time network configuration. Table 4 evaluates the contribution of each major com-ponent in PEAM. Removing clustering reduces RCR from 60.58% to 49.57% and decreases JMS from 81.32 to 65.80, while REA and TRR remain relatively high. This is due to that clustering primarily improves evidence organization, be-havioral coverage, and generation quality by grouping coher-ent records before LLM inference. Removing Cross-Batch Reflection increases RCR to 67.96%, but substantially de-creases REA, TRR, and JMS to 92.44%, 43.21%, and 70.43, respectively. The increased coverage therefore comes at the cost of many redundant, conflicting, or weakly supported rules, confirming that reflection acts as an essential relia-bility filter. Removing User Profiling leaves coverage nearly unchanged, but reduces REA, TRR, and JMS to 97.36%, 85.26%, and 75.27. This pattern shows that user profiling mainly improves the consistency and personalization of gen-erated rules rather than simply increasing their number. Over-all, the three components provide complementary benefits and jointly contribute to PEAM’s performance. 

Conclusion 

In this paper, we presented PEAM, an on-device communi-cation agent for personalized mobile network configuration. PEAM decouples LLM-based deliberation from latency-critical execution by distilling historical user decisions into persistent condition–action rules during offline updates and retrieving matched rules online without invoking the LLM. To support compact on-device reasoning over long and het-erogeneous histories, PEAM combines batch-wise analysis with cross-batch reflection, while a rule-grounded hybrid memory connects executable rules with semantic user pro-files for cross-cycle personalization. Evaluations on task-level, simulated-user, and held-out real-user benchmarks demonstrate competitive performance in rule execution, cov-erage, triggering, and generation quality, while smartphone deployment of a quantized 4B model confirms its practical on-device feasibility. Overall, PEAM demonstrates that on-device LLM agents can support latency-critical mobile sys-tem decisions by shifting complex reasoning offline and ex-ecuting personalized decisions through efficient local rules. 7References

Training Details 

We fine-tune Qwen3-4B and AndesVL-4B through multi-task supervised fine-tuning using LoRA on a single NVIDIA A100 GPU, with a rank of 32, a scaling factor of 32, and a dropout rate of 0.1. We train the model for 5 epochs using AdamW with a learning rate of 5 × 10 −5, cosine decay, a warmup ratio of 0.05 and a batch size of 4. We jointly train the model on Record Analysis, Cross-Batch Reflection, and User Profiling. A task-aware sampler enforces a 2:1:1 allocation within each effective batch, corresponding to 2, 1, and 1 samples from the three tasks, respectively. All tasks use equal sample-level loss weights. We further adopt field-aware token weighting to emphasize task-critical outputs. Prompt tokens are excluded from loss computation; within the responses, tokens in the rules field of Record Analysis and the result field of Cross-Batch Reflection are assigned a weight of 10, while all remaining response tokens retain a weight of 1. The weighted token losses are normalized within each sample before being averaged across the batch. This design emphasizes the structured outputs directly used for rule generation and consolidation without uniformly amplifying the loss of an entire task.

Data Preprocessing 

Because the communication context is recorded at one-second granularity, even a single switching record can result in a lengthy textual representation. Meanwhile, each per-second snapshot provides only an instantaneous view, making it difficult for an LLM to directly identify temporal changes. We therefore statistically summarize the raw data before presenting it to the model. We categorize the collected fields into three types: stable fields, continuously varying fields (e.g., RSRP and RSRQ), and discretely varying fields (e.g., SSID). Stable fields mainly include temporal and location-related information, which typically exhibits no significant change around a network switch. We therefore use the value observed at the switching moment as the representative value for the entire snapshot. For continuously varying fields, we compute the mean separately over the pre-switch and post-switch windows. For discretely varying fields, we use the mode within each window. Because the foreground application provides the most direct indication of user–device interaction, we preserve the complete foreground-application trace throughout the observation window rather than aggregating it. Figure A2 illustrates an example of the resulting standardized data representation. The statistically summarized data still cannot be directly provided to the model, as compact LLMs often struggle to interpret raw numerical communication metrics. We therefore apply a semantic transformation to make the underlying context and its changes more explicit. For each record, the transformation program first reads the pre-switch and post-switch values and then processes each field individually. For the temporal field, it extracts the switching time and determines whether the date is a working day and which period of the day the event belongs to. Location is represented by combining geofence and point-of-interest (POI) information. For foreground applications, the program maps package names to human-readable application names and lists the application changes over time line by line. Numerical network-quality metrics are converted into qualitative descriptions, allowing the model to interpret changes in network conditions more intuitively. Following this procedure, each field transition is expressed in the form A → B,producing a semantic representation of the complete switching process. D User-Level Local Memory Management 

Each rule r is represented by a condition–action pair, an LLM-assigned confidence score qr , and a state sr ∈{silent , active , invalid }. Although the LLM provides an initial confidence score q0

r during rule generation, every newly generated rule enters the rule base in the silent state. A silent rule can participate in condition matching but cannot recommend or execute its action. Instead, when its condition is satisfied, PEAM passively observes the network configuration selected by the user without presenting a recommendation. If the user’s choice agrees with the rule action, the observation is regarded as positive evidence; otherwise, it is treated as negative evidence. A new rule is activated only after two consecutive positive observations, which prevents rules supported by incidental or noisy records from being immediately applied. PEAM updates rule confidence using fixed positive and negative steps. Let yr ∈ { 0, 1} denote the feedback associated with a matched rule, where yr = 1 indicates positive evidence and yr = 0 indicates negative evidence. The confidence update is defined as

For a silent rule, yr is determined by whether the user independently selects the same network configuration as the rule action. Any inconsistent observation resets the consecutive-match counter. For an active rule, PEAM presents the retrieved configuration to the user and asks whether it should be accepted. Acceptance is treated as positive feedback, whereas rejection or the absence of feedback is treated as negative feedback. The configuration is executed only after explicit acceptance. Active rules are eligible for real-time recommendation and execution. When the confidence of an active rule falls below the activation threshold τa, the rule returns to the silent state and is subsequently evaluated through passive observations. Unlike newly generated rules, a previously active rule can be reactivated once its confidence recovers to 

τa, without requiring two additional consecutive matches. If the confidence falls below the invalidation threshold τi, the rule becomes invalid and is permanently excluded from subsequent matching, execution, and user-profile construction. Thus, active and silent states are mutually reversible, whereas the invalid state is irreversible. When multiple active rules match the current context, PEAM first selects the rule whose condition contains the largest number of matched fields. If several rules have the same number of matched fields, the rule with the highest confidence is selected. Only the selected rule receives the current user feedback and updates its confidence. The user profile is periodically reconstructed using active rules only, ensuring that it is grounded in validated and currently reliable configuration preferences. 17
