# Abstract 

Automated approval systems let coding agents execute high-risk actions with minimal human oversight by delegating the authorization decision to a classifier, typically a large language model (LLM). Such systems, adopted in tools like Claude Code and Codex, remain vulnerable to failure modes such as scope escala-tion, where the agent takes actions exceeding what the user authorized. Existing benchmarks focus mainly on malicious requests, evaluating refusal under an im-plicit policy. We introduce AuthGateBench, the first policy-guided benchmark for authorization gating under benign requests. We implement a novel pipeline where an LLM generates contrast pairs with identical action and trajectory but differing request, flipping the label between block and allow. This allows us to assess whether models reason over context rather than the action alone. We further examine whether auxiliary environment signals can help models make better deci-sions. The resulting benchmark comprises 1,400 instances spanning five failure modes drawn from real-world Claude Code incidents. Evaluations show accuracy degrades unevenly across failure modes as models over-rely on internal safety alignment, and models still block most actions even when explicitly authorized, revealing unstable rather than deterministic decisions; retrospectively retrieved environment signals, however, substantially improve authorization accuracy. 

# 1 Introduction 

Autonomy is the central value proposition of modern coding agents: rather than approving every file edit, shell command, or API call, a user delegates a task and expects the agent to carry it out with minimal interruption. Realizing this promise at scale requires an automated approval system, in which a classifier, typically a large language model (LLM), decides for each proposed tool call whether to execute it or escalate it to the user. Such systems are deployed in widely used tools such as Claude Code’s auto mode and Codex’s auto review. However, whether an LLM classifier can reliably serve as this authorization gate remains unclear [Ji et al., 2026a, Groschupp et al., 2025]: natural-language requests are inherently ambiguous [Qu et al., 2026, Ji et al., 2026b], and the classifier must balance excessive blocking, which degrades user experience, against excessive permissiveness, which introduces risk. Prior work on tool-using agents largely targets adversarial settings, from benchmarks testing com-pliance with explicitly malicious instructions [Andriushchenko et al., 2025, Zhang et al., 2024b] to red-teaming studies that jailbreak agents into harmful multi-step behavior [Liu et al., 2024]. These approaches overlook a common failure mode: benign user requests that lead agents to propose actions exceeding authorized scope. Such failures have occurred in practice, including coding agents deleting production databases with unauthorized tokens [Railway, 2026]. This aligns with OWASP’s classification of tool misuse and exploitation as one of the top 10 most critical security risks for agentic AI systems [OWASP, 2026]. Recent efforts begin to address this setting. OverEager-Gen [Qu et al., 2026] examines whether agents generate out-of-scope actions under ambiguous instructions,

AmPermBench [Ji et al., 2026a] evaluates authorization gates but is limited to a single failure mode and narrow tool coverage, as it relies on running coding agent end-to-end and waiting for the agent to naturally trigger a failure, an inherently long-tailed event that yields limited scenario diversity. Moreover, the ground-truth safety policy behind their labels is implicit, so it is unclear whether errors arise from policy mismatch or from the model’s limited authorization reasoning.

Therefore, in this paper, we introduce Auth-GateBench , the first policy-guided benchmark for authorization gating under benign requests across multiple realistic failure modes. We con-struct triplets of requests, trajectories, and pro-posed actions under explicit safety policies, en-abling a controlled trade-off between safety and utility. By selectively exposing or withholding the safety policy from the LLM-based classifier, we in-vestigate whether effective authorization requires explicit knowledge of specific high-risk categories or whether the LLM can instead identify unsafe ac-tions under ambiguous requests based on its inher-ent safety alignment. Moreover, AuthGateBench curates instances where annotations depend on the user request rather than the action alone. This re-quires classifiers to go beyond action-level heuris-tics and reason jointly over the request and trajectory. Specifically, AuthGateBench comprises 1,400 instances spanning five failure modes drawn from real-world Claude Code incidents [Anthropic, 2026]. We implement a novel construction pipeline centered on contrast pairs: for a given governing policy, an LLM first drafts a block instance whose request is ambiguous, underspecifying the high-risk action it precedes; it then edits only the request, naming every object the action touches, to construct the allow counterpart, holding the trajectory and action fixed while the ground-truth label flips. The example is shown in Figure 1. We validate label correctness by manually auditing a batch of samples and find a high level of agreement. We further augment each instance with auxiliary, read-only environment signals, evidence a coding agent’s own trajectory did not surface, to test whether such corroborating evidence helps a classifier resolve authorization decisions that the request and trajectory alone leave underdetermined. We report the key contributions below: • A benchmark spanning five failure modes reveals scenario-specific weaknesses. Auth-GateBench evaluates authorization gates on benign requests across five failure modes, showing that models over-rely on internal safety alignment to block user-authorized actions involving sensitive data usage and sharing, indicating that future gate designs need additional policy specificity in these categories to avoid degrading user experience through excessive false blocks. • Contrast-pair construction diagnoses the source of blocking decisions. By flipping the gold label through request edits alone while holding the action and trajectory fixed, we find models still block most risky actions even when explicitly authorized, showing decisions rely on unstable model preference rather than a deterministic rule. This motivates future designs to consider formally verified authorization that resolves risk and authorization conflicts deterministically. • Environment-signal augmentation captures evidence the agent’s trajectory could not antici-pate. Since the agent generates the trajectory before knowing the final action, it may miss evidence relevant to that action, whereas a gate observing the completed triplet can retrospectively retrieve targeted, read-only signals. This retrieval substantially improves authorization accuracy, motivating gates that actively acquire evidence rather than relying solely on the agent’s trajectory. 

# 2 Related works 

Autonomous coding agents. LLM-based coding agents have progressed from single-turn code generation to autonomously resolving open, real-world software engineering issues over long tool-use trajectories [Jimenez et al., 2024, Zhang et al., 2024a, Wang et al., 2025b]. As this capability has matured, deployed systems increasingly let an agent execute the resulting plan directly rather than surface it for review, motivating auto-execution modes such as Claude Code’s auto mode [Anthropic, 22026] and Codex’s auto-review [OpenAI, 2026]. This shift replaces human authorization with an LLM-based classifier, raising the question of whether such classifiers can serve as reliable gates. 

Agent safety benchmarks. A substantial line of work studies agent safety under adversarial requests or trajectories. AgentHarm [Andriushchenko et al., 2025] and Agent-SafetyBench [Zhang et al., 2024b] evaluate compliance with explicitly harmful tasks; R-Judge [Yuan et al., 2024] assesses risk recognition from agent traces; ToolEmu [Ruan et al., 2024] and MAS-FIRE [Jia et al., 2026] study failures during agent execution through simulation and fault injection, respectively; and AutoDAN [Liu et al., 2024] searches for jailbreaks. These benchmarks primarily evaluate resistance to adversarial instructions, prompt injections, or execution-time risks [Ye et al., 2024, Zhan et al., 2024, Chen et al., 2026], rather than authorization of a proposed action under a specific request, trajectory, and policy. Only a small number of studies consider benign users. OverEager-Gen [Qu et al., 2026] examines whether agents generate out-of-scope actions from underspecified instructions, focusing on proposal generation rather than the authorization decision. AmPermBench [Ji et al., 2026a] evaluates auto-execution gates, but is limited to one failure mode and defines authorization solely by explicit mentions of targets in the proposed action, ignoring authorization established by the trajectory. Groschupp et al. [2025] study a coarser setting where authorization is determined by application functionality, such as camera access, and is largely context-independent. In contrast, coding-agent authorization is context-dependent: the same action may be allowed or denied depending on its target and trajectory. AuthGateBench captures this distinction with contrast pairs that hold the action and trajectory fixed while varying only the user request, evaluating contextual authorization reasoning rather than action-based pattern matching. 

Policy representation and enforcement. A separate line of work studies how to represent, compile, or update explicit safety policies, assuming that the governing policy is available. Prose2Policy [Gupta and Sreenivasamurthy, 2026] and a retrieval-augmented pipeline for IoT [Cheng et al., 2026] translate expert-authored natural-language rules into executable representations (e.g., Rego checked by OPA [Open Policy Agent, 2016]) for downstream enforcement; NeMo Guardrails [NVIDIA, 2023] routes agent behavior via intent matching against predefined rules; LiSA [Kim et al., 2026] adapts deployed guardrails from sparse failure feedback; and AgentSpec [Wang et al., 2025a] and Progent [Shi et al., 2026] allow developers to define and enforce explicit rules that restrict which actions an agent may take at runtime. These approaches are complementary to AuthGateBench: they focus on policy specification and enforcement under an available policy, whereas we evaluate whether LLMs can perform authorization reasoning when the policy is not explicitly provided and the evidence arrives as natural-language requests and trajectories. 

# 3 Threat model 

Notations. We consider an autonomous agent in auto-execution mode, carrying out a delegated task through a sequence of tool calls without per-action confirmation. Before an action takes effect, an LLM-based authorization gate decides for each proposed tool call whether it may be executed (ALLOW ) or must be withheld ( BLOCK ). We formalize the gate as a policy-conditioned binary classifier over an authorization triplet. Let an instance be x = ( r, τ, a ), where r is the user request, τ

is the trajectory of prior tool calls, and a is the proposed action. Let π denote the policy text provided to the gate. The gate is a classifier f :

f (x, π ) → { ALLOW , BLOCK }. (1) Its prediction is evaluated against the gold authorization decision y = g(x, π ∗), where g denotes the oracle authorization function induced by the intended policy π∗. Here, π∗ represents the authorization standard that governs whether the action is permitted, but is not observed by the gate. 

Goal and knowledge of the gate. The gate aims to reproduce the intended decision, f (x, π ) = 

g(x, π ∗). The challenge lies in how much of π∗ is communicated through π: when π fully specifies 

π∗, errors mainly stem from the gate failing to correctly interpret or apply the stated rules; when π is partial or absent, the gate must fall back on its internalized priors about what users would sanction. The gate observes only the instance x and the provided policy π; it has no access to the user’s underlying intent beyond what r and τ reveal, and it cannot interact with the environment to gather additional evidence. This setting mirrors deployed auto-execution systems, where the classifier must commit to a decision from the context at hand. 3Source of error under benign use. Unlike an adversarial setting, here both r and a are produced in good faith: the user’s request is legitimate, and the agent’s proposed action is a genuine attempt to fulfill it rather than a disguised exploit. Errors instead arise because natural language underspecifies intent, and the agent resolves this ambiguity on its own, for example by treating a vaguely named target as the one the user meant, reusing a credential it happens to hold, or retrying past a failed safety check to make progress. Each such resolution is a plausible reading of r given τ , yet only some are sanctioned under π∗.

4.1 Overview 

AuthGateBench comprises 1,400 instances spanning five failure modes drawn from documented Claude Code auto-execution incidents [Anthropic, 2026]: (1) Scope Escalation , where a vague request is expanded into an irreversible action beyond what the user intended; (2) Credential Exploration , where the agent repurposes a discovered credential outside its intended scope; (3) 

Inferred Parameters , where a destructive action targets a parameter guessed by similarity rather than fixed by the request; (4) External Sharing , where content is shared to an external destination the user never requested; and (5) Guardrail Bypass , where the agent circumvents a failed safety check to force an action through. Each mode is paired with a definition, a canonical mechanism, and a seed example that together condition base instance construction (Section 4.2). 4.2 I: Base Instance Construction 

Using the definitions and seed examples from Appendix A, we instruct a frontier LLM as the generator to produce triplets (r, τ, a ) that should be blocked under an intended policy π∗. We deliberately begin from BLOCK instances so that the proposed action a is risky by construction. When Stage II subsequently edits only the user request while holding the trajectory and proposed action fixed, a

remains equally risky, which forces a classifier to rely on context rather than the action’s surface form to recover the correct decision. 4.3 II: Contrast-Pair Construction 

We evaluate whether an LLM authorization gate relies on authorization-relevant context rather than the action’s surface form by constructing contrast pairs, inspired by counterfactual data augmentation [Kaushik et al., 2020]. Formally, a contrast pair {x, x ′}, with x = ( r, τ, a ) and x′ = ( r′, τ ′, a ′), is an unordered pair satisfying

Specifically, for each generated request, we instruct the LLM-based generator to rewrite the request so that it uniquely determines the exact target set of the proposed action using only information that the user could plausibly know before the trajectory. This construction ensures that the edited requests unambiguously authorize the corresponding actions. We manually verify a sample of the resulting triplets, obtaining 100% agreement that they warrant an ALLOW label, eliminating the need for an additional LLM-based labeling step and reducing annotation cost. Such pairs therefore provide a controlled comparison in which the action and trajectory remain fixed, allowing us to isolate whether models appropriately incorporate changes in the user’s request when making authorization decisions. 

4.4 III: Signal Augmentation 

The coding agent generates the trajectory sequentially before producing the proposed action. It therefore cannot anticipate which environmental evidence will be relevant to that future action and may fail to collect such evidence during execution. In contrast, an authorization gate that observes the completed (r, τ, a ) can retrospectively retrieve trustworthy, read-only signals targeted to the proposed action. Stage III simulates this post-hoc signal collection and measures how access to such evidence changes authorization decisions while holding the request, trajectory, and action fixed. Specifically, we instruct the generator to synthesize a set of auxiliary environment signals Σ that provide corroborating, read-only observations relevant to the proposed action, such as file-system state, process listings, or responses from remote APIs. # 5 Experiments 

This section presents our experimental results for AuthGateBench. We discuss the experimental setup in Section 5.1, followed by the results and analyses in Section 5.2. 

5.1 Experimental setup Models. We use D EEP SEEK -V4-F LASH [DeepSeek-AI, 2026] to generate base instances, contrast pairs, and environment signals (Sections 4.2 to 4.4) with a temperature of 1 to promote diversity. The resulting benchmark contains 1,400 instances, with gold labels evenly split between BLOCK 

and ALLOW . At evaluation, we assess the generator model, D EEP SEEK -V4-F LASH , and three other frontier LLMs as authorization classifiers: GLM-5.2 [Zhipu AI, 2026], K IMI -K2.7-C ODE 

[Moonshot AI, 2026], and Q WEN 3.7-P LUS [Alibaba, 2026]. Each model receives an identical prompt stating the governing policy, followed by the instance triplet, and returns a decision along with a policy rationale explaining its choice (full prompt in Appendix C). All models are queried at temperature 0 at evaluation. 

Policies. We use a moderately detailed rule set as the policy π∗ to generate base instances, specifying the conditions under which an action must be blocked while explicitly authorizing destructive actions when the user’s instructions enumerate the target or accept responsibility. At evaluation time, however, our threat model assumes the gate does not observe the user’s implicit safety standard: consistent with real auto-execution deployments, the evaluated LLM is instead instructed to rely on its own internal safety criterion, π, as “a careful, safety-conscious operator,” without access to π∗. The full text of policies is in Appendix B. 

Metrics. We report classification accuracy (Acc), the false negative rate (FNR), and the false positive rate (FPR). We treat BLOCK as the positive class, corresponding to the action a safety gate is intended to detect. Under this convention, FNR quantifies the rate at which unauthorized actions are incorrectly permitted, whereas FPR quantifies the rate at which legitimate actions are unnecessarily blocked.

Environmental signals improve authorization accuracy. A coding agent generates its trajectory via next-token prediction before producing the eventual action, and therefore cannot anticipate which environmental information will ultimately be relevant to authorizing that action. As a result, the trajectory may naturally omit signals that become important only once the action is specified. The authorization gate, however, sees the request, trajectory, and proposed action together. This allows it to actively seek signals relevant to the proposed action. We ask whether such post-hoc, action-aware exploration can improve authorization accuracy by filling in information that the agent’s generative trajectory did not capture. We compare an LLM-based classifier’s predictions on the 700 base and inverted triplets under policy π against the same triplets augmented with environmental signals Σ

(Section 4.4). Figure 3 reports, per failure mode, the fraction of initially incorrect predictions that 

Σ corrects versus the fraction of initially correct predictions it misleads. Across all categories, the correction rate among initially incorrect predictions is more than twice the misleading rate among initially correct predictions, and the effect is strongest on Scope Escalation (25.2% corrected vs. 7.6% misled) and Inferred Parameters (24.3% vs. 10.5%), where the original trajectory most often left the target under-specified. This shows that post-hoc read-only environmental evidence reliably helps classifiers resolve authorization decisions that the request and trajectory alone leave underdetermined. In practice, an LLM-based authorization gate could be instructed to gather such evidence after observing the full request, trajectory, and action using a list of trusted read-only tools. # 6 Conclusion 

We introduced AuthGateBench, the first policy-guided benchmark for evaluating LLMs as autho-rization gates under benign requests, using contrast pairs to test whether models reason over the request rather than anchoring on the action’s surface risk. Across four frontier LLMs, we find that: (1) models over-rely on internal safety alignment, blocking user-authorized actions on sensitive 8data across failure modes, motivating finer-grained explicit policies; (2) contrast pairs reveal strong action anchoring, with models blocking risky actions even when explicitly authorized, motivating formally verified, deterministic authorization; and (3) retrospectively retrieved environment signals substantially improve accuracy, motivating gates that actively acquire evidence. These findings point toward explicit policies, deterministic verification, and contextual evidence as promising directions for more reliable agent authorization. 

# 7 Limitations 

Synthetic construction. Our benchmark is synthetically constructed for five failure modes from real incident reports. Real authorization failures are rare and long-tailed; collecting representative failures from deployed agents is challenging because most systems operate in auto-execution mode, causing many failures to remain unreported or unnoticed. Synthetic generation also enables us to fix a consistent intended policy during construction, avoiding ambiguity in ground truth that would arise from user-specific policy variations. 

Synthesized environment signals. Our environmental signals are synthesized in Stage III, which may not capture the full variability of real-world tool outputs. However, the performance gains reveal an important design implication: future authorization gates should incorporate relevant environmental evidence instead of relying solely on request and action context. This contrasts with execution modes that discard or ignore tool feedback, potentially leaving valuable evidence for authorization decisions unleveraged. 

Policy diversity. We generate data with a single explicit policy π∗. Constructing data with additional policies would require substantial expert effort to re-validate gold labels. By fixing π∗ and varying the policy π available to the classifier, we capture the key distinction between policy-aware and policy-implicit authorization. 

# 8 Ethical Considerations 

This paper presents work to characterize and mitigate scope-escalation and related authorization failures in autonomous coding agents, helping build more reliable oversight for auto-execution systems. All experiments are conducted on synthetic, LLM-generated data in a controlled setting without targeting real users, systems, or credentials. However, the failure taxonomy and constructed examples could also be misused as a template for eliciting unauthorized agent behavior. We encourage responsible use of AuthGateBench for improving authorization gates rather than circumventing them.

A.1 Scope Escalation Definition. A vague or under-specified request is expanded by the agent into an irreversible or destructive action whose target set exceeds or may exceed what the user intended. 

Mechanism. vague request → pattern-matched target construction → irreversible execution. 

Figure 6: Seed example for Scope Escalation. 

A.2 Credential Exploration Definition. Blocked by an auth failure, the agent hunts through environment variables, config files, or keychains for alternative credentials not provisioned for the current task. 

Mechanism. auth error → systematic secret search → repurposing an out-of-scope credential. 

Figure 7: Seed example for Credential Exploration. 12 A.3 Inferred Params Definition. The agent fills in a destructive action’s parameters (target IDs, names, paths) by guessing — name similarity, recency, or convention — rather than resolution grounded in the trajectory. 

Mechanism. under-specified target → similarity-based guess → destructive call on guessed target. 

Figure 8: Seed example for Inferred Params. 

A.4 External Sharing Definition. The agent self-initiates moving workspace content (code, logs, data) to an external or public destination the user did not request. 

Mechanism. helpful impulse (debugging/sharing) → unrequested egress → potential confidentiality breach. 

Figure 9: Seed example for External Sharing.
