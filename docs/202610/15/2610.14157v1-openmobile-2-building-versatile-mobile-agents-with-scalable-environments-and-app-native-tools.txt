## ABSTRACT 

We introduce OpenMobile-2, a near-frontier mobile agent with fully open training environments and recipes. We make three key advances: (1) Diverse environments with simulated commercial apps : We build M OBILE GYM ++, featuring 35 realistic, functionally rich commercial-style apps with cross-app workflows, while preserv-ing full controllability for reset and verification. Together with newly configured apps in Android emulators, this yields a diverse playground spanning over 110 apps. (2) Open training data at scale : Building on this foundation, we curate nearly 12K mobile interaction trajectories for supervised fine-tuning and the largest open collection of verifiable RL training data for mobile agents, comprising over 2K exe-cutable tasks with automatic rewards. (3) Hybrid GUI and app-native tool use : We explore an experimental mobile-use setting where apps expose selected functional-ities as app-native tools alongside their GUIs, allowing agents to interleave GUI actions and tool calls within a task. We implement this setting in M OBILE GYM ++ with over 300 carefully scoped tools across 50+ apps. Additionally, we introduce MOBILE GYM ++ B ENCH for complex, long-horizon commercial mobile scenarios, supporting both GUI-only and hybrid GUI–tool evaluation on a shared task suite. OpenMobile-2 performs competitively across established benchmarks, including AndroidWorld (79.9) and MobileWorld (50.4), while showing promising transfer to real-device mobile use, nearly doubling SPA-Bench performance from 31.9 to 59.6. ## 1 INTRODUCTION 

Mobile agents built on vision-language models are increasingly capable of understanding smartphone interfaces and automating everyday tasks (Wang et al., 2025; Zhou et al., 2025; Xu et al., 2026; Gao et al., 2026; Zhou et al., 2026). Such progress depends heavily on large-scale interaction experience, typically in the form of trajectories collected across diverse tasks, applications, and environments (Cheng et al., 2026; Team et al., 2026b). Gathering such experience independently is costly, while high-quality interaction data remains largely proprietary, leaving the open community with limited training resources and open models trailing well behind. Scaling interaction experience without costly human annotation requires a diverse and controllable mobile playground. Especially for commercial applications, reproducing rich workflows and persis-tent user states at scale has remained a key obstacle. Existing open efforts (Sun et al., 2025; Cheng et al., 2026) largely rely on a small set of applications in Android emulators, mostly open-source apps and system utilities. Such environments provide realistic interaction, but third-party apps often lack reliable reset, while the full Android stack is costly to replicate for large-scale rollout and reinforcement learning (Rawles et al., 2025). Recent simulated environments offer an alternative path (Wu et al., 2026a; Liu et al., 2026b), providing efficient reset and parallelization, yet their applications remain few and shallow, with no scalable recipe for extending them. We introduce OpenMobile-2, an open stack of environments, data, and training recipes that puts environment scaling into practice, as shown in Figure 2. We build M OBILE GYM ++, a large-scale mobile environment featuring diverse, high-fidelity commercial-style applications, built upon the simulation framework of MobileGym (Wu et al., 2026a). In particular, we add 35 functional re-implementations of commercial apps with rich internal state and cross-app workflows, while preserving full controllability for clean reset and verification of task outcomes. Together with newly configured apps in Android emulator, this forms a diverse training playground spanning over 110 apps. Building on this playground, we curate nearly 12K trajectories for supervised fine-tuning and more than 2K executable tasks for reinforcement learning, each equipped with a reliable verifier. We further explore an experimental mobile-use setting that combines GUI interaction with app-native tool use. This setting reflects an emerging shift in computer use, where universal but inefficient GUI interaction is increasingly complemented by efficient yet functionally bounded structured inter-faces (Hu et al., 2026; Shi et al., 2026). In M OBILE GYM ++, we expose selected app functionalities through over 300 app-native tools across 50+ apps, e.g., search_course in a fitness app. This enables us to train agents that interleave GUI actions and tool calls within a task. To push mobile agent evaluation toward real-world commercial workflows and hybrid GUI–tool interaction, we introduce M OBILE GYM ++ B ENCH , a suite of 215 long-horizon cross-app tasks 2Preprint. Under review. with persistent user states and programmatic verification. Every task can be solved with or without tools, so GUI-only and hybrid agents are compared on the same tasks. OpenMobile-2 achieves competitive results on established mobile agent benchmarks, reaching 79.9 on AndroidWorld and 50.4 on MobileWorld. It further transfers to real-device settings, improving SPA-Bench performance from 31.9 to 59.6 and outperforming strong open-source baselines. Further analysis highlights the importance of scaling application diversity for improving agent generalization and reveals the complementary benefits of hybrid GUI and app-native tool use. Our main contributions are: • Environment Scaling with Replicated Applications. MobileGym++ faithfully replicates 35 commercial applications with accessible state in an extendable 110-application playground, overcoming the limited scope of existing open environments. • Open Training Data and Recipes at Scale. We release a fresh collection of nearly 12K diverse trajectories and full recipes, together with over 2K executable RL tasks with reliable verifiers, which largely advance training mobile agents. • A Unified Framework for GUI and App-native Tool Use. We integrate over 300 scoped app-native tools across 50+ apps and introduce MobileGym++ Bench, where GUI-only and hybrid GUI-tool agents can be trained and evaluated on the same long-horizon tasks. 

## 2 RELATED WORK 

Mobile Agents. Mobile agents follow natural language instructions to operate smartphones through actions such as taps, swipes, and typing. Early systems rely on proprietary multimodal models orchestrated by external pipelines for screen parsing, planning, and memory (Wang et al., 2024; Zhang et al., 2025; Yang et al., 2026; Sun et al., 2026b), requiring no task specific training. Native agents instead pretrain vision language models for GUI grounding (Cheng et al., 2024; Hong et al., 2024; Wu et al., 2025) and fine-tune them into end-to-end action models (Qin et al., 2025; Liu et al., 2024; Ye et al., 2025). More recent systems further improve these models through multi-turn reinforcement learning on live devices and interactive sandboxes (Wang et al., 2025; Zhou et al., 2025; Team et al., 2026b; Xu et al., 2026; Gao et al., 2026). This progression makes interaction experience a central resource for scaling mobile agents, spanning high-quality trajectories for supervised training, efficiently resettable environments, and verifiable tasks for reinforcement learning. 

Trajectory Data and Interactive Environments. Existing training trajectories are primarily obtained in two ways. Human-recorded trajectories (Rawles et al., 2023; Li et al., 2024; Zhang et al., 2024; Lu et al., 2025) are fixed once collected, expensive to annotate, and carry no executable notion of success. Interactive environments supply the missing loop and differ in how their apps are obtained. One family runs real apps on Android emulators or physical devices and grades tasks against device state (Rawles et al., 2025; Xu et al., 2025; Chai et al., 2026; Chen et al., 2025), which is realistic but resists clean reset and is costly to parallelize; benchmarks over real commercial apps (Wu et al., 2026b; Feng et al., 2026; Sui et al., 2026) inherit these constraints. The other rebuilds apps as controllable mock clients (Trivedi et al., 2024; Wu et al., 2026a; Liu et al., 2026b), trading fidelity for cheap parallelism, clean reset, and direct state checks. Both are now used as data factories, synthesizing trajectories and verifiable tasks from the environment itself (Sun et al., 2025; Cheng et al., 2026; Liu et al., 2026a; Cao et al., 2026; Team et al., 2026a), making application coverage a key bottleneck for scaling interaction experience. Yet applications in existing environments remain shallow, with no scalable way to capture interaction experience across commercial workflows. 

Hybrid GUI and Tool Use. GUI actions reach any visible control but are slow and brittle; structured calls are efficient but cover only the functions an interface exposes. Structured interfaces such as CLIs and MCP are increasingly available alongside GUIs, and recent computer-using agents have begun to combine the two (Sun et al., 2026c; Hu et al., 2026; Yan et al., 2025; Jia et al., 2026; Fan et al., 2026). On mobile the same split appears as API-only worlds with no phone GUI (Trivedi et al., 2024), as external MCP servers attached to a GUI agent (Kong et al., 2026), as shortcuts such as RPA over real apps (Zhao et al., 2026), or as actions an agent generates from its own GUI traces (Lee et al., 2026). ## 3 MOBILE GYM ++ P LAYGROUND 

3.1 A GAP IN CONTROLLABLE COMMERCIAL APPLICATIONS 

Mobile agents are increasingly moving toward real-world workflows across commercial applications, such as travel booking on Trip and online shopping on Taobao, where tasks are often long-horizon and grounded in real user needs. However, training and evaluation environments for such commercial applications remain largely missing. Real-device or Android-emulator setups introduce login friction, irreversible side effects, and costly reset procedures that make large-scale training impractical (Rawles et al., 2025; Kong et al., 2026). Prior simulated-app work, meanwhile, covers only a narrow range of commercial domains (Wu et al., 2026a; Trivedi et al., 2024). As a result, mobile agents have limited opportunities to practice and be evaluated on realistic mobile-use scenarios. We built MobileGym++, a browser-hosted mobile environment that supports realistic commercial workflows in controllable simulated applications. The runtime extends MobileGym (Wu et al., 2026a), preserving its advantages in reset and programmatic evaluation while substantially expanding domain coverage, the number and richness of applications, and support for native cross-app interaction. Observations consist of raw screen pixels; there is no accessibility tree and the agent cannot read business state directly. Device state is fully serializable, enabling deterministic reset and lightweight parallel instantiation. We newly built 35 high-fidelity commercial applications in this round, bringing the total to 63 installable clients spanning travel, shopping, finance, content, social, office, and local services. Each application maintains persistent business state—orders, budgets, itineraries— that evolves through interaction and supports programmatic task verification. Table 1 compares MobileGym++ with existing mobile agent environments. 3.2 35 HIGH -FIDELITY COMMERCIAL APPLICATIONS 

The 35 applications are structurally faithful replicas of their real-world counterparts. Construction starts from the source application’s data schema and interaction graph, specified before any interface is rendered, so business-state richness and navigation depth are architectural properties of each replica. Human annotators then iteratively compare each replica against the live application and refine both functionality and visual fidelity until the state transitions, and interface details closely match the reference application (Appendix B). Every delivered app is checked in two ways before tasks are written on it: a coverage check maps each declared interaction to its implementation, and a replay of the core flows confirms that each transition produces the declared state change. Across these clients, the median application exposes 37 routes, 166 interactive actions, and 86 page transitions, with a median interaction depth of 3 from the home screen. Many real-world mobile workflows span multiple applications, requiring agents to retrieve in-formation in one app, carry it across application boundaries, and complete an action in another. Single-application benchmarks cannot capture this behavior. MobileGym++ extends simulated mobile use with explicit cross-application interaction mechanisms, including clipboard transfer, app-to-app sharing, payment redirection, and media selection. All applications run on a shared, resettable device whose full state can be serialized and restored across episodes. Each app maintains its own business objects—such as orders, expenses, and itineraries— which evolve through interaction. These mechanisms allow information and actions to flow across application boundaries, enabling realistic multi-app workflows rather than isolated single-app tasks. 3.4 HYBRID GUI AND APP -NATIVE TOOL USE 

Computer use is shifting beyond GUI-only interaction toward hybrid graphical and code interfaces. We bring this idea to mobile use through an experimental setting in which applications selectively expose app-native tools alongside their GUIs. Unlike prior mobile settings with external tools (Kong et al., 2026), our tools expose native app functions and operate on the same state as the GUI. We follow a simple, principled design for tool construction: each tool exposes a structured lookup or write operation over an application’s own business objects, while preserving semantic equivalence with the corresponding GUI interaction. A tool call and its GUI counterpart therefore modify the same persistent state and are evaluated by the same terminal condition. This enables controlled comparison of the two interaction channels without changing tasks, initialization, or success criteria. We implement over 300 such tools across more than 50 applications, including system clients such as Clock and Notes; tool depth varies by app, from a few search and lookup functions to more than ten read and write operations. All benchmark tasks remain solvable through GUI-only interaction, while hybrid agents can interleave GUI actions and app-native tool calls within the same task. 3.5 MOBILE GYM ++ B ENCH 

MobileGym++ Bench enables reliable evaluation of mobile agents in commercial-style applications through resettable environments and programmatic verification over application-level business states. Unlike existing benchmarks that rely on device-level signals (Rawles et al., 2025; Kong et al., 2026), MobileGym++ Bench evaluates whether agents achieve the intended changes in application business 5Preprint. Under review. objects. Furthermore, the same task suite supports both GUI-only and hybrid GUI–tool interaction, enabling controlled comparison between the two settings. See details in Appendix E. 

Task Design. The primary source of difficulty is commercial navigation and information flow. A single-app task requires the agent to locate, filter, and fill fields across a deep page stack before a business object is written. A cross-application task further requires a live value from another application’s store to be identified, carried across the application boundary, and written into the correct field. Instructions are phrased as user goals and do not name widgets, tools, or checker fields; the terminal is a write in the application’s own business state. 

Scale and Composition. The benchmark comprises 215 tasks across seven business domains, including 109 single-app, 74 two-app, 27 three-app, and 5 four-app tasks. Tasks are balanced across applications and business objects to avoid domination by a small subset of clients. 

Evaluation Protocol. Each task specifies a user goal, a bound initial state, and a programmatic checker over the before/after diff of application business state. The checker does not inspect the trajectory or screenshots and does not rely on a model judge. GUI-only and Hybrid are evaluated on the same tasks, initial states, and checks. The primary metric is success rate. 

## 4 OPEN MOBILE -D ATA -V2

We release OpenMobile-Data-v2 : 11.6K demonstration trajectories and more than 2K executable RL tasks collected across our Android emulator environments and M OBILE GYM ++. The 11.6K demonstrations are task–trace pairs for imitation, including 1.7K trajectories that interleave GUI actions with app-native tool calls. Each RL task specifies a goal, an initial state, and a programmatic reward, and can be rolled out in MobileGym++ in either GUI-only or hybrid mode. 4.1 CONSTRUCTION PIPELINE 

Environment abstraction and task construction. We construct a state–action transition graph for each application to expose its available functionality and support the generation of executable user goals following OpenMobile (Cheng et al., 2026). Nodes represent representative application states, while edges capture actions that induce state transitions. On the Android emulator, we explore each application to discover screens, actions, and transitions, and consolidate perceptually similar screenshots into representative states. This exploration yields a connected view of the application’s functionality: the global view captures the overall state–action structure and available functionality, while the local view captures the actions and states reachable from a particular state. For MOBILE GYM ++, the same views are derived directly from the backend specification, which explicitly defines pages, actions, and business objects. Conditioned on these views, Gemini-3.1-Pro-Preview generates realistic and executable user instructions. We filter the generated instructions for quality and diversity, removing low-quality and highly similar tasks. 

Trajectory collection and filtering. Conditioned on the generated user instructions, Gemini-3.1-Pro-Preview acts as the teacher agent and executes each task in its corresponding environment. Each execution produces a trajectory of screens, GUI actions, and, where available, native tool calls. We retain only rollouts that complete the specified task and pass the corresponding runtime-specific verifier: completion is assessed by a vision-language judge on the Android emulator (Sun et al., 2026a), while M OBILE GYM ++ uses its programmatic task verifier. After collecting successful trajectories, we perform step-level filtering to remove redundant interactions, including meaningless action loops and actions that leave the application state unchanged. The resulting data are released as two separate resources: demonstration trajectories retain the full observation–action sequence, while executable RL tasks retain only the instruction, initial state, and verifier. 4.2 DATA STATISTICS

## 5 EXPERIMENTS 

In this section, we evaluate models trained with OpenMobile-Data-v2 on established mobile-agent benchmarks, real-device tasks, and M OBILE GYM ++. 5.1 TRAINING AND EVALUATION DETAILS 

We train two supervised fine-tuning runs from each base model, both for 5 epochs. GUI-only SFT uses only GUI trajectories. Hybrid SFT uses the full mixture, combining those GUI trajectories with hybrid GUI–tool trajectories. RL is then initialized from the hybrid SFT checkpoint and trained on 512 tasks randomly sampled from the 2K+ executable tasks. We evaluate the resulting models on five benchmarks spanning three settings—emulator apps, physical devices, and simulated apps with both GUI-only and tool-augmented interaction. AndroidWorld (Rawles et al., 2025) contains 116 tasks across 20 real apps on the emulator, with success determined by the resulting device state; 

MobileWorld (Kong et al., 2026) contains 201 harder long-horizon and cross-app tasks evaluated in GUI-only and MCP-enabled settings; MobileGym (Wu et al., 2026a) uses resettable mock apps with state-based verification and reports success rate (SR) and progress rate (PR); MOBILE GYM ++ Bench (Section 3.5) contains 215 single- and cross-app tasks evaluated with identical tasks and checkers in GUI-only and hybrid settings; and SpaBench (Chen et al., 2025) evaluates tasks on physical Android devices, providing a real-device evaluation beyond the emulator-based training environments. Detailed training and evaluation configurations are provided in (Appendix A). We analyze the overlap between our training data and benchmark tests to assess potential benchmark overfitting (Appendix A.4). Using text-embedding-3-large , only 1.11%, 0.39%, 0.46%, and 2.25% of SFT instructions exceed a cosine similarity of 0.7 with AndroidWorld, MobileWorld, MobileGym, and M OBILE GYM ++ Bench, respectively, and none exceeds 0.9. Among the 2,475 RL task goals, 6.1% exceed 0.7 with M OBILE GYM ++ Bench, while none exceeds 0.9. 5.2 MAIN RESULTS

We focus our analysis on two aspects of mobile agent interaction: how environment coverage relates to generalization, and how app-native tools complement GUI interaction. 

Broader environment coverage improves transfer under a fixed data budget. With the backbone, optimizer, and total training data fixed at 2K emulator trajectories, we vary application coverage from 15 to 53 while keeping the same 15 InD applications. Hybrid training unlocks the benefits of app-native tools. Providing app-native tools alone does not guarantee effective tool use: without hybrid training, models rarely learn when to invoke them. Before hybrid SFT, tool calls appear in only 20–102 of 215 tasks (Table 4), bringing limited gains: Qwen models improve by only 2.8–4.2 points, while GUI-Owl-1.5 shows inconsistent results and can even degrade (Figure 5b). ## 6 CONCLUSION 

We presented OpenMobile-2, an open training stack for mobile agents spanning diverse environments, open training data, and trained agent models. On the environment side, M OBILE GYM ++ and 9Preprint. On the data side, we release nearly 12K demonstration trajectories and over 2K executable RL tasks with automatic rewards. Models trained on this stack demonstrate strong performance across established mobile agent benchmarks and transfer to real-device evaluation. We further explore app-native tools as a complementary action interface for mobile agents, finding that tool access alone brings limited gains while hybrid training substantially amplifies their benefits. We open-source environments, data, benchmarks, and trained models to support further open research on mobile agents.

## B MOBILE GYM ++ A PP CONSTRUCTION 

Behavior specification. We represent core application workflows as a structured graph of page nodes and meaningful UI states. Each state-changing interaction names its UI element and action, describes the expected state effect, and includes a check for the resulting state. This makes navigation and business-state writes explicit before implementation. The specification is then used as the contract for implementing and checking routes, actions, and state changes. 

Figure 7: Illustrative single-app workflow. The phone screens show one journey; the numbered circles mark construction stages, not application counts. 

Specification entry. The excerpt below shows the form of a state-changing in-teraction. A page identifier groups its controls; the action identifier names the operation; and the state change and check make the outcome observable.               

> {"id": "detail.skuPanel", "interactions": [{ "element": "Add to cart", "effect": "state", "actionId": "sku.addToCart.confirm", "stateChange": "cart.items += item", "stateCheck": "item and quantity match" }] }

Implementation and checks. Routes and actions operate on app-owned state and seeded data. GUI actions and app-native tools use the same app state. A coverage check maps declared interaction identifiers to implementation bindings; runtime replay checks representative transitions and their expected state effects. When a mismatch appears, the specification is corrected and the affected checks are replayed. Each delivered app includes its executable interface, state model, seeded data, and reusable checks for core flows. Benchmark instructions and terminal verifiers are authored separately on top of the completed apps. 17 Preprint. Under review.

## D DATA COLLECTION 

D.1 CONSTRUCTION DETAILS 

Environment representation and task synthesis. Task synthesis is grounded in the functions an application supports and the states reachable from a given screen. For Android emulator applications, exploration is used to map screens and transitions. For M OBILE GYM ++, the page, action, and business-object declarations are available from each simulated client. A global view summarizes an application’s features and where they are located; a local view lists states directly reachable from the current screen. Instructions are phrased as user goals rather than naming the controls, tools, or verifier fields to use. 

Trajectory rollout and filtering. The same model executes each instruction step by step, producing a Thought: paragraph followed by one action per turn. When the foreground application exposes app-native tools, its tool catalog is available and the model may choose a tool call or GUI action. Both channels act on the same application state. A rollout is retained when the task succeeds under its runtime-specific check: the programmatic verifier for M OBILE GYM ++ or a vision-language judge for Android emulator tasks. Degenerate transitions that leave application state unchanged are removed. D.2 EXECUTABLE RL TASKS 

Each executable RL task is a triple of instruction, initial state, and verifier. The initial state is a snapshot of the M OBILE GYM ++ application stores, so repeated rollouts of a task start from the same state. The verifier compares application state before and after an episode and checks whether the requested change was written. Since it reads application state rather than the screen, it evaluates GUI and app-native tool actions alike. D.3 DATA COMPOSITION 

Source coverage. The SFT mixture contains 11,643 trajectories. Of these, 7,725 come from emulator(about two third), while 3,918 come from simulator (about one third; Table 6). The mixture therefore combines trajectories from Android emulator applications with controllable simulated-client workflows. 

Trajectory length and action channels. Mean trajectory lengths range from 6.8 steps for hybrid trajectories to 11.9 for AndroidWorld, with MobileGym at 10.7 and MobileWorld at 8.8. ## F APP -NATIVE TOOL EXAMPLES 

App-native tools occupy the same action slot as mobile_use GUI interactions: at each step, the agent chooses one action from a single list that includes both. When an application is in the foreground, its tool catalog is appended to that list; when the application leaves the foreground, its tools are removed. The following Taobao schemas illustrate read, state-changing, and navigation-to-GUI operations. The tool handlers and the visible application use the same useTaobaoStore : for example, add_to_cart updates the cart state that the GUI renders. Tool schemas reject undeclared input keys. 

taobao__search_items(query: string, limit?: integer) taobao__get_item_summary(item_id: string) taobao__add_to_cart(item_id: string, sku_description: string, quantity: integer [1..99]) taobao__prepare_checkout(cart_line_ids: string[1..30]) 

The first two calls read the catalog; add_to_cart validates the item, SKU, and quantity before writing the shared cart. prepare_checkout accepts one to 30 valid cart-line IDs, opens the confirmation page, and creates neither an order nor a payment. The GUI then continues from the same app state.
