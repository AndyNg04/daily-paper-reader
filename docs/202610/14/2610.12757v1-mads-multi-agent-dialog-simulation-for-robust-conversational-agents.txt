# Abstract 

Task-oriented conversational agents remain fragile under real-istic conditions, especially when users exhibit non-cooperative behavior. Existing function-calling benchmarks underrepresent adversarial conversation trajectories, thereby limiting the train-ing resources available for developing robust agents. We present 

MADS (Multi-Agent Dialog Simulation) , a synthetic data generation pipeline that produces structured, diverse dialogue trajectories. We inject adversarial conversation, producing val-idated conversation trajectories that capture realistic, unhappy paths. Using MADS, we construct MADS-Bench: a benchmark spanning six domains, 55 personas, and 1095 conversations, with approximately 66% of conversations containing failure-prone conversation scenarios. We evaluate the robustness of the trained models using a two-stage training approach that com-bines supervised fine-tuning (SFT) and reinforcement learning with verifiable rewards (RLVR). 

Index Terms : conversational agents, LLMs, dialog manage-ment, synthetic data, human-computer interaction 

# 1. Introduction 

Task-oriented dialog systems are a central component of mod-ern enterprise conversational AI, powering applications such as customer support, transaction handling, and automated ser-vice workflows. Despite significant advances in natural lan-guage understanding and generation driven by large language models (LLMs), the dialog management layer in many de-ployed systems remains largely unchanged. Most enterprise-grade systems continue to rely on rigid, finite-state dialogue managers or pre-scripted call flows that enforce fixed interac-tion paths. While such architectures offer predictability and control, they struggle to handle deviations from expected user behavior, evolving goals, or incomplete information, often lead-ing to brittle interactions and increased user friction. This lim-itation is particularly acute in spoken dialogue systems, where users expect natural, flexible interaction and cannot easily nav-igate rigid menu-driven flows. In contrast, human agents exhibit a high degree of flexibil-ity in task-oriented conversations. They maintain rich conver-sational context, infer missing information when possible, and dynamically decide whether to ask clarifying questions or con-sult external resources. Human agents can also revise previous assumptions as new information emerges, enabling graceful re-covery from errors or unexpected user inputs. Bridging this gap between rigid automated systems and adaptive human behavior remains a core challenge in conversational AI.

Recent work on LLM-based agents has begun to explore mechanisms for integrating reasoning, action, and interaction with external tools. Chain-of-thought prompting [1] demon-strated that explicitly eliciting intermediate reasoning steps im-proves performance on complex tasks. Building on this idea, ReAct [2] introduced a framework that interleaves natural-language reasoning with environment actions, enabling LLMs to plan and execute multi-step tasks without task-specific fine-tuning. ReSpAct [3] further extended this paradigm by incor-porating an explicit conversational channel, allowing agents to ask clarifying questions and incorporate user feedback during execution. More recently, Pre-Act [4] showed that internaliz-ing multi-step planning within the model through fine-tuning can substantially improve action selection and task completion across both conversational and non-conversational domains. While these methods demonstrate promising capabilities across agent reasoning and planning, applying them directly to customer-enterprise dialog management presents several open challenges. First, customer-enterprise interactions often require agents to decide not only what action to take, but whether to act autonomously or defer to the user for clarification. Existing function-calling benchmarks [5, 6, 7, 8, 9] do not model failure-prone conversation trajectories and evaluate tool-use across nor-mal, ambiguous, and agentic settings. The lack of robust training data, which comprises real-world scenarios such as user goal changes, policy violations, or infeasible requests, in multi-turn dialogue trajectories. This leaves a resource gap for training and evaluating agents robustness under realistic, non-cooperative conversational conditions. To address this gap, we propose MADS (Multi-Agent Di-alog Simulatation) a synthetic data generation pipeline based on a multi-agent LLM simulation framework. Specifically, we target the absence of training resources that systematically cap-ture non-cooperative user behavior, tool failures, and infeasible requests within validated multi-turn dialogue trajectories. The pipeline comprises of three interacting agents: a user agent that simulates realistic user behavior, a system agent that performs dialog reasoning and action selection, and a tool agent that emulates external APIs and environmental feedback. By explicitly modeling these roles, the pipeline produces synthetic multi-turn dialog traces with structured reasoning and action su-pervision, including both successful and failure-prone scenarios categorized into unhappy-path and impossible scenarios. Using MADS, we construct MADS-Bench spanning six domains, comprising 72 tools and 55 personas, with unhappy-path scenarios forming the majority of tasks. We then use this benchmark both to fine-tune open-source models and to evalu-ate them using a two-level evaluation paradigm as proposed in Pre-Act [4]. # 2. Related Work 

2.1. Benchmarks and Datasets 

Several benchmarks evaluate LLMs’ performance in function calling and tool use across varying levels of complexity. The Berkeley Function-Calling Leaderboard (BFCL) [10] provides a large-scale collection of real-world API schemas linked to natural-language instructions, emphasizing schema grounding, argument inference, and relevance detection, with later ver-sions extending evaluation to multi-turn and multi-step set-tings requiring API state tracking across turns. Complex-FuncBench [11] targets constrained, multi-step function calling under long-context conditions, requiring implicit parameter rea-soning across sequences of up to 128k tokens. ToolBench [8] assesses pipeline-level tool use across heterogeneous APIs, cov-ering multi-step planning, cross-tool coordination, and error re-covery. More recent benchmarks, such as τ -bench [12] and τ 2-

bench [13], further evaluate the behavior of conversation inter-action agents with simulated users and tools. τ -bench simulates dynamic conversations between a user and a tool-augmented agent across common task domains and introduces evaluation metrics to assess agent reliability across trials. τ 2-bench ex-tends previous work to a dual-control environment in which both the agent and the user use tools within a shared state space, examining user-agent coordination. However, these bench-marks evaluate models under cooperative user behavior and do not systematically expose agents to non-cooperative dynamics such as goal changes, tool failures, or infeasible requests. In contrast to human-annotated task-oriented dialogue cor-pora such as MultiWOZ [14] and the Schema-Guided Dialogue dataset [15], which provide naturalistic multi-turn conversa-tions, but at a limited scale and without explicit tool-use super-vision. MADS-Bench addresses this gap by providing training and evaluation data specifically designed for unhappy-path con-versational scenarios involving agent reasoning and planning. By providing structured reasoning, the dataset steers models to learn underlying multi-step planning for navigating a conversa-tional scenario. The structure of the dataset is beneficial for su-pervised post-training and RL post-training, making the agents robust by enabling reasoning across conversation turns. 

2.2. Synthetic Data for Tool-Augmented Dialogue 

Generating synthetic training data for tool-augmented dialogue has emerged as a practical alternative to costly human anno-tation. ToolFlow [16] proposes a multi-agent pipeline using graph-based tool sampling and planned-generation strategies to synthesize coherent multi-turn tool-calling dialogues, demon-strating that SFT on 8,000 synthetic dialogues can match GPT-4-level tool-calling performance. xLAM [17] unifies diverse agentic datasets through a scalable synthesis pipeline, yield-ing strong generalization across function-calling benchmarks. While these approaches prioritize dialogue coherence and tool coverage, they generate predominantly cooperative scenarios. MADS complements this line of work by explicitly modeling non-cooperative user behavior through controllable behavior in-jection, producing training data that covers both cooperative and unhappy-path dynamics within a validated multi-turn simula-tion framework. 2.3. Reinforcement Learning for Tool-integrated Reason-ing 

Supervised fine-tuning on curated tool-use trajectories remains the dominant paradigm for adapting LLMs to function calling. Reinforcement learning (RL) offers a complementary approach for optimizing grounding and correctness beyond what imita-tion learning achieves. ToolRL [18] demonstrates that RL with verifiable rewards, using tool execution outcomes as training signal, substantially improves tool selection and argument generation. StepTool [19] extends this by using step-grained reward shaping, assigning re-wards at each tool interaction based on invocation correctness and task contribution, rather than rewarding only outcomes. Our training pipeline combines SFT for structural competence with GRPO-based RLVR for grounding and correctness. Unlike StepTool, our rewards are computed against gold reference ac-tions rather than live execution outcomes, making the approach applicable to simulated environments without API access. 

# 3. MADS-Bench 

3.1. MADS Pipeline 

We propose a Multi-Agent Dialog Simulation (MADS) pipeline that produces synthetic conversations with intermediate reason-ing and planning traces. Each conversation represents a user attempting to complete a task with the help of an LLM agent that uses external tools throughout the interaction to solve task guided tasks. The proposed pipeline comprises of three distinct LLM-based agents that interact to generate realistic dialogues be-tween human and Tool augmented-AI assistants. 

Assistant Agent The assistant being trained or evaluated. At each step, it receives the conversation history and available tool definitions. Then it produces a structured response that includes reasoning ( <think> ), an optional plan ( <plan> ), and an action ( <action> ). Actions are either tool invocations (type="tool" ) or user-facing utterances ( type="say" ). 

User Agent A simulated user agent is instantiated with a person, task objectives, known slot values, and optional injected behaviors. The user agent acts as the human and generates ap-propriate responses to the assistant and terminates the conver-sation by outputting an explicit [DONE] token when the task is completed or abandoned. 

Tool Agent The tool agent receives tool definitions, scenario-specific seed data, and injected behaviors, allowing it to produce realistic outputs, including edge cases such as time-out conditions, empty results, and manage termination condi-tions. Each agent maintains its own distinct view of the conver-sation history. The assistant agent observes all steps, including tool calls and results; the user agent observes only user-facing exchanges; and the tool agent observes only tool invocations and their context. A central runner orchestrates turn-taking and manages termination conditions; the assistant agents interact with the user agents to execute dialogue traces and can access the tool agent for tool calls and tool responses. 

Multi-Stage Evaluator Once the synthetic conversation traces are generated, they undergo a multi-stage automatic data validation combining rule-based checks with LLM-as-judge evaluators. The generated conversation samples go through a checklist of four validation stages; a conversation enters the fi-nal dataset only if all the following four evaluation checks suc-ceed: • Syntax Evaluator Verifies structural correctness: each As-sistantAgent step must contain a <think> block; the first step of each turn must include a <plan> ; and each turn must end with exactly one <action type="say"> . Tool calls are validated against their schemas for correct names, required parameters, and value types. • Faithfulness Evaluator Detects hallucination. For tool calls, the judge verifies that parameter values are grounded in user intent. For say actions, it checks that the assistant’s utter-ances accurately reflect tool results rather than introducing unsupported information. • Role Confusion Evaluator Identifies cases where the User-Agent broke character and began acting like an assistant. We filter conversations where the user asks questions to help the assistant or offers assistance. • Task Success Evaluator 1 Evaluated by an LLM judge that receives the task objective, slot constraints, and preferences, success criteria, and conversation transcript. The judge de-termines whether the assistant has achieved the user’s goal, while respecting the distinction between hard constraints and soft preferences. In cases where a scenario is impossible, success requires appropriate explanations and alternatives. 

3.2. Dataset Construction 

Using MADS, we generate a synthetic dataset spanning mul-tiple task-oriented domains, including online shopping, home services, and enterprise support workflows. Dialogs are gener-ated using diverse user personas and scenario templates to en-courage variability in language, goals, and interaction patterns. We designed scenarios across six task-oriented domains: banking assistance, online shopping, calendar assistance, restaurant booking, travel assistance, and home services. Each scenario is defined by a JSON configuration containing: • Task specification : An objective (e.g., “Cancel an order that was placed”), slot values divided into hard constraints and soft preferences, and success criteria defining task comple-tion. • Tool definitions : Domain-specific APIs with typed parame-ters and return schemas. Across all domains, we defined 72 unique tools. • Seed data : Realistic backend state (e.g., order records, flight options, account information) that grounds the ToolAgent. The distinction between user slot-value constraints and preferences enables nuanced evaluation: constraints must be satisfied for the task to be judged successful, whereas prefer-ences may be relaxed at the user’s discretion. To increase dia-logue diversity in our dataset, we created a catalog of 55 per-sonas derived from the PersonaHub dataset [20], spanning dif-ferent demographics, occupations, and communication styles. Each persona includes a name, age, hometown, occupation, bio-graphical background, a description of writing style, and sample messages. For example, one persona is a geology research as-sistant who communicates in short, action-oriented fragments, while another is a history professor who uses formal, structured sentences. Personas are assigned to scenarios based on domain rele-vance. When a simulation is run, the UserAgent’s prompt incor-porates the full persona specification to encourage stylistically consistent responses throughout the conversation.

3.3. Taxonomy of Unhappy Paths 

Real-world dialogues frequently involve complications: users provide incomplete information, change their minds, encounter system errors, or request impossible outcomes. To ensure our dataset covers such phenomena, we implemented an injected-behavior mechanism. 

Conversational adversities. These capture dynamic user be-haviors that stress the agent’s planning and clarification strat-egy. • Partial information : The user provides incomplete or un-derspecified task details. • Incremental constraint revelation : Preferences and con-straints are disclosed gradually over several turns. • Goal revision : The user modifies their objective or con-straints during the conversation. • Adversarial tone : The user expresses frustration, skepti-cism, or challenges system suggestions. 

Execution-level adversities. These model realistic tool or en-vironment failures that require recovery or principled refusal. • Backend failure : Simulated server-side errors during tool invocation. • Empty results : Tool queries return no valid candidates. • Timeout : Tool calls exceed execution limits. • Policy constraint : Requests are denied due to domain-specific business rules (e.g., expired refund window). For scenarios in which the user’s objective is lit-erally unattainable given the scenario configuration, we mark the task with an impossible flag and specify a fallback behavior that describes how the assistant should gracefully decline while offering alternatives. Approxi-mately 66% of our final dataset contains unhappy-path scenar-ios.

3.5. Evaluation 

Inspired from Pre-Act [4], we evaluated the performance of models across two levels of evaluation. First, we compute the turn level evaluation (L-1), in which each conversation turn is evaluated against the ground-truth. Further, we evaluated the agents trajectory level success rate (L-2), assessing multi-turn reasoning and planning across the entire conversation trajectory. 

3.5.1. Turn Level Evaluation (L-1) 

In turn level evaluation, we compare the model’s performance for each conversation turn against the ground-truth response. For inference on the test split, we used the following two meth-ods Pre-Act [4] and ReAct [2]. For each user query, the model must decide between two actions either to make a tool call and generate response based on the tool’s response, or to have a con-versation with the user to clarify the user query. We compute the following metrics: 

Action Classification We measure recall for the binary ac-tion decision (tool call vs. answer), which captures the model’s ability to correctly identify the correct action to perform given the user query and conversation context. 

Tool Call Accuracy When the ground-truth action requires a tool call, we evaluate the tool invocation accuracy, whether the right tool was invoked, and whether the tool parameters Figure 4: MADS-Bench training split distribution by domain (left) and scenario complexity (right). 3.5.2. Trajectory Level Evaluation (L-2) 

We evaluate the models at the trajectory level by scoring whether a model can sustain correct multi-turn decision-making and action sequence over an entire conversation, rather than matching isolated turns. Concretely, we run the model on the held-out MADS test set and obtain a sequence of predicted assistant outputs, each containing a structured <action> 

block. We then group predictions into full conversations by 

scenario id and conversation boundaries, and score each conversation in temporal order using a strict “stop-on-first-error” criterion. A turn is marked correct if the predicted ac-tion type matches the reference (i.e., tool vs. say ); for tool actions, the predicted tool name must match the reference tool name under case-insensitive exact matching with a small edit-distance tolerance. If a turn is incorrect, scoring terminates im-mediately for that conversation. The conversation score is de-fined as the fraction of turns that are correct up to the first error, i.e., correct /attempted with attempted equal to the index of the first incorrect turn. The reported L2 success rate is the mean conversation score, which penalizes early failures and re-wards agents that maintain consistent grounded behavior over longer turn conversations.

In this section, we demonstrate the effectiveness of MADS-Bench through a series of evaluations across different train-ing stages. We frame the task of agentic dialogue output as a sequential decision-making problem where, at each step, the

Actions are ei-ther tool invocations or user-facing utterances. We adopted a two-stage training pipeline consisting of supervised fine-tuning (SFT) followed by reinforcement learning with verifiable re-wards (RLVR) inspired by [18, 21]. 

4.1. Training Setup Supervised Fine-Tuning (SFT) During the SFT stage, models are trained on the full MADS-Bench training split, consisting of 106 conversation trajectories, using a learning rate of 2 × 10 −4,batch size 4, with gradient accumulation over 4 steps. The ob-jective is next-token prediction over structured outputs contain-ing reasoning ( <think> ), planning ( <plan> ), and action to-kens ( <action> ). 

Reinforcement Learning with Verifiable Rewards (RLVR) RLVR training is performed on a subset of 50 sampled conversations from the training set. The RL stage uses a learning rate of 1 × 10 −5, batch size 1 with gradient accumulation of 4 steps, and is trained for 5 epoch. During training, the model generates multiple candidate responses (K = 8 generations) for each rollout. We adopt the Group Relative Policy Optimization (GRPO) objective, following prior work [18], which reports stronger performance compared to PPO in ablation studies. 

4.2. Supervised Fine-Tuning 

While supervised fine-tuning (SFT) substantially improved the model’s ability to follow the required format structure and in-creased tool-use frequency, it did not eliminate several critical failure modes that emerged repeatedly during trajectory-level evaluation. Most notably, the assistant often: • Hallucinated task completion without invoking any tools. • Generated ungrounded or fabricated tool arguments, includ-ing nonexistent IDs and incorrect temporal values. • Ignored or contradicted tool outputs, e.g., promising a refund when the tool explicitly returned a zero-refund result. These errors are not rare formatting mistakes but fundamen-tal reasoning failures that compromise safety, robustness, and correctness in agentic systems. Crucially, they arise precisely in situations where the environment provides verifiable signals, tool schemas, argument types, tool outputs, and scenario con-straints that a correct agent should incorporate. Therefore, we perform reinforcement learning post-training within our train-ing pipeline to optimize the model for action correctness, accu-rate tool invoking and the semantic similarity of user-facing re-sponses using signals that the environment can objectively ver-ify. 

4.3. Reinforcement Learning with Verifiable Rewards (RLVR) 

RLVR shifts the training objective from imitating demonstra-tions to behaving correctly according to tool outputs, argument validity, and action criteria. To incorporate RL into our agent training pipeline, we adopt a GRPO policy gradient, but adapted to the design constraints of our Pre-Act simulation conversation. Our RLVR setup uses three verifiable reward components that directly reflect the reward functions implemented in our code: (1) an action-type reward, (2) a tool-match reward, and (3) a final-answer F1 reward. Each component is computed de-terministically from the model’s generated <action> block and a gold reference action extracted using the same parsing logic. No heuristic scoring or human annotation is used. • Action Reward This reward measures whether the assistant predicted the correct high-level action type ( tool vs. say ). The implementation compares the predicted action type with the gold action type extracted from the reference output. • Tool Accuracy Reward This reward is computed only when both the gold and predicted actions are tool invocations. It checks two conditions: (a) whether the predicted tool name matches the gold tool name, and (b) whether the predicted parameter dictionary exactly matches the gold parameters. • Semantic Reward This reward is evaluated only when both the predicted and gold actions are of type say . Instead of relying on token-level overlap, we compute the reward using a sentence-transformer model that outputs a semantic simi-larity score between the predicted natural language response and the gold reference response. Scenario Complexity Analysis 

Table 6 shows task success rates broken down by task com-plexity, i.e., whether it can be completed “normally” (without problems), via an “unhappy path”, or encounters an “impossi-ble” scenario. In cooperative normal scenarios, models trained by RLVR achieve the strongest performance, suggesting that RLVR helps follow the correct sequence of steps and reduces failure cases. Using SFT only, APIGen training is actually bet-ter than MADS-Bench training, given that the dataset is focused on “normal” conversations. However, RLVR improves both the “normal” and “unhappy path” cases dramatically, and outper-forms the APIgen baseline. The RLVR improvement is largest for the small model, but still substantial for the large (32B) model. We also find that RLVR degrades the performance for “impossible” conversations. This could simply be due to a lack of training data, since our limited RL fine-tuning set has only five instances of impossible cases. In terms of model size, we note that the 32B model per-forms overall better than the 7B version, but that the advantage is especially large for the harder conversations (unhappy and impossible). It makes sense that larger models have better rea-soning ability, allowing them to deal better with more complex tasks. 

# 6. Conclusions 

Real-world task-oriented conversational systems must operate under conditions that diverge substantially from the coopera-tive settings typically represented in existing function-calling benchmarks. Users frequently provide incomplete information, revise goals during interaction, or issue requests that cannot be satisfied due to system constraints or policy limitations. Despite the rapid progress of LLM-based agents, the lack of training re-sources that systematically capture such failure-prone conver-sational dynamics remains a key bottleneck for building robust dialog managers. Impossible 40.0 40.00 63.33 36.67 56.67 In this work, we introduced MADS, a multi-agent dia-log simulation pipeline designed to generate structured multi-turn conversations that include reasoning, planning, and tool-invocation supervision. By orchestrating interactions between simulated user, assistant, and tool agents, the pipeline enables controllable injection of both conversational adversities (e.g., partial information, goal revisions) and execution-level fail-ures (e.g., backend errors, policy constraints). Using this sim-ulator, we constructed MADS-Bench, a multi-domain bench-mark spanning six task-oriented domains, 72 tools, and diverse user personas, with a large proportion of scenarios representing unhappy-path or impossible interactions. Empirical results demonstrate that training on MADS-Bench improves the robustness of tool-augmented agents be-yond that achievable with cooperative datasets alone. While su-pervised fine-tuning establishes structural competence for rea-soning and tool usage, reinforcement learning with verifiable rewards (RLVR) significantly improves action correctness and trajectory-level task success across both small and large mod-els. These findings suggest that verifiable reward signals de-rived from tool-grounded environments are critical for stabiliz-ing long-horizon decision making in conversational agents. Future work may extend this pipeline along several direc-tions. First, scaling the simulator to larger tool ecosystems and more diverse adversarial behaviors could further improve the coverage of realistic dialog conditions. Second, integrating real tool execution environments or sandboxed APIs may en-able richer reward signals and more faithful agent evaluation. Finally, extending the simulator to multimodal or speech-to-speech systems would enable the study of robustness in next-generation conversational assistants operating in real world hu-man–AI interaction scenarios. Overall, MADS provides a scalable approach to generating structured training data that exposes conversational agents to re-alistic failure modes, thereby enabling the development of more robust and reliable task oriented conversational agents. 7.
