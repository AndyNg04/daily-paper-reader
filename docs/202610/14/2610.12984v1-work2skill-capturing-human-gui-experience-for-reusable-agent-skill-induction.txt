## ABSTRACT 

Computer-use agents can perform increasingly complex GUI tasks, yet unfamil-iar software and workflows requiring human domain knowledge remain challeng-ing. Human demonstrations convey procedural knowledge through the same GUI interaction space, but reuse requires interpreting actions in context and separat-ing workflow rules from task-specific details. We thus introduce Work2Skill, a framework that captures human GUI experience for reusable agent skill induc-tion. WorkRecorder provides the framework’s infrastructure for collecting this experience, aligning screen recordings, mouse and keyboard events, and available accessibility-tree information. Using WorkRecorder, we construct WorkDemo-350, the first synchronized multimodal dataset of human desktop GUI demon-strations for reusable agent skill induction and downstream evaluation. Its 350 demonstrations are screened for completeness and task success. We then pro-pose an agentic skill-induction method that inspects evidence on demand to pro-duce reusable skills capturing workflow rules, step dependencies, and completion checks. When the same four execution models are equipped with skills induced by each method under shared execution settings, Work2Skill achieves the highest scores and success rates. Mean score improvements over the corresponding No Skill baseline are 4.67 –10 .54 points on MyPCBench Bounded Action and 3.11 –

7.50 points on a 286-task subset of OSWorld-Verified. Our code and data are available at https://github.com/china-qijizhifeng/Work2Skill .

Computer-use agents can perform increasingly complex desktop and web tasks, supported by advances in GUI grounding and plan-ning (Qin et al., 2025; Agashe et al., 2025; Wang et al., 2025a). Yet agents still struggle with unfamiliar software and workflows that require domain knowledge, where successful execution depends on procedures not spelled out in the user’s request (Zhang et al., 2026e; Jang et al., 2026). For example, “submit my reimburse-ment” does not specify which internal portal to use, which receipts to attach, or what to check before submission. Agents need this user- or organization-specific procedural knowledge to translate a user’s goal into GUI actions. Human demonstrations offer a direct source of this knowledge be-cause humans and computer-use agents share the same GUI in-teraction space. Demonstrated controls, action sequences, and visible outcomes can therefore guide an agent’s own execu-tion. Prior work converts demonstrations into expert instruc-tions and semantic action traces (Li et al., 2025; Zhang et al., 2026e), multimodal tutorials (Bai et al., 2026), or reusable skills 1arXiv:2610.12984v1 [cs.AI] 9 Oct 2026 Preprint (Yang et al., 2026a; Xiao et al., 2026). OpenAI’s Record & Replay (OpenAI, 2026b) and Claude’s Record a skill (Anthropic, 2026b) bring this approach to user-facing tools. We thus introduce Work2Skill, a framework that captures human GUI experience for reusable agent skill induction (Figure 1). Its three components address the following challenges in action grounding, method comparison, and evidence inspection. First, action coordinates reveal where an operation occurred but not what the target control means. ShowUI-Aloha interprets actions from full-screen frames and target crops (Zhang et al., 2026e), while Demo2Tutorial uses before-and-after screenshots (Bai et al., 2026). Without accessibility-tree (AX) evidence, these parsers depend on visual grounding to infer target semantics; selected frames can also miss transient states and intermediate operations. WorkRecorder addresses this ambiguity by aligning screen recordings, mouse and keyboard events, and available AX information. Recorded element names and roles provide explicit control semantics, while linked video preserves the surrounding state changes. The induction agent can thus interpret an operation using both its visual context and available structured UI evidence. Second, representative desktop GUI studies use different demonstrations, task sets, and execution protocols (Zhang et al., 2026e; Bai et al., 2026). Their results mix differences in induction with differences in source experience and evaluation conditions. WorkDemo-350 provides a common demonstration resource for skill induction in desktop environments. Collected with WorkRecorder, it contains 350 human GUI demonstrations covering 64 MyPCBench Bounded Action tasks (Jang et al., 2026) and a 286-task OSWorld-Verified subset (Xie et al., 2024). Each demonstration is screened for completeness and task success and packaged with synchronized visual and action evi-dence, plus available AX information. This shared evidence and a controlled downstream protocol support comparisons of induction methods using the same task evaluators and execution conditions. Third, representative pipelines prescribe an order for action parsing and procedure abstraction, even when individual stages refine their outputs (Zhang et al., 2026e; Bai et al., 2026). This couples ev-idence inspection to predefined stages. Loading a long recording into context at once also creates context pressure, while selecting a fixed subset can omit details needed later. Our agentic skill-induction method addresses both constraints by interleaving on-demand evidence inspection with skill writing and revision. Drawing on active evidence acquisition in agentic video understand-ing (Yuan et al., 2025; Wang et al., 2026; Li et al., 2026), the agent selects linked files, images, and video intervals to resolve questions as they arise. It can revisit the source after drafting with-out loading the entire recording at once. During skill writing, we guide the agent to generalize demonstration-specific inputs into task-dependent descriptions while preserving procedural rules, step dependencies, and completion checks. The skills guide execution without the source recording. We evaluate the resulting skills through downstream execution on the WorkDemo-350 tasks. Us-ing official evaluators and a shared text-guidance interface, we compare Work2Skill with No Skill and text-adapted versions of ShowUI-Aloha and Demo2Tutorial. Across four execution models, Work2Skill improves mean evaluation scores over No Skill by 4.67 –10 .54 points on MyPCBench Bounded Action and 3.11 –7.50 points on the evaluated OSWorld-Verified subset. Further experi-ments test reuse under changed requirements within the same application (MyPCBench Jitter) and transfer between two execution models. Evidence ablations and the Pipeline Prompt comparison examine the roles of input modalities and induction-prompt design. Our contributions are threefold: 1) We introduce WorkRecorder , the human GUI experience collection infrastructure of Work2Skill, which aligns recorded inputs with visual and available AX evidence to clarify demonstrated actions. 2) We construct WorkDemo-350 , the first synchronized multimodal dataset of human desktop GUI demonstrations for reusable agent skill induction and downstream evaluation. 3) We propose an agentic skill induction method that interleaves on-demand evidence inspection with skill writing and revision. Across two benchmarks and four execution models, it achieves the highest scores and success rates among the evaluated methods.

WorkRecorder captures screen video, keyframe images, mouse and keyboard activity, and available UI information as multimodal evidence (Figure 3). An action trace links each recorded operation to its supporting evidence so that the induction agent can inspect individual steps. Task setup and outcome evaluation follow the corresponding benchmark procedures. A macOS interface records local workflows or interactions with a remote Linux desktop. For remote tasks, the Mac captures the displayed workflow and local inputs, while a collector in the target environment supplies UI evidence. Platform-specific collectors provide target-element metadata, accessibility-tree (AX) snapshots, and application or window context when available. Coverage depends on the recording configuration and the application’s accessibility support. 

Multimodal Capture and Alignment. WorkRecorder aligns input events and visual observations on a common video-relative timeline. It groups timestamped events into actions such as clicks, drags, scrolling, and hotkeys, then links these actions to keyframes. An agent can therefore inspect a click alongside its screen image, available target information, and surrounding video to determine what changed. Target-element association uses pointer location and event timing, with window context and control semantics helping select among candidates. On Linux, AT-SPI point queries and nearby accessibility events supply available names, roles, and bounds for click and drag records. UI annotations are derived from the corresponding target elements in the AX tree. AX snapshots provide additional interface context but need not reflect the exact action-time state. Appendix A details the recording architecture, capture policies, target-matching rules, and time alignment. 

Evidence Representation and Packaging. Each demonstration becomes an evidence episode containing the task instruction and metadata, an ordered action trace, and the available multimodal evidence. A manifest indexes these resources; action records link to keyframes and video times. These links support targeted inspection without processing the recording sequentially. Descriptions help locate operations; linked recordings let the agent verify their interpretation. The available evidence depends on capture and export settings. Appendix B provides details. 3.2 WORK DEMO -350 WorkDemo-350 provides a common evidence resource for studying skill induction. We screen tasks and recordings to re-tain successful, high-quality demon-strations. For OSWorld-Verified, we first exclude infeasible tasks for which a valid human demonstration cannot be completed. Across both benchmarks, demonstrators follow valid GUI work-flows and verify the final state without being restricted to a prescribed action sequence. We then review task suc-cess and recording completeness, dis-carding demonstrations that omit key operations or end in an incorrect state (Appendix E). Each episode links task and action records to available visual and UI evidence. Episodes are organized by benchmark and task so that methods can draw on the same demonstra-tions while choosing which modalities and time intervals to inspect. The collection contains ap-proximately 8.48 hours of recorded experience, accompanied by action traces and evidence images. Table 1 summarizes the dataset’s size and multimodal evidence statistics. 3.3 AGENTIC SKILL INDUCTION 

Skill induction turns an evidence episode into reusable procedural guidance. Given the task instruc-tion and recorded evidence, a NexAU tool-using agent (Nex-AGI, 2026) generates skills in an output directory separate from the recordings. The default system prompt is concise: it sets evidence-access boundaries, prerequisite checks, and completion requirements while leaving the detailed exploration and revision sequence to the agent. A bundled skill-creator policy guides skill authoring. After reading this policy and the task definition in task.json , the agent alternates evidence inspection with skill writing and revision. Appendix D provides the prompts and authoring policy. 

Evidence Exploration Tools. We select file, image, and video tools that expose complemen-tary views of a demonstration at different granularities. File discovery and reading provide task definitions, manifests, action traces, key logs, and available structured UI evidence. Traces and in-dices link operations to their supporting media, while AX records supply available control names and roles. read visual evidence returns selected images with source-path labels, exposing visible controls and entered or selected values. Video tools provide access to states and transi-tions beyond the indexed images. After reading video metadata, the agent can sample an interval with watch video or request individual timestamps with extract video frames ; both return timestamp-labeled frames. Source-path and timestamp labels preserve the correspondence between returned observations and source artifacts. Appendix C details the interfaces, and Section 4.5 eval-uates the contribution of the available evidence to downstream execution. 

Active Evidence Acquisition. The agent chooses its next observation according to the task and unresolved questions in the evidence, following iterative inspection in agentic video understanding (Yang et al., 2025; Wang et al., 2026; Li et al., 2026). The prompt requires representative initial, crit-ical, and final-state images to be inspected when indexed images are available; the agent otherwise determines the inspection sequence and level of detail. For example, an ambiguous click can prompt inspection of the target frame to identify the control, followed by a later video frame to check the resulting state. Tool guidance encourages coarse video sampling followed by closer examination of relevant actions. Evidence inspection and skill writing share one conversation, so a draft can ex-pose missing constraints or unverified transitions. The agent can then return to the relevant evidence and revise the procedure to incorporate supported dependencies and completion checks. Candidate skills are not executed during induction, and downstream evaluation results are not used as revision feedback. When the available observations do not resolve an uncertainty, the authoring policy re-quires an observable conditional check or an explicit limitation in the skill. Section 4.5 compares this prompt with Pipeline Prompt, which sets exploration order but allows further inspection. 5Preprint 

Skill Generation. The agent expresses each coherent reusable capability in a SKILL.md , with YAML frontmatter containing its name and description, following the Agent Skills file convention (Zhang et al., 2025). Through the authoring policy, we guide the agent to generalize demonstration-specific inputs into task-dependent descriptions and describe UI targets semantically. The policy instructs the agent to keep phases together when they share state, task-derived data, quantities, or required ordering, and to retain selection rules, calculations, dependencies, requested scope, stop conditions, visible completion checks, and supported recovery. Skills must preserve visible GUI interaction and include all instructions needed for execution without the source recording. Before completion, the agent calls finalize extraction to validate output structure and required tool use. Checks cover task-file access, required skill structure, a recorded write followed by a read of each final skill, and metadata inspection before video sampling. Successful finalization records skill hashes, inspected source paths, validation results, and run provenance. These checks verify output structure and required tool use; they do not verify skill correctness or task success. For downstream evaluation, the executor receives the target task instruction and generated skill. It selects GUI actions using this guidance together with its observations and action history, without accessing the source recording. Sections 4.4 and 4.3 evaluate reuse across execution models and task instances. Appendix D.4 details the authoring policy and output requirements. 

## 4 EXPERIMENTS 

We organize our experiments around the following four research questions. RQ1 tests whether the induced skills improve execution on the demonstrated tasks. RQ2 and RQ3 then examine two dimensions of reuse: changes to task requirements and changes to the execution model, respectively. RQ4 investigates how the available evidence and induction prompt affect downstream utility. A case study illustrates how induced skills handle dependent subgoals in a multistep workflow. 4.1 EXPERIMENTAL SETUP 

Benchmarks. We evaluate on the 64 MyPCBench Bounded Action tasks and 286 OSWorld-Verified tasks in WorkDemo-350 using official task evaluators. On MyPCBench, the execution agent has access to both GUI actions and Bash commands. Benchmark selection and demonstration screening are described in Section 3.2. OSWorld results apply to this curated subset. Appendix E.3 describes our OSWorld execution harness and evaluator configuration. 

Skill-based Evaluation. We evaluate skills as plug-in guidance by appending their text as a clearly delimited block to the end of the executor’s base system prompt. All text-guidance methods use the same <task skills> wrapper; Appendix D.5 gives the template and injected contents. Separating procedural guidance from the execution loop supports reuse across execution models and integra-tion with different agent harnesses. We therefore use shared execution settings for each model and benchmark, varying only the appended guidance to control for differences in native agent pipelines. We compare Work2Skill with No Skill, action semantics from ShowUI-Aloha (Aloha) (Zhang et al., 2026e), and tutorial text from Demo2Tutorial (D2T) (Bai et al., 2026). The demonstration-based methods use the same source episodes, while their input modalities and evidence representations follow each method’s design. RQ1 thus compares their overall ability to produce useful guidance un-der shared execution conditions; RQ4 separately examines evidence and induction-prompt choices within Work2Skill while holding the model and skill-authoring policy fixed. 

Models and Metrics. We use GPT-5.5 (OpenAI, 2026a), Opus-4.8 (Anthropic, 2026a), Qwen3.5-35B-A3B, and Qwen3.5-9B (Qwen Team, 2026). By default, the same model induces skills and executes tasks with them; RQ3 varies this pairing. We report mean evaluation score (Score, 0– 100), full-credit success rate (SR), mean execution steps, and mean skill-induction token usage. ## 5 CONCLUSION 

We presented Work2Skill, a framework for capturing human GUI experience and converting it into reusable agent skills. WorkRecorder collects aligned multimodal evidence, WorkDemo-350 orga-nizes 350 curated demonstrations, and agentic skill induction combines on-demand evidence inspec-tion with iterative skill writing and revision. Across four execution models, Work2Skill achieves the 9Preprint highest scores and success rates among the compared methods on MyPCBench Bounded Action and the evaluated OSWorld-Verified subset. Further experiments support reuse under changed task requirements within the same application and transfer between the tested models. These results highlight the value of aligned human demonstrations and flexible evidence exploration for building reusable procedural guidance that computer-use agents can apply through a shared text interface without accessing the original recordings or other demonstration evidence.

## A RECORDER IMPLEMENTATION 

A.1 ARCHITECTURE AND DEPLOYMENT 

WorkRecorder consists of a native macOS recording application, a local service for capture coor-dination and storage, and accessibility providers. In local macOS mode, the application records the selected screen region and input activity, with available accessibility evidence supplied by the macOS provider. For a remote Linux workflow, recording remains on the Mac, while an AT-SPI collector runs inside the target desktop session. The Linux launcher connects this collector to the local service through an SSH tunnel; the remote-desktop client supplies the displayed workflow. Task initialization and official benchmark evaluation are handled separately from recording. 

Video and input capture. The macOS application records a selected screen region through ScreenCaptureKit and encodes video with H.264. CoreGraphics event taps supply mouse and key-board activity, which is also grouped into semantic operations. The operator can pause, resume, stop, and review a recording. Full keystroke capture is disabled by default; when enabled, it records key presses and releases, characters, modifiers, and timestamps. Otherwise, ordinary typing is repre-sented through aggregate typing events. The capture policy therefore determines the detail available in the input stream. 

Accessibility evidence. The Linux collector supports X11/Xorg desktops and uses AT-SPI to ob-tain Accessibility Trees, interface events, and target UI elements. Its default periodic tree sampler runs every two seconds, with limits of six levels and 400 nodes; these are implementation defaults rather than dataset collection settings. Events may reference the latest completed tree snapshot, with its sampling timestamps. Target-element queries return available names, roles, and bounds at a screen location. The recorder maps positions in the displayed remote-desktop region to Linux desktop coordinates for these queries. Availability depends on application accessibility support and sampling limits. 

Target-element association. When resolving clicks from accessibility snapshots, the resolver considers nodes whose bounds contain the click coordinate. It ranks these candidates by node confi-dence and interactive role, with an area penalty favoring smaller controls. Resolution records retain the selected source, confidence, and evidence anchor; uncertain cases can remain flagged for review. The remote Linux probing path is triggered by clicks and drags. Configured remote-display geome-try maps local pointer positions to Linux desktop pixels; positions outside the displayed desktop do not trigger a point probe. The AT-SPI watcher combines bounded point queries with nearby focus, selection, and state-change events. Its point-query ranking prioritizes active windows, named inter-active controls, other named nodes, greater depth, and smaller area, in that order. Event correlation normally checks whether the target bounds contain the pointer position, with additional handling for transient controls such as menus that disappear after selection. Pointer-resolution records retain the originating pointer sequence identifier and distinguish resolved, coarse, unresolved, and error or timeout outcomes. During export, recorded probe results are associated with actions using their trigger’s monotonic timestamp and action kind, with a nearest-action fallback within 2.5 seconds. In normal export mode, a missing click or drag target can also be recovered from the nearest specific accessibility event within a 3-second window. This backfill excludes generic page or window focus and uses each candidate event at most once. For drags, the matching anchor is the drag start, computed from the release time and recorded duration. Backfilled records retain their source, event identifier, and time offset. These are heuristic temporal associations; the matching windows are implementation tolerances, not measured accuracy bounds. Keyboard input does not trigger this Linux target probe. AX snapshots are attached independently as interface context. A.2 KEYFRAME SELECTION 

Capture triggers. WorkRecorder selects keyframes primarily around recorded operations and in-terface transitions. Recording start, stop, pause, and resume provide boundary frames, while users can explicitly mark additional frames. Routine candidates are triggered by clicks, drag releases, 14 Preprint scroll completion, recognized hotkeys, command submission, and window or tab switches. A typ-ing pause can trigger a frame when text is submitted or a typing milestone is reached; the default milestone requires at least eight characters or input events in the typing segment. Individual key presses and releases do not independently trigger screenshots. Additional enabled policies can re-quest frames at scroll milestones or when a provider reports an error or warning surface. 

Action context and capture timing. For clicks, hotkeys, and window or tab switches, the recorder can reuse a recent preceding keyframe as before-action context, with a default freshness limit of 1.5 seconds. A new before-action capture requires an explicit pre-action event; otherwise this context can remain unavailable. Result frames use a bounded settling window to allow the interface to respond. With adaptive polling enabled, capture can proceed when a provider reports readiness or when visual or text observations stabilize after a detected change; the default stability rule requires two consecutive stable samples. Waiting limits depend on the action type. If settling times out, the policy can capture the available state and flag it for review, or suppress the candidate. Thus, a result-frame link does not by itself establish that the interface has finished updating. 

Candidate filtering. The planner removes duplicate triggers within an action’s timing plan. The scheduler applies a minimum gap between separate plans, limits result frames per action, and en-forces capture budgets. When change or quality signals are available, it can also reject candidates with insufficient change or information gain. Defaults include a 500-ms gap, at most two result-related candidates per action, and a session budget of 64 keyframes; required boundary frames and explicit user marks have exemptions. These are implementation defaults, not verified settings for every collected demonstration. Retained keyframes carry identifiers and timestamps, while trig-ger decisions retain acceptance or rejection reasons. Frame reuse and candidate filtering mean that actions and keyframes need not have a one-to-one correspondence. Exported image counts are dis-tinguished from recorded keyframe counts in Appendix B. A.3 TIME ALIGNMENT 

The recorder maps evidence onto the stitched video’s timeline. Native input uses a monotonic times-tamp anchored to the first captured frame of each recording segment, rather than the time at which recording was requested. Remote Linux events use wall-clock timestamps, which are projected onto the same timeline using the corresponding first-frame wall-clock anchors and segment durations. Segment offsets account for pause/resume boundaries; remote events falling within a pause have no corresponding video frame. The Linux launcher checks host clock agreement before recording and rejects a difference greater than two seconds. This check is a deployment condition, not a measured alignment-error bound. Legacy recordings without first-frame wall-clock anchors use the session start as a fallback.

---name: tablefind-reservation-with-fallbacks description: Use TableFind to reserve a requested restaurant for a specified party/date/time, identify fallback Scranton-area restaurants, favorite the requested top fallback choices, and verify the confirmed reservation details. ---

Use this workflow when a task asks for a TableFind restaurant reservation plus fallback restaurants and favorites. 

Inputs to carry through the workflow 

• Primary restaurant name. • Party size. • Reservation date expression or exact date. Resolve relative dates such as ”next Friday” before interacting with the calendar; if the task is based on the current TableFind/session date, use that context to choose the next matching weekday. • Reservation time. If the task does not specify a time and TableFind already provides a default time in the search form, leave the default time unchanged rather than inventing a different one. • Reservation note or special-request text. • Fallback scope, count, and favorite rule, such as ”three other Scranton-area restaurants” and ”favorite the top two.” Keep the same date, time, and party size for fallback searches unless the task explicitly gives different fallback criteria. Fallback restaurants must be different from the primary restaurant. 

Set the primary search criteria 

1. Open TableFind and use the visible Search page or TableFind logo/home link to reach the main search form. 2. Set the Date field to the task date. Use the calendar picker and select the resolved day; verify the date field updates to the intended date. 3. Leave or set the Time field to the task time. If no time is specified, keep TableFind’s visible default time. 4. Open the Party Size combo box and choose the requested party size, e.g. the menu item labeled with the required number of people/guests. Verify the party-size field shows the requested count. 5. Click the Restaurant or Cuisine entry, type the primary restaurant name, and click Search. 6. On the results page, verify the heading matches the requested party size, date, and time, and select the result whose visible name exactly matches the primary restaurant. 

Check and prepare the primary reservation without losing task details 

1. On the primary restaurant detail page, verify the restaurant name, cuisine/location summary, booking panel date, party size, and available time slots are visible. 2. Select the requested time slot if it is not already selected. The selected summary should show the intended date and time and indicate remaining tables, not sold out or waitlist. If the exact requested/default time is unavailable, do not confirm an alternate unless the task authorizes alternatives. 3. Enter the task’s note in the Special requests field exactly enough to communicate the requested purpose or constraint. Verify the note text is visible in the field. 4. If the task says to gather/favorite fallbacks before confirming the primary reservation, do not click the final Confirm Reservation yet. You may leave the primary detail page and return later, carrying forward the restaurant name, date, time, party size, and note.
