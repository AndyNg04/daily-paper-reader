## Abstract 

Memory serves as the core component of LLM-based agents, enabling personalized responses via extracting and using user preferences from past interactions. However, its use may reduce response diversity, thereby narrowing the range of information available to users. Existing eval-uations rely largely on synthetic interactions and cover few memory systems, leaving the effects of memory on response diversity insuf-ficiently evaluated in real-world scenarios. We introduce MemBubble , a benchmark of 1000 in-stances built on preferences extracted from real user–assistant conversations. To measure the extent to which memory concentrates response distributions, we construct test queries in sce-narios distinct from user preferences while pre-serving topical relevance through shared prefer-ence categories. Across multiple LLMs and memory mechanisms, entropy decreases by 34.7% on average compared with directly pro-viding the full interaction history, highlighting the important role of memory processing in diversity loss. We also explore simple user-side interventions and changes in information availability but find that these do not effectively close the diversity gap. Our findings highlight the need to consider preserving diversity and user access to information alongside improve-ments in personalization when designing and using agent memory systems. 

## 1 Introduction 

LLM-based agents increasingly rely on persistent memory to extract and utilize user preferences from past conversations (Zhang et al., 2025b; Hu et al., 2025). This allows agents to provide personalized support for users with a wide range of tasks (An-thropic, 2025b). However, recent studies show that memory-based personalization can also cause prob-lems such as sycophantic responses and irrelevant content (Hu et al., 2026; Xiang et al., 2026).

In this paper, we focus on a further risk: the ef-fect of memory on response diversity (Wang et al., 2026). Users increasingly turn to AI assistants for information and ideas (Chatterji et al., 2025). Many of these requests are open-ended with a wide range of suitable answers. By drawing on stored user pref-erences, memory can steer models toward a limited set of responses, restricting user exposure to di-verse advice and perspectives (Wang et al., 2026). This narrowing may in turn reinforce existing bi-ases and fuel polarization (Sharma et al., 2024b), similar to the filter bubble effect in recommender systems (Nguyen et al., 2014; Lazovich, 2023). For example, Figure 1 illustrates a user asking for local news recommendations after expressing frustration with immigration. Having captured this frustration in memory, the assistant may repeatedly suggest negative stories about people from abroad, poten-tially strengthening negative stereotypes about for-eigners while overlooking other important issues. Although prior studies have shown that user pref-erences can narrow the response space (Wang et al., 2026; Feng et al., 2026), their evaluations largely rely on synthetic interaction histories. Such syn-thetic dialogues not only suffer from the homo-geneity of LLM generations (Jiang et al., 2025), 1arXiv:2610.25127v1 [cs.CL] 18 Oct 2026 but also express preferences in ways that differ from those of real users (Xiao et al., 2026; Guo et al., 2026). Moreover, these studies provide pref-erences directly in context or through simple re-trieval (Wang et al., 2026), leaving representative memory architectures unexamined. These concerns motivate a systematic evaluation regarding how user preferences from natural conversations affect LLM response diversity after being processed by actual memory systems. To this end, we introduce the MemBubble bench-mark, which aims to test whether memory narrows the range of plausible responses by constructing evaluation tasks that admit multiple valid answers while leaving room for memory to influence the re-sponse distribution. We first filter user–assistant di-alogues from widely used large-scale real conversa-tion datasets (Zheng et al., 2024; Zhao et al., 2024). LLMs then extract user preferences from the fil-tered dialogues and identify the preference category and corresponding scenario. We construct open-ended queries with same category but different sce-nario to maintain relevance to the preferences while avoiding tasks that call for preference-aligned an-swers. Each query is paired with a multi-session interaction history formed by randomly mixing the preference dialogue with unrelated background dia-logues. The final benchmark contains 1000 history– query pairs based on source dialogues in 35 lan-guages and queries spanning 14 topic categories. Building on this dataset, we develop an evalu-ation framework that approximates model output distributions by repeatedly sampling responses to each query and measures diversity over functional equivalence classes (Zhang et al., 2025a). Experi-ments on six LLMs and five representative memory mechanisms reveal a widespread decrease in re-sponse diversity. Entropy over functionally distinct answers decreases by 34.7% on average compared with directly providing the full interaction history, indicating that memory systems play an important role in diversity loss. We also explore simple user-side interventions to response generation but find that they do not effectively close the diversity gap. Further analysis of information availability reveals that the magnitude of diversity loss varies with in-teraction history length and retrieval depth, with patterns differing across memory systems. These findings underscore the importance of preserving response diversity and user access to information in agent memory design and use as personalization capabilities advance. Our contributions are summarized as follows: • We propose MemBubble , a benchmark with 1000 instances built from real user–assistant conversations for evaluating how agent mem-ory shapes LLM response diversity. • We conduct experiments across multiple LLMs and memory mechanisms, revealing widespread diversity loss and the important role of memory systems in this phenomenon. • We show that the diversity gap persists under simple adjustments to response generation and information availability, motivating attention to diversity and information access alongside personalization in memory design.

## 3 Benchmark Construction 

In this section, we describe how we construct the 

MemBubble benchmark by designing evaluation tasks based on user preferences observed in real-world interactions. To facilitate observing effects of agent memory on LLM response diversity, we argue that these tasks should admit multiple valid answers while leaving room for memory to influ-ence the response distribution. Those unrelated to user preferences may offer little opportunity to observe their influence, while response concen-tration in tasks that require preference alignment may primarily reflect appropriate personalization. Therefore, we identify the preference category and corresponding scenario and construct test queries with same category but different scenario. Figure 2 outlines our automated construction pipeline, with further details in Appendix A. 

3.1 Dialogue Filtering Source corpus. We utilize two large-scale datasets containing real user–assistant conversa-tions: LMSYS-Chat-1M (Zheng et al., 2024) and WildChat (Zhao et al., 2024). Each dataset origi-nally contains approximately 1,000,000 samples. 

Length filtering and deduplication. We keep con-versations containing 10–100 messages to provide sufficient context for identifying user preferences while limiting the cost of subsequent processing. We then deduplicate conversations by hashing the concatenation of all user messages after normaliz-ing case and whitespace. 

Template and placeholder filtering. We dis-card dialogues initiated in batches with same main prompts, differing only in a few words of variable fields and therefore missed after deduplication. We also remove samples containing dataset-specific placeholders, as these can obscure key information about preferences. 

Task-type filtering. We further exclude conversa-tions dominated by rewriting, translation, polishing, proofreading, or summarization, which typically express temporary requirements rather than stable preferences. We also exclude role-playing and jail-break conversations, where persona descriptions and instructions can easily be confused with the user’s own preferences. For each task category, we define exclusion rules combining keyword lists with textual features of user messages. 

3.2 Preference Curation Preference extraction. We prompt an LLM extrac-tor with a predefined extraction template adapted from Xiao et al. (2026) to extract candidate pref-erences. Each memory records a preference de-scription and supporting evidence quoted from user messages in the corresponding dialogue. A single dialogue may yield multiple preferences, but each must be supported by explicit evidence.

The check covers two aspects: i) whether facts in preference description are consistent with the preference dia-logue; and ii) whether it describes the preference with an appropriate scope, without overstating pref-erences that are not clearly expressed. We discard samples that fail either of these two criteria. 

Semantic assessment. After verifying consistency, we use two LLM judges from different providers to independently assess the suitability of the remain-ing preferences for diversity evaluation. Each judge first applies an exclusion checklist to retain clear and stable preferences compatible with our evalua-tion setting, excluding temporary emotional states and surface-level preferences for style and format-ting. It then checks whether the option indicated by each preference belongs to a nameable category with several plausible alternatives and whether the category can be described without revealing that option. For preferences that pass these checks, the judge extracts the preference category c and corre-sponding scenario s. Two LLM judges from differ-ent providers assess each preference independently given the importance of this step, and we only keep samples that are accepted by both judges. 

3.3 Query Construction Query generation. We construct test queries based on identified suitable preferences with key attribute fields. We prompt an LLM generator to write queries using only the category c and attached sce-nario s extracted in the previous stage, without pro-viding the concrete preference value. We require each query to present a single, impersonal request for one member of c, with a scenario that must dif-fer substantively from s without adding conditions that narrow the range of reasonable answers. 

Leakage and relevance check. We check the re-lation between each generated query and its cor-responding preference to ensure the query leaves room for memory to influence the response distri-bution. An LLM judge verifies that the option indi-cated by the preference remains a natural answer to the query and that the query does not directly name or narrowly imply that option. 

Diversity pre-test. To facilitate the observation of diversity changes, the query should elicit diverse responses without user preference involved. For each candidate query, we independently sample 5 responses from an LLM. A separate judge groups these responses according to functional equivalence as defined in §2.2 and computes the class entropy 1

over the resulting groups. We set a entropy thresh-old of 1.4 bits and include samples exceeding this threshold in the final dataset. 

3.4 Building Interaction History 

In real-world applications, users may interact with agents over time, and their conversations often span different tasks and topics. To simulate this pattern, we extend each preference dialogue in MemBubble 

into a multi-session interaction history. We draw additional background dialogues from LMSYS-Chat-1M and WildChat, excluding those used to construct the benchmark. Then we uniformly sam-ple 50 background dialogues in the same language as the preference dialogue and randomly remove dialogues until their combined length is no more than 30,000 tokens. Following Wu et al. (2025), we combine the preference dialogue with these back-ground dialogues in random order to form the final interaction history.

## 4 Evaluation Settings 

Based on MemBubble dataset, we evaluate how agent memory affects LLM response diversity. We compare responses generated under different mem-ory conditions using diversity metrics based on functional equivalent classes. This section outlines the evaluation setup, and further details are pro-vided in Appendix B. 

4.1 Memory and Response LLMs Memory conditions. We evaluate four repre-sentative agent memory architectures: Memory-Bank (Zhong et al., 2024), A-Mem (Xu et al., 2025), mem0 (Chhikara et al., 2025), and Mem-oryOS (Kang et al., 2025). Each architecture builds persistent memory from the multi-session history and retrieves relevant memory items to con-dition responses to the test query. We also include NaiveRAG (Xiang et al., 2026) as a simple mem-ory baseline that retrieves relevant sessions from the original interaction history. We use two refer-ence conditions: the input context contains only the query under No mem. and additionally the com-plete interaction history under Full history .

Response Models. We consider four closed-source LLMs from different providers and different tiers: GPT-6-Sol (OpenAI, 2026c), GPT-5.6-Luna (Ope-nAI, 2026b), Claude Haiku 4.5 (Anthropic, 2025a), and Gemini 3.7 Flash (Google DeepMind, 2026). We also include two open-source LLMs: GLM-5.3-flash (Z.ai, 2026) and Llama3.3-70B (Meta, 2024). We report results for all six models in the main experiment and use GPT-5.6-Luna for other experiments unless otherwise specified. For each query and memory condition, we independently sample k = 10 responses at temperature 1.0 with a maximum output length of 512 tokens.

## 5 Experimental Results and Analysis 

In this section, we apply the evaluation protocol from §4 on our proposed MemBubble benchmark to empirically examine how agent memory shapes LLM response diversity, guided by the following three questions: Q1: To what extent does memory affect response diversity? 5.1 Q1: To what extent does memory affect response diversity? 

We first assess how memory affects LLM response diversity by comparing five memory mechanisms against references. Table 1 shows average reduc-tions of 25.0% in distinct-k and 34.1% in class entropy across the six response models and five memory mechanisms compared to No mem. , and distinct-k decreases by 25.7% and class entropy by 34.7% compared to Full history . Figure 4 shows a corresponding shift toward fewer functional equiv-alence classes: about 34% of samples have dk = 1 

on average across memory mechanisms, compared with about 6% under No mem. and 9.5% under Full history . These results show widespread reductions in response diversity and suggest that memory pro-cessing plays an important role in this reduction. The magnitude of this reduction varies across memory mechanisms and response models. mem0 produces the largest average reductions in both met-rics, while MemoryOS has the mildest effect. Mem-oryBank and A-Mem also concentrate the distribu-tion at low distinct-k values, whereas MemoryOS retains a broader spread. Among response models, GPT-6-Sol shows the largest average reductions in both metrics, while Gemini 3.7 Flash shows the smallest. Figure 5 (left) shows that memory mecha-nisms bring distinct-k to similarly low levels across response models despite differences in diversity un-der No mem. In the right panel, larger diversity re-ductions coincide with higher preference hit rates, indicating that reduced diversity accompanies more frequent preference-aligned responses even when the query does not require such alignment.

## 6 Related Work 

Agent memory. LLM agents use memory to keep user preferences and personalize responses (Zhang et al., 2025b; Xu et al., 2026). Representative sys-tems summarize useful information from past user interactions (Zhong et al., 2024; Chhikara et al., 2025) and store it externally in forms such as user profiles (Westhäußer et al., 2025) or linked memory notes (Xu et al., 2025) for later retrieval. 

LLM response diversity. Existing research has revealed limited diversity in LLM-generated re-sponses (Padmakumar and He, 2024; Sourati et al., 2026), showing substantial homogeneity in genera-tions both within a single model and across differ-ent models (Zhang et al., 2025a; Jiang et al., 2025). Human studies further report reduced collective diversity in AI-assisted writing (Doshi and Hauser, 2024; Meincke et al., 2025) and increased selective exposure in conversational search, especially when models reinforce user views (Sharma et al., 2024b). Most of these works focus on direct model gen-eration and do not investigate how agent memory affects response diversity. 

Over-personalization of memory-augmented LLMs. Memory substantially enhances personal-ization in LLM assistants (Zhang et al., 2026; West-häußer et al., 2025). However, research has iden-tified over-personalization as a potential risk (La-zovich, 2023; Hu et al., 2026). Most studies pay attention to sycophancy (Cheng et al., 2026), where models prioritize agreement with users over truth-fulness (Sharma et al., 2024a; Xiang et al., 2026), and irrelevant memory usage in generated con-tent (Hu et al., 2026; Feng et al., 2026). Regarding memory-induced response diversity loss, existing evaluations largely rely on synthetic interaction his-tories (Wang et al., 2026; Huang et al., 2026) and provide preferences directly in context or through simple retrieval (Wang et al., 2026), limiting their coverage of risks in real-world applications. 

## 7 Discussion and Conclusion 

Our study focuses on measuring the effects of mem-ory on LLM response diversity, specifically the extent to which user preferences from real conver-sations influence model output distributions after being processed by memory systems. To observe this influence, our dataset construction requires the scenarios of test queries to be distinct from those as-sociated with user preferences, aiming at avoiding tasks that clearly call for memory usage. Never-theless, the applicability of preferences stored in memory to specific samples may still be open to debate. We argue that this should be comprehen-sively assessed by considering both the task and the intent of the user, which constitutes a separate research question beyond the scope of this work. In this paper, we introduced the MemBubble 

benchmark to systematically evaluate how user preferences from natural conversations affect LLM response diversity after being processed by actual memory systems. We find that memory mecha-nisms lead to widespread reductions in response diversity across models and tasks. We also try simple user-side interventions and adjustments to information availability but find that these do not effectively close the diversity gap. Our findings highlight the need to weigh improvements in per-sonalization against decrease in response diversity in agent memory systems to preserve user access to diverse information and perspectives. 8Limitations 

This work primarily examines memory-induced diversity loss on open-ended tasks. We leave a de-tailed investigation of the mechanisms underlying this phenomenon and the development of effective mitigation methods for future work. Additionally, our evaluation uses fixed interaction histories and does not capture the dynamic evolution of response diversity under continued user interaction and mem-ory updates. 

## Ethical Considerations 

The real user–assistant conversations used in our experiments were drawn from publicly released datasets and do not raise any privacy concerns. We used generative AI to polish the manuscript and assist in preparing figures and tables. As described above, LLMs also participated in dataset construc-tion and response evaluation processes. We do not use AI to develop the core contributions of this work, including the identification of research problem, the design of dataset construction and evaluation pipelines.

11 A Dataset Construction Details 

A.1 Rule-based Filtering Details 

We apply the same filtering pipeline to LMSYS-Chat-1M and WildChat. For template filtering, we group messages from the user by the MD5 hash of the first 200 characters of the opening user message, considering only openings of at least 60 characters. Within each group, we retain the conversation with the most messages, breaking ties by the lexico-graphically smallest conversation ID. 

Placeholder filtering. We remove samples containing dataset-specific anonymization mark-ers, as these can obscure key information about preferences. For LMSYS-Chat-1M, we match 

NAME_\d+ , such as NAME_1 . For WildChat, we match <PRESIDIO_ANONYMIZED_[A-Z_]+> .

Task-type filtering. We apply case-insensitive matching over user messages using the keywords and textual features listed in Table 4. For rewriting, translation, polishing, proofreading, or summariza-tion, a user message must contain a trigger within its first 200 characters and a long text block satisfy-ing one of the listed length conditions. We exclude a conversation if its first user message meets these criteria or at least 50% of its user messages do. For role-playing and jailbreak filtering, any user mes-sage matching a listed expression or containing at least two asterisk-delimited spans of 2–60 charac-ters triggers exclusion. We also exclude conversa-tions whose first user message contains at least 800 characters and at least three persona-field lines. 

A.2 Semantic Assessment Details 

Each judge reviews the extracted preference and its supporting evidence, together with metadata such as the time scope and conversation language. Per-sonal background facts and transient states are ex-cluded, as are isolated requests that do not establish a stable preference. We also exclude preferences limited to response form or transforming supplied text, along with language or cultural defaults in-ferred from the conversation. Unsafe material and tasks requiring the model to output code or images are ineligible. For a preference to pass, its indicated option must belong to a natural category c with several plausible alternatives. The category name must contain at most ten words and must not repeat words from the indicated option. For example, a preference for writing AWS Lambda functions in Python yields programming language as c and 

AWS Lambda function as the original scenario s,with Java and Go as alternative members of the category. Entries for which no suitable category or open-ended task can be formed are rejected. Query construction uses only c and s, without access to the indicated option. GPT-5.5 and Claude Opus 4.8 independently as-sess each preference. Only preferences accepted by both judges proceed to query construction. For these preferences, we use the category c and sce-nario s extracted by GPT-5.5. Table 5 lists the model and prompt used for each LLM role in the construction pipeline. In general, each stage uses a fixed model choice for all samples. Stages that are central to the dataset design use top-tier commercial models, while auxiliary stages use lower-cost or open-weight models. 

A.4 Quality Control and Human Validation 

We randomly sample 200 candidates from each selection step listed in Table 6, including accepted and rejected items. ## B Evaluation Details 

B.1 Baseline Description MemoryBank (Zhong et al., 2024) maintains con-versation records alongside hierarchical event sum-maries and user portraits inferred from past inter-actions. It encodes dialogue turns and event sum-maries for dense retrieval of relevant memories. An optional updating mechanism follows the Ebbing-haus forgetting curve, allowing memory strength to decay over time and reinforcing memories when they are recalled. 

A-Mem (Xu et al., 2025) organizes interactions into interconnected memory notes inspired by the Zettelkasten method. Each note retains the origi-nal content with generated semantic annotations, including a contextual description. An LLM links new notes to related memories and updates existing notes as additional context becomes available. At retrieval time, semantic matching identifies rele-vant notes, with links providing access to associ-ated memories. 

mem0 (Chhikara et al., 2025) extracts salient facts from conversational exchanges using recent mes-sages and a conversation summary as context. For each candidate fact, it retrieves similar stored mem-ories and uses an LLM to select an ADD, UPDATE, DELETE, or NOOP operation. B.2 Retrieval and Generation Settings 

We build the memory stores for MemoryBank, A-Mem, mem0, and MemoryOS once using a shared writer model and reuse them across response-generation models. Retrieval uses a shared text-embedding-3-small embedding model; Memo-ryBank retrieves 3 entries, while A-Mem and NaiveRAG retrieve 5, and mem0 and MemoryOS retrieve 10. Unless otherwise specified, we disable reasoning during response generation or use the lowest available reasoning effort when it cannot be disabled. 

B.3 Diversity Judge and Human Validation 

For each test query and memory condition, we pro-vide DeepSeek-V4-Flash with the query and all 

k complete responses in a single judge call. Us-ing deterministic decoding, the judge partitions the responses according to the functional-equivalence criterion in Section 2.2. The resulting classes form a partition, where every response belongs to exactly one nonempty class. The prompt for functional-equivalence grouping is provided in Figure 17. 

Human validation. We randomly sample 100 response sets across response models and mem-ory conditions, each containing k = 10 complete responses. Two experienced annotators indepen-dently group the responses using the functional-equivalence criterion, with model identities and LLM judgments hidden. Following Chirkova et al. (2026), we measure agreement between human and LLM-generated par-titions using the adjusted Rand index (ARI) (Hu-bert and Arabie, 1985). ARI measures partition similarity by checking whether pairs of responses are assigned to the same or different groups consis-tently across two partitions, with a correction for chance agreement. We compute ARI for each re-sponse set and average it across the 100 sets. Mean human–human ARI is 0.843, while LLM–human ARI is 0.762 and 0.791 for the two annotators, re-spectively. These results indicate that the diversity judge is roughly aligned with human judgments of functional equivalence.

B.5 History Length Settings 

We vary the initial number of background di-alogues over {0, 5, 10 , 20 , 50 , 100 } while retain-ing the complete preference dialogue. For each nonzero setting, we uniformly resample back-ground dialogues in the same language as the pref-erence dialogue following Section 3.4, with the token budget scaled proportionally from 30,000 to-kens for 50 background dialogues. We randomly remove background dialogues until their combined length is within the scaled budget, then combine the retained dialogues with the preference dialogue in random order. We rebuild the memory stores from each resulting interaction history and repeat response generation with all other parameter set-tings unchanged. 

B.6 Preference Hit Rate Calculation 

For each test query, we retrieve the corresponding user preference description obtained during dataset construction and use the DeepSeek-V4-Flash ex-tractor to identify all nouns related to the prefer-ence. We perform substring matching between every response and the nouns extracted for its test query. For each response model and memory con-dition, preference hit rate is the proportion of re-sponses across all samples that contain at least one match.

27 Prompt for Diversity Evaluation 

You are annotating language model outputs into functional-equivalence classes. Definition of equivalence (use it exactly): Two generations are DIFFERENT if and only if a user who has seen one generation would likely benefit from seeing the other. Language model outputs can be trivially different from each other (e.g., in terms of style, tone, or length). True diversity should go beyond these surface-level differences, since such variations provide little utility to the user. This is called FUNCTIONAL equivalence. For example, in a story generation task, if two generations retell the original story with an identical plot but different character names, they are functionally EQUIVALENT.
