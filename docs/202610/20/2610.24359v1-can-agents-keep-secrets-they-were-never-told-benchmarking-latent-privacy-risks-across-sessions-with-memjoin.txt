## ABSTRACT 

To support sustained interactions and personalized assistance, agents use long-term memory to retain and combine user information across sessions. Reusing such memories can lead an agent to state a sensitive relation while completing an ordinary task that does not require it. The relation to protect and the combination of clues that reveal it may remain hidden at memory write time, when later records and tasks are still unknown. In this paper, we introduce MemJoin, a privacy benchmark of 288 synthetic analysis cases in which the complete history entails a sensitive relation, but every individual session is insufficient. We evaluate six memory systems with the same answer-generating model, alongside full-history and no-history controls. Each system writes and updates memories in session order and later retrieves context for an ordinary task, while target annotations remain with the evaluator. We separately check which target attribute values appear in stored records and retrieved context, and whether the final answer states the complete, person-linked relation. In a separate paired test on a prespecified subset, removing shared identifiers and other connecting clues can change complete-relation output while all checked target attribute values remain visible. These findings show why checking attribute visibility alone is insufficient to evaluate what records from different sessions reveal together. 

## 1 INTRODUCTION 

Long-term memory is becoming a core component of LLM agents. An agent that assists the same user over weeks or months writes records of each session, updates them as the user’s circumstances change, and retrieves them when a later task needs them (Packer et al., 2023; Chhikara et al., 2025; Zhong et al., 2024; Xu et al., 2025; Yang et al., 2026b; Zhang et al., 2026). This persistence is what lets an agent remember a preference stated once, follow up on an earlier request, and personalize its assistance without asking the user to repeat themselves; memory is now a standard feature of deployed assistants, and benchmarks evaluate these abilities directly (Mireshghallah et al., 2025; Hu et al., 2025). The same persistence, however, may create privacy risks that do not arise within a single interaction. Because memory accumulates information across sessions and reuses it later, an agent can combine facts that the user supplied at different times and for different purposes, and infer from them a relation that the user never stated in any one session. Consider a user who, in one session, asks the agent to note the date of an upcoming appointment; in another session, mentions the program code used to book it; and in a later session, encounters a public directory entry explaining that this code denotes a counseling program at a named clinic. One records only a date, one only a code, and one only what a code means in general. Together, however, the records show that this user is attending a counseling program at that clinic on that date. This sensitive relation, linking the user to a service, location, and time, is supported by the full history but by no single session. While completing an ordinary later task, such as preparing a packing list for the next appointment, the agent may state this relation even though the task does not require it. We call this risk cross-session inference .This risk is hard to detect for three reasons. First, it cannot be seen when the record is written. Second, the combination can form at different stages. A memory writer may merge clues into one record, an update may consolidate an earlier and a later state, or retrieval may bring separate records into the same context for a later task. Third, by the time the risk can be recognized, the agent may already have stated the relation, and deleting the stored records then does not retract what the recipient has learned. Therefore, checking each session for sensitive statements cannot rule out the risk, and checking only final answers cannot explain it. A privacy evaluation of long-term agent memory must observe separately which clues reach the agent through memory storage and retrieval, and whether the final answer states the relation. However, existing privacy evaluations do not isolate this risk. Privacy benchmarks for agents and memory test whether sensitive information that is already supplied is used inappropriately; because this information is present in full within a task trajectory or a memory item before the task begins, the construction of memory is abstracted away and no combination of items is required (Shao et al., 2024; Zharmagambetov et al., 2025; Mireshghallah et al., 2025; Pulipaka et al., 2026; Dong et al., 2025; Zhang et al., 2025). Memory systems and diagnostic studies examine whether information is stored and retrieved, and whether retrieved content leads to unsafe output (Packer et al., 2023; Chhikara et al., 2025; Ma et al., 2026; Al-Tawaha et al., 2026). These settings therefore leave cross-session relation formation largely untested. None of them constructs sensitive targets that are supported by the full history but not by any individual session, or tests whether such a relation is later stated in an ordinary task that does not require it. 2To study this risk, we introduce MemJoin (Figure 1), a benchmark of 288 synthetic cases that distribute the supporting facts and connecting clues of a sensitive relation across sessions. Each case is constructed so that the full history supports the relation, no individual session does, and the later task does not require it. MemJoin further tracks how these clues propagate through memory storage and retrieval and whether the final answer states the complete relation, allowing cross-session inference to be diagnosed across stages. We evaluate six memory systems with a fixed answer-generating model and observe cross-session inference under every system. Our analysis further shows that what memories reveal together depends not only on which attribute values are retained, but also on how information across sessions is connected. To our knowledge, MemJoin is the first benchmark to evaluate cross-session privacy risk in memory construction, retrieval, and downstream answers. To summarize, our contributions are as follows: • We identify and formalize cross-session inference, a privacy risk of long-term agent memory. A sensitive relation is obtained only by combining records from several sessions, and no single session contains it; yet an agent may state it while completing an ordinary task that does not require it. • We introduce MemJoin, a benchmark of 288 synthetic cases that evaluates this risk, together with a stage-wise diagnostic protocol that distinguishes, when an answer does not state the relation, whether the needed attribute values never reached the agent or reached it without being combined. • We benchmark six memory systems under a fixed reader with full-history and no-history controls, examining which clues each system delivers to the agent and whether its answers to ordinary tasks combine them into the sensitive relation. We show that attribute visibility is insufficient for privacy evaluation. What memories from different sessions reveal together depend not only on which attribute values they contain, but more on how they connect. 

## 2 RELATED WORK 

Memory construction and capability evaluation. Long-term memory enables agents to reuse information from past interactions in later tasks (Zhong et al., 2024). Existing systems organize this information through a memory hierarchy (Packer et al., 2023; Yang et al., 2026a;c), fact extraction and memory updates (Chhikara et al., 2025), or evolving networks of linked notes (Xu et al., 2025). How this information is indexed and retrieved affects both memory recall and downstream question answering, as shown in LongMemEval (Wu et al., 2025). For evaluation, LoCoMo tests recall and reasoning across sessions (Maharana et al., 2024), and MemoryAgentBench tests retrieval, test-time learning, long-range understanding, and selective forgetting under incremental interactions (Hu et al., 2025). 

Contextual privacy and memory use. Beyond recall accuracy, contextual integrity concerns whether information sharing conforms to the norms of its context (Nissenbaum, 2004). ConfAIde tests privacy reasoning through sensitivity judgments, multi-party information sharing, meeting summarization, and action-item generation (Mireshghallah et al., 2024). PrivacyLens evaluates disclosure in simu-lated tool-use trajectories (Shao et al., 2024), while AgentDAM measures task utility and unnecessary use of sensitive information in isolated, controllable web environments (Zharmagambetov et al., 2025). For long-term memory, CIMemories pairs profile attributes with tasks and evaluates necessary and inappropriate sharing under different memory compositions (Mireshghallah et al., 2025). Per-sistBench studies cross-domain leakage and memory-induced sycophancy when stored information influences later responses (Pulipaka et al., 2026). It also evaluates beneficial memory use and tests interventions based on prompting, embedding retrieval, or LLM filtering. Both CIMemories and Per-sistBench start from supplied memories rather than evaluating their construction from raw interaction histories (Mireshghallah et al., 2025; Pulipaka et al., 2026). MemJoin instead constructs histories whose cross-session facts and connecting clues jointly support a sensitive relation, then tests whether ordinary-task answers express that relation. 

Diagnostic evaluation and compositional inference. LLMs can infer personal attributes from text supplied at inference time, as shown by Staab et al. (2024). MEMPROBE follows evidence through user interaction and memory construction, then compares user-state recovery under full-store and top-k retrieval access (Ma et al., 2026). Its recovery stage uses fixed, dimension-specific queries, whereas MemJoin checks for sensitive relations in answers to ordinary tasks that do not require them. Al-Tawaha et al. (2026) separate risk-enabling retrieved contexts from unsafe output as memory 3accumulates. They also examine summarization combination, where a statement assembled from multiple memory items exceeds what each item supports individually. Fairoze et al. (2026) study recovery of in-context secrets from statistical properties of benign outputs, even when the text does not explicitly state the secret. MemJoin requires each target relation to be supported by the complete history but by no individual session. Separate paired tests remove connecting clues and compare whether answers state the complete relation on a prespecified subset where all checked target attribute values remain visible.

3.1 DATA CONSTRUCTION 

A history written freely may reveal the relation within one session, so we construct each case backward from its target: we first bind the user to a service or attribute, a site, and a date, and then distribute these facts over sessions so that no single session binds the user to the tested service (Qiao et al., 2025). Each session contains one user message and the assistant’s acknowledgment, so that what a memory framework later keeps or loses can be traced to its own writing and retrieval. Backward construction fixes one relation per case, which leaves open which relations to test and when stating them is inappropriate. The tested services and attributes come from 12 categories that group the personally identifiable information in NIST SP 800-122 (McCallister et al., 2010), so that they cover what privacy guidance treats as sensitive. Because a relation can be inappropriate either as excessive disclosure to a legitimate recipient or as disclosure incompatible with the recipient or task purpose, each category has two scenario families. Following three stages at which a cross-session relation can be combined, we obtain three evidence configurations of linking clues, each with 96 cases: 1). Writer materialization spreads complementary facts over four sessions, so the relation can be completed when the framework merges these facts into one record as it writes; 2). Update consolidation uses five sessions, one of which revises or links earlier records, so the relation can be completed when an update consolidates earlier and later records; 

3). Retrieval join spreads the facts over four sessions whose records reference one another, so the relation can be completed only when retrieval brings these separate records into the same context. Dialogues and tasks are filled from scenario templates with synthetic values, so no personal records are used, and selected lines are rephrased by gpt-5.6-luna (OpenAI, 2026) to remove template regularities while preserving facts and references. The prompt forbids words such as sensitive, private, 4or confidential, because a model could react to words without recognizing the relation (Shao et al., 2024). Adjacent sessions are 21 or 28 days apart and the task arrives 49 days after the last, so that consolidation and retrieval span weeks. Appendix A reports the timeline, prompts, and counts. Before any agent is evaluated, each case passes three checks, each targeting a different part of the case. extbfDeterministic checks verify the case files: field consistency, provenance, and that agent inputs contain no evaluator annotation. A extbfnorm audit verifies the scenario-family label: three annotation models label diagnostic probes for every family, and any mismatch with the frozen label is adjudicated by hand. A extbfsemantic validation verifies that the relation arises only from combining sessions: three transcript-only validators, deepseek-reasoner, gpt-5.6-terra, and gemini-3.6-flash, must all find the relation unsupported in every single session and in a control with one annotated link broken, and at least two of them must recover it from the full history. Appendix A.3 gives more details of the data checks. 3.2 EVALUATION PROTOCOL 

An evaluated agent is a memory framework together with the model that answers the task, which we call the reader. We fix the reader to Qwen3.5-9B in non-thinking mode for every framework, so that differences between frameworks come from what reaches it. A trial starts from an empty store; the framework’s own writer ingests the sessions in the order a user would have produced them (Hu et al., 2025), and its own retrieval selects at most five items, the same budget for every framework, with neither procedure altered. The reader answers the task under a short instruction not to volunteer private facts the task does not need. The task never asks for the relation, so any stated relation comes from the reader’s own inference. The relation stays with the evaluator, with three trials per condition. The reader receives the history under four input conditions. Task only supplies no history and serves as the no-history control. Full history supplies every session verbatim and serves as the no-memory control. Retrieved memory supplies the items returned by the framework’s retrieval, which is how a deployed framework answers. All memory bypasses retrieval and supplies every item exported from the same trial (Ma et al., 2026). On a subset of cases, we additionally grade every combination of sessions and the store after each ingested session. Appendix B gives the full protocol. 3.3 MEASUREMENT 

In this subsection, we measure the risk from three perspectives: availability asks whether the target values reach the reader, disclosure asks whether the reader states the relation, and utility asks whether the task is still served. Each answer is graded against the relation fixed at construction, by degree, so that an answer listing values scores lower than one stating the relation and partial leakage remains visible: A0 reports no target component, A1 reports components without binding them to the user, A2 binds the user to the tested service, A3 adds the site or the date, and A4 states service, site, and date bound to the correct user and is a disclosure. 4.1 EXPERIMENTAL SETUP 

We evaluate six memory frameworks: A-Mem (Xu et al., 2025), LangMem (LangChain, 2025), Mem0 (Chhikara et al., 2025), MemGPT (Packer et al., 2023), MemoryBank (Zhong et al., 2024), and SimpleMem (Liu et al., 2026). All six are configured to use the reader’s model and the BGE-M3 embedding model. Uncertainty uses 95% case-bootstrap intervals and, for paired binary outcomes, two-sided exact McNemar tests (McNemar, 1947; Fagerland et al., 2013) with Holm correction (Holm, 1979); Appendix D lists the comparison families. 4.2 RQ1: W HAT PRIVACY RISKS ACCOMPANY MEMORY REUSE IN ORDINARY TASKS ?We first check whether the risk arises in existing frameworks and whether preventing it would cost the user useful answers. Every framework discloses fewer cases than Full history, but the reduction does not come from withholding the relation because the task does not need it. It comes from what memory loses and from how it rewrites what it keeps. First, part of the reduction is lost values. LangMem has the lowest disclosure rate and the lowest availability, 60.2%, yet among its inputs that contain the service, site, and date, 13.8% of answers state the relation, in line with the other five frameworks. Its reader discloses as often as the others once the values arrive, so its low rate reflects values that did not arrive. Availability does not close the whole gap, since even with the service, site, and date present the six frameworks stay at 10.8% to 14.4%, against 22.9% under Full history. Second, memory rewrites the evidence it keeps, and the rewriting changes which cases are disclosed. Of the 168 cases disclosed across the six frameworks, one in three are not disclosed under Full history; the Mem.-only column of Table 1 gives these counts, from 1 for LangMem to 15 for A-Mem. Models draw different conclusions from the same information presented differently (Laban et al., 2025; Al-Tawaha et al., 2026). Memory thus lowers disclosure as a by-product of losing and rewriting evidence, not by withholding what the task does not need, and the same rewriting discloses cases that Full history does not. Two consequences follow for evaluation. Giving the reader the history directly would miss one in three of the cases that memory frameworks disclose, so an evaluation has to run the memory system itself. A rate reported without availability would rank LangMem safest for delivering fewer values, so every rate needs its availability. 4.3 RQ2: H OW DO MEMORY CONTENTS AND THEIR CONNECTIONS SHAPE SENSITIVE

The six frameworks organize the same sessions differently, and Figure 3a shows that they lose the values at different stages. ## 5 DISCUSSION AND CONCLUSION 

Our work shows that cross-session privacy risk is not determined by the contents of individual memory records alone. Across six memory frameworks, ordinary-task answers disclose sensitive 9relations that no individual session states, while the same target values can lead to different disclosure behavior depending on how memory rewrites, links, and retrieves the underlying records. This shifts the privacy question from whether a record contains a sensitive value to whether multiple records can be joined into a sensitive relation. 

Implications for privacy evaluation. Privacy evaluation should look beyond the final answer and follow what happens to information throughout the memory pipeline. A low disclosure rate does not necessarily mean that a system protects the relation better: it may simply mean that some of the needed values were never written or retrieved. At the same time, memory processing can make a relation easier to state even when the same reader does not state it from the original history. Evaluating long-term memory therefore requires separating what information is preserved, what reaches the reader, how records become connected, and what relation is finally expressed. 

Implications for future memory systems. Future memory systems should control not only which records are stored or retrieved, but also which records are brought together. Our results show that disclosure can drop substantially when the cues connecting records are removed even though the underlying target values remain available, while removing the values themselves can also hurt the ordinary task. A better design should therefore preserve the information needed for the current task without automatically exposing every related record or connection. In long-term agents, protecting privacy may depend as much on limiting unnecessary combinations of memories as on deciding what to remember. AI USE STATEMENT

Each case combines source conversations, a later ordinary task, and an annotated target relation. The target annotation records the subject, service or attribute, site, date, and references that connect these facts. The 288 cases are balanced across three evidence configurations, with 96 cases per configuration and four cases per configuration within each family. This allocation links the family level counts in Table A.1 to the evidence layouts used during construction. A fixed synthetic calendar supplies reproducible relative timing, but its dates have no experimental meaning and are distinct from dates mentioned inside conversations. A.2 CASE GENERATION 

Case construction starts from the target relation. The generator fixes the subject and the target service or attribute, then creates the identity, record, site, and date components needed to support that relation. These components are placed in separate source sessions. An alias or other reference appears before the record is linked to the subject, while the service or attribute and site are introduced later. A date is 14 added separately only when the configuration requires temporal composition. The later task remains ordinary and useful, but it does not require the target relation. The complete history therefore supports the target only after the reader joins facts across sessions, and isolated values without a subject to service link do not satisfy the target. Templates then instantiate synthetic names, aliases, services, sites, and dates and apply the data generation prompt in Prompt A.1 only to selected existing lines. The rewriting step preserves identifiers, dates, fact roles, and connecting references, and introduces no real personal records. The system instruction prevents factual invention, the user template supplies the line and its situation, and the role rules distinguish a user speaking about themselves from a user quoting a record. This keeps the generated wording natural while leaving the case level relation fixed by the construction protocol. A.3 DATA -GENERATION PROMPT

Prompt A.1. Data-generation prompt 

> \textbf{System:} You rewrite one existing line of a user’s message to an assistant so it sounds natural. Never add information or change any identifier, date, fact role, or connecting reference. \textbf{User:} Rewrite the line below as a natural message to an assistant. Line: \{line\} Why it is being said right now: \{situation\} Rules: − Keep every identifier and every date exactly as written. − Invent no names, numbers, places, events, or relationships. − Do not use the words sensitive, private, confidential, or personal. − If the line is about the user, write it in the first person. − If the line quotes a record, do not use I, me, my, we, or our; state what the record says without linking it to the speaker. − Output one or two sentences and nothing else.

Before a case is retained, deterministic checks verify required fields, task constraints, provenance, duplicate content, and the separation between runtime inputs and evaluation annotations. Semantic checks then apply three acceptance conditions. Every isolated session must fail to establish the tested subject-to-service binding. At least two of three transcript-only validators must recover the complete target from the intact history. No validator may recover the complete target after a connecting reference is broken. The broken-reference probe may retain an individual target value because it tests whether the connection is necessary, not whether every sensitive word has disappeared. These checks validate case construction and do not grade reader answers.

## C ANSWER ANNOTATION AND METRIC CALCULATION 

C.1 JUDGES AND ANNOTATION INPUTS 

The answer judges are deepseek-reasoner, gpt-5.6-terra, and gemini-3.6-flash. Each receives the task, recipient, purpose, permitted scope, completion criterion, reference facts, tested service, site, date, and anonymously identified answers. Prompts C.1 and C.2 require judgments supported by the 16 answer itself, without filling gaps from world knowledge or transferring facts between answers. The same response is assessed for disclosure, appropriateness, completion, and helpfulness, but each has a separate criterion. These annotations are unavailable to the ordinary reader. Fields are aggregated before assigning an answer level. Binary fields and individual list items require support from at least two judges. Authorization retains the majority of true, false, or null, with a three way split remaining null. Helpfulness uses the median grade. Procedure C.1 then applies the case thresholds across trials. Voting across judges and aggregating across trials are different operations, neither of which increases the number of cases. Several answers can share a request, so the instructions to judge independently do not establish independent annotation errors. Prior work documents position, verbosity, and self enhancement biases in model based judging (Zheng et al., 2023). Aggregating several judges still requires independent validation. 

Procedure C.1. Answer annotation and aggregation 

> 1. Give each of three judges the task, reference facts, tested relation, and anonymously labelled answers under the same annotation instructions. 2. Obtain semantic fields, appropriateness judgments, task completion, and a helpfulness grade for each answer. 3. Aggregate each field across judges: majority for binary and list fields, majority or null for authorization, and median for helpfulness. 4. Derive A0−A4 from the aggregated fields and registered component IDs. 5. For each complete case, apply the two−of−three A4 and completion rules. The CI count also requires an inappropriate A4 answer in that case. 6. Report answer−level rates, case−level counts and rates, and mean helpfulness using their respective valid denominators.

Appropriateness is judged against task scope. The necessity field is false when no inappropriate content is stated. D.1 EXPERIMENTAL COVERAGE AND COMPLETE CASES 

All conditions use Qwen3.5-9B in non-thinking mode, BF16 inference, temperature 0, and a 320 token output limit. The six frameworks each provide Retrieved memory and All memory. Full history and Task only complete the 14 original views, each with 288 cases and three trials, or 864 answers. Repeated memory trials can vary through the memory pipeline. Direct history trials can have identical prompts, with numerical execution and batching still permitting variation at temperature 0. Trials characterize the recorded execution conditions, not independent users. Analyses and bootstrap resampling keep each case’s trials together. The input supplement has 16 conditions. M1 covers six frameworks and Full history, M2 and M3 cover A-Mem, MemGPT, and history inputs, M4 covers A-Mem and MemGPT, and Itemized history is a presentation control. These runs replay frozen inputs without repeating writing or retrieval. Output filtering separately edits answers from eight original views, namely the six Retrieved memory views, Full history, and Task only. It is not applied to All memory or M1 through M4 outputs. Table 3 covers the two frameworks with all five interventions, while Figure 4 compares the two operations available across six frameworks. The intervention pass returned 13,800 of 13,824 requested annotations. A batch of 24 answers for 

public_validation_f22_wm_04 failed validation when a judge returned several dates in a field requiring one ISO date. Fifteen conditions therefore have 287 complete pairs. M1 utility summaries consequently use 861 paired answers per arm, versus 864 for filtering. Case endpoints require three valid annotations in both arms. Disclosure and TCR apply their respective two of three thresholds. Help. averages median judge grades within cases and then across cases, and refusal uses the corresponding answer indicators. Appendix C defines these metrics. Intervals use 10,000 percentile bootstrap resamples of cases (Efron, 1992), preserving both arms and all trials, with seed 20260816 for supplemental paired analyses. Figure 4 uses reported disclosure intervals, reaggregated refusal and M1 TCR intervals, and output filtering TCR intervals from Table F.3. These are pointwise intervals. A zero bootstrap interval does not establish zero population risk, and an interval spanning zero does not establish equivalence (Lakens, 2017). Two sided exact McNemar tests use discordant case pairs (McNemar, 1947). We use the exact conditional binomial form, whose discreteness can make the test conservative (Fagerland et al., 2013). Holm correction (Holm, 1979) is separate for the six Retrieved memory versus Full history comparisons, 11 primary input comparisons, and four M1 extensions. Itemization is an unadjusted secondary comparison, and M3 strata do not form another Holm family. Output filtering uses separate paired effects and pointwise intervals. Differences expressed in percentage points subtract the two 22 percentage rates, not their relative reduction. These analyses test specified condition pairs rather than every pair of frameworks, so corrected results must remain attached to their original comparison families. The framework analysis is exploratory. RQ2 comparisons were fixed after framework outcomes were available but before evaluating new controls. The input intervention plan was frozen on 27 August 2026 after baseline results, with a documented M2 extraction revision before intervention outputs. The critic protocol was frozen on 29 August before its outputs. These timings describe prospective decisions for individual supplements, not preregistration of the entire benchmark. We retain the original comparison families and predefined M3 strata rather than selecting them from the strongest observed effects.

## F PRIVACY MITIGATIONS 

This appendix defines the five interventions in Table 3 and reports their complete comparisons. Four of them, M1 to M4, act on the input the reader receives and are described in Appendix F.1; the fifth, output filtering, acts on the answer the reader has already given and is described in Appendix F.2. Each is applied alone after memory construction and retrieval have been frozen, so the five are separate interventions rather than a sequential defense. None of them receives the hidden target values or the answer grades; only the critic of output filtering sees the permission metadata of the task. 25 F.1 INPUT INTERVENTIONS 

The four input interventions change only what the reader receives: memory writing and retrieval are not rerun, and the frozen input of each original trial is edited and answered again. The privacy instruction M1 replaces the reader’s system instruction with data minimization guidance that warns that several individually harmless items can jointly form a sensitive relation; it leaves the task and the context unchanged, so availability is identical in both arms, and it is applied to the six frameworks and to Full history. Value sanitization M2 identifies exact spans of names, organizations, places, dates, times, and identifiers and applies the same predefined substitution to every occurrence: names, organizations, and places become indexed placeholders, dates are coarsened, times are removed, and identifiers are masked except for at most four final characters, which may also remove information that the ordinary task needs. Cross-record cue removal M3 removes, without calling a model, the names and identifier cues shared across records. Top-1 retrieval M4 keeps only the first item of each frozen retrieval result; because both retrievers rank every item before cutting the list, this item equals what a rerun with a budget of one would return, assuming for MemGPT, which records no scores, that its return order is its relevance order. M2, M3, and M4 are applied to A-Mem and MemGPT with Retrieved memory as the reference, and M2 and M3 are also applied to history. M2 edits the source messages of Full history, whereas M3 also splits the sessions into separate items, so its history reference is Itemized history, which presents the untouched sessions as items; Itemized history against Full history serves only as a presentation control. Removing the values lowers disclosure only by taking the task with it, whereas removing the links lowers disclosure while the task survives. Tables F.1 to F.1 show this contrast on every input. M2 and M4 leave no input with all three values, and every disclosed case disappears with them, but M2 cuts TCR to between 5.2% and 7.7% while 26.4% to 33.9% of the answers are refusals, and M4 cuts the TCR of A-Mem from 20.1% to 13.2%. M3 keeps all three values in about 72% of inputs and still lowers the disclosed cases on every input, from 60 to 18 on Itemized history, from 40 to 16 on A-Mem, and from 32 to 4 on MemGPT, while TCR moves by less than 2.5 points. Its cost appears in refusal instead, which roughly doubles, plausibly because replacing shared names also hides names the task refers to. Presenting the history as items without removing any cue changes disclosure by only −2.1 points, with an interval that includes zero, so the drop under M3 on history comes from the removed cues rather than from the itemized presentation.

Output filtering passes the answers the reader has already given to a critic, a language model that deletes what the recipient should not receive, and never calls the reader again. We prompt gpt-5.6-terra at medium reasoning effort to act as the critic. For each case, the critic receives the 24 answers of the six Retrieved memory views, Full history, and Task only, in shuffled order with framework, view, and trial hidden, together with the task, its recipient and purpose, the permitted scope, and the names of the necessary, prohibited, and disputed fields, but no target value or reference answer. For each answer it keeps the text, deletes exact spans from it, or, only when deletion would leave nothing useful, replaces it with a fixed refusal, and the three answer judges then grade the edited answers again. Once the permitted scope is known, the relation can be deleted from an answer, because it occupies a few phrases beside the content the task needs. Table F.3 shows that the critic changes 4,373 of the 6,912 answers, 4,210 of them by deleting spans and only 163 by blocking. Table F.3 shows that the deletions leave 5 of the 546 A4 answers of the six frameworks and none of the 198 under Full history, so a single disclosed case remains, a MemGPT case that was not disclosed before editing. Table F.3 shows that Help. does not change in any view, since every interval includes zero. The reader thus gives the content the task needs and adds the relation beside it, the granularity failure of Section 4.2.

The rise in TCR in Table F.3, however, is not a gain in utility. It comes entirely from the 84 cases whose completion criterion excludes unrelated personal details, where deleting details is exactly what completion asks for; on these cases the mean TCR of the six frameworks rises from 21.4% to 54.8%. On the other 204 cases, filtering raises TCR in no view and lowers it in seven of the eight, and the mean of the six frameworks falls from 13.6% to 12.0%, suggesting that deletion also removes some of the content the task requires. The result is also an optimistic estimate, because the critic knows what the recipient may receive, which the reader never does, runs on a different model from the reader, and shares its model with one of the judges. Output filtering therefore measures how much disclosure a filter can remove once each task’s permitted scope is given, not what the reader achieves on its own. 29
