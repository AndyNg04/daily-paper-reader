# UserSWE: Evaluating Coding Agents in Multi-Turn Conversations with Dynamic Users 

Zhan-Yu Wu 1, ∗, Ji Luo 1, ∗, Alyssa Wu 1, Junjielong Xu 1,

Richeng Xuan 1, Zhichao Hu 1,† , Chongming Gao , Xinting Hu †1Tencent Hunyuan 

## Abstract 

As coding agents become more capable, developers increasingly use them to fix bugs through multi-turn interactions. Existing benchmarks do not adequately cover this scenario. Most present a complete issue report in a single turn without interaction. Their evaluation can produce both false positives and false negatives, accepting incorrect patches or rejecting correct ones. We introduce UserSWE for evaluating coding agents’ ability to fix repository-level bugs through multi-turn interactions with dynamic users and execution-grounded verdicts at every turn. Its construction pipeline turns reposi-tory history and existing single-turn benchmarks into multi-turn tasks. At each turn, information pools constrain what the simulated user can reveal, while a persona chain sampled from a transition model calibrated on 20,859 development sessions governs how it speaks. Tests run after every turn, and a pair of agents from different model families writes and gates each verdict, using test results as primary evidence and model judgment only for aspects the tests cannot resolve. We evaluate eleven agents on 72 tasks from 42 repositories and find that agent rankings change with the interaction budget. Claude Fable 5.1 resolves the most tasks in one turn, GPT-6-Astra resolves the most by the eighth turn, and Claude Opus 5 leads at most intermediate budgets. These results indicate that single-turn performance is insufficient to characterize interactive coding ability.

However, prevailing benchmarks do not measure how well an agent works in this scenario for two main reasons. One is that most use a single-turn setup, handing the agent everything at once and asking for a correct patch in return, so the agent is never put in the conversation where the work actually happens. The few that do run several turns stay static, releasing the information in a written order or phrasing every turn in one fixed conversational style, which leaves the agent talking to an unresponsive mechanism and not to a simulation of a developer. Figure 1 sets a static user beside a dynamic one on the same task. The other concerns multi-turn judging, where every intermediate turn calls for independent assessment, but standard tests can only provide factual execution evidence, and unrestricted LLM judges are prone to making inferences beyond what results actually demonstrate. For both reasons, a benchmark that measures coding agents’ abilities in conversation is still missing. To address this, we propose UserSWE, which settles where the tasks come from, where the turns come from, and how each turn is judged. The first is a construction pipeline that produces multi-turn tasks along two routes. One route mines a repository’s own history for paired issues that a maintainer publicly recorded as linked. The other takes an instance of an existing single-turn benchmark and stages it as a conversation. As we continue running the pipeline along these two routes, it consistently generates new and up-to-date tasks. The second is a method for simulating the user across the turns of a conversation. We calculate a persona transition matrix on 20,859 real development sessions from an internally deployed commercial coding assistant, and we write each turn’s utterance from that matrix together with the information pools of the task, so the persona an agent meets becomes dynamic as the session goes on. For each task we draw the whole chain in advance, which ensures any agent on the same task meets the same user. The third is an evaluation framework , which enables the coding agent to operate under constraints, with dual agents judging its generated outputs based on evidence. The framework sets rules that prevent coding agents from receiving credit beyond their demonstrated ability. Based on tests run after every turn, a Judge from one family writes the verdict, and a Reviewer from another family clears it before it counts. We select 72 tasks from the pipeline as UserSWE and evaluate agents on it. The evaluation on UserSWE reveals behavior that a single-turn evaluation cannot show. Claude Fable 5.1 resolves the most tasks within a single turn, 31.9%, and still finishes second on the length-discounted pass rate, behind Claude Opus 5, which reaches a similar place in fewer turns, 2.99 against 3.14. GPT-6-Astra resolves the most tasks of any agent by the eighth turn, 81.9%, and places fourth once the turns it spends getting there are discounted. In this paper, we make the following contributions. (1) A construction pipeline. It builds multi-turn tasks from repository evidence and existing single-turn benchmarks. (2) A multi-turn user simulation. 

We introduce a user simulator with dynamic personas grounded in real development conversations. (3) An evaluation framework. We propose a dual-agent judging evaluation framework complemented by a suite of supporting mechanisms, such as equivalent pass testing. UserSWE will be released along with the evaluation framework.

Multi-turn benchmarks and simulated users. Multi-turn evaluations must specify both what the user reveals and how the user speaks. SWE-Interact releases a task’s requirements one at a time and uses a fixed, terse senior-developer persona derived from SWE-chat (Raghavendra et al., 2026; Baumann et al., 2026), while SWE-Together reconstructs a task-specific simulator from a recorded session and triggers utterances according to the live trajectory (Wu et al., 2026). These approaches condition information release on the trajectory but do not vary the user’s voice according to a measured distribution of developer personas. More broadly, simulated users can diverge from real developers, and persona choice can substantially change measured performance (Seshadri et al., 2026; Zhou et al., 2026; Truong et al., 2025). ## 4 UserSWE 

We introduce UserSWE, which evaluates agents on issue fixing inside a multi-turn conversation and so measures coding ability more completely than a one-shot format can. Where Section 3 is settled in a single exchange, an agent here works on the issue over several turns, each turn answering what the user has just asked for, and we check the fail-to-pass and the pass-to-pass set after every one of those turns. Turning both sets green in as few turns as possible is what UserSWE credits as strength at resolving code issues interactively. Figure 2 lays out in order where the tasks come from, how the multi-turn form is designed, and how each turn is judged.

Each side has a merged fix with tests, giving the task two related acceptance points. The second route takes tasks from published single-turn benchmarks, preserving their repository state, gold patch, tests and original acceptance point while changing how their information is released across a multi-turn conversation. 4.2 Multi-turn Interaction 

Section 4.1 fixes what the simulated user may say, but not which item should be selected at each turn or the voice in which it should be expressed. We handle these questions separately, first selecting the content through a release policy and then rendering it through a conversational persona model calibrated on real development sessions. After each turn, the simulated user selects guidance from the information pool according to the agent’s response and the canonical test results. The information selection process follows a fixed priority hierarchy designed to mirror the logic of natural developer interactions. If the agent poses a direct question, the simulated user responds with a direct answer. Otherwise, it selects content in descending order of priority: the most severe user-observable blocking failure, an unaddressed core business boundary, or a secondary edge case. This hierarchy governs what information the user simulator releases at the current turn. Once the content is selected, the framework must decide how to express it. The expression of the developer varies between people and between turns of the same session. Its two common components align with the two kinds of content in the information pool, namely how a developer describes what was observed and whether they offer a view of the cause . We therefore factor the simulated user along two axes. Clarity records whether the symptom is stated precisely or vaguely, and veracity records whether the user offers no view, a correct one, an off-target one, or a wrong one. We do not assume the eight cells occur uniformly. From 20,859 real development sessions from an internally deployed commercial coding assistant, we measure the opening persona and its turn-to-turn transitions. Of these sessions, 13,530 change code, and the eight cells account for 98.65% of them, with 52.98% opening on a clear symptom and no view of the cause. The transitions form a family of matrices conditioned on the opening persona rather than one global matrix. We pseudorandomly draw a complete persona chain for each task in advance so that different agents on the same task face the same changes in the user. The selected content is rendered in the persona assigned to that turn. Appendix B gives all eight opening-conditioned transition matrices and the persona design. 4.3 Evaluation 

A multi-turn evaluation framework entails two dimensions of freedom, each causing evaluation misjudg-ments when improperly calibrated. The degree of freedom allowed by the framework, when set too loose or too tight, renders the evaluation scores unreliable. The degree of freedom granted to the agent, when set too loose or too tight, prevents it from demonstrating its true capabilities. Our evaluation framework for UserSWE addresses these two dimensions separately. 

Freedom for the agent. Deciding whether a solution is correct can fail in either direction. Tests are written around the maintainer’s own fix, so they may reject a patch that implements the behavior without converging on the interface of the gold patch, producing a false negative. In a neighboring setting this is measurable, where rule-based evaluation of agent trajectories recovers only 55.9% of the runs an expert calls successful, because the check demands an exact match and turns away trajectories that differ in ways that do not matter (L ` u et al., 2025). At the other end, tests weak enough to pass a patch that fixed nothing give a false positive (Xue et al., 2026). Moving the primary signal off test execution and onto 5a model’s reading of whether the semantics are satisfied (Wu et al., 2026) widens the false positives. Admitting only the verbatim passing of the shipped tests (Jimenez et al., 2024; Deng et al., 2026) widens the false negatives. In UserSWE the framework may, on the basis of what the agent actually implemented, propose a change to a test and count a pass on the genuinely modified test as an equivalent pass , which is E QUAL PASS in Algorithm 1. How much capability it brings to bear is likewise not capped, since a setting that gives no tools and asks for a patch from the issue body alone cannot measure the difference between scaffolds (Jimenez et al., 2024; Yang et al., 2024). We block its access to the assets that would settle the task for it, and restrict outside lookup where that is necessary. 

Freedom for the instrument. The freedom given to the simulated user and the Judge does not decide what is correct. It decides whether the instrument has itself become a variable. A simulated user left to improvise drifts with whichever model it runs on, so one task stops being the same task across two evaluations (Raghavendra et al., 2026). A simulated user whose every line is written in advance is not a user. We freeze the agenda and not the wording. Which persona holds at which turn and which facts may be said are fixed by the persona chain and the information pools, and the opening request is fixed outright so that every agent starts from the same point. Which fact to raise at a later turn and how to phrase it is left to the simulated user. The Judge side is the same problem seen from the other end. A language model scores its own family’s output too highly (Zheng et al., 2023; Wataoka et al., 2024), and a panel drawn from disjoint families brings that bias down (Verga et al., 2024), so we chain two families. The Judge writes a verdict and a Reviewer from a different family may rewrite it before it takes effect, with the two swapped between tasks. This is an inline gate rather than a post-hoc audit, and every judgment the framework issues has passed through both. Both halves rest on the same thing. A verdict counts only where the tests have been run and have said so, since the outcome the loop returns is the outcome of executing them, and a model’s reading enters where the tests are silent rather than where they disagree with it. 

Metrics. A multi-turn setting admits a quantity the one-shot format has no room for, namely how much of the turn budget an agent had left when it succeeded. Beyond the plain resolve rate we therefore report the Length-Discounted Pass Rate (LDPR), which is counted as LDPR =

((K + 1 − k)/K tests all pass, 0 otherwise, (2) where k is the weighted number of turns used; a turn without a code edit counts as half a turn. Agents that resolve a task in fewer conversational turns receive higher scores, while those that fail to complete the task within the predefined maximum turn limit are assigned a score of zero. 5.2.2 Dynamic conversational persona 

Most existing benchmarks model the simulated user as a static persona with both clear expression and correct causal views (Raghavendra et al., 2026; Baumann et al., 2026). That profile opens only 19.03% of the 13,530 observed sessions, and holding it for a whole session is rarer still: 0.72% of sessions stay clear and correct for five consecutive turns on the same issue and 0.24% do so for eight. Even among the sessions that actually run that long, the shares are 2.81% and 1.86%. We compare a reference arm that remains clear and correct at every turn with the persona chain. Both arms run the 50 single-issue tasks, which fit a five-turn budget and so isolate the persona from the cascade’s issue-to-issue carryover, and each comparison uses the same task and agent and changes only the user trajectory. Table 4 reports LDPR and mean weighted turns k. Three of the four agents move the same way, scoring higher and finishing sooner under the clear-and-correct user, and the size of the shift varies widely between them, from 0.020 to 0.076 in LDPR. The largest is GPT-6-Astra, whose LDPR increases from 0.580 to 0.656 while k decreases from 2.92 to 2.54, and Kimi-K3 moves the other way. How much an agent depends on precise phrasing is itself a property of the agent, and it shows across all 72 tasks and all eleven agents. Splitting the full set by whether the opening states the symptom precisely or as an impression, the gap between the two halves runs from 0.268 for Claude Fable 5.1 down to −0.088 for DeepSeek-v4.1-Flash (Appendix F). An idealized user therefore reports a benchmark easier than the one most users present, and it flatters some agents more than others.

## 6 Limitations 

UserSWE has three limitations. (1) Scale. Multi-turn evaluation runs a full session and reruns tests after every turn, making it more expensive than scoring one patch per task and limiting the released set to 72 tasks. Table 15 reports detailed per-task costs. (2) Horizon. UserSWE covers one maintenance episode over one or two issues, from a base commit to a fixed set of acceptance points. It does not cover longer-term work such as building a repository from scratch, which remains a direction for future extensions. (3) Session logs. The user model uses opening distributions and turn-to-turn transitions measured from 20,859 sessions collected from an internally deployed commercial coding assistant. Future versions could incorporate additional signals about task types and request phrasing. 

## 7 Conclusion 

We present UserSWE, a benchmark for evaluating coding agents in multi-turn conversations with dynamic users. We contribute a construction pipeline that builds multi-turn tasks from repository history and existing benchmarks, a user simulator with dynamic personas grounded in real development sessions, and an evaluation framework that anchors cross-family judging and review to executed tests. Together, these components produce UserSWE, which we use to evaluate eleven agents on 72 tasks and uncover behaviors that single-turn evaluation cannot reveal.

We used generative AI tools to polish the manuscript and as necessary components of the experimen-tal framework, as described in the paper. The authors reviewed all AI-assisted work and take full responsibility for the final content and reported results.

## A How a task is built 

The released benchmark contains 22 cascades mined from repository history and 50 single-issue tasks converted from published benchmarks. This appendix follows both routes from source material to a task package. 

A.1 Two source routes 

The cascade route searches repository text for two signals. Reveal signals occur when a later issue says it was exposed while investigating or fixing an earlier issue. Dependency signals occur in pull-request text that states one change is stacked on, depends on or follows another. A pair is retained in the stated order only when both issues have merged fixes and the later record points to the earlier work. Of the 22 mined cascades, six come from reveal signals and sixteen from dependency signals. The separability check in Section A.4, rather than the phrase category, establishes that the fixes must land in a fixed order. The conversion route starts from a published single-turn task. It retains that task’s repository state, gold patch, test lists and container image, and changes only how the issue is presented across turns. 

A.2 From source to task package 

For a mined cascade, the pipeline retrieves both merged fixes, builds the grading image and tests, maps acceptance points to the two phases, and creates one task package and information pool. For a converted task, it preserves the upstream repository state, image and test verdicts while reorganizing the user-visible report into turn material. Both routes use the same admission checks below. 11 A.3 Information pools 

Each task has one information-pool file. The simulator selects from the file before applying a persona’s wording.        

> Field Content clear symptom one reproducible user-visible observation and a broad request vague symptom the same problem as an impression, without implementation identi-fiers correct idea a low-confidence direction consistent with the cause, not a repair step wrong idea a plausible direction that points somewhere real but is not causal follow-up set the same four fields for the second issue, phrased as appearing after the first fix phase map the acceptance points assigned to each phase

Because pool construction can inspect the gold patch, it applies two leak guards. Gold-introduced identifiers are forbidden and checked after generation. B.4 Human validation 

The evaluation framework can pause before any simulated user turn is sent. At such a breakpoint a human reads the utterance the simulator is about to send and checks that a user experiencing the issue could plausibly say it, and that it stays within the information pool and the sampled persona. A turn must also react to what the agent has just done while respecting the per-turn information budget, so the check covers whether it volunteers the cause, the test names or the shape of the fix. Every task in the released set passed this review at least once. When a turn fails the check we do not edit that sentence. We change what produced it: the generation rule, the utterance-writing prompt or the information pool, and then regenerate; the regenerated turns go through the breakpoints again. A single such change applies to every turn generated afterwards, so the review effort does not grow with the size of the set. Review at these breakpoints required 50 human-hours in total and no repository-specific expertise. 

## C Evaluation framework 

The framework separates environment controls, the Judge, the Reviewer and a post-run audit. 

C.1 Environment controls Internal assets. The agent sees the agent-facing task statement and its workspace, but not the source issue or pull-request records, gold patch, fail-to-pass tests, acceptance list, phase map, scorecard, Judge– Reviewer records or other evaluation metadata. These assets are mounted outside the workspace, and tool controls block direct and indirect access to them. 

External retrieval. General technical documentation is allowed. The agent may not retrieve this task’s issues, pull requests, commits, releases, other source versions or ready-made fixes from code hosts, package registries, mirrors or caches. External lookups are recorded. A violation is terminal only when task-specific protected material is returned and used. 

C.2 Judge 

The framework sends the Judge the canonical user message, agent response, external-lookup and private-access audits, canonical test window, workspace fingerprints, previous equivalence ruling, remaining turn budget and recent user messages. It returns a candidate state, item-level verdicts, supporting evidence and the next user message. Table 10 gives the action associated with each state. Table 10: Judge states.                                 

> State Name Meaning Framework action
> Uunchanged The agent asks or dis-cusses without changing the workspace. Return the user’s answer and con-tinue; add 0.5 to the weighted turn count.
> Fcontinue At least one acceptance item re-mains unsatisfied. Send the selected guidance and begin the next turn.
> Cframework step Automated items pass, but an-other framework step remains. Run that step and return its evidence to the Judge.

C.4 Audit rubric 

We maintain the rubric by reading trajectories after each evaluation batch and adding rules for newly observed failure modes. This requires about one human-day per batch. On the same tasks and the same 55 pairs, LDPR separates 17 pairs, against 5 for whether a task is resolved on the first turn and 5 for whether it is resolved at all. Resolution over the full budget carries the highest base rate of the three at 71.8% and still separates the fewest pairs, so the discount for length is what carries the additional signal.
