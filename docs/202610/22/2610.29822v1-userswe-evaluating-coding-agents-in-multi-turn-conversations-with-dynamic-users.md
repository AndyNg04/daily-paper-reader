## 摘要
随着编程智能体能力不断增强，开发者越来越多地通过多轮交互使用它们修复错误。现有基准未能充分覆盖这一场景：大多数基准在单轮中提供完整的问题报告，不包含交互过程。此类评测可能产生假阳性和假阴性，既可能接受错误补丁，也可能拒绝正确补丁。我们提出 UserSWE，用于评测编程智能体通过与动态用户进行多轮交互来修复仓库级错误的能力，并在每一轮基于执行结果作出判定。其构建流程将代码仓库历史记录和现有单轮基准转化为多轮任务。在每一轮中，信息池限制模拟用户能够透露的内容；同时，从基于 20,859 次开发会话校准的转移模型中采样得到的人设链决定其表达方式。每轮交互后都会运行测试，并由来自不同模型家族的两个智能体共同生成并审核判定结果：以测试结果作为主要依据，仅在测试无法判定的方面依赖模型判断。我们在来自 42 个代码仓库的 72 项任务上评测了 11 个智能体，发现智能体排名会随交互轮数上限而变化。Claude Fable 5.1 在一轮交互中解决的任务最多，GPT-6-Astra 在第八轮前解决的任务最多，而 Claude Opus 5 在大多数中间轮数上限下表现领先。这些结果表明，单轮表现不足以全面刻画智能体的交互式编程能力。

## Abstract
As coding agents become more capable, developers increasingly use them to fix bugs through multi-turn interactions. Existing benchmarks do not adequately cover this scenario. Most present a complete issue report in a single turn without interaction. Their evaluation can produce both false positives and false negatives, accepting incorrect patches or rejecting correct ones. We introduce UserSWE for evaluating coding agents' ability to fix repository-level bugs through multi-turn interactions with dynamic users and execution-grounded verdicts at every turn. Its construction pipeline turns repository history and existing single-turn benchmarks into multi-turn tasks. At each turn, information pools constrain what the simulated user can reveal, while a persona chain sampled from a transition model calibrated on 20,859 development sessions governs how it speaks. Tests run after every turn, and a pair of agents from different model families writes and gates each verdict, using test results as primary evidence and model judgment only for aspects the tests cannot resolve. We evaluate eleven agents on 72 tasks from 42 repositories and find that agent rankings change with the interaction budget. Claude Fable 5.1 resolves the most tasks in one turn, GPT-6-Astra resolves the most by the eighth turn, and Claude Opus 5 leads at most intermediate budgets. These results indicate that single-turn performance is insufficient to characterize interactive coding ability.

## 1. 核心问题与整体含义

### 研究背景与动机
- 真实的编程智能体调试过程通常是**多轮、需求不完整且持续变化的交互**：用户先报告现象，随后根据智能体的修改补充要求、澄清边界，甚至提出错误的原因判断。
- 现有评测存在两方面不足：
  1. **交互不真实**：多数基准一次性给出完整问题；部分多轮基准虽然分步提供信息，但用户风格固定，难以模拟真实开发者。
  2. **判定不可靠**：严格绑定标准补丁接口的测试可能拒绝功能正确的实现，形成假阴性；不充分的测试或过度自由的模型裁判可能接受错误实现，形成假阳性。

### 论文的核心目标
UserSWE 希望同时解决三个问题：**任务从哪里来、用户如何逐轮互动、每轮结果如何可靠判定**。

其整体含义是：编程智能体的能力不仅是“一次生成正确补丁”，还包括在模糊、错误或逐步揭示的信息下澄清需求、修正方向，并以较少交互完成修复。因此，评测应观察**成功率随交互预算变化的曲线**，而不只报告单轮或最终成功率。

## 2. 方法论：任务构建、动态用户与执行驱动评测

### 2.1 任务构建：两条来源路线

- **仓库历史挖掘**
  - 寻找维护者明确关联的两个 issue，例如后一个问题在修复前一个问题时暴露，或后一个 PR 明确依赖前一个 PR。
  - 两个问题都必须具有已合并的修复及测试。
  - 通过中间状态检查确认：应用第一阶段修复后，第一阶段验收通过，第二阶段仍未解决，且已有功能不回归。

- **已有单轮基准转换**
  - 保留原任务的基础代码、标准补丁、测试和容器环境。
  - 将一次性问题说明拆分为多轮可释放的信息。

### 2.2 信息池：限制“用户知道什么”

每项任务预先构建并冻结信息池，包括：

- 清晰和模糊两种症状描述；
- 与真实原因一致的低置信度猜测；
- 看似合理但错误的原因猜测；
- 双问题任务的后续信息与阶段验收映射。

信息池构建可以参考标准补丁，但会检查并禁止泄露标准补丁新增的标识符；双阶段任务还进行跨阶段信息泄露检查。

每轮内容按固定优先级选择：

1. 优先回答智能体的直接问题；
2. 提供最严重的用户可观察阻塞故障；
3. 补充尚未满足的核心业务边界；
4. 最后补充次要边缘情况。

**关键设计是将“允许透露什么”“本轮透露什么”“如何表达”分开控制。**

### 2.3 动态人设：控制“用户怎么说”

作者以两个维度组成八种人设：

| 维度 | 设置 |
|---|---|
| 症状清晰度 | 清晰、模糊 |
| 原因判断 | 不提供原因、正确猜测、偏离方向的猜测、坚持错误原因 |

其中，两种错误原因人设的区别主要体现在后续互动：

- **偏离方向**：智能体给出合理的代码或行为解释后即可放弃；
- **坚持错误原因**：需要执行测试、复现结果或明确代码事实才能改变判断。

人设分布与转移规律来自内部商业编程助手的 **20,859 次开发会话**：

- 排除没有代码修改的会话后剩余 **13,530 次**；
- 八种人设覆盖其中 **98.65%** 的开场；
- 最常见的是“清晰症状、不提供原因”，占 **52.98%**。

框架不是使用单一转移矩阵，而是**根据开场人设选择对应的转移矩阵**，提前采样并冻结完整人设链。不同智能体在同一任务上使用相同链，但具体后续内容仍响应各自的执行结果。

> 人设类别和交互规则由作者设计，真实会话用于校准频率与转移概率，并非自动学习完整的用户行为模型。

### 2.4 每轮测试与跨模型家族审核

每轮智能体操作后：

1. 检查工作区变化并运行规范测试；
2. **Judge** 根据执行证据生成逐项判定及下一轮用户消息；
3. 如有必要，执行“等价通过”测试；
4. 来自另一模型家族的 **Reviewer** 检查判定、证据、信息释放和人设执行，可整体重写结果；
5. 继续交互，或在全部验收通过后停止。

主要测试包括：

- **Fail-to-pass**：基础代码应失败，修复后应通过；
- **Pass-to-pass**：基础代码和修复后均应通过，防止回归。

评测模型为 **GPT-5.6-Sol / Codex** 与 **Claude Opus 5 / Claude Code**，并在任务间交换 Judge 和 Reviewer 角色。审核不可用时，框架不会直接接受未经审核的判定。

### 2.5 等价通过：避免被标准实现形式绑死

若候选补丁实现了正确行为，但因辅助函数名称或内部结构不同而无法通过原测试，框架允许提出针对性的测试改写。

改写必须同时满足：

- 在候选补丁上通过；
- 不破坏回归测试；
- 在未修复的基础代码上仍失败；
- Reviewer 确认保留原有行为要求。

因此，这不是用模型判断直接覆盖失败测试，而是**以新的执行证据确认行为等价性**。不过，行为是否完整保留，仍包含模型判断。

### 2.6 评价指标

除解决率外，论文提出**长度折扣通过率 LDPR**：

- 成功任务得分为“最大轮数加一，减去实际加权轮数，再除以最大轮数”；
- 失败任务记为零；
- 修改代码的一轮计 1，未修改代码的讨论或澄清计 0.5。

该指标奖励更早完成任务的智能体，但它衡量的是交互效率，**不直接衡量 token、费用或实际运行时间**。

## 5. 实验数量与充分性

### 5.1 大致实验规模

按“智能体—任务会话”粗略计算：

### 5.2 公平性与充分性评价

**较为充分之处：**
- 同一任务为所有智能体提供相同信息池、开场和预采样人设链；
- 使用相同验收要求，并阻止访问隐藏测试、标准补丁及任务相关现成答案；
- 每轮都有执行证据，且跨模型审核角色轮换；
- 提供配对统计检验，而非只看排行榜上的点估计；
- 人设消融使用相同任务和智能体，比单纯比较不同任务组更有说服力。

**仍不充分之处：**
- 72 项任务、其中仅 22 项级联任务，样本量有限；
- 人设消融只覆盖 4 个智能体和单问题场景；
- 缺少多随机种子、多人设链重复运行，尚不能充分衡量轨迹随机性；
- 缺少与真实用户协作结果的直接对照；
- 缺少用人工金标准量化“双裁判相对单裁判”的最终误判率改善；
- 不同运行框架与模型绑定，无法将差异完全归因于模型本身。

**判断：实验足以展示“排名会随交互预算改变”这一现象，但尚不足以支持稳定、普适的精细排名或证明模拟用户充分代表真实开发者。**

## 6. 主要结论与发现

### 6.1 领先者取决于交互预算

| 智能体 | 首轮解决率 | 各任务完整预算内解决率 | LDPR |
|---|---:|---:|---:|
| Claude Opus 5 | 25.0% | 80.6% | **0.640** |
| Claude Fable 5.1 | **31.9%** | 76.4% | 0.593 |
| Grok-4.6 | 18.1% | 80.6% | 0.569 |
| GPT-6-Astra | 12.5% | **81.9%** | 0.561 |

- **Claude Fable 5.1** 首轮最好；
- **Claude Opus 5** 在多数中间预算领先，且 LDPR 最高；
- **GPT-6-Astra** 最终解决最多任务，但达到成功所需轮次更多，LDPR 仅列第四。
- 四个领先智能体在八种预算下出现六种排序，三个智能体曾居首。

需注意：表中的最终结果汇总了单问题最多 5 轮、双问题最多 8 轮的不同预算，并非全部任务均运行 8 轮。

### 6.2 理想化用户会改变评测结果

动态人设相较始终清晰且正确的用户：

- Claude Opus 5 的 LDPR 下降 **0.020**；
- GPT-6-Astra 下降 **0.076**；
- DeepSeek-v4.1-Flash 下降 **0.066**；
- Kimi-K3 反而上升 **0.042**。

说明用户风格对不同智能体的影响不一致，静态理想用户可能不均衡地抬高部分系统的成绩。Kimi-K3 的反向结果也提示，不能简单断言动态人设必然让所有智能体更困难。

### 6.3 Reviewer 和等价通过确实参与了评测

- Reviewer 重写了 **40.9%** 的逐轮判定；
- 相关异议中 **87.4%** 被归为重大或严重问题；
- 约 **14.6%** 的“智能体—任务”运行提出过等价请求；
- 请求中 **51.2%** 获准。

但重写可能只改变下一轮用户消息或证据记录，因此 **40.9% 不能解释为原始成功判定的错误率**。

### 6.4 LDPR 提供额外区分信号

在 55 对智能体比较中，经多重比较校正：

- LDPR 区分出 **17 对**；
- 首轮是否成功仅区分出 **5 对**；
- 最终是否成功也仅区分出 **5 对**。

这支持将交互效率纳入评测，但不代表所有相邻排名都具有统计显著性。

## 7. 主要优点

- **问题定义贴近实际使用**：将需求逐步明确、用户误诊和反馈后的修复纳入评测。
- **任务、信息和表达解耦**：信息池控制泄露，人设链控制表达变化，反馈选择仍能响应智能体行为。
- **具有真实行为统计基础**：人设频率与转移来自实际开发会话，而非均匀或任意设定。
- **执行证据优先**：避免单纯依赖语言模型阅读补丁给出结论。
- **兼顾行为等价性**：允许正确但形式不同的实现通过，且设置基础代码反例和回归测试门槛。
- **可比较性较好**：固定任务与人设轨迹，配合任务内配对分析。
- **披露较完整**：给出成本、置信区间、审核重写、等价拒绝原因及案例，而不只报告最终榜单。

## 8. 不足与局限

### 8.1 任务规模与应用边界有限
- 仅覆盖一至两个问题的维护过程，不能代表从零构建项目、长期架构演进或多人协作。
- 级联任务通常需要先完成第一阶段再获知第二阶段信息，其首轮成功率天然受任务结构限制，不能直接等同于传统完整说明下的单轮能力。
- 现有公开基准转换任务仍可能有训练污染；持续更新流程本身不能证明已排除记忆效应。

### 8.2 用户模拟的外部有效性尚待验证
- 数据来自单一内部商业助手，用户群体和工作习惯未必具有代表性。
- 人设由模型标注，每类仅人工检查十次会话，缺少更系统的标注一致性评估。
- 部分稀有人设开场仅有数十个样本，转移概率可能不稳定。
- 开场条件化的一阶转移模型难以刻画更长历史、情绪和任务难度的影响。
- 删除结束会话转移并重新归一化，没有模拟用户因挫败而退出的真实情况。

### 8.3 裁判机制仍存在偏差风险
- Reviewer 能重写 Judge，但本身仍可能出错；跨模型家族并不等于无偏。
- 两类 Reviewer 的重写率差异很大，分别为 **62.4%** 和 **25.4%**，说明判定结果可能受配置影响。
- 两个裁判模型本身也是被评测对象，角色轮换可以缓解、但不能证明完全消除家族偏好。
- 等价测试可能遗漏原有行为要求，“基础代码失败、候选通过”并不足以单独证明完整语义等价。

### 8.4 指标与统计解释需要谨慎
- LDPR 将无代码修改的澄清计为半轮，这是一种人为效用设定，不一定对应真实用户负担。
- LDPR 不惩罚单轮内的大量工具调用或高费用，无法独立衡量经济效率。
- 头部模型置信区间较宽，细小领先不应被解释为稳定优势。
- 清晰与模糊开场的分组包含不同任务，相关结果是观察性分析，不能直接作为清晰度影响的因果估计。

### 8.5 成本与复现门槛较高
- 每轮测试、双模型审核及人工规则维护，使大规模复测较昂贵。
- 原始用户日志不公开，外部研究者只能复用聚合统计，难以完整复核标注与分布。
- 论文表述为“将发布”基准及框架，仅依据提供文本无法确认实际开放状态。

**总体评价：UserSWE 的核心价值在于，把“能否修复代码”扩展为“能否在真实感更强的交互中高效修复代码”，并提供执行驱动的逐轮评测框架。其结果较有力地说明了单轮排名的局限，但真实用户有效性、裁判可靠性及更大规模的排名稳定性仍需进一步验证。**
