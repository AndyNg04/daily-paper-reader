ABSTRACT 

Smartphone GUI agents complete tasks in mobile apps by repeatedly reading the screen and asking a model for the next action. Mobile neural processing units (NPUs) enable local execution, keep-ing screen contents on the phone, but model latency accumulates with every action. Hybrid linear-attention models reduce memory requirements, yet reusing their recurrent state requires checkpoints at the appropriate input positions. Agent requests retain instructions but rewrite recent history, so checkpoint policies designed for chat continuation can miss reusable prefixes. Retaining rollback states for speculative decoding can also move prompt processing off the NPU’s matrix unit, adding overhead that outweighs decoding savings on short action outputs. A loaded model can further hold the NPU awake between tasks. We present Tandem, a runtime for hybrid GUI agents on mobile NPUs. Tandem saves recurrent state where consecutive prompts diverge, allowing later requests to reuse previously processed context. It keeps most prefill on the matrix unit and produces rollback states through a short per-token tail. Its verification kernel reads each weight block once for all pro-posed tokens. Between request bursts, Tandem releases NPU power votes without unloading the model. We implement Tandem in llama.cpp and evaluate it on recorded agent interactions across two Snapdragon generations. On a Snapdragon 8 Elite, Tandem reduces per-step latency by 30% for text-based screen descriptions and 16% for screenshots relative to llama.cpp’s fastest NPU configura-tion, reduces energy per text step by 33%, and lowers standby power with the model loaded from 0.76 to 0.22 W. The project is available at https://github.com/flyingdoog/tandem .

1 Introduction 

GUI agents let users operate phone apps through natural-language instructions. A request to change an app setting, for example, may require opening a menu, locating an option and con-firming the change. At each step, the agent reads the screen and asks a model to choose a tap, scroll or text input (Wen et al., 2024; 2025; Liu et al., 2024; Qin et al., 2025). It then waits for the app to respond before deciding what to do next. Model latency accumulates throughout the task, while pauses between requests and tasks also make idle power relevant. Running the model on the phone keeps screen contents local and removes a network round trip from each step; mobile neural processing units (NPUs) provide the compute for this execution (Xu et al., 2025; Yin et al., 2026). Hybrid linear-attention models make longer interactions possible within a phone’s memory bud-get. Models such as Qwen3.5-4B replace most attention layers with recurrent layers that summarize earlier input in a fixed-size state (Qwen Team, 2026; Yang et al., 2025). This slows memory growth as prompts lengthen. Efficient agent execution requires two distinct uses of recurrent state: reusable checkpoints across changing requests and short-lived rollback states for speculative generation within a request. Checkpoint placement and NPU execution determine the cost of maintaining both.

2 Background  

> 2.1 The agent step

The agent executes a task as an episode of screen observations and actions. It reads Android’s accessibility tree, asks the model for an action, executes it and waits for the app to update. Each action determines the next screen, so model requests form a sequential chain. Model latency ac-cumulates across steps, while app interaction and pauses between tasks leave intervals with no inference work. Each request contains fixed rules, the task and foreground app, recent actions and a text description of the on-screen controls. The model returns a short JSON response specifying an action, such as tapping an indexed control, entering text or finishing the task. When accessibility data is sparse, the app also attaches a screenshot. Our policy is Qwen3.5-4B (Qwen Team, 2026) fine-tuned with LoRA (Hu et al., 2022) on public GUI-agent data and demonstrations recorded on the phone. Between steps, the app rebuilds this message from the current observation and the last three ac-tions. For example, after opening a settings page, the next request carries the new controls and a record of the preceding action, while retaining the rules and task. Once the history window is full, its oldest entry disappears on the next step. The resulting prompts overlap but also replace text from the previous prompt. Serving a request has two phases. Prefill processes the input tokens to build the model’s state; 

decode produces the action one token at a time. Reusing state from a shared prompt prefix skips part of prefill. Speculative decoding lets a lightweight drafter propose tokens that the full model verifies together, reducing decode passes when several proposals are accepted.

Screenshots add a vision encoder that converts pixels into feature vectors. These vectors form image tokens in the language model’s input, adding prefill work before action generation. Reducing the image-token budget changes both this work and the visual information available to the policy.  

> 2.2 Hybrid linear-attention models

Hybrid models combine two ways of retaining context. Attention layers keep separate entries for past tokens in a key-value (KV) cache. Recurrent layers repeatedly update one compact state, folding each new token into the information already stored. A checkpoint is a copy of this state saved at a particular token position so that execution can resume there later. Consider two prompts that share their first 350 tokens and differ afterward. Once the first prompt has been processed, its KV cache can be truncated to 350 entries. Its final recurrent state, however, also contains the later tokens; the server needs the state saved after token 350 to resume there. If its latest usable copy is at token 300, it reprocesses 50 shared tokens before reaching the new suffix. A hybrid model performs both operations: it restores the recurrent checkpoint and aligns the attention cache to that position. Qwen3.5-4B has 32 layers (Qwen Team, 2026). Every fourth layer is a full-attention layer, and the other 24 are Gated DeltaNet layers (Yang et al., 2025). Each of the 32 heads of a Gated DeltaNet layer keeps a matrix state 𝑆 and updates it once per token,

The model’s multi-token prediction (MTP) head (Gloeckle et al., 2024) provides the lightweight drafter. It uses information already computed by the main model to propose the next token, then repeats this process to form a short sequence. The main model checks the sequence in one batched pass (Leviathan et al., 2023). Accepting several proposals can replace several ordinary decode passes. If a proposal is rejected, execution resumes from the last accepted token, requiring both the attention cache and the recurrent state at that position.  

> 2.3 The Hexagon NPU

The Hexagon NPU provides two execution paths used by the model: a matrix unit (HMX) for processing many token vectors together and vector units (HVX) for smaller operations. On the Snapdragon 8 Elite, Hexagon v79 has six hardware threads with 1024-bit HVX units, an HMX unit for fp16 tiles and 8 MB of tightly coupled memory (VTCM). This local memory holds data close to the compute units; DMA engines transfer larger blocks between it and DRAM. Model weights exceed the local capacity, so execution repeatedly loads weight blocks and applies them to the available tokens. The amount of useful work per transfer determines how well computation can keep up with this data movement. The amount of work available at once determines how these units are used. During prefill, a weight matrix is applied to many token vectors, allowing HMX to reuse its tiles across the batch. Ordinary decode presents one token vector at a time, and quantized matrix–vector products run on HVX. Speculative verification supplies a few vectors together. This creates an opportunity to share weight traffic across drafts, provided the kernel processes those vectors jointly. The relevant batch size is the number of tokens in a model pass, including tokens from a single request. The host communicates with the NPU through FastRPC. llama.cpp’s Hexagon backend (ggml-org, 2026) loads a DSP library, maps shared tensor buffers and submits batches of operators to a work

> 2.4 Hybrid-state management in llama.cpp

llama.cpp (ggml-org, 2023) runs all layers of the hybrid model on the Hexagon NPU. Its server compares each incoming prompt with the input it processed last and finds their longest common prefix. For an attention-only model, it truncates the KV cache at that position and processes the new suffix. For a hybrid model, it restores the newest saved recurrent state at or before that position and aligns the attention cache with it. Any shared tokens between the saved state and the end of the common prefix are processed again. Checkpoint placement determines how much of this repeated work is necessary. The stock server saves state at user-message boundaries and near the end of a prompt to support chat continuation. Each checkpoint also ends an input batch and copies about 50 MiB of recurrent state. Saving more positions therefore consumes memory and adds execution passes. A slot is the server context that holds a request’s cached tokens and model state; it retains a bounded set of checkpoints between requests. A host prompt cache can reload states from earlier requests with a longer matching prefix. Speculative decoding also saves states within a request. Verification updates the recurrent state as it checks each proposed token. If only the first two of three proposals are accepted, for example, the server needs the state after the second proposal to continue. These short-lived rollback states serve a different purpose from checkpoints retained for future requests. The backend produces them at batch boundaries, including during prompt processing; §3.3 examines the cost of doing so on the NPU.

> 3.1 A step is a medium prefill and a short decode

An agent step reads far more than it writes. In the app set, a text prompt averages 648 tokens, split mainly between fixed rules and on-screen controls (Table 1); its answer is about 14 tokens. The controls change with the screen, while the rules provide a reusable prefix. In the app-set profile, prefill and decode take comparable time: 0.58 and 0.54 s of a 1.31 s text step (Figure 2). Decode streams 2.9 GB of weights for every token. Within a prefill pass, element-wise operators and the short convolution account for 30% of NPU time, largely moving data. Batch boundaries add a separate cost. A calibrated prefill model estimates 1.30 ms per token plus 86 ms per pass over the model. Ending a batch early therefore costs roughly as much as processing another 66 tokens. The stock policy spends 0.13 s on a four-token tail pass and recurrent-state copies that prepare chat continuation. This fixed per-pass cost motivates consolidating unneces-sary input batches (§4.4). Screenshot requests take 4.1 × as long as text requests. The encoder takes 1.70 s to produce 1,127 image tokens, and prefilling those tokens takes another 1.66 s. The stock checkpoint policy also recomputes the 640 text tokens before the image at every step because it retains no checkpoint before the image. The image-related work limits the gains available from text-prefix reuse alone.  

> 3.2 Stock checkpoint placement limits prefix reuse

Consecutive agent prompts share a substantial text prefix. All prompts share the first 309 tokens, and within an episode consecutive prompts diverge a few tokens into the action history, about 360 to 400 tokens in. A KV cache reuses such a prefix exactly. A recurrent state cannot, because it has absorbed every token it has seen and resumes only from a stored checkpoint. The checkpoint gap is visible on the hybrid model’s own token stream. Over requests 2–61 of the replay trace, the stock policy processes 539 new prompt tokens per step; a KV cache on that same token stream would process 428 (Figure 3). The difference is 111 recomputed tokens, or about 140 ms per step. For context, the full-attention Qwen3-VL-4B processes 420 new tokens per step on the same engine. The gap comes from checkpoint placement. For a prompt containing one user message, the check-point 516 tokens before the end can fall well before the next request’s divergence point; the check-point four tokens before the end is usually too late to reuse. 3.3 Stock speculative decoding slows hybrid inference 

Enabling MTP through the stock rollback and verification paths makes a text step slower, from 1.85 to 2.52 s in the replay-trace ablation. Both configurations use the same prefill and memory-traffic optimizations (§6.4). Decode time also rises from 62 to 67 ms per token, but most of the step-level increase occurs during prefill, when the engine retains intermediate recurrent states. The added prefill cost comes from how the engine prepares to undo a rejected draft. It saves states after the final tokens of every batch, including prompt batches. The chunked Gated DeltaNet kernel on HMX produces only one final state. Requesting intermediate snapshots therefore sends the entire batch through the per-token HVX recurrence. This rollback tax adds 614 ms to prefill. A need for a few recent states changes how the whole prompt is processed. Verification and drafting also add work. The stock vector kernel replicates activations in on-chip memory, making four-token verification 2.1 × as expensive as one token. The draft head then scans a 248,320-row output matrix to propose each new token; vocabulary-sized operations consume 35% of decode time. Thus both preparing the input and producing the short answer contribute to the slowdown. 

Short outputs amplify the prefill cost. The rollback penalty is paid once per request, but a short answer offers few decode rounds in which to recover it. For an answer of about 14 tokens, the measured 614 ms prefill penalty is equivalent to roughly 44 ms per output token. Accepting several drafts in one round helps only if the decode saving exceeds this initial cost. Speculation therefore needs both matrix-based prefill and cheaper verification and drafting (§4.3). 

3.4 A loaded model keeps the NPU awake 

A loaded model can leave the NPU powered between requests even when no inference work is running. With the screen on, the idle phone draws 0.48 W without a server and 0.89 W with the model loaded; with the screen off, power rises from 0.25 to 0.76 W. The NPU’s power-collapse counter stops advancing, and its core and matrix unit remain at their top clocks at zero utilization. Session-wide power votes cause this residency tax , including while the phone is suspended. The app retains the model for five minutes after a task. At the measured excess idle power, this interval amounts to 120–150 J, equivalent to 12–15 text steps. Unloading the model reduces that

4 Design  

> 4.1 Overview

Tandem follows the agent’s request cycle (Figure 4). Across requests, unchanged instructions and task text make the current shared prefix a candidate for reuse by later steps. The server compares the incoming prompt with its cached tokens, restores the latest checkpoint within their common prefix and processes the remaining input. When it reaches the point where the prompts diverge, it can save a new checkpoint for subsequent requests. The placement rule accounts for the cost of creating that checkpoint (§4.2). Within a request, speculative verification needs states only for the few recent positions to which execution may roll back. The earlier context needs no per-token snapshots. Tandem therefore processes most of each prompt batch on the matrix unit and obtains its remaining rollback states from a short per-token tail. During verification, all proposed tokens share the same weight-block reads. These choices reduce the state-management and verification costs that otherwise outweigh decoding savings on short action outputs (§4.3). Batch consolidation removes small input passes, while fused operators reduce memory traffic within each pass (§4.4). For screenshots, the vision encoder supplies new image tokens after the reusable text prefix. The server returns the selected action through the existing interface; the app executes it and supplies the next observation. Between request bursts, the backend releases active NPU resources while retaining model weights and cached state.  

> 4.2 Divergence-point checkpoints

Reusing context requires a saved state close to the point where two requests begin to differ. A checkpoint costs a state copy and a batch boundary, so placing one at every potentially reusable token would erase the prefill saving. Within an episode, rules and task text stay fixed while recent actions and the screen description change. The current divergence point therefore predicts a prefix that the next request can reuse. In the recorded episodes, divergence points remain at or beyond previously retained checkpoints once the episode settles. Tandem uses this locality to place checkpoints online. For each request, let 𝐿 be the longest common prefix between the new prompt and the tokens cached in the slot, including any entry loaded from the prompt cache. After restoring the newest checkpoint at 𝑅 ≤ 𝐿 , Tandem splits the batch that crosses 𝐿 and stores the state there. It does so only when 𝐿 precedes the prompt’s end and any image, and 𝐿 − 𝑅 ≥ 32 . The rule creates at most one checkpoint per request. Subsequent requests reuse it through the server’s existing restore and eviction rules; a request that diverges earlier falls back to an earlier checkpoint. The 32-token threshold avoids closely spaced copies; we select it using a cost model calibrated to the measured prefill and checkpoint costs. The policy follows changes in tasks and screens. A new task makes requests diverge near the end of the fixed instruction block. The resulting checkpoint can survive later restores within the episode. As the action-history window fills, divergence moves farther into the prompt and may justify a new checkpoint. Once the window starts sliding, requests tend to diverge near its beginning, allowing that position to be reused. These transitions explain why the server creates checkpoints on a minority of requests rather than on every step. Checkpoint spacing trades a cost now for reuse later. With a per-pass cost of about 86 ms and a per-token cost of 1.30 ms, advancing reuse by 32 tokens saves about 42 ms per future hit. Roughly three hits would amortize the added pass, excluding the state-copy cost. A 64-token threshold misses many of the 25–60-token advances between prompt fields. We sweep the threshold using a replay model of the server’s restore, eviction and prompt-cache rules. The model reproduces 422/422 measured prompt-token counts; under its calibrated latency model, the 32-token setting is within 4 ms of the best setting on each trace. On the replay trace, the rule creates a checkpoint on 10 of the 60 requests after the first and retains one additional state copy of about 50 MiB. Over these 60 requests, new prompt work falls from 539 to 443 tokens per step, within 15 tokens of the KV-cache reuse bound. The same rule applies to the text prefix of screenshot requests. 

4.3 Rollback-aware speculative decoding 

Speculation can generate an action with fewer model passes. On this NPU, that saving depends on preparing rollback states without slowing the whole prompt and checking several drafts with less work than separate decode passes. Tandem changes the prefill path, the verification kernel and the draft head to address these costs together.  

> 9PREPRINT Tandem: Serving Hybrid Linear-Attention GUI Agents on Mobile NPUs

Rollback-aware recurrent prefill. Undoing rejected drafts requires only the states near the end of a batch. GPU verification kernels recompute or scan recurrent states for candidate tokens (Wang et al., 2024a; Wu et al., 2026). On Hexagon, requesting those states displaces the chunked HMX kernel even during prefill. Tandem divides the batch into a large prefix that uses HMX and a short tail that saves each intermediate state. With up to three drafts, the engine retains the final 𝐾 = 4 states of a batch. For 𝑛 ≥ 𝐾 tokens, Tandem processes the first 𝑛 − 𝐾 + 1 tokens with the chunked kernel and writes the resulting state directly into snapshot slot 𝐾 − 1 . The HVX recurrence continues from that state for the remaining 

𝐾 − 1 tokens, saving each intermediate state. Shorter batches use the per-token path. All required snapshots are available, while all but three tokens of a large batch use the matrix unit. Figure 5 illustrates this division for a 448-token batch. 

Column-shared verification kernel. A verification pass applies the same weights to the last accepted token and up to three drafts. Processing these token vectors together lets them share weight reads. Tandem dequantizes each weight block once, and HVX threads apply it to all to-ken columns with vector-by-scalar instructions before advancing to the next block. Four-column verification takes 1.27 × the time of one column, versus 2.1 × with the stock kernel. The activation quantizer writes compact int8 values to DRAM, packing four values into each scalar-register load. This removes the stock kernel’s 32-fold activation replication and avoids slow scalar reads from VTCM. Per-block activation sums account for weight-format offsets. The backend uses this kernel for products with up to five columns, or eight with 6-bit weights; larger products use HMX. 

Trimmed draft head. Proposing a token should cost substantially less than generating it with the full model. The MTP head uses a lightweight transformer block, but its 248,320-row output matrix still occupies 521.5 MB. Multiplying by that matrix and selecting a token costs about 12 ms per draft. Following frequency-ranked drafting (Zhao et al., 2025), Tandem copies 32,768 rows into a 68.8 MB draft matrix: special and byte tokens, the first 8,000 CJK tokens and frequent tokens from the agent’s training data. The model file also stores each selected row’s original token ID. The draft sampler maps its chosen row back to that ID before verification, so the compact matrix integrates with the existing token stream. Verification and the final output decision use the target model’s full vocabulary. The speculative path adds 201 MiB for four recurrent-state planes and 68.8 MB for the draft matrix. §6.4 separates its prefill, verification and drafting costs.  

> 4.4 Lean prefill

After context reuse removes shared input, the remaining prompt still passes through every model layer. Each additional batch repeats that traversal, and separate operators within a layer may write intermediate results to DRAM only to read them back immediately. Tandem reduces these costs by consolidating input batches and keeping intermediate data close to the NPU’s compute units. 

Batch consolidation. The stock checkpoint policy ends batches 516 and 4 tokens before the prompt’s end, preparing a state for chat continuation. This leaves a four-token pass even when those tokens would fit in the preceding batch. For the agent’s independently submitted requests, Tandem replaces these breaks with one 512 tokens before the end, matching the server’s micro-batch limit. After restoring a checkpoint, the server updates its eviction order and reuses the saved copy. With 600 tokens remaining, the stock boundaries produce passes of 84, 512 and 4 tokens; the new boundary produces 88 and 512. The token sequence is unchanged, but one model traversal and its associated checkpoint copy disappear. Shifting the earlier boundary is necessary: removing only the final break would leave 516 tokens, which the 512-token micro-batch limit would split again. removes one pass from every step. 

Fused SwiGLU. A feed-forward block multiplies its input by gate and up matrices and combines the products with SwiGLU. The stock backend writes these temporary products to DRAM and reads them back in a separate operator. Tandem computes paired columns of the two matrices in adjacent VTCM tiles. While HMX processes the next chunk, HVX applies SwiGLU to the completed tiles and stores only the combined output. At 448 tokens, this removes 66 MB of traffic per layer while preserving the arithmetic order. Pairing gate and up weights within one HMX job retains the pipeline’s two output buffers. Al-ternating separate jobs would require four buffers, exceeding the VTCM budget for a 448-token batch. The host enables fusion when the plan fits the session’s memory budget without adding row blocks or changing the pipeline mode; otherwise it keeps the separate operators. 

Channel-major convolution. The recurrent layers’ short convolution operates along time within each channel. Tandem keeps this channel-major layout, using 2D DMA to stream chan-nel slices into VTCM for convolution and the following SiLU. This removes the stock path’s two transposes, each 14.7 MB per layer at 448 tokens. During decode, one DMA per thread and vector gathers move the short per-channel state rows. The backend also requests the memory controller’s performance mode during active execution.  

> 4.5 Image path

Tandem reuses the processed text prefix and runs the new screenshot through the NPU vision encoder. Keeping the encoder on the NPU avoids a lengthy CPU stage before the model processes the screen. The divergence rule checkpoints text before the image, where multimodal rotary positions still equal token indices. Restoring this state reuses the shared text before encoding and prefilling the new screenshot. An optional checkpoint immediately before the image also serves repeated queries with identical text; it is disabled by default because it adds no reuse on top of divergence-point checkpoints in our traces. The image-token budget independently controls encoding and prefill work. We evaluate its latency–accuracy tradeoff in §6.6.  

> 4.6 Idle power release

Keeping the model ready for another task requires retaining its weights in memory. The NPU can enter a low-power state during the wait. Tandem tracks operator batches in each session and, after 3 s with no batch submitted or in flight, releases the session’s active power requests. It drops the bandwidth vote, powers down HMX, drops the DDR performance mode and restores platform-default clocks and low-power modes. Before submitting the next batch, it reapplies the active votes and waits for the clocks to recover. Power management uses the existing FastRPC power call, independently of the operator queue. The three-second timer and the app’s five-minute unload timer control different resources. The backend timer releases compute and memory-controller votes between bursts. The app timer eventually frees the model’s memory after a longer idle period. A request arriving between these deadlines restores the active votes and continues with the loaded weights and cached state. The backend also reduces wakeups while relaxed. Increasing the queue timeout from 50 to 500 ms reduces periodic wakeups from twenty to two per second; an arriving operator packet wakes the queue immediately. The idle timer accounts for time spent in phone suspend. Power release is synchronized with operator submission and completion. The host waits until all submitted batches have completed and the matrix unit has been relinquished before releasing active votes. Submission and release share a mutex, so a new batch either prevents the release or waits for the NPU to return to its active state. Model weights and inference state remain allocated throughout the transition. Restoring the votes takes 2–4 ms (§6.8).

5 Implementation 

Tandem builds on llama.cpp release b11200, adding about 3,000 lines of C and C++ across 24 files. Two thirds of the added code runs on the NPU. The server handles checkpoints and batching; the host backend selects kernels, rewrites fused operators and manages power transitions; the DSP library implements the kernels and power handlers. We compile with Android NDK r28b and Hexagon SDK 6.6. An offline tool adds the trimmed draft matrix and its original token IDs to the model file. Runtime switches independently control the optimizations. With them disabled, the same build uses the stock serving policy and kernels while retaining the correctness fixes, allowing ablations within one executable. 

Service lifecycle. The app loads the server on demand and unloads it after five idle minutes; the prompt cache is bounded at 512 MiB. Repeated requests exposed a work-queue race in the upstream backend that could execute a task twice, causing hangs or aborts. We fixed the queue synchronization and reported the race to llama.cpp; its maintainers confirmed the issue and merged a fix. Both Tandem and our llama.cpp baseline include the correction. A watchdog converts an unresponsive NPU into a restartable server failure. 

DMA coherence. The convolution writes inputs through DMA, while the state-copy operator reads them through the NPU data cache. Stale cache lines can therefore save a previous layer’s state in small batches. The copy path cleans and invalidates the source range through the operating system before reading it.

We measure latency, energy and action fidelity on recorded GUI-agent requests. We vary model size, recurrent architecture, workload and NPU generation to examine how the gains depend on the model and execution platform.

6.4 Where the gains come from 

Speculation becomes beneficial only after reducing both rollback and decode costs (Figure 7). This experiment uses the warmed replay trace and runtime switches in one executable (§6.1). Starting with the stock policy and kernels, prefill and memory-traffic optimizations reduce text-step latency from 1.98 to 1.85 s. Adding MTP increases it by 0.67 s. Rollback-aware prefill recovers most of that loss; column-shared verification and the trimmed draft head reduce the step to 1.65 s. Batch consolidation and divergence-point checkpoints bring it to 1.41 s. Removing one mechanism at a time measures its contribution within the full configuration. Rollback-aware prefill has the largest effect: 0.46 s per text step and 1.42 s per screenshot step. The shared verification kernel and the trimmed draft head save 0.18 and 0.14 s per text step, batch consolidation and divergence-point checkpoints another 0.17 and 0.08 s. Batching policies also change kernel work, so these individual reductions need not sum to the total latency saving. For screenshots, placing a checkpoint at the divergence point restores 266 text tokens and saves 0.41 s. A checkpoint immediately before the image restores the same prefix on this workload, adding little when divergence-point checkpoints are already enabled. We therefore leave it off.

6.7 Sensitivity to configuration 

Figure 8 varies one setting at a time on the replay trace. > 6.10 Fidelity and overhead

With the vision encoder fixed on the NPU, each tested serving or kernel optimization preserves action outputs on the 61-request text trace and the 21-screen app set when added or removed individually. Changes in batching or speculative execution reword at most one free-text summary per trace. For text requests, the fused operator, data-movement paths, verification kernel, trimmed draft head and idle power release also preserve the measured first-token top-five log-probabilities. Both Tandem and the llama.cpp NPU baseline use the same NPU encoder. CPU and NPU encoder paths can produce different answers. The memory cost of Tandem is 201 MiB of rollback planes, 68.8 MB for the draft head and one additional checkpoint of about 50 MiB. The prompt cache is capped at 512 MiB. 

7 Related Work 

LLM inference on mobile NPUs. llm.npu accelerates prefill with chunk-sharing graphs and shadow execution of outliers (Xu et al., 2025); HeteroLLM partitions computation across the NPU, GPU and CPU (Chen et al., 2025); PowerInfer-2 exploits activation sparsity (Xue et al., 2024); T-MAN uses table lookups for low-bit decode (Wei et al., 2025); and ShadowNPU offloads sparse at-tention (Yin et al., 2026). These systems target full-attention models. Measurement studies examine mobile-NPU efficiency (Cai et al., 2026) and test-time scaling (Hao et al., 2026). Mobile deployments use engines such as MNN (Jiang et al., 2020), MLC LLM (MLC team, 2023) and llama.cpp (ggml-org, 2023; 2026). Tandem addresses recurrent-state management and the request pattern of a resident phone agent. 

Serving hybrid and recurrent models. Marconi checkpoints hybrid states at radix-tree branch points, uses estimated reuse for cache admission, and accounts for compute savings per byte in eviction (Pan et al., 2025). Sparse prefix caching chooses checkpoints through dynamic program-ming over prefix-overlap distributions (Shirokikh & Nikolenko, 2026). GPU systems support spec-ulative rollback through verification kernels and tree scans (Wang et al., 2024a; Wu et al., 2026). Tandem uses cost-calibrated checkpoint spacing for a single agent’s requests and preserves chun-ked NPU prefill by confining rollback-state generation to a short tail. 

Speculative decoding. Speculative decoding verifies the drafts of a small model in one pass of the large one (Leviathan et al., 2023). MTP heads (Gloeckle et al., 2024) and feature-level drafters (Li et al., 2026) draft from the target model itself, and FR-Spec restricts drafting to fre-quent tokens (Zhao et al., 2025), which Tandem’s trimmed draft head follows. Agent-X (Chung et al., 2026) improves on-device agent inference through prompt rewriting for KV-cache reuse and example-based drafting. Tandem instead targets recurrent-state reuse and reduces Hexagon veri-fication overhead by sharing weight reads across drafts. 

On-device GUI agents. GUI agents automate app interactions using language models (Wen et al., 2024; Wang et al., 2024b; Qin et al., 2025; Liu et al., 2024). On-device approaches reduce model calls (Wen et al., 2025), shrink the policy (Wang et al., 2026; Jiang & Huang, 2026), divide work be-tween device and cloud (Yi et al., 2026), learn through exploration (Huang et al., 2026) or reuse pre-fixes across screens (Zhang et al., 2026). Other work reduces power during mobile inference (Chu et al., 2026). Tandem accelerates individual calls of a hybrid policy and releases the NPU’s power votes between request bursts. 

8 Discussion 

Serving policies. Checkpoint gains depend on prompt structure and may be smaller when the baseline already preserves reusable prefixes (§6.2). Checkpoint placement, batch consolidation and idle power release can be adopted independently of Tandem ’s kernels. 

Other models and accelerators. Divergence-point checkpoints require a server that can save and  

> 19 PREPRINT Tandem: Serving Hybrid Linear-Attention GUI Agents on Mobile NPUs

restore recurrent state. Idle power release requires session-level power control. Both mechanisms apply to the short-convolution and Mamba2 hybrids we evaluate. The speculative path depends more closely on the model and hardware: rollback-aware prefill uses Gated DeltaNet’s chunked recurrence, and the MTP head drafts from the target’s hidden states. The Hexagon kernels carry from v79 to v81 through recompilation; another accelerator would need corresponding matrix and vector implementations. 

Screenshot cost. Screens requiring fine visual detail may favor a larger image-token budget, despite the latency savings from reducing it (§6.6). Adapting the budget to screen content and accelerating the vision encoder could further reduce screenshot latency. 

9 Conclusion 

Hybrid models reduce the memory needed to run GUI agents on a phone. Tandem adapts their serving to changing prompts, short action outputs and idle intervals: it preserves reusable recurrent states across steps, supports speculative execution while retaining fast prompt processing, and releases idle NPU resources without unloading the model. On a Snapdragon 8 Elite, it reduces text-step latency by 30%, screenshot-step latency by 16% and energy per text step by 33% relative to llama.cpp’s fastest NPU configuration. Standby power with the model loaded falls from 0.76 to 0.22 W. The text-step latency reduction remains 27% on the next NPU generation.
