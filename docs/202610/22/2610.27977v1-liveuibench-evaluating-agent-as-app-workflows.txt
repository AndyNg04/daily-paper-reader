# ABSTRACT 

Applications provide convenient features for users to complete daily tasks. How-ever, different users may have different or even conflicting requirements for the same application, while the requirements of the same user may change over time. Personalizing applications produced by agent-to-app or UI-to-code approaches can require changes to the generated implementation. We propose Agent as App, a task in which users express their requirements in natural language and an agent creates a personalized application while continuing to supply its behavior during use. We implement L IVE UIA GENT , which generates a task-specific orchestration connecting the user interface, saved information, and service actions. A shared agent runtime renders and updates the interface while carrying out the requested operations. Revising the orchestration and interface while reusing that runtime pro-vides a lightweight basis for personalization as requirements evolve. We introduce LIVE UIB ENCH , a benchmark with diverse requirements and ordered interactions across personal services. The empirical findings show that the evaluated models struggle to complete these workflows reliably. Applications can satisfy many local checks while leaving the overall task unfinished, and greater partial coverage can coincide with fewer completed workflows. 

# 1 INTRODUCTION 

Applications help users complete everyday activities, but people can have different or conflicting requirements for the same application. A music listener may want a simple play button, while another wants to compare candidates and maintain a listening journal. Personalization also changes over time. A listener can begin with a playlist and later ask to keep notes about songs, revise earlier choices, or prepare a selection for an event. The application must connect each request to information already saved. Generative and malleable interfaces make such variation a concrete design goal (Vaithilingam et al., 2024; Min et al., 2025; Cao et al., 2025). Adaptive and mixed-initiative interfaces provide earlier foundations for matching interaction to a user’s needs (Gajos & Weld, 2004; Horvitz, 1999). Language agents provide a way to express these requirements directly. An agent can produce an application implementation, a producer role we call agent-to-app. End-user software and data-driven authoring systems connect user intent to executable behavior (Ko et al., 2011; Verou et al., 2016). UI-to-code systems translate a visual design into an implementation (Si et al., 2025), while website-generation benchmarks test whether produced artifacts support their requested functions (Lu et al., 2025). An agent can also remain responsible for interpreting task actions after an interface has been created. The application then combines visible interface elements, continued agent reasoning, and saved information. Its behavior depends on their connection during use. 

We propose Agent as App as a task for persistent, personalized applications. Given a natural-language application requirement and permitted context, an agent must create an interactive workspace and continue to provide its task behavior as the user supplies inputs, changes requests, and returns. The application-side agent interprets inputs and retained information, performs service operations, and updates the interface. Success concerns the requested effects across this sequence. A convincing initial screen does not establish that its interface reaches the intended service operations. A successful service call can affect the wrong record. A return visit can preserve a mistake. These outcomes look similar if evaluation records only whether a screen opens, an action returns, or stored information remains present. They differ when the requested goal, visible result, and saved effect are checked together. We implement Agent as App in L IVE UIA GENT . A user’s requirement produces an orchestration that links the generated interface to service actions and saved application state. The agent remains responsible for executing later requests through this interface. Revising a requirement updates the orchestration and workspace, while a shared runtime continues to execute actions and retain the user’s information. Personalization can therefore proceed through changes to the task-specific plan without rebuilding the execution machinery. LIVE UIB ENCH evaluates these applications through sequences of user requests. An initial require-ment is followed by submissions, revisions, and return visits across personal services. The benchmark measures whether the generated application completes the sequence, alongside its coverage of indi-vidual assertions. We analyze the underlying task records to locate the earliest unmet requirements and compare which tasks different models complete. The results reveal a large gap between opening an application and completing its workflow. They also show that stronger partial assertion coverage can coexist with fewer completed tasks, and that combining the successes of different models still leaves much of the benchmark unresolved. Our contributions are listed below. 1. We propose the Agent as App task. The task connects personalized application creation with continued agent-mediated use as users supply inputs, revise requirements, and return. 2. We implement L IVE UIA GENT . The implementation connects personalized interfaces to a shared agent runtime and saved service state through lightweight orchestrations. 3. A benchmark and empirical findings. LIVE UIB ENCH provides diverse task requirements and ordered interactions. The empirical analysis follows failure stages, unmet checks, and the shared and distinct tasks completed by different models.

# 4 EVALUATION 

The model survey evaluates generated orchestrations against the benchmark’s original operational assertions. Opening checks test whether the expected views, inputs, and action bindings are available. Later assertions examine service calls, changes to saved information, evidence in the displayed result, and retained state. Table 2 reports the model configurations and task-family results. The full-workflow rate is the fraction of tasks satisfying every assigned assertion. The assertion pass rate measures coverage across the complete set of assigned assertions. These measures establish the recorded checks; semantic requirements beyond those checks need separate service evidence. Opening coverage requires every opening episode within a task to pass, including the later application in a shared-world task. The metrics retain rejected generations and unavailable responses in their assigned denominators. The survey uses the recorded generation procedures for each model, so comparisons describe the evaluated systems. Metric definitions and the survey display rule appear in Appendix B. We recompute the measures from the archived per-task and per-episode records. For each failed task, the first episode containing an unmet assertion determines its failure stage. The failed checks in that episode identify what evidence was missing. Recorded generation and episode errors remain separate from completed operations. This analysis locates observed failures within the prescribed sequence without inferring an internal cause from the stage label. 5We also compare the sets of tasks completed by different models. Their union measures which tasks have been completed by at least one evaluated model. It is a retrospective coverage diagnostic, not a measured ensemble or a model-selection procedure. The recorded application examples provide a complementary view of interaction and saved service effects. Appendix C specifies the recount and grouping rules.

This distinction matters when interpreting partial progress: a recorded operation can contribute to assertion coverage while the application still fails to present a supported result to its user. 

Different successes leave a large common set of unsolved tasks. Comparing task identities reveals complementary successes that aggregate scores conceal. Combining the observed successful tasks of all evaluated models expands coverage beyond the strongest model, but most tasks remain unresolved by every model. The shared difficulty is particularly clear in the multi-tool and shared-world families, where even this union covers few tasks. The union is a retrospective diagnostic of existing results, rather than a tested ensemble. Table 3 reports the counts and task-family denominators. The success sets are also not nested in the aggregate ranking. A model with fewer completed tasks can still complete tasks that a higher-scoring model fails. This explains why pooling observed successes increases coverage, but the gain does not remove the large unresolved part of the collection. The union is useful for separating shared difficulty from complementary strengths. It does not establish that the successful model can be identified before executing a task, and it does not count a partially successful application as a completed workflow. 86 RELATED WORK 

End-user software engineering studies how people develop software for their own tasks (Ko et al., 2011), and Mavo connects authored interfaces to persistent user data (Verou et al., 2016). Mixed-initiative interfaces and SUPPLE adapt interaction to users and devices (Horvitz, 1999; Gajos & Weld, 2004). Recent generative and malleable interfaces extend this flexibility through language and dynamically produced views (Chen et al., 2026; Vaithilingam et al., 2024; Min et al., 2025; Cao et al., 2025). Agent as App follows the application beyond its initial presentation. The generated interface must support later requests, preserve relevant information, and connect a user’s changing intention to service behavior. Reusable automation offers a related way to turn user intentions into repeatable actions. Sikuli, SUGILITE, PUMICE, and CoScripter use visual references, demonstrations, or accessible scripts to specify behavior (Yeh et al., 2009; Li et al., 2017; 2019; Bogart et al., 2008). Language agents combine reasoning with external actions (Yao et al., 2023; Li et al., 2023; Qin et al., 2024), while workflow memory supplies reusable execution structure (Wang et al., 2024b). Self-Refine and Reflexion improve outputs or later attempts through feedback (Madaan et al., 2023; Shinn et al., 2023), and generative agents maintain memory for continuing behavior (Park et al., 2023). Agent as App follows requests made within a retained application, where earlier information and service effects constrain each subsequent action. Feedback during an attempted solution and a new request from the user impose different requirements on an application. A new request can revise the intended outcome while preserving earlier information that remains relevant. For example, extending a gift queue should retain the entries the user still needs, while revising a task should preserve the identity of the record being changed. These dependencies connect reasoning about the current request to the application state created by earlier requests. The benchmark makes that connection observable across the same application. Evaluation also depends on what generation is expected to deliver. HumanEval and APPS test executable programs, while SWE-bench tests changes to existing repositories (Chen et al., 2021; Hendrycks et al., 2021; Jimenez et al., 2024). Design2Code evaluates implementation from visual designs (Si et al., 2025). WebGen-Bench and ProgramBench examine functionality after artifact generation (Lu et al., 2025; Yang et al., 2026), and AUI-Gym evaluates task solvability on generated interfaces (Lin et al., 2025). L IVE UIB ENCH examines an application whose agent remains involved during use. Its ordered requests test whether local successes form a complete workflow, including revisions and return visits. Existing agent environments provide complementary coverage of these demands. Web tasks span compact interfaces, shopping, and realistic websites (Shi et al., 2017; Yao et al., 2022; Deng et al., 2023; Zhou et al., 2024; He et al., 2024). Mobile, desktop, enterprise, and office benchmarks assess interaction across richer workspaces (Rawles et al., 2025; Xie et al., 2024; Kapoor et al., 2024; Drouin et al., 2024; Wang et al., 2024a). AppWorld and the τ benchmarks emphasize service use and shared state (Trivedi et al., 2024; Yao et al., 2025; Barres et al., 2025). AssistantBench, GAIA, and Agent’s Last Exam examine broader assistant work (Yoran et al., 2024; Mialon et al., 2024; Sun et al., 2026), while ScienceWorld and AgentBench include stateful interaction (Wang et al., 2022; Liu et al., 2024). Actions in these environments alter information that later steps depend on. Alongside model-based judgments (Zheng et al., 2023), our evaluation retains action evidence and saved service observations to distinguish visible completion, persistence, and the requested result. 

# 7 CONCLUSION 

We propose Agent as App as a task for applications that adapt to a user’s changing requirements. LIVE UIA GENT connects task-specific orchestrations to a shared agent runtime, and L IVE UIB ENCH 

evaluates continued use through ordered requests. The raw survey records show where opening readiness and partial assertion coverage stop short of full-workflow completion. Submission failures, disagreements between service and displayed evidence, and tasks left unresolved across models identify distinct challenges. The benchmark connects these measurements to the behavior of a retained application. 9AI U SE STATEMENT

# D HUMAN ANNOTATION OF TASK SPECIFICATIONS 

Review criteria. Five human annotators inspect selected tasks’ intentions, expected behavior, interaction sequence, and prepared test conditions. They assess whether the intention is clear and reasonable and whether the expected behavior and its checks follow that intention. They select one of three verdicts, reasonable, problematic, or uncertain, and provide a comment for a problematic or uncertain verdict. These judgments evaluate task specifications. 

Aligning goals and tests. The comments expose two ways that an apparently reasonable test can fail to express its goal. A question tracker preserved question text without checking the answer status that the user wanted to monitor. The task now includes a follow-up that checks that status. An anniversary countdown left open whether a date represented a one-time event or a recurring annual event. The goal specifies the one-time interpretation required by its expected behavior. The first change strengthens coverage of the promised outcome. The second removes ambiguity about what outcome is correct. Adjudication also checks whether an objection introduces a requirement beyond the user’s goal. Details supplied during the scripted interaction, or quantities that follow directly from those inputs, need not appear in the initial intention. Adjudication reconciles these comments with the task inputs and expected outcomes. 

Annotation interface and recorded decisions. The review interface presents the task’s initial intention and expected behavior, together with its service dependencies and benchmark partition. The detailed view includes the interaction episodes, prepared starting records, assertions, and existing comments. Annotators can therefore compare an objection with the complete task sequence rather than only its opening requirement. Each submitted review associates a task with a reviewer identity, a judgment, a comment, and a timestamp. Reasonable, problematic, and uncertain are the displayed meanings of the stored review labels. Problematic and uncertain submissions require a comment. An additional free-form comment mechanism supports discussion of a task. # F LIMITATIONS 

The evaluated models cover part of the range of systems that could implement Agent as App. Future evaluation can include additional model families, different model scales, and models specialized for interface understanding or service use. Such coverage would help establish whether the observed relationship between partial assertion coverage and complete workflows persists across a broader set 17 of capabilities. It would also allow comparison of how different models interpret later requests, use information established earlier, and maintain the user’s intention throughout an application session. Generalization remains to be examined across additional tasks and service environments. New do-mains may require different combinations of user input, service operations, and retained information. Longer interaction histories can also introduce repeated revisions and changes in the user’s prefer-ences that are less prominent in short workflows. Evaluation in these settings would test whether a personalized application continues to support a changing goal as its accumulated context grows. Extending task diversity, service coverage, and duration of use would provide a broader account of the generality of Agent as App.
