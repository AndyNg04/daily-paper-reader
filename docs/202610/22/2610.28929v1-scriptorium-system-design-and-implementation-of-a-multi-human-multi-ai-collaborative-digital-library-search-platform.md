## 摘要
本技术报告记录了 Scriptorium 的设计与实现。Scriptorium 是一个数字图书馆搜索界面，旨在支持多人与多 AI 协作：一方面，用户之间可全面透明地查看彼此的搜索活动；另一方面，系统采用由七个角色专门化生成式 AI 智能体组成的管理者—工作者（Manager--Worker）架构。配套的简短演示论文介绍了 Scriptorium 的交互设计；由于演示论文的篇幅限制，无法详述大部分实现细节。本报告完整记录了 Scriptorium 的系统架构、数据模型、协作交互设计理念及 AI 编排机制，其中包括智能体提示词原文、用于约束智能体的确定性防护机制、语言模型与检索配置，以及运行系统所需的步骤，以便其他研究人员能够审视、评议、复现并复用该设计。我们还讨论了系统当前的局限性，以及正在规划的用户研究。该研究旨在评估 Scriptorium 的核心假设：将协作透明度与范围明确的多智能体 AI 辅助相结合，能够促进协作者不同研究脉络之间意外而富有启发性的交叉融合。

## Abstract
This technical report documents the design and implementation of Scriptorium, a digital library search interface designed to support multi-human, multi-AI collaboration: full cross-user transparency of search activity combined with a Manager--Worker architecture of seven role-specialized generative AI agents. A companion short demonstration paper describes Scriptorium's interaction design; because a demonstration format is constrained to a few pages, it necessarily omits most implementation detail. This report documents Scriptorium's complete system architecture, data model, collaborative-interaction design rationale, and AI orchestration mechanism, including verbatim agent prompts, the deterministic guardrails that constrain them, the language model and retrieval configuration, and the steps needed to run the system, so that the design can be inspected, critiqued, reproduced, and reused by other researchers. We also discuss the system's current limitations and the user study we are planning to evaluate its central hypothesis: that combining collaborative transparency with scoped multi-agent AI assistance increases serendipitous cross-pollination between collaborators' research threads.

## 2. 方法论：透明协作工作空间与受限多智能体编排

### 2.1 核心思想

系统由两个相互配合的设计轴组成：

- **默认透明的协作过程**：无需主动推荐或邀请，登录用户即可查看所有工作空间及其中的检索活动。
- **按角色限定证据范围的 AI 辅助**：不同智能体只接收完成任务所需的数据，而不是共享一个无限制的大上下文。

这里的“多智能体”主要指**管理者路由到一个专门化工作者**，并非多个智能体自主讨论、迭代辩论或联合制定计划。

### 2.2 软件架构与数据设计

- 使用 **MERN 技术栈**：
  - React 前端与 Redux Toolkit 状态管理；
  - Express／Node.js 后端；
  - MongoDB 与 Mongoose 数据存储。
- 图书馆检索结果来自 **Ex Libris Primo API**；系统是在既有发现服务上添加协作与 AI 功能，而非重新开发检索引擎。
- AI 编排位于服务端，通过 OpenAI API 调用模型，模型密钥不会传到浏览器。

核心数据包括用户、工作空间、查询、文献、聊天消息和文献打开日志。两项设计尤其重要：

- **软删除文献**：弃用文献仍保留，作为团队曾考虑后放弃某方向的记录。
- **独立记录打开事件**：时间线中的搜索、保存、删除、打开均对应真实系统操作，而非人为补造的活动。

聊天和时间线每 **3 秒轮询**一次；部分当前主题文献列表每 **60 秒**刷新一次。

### 2.3 七个智能体及其职责

| 智能体 | 主要输入 | 主要功能与限制 |
|---|---|---|
| **ARIA：摘要者** | 当前消息附加文献的标题与摘要、近期聊天 | 逐篇总结，不进行跨文献比较；提示词限制为 120 词 |
| **CLIO：引用助手** | 附加文献的元数据；无附件时使用已保存文献 | 格式化参考文献，标记缺失字段，不编造 DOI、页码或出版社 |
| **HERMES：检索导航者** | 团队查询历史、保存及删除文献的标题 | 输出 5 条新查询，每条不超过 7 词 |
| **SOCRATES：批评者** | 工作空间查询、保存及删除文献的标题与摘要、近期聊天 | 指出证据缺口或判断特定主张，最后提出一个聚焦问题 |
| **MINERVA：方法分析者** | 附加文献或已保存文献的标题与摘要、近期聊天 | 提取研究设计、数据来源、样本与分析方法，缺失部分标记为未说明 |
| **MOMUS：反方论证者** | 团队保存及删除文献、查询历史、近期聊天 | 识别语料倾向、内部矛盾与潜在反证 |
| **JANUS：研究线索桥接者** | 按协作者组织的查询与已保存文献标题、近期聊天 | 概括各成员方向、发现连接点，并提出一条桥接查询 |

其中，JANUS 最直接体现多人协作的独特性：其输入是**不同成员之间研究活动的差异**，而非单个用户的文献集合。

### 2.4 编排与算法流程

系统没有提出新的训练算法或数学目标函数，主要流程为：

1. **解析请求**：若用户明确写出 `@agentname`，直接指定工作者。
2. **自动路由**：否则由管理者模型仅根据用户消息判断任务类别，不读取工作空间内容。
   - 路由置信度低于 **0.7** 时要求澄清；
   - 路由调用失败时，退回固定顺序的关键词分类。
3. **构建上下文**：服务端从数据库读取查询、保存与删除文献、成员活动及近期聊天。
4. **确定性前置检查**：
   - ARIA 没有附件则拒绝；
   - CLIO／MINERVA 没有可用文献则拒绝；
   - SOCRATES／MOMUS 没有保存或删除文献则拒绝；
   - JANUS 不足两名活跃成员则拒绝。
5. **代码级输入裁剪**：为不同智能体构造不同对象，未选中的字段不会发送给模型。例如 HERMES 只能读取文献标题，不能读取摘要。
6. **调用工作者并展示输出**：响应进入共享聊天；HERMES 的查询数量与词数额外由代码限制。

需要区分：**输入范围和前置检查由程序执行；大多数自然语言输出长度与行为要求仍依赖模型遵循提示词。**

### 2.5 WAG 与 RAG 的区别

作者将系统定位为 **工作空间增强生成（WAG）**：

- AI 主要基于人类已经保存、附加或弃用的材料工作；
- 不会在每次回答时自动检索一批文献，再据此生成答案。

但这一“封闭证据范围”并非绝对：MOMUS 可以提出模型知识中的反方文献或观点，JANUS 也可以推荐已知综述或桥接文献，均要求标记为 **“待核验”**。

## 6. 主要结论与发现

### 已经成立的实现层面结论
- 系统实现了多人共享检索活动、跨会话协作和七类专门化 AI 辅助。

## 7. 优点与亮点

- **实现透明度高**：公开架构、数据模型、路由提示词、全部工作者提示词、运行配置与 MIT 许可代码。
- **不只依赖提示词约束**：通过实际删减输入字段限制模型可见信息，约束比“请忽略无关内容”更明确。
- **失败处理清晰**：输入不足时由程序拒绝，路由不确定时要求澄清，降低无依据执行的风险。
- **保留负向选择信息**：软删除记录有助于理解团队放弃的方向，并为证据缺口分析提供背景。
- **协作机制具有针对性**：JANUS 聚焦异步积累的成员研究线索，不要求固定领导者或预先分工。
- **交互保持熟悉性**：在传统搜索结果页上叠加时间线和聊天，避免完全替换用户熟悉的检索模式。
- **研究定位较克制**：明确承认原型、安全性和效果证据的限制，没有把实现成功等同于研究假设成立。

### 8.2 证据与偏差风险
- 主要依据标题和摘要，无法可靠判断全文中的研究方法、局限与证据强度。

### 8.3 约束与提示词的一致性问题
- 管理者将“总结／比较附件”路由给 ARIA，但 ARIA 明确禁止跨文献比较，存在任务映射冲突。
- 正文强调 MINERVA 不推断缺失信息，实际提示词却允许从摘要中“明确可推断”的内容，边界仍有解释空间。

- 部分智能体仍接收近期聊天，因此字段级裁剪并不意味着相关内容完全不可能通过聊天再次进入上下文。

### 8.4 安全、隐私与适用范围
- **没有生产级身份认证**：客户端保存普通用户对象，后端信任客户端提交的标识，不能可靠防止身份冒用。
- 所有登录用户可查看所有工作空间，不适合直接用于保密项目或多租户部署。
- 查询、摘要和聊天等内容会发送给外部模型服务，需要知情同意与数据治理。
- Primo API 密钥配置在前端环境变量中，也需要在生产部署中评估暴露风险。

### 8.5 扩展性与复现限制
- 3 秒轮询适合小规模原型，但未验证大规模并发下的数据库负载和网络开销。
