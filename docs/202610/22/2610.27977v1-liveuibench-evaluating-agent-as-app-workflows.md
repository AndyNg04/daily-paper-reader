## 摘要
应用程序提供了便捷功能，帮助用户完成日常任务。然而，不同用户对同一应用程序可能有不同甚至相互冲突的需求，而同一用户的需求也可能随时间变化。通过 Agent-to-App 或 UI-to-Code 方法生成的应用程序，要实现个性化，可能需要修改其生成的实现。我们提出 Agent as App 这一任务：用户用自然语言表达需求，智能体据此创建个性化应用程序，并在用户使用期间持续提供应用行为。我们实现了 LiveUIAgent，它能够生成针对特定任务的编排，将用户界面、已保存的信息和服务操作连接起来。共享的智能体运行时负责渲染和更新界面，同时执行用户请求的操作。通过复用该运行时来修改编排和界面，为随需求变化而进行个性化提供了一种轻量级基础。我们推出 LiveUIBench，这是一个涵盖个人服务中多样化需求和有序交互的基准。实证结果表明，受评估的模型难以可靠地完成这些工作流。应用程序可能通过许多局部检查，却仍未完成整体任务；而局部覆盖率提高，也可能伴随着已完成工作流数量减少。

## Abstract
Applications provide convenient features for users to complete daily tasks. However, different users may have different or even conflicting requirements for the same application, while the requirements of the same user may change over time. Personalizing applications produced by agent-to-app or UI-to-code approaches can require changes to the generated implementation. We propose Agent as App, a task in which users express their requirements in natural language and an agent creates a personalized application while continuing to supply its behavior during use. We implement LiveUIAgent, which generates a task-specific orchestration connecting the user interface, saved information, and service actions. A shared agent runtime renders and updates the interface while carrying out the requested operations. Revising the orchestration and interface while reusing that runtime provides a lightweight basis for personalization as requirements evolve. We introduce LiveUIBench, a benchmark with diverse requirements and ordered interactions across personal services. The empirical findings show that the evaluated models struggle to complete these workflows reliably. Applications can satisfy many local checks while leaving the overall task unfinished, and greater partial coverage can coincide with fewer completed workflows.

## 1. 核心问题与整体含义

### 研究动机
传统应用通常提供预先固定的功能，但个性化需求具有两种变化：
- **用户之间不同**：同一音乐应用，有人只需要播放按钮，有人需要候选曲目比较和听歌日志。
- **同一用户持续变化**：用户可能先创建歌单，随后要求添加笔记、修改选择，并在下次访问时继续使用已有记录。

Agent-to-App、UI-to-Code 等方法主要让智能体生成应用实现，后续个性化可能仍需修改实现。论文关注的是另一种模式：**智能体不仅创建应用，还在应用使用期间持续解释请求、执行操作和维护状态。**

### 核心研究问题
论文将这一任务称为 **Agent as App（智能体即应用）**，重点考察：

> 一个由智能体创建的应用，能否在提交、修改、扩展和重新访问等连续交互中，使用户意图、界面显示与实际服务状态始终一致？

因此，评价对象不是初始界面是否美观、按钮是否可点击，甚至也不是某次 API 是否成功，而是**整个持续工作流是否完成**。

## 2. 方法论：核心思想与技术流程

### 2.1 应用生命周期建模

论文把应用表示为两个部分：
- **界面与行为定义**：决定应用呈现什么、如何响应操作。
- **已保存状态**：保存此前输入、执行结果和后续操作需要引用的信息。

应用还与外部服务世界交互，例如 Todoist 中的任务、Amazon 中的购物记录。

整个生命周期包含：
1. 根据初始自然语言需求和允许使用的上下文创建应用。
2. 接收后续用户输入，结合已有应用状态与服务状态执行操作。
3. 更新界面、应用记录及外部服务状态。
4. 当需求变化时，调整应用行为，但保留仍然相关的信息。
5. 用户返回时，读取已有结果，而不是重新创建一个应用来替代原应用。

其中，交互阶段表示请求的先后顺序，**不代表真实日历时间上的长期使用**。

### 2.2 LiveUIAgent：任务编排与共享运行时分离

作者实现了 **LiveUIAgent**，核心是生成轻量级的、针对特定任务的编排，将以下要素连接起来：
- 界面组件与输入；
- 提交动作对应的目标；
- 执行这些目标的智能体角色；
- 允许使用的服务；
- 跨交互保存的信息。

系统的职责划分为：
- **编排生成部分**：根据需求定义动作目标及其服务使用范围。
- **UI 设计部分**：生成组件布局。
- **共享渲染器**：结合当前输入和已保存状态呈现界面。
- **应用侧智能体**：解释提交请求、调用服务、保存结果。
- **共享运行时**：持续执行上述过程，避免每次个性化都重建整套执行机制。

普通操作复用已有编排；需求变化时，可以更新编排和界面，同时保留应用身份与相关信息。纯展示类事件也可以不调用模型。

### 2.3 评测流程与成功标准

评测分四步：
1. **准备任务**：提供初始意图、服务初始状态和有序交互目标。
2. **生成应用**：模型只获得初始需求和允许使用的服务文档，后续需求在对应阶段到来。
3. **执行交互**：依次进行打开、提交、修改、后续请求及重新访问。
4. **核验结果**：检查可见输出、服务操作、保存状态及目标记录。

论文使用两个主要指标：
- **完整工作流成功率（FWR）**：一个任务的所有预设断言都通过，才算该任务成功；每个任务权重相同。
- **断言通过率（APR）**：全部通过断言占全部分配断言的比例；每条断言权重相同。

这一区别意味着：**通过很多分散的检查，不等于完成了很多完整任务。**

对于额外的记录中心任务，评测还通过稳定标识符独立读取同一记录，区分：
- 修改原记录与新建替代记录；
- 界面声称修改与服务真实修改；
- 正确保留状态与持续保存错误状态。

## 6. 主要结论与发现

### 6.1 打开应用远比完成工作流容易

代表性结果如下：

| 模型 | 通过全部打开检查 | 完整工作流成功率 | 断言通过率 |
|---|---:|---:|---:|
| Grok 4.6 | 491/500 | **19.60%** | **76.61%** |
| Grok 4.5 | 496/500 | 15.20% | 73.42% |
| Kimi K3 | 395/500 | 14.40% | 61.11% |
| Gemini 3.8 Flash | 463/500 | 12.40% | 65.07% |
| GPT-5.6-sol | 483/500 | 11.40% | 71.09% |

即使最好的模型也只完成 **98/500** 个工作流。界面入口基本可用，并不能保证后续操作可靠。

### 6.2 局部指标与完整任务指标可能给出相反排名
- GPT-5.6-sol 的打开覆盖与 APR 高于 Kimi K3，但 FWR 更低。
- Kimi 的完整成功优势在三个任务类型中都存在。
- Grok 4.5 的打开覆盖略高于 Grok 4.6，但完整成功率反而较低。

因此，仅优化局部检查数量或初始界面可用性，可能高估应用的实际价值。

### 6.3 主要损失出现在提交与修改阶段
对较强模型，首次失败主要发生在：
- 提交请求后执行目标操作；
- 修改此前创建的记录或结果。

重新打开较少成为首次失败，**不能据此证明持久化可靠**：很多任务已在更早阶段失败，首次失败统计会遮蔽后续问题。

### 6.4 服务操作与可见结果经常不一致
在同时包含两类检查的交互中：
- 2,305 个片段通过服务检查、但未通过界面检查；
- 1,351 个片段通过界面检查、但未通过服务检查。

湿地案例进一步表明：用户要求把优先级改为 medium，界面显示已更新，但同一记录在修改、刷新、重新打开后均仍为 low。**状态被保留下来，可能只是错误被保留下来。**

### 6.5 模型互补性存在，但共同难题仍占多数
- 最佳单模型完成：98/500。
- 最佳模型对的成功集合并集：118/500。
- 全部模型成功集合并集：161/500，即 **32.2%**。
- 所有模型均未完成：339/500，即 **67.8%**。

全部模型合并后，多工具任务也仅覆盖 12/130，共享世界任务仅覆盖 10/68。这里的并集是**事后诊断**，不是已经验证有效的集成系统。

## 7. 主要优点

- **任务定位清晰**：把研究重点从“生成应用”推进到“持续承担应用行为”，符合个人智能体的真实使用需求。
- **关注完整生命周期**：覆盖创建、提交、修订和返回，能揭示单次任务评测忽略的状态依赖问题。
- **架构分工合理**：任务编排与共享运行时分离，为轻量级个性化提供了可实现的路径。
- **证据类型丰富**：联合检查界面、操作轨迹、应用状态和服务记录，避免把“显示成功”当成“实际完成”。
- **指标互补性强**：FWR 与 APR 分别衡量完整可用性与局部进展，有助于解释排名反转。
- **分析边界较谨慎**：明确区分首次失败与内部成因、持久化与正确性、事后成功并集与真实集成效果。

## 8. 不足与局限

### 方法与效果验证
- 论文更偏向**任务定义、系统实现与基准诊断**，并未证明共享运行时或编排机制本身带来多少收益。
- “轻量级个性化”缺少成本、响应延迟及维护开销的量化对照。
- 未报告真实用户研究，无法直接判断交互体验、信任和需求表达成本。

### 评测覆盖
- 模拟服务无法充分代表真实系统中的网络故障、权限变化、接口漂移及不可逆操作。
- 当前工作流相对短，不能证明应用能在数周或数月的反复修改中持续可靠。
- 大规模评测通过声明动作执行，并不等同于完整的鼠标、键盘或触屏端到端测试，可能遗漏界面交互障碍。

### 指标与偏差风险
- **断言全通过不等于所有语义要求都满足**：原始服务检查有时只确认调用或状态变化，并不独立核验每个字段的含义。
- FWR 很严格，但也受任务长度和断言数量影响；不同任务族的难度差异不能简单归因于组织结构。
- 基准构建使用了生成式 AI，虽有人类审阅，仍可能存在模板化、覆盖盲区或模型偏好。
