## 摘要
AI 编码智能体正日益融入软件开发工作流。然而，大多数编码智能体研究依赖于类似 SWE-bench 的基准测试，这类测试假设智能体能够沿单一轨迹自主运行。这一假设并不能反映现实中的使用方式，因为开发者会与智能体进行交互式协作。为弥补这一研究空白，我们研究了真实场景中人类参与的智能体轨迹，重点分析了 7,581 个具有公开会话数据的 Copilot 撰写的 PR。我们发现，58% 的 Copilot PR 没有人工干预；而当开发者介入时，协作过程较为简短（人机交互循环次数的中位数为 2）。与未合并的 PR 相比，已合并的 PR 在初始轨迹中的迭代次数也往往更少。我们还发现，首次人工干预后的轨迹在迭代次数上显著减少了 20.8 次，持续时间显著缩短了 8.4 分钟。然而，后续干预后的轨迹迭代次数仅略有减少，持续时间也没有显著变化，这表明大部分工作是在初始轨迹中完成的。对典型 PR 的定性分析解释了这一模式：开发者的许多干预都是范围明确的小型请求，Copilot 能在后续较短的轨迹中完成这些请求。我们还展示了开发者与 Copilot 协作的多种方式，包括通过反馈委派任务，以及自行添加提交。不过，我们发现，开发者可能需要在 PR 中多次（有时是重复地）引导 Copilot，甚至需要在 PR 的多个版本中持续引导。

## Abstract
AI coding agents are increasingly integrated into software development workflows. However, most coding agent studies rely on benchmarks similar to SWE-bench, which assume autonomous agents operating in a single trajectory. This assumption does not mirror real-world usage, where developers interactively collaborate with agents. We address this gap by studying human-in-the-loop agent trajectories in the wild, focusing on 7,581 Copilot-authored PRs with publicly accessible session data. We find that 58% of Copilot PRs have no human intervention, and that when developers do intervene, collaboration is brief (median of 2 Human-AI loops). Merged PRs also tend to have fewer initial trajectory iterations than unmerged ones. We also find that the trajectory following the first human intervention exhibits a significant drop of 20.8 iterations and 8.4 min in duration. However, trajectories following later interventions show minimal iteration drops and no significant duration change, signifying that most of the work happens in the initial trajectory. Our qualitative analysis of illustrative PRs explains this pattern: many developer interventions are small, focused requests that Copilot completes in shorter later trajectories. We also illustrate that developers collaborate with Copilot in multiple ways, including delegated work through feedback as well as adding their own commits. However, we find that developers may need to guide Copilot through multiple (sometimes repeated) interventions in the PR, or even across multiple editions of the PR.

### 研究背景与动机
- SWE-bench 等主流编码智能体基准，通常要求智能体在**没有后续人工反馈的单次自主执行过程中**完成任务，并通过测试判断成功与否。
- 真实开发则更复杂：开发者可能补充需求、提出实现建议、指出错误、直接修改代码，甚至关闭当前 PR，再让智能体重新尝试。
- 因此，仅分析自主执行轨迹，难以完整理解编码智能体在实际软件工程中的工作方式与价值。

### 核心研究问题
论文围绕 GitHub Copilot 云端编码智能体提出四个问题：
1. 一个 PR 生命周期中存在多少人机交互？
2. 智能体投入了多少迭代和执行时间？
3. 人工介入前后，智能体的工作量如何变化？
4. 开发者实际上如何与智能体协作？

**整体意义**：将研究单位从“智能体的一次自主运行”扩展为“包含多次反馈、后续执行和人工提交的 PR 生命周期”。这是一项**真实场景观察性研究**，而非提出新模型或提升基准成绩的算法论文。

## 2. 方法论：PR 生命周期建模与混合方法分析

### 2.1 核心表示：扩展 Thought–Action–Result
论文基于已有的“思考—行动—结果”轨迹结构，增加对交互式开发的支持：

- **迭代（iteration）**：一个推理与执行周期，由可选的思考文本，以及零个或多个“行动—结果”对构成。
- **轨迹（trajectory）**：智能体一次连续执行会话，由多个迭代组成。
- **人工介入（human intervention）**：开发者明确使用 `@copilot` 指向智能体、并触发后续工作的评论或评审意见。
- **人机循环（Human–AI loop）**：一次人工介入及其对应的后续智能体轨迹。
- **PR 生命周期**：初始轨迹，随后接零次或多次“人工介入—后续轨迹”。

与传统单轨迹表示相比，该结构支持**每次思考对应多个动作，以及同一个 PR 包含多次执行轨迹**。

### 2.2 数据提取与编码流程
1. **提取 PR 元数据**：仓库、关联 issue、描述、合并状态、评论、提交记录等。
2. **恢复初始信息**：利用 PR 描述的编辑历史，提取初始计划和额外指令。
3. **抓取会话**：从 PR 页面发现 Copilot session 链接，通过无头浏览器读取完整渲染内容。
4. **解析轨迹**：
   - 将代理消息和“Thinking”块识别为思考；
   - 将工具调用解析为动作及其结果；
   - 根据思考与动作的先后关系划分迭代；
   - 记录每条轨迹的执行时长。
5. **匹配人工介入**：按时间顺序，将带 `@copilot` 的评论关联到随后启动的第一个会话；多个评论若对应同一会话，则合并为一次介入。
6. **分类 PR 类型**：采用 AIDev 提供的、基于 `gpt-4.1-mini` 的脚本，区分修复、功能、文档、测试等类型。

### 2.3 统计分析
- 数值指标的组间比较：**Mann–Whitney U 检验**，并报告 Cliff’s delta。
- 类别变量关联：**卡方检验**，并报告 Cramér’s V。
- 多重比较：采用 **Benjamini–Hochberg 校正**。

针对介入前后变化，论文使用线性混合效应模型：

\[
Y_{ij}=\beta_0+\beta_1 Post_{ij}+u_i+\epsilon_{ij}
\]

其中：
- \(Y_{ij}\)：轨迹的迭代次数或执行时长；
- \(Post_{ij}\)：是否为介入后的轨迹；
- \(u_i\)：PR 层面的随机截距，控制不同 PR 的基础差异；
- \(\beta_1\)：介入前后工作量的估计变化。

作者分别分析**首次介入**和**后续介入**，避免直接混合“初始任务实现”和“后续局部修改”。

## 6. 主要结论与发现

### 6.1 多数 PR 没有触发后续人工反馈，但不能直接等同于完全自主
| 类别 | PR 数量 | 合并率 |
|---|---:|---:|
| 无介入 | 4,376，约 58% | 62% |
| 有介入 | 3,205，约 42% | 78% |

- 有介入 PR 的循环次数**中位数为 2，最多为 25**。
- 无介入且已合并的 PR 中，仍有 **38% 包含开发者自行追加的提交**。
- 其余约 **62% 没有开发者追加提交**，被论文定义为“完全自主”；这不意味着没有人工审阅、讨论或合并决策。

### 6.2 介入与更高合并率相关，但更多介入不一定更好
- 有介入与无介入的合并率差异显著，效应量较小：**Cramér’s V = 0.17**。
- 在有介入 PR 内，已合并和未合并组的循环次数中位数都为 2；介入数量与结果的关联很弱。
- 按任务类型分析，介入与更高合并率的关联主要在修复、功能、文档、测试类中成立。

### 6.3 初始执行是重要工作阶段，初始轨迹更长通常与较差结果相关
以下均为中位数：

| 指标 | 全部 PR | 无介入 PR | 有介入 PR |
|---|---:|---:|---:|
| 初始轨迹迭代数 | 35 | 33 | 38 |
| 全生命周期迭代数 | 44 | 33 | 72 |
| 初始轨迹耗时 | 14.9 分钟 | 14.0 分钟 | 16.4 分钟 |
| 全生命周期耗时 | 19.2 分钟 | 14.0 分钟 | 33.4 分钟 |

- 已合并 PR 的初始迭代数通常更少：整体中位数为 **34 对 39**。
- 这与“更困难的任务需要更多探索或更容易陷入反复尝试”的解释一致，但不能证明迭代多导致失败。
- 功能类存在例外：已合并功能 PR 的总迭代数略多，且效应量可忽略。

### 6.4 首次介入后轨迹明显缩短，后续变化有限
- 首次介入后：
  - 迭代数从约 **41.1 降至 20.3**，减少 **20.8 次**；
  - 耗时减少 **8.4 分钟**；
  - 均显著。
- 后续介入后：
  - 迭代数从约 **20.6 降至 19.2**；
  - 耗时无显著变化，\(p=0.74\)。

定性案例表明，首次执行往往承担完整实现，后续反馈多是命名调整、局部修复、补充要求等小范围任务。因此，**轨迹缩短不应直接解释为人工反馈提高了同等任务的执行效率**。

### 6.5 实际协作包含委派、直接修改和重复探索
案例中出现的协作方式包括：
- 要求替换实现方案、补充需求、纠正误解、修复错误；
- 开发者直接提交代码，而非继续委派；
- 关闭原 PR 后复用其中的代码；
- 对同一 issue 多次重新分配 Copilot，创建新的 PR。

这意味着，**单个 PR 未合并不一定代表代理贡献完全无效，单个 PR 内的循环数也可能低估任务层面的协作成本**。

## 7. 优点与亮点

- **研究问题贴近实践**：关注真实开发中的反馈与共同修改，而不只看自主解题成功率。
- **提供可复用的数据表示**：将轨迹、人工介入和 PR 生命周期统一编码，为后续行为分析提供基础。
- **样本规模较大**：覆盖数千 PR、上千仓库，比少量交互案例更有描述性价值。
- **区分概念清晰**：没有把“无 `@copilot` 反馈”直接等同于“没有人工代码贡献”。
- **分离首次与后续介入**：识别两类比较的任务性质不同，减少简单汇总带来的误导。
- **定量与定性相互补充**：案例揭示了跨 PR 重试、代码复用及未标记评论不可见等统计汇总难以体现的问题。

## 8. 不足与局限

### 8.1 覆盖范围有限
- 仅研究 **Copilot 云端智能体**，不涵盖 IDE agent mode 或其他代理。
- 仅包含至少 100 stars、明确由 issue 分配、且已关闭的 PR。
- 排除了仍在进行的任务，以及部分零迭代失败，可能影响对整体使用情况和失败率的估计。
- 结果依赖特定时期的 Copilot 产品规则，未必适用于其他版本。

### 8.2 代理指标不能完整代表成功与成本
- **合并不等于代码正确，未合并不等于任务失败**：任务可能过时，代码也可能被转移到其他 PR。
- 迭代数和时长不能全面反映 token 成本、动作复杂度、人工审阅时间或最终代码质量。
- “完全自主”仍可能包含大量人工判断和审阅，因此不是“完全无人参与”。

### 8.3 介入识别与解析存在误差
- 主要捕获显式 `@copilot` 且触发后续工作的反馈，无法覆盖线下沟通、隐式指导或未成功触发的意图。
- 基于时间顺序匹配评论与会话，不保证精确恢复每条反馈实际被处理的关系。
- 网页解析依赖 HTML 结构；人工核验规模较小。
- PR 类型来自 LLM 分类，文中未提供充分的人工分类准确率验证。

### 8.4 因果解释与统计假设仍有限
- PR 随机截距不能消除所有仓库、任务和开发者层面的混杂因素。
- 首次轨迹与后续轨迹的任务范围天然不同，工作量下降部分可能由这一结构决定。
- 相邻后续介入比较可能重复涉及同一轨迹；文中对该依赖结构、模型诊断和稳健性检验的披露有限。
- 大样本下显著性不等于实际收益，尤其部分结果效应量很小。

### 8.5 尚未回答“何时值得继续协作”
论文没有直接测量开发者耗时、认知负担和替代工作成本，因此无法确定：
- 何时继续指导智能体比自己修改更划算；
- 多少次失败后应停止委派；
- 更清晰的初始需求能减少多少反馈轮次。
