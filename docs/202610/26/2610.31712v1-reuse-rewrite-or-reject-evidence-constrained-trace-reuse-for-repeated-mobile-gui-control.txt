## ABSTRACT 

Mobile GUI agents frequently perform repetitive tasks with similar interaction procedures. Reusing previous executions can reduce redundant LLM inference and execution overhead, but variations in user instructions and execution envi-ronments may invalidate previously successful actions. We systematically char-acterize these variations into six representative categories and observe that such changes do not necessarily invalidate entire procedures: individual transitions can remain reusable when validated against the current task context and interface state. Based on this insight, we propose graph–text templates for selective execution-trace reuse. The graph captures UI states and action transitions, while the text encodes task intent, procedural structure, and typed slots for variable content. A record–template–replay framework constructs templates from verified execu-tions and leverages the current instruction and live UI state to reuse, adapt, or discard individual transitions. Given an execution trace, our framework reduces LLM inference token consumption by approximately 80% on average across five base agents on AndroidWorld, with most agents achieving at least 1.5 × execution speedup over LLM-only execution. In real-device evaluations on Android and HarmonyOS, our framework achieves action reuse ratios of 70.7–79.8% while maintaining over 2 × execution speedup in most evaluated configurations. 

## 1 INTRODUCTION 

A central goal for mobile GUI agents is to become faster as they accumulate experience. In everyday use, an agent repeatedly encounters familiar tasks and interaction patterns, creating opportunities to reuse what it has already learned from execution. An agent that invokes a large language model (LLM) before every action continues to pay for decisions it has successfully made before. Turning previous executions into reusable experience can reduce these repeated model calls and user waiting time. The question is how to sustain this benefit as task conditions change. Two obstacles remain: changes in the environment and instruction. Even when the request remains the same, the application may be in a different state, its interface may have changed, or a dialog may interrupt the expected workflow. Conversely, a familiar interface may receive a request with a different value, target, or wording. These changes can make a previously successful action unnec-essary, inappropriate, or insufficient for the current task. Repeated use therefore requires an agent to determine which parts of its experience remain useful under the current conditions. Addressing these two sources of variation is central to making experience translate into faster execution. We organize these obstacles into six main categories. Environment changes comprise background-state changes, layout and workflow changes, and modal interruptions; instruction changes comprise parameter changes, entity substitutions, and goal-expression changes. This categorization guides our analysis of when historical steps can be retained, need adaptation, or should be abandoned. We introduce their implications for reuse in Section 3 and develop the detailed case analysis in Section 4.

MobiMem regenerates variable-step actions when parameters change, while SkillDroid and PreAct execute parameterized skills or programs (Liu et al., 2025; Chen et al., 2026b; Li, 2026). We instead organize reuse around candidate transitions in a unified graph–text template: semantic descriptions retrieve executable structure, local annotations expose replaceable content, and live evidence deter-mines whether each transition is reused, rewritten, or rejected. Each admitted transition is further guarded by pre- and post-action evidence checks, with rejected or failed steps falling back to the base agent. We propose an evidence-constrained record–template–replay framework. During recording, the agent stores each action with its target and checked before-and-after states (Figure 1). The add-to-cart example links the selected item and quantity to the resulting cart state. Template extraction then preserves reusable procedure structure, exposes variable content as typed slots, and retains in-compatible paths as separate branches. The resulting graph–text template integrates a capability description for semantic retrieval with executable UI transitions. Within the same template, local annotations mark entities and values that can be rebound to the current request, allowing applicable parts of a recorded procedure to be reused while changed steps are rewritten. During replay, the current instruction and live interface determine whether a candidate transition can be reused, rewrit-ten with an explicitly supplied value, or rejected. Each admitted transition undergoes a pre-check, one-step execution, and a post-check; insufficient evidence or a failed check returns control to the same base agent. The controller thus reuses applicable steps while adapting to or recovering from changes elsewhere. We first evaluate the framework on AndroidWorld, which provides reproducible mobile tasks with parameterized initialization and programmatic outcome checks (Rawles et al., 2025). Across five base agents, we measure task success, executed reuse, token consumption, LLM calls, and execution time. Given a verified execution record, our framework achieves 82.0–87.5% executed reuse and 1.2–1.9 × execution-time speedup. These tests establish a basis for assessing repeated execution, while comparison with practical phone use highlights differences in devices, operating systems, interface languages, and operating conditions. Although AndroidWorld supports variation in task parameters and initial states, its benchmark setting alone cannot establish how reuse performs across these real-use conditions. This motivates extending the evaluation to physical devices. We therefore conduct real-device evaluations on OnePlus 13, OPPO Find X8, Redmi K50, and Huawei Pura 80, spanning Android and HarmonyOS. Building on the six-category analysis, the quantitative studies focus on three representative conditions: background-state changes, parameter changes, and paraphrased instructions. These conditions examine whether the controller can account for a changed state, bind a newly requested value, and retrieve a familiar procedure under different 2wording. We report task success and execution efficiency, with component ablations examining state rechecking, value binding, and semantic retrieval. Across these conditions, our framework achieves 1.8–3.9 × execution-time speedup. Together, these studies examine repeated-execution efficiency and the mechanisms needed to reuse experience under environment and instruction changes. Our contributions are threefold. First, we analyze environment and instruction changes as two cen-tral obstacles to faster repeated GUI execution and organize them into six main categories of varia-tion. Second, we develop graph–text transition templates and evidence-constrained selective replay to retain applicable actions, adapt explicitly bound values, and return control to the base agent when reuse is unsupported. Third, we combine AndroidWorld evaluation with experiments on four phone models spanning Android and HarmonyOS, measuring execution efficiency and task outcomes and using targeted ablations to examine adaptation to state, parameter, and wording changes. 

## 2 RELATED WORK 

GUI Agents for Mobile. AutoDroid and AppAgent support mobile automation through app knowl-edge or demonstrations, while UI-TARS integrates perception and action modeling (Wen et al., 2024; Zhang et al., 2025b; Qin et al., 2025). For efficient execution with smaller models, AutoDroid-V2 generates scripts from app documentation, Ferret-UI Lite develops compact policies, MobileEx-plorer overlaps inference with exploration, and UI-KOBE constrains runtime decisions through app graphs (Wen et al., 2025; Yang et al., 2025; Huang et al., 2026; Chai et al., 2026). These approaches address model and planning costs through complementary mechanisms. 

Memory and Skill Learning for GUI Agents. Agent Workflow Memory, Agent S, and LearnAct organize workflows, experience, or demonstrations to support subsequent execution, with Agent Workflow Memory also offering an executable action-space variant (Wang et al., 2025b; Agashe et al., 2025; Liu et al., 2026b). UI-Mem, MementoGUI, and MMSkills further use hierarchical experience or multimodal memory and procedures (Xiao et al., 2026; Zeng et al., 2026; Zhang et al., 2026). Executable skill construction takes several forms: callable APIs in SkillWeaver, recur-sive parameterized skills in SCAFFOLD, and state-machine memory or execution graphs in Actio-nEngine and CUA-Skill (Zheng et al., 2025; He et al., 2026; Zhong et al., 2026; Chen et al., 2026c). WebXSkill and SGDR pair executable skills with text for context-aware retrieval (Wang et al., 2026; Li et al., 2026a). EvoSkill-GUI, KnowAct-GUIClaw, and online skill evolution maintain and revise persistent procedures (Chen et al., 2026a; Li et al., 2026b; Hu et al., 2026). 

Trace Replay for GUI Agents. V2S and GPA derive replayable procedures from recordings or demonstrations (Havranek et al., 2021; Zhao et al., 2026b). Mobile-Agent-E and AppAgentX learn executable shortcuts, while AgentRR adds experience abstractions with precondition and parameter checks (Wang et al., 2025a; Jiang et al., 2025; Feng et al., 2025). MobileGPT, MobiAgent, and MobiMem use structured memories to reuse subtasks or local actions: MobileGPT adapts param-eters and UI attributes with model-assisted parameter filling, MobiAgent combines action caching with UI-change detection, and MobiMem reuses prefixes and suffixes around steps requiring fresh reasoning (Lee et al., 2024; Zhang et al., 2025a; Liu et al., 2025). Executable Agentic Memory uses a lightweight value model for graph search, whereas MemoryPlayback uses confidence to switch between replay and VLM reasoning (Qin et al., 2026; Luo et al., 2027). PreAct, SkillDroid, and EchoPath combine parameterized replay with execution checks and agent fallback or repair (Li, 2026; Chen et al., 2026b; Zhao et al., 2026a). SkillDroid checks state at each step and skips satisfied steps; its semantic matching invokes an LLM for confirmation and slot extraction. Selective replay, parameter adaptation, and fallback are therefore established capabilities. The comparison concerns admission/rewrite evidence under changed intent and state, and its acquisition cost. 

Action Verification for GUI Agents. VeriSafe Agent checks actions against formalized user intent, while SenseAct uses typed control primitives and programmatic postconditions (Lee et al., 2025; Cai et al., 2026). AppAgent-Claw validates outcomes after execution (Song et al., 2026); ReUseIt, Con-tractSkill, and SKILL.nb combine pre/postcondition checks with local recovery in reusable work-flows or skills (Liu et al., 2026c; Lu et al., 2026; El Hattami et al., 2026). ## 3 METHOD 

To make repeated mobile tasks faster, the controller must replace selected LLM calls without re-playing actions that have become stale. Both the execution environment and instruction can change. We separate memory formation from memory use: the record phase captures evidence from an exe-cution, template extraction turns that evidence into a reusable graph–text procedure, and the replay 

phase admits one transition at a time under live checks. The resulting decision is REUSE , REWRITE ,or REJECT ; rejection or a failed postcheck returns control to the fallback policy. 

Environment and instruction changes. Historical actions can become invalid under an unchanged instruction. Background state and TOCTOU may make a goal true at check time but false at action time, so duplicate or inverse actions are suppressed and the state is checked again before execu-tion. Layout and workflow drift may move a target or change the required path; semantic relocation can handle the former, while the latter requires fallback. Overlays and interruptions can block the underlying page; only separately verified benign overlays are handled locally, whereas permission, login, payment, and task-relevant dialogs remain blocking states. These changes usually invalidate individual transitions rather than entire trajectories. The same environment can receive a different request. Parametric changes in quantity, time, or amount can be rewritten only when the live in-struction supplies a matching typed slot. Entity changes require re-grounding products, contacts, or places in the current UI. Paraphrase and reference changes can share a canonical procedure when their intent is supported; an under-specified preference reference is rejected rather than silently filled. Instruction changes allow constrained local rewriting, not implicit replacement of critical values. 

Recording transition evidence. During record , the fallback agent completes the task normally while the system stores the evidence needed for later decisions: the observable state before and after each action, the action and its target, the procedure step, any typed value, and the resulting progress or completion signal. Extracting reusable templates. Template extraction consolidates recorded transitions into a graph– text representation. Compatible observable states and actions are merged, while conflicting states remain separate branches. Values that may change across instructions are represented as typed slots; stable navigation and progress structure are kept as reusable edges. Transitions with missing evi-dence, an ungroundable target, or a failed terminal outcome are excluded from the released template. An “ideal” template is as reusable as the record supports without hard-coding incidental state. The resulting transition contract is 

e = ( vi, a, v j , z ), z = ( g, k, s, r, ϕ −, ϕ +), (1) where the text procedure supplies intent g and typed slots k, the graph supplies source and target states vi, v j and selectors s, and ϕ−, ϕ + encode the evidence required before and after the action. The text view states what progress is intended; the graph view states how that progress changed a concrete UI. These complementary views correspond to the graph and text panels in Figure 1. 

Guarded selective replay. During replay , the current instruction and live UI select a candidate edge from the template. Figure 2 illustrates this process for a request to order two milk teas: the text procedure identifies the intent and quantity slot, UI-graph retrieval finds a compatible candidate, and live grounding checks its target and execution conditions. These retrieval checks identify a candidate; execution additionally requires evidence that its action remains valid for the current task. Specifically, the candidate’s procedure step must agree with the current instruction, and its source-state conditions and target selector must be supported by the live UI. Matching the historical page alone cannot justify copying its action payload. The controller emits REUSE when the payload remains valid under these conditions, or REWRITE when a changed value is explicitly bound to a compatible typed slot. If the required value or target cannot be established, it emits REJECT even when the navigation context matches. High-risk entity/value pairs require stronger evidence and cannot be filled from preference alone. Figure 3 (left) summarizes the checks and decisions. For an admitted edge, the controller refreshes the required evidence in a pre-check, executes the ac-tion once if the check passes, and performs a semantic post-check. The post-check must confirm the expected state change or completion predicate using the current slot bindings; a page change alone is not sufficient for every action. A failed post-check blocks the edge for the current episode and re-turns control to the fallback policy, preventing one mismatch from propagating through a trajectory. 5The right panel of Figure 3 shows how a rejected edge remains unexecuted while fallback produces a new observation for realignment. Each subsequent transition is rechecked before execution. For example, changing “order one jasmine milk tea” to “order two jasmine milk teas” connects the recorded transition in Figure 1 to the live task in Figure 2. Valid navigation transitions remain reusable, while the quantity-setting action is rebound to 2 and checked against the live UI. Its post-check must confirm the displayed quantity. If the quantity control cannot be grounded, that transition is rejected and control returns to the base agent, following Figure 3. Adding the item to the cart is a separate transition whose post-check must confirm the requested item and quantity; it does not itself establish completion of the order. Thus, both action and verification change. 

## 4 EXPERIMENTS 

We evaluate whether historical experience can support reliable and efficient repeated mobile execu-tion. We report success and efficiency on AndroidWorld and on real phones under background-state changes, parameter changes, and paraphrased instructions. Three real-device ablations examine how to preserve valid actions, adapt values, and retrieve procedures across paraphrases. 4.1 OVERALL RESULTS ON ANDROID WORLD AND REAL -W ORLD TASKS 

Benchmark and agents. AndroidWorld is a widely adopted benchmark for online mobile GUI agents. Its original suite contains 116 tasks across 20 Android applications, with parameterized task initialization and programmatic success evaluation (Rawles et al., 2025). We evaluate our replay-assisted pipeline with GUI-Owl-7B, MAI-UI-8B, GELab-Zero-4B-preview, AutoGLM-Phone-9B-Multilingual, and UI-TARS-1.5-7B. Token consumption and LLM calls decrease across all reported settings. 74.2 REAL -W ORLD EVALUATION AND ABLATIONS 

Real-device evaluation is essential for understanding how reduced LLM inference translates into practical execution speedups across devices and operating systems. Our timing measurements on AndroidWorld show that pre-action preparation and post-action state acquisition together can even account for 40.02% of total execution time. The benchmark protocol involves repeated UI-structure acquisition during these stages, reducing the fraction of runtime spent on LLM inference and thereby limiting the overall speedup achievable by avoiding model calls. This helps explain the compara-tively modest speedups on AndroidWorld despite substantial reductions in LLM calls. We therefore extend our evaluation to four phone models spanning Android and HarmonyOS, optimizing UI-structure acquisition and reducing its frequency to lower observation overhead. This increases the fraction of runtime that can benefit from trace reuse, allowing us to assess its acceleration benefits alongside robustness to changes in device state and user instructions. Table 2 summarizes six categories of variation in real-world phone use. We evaluate three repre-sentative conditions: background-state changes preserve the instruction while changing the device state; parameter changes modify a requested value within a familiar procedure; and paraphrased instructions change wording while preserving intent. Evaluation protocol. We evaluate record–live task pairs on physical Android and HarmonyOS phones. Each case compares replay only, two cumulative component additions, and the full con-troller under similar live instructions, initial states, and completion criteria. Figure 4 reports human-assessed outcomes. For automated re-evaluation, we specify an independent task-specific verifier that checks the requested object, values, and terminal state against predefined predicates using ac-cessible system/application state or structured UI evidence, following AndroidWorld’s state-based evaluation principle (Rawles et al., 2025). 

Ablation analysis. For background-state changes, parameter changes, and paraphrased instruc-tions, the full configuration improves success across all five agents; the full configuration reaches 93.0–98.0% success, exceeding replay only by 38.0–45.0 percentage points. Given verified execution records, our results support selective trace reuse as a way to reduce repeated model inference and execution time in the evaluated settings. The framework combines applicable transitions, local rewriting of explicitly bound values, and fallback to the base agent within the same execution. This allows useful parts of prior experience to remain available as instructions and UI states change, with each reused action checked against current conditions. 

## 5 LIMITATIONS AND BROADER IMPACT 

Reuse depends on fallback coverage and UI observability; novel free-form content, inaccessible metadata, rapid visual changes, and unsupported workflows limit reuse. We evaluate five Android-World base agents and selected real-device changes in background state, parameters, and instruction wording. Combined variations, cross-system trajectory transfer, and long-term adaptation need fur-ther study. Execution-time ratios omit recording and template-construction cost amortization. Reusing private actions can expose stale or sensitive choices. Single-step admission, explicit high-risk slot checks, post-state validation, fallback, audit logs, and permission boundaries mitigate but do not eliminate this risk. Real-device studies should use reversible tasks or sandbox accounts; learned preferences must not be treated as authorization. 

## 6 CONCLUSION 

Experience can accelerate repeated mobile GUI execution when reusable procedure structure is pre-served and each action is reassessed under current conditions. We analyzed six categories of envi-ronment and instruction changes and developed a record–template–replay framework that captures verified executions as graph–text templates. By combining task intent with live UI evidence, the con-troller retains applicable transitions, rewrites explicitly specified values, and invokes the base agent when reuse is unsupported. Given a verified execution record, evaluation across five base agents yields 1.2–1.9 × execution-time speedup on AndroidWorld. In real-device evaluations on Android and HarmonyOS, our framework achieves action reuse ratios of 70.7–79.8% while maintaining 1.8– 93.9 × execution-time speedup. Together, these findings support selective reuse as a means of trans-lating past execution into fewer repeated model decisions and faster execution under changing task conditions.

A.2 TEMPLATE EXTRACTION , MERGING , AND CONFLICT BRANCHES 

Extraction preserves stable navigation and procedure structure while exposing changeable quanti-ties, times, and entities as typed slots. Two observations can support a shared template edge only when their intended progress, relevant source-state conditions, action semantics, and checked out-comes are compatible. Visual resemblance alone does not justify merging. For example, settings pages with a toggle off or on may share navigation but require different action preconditions. Conflicting conditions remain separate branches. An edge that opens a product’s specification sheet cannot be replaced by one that directly adds the product to the cart unless the different preconditions and effects are represented. Source-record links preserve the evidence behind each branch. A tran-sition with missing evidence, an ungroundable target, or a failed terminal outcome does not become an executable template edge merely because another record contains a similar instruction. A.3 RETRIEVAL , SLOT BINDING , AND LIVE TARGET GROUNDING 

Retrieval first identifies a procedure compatible with the live instruction and application context. The controller then checks candidate transitions against procedure progress and the current UI. Retrieval supplies candidates; a high similarity score does not itself authorize an action. A slot binding connects a value in the live instruction to the action that uses it. A changed duration, for example, must update the duration-bearing action and the expected outcome. Navigation edges 14 may remain reusable. Entity substitutions additionally require identifying the requested live product, contact, or location. An ambiguous reference does not justify silently importing a historical value. Target grounding uses current observations to identify the control that implements the candidate action. A displaced control may remain usable if its semantics and state are supported. A miss-ing control, conflicting identity, or blocking window instead requires rejection or fallback. The paraphrase comparison separately examines app-level semantic retrieval and soft task matching; the cumulative configurations are summarized in Section B.4. A.4 PRECHECK , POSTCHECK , AND FALLBACK 

Before execution, the controller refreshes the evidence needed by the selected edge and checks whether the goal is already satisfied. It emits REUSE for a supported unchanged action, REWRITE 

for a supported action whose typed payload is rebound, and REJECT when evidence is missing or contradictory. Rejection executes no GUI action; fallback follows it, not as a fourth decision. An admitted action executes once. Its postcheck verifies the expected semantic effect; a page change alone does not prove that a requested value or entity is correct. A failed postcheck blocks that edge for the current episode and returns control to the base agent. The next decision uses a fresh observation.

B.3 RECORD –LIVE COMPARISONS AND OUTCOME JUDGMENT 

A record–live pair connects an earlier verified execution with a current request and device state. Taobao: search entry versus cart entry. Record task. Open Taobao, search for Smartphone A, open the first matching product, tap Add to Cart, select the default configuration, and confirm adding one unit to the cart. 

Live task. Open the cart, open its first item corresponding to Smartphone A, and add one more unit of that product to the cart. 

Shared suffix. Once product identity and the required option-selection state agree, the relevant product-configuration and add-to-cart transitions can be considered for reuse. The instruction’s extra con-firmation tap is a UI step, not a request to add another unit.

The current follow state must also be checked so that an already satisfied goal does not trigger an inverse action. C.4 RELATION TO THE VARIATION TAXONOMY 

The main-text quantitative comparisons cover background-state changes, parameter changes, and paraphrased instructions. The examples below explain these conditions. They are illustrative con-trolled pairs rather than additional measured episodes. 

Background-state changes. For “Turn on dark mode,” the record begins with dark mode off while the live state already has it on. The instruction and relevant page remain fixed; the changed factor is the toggle state. Correct completion preserves the enabled state without another toggle. This differs from the Taobao suffix example, whose live instruction requests an additional item. 

Parameter changes. A record sets a 10-minute timer, whereas the live instruction requests a 15-minute timer from the same initial timer state. The duration changes while the procedure remains stable. Navigation can be reused, but duration entry and its expected effect use the live value. Table 4 specifies this illustrative transition. Shopping quantities and hotel dates provide other typed values in the task descriptions; their presence alone does not establish a controlled parameter-change experiment. 

Paraphrased instructions. “Turn on Wi-Fi” and “Enable Wi-Fi” express the same goal from the same initial off state. The changed factor is wording, so retrieval should identify the same procedure while execution still checks the live toggle. A contextual reference such as “my usual item” instead requires additional evidence and is not an equivalent paraphrase when its referent is unresolved. 

Other variation categories. Layout/workflow changes, modal interruptions, and entity substitu-tions complete the six-category taxonomy. A displaced product requires live grounding; an inserted selection page changes the procedure; a blocking dialog changes action admissibility; and a substi-tuted destination requires resolving the new place. These categories explain possible mismatches but are separate from the three quantitative conditions. The shared-suffix examples likewise explain task structure without adding a new quantitative evaluation. 

## D METRIC DEFINITIONS AND SUPPLEMENTARY RESULTS 

D.1 TASK SUCCESS AND EVALUATION SCOPE 

Task success is the number of verified successful episodes n divided by the number of evaluated eligible episodes N . Failed actions, budget exhaustion, and human safety terminations contribute failures. Setup exclusions, if any, are distinct from failures within the evaluated set. For Android-World record-conditional success, N counts trials supported by records from successful base-agent executions, and n counts successful trials within that set. Table 1 reports base success multiplied by this conditional rate, rounded to one decimal place. This product is computed from the reported aggregate percentages rather than a separate full-suite evaluation. In the real-world ablations, all configurations are evaluated on the same tasks designed for practical usage scenarios and executed on physical phones. This task set is not restricted to tasks previously completed successfully by the base model. The full configuration combines replay with model fallback; its success rate is not conditional on replay-only success. The ablation plots report these per-configuration success rates directly. The real-world “Success score with replay” column in Table 1 is the arithmetic product of the replay-only and full-configuration percentages, divided by 100; it is a derived score, not the mea-sured success rate of the full controller. Real-device results identify the variation and configuration. Counts are not reconstructed from rounded percentages. D.2 EXECUTED REUSE AND ZERO -ACTION COMPLETION 

Executed reuse counts actions supplied by replay without a model call. A local rewrite counts only when it meets this condition. Retrieved or rejected candidates are not executed reuse. Total executed 19 actions include replay, fallback, and recovery actions. All reported replay rates use the task-mean definition rtask in Equation 2: first compute the ratio of replayed actions to all executed actions for each episode with at least one action, then take the arithmetic mean across episodes. Each episode receives equal weight. The pooled step rate rstep instead weights episodes by their action counts; it is used in the explanatory cost relationships below, not as the reported replay-rate aggregation. If the goal is already satisfied and the controller correctly stops without a GUI action, the episode remains eligible for task success. Such an episode is a zero-action completion: its action-based reuse ratio is undefined, so it is excluded from action-based reuse-rate aggregation. A false completion declaration is a failure. Any model calls used to verify completion still contribute to cost. D.3 PAIRED COSTS , COVERAGE , AND TIMING BOUNDARIES 

An efficiency pair matches the task instance, initial state, model, and completion criterion between an LLM-only execution and execution assisted by the full replay controller. The real-device replay-only success baseline is not this cost reference. Cost and execution-efficiency statistics include only pairs in which both executions succeed. Task success is evaluated over the eligible task set and reported separately from efficiency on successful pairs. Paired-success coverage is defined as the number of successful pairs divided by all eligible pairs. ## E TASK EXAMPLE PRESENTATION AND DATA PRIVACY 

Privacy and neutral presentation. The task descriptions use stable aliases within each example so that product, store, creator, and destination relationships remain understandable. App names identify the tested interfaces; personal identifiers and preference-specific details are unnecessary for explaining the reuse mechanism. Numeric task constraints and distinctions such as “one unit” ver-sus “one additional unit” remain explicit. English translation, anonymization, and neutral wording are presentation choices; they do not change reported aggregate results or substitute for a fairness evaluation. Anonymization applies to the textual examples in this appendix. Sharing screenshots, UI trees, action payloads, or logs requires separate review for account identifiers, names, contact details, addresses, private messages, and payment information.
