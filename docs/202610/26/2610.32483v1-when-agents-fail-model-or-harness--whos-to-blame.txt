## Abstract 

LLM agents combine models with execution harnesses, so agentic benchmark performance reflects their joint behavior. We argue that harnesses should therefore be evaluated through their interactions with underlying models. We develop a framework combining five complementary measures: (i) Valid Completion Rate (VCR), how reliably agents finish normally and deliver evaluable results, irrespective of task correctness; (ii) Model–Harness Fit, how well a harness supports task achievement through valid completion for a given model; (iii) Cross-Model Fit, a harness’s overall suitability across evaluated models; (iv) Interaction Residuals, pairing-specific execution strengths and weaknesses hidden by component-level summaries; and (v) Token Load, the token demands of agent execution, including failed attempts. We evaluate four general-purpose harnesses ( OpenCode , Codex CLI , Pi CLI , and 

DeepAgents ) with four core models, plus two fixed native model–harness systems, on six benchmarks covering context management, tool use, long-context planning, multimodal interaction, and artifact handoff. Including native references and stress conditions, 111 evaluation settings yield 52,168 trajectories . Harness rankings vary across models and benchmarks; task performance and valid completion can favor different pairings, and similar task scores can accompany distinct execution profiles. OpenCode ranks first in cross-model performance, while DeepSeek V4 Flash Preview maintains consistently high Mean VCR across harnesses on the shared four-benchmark panel .These findings support evaluating model–harness interactions, training transferable harness-use capabilities in models, and harness designs adapted to the model and task. arXiv:2610.32483v1 [cs.AI] 23 Oct 2026 When Agents Fail: Model or Harness—Who’s to Blame? 

## 1. Introduction 

Classical views describe intelligent agents as goal-oriented systems that continuously perceive their environment, maintain internal state, select actions, and improve behavior through feedback (Wang et al., 2024; Wooldridge and Jennings, 1995). An LLM agent implements this paradigm by integrating a large language model (LLM) into an executable system for perception, reasoning, and action in external environments (Yao et al., 2023). At the system level, an LLM agent combines its model with an execution layer, the agent harness , that connects the model to the environment (Guo et al., 2026; Kwa et al., 2025; Yao et al., 2026). The harness provides mechanisms for observation processing, context management, tool and action interfaces, workflow control, state management, execution, evaluation, and error handling. By controlling how information is presented to the model and how its outputs are executed, the harness shapes agent behavior and task performance (Zhang et al., 2025b). Under this system view, end-to-end benchmark performance reflects the joint behavior of the model–harness system rather than model capability alone (Yang et al., 2024; Yao et al., 2026). Yet most benchmarks remain task-centric, evaluating fixed model–harness configurations by task success or aggregate reward while treating the harness as part of the setup. These evaluations summarize system-level success; execution diagnostics and crossed comparisons provide complementary views of performance sources. Failures may reflect insufficient model capability, ineffective harness use, or harness limitations in observation processing, action interfaces, state management, or recovery (Ma et al., 2024; Yao et al., 2026; Zhu et al., 2026). An empirical issue study reports failures occurring only when particular model behaviors interact with harness parsing, control flow, or context handling (Chen et al., 2026). Conversely, high performance may partly reflect the harness’s task-specific workflows or additional computation (Lee et al., 2026; Lou et al., 2026). Controlled studies show that changing harnesses can alter performance and rankings with models and tasks fixed (Yao et al., 2026; Zhu et al., 2026). Understanding agent failure therefore requires examining the model, the harness, and their particular pairing through crossed comparisons and execution evidence. This assessment distinguishes failure to solve the task from abnormal termination or invalid evaluator handoff: a run may complete validly without solving the task, or earn task credit despite abnormal termination. The missing object of evaluation lies at the model–harness boundary. A model’s harness-use capability depends on how effectively it can interact with a given harness: the same interface, action space, or feedback mechanism may be easy for one model to use but challenging for another, while the same model may behave differently under different harness designs (Yang et al., 2024; Yao et al., 2026). Accordingly, harness difficulty should be understood as a model-dependent interaction cost introduced by the harness’s observation format, action interface, state management, control flow, and recovery mechanisms. When this cost exceeds the model’s harness-use capability, the harness may prevent the model from realizing its underlying capabilities; when the harness provides extensive task-specific support, it may improve performance by contributing part of the task-solving process. Existing task-level evaluations conflate these effects into a single outcome, making it difficult to distinguish model capability from harness effects (Messick, 1995; Yao et al., 2026; Zhu et al., 2026). Therefore, evaluating agents requires examining both task achievement and valid completion, together with how these outcomes vary across model–harness pairings. We develop metrics to analyze model–harness interaction through task performance and operational validity . Valid Completion Rate (VCR) measures how often attempts terminate normally with valid evaluator handoff, regardless of task correctness. Model–harness Fit and Cross-Model Fit summarize task performance from valid completions for individual models and across models. We analyze their diagnostic value and robustness, failure patterns, and resource use. We implement a common agent adapter for this study, preserving native execution loops under matched tasks and controlled execution conditions. ## 2. Related Work 

Harness design and optimization. LLM agents couple a model to an execution layer that constructs observations, exposes actions, maintains state, and closes the feedback loop. ReAct made this loop explicit, while SWE-agent and OpenHands showed how interfaces and runtime infrastructure shape agent behavior (Wang et al., 2025; Yang et al., 2024; Yao et al., 2023). A parallel line treats the surrounding system as an optimization target: GPTSwarm optimizes agent graphs, and ADAS and AFlow search over code-defined agent systems and workflows (Hu et al., 2025; Zhang et al., 2025a; Zhuge et al., 2024). More recent methods optimize constraints, context, full harness implementations, or editable agent code from execution feedback (Lee et al., 2026; Lin et al., 2026; Lou et al., 2026; Xu et al., 2026b; Zhang et al., 2026a,b). These methods show that the surrounding program can substantially change fixed-model performance. These methods focus on agent-system optimiza-tion. Evaluating interaction difficulty, task-solving structure, and pairing-specific compatibility is a complementary objective.

Harness evaluation. Most agent benchmarks report task outcomes for a complete system (Fu et al., 2026; Liu et al., 2024; Mialon et al., 2024; Yao et al., 2025); AgentBoard adds progress and trajectory diagnostics but remains task-centered (Ma et al., 2024). Recent work addresses execution-layer confounding by crossing native harnesses and models or using shared adapters with standardized traces (Wang et al., 2026a; Yao et al., 2026; Zheng et al., 2026). Harness-Bench and harness-evolution analyses further show that harness effects are model-dependent (Zhang et al., 2026a). Other studies recommend reporting harness–model pairs, resource use, and failure profiles, and matching feedback budgets and held-out tasks (Vats and Golev, 2026; Wang et al., 2026b). Trace-level scaling work further distinguishes useful feedback from raw resource expenditure (Zhang et al., 2026c). These studies complement final-success measurements with rankings and diagnostics of complete configurations. Our work measures task performance and operational validity across model–harness pairings, evaluates their joint contribution to effective operation, and quantifies pairing-specific deviations from additive component averages. 

## 3. Preliminaries 

Interpreting agent scores requires specifying the model, harness, and task conditions that produced them (Messick, 1995). We first describe how a model and harness form an executable agent, then distinguish task performance from operational validity and explain how their joint assessment charac-terizes effective operation. We also establish conditions for comparing model–harness pairings. 

3.1. Model–Harness Configurations 

An LLM agent combines a language model with an execution harness to interact with an external environment, which holds task state such as repository files or application records. The model proposes text or tool use; the agent harness prepares model context and manages action execution (de Macedo, 2026; Guo et al., 2026). Model proposals are distinct from executed actions, whose results and errors feed back into subsequent steps (Yang et al., 2024; Yao et al., 2023). 3.3. Operational Dimensions and Controlled Comparisons 

Building on this execution loop, we distinguish two dimensions of model–harness operation: task performance , how well the final state satisfies the task’s success criterion, and operational validity ,whether execution terminates normally with an evaluator-consumable state, regardless of correctness. The same interface can impose different demands across models and tasks (Cronbach et al., 1972). Task success and intermediate-action correctness describe the task-solving process, and task credit may survive abnormal termination. We therefore assess the two dimensions separately for diagnosis and jointly to characterize effective operation : task performance achieved through valid completion of the same attempt. Crossed comparisons vary the model and harness independently, holding one fixed while changing the other. Task instances and external conditions, including tool access and resource limits, are matched to separate pairing effects from changes in task conditions (Fisher, 1935). Each harness retains its native execution loop and bundled design choices, so the unit of comparison is the complete model–harness system (Holland, 1986).

## 6. Results and Implications 

To understand agent failures, we examine task achievement, valid completion, and resource use across model–harness pairings. We address three research questions: 

RQ1: Model–Harness Interaction. How do task performance, valid completion, and resource use vary across model–harness pairings and benchmarks? 

RQ2: Cross-Model Fit. How do harnesses compare across models when task performance and valid completion are evaluated jointly? 

RQ3: Metric Validity and Robustness. What information do the proposed metrics add beyond task scores, and how sensitive are their conclusions to aggregation choices and the evaluated models and benchmarks?

6.5. Implications for Evaluation, Training, and Harness Design Evaluation. Ranking reversals motivate crossed evaluation on matched tasks. Use model-conditioned outcomes, VCR, and execution diagnostics to distinguish task failure from execution or handoff failure. Cross-Model Fit supports a harness shared across models; benchmark profiles, uncertainty, and resource use reveal pairing differences and their costs. 

Model training. Native- and mixed-harness RL provide trajectories from diverse execution interfaces (Song et al., 2026; Wei et al., 2026; Xu et al., 2026a). Our ranking reversals motivate pairing the same training tasks with multiple harnesses to develop transferable action realization, feedback use, recovery, and stopping. Non-clean successes motivate combining task rewards with execution validity feedback. Evaluate outcomes, VCR, and Fit on held-out tasks and unseen harnesses under matched training budgets. 

Harness design. Use model-specific Fit and VCR profiles to guide interface, recovery, and context-management choices. Feedback should distinguish rejected from executed operations, and compres-sion should retain task-relevant state. Adapt resource limits to the model and task, bound failed retries, and detect stagnation and repeated actions. Reserve verification and handoff budgets. Component ablations can assess which mechanisms improve outcomes. 

## 7. Conclusion 

We presented a framework for evaluating model–harness interaction through task performance, valid completion, and resource use. Across six benchmarks, harness rankings depend on the model 

> 16 When Agents Fail: Model or Harness—Who’s to Blame?

and task, and similar task scores can accompany different execution profiles. These findings show that interpreting agent failures requires examining both components and their particular pairing. Task failure must be distinguished from execution or handoff failure: valid completion can leave a task unsolved, while abnormal termination can coexist with task credit. Model–harness Fit and Cross-Model Fit summarize task performance achieved through valid completion, while VCR and trajectory diagnostics provide information on execution failures beyond task scores. These findings support evaluating model–harness pairs and designing harnesses for reliable, efficient operation across models. They also motivate treating harness-use capability as a training objective, with the goal of sustaining strong task performance and valid completion across diverse execution interfaces, including harnesses unseen during training.

## A. Experimental Configuration Details 

Four repetitions of each task are scheduled for every model–harness configuration unless specified otherwise. Each harness retains its native prompts and internal agent policy, with compatibility changes for unattended execution. This appendix records model serving, execution configurations, and benchmark-specific evaluator mappings. 

A.1. Model Serving and Software Versions 

DeepSeek V4 Flash Preview was evaluated through its official API. MiniMax M3, Kimi K2.7, and DeepSeek V4 Pro 0813 were served locally with SGLang on a single node with eight NVIDIA H200 GPUs. The four crossed harnesses used DeepAgents Code 0.1.3, OpenCode v1.15.6, Pi CLI 0.79.3, and Codex CLI. The DeepSeek V4 Pro 0813 fixed reference used DeepSeek Harness SDK 0.1.0rc6. The GPT-5.5 xhigh–Codex CLI fixed reference was run through an official Codex subscription. 

A.2. Execution and Benchmark Configurations Execution environment and records. Runs use fresh task-scoped sandboxes without elevated privileges, isolated from evaluator internals, shared experiment storage, and other runs; protected cre-dentials and resource controls remain outside. The adapter records final submissions or environment states, trajectories, resource use, and termination status in a common format. 

SWE-bench-45. SWE-bench Verified assigns each task a human-annotated difficulty label based on the time an experienced developer is expected to need to identify and implement a solution. We include every task whose estimate is at least one hour, yielding 45 of the 500 verified tasks: 42 labeled 

1–4 hours and three labeled >4 hours . The selected tasks span eight Python repositories, with 22 from Django, seven from SymPy, five from Sphinx, and 11 from the remaining five repositories. The subset includes all tasks with released difficulty estimates of at least one hour; “long” denotes estimated human completion time. Each run starts from the prescribed base commit in the official containerized environment and receives the original GitHub issue description. We retain the task-specific regression tests and apply the official verifier to the final repository state. All harnesses operate on the same task images through the common adapter. 

Terminal-Bench 2. We execute all 89 tasks through Harbor while retaining their original task definitions, containerized environments, verifier scripts, and per-task time limits. Every configuration starts from the same task environment and is assessed by the same task-specific verifier. All 16 core configurations contain four distinct trajectories for each of the 89 tasks; both fixed system references use the same 89 × 4 support. 

VitaBench. We use English task variants for 400 tasks across four environments (100 per envi-ronment), covering multi-turn services, domain-specific APIs, and cross-domain requests. Each task is repeated four times, giving 400 attempts per environment and model–harness configuration. A trajectory is limited to 300 interaction steps. We report the strict tool-permission setting: harness-native tools and external filesystem, shell, browsing, and delegation capabilities are disabled where applicable, so the agent can affect the simulated environment only through the VitaBench business APIs. A.3. Benchmark-Specific Evaluation Metrics 

This section specifies how each benchmark’s official evaluator output is converted into task-level scores. Best-of-4 and stress-condition results are secondary analyses. 

Operational validity status mapping. For SWE-bench-45, the normal-termination condition is a recognized normal stop ( Submitted , NoPatch , or a successful exit-zero completion), and the valid-handoff condition requires the evaluator to accept the patch at its application stage. For Terminal-Bench 2, normal termination requires a clean return without a timeout or unhandled framework failure, and valid handoff requires the post-run verifier to produce a consumable result. For LOCA-Bench, normal termination requires status=success ; valid handoff requires a finite final-state evaluator result, including one produced before a subsequently abnormal backend exit. For ClawMark, normal termination requires status=ok , return code zero, and no recorded framework failure; valid handoff requires a finite official score. For AgentSkillOS, normal termination requires the task runner to record status=completed ; valid handoff requires a newly copied generated file whose path matches, or is nested under, at least one task-declared expected output path. Task correctness is not required. For VitaBench, normal termination requires termination_reason=agent_stop , and valid handoff requires a finite evaluator reward. In every benchmark, correctness affects the official task outcome but is never part of the valid-handoff condition.
