## 摘要
移动端 GUI 智能体经常执行交互流程相似的重复任务。复用以往的执行过程可以减少冗余的 LLM 推理和执行开销，但用户指令和执行环境的变化可能使先前成功的操作失效。我们系统地将这些变化归纳为六类典型情形，并发现此类变化并不一定会使整个流程失效：只要依据当前任务上下文和界面状态进行验证，个别状态转移仍可复用。基于这一发现，我们提出用于选择性复用执行轨迹的图文模板。图结构表示 UI 状态和操作转移，文本则编码任务意图、流程结构以及用于表示可变内容的类型化槽位。记录—模板—重放框架从经过验证的执行过程中构建模板，并利用当前指令和实时 UI 状态，复用、调整或舍弃个别状态转移。给定一条执行轨迹，在 AndroidWorld 上对五种基础智能体进行评估时，我们的框架平均可减少约 80% 的 LLM 推理 token 消耗；大多数智能体相较于仅依赖 LLM 执行，速度至少提升 1.5 倍。在 Android 和 HarmonyOS 真机评估中，我们的框架实现了 70.7%–79.8% 的操作复用率，并在大多数评估配置下保持超过 2 倍的执行加速。

## Abstract
Mobile GUI agents frequently perform repetitive tasks with similar interaction procedures. Reusing previous executions can reduce redundant LLM inference and execution overhead, but variations in user instructions and execution environments may invalidate previously successful actions. We systematically characterize these variations into six representative categories and observe that such changes do not necessarily invalidate entire procedures: individual transitions can remain reusable when validated against the current task context and interface state. Based on this insight, we propose graph-text templates for selective execution-trace reuse. The graph captures UI states and action transitions, while the text encodes task intent, procedural structure, and typed slots for variable content. A record-template-replay framework constructs templates from verified executions and leverages the current instruction and live UI state to reuse, adapt, or discard individual transitions. Given an execution trace, our framework reduces LLM inference token consumption by approximately 80% on average across five base agents on AndroidWorld, with most agents achieving at least 1.5-fold execution speedup over LLM-only execution. In real-device evaluations on Android and HarmonyOS, our framework achieves action reuse ratios of 70.7-79.8% while maintaining over 2-fold execution speedup in most evaluated configurations.

## 1. 核心问题与研究背景

### 1.1 论文要解决什么问题？

移动端 GUI 智能体经常重复执行类似任务，例如搜索商品、加入购物车、设置计时器或修改系统设置。如果每一步都重新调用大语言模型（LLM），就会重复支付推理成本，并增加用户等待时间。

但直接回放历史成功轨迹也不可靠，因为：
- **环境可能变化**：目标已完成、控件移动、流程调整，或出现弹窗。
- **用户要求可能变化**：数量、时间、对象或表达方式与历史任务不同。

论文的核心问题是：**如何在任务与界面发生变化时，判断历史轨迹中的哪些动作仍然有效，从而减少推理，又避免错误执行？**

### 1.2 核心观点与整体意义

作者认为，局部变化不应导致整条历史流程作废。复用的基本单位应从“完整脚本”转向**经过当前证据验证的单步状态转移**：

- 条件未变：直接复用。
- 当前指令明确改变了某个参数：局部改写。
- 当前证据不足或存在冲突：拒绝复用，交回基础智能体处理。

因此，这项工作的重点不是让智能体盲目“记住操作”，而是把历史执行转化为**带适用条件、可验证、可中断恢复的执行经验**。

## 2. 方法论：图文模板与证据约束的逐步重放

### 2.1 六类变化的分类框架

论文将轨迹失效因素分为两大来源、六类情况：

| 来源 | 变化类别 | 复用时的处理原则 |
|---|---|---|
| 环境 | 后台状态变化 | 检查目标是否已完成，避免重复操作或反向切换 |
| 环境 | 布局与工作流变化 | 控件移动可尝试重新定位；流程不兼容则回退 |
| 环境 | 模态窗口与中断 | 检测遮挡；权限、登录、支付等窗口不能盲目跳过 |
| 指令 | 参数变化 | 从当前指令绑定数量、时间、金额等类型化值 |
| 指令 | 实体替换 | 重新确认当前商品、联系人、地点等对象 |
| 指令 | 目标表达变化 | 支持同义改写检索；不明确的上下文指代不能擅自补全 |

### 2.2 总体框架：记录—模板—重放

#### 第一阶段：记录经过验证的执行

基础智能体正常执行任务，系统记录每步动作的：
- 执行前后截图、可用的 UI 树及窗口信息。
- 动作类型、动作参数、目标控件及定位依据。
- 当前步骤的任务意图、可变参数。
- 预期结果、实际结果、完成状态与风险信息。

**历史任务成功不代表其中每一步都可直接复用。** 每条候选转移还需要可识别的局部结果；缺失证据、目标无法定位或终止结果失败的动作，不应成为可执行模板。经过明确验证的成功前缀可以保留，但必须标明截断边界。

#### 第二阶段：提取图文模板

模板包含两个互补部分：

- **图结构**：表示可观察 UI 状态及动作转移，回答“从哪里、通过什么操作、到哪里”。
- **文本结构**：表示任务意图、流程步骤和类型化槽位，回答“为什么操作、哪些内容可以变化”。

状态和动作只有在语义、前置条件及结果兼容时才能合并；冲突路径保留为不同分支，不能仅因页面外观相似就合并。

### 2.3 转移契约的技术细节

论文将一个可复用转移表示为：

\[
e=(v_i,a,v_j,z),\qquad z=(g,k,s,r,\phi^-,\phi^+)
\]

其中：
- \(v_i,v_j\)：动作前后的可观察状态。
- \(a\)：动作及其参数。
- \(g\)：该动作对应的流程意图。
- \(k\)：类型化槽位，如数量、时长、商品身份。
- \(s\)：目标控件的定位依据。
- \(r\)：动作风险。
- \(\phi^-,\phi^+\)：执行前、执行后的证据要求。

这使历史动作不再只是“点击某个坐标”，而是一个**具有语义和适用条件的局部操作契约**。

### 2.4 候选检索与三类决策

系统依次利用：
1. **任务语义**：检索相关应用与流程。
2. **当前 UI 和流程进度**：选择候选转移。
3. **实时目标定位和安全检查**：判断候选是否真的可以执行。

检索相似度只用于推荐候选，**不能直接授权动作**。最终决策为：

- **REUSE，复用**：当前任务、状态、目标与原动作参数均兼容。
- **REWRITE，改写**：当前指令明确提供新值，且能绑定到兼容槽位；只修改局部参数或定位，不改变动作意图。
- **REJECT，拒绝**：对象不明确、参数缺失、状态冲突、存在阻塞窗口或验证证据不足。

高风险实体和值不能仅凭历史偏好自动填充。

### 2.5 单步执行与回退流程

算法每次只批准一个动作：

1. 观察当前界面，检查任务是否已经完成。
2. 检索候选转移，绑定当前参数并定位目标。
3. 刷新必要的执行前证据。
4. 条件满足时复用或改写；否则拒绝并调用基础智能体。
5. 执行动作一次，重新观察界面。
6. 验证动作的语义结果，而不只是检查页面是否变化。
7. 若验证失败，在本次任务中禁用该边并回退；后续仍可重新对齐模板、继续局部复用。

例如，将“设置 10 分钟计时器”改为“设置 15 分钟计时器”时，导航可以复用，但时长输入及结果检查都必须改成 15 分钟；“启动计时器”则是另一条独立转移。

## 6. 主要结论与发现

### 6.1 效率结果

| 场景 | 动作复用率 | Token 减少 | LLM 决策步数减少 | 执行加速 |
|---|---:|---:|---:|---:|
| AndroidWorld | 82.0%–87.5% | 78.0%–89.6% | 71.1%–79.8% | 1.2–1.9 倍 |
| 真机：后台状态变化 | 72.6%–78.0% | 65.4%–78.9% | 80.6%–88.8% | 1.9–3.6 倍 |
| 真机：参数变化 | 70.7%–79.8% | 68.3%–78.7% | 73.1%–85.8% | 1.8–3.5 倍 |
| 真机：指令同义改写 | 73.2%–79.2% | 60.8%–79.6% | 76.0%–86.8% | 2.9–3.9 倍 |

这里的复用率是**先计算各任务的复用动作占比，再对任务取平均**，不是所有动作汇总后的比例；正确的零动作完成任务不参与该比例统计。

### 6.2 可靠性与机制发现

- AndroidWorld 中，已有成功记录条件下的重放与回退成功率为 **94.0%–97.7%**，说明并非无损复用。
- 真机完整配置的直接成功率约为：
  - 后台状态变化：**93%–98%**。
  - 参数变化：**93%–98%**。
  - 同义改写：**92%–97%**。
- 与 replay-only 相比，完整配置提升约 **35–50 个百分点**，但这一收益包含基础模型回退的作用。
- 大幅减少模型调用不等于同幅度缩短总时间。AndroidWorld 中界面采集等开销较高；真机实现优化了 UI 获取，因此加速更明显。跨平台速度差异不能只归因于复用机制。

核心结论是：**经过实时证据检查的局部复用，可以在保留基础智能体处理能力的同时，显著减少重复推理。**

## 7. 优点与亮点

- **复用粒度合理**：既避免整段脚本的脆弱性，又允许在回退后重新进入可复用流程。
- **同时约束任务语义与界面状态**：明确区分“页面相似”和“动作适用”，防止复制过期参数。
- **参数与验证同步改写**：不是只替换输入，还更新对应的结果检查。
- **安全边界清晰**：拒绝不执行动作；失败后禁用当前边；不将历史偏好当作高风险操作授权。
- **跨模型、跨真机验证**：覆盖五种基础智能体、四款手机和两个系统生态。
- **指标定义较细致**：区分复用、模型调用、token、物理动作与端到端延迟，附录也明确说明派生成功分数的含义。

## 8. 不足与局限

### 8.1 方法与应用限制

- 依赖已有的可靠执行记录，冷启动和新工作流仍主要由基础智能体解决。
- 依赖 UI 可观察性；缺少可访问元数据、快速动态页面和自由形式内容会降低定位与验证能力。
- 实时前置检查只能缓解状态变化风险，不能完全消除检查与执行之间的竞态。
- “通常买的那个”等模糊指代无法仅凭历史记录安全处理。
- 前后置条件生成、状态合并、语义检索及风险判定的具体实现仍较概括，可复现性有限。

### 8.2 实验覆盖与偏差风险

- 六类变化只对三类做了重点定量测试。
- 缺少多种变化叠加、长期应用升级、跨系统轨迹迁移和记忆失效管理实验。
- 多设备覆盖不等于轨迹可以直接跨设备或跨系统迁移。
- AndroidWorld 记录来自基础模型成功任务，存在记录可得性限制。
- 缺少统一强基线比较、充分的逐任务数据和统计分析。
- 表格中派生成功分数与直接成功率并存，容易导致误读。

### 8.3 成本与隐私

- 未计入记录、模板构建及长期维护成本，不能直接推导全生命周期经济收益。
- 截图、UI 树和动作参数可能包含联系人、地址、消息和支付信息。
- 过期记录可能携带敏感或错误选择；日志、权限边界与人工安全终止只能降低风险，不能替代用户授权。

**总体评价：**这是一项以系统设计为主的工作，最有价值的贡献是将历史轨迹组织为可逐步准入、局部改写和失败回退的图文契约。实验证据支持其在已有可靠记录的重复任务中降低在线成本，但尚不足以证明它在所有变化场景下都可靠，或全面优于现有轨迹复用系统。
