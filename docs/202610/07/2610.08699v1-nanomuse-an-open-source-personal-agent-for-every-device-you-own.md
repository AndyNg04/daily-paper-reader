## 摘要
2011 年的助手会回答问题，然后等待；2023 年的智能体会完成一项任务，然后停止。2026 年 9 月，Meta 推出了 Muse，展示了一种面向单个人的智能体：它拥有账户、设备和记忆，并能持续对话；但它封闭运行于某个供应商的云端，且仅在一个国家提供服务。人们期待这类智能体能够操作个人的账户与设备，跨越数周记住相关信息，在适当时主动开启对话，并为自己的行为负责。它是一种软件，而非模型；此前，这类软件尚无开放的对应产品。本报告通过五个问题和三个时间跨度来界定个人智能体，并依据 Meta 的公开资料及其生产环境提示词副本，梳理 Muse 的构建方式，同时为每项陈述注明来源。随后，报告介绍了 nanoMuse：一个基于 GPL-3.0 协议的开源对应产品，让用户拥有的每台设备上都运行一个智能体，并能操作手机和电脑的屏幕。各设备上的智能体通过任何人都能自行部署的中继服务共享同一段对话；每项操作都经过 Sentinel，记忆以用户可读取的文件形式保存，模型则由用户自行选择。报告还给出了规模和成本的估算，并提出后续路线图，涵盖开放的记忆溯源机制、针对操作能力的评测套件，以及面向这些能力的开放模型。

## Abstract
Assistants from 2011 answered and waited, and agents from 2023 did a task and stopped. In September 2026 Meta's Muse showed an agent for one person, with accounts, devices, memory and a conversation that lasts, closed, in a vendor's cloud, in one country. Such an agent is expected to act on a person's accounts and devices, remember them across weeks, speak first when it is worth it, and answer for what it did. It is a kind of software, not a model, and until now had no open counterpart. This report defines the personal agent in five questions and three horizons. It reads how Muse is built from Meta's public record and a copy of its production prompt, each statement marked by its source. It then presents nanoMuse, the open-source counterpart under the GPL-3.0, one agent on every device a person owns, with hands on the phone's screen and the computer's. They share one conversation over a relay anyone can run; every action goes through a Sentinel, memory is files the person can read, and the model is their choice. Its size and cost are given as estimates. What is open, memory with provenance, an evaluation suite for the hands and an open model for them, is set out as a roadmap.

## 1. 核心问题与整体含义：个人智能体应由谁掌控？

### 1.1 研究背景与动机

- 作者将智能助理的发展概括为三个阶段：
  - **问答助手**：回答问题后等待下一条指令。
  - **任务型智能体**：执行一项任务，完成后停止。
  - **个人智能体**：长期服务于同一个人，能够操作其账户、设备和文件，维持跨周记忆，在适当时主动联系，并说明自己做过什么。
- 根据论文对相关产品的描述，现有个人智能体主要采用“**厂商云端运行智能体，用户设备作为客户端**”的模式，由此产生：
  - 用户难以检查代码、权限机制和数据处理流程。
  - 长期记忆、凭据与对话依赖厂商基础设施。
  - 云端浏览器和 API 无法覆盖许多只有原生手机界面的应用。
  - 每用户一台云端虚拟机带来持续托管成本和平台依赖。

### 1.2 核心问题

论文关注的不是“如何训练更强的模型”，而是：

> **如何构建一个用户能够检查、自行部署并掌控的个人智能体，使其跨设备长期工作，同时让操作、记忆和权限保持可理解、可撤销与可追责？**

### 1.3 整体意义

- nanoMuse 尝试将个人智能体从“厂商拥有的云服务”转变为“**运行于用户设备、模型可替换、共享组件可自托管的软件系统**”。
- 论文强调：个人智能体的定义取决于**它属于谁、向谁负责**，而不是使用何种模型或工具。
- 其贡献主要是系统整合、用户控制和安全交互设计，**并未证明其性能或安全性优于现有系统**。

## 2. 方法论：设备端智能体、跨设备协作与行动权限控制

### 2.1 概念框架：五个问题、三个时间跨度

论文通过五个问题组织设计要求：

| 问题 | 对应设计目标 |
|---|---|
| 它知道什么？ | 记忆可读、可编辑、可导出，未来应具备来源与置信信息 |
| 它在哪里行动？ | 一个用户身份对应多个设备的执行能力 |
| 它向谁负责？ | 操作需有明确授权范围、审批记录与撤销机制 |
| 它如何学习？ | 主动交互可调节，数据使用需获得用户同意 |
| 它如何付费与治理？ | 模型供应商可选，共享服务可自托管，长期面向社区治理 |

三个时间跨度分别是：**当前已有能力、开放替代系统下一步应补充的能力、能够持续多年工作的长期目标**。这一框架属于设计主张，不是经过实验验证的理论模型。

### 2.2 系统架构

nanoMuse 采用 GPL-3.0，报告描述的版本为 **0.1.40**。

- **设备端运行完整智能体**：
  - Android：基于修改后的 OpenMinis，包含 Alpine Linux 沙箱、Shell、浏览器、MCP 服务、技能与定时任务。
  - 桌面端：Electron 外壳结合 DeepSeek harness、nanoMuse 插件和 Python 运行时。
  - iOS：包含智能体功能，但不能操作其他应用的屏幕。
  - Web：由用户电脑上的运行时提供服务。
- **共享体验不等于单一中央执行进程**：
  - 每台设备都有自己的智能体和 Sentinel。
  - 设备通过中继共享对话并互相调用，形成逻辑上的“一个个人智能体”。
- **中继服务可选**：
  - 单设备使用自有 API Key 时无需中继。
  - 跨设备协作与对话同步需要中继，可使用社区服务或自行部署。
- **模型可替换**：
  - 支持十八家模型供应商、自有模型服务及部分订阅授权方式。
  - 设备本地执行不意味着模型推理必然本地完成。

### 2.3 Sentinel：每个工具调用都经过权限判断

论文给出的固定检查顺序为：

1. 检查禁止使用的工具。
2. 应用用户自定义规则。
3. 检查始终允许、始终询问列表。
4. 应用隐私数据“污染”规则：对话读取私有数据后，向允许列表之外发送数据的调用转为询问。
5. 根据工具风险和用户设置的模式判断。
6. 最后检查不可被普通模式或列表豁免的警告，例如破坏性命令、下载后立即执行、涉及提交操作的标签。

授权不是简单的“是/否”，而是有范围的许可：

- 仅本次；
- 本次对话；
- 针对指定收件人、站点、目录、设备或应用的持续许可。

权限可查看、撤销，决策进入日志；带警告的操作只能获得单次授权。

**关键边界**：nanoMuse 的 Sentinel 是同一进程体系内的**策略边界**，并非论文所描述的 Muse 那种由独立高权限组件保护凭据和网络出口的**权限隔离边界**。

### 2.4 Hands：逐截图、逐动作的屏幕操作

系统先选择成本更低、结构更明确的执行方式：

**技能 / 命令行 / MCP → 带登录状态的页面获取 → 浏览器 → 设备屏幕操作。**

屏幕操作默认关闭，启用后按以下流程执行：

1. 获取当前截图，以及可用的无障碍元素。
2. 将截图、目标和逐步简短历史输入模型。
3. 模型输出操作意图、用户可读说明和一个手势。
4. Sentinel 检查操作说明和目标标签。
5. 如涉及支付、发送、删除、提交等敏感操作，则请求批准。
6. 执行一个动作，重新截图并继续。

补充机制包括：

- Android 同时检查点击位置的无障碍文本，采用更严格的判断结果。
- 没有操作标签的步骤会触发警告。
- 输入同时提交的动作也被视为敏感操作。
- 提示词禁止输入密码、PIN、银行卡号和一次性验证码。
- 用户可通过停止按钮或接管控制暂停执行。
- 桌面端保留带截图与动作标记的轨迹，便于事后审查。

**安全弱点**：审批主要依赖模型对动作的文字描述，未必能可靠识别截图中的真实后果。

### 2.5 文件化记忆与跨设备协作

- 手机端采用 Markdown 文件保存身份、用户信息、长期记忆、日记和例行任务。
- 桌面端支持逐条记忆、修改日志、撤销、关键词检索及可选的向量检索。
- 整理过程可建议合并或删除，但不删除用户亲自写入的内容。
- 跨设备任务由目标设备自己的 Sentinel 审批，发起设备不能直接转移自身权限。

论文**没有提出数学公式或新的优化目标**；算法细节主要体现为权限判断顺序和屏幕操作循环。

## 6. 主要结论与发现

- **个人智能体首先是一套软件系统，而非单个模型**：其核心是长期记忆、持续交互、多设备执行、权限治理和责任记录。
- nanoMuse 提供了一个开源、设备端执行、可自托管且模型可替换的实现方案。
- Android 原生屏幕操作是其重要定位，旨在覆盖缺乏 API 或网页入口的应用。
- 可读记忆、可撤销授权、停止控制和操作轨迹，有助于让后台执行更易理解和审查。
- 轻量中继降低了共享基础设施门槛，但**不消除同步数据的服务器依赖，也不证明系统总体成本低**。
- 记忆来源追踪、系统化评测和自有开放操作模型仍是路线图内容，而非已完成成果。

## 7. 优点

- **问题定位清晰**：将用户所有权、可迁移性和授权责任放在核心，而不仅追求任务完成率。
- **系统实现覆盖较完整**：连接移动端、桌面端、Web、中继、记忆和操作机制，具有实际工程价值。
- **执行策略合理**：优先使用结构化工具，将截图操作作为最后手段。
- **跨设备权限保持独立**：目标设备自行审批，有助于限制设备间权限传递。
- **可审计与可接管设计较具体**：权限列表、日志、停止控制和轨迹共同提升可理解性。
- **模型与部署选择开放**：支持自有 Key、本地模型和自托管中继，减少单一厂商绑定。
- **局限披露坦诚**：明确说明安全隔离不足、记忆缺少来源以及评测缺失。

## 8. 不足与局限

### 8.1 安全保证有限

- Sentinel 与智能体处于同一信任域，缺少独立凭据代理和强权限隔离。
- 对支付、发送等危险操作的识别依赖文字标签，可能受误描述、无标签按钮或视觉误定位影响。
- 禁止输入秘密主要是提示词规则，不能等同于系统级秘密隔离。
- 日志有助于追责，但不能撤销已经发生的付款、发送或删除。

### 8.2 隐私与同意机制存在张力

- 本地执行仍可能将截图、上下文发送给云端模型。
- 同步对话会保存在中继服务器上。
- 社区中继的新账户默认开启聊天文本用于模型改进，虽然可关闭，但与“主动选择贡献数据”的目标存在张力。
- 作者也将这一默认设置列为最不确定的设计选择之一。

### 8.3 长期记忆与个性化尚不成熟

- 记忆尚未记录生成模型、置信度及完整来源信息。
- 缺少对旧记忆重新核实、更新或标记怀疑的机制。
- 不同能力模型共用记忆，可能使早期错误被后续模型当作事实。
- 主动交互阈值可调，但尚无证据表明系统能长期准确判断何时应打断用户。

### 8.4 平台与应用限制

- iOS 无法操作其他应用屏幕。
- Linux 屏幕操作仅支持 X11 会话。
- 图标式按钮、缺少无障碍标签的界面和高密度专业软件仍具有较大难度。
- 论文尚未系统分析设备离线、并发编辑、同步冲突及权限撤销传播等问题。

### 8.5 证据与创新边界

- Muse 的分析部分依赖来源无法独立核实的生产提示词副本；其内容也可能随部署变化。
- 对竞品的结论应视为作者基于特定材料的描述，而非独立验证事实。
- nanoMuse 大量复用现有运行时和 GUI 操作组件，其主要创新是**整合架构与治理机制**，不是新模型或已验证的新算法。

**总体评价**：nanoMuse 是一个有价值的开源个人智能体系统原型，清楚展示了“用户可控、跨设备协作、操作可审查”的实现方向。但其可靠性、安全性、长期个性化效果和真实使用成本尚缺乏系统性证据，更适合作为架构方案和后续研究平台，而非已经验证成熟的自主代理系统。
