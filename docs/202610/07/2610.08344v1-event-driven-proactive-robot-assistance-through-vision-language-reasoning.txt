Abstract — Assistance in collaborative manipulation is often initiated by user instructions, making high-level reasoning request-driven. In fluent human teamwork, however, partners often infer the next helpful step from the observed outcome of an action rather than waiting for instructions. Motivated by this, we investigate an event-driven formulation of proactive assistance, where human–object interaction outcomes initiate assistive reasoning without user-provided task specifications at inference time. To this end, we propose an event-driven framework that monitors workspace state changes with an event monitor and, upon event completion, extracts stabilized pre/post snapshots that characterize the resulting state transition. A frozen pretrained Vision-Language Model (VLM) then uses its semantic priors to infer the task context, decide whether assis-tance is appropriate, and, when needed, generate a sequence of assistive actions from the observed transition. To make outputs executable and verifiable, we restrict actions to a set of action primitives and reference objects via integer IDs. We evaluate the same framework across three distinct real world tabletop collaboration tasks without task-specific training or fine-tuning. The event-driven framework achieves performance comparable to variants given user instructions. 

I. I NTRODUCTION 

Recent advances in embodied intelligence have enhanced robots’ ability to interpret task instructions, ground them in perception, and generate executable actions in diverse manipulation settings [1], [2]. However, instruction following mainly addresses what to do once a specification is provided. To move toward fluent teamwork, a robot should be able to decide when to intervene and what assistance to provide by inferring human intention, the unobserved internal states or goal-oriented constructs that underlie observable human behavior [3]. Recent reviews further suggest that proactive interaction can be facilitated by anticipation from observa-tions and contextual information, often without explicit input from a human [4]. Translating this vision into practice reveals a bottleneck: many assistive systems remain request-driven, meaning that robot actions are initiated only after the human issues a request to the robot. In human-human teamwork, partners often do not wait for explicit instructions after every step. Instead, they use the observed outcome of an action to infer the likely next sub-goal and decide whether to assist. To improve reliability and mitigate errors from generative planning, we incorporate multi-layer safeguards in the control loop, including schema-constrained outputs, ID-grounded references, and local verification. A. Request-Driven Assistance 

Many collaborative robot systems remain request-driven: even as foundation models improve the perception of human behavior and contextual reasoning, robot actions are still typically initiated from explicit or inferred user requests. 

1) Explicit Request: Systems based on explicit requests initiate robot actions from user-provided commands or task specifications. Language-to-plan pipelines condition action generation on the given instruction and ground candidate steps for execution [5], while other systems translate in-structions into executable code or task structures combine visual perception [12], [13] with reusable robot skills [14], [7], [15]. Interactive feedback and execution-time refinement can further adapt robot behavior when uncertainty or failures arise [8], [15]. Recent embodied foundation models substantially ex-pand instruction-conditioned manipulation through multi-modal reasoning and grounded execution [16], [17], [18]. Recent VLA systems further extend instruction modalities and generalist manipulation capabilities [19], [20], [21]. Despite differences in architecture and execution interface, these systems still typically initiate high-level reasoning from an instruction or stated goal. 

2) Implicit Request: Other systems operate from a user request, control cue, or task framing that indicates an in-tended goal without fully specifying the robot action. The robot must therefore combine this information with observed context to infer appropriate assistance. Prior work resolves ambiguous language using physical context, preceding hu-man actions, or situational reasoning [22], [23], while recent work using foundation models infers latent human goals or task structure from under-specified instructions to guide planning [24], [25], [6]. Nonverbal or partial control signals can serve a similar role: gaze is combined with scene context to infer manipulation intent [9], while shared-autonomy systems combine partial user control with environmental observations to infer or refine user goals [26], [27], [28]. Related VLM work further demonstrates contextual infer-ence of latent goals, human states, or manipulation intent from visual or multimodal observations [29], [30], [31], [32]. Complementary work captures individual differences in human judgments through annotator-specific modeling [33] and learning from incomplete annotations [34]. Collaborative systems can likewise combine shared task framing with changing workspace observations to infer human intent and update robot actions [11]. Across these settings, contextual observations complement an already supplied but incomplete request, cue, or task framing, rather than determining when assistance reasoning is initiated. Despite increasingly capable intent inference, request-driven systems still depend on a user request, control cue, or task framing to initiate assistance. This leaves the ini-tiative primarily on the human side, even when the robot can infer substantial task context on its own. To support proactive collaboration closer to human–human teamwork, robots should also be able to initiate assistance from the observed outcomes of human interaction without waiting for an additional request. This motivates the event-driven assistance setting considered here. 

B. Event-Driven Assistance 

Prior work has taken steps toward proactive collaboration by using observed human activity and context to derive cues for assistance without relying on a user request [35]. Such systems typically model semantic aspects of the on-going interaction, including anticipated human–object inter-actions [36], action completion [37], human intent or latent goals [38], [39], or broader mental states [40]. These esti-mates are then used to determine or adapt robot assistance. Across these approaches, proactive assistance is mediated by semantic representations of human behavior, such as human–object interactions, action progress, intent, goals, or mental states. M ETHODOLOGY 

A. Problem Setting: Event-Driven Proactive Assistance 

We focus on proactive assistive manipulation in human– robot shared workspaces. An interaction event is a human– object interaction interval that induces a sustained workspace state change, with onset and offset times detectable from changes in the observed workspace state. We assume that the outcome of such interactions provides task-relevant evidence. Accordingly, we define the assistance objective at the task-level from the observed pre/post state transition, such as completing an object placement or establishing a spatial relation. Once an event terminates, the system infers an appropriate assistive response and decides whether to act or wait. Triggering at event completion provides more informa-tive evidence than intermediate frames and supplies sufficient context for inferring an appropriate assistive response. 

B. System Architecture 

Completed human–object interactions serve two roles in our framework: event completion determines when assistance reasoning is invoked, while the paired pre/post observations expose the semantic consequence of the interaction. This context allows a pretrained VLM, used without task-specific fine-tuning, to infer an appropriate assistive response from the observed state transition. To connect this event-level reasoning to robot control, the planner operates over astructured event payload and returns ID-indexed actions from a restricted primitive set, while the robot system handles metric grounding and execution checks. Fig. 2 illustrates the architecture, consisting of a robot sys-tem and an event-triggered VLM planner. The robot system monitors the RGB–D stream, maintains the event state, and forms a pre/post snapshot pair (I−, I +) when an interaction event completes. The post-event scene is parsed into an ID-indexed object map T +, with the IDs overlaid on I+ for VLM reference. Given (I−, I +), the VLM planner returns an ID-indexed symbolic plan over the allowed primitives. The robot controller then validates and grounds the plan using T +, executes it, and verifies the resulting workspace state. We next detail the three stages of this pipeline: event processing and representation, event-driven VLM planning, and geometric grounding and execution. 

C. Event Processing and Representation 1) Event Monitoring: Event progress is tracked through three states: pre-event → interacting → post-event. In the pre-event state, the system maintains a stable workspace height map H− and its RGB observation I−, with height maps expressed relative to the table plane. For each incoming height map, change statistics are computed over the union of the current and reference regions within a fixed height band above the table, capturing both removed and newly occupied areas while excluding operator-side intrusions. The system computes an instantaneous change ratio et between consecutive observations and a cumulative change ratio dt

relative to H−, with the height threshold for et adapted to stationary noise. The system enters interacting when either 

et > θ e or dt > θ d persists for the required evaluations, and enters post-event when et < θ q for a fixed dwell. Renewed disturbance returns it to interacting. In the post-event state, the changed region relative to H− is evaluated across con-secutive observations for spatial overlap, geometric height consistency, intrusion overlap, and valid depth. Satisfying these conditions confirms event completion, while an empty region or timeout returns the system to pre-event without invoking the VLM planner. The confirmed stable observation becomes I+, so (I−, I +) spans two stable workspace states without intermediate manipulation frames. Monitoring then pauses and resumes using the resulting stable workspace state as the new baseline. 

2) Post-Event Parsing and Object Map Construction: Af-ter an event terminates, the robot system parses the post-event snapshot I+ to obtain object instances for manipulation and grounding. For efficient instance labeling, we use FastSAM, followed by RGB–D refinement relative to the table plane. The resulting instances are represented as 

D(I+) = {(bk, m k)}Kk=1 , (1) where bk and mk denote the bounding box and instance mask of object k. Each instance is assigned an integer ID and associated with its geometric information, yielding an ID-indexed object map

For VLM planning, the snapshots are marked as PRE and POST, with object IDs overlaid only on I+ so that they refer unambiguously to the executable scene. The IDs are rendered within their corresponding bounding boxes while avoiding overlaps be-tween labels. The robot system then forms the event payload 

E = ( I−, I +) and provides it to the VLM planner. 

D. Event-Driven VLM Planning 

Given the event payload E, the VLM interprets the state transition to infer an appropriate assistive goal and grounds it to the identified objects. A fixed system prompt specifies the available action primitives and structured output format. The resulting symbolic plan uses only object IDs and contains 

pick , place , or wait , with placement defined by areference ID and qualitative spatial relation. To avoid overthinking after a target has stabilized, the generated chain-of-thought (CoT) is continuously monitored for manipulation-related statements. Inspired by prior work on CoT convergence [43], a parser extracts the target object ID from sentences containing verbs such as move , place ,or pick , and tracks repeated IDs across the reasoning trace. Questions, speculative phrasing (e.g., maybe , perhaps , or 

what if ), and meta-level references are ignored, while pro-nouns inherit the most recent candidate ID. Let c1, c 2, . . . 

denote the resulting sequence of candidate IDs. Generation is stopped when the same ID appears for k = 3 consecutive candidates, cn−k+1 = · · · = cn. The converged ID is then fixed in a separate finalization call that reuses the generated reasoning as context and completes the remaining plan fields without revisiting the selected target. Consequently, wait 

is no longer available after early stopping. If reasoning terminates normally without producing any candidate ID, the model’s original structured outcome is retained. When only one candidate ID is observed and the final plan selects it, the plan is accepted without further interaction. To avoid premature target decisions, other normally ter-minated but non-converged candidate sequences are treated as unresolved target decisions and invoke a brief QA step. The QA menu contains the distinct candidate IDs extracted from the CoT together with an additional wait option. If the human selects an ID, that ID is fixed through the same finalization call, again reusing the preceding reasoning; selecting wait directly yields a wait outcome. The selected response is then used to produce the final structured outcome consumed by the grounding and execution stages. 

E. Geometric Grounding and Execution 

After the VLM planner returns an action list, the robot controller validates the primitive type and referenced IDs, then binds each action to the corresponding geometry in T +.The resulting metric targets are transformed into the robot base frame using the calibrated camera-to-base transform. For pick(target id) , the controller resolves the tar-get ID and uses the planar coordinates of its top-surface cen-ter p as the grasp location. The grasp height is determined by the controller configuration, with a fixed downward gripper orientation. The resulting grasp target is executed through MoveIt. For place(reference id, relative pos, offset scale) , the controller resolves the reference cen-ter pr and converts the qualitative relation into a metric placement target. For a directional relation q,

pplace = pr + ( sr α + δ) uq , (3) where α denotes offset scale , sr is the full extent of the reference object’s top surface along direction uq , and δ

is a local safety margin. Directional relations, such as left 

and right , are interpreted in the camera view, while on is handled separately by centering the target over the reference object and adjusting the release height. Before execution, the action sequence is validated, and any place without a preceding pick is rejected. The resulting placement target is executed through the same MoveIt motion planner. Thus, the VLM plan remains symbolic while metric grounding and motion execution are handled by the robot system. After execution, the system captures a refreshed observa-tion and verifies whether the qualitative relations specified by the symbolic plan hold in the resulting scene. A failure is declared when expected relations are violated or referenced objects cannot be recovered. If verification fails, the plan may be re-executed once and verified again. The settled workspace then provides the baseline for subsequent event monitoring. IV. E XPERIMENTS

A. Experimental Setting 1) Task Design: We evaluate three tabletop collaboration tasks (Fig. 3): equation completion (T1), tabletop sorting (T2), and tool introduction (T3). Each event uses a distinct object layout, while T1 varies the candidate block composi-tion. In T1 (60 events), the human adds one of five candidate blocks to a partial single digit arithmetic expression covering addition, subtraction, multiplication, and division, and the robot completes it. In half of the scenes, the same digit also appears in the expression while the correct block to move remains unique. In T2 (30 events), the candidate items are a lemon, an orange, a potato, and a green pepper. The human places three to establish the fruit/vegetable mat mapping, and the robot places the remaining item. B. Baselines 

The request-driven variants add only a user instruction to the corresponding system prompt, adapting prior task-specification settings to a common planner and observation interface for controlled comparison. Explicit Request [14], [18] instead specifies the task rule: “Compute the equation and move the resulting number to the end of the equation.” for T1, “Move one of the remaining items onto the mat where an item of the same category has already been placed.” for T2, and “Work out which item on the table the tool the human just put down is used on, and if there is such an item, move it onto the cutting board.” for T3. Implicit Request [24], [11] uses broad collaborative goals: “Work together with the human to complete this equation.” for T1, “Help the human organize the items on the table.” for T2, and “Help the human with what they are about to do.” for T3. Both use the same pre- and post-event observations as ours and are also evaluated without pre-event context. 

C. Experimental Results 1) Qualitative Results: Fig. 3 shows representative inter-action sequences across the three tasks. The robot completes an arithmetic expression in T1, places the object according to the inferred category mapping in T2, and identifies an object through its functional relation to the introduced tool in T3. Although these tasks require different forms of relational reasoning, the framework consistently turns the observed workspace transition into proactive assistive execution. 

2) Quantitative Results: Ours achieves 95.0% appropriate over the 120 evaluated events, as summarized in Fig. 4. Explicit request and implicit request achieve 95.8% and 90.8%, respectively, with no significant difference in failure rate from ours in paired exact McNemar tests (5.0% vs. 4.2%, 

p = 1 .0; 5.0% vs. 9.2%, p = 0 .27 ). Thus, when a correct assistive action is available, inferring it from the observed event without a user request achieves comparable appropriate rates to the request-driven variants in the evaluated tasks. The results further show that additional request informa-tion does not consistently improve assistance. In T1, all methods achieve near-saturated appropriate rates, leaving little room for additional target information to help. In T2, even with the task rule provided, the VLM can still fail to infer the correct relative placement, for example by selecting the correct object but placing it outside the target mat. Thus, task instructions do not eliminate errors in relative placement reasoning. In T3, explicit request achieves a similar appro-priate rate to ours but enters QA more often. Its reasoning trajectories are substantially shorter, and every QA case includes a candidate switch; the shorter generation may leave insufficient room to rebuild a stable run satisfying the early-stopping threshold. In contrast, our design provides event-aligned pre/post context from which the required assistive action can be inferred. During the experiments, we observed that request-driven performance was sensitive to instruction wording. Before fixing the prompts used in the main comparison, we tested semantically similar wording variants to remove linguistic ambiguity. In T2, the explicit request phrase “same kind of item” was often interpreted as requiring an identical object and caused unnecessary abstention; replacing it with “same category” reduced such errors from 28 / 60 to 6 / 60. Table I reports the revised wording. A separate T1 wording test showed a similar effect: a target description such as “the block showing 6” could also refer to the identical digit already placed in the equation, while adding “in the back row” eliminated these errors (20 / 60 → 0 / 60). Thus, request-driven performance can depend not only on the information provided but on how it is expressed, whereas ours introduces no such user instruction variable.

We next evaluate 150 boundary events across five 30-trial designs using the same object sets, grouped by whether action is optional or inappropriate. The 90 optional intervention cases include T2 with two or one demonstrated placements and T3 with a knife applicable to multiple targets. Under the system prompt in Fig. 3, unresolved multiple candidates may return wait. Thus, either a valid action or wait is accepted. V. C ONCLUSION 

We present an event-driven framework for proactive assis-tance, where robot actions are triggered by human-induced workspace state transitions rather than task instructions. Across three collaborative tasks, the framework provides overall performance comparable to request-driven variants, supporting event-driven assistance as a viable alternative to request-driven interaction.
