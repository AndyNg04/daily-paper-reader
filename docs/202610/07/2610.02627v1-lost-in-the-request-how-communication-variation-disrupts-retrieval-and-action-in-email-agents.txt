# Lost in the Request: How Communication Variation Disrupts Retrieval and Action in Email Agents 

Feng Chen, Ritam Dutt, Atnaz Taheri, Alex Williams 

fengc9@uw.edu 

## Abstract 

An email assistant should not complete less work simply because a user phrases the same request differently. Yet most benchmarks test each task with only one canoni-cal request, leaving this form of robustness largely unmeasured. We test whether email assistants remain reliable when the requested information, available evidence, and expected outcome stay fixed, but the communication style or English variety changes. We construct validated variants along five communication-style axes and four rule-based dialect conditions, and evaluate them on three benchmarks: a retrieval-augmented generation (RAG) pipeline and two tool-using agents. Indirect requests reduce performance on all three benchmarks, while formal requests reduce performance on both agentic benchmarks. Examining the systems more closely shows that these failures have different causes. Verbose requests mainly hurt a lexical retriever by making the relevant email harder to find. By contrast, indirect and dialect variants remain harmful even when the relevant email is retrieved. In the agentic setting, indirect and formal requests mainly cause the agents to omit required actions, not to take more unsupported actions. These results show that a successful response is not enough to establish robustness: evaluations should vary how requests are expressed and separately measure whether agents complete the requested work. 

## 1 Introduction 

An email assistant should not complete less work because a user asks indirectly, writes formally, adds surrounding context, or uses a different variety of English. These differences are common in real communication, but they do not necessarily change what the user wants. If the requested information, relevant evidence, named entities, and intended outcome remain the same, a reliable assistant should return the same answer or carry out the same actions. Current evaluations rarely test this expectation. Most benchmarks represent each task with one canonical request, even though the same task can be expressed in many ways. Prior work shows that semantically equivalent query formulations can change retrieval results, including for recent retrieval architectures [Penha et al., 2022, Hagen et al., 2024], and that linguistic reformulation affects both retrieval and answer generation in retrieval-augmented question answering [Cao et al., 2026]. Performance also varies across systematic varieties of English [Ziems et al., 2022, 2023, Sap et al., 2019, Srirag et al., 2025]. These findings establish that wording matters for finding and answering information, but they leave an important question for interactive agents: can a change in wording alter whether the requested work is completed? This question matters because an agent can fail without producing an obviously bad response. An assistant may identify the task, call some appropriate tools, and reply fluently while still omitting an action needed to finish the request. Conversely, it may retrieve the wrong evidence or take an unsupported action. These failures require different responses from system designers, but a single end-to-end success score does not distinguish them. Diagnostic agent benchmarks similarly show that aggregate scores can combine failures such as skipping a required tool, ignoring a tool result, or producing unsupported output [Kokane et al., 2024, Soni, arXiv:2610.02627v1 [cs.AI] 2 Oct 2026 2026]. Robustness evaluation should therefore ask not only whether performance changes, but what the system stopped doing correctly. We study whether email assistants remain reliable when the same request is expressed in different ways. We evaluate the two settings for email assistants: the retrieval-augmented generation (RAG) setting, where the system retrieves evidence from the archive and answers from it, and the agentic 

setting, where the system calls tools to carry out the request. Covering both lets us examine whether communication variation affects the information an assistant returns as well as the actions it performs. We vary communication style and English variety while keeping the underlying task and expected outcome unchanged, and validate the resulting requests to ensure that they preserve the original intent. Our work makes three contributions: • A framework for generating validated request variants. Figure 1 shows it. An LLM rewriter produces the communication-style poles and a rule-based transducer produces the dialect varieties, and a set of gates admits a variant only once it still requests the information or action asked for, carries the relevant task details, and expects the same outcome. • An evaluation spanning RAG and agentic settings. We apply the framework to email question answering and to tool-using agents, so that the same variation can be traced through retrieval, answering, and execution. • A closer analysis of assistant failures. We examine not only whether performance changes, but also whether failures come from finding the wrong information, producing an incorrect answer, omitting required actions, or taking unsupported actions. 

## 2 Evaluation Framework 

We evaluate whether a system fulfills the same request when the request is expressed differently. We consider two forms of variation. Communication style changes how a writer presents a request. 

Dialect changes grammatical and dialectal features according to patterns documented for varieties of English. Figure 1 shows how a variant is built and follows one request through a RAG pipeline. 

2.1 Variation Taxonomy 2.1.1 Communication-Style Axes 

The five axes and the definition of each pole are listed in Table 1. Each style axis pairs a reference 

pole, a plain rewrite that carries no marked style, with a contrastive pole that carries the property under test. Formality is the exception: neither a formal nor a casual register is neutral, so both of its poles are contrastive. Each axis rests on a documented distinction: directness on the contrast between on-record and off-record requests [Brown and Levinson, 1987, Mannekote et al., 2025]; formality on register variation [Pavlick and Tetreault, 2016, Rao and Tetreault, 2018]; verbosity on evidence that input length and the position of the relevant information affect model behavior [Levy et al., 2024, Liu et al., 2024]; emotion on evidence that emotional framing changes behavior on an otherwise fixed task [Li et al., 2023, Sharma et al., 2024]; and grammaticality on reported sensitivity to grammatical form [Cao et al., 2026] and on work measuring encoder robustness to grammatical error [Yin et al., 2020]. Appendix A describes each axis in full. 

2.1.2 Dialect Conditions 

We evaluate four varieties: Indian English, Colloquial Singapore English, Black South African English, and Nigerian English. Dialect differs from the non-grammatical pole in both source and interpretation. The non-grammatical pole is a constructed set of learner-like slips deliberately detached from any speech community, whereas the dialect conditions apply features documented for particular varieties. The variants are synthetic stress tests rather than samples of how individual speakers write, and every claim we make concerns system behavior rather than speakers.

2.3 Variant Validation 

Across a base query and all of its variants we hold fixed the information need or requested action, the supporting evidence, named entities, numbers, dates, protected literals, and the expected outcome. Only the wording may differ. A candidate enters the evaluation set only after clearing every gate that applies to its pole. A deterministic factual gate requires the variant to be non-empty, to differ from the original, and to preserve every numeric token and protected literal. An intent gate , a rubric judge ( gpt-5.4 ,temperature 0.0), asks whether the variant requests exactly the same information. This gate is what protects the paired design: a variant that clears it is still answerable by the same gold answer, so a difference in outcome cannot be a difference in task. A style gate asks whether the variant realizes its target pole, given that pole’s operational definition from Table 1; for dialect it instead requires at least two features documented in the electronic World Atlas of Varieties of English to have changed [Kortmann et al., 2013]. A human-likeness gate asks whether the text reads as something a person would type, which guards against rewrites that reach the style label while reading synthetic. It applies to four of the six contrastive poles except verbose and non-grammatical (prompts in Appendix E). Two authors independently labeled the same 120 variants, 20 per contrastive pole, answering the questions the gates ask. Agreement was complete on intent ( κ=1 .00 ), and reached 

82 .5% on style and 80 .0% on human-likeness. 

## 3 Experimental Setup 

3.1 Evaluation Tasks 

We apply the framework to three tasks, one RAG task and two agentic benchmarks. 

EnronQA (RAG). Retrieval-augmented question answering over a personal email archive Ryan et al. [2025]. We sample 400 questions from the training split under an isolated-axes design: four bins of 100, where each complex bin flips exactly one complexity property against the simple control. The three complex bins are 3-hop (three or more reasoning hops), multi-question (the question asks for two or more distinct things), and threaded (resolution depends on earlier messages in the thread)(detail in Appendix B). Holding the other two properties at their control setting is what makes the per-bin breakdown of §4.2.1 attributable to one property rather than to overall difficulty. Each question is paired with a gold answer and the gold email that contains it, and retrieval runs over the target user’s own inbox. 

ToolTalk (Agentic). A multi-turn tool-using benchmark [Farn and Shin, 2023]. We use the hard 

split: 50 conversations comprising 194 user turns over 28 tool APIs. Grading compares the agent’s calls against ground-truth API calls. The harness is teacher-forced: the conversation is rebuilt from the gold trajectory and the databases are reset before each assistant turn, so an error on one turn cannot propagate to the next. 

WorkBench (Agentic). A sandbox benchmark of workplace tasks across five domains [Styles et al., 2024]. We use its 90-task email domain, the subset solvable with the email toolkit alone, and expose all 26 tools on every task so that the agent must still select among them. Grading is by database state: a task is correct only if executing the agent’s predicted calls leaves the sandbox in the ground-truth state, which makes the metric binary and unforgiving of a single wrong argument. We report task accuracy. 

3.2 Models and Retrieval Systems Retrieval. EnronQA is run with three retrievers over the same corpus, all returning the top k=5 

emails. BM25 is lexical ( rank_bm25 ) and indexes the full text of every email [Robertson and Zaragoza, 2009]. SPLADE is learned-sparse ( naver/splade-v3 ), producing term-weight vectors scored by dot product [Formal et al., 2021]. BGE-M3 is dense ( BAAI/bge-m3 ) [Chen et al., 2024]. 4Both neural retrievers truncate to 512 tokens. Retrieval is identical within a retriever, so any difference between answerers under a fixed retriever is a generation difference. We use SPLADE as the headline retriever because it provides the strongest baseline retrieval among the tested systems. 

Answering and grading. We evaluate three models: gpt-5.6-terra , gpt-5.4-mini , and 

Kimi-K2.6 . All headline results use gpt-5.6-terra , which is run on all three benchmarks. The cross-model comparison of §4.3 is restricted to EnronQA and ToolTalk: running the full ten-pole grid on WorkBench for the two additional models was beyond the compute available, so that benchmark is reported on the headline model alone and the coverage actually obtained is stated in Table 6 so that what is missing is explicit. On EnronQA each model receives the retrieved emails and the question and is instructed to answer in one sentence using only the information in the email. Each agent condition is repeated with K=3 replicates whose per-scenario metrics are averaged before any test. Answers on EnronQA are graded by gpt-5.4 at temperature 0, which sees the email, the question, the gold answer, and the candidate answer and returns a single-line judgement. 

3.3 Evaluation Metrics 

Each task has its own success metric, so a percentage point is not the same quantity across benchmarks and magnitudes should not be compared between columns. EnronQA reports judged answer accuracy, and additionally Recall@5, the rate at which the gold email appears in the retrieved set. ToolTalk reports conversation success, which requires every ground-truth call to be matched with no incorrect action, along with recall of required calls, precision, and the incorrect-action rate. WorkBench reports task accuracy against the ground-truth sandbox state, and additionally the F1 between predicted and ground-truth tool calls, the rate at which no tool call is issued, and the rate at which execution leaves an unwanted change to the sandbox. 

3.4 Statistical Analysis 

Every variant is compared against the base item on the items present in both conditions. Detail shows in Appendix G. For EnronQA, each item yields one binary outcome from a single run, so the paired difference is −1, 0 or +1 . We use the exact McNemar test on those pairs, which conditions on their number and is exact at any sample size. For the other two agent benchmarks, each condition is run 

K=3 times, so for item i we average a metric over replicates before any test, then form the paired difference di = ¯ vi − ¯ni against the base item. We test the mean of those differences with a paired percentile bootstrap over items, resampling item indices with replacement B=10 ,000 times under a fixed seed, reading the 95% interval off the 2.5 and 97 .5 percentiles of the resampled means and a two-sided p-value off the proportion of them falling either side of zero.

## 5 Discussion 

5.1 Request Explicitness Affects Performance 

The most consistent communication-style effect is not the one that changes the most text, but hiding the main request in the query. Parsing every variant against its own original with a dependency parser [Honnibal et al., 2020] (Table 13), the indirect pole retains the head verb of the request as the main predicate least often on all three benchmarks, from 12 .5% of slots on EnronQA down to 

4.7% on WorkBench, and the formal pole is in the bottom three poles on all three. The two poles reach that position differently: the indirect pole deletes the original head verb in 16% to 40% of slots, whereas the formal pole retains it in 68% to 91% of slots but frequently places it in a subordinate clause. This pattern suggests that performance is influenced by changing how explicitly the request is expressed [Austin, 1975, Searle, 1975, Mannekote et al., 2025]. Recent evaluations report that models remain weaker at recovering indirect illocutionary force than at interpreting explicit requests [Koo et al., 2025, Solidjonov, 2026]. 

5.2 Incomplete Fulfillment as an Agentic Failure Mode 

An end-to-end success score combines two failures with different consequences: an agent can take an unwanted action, or it can omit an action that the request requires. For the indirect and formal poles, the dominant change is in the second type. Shown in both agentic settings, the affected agents complete less of the requested work without a corresponding increase in unsupported actions. The WorkBench trajectories show two routes into that outcome (Table 17). Under formal the agent more often never starts: the share of tasks with no tool call at all rises from 0.4% to 12 .2% (p<. 001 ), close to the −12 .2 point accuracy loss. Under indirect that share moves only to 1.5% (p=.25 ), while the F1 between predicted and ground-truth calls falls −8.42 points ( p<. 001 ), so the agent acts but the calls land in the wrong state. This result complements work showing that aggregate success rates do not identify which tool-use failure occurred [Kokane et al., 2024, Soni, 2026]. We hold the task and tool environment fixed and find that wording alone moves a system between completing a task and skipping required calls. 85.3 Dialect Robustness and Fair Access 

Dialect variation reduces performance on all three benchmarks. Our finding of performance drops across English varieties is consistent with the disparities reported for language understanding [Ziems et al., 2022, 2023, Srirag et al., 2025], for social tasks such as hate-speech detection [Sap et al., 2019], and for model judgments about people [Hofmann et al., 2024]. The dialect transformations apply grammatical features documented for each variety, whereas the non-grammatical pole is a constructed set of slips produced by a language model, which suggests that variation beyond isolated grammatical slips carries part of the effect. It is worth noticing that dialect variants are generated at feature density 

1.0, the attested upper bound, so this condition is a deliberate worst case. 

5.4 Implications for Evaluation and System Design 

Three implications can be derived from the results. First, a task should not be represented by a single canonical wording. Retrieval research has shown that results move under semantically equivalent query variation [Penha et al., 2022, Hagen et al., 2024], and Cao et al. [2026] reports the same fragility in the RAG setting. Our results extend that requirement to the agentic setting, where the same variation changes whether the requested work is carried out. Second, robustness evaluation should be stage-aware, because the same drop in a success score has different causes and therefore different fixes. Replacing BM25 with SPLADE removes most of the verbosity penalty at a comparable baseline. The indirect and dialect penalties persist when the gold evidence is retrieved. Component-level measurement has to come before the choice of mitigation, and choosing a stronger model is not a substitute for it: the model with the highest baseline on both systems where all three models were run is also the one whose results move significantly in the most conditions. Third, completeness and unsupported action should be reported separately. Required-call recall, failure to act, and read-without-write behavior are computable from a trajectory without a gold final answer, so they can be monitored where end-state grading is unavailable. They are not a substitute for final grading, but they expose a failure that response quality and safety metrics miss, and they distinguish an agent that has become appropriately cautious from one that is quietly doing less of the requested work. 

## 6 Conclusion 

We tested whether RAG-based and agentic assistants fulfill the same task when only the request’s communication style or English variety changes. Indirect requests produced the most consistent style loss; verbosity primarily disrupted lexical retrieval; and dialect sensitivity remained after accounting for whether the gold email was retrieved. Across the agentic benchmarks, indirect and formal requests mainly reduced completion of required actions. Evaluations should therefore vary request formulation, inspect intermediate retrieval and execution signals, and report required-action completion separately from unsupported action. 

## Limitations 

There are several limitations in this work. First, dialect variants are generated at feature density 1.0

only, a deliberate worst case rather than an estimate of typical use. Second, the WorkBench indirect 

pole passes only 64 of 90 slots, leading to lower coverage. Third, on ToolTalk the concise reference pole moves −9.0 points, so the reference poles are an imperfect control there. In Proceedings of the 61st Annual Meeting of the Association for Computational Linguistics (Volume 1: Long Papers) , pages 744–768, 2023. 11 A Communication-Style Axes in Detail 

The five axes summarized in Table 1 are described here in full. 

Directness. This axis separates an explicit request from one whose information need must be inferred. At the direct pole the request is stated as a question or command; at the indirect pole it is conveyed through a need, hint, observation, or expression of uncertainty. The contrast follows the distinction between on-record and off-record requests in Brown and Levinson [1987] and Mannekote et al. [2025]. 

Formality. This axis separates a polished professional register from a casual, chat-like one, fol-lowing the register variation studied in Pavlick and Tetreault [2016] and Rao and Tetreault [2018]. Formality has been reported as a source of variation in retrieval-augmented question answering in Cao et al. [2026]. 

Verbosity. This axis separates a concise request from the same request embedded in additional text. The added material is generic chatter, hedging, or digression, and introduces no new fact about the task, the evidence, or the expected answer. Prior work suggests that input length and the position of the relevant information affect model behavior [Levy et al., 2024, Liu et al., 2024]. 

Emotion. This axis separates neutral wording from wording that expresses frustration, stress, anxiety, or urgency. Emotional content in a prompt is known to change model behavior on an otherwise fixed task [Li et al., 2023], and models have been shown to revise responses under user pressure [Sharma et al., 2024]. The axis tests whether that occurs when the task, evidence, and expected outcome are held constant. 

Grammaticality. This axis separates standard written English from understandable English carrying systematic grammatical deviation, including the topic or object fronted, the question word moved with the auxiliary dropped, the verb flattened with an adverb carrying the time, or clauses split and reordered. Systematic slips sit on top of that restructuring, including dropped or wrong articles, missing plural marking, and tense or agreement errors. The pole is defined by properties of the text alone and is not conditioned on any writer attribute. 

## B EnronQA Sampling Design 

EnronQA is the only benchmark in the study for which we choose the items, so the choice is described in full. The goal was a sample on which question complexity could be read as an effect of one property at a time rather than of overall difficulty. 

Classification. Three complexity properties are assigned by a rule-based classifier over the question text alone: reasoning depth ( 1-hop , 2-hop , 3+-hop ), scored from the presence of a context prefix, a relative clause, a nested reference to something mentioned elsewhere, and two or more clause connec-tives; question multiplicity ( single-question , multi-question ), triggered by coordinating and ,

as well as or along with that introduce a new wh-clause; and context dependency ( self-contained ,

thread-dependent ), triggered by explicit reference to an earlier or prior message. Broad threading markers such as forwarded or re: were deliberately excluded, since a message in a thread can still be self-answerable. A fourth label, reasoning type, is assigned from the question and gold answer under a fixed priority order: causal, comparative, aggregation, temporal, bridging, and otherwise extraction. 

Isolation. Each bin of 100 requires exactly one of the three properties at its hard setting and the other two at the easy setting. The simple control is at most two hops, single-question and self-contained; 

3-hop raises depth only; multi-question raises multiplicity only; threaded raises context dependency only. The final selection asserts that the number of hard properties is 0 for every simple item and exactly 1 for every other item. A difference between the control and one complex bin is therefore a difference in that one property. 

Selection. The pool is the EnronQA train split restricted to users with at least 25 emails, dedupli-cated on question text and thinned to at most one question per email. Within each bin, items are 12 drawn stratified by reasoning type so that every type reaches at least 30 items across the 400 , with the residual filled to 100 per bin. Two filters run during selection. A near-duplicate guard rejects a candidate whose embedding has cosine similarity ≥ 0.80 to any question already kept. A content screen runs the question through an oracle answerer and drops it if the provider blocks or the model refuses. 

Composition. The result is 400 questions over 400 distinct emails and 99 users, 100 per bin. Reasoning types are distributed as extraction 126 , bridging 74 , causal 61 , temporal 57 , aggregation 45 

and comparative 37 . The distribution tries to replicate the distribution in the whole dataset. Retrieval runs over the target user’s own inbox, which ranges from 41 to 1023 emails with a median of 273 .

## C Verbalized Sampling 

A single rewrite request per item produces low-diversity output: the model converges on one stock opener and reuses it across items, so the resulting variant set measures one phrasing rather than a style. We therefore generate each contrastive pole with verbalized sampling, in which one call returns 

k candidates and each candidate is assigned a different framing drawn from a per-pole menu. 

Procedure. For an item with identifier q and a pole with menu M , we request k = 6 candidates in a single call. The candidates are returned as a JSON array. The six rewrites restructure the sentence six different ways rather than repeating one edit. The rotation is a deterministic function of q, seeded by an MD5 digest, so runs are reproducible and order-independent. 

Selection. Candidates are first filtered by the deterministic checks of Appendix E. The surviving candidates are then scored by the novelty of their opening words, measured as the number of times that opener has already been kept during the run, and the least-used opener wins. Ties are broken by a per-item seeded permutation of the candidate order, which prevents a fixed menu position from being systematically preferred whenever several candidates score equally. The winning candidate is then passed to the judges. If none passes, the call is repeated, twice for most poles and three times for the charged pole. 

Prompt template. The user message is constructed as shown in Appendix D.19, where k is the candidate count.

D.2 Indirectness Mechanisms 

1. PREPARATORY (hearer's knowledge): imply the ask by wondering whether the reader happens to know or could tell you the specific thing -- not a bare 'what/who/when' question. 2. DESIRE (speaker's want): state that you would like or want to know the specific thing, as a wish rather than a question. 3. REASON / MOTIVATION: give the reason or goal that makes the specific answer necessary, and let the request follow from it rather than asking outright. 4. UNMET PRECONDITION: note that you still lack the specific piece of information (you don't have it, or can't find where it is stated), so the need for it is implied. 5. EPISTEMIC UNCERTAINTY: say you can't tell or work the specific answer out from the email, leaving the question implied. 6. ASSOCIATIVE HINT: name the exact detail in the email the answer hangs on and flag that its meaning or reference is unclear, so the reader infers the ask. 7. UNDERSTATEMENT: be tentative and under-specify -- say you're a little fuzzy or hazy on the specific point, without naming it as a question. 8. PRESUPPOSITION: presuppose the specific answer exists in the email and comment around it rather than requesting it outright. 9. HYPOTHETICAL / CONDITIONAL: embedding the request inside the condition. 10. REPORTED / THIRD-PARTY: frame it as someone else having asked you this and you being unable to answer it from the email. 11. GAP OBSERVATION: point out that the email leaves the specific point unspecified or open, implying you want it resolved. 12. HEDGED APOLOGY: preface with a hedge or apology for possibly missing it, then gesture at the specific point.

D.12 Non-Grammatical Structural Profiles 

1. Topic-fronting — move the object or topic to the FRONT and comment after it, dropping articles and 'is/are' ('this report, already sent?', 'the two addresses, what they are?'). Question-inversion — break the normal question order: put the wh-word in the middle or at the END and drop the do/does/did/will auxiliary ('Larry Campbell receive confirmation by what two method?', 'the timing and start date is what?', 'why not you told me?'). You rewrite a user's QUESTION about an email to change ONLY its communication STYLE, never its meaning. Hard rules: - Preserve the intent EXACTLY: the rewritten question must request the same information and be answerable by the same answer as the original. - Keep every specific detail from the original: names, dates, numbers, quoted phrases, and the subject of the question. - Do NOT add any new question, requirement, fact, or assumption, and do NOT answer the question. - Change ONLY the target style described by the user. Never describe or alter the email itself. - Output ONLY the rewritten question text — no quotes, no labels, no commentary. 

D.14 Reference-Pole Rewrite Instructions 

Given to the generator for the four reference poles, which are produced by a single plain rewrite without verbalized sampling. The contrastive poles are generated from the pole-specific system prompts above instead. 

[directness / direct] rewrite_instruction: Rewrite as a fully explicit, on-record request: state exactly what is being asked, up front, as a clear direct question or imperative. [verbosity / concise] rewrite_instruction: Rewrite as tersely as possible: put the ask first, in one short sentence, with no extra context. [emotional_charge / calm] rewrite_instruction: Rewrite with calm, matter-of-fact, neutral affect and no emotional language. [native_likeness / native] rewrite_instruction: Rewrite in fluent, idiomatic native-English phrasing: natural word order, correct articles and prepositions, and natural collocations. Keep the exact same ask and add no new facts. 

17 D.15 Gate A: Intent Preservation 

You compare two versions of a question asked about an email. Decide whether the VARIANT asks for EXACTLY the same information as the ORIGINAL — i.e. any answer that correctly answers one would correctly answer the other. Ignore differences in tone, politeness, directness, length, or wording; judge ONLY the information requested. Respond with exactly one line: 'Verdict: yes' (same information) or 'Verdict: no' (different information). 

D.16 Gate B: Style Realization 

You check whether a rewritten question exhibits a specified communication style. Judge only the style, not the correctness or meaning of the question. Respond with exactly one line: 'Verdict: yes' (clearly exhibits the style) or 'Verdict: no' (does not). 

D.17 Fidelity Criteria for All Ten Poles 

Supplied to Gate B as the definition of the target pole. native_likeness is the grammaticality axis, and native and non_native are its two poles. 

[directness / direct] fidelity_criterion: The request is explicit and on-record — a reader immediately sees exactly what is being asked, as a direct question or command. [directness / indirect] fidelity_criterion: The request is indirect — hedged, hinted, or phrased as a wondering or a stated need — rather than a blunt, bare, on-record question or command. Conventionally-indirect forms ('I was wondering what. . . ', 'I'm trying to figure out. . . ', 'Do you happen to know. . . ') and off-record hints both count; a plain direct question ('What is X?') or an imperative does NOT. [formality / formal] fidelity_criterion: The text reads as a formal/professional register — full words (no contractions or slang) with standard capitalisation and punctuation. [formality / casual] fidelity_criterion: The text reads as casual / chat-like / informal (contractions, slang, or relaxed punctuation), while the underlying ask is unchanged. [verbosity / concise] fidelity_criterion: The text is short and the ask is stated up front. [verbosity / verbose] fidelity_criterion: The text is long and the ask is buried in the middle rather than stated up front, and no new request or factual detail has been added. [emotional_charge / calm] fidelity_criterion: The tone is calm and neutral, with no strong emotional language. [emotional_charge / charged] fidelity_criterion: The text clearly conveys frustration, anxiety, stress, or urgency (not just a plain, neutral question), while the underlying ask is unchanged. [native_likeness / native] fidelity_criterion: The text reads as fluent, idiomatic native English — natural grammar, articles, prepositions, and word choice, with no learner-like errors. [native_likeness / non_native] fidelity_criterion: The text reads as non-native / second-language (L2) English rather than fluent idiomatic native English. It may carry one or more learner-like errors (article, preposition, agreement, verb-tense, or word-order slips) or simply read as awkward or unidiomatic; it need not be heavily broken to count. 

D.18 Gate C: Human-Likeness 

You judge whether a short message reads as if a REAL PERSON genuinely wrote it, or reads as ARTIFICIAL — machine-generated, templated, or performative. The message is a QUESTION about an email, rephrased in a particular style. It may legitimately be LONG and DETAILED and name specific people, dates, addresses, or figures — length, detail, and formality are NOT signs of artificiality, so never penalize a message just for being long or thorough. It may be in any register (formal, casual, emotional, or non-native / learner English) and still be human: judge authenticity and naturalness, NOT fluency, correctness, or politeness. A non-native writer's 

18 careful, mostly-fluent question carrying a few uneven slips (missing articles, agreement, tense, or word order) IS human — it need not be heavily or evenly broken. Mark it artificial ('no') only if it reads as machine-produced: it stacks unnatural intensifiers, uses robotic or templated phrasing or mechanical eye-dialect, or bolts a foreign greeting, honorific, or tag onto otherwise-perfect native English as decoration rather than a genuine change in how the sentence is built. Respond with exactly one line: 'Verdict: yes' (reads as genuinely human) or 'Verdict: no' (reads as artificial / AI-like). 

D.19 Verbalized-Sampling User Template 

> Produce {k} DIFFERENT rewrites of the question below, each a different {noun} drawn from this list: {menu} Make the {k} rewrites as different from one another as possible (different openings and sentence shapes) while each keeps the SAME single answer and every specific detail. Each must follow all the rules in the system message. Write only the rewritten question itself for each -- never prefix a rewrite with its {noun} name, number, or any label. Original question: {question} Return ONLY a JSON array of exactly {k} strings, e.g. ["...", "..."]. No other text.

## E Validation Gates 

The candidate rewrite passes through a three-layer gate before it is admitted. Overall gate-passing rate per dataset is in Table 4 and per-pole gate-passing rate in Table 5. 

Layer 1: deterministic checks. A candidate is rejected if it is empty, if it is byte-identical to the original after normalization, or if any numeric token present in the original is absent from the variant. Missing capitalized tokens are recorded as a soft signal but do not reject, since names may legitimately be rephrased. 

Layer 2: rubric judges. Gate A (Appendix D.15) asks whether the variant requests exactly the same information. Gate B (Appendix D.16) asks whether the variant realizes the target pole, and is given that pole’s fidelity criterion from Appendix D.17. Gate C (Appendix D.18) asks whether the text reads as something a person would genuinely type. All three answer on a single line so the verdict can be parsed deterministically. 

Gate C exceptions. Gate C is not applied to the verbose pole, where a long message wrapped around a one-line question is inherently machine-like and shortening it would remove the property under test; that pole is admitted on Gates A and B alone. On the non-grammatical pole Gate C is computed and recorded but does not filter, because blocking on it would bias selection toward the mildest, least restructured rewrites. 

One low-gate-passing cell. Yield is above 80% for 29 of the 30 dataset-pole cells. WorkBench 

indirect admits 64 of 90, with the loss concentrated at Gate A: WorkBench instructions name a specific record to modify, and an indirect rewrite that hides the operation often also loses the record identifier, at which point the variant is no longer holding the same question intent as the original query.

## F EnronQA Error Labeling 

The error analysis of §4.2.1 covers the headline condition ( gpt-5.6-terra , SPLADE, judged by 

gpt-5.4 ) for baseline and ten communication style variants poles. There are 118 generation errors are slots in which the gold email was retrieved and the answer was still judged wrong, so the reader had the evidence in front of it. There are 237 retrieval failures that are slots in which the gold email never reached the reader. 

Taxonomy. Each generation error carries exactly one code, assigned under a fixed precedence so that no slot is double-counted. E6 , not a genuine reader failure, fires first and covers defective gold answers and judge strictness. E3 is an answer faithful to one of the other four retrieved emails rather than the gold one. E2b is a real proposition attached to the wrong role, subject or event, and E2a afield filled with a wrong value. These two combines to E2 , unsupported content. E4 is an answer of the wrong semantic type, for instance a name where a time was asked for. E1 is an answer that is not false but incomplete. E5 , false abstention, is a claim that the evidence does not contain the answer when it does. Retrieval failures use three codes: R1 reports the asked fact absent, R2 hedges, and R3 

answers confidently anyway. 

Procedure. Labels were assigned by claude-opus-5 . For each slot it saw the original question, the rewrite, the gold answer with its accepted alternates, the model answer, the baseline answer, and the full text of every retrieved email, and returned one code with a written rationale. One author then reviewed all 118 labels against the same evidence and recoded 23 where the rationale did not support the code under the precedence rule. 

Slices. An error is style-induced when the unperturbed request answered the item correctly and the rewrite broke it ( 44 slots), persistent when the baseline was already wrong ( 65 ), and baseline 

when it is the unperturbed run’s own error ( 9). Table 8 sets the style-induced slice against the other two pooled, which isolates the kind of failure a rewrite produces. Two codes appear only in the style-induced slice: answering in the wrong semantic type ( 4 slots) and falsely reporting the answer absent ( 2), both of which misread the request. Answering from another retrieved email runs the other way, 9.1% of the style-induced slice against 27 .0% of the rest. Unsupported content is the largest category in both, 43 .2% and 47 .3% .

Missing evidence. The 237 retrieval failures are coded separately. The reader reports the fact absent in 55 of them ( 23 .2% ), hedges in 6 (2.5% ), and answers confidently anyway in 176 (74 .3% ). The checklist is designed to encourage best practices for responsible machine learning research, addressing issues of reproducibility, transparency, research ethics, and societal impact. Do not remove the checklist: The papers not including the checklist will be desk rejected. The checklist should follow the references and follow the (optional) supplemental material. The checklist does NOT count towards the page limit. Please read the checklist guidelines carefully for information on how to answer these questions. For each question in the checklist: • You should answer [Yes], [No], or [N/A]. • [N/A] means either that the question is Not Applicable for that particular paper or the relevant information is Not Available. • Please provide a short (1–2 sentence) justification right after your answer (even for [N/A]). 

The checklist answers are an integral part of your paper submission. They are visible to the reviewers, area chairs, senior area chairs, and ethics reviewers. You will also be asked to include it (after eventual revisions) with the final version of your paper, and its final version will be published with the paper. The reviewers of your paper will be asked to use the checklist as one of the factors in their evaluation. While [Yes] is generally preferable to [No], it is perfectly acceptable to answer [No] provided a proper justification is given (e.g., error bars are not reported because it would be too computationally expensive” or “we were unable to find the license for the dataset we used”). In general, answering [No] or [N/A] is not grounds for rejection. While the questions are phrased in a binary way, we acknowledge that the true answer is often more nuanced, so please just use your best judgment and write a justification to elaborate. All supporting evidence can appear either in the main paper or the supplemental material, provided in appendix. If you answer [Yes] to a question, in the justification please point to the section(s) where related material for the question can be found.
