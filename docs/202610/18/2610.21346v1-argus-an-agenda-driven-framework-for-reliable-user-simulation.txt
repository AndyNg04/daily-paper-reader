Abstract 

High-fidelity user simulators are essential for evaluating and training agents in interactive environments. However, current LLM-based simulators struggle with reliability issues, such as goal omission and policy non-compliance. We propose A RGUS (Agenda-d Riven Goal-oriented 

User Simulator), a neuro-symbolic framework that maintains the user’s goal state using a dynamic agenda stack manipulated via symbolic operations. By rigorously decoupling state tracking from natural language generation, A RGUS facilitates strict goal progression and constraint-aligned interactions. For cost-efficient deployment, we distill A RGUS into compact models using a unified pipeline: evaluator-guided SFT followed by online RL with dense step-level rewards. To rigorously evaluate behavioral fidelity, we introduce a rubric-based metric Composite Behavioral Score (CBS). Evaluations on τ 3-Bench and MultiWOZ demonstrate the significant superiority of the A RGUS 

architecture and the efficacy of our training pipeline. Code and data will be released soon. 

# 1 Introduction 

As large language models (LLMs) increasingly operate as autonomous agents in open-ended tasks, the demand for robust, scalable interactive environments has surged (Wang et al., 2024). Given the prohibitive cost of human-in-the-loop interaction, User Simulators have become indispensable. Beyond its traditional role for automated agent evaluation, a reliable user simulator is now recognized as a critical engine for synthetic data generation across domains like task-oriented dialogue and simulated human feedback (Balog and Zhai, 2026). Regardless of the application, the core prerequisite is exceptional behavioral fidelity : the simulator should strictly adhere to complex, multi-step goals and interaction protocols without hallucination or arbitrary deviation. Simulating authentic user behavior is inherently a complex sequential decision-making process. Over multiple turns, simulators struggle with maintaining strict goal progression (tracking subtask completion to prevent omissions) and enforcing policy adherence (following constraints without hallucinating or leaking unprompted information). Existing paradigms manage these challenges suboptimally. Most native LLM-based simulators operate statelessly, collapsing intent reasoning, progress tracking, and response generation into a single forward pass (Terragni et al., 2023). ## 3.1 Neuro-Symbolic User Simulation 

ARGUS processes each user turn in two decoupled phases: state updating and response generation. 

State Representation. The runtime state St comprises a static user profile frame and a dynamic Last-In-First-Out (LIFO) agenda stack. At initialization, a parser (GPT-5.1, Appendix A) converts the textual goal G into a user profile P (encompassing the persona and communication policies) and a task set T = {T1, . . . , T n}, which encapsulates the tasks the simulator must convey and advance, alongside their static attributes and conditional triggers. Each stack frame f is structured as a ⟨task , type ⟩ pair. We label persistent goals initialized from the structured goal as main tasks and transient interaction needs introduced during dialogue as sub-tasks; both are ordinary agenda frames. 

Phase 1: State Updating ( Φ). The state transition function Φ leverages the LLM’s tool-calling capabilities to execute constrained symbolic operations on the agenda stack: 

op t ∈ { PUSH , POP , MODIFY , WAIT } (4) At each turn, the state controller emits one or more agenda operations. P USH creates a new frame at the top of the stack when an unmet interaction need must be handled before the pending frame. P OP 

removes the top frame once its corresponding interaction need has been satisfied, subject to the stack lifecycle rules. M ODIFY updates the content or status of a relevant pending frame when an observed agent message triggers a conditional behavior, without changing the stack depth. W AIT leaves the agenda unchanged when the latest agent message requires no state transition; the response generator still produces the next user utterance from this unchanged state. Consequently, the model can focus on realizing a response consistent with the updated agenda and dialogue context. 43.2 Training Pipeline 

While prompt-based A RGUS excels with frontier LLMs, practical deployment requires cost-efficient inference. We propose a two-stage training pipeline to distill this architecture into compact models (e.g., 4B/8B parameters). A unified Step-Level Evaluator serves as a shared supervision mechanism for SFT data filtering and RL reward assignment. 

The Step-Level Evaluator. Relying solely on trajectory-level task success to train user simulators has several structural limitations. First, it reduces data efficiency by discarding valid intermediate behaviors from challenging or ultimately unsuccessful dialogues. Second, it may reward behavioral “shortcuts,” whereby the simulator violates user constraints or deviates from the intended agenda but nevertheless reaches a successful terminal state. To encourage realistic and consistent user behavior, we employ an LLM-based evaluator that assesses every user step (defined as either Phase 1 or Phase 2 of a turn) via scoring across three dimensions: Soundness , Faithfulness , and Adherence 

(Appendix §B). Each dimension is further operationalized through multiple binary atomic checks, enabling fine-grained and interpretable supervision. 

Stage 1: Evaluator-Guided SFT. A strong teacher LLM interacts with a capable agent to generate candidate trajectories. Instead of traditional trajectory-level rejection sampling, we apply our Step-Level Evaluator for rigorous filtering: a user step is retained for supervised fine-tuning (SFT) only if 

it achieves a perfect score across all three dimensions. This discards flawed intermediary behaviors and establishes a robust behavioral prior for the student model. 

Stage 2: Online RL with Adapted DAPO. To explore broader interaction distributions and recovery strategies, we further optimize the model through online reinforcement learning using an adapted variant of DAPO (Yu et al., 2025). At each training step, we discard rollout groups whose candidates receive identical rewards and continue collecting informative groups until the predefined batch size is reached, thereby ensuring sufficient gradient signal for policy updates. We additionally balance the numbers of Stack and NLG groups within each training batch and maintain equal samples across domains, preventing the training distribution from becoming biased toward particular stages or domains due to differences in task difficulty. We use the Step-Level Evaluator as the reward model. During online interaction with the environment, we collect N rollouts for each user step under the same environment state. The evaluator scores each rollout using a fine-grained reward computed as the harmonic mean of the three dimension scores, where each dimension score is the arithmetic mean of its binary atomic checks. These rewards are subsequently used for policy optimization. To advance the live environment, we randomly sample one of the N rollouts rather than greedily selecting the highest-scoring branch. In the spirit of TreeRL (Hou et al., 2025), this strategy encourages broader exploration and reduces overfitting to the reward model. The resulting step-level rewards provide localized behavioral supervision for reducing hallucinations and improving agenda adherence throughout training.

## 4.1 Evaluation Metrics 

Task Success Rate (TSR) is a widely adopted metric in complex interactive tasks that measures whether the agent completes all assigned goals. TSR indirectly reflects the performance of a user simulator because the simulator must communicate its objectives effectively for the agent to succeed. However, it remains fundamentally an agent-side signal and has structural limitations as a primary measure of simulator quality. Specifically, TSR is highly susceptible to unrealistic simulator “shortcuts,” such as prematurely revealing constraints or hallucinating details, which easily guide the agent to success while violating realistic user protocols. Consequently, TSR serves solely as an auxiliary reference in this work; we provide a detailed discussion regarding its unreliability in §6.2. To rigorously evaluate simulator fidelity, we propose the Composite Behavioral Score (CBS) as our primary metric. CBS leverages an LLM-as-a-judge (Qwen3-MoE-235B) to evaluate the dialogue across four rigorous dimensions: Faithfulness & Consistency (Sfaith ), Policy Adherence (Spolicy ), Goal 

6Completion & Progression (Sgoal ), and Format & Protocol (Sformat ). For a given dimension to pass, all of its constituent binary sub-criteria must be satisfied. The final CBS is computed as the harmonic mean of these four pass rates: CBS = 4

# 5 Empirical Results 

## 5.1 Prompt-Based Simulators 

Table 1 demonstrates that the prompt-based A RGUS consistently outperforms the baselines across most backbones and domains. This performance gap widens in the more challenging Retail domain, validating the necessity of robust state management for user simulation in complex tasks. Concurrently, Task Success Rates (TSR) generally improve alongside CBS, aligning with our expectations: by strictly adhering to user goals and committing fewer behavioral errors, A RGUS 

avoids artificially hindering the agent’s task resolution. Controlled variants with matched structured goals and behavioral prompt constraints improve the stateless baselines in several settings, but A RGUS 

retains the highest CBS throughout the controlled comparisons (Appendix §G.2). We provide a fine-grained analysis of error patterns in §6.1, highlighting the distinct advantages of A RGUS .Interestingly, the performance margin of A RGUS exhibits an inverse U-shape relative to underlying model capability. For smaller 8B models, the margin is narrow because Phase 1 relies heavily on tool-calling. These models struggle to execute consecutive agenda operations flawlessly, which leads to state preservation errors. Conversely, massive frontier models (e.g., 235B) raise the baseline floor, enabling even Vanilla to achieve high CBS scores. Consequently, the intermediate capability tier is where A RGUS yields the largest benefits. Nevertheless, A RGUS retains a clear advantage even in the high-capability regime, demonstrating robust generalizability and structural superiority.

## 5.3 Robustness Across Task Complexity 

To test whether A RGUS maintains its advantage as goal complexity increases, we partition the 114 Retail tasks into four balanced tiers—Easy, Medium, Hard, and Expert—by the number of key database-modifying actions and conditional behaviors (Appendix H). As Figure 3 illustrates, TSR decreases monotonically with rising complexity, validating our partition. Across all tiers, A RGUS consistently achieves the highest CBS, demonstrating its robust structural advantage regardless of goal complexity. Synthesizing both metrics reveals the intricate interplay between TSR and CBS. On Easy tasks, TSR saturates due to sufficient agent capability, thereby failing to differentiate simulator quality. Conversely, on Expert tasks, the agent itself becomes the bottleneck; thus, a substantial lead in simulation quality (e.g., A RGUS ’s +10.3% CBS over Vanilla) yields only a marginal TSR gain (+2.8%). Only on Medium and Hard tasks does superior simulation prominently translate into higher downstream TSR. This dynamic reinforces the necessity of adopting CBS as the primary behavioral benchmark, rather than relying solely on the task success rate. 

## 5.4 Inference Cost Analysis 

While prompt-based A RGUS sets a high behavioral ceiling, its two-stage paradigm adds inference overhead, motivating our training pipeline. Figure 4 plots inference cost per dialogue (from official API pricing; Appendix §J) against CBS, with the upper-left region denoting the low-cost, high-quality Pareto frontier. Prompt-based baselines cluster in either low-quality/cheap or high-quality/expensive regions, whereas trained A RGUS variants advance this frontier. By matching massive 235B configurations at a fraction of the cost, trained A RGUS mitigates the cost-quality dilemma and enables reliable deployment at large scale.

## 6.2 The Illusion of Success 

Our fine-grained error analysis reveals a critical measurement flaw: baseline simulators often violate behavioral protocols while still guiding the agent to task success. We define an Illusory Success 

(False Positive, FP) as a dialogue where the agent succeeds (TSR = 1 ) despite simulator violations (CBS < 1). The False Positive Rate (FPR = FP TP +FP ) measures the share of reported successes built on flawed simulations. As Figure 6 illustrates, baselines exhibit severe FPRs of 48.1%–60.6%, whereas A RGUS reduces the FPR to 33.6%. Qualitative analysis indicates that many “illusory successes” arise from unrealistic simulator shortcuts, including the premature disclosure of key information or future trajectories and unconditional compromise when the agent struggles. These behaviors artificially ease the agent’s decision-making burden. This also suggests that for RL-based agent training, using TSR alone could therefore induce reward hacking, encouraging agents to exploit simulator loopholes rather than improve genuine task-solving ability. For benchmarking, isolating dialogues where the simulator fully satisfies all criteria (CBS=1, covering both Genuine Successes [TP] and Unfair Failures [FN]) yields a stricter testbed that better reveals agent capability boundaries. ## 6.3 Advantage of RL over SFT 

A natural question is whether RL is necessary, or whether more SFT data suffices. # 7 Related Work 

Agenda-Based User Simulators. Classical user simulators use explicit goals and agenda-based dialogue acts to support controllable state updates and policy learning (Schatzmann et al., 2007; Schatzmann and Young, 2009). 

LLM-Based User Simulators. LLM-based simulators replace hand-crafted acts with prompting or in-context learning, making user simulation more flexible across domains (Terragni et al., 2023; Davidson et al., 2023; Chen et al., 2021; Algherairy and Ahmed, 2025). Related work also uses LLMs for interactive evaluation, data generation, fine-tuning, and verification (Kazi et al., 2024; Cheng et al., 2022; Niu et al., 2024; Sekuli´ c et al., 2024; Luo et al., 2024), while another line studies diversity, persona control, and implicit user profiles (Liu et al., 2023; Ahmad et al., 2025; Nakano et al., 2025; Gromada et al., 2025; Wang et al., 2025; Sun et al., 2023; Naous et al., 2025). 

Stateful User Simulators. UGST is the most relevant stateful baseline, tracking user-goal progress and using the tracked state to guide response generation (Mehri et al., 2025). Recent methods add persona control or structured reasoning over dynamic goals and trajectories (Karthikeyan, 2025; Zhang et al., 2026). ARGUS differs by making state operational through a LIFO agenda stack updated by constrained symbolic operations, rather than treating state as a descriptive summary or trace. 10 8 Conclusion 

This paper presents ARGUS, a novel neuro-symbolic framework that addresses the persistent challenges of goal omission, context drift, and policy non-compliance in LLM-based user simulators. By decoupling logical state tracking via a dynamic LIFO agenda stack from natural language generation, ARGUS enhances rigorous goal progression and high behavioral fidelity. To overcome the inference costs associated with large models, we introduced a unified two-stage distillation pipeline comprising evaluator-guided SFT and behavior-aware online RL. This pipeline transfers these capabilities to compact 4B and 8B models. Evaluations across complex interactive environments, using our newly proposed multi-dimensional Composite Behavioral Score (CBS), demonstrate that ARGUS structurally advances the existing cost-quality Pareto frontier. Despite these gains, A RGUS has two main limitations. Errors in goal parsing or agenda updates may propagate to response generation because the current pipeline does not explicitly verify or revise its intermediate state. Moreover, the agenda-based design assumes that goals can be represented as structured tasks, and its extension to open-ended conversations without clear target states remains to be studied. Ultimately, ARGUS provides a scalable, highly reliable solution for synthetic data generation and the rigorous evaluation of autonomous agents. 11 AI use statement

# A Initial Goal Extraction and Agenda Initialization 

This appendix describes the initialization step used in § 3.1. The goal of this component is to convert a natural-language user scenario into a structured goal state, which is then used to initialize the static user profile and the initial agenda stack of A RGUS .15 A.1 Extraction Pipeline 

For each benchmark instance, the input is the full natural-language user scenario, including the user’s background information, private constraints, task instructions, and reason for contacting the agent. This scenario is inserted into the extraction prompt in Prompt 1. The model output must be a strict JSON object containing a global user profile and a list of task objects. The extracted JSON is verified before it is used. We first check whether the output is parseable JSON. If parsing succeeds, a verifier model receives the raw scenario and the generated JSON, and scores whether the JSON faithfully represents the scenario under the schema rules in Prompt 2. If the verifier returns a failing score, the extraction model revises the JSON using the verifier feedback. We retry this extract-and-verify loop up to five times. 

## A.2 Structured Goal State 

The extracted user_profile stores global persona, communication policies, and static data such as names, zip codes, email addresses, or other hard facts. Each extracted task contains four components: the task itself, a requirements field describing the user’s requested outcome and constraints, task-specific static_data , and optional conditional_behaviors . The extracted tasks are used to initialize the agenda stack in scenario order: the task that should be handled first is placed at the top of the stack, while later tasks are placed below it. We separate default requirements from conditional behaviors because the stack controller must trigger fallback, narrowing, or abandonment logic only when the corresponding agent message makes the condition true.

# B Step-Level Evaluator 

This appendix details the step-level evaluator used in § 3.2. Each user turn in A RGUS contains two separately judged steps: the stack operation step and the natural-language generation step. The evaluator first audits whether the stack operations are correct, and then audits whether the final user response is consistent with the updated agenda stack and the original goal. For supervised fine-tuning, a candidate turn is retained only if both the stack operation step and the natural-language generation step pass all three evaluation dimensions. For reinforcement learning, the two stages are evaluated separately and their dimension-level scores provide dense rewards for the corresponding model outputs. 

## B.1 Stage 1: Stack Logic Evaluation 

The stack logic evaluator receives the user goal, conversation history, latest agent message, stack before the operation, simulator reasoning, and the executed stack operations. It judges push_task ,

pop_task , modify_top_task , and wait under three binary dimensions: Soundness , Faithfulness ,and Adherence . Soundness checks stack lifecycle correctness, including timely pushes, non-premature pops, cascade popping of completed subtasks, and main-task popping only after explicit completion. Faithfulness checks that operation arguments and reasons are grounded in the user goal or dialogue context. Adherence checks whether conditional behaviors and persona constraints are triggered exactly when required. The full prompt is shown in Prompt 3. 

## B.2 Stage 2: NLG Consistency Evaluation 

The NLG consistency evaluator receives the updated agenda stack, user profile, dialogue history, the agent’s latest message, and the generated user response. It again uses the three binary dimensions. Soundness checks whether the response directly and completely fulfills the updated stack top without scope creep. Faithfulness checks whether all factual content is grounded in the goal, profile, or dialogue. Adherence checks persona, communication policy, privacy, bundling policy, and response realism. The full prompt is shown in Prompt 4.

# C Interactive MultiWOZ Environment 

We convert MultiWOZ into an executable environment with writable domain state, shared service layers, and final-state verification. Starting from the original MultiWOZ entities and constraints, we add normalized schemas, controllable state, transactional records, contact and payment information, and executable APIs for hotel, restaurant, train, taxi, attraction, and public-service domains, together with shared geographic, contact, payment, and utility services. The resulting MultiWOZ test set contains 155 tasks, including 125 single-domain tasks and 30 multi-domain tasks. 

## C.1 Data Cleaning and State Construction 

We first normalize the original database. Entity identifiers are converted to strings and standardized with domain-specific prefixes, such as hotel_ , rest_ , and attraction_ . Postcodes are lowercased and stripped of spaces. Missing or inconsistent key fields, including address, phone number, and location, are repaired when necessary. For public-service domains, we enrich hospital and police records with missing addresses and geographic coordinates. Hospital records are deduplicated and separated into hospital-level metadata and department-level entries. We introduce a controllable seven-day state window starting from 2026-01-05. Dates are represented in YYYY-MM-DD format and times use 24-hour HH:MM format. The state covers domains that require availability checks or transactional updates, including hotels, restaurants, trains, and taxis. Each domain maintains its own writable inventory and booking state, while time, geography, contact, and payment are represented as shared service layers. This separation allows single-domain tasks to be generated and verified without unintended interference, while still supporting cross-domain dependencies when a task explicitly requires them. For hotels, we add room catalogs and room types, together with daily prices, inventory, and booking calendars. Hotel state also includes attributes such as breakfast inclusion and checkout time, enabling tasks involving room-type constraints, price comparison, unavailable options, booking modification, and cancellation. For restaurants, we add table types, structured opening hours, reservation availability, and slot-level table inventory. Reservation state is generated for lunch and dinner periods with 30-minute granularity. This supports tasks involving unavailable time slots, party-size constraints, fallback times, and reservation changes. For trains, we retain the original train identifiers and add seat inventory over the seven-day state window. Inventory is organized by class and seat type. Seat maps distinguish window and aisle preferences, with A/D seats treated as window seats and B/C seats treated as aisle seats; first and business classes use A/D seats only. ## C.2 Tool Design 

The API design follows three principles. First, each transactional domain supports a closed-loop interaction pattern: search, availability or feasibility checking, booking, modification, cancellation, and booking lookup. Second, state-changing tools are verifiable: booking, modification, and cancellation operations update domain state, inventory, calendars, contact records, and payment information when applicable. Third, tools enforce identity and payment constraints. Modification and cancellation require matching contact information, and paid operations validate the required amount before updating state. Table 4 summarizes the supported operations by domain and shared service layer. 

## C.3 Closed-loop Behavior and Verification 

For each transactional domain, tools support a complete execution loop. Search tools retrieve candidate entities under static and optional dynamic constraints. Availability or search-based feasibility checks verify whether a candidate can satisfy the requested date, time, capacity, room type, seat type, or route constraint. Booking tools create records and update domain state. Modification tools verify contact identity, recompute availability and price differences, and update inventory and 19 payment state. Cancellation tools mark bookings as cancelled, release reserved resources, and refund balances when applicable. This closed-loop design allows tasks to include realistic failure and fallback paths. For example, a hotel task may require fallback when the requested room type is unavailable; a restaurant task may require selecting another time slot; a train task may require falling back from a preferred seat type; and a taxi task may require comparing fares before booking. Since these tools update state, task success can be evaluated through final-state checks rather than surface-form matching. 

## C.4 Cross-domain Support 

The converted environment supports cross-domain task construction. Geographic tools enable constraints such as nearest hotels, restaurants near attractions, taxi routes between selected entities, and maximum-distance requirements. Temporal state enables dependencies among train arrival times, taxi pickup times, restaurant reservations, and hotel check-in dates. The contact and payment layer supports cost-sensitive tasks, including insufficient-balance failures, alternative selections, and refund verification. These additions make the converted MultiWOZ environment suitable for interactive user simulation and agent evaluation, where success depends on both retrieving correct information and performing valid state-changing actions under realistic constraints. 

# D Data Construction Details 

## D.1 Case Construction 

We use the following construction pipeline to generate Retail and MultiWOZ training and evaluation cases. The pipeline automatically transforms high-level user intents into executable tasks and verifiable final-state checks, while ensuring that the generated cases are grounded in the actual database and environment state. All construction stages are performed with GPT-5.4. We first generate a general case description from the environment background, database and state format, available task types, and few-shot examples. The description specifies the user’s high-level intent, the intended interaction pattern, and possible failure or fallback rules, but does not yet bind the task to concrete entities or database values. We then ground the case through an agentic planning process. The planner interacts with the actual database and state through a small set of controlled resolvers, including initial booking construction, pool-based case selection, search, and candidate selection. Search handles filtering and feasibility checks over the database and state, while candidate selection can directly choose one returned search result as the entity or value needed by the case. To keep the process controllable, each planning step calls only one resolver and resolver arguments are expressed by referring to previous results rather than by inventing free-form values. As part of pool-based case selection, we maintain precomputed pools built from the database and environment state. These pools improve both feasibility and coverage. Common-case pools cover ordinary valid scenarios, while corner-case pools target rare or difficult situations such as inventory boundaries, partially available slots, ambiguous candidates, price extremes, and fallback-triggering failures. During planning, the model may directly select cases from these pools or use them as anchors for grounding more complex cases. The planner iteratively updates the case according to resolver feedback, such as missing candidates, non-unique results, or confirmed shortfalls. It may revise non-essential details, add grounded 20 constraints, or apply deterministic tie-breaking rules while preserving the core user intent. Cases that cannot be grounded into feasible and coherent tasks are discarded or regenerated. The output of this stage is an agentic trajectory that records resolver calls, selected entities, grounded facts, state-dependent values, and fallback decisions. Based on this trajectory and the initial case description, we generate the natural-language user task, the simulator initial state, and a gold executable solution used to derive the expected final-state check. The generation follows the trajectory order, so the user task reflects the intended information-disclosure process. Although the gold solution records the intended action sequence, task success is ultimately determined by comparing the resulting environment state against the expected final-state check. 

## D.2 Case Validation 

Generated cases are validated through a two-stage process. First, we use a solo-mode procedure from 

τ 2-Bench (Barres et al., 2025). An LLM is given the generated task and asked to solve it directly by executing actions in the environment, without simulating a full user-agent conversation. We then compare the final database or environment state against the expected final-state check. This validation is performed as a single attempt without retry; if the final state satisfies the check on that attempt, the case passes the first validation stage. Second, we use another LLM as an auditor. The auditor compares the task, trace, and expected final-state check to verify that the task is faithful to the grounded facts, all user constraints are supported by the trace, the expected final state correctly captures task completion, and the case does not contain ambiguity or missing information. We retain only cases that pass both validation stages, which helps ensure the correctness of the generated tasks and final-state checks. For the MultiWOZ test set, we additionally perform manual review to further ensure case correctness. 

## D.3 Human Evaluation Setup 

All human evaluations in this work were conducted internally by the authors acting as expert annotators. No external participants or crowdworkers were recruited, and therefore no financial compensation was applicable. For MultiWOZ test-set verification, annotators were instructed to check whether each constructed task was grounded in the database state, whether the user requirements were unambiguous and executable, and whether the expected final-state check correctly captured task completion. For CBS alignment validation, annotators followed the CBS criteria and binary subcriteria defined in Appendix §E.1. The evaluated materials consist only of synthetic or benchmark-derived task descriptions and dialogue transcripts, without personally identifiable information. 

# E CBS Evaluation Framework 

## E.1 Evaluation Protocol 

The Composite Behavioral Score (CBS) evaluates simulator quality along four dimensions, each decomposed into binary subcriteria. Table 5 lists all 12 subcriteria. For each dialogue, a subcriterion is scored 1 (pass) or 0 (fail). A dimension passes only when all of its subcriteria pass (strict AND logic). The final CBS score is the harmonic mean of the four dimension-level average pass rates across all evaluated dialogues. To reduce variance, we use structured prompting with explicit pass/fail definitions for each subcriterion. The strict AND aggregation within dimensions ensures that a single violation in any subcriterion causes the entire dimension to fail, reflecting the principle that a reliable simulator must avoid all categories of errors rather than compensating one type with strength in another. The harmonic mean makes CBS sensitive to the weakest behavioral dimension rather than rewarding high average performance alone. For example, a simulator scoring 0.95 on three dimensions but only 0.35 on the fourth receives a CBS of 0.665, below a simulator that scores 0.80 on all four dimensions. This reflects our evaluation goal: a reliable simulator should avoid critical failures across all CBS dimensions, rather than compensating for a severe weakness in one dimension with strong performance in others. 

## E.2 Human Alignment Validation 

We validate the reliability of CBS in two ways: first, by checking whether expert annotators can apply the rubric consistently, and second, by measuring whether LLM judges agree with human labels and with each other. This validation is intended to test the rubric itself, not only the particular judge model used in our main experiments. We randomly sample 90 dialogues, with 45 from Retail and 45 from MultiWOZ, covering 3 simulator types and 3 backbone models. Five authors of this paper act as expert annotators and label the 12 binary CBS subcriteria. To estimate inter-annotator agreement (IAA), all annotators label the same 15 shared cases. The remaining 75 cases are split across annotators so that each annotator labels 30 cases in total, including the 15 shared cases and 15 unique cases. This design yields 150 human–LLM annotation pairs for each subcriterion. We then evaluate Qwen3-MoE-235B, our primary CBS judge, against the human labels, and run GPT-5.4 with the same evaluator prompts as an independent cross-model check. Because CBS labels are highly imbalanced, with most subcriteria passing in most dialogues, we report Gwet’s AC2 for the multi-annotator IAA setting and Gwet’s AC1 for pairwise comparisons. These metrics are better suited to high-prevalence binary labels than agreement measures whose chance correction is dominated by marginal label frequencies (Gwet, 2008). Table 7 consolidates the validation results. Human annotators reach strong overall agreement (AC2 = 0.861), indicating that the CBS rubric is sufficiently clear for consistent human application. Qwen3-MoE-235B also aligns closely with human labels (AC1 = 0.812), and GPT-5.4 provides a consistent independent check (human agreement AC1 = 0.748; Qwen–GPT agreement AC1 = 0.775). Agreement is strongest on objective structural subcriteria such as Protocol Failure, State Confusion, and Stagnation, and weakest on Conditional Logic Failure, where judging whether a conditional rule was correctly enforced is inherently more context-dependent. We therefore use Qwen3-MoE-235B as the primary judge in the main experiments, while the GPT-5.4 results provide additional evidence that the CBS rubric is not tied to a single judge model. To further test whether CBS-based model comparisons depend on the choice of judge, we conduct a full-cell robustness analysis on R ETAIL using DeepSeek-V4.1-Flash as an alternative judge. This analysis covers 24 method cells formed by four Qwen-series backbones and six user-simulation methods. As shown in Table 6, the cell-level CBS scores produced by Qwen3-MoE-235B and DeepSeek are strongly correlated (Pearson’s r = 0 .873 , Spearman’s ρ = 0 .886 , and Kendall’s τb =0.746 ). Agreement reaches 93 .81% with Cohen’s κ = 0 .624 for Protocol Failure. More importantly, the two judges agree on 91 .67% of within-backbone method orderings, with an aggregate-ranking Kendall’s τb = 0 .966 . Under task-level cluster bootstrap resampling, the probability that ARGUS ranks first under the DeepSeek judge ranges from 95 .49% to 99 .92% across the four backbones. 23 These results indicate that the relative method rankings, particularly the leading performance of ARGUS, are robust to the choice of CBS judge. # F Implementation Details 

## F.1 ARGUS Implementations 

As a decoupled two-phase architecture, the core state management of ARGUS is driven by an external agenda stack, which we implement as a dedicated Python class that securely maintains the dynamic Last-In-First-Out (LIFO) structure. 

Prompt-Based Implementation Phase 1 and 2 utilize distinct system prompts (Prompts 9 and 10). Because we found that open-weight LLMs (e.g., Qwen series) struggle to simultaneously reason and execute tool calls in a single turn, Phase 1 provides five OpenAI-format tools: an explicit think tool, alongside four core stack operations (P USH , P OP , M ODIFY , W AIT ). The LLM must invoke think 

before updating the stack. Consecutive tool calls are parsed and applied sequentially to the Python class. To ensure stack safety, any invalid or malformed tool calls are automatically intercepted and ignored, preventing execution. In the current implementation, we do not utilize an exception-handling mechanism (e.g., returning error messages to prompt a retry loop), which remains a direction for future optimization. In Phase 2, the model is not provided with any external tools and instead strictly utilizes a ReAct-style reasoning format to generate the final natural language response based on the updated stack. 

Trained Implementation For the trained ARGUS variants, the complex two-phase operational logic is deeply internalized into the model weights through our training pipeline. Having learned the syntax and semantics of the stack operations natively, they no longer require the heavy tool-calling workarounds or the extensive instruction sets used in the prompt-based setup. Consequently, the system prompts for the trained models (detailed in Prompts 11 and 12) are significantly more concise, allowing the distilled models to manipulate the stack and generate high-fidelity responses with minimal input overhead.

## F.3 Training Details 

All training experiments are conducted using the veRL framework (Sheng et al., 2024) on eight NVIDIA A800 GPUs. 

Supervised Fine-Tuning (SFT). All SFT experiments (Naive-SFT, UGST-SFT, and A RGUS -SFT) employ the following hyperparameters: 10,000 training samples, a maximum sequence length of 8192, a batch size of 64, a learning rate of 1 × 10 −5, and 1 training epoch. For Naive-SFT and UGST-SFT, the training data is constructed by extracting teacher-simulator trajectories (Qwen3-MoE-235B) that successfully complete the task, without additional step-level filtering. In contrast, A RGUS -SFT utilizes the Evaluator-Guided filtering mechanism to rigorously select training samples step-by-step, as detailed in §3.2. 

Reinforcement Learning (RL). All RL experiments (UGST-RL and A RGUS -RL) utilize the following hyperparameters: a batch size of 64, a KL penalty coefficient of 0.005, N = 4 rollouts per sample, and a total of 25 training steps. UGST-RL uses pre-sampled interaction states for rollout collection and step scoring. For A RGUS -RL, we customize the data collection module within the veRL framework to dynamically acquire rollout data and corresponding reward signals directly from the live τ 3-Bench environment, thereby strictly preserving the on-policy nature of the training process. To optimize efficiency, we implement a parallel session manager for the τ 3-Bench environment that maintains 24 concurrent interaction sessions. This asynchronous design provides a robustness margin, ensuring that the buffer accumulates a full batch of training data within approximately a single interaction round per step, thereby substantially reducing the overall training time.

Although our SFT data comprises step-level transitions filtered from both successful and unsuccessful trajectories, imitating these high-quality, progress-making steps inherently biases the model toward sustaining the conversation. Conversely, we hypothesize that RL’s dense step-level rewards induce a risk-averse, myopic effect: while strict penalties for local errors explain its high FC and PA, they inadvertently encourage the agent to prematurely terminate dialogues to avoid accumulating future penalties. Future work will explore integrating trajectory-level global scoring—such as incorporating CBS directly into the reward formulation—to better balance step-wise compliance with long-term goal completion.

Implications for CBS aggregation. The harmonic mean used by CBS heavily penalizes the weakest dimension. Although SFT leads on GC, its persistent shortfall on FC and PA (the two most semantically demanding dimensions) dominates the harmonic aggregation, keeping its overall CBS below RL. This reflects the metric’s design: reliable simulation requires jointly avoiding hallucination, policy violations, and incomplete goal progression, rather than allowing strength on one dimension to compensate for weaknesses on others.
