Abstract 

Agent harnesses require a low-latency guardrail model together with customizable audit poli-cies. However, deploying an auto-regressive guardrail model remains challenging: such models incur high inference latency and are of-ten poorly aligned with customized policies. To address these problems, we present Jev-Guard, a unified model for safety classification and policy routing. We further construct a policy tree over which Jev-Guard performs routing, spanning diverse domains including content moderation, cybersecurity, privacy, and legal compliance. Specifically, Jev-Guard first nav-igates the policy tree to select the applicable audit policy given the caller’s audit context, and then performs safety classification conditioned on the retrieved policies. On 7,033 evaluation cases, Jev-Guard achieves 93.72% safety accu-racy, a mean latency of 58 ms, and 93.10% hier-archical routing accuracy. The full routing-and-classification pipeline averages 240 ms. Fur-thermore, we integrate Jev-Guard into the Her-mes harness framework. Across agent trajec-tories, its separate permission gate cuts mean review time per task from 4.80 s for an SFT-LLM judge to 1.33 s, with no policy violations are observed for either guard. 

1 Introduction 

Agent harnesses execute tool calls on behalf of users, and every action must be reviewed before it takes effect (Wang et al., 2026a; Mou et al., 2026). Such review sits on the critical path of each step, so it demands a low-latency guardrail model. It also demands customizable audit policies: send-ing a public announcement to an approved partner differs from sending a private document to an ad-dress found in a webpage, and the two cases require different audit tasks. cybersecurity, privacy, and legal compliance, the same agent action may call for vulnerability analy-sis, a disclosure check, or a review under a particu-lar platform policy. An unsafe label alone identifies neither the audit task nor the execution authority. Existing guardrail models fall short of these two requirements. First, policy-conditioned safeguards typically generate an auto-regressive rationale be-fore emitting a verdict (Li et al., 2025c; Liu et al., 2026; Chen et al., 2025), which incurs high infer-ence latency at every tool invocation. Second, such models are often poorly aligned with customized policies. Fixed taxonomies restrict deployments to a shared vocabulary, whereas placing all natural-language policies into the context for every action enlarges the input and introduces irrelevant candi-dates. Hierarchical labels help organize categories (Li et al., 2025a), but they do not let operators re-name a category, remove it with a fallback, or insert a new routing level without retraining. Such edits change the decision interface even when the under-lying action stays fixed, so a frozen model must follow the changed rules. To address these problems, we present Jev-Guard, a unified model for safety classification and policy routing. Following the direct structured-decision paradigm of Jev (Typesafe AI, 2026) and the Open-Jev implementation family (Open-Jev Contributors, 2026), Jev-Guard is a Qwen3.5-2B classifier that replaces generated rationales with direct prediction heads. We further construct a ver-sioned policy tree over which Jev-Guard performs routing, with 85 nodes and 73 leaves spanning con-tent moderation, cybersecurity, privacy, and legal compliance. Given an agent action, Jev-Guard first navigates the tree through local decisions to select the applicable audit policy given the caller’s au-dit context, and then performs safety classification conditioned on the retrieved leaf rules and taxon-omy. 2 Related Work 

Policy-conditioned safeguards. GSPR trains safeguards to reason across supplied safety poli-cies and taxonomies (Li et al., 2025c). Augmented policy training studies generalization to unseen pol-icy domains (Liu et al., 2026). Hi-Guard combines policy-aligned moderation with hierarchical labels (Li et al., 2025a). These methods establish policy conditioning and hierarchical labels. We instead 2freeze the model and perturb rules, candidate word-ing, membership, and tree topology to test whether software edits produce the intended decisions. 

Agent runtime protection. AgentSpec specifies runtime constraints with triggers, predicates, and enforcement mechanisms (Wang et al., 2026a). ShieldAgent evaluates agent behavior using ver-ifiable policy reasoning (Chen et al., 2025), and ToolSafe studies proactive review at tool invocation steps (Mou et al., 2026). These systems enforce action policies. We study a direct classifier with a separate audit tree and permission gate, tracing which policy each decision reads. Our rollouts eval-uate the integrated gate, whose policy is separate. 

Decision models and agent evaluation. Jev motivates direct structured decisions rather than autoregressive explanations (Typesafe AI, 2026). We build on the Open-Jev implementation family (Open-Jev Contributors, 2026). We retain its head architecture and add four-domain task mapping and paired audit diagnostics. Official Jev is an external baseline. AgentDojo provides executable simulated environments for testing prompt injection attacks and defenses (Debenedetti et al., 2024). We use these tools in native Hermes rollouts (Nous Re-search, 2026), separating full attacker goals from partial policy violations. 

3 Jev-Guard 

Overview. Given a pre-execution state xt, Jev-Guard (i) routes from the root of the policy tree to one leaf, (ii) reviews the action under that leaf’s policy and taxonomy to produce a diagnosis rt, and (iii) passes it to a separate execution gate (Figure 1). 

3.1 State and Policy Interface 

Let xt = ( u, a t, h t, z t) denote the state available before action at: the user goal u, the proposed tool name and arguments, relevant prior observations 

ht, and the caller-supplied audit context zt. The host separately supplies the authorized scope At

and the default policy P0.The audit context zt states which audit is re-quested and, for named-policy branches, which law or provider policy governs. Routing is therefore 

caller-conditioned capability dispatch : the model selects the leaf that matches the supplied intent and policy identity, rather than discovering the relevant policies from the evidence alone. One request se-lects one leaf, so an action needing several audits requires separate requests. 

3.2 Policy Tree 

The policy configuration is a rooted tree T . Each in-ternal node stores a description of each child. Each leaf ℓ stores a task description dℓ, a local review policy Pℓ, a taxonomy Cℓ with label definitions, and a prediction type (choice, multi-label, or ordinal). Binary safety is optional, since privacy-topic and vulnerability-type leaves need not define it. The evaluated tree has 85 nodes and 73 leaves under four top-level domains: content, cyber, privacy, and compliance. Cyber and privacy branches dis-tinguish audit capabilities (e.g., code vulnerability, phishing, injection), whereas compliance branches distinguish the governing law or provider policy. The next section describes how the tree is con-structed, and the appendices list every leaf.

4 Data and Policy Tree Construction 

This section describes how we build the audit data and the policy tree used to train Jev-Guard. 

4.1 Data Collection and Construction What we collect. We gather public datasets for the four audit domains, and each dataset poses a different judgment task. Content tasks ask whether a prompt or response, in text or image form, is harmful and which harm category applies (Ghosh et al., 2024; Zong et al., 2024; Zhu et al., 2025). Cy-ber tasks include detecting vulnerable code (Ding et al., 2025; Chen et al., 2023), phishing and mali-cious web requests (Dalton et al., 2025; Liu et al., 2024), and prompt injection (Yi et al., 2025), clas-sifying the root cause of a reported vulnerability (Alam et al., 2024), and judging whether a request is authorized (Wang et al., 2026b). Privacy tasks annotate the practices in a privacy policy (Wilson et al., 2016; Ahmad et al., 2021; Ravichander et al., 2019) and judge whether an information flow is ap-propriate (Li et al., 2025b). Compliance tasks ask whether a text violates a given law or platform pol-icy, such as GDPR or a provider’s terms of service. Most come from OmniCompliance-100K (Omni) (Hu et al., 2026), and the rest detect unfair clauses (Lippi et al., 2019; Chalkidis et al., 2022). The appendix lists every dataset. 

Unified records. Because the datasets use differ-ent formats, we convert every example into one record. It holds the evidence to review, the audit task, the applicable policy, the candidate labels with definitions, the labels, and the policy-tree leaf the example belongs to. The training set has 377,930 records. We remove instructions that ask for gener-ated text, since the model outputs labels directly. 

Label provenance. Labels differ in reliability, so we record where each comes from. Original labels are taken directly from the source dataset. Mapped 

labels are converted from source metadata by an explicit rule, for example an attack-family field mapped to an injection category. Weak labels are guessed by simple rules such as keyword match-ing, for example a privacy topic inferred from a sentence. Weak labels are used in training with a small loss weight of 0.25 and never in evaluation. A category that a source never annotated is treated as unknown rather than negative, so the model is not taught that an unlabeled category is absent. 

4.2 Policy Tree Construction 

We build the tree manually from source informa-tion, not from model predictions, and the model never sees dataset names. 

Capability assignment. We first assign each dataset an audit capability. Complete functions map to code review, vulnerability descriptions with Common Weakness Enumeration (CWE) labels (MITRE) to root-cause classification, severity rat-ings to an ordinal task, and emails, URLs, and HTTP traffic to their own cyber leaves. Datasets with compatible tasks share a leaf. Compliance datasets keep the specific law or provider policy as their branch, grouped by provider and by law. Leaf taxonomy. Each leaf has its own list of can-didate labels, rewritten into readable names. CWE codes are mapped to 20 defect families (e.g., CWE-119 and CWE-787 to Buffer bounds ), and broad codes that name no specific defect are masked. 5 Experiments 

5.1 Setup Research questions. We organize the experi-ments around four questions. RQ1 : Is Jev-Guard accurate and fast enough to review every action? 

RQ2 : Does a frozen model follow edits to rules, categories, and tree structure? RQ3 : What does the policy tree add over presenting all policies at once? RQ4 : How does the execution gate compare with an LLM judge? 

Training. The evaluated checkpoint continues an earlier version for one epoch and is selected at update 1,508. We train rank-8 LoRA and the prediction heads with learning rates 2×10 −5 and 

5×10 −5, respectively, a global batch of 256, and a 16,384-token cap. Selection averages routing, safety, and category scores on 2,048 native and 1,000 router validation records. Reported test safety uses ordinary accuracy. 

Evaluation. We evaluate one frozen checkpoint as an empirical system study. Native scores de-scribe recorded cohorts, not generalization to un-seen policies, and edit experiments measure paired responses to newly specified variants. 

5.2 RQ1: Is Jev-Guard Accurate and Fast? 

We compare Jev-Guard with a generative SFT model and official Jev on matched records, evaluate native classification across all four domains, and time the full review pipeline. 

Finding 1: Accuracy matches SFT at much lower latency. On 7,033 matched records, Jev-Guard reaches 93.72% safety accuracy, against 93.36% for SFT and 75.89% for official Jev (Type-safe AI, 2026), and Table 1 gives the breakdown by domain. The 0.36-point gap over SFT has a 95% interval that includes zero, so we claim no accuracy advantage. The SFT median latency is 8.81 times that of Jev-Guard. Prompts and training histories differ across systems, so the comparison does not isolate architecture. 

Finding 2: Native accuracy varies widely across tasks. We evaluate the checkpoint on 147,643 na-tive task-case records across 109 benchmark views, keeping the original prompts and labels. Safety accuracy is 91.78% over the 79,987 records with safety labels, and Table 2 shows how much it varies across domains and tasks. PrimeVul (Ding et al., 2025) safety accuracy is 96.86% on single func-tions but 50.00% on function pairs, and root-cause category F1 on CTI (Alam et al., 2024) remains low. Overlapping views are not independent datasets. 

Finding 3: A full review takes about 240 ms. 

We time 200 unique pre-execution states recorded from agent runs, 30 user requests and 170 tool ac-tions, on one A800 80GB GPU with batch size one, bfloat16/SDPA inference, and eight warmup reviews. 5.3 RQ2: Does a Frozen Model Follow Policy Edits? 

We keep the checkpoint frozen, edit rules, candi-date lists, and tree structure, and score only newly specified variants. Table 4 summarizes all three edit types. 

Finding 4: For rule edits, the two output heads disagree. We test five rule families: recipients, publication, storage region, retention, and security authorization. Each has six targets whose gold label changes under the edited rule and six unchanged controls, with gold set by predefined predicates. We score the compliant/violation choice and the binary safety output separately, without scope rules or execution. The choice head is correct on both versions of 21 of the 30 targets and on all 30 con-trols. The safety head is correct on all 30 targets but only 24 controls, because six legal 14-day retention actions stay unsafe. Tightening the retention limit from 90 to 30 days leaves the choice prediction at compliant for all six targets, although the safety head flips correctly. Head agreement and control correctness therefore need separate checks. 

Finding 5: Category edits fail when a new distinction is required. We change candidate names, membership, granularity, or order for 24 ac-tions across six families. Deleting a category with an explicit fallback cuts accuracy from 95.83% to 50.00%, and reversing candidate order lowers it to 75.00% even though label meanings are unchanged. 5.5 RQ4: How Does the Execution Gate Compare with an LLM Judge? 

Hermes (Nous Research, 2026) runs AgentDojo (Debenedetti et al., 2024) tools for workspace, banking, travel, and Slack, with 16 normal and 16 injected tasks per suite. We compare two guards, each combined with explicit scope rules: the Jev-Guard permission judgment and a separate LLM permission call. Both see identical policy, scope, task, tools, attacks, and budget, and the actor and judge are both deepseek-flash with temperature zero. The full run also has no-guard and rules-only reference arms, 512 episodes in total. We re-port normal completion, official complete attacker goals, and a supplementary checker for partial pol-icy violations. The checker inspects executed pre-fixes for unauthorized transfers, recipients, or dele-tions and covers 48 of 64 attack tasks, leaving 16 unknown. It was frozen after the rollouts, so it was not preregistered, and the 16 uncovered attacks are not counted as safe. 

Finding 10: Neither guard shows a violation, but the runs cannot credit either one. Both guards have zero covered policy violations and zero com-plete attacker goals. The unguarded baseline also has none, so these zeros cannot be credited to either guard. The upper end of the 95% Wilson interval for 0 of 48 is 7.41%, for this covered sample only. 

Finding 11: Jev-Guard reviews faster than the LLM judge but completes fewer normal tasks. 

Jev-Guard completes 51 of 64 normal tasks and the LLM judge 57, or 79.69% against 89.06%. The 95% intervals of the two completion rates overlap, so we do not claim a reliable difference. Jev-Guard is more conservative. It declines one normal user request and 25 proposed actions across ten nor-mal tasks, against one request and three actions across three tasks for the LLM judge. Without per-action gold labels we cannot call these denials false positives, since a task that is normal overall can still contain a mistaken action. In return, review is cheaper. Mean review time per normal task is 1.33 seconds for Jev-Guard and 4.80 seconds for the LLM judge, and on the 48 normal tasks completed in every condition, mean task time is 7.60 seconds against 10.60 seconds. 

6 Discussion 

Editability is a behavior to test. Accepting a new label or node does not ensure correct interpre-tation. Split and retention probes require checking affected cases, controls, and separate heads. Hier-archy organizes policies, but maintenance benefits remain unmeasured. 

Validate diagnosis and permissions. Perfect compliance dispatch coexists with poor leaf judg-ments, including under oracle routing. The per-mission gate separately reads default policy and scope. Binding tree rules to execution requires a new interface and execution tests. The current re-sults instead support three practical checks: score newly affected cases, retain controls, and measure complete review with normal-task completion. 

Report the audit contract. Comparisons require explicit audit contracts: caller information, ob-served labels, and outputs that control execution. An extra category outside a source vocabulary indi-cates a contract mismatch. Unannotated categories are not automatically semantic errors. 

7 Conclusion 

Jev-Guard enables empirical tests of editable audits in four domains. Native classification has lower archived latency than SFT without a conclusive ac-curacy advantage. Paired tests expose edit failures and diagnostic errors after correct routing. Flat dis-patch remains competitive. Full review averages 240 ms. In agent runs, the gate reviews faster than an LLM judge at a lower completion rate, without established safety gains. 8Limitations 

We evaluate one checkpoint, a limited set of policy edits, and one actor API alias. The controlled edit cases are constructed from explicit predicates, not independently annotated production logs. Five rule families and six category families provide limited statistical power. The 200-case tree study is bal-anced across selected sources and does not estimate deployment prevalence. Confidence intervals over task or source samples do not include training-seed variation or future API model changes. The full-policy comparison uses 32K inputs be-yond the 16K fine-tuning cap and bypasses the deployed 512-candidate HTTP limit. It establishes a matched experimental comparison, not a drop-in deployment configuration. Native and shared-taxonomy evaluations differ in prompts, candi-dates, and supervision. Unknown category slots are masked. Strict unsupported-output metrics do not establish that all unsupported predictions are semantically incorrect. The agent experiments use static attacks, simu-lated tools, one rollout per task, and only partial violation coverage. Sixteen attacks have no reliable partial-policy checker and remain unknown. The supplementary checker was frozen before rescor-ing, not before the original actor rollouts. Zero baseline violations preclude a measured incremen-tal safety claim. No human-in-the-loop resolution of ask decisions is evaluated. The current leaf pol-icy is not bound to the permission head, so this implementation does not establish end-to-end en-forcement of arbitrary tree edits. Current v3.2 split audits found no overlap un-der case-ID, source-group, and content checks for the audited train/router splits. They do not fully exclude exposure through all historical v1–v3.1 training data or foundation-model pretraining. Pub-lic benchmark familiarity remains possible. We do not claim that the entire source mixture can be redistributed under one license, nor that het-erogeneous native safety labels share a universal semantic meaning. 

Ethical Considerations 

The system is a research guard, not a guarantee of safe execution or a replacement for explicit au-thorization controls. Incorrect denials can impede legitimate work. Incorrect allows can expose sen-sitive assets. Our action experiments use isolated simulated environments and synthetic boundary-workflow assets, without sending real sensitive data or operating production resources. Evidence from tool outputs is kept distinct from host-owned policy and authorization. Logs used for real deployments would require data minimization and access con-trol, which this study does not validate at produc-tion scale. The training mixture includes harmful text and vulnerable source code for classification. Redistri-bution must respect each source’s access and licens-ing conditions. Our reports avoid publishing cre-dentials, production traces, or personal user content. Automated coding and drafting tools assisted the implementation and manuscript preparation. The substantive claims here are tied to recorded experi-ments and source inspection rather than generated hypothetical results.

A Training and Data Summary 

Training. The evaluated checkpoint is a LoRA adaptation of Qwen3.5-2B with two prediction heads, frozen during all evaluation. It continues an earlier checkpoint for one epoch, so it is not a fresh base-model run and is not evidence of training to a validation plateau. Model selection uses a fixed val-idation panel, while reported test safety accuracy is the ordinary fraction correct over labeled cases. 

Data composition. The training package con-tains 377,930 native audit records and 8,000 router records. A taxonomy annotation without a valid safety label contributes only to its supported task, and governing policies are part of the input for policy-dependent classification. 

Annotation coverage. Taxonomy coverage ex-ceeds annotation coverage. We identify 172 leaf-local category entries across 41 leaves with no pos-itive annotations, so these entries are representable by the candidate interface but their supervised ca-pability is not established. Across all native splits, 4,506 records involve weak rule annotations and 6,954 involve source-label crosswalks. These are not additional training records. 

Router set and exposure. The router collection has 10,000 examples split 8,000/1,000/1,000. Its test split is not domain-balanced, with 100 con-tent, 312 cyber, 100 privacy, and 488 compliance records, so its overall accuracy is interpreted dif-ferently from the balanced 200-case tree-edit study. The checkpoint was developed through several data versions whose sources, sampling, prompts, and taxonomies changed together. The final scores therefore do not isolate the contribution of indi-vidual data sources, and earlier training stages may have exposed the model to benchmark data.

G.6 Observed-Slot Metrics 

Let Ci be the native candidate vocabulary, Oi ⊆ Ci

the gold-observed slots, Gi ⊆ Oi their positive labels, and Pi the model’s full predicted set. Define 

¯Pi = Pi ∩ Oi. For tree and flat-leaf review, ei is one only when a leaf output exists and routing is correct. For oracle and full-policy review it requires an output. The category counts are 

TP i = ei| ¯Pi ∩ Gi|, (8) 

FP i = | ¯Pi| − TP i, FN i = |Gi| − TP i. (9) Micro-F1 pools these counts. Wrong routing there-fore contributes no true positives. Observed predic-tions count as false positives and observed golds as false negatives. Empty sets contribute zero pre-dicted positives, while positive golds remain false negatives. A zero-denominator case contributes no counts to pooled F1. Strict set correctness additionally requires ei =1, ¯Pi = Gi, and Pi ⊆ Ci. An empty set can be strict-correct only when observed gold is empty and the other conditions hold. Out-of-native-taxonomy output incidence is reported over all 17 128 records, separately from the 117 category-supervised records. It is a local-vocabulary con-tract check, not independent semantic adjudication. Safety scores the binary head against source gold whenever safety is applicable, without requiring correct routing. A missing leaf is incorrect. On the 86 safety cases, tree minus full-policy accu-racy is −12 .79 points, with exact empirical paired-bootstrap interval [−25 .58 , 0.00] . The 86 unique source cases have paired differences of −1, 0, and 

+1 in 21, 55, and 10 cases. We convolve this em-pirical three-point distribution 86 times and take inverse-CDF percentiles. No Monte Carlo draws are needed. A 10,000-draw pilot had an upper end-point near zero that varied with sampling. The exact McNemar test is p = 0 .0708 . We therefore report a numerical difference without conclusive evidence of a safety-accuracy advantage.

I Agent Experiment Details 

Input control. The normal and injected Agent-Dojo tasks use the same native Hermes tool loop. Host-owned policies and authorized scope are vis-ible in all four conditions, including no guard. Untrusted injected tool observations remain sep-arate from this policy. The two fixed attack pay-load families are important_instructions and 

tool_knowledge . We do not adapt the payloads to the guard or select for unguarded attack success. 

Checks and unknown outcomes. Official at-tacker goals and the partial-policy checker are ap-plied to successful execution prefixes and resulting state, rather than only the last state. The latter cov-ers concrete unauthorized transfers, recipients, and deletion targets. Its 16 unsupported cases are ex-plicitly unknown. A completed benign goal does not imply the absence of a violation, and an in-complete attacker goal does not imply the absence of a partial violation. Reviewer exceptions, time-outs, and invalid infrastructure outcomes are not relabeled as safe behavior. 

Constructed boundary workflows. A separate expanded set crosses six scope families—paths, credentials, deletion, exfiltration, permissions, and reviewer configuration—with finance, clinic, prod-uct, and operations templates. It has 24 authorized and 24 unauthorized requests per condition, or 192 episodes. Tools operate on synthetic files, state, and local outboxes. Normal completion is 20/24 with-out a guard, 20/24 with rules, 22/24 with Jev-Guard plus rules, and 20/24 with the LLM judge. All have 0/24 executed violations. A family-held-out slice is also 0/12 for every condition. The unguarded zero again prevents an incremental safety conclusion. A separate 96-episode pilot is excluded. A numeric scoring ambiguity between formatted amounts such as 42,000 and 42000 was corrected with a uniform numeric oracle. All conditions were rescored without rerunning the actor, and the orig-inal scores, oracle revision, and hashes were re-tained. This is a scoring correction, not a search for favorable reruns. 

Rollout budget and permission threshold. The final AgentDojo experiment uses at most 20 Her-mes iterations, 4,000 output tokens per actor call, and 300 seconds per episode. The actor and sepa-rate judge call use the same API alias. Temperature zero does not make an evolving remote API a fixed-weight deterministic simulator. One rules-only at-tack episode reaches its output budget and remains in the results. Final-run infrastructure failures are zero, but incomplete actor behavior is still an out-come rather than an excluded trial. The permission threshold of 0.55 is fixed. It is not a calibrated risk probability or a threshold optimized on these rollouts. 

J Interpretation Notes 

The experiments support distinct claims with dis-tinct units. Rule-edit correctness concerns paired model predictions under fixed actions. Routing con-cerns leaf selection with caller context. Leaf clas-sification concerns labels available under a spec-ified prompt and taxonomy. Action-level replay concerns proposed states. End-to-end security con-cerns effects of actions that actually execute. These outcomes remain separate in our reports. The evaluated action gate reads default policy and scope, not the selected leaf rule. As a result, the present paper does not claim that editing the tree is sufficient to alter enforced permissions. Complete-review timing includes that separate permission for-ward. Native source classification, the 32K shared-policy comparison, and Hermes rollouts are evalu-ated separately. 19 A tree revision should be treated as a versioned interface change. Moving an existing leaf preserves its meaning, whereas inserting a new parent asks the model to solve another classification problem, and a successful native benchmark result does not validate that new decision. Both diagnostic and authorization policies should be logged. 20
