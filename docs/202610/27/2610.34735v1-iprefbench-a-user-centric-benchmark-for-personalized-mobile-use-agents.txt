# iPrefBench: A User-Centric Benchmark for Personalized Mobile Use Agents 

Yuting Ning 1,†, Ruijia Cheng 2, Sushobhan Ghosh 2, Peitong Duan 2, HungShi Lin 2, Abhishek Sundararajan 2,

Shreyash Pandey 2, Huan Sun 1, Jeffrey Nichols 2, Eldon Schoop 21The Ohio State University, 2Apple  

> †Work done during an internship at Apple.

An agent that truly knows and acts on behalf of its user has been a long-standing promise of AI assistants. Computer-use agents bring this promise within reach by capably executing fully specified tasks across apps. However, real-world user requests are often underspecified. To act correctly for the particular user, an agent must infer some missing information from the user’s activity history and ask for other information that only the user can provide, without making unsupported assumptions or burdening the user with unnecessary questions. We present iPrefBench, a benchmark for evaluating the 

infer and ask capabilities of personal mobile-use agents in an executable iOS environment with an interactive simulated user. Grounded in a coherent persona with 3,051 past activity events, iPrefBench comprises 130 underspecified user tasks across 26 apps. Each omitted user-dependent requirement is, by construction, either history-inferable or ask-only. iPrefBench evaluates personalized mobile agents on both whether agents complete tasks correctly for the user (i.e., per-sonalized task completion) and whether they seek user input when necessary (i.e., user-agent interaction). Evaluation of 

7 frontier agents reveals a substantial gap between execution and personalization. Agents achieve high action comple-tion scores (up to 91 .6%) but low full task success (up to 47 .7%) because personalization lags behind. They especially struggle with ask-only information, failing to request enough necessary information. Our findings highlight a challenge for personalized agents in knowing what to infer and when to ask. We hope that iPrefBench can serve as a valuable testbed for building agents that know their user and work with them.

# 1 Introduction 

It has been a long-standing goal in Artificial Intelligence and Human-Computer Interaction to develop agents that can understand and act on behalf of users (Maes and Kozierok, 1993; Lieberman, 1997; Horvitz, 1999). Recent computer-use agents (CUAs) have made rapid progress in completing digital tasks across apps and over long horizons (Xie et al., 2024; Yuan et al., 2026; Rawles et al., 2025; Ye et al., 2025). These agents often excel at fully specified tasks (e.g., “make a reservation at Harborline Seafood tomorrow at 7:30 PM for a party of four.”). However, realistic user queries rarely provide complete details, and are often underspecified (Völkel et al., 2021). For example, a user may say “book me my usual restaurant for tomorrow” instead of specifying the restaurant name, reservation time, and party size. Contending with such underspecified tasks requires personalization capabilities, in which an agent resolves missing information in two ways: infer from knowledge of the user (e.g., the user’s usual restaurant from past reservations and orders), and ask for details that the available history does not establish (e.g., the desired time and party size). An agent that silently makes unsupported assumptions can diverge from a user’s actual intent, while an agent that asks for details already inferable from the user’s history defeats the purpose of autonomy. A truly useful personal agent must reason not only about what information is missing, but also where it should come from. Yet this challenge is not fully captured by existing evaluations. Benchmarks with underspecified tasks usually supply only one resolution source: personalization benchmarks expose a user history but offer no one to ask (Lyu et al., 2026; Yang et al., 2025), while interactive benchmarks provide a simulated user but no user history that would make some questions unnecessary (Yao et al., 2024; Vijayvargiya et al., 2026). Some provide both (Chen et al., 2026b,c), but do not distinguish which missing details should be inferred and which require clarification. Therefore, they cannot measure whether the agent knows what to infer and when to ask. To bridge the gap, we present iPrefBench, a benchmark designed around the infer-and-ask capabilities of personalized mobile-use agents in an executable iOS environment. As shown in Figure 1, agents can know about the user through two sources: an activity history, provided as their only prior context, and a simulated user, reachable through an ask_user action, who answers clarification questions. Both are grounded in rich seeded data around one coherent persona in the environment. iPrefBench comprises 130 underspecified tasks, and each omitted detail is designed to be either inferable (i.e., grounded in specific evidence in activity history) or ask-only (i.e., held solely by the simulated user). To further assess whether agents can apply historical preferences appropriately in challenging real-world scenarios, we include tasks in which current instructions override past patterns, recent behavior indicates changing preferences, or preferred options are unavailable. iPrefBench assesses both whether agents complete tasks correctly for the user (i.e., personalized task com-pletion ) and whether they seek user input when necessary (i.e., user-agent interaction ). Personalized task completion is measured by task-specific rubrics, split into two types: action-completion criteria measure whether required operations were successfully executed (e.g., a restaurant reservation was made), while per-sonalization criteria measure whether each user-dependent decision matches the intended values (e.g., the restaurant, time, and party size). However, correct outcomes alone do not establish user satisfaction: an agent may succeed by interrogating the user about every detail, or luckily guessing the ask-only information correctly. Therefore, inspired by Grice’s maxims (Grice et al., 1975), we also evaluate user-agent interaction through recall and precision on ask-only information: recall measures whether the agent elicits all required ask-only information, while precision measures whether its requests obtain new ask-only information rather than ask for inferable or irrelevant details or repeat earlier requests. We evaluate seven frontier agents on iPrefBench. The results reveal a substantial gap between executing a task successfully and personalizing it for a particular user. Although Claude Opus 5, the best-performing agent evaluated, achieves a 91 .6% action-completion score, its task success rate is only 47 .7% because person-alization lags behind. Agents struggle particularly with ask-only information, and our interaction evaluation 2reveals a corresponding shortfall. By default, agents ask far too little: the recall on ask-only information is low across the board, with the highest at only 44 .3%. Yet what they do ask is not reliably necessary either, with precision between 60 % and 77 %. Explicitly adding a clarification phase can substantially increase the number of questions and raise the recall and task success rate, but lower precision in turn, exposing a tradeoff between silent guessing and excessive user burden. The challenge is therefore not simply to ask more, but to determine when asking is necessary. We hope iPrefBench can serve as a valuable testbed for building agents that know their user and work with them effectively. 

# 2 Related Work 

Computer-Use Agent Benchmarks. Computer-use agents have advanced rapidly (Zheng et al., 2024; Hong et al., 2024; Qin et al., 2025; Wang et al., 2026b), supported by executable benchmarks across desk-top (Xie et al., 2024; Yuan et al., 2026), mobile (Rawles et al., 2025), and web environments (Zhou et al., 2024; Koh et al., 2024; Xue et al., 2025; He et al., 2024). These benchmarks typically use fully specified tasks without prior user knowledge. MobileWorld (Kong et al., 2026) introduces underspecified tasks and an 

ask_user action, but without user history, every missing detail must be asked. 

Personalized Agent Benchmarks. A growing line of work evaluates preference inference from user his-tories for personalized tasks, but does not support interactive clarification (Cai et al., 2025; Yang et al., 2025; Wang et al., 2026a; Kim et al., 2026; Lyu et al., 2026). iOSWorld (Jang et al., 2026), on which our environment builds, seeds an iOS simulator with a coherent persona but neither exposes user history as prior context nor supports user interaction. VitaBench 2.0 (Chen et al., 2026c) and KnowU-Bench (Chen et al., 2026b) incorporate user histories and, in some cases, hidden information accessible through simulated users, but do not explicitly distinguish whether each missing detail is recoverable from the history or known only to the user, and thus cannot evaluate the efficiency of user-agent interaction, i.e., whether agents only ask necessary questions. 

Interactive and Clarification Benchmarks. Interactive benchmarks (Yao et al., 2024; Qian et al., 2024, 2025; Barres et al., 2025; Vijayvargiya et al., 2026) study clarification with simulated users whom agents have no prior knowledge of, and mainly measure task outcomes or how much hidden information agents elicit. Ask-before-Plan (Zhang et al., 2024) penalizes missed and unnecessary questions, while AppWorld-UL (Chen et al., 2026a) evaluates information elicitation under underspecification, infeasibility, and confirmation-seeking scenarios. However, all of these settings lack user histories against which the necessity of clarification questions can be assessed. In contrast, iPrefBench evaluates agents on underspecified tasks, whose missing information can either be inferred from grounded user history or only be obtained by asking the user, and explicitly distinguishes the resolution source, enabling evaluation of personalized task completion and necessity-aware user-agent interaction. We provide a detailed comparison in Table A.1. 

# 3 iPrefBench 

3.1 Benchmark Overview 

iPrefBench evaluates whether mobile-use agents can complete underspecified tasks for a user, by inferring missing information from user history and seeking clarification when necessary. For each task t ∈ T , let Ut denote the user-dependent details left unresolved by the instruction. Each 

u ∈ Ut has an intended value and exactly one resolution source: (1) Inferable information (u ∈ U infer  

> t

): Information whose intended value can be recovered from consistent evidence in the user activity history H,such as a dominant pattern across past events or a stable user fact. (2) Ask-only information (u ∈ U ask  

> t

): Information unavailable in H that must be obtained by asking the user, such as the context of the current occasion. This split mirrors what a personal assistant can know about its user: stable preferences and habits leave traces in past activity, whereas the specifics of the current situation do not. This distinction allows us to 3evaluate both whether agents infer user-specific details correctly from the history, and whether they seek clarification only when needed, without unnecessary questions. 

3.2 Environment 

Executable iOS Environment. iPrefBench builds on the executable iOS simulator from iOSWorld (Jang et al., 2026), containing 26 mock apps populated with interconnected data (e.g., past restaurant reservations, financial transactions, messages, workouts and ticket orders) for a coherent user persona, Jordan Avery . The agent operates through standard mobile GUI actions (e.g., tap , type , and swipe ). We extend the action space with an ask_user action, which allows the agent to send a natural language message to the simulated user and receive a user response. Full details of the action space are provided in Appendix B.2. 

User Activity History. We compose seeded application data as a chronological user activity history 

H (Appendix C.1), representing a timeline of what the user did on their personal phone. Each event is converted from the underlying application metadata into natural-language descriptions. The activity history 

H is provided to the agent as the only prior knowledge and context of the user. All inferable information (e.g., recurring preferences, habits and user facts) is designed to be recoverable from evidence in H.

User Profile and User Simulator. To ground simulated user responses and facilitate evaluation, we derive a structured user profile P from the seeded application data (Appendix C.2), consolidating the persona’s preferences, habits, and personal information into 13 dimensions (e.g., identity, social relationships, finances, dining and travel preferences, and fitness habits). P is hidden from the agent and serves as a ground-truth reference for user simulation and evaluation. We simulate the interactive user with an LLM grounded in 

P and, when applicable, task-specific hidden context. When the agent issues an ask_user action, the user simulator answers the question in character. To faithfully evaluate the agent’s own ability to recognize what is missing, we instruct the simulator to answer only what is asked, without proactively volunteering additional information. 

3.3 Tasks 

Task Design. As described in §3.1, each task intentionally leaves user-dependent details unspecified, with their intended values and resolution sources explicitly annotated. For example, “book me my usual restaurant for tomorrow” leaves three pieces of information underspecified: the restaurant, party size, and time. The user’s reservation history in H can resolve the usual restaurant, so asking the user about it is redundant. In contrast, the reservation time and party size, which describe the current occasion and cannot be supported by any history, must be obtained by asking rather than assumed. A single task may contain multiple inferable and ask-only requirements, and often requires agents to integrate supporting evidence across multiple historical events or transfer preferences inferred in one app to decisions in another. Success therefore requires reasoning about the user rather than simply retrieving a single past event. Real-world personalization can be even more complex, as things can diverge from past trends and historical behavior cannot be treated as unconditional specification of future intent. Therefore, we introduce three perturbation types: (1) Instruction perturbation : The current user instruction explicitly contradicts the dominant historical pattern. For example, a user who typically selects an inexpensive tier for rideshare may explicitly ask for a premium ride for a special trip. The agent must prioritize the current instruction over an inferred historical preference. (2) Preference perturbation : Recent behavior in H suggests that the user’s preference has shifted over time and departed from the long-run mode. For example, the user selected aisle seats consistently in recent months, while most historical flights were window seats. A personalized agent should therefore identify the evolving preference trend, rather than simply selecting the most frequent historical value. (3) Environment perturbation : The preferred option becomes unavailable in the current environment. The agent should respond to the situation by recognizing the unavailability, surfacing it to the user, and acting according to the user’s preference for alternatives or stopping if no substitution is acceptable. 

Task Authoring and Quality Assurance. We use a three-stage task authoring and validation pipeline to ensure realistic underspecification, task feasibility, grounded resolution for each omitted requirement, and verifiable outcomes. First, coding agents with task-authoring skills generate candidate personalized tasks using the source code of the apps, user activity history and profile, and fully specified iOSWorld tasks as 4references. Second, human task-refinement experts review and revise each candidate task. Specifically, for each omitted detail, experts verify its resolution source. An inferable detail must be supported by a dominant pattern or explicit fact in H, and where the evidence is weak or mixed, we revise the seeded data so that H can support a clear preference sufficiently. An ask-only detail must not be recoverable from H, and its intended value is chosen to differ from the app’s pre-filled default when possible, so that silently accepting a default or guessing is unlikely to succeed by chance. At this stage, experts also remove duplicate tasks and diversify the candidate tasks to cover as many user preferences and apps as possible. Finally, experienced validation experts execute refined tasks in the simulator to verify environmental feasibility and rubric correctness, and correct remaining issues accordingly. Every task in the final iPrefBench therefore undergoes two rounds of human review and revision. More details are provided in Appendix D.1. 

3.4 Evaluation 

A personalized agent should complete user requests successfully with appropriate personalization, asking the user for additional information only when necessary. There are multiple failure modes: it may execute the correct operation while making wrong user-dependent choices (e.g., purchasing a game controller as requested, but not the model compatible with the user’s console), or eventually reach the correct outcome by repeatedly asking the user for every detail. We therefore evaluate two aspects of agent behavior: (1) Personalized Task Completion, for whether the agent completes the required operations and whether it personalizes them for the user correctly; and (2) User-Agent Interaction, for whether it involves the user only when necessary. More details are provided in Appendix E. 

Personalized Task Completion. Each task is accompanied by a task-specific rubric containing two types of criteria. Each action-completion criterion evaluates an operation required by the instruction, indepen-dent of user-specific choices. For instance, a criterion requires that the agent successfully creates a restaurant reservation, regardless of the restaurant, time, or party size. Each personalization criterion corresponds to a user-dependent decision involved in the task, and is additionally labeled with its resolution source (i.e., inferable or ask-only). For example, correctly reserving the user’s usual restaurant satisfies an inferable per-sonalization criterion, and reserving at the intended time and party size satisfies the ask-only personalization criteria. An LLM judge (Zheng et al., 2023) evaluates each criterion as pass or fail using the execution trajectory (including screenshots, actions, and the final answer), user profile, task-specific hidden context, and rubric. Action-completion and personalization scores are computed as the fractions of satisfied criteria in their corresponding category, macro-averaged over tasks. A task counts as a success only if all of its criteria are satisfied. 

User-Agent Interaction. Following the cooperative principle in conversation that a contribution should be as informative as required, and no more (Grice et al., 1975), we evaluate whether agents request all ask-only information while avoiding unnecessary questions. We first use an LLM judge to decompose ask_-user messages from the agent into a multiset of individual information requests Qt. Multiple indepen-dent requests within one message are treated separately, and repeated requests are counted as separate occurrences. # 4 Experiments 

4.1 Experimental Setup 

We evaluate seven frontier models under the same mobile-use agent harness on iPrefBench: Claude Opus 5 (Anthropic, 2026a), Claude Sonnet 5 (Anthropic, 2026b), Gemini 3.1 Pro (Google, 2026a), Gemini 3.7 Flash (Google, 2026b), Kimi K3 (Kimi Team et al., 2026), Qwen3.8-27B (Qwen Team, 2026b), and Qwen3.8-Flash-Next (Qwen Team, 2026a). We also attempted to evaluate specialized GUI agents, but their limited context capacity or frequent invalid actions under our setting prevented meaningful personalization compar-isons (Appendix F.1). Each episode runs on a freshly seeded iOS simulator, with task-specific perturbations applied when applicable. Agents receive the full user activity log as context in all experiments except the study on user history exposure, to avoid confounding preference inference with retrieval or navigation ability. At each step, the agent observes the current screenshot and acts through the standard mobile-use action space including ask_user (Appendix B.2). Episodes end when the agent issues a stop action or reaches the maximum 50 -step budget. We use Claude Sonnet 5 for both the user simulator and LLM judges (validated in §4.5). Following §3.4, we report full task Success Rate (SR) , Action Completion and Personalization scores, and interaction Recall and Precision . Further details of the experimental setup are in Appendix F. 

4.2 Main Results 

Table 1 shows the performance of evaluated agents on iPrefBench, with the following observations: 

Strong execution, weak personalization. Across all agents, action execution is substantially stronger than personalization. While agents achieve relatively high action-completion scores ( 77 .5% – 91 .6%), the full task success drops to 26 .2%– 47 .7% because personalization lags behind. For example, Claude Opus 5, the best-performing agent we evaluate, completes 91 .6% of required actions but only 69 .4% of user-dependent decisions and therefore succeeds on only 47 .7% of tasks. These gaps show that successfully executing required operations does not necessarily lead to user satisfaction. Frontier agents that can excel at short- to medium-horizon mobile navigation still fail to resolve user-dependent decisions for a specific user. 

Ask-only information poses a particular challenge: agents struggle to decide when to ask. 

Splitting personalization by resolution source, performance on ask-only information is consistently lower than on inferable information across the board, by up to 46 points for Gemini 3.7 Flash. This suggests that recognizing and resolving information that requires user input during execution remains a major bottleneck for current agents. The interaction metrics locate the cause in how agents involve the user. Although tasks contain 0.89 ask-only requirements on average, agents issue only 0.08 to 0.35 ask_user calls per task, eliciting at most 44 .3% of the information they could not know (i.e., Recall). 4.3 Error Analysis 

To better understand where personalization fails, we manually label failed trajectories from Claude Sonnet 5 and Qwen3.8-27B. We categorize personalization errors along two dimensions: where the missing information must come from (user history or the user) and whether the agent recognized what information was needed. The categorization yields four error types in Figure 3. For ask-only information, agents may recognize that a value is unspecified but nevertheless commit to one with their own guess without consulting the user (i.e., Silent Guess , Ex. F.3). Examining Qwen3.8-27B’s reasoning, we find that it often raises “should I ask?” before talking itself into a guess or over-reasoning from past behavior. In other cases, the missing requirements are never recognized as an open decision at all (Silent Default , Ex. F.1). For example, an agent asked to book a round trip without specified travel dates never considers the dates to be user preferences at all, and the app’s pre-filled dates simply pass through unchanged. Inferable information exhibits an analogous distinction. Some preferences are never surfaced as decisions ( Missed Inference , Ex. F.2), while others are recognized but resolved incorrectly from history (Wrong Inference , Ex. F.4). These errors suggest two distinct challenges for current agents: (1) identifying which user-dependent choices remain unresolved, and (2) once a choice is recognized, determining whether its value should be inferred from history or elicited from the user, and resolving it correctly. Effect of Explicit Clarification. Motivated by the low interaction recall observed, we introduce a pre-execution clarification phase, in which the agent examines the user task and activity history, identifies ambiguities that cannot be resolved from history, and asks the user before executing the task. As shown in Table 2, the explicit clarification phase substantially improves personalization and interaction recall, eliciting more questions from the agent. However, interaction precision decreases at the same time, indicating that explicit clarification alleviates under-asking at the cost of more unnec-essary requests. Simply encouraging agents to seek clarification improves coverage of ask-only require-ments, but does not help agents distinguish neces-sary requests from unnecessary ones. 

Effect of User History Exposure. We further investigate how performance changes when differ-ent user history is exposed to the agent, ranging from no history to different retrieved subsets of task-relevant events, and the full unfiltered history. Task-relevant events are retrieved using the task instruction as query and text-embedding-3-small (OpenAI, 2024) 8as the embedder. As shown in Figure 4(a), inferable personalization rises sharply with a small set of relevant events (e.g., from 35 % to 63 % for Qwen3.8-27B with the top-50 events) and then plateaus, with the full history adding no further gain. Ask-only personalization, in contrast, barely moves. Figure 4(b) shows how history exposure instead changes user-agent interaction: with more history, agents ask fewer questions and interaction precision rises, as questions whose answers are already in the history are avoided. However, this does not necessarily indicate more appropriate interaction, as recall on ask-only information does not improve and even decreases (e.g., 33 .6 → 21 .2 for Qwen3.8-27B). More user history thus helps agents infer preferences and avoid unnecessary questions, but does not help them recognize what genuinely remains unresolved. 

4.5 Validation of User Simulator and LLM Judges 

We validate whether the user simulator faithfully answers agents’ questions and whether the LLM judges reliably produce assessments. 

User Simulator. We inspect all question–answer pairs produced when interacting with four representative agents, and 96 .6% of responses are grounded in the user profile or task-specific hidden context and answer exactly what was asked without volunteering additional information (Appendix C.4). 

LLM Judges. We first validate the LLM-based evaluation against human annotations on 100 sampled trajectories. Human annotators label each task-rubric criterion and each message issued by the agent. Our LLM judges agree with human labels on 95 .7% of rubric criteria ( κ = 0 .89 ), 97 .0% of task-level success (κ = 0 .94 ), and 95 .2% / 93 .9% of recall / precision judgments ( κ = 0 .90 / 0.82 ), and results are consistent with Gemini 3.7 Flash as an alternative judge (Appendix E.4). 

# 5 Conclusion 

In this work, we introduce iPrefBench, a user-centric benchmark for evaluating personalized agents in 130 

underspecified mobile-use tasks. We center on two core capabilities for personalized agents: inferring user preferences from the user’s activity history, and asking the user for clarification when necessary. For each underspecified task, the agent needs to determine not only which information is missing, but also where it should come from. By controlling the provenance of each omitted detail, iPrefBench enables evaluation of whether the agent can execute the required action (i.e., action completion) and complete the task correctly for the particular user (i.e., personalization), and whether it involves the user only when necessary (i.e., user-agent interaction). Our evaluation on seven frontier agents reveals a clear gap between action execution and personalization, especially when the user preferences can only be obtained by asking. Agents struggle most to recognize which information is genuinely unavailable and requires user input. Explicitly encouraging clarification increases the number of questions, but at the cost of over-asking. These findings suggest that we are still far from a truly personalized agent that can know what to infer and when to ask.

B.3 Per-Task Environment Control 

All tasks in iPrefBench share a single seeded environment and base activity history H. However, some tasks, particularly the perturbation tasks (§3.3), require the environment to differ from this shared seed. iPrefBench supports a small set of declarative per-task fields, which are applied at episode setup and reverted afterwards: 1. Data overrides patch the data served by an app for the current task, e.g., marking an item out of stock, clearing a restaurant’s availability, or extending an app’s in-app history. 2. Log events append synthetic activity events to the history H rendered for the current task only. 3. Profile overrides update entries of the user profile P used by the simulator and the judges, for tasks where the user’s present preference diverges from the historical pattern. For example, environment perturbations are implemented through data overrides, while preference perturba-tions require log events to change the agent-received user activity history, data overrides to make sure the on-screen app data is consistent, and profile overrides to reflect the updated preference for the user simulator and evaluators.

C.1 User Activity History 

We construct the user activity history H by converting the seeded application data into a unified, chronological sequence of natural-language events. Each event is represented by its timestamp followed by a natural-language description of the activity, which is converted from its metadata with an LLM (Claude Sonnet 5). Events are ordered chronologically, preserving temporal information that may be important for inferring recurring habits and evolving preferences. The following are two example events from the activity history: 

> [2025-08-01 16:55] in MyBank transferred $300.00 from Total Checking to Savings for monthly savings. [2026-02-19 02:06] in QuickChat received a message from Camille Hart in Brunch Crew: “Alright, making this group official. Monthly brunch is non-negotiable.”

By combining activities from different applications into a single history, H allows agents to infer user informa-tion beyond the context of any individual application. For example, payment transactions, restaurant orders, and restaurant ratings may jointly provide evidence of dining preferences, and messages and travel bookings may provide complementary information about travel plans. The activity history H is provided to the agent as its only prior knowledge of the user. In the default evaluation setting, the agent receives the full history at the beginning of each task. All inferable requirements in iPrefBench are grounded in evidence available in H. In contrast, ask-only requirements cannot be resolved from the history and must be obtained through the ask_user action. 

C.2 User Profile 

We derive a structured user profile P for the persona, grounded in the seeded application data and the corresponding user activity history H. The profile captures the user’s identity, relationships, preferences, habits, and other personal information across 13 dimensions, comprising 92 entries in total. Each entry records its value together with an evidence field that points to the supporting events in H, and every piece of information in P is designed to be recoverable from the history. Profile entries are first extracted with coding agents from the seeded data in H, and manually verified against their evidence in H during the task-authoring process. The structured profile serves as a hidden oracle for the user simulator and evaluation. It is not directly exposed to the agent under test. C.3 User Simulator 

We simulate the user with Claude Sonnet 5, prompted to role-play the persona (prompt in Appendix G). The simulator receives three sources of information: (1) the user profile P, with task-specific overrides applied when applicable; (2) the task-specific hidden context, i.e., the intended values of the task’s ask-only requirements (e.g., travel dates or party size); and (3) optional simulator context, which supplements additional situational details about the current request to keep the simulator’s replies coherent, without introducing additional evaluated requirements. To ensure faithful evaluation of the agent’s own ability to identify ambiguities, the simulator is instructed to answer only what the agent explicitly asks and never volunteer additional information. C.4 Human Validation of User Simulator 

We manually annotate all agent-user interactions produced by four representative agents in our experiments (Claude Sonnet 5, Gemini 3.7 Flash, Kimi K3, Qwen3.8-27B), yielding 89 question-answer pairs. For each question-answer pair, we check it in two aspects: • Grounding: Whether every fact in the reply is supported by the user profile, hidden task context, or the reply honestly declines something the profile genuinely does not cover. Fabricated (i.e., the reply states a concrete detail that appears nowhere in the profile or context), Contradicts (i.e., the reply gives 17 a value that conflicts with the profile or task context), Wrongly withheld (i.e., the reply claims not to know, or refuses, when the answer is in fact available) and Can’t tell (i.e., the profile is ambiguous or the question is too vague to judge) are all counted as failures. • Scope: Whether the reply answers everything asked and nothing more. Volunteered extra (i.e., the reply adds information the agent did not request) and Incomplete (i.e., the reply leaves part of the question unanswered) are all counted as failures. 

96 .6% of pairs (86 of 89) are valid on both axes. Both grounding failures occur in tasks without ask-only requirements, where the simulator has no direct answer and must improvise for agent-produced unnecessary questions. The single scope failure is a reservation task in which the agent asks three specific questions (date, party size, and restaurant) and the simulator answers all three but additionally supplies the time. 

# D Task Details 

D.1 Task Collection 

We construct iPrefBench through a three-stage pipeline consisting of automated candidate generation, human refinement, and execution-based validation. The pipeline produces 188 initial candidate tasks, from which 

130 tasks are retained in the final benchmark.  

> Stage 1: Automated Candidate Generation.

We develop two task-authoring skills for coding agents to generate candidate tasks. The first skill generates personalized mobile-use tasks using the application source code, seeded user data, user activity history, structured user profile, and fully specified tasks from iOSWorld as references. Candidate tasks are designed to resemble realistic user requests while leaving user-dependent information underspecified. The second skill focuses on generating tasks with three types of perturbations: instruction perturbations, preference perturbations, and environment perturbations. These tasks introduce cases in which an explicit instruction overrides historical behavior, recent evidence indicates a change in preference, or a preferred option becomes unavailable in the environment. Together, the two skills generate an initial pool of 188 candidate tasks.  

> Stage 2: Human Refinement.

Eight human reviewers refine the generated candidates. They review the nat-uralness of each user instruction, verify that the requested operations are feasible in the environment, and identify the user-dependent information omitted from the instruction. For each omitted requirement, reviewers determine its resolution source and ensure that it is well grounded. An inferable requirement must be supported by a dominant pattern or an explicit fact in H; when the supporting evidence is weak or mixed, reviewers revise the seeded data so that H supports a clear preference. An ask-only requirement must not be recoverable from H, and its intended value is specified in the task-specific hidden context. Whenever possible, this value is chosen to differ from the app’s pre-filled default, so that silently accepting the default or guessing is unlikely to succeed by chance. Reviewers revise ambiguous requirements and the corresponding task rubrics to ensure that each requirement has a well-defined ground-truth value and resolution source. For tasks whose conditions must diverge from the shared environment, such as perturbation tasks, reviewers also specify or revise the corresponding per-task overrides (Appendix B.3). The reviewers also remove duplicate tasks and refine the candidate pool to improve coverage of different applications, user preferences, and task scenarios.  

> Stage 3: Execution-Based Validation.

Two experienced human validators execute the refined tasks in the iOS simulator. This stage checks that the requested operations can be completed in the environment and that the task rubrics correctly specify the expected outcomes. Remaining issues in task instructions, environmental feasibility, and rubrics are corrected during validation. Following refinement and validation, we retain 130 tasks in the final benchmark. Each retained task undergoes both human refinement and execution-based validation. 18 D.2 Benchmark statistics

# E Rubric and Interaction Judge Details 

E.1 Task-specific Rubrics 

Each task is associated with a rubric containing two types of criteria: action-completion and personalization criteria. Action-completion criteria specify the operations required to complete the task, independently of the values selected for user-dependent parameters. Personalization criteria assess whether the agent makes the correct user-dependent decisions. Each personalization criterion is additionally annotated with its information reso-lution source: inferable , if the intended value can be recovered from the user activity history H, or ask-only ,if the value is unavailable in H and must be obtained through user interaction. 

E.2 Rubric-Based Completion Judge 

We use an LLM-based judge (with Claude Sonnet 5) to evaluate each rubric criterion independently. The judge receives the task instruction, the complete execution trajectory, and the agent’s final answer. The trajectory contains the executed actions and screenshots at each step, together with a screenshot of the final interface state. The judge additionally receives the ground-truth user profile and task-specific hidden context when applicable. The judge is also given the run time of the task, i.e., the simulator clock during execution, to resolve relative temporal expressions such as “tomorrow” or “next Saturday.” For each criterion, the judge returns a binary label and a supporting explanation. A criterion passes only when the trajectory provides clear evidence that it has been satisfied. We compute action-completion and personalization scores as the fractions of satisfied criteria within their respective categories. Both action-completion and personalization scores are macro-averaged across tasks. 19 0 5 10 15 20

E.3 Interaction Judge 

To evaluate whether agents ask appropriate clarification questions, we analyze the ask_user messages pro-duced during each task. The interaction judge receives all clarification questions issued during a task and the task’s annotated set of ask-only information. It identifies the individual pieces of information requested by the agent and semantically matches each piece to an ask-only requirement, if applicable. One information piece corresponds to a single decision or value the user must supply. A question requesting several independent values is decomposed into multiple pieces. Conversely, a question offering several candi-date answers for the same decision is counted as a single piece. Repeated requests are counted separately, even when they concern the same information. For each extracted piece, the judge returns a short description and either the matched ask-only requirement or a null match. Matching is semantic rather than based on exact wording. Requests for information that is inferable from history, irrelevant to the task, or otherwise not among the ask-only requirements receive null matches. Both interaction Recall and Precision are micro-aggregated: we sum the number of distinct ask-only require-ments elicited, the total number of ask-only requirements, and the total number of information requests across all tasks.  

> Format-Level Message Quality.

We also examine the format-level quality of each agent message along three criteria: specificity (i.e., it is clear which piece of information is being requested) (Vijayvargiya et al., 2026), 

answerability (i.e., the user can answer from knowledge they plausibly have, given the context the message supplies) (Vijayvargiya et al., 2026), and option provision (i.e., when the answer space is a small closed set, the message surfaces the candidates rather than leaving the user to enumerate them) (Peng et al., 2025). An LLM judge scores each criterion on every message issued by the agent whenever the criterion applies, and the overall quality score is the message-level average over the applicable criteria.

> Human Validation.

To assess the reliability of our LLM-based evaluation, we compare judge outputs against human annotations on 100 sampled agent trajectories. The trajectories are divided into two disjoint subsets of 50, each assigned to one human annotator. Each annotator evaluates the satisfaction of individual rubric criteria and the information requested in agent-user interactions. For personalized task completion, we measure agreement at both the rubric-criterion level and the task-success level. At the criterion level, agreement between human annotations and the LLM judge reaches 95.7%, with Cohen’s κ = 0 .89 . At the task level, agreement reaches 97.0%, with κ = 0 .94 .For interaction Recall, we compare the required-to-ask slots identified as elicited by the interaction judge with human annotations. Agreement reaches 95.2% ( κ = 0 .90 ). For interaction Precision, direct comparison at the level of individual extracted information pieces is not well-defined because the number and description of extracted pieces may differ between human annotators and the LLM judge. Instead, we compare the number of extra information requests identified by each, including requests for inferable or irrelevant information and redundant requests. Agreement on extra-request counts reaches 93.9% ( κ = 0 .82 ). Since these counts are ordinal, we additionally compute weighted Cohen’s κ, which accounts for the magnitude of disagreements between counts and reaches 0.91 .These results support the reliability of our LLM-based evaluation for both personalized task completion and information-request behavior.  

> Cross-Judge Validation.

We further re-evaluate all trajectories in Table 1 with Gemini 3.7 Flash as an alterna-tive judge. For personalized task completion, the two judges agree on 95 .9% of rubric criteria ( κ = 0 .91 ) and 

96 .4% of task-level success labels ( κ = 0 .92 ), with similar agreement on action-completion ( 95 .7%, κ = 0 .87 )and personalization criteria ( 95 .9%, κ = 0 .92 ). For interaction evaluation, they agree on 99 .1% of ask-only requirements for recall ( κ = 0 .98 ) and on 98 .6% of per-task extra-request counts for precision ( κ = 0 .90 ;weighted κ = 0 .87 ). Overall, the results remain consistent with an alternative judge, demonstrating the consistency and reliability of our LLM-as-a-Judge. 

# F Experiment Details 

F.1 Evaluated Agents 

We evaluate seven frontier agents in our experiments: Claude Opus 5 (Anthropic, 2026a), Claude Sonnet 5 (Anthropic, 2026b), Gemini 3.1 Pro (Google, 2026a), Gemini 3.7 Flash (Google, 2026b), Kimi K3 (Kimi Team et al., 2026), Qwen3.8-27B (Qwen Team, 2026b), and Qwen3.8-Flash-Next (Qwen Team, 2026a). We additionally attempted to evaluate open-weight specialized GUI agents under our standard full-history setting. Some (e.g., UI-TARS-1.5-7B (Qin et al., 2025) and GUI-Owl-1.5-32B-Instruct (Ye et al., 2025)) could not accommodate the complete user activity log within their supported context windows. Some (e.g., MAI-UI-8B (Zhou et al., 2025)) could accommodate the input length but frequently produced malformed or unparsable actions when the full history was included, resulting in a low Action Completion score of 16 .9%. Since these failures occur at the basic action-execution level, the resulting personalization scores would be heavily confounded by execution failures rather than reflecting the agents’ ability to infer preferences or seek clarification. We therefore exclude these models from the main comparative evaluation and focus on agents that can reliably operate under the same full-history setting. 

F.2 Error Analysis 

To understand how personalization fails, we manually label the error types in every failed trajectory of Claude Sonnet 5 (79 failed tasks) and Qwen3.8-27B (96 failed tasks), which are representative of closed and open agents. We first categorize personalization-related errors based on two axes: whether the underspecified information is ask-only or inferable, and whether the agent recognized the slot as open at all or resolved it incorrectly on its own without the user. This yields four error types: 22 • Silent Default (e.g., Figure F.1): an ask-only requirement is never considered, and the app’s pre-filled value is accepted directly as fact; • Missed Inference (e.g., Figure F.2): an inferable preference that the task depends on is never consid-ered; • Silent Guess (e.g., Figure F.3): the agent does treat an ask-only detail as open but fills it in incorrectly on its own, by guessing at the current situation and user intention, e.g., based on history, plausibility, instead of asking; • Wrong Inference (e.g., Figure F.4): the agent reasons about a preference based on H but resolves it to the wrong value. Figure 3 shows the error distributions. Note that a single trajectory may exhibit multiple error types. The results show that failures on iPrefBench are mostly personalization failures rather than navigation failures: 89 % of Sonnet 5’s and 84 % of Qwen3.8-27B’s failed trajectories contain at least one of the four personalization errors, consistent with the gap between action completion and personalization in Table 1. Although Qwen3.8-27B fails on more tasks, the error distributions of these two agents are close, suggesting that these are shared behaviors of agents optimized for autonomous execution rather than a weakness of any single model. 

F.3 Additional Case Studies 

In environment-perturbation tasks, the expected behavior is to recognize that the preferred option is un-available, surface this to the user, and then either proceed with an acceptable alternative or stop when no substitute is acceptable (§3.3). We observe three different failure patterns of handling such unavailabil-ity: (1) after finding the item unavailable, the agent keeps attempting other ways to obtain the same item (e.g., Figure F.5); (2) the agent directly substitutes an alternative without consulting the user (e.g., Fig-ure F.6); and (3) the agent skips the unavailable item, without considering alternatives or consulting the user (e.g., Figure F.7).
