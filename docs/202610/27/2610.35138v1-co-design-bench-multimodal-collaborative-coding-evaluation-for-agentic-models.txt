## Abstract 

Evaluating human–AI co-design requires testing whether coding agents can translate real users’ multimodal requests into working application revisions. We introduce Co-Design Bench , a reference-free benchmark of 273 tasks curated from 37,463 deduplicated queries across 26,314 real user coding sessions. Its two tracks, Multimodal Editing (ME) and Repository Editing (RE), cover localized edits with optional image, audio, video, or document inputs and coordinated repository revisions. Tasks span three capability dimensions: Grounded Understanding, UI Transformation, and Functional Implementa-tion. The tasks pair normalized requests and runnable pre-edit applications with 2,331 hidden expert-authored acceptance criteria. Our judge-then-refute protocol grades criteria using source and browser evidence, challenges positive verdicts with a separate LLM verifier, and audits visual and interaction claims without gold code or target screenshots. Under a shared agentic harness, the strongest of ten model endpoints passes an average of 69.9% of criteria per task but fully satisfies only 26.4% of tasks. All ten endpoints achieve lower criterion completion on repository edits spanning three or four change types than on those spanning one or two. Co-Design Bench provides a testbed for studying the gap between partial requirement satisfaction and complete task success under agentic execution for real-user application revisions. 

## 1 Introduction 

Web application co-design follows an iterative cycle of inspecting an existing artifact, requesting changes, and assessing the result (Schön, 1983). Coding agents can participate in this cycle by inspecting visual context, modifying source files, and executing applications (Yang et al., 2024a; Anthropic, 2025; OpenAI, 2026a; Qwen Team, 2026b). Success requires translating user intent into working revisions of the current application. A request may combine image, audio, video, or document inputs with changes to layout, interaction, and application state, requiring the agent to connect multimodal evidence to dependent revisions across the application’s interface and behavior. Existing benchmarks capture important parts of this problem: reference reconstruction (Si et al., 2024; Lai et al., 2025; Chen et al., 2025), synthetic or predefined edits and repairs (Li et al., 2026; Lei et al., 2026), edits extracted from version histories (Xiao et al., 2025), and implementation of repository issues or freelance requests (Jimenez et al., 2023; Yang et al., 2024b; Miserendino et al., 2025). Coverage remains limited for compound revisions drawn from coding sessions across both localized multimodal edits and coordinated repository changes (Table 1). For example, the sports clip editor request in Figure 1(b) couples clip-count and duration limits, timeline alignment under zoom, and state updates that re-enable insertion after clip removal or splitting. Such a request ties success to the behavior of the edited application across several interacting requirements at once. Agentic execution also changes how benchmark scores should be interpreted. On the same 150 WebCompass-edit tasks (Lei et al., 2026), switching qwen3.7-plus (Qwen Team, 2026a) from single-shot to agentic execution raises mean graded feature completion from 73.6% to 95.1%, with the feature rubric, judge, and render pipeline held fixed (Figure 1(a); Appendix A). On these 150 tasks, opus-4-8 (Anthropic, 2026a) reaches 99.4% mean graded feature completion with agentic execution. We introduce Co-Design Bench , comprising 273 tasks and 2,331 expert-authored acceptance criteria, curated from 37,463 deduplicated queries across 26,314 real user coding sessions. We recover and validate runnable pre-edit applications, retain available session context and attachments, and consolidate user requests into bounded editing tasks. The benchmark covers two complementary settings: Multimodal Editing (ME) evaluates localized visual, structural, and content edits with optional image, audio, video, or document inputs; Repository Editing (RE) evaluates coordinated UI and feature changes across components, routes, state, and data flow. Both tracks pair the starting application with a normalized request and hidden acceptance criteria that specify the requested changes while allowing multiple valid implementations. A document-grounded edit can require consistent updates to a displayed value and its dependent summaries, while a repository request can couple visible controls with state transitions across components. The shared task formulation captures these dependencies as auditable requirements, connecting the interpretation of user evidence to observable visual changes and state transitions in the edited application. Evaluating these tasks requires checking whether requested features are reachable and behave correctly in the edited application. Our judge-then-refute protocol first grades hidden criteria using source code and browser execution evidence. A separate LLM verifier challenges P ASS and P ARTIAL verdicts against the collected evidence, checking for stubs, hardcoding, unreachable functionality, and requirement mismatches. Audits require successful renders and screenshots for visual claims and recorded browser actions for interaction claims; missing evidence aborts evaluation before score aggregation. The pre-edit application grounds the requested changes, enabling reference-free acceptance without gold code or target screenshots, while retained verdicts and traces link each criterion judgment to its supporting evidence for inspection. We evaluate ten model endpoints under a shared agentic harness. The strongest endpoint passes an average of 69.9% of criteria per task but fully satisfies only 26.4% of tasks. Model rankings vary between tracks, and all ten endpoints achieve lower criterion completion on repository edits spanning three or four change types than on those spanning one or two. These results show that substantial coverage of individual requirements can coexist with limited complete-task success, motivating evaluation of both criterion satisfaction and complete delivery.

## 2 Related Work 

Multimodal web generation and editing. Design2Code, WebSight-Test (from WAFFLE), and WebRen-derBench evaluate screenshot-to-code reconstruction against reference pages (Si et al., 2024; Liang et al., 2024; Lai et al., 2025). IWR-Bench extends reconstruction to interaction videos, using annotated action replay and reference screenshots (Chen et al., 2025). WebGen-Bench and FrontendBench add browser-or sandbox-based functional tests for websites generated from scratch (Lu et al., 2025; Zhu et al., 2025). Editing benchmarks instead revise an existing artifact. DesignBench extracts adjacent-version pairs from V0/Vue0 histories for before/after screenshot assessment (Xiao et al., 2025). MT-Web2Code synthesizes repair trajectories by corrupting reference pages (Li et al., 2026), while WebCompass constructs tasks around predefined edit operations (Lei et al., 2026). FronTalk studies conversational front-end generation with multimodal feedback (Wu et al., 2026). Co-Design Bench instead fixes a bounded revision recovered from a production coding session, retaining its runnable starting application, context, and attachments; hidden criteria specify requested changes without gold code or a target screenshot as supervision. 

Repository-level coding. SWE-bench evaluates changes for real GitHub issues through executable tests (Jimenez et al., 2023). SWE-bench Multimodal covers frontend JavaScript software with visual tests (Yang et al., 2024b), and SWE-Lancer evaluates real freelance implementation requests through browser-based end-to-end tests (Miserendino et al., 2025). Co-Design Bench focuses on compound design and feature revisions within coding sessions. Its repository track covers coordinated changes to components, routes, state, and data flow. A shared task interface and acceptance protocol connect this setting to localized multimodal edits, allowing both requirement coverage and complete delivery to be measured on a common scale across the two tracks. 

Agentic artifact evaluation and verification. Agent-as-a-Judge assesses generated artifacts against user requirements using agent capabilities (Zhuge et al., 2024). WebCompass uses browser interaction and adaptive tests for generation; its editing and repair settings use checklist-guided judgments from code, logs, and screenshots (Lei et al., 2026). Structured LLM evaluation can improve agreement with human judgments, yet evaluators can exhibit self-preference and benchmark-dependent reliability (Liu et al., 2023; Panickssery et al., 2024; Lù et al., 2025). For application revisions, source presence alone does not establish reachability or correct behavior. Our judge-then-refute protocol therefore combines source and browser evidence with a separate verifier; mandatory audits require screenshots for visual claims and recorded actions for interaction claims. Retained evidence makes positive credit traceable, though it cannot eliminate judgment error.

3.2 Data Source and Curation 

The source corpus contains 39,325 production queries across 26,314 coding sessions; deduplication retains 37,463 candidates. Each candidate is anchored to a target edit turn with its repository, available context, and attachments. Figure 2 summarizes the construction pipeline. 

Recovering executable starting states. We reconstruct applications from session logs, repository archives, or HTML bundles. Candidates must pass dependency, build, container launch, and Playwright rendering checks (Microsoft, 2026). Tasks requiring unrecoverable services are excluded, and repaired applications pass the same validation gate. This gate establishes a working starting point, allowing evaluation to assess the changes made during solver execution. 

Selecting requests and authoring acceptance criteria. Normalization packages attachments and clarifies request wording. Hard filters remove environment-blocked, non-actionable, and non-editing requests. Remaining candidates are ranked by structural difficulty, verifiability, and historical failure signals such as reformulations and rollbacks, then consolidated into bounded session intervals. Experts refine the requests and author hidden criterion-level rubrics. The resulting tasks preserve session-derived revision goals but evaluate a fixed request; they do not simulate further user feedback during execution. Appendix I gives filtering thresholds, ranking rules, and selection parameters. 43.3 Multimodal Editing (ME) 

The 100 ME tasks cover localized visual, structural, and content edits. The solver receives a runnable page, an annotated target region, a normalized request, and optional image, audio, video, or document attach-ments, available for direct inspection or tool-based processing. These assets can specify a visual treatment, a spoken instruction, or a value to reconcile across views. Validation checks the initial Playwright render, attachment decodability, target-region annotations, and criterion verifiability. Rubrics specify requested visual treatments, content placement, and spatial relationships, including preservation of unrelated content when requested. Different CSS and DOM implementations can satisfy these outcomes. For example, the receipt-grounded case requires reconciling a value across a source document, an editable row, and dependent summaries: the local edit must preserve consistency across the requested views (Appendix E). The modality split comprises 20 tasks without attachments, 4 with images, 27 with video, 32 with audio, and 17 with documents. These tasks contain 553 criteria, with a mean of 5.5, a median of 6, and a maximum of 11 per task. See Table 8 for more detail. 

3.4 Repository Editing (RE) 

The 173 RE tasks start from runnable multi-file frontend repositories and require coordinated changes across components, routes, state, data flow, or content. Each task pairs a consolidated request with repository context and relevant local assets. Experts decompose compound requests into separately auditable criteria, retaining explicit wiring or artifact constraints while leaving other implementation choices open. Validation checks dependency resolution, builds, runtime launch, route reachability, and browser rendering; tasks requiring unrecoverable services are excluded. In the clip-editor case, controls must respect duration and count limits and recover after removing or splitting clips, coupling visible interface changes to application state (Appendix E). Both tracks use the same (S, I, C) interface and PASS /P ARTIAL /F AIL verdicts. They differ in the requested editing scope: a localized edit may also start from a bundled application. Appendix F.1 details dataset composition, and Table 1 compares existing web-coding settings. This track contains 1,778 criteria, averaging 10.3 per task, with a median of 8 and a maximum of 46. Structural, stylistic, interactive, and content edits occur in 151, 133, 131, and 112 tasks, respectively. These counts overlap: 166 of the 173 tasks require multiple edit types, making coordinated changes a common property of the selected requests (Table 8). 

## 4 Evaluation Protocol 

Evaluation assesses the final application W against the request and hidden criteria, using baseline B to ground the changes. Figure 3 shows the judge-then-refute pipeline. 

4.1 Evidence and Adversarial Verification Evidence and primary grading. The candidate is built and rendered in an isolated environment. A fixed agentic evaluator (Zhuge et al., 2024) assigns P ASS , P ARTIAL , or F AIL to each criterion using source diffs, rendered pages, and Playwright traces. Evidence must match the claim: source inspection can establish a static property, a screenshot can support a visual requirement, and recorded actions can establish an interaction and its resulting state. Failed builds or missing DOM nodes invalidate render-dependent criteria; a handler in source code alone cannot establish that users can reach and operate the requested functionality through the rendered interface. 

Refutation and evidence audits. A separate LLM verifier receives the initial judgments and collected evidence, then challenges P ASS and P ARTIAL verdicts. It checks for stubs, hardcoded outputs, unreach-able entry points, failures under varied inputs, and request mismatches. This pass targets unsupported completion credit; it does not by itself establish the correctness of every verdict. Subsequent audits re-quire successful renders and screenshots for visual claims and browser-action logs for interaction claims. Violations abort evaluation before aggregation. Verdicts, evidence, and refutation logs are retained for inspection, linking each reported outcome to its supporting observations. Two frontend experts addition-ally checked rubric scores for 200 task–model outputs. They examined the task requirements, evaluation rubric, and generated interface, including browser interactions when required, to assess whether each PASS /P ARTIAL /F AIL verdict reflected the output’s satisfaction of the corresponding criterion. 5.2 Main Results 

Table 2 reports completion, execution effort, and tool use across endpoints. The strongest model, 

gpt-6-astra , leads both tracks in mean strict completion. The remaining endpoints vary in their relative strengths, while complete task success remains limited even for the highest-scoring model. 

Criterion coverage exceeds complete delivery. The leading endpoint achieves ¯ R = 0.754 on ME and 0.667 on RE, but fully passes only 41.0% and 17.9% of tasks, respectively. Across all 273 tasks, its mean strict completion is 0.699 and full-pass rate is 26.4%. Thus, 73.6% of tasks retain at least one criterion that is not fully satisfied. Reporting both metrics exposes incomplete delivery because average requirement coverage does not directly measure full-task success. 

Rankings differ across editing settings. Strict-completion rankings correlate across tracks (Spearman 

ρ = 0.818), yet kimi-k3 moves from fourth on ME to sixth on RE, while Qwen3.8-27B moves from fifth to second. The latter achieves ¯ R = 0.645 on repository edits, compared with 0.642 for opus-5 , making it the second-ranked endpoint in this setting. It ranks fourth overall at 0.644, following gpt-6-astra (0.699), 

opus-5 (0.661), and qwen3.8-max-0902 (0.653; Table 5). The small repository-track gap does not establish a general model advantage. Endpoint mean strict scores span 28.7 percentage points on ME and 13.0 on RE; a combined ranking can conceal strengths specific to an editing setting within this benchmark. 

Execution profiles differ across tracks. ME video tasks have a median of 44 turns, compared with 27 for text-only tasks. Media interactions account for 82.8% of activity in the upper-quartile longest rollouts. Image-inspection calls average 14.47 per run on ME and 2.78 on RE, while the share of Edit /Write calls rises from 7.3% to 27.6%. 5.3 Task-Level Analysis 

We examine three complementary task groupings: attachment modality on ME, edit breadth on RE, and primary capability across both tracks. These descriptive comparisons reflect the selected requirements and composition of each task group rather than isolated causal effects. 

Attachment modality. Qwen3.8-27B leads text-only tasks ( ¯ R = 0.779), opus-5 leads image tasks (0.891), and gpt-6-astra leads video, audio, and document tasks (Figure 4a). Pooled mean strict completion ranges from 0.584 to 0.652 across modalities. Documents have the highest pooled strict score (0.652), yet only 18.2% of their model–task pairs fully pass, compared with 37.0% for text-only tasks (Table 6a). Criterion coverage and all-pass success thus give different views of task difficulty. Tool traces document diverse processing strategies: OpenCV (Bradski, 2000) appears in 68.5% of video trajectories, ffmpeg (FFm-peg Developers, 2026) in 31.5% of video and 25.0% of audio runs, and faster-whisper (Klein, 2023) in 4.4% of audio runs. Some agents also execute pretrained perception models to obtain descriptions, transcripts, class scores, or detection boxes from media inputs to ground subsequent edits (Appendix G). 

Edit breadth. On RE, overlapping groups of structural, stylistic, interactive, and content edits have similar pooled strict scores (0.599–0.607). Grouping by the number of edit types reveals a larger difference: tasks with one or two types score 0.654, versus 0.591 for three or four types, a 6.3-point gap. Every endpoint scores lower on the broader group (Figure 4b). Full-pass rates remain similar (9.1% versus 9.7%), while zero-pass rates rise from 0.9% to 5.8% (Table 6b). Broader edits have lower criterion coverage while maintaining similar pooled full-pass rates. 

Primary capability. Table 3 groups all 2,730 evaluation pairs by the task’s main delivery objective. Functional Implementation is the largest group (126 tasks, 46.2%). It has the highest pooled strict 8completion (0.619) but the lowest full-pass rate (10.3%), compared with Grounded Understanding (0.604; 20.2%) and UI Transformation (0.615; 13.6%). The distinction between requirement coverage and complete delivery persists across these groups. gpt-6-astra leads all three dimensions, scoring 0.738, 0.692, and 0.673 on Grounded Understanding, UI Transformation, and Functional Implementation, respectively; 

Qwen3.8-27B reaches 0.661 on the latter. These groups overlap strongly with track membership, so the breakdown describes performance rather than isolating independent abilities. The accompanying multi-label annotation records 1,172 task–capability associations: 265 tasks (97.1%) have multiple capability labels, and 174 (63.7%) span more than one high-level dimension. Appendix F details category results and coverage. 

5.4 Ablation and Robustness Studies 

We conduct systematic ablations across three critical experimental axes. Execution Regimes: Compar-ing single-shot against agentic execution on 150 WebCompass-edit tasks demonstrates the necessity of iterative agentic loops (Appendix A). Evaluator Sensitivity: Swapping the underlying judge model confirms that relative model rankings and score distributions remain highly robust across different evalu-ators (Appendix C). Scaffold Robustness: Evaluating identical solvers across three distinct harnesses reveals strong model ×harness interactions and highlights the decisive role of closed-loop verification (Appendix H). 

## 6 Conclusion 

Co-Design Bench evaluates 273 real-user application revisions with runnable starting states and 2,331 hidden acceptance criteria. Its two tracks span localized multimodal edits and coordinated repository changes under a shared protocol of source evidence, browser execution, and adversarial review. Across ten endpoints, the strongest model reaches 69.9% mean strict completion but fully satisfies only 26.4% of tasks. Track-specific rankings, edit-breadth differences, and harness sensitivity show where reliable delivery remains difficult. Runnable baselines and criterion-level evidence support analysis of failures in request grounding, change propagation, and final-state verification. The benchmark provides a common setting for measuring progress toward complete delivery by coding agents, while retaining the task context and execution evidence needed to analyze unmet requirements and compare future solvers.

## D Implementation and Resource Accounting 

Execution constraints. Each trajectory has a three-hour wall-clock limit and a 120-turn cap. A wall-clock timeout terminates execution and is recorded as an infrastructure failure. Reaching the turn cap instead triggers a build, render, and evaluation of the final workspace state. 

Telemetry and token accounting. Resource totals come from request-level API logs and include retries. For Anthropic routes, token totals sum prompt, completion, cache-creation, and cache-read entries. For OpenAI routes, reported prompt usage already includes cached input. The evaluated trajectories contain 135,370 tool calls. These accounting conventions distinguish actual requests from a count of unique attempted actions. 14 Trace integrity and final-state evaluation. Tool invocations and returns are paired sequentially within the same assistant scope. This prevents identifiers reused by nested agents from merging unrelated events. Intermediate renders and edits remain available for inspection. Scores use the final candidate: earlier behavior earns credit only if it remains present in the final workspace.

## I Data Curation Details 

This appendix specifies the recovery, filtering, and selection procedures summarized in Section 3.2. 

Source corpus and notation. The corpus contains 39,325 query records from 26,314 coding sessions, including 25,373 frontend application sessions. Deduplication leaves 37,463 candidates, each anchored to an edit turn, repository, available history, and attachments. In Figure 2, Q · I · B · C is shorthand: Q = q,20 the figure’s I = ( X, K) combines attachments and context, and the manifest bundled with B specifies environment E.

Environment recovery and validation. Starting applications are recovered from telemetry logs, reposi-tory archives, standard scaffolds, or static HTML bundles. Recovery restores code, assets, and available history while recording the original source hash. Validation checks code integrity, dependencies, builds, container launch, and headless Playwright rendering. Candidates requiring inaccessible private APIs, authenticated backends, or proprietary SDKs are excluded. Other faulty repositories undergo P0 script-able batch repair, P1 agentic repair, or P2 structural pruning, followed by the same validation gate. A validated package contains the baseline, request context, attachments, container manifest, and validation logs. 

Deduplication and filtering. Content hashes identify exact duplicates; near-duplicates with tokenized Jaccard similarity above 0.80 are removed. Normalization decodes attachments and replaces local image paths with packaged asset references. An optional OCR and content-inspection module screens confidential references while retaining task specifications. Before ranking, deterministic filters F1–F6 reject environment-blocked turns, non-actionable chatter, unbounded requests, system trajectory artifacts, and non-editing interactions. Candidates must pass every applicable filter. 

Candidate ranking. Surviving queries receive a heuristic score combining structural difficulty, verifia-bility, and historical failure signals: 

r(q) = d(q) + v(q) + f (q), d ∈ [0, 5 ], v ∈ [0, 3 ], f ∈ [0, 2 ]. (4) The structural difficulty score prioritizes coordination requirements: d = 1 denotes localized cosmetic edits such as changing one CSS property; d = 2–3 denotes dynamic client-side state changes or intra-component reflow; and d = 4–5 denotes multi-component refactoring, cross-file data propagation, or complex edge cases. Verifiability depends on the required inspection: static source diffs ( v = 1), rendered visual DOM properties ( v = 2), or dynamic post-interaction state transitions ( v = 3); ambiguous or non-auditable targets receive v = 0. Historical failure signals are scored after removing environment-blocked turns: a single-turn resolution receives f = 0; two or three query reformulations receive f = 1; and four or more repetitive follow-up attempts or an explicit rollback receive f = 2. 

Session consolidation and rubric authorship. The selector keeps at most three eligible queries ( r(q) > 1) per session. Their bounding message indices define a closed interval that retains intervening user turns in chronological order. Sessions with question_total_score ≥ 10 proceed to consolidation. For RE, experts refine the request, assign metadata, and author hidden criteria based on the selected user intent. Solver packages contain the task description and working copy; evaluator packages additionally retain the rubrics. 

## J Evaluation Implementation Details 

The evaluator receives the request q, hidden rubric C, baseline B, candidate application W, and execution logs. The procedures below implement the evidence requirements in Section 4. 

Sandbox execution and rendering. The candidate is mirrored into an isolated workspace. Fixed render-recovery heuristics address non-blocking environment issues before the evaluator runs the appropriate 

vite build or static HTML pipeline, starts the application server, and launches headless Chrome. Build, server, and browser outcomes become part of the retained execution evidence. 

Evidence extraction and primary grading. Evidence includes source diffs, DOM trees, body text, view-port screenshots, and source-to-entry reachability logs. When interaction checks are active, Playwright records action sequences and network telemetry. The primary evaluator applies the hidden rubric to this evidence with the baseline available for comparison. All primary passes share an evaluator configuration and Playwright automation; a fixed configuration does not make LLM generations deterministic. Output normalization preserves the original criterion count |Ct| = nt.

Evidence requirements by criterion type. Reachable source and DOM state can support static criteria. Visual claims require a successful render and screenshot evidence; interaction claims also require recorded user actions and the resulting state transition. Internal state or a handler in source code cannot substitute for an executed interaction. Failed builds or missing DOM nodes invalidate render-dependent claims, and missing required evidence cannot be replaced with a weaker proxy. 21 Scoring conventions. Strict Completion counts only P ASS ; Graded Completion also gives half credit to P ARTIAL , ensuring 0 ≤ Rt ≤ Gt ≤ 1. A zero strict score can therefore coexist with partial credit. Pooled task scores average the model–task grid, while criterion-verdict shares pool individual judgments. Non-editing conversational and diagnostic auxiliary records are excluded from implementation-scoring denominators. Raw and environment-adjusted scores are retained separately so that attribution does not overwrite the original judgments. 

Human review of rubric scoring. Two frontend experts checked the judge model’s rubric scores for a total of 200 task–model outputs. They examined the task requirements, evaluation rubric, and generated interface, including browser interactions when required, to check whether the criterion-level PASS /P ARTIAL /F AIL verdicts reflected the output’s satisfaction of the corresponding requirements. 

Audit trail and reproducibility. Each record links the request and rubric to the baseline, final workspace, build outcome, evidence, primary verdicts, and refutation trace. This chain supports criterion-level inspection and score re-aggregation without revealing hidden rubrics to the solver. Stored outputs document the sampled solver and evaluator generations; an endpoint name alone is insufficient to reproduce those generations exactly. 

J.1 Conditional Failure Attribution 

Attribution is triggered for low-scoring cases ( Gt < 0.8) when an independently rendered baseline passes the startability gate. A parallel solvability probe attempts a minimal patch in an isolated sandbox, stubbing inaccessible network endpoints while preserving core business logic. Unfulfilled criteria are attributed to model limitations, environmental blockage, mixed causes, or initial-artifact defects. These diagnoses leave raw scores and denominators unchanged. Supplementary environment-adjusted scores grant attribution credit only when infrastructure failures are established. 22
