## 摘要
评估人机协同设计能力，需要检验编程智能体能否将真实用户的多模态请求转化为可运行的应用程序修改。我们推出 Co-Design Bench，这是一个无需参考答案的基准，包含 273 项任务；这些任务从 26,314 场真实用户编程会话中的 37,463 条去重查询中筛选而来。基准设有两条赛道：多模态编辑（ME）和代码仓库编辑（RE），分别涵盖可选输入图像、音频、视频或文档的局部编辑，以及协同进行的代码仓库修改。任务覆盖三个能力维度：基于依据的理解、用户界面转换和功能实现。每项任务均配有规范化请求、可运行的编辑前应用程序，以及 2,331 条由专家编写的隐藏验收标准。我们的“先判定、后质疑”评测流程利用源代码和浏览器证据评估验收标准，再由独立的 LLM 验证器对肯定判定提出质疑，并在没有标准代码或目标截图的情况下审查视觉与交互相关判断。在统一的智能体执行框架下，十个模型端点中表现最强者平均每项任务通过 69.9% 的验收标准，但仅完整满足 26.4% 的任务。对于涵盖三至四种变更类型的代码仓库编辑任务，所有十个端点的验收标准完成率都低于涵盖一至两种变更类型的任务。Co-Design Bench 为研究智能体执行真实用户应用修改时，部分满足需求与完整完成任务之间的差距提供了测试平台。

## Abstract
Evaluating human-AI co-design requires testing whether coding agents can translate real users' multimodal requests into working application revisions. We introduce Co-Design Bench, a reference-free benchmark of 273 tasks curated from 37,463 deduplicated queries across 26,314 real user coding sessions. Its two tracks, Multimodal Editing (ME) and Repository Editing (RE), cover localized edits with optional image, audio, video, or document inputs and coordinated repository revisions. Tasks span three capability dimensions: Grounded Understanding, UI Transformation, and Functional Implementation. The tasks pair normalized requests and runnable pre-edit applications with 2,331 hidden expert-authored acceptance criteria. Our judge-then-refute protocol grades criteria using source and browser evidence, challenges positive verdicts with a separate LLM verifier, and audits visual and interaction claims without gold code or target screenshots. Under a shared agentic harness, the strongest of ten model endpoints passes an average of 69.9% of criteria per task but fully satisfies only 26.4% of tasks. All ten endpoints achieve lower criterion completion on repository edits spanning three or four change types than on those spanning one or two. Co-Design Bench provides a testbed for studying the gap between partial requirement satisfaction and complete task success under agentic execution for real-user application revisions.

## 1. 核心问题与研究背景

### 1.1 论文要解决什么问题？

论文关注：**编程智能体能否理解真实用户的多模态修改需求，并将已有应用修改为完整、可运行、可交互的最终产品？**

这一问题不仅要求模型生成代码，还要求它同时做到：

- 理解文本、图片、音频、视频和文档中的依据；
- 在已有应用上修改，而不是从零生成；
- 协调界面、组件、路由、状态和数据流之间的依赖；
- 保留用户未要求改变的内容与行为；
- 验证功能在浏览器中实际可达、可用，而非仅存在于源码中。

### 1.2 为什么需要新基准？

作者认为，已有评测主要覆盖截图重建、预定义编辑、人工合成修复、GitHub issue 或独立开发需求，对**真实编程会话中的复合应用修改**覆盖不足。

另外，执行方式会显著影响分数：同一模型从单次生成转为可以反复检查、修改和运行的智能体模式后，已有基准可能接近饱和。因此，评测应同时关注：

- **单项需求满足多少**；
- **整项任务是否完整交付**。

**整体含义**：论文将评测重点从“生成了多少看似正确的代码”，转向“是否将真实用户的全部要求落实为可验证的应用行为”。

## 2. 方法论：任务构建与“先判定、再反驳”

### 2.1 任务形式化

每项任务由三部分组成：

- **初始状态**：可运行的编辑前应用及其容器化环境；
- **用户输入**：规范化请求、可选多模态附件、保留的会话上下文；
- **隐藏验收标准**：专家编写的、允许多种正确实现的结果要求。

智能体可以检查文件、编辑代码、构建和运行应用，但看不到隐藏标准。评测针对**最终应用状态**，中间曾实现、最终又丢失的功能不计分。

这里的“无需参考答案”是指**不需要标准实现代码或目标截图**，并不是没有评判依据：原始应用、用户请求和隐藏标准仍构成验收基础。

### 2.2 数据构建流程

1. **恢复起始应用**：从会话日志、仓库归档或 HTML 包中恢复代码、资源和上下文。
2. **验证可运行性**：检查依赖、构建、容器启动及 Playwright 浏览器渲染；修复后重新检查，无法恢复的服务依赖任务被排除。
3. **去重与规范化**：通过内容哈希和 token Jaccard 相似度去重，近重复阈值为 0.80；统一附件引用与请求表述。
4. **过滤不可评测请求**：删除环境阻塞、闲聊、目标不明确、范围无界或非编辑类请求。
5. **排序与整合**：按结构难度、可验证性和历史失败信号加总排序，将有限会话区间整合为一个固定任务。
6. **专家编写标准**：将复合需求拆为可分别审计的验收条目，同时保留明确的架构与行为约束。

这种筛选更重视复杂、可验证且可能暴露失败的请求，因此最终数据集不是原始用户请求的随机样本。

### 2.3 双轨任务设计

| 赛道 | 主要目标 | 典型要求 |
|---|---|---|
| **ME：多模态编辑** | 局部视觉、结构和内容修改 | 根据票据修改金额并同步汇总；根据视频改变某张卡片，同时保留相邻内容 |
| **RE：仓库编辑** | 跨组件、路由、状态和数据流的协同修改 | 剪辑数量与时长限制、删除后的状态恢复、缩放时的时间轴对齐 |

### 2.4 “先判定、再反驳”评测协议

评测分为四步：

1. **构建与收集证据**：获得源码差异、DOM、截图、浏览器操作轨迹和运行结果。
2. **初步判定**：固定的智能体评估器对每条标准给出 `PASS / PARTIAL / FAIL`。
3. **独立反驳**：另一次 LLM 验证调用专门质疑 `PASS` 和 `PARTIAL`，检查占位实现、硬编码、入口不可达、输入变化后失败或需求错配。
4. **证据审计**：
   - 视觉判断必须有成功渲染和截图；
   - 交互判断必须有操作记录及结果状态；
   - 缺少必要证据时，中止评测，不直接汇总分数。

**关键原则**：源码里有处理函数，不等于用户真的能在界面中触发它。

### 2.5 三类评分指标

- **严格完成率**：每项任务中，完全通过的标准占比。
- **分级完成率**：通过计 1 分、部分通过计 0.5 分、失败计 0 分。
- **完整通过率**：所有标准均完全通过的任务占比。

前两项先在任务内部计算，再对任务等权平均，避免标准较多的任务支配总体分数。

此外，论文对分级得分低于 0.8 且基线可启动的案例进行失败归因，区分模型问题、环境阻塞、混合原因和初始应用缺陷；**归因不改变原始分数与分母**。

## 6. 主要结论与发现

### 6.1 高标准覆盖率不等于完整交付

最强端点 gpt-6-astra 的表现为：

| 范围 | 严格完成率 | 分级完成率 | 完整通过率 |
|---|---:|---:|---:|
| ME | 75.4% | 79.8% | 41.0% |
| RE | 66.7% | 72.8% | 17.9% |
| 全部任务 | **69.9%** | **75.3%** | **26.4%** |

也就是说，即使表现最好的模型，仍有 **73.6% 的任务至少存在一条未完全满足的标准**。

### 6.2 更广泛的仓库修改降低标准覆盖率

RE 中：

- 1—2 类修改：平均严格完成率 **65.4%**；
- 3—4 类修改：**59.1%**，低 **6.3 个百分点**；
- 十个模型均呈下降趋势。

但两组完整通过率分别为 9.1% 和 9.7%，基本相近。因而更准确的结论是：**修改范围更广与更低的标准覆盖率相关，而非所有成功指标都同步下降。**

### 6.3 模型排名依赖编辑场景

- kimi-k3 在 ME 排第四，在 RE 排第六；
- Qwen3.8-27B 在 ME 排第五，在 RE 排第二。

两条赛道排名相关，但总体排名仍可能掩盖模型在具体场景中的差异。

### 6.4 执行模式与框架显著影响测量结果

- WebCompass-edit 上，同一 Qwen 模型从单次生成转为智能体执行，分级完成率从 **73.6% 提升至 95.1%**。
- 跨框架实验中，Qwen3.8-27B 的 RE 得分跨度达到 **18.9 个百分点**，两个模型的相对排序也可能改变。

因此，成绩应解释为**模型、执行框架和评测协议共同作用的结果**。

### 6.5 更多执行投入不保证更高完成度

部分模型消耗更多轮数和 token，却取得更低分数。这说明长轨迹和高资源消耗不能直接替代有效的需求理解与最终验证。

## 7. 优点与亮点

- **任务来源更贴近真实开发**：保留用户会话、初始应用和附件，而不是只评估孤立指令。
- **突出需求之间的依赖**：覆盖跨视图一致性、状态恢复、修改传播和既有行为保留。
- **无标准实现限制**：不依赖唯一代码答案或目标截图，允许多种合理方案。
- **证据要求清晰**：区分源码存在、视觉呈现和实际交互，减少“看起来实现了”的误判。
- **反驳机制针对正向误判**：专门检查虚假实现、硬编码和不可达功能。
- **指标具有工程意义**：将完整交付与局部达标分开衡量。
- **主动分析评测系统影响**：框架敏感性结果提醒读者避免把系统成绩当作纯模型能力。

## 8. 不足与局限

### 8.1 数据代表性与应用范围有限

- 仅 273 项任务，且主要来自前端 Web 开发，不能直接推广到后端、移动端、数据工程或大型企业系统。
- 数据筛选偏向困难、可验证和历史失败较多的请求，不能代表真实请求的自然分布。
- 排除不可恢复服务、私有 API 和认证后端，降低了环境噪声，但也削弱了对复杂生产环境的覆盖。
- 图片附件任务仅 4 项，部分能力类别也只有 4 项，细分排名不稳定。

### 8.2 “协作”仍是固定请求下的执行

虽然任务来自真实人机会话，评测时并没有继续模拟用户澄清、反馈和偏好变化。因此，它主要衡量**会话来源的固定修改任务**，而非完整的长期人机共同设计过程。

### 8.3 评测可靠性尚未充分量化

- 独立 LLM 反驳不等于独立真值，评估器仍可能共享盲点。
- 反驳主要挑战正向判定，对错误的 `FAIL` 缺少对称纠错机制。
- 人工复核虽覆盖 200 个输出，但未报告人机一致率、专家间一致率或误判类型分布。
- 未给出清晰的“有无反驳阶段”消融，无法量化其净收益。
- 缺失证据时中止评测，但中止案例数量及后续处置披露不足，影响完整审计。

### 8.4 统计与复现信息仍可加强

- 缺少重复采样和统计不确定性分析。
- 跨框架表格中的“平均完成率”未明确标注对应严格还是分级指标，不宜直接与主榜比较。
- 使用外部感知模型意味着成绩包含工具生态能力，不能单独归因于端点的原生多模态能力。
- 附录文字称文档任务的分级完成率最高，但表中图片组为 0.731、高于文档组 0.682，存在一处文字与表格不一致。
- 未披露 GPU 与总成本，限制了效率和可复现性的评估。

**总体评价**：论文最有价值的贡献，是构建了一个以真实需求、可运行起点和可审计验收为核心的评测体系，并明确展示了“满足多数要求”与“完整交付”之间的差距。但其结果应限定在所选前端任务、执行框架和评测协议内理解，尚不足以代表广义软件工程或长期人机协作能力。
