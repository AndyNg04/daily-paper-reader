# “Then there’s prompt injection, a malicious email, ...” : The Wild Wide West of OpenClaw Agentic System Security 

MOSTAFIJUR RAHMAN AKHOND, York University, Canada 

MAHMUDA KHATUN, York University, Canada 

GIAS UDDIN, York University, Canada AI-powered personal assistant frameworks such as OpenClaw combine LLM reasoning, persistent memory, tool invocation, local execution, and web-based workflows. These capabilities enable useful automation, but they also create security risks when untrusted inputs, model reasoning, tools, memory, and deployment configuration interact without explicit trust boundaries. This paper presents an empirical study of reported security concerns in OpenClaw using two complementary data sources: Reddit discussions and security-tagged GitHub issues. We analyze more than 25K Reddit posts from 13 OpenClaw-related subreddits and identify 162 security-relevant posts with 1,787 associated comments. We further collect 358 security-tagged GitHub issues and retain 180 issues describing concrete security concerns. Using qualitative analysis and evidence-grounded CWE mapping, we identify 521 CWE instances across 59 distinct weakness types, concentrated in access-control failures, sensitive-data exposure, injection, and unsafe execution. We also extract 543 practitioner mitigation suggestions and consolidate them into seven recurring strategies. To complement the empirical analysis, we present an evidence-grounded illustrative reconstruction of a representative sensitive-data exposure pathway using dummy secret values. Our findings show that OpenClaw security issues are not isolated implementation bugs; they reflect recurring trust-boundary failures across the agent execution pipeline. We discuss how these weaknesses map to both traditional software-security categories and agent-specific failure mechanisms, and derive implications for safer agentic systems, including explicit trust boundaries, least-privilege tool access, execution containment, runtime oversight, and defense-in-depth deployment. 1 Introduction 

Large Language Models (LLMs) have rapidly expanded beyond standalone chat-based assistants into autonomous, system-integrated agents that support complex workflows [9, 11]. These systems combine LLM reasoning with external tools, persistent memory, and system-level capabilities, enabling multi-step task execution and continuous operation [17, 18]. OpenClaw [27] exemplifies this paradigm as a self-hosted, tool-integrated assistant with persistent state, tool access, and direct interaction with local and web-based resources. Unlike traditional LLM applications that generate isolated responses, such agentic systems can interact with files, execute commands, invoke external services, and retain context across sessions. These capabilities enable useful automation, but they also introduce security risks when untrusted inputs, model reasoning, tools, memory, and deployment configuration interact without explicit trust boundaries [6, 32, 47]. Many resulting failures resemble familiar software weaknesses, including improper access control, data exposure, unsafe execution, and input validation errors. Prior work identifies key risks in LLM-based and agentic systems, such as prompt injection, unsafe tool use, privilege escalation, malicious skill execution, memory manipulation, and cross-context data exposure [8, 16, 21]. Motivated by such boundary-crossing behavior, we study OpenClaw as a real-world case of security boundary failure in agentic systems. We combine two complementary sources: Reddit discussions and security-tagged GitHub issues. Reddit captures deployment-level experiences, operational failures, configuration concerns, and practitioner mitigation advice, while GitHub issues provide implementation-level evidence of weaknesses, fixes, and maintainer-side triage. We treat these sources as reports of security-relevant behavior and concerns rather than definitive ground truth for exploitable vulnerabilities. Our work differs from prior OpenClaw-focused security analyses, which primarily study advi-sories, controlled attacks, layered threat models, or predefined failure scenarios [6, 7, 32, 35, 40, 44, 47]. Using a mixed-methods approach (Section 3), we analyze more than 25K Reddit posts from 13 OpenClaw-related subreddits and 358 security-tagged GitHub issues, retaining 162 security-relevant Reddit posts and 180 validated GitHub issues for detailed analysis. We map reported issues to CWE [37] to normalize heterogeneous Reddit and GitHub reports into a standard software-weakness vocabulary and identify recurring weakness mechanisms rather than isolated incidents. This mapping yields 521 CWE instances across 59 distinct classes. Beyond CWE, we analyze how these weaknesses become agent-specific failures when model reasoning, memory, tools, plugins, credentials, and autonomous execution interact. We also extract 543 practitioner mitigation sugges-tions from Reddit comments, covering least-privilege access, isolation, monitoring, supply-chain review, credential management, human approval, and network restriction. These suggestions show that secure OpenClaw deployment requires defense-in-depth rather than a single category-specific fix. In summary, this paper makes the following contributions: 

• Empirical study of OpenClaw security concerns: We analyze 162 security-relevant Reddit posts and 180 GitHub issues to characterize deployment-level and implementation-level security concerns in a real-world agentic system. 

• Evidence-grounded CWE mapping: We map reported issues to 521 CWE instances across 59 distinct CWE classes, providing a standardized view of recurring weakness patterns. 

• Agent-specific failure analysis: We identify how conventional weaknesses become agentic failures through interactions among model reasoning, memory, tools, plugins, credentials, and autonomous execution. 

• Mitigation insights: We extract 543 practitioner mitigation suggestions and consolidate them into seven defense-in-depth strategies for safer OpenClaw deployment. 

2 Background and Related Work 

This section reviews prior work on AI agents, personal assistant systems, and security analysis in agentic systems, then positions our study relative to recent OpenClaw security research. 

2.1 AI Agents and Personal Assistants 

Recent advances in large language models (LLMs) have transformed AI systems into agents capable of reasoning, planning, tool use, and persistent interaction. Systems such as Generative Agents [29], 

ReAct [46], Toolformer [31], Reflexion [33], AutoGen [43], and Voyager [39] establish capabilities including memory, reasoning-action loops, tool invocation, feedback-driven improvement, multi-agent coordination, and reusable skill acquisition. Evaluation frameworks such as AgentBench [22], 

SWE-bench [14], and SWE-agent [45] further reflect the shift toward interactive and software-engineering task environments. However, these benchmarks do not directly evaluate security-boundary enforcement, tool-use safety, context leakage, or runtime approval in deployed agentic systems.

This progression has also led to personal AI assistants embedded into everyday workflows. Systems such as MagicSchool.ai [10] and PersonaLens [49] illustrate domain-specific automation and long-term personalization, while broader work highlights the societal and infrastructural im-plications of large-scale deployment [30]. Within this landscape, OpenClaw represents a persistent, tool-integrated assistant connected to local files, external services, and communication platforms, amplifying both capability and security risk. 

2.2 Security-Relevant OpenClaw Architecture 

OpenClaw is an agentic LLM-based assistant framework with persistent state, external inputs, memory, and tool-calling interfaces [27]. In a typical OpenClaw-like workflow, user queries and external data can be combined with conversation history, retrieved memory, and execution results. The LLM reasons over this context and may produce responses, tool calls, or parameterized ac-tion directives that are dispatched to tools connected to files, shell execution, external APIs, or communication platforms. This architecture creates direct security implications. OpenClaw maintains state across sessions, processes external content alongside trusted user input, and allows model outputs to mediate system-level actions through tool dispatch. As a result, vulnerabilities can span the full inference-to-action pipeline: untrusted inputs can influence reasoning, reasoning can trigger tools, tools can access sensitive resources, and persistent memory can carry information across interactions [8, 16, 19]. These properties make OpenClaw representative of agentic systems in which security failures arise from interactions among model behavior, tool execution, memory, and deployment configuration [6, 23, 32, 47]. 

2.3 Security and Vulnerabilities in AI Agents 

The integration of AI agents expands the attack surface beyond traditional model-level risks. Recent surveys characterize vulnerability classes such as prompt injection, unsafe tool execution, memory manipulation, persistent-state corruption, and cross-component attacks [8, 16, 19]. Empirical benchmarks and analyses further show how adversarial inputs can propagate through long-horizon planning, web-enabled interaction, and tool pipelines to trigger unsafe actions [5, 15, 21]. These studies establish that agent vulnerabilities emerge from multi-stage execution flows, but they are often studied through predefined threat models, controlled attack scenarios, or synthetic evaluation environments. Recent defenses and system-level analyses propose mitigations such as deception-based protec-tion, access control, sandboxing, runtime enforcement, and human-in-the-loop validation [3, 12, 48]. AI- and agent-specific taxonomies, including MITRE ATLAS and the OWASP Top 10 for Agentic Applications, further highlight risks that are not always captured cleanly by traditional software weakness taxonomies, including indirect prompt injection, tool misuse, memory poisoning, and agentic workflow abuse [24, 28]. These taxonomies motivate our use of an agent-specific mechanism layer in addition to CWE-based coding. OpenClaw-specific studies examine realistic agent vulnerabilities, including prompt injection, malicious skill execution, trajectory-level failures, layered threat models, advisory-based security analyses, and defense strategies [6, 7, 23, 32, 35, 40, 41, 44, 47]. These studies establish OpenClaw as an important case for studying agentic-system security, but they primarily rely on controlled experimentation, predefined attack scenarios, advisories, or framework-level threat analysis.

3 Study Design 

This section describes how we collected, filtered, validated, and coded OpenClaw-related security reports from Reddit and GitHub. Figure 2 summarizes the end-to-end pipeline. 

3.1 Data Collection 

To analyze security concerns reported by users and developers, we collected evidence from two com-plementary sources: Reddit discussions and security-tagged GitHub issues. Both platforms have been used in prior empirical studies to examine developer discussions and software-security concerns [34]. Reddit captures deployment-level experiences, operational failures, configuration practices, and mitigation advice from community discussions, while GitHub issues provide implementation-level evidence of weaknesses, fixes, and maintainer-side triage. For Reddit, we collected OpenClaw-related discussions from 13 dedicated and closely related subreddits using the ArcticShift API [13]. The resulting corpus contains more than 25K posts

3.2 LLM-Assisted Filtering 

The Reddit dataset contains 175,984 total entries, including more than 25K posts and their associated comments, making fully manual identification of security-relevant posts infeasible. The diverse taxonomy and free-form nature of discussions also make rule-based or static-analysis approaches less suitable, as security concerns may be implicit and context-dependent. We therefore used LLM-based filtering to identify relevant posts from their broader context. Rather than relying on an out-of-the-box model, we curated a seed set of 20 posts covering diverse concerns, including data leakage, unauthorized access, unsafe code generation, and policy or compliance risks, and used it solely for prompt development. Because false negatives are more consequential in our pipeline, the prompt prioritized recall over precision to maximize the inclusion of potentially relevant posts. We then applied the prompt independently using two open-weight models, GPT-OSS:20B and Qwen-3:32B, to provide a cross-model consistency check and reduce dependence on the behavior of a single model. We selected open-weight models to support reproducibility, local auditability, and inexpensive reruns. We retained posts identified by both models as candidate positives, using model agreement to reduce false positives before manual review, yielding 1,218 candidate posts for subsequent manual analysis. To assess whether LLM-based filtering discarded relevant security posts, we audited each model and the intersection filter on separately drawn balanced samples of 200 Reddit posts that were not used during prompt development. Table 1 reports TP, FP, TN, and FN for each audit, where FN is the critical error for our pipeline: a post marked as non-relevant by the LLM but judged security-relevant during manual review. Across all three audits, FN = 0, indicating that the evaluated filters did not miss any relevant security posts in these samples. The filters show low precision because they intentionally retain many false positives. This is acceptable for our pipeline because all LLM-positive posts were later manually reviewed, so false positives increase annotation effort but do not contaminate the final dataset. To further examine missed-post risk, we manually audited 200 randomly selected posts classified as non-relevant by both models; all 200 were confirmed as non-relevant. Overall, Table 1 supports our use of the LLM filters as recall-oriented candidate-generation tools rather than final classifiers.

3.3 Human Validation 

Because automated labels and platform-provided security tags may contain noise, we performed three manual validation tasks before analysis. First, we validated the LLM-filtered Reddit posts to remove false positives and retain only posts that described concrete OpenClaw-related security concerns. Second, we validated the security-tagged GitHub issues because repository labels may be broad or inconsistent, and not every security-labeled issue describes a concrete weakness. Third, we validated Reddit mitigation suggestions because comments often include jokes, vague opinions, tool recommendations, or non-security discussion rather than actionable security advice. For each validation task, two annotators independently reviewed the item and assigned an inclusion or coding decision. Exact agreements were retained directly, while partial agreements and disagreements were resolved by a third annotator after reviewing the original evidence. The final validated datasets consist of 162 Reddit posts, 180 GitHub issues, and 543 mitigation suggestions. Table 2 summarizes the validation outcomes across these three tasks. The aggregate exact agreement rate was 96.6%. We report exact agreement as the primary reliability measure because CWE mapping is multi-label and evidence-based, while mitigation coding involves both inclu-sion/exclusion decisions and open coding. As a secondary reliability measure, Cohen’s 𝜅 ranged from 0.875 to 0.920. 

3.4 CWE Mapping 

To represent the identified security concerns using a well-established security taxonomy, we mapped the validated security-relevant reports to MITRE’s Common Weakness Enumeration (CWE). CWE provides a structured vocabulary for describing and organizing software weaknesses and has been used in empirical software-engineering studies to systematically classify security concerns associated with software systems [20, 26]. We use CWE as a standardized vocabulary for categorizing reported weakness patterns, not to claim that every report is a verified exploitable vulnerability. A CWE label therefore means that the report contains evidence of that type of weakness; it does not imply that we independently confirmed exploitability or assigned an official vulnerability record. Annotators considered the reported behavior, affected asset, apparent root cause, and security impact, and assigned a CWE label only when the report provided supporting evidence. Because Reddit and GitHub reports differ in technical detail, we used a source-aware mapping strategy. Reddit posts often describe deployment-level concerns without much implementation detail, so we retained higher-level CWE identifiers when implementation details were unavailable. GitHub issues typically provide more precise technical evidence, so we prioritized specific, action-able mappings and avoided overly abstract identifiers when finer-grained CWEs applied; in several cases, CWEs were also mentioned in the issue. To complement CWE, we align the observed weakness categories with the AI Vulnerability Database (AVID) taxonomy. CWE provides a mature vocabulary for traditional software weaknesses, while AVID provides a taxonomy library for classifying failure evidence in general-purpose AI systems, including developer tools, end-to-end applications, and agents [1, 2]. We use AVID only as a secondary interpretive layer for agent-specific failure modes; the primary coding remains CWE-based.

4 Findings: Reported Weakness Patterns and AVID Alignment 

We first characterize reported OpenClaw security concerns using CWE as the primary structur-ing mechanism. Because Reddit reports often describe deployment-level behavior while GitHub issues provide more implementation detail, we interpret cross-source differences qualitatively and aggregate individual CWE labels into higher-level categories. We then use AVID as a secondary interpretive layer to connect the CWE results to AI-agent-specific failure patterns. AVID does not replace CWE in our analysis; it helps explain how conventional weakness mechanisms appear in a general-purpose AI agent system. Across the validated dataset, 162 Reddit posts yielded 329 CWE instances across 50 distinct CWE types, while 180 GitHub issues yielded 192 CWE instances across 41 distinct CWE types. After cross-source deduplication, the combined dataset contains 521 CWE instances across 59 unique CWE types (Table 3). 

4.1 Overview of CWE Categories and AVID Alignment 

We group the 521 CWE instances into eight higher-level categories: Access , Exposure , Injection ,

Execution , Secrets , Network , Resources , and Monitoring . Table 4 summarizes the category-level distribution, most frequent CWE, and closest AVID alignment. The complete CWE distribution is provided in the supplementary material. The distribution is concentrated in a small number of categories. Access-related weaknesses are the largest group, accounting for 184 instances (35.3%). Exposure follows with 96 instances (18.4%), and Injection accounts for 87 instances (16.7%). Together, Access, Exposure, and Injection represent 70.4% of all mapped CWE instances. This concentration suggests that the reported OpenClaw risk surface is shaped primarily by failures in permission boundaries, sensitive-data handling, and the treatment of untrusted inputs. The AVID alignment suggests that many OpenClaw reports sit at the boundary between con-ventional software security and AI-agent-specific failures. CWE captures the software weakness mechanism, while AVID helps interpret how the same weakness appears in an agentic system, such as untrusted content entering model context, skills acting as executable instructions, model-mediated disclosure of local secrets, or long-running agents consuming resources without effective oversight. The taxonomy in Table 4 also shows that OpenClaw weaknesses arise at agentic inter-action boundaries rather than in isolated components. 5 Agent-Specific Failure Mechanisms 

The CWE and AVID mappings identify the weakness types observed in OpenClaw reports, but they do not fully explain why these weaknesses become risky in an agentic system. OpenClaw combines natural-language instructions, persistent context, external tools, local execution, third-party skills, and deployment configuration into a single action pipeline. As a result, weaknesses can propagate across layers: untrusted content can influence reasoning, reasoning can trigger tools, tools can access sensitive resources, and missing audit trails can obscure the resulting actions. Table 5 synthesizes the observations from Section 4 into six agent-specific failure mechanisms. These mechanisms are not additional coding labels; rather, they explain how the observed CWE categories interact across model reasoning, context construction, tool invocation, execution privi-leges, and deployment boundaries. These mechanisms show that the observed weaknesses are not merely ordinary software bugs appearing in a new application. Their impact is amplified by the agent execution pipeline. Access failures can expose tool-mediated actions; injection can influence reasoning; exposure can occur through model context; execution risks can arrive through skills and plugins; resource bugs can be amplified by autonomy; and weak monitoring can make all of these failures harder to detect or reconstruct.

7 Discussion 

The findings show that OpenClaw security issues are concentrated around recurring boundary failures rather than a broad set of unrelated bugs. From the observed weakness patterns (O1– O8), agent-specific mechanisms, mitigation findings (M1–M7), and supplementary advisory/CVE analysis, we derive several implications for OpenClaw stakeholders and the broader agentic-system community. 

Trust-boundary failures are harder than hygiene gaps. Some observed weaknesses reflect conventional security hygiene gaps: Secrets (O5, 6.7%), Network exposure (O6, 4.2%), Resources (O7, 3.5%), and Monitoring (O8, 3.5%) map to established controls such as scoped secrets, segmentation, resource limits, logging, and auditability. By contrast, Access (O1, 35.3%), Injection (O3, 16.7%), and Execution (O4, 11.7%) are more structural to the agent execution model because permissions are exercised through tool selection, untrusted content may enter prompt or memory context, and model outputs can trigger privileged actions. Exposure (O2, 18.4%) often appears as a downstream symptom of unresolved access, context, or injection failures. This suggests that OpenClaw-like systems need both conventional hardening and agent-specific primitives for dynamic authorization, instruction/data separation, and context-aware execution control. 

Access dominates the surface, while execution amplifies damage. Access concerns account for the largest share of observed issues (O1), but execution-related failures (O4) can drive high-impact outcomes because they connect agent decisions to system-level actions. Supplementary CWE–CVE and advisory evidence suggests that access bypass and unsafe execution are recurring classes that may interact within broader attack paths. Together, these findings point to a dual requirement: access must be tightly scoped and continuously enforced at runtime, while execution pathways—especially tool invocation, plugin handling, and skill installation—must be treated as high-risk operations requiring validation, containment, and policy-aware control. 

Defense-in-depth must be integrated into the agent, not left to users. The mitigation findings show that practitioners already recommend familiar controls: least privilege (M1), isolation (M2), monitoring (M3), supply-chain review (M4), credential scoping (M5), human approval (M6), and network restriction (M7). However, the recurrence of these suggestions indicates that users often compensate for missing or weak built-in safeguards. This is especially important for agentic systems, where a single failure can cross boundaries: untrusted content can influence reasoning, reasoning can trigger tools, tools can access secrets or files, and weak monitoring can obscure the action

8 Threats to Validity 

Construct validity. Our analysis relies on public Reddit reports and GitHub issues, which may lack complete configuration details, exploit evidence, or root-cause information. We therefore treat them as reports of security-relevant behavior, concerns, misconfigurations, and implementa-tion weaknesses rather than confirmed exploitable vulnerabilities. We mitigate this risk through evidence-grounded CWE mapping, conservative ambiguity handling, cross-source comparison, and advisory/CVE context where available. 

Internal validity. LLM-assisted filtering may miss relevant Reddit posts. To reduce this risk, we used a frozen recall-oriented prompt, two independent open-weight models, manual validation of all LLM-positive candidates, and filter audits. The audited samples showed no false negatives, and 

, Vol. 1, No. 1, Article . Publication date: October 2026. 18 Mostafijur Rahman Akhond, Mahmuda Khatun, and Gias Uddin 

a separate audit of 200 posts excluded by both models found no missed relevant posts. Because these audits are sample-based, our counts should be interpreted as lower-bound estimates rather than exhaustive coverage. 

Coding validity. CWE assignment and mitigation coding involve judgment, especially for low-detail Reddit reports and practitioner comments. We mitigate this through source-aware mapping rules, conservative ambiguity handling, two-annotator review, third-author resolution, and docu-mented coding criteria. Across the three validation tasks, exact agreement was 96.6%, with Cohen’s 

𝜅 ranging from 0.875 to 0.920. AVID is used only as a secondary interpretive layer, not as an official vulnerability assignment or replacement for CWE. 

External and temporal validity. Our findings are limited to OpenClaw and to public Reddit and GitHub sources, which may overrepresent visible failures and exclude enterprise deployments, private disclosures, or silent failures. The study is also time-bound because OpenClaw and its ecosys-tem evolve rapidly. We mitigate these risks by combining two structurally different public sources, interpreting results as a snapshot of reported concerns rather than statistically representative prevalence, and releasing anonymized replication materials. 

9 Concluding Remarks 

We presented an empirical study of reported security concerns in OpenClaw using Reddit discus-sions and security-tagged GitHub issues. Our analysis covers 162 security-relevant Reddit posts with 1,787 associated comments and 180 validated GitHub issues. Through evidence-grounded CWE mapping, we identified 521 CWE instances across 59 distinct weakness types, with recurring concentrations in access control, sensitive-data exposure, injection, and unsafe execution. These results show that OpenClaw security concerns are shaped by recurring trust-boundary failures rather than isolated implementation bugs. Beyond cataloging conventional weaknesses, we synthe-size agent-specific failure mechanisms showing how familiar issues become amplified when model reasoning, persistent memory, tool invocation, third-party skills, credentials, and local execution interact within the same pipeline. We also analyze 543 practitioner-proposed mitigation suggestions and consolidate them into seven defense strategies, including least privilege, isolation, monitoring, supply-chain review, credential management, human approval, and network restriction. Together, these findings suggest that safer OpenClaw-like systems require defense-in-depth controls that are built into the agent pipeline, rather than left only as deployment advice. 

Message to OpenClaw Designers and Developers: Security should be enforced across the full agent execution pipeline. OpenClaw-like systems should scope permissions at action time, separate trusted instructions from untrusted data, constrain tool invocation, isolate execution contexts, and provide auditable traces for high-risk actions. 

Message to Users: OpenClaw should be treated as a long-running software system with persis-tent state, external inputs, and access to sensitive resources. Users should restrict permissions, avoid public exposure of agent interfaces, isolate deployments, scope credentials carefully, and review high-risk actions before execution. 

Message to Researchers: Future work should evaluate agentic systems end to end, rather than only testing model outputs or isolated tools. In particular, controlled reproduction of reported pathways can help determine exploitability, identify root causes, and guide concrete fixes for trust-boundary failures involving context, tools, memory, plugins, and deployment configuration.
