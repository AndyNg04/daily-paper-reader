## Abstract 

Interaction traces record how people and agents use computers, and comparing them can reveal usability barriers, differences in expertise, and human–agent similarity. Yet traces are recorded as low-level, interface-specific actions, making comparisons difficult across tasks, interfaces, and input modalities. Existing approaches either compare these actions directly, reduce traces to aggregate out-comes, or summarize them at higher-level goals, obscuring where behavior differs. We present MAP (Multi-level Action Parsing), a hierarchical semantic representation and annotation pipeline that maps traces into a common vocabulary across linked levels of ab-straction. MAP compares traces by sequence, recurring patterns, and effort, localizing differences by type and abstraction level. A technical evaluation across three computer use datasets shows high agreement with manual annotations and broad coverage of behavior. Applying MAP shows that sighted and blind users in-creasingly converge at higher levels despite navigation differences, while agents omit corrective, help-seeking, and recovery behaviors present in human traces.

## 1 Introduction 

Understanding how people use computers has long been a core goal of HCI [25]. A rich source of evidence is the interaction trace :a logged sequence of computer use actions ( e.g. , clicks and key-presses) together with their context ( e.g. , applications and interface elements) [25, 67]. Researchers use such traces to understand how an individual performed a task and to compare how people use com-puters — e.g. , to reveal usability issues by identifying deviations from an ideal trace [49, 60], characterize interaction patterns of ex-perts and novices [21], and surface web browsing strategies [13, 55]. Prior work makes such comparisons by holding the task, inter-face, and input modality constant to compare low-level actions directly [49, 55, 60], or by reducing the trace to aggregate mea-sures such as completion time, action count, or success [5, 21, 22]. But, such work does not yet compare computer use behaviors that cut across tasks, interfaces, and input modalities – e.g. to compare across tasks to surface usability barriers, across modalities to lo-cate accessibility gaps, or across interfaces to characterize general computer use expertise. Recent datasets of interaction traces record this kind of variation [17, 22, 44, 64], creating the opportunity to make such comparisons at scale. But, it remains challenging to compare traces as they are recorded in a low-level input- and interface-specific vocabulary. For example, a screen reader user may press Tab six times while a sighted user points to reach the same button, but their traces differ. Recent work thus describes traces at a higher level of abstraction by using LLMs to summarize low-level actions into goals ( e.g. , search for a product, fill in the shipping form) [59, 66], then aligns those descriptions to report where two traces cover the same steps [59]. However, as each trace is labeled independently the same goal may be described in different ways, such that it remains challenging to count or match goals across a corpus of traces ( e.g. , to identify where a group of users got stuck). Further, this level of abstraction is useful for comparing higher-level workflows but obscures differences we care about when comparing how people use computers: people can reach the same goal by different methods ( e.g. , search vs. faceted browsing), or follow the same method with different costs ( e.g. ,navigating facets linearly vs. by heading). To meaningfully compare computer use behavior across heterogeneous interaction traces thus requires a representation with a shared vocabulary to aggregate labels across traces and multiple linked levels of abstraction so that we can recover how and at what level interaction traces differ. We introduce MAP (Multi-level Action Parsing), a framework for comparing computer use behavior across multiple levels of ab-straction and dimensions of similarity. MAP provides a hierarchical semantic representation of interaction traces across four connected levels, from input actions as Operations (L1) , to their Functions & Consequences (L2) , Methods (L3) , and Goals (L4) . We con-struct these levels through the following procedure: Operations (L1) are low-level actions common to interaction traces ( e.g. , point-ing, clicking), Functions and Consequences (L2) are derived by unifying existing standards that describe how interfaces are im-plemented [2, 31] ( e.g. , “focus ⟨search box ⟩”), Methods (L3) are derived by open-coding interaction traces and consolidating equiva-lent labels ( e.g. , “edit”, “search”), and Goals (L4) are task-dependent and thus open-vocabulary as in prior work ( e.g. , “Edit the file named final.txt”) [59, 66]. MAP’s vocabulary instantiates this procedure for desktop GUI computer use. To assign this vocabulary to inter-action traces at scale, MAP applies labels deterministically when possible ( e.g. , L1 operations and L2 functions) and otherwise with an LLM with a fixed vocabulary ( e.g. , L3 methods), such that only task-dependent fields remain open-vocabulary. MAP’s shared rep-resentation thus makes it possible to identify where traces diverge. To capture different ways in which behavior can be similar, MAP applies three complementary metrics: sequence similarity , which measures alignment in the order of interactions; pattern simi-larity , which captures recurring local interaction patterns; and 

effort similarity , which captures how actions and time are al-located across a workflow. Each metric can be computed at each abstraction level, enabling MAP to localize both the type and level 

of behavioral differences between interaction traces. We validate MAP via a technical evaluation and an examination of its capacity to answer questions posed in prior research. Our technical evaluation compares MAP’s annotations against manual annotations of 2,342 actions across three computer use datasets spanning human and agent traces and sighted and screen reader interactions (A11y-CUA [22], AgentSynth [63], and AgentNet [65]). semantic field, and 99.2% of actions across the full corpus receive a defined label rather than unknown , indicating that the vocabularies cover observed behavior. We further characterize where the pipeline disagrees with annotators: most L3 errors reflect segmentation differences, and L2 errors rarely propagate to L3. We use MAP to replicate and extend prior findings on how sighted users, blind users, and computer use agents complete the same tasks [10, 22, 46, 59]. Consistent with prior work, blind and sighted users differ sharply in low-level interactions, and agents differ from their corresponding human groups in how they execute tasks. MAP further localizes where these differences occur: the additional effort for blind users is concentrated in navigation rather than selection or typing, while the two groups largely converge on the same higher-level Methods. Agents likewise become more similar to humans at the Method level, but reproduce fewer of the corrective, help-seeking, and recovery behaviors found in human traces. We then discuss opportunities to apply MAP’s framework in the future to surface efficient strategies from expert traces to inform novice users on how to improve, to localize usability problems on interfaces across tasks and users, and to share a user’s computer use behavior without exposing their identity. We also discuss limitations of MAP and potential opportunities to generalize MAP beyond desktop GUIs in the future. Collectively, MAP enables researchers to compare computer use behavior across tasks, interfaces, and input modalities by localizing similarities and differences at multiple abstraction levels. In summary, we contribute: 

• MAP, a hierarchical semantic representation of inter-action traces that labels recorded actions across four levels of abstraction and an automatic pipeline that assigns these labels to interaction traces. 

• A decomposition of behavioral similarity into three dimensions — sequence, recurring patterns, and effort allo-cation — computed with standard measures over MAP labels at any level, so that behavioral differences can be localized by type and level of abstraction. 

• A technical evaluation and comparative analysis using MAP — replicating and extending prior work comparing blind and sighted computer users, and assessing differences between human and agent traces. 

## 2 Related Work 

Interaction traces capture how humans and agents carry out com-puter tasks, from individual inputs to higher-level goals. Prior work has recorded and represented traces in machine-readable formats, abstracted interaction traces into meaningful higher-level units, and compared executions with interaction traces. We build on these directions to create MAP, a shared semantic hierarchy that captures intermediate functional levels between inputs and goals, enabling consistent analysis across traces. 

## 2.1 Recording Interaction Traces 

An interaction trace records a sequence of low-level actions a per-son or agent performs while completing a computer task, often together with the interface state in which each action occurred. Such traces are used to study computer use behavior [22] and to train and evaluate computer use agents [17, 44, 58, 64]. Prior work has progressively enriched these records with information about the context of each action [4, 15, 16]. Early systems paired actions with UI states [16], while later datasets added screenshots and structured interface hierarchies [15]. More recent work standardizes which fields a UI log should record, including actions, UI elements and states, applications, and tasks, so logs from different collection tools can be combined for analysis and automation [4]. This standardizes what events are recorded, but not how different events that accom-plish the same behavior are represented. For example, clicking a 

Save button and pressing Ctrl+S can be recorded using the same fields, but the data model does not itself represent that both actions accomplish save . MAP addresses this second problem by mapping different recorded actions to shared semantic labels based on what they accomplish. OneTrace similarly brings interaction histories from different applications and users into a common trace structure so that they can be viewed and used together [8]. Users then manually group these low-level interaction traces they consider relevant to the same activity. MAP differs by automatically mapping heterogeneous actions to shared semantic labels based on what they accomplish and the Methods they contribute to. Thus, mouse pointing and repeated keyboard navigation can remain distinct low-level actions while being recognized as equivalent at a higher semantic level. Interaction traces support learning, behavioral analysis, and agent evaluation and debugging [17, 18, 22, 24, 36, 44, 56, 58, 64]. Learned representations of screens and UI components support retrieval and action prediction [24, 36]; computer use datasets use traces to train agents, evaluate task completion, and study behav-ior [17, 22, 44, 58, 64]; and tools use traces to inspect agent behavior or identify failures [18, 56]. These analyses generally operate on recorded actions, interface states, or task outcomes, making direct comparison difficult when different inputs accomplish equivalent behavior. MAP preserves those low-level differences while addition-ally mapping them into shared Functions, Consequences, Methods, and Goals, allowing traces to be compared at the level where their behavior becomes equivalent. 

## 2.2 Semantic Abstraction of Interaction Traces 

Abstracting interaction traces makes it possible to recognize when different low-level actions accomplish the same thing and to com-pare behavior beyond exact input sequences. Task models provide an early precedent for representing computer use at multiple levels of abstraction. Hierarchical Task Analysis decomposes tasks into goals and subgoals [50], GOMS represents goals through methods and lower-level operators [30], and the Keystroke-Level Model rep-resents execution through primitive operators [11]. These models are typically constructed top-down by researchers for a known task rather than inferred from recorded traces. MAP adopts this hierarchical structure but derives its labels from traces, connect-ing low-level Operations (L1) to what actions do and change (L2), Methods (L3), and task-level Goals (L4). More recent work infers semantic structure directly from recorded traces. Early systems classified sequences of UI states into pre-defined procedure-like categories, such as searching or compos-ing [16], corresponding to MAP’s Methods (L3). categories are drawn from a fixed vocabulary. However, they repre-sent only this procedure level rather than linking it to lower-level actions, their outcomes, and higher-level task Goals. LLM-based approaches instead infer open-ended descriptions: some extract exe-cutable multi-action units such as logging in or booking a flight [28], while others group low-level actions into intermediate subgoals and then an overall task goal [66]. Recent work similarly induces natural-language steps from human and agent traces and aligns them to compare how the same task is completed [59]. These ap-proaches capture semantics similar to MAP’s Methods and Goals, but their labels are generated independently for each trace, so equiv-alent behavior may be phrased differently and must be matched afterward. They also do not represent MAP’s L2 distinction be-tween what an action does, what it acts on, and what changes as a result. MAP instead uses shared vocabularies at L2 and L3 and links them to both the underlying Operations and task-dependent Goals, enabling equivalent behavior to be aggregated across traces while preserving how it was carried out. 

## 2.3 Comparing User Workflows 

Prior work compares low-level interaction traces directly. Click-stream visualizations reveal common page transitions [68], while sequential pattern mining identifies ordered action subsequences that recur across traces [38]. Other tools align traces around selected actions [33] or compare observed traces with supported task paths to identify inefficient behavior [19]. These approaches work well when traces share the same interface and action vocabulary, but equivalent behavior may appear different when users accomplish the same thing through different low-level actions. Other work first transforms low-level traces into representations specific to a task or agent environment [12, 62]. Traces are com-pared using higher-level semantics by defining a semantic model for each benchmark website that maps GUI interactions to task-level actions and states [12]. This enables precise comparison within that environment, but the semantic actions must be defined separately for each website and do not directly provide a shared representa-tion across different applications or interfaces. Tool-using agent traces can instead be aligned through tool calls and dependencies among their inputs, outputs, and artifacts [62]. This requires a shared tool environment rather than providing a common semantic representation of computer use behavior. MAP instead applies the same semantic representation across tasks, interfaces, and input modalities, allowing heterogeneous traces to be compared without defining environment-specific semantic actions or requiring shared tools. 

## 3 MAP Taxonomy 

To enable systematic comparison of computer use interaction traces across multiple users and tasks, we introduce MAP, a hierarchical labeling approach to semantically annotate traces from various domains including web browsing, system operations, media, docu-ment editing, and workflow applications. MAP represents interac-tion traces at four connected levels so behavior can be compared at different granularities. Operations (L1) capture the recorded input, Functions & Consequences (L2) capture what each action does and changes in the interface, Methods (L3) capture how users accom-plish an immediate objective, and Goals (L4) capture the broader task outcome. The hierarchy builds on the decomposition used in GOMS [30], while adding interface-level semantics between L1 operators and L3 methods (Table 1 summarizes each level, refer to Appendix B for full taxonomy). To support comparisons across users, tasks, and datasets, we aimed for the MAP taxonomy to provide coverage for interac-tions across diverse interfaces, generalize across applications and operating systems, and assign consistent labels to behaviors so recurring patterns can be aggregated within and across traces. MAP therefore annotates behavior from the recorded actions and their interface context, including the active application, interacted UI elements, and assistive technology when needed. 

## 3.1 Operations (L1) 

Operations preserve the low-level mouse or keyboard input used to interact with the interface, allowing MAP to compare how users physically carry out the same behavior before higher-level abstrac-tion. MAP represents mouse input as scroll , primary click ,

double primary click , secondary click , point , and drag drop ,and keyboard input as keypress or shortcut (Table 3). Because datasets record these inputs differently ( e.g. , mouse_press vs. mouse_click ,or separate mouse_down and mouse_up events), they need to be mapped to this common L1 operation set. We also collapse con-secutive point and scroll events, since their logging frequency varies across datasets and would otherwise reflect sampling differ-ences rather than behavior. Cursor coordinates are retained, when available, as context for assigning higher-level labels. Keyboard input requires additional normalization because the same raw key event may represent ordinary keypress or a shortcut, particularly for screen reader interaction. We therefore use a dic-tionary of approximately 400 known shortcuts, including screen reader commands, and their expected outcomes to deterministically distinguish shortcut from keypress operations (Table 2). 

## 3.2 Functions & Consequences (L2) 

L2 makes individual actions comparable by describing what each action does in the interface and what changes as a result. Each action is represented by its function and the UI element it acts on, followed by its consequence and the UI element where that change occurs (if applicable). For example, selecting a button may close a dialog box: select ⟨button ⟩ → close ⟨dialog box ⟩.Functions describe how an L1 operation acts on its direct UI tar-get. Mouse operations map deterministically to functions (Table 3): for example, primary click maps to select , while point maps to navigate . Keyboard operations depend on context because the same key can serve different functions. For example, Shift+h may type “H” in a text field or navigate to a heading when a screen reader is active. We therefore use the focused UI element and screen-reader state to deterministically distinguish typing, navigation, selection, and program commands (Table 2). Consequences describe the observable change produced by an action and where that change occurs. In select ⟨button ⟩ → close

## 3.3 Methods (L3) 

L3 captures the higher-level procedure a sequence of interactions carries out, allowing traces with different low-level executions to be compared as the same method. L3 therefore makes the shared pro-cedure comparable while L1 and L2 retain the differences in how it was executed and the intermediate outcomes observed respectively. ## 3.4 Goals (L4) 

Goals provide the highest level of abstraction in MAP, grouping contiguous L3 Methods that jointly accomplish the same task-level objective. This corresponds to the level of semantic abstraction commonly inferred from interaction traces in prior work [29, 66]. Because Goals are task-dependent, they use an open vocabulary to accommodate diverse objectives across datasets. 

## 4 MAP Similarity Metrics 

The MAP taxonomy provides a common semantic representation of interaction traces, but comparing users also requires specifying 

what aspect of their behavior is similar. We capture three comple-mentary dimensions: sequence similarity measures whether two traces progress through a task in a similar order, pattern similar-ity measures whether they exhibit similar recurring local behaviors, and effort similarity measures whether they allocate comparable time and actions to the same parts of a workflow. After annotat-ing two traces with MAP, we compute each metric independently at L1–L3, allowing similarity to be examined both by behavioral dimension and level of abstraction. 

## 4.1 MAP-Sequence Similarity 

MAP-Sequence similarity captures whether two traces perform interactions in a similar order , distinguishing traces that contain similar interactions but arrange them differently. Prior work has used edit-distance-based methods to compare text [35] and inter-action sequences in software tutorials [32, 43]. We similarly use Needleman–Wunsch global alignment [42] to identify which in-teractions correspond across the two complete traces and where they differ. At each level, identical labels receive a match score of 

+1, while mismatches and gaps receive a penalty of −1. We define sequence similarity as the proportion of positions in the resulting alignment whose labels match exactly. The alignment addition-ally identifies interactions that are substituted, added, or omitted between traces. 

## 4.2 MAP-Pattern Similarity 

MAP-Pattern similarity measures whether two MAP-labeled traces exhibit similar local interaction patterns , even when their overall task paths differ ( e.g. , two traces that use hotkey shortcuts vs. point-and-click). This complements sequence similarity by capturing recurring behavioral tendencies. For each of MAP levels from L1-L3, we extract n-grams of lengths 1, 2, and 3 and compute cosine similarity between n-gram frequency vectors at each length, similar to bag-of-words metrics frequently used for text comparison [23]. We then compute a weighted average that rewards longer n-grams to capture more specific behavioral styles between the two traces. This metric can reveal similarity between user interaction traces within task and across tasks.

MAP-Effort similarity measures whether two users allocate com-parable interaction effort to equivalent parts of a task: two traces may be semantically identical yet differ substantially in cost – e.g. ,formatting a document in 5 actions and 10 seconds versus 15 actions and 40 seconds. ## 5 MAP Pipeline 

The MAP pipeline builds the hierarchy from low-level Operations (L1) to higher-level Goals (L4). It assigns labels deterministically when they can be derived directly from recorded inputs, and uses an LLM to infer labels that require interaction context. 

## 5.1 MAP Annotation 

MAP annotates traces hierarchically from L1 to L4, with each level using the recorded interaction trace and labels from preceding levels. Before annotation, dataset-specific action names are mapped to the common L1 Operations defined in Sec. 3. Both L1 Operations and L2 Functions labels are assigned deterministically. The remaining L2 fields (Direct UI Target, Consequence, and Indirect UI Target) are selected from their fixed vocabularies using the surrounding interaction context (refer to Appendix A for L2, L3, L4 prompts). Annotation uses information available in the trace, including the active application or window, interacted or focused UI element, and preceding actions and labels. Screen-reader state is included when available and needed to interpret keyboard interaction. We exclude task descriptions, task outcomes, user metadata, and screenshots, allowing the same procedure to be applied across datasets with different recording setups. This differs from approaches that addi-tionally use screenshots for segmentation or goal inference [59]. At L3, MAP divides the trace into segments : contiguous runs of interactions that carry out the same Method on the same Specific Entity within the same UI Container. The model jointly determines these boundaries and assigns the three L3 fields. A new segment begins when the Method, Specific Entity, or UI Container changes, or when the active interface changes. The full segmentation rules and L3 prompt are provided in Appendix A. At L4, contiguous L3 segments that contribute to the same task-level objective are grouped under a Goal. We annotate the non-deterministic semantic labels from L2–L4 using Claude Sonnet 5. Refer to supplementary materials for all prompts and full MAP vocabulary. 

## 5.2 Pipeline Evaluation 

We evaluate how accurately MAP annotates interaction traces and how well it generalizes across users, agents, tasks, and applications. 

5.2.1 Datasets. We evaluate MAP on three computer use datasets: A11y-CUA [22], AgentSynth [63], and AgentNet [65]. A11y-CUA contains the same 60 tasks completed by 16 participants (8 sighted and 8 blind users) and by agents under a default condition (CUA-D) or screen reader condition (CUA-SR). Its timestamps and detailed interaction context support both annotation evaluation and the similarity analyses reported later. We use a subset of A11y-CUA to construct the L3 Method vocabulary. However, these traces are disjoint from the A11y-CUA traces used in our annotation evalua-tion. We additionally evaluate on AgentSynth and AgentNet to test whether MAP’s labels apply beyond the dataset used during vocab-ulary development. AgentSynth contains synthetic agent traces, while AgentNet contains human demonstrations; together they introduce applications and interaction patterns beyond those in A11y-CUA. Because neither provides the timing information needed for time-based effort similarity, we use all three datasets to evaluate annotation accuracy and vocabulary coverage, and A11y-CUA for the cross-user and agent similarity analyses. 

5.2.2 Manual Annotation. We manually annotated 30 traces con-taining 2,342 actions: 20 from A11y-CUA (10 SU, 5 BLVU, and 5 Agent-Default), 5 from AgentSynth, and 5 from AgentNet. A11y-CUA traces were sampled randomly within each condition. For AgentSynth and AgentNet, we selected traces from five different applications in each dataset to evaluate MAP beyond the applica-tions represented in A11y-CUA. For each action, we annotated L2’s Direct UI Target , Consequence ,and Indirect UI Target . We also divided each trace into L3 seg-ments and annotated each segment’s Method , Specific Entity ,and UI Container . We did not manually annotate L1 Operation or L2 Function , which are assigned deterministically. For A11y-CUA, annotators inspected the action trace together with the recorded video and audio, including screen-reader output when present. AgentSynth and AgentNet do not provide corresponding videos, so annotators instead used the interaction trace together with the textual observations and reasoning recorded with the actions. Annotators followed a codebook specifying how to apply the L2 and L3 labels, including label definitions, and L3 segmentation rules (full codebook is provided in the Appendix B). Two researchers independently annotated three A11y-CUA pilot traces (249 actions; 1,245 labels across the five closed-vocabulary fields). We refined the annotation instructions and examples based on disagreements until reaching Cohen’s 𝜅 = 0.79, conventionally interpreted as substantial agreement [34]. One researcher then annotated the remaining 27 traces using the finalized codebook. Annotation took approximately 25 minutes per trace, or about 12 hours in total. We then ran the complete MAP pipeline on the same 30 traces without access to the manual annotations. We compared its L2 and L3 annotations with the manual annotations to evaluate semantic labeling and L3 segmentation.

## 6 Results 

We demonstrate MAP by investigating two research questions from prior work. RQ1: How do sighted and blind users differ in how they complete tasks with computers? [9, 22, 46, 51, 53] Comparing these groups can characterize accessibility gaps in com-puter interaction and identify where interfaces create additional effort for blind users. RQ2: How closely do computer use agent workflows align with human workflows? [22, 59] This question is increasingly relevant as agents are used to simulate users for applications such as usability testing and design evaluation [26, 45]. Comparing agent and human traces can therefore show which aspects of human behavior agents reproduce and which they omit. We investigate these questions using A11y-CUA [22], analyzing 30 tasks performed by 16 users (SU1–SU8, BU1–BU8) and two agents (CUA-D and CUA-SR). We compare within- and across-group behavior using MAP-Sequence, Pattern, and Effort similarity at L1– L4. We report pairwise similarity matrices and cluster participants and agents using K-means over the three similarity metrics at each level. For each clustering, we report the Silhouette score, where higher values indicate that traces are more similar within clusters and more distinct across clusters, to quantify how strongly each abstraction level separates behavioral groups. 

## 6.1 How do blind and sighted users differ in how they complete tasks with computers? 

Operations (L1): Blind and sighted users differ in how they interact with the interface. Prior work has shown that SUs and BLVUs differ in their input methods: sighted users primarily use mouse actions, whereas blind screen reader users use keyboard actions [9, 22]. MAP confirms this at L1. The two groups are sepa-rated across all three similarity metrics, especially for Effort and Pattern (Silhouette: Sequence=0.40, Effort=0.70, Pattern=0.77). SUs use point and primary click for 32.9% and 25.1% of their actions, respectively, while BLVUs interact entirely through keypresses and shortcuts. However, SUs are not only mouse users: keypresses still account for 28.0% of their actions, showing that they regularly combine mouse and keyboard input. The similarity metrics further show that BLVUs use more simi-lar recurring action patterns, but vary more in their overall action sequences. Their most common bigrams are keypress →keypress 

(70.9%) and keypress →shortcut (16.3%). SU traces, in contrast, reflect their use of both input methods: their most common bi-grams include keypress →keypress (24.7%) and point →primary click (22.4%). BLVUs therefore have higher within-group Pattern similarity than SUs (93.8 vs. 86.2), but lower Sequence similarity (46.6 vs. 52.9). ## 6.2 How closely do computer use agent workflows align with human workflows? 

Prior work shows that humans and agents can follow similar high-level steps despite differences in how they execute them [59]. A11y-CUA further shows that changing an agent’s access mode substan-tially changes its behavior and performance [22]. We use MAP to connect these findings by examining where agents align with humans across abstraction levels. We compare CUA-D with SUs and CUA-SR with BLVUs, using the corresponding within-human similarity as a baseline. 

Operations (L1): Agents mirror human access modality, but not execution. Prior A11y-CUA analysis showed that neither agent condition fully reproduces the interaction of its corresponding human group. CUA-D uses mouse and keyboard input like SUs but differs in its mix of actions, while CUA-SR uses keyboard input like BLVUs but differs in the specific keys and shortcuts it uses [22]. MAP shows how these differences appear when human and agent traces are represented using the same L1 operations. CUA-D is much less similar to SUs than SUs are to one another: its Pattern similarity with SUs is 42.8, compared with 86.2 within SUs. Although both use mouse and keyboard input, their recurring operation patterns differ. For example, CUA-D uses double primary click more often than SUs (8.8% vs. 4.5%) and does not use drag drop at all (vs. 1.5% for SUs). CUA-SR, in contrast, is much more similar to BLVUs at L1. Its Pattern similarity with BLVUs is 88.7, reaching 95% of the 93.8 sim-ilarity observed between BLVUs themselves. This high similarity reflects their shared reliance on keypress and shortcut opera-tions. However, the specific keyboard inputs still differ: CUA-SR uses 102 distinct keystrokes and shortcuts, compared with 225 for BLVUs. Thus, L1 captures the shared access mode between agents and their corresponding human groups, while differences in their specific execution remain within those operations. 

Functions & Consequences (L2): Screen reader use shows similar increases in actions for agents and humans. Agents make fewer corrections than humans. A11y-CUA found that screen reader use substantially increases agent actions [22]: CUA-SR performs 3.0 × as many actions as CUA-D, closely matching the 2.9 ×

increase from SUs to BLVUs. MAP shows where this increase occurs at L2. For agents, actions with no recorded interface consequence increase from 5.7% for CUA-D to 16.7% for CUA-SR; for humans, they similarly increase from 4.3% for SUs to 21.1% for BLVUs. Thus, much of the additional interaction introduced by screen reader use occurs in actions that do not immediately produce a recorded interface change. A11y-CUA also observed that agents often type long URLs or commands to navigate or complete tasks, whereas humans more of-ten navigate through the interface [22]. MAP makes this difference visible at L2. For CUA-D, type ⟨text area ⟩→ text input ⟨text area ⟩

accounts for 27.1% of its L2 patterns, compared with 10.4% for SUs, showing that the agent spends more of its interaction in un-interrupted typing. When typing is interrupted, 86% of CUA-D interruptions are followed by select and only 2% by navigate ,compared with 44% and 47% for SUs. CUA-SR also almost never produces the mute consequence that BLVUs use to manage screen reader speech (0.02 vs. 3.26 per 100 actions). Thus, similar increases in total actions do not imply similar interaction behavior: humans more often interleave typing with navigation and screen reader management, whereas agents rely more on extended typing and direct selection. This distinction matters when agents are used to simulate users for interface evaluation [26, 45]: matching task com-pletion or action count does not necessarily mean reproducing how humans interact with the interface. 

Methods (L3): Humans and agents converge on Methods de-spite different low-level execution. Prior work finds that hu-mans and agents can complete tasks using similar high-level steps even when their low-level actions differ [59]. MAP confirms this at L3. SU–CUA-D Pattern similarity rises from 42.8 at L1 to 73.5 at L3, reaching 96% of the within-SU similarity (76.8). BLVU–CUA-SR similarity shows the same pattern, reaching 70.7 at L3, or 99% of the within-BLVU similarity (71.4). In other words, by L3, each agent is almost as similar to its corresponding human group as humans within that group are to one another. The L3 labels show where this similarity comes from. For CUA-D and SUs, open accounts for 36.8% and 38.4% of L3 Method instances, respectively, while edit accounts for 18.4% and 17.7%. Methods at similar rates. 

Goals (L4): Agents usually reach the same primary task goals as humans, but omit auxiliary goals. Prior work finds that humans and agents can pursue similar high-level task goals despite differences in lower-level execution [59]. MAP confirms this most clearly for CUA-D. Its Pattern similarity with SUs is 77.5, comparable to the within-SU similarity of 76.8, and 96.7% of CUA-D traces end in the most common final goal observed for humans on the same task. CUA-SR shows weaker alignment: 76.7% of its traces end in the most common human final goal, and it averages 1.17 goals per trace compared with about 1.5 for humans. The L4 labels also reveal a difference that final task goals alone do not capture. Both agents use fewer distinct goals across their traces than humans (45 for CUA-D vs. 86 for SUs; 35 for CUA-SR vs. 88 for BLVUs). In particular, agents often omit auxiliary goals that appear in human traces, such as seeking help or closing extra windows and tabs. Thus, agents often match humans on the primary goal of the task, while differing in the additional goals humans pursue along the way. 

## 7 Discussion 

Our results show that the level at which interaction traces are com-pared matters: users and agents can differ substantially in their low-level actions while converging on similar methods and goals, and similar workflows can still differ in the effort required to carry them out. We discuss how MAP’s linked abstraction levels can support applications that build on these distinctions, how the rep-resentation may generalize beyond computer use, and limitations of the current approach. 

## 7.1 Potential Applications of MAP 

MAP can surface more efficient strategies from interaction traces. Our results suggest that MAP could support systems that help users discover easier ways to complete computer tasks. Prior work has recommended commands and keyboard shortcuts to im-prove efficiency [14, 37, 40, 41, 57]. MAP offers a way to find such alternatives directly from interaction traces by comparing users who complete the same L3 Method but use different lower-level actions. For example, three screen reader users all performed convert 

⟨file ⟩ in ⟨spreadsheet ⟩, but took very different paths. One user pressed F12 to open Save As directly and finished in 42 actions. An-other opened the File menu with Alt+F and then pressed a, taking 70 actions. A third user moved through the menu item by item and took 100 actions, including 43 navigate →focus actions. Because all three users were carrying out the same Method, MAP makes it possible to identify the shorter interaction path and the specific shortcut that enabled it. We see a similar case for export ⟨webpage ⟩

in ⟨browser ⟩: one user opened the print dialog directly with Ctrl+P ,while another reached it by navigating through browser controls. This points to a broader use of semantic interaction traces: in-stead of recommending a shortcut in isolation, a system could first find users performing the same Method, identify which executions require fewer actions, and surface the strategy that produced that difference. Such recommendations would still need to account for context, since a trace alone cannot establish whether a shortcut is available, accessible, or appropriate in another user’s current interface state. Future systems could combine MAP with interface-state information and user preferences to decide when an observed strategy is actually useful to recommend. 

MAP can flag potential usability issues from interaction traces. Our results also suggest that MAP could help identify parts of an interface where users repeatedly encounter difficulty. Prior work has used interaction time, repeated actions, path deviations, and corrective actions as signals of usability problems [6, 19, 27, 48]. MAP adds a way to connect these signals to the part of the task where the difficulty occurs. By comparing the time and number of actions required for the same L3 Method across users, it can flag unusually costly Methods and then use the lower levels to show which interactions contributed to that cost. For example, in an A11y-CUA task that asked users to change a presentation to the Gallery theme, the format ⟨Gallery theme ⟩

Method required unusually many actions for seven of nine blind users and five of nine sighted users (Fig. 4). The interface presents themes in a horizontally scrolling gallery without a direct way to select Gallery by name. At L2, the flagged traces contain many repeated navigate →focus interactions as users move through theme options to reach the desired theme. MAP therefore identifies not only that this Method requires unusually high effort, but also that much of that effort comes from repeatedly navigating through the gallery. More broadly, this could support usability analysis at scale. Rather than inspecting every trace manually, designers could use MAP to find Methods that repeatedly require high effort across users, inspect the lower-level interactions associated with those Methods, and prioritize them for further study or redesign. Future systems could also combine these signals with information about the in-terface itself to distinguish difficulty caused by the interface from differences in user strategy, and to suggest possible changes such as adding direct selection, shortcuts, or more accessible navigation. These flags should be treated as candidates rather than automatic diagnoses: unusual time or action counts can indicate a usability problem, but still require inspection or follow-up testing to under-stand why it occurred. 

MAP may help reduce identifiable information when shar-ing interaction traces. Interaction traces are useful for studying computer use, but they can also reveal who produced them. Prior work shows that keyboard, mouse, and GUI behavior can identify individual users and distinguish humans from agents [7, 39, 54]. Our results suggest that the level at which a trace is represented may affect how much of this identifying behavior remains. We test this by predicting which of 18 trace sources produced a trace using the features available at each MAP level, including label frequencies, action and time allocation, and similarity scores. Under leave-one-task-out evaluation, top-1 classification accuracy is 25.4% at L1 and rises to 43.3% at L2, showing that adding semantic information can initially make users more distinguishable. ## 7.2 Generalizing Semantic Trace Abstraction Beyond Computer Use 

MAP is designed for desktop GUI interaction, and its current vo-cabulary reflects that scope. For example, labels such as keypress ,

navigate , and open describe actions and outcomes that occur when people use desktop applications. Extending MAP to a different inter-action setting would therefore require new labels. What may gen-eralize is not the vocabulary itself, but the idea of linking multiple levels that describe how an action is performed , what it accomplishes ,

which method it contributes to , and which larger goal that method serves .This distinction becomes clearer for interfaces outside desktop computer use. In virtual reality, L1 might include controller move-ments, gaze, or gestures; L2 could describe effects such as selecting, grabbing, or moving a virtual object; L3 could represent meth-ods such as placing or assembling objects; and L4 could capture the larger task goal. In robotics demonstrations, L1 could contain low-level robot motions, L2 their effects on objects, L3 manipula-tion methods such as grasping or placing, and L4 the task being completed [61]. These domains would need different labels from MAP, but could retain the same links between execution, outcome, method, and goal. Programming and CAD are closer to our current setting because they are often performed through desktop interfaces, but their domain-specific behavior is not fully represented by our current vocabulary. A programming extension, for example, may need to dis-tinguish methods such as debugging, refactoring, and testing rather than treating them only as generic editing or navigation. ## 7.3 Limitations 

MAP relies on information that is available across the interaction logs we study: keyboard and mouse actions and the available inter-face context around those actions [22, 63, 65]. It does not require signals that are only available in some datasets, such as screen reader speech, screenshots aligned to every action, or accessibility-tree state. This allows the same pipeline to be applied across dif-ferent logging setups, but it also limits what MAP can infer. For example, a keypress may move screen reader focus even when that change is not recorded in the trace. Additional signals could help resolve such cases, and future work could test how much Conference acronym ’XX, June 03–05, 2018, Woodstock, NY Ananya Gubbi Mohanbabu, Rosiana Natalie, Anhong Guo, and Amy Pavel 

screenshots, accessibility-tree information, or screen reader output improve annotation accuracy. L3 introduces another source of ambiguity because MAP must decide both where one Method ends and another begins and which Method those actions represent . For example, when a user opens the Save As dialog and then changes a file’s format, the action that opens Save As could be grouped with the preceding open Method or with the following convert Method. Moving this boundary changes which actions are grouped together and can therefore change the assigned Method. Specific Entities and L4 Goals are also open vo-cabulary: for example, two traces may describe the same goal using slightly different wording that must be mapped to the same concept. We canonicalize these labels, but some interactions can still reason-ably be divided or described in more than one way. Our manual agreement results therefore show how consistently MAP follows our annotation scheme, while recognizing that another reasonable annotation may sometimes differ. The L3 Method and UI Container vocabularies were developed from A11y-CUA and then evaluated on A11y-CUA, AgentSynth, and AgentNet. They cover nearly all interactions in these datasets, but those datasets represent only a subset of computer use. Other workflows may introduce behavior that our current labels do not distinguish well. For example, creative work may involve repeated experimentation without a clear sequence of Methods, recovery may alternate between diagnosing and fixing a problem, and users may interleave several goals rather than completing one before starting another. Applying MAP to these settings may therefore require adding or refining labels while keeping the same linked levels. Finally, our similarity metrics capture three aspects of work-flow behavior: the order of semantic labels, recurring patterns, and the effort spent at each level. They do not capture every mean-ingful difference between workflows. Prior work also compares loops, skipped steps, alternative paths [47], and how far a workflow progresses before failure [12]. Future work could extend MAP to represent errors and recovery, transitions between applications, task success, and consistency across repeated attempts. 

## 8 Conclusion 

We presented MAP, a hierarchical taxonomy for representing in-teraction traces across four levels of abstraction from input-level operations to high-level goals. MAP uses an automated annotation pipeline to assign MAP labels. The pipeline achieves strong agree-ment with human annotations and we demonstrate this on three datasets that record computer use interaction traces of humans and agents. MAP also provides three similarity metrics (sequence, pattern, and effort) that can be computed at any level or combined across abstraction levels. We compared how sighted users, blind users, and computer use agents complete tasks using the A11y-CUA dataset. We show that MAP replicates prior findings at lower ab-straction levels while surfacing new findings at intermediate and higher abstraction levels. We demonstrated MAP’s use cases in im-proving novice users’ expertise in computer use tasks by deriving efficient strategies from expert users, identifying potential usability issues in GUIs, and identifying users’ behavioral fingerprints in computer use. Together, MAP’s hierarchical taxonomy and similar-ity metrics provide a unified framework for researchers analyzing and comparing interaction traces across multiple levels.

## A MAP Prompts A.1 L2 Functions & Consequences 

Infer L2 labels for each action in the UI interaction trace. L2 structure: Function, Direct UI Target → Consequence, Indirect UI Target. Function shows what the operation did (already determined for each action in the input). Direct UI Target is the element on which the action occurs. Choose the most specific directly interacted-with element supported by the trace. For example, use cell rather than table and list item rather than list for Direct UI Target. Consequence is the direct result of the action. Indirect UI Target is the affected UI object on which change is observed because of the consequence of the action. Examples: a "select" Function on a "list item" (Direct UI Target) representing a file, where the action opens that file, gives the Consequence "open" on Indirect UI Target "file". A "drag" Function on "list item" (Direct UI Target) representing a file, dropped into a folder, gives the Consequence "move" and Indirect UI Target "folder". Instructions for determining the L2 output for each operation: 

• The direct and indirect target may be the same or dif-ferent. For direct target, choose the specific UI element on which action occurs and not its container (indirect UI target). 

• For point actions, infer the direct and indirect UI target from the destination, using the following action only when needed. For keyboard actions, use the focused element as the Direct UI Target. 

• Use the given Function, lower-level labels, and raw action details (event, keys, application, window_title, target, focused_element, and nearby actions) to infer the remaining labels. 

• For each action, output only index, direct_ui_target, consequence, indirect_ui_target, rationale, confidence (0–1), and a short plain-language description. 

• Output a JSON array with exactly actionCount en-tries, one per action, sorted by index. Do not merge or omit actions.

## A.3 L4 Goals 

Infer L4 semantic labels for actions in the UI interaction trace. Goal is a short, task-level phrase that names the user’s objec-tive achieved by a group of L3 methods, describing the out-come of the high-level goals. A goal must normally contain multiple L3 steps rather than restating a single L3 Method. Instructions for determining the L4 output for each operation: 

• Use the lower-level labels and lower-level action de-tails (event, keys, application, window_title, target, focused_element, and nearby actions) for grounding. 

• Group contiguous L3 steps that jointly serve the same objective. 

• Every L3 step must belong to exactly one Goal; groups cannot overlap or skip intervening steps.

## B.2 UI Targets (L2) 

Label Definition 

button A clickable UI control (e.g. toolbar button) that triggers an action when selected.

column A vertical series of cells in a table.

scrollbar A draggable control that moves the viewport through content that extends beyond the visible area. 

webpage A page’s general content or background, e.g. clicking whitespace.

image A static photo, illustration, or graphic viewed or placed as content, e.g. a thumbnail or inserted picture. 

video A dynamic visual media element that can be played, paused, or scrubbed. 

audio † A media element containing only sound content. 

canvas An editable workspace where visual content is drawn or manipulated, e.g. a chart canvas or drawing tool’s working area. 

desktop The main system workspace containing windows, icons, and other items. 

list A grouped collection of related items or options.

caret Active cursor position where text insertion happens. 

command A text or voice instruction issued to execute an action, e.g. via a command line.

unknown None of the other direct UI target options clearly fit this action. 

file A UI item containing data, content, or executable information. 

context menu A menu opened for a specific item or location, usually by right-clicking, containing actions for that context; unlike a regular menu, it is tied to the item or location where it was opened. 

dialog box A temporary modal that appears over the current interface to request input, confirm an action, or display a message before the user can continue. 

item card A bounded card element displaying details for a single item in a collection, feed, or grid layout. 

folder A container used to organize files and subfolders. 

application A desktop application excluding the browser. 

none No UI object was affected, because the action produced no change in the interface; applies whenever the Consequence is none, mute, or announce. Distinct from unknown, which means an object was affected but could not be identified.
