# ABSTRACT 

Large language model (LLM) agents increasingly use persistent memory to per-sonalize responses, and personal attributes in this memory pose a privacy risk if exposed. We ask how consulting memory during dialogue changes what users go on to say, and thus what the memory comes to reveal. In multi-session simula-tions, a simulated user with 24 personal attributes talks with a support agent that does or does not consult memory, and in both settings attributes are inferred from the full accumulated record. Across four support models, memory raises response quality but also empirical leakage, the share of attribute values correctly inferred from the record, by a margin that widens over sessions. The cause is a loop in ordinary, non-adversarial assistance. Memory-conditioned responses carry earlier values forward, often as presuppositions, and users affirm them or leave them un-corrected, so that cues and the agent’s own guesses become recorded values. The loop reinforces itself, and removing the agent’s mentions of an attribute lowers its later disclosure about twice as much as single-turn effects predict. Users cannot leave it on their own, since correcting a value discloses the attribute, declining to discuss it shifts later predictions toward sensitive values, and incorrect values left in place become entrenched. The loop is best weakened at the agent’s response. Instructing the agent not to state or presuppose attributes brings leakage to about the no-memory level while keeping most of the quality gains, whereas filtering or anonymizing what users say or what is stored gives up much of them. 

# 1 INTRODUCTION 

Commercially deployed LLM agents increasingly maintain persistent memory across sessions. 1 We use “agent” for an LLM-based system that keeps and consults such memory. Memory lets an agent condition its responses on earlier conversations, so users need not restate their specifics (Xu et al., 2022; Maharana et al., 2024; Tan et al., 2025). It also accumulates information about the person behind the account (Zhong et al., 2024; Jiang et al., 2025; Prottasha et al., 2025). An agent can infer personal attributes such as age and sex from this information (Jiang et al., 2025; Wang et al., 2026), even when they are never stated directly (Staab et al., 2024). Such inferences can be exposed through the agent’s interactions with external services or accessed without authorization (Zhang & Pei, 2026; Lyu et al., 2026; Dong et al., 2025). The agent also conditions its later responses on this memory. These responses may reflect what the agent has inferred about the user, and the user’s replies may confirm, correct, or refine it (Figure 1). This loop arises in the standard operation of a personalized agent, without any adversarial intent. It matters whether or not the values it carries are correct, since correct values add to what the record reveals and incorrect ones stay in the record, because users cannot correct them without disclosing the attribute. Existing work largely treats the record as given, asking what can be recovered from it (Jiang et al., 2025; Wang et al., 2026; 2025a) or how agents handle information they already hold (Mireshghal-

The tension between personalization and privacy has been discussed as a design concern (Kirk et al., 2024) and through users’ perceptions of memory (Zhang et al., 2025). How an ordinary agent’s use of memory changes what users go on to say, and thus what the record comes to contain, remains open. We study this question in multi-session simulations. An LLM plays a user whose attributes are drawn from U.S. Census microdata and converses with a support agent that does or does not see its memory during dialogue. Both settings summarize every session into the same kind of record, and inference always reads the full record, so the comparison isolates the effect of dialogue-time memory access on what the record contains. We make three contributions. First, consulting memory during dialogue raises both response quality and what can be inferred about users, by a margin that grows with sessions, and even idealized filtering of what users say lowers leakage only by giving up that quality (Section 3.2). Second, the gap comes from a loop in which the agent carries earlier values forward, often as presuppositions, and users affirm them or let them pass (Section 3.3). The loop reinforces itself, entrenches incorrect values, and cannot be left by users on their own (Section 3.4). Third, a short instruction that keeps the agent from stating or presupposing attributes brings leakage to about the no-memory level at little cost to quality, whereas anonymizing user turns or memory does not (Section 3.5). 

# 2 MEASURING ATTRIBUTE INFERENCE UNDER PERSISTENT MEMORY 

2.1 PROBLEM SETTING 

We simulate repeated interactions between a profile-conditioned user agent and a support agent, fol-lowing prior uses of LLM agents in social simulation (Park et al., 2023; Zhou et al., 2024; Hashimoto et al., 2026), multi-turn evaluation of user–LLM interactions (Hida et al., 2026), privacy evalua-tion (Shao et al., 2024), and persona-conditioned text generation (Yukhymenko et al., 2024). The support agent is the assistant the user talks to, and we call its underlying LLM the support model. The support model also writes the session summaries and performs attribute inference. A run con-sists of S sessions under one of three user-response conditions, in which user turns are unfiltered or pass through one of two filters (Section 2.5). Each session starts with a fresh support-agent context, which receives earlier summaries only in the memory setting. The user agent makes a request and ends the session when it considers the request resolved, within at most T turns. After each ses-sion, the support model writes a free-text summary of the transcript, which is appended to memory. Attributes are inferred after every fifth session, and we call these sessions checkpoints. Response quality is evaluated in sessions 40 , 45 , . . . , 80 . Inference and evaluation outputs are never added to memory, and all prompts are given in Appendix N. 22.2 THREAT MODEL 

We are concerned with what the accumulated record reveals about the user. Once a record exists, it can be exposed through the agent’s interactions with external services or accessed without authoriza-tion. We therefore measure privacy loss as empirical leakage, the share of the user’s attribute values that can be correctly inferred from the full record (Section 2.6). We model the party that learns about the user as one that obtains the accumulated record and applies an LLM to it, with no auxiliary data about the user. We instantiate this party with the support model itself, so leakage measures what the agent’s own record already exposes. Appendix I repeats inference with stronger models from other developers. The agent itself is not adversarial, since its instruction neither encourages nor discour-ages inferring or eliciting attributes (Appendix N.7). The same 24 attributes A (Section 2.3) define each simulated user and are what the filters, the disclosure measurements, and inference all refer to. 2.3 PERSONAL ATTRIBUTES OF SIMULATED USERS 

Each simulated user is defined by its values of the 24 attributes in A, taken from one respondent of the 2024 American Community Survey Public Use Microdata Sample, which the U.S. Census Bureau releases with statistical disclosure limitations (Appendix A.1). The first eight, adapted from Staab et al. (2024), are age, sex, location, place of birth, income, education, occupation, and mar-ital status, the last replacing their relationship status. Sex is recorded as binary in the survey and is not a measure of gender identity. The 16 attributes we add are employment status, citizenship, seven household attributes (own children, size, type, income, tenure, housing type, and vehicles), five attributes close to sensitive categories (race, Hispanic origin, disability, health insurance cover-age, and military service), school enrollment, and internet access. Such categories can contribute to re-identification when combined with auxiliary data (Sweeney, 2002; Golle, 2006). Each attribute is categorical, with 2 to over 200 candidate values (Appendix A), so absolute accuracy is not com-parable across attributes, and we interpret results through comparisons between conditions. 2.4 USER SIMULATION 

Profiles are drawn in proportion to the survey’s person weights and then selected so that rare values are covered (Appendix B). The user agent receives its own attributes, those of co-resident household members, and the user summary, a summary of its own earlier statements (Appendix N.3, Ap-pendix N.6). Before any dialogue, an LLM writes one request per session for each profile, and the same request sequence is used in all conditions, so that conditions differ only in how each conver-sation unfolds. Requests that would change a fixed attribute value, such as a move, are regenerated (Appendix N.1, Appendix N.2). Under the direct filter, the user agent is also instructed not to state or confirm any attribute value, and under the strict filter, also to leave out any detail that would narrow one down (Appendix N.4). A turn is one user message together with the support agent’s response. 2.5 MEMORY AND USER -T URN FILTERING 

After each session s, the summary σ(τs) of its transcript τs is appended to earlier ones without rewriting them, ms = ms−1 ⊕ σ(τs), following the session-level approach of MemoryBank (Zhong et al., 2024) (Appendix N.8). In the memory setting, the support agent generates session s con-ditioned on ms−1, given as “information about the user from previous conversations”, and in the no-memory setting it receives nothing. A no-memory run still accumulates its own record, and at each checkpoint both settings are inferred from their own record. They thus have the same access to their history, which differs only because memory changes the conversations. Crossing the two settings with the three user-response conditions gives six conditions. Filtering uses two LLM judges that classify a user turn against A (Appendix N.9, Appendix N.10). For each attribute, the direct judge decides whether the turn states or confirms the user’s value. The inferable judge, which also receives the ground-truth profile, decides whether the turn together with the preceding dialogue narrows the value down, that is, makes some values substantially more likely than others. We say that a turn discloses an attribute at the value level if the direct judge flags it, which includes statements coarser than the attribute’s categories, and as a cue if only the inferable judge does. The same judges are applied after the fact to measure disclosure, whereas empirical leakage comes only from attribute inference. 3Under either filter, the judges check each user turn as a candidate before the support agent sees it. The direct filter rejects it if it discloses any attribute at the value level, and the strict filter if it discloses any attribute at all. A rejected candidate is discarded without a trace, and a new one is sampled without adding it to the dialogue context (Appendix N.5). Each filter thus combines the instruction of Section 2.4 with rejection. Because they reject whole turns and the strict filter uses the ground-truth profile, both are stricter than deployable filters. We use them to test whether even such filtering can lower leakage without giving up the quality gains of memory. 2.6 MEASURING LEAKAGE AND RESPONSE QUALITY 

At each checkpoint s ∈ E = {5, 10 , . . . , 80 }, the support model receives the full record of its run and infers all 24 attributes at once (Appendix N.11). We use N = 300 profiles, S = 80 sessions, and at most T = 10 turns per session (Appendix B). Claude Sonnet 5, from a different developer than the support models, plays the user agent, generates the requests and user summaries, and serves as the two judges and the evaluator. The judges and the evaluator are validated against human annotation (Appendix D). Besides comparing the six conditions, we separate consulting memory from elapsed sessions by branching. We continue each unfiltered memory run from branch points b ∈ { 10 , 20 , . . . , 70 } for ten sessions in two arms that do or do not consult memory, from the same history and with the same requests, and count the attributes predicted correctly for the first time after b (Appendix G).

3.3 HOW THE LOOP WORKS 

To find what in the conversations produces the gap, we follow the loop of Figure 1, which we first make precise. For an attribute, a mention is part of a support-agent response that states a value for the user (a reference), asks the user to confirm one (a confirmation question), or tailors its content in a way appropriate only for some values (a presupposition). An open question about the attribute is not a mention. The loop consists of three links . A value or cue in memory leads to a mention in a later session (memory → response). The user reacts by affirming the value, correcting it, declining to discuss it, or leaving it uncorrected (response → user). The summary of that session records the reaction (user → memory). Each link can be explicit, as when a value is stated or affirmed, or implicit, as when only a cue is recorded, a value is presupposed, or a mention is left uncorrected. An annotator model , Mistral Small 4, which generates none of the analyzed text, labels each mention and where its value came from, the user’s reaction, whether a disclosure gives the value or only a cue, and what each summary records (Appendix K). Session 1, in which memory is still empty, serves as a placebo. We also replay single memory-conditioned responses after regenerating them without memory or after an editing model , also Mistral Small 4, removes their mentions, and sample the next user turn for each version (Appendix K.4). Human annotators confirm both the labels and the edits (Appendix D.4). 

Memory changes disclosure only after the agent responds. In session 1 and in the opening turn of later sessions, the two settings disclose at the same rate, and the difference appears only in later turns (Table 1). 

Memory-conditioned responses carry values forward. More than a third of memory-conditioned responses carry forward a value from an earlier session, most of them correct. Re-sponses without memory instead ask more open questions and more often rest on assumptions with no basis in anything the agent could see. 

Users mostly affirm, and what they affirm reaches the value level. The additional disclosures are mostly affirmations of a presupposed value and almost entirely at the value level, and over whole runs more user turns state or narrow down an attribute (Table 10). Memory thus mainly raises attributes already hinted at as a range or a cue to the value level, consistent with the branching results. Replaying single responses points the same way. Removing only the mentions from a memory-conditioned response removes most of its effect on the next user turn, while keeping most of the coherence advantage and leaving helpfulness unchanged (Table 16, Appendix K.4). 

The loop also closes through implicit links. Every link occurs in both explicit and implicit forms (Table 17). To test whether each pass of the loop makes the next more likely, we continue the unfiltered and direct-filter memory runs from b = 40 for ten sessions while the editing model edits every response. For one random group of attributes it removes all mentions (all removed), for another only references and confirmation questions (explicit removed), and a third group is left untouched. We count the first turn in the run that discloses each attribute at the value level, or, under the direct filter, which removes such turns, the first that gives a cue to it. If a mention only prompted the next user turn, removing it would cost exactly that turn’s disclosures, which we measure by replay. A larger reduction means that the mention also made later mentions, and thus later disclosures, more likely. We call the loop self-reinforcing for a group if the reduction in its first disclosures, relative to the untouched group, exceeds this single-turn prediction (Appendix L). 

The loop is self-reinforcing. Removing the agent’s mentions of an attribute lowers its later disclo-sure by about twice what single-turn effects predict (Table 2). This holds with and without filtering, and fewer of these attributes are newly inferred. Removing only references and confirmation ques-tions also exceeds its prediction, even under the direct filter, where no link of the loop is then explicit, and the excess grows over the ten sessions (Table 19). 

The loop also entrenches errors. An incorrect value carried forward from an earlier session is often left uncorrected, recorded, and predicted again at the next checkpoint (Table 21). Under the direct filter, where correcting it would state the attribute, users rarely correct it. 

Refusing does not avoid the loop. Under the direct filter, users decline to discuss a mentioned attribute more often when its true value is in a set fixed before labeling, such as lacking health insurance or citizenship (Table 22). A refused incorrect value is also recorded and predicted again about as often as one left uncorrected (Table 21). A refusal thus tends either to reveal a sensitive value or to attribute one to users who do not hold it. 3.5 WHERE TO INTERVENE 

We compare mitigations that intervene at three points in the loop. The adversarial anonymization of Staab et al. (2025), with A as targets, is applied either to each user turn (user-side anonymization) or to each summary before it is stored (write-time anonymization). Alternatively, the support agent’s instruction is extended so that it does not state, presuppose, or ask to confirm the user’s attributes unless the user raises them (response-side instruction). Each is added to the unfiltered memory setting for the two open-weight support models on all profiles, and we also record the share of responses with mentions (Appendix M). The two filters serve as idealized bounds, whereas the instruction is a change a provider can deploy directly. 

The response is the cheapest place to intervene. Only the response-side instruction lowers leak-age without giving up most of the quality gains (Table 3). It cuts mentions below even the no-memory level and brings leakage to about the no-memory level, as the idealized direct filter does. Helpfulness is unchanged, and most of the coherence gain remains. The other conditions lower leakage only by giving up quality. User-side anonymization lowers leakage almost as much as the strict filter and, like it, gives up nearly all of the gain in coherence. Write-time anonymization keeps most of the gain in helpfulness but loses most of the gain in coherence, since what is removed from the record can no longer be carried forward. This ordering holds for both support models (Table 24), and the instruction works similarly with another user model, other memory formats (Appendix F), and stronger inference models (Appendix I). 

# 4 RELATED WORK 

Attribute inference and persistent memory. LLMs infer personal attributes from text (Staab et al., 2024; Yukhymenko et al., 2024), and evaluations measure what given histories and streams reveal (Jiang et al., 2025; Wang et al., 2026; Cögendez et al., 2026). Persistent memory is common in deployed assistants, and research systems such as MemoryBank (Zhong et al., 2024) carry session-level summaries forward, as does later work on user profiles (Prottasha et al., 2025). These studies analyze given records, whereas we intervene on dialogue-time memory access. That disclosure elicits disclosure was documented long before LLMs, between people (Jourard, 1971; Collins & Miller, 1994; Altman & Taylor, 1973) and with computers and chatbots (Moon, 2000; Lee et al., 2020), alongside the tension between personalization and privacy (Awad & Krishnan, 2006). In that work, disclosure is elicited by the system’s own disclosure or requests, whereas here it arises as the agent carries the user’s earlier disclosures and its own guesses forward, often by presupposing them. 8Agent privacy and memory attacks. Privacy risks of language models were first studied mainly for training data, through membership inference and extraction (Shokri et al., 2017; Carlini et al., 2021; Kaneko et al., 2025). Other work asks whether agents handle available personal information appropriately (Mireshghallah et al., 2024; 2026; Shao et al., 2024; Wang et al., 2025b) or attacks memory by extraction (Wang et al., 2025a; Lyu et al., 2026), exfiltration (Zhang & Pei, 2026), or injection (Dong et al., 2025) (see Lin et al. (2026) for a survey), and the information an adversary can extract per query has been bounded theoretically (Kaneko & Baldwin, 2025). These studies take the information as given, whereas we study how it comes to be there. On the defensive side, Staab et al. (2025) anonymize text by rewriting what makes an attribute inferable, and we apply their approach to user turns and to memory and compare it with filtering and with changing the agent’s responses. 

# 5 CONCLUSION 

Consulting memory during dialogue changes what users say, and with it what their record reveals. Across four support models, memory raised leakage together with response quality, through a loop in which the agent carries values forward and users affirm them or let them pass. The loop rein-forces itself, entrenches incorrect values, and is not escaped by refusing, so weakening it falls to the provider. The most effective place to do so is where the loop starts, at the agent’s response. A human pilot points in the same direction, although whether its rates hold across many users remains to be measured. 

# ETHICS STATEMENT 

The main experiment uses no data about real individuals, since profiles come from the disclosure-limited ACS PUMS and all dialogues are generated by LLM agents. The eight annotators of Ap-pendix D were paid $25 per hour, informed of the purpose of the task and of how their annotations would be used, and consented before beginning. In the main annotation tasks, they saw only gen-erated dialogues and profiles built from Census records. The eight participants of the human pilot (Appendix J), none of whom served as annotators, were paid $25 per hour and consented to take part, including to the analysis of their conversation logs by the research team. Three of the annota-tors read these logs, two to label mentions and reactions and one to adjudicate disagreements, and no participant-level attribute values or conversation content are reported. Both the annotation study and the pilot were reviewed and approved by our institution. We do not propose an attack. The support agent receives a neutral instruction and default settings, and inference uses only memory that such an agent already holds. Our aim is to inform the design of memory and of how agents draw on it in their responses.

Retrieval-based memory. Memory stores the session summaries of Appendix N.8, one document per session, embedded with bge-m3. At every user turn, the five summaries most similar to that turn by cosine similarity are retrieved with FAISS (Douze et al., 2024), ordered by session, and given to the support agent in the memory block. The current session is not yet stored and cannot be retrieved. At each checkpoint, inference reads all summaries, so the record is the same kind as in the main experiment, and the formats differ only in which summaries the agent sees during dialogue. 

Conditions and reuse. Each format is run under memory, no memory, and the response-side instruction of Appendix N.18, all without filtering. Results. Memory raises leakage over no memory in all three formats and both models, together with helpfulness and coherence (Table 6). The gap is smallest with retrieval, where the agent sees only the summaries most similar to the current turn. Consulting less of the history during dialogue thus gives a smaller gap, although inference reads the same record as in the append-only format. Update-based memory gives a gap close to that of the append-only format, although Mem0 con-solidates, overwrites, and deletes what it stores. In every format, the response-side instruction cuts mentions to or below the no-memory share, below it with append-only memory as with Claude Son-net 5 on the user side, and brings leakage to about the no-memory level. With Mistral Small 4 on the user side, it lowers helpfulness and coherence slightly in every format, unlike with Claude Sonnet 5 (Table 3), but keeps most of the quality gain of memory.

# K ANNOTATION OF RESPONSES , R EACTIONS , AND RECORDS 

This appendix supports Section 3.3, and its definitions are also used in Appendix L. K.1 SCOPE AND INPUTS 

The annotator model and the editing model are Mistral Small 4 (model ID in Appendix E), which generated none of the annotated text. There are two annotations. 

Turn-level annotation. It covers the unfiltered runs of all four support models and all profiles, in sessions 40 , 45 , . . . , 80 and in session 1, which serves as a placebo because the memory is then empty and the memory block is omitted, so both settings receive identical inputs. For each support-agent response, it labels the mentions of each attribute and their source. For each disclosure flagged by the judges, it labels the trigger and specificity (Appendix N.13). Which attributes are disclosed is determined by the judges, as in Table 10, not by the annotator. Each call receives the ground-truth profile, the current-session dialogue up to and including the annotated message, and the user summary through the preceding session. 

Session-level annotation. It covers every session of the unfiltered and direct-filter memory runs for 100 profiles per support model, drawn at random from the 300, and sessions 40 , 45 , . . . , 80 of the corresponding no-memory runs. It is also applied to the unfiltered runs of Appendix E, and to its direct-filter memory runs for the refusal analysis. For these runs, whose user agent is Mistral Small 4, the annotator is Claude Sonnet 5. Each call receives the transcript of one session, its support-agent summary, the ground-truth profile, the user summary through the preceding session, and the support-agent memory through the preceding session, and returns labeled mentions, reactions, and records per attribute (Appendix N.14). User-turn forms reuse the judge outputs and specificity labels of the turn-level annotation, giving a value if flagged with value specificity and a cue only otherwise. 23 K.2 DEFINITIONS 

Mentions. An explicit reference states a value of the attribute for the user. A presupposition does not state a value but tailors the response in a way that is appropriate only for some values. Aconfirmation question asks the user to confirm a specific value. An open question asks about the attribute without proposing one and is not a mention. References and presuppositions are marked correct or incorrect against the profile. 

Sources. The source of a mention is the current session if the value is stated or implied earlier in the current session, an earlier session if it appears only in what was said or recorded in earlier sessions, and neither otherwise. In no-memory runs, where the agent has no access to earlier sessions, a value that appears only there is counted as neither, so the earlier-session source is zero by construction. The turn-level annotation does not receive the support-agent memory, so there an earlier session covers only what the user said. The session-level annotation distinguishes earlier_user and 

earlier_record , the value appearing only in what the user said or only in what the support agent recorded in earlier sessions, and together they make up the earlier-session source. 

Specificity and first value-level disclosures. Specificity is the value itself, a range, or a cue only, and is labeled by the annotator independently of the judges. A range stated outright can be flagged by the direct judge, which counts statements coarser than the attribute’s categories, and still be labeled a range, which is why direct-flagged attribute–turn pairs slightly outnumber value-level disclosures (Appendix K.3). An attribute is disclosed at the value level for the first time in a turn if it is flagged there with value specificity and has no earlier value-level disclosure among the accepted user turns of the run. It was hinted earlier if it had been disclosed earlier as a range or a cue, and not hinted earlier otherwise. 

Triggers. The trigger of a flagged disclosure is assigned in two steps. First, the response anno-tations determine whether the preceding support-agent response contains a mention of the same attribute, and otherwise whether it contains an open question about it. If it contains a mention, the annotator judges only whether the user turn affirms or elaborates the proposed value or replaces it, and the disclosure is then an affirmation or a correction. If it contains only an open question, the disclosure is an answer to a question, and otherwise it is unsolicited. 

Reactions. A reaction is labeled for each user turn that follows a response mentioning an attribute. It is an affirmation if the user states or confirms the proposed value, a correction if the user replaces it, a refusal if the user declines to discuss the attribute or asks the assistant not to assume or use it, without stating, confirming, or replacing the value, and no correction otherwise. A turn that declines to discuss an attribute but also states, confirms, or replaces its value is labeled by that content. 

Records. For each summary and attribute, the record is a value if the summary states a value for the user, a cue if it narrows down the value without stating it, and nothing otherwise. Its source is a user statement if a user turn of the session states the value, a user cue if a user turn only narrows it down, a user refusal if the record reflects only that the user declined to discuss the attribute, and an uncorrected agent value if the value appears only in a support-agent response and no later user turn in the session contradicts it. A refusal does not count as contradicting it. Recorded values are marked correct or incorrect against the profile. 

Cycles. A cycle on attribute a is one pass through the loop, matched from three events in order, namely a record of a in the summary of session s, a response in a later session s′ that mentions a

with an earlier session as its only source, and a record of a in the summary of s′ whose source is the reaction to that response. Each response opens at most one cycle per attribute, matched to the most recent record of a. The form of a cycle is the combination of the source of the first record and the reaction. K.4 RESPONSE REPLAY AND REFERENCE REMOVAL 

We sample support-agent responses from unfiltered memory sessions 40 , 45 , . . . , 80 that are fol-lowed by a user turn, stratified by whether the response contains a mention, with nref per support model that contain one and nnoref that do not. For every sampled response, we construct the original and a regeneration from the same within-session context without the memory block. For responses with a mention, we also construct a version in which the editing model removes every mention and leaves the rest unchanged, and for responses without one, the removal version equals the original. In the reverse direction, we sample nrev no-memory responses and regenerate each with the mem-ory block filled by the run’s own record ms−1. For each version, we sample the next user turn L

times from the user agent with its original inputs and apply both judges, and the evaluator rates the response itself for helpfulness and coherence. We use nref = 400 , nnoref = 100 , nrev = 200 , and 

L = 3 . Of memory responses in sessions 40 , 45 , . . . , 80 , 54% contain at least one mention. This share, estimated from the full annotation, is used to reweight the two strata. The next user turn is generated by Claude Sonnet 5 with the prompt, profile, request, user summary, and dialogue context of the original turn, and both judges are applied to each sample with the inputs used for Table 10. The evaluator rates each response version with the prompts of Appendix N.12 and the same inputs as for the original response. Intervals for the reweighted estimates resample profiles within each stratum and treat the share as fixed. For memory responses with a mention, regenerating without memory lowers both helpfulness and coherence, whereas removing only the mentions leaves help-fulness unchanged, with an interval that includes zero, and lowers coherence by less than half as much as regenerating without memory. 

Reference removal. The editing model (Appendix N.16) receives the response and its annotated mentions, and deletes or neutralizes them while keeping all other content. An edit is accepted if the response annotation (Appendix N.15) finds no remaining instance and the content check (Ap-pendix N.17) returns that content is kept and none is added. Otherwise it is regenerated, up to 3 times. Edited responses are 87% of the original length on average.

N.5 RESAMPLING PROCEDURE
