Abstract 

Agents can create rich representations, yet these representations are rarely used as a medium for expressing user intent. We present 

Agent-Bound UI , an interaction model that sep-arates reusable interaction structures from task-specific meanings. Agents bind task-specific meanings to interactions in reusable views and publish the resulting bindings as shared state, enabling humans and agents to understand and act on shared surfaces whose meanings vary across tasks. We implement ABRA, a framework-agnostic prototype of Agent-Bound UI, in which users and agents collaborate through chat and shared interactive canvases. We demonstrate ABRA through a representa-tive use case and evaluate four LLM-backed agents on canvas authoring, owner-side con-sequence resolution, and cross-agent invoca-tion. The code and demo video are available at 

https://github.com/megagonlabs/abra .

1 Introduction 

Agentic AI is increasingly used to assist users with a wide range of tasks (Wang et al., 2024b), from everyday activities such as drafting emails and plan-ning trips to professional work including cleaning datasets (Chen et al., 2026b), curating knowledge graphs (Pan et al., 2024), and writing code (Liu et al., 2026). Unlike conventional conversational assistants that primarily answer questions, modern agents are connected to external tools and services to actively carry out these tasks, often across multi-ple coordinating agents. In this setting, chat serves as the primary medium through which humans and agents collaborate. Users specify task goals, review and revise plans, inspect intermediate results, and provide feedback throughout the task lifecycle. Meanwhile, the way agents present their work to users has steadily evolved. Early agents responded in plain text (OpenAI et al., 2024), markdown has since become the standard (Chen et al., 2025), and more recently interactive HTML-based representa-tions (e.g., artifacts, canvases, and inline widgets) have begun gaining traction (Shihipar, 2026). For example, an agent may present a plan as a flowchart or a set of results as a table rather than as text. Yet while representations from agents to humans have become increasingly rich, the human-to-agent channel remains largely unchanged, with chat con-tinuing to serve as the dominant interface for user input. This creates a representation–interaction asymmetry : the output side is increasingly struc-tured and multimodal, whereas the input side re-mains constrained to natural language. This asymmetry, however, reveals an opportu-nity: rich representations are already rendered on the user’s screen. We therefore ask whether these arXiv:2610.30780v1 [cs.HC] 22 Oct 2026 representations can themselves be made directly manipulable (Shneiderman, 1981). Rather than introducing a separate input modality, the same sur-face the agent renders becomes one the user acts on, grounding interaction in the very objects the agent produced. The agent can then interpret these interactions as expressions of user intent grounded in task representations, incorporating them into its reasoning. The effectiveness of chat and direct manipulation depends on the verbalizability of user intent . When intent can be readily expressed in language, chat is concise and effective. However, when intent is difficult to verbalize or closely tied to a rendered representation, text-only interaction can become inefficient or ambiguous (Shen et al., 2026). Recent approaches that make agent-rendered rep-resentations interactive can be broadly grouped into three categories. Generative approaches (Chen et al., 2026a) synthesize interfaces for individ-ual tasks, enabling long-tail scenarios that require novel interaction surfaces, but limiting reuse across tasks. Composable ones (Google, 2026a) assem-ble interfaces from reusable widgets and controls, making them effective for routine interactions, but providing limited support for rich, task-specific manipulation over representations. Task-specific systems (Kim et al., 2025; Shao et al., 2026; Feng et al., 2026) provide richer interaction surfaces tai-lored to particular workflows, but their interactions remain coupled to the targeted application. Taken together, these systems leave an impor-tant regime underserved: tasks that require direct manipulation over recurring representations, where the surface itself is reusable but the meaning of each manipulation changes across tasks. For exam-ple, the same graph view may represent a project plan in one task and a social network in another; connecting two nodes creates a dependency be-tween steps in the first and represents a social re-lationship in the second. Supporting this regime requires separating reusable interaction structures from task-specific semantics and binding those se-mantics to each task. Once meanings vary across uses, the binding itself can no longer remain im-plicit: it must be published as shared, observable state. This allows any participant, human or agent, to inspect the available interactions and understand their meanings when interpreting or performing ma-nipulations. In particular, as tasks are increasingly shared among agents, a second agent can use an in-teraction surface created by another agent because its interaction semantics are explicitly shared. To this end, we present Agent-Bound UI , an inter-action model that turns reusable interactive views into task-specific communication surfaces by allow-ing agents to bind and publish interaction seman-tics. We realize this model in ABRA (Agent-Bound 

Readable inter Actions) prototype. Our contribu-tions are as follows: • Agent-Bound UI , an interaction model that enables agents to bind and publish interaction semantics over reusable interactive views. • ABRA , an open, framework-agnostic proto-type in which multiple agents and users col-laborate over shared interactive canvases. • A case study and experiments demonstrating agent-bound interaction in practice. 

2 Related Works 

2.1 Generative and Composable Interfaces 

Generative approaches 1 synthesize the interface itself, typically turning a chat request into a gener-ated interactive artifact: a page produced in place of a response (Hojo et al., 2025; Chen et al., 2026a; Leviathan et al., 2026), or an application that per-sists and evolves with the task (Xu et al., 2026; Xie and Xie, 2026). Either way, what a manipu-lation means is frozen in the generated code, and changing it means regenerating. Cao et al. (2025) make the artifact malleable through an evolving data model, but each manipulation still means a fixed, system-defined edit. Composable approaches provide reusable UI primitives that agents assemble into task-specific interfaces. Systems such as A2UI (Google, 2026a) assemble task-specific interfaces from component catalogs, enabling reuse of interface components rather than interaction semantics. Adaptation, how-ever, still occurs primarily through interface compo-sition, with richer representation-level interactions often requiring additional task-specific components or application logic. In contrast, Agent-Bound UI keeps the interaction structure reusable while mov-ing adaptation to task-specific semantic bindings. 

2.2 Task-Specific Interaction Surfaces

specific systems provide developer-authored in-teraction surfaces tailored to particular work-flows (Shao et al., 2026). Examples include writ-ing (Reza et al., 2024; Laban et al., 2024; Masson et al., 2025), agentic coding IDEs, data analysis and visualization (Wang et al., 2024a; Xie et al., 2024; Zhao et al., 2026), planning (Cai et al., 2024; Kim et al., 2025; Feng et al., 2026; He et al., 2026), and sensemaking (Jiang et al., 2023; Suh et al., 2023). These systems support rich manipulation, but both the interaction surface and the meaning of its interactions are fixed for the target application. Unlike these dedicated systems, MCP Apps (Maintainers, 2026) bring interactive surfaces into chat environments through developer-authored components. However, interaction semantics remain defined by the underlying implementation and encapsulated within tool-agent interactions, rather than published as shared state. Agent-Bound UI instead binds and publishes interaction meanings at task runtime, allowing other participants to inspect and use the same interaction surface. 

2.3 Agent–UI Communication Protocols 

Several protocols standardize the wiring around an agent: AG-UI (2026) (from CopilotKit) carries state and events between an agent and a frontend, A2A (Google, 2026b) carries messages between agents, and MCP connects agents to tools, with MCP Apps as its interface extension. These trans-ports move state, messages, and events, but say nothing about what an interaction means. Agent-Bound UI defines that missing layer independently of the underlying transport. Because bindings and events are represented as ordinary messages and state, a canvas can be implemented over any of these protocols, subject to their respective capabili-ties. 

3 Agent-Bound UI 

Agent-Bound UI models an interaction as areusable interaction structure paired with a task-specific semantic binding (Fig. 1). We define a 

view as a reusable interaction vocabulary over a particular representation, while a canvas instanti-ates one or more views with task-specific content and interaction semantics. We distinguish user gestures from agent-facing actions: a gesture describes how a user performs an interaction (e.g., click or drag) on an element (e.g., a node or column), while an action captures the op-eration communicated to the agent (e.g., edit a cell or add an edge). The meaning of an action, how-ever, depends on the task context. Agent-Bound UI separates these layers by allowing views to define reusable interaction vocabularies while agents bind task-specific meanings to these actions and publish the resulting bindings as shared canvas state. 

3.1 A Reusable Action Vocabulary 

Agent-Bound UI builds on the observation that many interaction structures recur across tasks and treats them as a reusable vocabulary rather than a task-specific implementation. Each view de-fines a set of available elements and actions over those elements, providing a stable interaction sub-strate (Mackay and Beaudouin-Lafon, 2025) that can be reused across tasks. Because these ac-tions describe operations rather than task meanings, the same vocabulary can support different tasks through semantic binding. The vocabulary may also include a bounded set of composable controls, such as buttons and drop-downs. These controls provide additional interac-tion elements that can acquire task-specific mean-ings through the same binding mechanism. 

3.2 Semantic Binding and Action Handling 

The interaction vocabulary is task-agnostic. To specialize it for a particular task, the agent binds view elements to task objects (referents), selects the applicable actions, and assigns task-specific meanings to those actions. This binding can apply both to interactions over existing representations (e.g., editing a table cell or connecting graph ele-ments) and to composable controls (e.g., a button triggering a task-specific operation). Semantic binding is independent of how an ac-tion is resolved. In Agent-Bound UI, actions fol-low one of two handling modes. A local effect 

is handled directly by the view when the interac-tion can be completed from view state alone, such as changing a selection or updating presentation state. In contrast, a consequence delegates res-olution to the agent when completing the action requires task-specific reasoning. This separation keeps the interaction vocabulary reusable while al-lowing task-specific behaviors to emerge through semantic binding and agent resolution. 3.3 Published Interaction Semantics 

Because interaction meanings are task-specific, Agent-Bound UI publishes semantic bindings as part of the shared canvas state rather than leaving them as private agent logic. A canvas state includes the bindings between view elements and task refer-ents, which actions are enabled for the canvas, and the task-specific meanings associated with actions. Making these bindings observable allows not only the agent that created the canvas, but also humans and other agents to inspect the available interac-tions and understand their intended meanings. Publishing thus turns a single-agent convenience into a multi-agent necessity: one agent can cre-ate a canvas and publish task-specific interaction bindings, and a second agent can later interpret or invoke those actions based on their published meanings, with no private channel between them. 

4 ABRA System 

4.1 Realization of Agent-Bound UI 

ABRA serves as a reference prototype of the Agent-Bound UI interaction model. It realizes the model through three components: (1) view definitions, (2) canvas specifications, and (3) an agent inter-face. Views provide reusable interaction struc-tures, while canvas specifications instantiate these structures with task-specific content and interaction bindings provided by agents. These bindings are published as shared canvas state, which agents can access and manipulate through tool calls. The prototype provides a unified interaction en-vironment with a chat panel for natural language interaction and a canvas panel for direct manipula-tion interaction on agent-rendered views (Fig. 2). 

4.2 View and Canvas Specification 

ABRA represents reusable interaction vocabular-ies through view definitions. Each view defini-tion specifies the element schemas and actions sup-ported by the view, along with view-specific meta-data. In the current prototype, each action is asso-ciated with a predefined execution mode: either a local effect handled directly by the view or a conse-quence resolved by the agent, for simplicity. Ges-ture mappings are implemented within each view and remain independent of task-specific semantic bindings. The prototype currently supports four view types: graph, table, text, and display views, summarized in Table 1. A canvas specification defines a task-specific canvas instance. Agents provide these specifica-tions when creating canvases, including selected views, task content, element-referent bindings, en-abled actions, task-specific semantic bindings, and optional controls or presentation settings.

4.4 Prototype Architecture 

The prototype is implemented with React-based views, a Node.js canvas hub, and agent adapters in Python. The canvas hub maintains canvas states and synchronizes updates among partici-pants, while views and adapters provide client-specific access to the shared environment. 2

For demonstration, we integrate multiple agents implemented with different agent SDKs. These agents can inspect published canvas states and in-teract with canvases through the provided tools. 

5 Use Case 

We demonstrate ABRA through a collaborative World Cup analysis task involving a user and three specialized agents (Fig. 2). Rather than produc-ing a static report, the agents progressively con-struct a shared workspace comprising a knockout-stage table, tournament bracket, player gallery, and explanatory notes. Researcher the explanatory notes. The canvases re-main active coordination surfaces where both users and agents communicate by manipulating shared representations rather than solely through chat. The interaction begins with the agents proposing an initial organization of the workspace, which the user refines directly on the rendered representations. For example, after the user abbreviates Forward to FW in a table cell, the agent proposes applying the same convention throughout the column, inter-preting the edit as a refinement rather than a lit-eral cell replacement. Likewise, the user connects nodes in the tournament graph to express relation-ships directly instead of describing them. Not ev-ery manipulation, however, is accepted: though the graph view supports edge creation, the owner agent rejects a connection that violates the tournament structure. Thus, views define what interactions users can attempt, while agents determine which are meaningful for the current task. The shared canvases also serve as the medium for inter-agent coordination. When Curator requires player statistics, it asks Analyst to extend the ex-isting table instead of modifying it directly or du-plicating the information. Once the updated table is published, Curator then reuses the information in its own canvases. Shared referent bindings keep teams and players synchronized across the table, graph, gallery, and notes, allowing participants to move between representations while maintaining a consistent interpretation of each entity. 

6 Experiments 

Agent-Bound UI assumes that agents can use our in-teraction vocabulary to author, interpret, and manip-ulate task-specific canvases. In particular, agents should be able to (1) author canvases, (2) resolve consequences on canvases they own, and (3) in-terpret and invoke interaction semantics published by other agents. We evaluate these capabilities in isolation rather than evaluating end-to-end task performance. This allows us to assess whether an agent can correctly ground and execute the required operations independently of longer interaction dy-namics. 

6.1 Tasks Canvas authoring The agent receives a natural language request and creates a task-specific canvas. We construct 45 cases covering 15 canvas config-urations, with four single-view and 11 multi-view configurations, each with three domain variations. Each case additionally includes an interactive vari-ant that requires direct manipulation. 

Consequence resolution The agent receives a pre-populated canvas that it owns with a pend-ing consequence and must resolve it through 

update_canvas . We construct 33 cases covering 11 consequence-producing actions across three do-main variations. 

Cross-agent invocation The agent receives a user request over a canvas owned by another agent and must invoke the appropriate published interac-tion through fire_action . We construct 33 cases covering 11 actions across three domain variations. 

6.2 Experimental Setup 

Each case is run three times per model, with a fresh agent instance for every trial. The agent re-ceives a task-specific context and a single input, and is allowed one response turn to submit canvas operations. The context differs by task: canvas authoring provides a user request; consequence res-olution provides a canvas state owned by the agent with a pending consequence; and cross-agent in-vocation provides a canvas state owned by another agent with published interaction semantics together with a user request. This one-turn setting evaluates whether agents can correctly ground and execute canvas operations from the available context with-out relying on iterative interaction. We compare four LLM-backed agents using models from two families: Claude Opus 4.8 and Haiku 4.5, and GPT-5.4 and GPT-5.4-mini. Agent performance is evaluated through automatic struc-tural checks and an LLM-based evaluator using predefined criteria. Details are provided in §A.

7 Conclusion 

We presented ABRA , a prototype of the Agent-Bound UI interaction model for shared interac-tive canvases. Our demonstration and experiments show that evaluated LLM agents can effectively operate over published interaction semantics, pro-viding a foundation for richer human–agent inter-action and cross-agent collaboration. 

Limitations 

Agent-Bound UI introduces a mechanism for bind-ing and publishing interaction semantics, but sev-eral questions remain open. First, determining reusable interaction vocabularies that provide broad task coverage remains challenging; future work will investigate methods for discovering common views and actions from existing interactive sys-tems and evaluating their coverage over diverse task benchmarks. Second, while published seman-tics are intended to make interactions understand-able to both human and agent participants, we have not yet evaluated how effectively users interpret these semantics or how they affect the overall inter-action experience. Future user studies will exam-ine how interaction semantics should be presented, and whether agent-bound interactions improve user experience and task outcomes compared with chat-based interaction.

A Evaluation Details 

We combine deterministic checks with an LLM-based evaluation (from a separate model family, Gemini 3.1 Pro) to assess agent outputs. Deter-ministic checks verify contract-level constraints, including schema validity and required output formats, as well as task-specific expected out-comes. For create_canvas , we additionally check whether the generated view and action types match the expected specification. For update_canvas ,we verify that the revised canvas matches the ex-pected content after applying the update. For 

fire_action , we check whether the fired action type matches the expected action. The LLM evaluator handles open-ended crite-ria that cannot be reliably determined through de-terministic checks, including semantic grounding, content correctness, and style conventions.
