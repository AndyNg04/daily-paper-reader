## ABSTRACT 

Unlike conventional GUI agents, personalized GUI agents require user prefer-ences to guide a sequential execution policy over changing GUI states. This creates two challenges for the agentic design: 1) Determining HOW each pref-erence should alter the agent’s execution strategy. 2) Determining WHEN each preference should take effect along the interaction trajectory. However, exist-ing benchmarks primarily evaluate overall task success only, making it difficult to evaluate agents’ reasoning ability to determine HOW and WHEN preferences should affect execution. To address this, we introduce PrefDiag-Bench with two key components: 1) a categorization of user preferences into five types, character-izing HOW they affect agent execution; and 2) a stage-wise diagnostic framework with 1,664 probes, tracing WHEN preferences should take effect along the in-teraction trajectory and where failures occur. Experimentally, we evaluate eleven GUI agent systems, including end-to-end agents and agentic workflows, under two forms of user context: explicit user profiles and behavioral memory logs. We find while existing GUI agents achieve relatively high task completion rates on non-personalized tasks, their performance remains substantially lower on preference-personalized tasks. Even the best-performing model, Seed-2.0-Pro, achieves only 47.17% on process preferences under explicit user profiles. Moreover, agents struggle particularly with Ranking and Process preferences, indicating substantial room for improvement. Further analysis reveals two key capability bottlenecks be-hind these failures: selecting relevant evidence from user history, and recognizing when user preferences should take effect during execution. Controlled interven-tions that explicitly provide relevant evidence improve end-to-end task success by up to 7.06%. We hope PrefDiag-Bench can provide a more systematic and comprehensive evaluation of GUI agents’ personalization capabilities, moving be-yond simply measuring overall task success. First, an agent is re-quired to determine HOW each preference should alter execution: it may change the desired out-come, restrict valid choices, change candidate priorities, or constrain the execution process or in-teraction behavior. Second, the agent is required to determine WHEN a preference should take effect along the interaction trajectory, based on the current task and GUI state. To address these challenges from a data-centric perspective, we introduce PrefDiag-Bench, a fine-grained diagnostic benchmark for personalized GUI agents. PrefDiag-Bench contains two com-plementary components corresponding to the challenges above. First, while the benchmark spans diverse application domains, including shopping, workflow, and transportation, its main evalua-tion axis is the primary effect of each preference on agent execution. We organize user prefer-ences into five execution-oriented types, i.e. , Outcome, Constraint, Ranking, Process, and Inter-action—characterizing HOW they affect agent execution, and construct corresponding end-to-end tasks to compare agents under different execution requirements. Second, we develop a stage-wise diagnostic framework that covers three high-level phases, i.e. , information processing, contextual reasoning, and action formulation, and further divides them into five diagnostic stages. The frame-work probes the capabilities required to apply preferences from user context to GUI actions, includ-ing recognizing WHEN a preference should take effect, and identifies capability bottlenecks arise during personalized execution. Based on this design, PrefDiag-Bench contains 318 end-to-end GUI tasks and 1,664 associated diagnostic probes. Each end-to-end task is paired with a set of diagnostic probes built around the same underlying preference instance. This paired design allows us not only to evaluate whether an agent completes the task while satisfying the user’s preference in an interac-tive GUI environment, but also to connect end-to-end performance with specific diagnostic stages. In addition, we construct explicit user profiles and behavioral memory logs as two user-context rep-2Preprint resentations at different levels of abstraction, enabling us to study how the form of user context affects personalized execution. Experimentally, we systematically evaluate 11 existing popular personalized GUI agentic designs, including nine end-to-end agents and two agentic workflows, M3A and T3A, using explicit user profiles and behavioral memory logs. Our results indicate three main findings. First, performance varies substantially across the five preference types, showing that collapsing performance across preference types into a single aggregate score can obscure important capability differences. Sec-ond, explicit user profiles do not consistently outperform behavioral memory logs, suggesting that compact preference summaries are not always more useful than logs that retain concrete behavioral evidence. Third, selecting relevant evidence from user history and recognizing when preferences should take effect emerge as the two main bottlenecks. Controlled interventions on a representative subset of systems further show that explicit evidence guidance improves end-to-end task success by up to 7.06 percentage points, demonstrating that evidence selection has a measurable impact on personalized execution and provides a concrete target for system improvement. 

## 2 RELATED WORK 

2.1 MOBILE GUI A GENTS AND THEIR PERSONALIZED EVALUATION 

Recent mobile GUI agents have made substantial progress in GUI perception, task planning, and multi-step task execution (Liu et al., 2025a; Nguyen et al., 2025; Hu et al., 2025). Existing systems include agent frameworks that organize task execution through explicit reasoning and control mod-ules, such as AppAgent (Zhang et al., 2025a), M3A (Rawles et al.), and Mobile-Agent-v3 (Ye et al., 2025), as well as end-to-end agents that directly generate reasoning traces and actions from GUI observations, such as UI-TARS (Qin et al., 2025) and GUI-Owl (Ye et al., 2025). As the GUI capa-bilities of these systems continue to improve, recent studies have begun to examine how agents can use user history and preferences to adapt their behavior during task execution. PersonalAlign (Lyu et al., 2026) uses long-term user records to recover preferences omitted from vague instructions; PSPA-Bench (Nie et al., 2026) decomposes tasks to evaluate preference-sensitive progress; KnowU-Bench (Chen et al., 2026) uses behavioral logs to assess preference inference, user clarification, and proactive decision-making; and Persona2Web (Kim et al., 2026) studies contextual reasoning from long-term user histories in web environments. These studies broaden personalized agent evaluation from complementary directions. However, they do not jointly examine how different preferences af-fect GUI execution or which capabilities become bottlenecks when preferences are applied from user context to GUI actions. PrefDiag-Bench complements this line of work with an execution-oriented and stage-wise diagnostic perspective. 2.2 PERSONALIZATION USER CONTEXT AND MEMORY 

Personalization relies on memory as a key source of user context, allowing agents to retain and reuse information from past interactions (Zhang et al., 2025b; Liu et al., 2025b). Memory systems such as MemoryBank (Zhong et al., 2024) and Mem0 (Chhikara et al., 2025) extract, update, and retrieve user information from ongoing interactions to support long-term personalization. Corre-sponding benchmarks examine this process from different perspectives. PersonaMem (Jiang et al., 2025) evaluates whether models can track evolving user profiles from multi-session interaction his-tories and generate personalized responses accordingly. AlpsBench (Xiao et al., 2026) decomposes personalized memory management into information extraction, updating, retrieval, and utilization. In mobile GUI environments, MemGUI-Bench (Liu et al., 2026) focuses on memory retention and use across steps, applications, and sessions.However, correctly inferring or retrieving user informa-tion does not necessarily mean that an agent can apply user preferences correctly in a GUI task. Personalized GUI agents must further connect user context with the current task and GUI state, and translate relevant preferences into concrete behaviors such as candidate selection, ranking, process control, or user interaction. ## 3 BENCHMARK DESIGN 

PrefDiag-Bench evaluates personalized mobile GUI agents at both the task and diagnostic levels. It contains 318 end-to-end GUI tasks, including 53 Basic and 265 preference-conditioned instances and 1,664 diagnostic probes, where each end-to-end task is linked to probes constructed from the same underlying preference instance. 3.1 PREFERENCE TAXONOMY 

User preferences concern different application domains and semantic content. For mobile GUI agents, however, a more direct distinction is the type of decision that each preference changes during task execution. We therefore use preferences’ primary effects on execution as our main evaluation axis, classifying each preference by the part of a personalized task’s success criterion that it directly changes. This yields five types, illustrated in Figure 1. Specifically, as shown in the Figure 1, Outcome preference specifies the desired outcome or final choice, such as selecting “no sugar” and “less ice” in a drink-ordering task. A Constraint prefer-ence sets conditions that a valid outcome or allowed action must satisfy, such as keeping the drink price at or below 20$. A Ranking preference specifies priorities among valid candidates, rather than determining whether a candidate satisfies a hard constraint. For example, when several stores offer the target drink, the agent should prioritize the store with the shortest delivery time and choose the cheaper store when delivery times are equal. A Process preference specifies how a task should be carried out, such as comparing the price of the same product across multiple platforms before making a choice. The final GUI state alone is insufficient to verify this requirement: the execution trajectory must also show that the prescribed procedure was followed. An Interaction preference specifies whether, when, and how the agent should interact with the user. For example, after finding a suitable item, the agent should request confirmation and add it to the cart only after the user agrees. Although both types affect the interaction trajectory, Process constrains the task procedure, whereas Interaction constrains communication with the user. A task may therefore reach the expected fi-nal state yet still violate its preference requirements if a required comparison or confirmation was skipped during execution. 3.2 BENCHMARK OVERVIEW AND STATISTICS 

PrefDiag-Bench evaluates agents’ ability to apply user preferences across diverse mobile tasks. It comprises 53 task families, each with one Basic task and five preference-conditioned variants, yield-ing 318 instances (53 Basic and 265 personalized). As shown in Figure 2(a), the tasks span seven application domains: communication, office, commerce, navigation, system settings, information retrieval, and social media. Within the diagnostic set, preference atoms also cover nine semantic cat-egories, including workflow, user control, time and context, resource limits, and safety and privacy (Figure 2(c)). We construct preference-conditioned variants from selected KnowU-Bench tasks (Chen et al., 2026), inspecting their goals, application settings, and success criteria. Every resulting variant is manually reviewed. The target preference is conveyed through user context rather than restated in the in-struction. We construct paired contexts by first drafting explicit user profiles with an LLM, revising and checking them with GPT-5.6 Sol, and reviewing every profile manually. Synthetic behavioral memory logs are then generated from the reviewed profiles, with four to five profile-related entries per collection, and undergo the same model-assisted revision and human review. The underlying preference, instruction, initial environment state, and success checker remain fixed across the two context forms. We derive task-linked diagnostic probes from execution failures under behavioral logs, retaining cases with valid checker results and deduplicating them across agents by task. Independently diag-nosable preference requirements are separated into atoms. Probe questions, options, and reference annotations are drafted with LLM assistance and revised by humans. For P4 and P5, we use atoms with clear trigger boundaries and usable reference trajectories. P5 reference actions are extracted from successful rollouts of the corresponding tasks and represented as semantic operations. ## 4 EXPERIMENTS 

We organize our experiments around the following five research questions. 

RQ1. How well do GUI agents satisfy different preference requirements during task execution? 

RQ2. What strengths and weaknesses do agents exhibit across stages of preference application? 

RQ3. What relationships emerge between task-level diagnostic results and end-to-end outcomes? 

RQ4. What effect does evidence guidance have on end-to-end task success? 

RQ5. What changes in performance occur under different memory construction methods? 4.1 EXPERIMENTAL SETUP 

Evaluated Systems. We evaluate 11 systems. The closed-source agents are Seed-2.0-Pro (Seed, 2026), Claude Sonnet 4.6 (Anthropic, 2026), and Qwen3.7-Plus (Alibaba Cloud, 2026). The open-source agents are MAI-UI-8B (Zhou et al., 2025), Qwen3-VL-8B-Instruct and Qwen3-VL-8B-Thinking (Team, 2025), Step-GUI-4B (GELab-Team & StepFun, 2025), GUI-Owl-1.5-8B-Instruct (Xu et al., 2026), and UI-Venus-1.5-8B (Team et al., 2026). We also evaluate two agentic workflows, M3A and T3A (Rawles et al.), both using GPT-5.4. Open-source models run on a server with eight NVIDIA RTX 4090 GPUs.

All systems share task environments and checkers while retaining their native observation and action interfaces. Instructions, initial states, and checkers remain fixed across profile–log pairs. Independent P1–P5 probes are applied to the nine directly queried agents; workflows are excluded to avoid assessing only their backbone or introducing workflow-specific probe adaptations. Personalized tasks are more challenging to execute. All 11 systems achieve lower average TSR on preference-conditioned tasks than on Basic tasks under both forms of user context. Seed-2.0-Pro obtains the strongest personalized results, reaching 62.64% with explicit profiles and 65.66% with behavioral logs, compared with 81.13% on Basic . In contrast, Claude Sonnet 4.6 achieves the highest Basic TSR of 86.79%, but is surpassed by Seed-2.0-Pro under both personalized settings. This ranking change shows that strong general GUI execution is important, but is not sufficient for applying user preferences throughout a multi-step interaction trajectory. 

Different preference types expose distinct performance patterns. Outcome is the best-performing type for 10 of the 11 systems under explicit user profiles and for all 11 systems under behavioral memory logs. At the other end, Ranking and Process emerge as recurring difficulties across systems and user-context forms. Process is the lowest-performing type for seven systems under explicit profiles and the lowest or tied-lowest type for eight systems under behavioral memory logs. Under behavioral memory logs, Qwen3.7-Plus drops from 62.26% on Outcome to 16.98% on Process, a gap of 45.28 percentage points. Ranking remains difficult even for the strongest system: Seed-2.0-Pro achieves 83.02% on Outcome but only 45.28% on Ranking under behavioral memory logs, a difference of 37.74 points. These results show that reporting only an overall personalized score would hide major differences in the execution requirements that each system can handle. The repeated difficulty on Ranking and Process is consistent with the additional candidate comparison required by Ranking and the longer execution procedure required by Process. 

More explicit user context is not always more effective. The profile–log comparison has no con-sistent direction across systems. Behavioral logs improve Seed-2.0-Pro from 62.64% to 65.66% and T3A from 24.91% to 29.44%, whereas M3A drops from 37.73% with profiles to 18.49% with logs. This contrast is notable because M3A and T3A use the same GPT-5.4 backbone, suggesting that the usefulness of a context form also depends on how the overall workflow processes user informa-tion. This pattern is consistent with the trade-off built into the two representations: profiles directly provide compact preference rules, whereas logs preserve concrete behavioral evidence but require the agent to identify which evidence is relevant. These task-level comparisons reveal performance gaps across execution requirements and context forms, but do not isolate the capabilities underlying preference application. For each of the nine directly evaluated agents, we pair every task-level diagnostic result with the corresponding end-to-end outcome under behavioral memory logs. Since the diagnostic set is dedu-plicated across agents, a task included due to one agent’s failure may still be completed by another agent. Figure 4 partitions the eligible paired instances into four joint outcomes: both task and probe pass (TT), the task passes but the probe fails (TF), the task fails but the probe passes (FT), and both task and probe fail (FF). 

P2 and P4 failures frequently co-occur with task failures. P2 Evidence Selection and P4 Trig-ger Recognition show markedly higher joint-failure proportions than the other diagnostic stages. 4.5 CONTROLLED EVIDENCE INTERVENTION 

To test whether P2 Evidence Selection is an actionable bottleneck, we evaluate Seed-2.0-Pro, Qwen3.7-Plus, Qwen3-VL-8B-Thinking, and Step-GUI-4B on a fixed subset of 85 tasks selected from the 265 preference-conditioned tasks. Table 3a compares three conditions: C0 Raw Logs 

uses the original logs; C1 Oracle Evidence Labels retains all entries and labels each as supporting 

or noise for the target preference, without changing its text or order; C2 Supporting Logs Only 

removes all noise entries and retains only supporting logs. C1 tests whether explicitly identifying supporting and noise logs helps execution, while C2 tests whether removing noise is more effective than retaining and labeling it. The task instruction, initial environment state, and success checker remain fixed. 

Evidence labeling can outperform noise removal. From C0 to C1, Seed-2.0-Pro improves from 76.47% to 83.53%, a gain of 7.06 percentage points, and Qwen3.7-Plus improves from 50.59% to 56.47%. These gains show that explicitly distinguishing supporting logs from noise can help agents complete personalized tasks. However, replacing labeled logs with supporting-only logs (C2) reduces their TSR to 81.18% and 51.76%, respectively. For these systems, identifying which logs support the preference is therefore more effective than simply discarding the rest. A possible explanation is that labeled noise provides contrastive cues about which historical behaviors should not guide the current decision, whereas deleting these entries removes those cues. 

Limited GUI capability may constrain intervention benefits. Qwen3-VL-8B-Thinking achieves 69.53% on P2 and 45.79% on P4, but only 30.19% on Basic tasks and 12.07% on the full preference-conditioned set under behavioral logs (Table 2). On the 85-task intervention subset, its TSR remains low: 17.65% under C0, 16.47% under C1, and 18.82% under C2. This contrast suggests that limitations in GUI execution constrain the gains from evidence guidance, even when evidence selection is relatively strong. Step-GUI-4B also reaches only 18.82% under both C1 and C2. These results suggest that strong GUI execution is a necessary foundation for personalized task success: when an agent’s basic GUI capability is limited, even accurate preference understanding may not translate into successful end-to-end execution. 4.6 ROBUSTNESS TO MEMORY CONSTRUCTION METHODS 

To test whether the preference-type differences in Section 4.2 depend on our original memory con-struction, we evaluate Seed-2.0-Pro on all 265 preference-conditioned tasks using alternative mem-ory inputs produced by Mem0 (Chhikara et al., 2025), LangMem (LangChain, 2025), and Hind-sight (Latimer et al., 2026) from the same source behavioral records. The task instruction, initial environment state, success checker, and execution settings remain fixed. Table 3b reports TSR by preference type, with the original behavioral memory logs included as O URS .

Preference-type differences persist across memory construction methods. Outcome remains the highest-scoring type, while Ranking and Process are the two lowest-scoring types under all three methods. With Mem0, TSR is 71.70% on Outcome, compared with 43.40% on Ranking and 50.94% on Process. Hindsight shows the same broad contrast, reaching 79.25% on Outcome, 45.28% on Ranking, and 37.74% on Process. Although the absolute scores and the ordering of Ranking and Process change, their relative difficulty persists across the tested methods. This consistency further 9Preprint supports our preference-conditioned task design, as the observed differences across preference types persist under alternative memory construction methods rather than being specific to our original behavioral memory logs. 

## 5 CONCLUSION 

We introduce PrefDiag-Bench to provide a more systematic and comprehensive view of personal-ization in mobile GUI agents. By categorizing user preferences into five types and combining this categorization with a stage-wise diagnostic framework, it examines how preferences affect agent execution, when they should take effect, and where capability gaps arise. Our evaluation shows that overall task success alone can obscure distinct strengths and weaknesses across preference types and stages of preference application. Connecting these capability-level assessments with end-to-end outcomes provides a basis for more informative evaluation and targeted interventions. We hope PrefDiag-Bench supports the development of GUI agents that not only understand user preferences but also apply them reliably throughout task execution.

A.2 USER -C ONTEXT CONSTRUCTION AND ANNOTATION 

Figure 5 summarizes the overall construction process. We detail below how explicit user profiles, behavioral memory logs, and their reference annotations are produced. 

Profile drafting and review. For each personalized task, we specify the intended preference and its applicable conditions. An LLM drafts an explicit user profile, which GPT-5.6 Sol checks and revises before human reviewers examine every profile. Reviewers check the requested behavior, applicable conditions, and task-specific details against the intended preference. The reviewed profile then serves as the basis for log synthesis. 

Behavioral-log synthesis. Using the reviewed profile, an LLM generates synthetic records of past choices, corrections, confirmations, and related activities. Supporting records provide evidence for the target preference, while distractors may share an application, product category, or recipient with-out establishing the same requirement. Contextual exceptions are retained where present. The logs undergo GPT-5.6 Sol revision and item-by-item human review alongside the profile. Reviewers check that both forms convey compatible requirements and that distractors remain plausible histor-ical records rather than explicitly declaring their irrelevance. ## B EXPERIMENTAL DETAILS 

B.1 ENVIRONMENT AND AGENT CONFIGURATION 

Environment and task inputs. We reuse the Android environment and evaluation infrastructure of KnowU-Bench, with task-specific initial data and checkers for PrefDiag-Bench. Each episode starts from its prescribed application state, with agent history reset between tasks. Episodes allow at most 65 environment steps with a one-second inter-step wait, and can end earlier when the agent reports completion or inability to proceed. Open-source models are served on eight NVIDIA RTX 4090 GPUs. The 53 Basic tasks receive no additional user context. Each of the 265 personalized tasks receives either its explicit user profile or its behavioral memory logs. The instruction and context remain available throughout execution, alongside the current observation, adapter-specific history, and any platform reply. Adapters retain native observation and action formats while mapping actions and coordinates to the common environment interface. 

Decoding and workflow interfaces. The Qwen, MAI-UI, Step-GUI, GUI-Owl, and UI-Venus adapters use temperature 0. Seed-2.0-Pro uses temperature 0.7, top-p = 0 .9, and a 4,096-token re-sponse limit; its adapter retains the three most recent screenshots alongside textual history. Claude’s adapter does not explicitly set temperature. M3A and T3A use GPT-5.4 with temperature 0, a 2,048 token action-response limit, and up to 20 objective action summaries. Both workflows use the same task contexts, step budget, and checkers as the directly evaluated agents. B.2 SCORING AND TASK –P ROBE ASSOCIATION

Task selection. The fixed subset contains 85 task–preference pairs from 43 families, with 17 pairs per preference type: 15 P2-target pairs, one downstream control, and one retention control. The totals are therefore 75, 5, and 5 pairs, respectively. Selection uses pre-intervention diagnostic and behavioral-log execution records. A P2-target pair requires at least one model that fails both P2 and the task, and at least one model that completes the task. Downstream controls have correct P2 answers but failed execution; retention controls have successful diagnostic and execution out-comes. Every selected pair has an audited supporting-log mapping and at least one distractor. This P2-enriched subset is shared across all four models and all conditions, and selection does not use intervention outcomes. 

Input conditions. C0 supplies the behavioral memory logs without evidence labels. C2 retains only supporting entries in their original order, without labels. All three conditions are executed anew with the same instruction, initialization, and checker.
