## 摘要
与传统 GUI 智能体不同，个性化 GUI 智能体需要依据用户偏好，在不断变化的 GUI 状态中指导序列化执行。这带来了两项挑战：确定每项偏好应如何改变执行策略，以及偏好应在交互轨迹的何时生效。现有基准主要评估总体任务成功率，难以深入揭示这些问题。我们提出 PrefDiag-Bench，包含两个组成部分：（1）将偏好划分为五种类型，以刻画偏好如何影响执行；（2）包含 1,664 个探测项的分阶段诊断框架，用于追踪偏好应在何时生效以及失败发生的位置。我们在两种用户上下文形式下评估了 11 种 GUI 智能体系统，包括端到端智能体和智能体工作流：显式用户档案和行为记忆日志。尽管现有智能体在非个性化任务中取得了相对较高的完成率，但在基于偏好进行个性化的任务中，表现显著较低。表现最佳的模型 Seed-2.0-Pro 在显式用户档案下处理流程偏好（Process preferences）的得分也仅为 47.17%。智能体尤其难以应对排序偏好（Ranking preferences）和流程偏好。进一步分析揭示了两个关键能力瓶颈：从用户历史中筛选相关证据，以及识别偏好应在执行过程中何时生效。通过受控干预明确提供相关证据，可使端到端任务成功率最高提升 7.06%。PrefDiag-Bench 为评估 GUI 智能体的个性化能力提供了比总体任务成功率更系统的方法。代码和数据见 https://github.com/Zhixin-L/PrefDiag-Bench。

## Abstract
Unlike conventional GUI agents, personalized GUI agents require user preferences to guide sequential execution over changing GUI states. This raises two challenges: determining HOW each preference should alter execution strategy and WHEN it should take effect along the interaction trajectory. Existing benchmarks primarily evaluate overall task success, offering limited insight into these questions. We introduce PrefDiag-Bench with two components: (1) a categorization of preferences into five types, characterizing HOW they affect execution; and (2) a stage-wise diagnostic framework with 1,664 probes, tracing WHEN preferences should take effect and where failures occur. We evaluate eleven GUI agent systems, including end-to-end agents and agentic workflows, under two forms of user context: explicit user profiles and behavioral memory logs. Although existing agents achieve relatively high completion rates on non-personalized tasks, performance is substantially lower on preference-personalized tasks. Even the best-performing model, Seed-2.0-Pro, achieves only 47.17% on Process preferences under explicit user profiles. Agents struggle particularly with Ranking and Process preferences. Further analysis reveals two key capability bottlenecks: selecting relevant evidence from user history and recognizing when preferences should take effect during execution. Controlled interventions that explicitly provide relevant evidence improve end-to-end task success by up to 7.06%. PrefDiag-Bench offers a more systematic evaluation of GUI agents' personalization capabilities beyond overall task success. Code and data are available at https://github.com/Zhixin-L/PrefDiag-Bench.

# 《诊断移动 GUI 智能体的个性化失败》论文总结

## 1. 核心问题与整体含义

### 研究背景与动机
- 移动 GUI 智能体已经能够完成购物、发消息、管理日历、修改系统设置等任务，但**“完成任务”不等于“按用户习惯完成任务”**。
- 个性化执行要求智能体将用户历史、习惯与当前任务及界面状态结合，解决两个问题：
  - **HOW：偏好如何改变执行？**例如改变商品选择、限定预算、调整候选排序、要求跨平台比价或提交前确认。
  - **WHEN：偏好何时生效？**例如“下单前确认”应在订单信息完整、提交动作尚未执行时触发，而不是搜索开始时或订单提交之后。
- 现有基准主要关注总体成功率，即使能够发现任务失败，也难以进一步区分失败来自历史理解、证据筛选、触发时机判断，还是 GUI 操作。

### 论文的整体定位
- 提出 **PrefDiag-Bench**，将“端到端任务评估”与“分阶段能力诊断”结合。
- 核心价值是建立更细粒度的评估体系，**不是提出新的 GUI 智能体或训练算法**。
- 其基本观点是：可靠的个性化不仅需要记住用户偏好，还必须在正确的决策点，将偏好落实为可验证的执行行为。

## 2. 方法论：偏好分类与分阶段诊断

### 2.1 按“对执行的影响”划分五类偏好

| 偏好类型 | 改变的执行要求 | 示例 |
|---|---|---|
| **Outcome：结果偏好** | 最终结果或具体选择 | 奶茶无糖、少冰；购买惯常穿的鞋款 |
| **Constraint：约束偏好** | 有效选择或允许动作的边界 | 鞋价不超过 300 元 |
| **Ranking：排序偏好** | 合法候选之间的优先级 | 同等条件下优先官方旗舰店 |
| **Process：流程偏好** | 必须遵循的执行程序 | 先跨平台比价，再选择更便宜的平台 |
| **Interaction：交互偏好** | 与用户沟通的方式和时机 | 下单前询问并等待明确确认 |

- 分类依据是偏好对执行的**主要影响**，而非购物、办公等应用领域。
- 特别强调：流程与交互要求不能只根据最终页面判断，必须检查执行轨迹。即使最终买对商品，跳过比价或确认仍应判为失败。

### 2.2 端到端任务形式化与成功判定
- 每个任务由四部分组成：**任务指令、用户上下文、初始环境状态、确定性成功检查器**。
- 智能体产生由观察和动作组成的执行轨迹。
- 检查器结合最终应用状态、数据库或回调记录，以及必要的操作和用户交互记录进行判断。
- 只有同时满足任务目标与全部偏好要求，才计为成功；部分完成不计为成功。
- 主要指标为 **任务成功率 TSR**，个性化总体分数是五类偏好成功率的宏平均。

### 2.3 五阶段独立诊断探针

论文将偏好应用划分为信息处理、上下文推理和动作形成三个高层阶段，并设计五种探针：

| 探针 | 测试能力 | 数量 |
|---|---|---:|
| **P1：记忆归纳** | 从行为日志中概括用户偏好 | 260 |
| **P2：证据筛选** | 已知偏好后，找出直接支持它的历史记录 | 260 |
| **P3：任务相关性判断** | 判断哪些偏好适用于当前任务 | 325 |
| **P4：触发时机识别** | 结合截图与历史动作，判断偏好尚未生效、正在生效或已错过窗口 | 601 |
| **P5：操作映射** | 已知偏好正在生效时，选择正确的下一步语义策略 | 218 |
| **合计** |  | **1,664** |

关键设计：
- **独立测量**：各探针单独提问，必要时直接提供正确的前置条件，避免上游错误传播。
- **严格匹配**：P2 必须完整选对证据集合；一个任务对应多个题目时，全部答对才算该阶段通过。
- **语义动作而非实际点击**：P5 测试下一步策略，不测试坐标定位或完整动作序列。
- **任务与诊断配对**：同一偏好实例同时关联端到端任务与诊断探针，以分析两者成功、失败是否共同出现。

### 2.4 数据构建流程
1. 从 KnowU-Bench 选取并改造基础任务。
2. 为每个任务构建五类偏好变体。
3. 生成并审核显式用户画像，再据此合成行为日志，包含支持证据与干扰记录。
4. 在行为日志条件下运行智能体，收集失败案例。
5. 将失败案例拆分为可独立诊断的“偏好原子”，构造 P1–P5。
6. 采用模型辅助起草、人工修改与审核，并进行标识符、字段及证据引用检查。

## 3. 实验设计：数据、场景与对比系统

### 3.1 Benchmark 的组成
- **53 个任务家族**，每个包含：
  - 1 个非个性化 Basic 任务；
  - 5 个偏好条件任务。
- 共 **318 个任务实例**，其中 53 个 Basic、265 个个性化任务。
- 场景覆盖七个领域：通信、办公、商业购物、导航、系统设置、信息检索、社交媒体。
- 使用 KnowU-Bench 的 Android 环境与评估基础设施，并配置任务专属初始数据和检查器。
- 诊断集来自行为日志条件下、跨系统去重后的 **256 个出现失败的任务**，涉及 **260 个偏好原子**。

### 3.2 两种用户上下文
- **显式用户画像（EUP）**：直接给出概括后的偏好规则。
- **行为记忆日志（BML）**：通过过去的选择、纠正和交互记录间接体现偏好。
- 配对条件下保持指令、初始状态和检查器一致，便于分析上下文形式的影响。

### 3.3 对比的 11 套系统
- **闭源端到端智能体**：Seed-2.0-Pro、Claude Sonnet 4.6、Qwen3.7-Plus。
- **开源端到端智能体**：
  - MAI-UI-8B；
  - Qwen3-VL-8B-Instruct、Qwen3-VL-8B-Thinking；
  - Step-GUI-4B；
  - GUI-Owl-1.5-8B-Instruct；
  - UI-Venus-1.5-8B。
- **智能体工作流**：M3A、T3A，均使用 GPT-5.4。

所有系统参加端到端评估；九个端到端智能体参加独立诊断。工作流未参加探针评估，以避免仅评估其底座模型，或因额外适配而改变评估对象。

### 3.4 附加实验
- **联合分析**：将诊断结果与对应端到端结果划分为同时通过、任务通过但探针失败、任务失败但探针通过、同时失败。
- **证据干预**：在 85 个任务上比较原始日志、保留全部日志但标注证据角色、仅保留支持日志。
- **记忆构建对比**：使用 Mem0、LangMem、Hindsight 生成替代记忆，测试主要发现是否依赖原始日志构建方式。

## 6. 主要结论与发现

### 6.1 个性化明显比普通任务困难

| 系统 | Basic TSR | 显式画像平均 TSR | 行为日志平均 TSR |
|---|---:|---:|---:|
| Seed-2.0-Pro | 81.13% | **62.64%** | **65.66%** |
| Claude Sonnet 4.6 | **86.79%** | 55.47% | 53.58% |
| Qwen3.7-Plus | 67.92% | 44.53% | 41.89% |

- 11 套系统在两种个性化条件下的平均表现均低于 Basic。
- Claude 的普通任务能力最强，但个性化表现不如 Seed，说明通用 GUI 执行能力不能完全代表个性化能力。

### 6.2 排序与流程偏好反复成为难点
- Outcome 通常最容易，Ranking 和 Process 普遍更困难。
- Seed 在显式画像下的 Process TSR 为 **47.17%**。
- 行为日志下，Seed 的 Outcome 为 **83.02%**，Ranking 仅 **45.28%**。
- 因而只报告个性化平均分，会掩盖候选比较、流程遵循等能力缺口。

### 6.3 显式画像不一定优于行为日志
- Seed 使用日志的平均 TSR 高于画像。
- M3A 则从画像条件的 **37.73%** 降至日志条件的 **18.49%**。
- M3A 与 T3A 使用相同底座但变化方向不同，提示上下文效用取决于整个工作流如何处理信息。

### 6.4 两项突出瓶颈是证据筛选和触发识别
在失败衍生诊断集上：
- P2 平均准确率：**40.06%**；
- P4 平均准确率：**39.69%**；
- P3：**88.80%**；
- P1、P5：均超过 **98.9%**。

这些结果表明：在该诊断设置下，“知道偏好是什么、激活后该怎么做”相对容易，**“哪些历史真正支持它、现在是否应当应用它”更困难**。但各探针形式与评分难度不同，不能将这些分数直接等同于真实执行中的能力上限。

### 6.5 证据指导有帮助，但依赖基础执行能力
- 在 85 个任务的干预子集上，Seed 从原始日志条件的 **76.47%** 提升至证据标注条件的 **83.53%**，提升 **7.06 个百分点**。
- 对 Seed 与 Qwen3.7-Plus，标注全部日志优于直接删除噪声；“噪声标签提供对照线索”是作者提出的可能解释，尚未被单独验证。
- Qwen3-VL-8B-Thinking 虽然诊断较强，端到端成功率仍低，说明偏好理解不能替代基本 GUI 操作能力。
- 替换记忆模块后，排序与流程偏好的相对困难仍然存在。

## 7. 优点与亮点

- **问题刻画贴近执行本质**：将个性化区分为“如何影响决策”和“何时生效”，比只检查是否记住偏好更有解释力。
- **重视过程正确性**：避免将“买对了但未确认”“选对了但未比价”误判为成功。
- **任务—探针配对设计**：将抽象能力测量与实际 GUI 失败关联，增强诊断的可操作性。
- **独立探针隔离错误传播**：有助于定位已知偏好条件下的证据判断和时机判断问题。
- **配对上下文控制合理**：保持任务条件一致，比较画像与日志的实际价值。
- **有干预而非只有相关性分析**：证据标注实验为改进方向提供了比失败共现更强的支持。
- **提供替代记忆构建检验**：减少主要结论完全依赖单一日志表达方式的风险。

## 8. 不足与局限

### 8.1 数据真实性与覆盖范围
- 日志由画像合成，不是真实用户长期自然产生的历史；即使经过人工审核，仍可能偏短、偏整齐，包含较强的语言提示。
- 缺少对长期偏好漂移、历史冲突、多人共享设备、跨会话更新等问题的充分覆盖。
- 每个任务家族分别设置五种偏好，便于控制变量，但真实任务中常同时存在多种甚至冲突的偏好，相关覆盖有限。

### 8.2 失败衍生诊断的选择偏差
- 探针来自既有系统的失败案例，适合定位这些系统的弱点，但不是对全部个性化状态的随机采样。
- 因此，P2/P4 是“本诊断集上的主要弱项”，不宜直接推广为所有真实用户任务中的普遍瓶颈。

### 8.3 探针难度与真实执行存在距离
- P2 采用多选精确匹配，P4 往往包含多个状态且要求全部正确，评分比单项选择更严格。
- P1/P5 的接近满分，可能部分来自选项提示、正确前提和语义级测量，不能证明系统已充分解决真实偏好归纳或动作执行。
- 缺失、截断或不可解析的诊断响应被排除；若不同模型排除比例不同，跨模型比较需结合覆盖率理解。

### 8.4 干预结论的外推限制
- 证据标注依赖人工参考答案，相当于提供 oracle 信息，真实系统仍需自动识别这些证据。
- 7.06 个百分点来自 P2 富集子集，不代表完整 benchmark 或真实部署中的平均收益。
- 尚未对 P4 触发识别进行同等程度的受控干预，因此其因果影响主要仍由诊断和失败共现支持。

### 8.5 公平性、统计与资源披露
- 原生接口、历史窗口和采样参数不完全统一，难以把差异完全归因于模型本身。
- 缺少重复运行与置信区间，对小幅提升的稳定性判断不足。
- Process 任务通常更长；统一 65 步预算可能同时测量流程遵循能力与长轨迹执行压力，二者尚未充分分离。
- 未披露完整运行成本，限制成本—性能评估；记忆模块也并非在统一检索策略下比较，不宜视为其通用能力排名。

**总体而言，论文最有价值的贡献是把个性化失败从“任务没做好”细化为可定位、可干预的能力问题。其证据支持优先关注历史证据筛选与偏好触发时机，但尚不足以证明这些结论可以无条件推广到真实、长期、复杂的个人助手场景。**
