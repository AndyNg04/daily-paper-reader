## 摘要
智能体能够创建丰富的表示形式，但这些表示形式很少被用作表达用户意图的媒介。我们提出了智能体绑定式用户界面（Agent-Bound UI）这一交互模型，将可复用的交互结构与特定任务的含义分离。智能体将特定任务的含义绑定到可复用视图中的交互上，并将生成的绑定关系发布为共享状态，使人类与智能体能够理解并操作共享界面，同时允许界面含义随任务而变化。我们实现了 ABRA，这是一个与框架无关的 Agent-Bound UI 原型，用户与智能体可通过聊天和共享交互画布协作。我们通过一个代表性用例展示 ABRA，并评估了四个由大语言模型（LLM）驱动的智能体在画布创作、所有者侧后果处理和跨智能体调用方面的表现。代码和演示视频见 https://github.com/megagonlabs/abra。

## Abstract
Agents can create rich representations, yet these representations are rarely used as a medium for expressing user intent. We present Agent-Bound UI, an interaction model that separates reusable interaction structures from task-specific meanings. Agents bind task-specific meanings to interactions in reusable views and publish the resulting bindings as shared state, enabling humans and agents to understand and act on shared surfaces whose meanings vary across tasks. We implement ABRA, a framework-agnostic prototype of Agent-Bound UI, in which users and agents collaborate through chat and shared interactive canvases. We demonstrate ABRA through a representative use case and evaluate four LLM-backed agents on canvas authoring, owner-side consequence resolution, and cross-agent invocation. The code and demo video are available at https://github.com/megagonlabs/abra.

## 1. 核心问题与研究背景

### 1.1 研究动机：输出越来越丰富，输入仍以聊天为主

当前智能体已经能够通过表格、流程图、交互式 HTML 等形式展示任务结果，但用户通常仍需用自然语言说明修改意图，形成了**“表示—交互不对称”**：

- **输出侧**：结构化、可视化、可交互。
- **输入侧**：仍主要依赖聊天，难以直接围绕屏幕上的具体对象表达意图。

例如，用户已经看到一个任务关系图，却仍需要用文字描述“把这个节点连接到那个节点”。对于难以语言化、但容易通过点击、拖动或编辑表达的意图，这种方式可能低效且含糊。

### 1.2 现有方案的缺口

论文将相关系统概括为三类：

| 路线 | 优势 | 论文指出的主要局限 |
|---|---|---|
| 生成式界面 | 为特定任务生成新界面，适应长尾需求 | 交互含义通常固化在生成代码中，跨任务复用有限 |
| 组件组合式界面 | 利用按钮、表单等组件快速构建界面 | 对复杂表示上的任务特定操作支持不足 |
| 任务专用交互系统 | 支持丰富、深入的领域操作 | 界面及交互语义与特定应用绑定 |

ABRA 关注的空缺是：**表示和操作结构可以复用，但同一种操作在不同任务中的含义会变化。**

例如，同样是图中的“添加边”：

- 在项目计划中表示“建立任务依赖”；
- 在社交网络中表示“建立人物关系”。

因此，论文主张将**可复用交互结构**与**任务特定语义**分离，并把语义公开为共享状态，使其他参与者也能理解并调用。

## 2. 方法论：核心思想与技术流程

### 2.1 Agent-Bound UI：结构复用，语义动态绑定

论文提出的 Agent-Bound UI 包含三个核心机制：

1. **定义可复用的交互词汇**：视图提供元素类型和可执行动作。
2. **绑定任务语义**：智能体说明元素对应什么任务对象，以及每项动作在当前任务中意味着什么。
3. **发布绑定关系**：将这些语义作为画布共享状态，而不是隐藏在创建者的内部逻辑中。

其核心关系可概括为：

> **任务交互 = 可复用视图中的动作结构 + 当前任务的语义绑定。**

这不是新的模型训练算法，而是一套**交互抽象、状态契约和工具调用机制**。

### 2.2 关键概念

- **视图（View）**：定义一种表示及其可用操作，例如表格中的行、列、单元格与编辑动作。
- **画布（Canvas）**：实例化一个或多个视图，包含任务内容、语义绑定及交互配置。
- **手势（Gesture）**：用户实际如何操作，如点击、拖动。
- **动作（Action）**：传递给智能体的抽象操作，如编辑单元格、添加边。
- **指称对象（Referent）**：界面元素对应的真实任务实体。不同视图中的同一实体可通过共享 `ref` 关联。

这种分层使“用户怎么操作”“执行什么动作”“动作意味着什么”彼此分离。

### 2.3 两种动作处理模式

| 模式 | 处理方式 | 示例 |
|---|---|---|
| **局部效果（Local effect）** | 由视图直接处理，不需要任务推理 | 选择、高亮、缩放、排序 |
| **后果（Consequence）** | 交给智能体进行任务相关推理后处理 | 修改内容、添加关系、删除对象 |

需要注意：

- 原型中，每种动作的处理模式是预先设定的。
- 需要推理的操作由**画布所有者智能体**处理。
- 用户发起的操作不一定被接受；所有者可以依据任务约束拒绝。

### 2.4 原型支持的视图

- **图视图**：节点、边；支持添加节点、连接关系、编辑和删除等。
- **表格视图**：行、列、单元格；支持编辑、增删、筛选、排序等。
- **文本视图**：段落、行；支持增删改、折叠和查找等。
- **展示视图**：展示项；支持聚焦、布局调整等，不提供内容修改类后果动作。

### 2.5 典型操作流程

1. 智能体调用 `create_canvas`，创建并拥有画布。
2. 发布任务内容、元素绑定、允许的动作及其语义。
3. 用户直接操作界面，或其他智能体通过 `read_canvas` 理解画布。
4. 其他智能体通过 `fire_action` 调用已发布动作。
5. 若动作需要推理，由所有者解析后，通过 `update_canvas` 更新状态。
6. 更新同步给参与者；任务结束后调用 `close_canvas` 关闭画布。

原型采用 **React 视图、Node.js 画布中心和 Python 智能体适配器**。其“框架无关”主要指交互模型及工具接口不绑定特定智能体平台，并不意味着原型没有具体技术栈。

## 6. 主要结果与发现

### 6.1 基础操作的结构成功率较高

| 操作 | Opus 4.8 | Haiku 4.5 | GPT-5.4 | GPT-5.4-mini |
|---|---:|---:|---:|---:|
| 创建画布 | 91.9% | 93.3% | 97.8% | 88.9% |
| 更新画布 | 98.0% | 100.0% | 100.0% | 98.0% |
| 跨智能体触发动作 | 100.0% | 91.9% | 97.0% | 66.7% |

结果说明，这套契约可以被多种大模型执行，但跨智能体调用对部分模型更困难。

GPT-5.4-mini 的 33 次调用失败中：

- 24 次错误调用 `update_canvas`，而非 `fire_action`；
- 8 次缺少必需的 `path`；
- 1 次未提交操作。

这反映出：**理解要修改什么，不等于能够遵循正确的调用路径和所有权边界。**

### 6.2 可执行不等于完整满足需求

画布创作中：

- 视图召回率仅为 **56%–78%**；
- 完整视图集合匹配率为 **33%–53%**；
- 动作召回率为 **53%–90%**；
- 动作完整集合匹配率为 **39%–80%**。

因此，模型通常能生成可运行画布，但容易遗漏用户要求的视图或交互。

### 6.3 语义绑定存在质量差异

- 元素绑定指标均达到 **100%**。
- 动作含义评分为 **76%–92%**。
- Haiku 有时只复述动作名称，没有说明任务特定效果。
- 跨视图共享 `ref` 的主动使用较少，Opus 在相关运行中没有实现该协调机制。

这意味着，**局部元素语义正确**与**跨视图实体协调完整**是不同能力。

### 6.4 跨智能体语义理解有潜力，但需注意统计条件

在结构有效的 `fire_action` 运行中，各模型的动作选择评分均为 **100%**，目标定位也接近满分。

这支持“其他智能体能够理解并使用公开语义”的可行性。但这些评分以结构有效运行为前提，**不能替代包含全部失败运行的总体成功率**。

## 7. 优点与亮点

- **问题定义清楚**：准确指出丰富输出与聊天输入之间的不对称。
- **抽象层次合理**：将手势、动作、任务语义和执行处理分离，支持复用与适配。
- **语义成为共享资源**：不仅服务界面创建者，也允许其他智能体读取和调用。
- **保留任务约束检查**：界面支持某项操作，不意味着智能体必须无条件执行。
- **聊天与直接操作互补**：并非试图完全取代自然语言，而是扩展表达渠道。
- **系统实现较完整**：包含多视图、共享状态、实体关联和工具生命周期。
- **实验揭示失败类型**：不只报告成功率，也展示遗漏需求、格式异常和错误调用路径。
- **评价透明度较好**：提供评价标准、提示词，以及代码和演示入口。

## 8. 不足、局限与应用边界

### 8.1 核心用户价值尚未直接验证

论文尚未证明：

- 用户能否准确理解动态绑定的交互含义；
- 是否比聊天更省时、更少出错；
- 操作被拒绝或被解释为更广泛修改时，用户是否感到可控。

例如，将单元格修改解释为全列规范具有帮助潜力，也可能超出用户原意，需要确认、预览和撤销机制支撑。

### 8.2 复用范围仍受视图词汇限制

当前只实现四类视图。能否覆盖地图、时间轴、空间设计等任务，以及如何发现更通用的交互词汇，仍未解决。

“无需重新生成界面”并不意味着无需新增视图开发。

### 8.3 长期协作与状态治理验证不足

共享语义和状态在持续使用中可能变化。论文尚未充分评估：

- 并发操作与冲突处理；
- 状态或语义版本不一致；
- 动作依赖旧状态时的处理；
- 所有者故障或响应延迟；
- 多步操作的回滚和追溯。

### 8.4 所有者解析可能成为瓶颈

由所有者统一处理后果有助于维护任务一致性，但也可能形成性能瓶颈或单点依赖。论文未提供吞吐量、并发负载或容错实验。

### 8.5 评价存在潜在偏差

- 单一 LLM 裁判不能替代人工一致性验证。
- 部分指标仅对适用运行或结构有效运行计算，需谨慎理解分母。
- 跨视图协调作为可选指标报告，其低覆盖可能被条件成功率掩盖。
- GPT-5.4 某些规格结构虽被契约允许，却在格式评价中被视为异常，说明“合法”与“推荐”格式之间仍有边界问题。

### 8.6 安全与权限保障仍需完善

**以下是进一步分析，而非论文已验证的结论：**

当智能体依据共享状态调用动作时，还需要考虑语义篡改、提示注入、越权更新、破坏性动作确认和审计追踪等风险。当前实验主要检验正常条件下的执行能力，并未验证对抗环境中的安全性。

**总体评价**：ABRA 最有价值的贡献，是提出并实现了“**可复用交互结构 + 任务语义绑定 + 公开共享状态**”这一协作层。现有结果支持其工程与模型执行可行性，但尚不足以证明它在真实人机协作中优于聊天或其他界面方案。
