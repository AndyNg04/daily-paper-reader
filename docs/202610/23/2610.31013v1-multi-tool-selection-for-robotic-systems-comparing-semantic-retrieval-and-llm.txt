# Multi-Tool Selection for Robotic Systems: Comparing Semantic Retrieval and LLM 

Miguel Sousa 1, Luis Ramos Pinto 1, and João P. Matos-Carvalho 1 

> 1

LASIGE, Faculdade de Ciências, Universidade de Lisboa, Portugal 

Abstract. Natural-language interfaces allow users to command robotic systems without interacting directly with mission planners or robotics middleware. Their reliable use depends on robot tool routing, defined here as the selection of the smallest complete subset of predefined exe-cutable capabilities required to satisfy a request. This task is particularly difficult for compound instructions, where incomplete selection may omit necessary sensing or monitoring capabilities, while excessive selection may expose irrelevant tools. We compare four routing strategies: three progressively refined ChromaDB-based methods – fixed-threshold re-trieval, relative-distance retrieval, and clause-aware aggregated retrieval – and a cloud-hosted 120-billion-parameter language-model baseline. The methods are evaluated on 164 manually annotated prompts organised into three complexity levels, from direct single-tool requests to compound requests requiring at least three tools. Using exact-match accuracy, com-pleteness, precision, a completeness-weighted composite score, and rout-ing latency, CDB-v3 achieves the best macro-average score among the retrieval-only methods, with 0 .7822, compared with 0 .8869 for the large-model baseline. Although the LLM provides higher routing quality, CDB-v3 exhibits substantially lower latency and can be deployed locally with-out requiring cloud connectivity. These results identify a quality–latency trade-off between direct large-model selection and clause-aware seman-tic retrieval for privacy-sensitive, connectivity-constrained, and resource-constrained robotic systems. 

Keywords: robotics · tool routing · semantic retrieval · ChromaDB · LLM 

# 1 Introduction 

Natural-language interfaces are becoming an attractive way to interact with robotic systems. Instead of invoking commands through mission planners, ter-minals, or custom graphical interfaces, users can express requests directly in nat-ural language, such as “land the drone”, “start mapping the area”, or “report the current battery level”. Large language models (LLMs) make such interfaces increasingly practical, but a critical challenge remains: mapping a user request to the correct robot capability or set of capabilities. In robotics, capability selection is not merely a usability problem. A rout-ing error may activate an incorrect process, produce misleading information, or

issue an unintended command to the robot. As the number of available robot functions grows, reliable intent-to-capability matching becomes a fundamental requirement for safe and effective natural-language control. Traditionally, this decision logic is encoded through behaviour trees, state machines, launch config-urations, or manually designed if–then rules that determine which robot capabil-ity should be activated under each condition. These approaches remain effective for predefined and well-structured workflows, but they become increasingly diffi-cult to design, extend, and maintain as the number of capabilities, mission types, operating conditions, and possible user requests grows. Conversational interfaces shift part of this burden from handcrafted decision logic to runtime capability selection, making the routing layer a critical component of the overall system. This challenge is particularly relevant in ROS-based systems, where a single robot or fleet may expose dozens of processes for navigation, mapping, moni-toring, mission execution, telemetry collection, payload operation, and system management. A request may require one capability or a coordinated set of ca-pabilities. For example, the instruction “monitor the battery and land when it drops below 25%” requires both a telemetry capability and an actuation capabil-ity. The routing layer must therefore determine not only which capabilities are semantically relevant, but also whether several tools must be selected to satisfy all parts of the request. Large LLMs can perform this selection directly by receiving the complete tool catalog and reasoning over the user request. However, dependence on a cloud-hosted model may be impractical in robotic deployments with intermittent connectivity, limited bandwidth, high communication latency, or strict confiden-tiality and data-sovereignty requirements. Robot telemetry, mission information, maps, and operational commands may be unsuitable for transmission to exter-nal infrastructure. Even when a large model can be deployed locally, its memory, computational, energy, and latency requirements may exceed the resources avail-able at the robotic edge. These constraints motivate lighter routing mechanisms that can execute locally, while preserving as much selection quality as possible. This paper studies tool routing as a bounded multi-label selection problem. The router cannot invent commands or generate arbitrary executable code. In-stead, it must select a subset from a fixed allowlisted catalog of 42 robot tools. We compare four implementations of this routing function: CDBv1, which uses a fixed semantic-distance threshold; CDBv2, which uses a threshold relative to the nearest result; CDBv3, which decomposes compound prompts into intent-like clauses and aggregates their retrieval results; and a cloud-hosted 120-billion-parameter LLM that performs direct selection from the complete catalog. The evaluation uses 164 manually annotated requests divided into three complexity levels: 43 direct single-tool requests, 52 consequential requests re-quiring exactly two tools, and 69 compound requests requiring three or more tools. All routers are evaluated against the same ground-truth assignments using exact-match accuracy, completeness, precision, a completeness-weighted compos-ite score, and routing latency. The main contributions of this work are the formalisation of robotic tool routing as bounded multi-label capability selection, an empirical comparison of fixed-threshold, relative-distance, and clause-aware semantic retrieval under the same tool catalogue and prompt dataset, and a direct comparison between the strongest retrieval-only method and a large cloud-hosted LLM, exposing the resulting trade-off between routing quality and latency. The results show that CDBv3 is the strongest retrieval-only strategy. Its macro-average composite score is 0 .7822, compared with 0 .5863 for CDBv2 and 0.3330 for CDBv1. The 120B LLM achieves a higher score of 0 .8869, but CDBv3 provides substantially lower routing latency and does not require cloud connec-tivity. The results therefore do not establish retrieval as a universally more accu-rate replacement for large-model routing. Instead, they show that clause-aware semantic retrieval is a practical local alternative when latency, connectivity, com-putation, privacy, or data sovereignty are primary deployment constraints. 

# 2 Related Work 

Tool-using language-model agents combine natural-language interpretation with calls to external functions or services. ReAct alternates reasoning, action selec-tion, and observation, allowing an agent to update its behaviour after receiving the result of a tool invocation [15]. Toolformer investigates whether language models can learn when to call external tools, which tool to use, which argu-ments to provide, and how to incorporate the returned result into subsequent generation [13]. ToolLLM extends this problem to large collections of real-world APIs and includes both single-tool and multi-tool instructions [11]. In embodied systems, Code as Policies translates natural-language instruc-tions into programs composed from predefined perception and control APIs [9]. SPINE uses language models to interpret incomplete mission specifications and connect them to semantic planning for ground and aerial robots [12]. These systems show that language models can mediate between human requests and executable robotic functions. Their principal focus, however, is task planning, policy generation, or orchestration rather than a controlled comparison of rout-ing mechanisms for selecting from an allowlisted set of independently executable robot tools. The present work treats tool selection as a separate classification and retrieval problem. The router cannot invent arbitrary commands, modify tool names, or directly generate shell instructions. It must return one or more known capability definitions whose executable interfaces are specified in advance. This restriction bounds the action space and separates probabilistic language understanding from the robot’s execution boundary. Dense retrieval represents queries and candidate records as vectors in a shared embedding space, allowing semantically related items to be matched even when they do not contain the same surface terms. Dense Passage Retrieval demon-strated the effectiveness of learned dense representations for selecting relevant passages from large collections [6]. Retrieval-augmented generation subsequently 4 M. Sousa, L. R Pinto, and J. P. Matos-Carvalho 

combined a neural retriever with a generative model, conditioning generation on retrieved external records [8]. Although the present study does not use retrieval to provide candidates to a smaller generative model, the underlying retrieval principle is relevant: a natural-language request is compared against textual de-scriptions of known capabilities, and the nearest capability records are used to determine the routing output. ChromaDB (CDB) is used as the implementation substrate for dense capa-bility retrieval [5]. Each allowlisted tool is stored with a textual summary, de-scription, and associated metadata. At query time, the user request is embedded and compared with the stored capability embeddings. CDB supports approxi-mate nearest-neighbour search through a Hierarchical Navigable Small World index [10]. CDB itself is not proposed as a new routing algorithm in this work; it provides vector storage, indexing, and similarity search. The evaluated contribu-tion lies in the routing policies implemented above this infrastructure, including fixed-distance filtering, relative-distance filtering, and clause-aware aggregation. Related retrieval-based systems have also been studied in software engineer-ing. Chen et al. evaluate a retrieval-augmented framework in which relevant code is selected from a repository before being supplied to a language model [4]. Koziolek et al. retrieve validated industrial function blocks for inclusion in LLM-generated control programs [7]. These works demonstrate how retrieval can con-nect generative models to existing domain-specific components. In contrast, the present work does not generate control code. It evaluates whether semantic re-trieval alone can select the predefined processes required by a robotic request. Agent-oriented software systems further illustrate the value of bounded tool sets. RepairAgent plans and invokes software-analysis and validation tools dur-ing program repair [3], while Batole et al. use an agent-oriented approach for locating software-design issues [1]. SALLMA proposes separate operational and knowledge layers for LLM-based multi-agent systems, including intent manage-ment, orchestration, and persistent agent configuration [2]. These architectures are related to the separation between capability descriptions, routing, and execu-tion considered here, but their evaluation targets software repositories or broader agent architectures rather than real-time robotic capability selection. The reliability of the routing boundary is important because retrieval and LLM components introduce integration failure modes beyond model accuracy alone. A study of open-source LLM applications with retrieval support identi-fied recurring functionality, efficiency, and security defects [14]. These findings support treating routing, output validation, and process execution as explicit components rather than combining them into an unrestricted end-to-end agent. Previous research has established that LLMs can invoke tools, generate poli-cies, coordinate multi-step tasks, and use retrieved context. Less attention has been given to the narrower routing boundary between an unconstrained natural-language request and a fixed set of robot-facing processes. In particular, there is limited empirical evidence comparing different embedding-only retrieval policies with direct large-model selection under the same capability catalog, annotations, and evaluation metrics. # 4 Routing Strategies 

We evaluate four implementations of the routing function in Eq. 2. CDBv1: Fixed-Threshold Retrieval At startup, each tool representation is embedded and inserted into an in-memory ChromaDB collection. At runtime, the complete user request is embedded and queried against the collection. Let 

d(x, t i) denote the vector distance between request x and tool ti. CDBv1 returns ̂

Yv1 (x) = {ti ∈ T : d(x, t i) ≤ τabs }, (13) where τabs = 0 .85 is a fixed global threshold. This method is inexpensive and straightforward to inspect. However, a sin-gle threshold must account for requests with different ambiguity and semantic complexity. A strict value may omit required tools, particularly for compound requests, whereas a permissive value may return several semantically related but unnecessary tools.

d(x, t i) ≤ (1 + ρ)dmin (x), ρ = 0 .60 . (15) The relative rule adapts the candidate-set size to the local distance structure of each query. When several tools are similarly close to the request, several may be returned. When the nearest result is clearly separated from the remaining cat-alog, the method returns a smaller set. CDBv2 therefore reduces dependence on one absolute distance scale, but it still embeds each request as a single undivided sequence. 

CDBv3: Clause-Aware Aggregated Retrieval CDBv3 is designed to im-prove retrieval for requests containing several conditions or actions. It searches both the complete request and a set of intent-like fragments extracted from it. The query set includes: (i) the full prompt; (ii) fragments separated by commas, semicolons, and coordinating terms such as and and then ; and (iii) condition or action fragments around terms such as if , when , before , and after . Duplicate or empty fragments are discarded. For example, the request 

“if the battery is low, land and announce a warning” 

can generate separate queries for “the battery is low” , “land” , and “announce a warning” , in addition to the complete prompt. Each fragment is queried inde-pendently. For every fragment, CDBv3 starts with the nearest match and retains at most three tools whose distance remains close to the best result. The retrieved records are then aggregated by tool. while lexical matches between the request and the tool name, summary, or de-scription provide additional support. The aggregated candidates are ranked, and the list is truncated using a score-gap value of 0.28 and a maximum output size of 8. CDBv3 remains a retrieval-only router: no language model performs a second selection stage. 

Direct 120B LLM Baseline The baseline provides a cloud-hosted 120-billion-parameter language model with the complete tool catalog and the original user request. The model is instructed to return the smallest complete set of catalog tools required to satisfy the request, using a fixed JSON schema and without inventing or renaming tools. Unlike embedding retrieval, the LLM can explicitly interpret logical opera-tors, monitored conditions, dependencies, and compound instructions. For ex-ample, it may infer that conditional landing requires both the tool that observes the condition and the tool that performs the action. The baseline, however, re-quires the complete catalog to be included in every request and depends on cloud connectivity, structured-output reliability, and remote inference latency. 

# 5 Routing Results 

5.1 Experimental Setup 

The 42-tool catalog (sensors and actuators) was designed by a robotics domain expert, who ensured that tool capabilities do not overlap. The prompt set was constructed to cover every sensor and actuator at each complexity level, maxi-mizing diversity, and the same expert assigned the ground-truth tool set to each prompt. CDB methods use mxbai-embed-large:v1 (Ollama) with ChromaDB 1.5.9 

(distance metric l2 , index configuration M =16, ef_construction =100, ef_search =100). The CDBv1–CDBv3 hyperparameters (Section 4) were selected through manual iteration directly against the same 164-prompt benchmark used for evaluation, rather than on an independent development set, so the scores reported below should be read as best-case, upper-bound estimates. The direct LLM baseline uses gpt-oss:120b-cloud (digest 569662207105 ; temperature 1.0; 120s time-out, no retry) and is run 10 times per prompt, in contrast to the deterministic CDB routers, which are run once. Malformed responses are parsed as JSON with a regex fallback; out-of-catalog names are kept as false positives; empty or unparseable responses yield no selected tools. Latency measurements were performed on an Intel Core i5-9600K CPU (3.70GHz), 24GB DDR4 RAM, and an NVIDIA RTX 5060 Ti (16GB VRAM) used for local inference acceleration, running Ubuntu. The cloud baseline was accessed over a home broadband network via a wired Ethernet connection. The analysis is organised in two stages. First, CDBv1, CDBv2, and CDBv3 are compared to determine how the successive retrieval refinements affect routing quality. Second, the strongest retrieval-only method, CDBv3, is compared with Multi-Tool Selection for Robotic Systems 9

the direct 120B LLM baseline. Results are segmented by request type and re-ported using exact-match accuracy, completeness, precision, the composite score 

L, and end-to-end routing latency. 

5.2 CDBv1, CDBv2 and CDBv3 

Figure 1 shows that the retrieval refinements substantially improve performance over the fixed-threshold baseline. CDBv1 has very low exact-match accuracy: its fixed threshold keeps most required tools (completeness between 87% and 100%) but also admits many unrelated ones. CDBv2 improves direct single-tool routing by adapting the cutoff to the nearest result, but its performance remains limited for compound requests. CDBv3 provides the strongest overall retrieval-only result. Clause-level queries allow different conditions and actions to contribute separate evidence, which improves completeness for two-tool requests and accuracy for multi-tool requests. The improvement is not uniform across every metric and request. CDBv3 may retrieve additional semantically related tools, so gains in completeness can be accompanied by false positives. Precision must therefore be considered together with exact match and completeness rather than treating retrieval recall as the only objective.

Latency is measured end-to-end, so it includes not only algorithmic execution but also confounding factors such as network conditions, cloud server availability, and inference queuing. We report it here in a comparative, order-of-magnitude sense rather than as an isolated measure of computation: even accounting for these factors, the local system consistently operates on the order of milliseconds, while the cloud-hosted baseline operates on the order of seconds. The quality advantage of the LLM is accompanied by substantially higher and more variable latency. Figure 5 shows that CDBv3 remains close to the local retrieval time across all request types, whereas the cloud baseline exhibits second-scale latency and larger outliers. The comparison therefore reveals a deployment trade-off rather than a single dominant method: the LLM provides better routing quality, while CDBv3 provides faster and connectivity-independent selection. 

5.4 Composite Score 

Table 1 reports the composite score for each request type. The final column is the macro-average of the three type-level scores. CDBv3 is the strongest retrieval-only router for all three types and improves the macro-average score by approx-imately 0 .196 over CDBv2. The direct LLM retains the highest routing score, exceeding CDBv3 by approximately 0 .105. Accordingly, the principal result of the short study is not that retrieval surpasses the large model in routing quality, but that clause-aware retrieval closes part of the quality gap while preserving a markedly lighter and faster deployment profile.

# 6 Conclusion 

This paper investigated the mapping of natural-language requests to the com-plete and minimal set of predefined robot tools required to satisfy them. The problem was formulated as bounded multi-label capability selection and evalu-ated using three embedding-based ChromaDB routers and a direct cloud-hosted 120-billion-parameter LLM baseline. The short benchmark contains 164 manu-ally annotated requests divided into direct single-tool, two-tool consequential, and three-or-more-tool compound categories. CDBv3 achieved the strongest performance among the retrieval-only meth-ods. Its macro-average composite score was 0 .7822, compared with 0 .5863 for Multi-Tool Selection for Robotic Systems 13 

CDBv2 and 0 .3330 for CDBv1. Clause-aware prompt decomposition and aggre-gation therefore provide a substantial improvement over both fixed-threshold and single-query relative-distance retrieval. The direct LLM baseline neverthe-less achieved the highest routing quality, with a macro-average score of 0 .8869. This distinction is important: the results support CDBv3 as a practical local alternative, but they do not show that retrieval-only routing is more accurate than direct large-model selection. The latency results expose a complementary advantage. CDBv3 executes locally and produces substantially lower and less variable end-to-end routing la-tency, whereas the baseline depends on cloud inference and network conditions. The preferred routing strategy therefore depends on deployment priorities. Di-rect large-model routing is preferable when selection quality is the dominant criterion and cloud access is acceptable. Clause-aware semantic retrieval is at-tractive when local execution, predictable response time, privacy, connectivity independence, or limited edge resources are more important. The paper has a limitation regarding retrieval-only results: the CDBv1– CDBv3 hyperparameters (Section 5.1) were tuned through manual iteration on the same 164-prompt benchmark used for the final evaluation, rather than on a held-out development set. The reported CDBv1–CDBv3 scores should there-fore be read as best-case estimates rather than as an evaluation on independent data. We also tested a small, locally deployable LLM (7-8B class) as a can-didate edge baseline; the results were discouraging, with routing quality well below both CDBv3 and the 120B model, so it was excluded from the main comparison. Future work should evaluate larger and evolving catalogs, separate development and test sets for routing-parameter selection, robustness to para-phrases and prompt injection, and execution-aware metrics. The use of a smaller language model to refine a retrieval-generated candidate set is intentionally left for a separate study.
