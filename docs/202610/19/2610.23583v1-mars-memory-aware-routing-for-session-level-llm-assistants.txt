Abstract 

Long-term LLM assistants must repeatedly decide what prior context to expose and which model should answer as an interaction evolves. Existing memory systems and model routers usually make these decisions separately, although memory construction changes the evidence, distractors, and difficulty of the resulting input. We introduce MARS, a memory-aware routing framework that uses session state as a shared control interface between memory construction and model selection. A Query and Topic Manager (QTM) estimates compact decision-relevant state that guides a fixed state-conditioned memory policy and an online router, enabling each turn to receive an appropriate memory view and a suitable model under a quality–memory–cost trade-off. We evaluate MARS on R EAL MEM and M ULTI CHALLENGE with 16 system configurations each, covering long-history memory-driven interaction and bounded sessions with structured context interference. On R EAL MEM , MARS preserves 98.2% of full-context GPT-4o’s QA while using only 14.5% of its generation API cost, including both generation and controller calls for MARS, and achieves the strongest measured memory-recall and retrieval scores among compared systems. On M ULTI CHALLENGE , MARS trails the strongest static system overall but approaches its performance at lower recorded cost on a mechanism-focused subset. Together, these results support a favorable quality–memory–cost trade-off for long-history, memory-dependent interaction. 

# 1 Introduction 

Modern LLM assistants are no longer used only for isolated questions; they increasingly support ongoing work across many turns and sessions. In long-term use, interactions can span many turns and recur across tasks, a setting highlighted by recent work on long-term conversational and memory-driven agents (Maha-rana et al., 2024; Park et al., 2023; Packer et al., 2023; Bian et al., 2026). Users may resume unfinished artifacts, request revisions, refer to earlier constraints, or ask for final answers that depend on decisions made several turns or sessions earlier. Before answering such turns, an assistant must decide both what prior context to include and which model should answer. This creates a quality–memory–cost trade-off: richer memory can provide necessary evidence but also increases context length and distractors, while stronger models can better interpret complex memory views but are more expensive. Existing systems usually handle these decisions separately. Memory systems store, update, and retrieve prior information (Lewis et al., 2020; Packer et al., 2023; Chhikara et al., 2025; Xu et al., 2025), while model routers select a generator from a candidate pool to trade off quality and cost (Chen et al., 2023; Hu et al., 2024; Ding et al., 2024; Ong et al., 2024; Nguyen et al., 2024; Poon et al., 2025; Wang et al., 2025). This separation overlooks a key dependency: memory construction determines what evidence, constraints, and distractors enter the prompt, while routing determines whether the selected model can use that context reliably and cost-effectively. This dependency makes memory construction and model routing inherently coupled. As Figure 1 illustrates, finalizing a launch brief requires using the updated launch date (May 19, superseding May 12) while preserving an earlier constraint of exactly three paragraphs. Omitting the constraint or exposing the obsolete date can cause errors, while an unsuitable model may fail even when the relevant memory is present. Motivated by this coupling, we study session-level adaptive memory routing : coordinating memory exposure and model selection throughout a session under a quality–memory–cost trade-off. We formulate this as a sequential decision problem: the system estimates session state, constructs a candidate memory view, selects a model, packs the view for that model, generates a response, and updates its routing preference from turn-level feedback. After generation, turn-level feedback updates the router, enabling lightweight adaptation without retraining the underlying LLMs. The QTM prompt, schema, guardrails, and state-to-memory mapping are fixed; the memory view varies by turn, while the router learns online. # 2 Related Work 

LLM routing and online model selection. Model routing reduces inference cost by selecting among candidate LLMs instead of using a single expensive model for every request. Prior work studies cascades, benchmark-trained routers, quality-aware routing, preference-trained routers, and dynamic model selection for quality–cost trade-offs (Chen et al., 2023; Shnitzer et al., 2023; Ding et al., 2024; Hu et al., 2024; Ong et al., 2024; Nguyen et al., 2024; Wang et al., 2025). Recent work builds on contextual-bandit foundations (Li et al., 2010; Chu et al., 2011; Abbasi-Yadkori et al., 2011) and frames multi-LLM choice as a sequential decision problem with feedback, preferences, or budget constraints (Poon et al., 2025; Panda et al., 2025; Wei et al., 2025). These methods primarily route from the current query, prompt, or learned query–model affinity. MARS differs in the decision interface: the router operates over structured session state, and this same state also controls memory construction. 

Long-term memory, adaptive retrieval, and session evaluation. Long-term memory systems help agents store, update, and retrieve information across interactions, from retrieval-augmented generation (Lewis et al., 2020) and generative agents (Park et al., 2023) to memory-management systems such as MemGPT, Mem0, and A-MEM (Packer et al., 2023; Chhikara et al., 2025; Xu et al., 2025). Long-context studies show that simply increasing context length does not guarantee reliable evidence use: agents still struggle with very long conversational history (Maharana et al., 2024), and models can fail depending on where evidence appears in the context (Liu et al., 2024; Bai et al., 2023). Closest to adaptive retrieval, MBA-RAG uses a multi-armed bandit to select retrieval strategies based on question complexity and retrieval cost (Tang et al., 2024); however, it does not jointly route the generator model or reason over evolving session state. Benchmarks such as R EAL MEM and M ULTI CHALLENGE evaluate complementary aspects of memory-driven and path-dependent multi-turn interaction (Bian et al., 2026; Sirdeshmukh et al., 2025). We use them to ask a different question: whether memory exposure and model routing remain reliable when the operating regime shifts from bounded session interference to longer histories, stronger memory pressure, and more difficult retrieval. 

# 3 Method: Session-Level Adaptive Memory Routing 

We study session-level adaptive memory routing : coordinating what memory to expose and which model to invoke during long-term assistant interaction. At turn t, the system observes the current query qt, previous interaction history H<t, and a persistent memory store Bt−1 containing active-task records, recent-turn summaries, and longer-term memories from earlier sessions. Let A be the candidate model pool. Before generating a response, the system builds a candidate memory view ˜ ct, chooses a model at ∈ A , and packs the final context ct(at) for that model. 3This formulation makes explicit how simpler systems restrict the decision space. A fixed configuration uses both a fixed memory policy ˜ ct = π0mem (qt, H<t, Bt−1) and a fixed generator a0. A routing-only system chooses at under a memory policy that does not share the router’s session-state interface, while a memory-only system adapts ˜ ct under a fixed generator. These abstractions are incomplete for session-level interaction because memory construction and at interact: the constructed context changes the input difficulty and evidence structure, while the selected model determines how reliably that context is interpreted. 

## 3.1 Session-State Interface 

MARS introduces an explicit state estimation step. A Query and Topic Manager (QTM) maps the current turn into a structured session state: 

zt = fQTM (qt, H<t, Bt−1). (1) Rather than producing a free-form summary, QTM emits a constrained control state designed around the two downstream decisions: constructing the candidate memory view ˜ ct and selecting the model at.We organize zt into three functional groups. First, session-continuity fields identify whether the turn continues the active thread, shifts topic, or enters a revision, verification, or synthesis phase. Second, memory-control fields indicate whether prior state is needed, which memory scope should be considered, whether recent history should be preferred, and how much evidence should be exposed. Third, routing-difficulty fields describe the expected burden placed on the generator, such as memory dependence, ambiguity, and interaction phase; the router later combines these state signals with pre-packing load statistics from the candidate memory view. These fields are control signals rather than topic labels: the memory policy uses them to determine what parts of Bt−1 enter ˜ ct, while the router uses them, together with the candidate-view statistics, to estimate which model capacity is appropriate. The full QTM schema and allowed values are provided in Appendix B.1, and the QTM prompt template is provided in Appendix B.2. The corresponding memory-view and router-feature mappings are detailed in Appendices B.3 and B.4. The key design is to use zt as the shared interface between memory construction and model routing, rather than treating retrieval as a preprocessing step and routing as a separate decision over the raw query. The QTM prompt, schema, guardrails, and mapping ψmem are fixed before evaluation, while the routing policy updates from online feedback. The two decisions are coordinated through a shared structured session-state interface.

# 4 Experimental Setup 

Our controlled experiments evaluate MARS across two complementary regimes. R EAL MEM tests long-history memory-driven interaction; M ULTI CHALLENGE tests bounded structured sessions with interference and path-dependent evaluation. The same 16-system matrix is used on both, enabling consistent comparison across the two regimes. 

## 4.1 Benchmarks 

REAL MEM . REAL MEM is an external benchmark for real-world memory-driven interaction (Bian et al., 2026). We evaluate its 10-persona evaluation slice: 10 personas and 1,415 queries. We report normalized QA, Mem Recall, Recall@20 (R@20), normalized discounted cumulative gain at 20 (NDCG@20), and API cost. Main quality and memory metrics are macro-averaged over personas; query-weighted aggregates and scored coverage are reported in the appendix. 

MULTI CHALLENGE . MULTI CHALLENGE evaluates state maintenance in bounded but structured multi-turn conversations (Sirdeshmukh et al., 2025). Our converted split contains 245 scenarios and 1,480 turns. Each scenario contains intermediate turns followed by a verification turn that uses the official binary rubric question as the final user query. The expected answer is YES when the supplied pass criterion is satisfied, testing whether the system preserved the required topic state and constraints (Appendix C.2). The four axes are I NFERENCE MEMORY (102 scenarios), I NSTRUCTION RETENTION (62), S ELF COHERENCE 

(46), and R ELIABLE VERSION EDITING (35). We report the full aggregate first and analyze the first and fourth axes (137 scenarios) separately because they directly test state recovery and local revision. Chunk size 3 bundles trajectories into context blocks with distractor sessions (Appendix C.2). For the MARS run, we use 

λcost = 0.002, matching the main R EAL MEM routing objective. 

## 4.2 Baselines 

For both benchmarks, we evaluate 16 systems formed from memory settings and model/router choices. Full-context baselines use one fixed generator for all turns: GPT-4o (OpenAI, 2024b), Qwen2.5 72B (Yang et al., 2024), Mixtral 8 ×7B Instruct (Jiang et al., 2024), or Llama3B (Meta, 2024). Memory baselines pair MEM 0 (Chhikara et al., 2025) or A-MEM (Xu et al., 2025) with each fixed generator. Routing baselines 6include a M ETA LLM-style router (Nguyen et al., 2024) and hybrids that combine M EM 0 or A-MEM with META LLM-style routing. MARS is the full system, using QTM-guided memory construction and online model routing. We use M EM 0 and A-MEM as representative plug-in memory substrates because they can be consistently crossed with fixed generators and routers across both benchmarks. QTM uses Qwen2.5-7B-Instruct (Yang et al., 2024) with a fixed prompt, schema, guardrails, and state-to-memory mapping. A GPT-4o-mini (OpenAI, 2024a) turn judge supplies local reward after generation; it never sees future turns, final labels, gold final answers, or benchmark pass decisions (Appendix B.5). 

## 4.3 Ablation Protocol 

We run diagnostic ablations on a fixed three-persona R EAL MEM evaluation slice containing 473 turns. All variants use the same candidate model pool, deterministic generation, and a matched top-10 historical retrieval budget. The slice uses λcost = 0.5, compared with λcost = 0.002 in the main R EAL MEM run; its retrieval budget also differs from the main policy’s top-k hints. Comparisons are therefore made within this diagnostic configuration. The ablations examine QTM-guided context construction versus raw-query semantic retrieval, QTM state/header exposure in the generator prompt, QTM-derived routing versus query-embedding routing with semantic or recency-based memory, and online adaptation via a no-update diagnostic. The no-update variant freezes the router at initialization, so we treat it as a stress test of online adaptation rather than as a tuned static-router baseline. Ablation metrics follow the official R EAL MEM 

evaluation pipeline, with QA normalized to the same scale as the main results. Full settings and diagnostics are provided in Appendix E. 

## 4.4 Evaluation, Cost, and Reporting 

For R EAL MEM , we use the official retrieval and generation evaluation pipeline, with GPT-4o as the final judge when judging is required. This final evaluator is separate from the GPT-4o-mini turn-level judge used for online routing updates. For M ULTI CHALLENGE , we use a GPT-4o path-aware final judge following the benchmark style: it checks trajectory continuity and final-answer correctness. A scenario passes only when both checks are accepted and the model’s parseable final YES/NO answer matches the expected criterion (Appendix C.4). For R EAL MEM , main tables report generator and QTM/controller API cost, excluding online feedback; Results separately reports reconstructed feedback-inclusive totals. For M ULTI CHALLENGE , the archived runs did not itemize QTM/controller cost separately, so tables retain the original run-level recorded-cost convention. Final benchmark evaluators and local memory compute and storage are excluded from these API cost views. The online reward uses only selected-generator cost (Appendix B.6). We bootstrap R EAL MEM 

by persona and M ULTI CHALLENGE by scenario, and separately test eight chunk orders on 30 fixed M ULTI -CHALLENGE scenarios; Appendix B.7 gives these diagnostics.

## 5.4 QTM Prompt and Controller Sensitivity

## C.2 MULTI CHALLENGE Conversion and Axes 

Of the 273 official M ULTI CHALLENGE scenarios, we reserved 28 (approximately 10%) for QTM prompt development and preliminary testing and excluded them from the reported evaluation split. The remaining 245 scenarios, comprising 1,480 turns, form the evaluation split; the split identifiers will be released with the implementation. We convert each scenario into a session-level memory-routing trajectory: intermediate turns provide the path over which systems must maintain state. The final verification turn uses the scenario’s official binary rubric question as the last user query. Under the supplied pass criterion, a trajectory satisfying the required memory and constraints supports the expected answer YES . This question originates from the official evaluation rubric; placing it in the assistant’s input trajectory is part of our conversion. In the converted evaluation format, intermediate turns are marked as eval_type=0 ; the final official rubric question is marked as eval_type=1 with its supplied PASS_CRITERIA ; exactly one eval_type=1 appears per scenario and it is always the final turn. ## C.3 Chunked Context Construction 

The current M ULTI CHALLENGE construction uses chunk size 3. A chunk bundles several session trajectories into a longer context block, creating topic interference. The system must identify the active trajectory, select relevant evidence, and ignore distractor sessions in the same chunk. The construction procedure is: 1. Group scenarios into chunks of size 3. 2. For each chunk, concatenate the trajectories into a shared context block. 3. Mark one scenario trajectory as the active trajectory for the current query. 4. Present the system with the chunked context and the active final-turn request. 5. Evaluate whether the final answer follows the active trajectory rather than distractor trajectories. This setting stresses both retrieval selectivity and model capacity because the correct response requires maintaining the active state under structured interference. 22 C.4 Final Evaluation Judges 

For R EAL MEM , we use the official retrieval and generation evaluation pipeline. The final reporting protocol uses GPT-4o as the generation/memory judge model where required, with retrieval-memory helpfulness evaluated using top-k = 5 evidence. This final evaluator is used only for benchmark reporting and is distinct from the step-level feedback path used for online routing updates. For M ULTI CHALLENGE , we use a path-aware final judge following the benchmark’s evaluation style. The judge first considers the trajectory through turns 1 to tmax − 1: whether the system maintained the correct topic memory, preserved constraints, and produced intermediate responses that support the final answer. It then evaluates the final turn at tmax by asking whether the maintained memory supports the response and whether the response itself is correct. A scenario is counted as passed under strict joint logic: the continuity/path verdict, final-answer judge verdict, and parseable model final-token answer must all satisfy the supplied pass criterion, with YES as the expected answer to the final official rubric question.

# G Deployment Feedback and Reproducibility 

## G.1 Replacing Turn-Level Judges with Deployment Feedback 

The experiments use a turn-level LLM judge to provide scalar feedback for online routing. This choice makes benchmark evaluation reproducible, but the MARS interface does not require the reward to come from an LLM judge. The online router only requires a scalar reward associated with the current state, selected model, response, and cost. In a deployed assistant, this reward could be replaced or supplemented by human or task-derived feedback. Examples include explicit user ratings, edit acceptance, task completion signals, human preference compar-isons, workflow success checks, or organization-specific quality audits. Over repeated interactions, such feedback could train a routing policy that reflects user-specific or domain-specific preferences. For example, one user may prefer cheaper models unless quality drops sharply, while another may prefer stronger models for revision or finalization tasks. This interface allows the routing policy to incorporate application-specific feedback without changing the shared-state memory construction and model-selection pipeline.
