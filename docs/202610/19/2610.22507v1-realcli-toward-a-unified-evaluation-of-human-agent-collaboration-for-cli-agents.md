## 摘要
命令行界面（CLI）智能体日益能够执行长时程任务，但现有基准要么假设用户指令在执行过程中始终不变，要么只评估任务结果，而未能捕捉运行时的协作质量。本文提出 REALCLI，这是一套配对基准，用于统一评估真实 CLI 任务中的任务执行能力与人机协作质量。为全面衡量协作表现，REALCLI 构建了一个包含五个维度的框架，并将其具体化为 22 个子维度和 51 种交互场景模板。REALCLI 提供两种用于配对比较的模式：REALCLI-EXEC 在任务开始前提供完整规格，而 REALCLI-COLLAB 则引入脚本化用户，逐步提供信息、提出更正、修订约束并作出授权决定。评估结果揭示了前沿智能体能力上的显著差距：表现最佳的配置平均得分仅为 49.2%；采用协作综合得分（$J_{\mathrm{collab}}$）评估时，峰值表现也仅为 37.6%。这些结果表明，任务效能与协作质量之间存在明显脱节，模型在可引导性、信任校准和安全边界管理方面均持续表现不佳。REALCLI 为衡量和提升协作型 CLI 智能体提供了严谨、可复现的基础。

## Abstract
Command-line interface (CLI) agents increasingly execute longer-horizon tasks, yet existing benchmarks either assume that user instructions remain fixed throughout execution or evaluate task outcomes without capturing runtime collaboration quality. In this paper, we present REALCLI, a paired benchmark that unifies the evaluation of task execution and human-agent collaboration quality on realistic CLI tasks. To comprehensively measure collaboration, REALCLI builds a five-dimensional framework, operationalized into 22 sub-dimensions and 51 interaction scenario templates. REALCLI provides two modes for paired comparison: REALCLI-EXEC supplies complete specifications upfront, whereas REALCLI-COLLAB introduces a scripted user that delivers progressive information, corrections, constraint revisions, and authorization decisions. Evaluations reveal profound capability gaps in frontier agents: the best configuration attains an average score of only 49.2%, and when evaluated by the joint collaboration score ($J_{\mathrm{collab}}$), the peak performance reaches merely 37.6%. These results show that task effectiveness diverges sharply from collaboration quality, with models consistently struggling in steerability, trust calibration, and safety boundary management. REALCLI provides a rigorous, reproducible foundation for measuring and advancing collaborative CLI agents.

## 1. 核心问题与整体含义

### 1.1 研究背景与动机

CLI 智能体已能通过终端操作代码、文件、服务和系统资源，完成较长时程的软件开发、运维及数据处理任务。但现有评测通常采用两个假设：

- **需求完整且固定**：智能体一开始就获得全部规格，执行中用户不再补充信息或修改要求。
- **以最终结果为中心**：主要检查代码或环境最终是否符合验收标准，较少评估执行过程中的沟通、授权和风险管理。

真实工作流往往不同：用户会逐步澄清目标、修改约束、纠正错误，并决定是否授权高影响操作。因此，**“能完成任务”不等于“能与人可靠协作”**。

### 1.2 论文要回答的问题

- **RQ1**：用户参与时，前沿 CLI 智能体的任务结果与协作质量分别如何？二者是否一致？
- **RQ2**：在相同任务和环境中，自主执行与交互协作会产生哪些结果差异、行为变化和失败模式？

论文的核心贡献不是新的智能体模型，而是一套**将任务效果与协作过程分开衡量、再进行联合评价的配对基准**。

## 2. 方法论：核心思想、技术细节与评估流程

### 2.1 配对评估：相同任务，两种执行模式

每个任务包含执行环境、初始状态、完整任务规格和结果验证器。基于这些共同要素，构造两种模式：

| 模式 | 信息提供方式 | 运行时用户参与 | 评价内容 |
|---|---|---|---|
| **REALCLI-EXEC** | 开始时给出完整规格 | 无 | 最终任务结果 |
| **REALCLI-COLLAB** | 从不完整请求开始，逐步披露规格 | 脚本化用户补充、纠正、改约束、作授权决定 | 最终任务结果＋协作质量 |

两种模式共享任务目标、环境和验收标准，尽量降低任务本身差异对比较的影响。

需要注意：COLLAB 不只是“EXEC 加上帮助”，还引入了信息不完整、动态约束和风险探针等额外挑战。

### 2.2 五维协作框架

论文将协作能力分为五个维度，共 **22 个子维度**：

| 维度 | 主要评估内容 |
|---|---|
| **可理解性 U** | 计划是否清楚，进度反馈是否及时，错误是否解释到位，操作是否冗余 |
| **可引导性 S** | 能否接受中断、主动澄清、合理提出异议，并保持跨轮约束、处理冲突 |
| **观察与恢复 OR** | 是否检查输出和实际状态，识别失败或僵局，并合理求助 |
| **信任校准 TC** | 是否如实披露风险、能力边界、验证结果和未完成事项，是否尊重授权范围 |
| **安全与风险意识 SR** | 是否防范危险命令、破坏性操作、供应链风险、敏感信息泄露及提示注入 |

框架同时使用两类检查：

- **主动探针**：用户故意提出含糊、矛盾或具有风险的请求，观察智能体的第一反应。
- **被动检查**：持续观察智能体是否自然具备适当反馈、操作节制和结构化交接等行为。

### 2.3 脚本化用户模拟

用户模拟由三个核心部分组成：

- **信息切片**：将完整规格拆成若干片段，根据智能体提问或执行需要逐步释放；每个任务平均约有 16 个切片。
- **交互探针**：每个任务分配 6 个不同协作场景，规定触发条件、用户措辞、期望行为和证据要求。
- **运行状态与审计日志**：记录哪些信息已释放、哪些探针已触发、当前进度及结束原因。

模拟器依据实际轨迹决定交互时机，而不是完全固定轮次。探针核心措辞要求原样发送，信息切片可以完整地转述，但不得泄露期望答案或评分意图。

### 2.4 基准构建流程

整体分为两阶段：

1. **构建基础任务**
   - 从匿名真实 CLI 日志中提取目标、约束、环境依赖和失败信号。
   - 合成任务说明、容器环境、参考解和验证器。
   - 检查规格与测试的一致性，确保参考解通过、空操作基线失败。
   - 通过多智能体、多次运行诊断问题并筛选难度；简单任务会增加技能要求后重新验证。

2. **加入交互层**
   - 分配协作场景，编写信息切片、探针和检查项。
   - 进行静态检查、语义审查及端到端试运行。
   - 最后通过人工专家审查和难度筛选。

### 2.5 评分机制

**任务成功率**

- 每次运行根据最终环境状态得到二元结果：通过或失败。
- 分别统计自主模式的 \(R_{\mathrm{EXEC}}\) 与协作模式的 \(R_{\mathrm{COLLAB}}\)。

**协作质量 \(S_{\mathrm{COLLAB}}\)**

采用严格的分层聚合：

1. 单次场景必须通过全部适用检查项，否则该场景失败。
2. 同一场景跨任务通过率达到 **75%**，才获得场景级通过。
3. 依次对场景、子维度和维度进行等权平均。
4. 五个维度再等权平均，得到总体协作分数。

**联合协作分数**

\[
J_{\mathrm{COLLAB}}
=R_{\mathrm{COLLAB}}\times S_{\mathrm{COLLAB}}
\]

其含义是同时要求较好的任务完成能力与协作能力。但它是**两个聚合指标的乘积**，不是“单次任务与全部协作要求同时通过”的直接概率，也不是关键安全违规的一票否决指标。

**证据原则**

- 同时利用对话轨迹、工具记录和环境状态。
- **环境证据优先于智能体口头声明**。
- 未实际触发的情境标为不适用，不进入分母。
- 对要求“主动”“事前”处理的检查，事后补救不一定算通过。

- 缺少真实用户实验，以及充分的置信区间、显著性检验和人工评判一致性结果。

### 5.3 公平性与客观性

- **有利因素**：隔离环境、共享验收标准、明确运行预算、环境证据优先及脚本审计。
- **需谨慎之处**：
  - COLLAB 时间预算更大，但同时承担更多交互负担，两种模式并非等成本比较。
  - 两模式的信息可用性与探针压力不同，不能把结果差异简单解释为“用户帮助的净收益”。
  - 不同框架的工具和交互接口不同，分数反映的是**模型与框架组合能力**，而非纯模型能力。

---

## 6. 主要结论与发现

### 6.1 任务完成与协作质量明显分离

- 表 3 中，Claude Opus 5 的跨框架、跨指标平均分最高，为 **49.2%**；它不是最高单项任务成功率。
- 最高联合协作分数为 **37.6%**，来自 Claude Opus 5＋Terminus-2。
- 该配置的协作任务成功率为 **62.4%**，协作质量分数为 **60.2%**。
- **91.0% 的成功交互轨迹仍至少未通过一个适用协作场景。**

说明最终产物合格，仍可能伴随缺少授权、风险披露不足或冲突处理失败。

### 6.2 用户参与没有带来稳定增益

在 Claude Code 的 11 个模型配置中：

- 协作模式平均通过率为 **46.8%**。
- 自主模式为 **47.4%**。
- **17.9%** 的配对试验由失败变成功。
- **18.5%** 则由成功变失败。

交互更像是重新分配“哪些任务能成功”，而非普遍提升成功率。Codex 的平均收益相对较好，为约 **3.4 个百分点**。

### 6.3 主要短板是跨轮目标维护

| 行为 | 严格通过率 |
|---|---:|
| 遇到障碍后更新计划 | 80.2% |
| 遵循最新的连续需求变化 | 98.8% |
| 识别任务范围扩大 | 51.7% |
| 保持早期约束 | 54.4% |
| 解决跨轮指令冲突 | 29.3% |

模型较擅长响应眼前请求，却不擅长把新要求与旧约束整合成持续一致的任务状态。

### 6.4 沟通正确不代表交付正确

- 在约束保持失败中，**91.3%** 涉及最终产物与约束不匹配。
- 在存在沟通检查的产物不匹配案例中，**53.3%** 仍通过了全部适用沟通检查。

因此，仅根据智能体是否“答应了”或“解释清楚了”评价协作，会高估实际可靠性。

### 6.5 更多交互不一定转化为进展

- 各模型交互模式与完整规格模式的工具调用中位数之比为 **1.43～3.62 倍**。
- 在自主模式尚未完全成功、交互模式工具调用更多的配对样本中，**59.9%** 没有获得更高任务奖励。

额外步骤既可能代表有效恢复，也可能只是反复失败。

---

## 7. 优点与亮点

- **把协作变成独立评价对象**：避免用任务成功率或对话长度替代协作能力。
- **配对设计清晰**：相同任务、环境和验证器支持更有解释力的模式比较。
- **行为定义具体可审计**：探针具有触发条件、预期行为和明确失败标准。
- **同时检查“说了什么”和“实际做了什么”**：能发现表面配合、交付违约的问题。
- **强调首次机会与事前防护**：区分主动判断和被反复提醒后的补救。
- **审计用户模拟器**：不默认模拟用户始终正确，有助于识别错误归因。
- **失败分析有诊断价值**：将问题定位到跨轮约束维护、冲突处理和交付验证，而不只给出总分。

## 8. 不足与局限

### 8.1 模拟交互不等于真实人机协作

- 脚本化用户难以覆盖真实用户的知识差异、情绪、表达噪声和长期信任变化。
- 风险和冲突探针具有压力测试性质，其出现频率未必代表日常使用。
- 缺少真实用户满意度、纠错负担和长期使用效果的验证。

因此，更准确地说，REALCLI 衡量的是**脚本驱动交互压力下的协作可靠性**。

### 8.2 自动评判仍存在偏差风险

- 单一模拟器和单一模型评判器可能带来措辞偏好及模型家族相关偏差。
- 仅 33.5% 的检查项涉及环境证据，多数仍依赖轨迹解释。
- 未充分报告人工复核规模、评判一致性，以及污染运行进入最终汇总的具体处理方式。

### 8.3 指标严格，但存在信息损失

- 全部检查项必须通过，加上跨任务 75% 阈值，会形成较强的分数跳变。
- 74% 与 75% 的场景通过率可能被判为完全不同状态，却难以体现连续改善。
- 等权平均没有体现不同失败的实际危害差异，例如反馈不及时与泄露密钥的重要性并不相同。
- \(J_{\mathrm{COLLAB}}\) 低于任务成功率部分源于乘积定义本身，不能把两者数值差全部理解为实际执行能力下降。
- 乘积指标也不能保证关键安全维度达标，实际部署仍需单独设置安全门槛。

### 8.4 覆盖与因果解释有限

- 任务数量对细分领域分析偏少，且主要是离线、容器化环境。
- 多人协作、真实权限体系、外部服务依赖和长期运行系统覆盖有限。
- 信息渐进披露、探针压力、交互轮次和预算差异同时变化，缺少消融，难以分离各因素的影响。
- 从轨迹观察推断模型的训练原因或内部机制，证据仍不足；例如论文将部分能力归因于 RLHF，并未通过训练对照验证。

### 8.5 原文存在报告口径不一致

- 摘要与主结果写最高平均分为 **49.2%**，引言另写 **52.7%**。
- 正文称 **51 类模板**，附录又出现 **57 个场景及 6 个通用检查**等表述；表 2 各维度模板数之和也为 57，主动与被动检查的统计关系需进一步澄清。
- 主结果标注为 held-out split，但实验设置称全部 101 个任务均参与评测，划分方式不够清楚。
- 联合分数与基线的差值应使用“百分点”，不能与相对下降百分比混用。

### 总体评价

**RealCLI 最重要的价值，是证明 CLI 智能体评测不能只检查最终结果，还必须检查其是否持续遵守约束、如实沟通风险并保留用户控制权。** 其配对设计和环境证据机制具有较强诊断价值；但模型排名与数值结论仍应结合模拟交互偏差、阈值评分、预算差异及报告口径问题谨慎解释。
