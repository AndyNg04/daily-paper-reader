# Not All Graphs Are Maps: A Task-Agnostic Exploration Framework for Mobile GUI Navigation

Abstract 

Modern mobile GUI agents can perceive visible screens and execute local actions, but they still lack persistent app-specific navigation knowl-edge: where functions live, which pages con-tain them, and which screens are equivalent across repeated visits. We introduce TAG-Nav, a Task-Agnostic Graph Navigation framework that wraps existing GUI-agent backbones with reusable destination memory. Offline explo-ration is distilled into compact records of app functions, target pages, and waypoint routes before any evaluated instruction is seen. When a future task’s destination is covered, TAG-Nav retrieves the destination and provides route guidance without task-specific demonstrations. This separates mobile GUI destination navi-gation from full task completion: many tasks share the prefix of reaching the right page, while final actions may enter content, send data, make purchases, delete information, or change sensitive settings. To evaluate route finding without downstream execution confounds, we introduce DestBench, a navigation-only proto-col that asks whether an agent reaches the cor-rect pre-action destination screen. DestBench enables a controlled graph-memory study com-paring no-memory agents with random, auto-mated BFS, and clean graph memory. Graph-derived memory improves strict navigation success rate of UI-TARS-1.5-7B from 52.4% without graph memory to 58.3% with auto-mated BFS memory, and improves Qwen-VL-Max success rate from 59.5% to 71.4% on the same conditions. Together, TAG-Nav and DestBench 1 show that destination coverage and route cleanliness strongly shape graph-memory value, making graph quality a measured vari-able rather than an assumed benefit of explo-ration.

1 Introduction 

Modern multimodal GUI agents perceive screens and execute visible actions well, but they lack a per-sistent map of the apps they operate (Zhang et al., 2025a; Wen et al., 2024; Qin et al., 2025). When asked to reach a deep setting, account-management page, privacy control, or app-specific tool, the agent must re-infer where the function lives and how to navigate there from the current screen on every task. Many user requests share the prefix of arriv-ing at a destination before any task-specific (and often sensitive or irreversible) final action: reaching an account-privacy screen is reusable navigation, while toggling the control itself is task-specific ex-ecution. We study mobile GUI destination navigation 

as a problem distinct from full task completion, focused on whether the agent reaches the correct pre-action destination screen. The standard response is to explore the app of-fline and retrieve from the resulting graph (Wen et al., 2024; Guan et al., 2025; Xie et al., 2025; Chen et al., 2025b), but exploration does not au-tomatically yield a useful map: a large random graph can have low target coverage and noisy routes, while a small clean graph can be highly navigable. Two graph-construction properties de-cide whether explored memory actually helps: tar-get coverage of the destinations users request, and 

route cleanliness from the app root to those des-tinations. We argue that graphs satisfying both, built by task-agnostic breadth-oriented exploration and post-processed into destination-anchored dedu-plicated routes, are the design that turns offline exploration into navigation memory that wraps any visual GUI actor. We instantiate this design in TAG-Nav, a Task-

Agnostic Graph Nav igation framework that wraps existing visual GUI agents with destination mem-arXiv:2610.22672v1 [cs.AI] 15 Oct 2026 ory without retraining. TAG-Nav explores apps with task-agnostic local breadth-first search (Local-BFS) and post-processes the result into compact destination records (target page summary, intents, waypoint route, transition hints); at inference time the matching record is injected as plain text into an unmodified backbone such as UI-TARS (Qin et al., 2025). The retrieved unit is a destination plus its route, not a per-task trajectory replay, so TAG-Nav can be evaluated under different graph-construction conditions while holding the actor and task set fixed. To evaluate this design on real apps, we intro-duce DestBench, a navigation-only protocol on real Android apps that judges whether the agent reaches the correct pre-action destination screen, with graph-aware target coverage and route clean-liness diagnostics. End-to-end task benchmarks would otherwise conflate memory quality with downstream execution, blurring the properties we want to measure. On 84 DestBench tasks span-ning six apps, TAG-Nav achieves higher observed navigation success than a no-memory baseline across two GUI backbones (Table 3). Controlled comparisons against random-exploration and clean manual-graph conditions examine the roles of tar-get coverage and route cleanliness (Table 6). Our contributions are: • TAG-Nav , a task-agnostic destination-memory module that wraps an unmodified visual GUI actor: offline exploration becomes compact destination records (target page, waypoint route, transition hints) injected as plain text at inference. • DestBench , a navigation-only page-reaching protocol on real Android apps with graph-aware diagnostics for target coverage and route cleanliness.

These benchmarks are valuable, but their success criteria usually mix navigation with downstream execution: typing user-specific content, changing app state, sending information, selecting items, or satisfying procedural completion checks. Because they sample task completion across many apps, they also provide limited visibility into how well app-specific memory covers the functional regions of a single target app. DestBench instead isolates page-reaching navigation by asking whether the agent reaches the pre-action destination screen for a given task. App Exploration and App-Specific Memory. 

Several systems build app-specific knowledge be-fore task execution. Earlier UI-guided testing tools such as DroidBot built app state-transition mod-els through device interaction, providing an im-portant predecessor to app exploration for automa-tion (Li et al., 2017). AutoDroid explores An-droid apps, builds a UI transition graph, and turns view-hierarchy/accessibility states into simplified HTML prompts and simulated-task app memory (Wen et al., 2024). Its memory is structured around explored UI trees, elements, and actions rather than visual screen perception, making it a strong early example of exploration-based app memory. AppA-gent and AppAgent-v2 use autonomous or manual exploration to build app documents for later task ex-ecution (Zhang et al., 2025a; Li et al., 2025). Their memory is element- and document-centered: per-element notes consulted on the current screen, not destination memory keyed to a target page. GUI-Xplore uses pre-recorded exploration videos and converts them into GUI transition graphs (Sun et al., 2025). GUI-Xplore is primarily evaluated as an of-fline app-understanding setup over those videos, whereas TAG-Nav studies graph memory under live device interaction with a stepwise actor. GUI-explorer autonomously explores apps and mines transition-aware knowledge for dynamic guidance (Xie et al., 2025). Across this family, exploration-derived memory is largely treated as an assumed benefit; what varies between systems is the explo-ration policy and the memory format, not a con-trolled comparison of when the explored graph yields useful navigation memory. Our narrower question is when exploration becomes reusable nav-igation memory: whether the graph contains des-tination pages, whether retrieval selects the right target, and whether the recovered route is clean enough to guide a future page-reaching task.

3 TAG-Nav 

3.1 Overview 

TAG-Nav is a navigation-memory module for mo-bile GUI agents that separates app-specific discov-ery from online task execution. Offline exploration builds an app graph over hypernode-clustered ob-servations, then post-processing turns each indexed graph state into a compact destination record de-scribing what the page is for and how it can be reached. At inference time, TAG-Nav retrieves the destination record for the user instruction, for-mats it as a plain-text destination-memory block, and injects it into an existing GUI-agent backbone without training a new actor or replacing the actor’s visual grounding module. Figure 1 summarizes the full pipeline: the offline input is an app/device con-figuration and the offline output is an app graph plus target-indexed records; the online input is a natural-language instruction and the online output is the executed trajectory together with the evalua-tor’s terminal status. 

3.2 Offline App Exploration 

TAG-Nav represents an app as a directed graph 

G = ( H, E ). A hypernode h ∈ H groups observed UI states that the matcher judges to be the same screen or screen family using visual or layout evi-dence. Each member observation stores its screen-shot, parsed UI or layout evidence when available, and metadata collected during exploration. An edge e = ( hi, a, h j ) records an executable tran-sition from source hypernode hi to destination hy-pernode hj , where a includes the action type, an action description, and available element evidence. The graph is therefore a state abstraction over re-peated screenshots rather than a literal log of every frame. Auto-BFS is our automated graph-construction condition, which builds the app graph through re-peated walks from the app’s initial screen. It com-bines walks using the local breadth-first search ex-ploration policy (Local-BFS) with random-action walks. Local-BFS walks probe unexplored actions and verify return to the current screen before prob-ing another action, skipping actions already ex-plored on matched sibling nodes within the same hypernode. Observed states are matched to exist-ing hypernodes or assigned to new ones, and transi-tions are recorded as edges. We treat Auto-BFS as an autonomous graph-construction condition rather than a novel graph-search algorithm. 3.3 Graph Construction and Post-Processing 

Raw exploration graphs are not used directly as prompts: mobile apps contain dynamic content, ads, pop-ups, scroll variants, and alternate paths that would produce noisy targets and brittle action scripts if copied verbatim. TAG-Nav therefore post-processes the graph into compact retrieval records that describe what each destination screen is for and how it can be reached. For each indexed graph state, a vision-language model generates a concise visual page summary and a set of user intents directly satisfied by the current screen. The prompt emphasizes the active interaction layer of the final screenshot, so if a modal, drawer, menu, or permission dialog is in the foreground, the metadata describes that foreground layer rather than the dimmed background. TAG-Nav also constructs the route field of each destination-memory record by extracting root-to-state paths from the graph, annotating the screen-shots along each path with action evidence, and ask-ing a vision-language model to distill the route into semantic waypoints and transition hints. The post-processing prompt removes loops, retries, oscilla-tions, and irrelevant detours, so the resulting mem-ory is expressed as page or state labels and high-level transitions, not fixed coordinates or event-log replay. Each processed graph state (h, n )

becomes a memory record rh,n =(h, n, d h,n , I h,n , W h,n , H h,n , z dh,n , z Ih,n ) with the summary, intent, waypoint, hint, and em-bedding fields defined in Algorithm 1; we write

3.4 Target Retrieval and Memory Formatting 

Given a user instruction q, TAG-Nav first retrieves candidate destination records. The instruction is embedded and compared against both the visual-summary embeddings and direct-intent embed-dings for all records. Top matches from the two fields are combined so that a candidate may be re-trieved because it looks like the requested page, because it directly supports the requested intent, or both. The candidate set is then passed to a compact target-selection prompt. The selector receives the user instruction, candidate screen summaries, and direct-intent text, then chooses the graph state whose current screen best satisfies the instruction as the final destination. The selector prefers loaded destinations over loading or transition screens, the destination page over foreground modals unless requested, routes page-style queries to the visual summary and action-style queries to the intents, rejects link or menu entries that merely point at the target, and prefers specific destinations for specific queries and general help pages for generic queries (full prompts in Appendix C). This target-first re-trieval step avoids a common graph-memory fail-ure mode in which a retrieved state is semantically close to the task but is not itself the destination page; unlike a direct retrieval of a past task trace, the destination is selected first and its memory is only then formatted for injection. TAG-Nav then formats a destination-memory block containing the original task, a final-goal de-scription, the relevant waypoint sequence, and tran-sition hints. The block is intentionally semantic and route-oriented: it orients the backbone toward the correct app region while leaving grounding, ac-tion selection, and local recovery to the backbone, and it never prescribes fixed coordinates, replays exploration verbatim, or asks the actor to perform the irreversible final task action. 

3.5 Agent-Agnostic Online Guidance 

Algorithm 2 formalizes the online actor loop: TAG-Nav launches the app, captures the current screen-shot, calls the GUI backbone with the user instruc-tion plus the retrieved destination-memory block, and executes the predicted action until the back-bone emits a terminal finished action or the step budget is reached. The memory interface itself is backbone-independent: the destination-memory block is plain text, and any GUI agent that consumes a task prompt and screen observation and emits mobile actions can be wrapped with the same retrieved memory without retraining. The canonical back-bone in our experiments is UI-TARS-1.5-7B; Sec. 5 pairs TAG-Nav memory with different GUI actors to test this agent-agnostic property empirically. Dy-namic variants that refresh or edit memory during execution are treated as controlled ablations in Ap-pendix H.7.

4.3 Graph-Aware Diagnostics 

DestBench records per-task structural metadata that attributes failures to specific causes rather than only reporting aggregate success: target coverage 

(whether the graph contains a node visually equiv-alent to xtarget ), retrieval correctness (whether top-1 retrieval picks the correct target), path ex-istence from s0 to the retrieved target, path clean-liness (route length in waypoints, detours, loops, backtracks, restarts, and transition-hint count), and 

judge match score (raw 1–5 rating). A target is covered only when a record matches the pre-action destination; a parent page or a screen one action too early or late is not covered. These let us distinguish between error types, including situations when the graph missed the page, when retrieval picked the wrong target, and when the route itself was noisy. 

4.4 Strict Judge and Calibration 

Primary navigation results use human judgments. Strict success requires the reference destination, allowing cosmetic differences on the same func-tional page; near misses fail. GPT-4o (Hurst et al., 2024) cross-checks final and reference screenshots on a 1–5 scale (4–5 indicate success); on a 530-pair calibration set it agrees with human judgments on 97.5% of binary labels (Appendix A.5).

5.5 Transfer to Additional Apps 

To test whether the benefit extends beyond the six core apps, we ran UI-TARS-1.5-7B with and with-out Auto-BFS memory on 68 tasks from five fur-ther apps, labeled with the same human strict rule. Memory raises success from 28/68 to 35/68 (+10.3 pp; 11 tasks improved, 4 regressed; exact McNe-mar p = 0 .12 ), with gains on four of the five apps and a loss on Instagram (Table 8). The direction matches the core results, though the gain is not significant in this small cohort. 

5.6 Failure Taxonomy 

Of 48 labeled open-loop TAG-Nav failures, 22 are wrong retrievals (A), 15 near misses (B), and 11 execution failures (C); A and B together account for 

∼77% and are addressable to the memory pipeline, so destination retrieval and target selection remain fragile (per-class notes in §7 and App. F.1). 

6 Conclusion 

TAG-Nav introduces a destination-memory mod-ule that wraps existing visual GUI agents without retraining, converting task-agnostic offline explo-ration into compact target and route records in-jected at inference time. Across two backbones and three benchmarks, this memory improves aggregate navigation success, and graph-quality controls as-sociate success more with route cleanliness than with graph size. This makes app-specific memory a measurable destination map rather than a larger exploration trace. 7 Limitations 

Current evidence is strongest for Android app-navigation tasks and a Qwen-VL-Max backbone. Auto-BFS graph memory still trails clean/manual memory in some conditions. Graph memory de-pends on app version, account/login state, UI drift, and exploration coverage. Apps with sufficiently large navigation-affecting UI updates require re-exploration before previously collected destina-tion memory can be trusted; in a small two-app probe, full-record memory gave no benefit over no memory before or after updates (Table 26). TAG-Nav is also not plug-and-play with arbitrary task-completion benchmarks because it requires page-reaching targets, safe stopping points, and graph-aware diagnostics. Manual/clean graph re-sults should be interpreted as a control rather than the deployment assumption. Comparisons to exter-nal benchmarks require careful protocol matching. TAG-Nav is most useful when the destination is graph-covered, the route is short and clean, and the backbone can reliably execute visible actions; coverage gaps, app-state drift, and sibling-page re-trieval errors are the dominant remaining failure modes. The three behavioral failure classes doc-umented in Table 24 (§5.6) correspond to these limits: wrong retrieval (Class A) reflects coverage and embedding limits, near miss (Class B) reflects last-step disambiguation limits that sharper target selection and cleaner routes may address, and ex-ecution failure (Class C) reflects step-budget ex-haustion and open-loop route-following limits that per-step memory refresh may address. 

Per-app heterogeneity. Gains are not uniform across apps (Figure 3): Calendar and Settings, where the residual difficulty is execution rather than navigation, show smaller or negative deltas (§5.2). We do not claim TAG-Nav improves every (app, backbone) cell. 

8 Ethical Considerations 

Authorized test setting and privacy. TAG-Nav exercises third-party mobile applications, so all exploration and evaluation used dedicated test de-vices, disposable accounts, and locally collected test data, not personal user accounts. DestBench tasks are derived from existing benchmark trajecto-ries and our disposable-account collection; released artifacts use scrubbed or generic targets, and we do not distribute user-identifiable content. Screenshots captured during exploration may incidentally con-tain account-specific content; explored graphs are intended for the same app version and account state in which they were collected, and we recommend that downstream users re-collect graphs under their own accounts rather than reusing ours when ac-count state matters. Downstream use should re-spect app-level terms of service and obtain autho-rization where required. 

Dual use and release. Autonomous mobile GUI agents can in principle be repurposed for spam, automated account creation, or unauthorized ac-tions on user accounts. TAG-Nav is a navigation-memory module for existing backbones rather than a new execution capability: it improves where the agent goes, not what novel actions it can perform. DestBench is intentionally scoped to page reaching and excludes the irreversible final actions most rele-vant to abuse scenarios such as purchasing, sending, deleting, or changing sensitive settings. All back-bone models are used under their respective open-weight or API licenses. We plan to release code, exploration scripts, and the evaluation protocol un-der terms limiting use to authorized accounts and test environments; app graphs and trajectories will be shared only where the underlying screenshots can be released. 

Compute and environmental impact. Offline ex-ploration and online evaluation run on commodity Android emulators; open-weight backbones run on a local GPU host, while Qwen models and GPT-4o are queried through the DashScope and OpenAI APIs. We do not train a new GUI backbone in this work, so compute usage is modest relative to model-training contributions, and the offline ex-ploration cost amortizes across all later navigation tasks for the same app version. At inference time, TAG-Nav adds one retrieval call per task to the backbone’s own calls; graph-construction counters are reported in Appendix D.8. 

Data minimization and annotator labor. Dest-Bench task descriptions and final-screenshot tar-gets were annotated by the authors. Strict-judge calibration used the same pool to label 530 (task, final-screenshot) pairs, with labelers shown only the two screens and the user instruction. References

A.2 Task-collection pipeline 

Tasks are derived from real user-trajectory recordings col-lected in our benchmark substrate. Each recording is seg-mented at the pre-action destination boundary (the last screen before a task-specific irreversible operation, defined in §4) and labeled with a natural-language instruction by paraphras-ing the original goal. Instructions are filtered to remove user-identifying content and to disambiguate destinations that admit multiple visually-distinct correct pages. 

A.3 Destination annotation protocol 

Each task instance is annotated with a target screenshot 

xtarget that visually identifies the pre-action destination, plus a dynamic-state tolerance mask that lists which UI regions (e.g., timestamps, scroll positions, advertisement slots) are ignored by the judge. The primary curator annotated the full core cohort; a second author audited a random 20% sample of the annotated targets, and the small number of disagree-ments (predominantly cases where multiple visually-distinct pages plausibly satisfied the instruction) were resolved jointly against the original trajectory recording. We report this rather than a full second-pass inter-annotator agreement because the dominant source of annotation noise in our pipeline is target ambiguity, not labeler disagreement on unambiguous cases, and the strict-judge calibration in App. A.5 provides a down-stream check on residual labeling noise. The primary metric requires the reference destination; a near miss is a failure.

B TAG-Nav Implementation Details 

B.1 Hypernode matching 

Hypernode matching compares a new screen against each stored member screen of a hypernode on two signals: visual similarity, as the cosine similarity of CLIP ViT-B/32 screen-shot embeddings (Radford et al., 2021), and layout similar-ity of the Android XML view hierarchy, using a normalized tree-edit distance and text-embedding-v4 embeddings of the page layout. A screen joins the hypernode when both signals are within thresholds tuned during graph collection. 

B.2 Local-BFS walk policy 

Exploration runs up to 1,000 walks from the app root, each with at most five forward steps. With probability 0.7, a walk expands locally: it tries untested actions on the current screen and verifies each return, for up to 15 successful undo-and-check cycles; otherwise it explores randomly. Actions already tried on the current screen or its matched siblings are skipped, and the rest are ordered by type (image elements first, then scroll, swipe, and card actions, then the rest), with random tie-breaking. C.2 Target selector prompt 

Given the user query and a list of candidate nodes, this prompt asks the VLM to rank the candidate nodes and select the single best target. Each candidate node has a visual_page_summary 

and intent_from_current_screen .

System prompt 

You are selecting the best target node in an Android UI graph. You receive: 1. a user query 2. a list of candidate UI nodes 3. each candidate has: index, visual_page_summary, intent_from_current_screen, optional retrieval scores Your job: Choose the candidate whose CURRENT screen best satisfies the user query as the final target node. Important ranking rules: - Prefer the actual target screen, not a loading screen before it. - Penalize loading screens, splash screens, blank screens, and temporary transition screens unless the user explicitly asks for them. - Penalize modals, dialogs, bottom sheets, overlays, drawers, and overflow menus unless the user explicitly asks for that foreground component. - Do not choose a page only because it has an option that leads to the target. - Do not choose a settings page merely because it mentions the requested feature. Example: "timer sound settings" is not the same as "timer section". - For page/navigation queries such as "navigate to the help page", "open timer", or "go to settings": prioritize visual_page_summary. - For task/action queries such as "turn off alarm", " change timer sound", or "send feedback": use intent_from_current_screen more strongly. - If the query asks for a general help page, prefer a help resources/support page over a specific help article, unless the query asks for that article. - If the query asks for a specific help topic, prefer the matching help article. - If a candidate is a loading screen for a page and another candidate is the actual loaded page/content, choose the actual loaded page/content. - Choose only from the provided candidate indices. Candidate labels: - target: the current screen is the best final target. - acceptable: relevant and usable, but not the best. - transient_related: loading/temporary state related to the target. - waypoint: can lead to the target but is not itself the target. - related_but_wrong: related terms appear, but it is not the target. - wrong: irrelevant. Return only valid JSON. No markdown. No explanation outside JSON. Output schema: {"best_index": 0, "best_label": "target", "confidence": 0.0, "reason": "short reason", "ranked_candidates": [{"index": 0, "label": "target|acceptable|transient_related|waypoint| related_but_wrong|wrong", "score": 0.0, "reason": "short reason"}]}

C.4 GPT-4o judge prompt

You are evaluating whether a mobile-app navigation agent reached the intended target page or target control for a user task. Task: {prompt} Image 1 is the AGENT's final screen. Image 2 is the GROUND-TRUTH target screen. Score from 1 to 5: 5 = exact target page/control reached. 4 = correct functional page/section reached; only minor visual, scroll, modal, or dynamic-content differences. 3 = partially correct: same broad area/app section, but wrong specific leaf, tab, field, or subpage. 2 = wrong section of the same app, or agent is clearly not at the requested destination. 1 = wrong app, launcher/home, stuck, or unrelated screen. Respond with ONLY a JSON object: {"score": 1-5, "justification": "<brief explanation>"}

H.2 Cross-app-version robustness 

Graphs are tied to a specific app version on a specific device configuration. In a limited 27-task probe on Instagram (about five months between versions) and eBay (about ten weeks), full-record memory matched no memory at both versions (Table 26). This probe does not establish general cross-version robustness. Apps with sufficiently large navigation-affecting changes still require the graph to be revalidated or rebuilt before its records can be trusted. H.5 Use of AI in paper preparation 

LLM-based assistants were used for literature and manuscript review, drafting, LaTeX editing, and analysis scripts. The authors are responsible for verifying all statements, evidence, and calculations and for approving the final manuscript. The assistants are not authors. 

H.6 Models used in the TAG-Nav pipeline 

All hosted models were called through Alibaba Cloud’s Dash-Scope API, except the GPT-4o judge, which used the Ope-nAI API. Exploration runs UI-TARS-1.5-7B locally for ac-tion grounding, uses qwen3.6-plus (Qwen Team, 2026b) to extract interactive elements, and uses qwen3.6-flash 

or UI-TARS-1.5-7B for loading-screen checks. Hyper-node matching uses CLIP ViT-B/32 screenshot embed-dings and text-embedding-v4 page-layout embeddings (Ap-pendix B.1). Offline post-processing (page summary, di-rect intents, waypoint route, and transition hints) makes one 

qwen3.6-plus call per root-to-state path. Record fields and user instructions are embedded with text-embedding-v4 ,a Qwen3-Embedding model (Zhang et al., 2025b), and the target selector is qwen3.5-flash (Qwen Team, 2026a). The navigation actors are UI-TARS-1.5-7B and Qwen-VL-Max ( qwen-vl-max-latest ); the closed-loop variant (Ap-pendix H.7) also describes the live screen with Qwen-VL-Max. GPT-4o (Hurst et al., 2024) is the evaluation judge. No proprietary data leaves the local environment except through these API calls. 

H.7 Dynamic-memory variants 

The closed-loop variant localizes the current screen against the graph at every step and refreshes progress annotations; the plan-edit variant rewrites the memory block when the actor sig-nals confusion. Both are controlled ablations of the canonical open-loop TAG-Nav configuration evaluated in Section 5.
