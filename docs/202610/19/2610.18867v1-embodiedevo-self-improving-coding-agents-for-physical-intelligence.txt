Bringing general-purpose agents into the physical world calls for an executable representation of
physical intelligence. Compared with vision-language-action (VLA) models, which map observations
and language instructions directly to actions, code makes control logic explicit and reusable. Code can
serve not only as a policy representation but also as the workspace in which the agent solves a task.
Rather than following a prescribed workflow of planning, execution, and verification, the agent can
autonomously inspect the state, revise and execute code, and use feedback to choose the next step.
The success of this SWE-style loop in digital environments motivates its extension to physical tasks.
Yet physical execution remains prone to recurring failures. To retain and refine experience for later
scenes, we introduce EmbodiedEvo, where a coding agent evolves reusable Skills and Lessons through
feedback on a single Playground scene, then freezes the resulting harness for diverse new scenes.
On RoboDojo-Sim, EmbodiedEvo achieves an average score of 44.48 and a success rate of 37.82%,
surpassing all officially verified results. Paired tests show the largest gains on memory-dependent tasks
and successful reuse of coordinated procedures, while fine contact control remains difficult. Experience
from stronger models also improves weaker executors: Astra’s experience raises Sol and Luna’s success
rates by 8.86 and 5.50 percentage points over no experience. Compared with raw interaction history,
Skills and Lessons achieve comparable task performance at 53.0% lower execution cost.

Introduction
“Intelligence is determined by the dynamics of interaction with the world.”
— Rodney A. Brooks
Agents are beginning to act beyond the digital world, entering real-world physical environments. Large
language models have enabled agents to reason, use tools, and iteratively develop solutions through feedback
in software environments [1]. Extending this autonomy to physical tasks requires agents to connect reasoning
with perception and execution while adapting to the consequences of their actions. Bringing these capabilities
to robotics calls for a representation of physical knowledge that agents can execute, inspect, and refine.
Compared with vision-language-action (VLA) models, which map observations and language instructions
directly to robot actions [2, 3], code makes control logic explicit, editable, and reusable. Code can represent
task-relevant objects, estimated states, relations, and progress in a form that the agent can inspect and
update. We define this as “Code as World”. Code also provides a workspace for developing solutions. Early
code-as-policy systems synthesize programs within predefined generation and execution scaffolds [4]. Software-
engineering-style (SWE-style) agents extend this process by directing their own inspection, editing, execution,
and diagnosis [1]. Applied to robotics [5, 6], this autonomy lets the agent decide when to observe, which code
to execute, and how to verify outcomes and recover from failure. We define this agent-directed interaction as
“Agent as Policy”.
Reliable physical execution requires more than editable code: programs must be grounded in a robot’s
observations, action conventions, and physical constraints. Even GPT-6 Astra can fail through inaccurate
approach geometry, mistimed corrections, and poor coordination between arms [7]. Interaction reveals useful
motions, tolerances, and checks, but knowledge confined to a single attempt must be rediscovered in later
scenes. Our baseline traces (Section 3.3) identify recurring failures that call for reusable progress checks,
physical postconditions, and recovery procedures. These observations motivate evolving the harness so that
subsequent agents can build on prior interaction. Building on feedback-driven skill optimization and harness
refinement [8–10], harness evolution retains and revises control code and experience while keeping model
weights and the robot interface fixed.
To this end, we introduce EmbodiedEvo, a self-improving coding agent that implements harness evolution
through reusable Skills and Lessons. We build a Playground for the agent using a single scene from each task.
In this scene, the agent executes code in a persistent simulation session and iteratively refines its Skills and
Lessons through physical feedback. Skills store control procedures and their usage conditions, while Lessons
retain observed failure modes, constraints, and recovery experience. We then freeze the resulting harness and
supply it to independent Test agents across a more diverse set of layouts of the same task, all distinct from
the Playground layout. Each agent starts with a fresh workspace, Python state, and simulator, using the
read-only harness to develop local programs while continuing to observe, execute, and recover.
Experiments on RoboDojo [7] simulation tasks show that inherited experience improves subsequent execution.
With task descriptions and wiki recipes, Astra/xhigh reaches 37.82% Average success rate over 50 Test
scenes per task, compared with the published Astra result of 22.48% . Paired tests hold the executor and
scenes fixed, raising success from 8.50% to 30.17% with task descriptions alone. The largest gains occur on
memory-dependent tasks, alongside successful reuse of coordinated procedures such as block stacking; fine
insertion and liquid handling remain difficult. Experience also transfers across models: Astra’s Skills and
Lessons raise Sol and Luna’s success rates by 8.86 and 5.50 percentage points over no experience. These
results distinguish the ability to produce useful control knowledge from the ability to apply it.
Our contributions are:
• Physical self-improvement through an evolving harness. We introduce EmbodiedEvo, which turns
physical interaction into persistent control procedures and decision guidance. Code as World, Agent as
Policy makes this knowledge explicit, editable, and reusable while model weights and the native robot
interface remain fixed.
• Experience that couples actions with their conditions. Our harness combines executable Skills with
Lessons on applicability, failure modes, and outcome verification. A Playground-to-Test protocol acquires
2


this knowledge on one scene per task and freezes it for independent agents, enabling reuse across unseen
layouts and different models without additional Playground exploration.
• Acquiring and applying experience are distinct capabilities. We show that unfinished tasks can yield
useful knowledge and that weaker executors benefit from experience they struggle to acquire themselves.
EmbodiedEvo surpasses all officially verified RoboDojo simulation results in Average Score and success rate;
Skills/Lessons retain comparable performance to raw history at 53.0% lower Test cost.

Related Work
General-Purpose Models for Robot Control.
VLA models integrate semantic knowledge, embodied
reasoning, heterogeneous data, and interaction experience into learned policies [2, 3, 11, 12]. RoboDawn
uses in-context demonstrations to ground robot-interface use, while early Astra evaluations expose geometric
and coordination failures in direct control [7, 13]. Coding approaches make behavior editable: CaP-X and
EmbodiedSWE develop programs through interaction, RAPID adapts demonstration-derived programs to scene
geometry, and closed-loop software optimization uses archived implementations to acquire policies [5, 6, 14, 15].
HexaAnything combines coded state and policies with perception and control tools [16]. EmbodiedEvo
combines this program-level adaptability with reusable experience, so that the agent can draw on earlier
interactions while revising code for a new scene.
Self-Evolving Agents and Harnesses. Self-improvement spans policy learning in R-Zero and SkillRL [17, 18],
and revision of skills, memory implementations, and context-construction code in SkillOpt, MemEvolve,
and SHAPER [8, 19, 20]. Continual Harness and RegenHarness study harness refinement and controlled
revision [9, 21]; Hyperagents revises task and meta-agent programs, while EnvHarness customizes the
surrounding environment [22, 23].
CORAL supports asynchronous exploration with shared notes and
skills [10]. Our focus is the physical control knowledge stored in the harness: executable procedures and
lessons about when they work, why they fail, and how to recover.
Reusable Physical Experience. RATs acquires and freezes code skills before downstream tasks arrive,
including transfer across coding agents [24]. RoboSkill combines reusable code and textual guidance with
tactile feedback, while ASPIRE evolves skill libraries across task sequences [25, 26]. RoboHarn-Evo updates
hierarchical physical knowledge, EmbodiedRSI selects experiments to distinguish code and skill hypotheses,
and PhysicalRSI selects harness successors through embodied evaluation [27–29]. We separate experience
acquisition from execution, testing whether knowledge from one scene helps the same or a different model
solve new layouts of the same task.

EmbodiedEvo
3.1
Code as World
Code as World organizes interaction with the physical environment into two levels of code. L1 provides the
basic operations for observing and acting; L2 combines these operations into executable Python procedures.
Figure 2 places this programmatic control within the broader set of embodied control paradigms.
L1: environment primitives.
The environment exposes four primitives for reading the task, observing the
scene, executing an action, and resetting the environment (Table 1). These operations form the fixed interface
available to the agent. Reset is restricted to Playground, where it enables another attempt on the same scene.
In RoboDojo, observations contain RGB images and robot state, including joint states, end-effector poses,
and gripper command states. Actions specify joint or end-effector targets together with gripper commands;
the native controller handles inverse kinematics and interpolation. Object ground-truth poses, depth, and
camera calibration are unavailable through this interface.
L2: programs composed from primitives.
The agent writes Python programs that combine L1 calls
through variables, functions, loops, and conditional branches. For example, a grasping procedure can read

3.2
Agent as Policy
Agent as Policy assigns the control decisions to the coding agent: what to observe, which program to execute,
and how to revise it after feedback. Using the L1/L2 interface, the agent directs an iterative process of
inspection, programming, execution, and repair (Figure 2d). It chooses the task decomposition and the timing
of each step from the current observations and execution history.
A workspace for acting through code.
The agent works in an isolated filesystem workspace (Table 2).
Task instructions and interface documentation provide the fixed specification; source files and scratch space
support program development. Execution records preserve what ran and what happened, allowing the agent
to inspect earlier attempts. Skills and Lessons provide the persistent knowledge introduced in Section 3.4.

An agent-directed interaction loop.
The agent reads the task and inspects the scene, edits submission/-
solution.py, and submits it through the execution client (Figure 3). After execution, it can examine the
submitted source, camera observations, standard output and errors, completion signal, and remaining budgets.
It then decides whether to gather another observation, adjust a target, revise a function, continue to the next
stage, or finish the episode. For example, after observing a dropped object, it can inspect the new scene and
revise the grasp before attempting another lift. These choices are made within one coding-agent session.
Adapting to the current physical state.
Robot state, Python variables, and function definitions persist
between submissions. Editing code or encountering an error does not undo completed actions, so the agent
must adapt its next program to the resulting scene. Playground permits same-scene resets and renews
the native action allowance, while execution slots and elapsed time remain cumulative. Test disables reset,
requiring recovery within the current scene and remaining budget. The workspace thus supports local program
revision throughout an episode; Section 3.4 explains how experience can also be retained across episodes.

3.3
Deep Dive into Astra’s Failures
To understand where coding agents struggle in physical interaction, we evaluate GPT-6-Astra with xhigh
reasoning effort in the code workspace described in Section 3.2. The evaluation is on RoboDojo-sim tasks
spanning Generalization, Precision, Long-Horizon, Memory, and Open, with 5 scenes per task. Astra receives
the task description and robot-interface documentation, without the task wiki described in RoboProbe [30].
Each episode starts with a fresh agent, workspace, and simulator, permits up to 100 accepted code executions
within the task’s native action allowance, and disables reset.
Astra achieves an average success rate of 8.50%. We examine its submitted programs, camera observations,
and feedback to locate where plausible plans fail during physical execution. Figure 4 shows two illustrative
episodes, each exposing a different gap between issuing a valid command and advancing the task.
A correct action sequence still lacks a reliable manipulation routine.
In tic-tac-toe, Astra attempts to
pick up a ring and place it on the board. The gripper reaches its target positions, yet two successive attempts
leave the ring on the table (actions 216 and 283). After inspecting a wrist-camera view and adjusting the
grasp, Astra first visibly retains the ring at action 367, consuming one-third of its 1,100-action budget. The
episode later times out without completing the board. This trace shows how constructing a local manipulation
routine can compete with task completion. It motivates retaining a parameterized procedure that combines
approach, alignment, closure, and verification of object pickup, so that subsequent attempts can build on a
working operation.
6


Action decisions lack explicit precondition checks.
In imitation sorting, Astra has identified only the
first three objects at action 240, yet starts approaching the first while the demonstration continues. The
episode terminates 16 actions later, leaving 1,344 actions unused. The visible gap is acting without checking
whether the demonstration has finished. Identifying a target alone does not establish readiness to manipulate
it. This motivates retaining observation-grounded guidance on what to verify before acting, with unresolved
explanations marked as hypotheses. Here, the trace supports checking demonstration completion; it does not
prove that early movement caused termination or that waiting would ensure success.
The two failures expose complementary needs: (1) reliable procedures for carrying out an operation, and (2)
explicit conditions for deciding when to attempt it. Within an episode, physical feedback can reveal both,
but each fresh Astra agent starts again from the interface and task description. This motivates a mechanism
that turns local corrections into reusable procedures and retains failure conditions to guide later decisions.
Section 3.4 develops that mechanism through harness evolution.
3.4
Self-Improvement through Harness Evolution
EmbodiedEvo addresses the two needs in Section 3.3 by retaining Skills and Lessons in an evolving harness
(Figure 5). Skills combine fixed native primitives into reusable control procedures, such as grasping with
a checked lift. Lessons record applicability conditions, observed failure modes, and guidance for diagnosis
and recovery. Together, they capture how to carry out an operation and what to check before or after it.
Self-improvement updates these artifacts while model parameters, task goals, and the robot interface remain
fixed.

stays read-only. Robot scenes are schematic.

namespace, and simulator. The agent uses the frozen harness to construct code and adapts that code through
execution feedback. Reset is disabled, and Test episodes do not update the harness or share new experience.
This separates within-scene adaptation from the contribution of knowledge acquired during Playground.
The same frozen artifacts can be supplied to another executor because their contents are explicit procedures
and guidance. Cross-model reuse requires no additional Playground exploration, parameter updates, or learned
adapter. We compare self-generated and transferred harnesses under the same executor and Test conditions
to assess whether the acquired knowledge remains useful across models.
4
Experiments
We evaluate EmbodiedEvo on RoboDojo-Sim to address the following research questions: (1) How well does
EmbodiedEvo perform compared with VLA- and WAM-based methods? (2) Which capabilities improve
through harness evolution, and which tasks remain difficult? (3) Can acquired experience transfer across
models and tasks?
4.1
Experimental Setup
Tasks and agents.
RoboDojo-Sim [31] is a challenging benchmark for evaluating generalist robot manipula-
tion policies. It comprises 12 Generalization, 8 Precision, 8 Long-Horizon, 6 Memory, and 8 Open tasks. Each
harness(skills + lessons) is acquired on one Playground scene layout distinct from the Test layouts. Executors
are GPT-6-Astra at xhigh and medium effort, GPT-5.6-sol at xhigh, and GPT-5.6-luna at xhigh, abbreviated
Astra, Sol, and Luna.
Evaluation scales.
We use two evaluation scales: (1) dev set: 5 scenes per task (210 episodes per condition)
for input comparisons, ablations, and cross-model analyses; and (2) full set: 50 scenes per task (2,100 episodes,
one seed) for Full Evaluation of the complete benchmark. Paired comparisons use identical scenes. For each
Generalization task, the two scales use three standard and two random scenes, and 25 standard and 25 random
scenes, respectively. Scene identities follow the public evaluation records [32]. Cross-task transfer uses a fixed
subset of 12 target tasks and is reported separately from the full-benchmark averages.
Inputs and budgets.
The task description states the goal in one sentence; the official wiki provides additional
task rules and operational guidance [33]. Full Evaluation uses task description + wiki to align task information
with the official GPT-6-Astra evaluation [7]. The input ablation compares both settings; all other paired
analyses use pure task description. Each Playground chain and Test episode allows up to 100 accepted code
executions and retains the task’s native action budget. Playground permits same-scene resets; acquired Skills
and Lessons are then frozen. Test starts a fresh agent, workspace, and simulator per scene, with read-only
experience and no reset.
Metrics.
We report Score (0–100) and success rate (SR, %). Score quantifies task completion, including
partial progress, according to the benchmark’s task-specific scoring rules. SR is the percentage of episodes
that satisfy the task’s success criterion.

EmbodiedEvo leads on Memory and Open tasks by large margins. EmbodiedEvo achieves 71.90 Score /

category: VPP2 at 55.56% on Memory and GPT-6-Astra at 31.00% on Open. The cases in Section 4.3 suggest

reaching a commanded pose can leave a grasp unsecured, and that completing some stages can leave the overall
task unfinished. Retained procedures and guidance therefore remain dependent on reliable physical execution:
contact accuracy and maintaining successful manipulation across a sequence are continuing bottlenecks.
4.3
What Does Harness Evolution Actually Change?
Research questions
(1) What can a coding agent already solve without evolution? (2) What new capabilities does evolution
add? (3) What remains unsolved after evolution?
To answer the questions above, we conduct paired evaluations of Astra/xhigh with and without evolved
experience, using identical scenes and task inputs. We test both wiki settings [33], then examine task outcomes
and execution traces to distinguish existing competence, newly acquired capabilities, and remaining failures.
Due to the cost of large-scale agent evaluation, we conduct this and all subsequent experiments on the dev set
(5 scenes per task).
EmbodiedEvo consistently improves performance across different input settings. In Table 4, Em-
bodiedEvo improves Average Score by 23.87 points and SR by 21.67 percentage points without wiki. With
wiki supplied to both methods, the gains remain 21.75 Score points and 21.72 SR points. Figure 6 shows
positive Score and SR gains across all five categories under both inputs. These gains suggest that experience
contributes execution knowledge under either input setting; the following traces show how Skills supply tested
operations and Lessons guide their use.

Transferring Evolved Experience across Models and Tasks
Research questions
(1) Can experience acquired by a stronger model improve weaker executors? (2) Can experience from
other tasks improve performance on the current task?
To answer the questions above, we conduct matched comparisons of No Experience, self-evolved harnesses,
and Astra/xhigh harnesses for each receiving executor. We also fix Astra/xhigh on twelve target tasks and
compare same-task, related-task, and mismatched-task harnesses against No Experience. All transferred Skills
and Lessons are frozen, with no further exploration by the receiver.
Stronger experience acquisition benefits weaker executors. Table 6 and Figure 9 compare No Experience
(No Evolution), Self-Evolved Harness, and Harness from Astra/xhigh at a fixed executor. Relative to No
Experience, Astra/xhigh experience raises SR by 18.72 points for Astra/medium, 8.86 for Sol/xhigh, and 5.50
for Luna/xhigh. Sol reaches 12.03% SR versus 2.50% with its own harness; Luna reaches 5.50% versus zero.
Astra/medium tests a change in source reasoning effort, while Sol and Luna test a change in source model.
These gains separate the ability to acquire useful experience from the ability to apply it: a weaker executor
can use procedures and conditions that its own exploration failed to establish.
Transferred experience supplies actionable conditions for control. On cover_blocks, Sol fails with its
own harness after 680 native actions, but succeeds with Astra/xhigh’s harness in 678 actions (Figure 13b). Its

empty cup from that for a cup covering a block. Sol applies these conditions and adapts the color order to
the current scene. The case links successful reuse to selecting an appropriate operation and its place in the
sequence, with nearly unchanged action expenditure.

How Experience Representation and Content Shape Reuse
Research questions
(1) Can compact experience preserve the benefits of full interaction history? (2) Can an agent acquire
useful knowledge without completing the task? (3) What makes retained knowledge useful for later
execution?
To answer the questions above, we conduct a controlled comparison of Skills/Lessons and Raw History from
the same Playground, using Astra/xhigh on matched Test scenes. We measure task performance and total
token use, then inspect artifacts from unfinished tasks and link saved procedures and guidance to subsequent
executions.
Skills/Lessons achieve comparable task performance with fewer tokens. Raw History provides the
ordered programs and public feedback from the same Playground. It reaches 36.41 Score / 29.78% SR,

5
Discussion
Code makes physical knowledge inspectable and revisable.
Code exposes the parameters, checks, and
control flow through which a physical strategy is executed. This gives feedback a concrete target for revision:
after a dropped load, the stacking agent retains bounded motion and checks object retention during later
execution. Parameterized procedures can then preserve a useful operation while allowing its targets to change
with the scene. Lessons complement this representation by recording when to apply or reconsider it. Raw
History achieves similar observed success, while Skills/Lessons reduce total Test token use by 11.3% . This
suggests that organizing interaction into accessible procedures and guidance is a practical benefit of the
representation; code alone does not guarantee valid physical assumptions.
Evolution changes the starting point of task solving.
With the model and robot interface fixed, evolution
changes which operations and decision conditions are available before a new episode begins. The tic-tac-toe
and sorting cases illustrate two consequences: a reusable grasp reduces repeated local search, while retained
guidance helps the agent decide when to move from observation to manipulation. These cases suggest that
evolution shifts part of the work from discovering an operation to adapting it to the current scene. The
remaining zero-success tasks and pickup regression show where this shift stops helping: contact conditions
and incomplete procedures still require physical verification. The useful unit of improvement is therefore an
operation together with evidence about its applicability.
Acquiring and applying experience are distinct capabilities.
Astra-produced experience helps Sol and
Luna where their own exploration yields little or no improvement. An agent can thus use knowledge that
it struggles to acquire, allowing one producer’s exploration to support multiple executors. The cross-task
results further suggest that reuse depends on the contents of an artifact: the selected related-task mapping
underperforms the mismatched mapping. Shared motion checks and recovery guidance may transfer across
different task labels. This motivates selecting experience by the operations and conditions a receiver needs,
with applicability checked against its current observations.
Future directions.
Our evaluation on RoboDojo-Sim provides a starting point for testing harness evolution
across additional benchmarks, robot platforms, and task distributions. Long agent-call latency also motivates
more efficient execution: future work can explore reusing validated routines with fewer model calls and
allocating intensive reasoning to uncertain states or recovery. Evaluating elapsed task time alongside success
would clarify the resulting responsiveness–reliability tradeoff.
6
Conclusion
We presented EmbodiedEvo, a framework for coding agents to turn physical interaction into reusable Skills and
Lessons without updating model parameters. On RoboDojo-Sim, EmbodiedEvo achieves 44.48 Average Score
and 37.82% SR. Paired evaluations show consistent gains across different input settings. Skills and Lessons
achieve comparable observed performance to raw interaction history at 53.0% lower Test execution cost. These
findings suggest that harness evolution improves the starting point of task solving by preserving executable
operations and the conditions for applying them. Precise contact and reliable long-horizon execution remain
important directions for extending this approach.

# Goal
You are an embodied coding agent controlling a robot through code. You are currently in
Playground Phase. Your goal is to explore the current robot task, develop a working
solution, and extract reusable skills and lessons that may transfer to future scenes.
[...]
Organize your work as an iterative loop:
observe −> reason −> implement −> record reusable knowledge when it appears −> submit
−> inspect −> revise
[...]
Whenever an observation reveals a reusable controller pattern, a repeated failure, a
recovery strategy, or an important edge case, pause and write it to `skills/` or
`lessons/` immediately while the evidence is fresh. Do not wait until the end of the
session to record it.
# Environment and Primitives
Read `primitives/primitives.md` before interacting with the environment. You have four
native primitives:
−`get_instruction()`: read the current task and goal.
−`get_observation()`: read the latest observation, including camera images and robot
state.
−`step(action, ...)`: execute a native controller action.
−`reset()`: restore the current scene and renew its official native action allowance.
The total {{EXECUTION_BUDGET}} code−execution requests and elapsed time are never reset.
[...]
# Evolution: skills and lessons
[...]
A skill should capture a general behavior or procedure, not merely rename a sequence of
open−loop `step` calls. A useful skill should:
−be parameterized by relevant targets, tolerances, and control budgets;
−derive scene−dependent decisions from observations and explicit inputs;
−be reusable across similar tasks or scenes;
−specify its preconditions and limitations;
−include evidence from experiments that supports its behavior.
Lessons are textual knowledge about what worked, what failed, and how to recover.
Record useful:
−failure patterns;
−diagnostic signals;
−recovery strategies;
−important edge cases;
−unresolved questions.
[...]
# Playground rules
You may reset with `reset()` in code or `python scripts/env.py reset` and update
`skills/` and `lessons/`. Exploration uses the configured single scene. Success here is
evidence about this scene; transfer to unseen scenes remains unverified.
Keep the task, primitives, and success conditions unchanged. Your transferable
deliverables are the skills and lessons you develop.
You cannot use `reset()` in formal evaluation.
[...]
When done, out of slots, or unable to continue, review the current `skills/` and
`lessons/` and run `finish`. If the connection breaks, query `status` before
resubmitting.

def pick_from_above(arm, grasp_pose, lift_z, action_budget, grip_dwell=12, descend_step=0.010,
lift_step=0.008, alignment_tolerance=0.003):
"""Pick from an already aligned hover; return for visual retention verification."""
obs = get_observation()
current = obs[’state’][arm + ’_ee_pose’]
lateral_error = sum((current[j] −grasp_pose[j]) ** 2 for j in range(2)) ** 0.5
if lateral_error > alignment_tolerance or current[2] < grasp_pose[2]:
return obs, {’error’: ’requires_aligned_hover’, ’steps’: 0}
used = 0
stages = [(’descend’, list(grasp_pose), 1.0, 3, descend_step),
(’close’, list(grasp_pose), 0.0, grip_dwell, descend_step)]
raised = list(grasp_pose)
raised[2] = lift_z
stages.append((’lift’, raised, 0.0, 3, lift_step))
for name, target, grip, dwell, speed in stages:
remaining = action_budget −used
if remaining < dwell:
return obs, {’error’: ’budget_exhausted’, ’stage’: name, ’steps’: used}
obs, result = move_ee(arm, target, grip, max_steps=remaining, min_steps=dwell,
max_translation_step=speed)
used += result[’steps’]
if not result.get(’reached’, False):
return obs, {’stage’: name, ’steps’: used, ’motion’: result}
return obs, {’stage’: ’lifted_needs_visual_check’, ’steps’: used, ’gripper’: obs[’state’][arm + ’
_ee_joint_state’]}

Matched comparison.
Raw History supplies the same Playground’s ordered programs and public feedback,
including raw observations and failed attempts, through read-only files. It excludes Skills/Lessons and private
scores and is not summarized by another model. Both representations use Astra/xhigh on matched Test
scenes, with no reset. Skills/Lessons exceed Raw History by 2.23 Score points (95% interval: −2.60–7.25)
and 0.39 SR points (−5.11–5.94). Intervals use 10,000 paired task-bootstrap draws within categories (seed
20261006). Similar observed performance is not a formal equivalence result.
Tokens and expense.
Figure 11 and Table 8 average terminal API-usage counters over complete Test
episodes, including failures and repeated context; Playground acquisition is excluded. Total tokens equal input
plus output, with cache reads included in input and reasoning included in output. A missing final event in one
local Raw History trace is recovered from its terminal report, without imputation. Cache reads account for
82.6% of Raw History input and 97.6% of Skills/Lessons input. The fixed Astra rates are $10/$1/$12.5/$50
per million ordinary-input/cache-read/cache-write/output tokens. These nominal rates explain the larger cost
saving (53.0%) than total-token saving (11.3%); the amounts are estimates, not invoices.

persistent Python namespace. The second helper is reproduced in Figure 14. Execution 7 adds an episode-local
move_both helper to reposition the empty arms together.
