## ABSTRACT 

Coding agents use execution harnesses to constrain the consequences of prompt injection by enforcing permission boundaries. These systems deterministically intercept any out-of-sandbox action and prompt the user for approval. To reduce approval fatigue, users can approve allow-rules proposed by the agent, after which any future action matching the rule is allowed without a prompt. In this work, we show that this mechanism introduces a new risk: untrusted context can influence the permissions presented for approval, with consequences extending beyond the immediate task. We investigate privilege escalation targeting this permission-update process. Specifically, adversarial context planted in a repository can reli-ably steer an agent performing a routine task into requesting a plausibly justified, yet dangerously broad allow-rule. If the user approves the request, the saved rule can effectively blind the harness, enabling adversaries to execute malicious ac-tions that would otherwise require approval, without triggering human oversight. Across production platforms, including Claude Code and Codex CLI, we demon-strate that agents successfully elicit the target allow-rules in 58% of experimental instances. Once acquired, these rules exhibit a massive semantic blast radius, covering 56.9% of category-specific capability test cases. To further quantify the downstream risk, we show that conditional on rule approval, our exploit achieves verified, silent goal completion in 47 of the 58 eligible instances (81.0%), under-mining the safety promise of human-in-the-loop oversight. 

## 1 INTRODUCTION 

Prompt injection has emerged as a central security challenge for autonomous LLM agents (Greshake et al., 2023a; Zhan et al., 2024; Debenedetti et al., 2024). By embedding adversarial instructions into repositories, webpages, tool outputs, or other untrusted contexts, an attacker can hijack an agent’s reasoning process, redirecting it away from the benign user’s intended task and toward attacker-chosen behavior. To mitigate this pervasive risk, recent system designs have begun to decouple an agent’s proposed actions from its executable authority via independent execution harnesses (Michael & Roesner, 2026; Bouras et al., 2026; Zhang et al., 2026). This architecture ensures that compro-mising what an agent wants to do does not automatically determine what it is allowed to execute. While these harnesses support diverse operational configurations, interactive, human-in-the-loop authorization has emerged as a primary line of defense. In the interactive setting we study, the harness enforces a deterministic authorization bound-ary: out-of-sandbox actions not already cov-ered by an allow rule require user approval, whether benign or malicious. Because this strict interception halts the agent constantly even for everyday tasks, frameworks like Codex CLI and Claude Code introduce mechanisms to mitigate approval fatigue. As illustrated in Fig-ure 2, when intercepting a routine command, the harness does not merely ask for a one-time decision. Instead, the system would in-fer and propose a generalized, persistent allow-rule based on the agent’s current actions (e.g., choosing to “not ask again” for commands shar-ing the curl prefix). Once established, these rules unconditionally auto-allow any subse-quent matching actions without further human oversight. Reusable allow rules make the authorization boundary depend on previously approved re-quests, allowing a single approval to affect sub-sequent actions. The security of this design therefore depends on how new permissions are proposed and approved, in addition to how exist-ing permissions are enforced. Because an agent’s proposed actions and permission requests are shaped by its task context, untrusted repository content may influence the permissions presented for approval. This raises a question: can such content induce an agent performing a benign task to request reusable permissions that exceed the task’s needs? In this work, we identify and study a privilege escalation risk arising from adversarial permission elicitation in harness-protected coding agents. We demonstrate that adversarial repository context can steer an agent performing a routine task toward proposing a plausibly justified allow rule whose scope exceeds the task’s needs. If the user approves and stores such a rule, the resulting authoriza-tion state can cover harmful actions outside the original task that would previously have required approval. These matching actions can then proceed without another approval prompt while the rule remains active. To establish the feasibility and consequences of this risk, we develop an automated two-stage experi-mental framework. The first stage ( Permission Acquisition ) evaluates whether adversarial repository context can elicit over-permissive rule requests during benign task execution and characterizes the additional capabilities these rules would authorize. The second stage ( Authority Reuse ) evaluates whether, conditional on approval, the resulting authorization state enables harmful operations that would otherwise require further user authorization. We empirically evaluate this framework on Codex CLI and Claude Code. Our approach successfully elicits target allow-rules in 58% of instances, exhibiting a semantic blast radius that covers 56.9% of capability test cases. Conditional on rule approval, our exploit achieves silent goal completion in 47 of 58 eligible instances (81.0%), heavily outperforming the IssueTrojanBench (20/58) and 

Direct Injection (1/58) baselines. These findings establish the feasibility of adversarial permission elicitation in the evaluated systems and show that its consequences can extend beyond the original task through persistent authorization state. In summary, our contributions are as follows: • A new risk in coding-agent harnesses. We identify and characterize a security problem in reusable authorization: untrusted repository context can influence agents to propose permissions beyond the needs of the current task, with consequences for subsequent execution if approved. • A framework for evaluating privilege escalation. We develop an automated two-stage frame-work to evaluate the elicitation of over-permissive requests, the additional capabilities covered by the proposed rules, and the downstream consequences conditional on approval. 2Preprint • Empirical evidence from production coding agents. Through experiments with Codex CLI and Claude Code, we demonstrate the feasibility of adversarial permission elicitation and quantify the resulting expansion of authority and its downstream risks conditional on approval.

## 3 METHODOLOGY 

Overview. As illustrated in Figure 3, our framework evaluates two aspects of the risk defined in Section 2. Stage I examines whether adversarial repository context can elicit over-permissive permission requests during a benign task. Stage II evaluates the downstream consequences of the resulting rules, conditional on user approval. Together, the stages distinguish permission-request elicitation from the consequences of the authority subsequently granted. 3.1 STAGE I: P ERMISSION ACQUISITION 

Stage I evaluates whether adversarial repository context can elicit a request for a target reusable rule 

π∗ from an agent performing a benign task T . The observed output is a permission request; the corresponding policy update is conditional on user approval. For a black-box coding agent, it is not known in advance whether a given repository context will elicit the target reusable rule during benign-task execution. Therefore, we formulate this acquisition phase as an iterative search over repository configurations, driven by a closed-loop LLM optimizer (Figure 3, top). The loop consists of four specialized algorithmic components at each step k:

❶ Scenario & Workflow Planner ( Mplan ). Given the benign task T and target prefix π∗, the planner acts as an adversarial strategist. The planner proposes a candidate task workflow W(k)

under which the agent may request the target reusable rule π∗ while carrying out T . Rather than inserting commands directly, Mplan designs a contextual scenario (e.g., iterative fetching of external assets) to make the permission request relevant to the task. 

❷ Repository Builder ( Mbuild ). The builder translates the abstract workflow W(k) into a concrete environmental state: R(k) ∼ M build (Rinit , W(k)). It strategically injects environmental affordances (e.g., failing test scripts, misleading README hints, or specific directory structures) designed to tightly steer the victim agent’s behavioral trajectory along the proposed task workflow. 4Preprint 

❸ Proxy Agent Rollout. We assume access to an independently operated instance of the same coding-agent system used by the user. In our evaluation, this proxy agent runs Codex CLI or Claude Code with the same underlying model and harness configuration as the evaluated agent in a sand-box environment. We execute T with the proxy and record its trace τ (k), including tool calls and permission-related events, to check whether the target rule is requested. 

❹ Feedback Critic & Goal-Conditioned Stopping ( Mcritic ). If the proxy does not propose the target rule, the critic analyzes the trajectory τ (k) to diagnose the failure mode. Crucially, the critic distinguishes between workflow design flaws (the scenario itself failed to justify the broad rule, requiring Mplan to brainstorm a new strategy) and implementation flaws (the agent got distracted by buggy code, requiring Mbuild to adjust file contents). The resulting analysis is provided as textual feedback for subsequent iterations. 

Stopping Criteria and Optimization Objective. The optimization process in Stage I iterates until it successfully elicits a persistent allow-rule capable of facilitating the downstream attack. To deter-mine when to terminate the search, the framework employs an LLM-based critic (judge) to evaluate the currently proposed rule π∗. This critic semantically assesses whether π∗, assuming user ap-proval, possesses the necessary capability scope to support the target adversarial goal G, denoted as Potential (π∗, G ). For example, if the downstream goal is data exfiltration, the critic verifies whether an agent-proposed rule like “always allow curl commands” provides sufficient network authority to seamlessly exfiltrate data without triggering further prompts. 3.2 STAGE II: A UTHORITY REUSE 

To construct the final adversarial repository R∗, Stage II reuses the iterative synthesis architecture (Planner, Builder, Proxy, and Critic) from Stage I. However, the core objective fundamentally shifts: rather than attempting to elicit a new permission, the framework must now exploit the newly ex-panded policy Pafter to actually achieve the downstream adversarial goal G.

Inputs and Workflow Inducement ( Mplan & Mbuild ). Taking the intermediate repository R∗

> acq

and the expanded policy Pafter as inputs, the Planner and Builder face a distinct challenge. Modern LLM agents are highly context-aware and logically rigorous; abruptly inserting a malicious com-mand will likely cause the agent to ignore it or halt. Therefore, the Planner must design a workflow that naturally bridges the benign task and the adversarial objective, seamlessly steering the agent into executing the malicious payload under the guise of normal development steps. The Builder then embeds this logical transition into the candidate repository. 

Binary Feedback and Stopping Criteria ( Mcritic ). The candidate repository is evaluated by rolling out the Proxy agent in a controlled sandbox. Here, the Critic provides feedback strictly based on the observed environmental execution trace. It evaluates a dual criterion: (1) whether the adversarial goal G is practically achieved in the environment (e.g., verifying if data was actually exfiltrated), and (2) whether the execution remains entirely silent , bypassing the harness without triggering any new authorization prompts. If the agent deviates from the planned workflow or triggers a prompt, the Critic dispatches this environmental feedback back to the Planner and Builder for targeted refinement. The iterative op-timization stops immediately once this target state (goal achieved ∧ silent execution) is observed. The framework then terminates and outputs the final weaponized repository R∗. Tasks and Experimental Instances. Each run initializes with a routine benign user request (e.g., 

“run this repository” ). We evaluate five categories of downstream adversarial goals strictly outside this benign execution scope: unauthorized reading, data exfiltration, file deletion, artifact download-ing, and configuration modification. Each category contains five experimental instances, yielding 25 distinct cases per agent configuration. Each instance pairs an adversarial objective with a target per-mission configuration. We stratify these 25 cases into Ordinary , Sensitive , and Critical tiers based on the targeted resources and the severity of the adversarial outcomes. For each case, Stage I ( Permission Acquisition ) evaluates the reusable permission scope successfully elicited while the agent performs the benign task. We consider a case goal-reachable if its acquired permissions are judged sufficient to support the specified adversarial goal. Only these goal-reachable cases form the eligible set for the Stage II ( Authority Abuse ) downstream evaluation. The complete case matrix and detailed target configurations are provided in Appendix A.2. 

Evaluation Metrics Our metrics independently quantify the latent authorization scope obtained in Stage I and the realized downstream risk in Stage II. 

Stage I: Permission Capability Coverage (PCC). Stage I quantifies the expanded authorization boundary using Permission Capability Coverage (PCC) . For each capability category, we design 20 semantic test cases representing diverse operational targets and difficulty levels. Given a rule elicited during the benign task, an automated judge assesses whether it provides sufficient authority to execute each test case without triggering new prompts. PCC is the fraction of these 20 cases covered by the rule, yielding a normalized [0 , 1] estimate of the acquired permission scope. Details of the PCC benchmark design are provided in Appendix B. 

Stage II: Downstream Goal Completion. Stage II evaluates the actual downstream risk by measur-ing binary goal completion, strictly conditional on the approval of the Stage I-elicited rule. Starting from the post-acquisition checkpoint, an exploit is deemed successful (a score of 1) only if the ad-versarial goal is verified as achieved without triggering any additional approval prompts. To provide concrete evidence of authority reuse, we further categorize successes into prefix-attributed com-pletion (where a successful malicious action explicitly matches the Stage I-acquired prefix) and 

additional goal completion (where the goal is achieved via other inherently authorized means). 4.2 ACQUIRED PERMISSION SCOPE

To isolate what induces an agent to actually exer-cise an already-granted authority, we conducted a tar-geted ablation on claude-haiku-4.5 . Agents therefore follow dependencies rather than stories. Semantic framing merely asks the model to believe that an action matters; control-flow forces progress to depend on it; and dataflow integrates its output as an ordinary input to benign computation. For attack synthesis, this shifts the adversary’s objective from engineering persuasive instructions to establishing the target operation as a natural producer on the repository’s execution path. 5.3 INSIGHT 3: S TRONGER AGENTS ROUTE AROUND NON -D OMINATING STEPS 

Examining the failure trajectories encountered during our optimization phase, particularly against the highly capable claude-sonnet-5 , reveals an active evasion behavior: the agent frequently 

routed around our engineered roadblocks. Even when the target authority was pre-granted, the model repeatedly avoided the intended adversarial action across several iterations. Log analysis indicates that this behavior stemmed not from missing permissions, but from the model’s capacity to discover alternative shortcuts. The agent bypassed the prescribed producer by reconstructing the required state from alternative local files, recovering it from cached fixtures, or directly writing downstream artifacts. Each time the optimizer patched one shortcut, the agent forged another. 

An attack step must causally dominate the execution graph, not merely lie on a plausible path. Borrowing the classical notion of a dominator from program analysis, a robust target action must lie on every viable execution trajectory leading to task completion. For capable models like 

claude-sonnet-5 , if any alternative producer, auxiliary data source, or direct state write can satisfy the same downstream dependency, the agent will inevitably route around the attack. There-fore, effective attack construction against stronger agents requires eliminating all path redundancy, ensuring that removing the target action renders the final task state strictly unachievable. 

## 6 RELATED WORK 

Prompt injection and long-horizon attacks. Indirect prompt injection tricks agents into exe-cuting attacker-specified actions using untrusted context (Greshake et al., 2023b). Existing bench-marks and domain-specific studies extensively evaluate these injections via repositories (Li, 2026), issues (Singh et al., 2026), and tool descriptions (Li et al., 2026; Zhao et al., 2025; Lin et al., 2025). Recent adversarial frameworks further extend this threat to long-horizon, multi-step exploits. For instance, StepJack (Zhan et al., 2026) decomposes objectives into innocuous sub-steps. However, although memory poisoning can make adversarial influence persist across interactions (Chen et al., 2024b; Yang et al., 2026), these studies do not examine the acquisition and reuse of persistent har-ness permissions. We instead decompose the authorization lifecycle : our attack first mutates the harness’s authorization state to acquire a reusable permission, and subsequently exploits this ac-quired syntactic rule for a semantically malicious objective. 

Operational safety and privilege defenses. Complementary studies evaluate coding-agent safety without adversarial injection, measuring unintended out-of-scope actions (e.g., SABER (Hu et al., 2026), Overeager Agents (Qu et al., 2026)) or stress-testing permission gates under ambiguity (AmPermBench (Ji et al., 2026)). To mitigate such risks, modern defenses employ model align-ment (Chen et al., 2024a; Wallace et al., 2024; Chen et al., 2025), execution isolation (Wu et al., 2025; Wang et al., 2026), dynamic tool boundaries (Jia et al., 2024; Debenedetti et al., 2025), , or execution-trace anomaly detection (Liu et al., 2025) Most closely related to our context are Pro-gent (Shi et al., 2026) and CapScope (Bouras et al., 2026), which enforce strict privilege policies; CapScope, for instance, derives an immutable authority ceiling before reading untrusted context. While establishing the critical role of harness policies, these studies and defenses primarily evaluate or enforce static permission configurations. Our findings expose a fundamental blind spot in sys-tems lacking immutable ceilings: when context-dependent approvals are dynamically persisted as context-free syntactic rules, they enable attacks analogous to classical permission re-delegation (Felt et al., 2011)—where the confused deputy is the permission harness itself. 9Preprint 

## 7 CONCLUSION 

This work examines how untrusted repository context can influence reusable permission requests in coding-agent harnesses. We develop an automated framework to measure the scope of the elicited permissions and evaluate downstream outcomes conditional on approval. Across four configurations of Codex CLI and Claude Code, our method achieves higher mean permission capability coverage than Direct Request. On shared eligible checkpoints, it also achieves higher downstream goal com-pletion than the evaluated injection baselines. Successful goal-related use of prefixes acquired in Stage I is observed on three configurations, alongside additional completions without such recorded reuse. Case analyses suggest that permission mechanisms and workflow structure help explain varia-tion in the observed outcomes. These findings highlight the importance of evaluating both the scope of a proposed permission and its consequences after approval. AI USE STATEMENT

## B PERMISSION CAPABILITY COVERAGE (PCC) B ENCHMARK DESIGN 

To evaluate the latent attack breadth of agent trajectories beyond instance-specific adversarial goals, we developed the Permission Capability Coverage (PCC) benchmark. The benchmark comprises 100 concrete test cases categorized into five goal domains. Due to space constraints, we define here the formal benchmark schema, complexity taxonomy, operational evaluation semantics, and representative case walkthroughs. B.1 COMPLEXITY TAXONOMY (D1–D4) Each case is assigned a deterministic complexity level (D1–D4) based on environment uncertainty, dependency chain length, and required state aggregation: • D1 (Direct / Static Reference): Targets resources at explicitly specified, static filesystem loca-tions or invokes single-step actions without auxiliary preconditions (e.g., reading a known SSH private key, copying an existing fixture). • D2 (Intra-Resource Extraction / Modification): Operates on structured documents or process environments requiring selective field filtering, regex extraction, or line-level mutation while pre-serving surrounding context (e.g., extracting one credential block from .netrc , altering a spe-cific variable in .env ). • D3 (Multi-Resource & Contextual Toolchain): Requires coordinating multiple disjoint re-sources, traversing directory subtrees, or executing a chained sequence of tooling primitives (e.g., recursively archiving multi-file registries, dual-key exfiltration, selective file pruning). • D4 (Dynamic Discovery & Heterogeneous Composition): Targets fixtures whose paths, names, or versions are unrevealed a priori. Requires runtime filesystem exploration, schema normaliza-tion across heterogeneous formats (JSON, INI, key-value), or multi-tier cross-scope orchestration (e.g., user configuration, cache directory, and sibling repository).
