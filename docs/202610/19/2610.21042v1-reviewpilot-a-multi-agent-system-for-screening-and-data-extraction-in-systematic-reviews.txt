## Abstract 

Systematic literature reviews follow the PRISMA process of screening scholarly works and extracting evidence from included stud-ies. Deep research tools based on large lan-guage models (LLMs) can search and sum-marize the literature but do not record which studies are excluded or where extracted values come from. We develop a conversational multi-agent system called ReviewPilot that automates the PRISMA workflow from paper screening to information extraction. Researchers can tai-lor criteria and schemas through dialogue, and a project memory keeps their configurations and revisions. Each screening decision comes with its reason and each extracted value with its source. On epidemiological expert reviews, ReviewPilot outperforms a single-prompt LLM and AgentSLR across three LLMs, with screen-ing macro F1 up to 0.776 and extraction F1 up to 0.788. Case studies in biomedicine and human-computer interaction show close agree-ment with human annotators, suggesting that ReviewPilot can transfer beyond epidemiology. Code is available at this link. 

## 1 Introduction 

Systematic literature reviews depend on a sequence of judgments, including eligibility check, full-text retrieval, and information extraction (Higgins et al., 2023; Page et al., 2021). Such a process if labor-intensive. Searches often result in high recall, so reviewers need to read thousands of titles and ab-stracts to find a few eligible studies (van de Schoot et al., 2021). A review can take over a year on av-erage from registration to publication (Borah et al., 2017). Automation can reduce this workload, but researchers still need to inspect decisions and docu-ment the process based on the PRISMA (Preferred Reporting Items for Systematic Reviews and Meta-Analyses) 2020 process (Page et al., 2021). 

> †Corresponding authors: Zhaoqian Xue and Lingyao Li.

Large language models (LLMs) are now widely used to search and summarize literature. Deep research tools such as ChatGPT (OpenAI, 2025), Gemini (Citron, 2024), and Perplexity Research (Perplexity, 2025) can generate a synthesized re-port. These tools help researchers explore a topic but do not follow the PRISMA process. They do not show which papers are screened or excluded and why, or where each extracted value comes from. Other review tools only limit these decisions to a single stage, such as ASReview (van de Schoot et al., 2021) and LGAR (Jaumann et al., 2025) for screening, and RobotReviewer (Marshall et al., 2017) for extraction, or an agent-based system for a few stages like AgentSLR (Padarha et al., 2026). However, designing an AI-assisted literature re-view workflow involves two key considerations. 

First, screening criteria and field definitions need operational instructions. Domain terms and borderline cases need to be iteratively interpreted consistently for screening and coding. Second, outputs must reflect the current configuration. 

Researchers refine criteria and fields as a review progresses (Higgins et al., 2023); confirmed set-tings and corrections must therefore be retained, and affected downstream outputs identified. We implement these requirements within a workflow that records the counts and inclusion-exclusion cri-teria needed for PRISMA-guided workflow. We present ReviewPilot , a conversational multi-agent system that addresses these challenges from search through information extraction (Figure 1). Researchers define eligibility criteria and an ex-traction schema through natural dialogue with the system, and a Prompt Agent turns them into review-specific guidance. Agents screen records and ex-tract information, delivering screening decisions with their reasons and extracted values linked to source passages in the papers. ## 2 Related Work 

LLM multi-agent systems. Multi-agent frame-works divide tasks among LLM agents with distinct roles (Guo et al., 2024b). For instance, AutoGen supports configurable conversations that combine LLMs, tools, and human input (Wu et al., 2024). MetaGPT encodes standard operating procedures as prompt sequences to coordinate software devel-opment and check intermediate results (Hong et al., 2024). Our system, ReviewPilot, leverages the po-tential of multi-agent workflow to review stages. 

Deep research and literature synthesis. Deep re-search tools in ChatGPT (OpenAI, 2025), Gemini (Citron, 2024), and Perplexity (Perplexity, 2025) iteratively search and analyze sources to produce reports. ChatGPT or Gemini can link citations and allows users to revise its research plan. For scien-tific literature, OpenScholar combines passage re-trieval, cited generation, and iterative self-feedback (Asai et al., 2026), while AutoSurvey retrieves pa-pers, constructs an outline, and delegates subsec-tion drafting to specialized LLMs (Wang et al., 2024b). These systems can synthesize reports but do not document the paper filtering process based on PRISMA 2020 (Page et al., 2021). 

Systematic review tools. Some tools support indi-vidual review stages. ASReview prioritizes records for human screening through active learning from relevance judgments (van de Schoot et al., 2021); LGAR ranks abstracts zero-shot using graded, criterion-based LLM scores and dense reranking (Jaumann et al., 2025). RobotReviewer extracts trial characteristics and supports risk-of-bias assess-ment with sentences linked to the source document (Marshall et al., 2017). Integrated workflows extend assistance across stages. AgentSLR pairs an epidemiological litera-ture review workflow with stage-specific evaluation and describes an interface for expert verification of extracted values (Padarha et al., 2026). Its pub-lished workflow uses predefined eligibility crite-ria and domain-specific extraction schemas. We compare against it in Section 4. Ren et al. (2026) 2translate user criteria into screening rules and use multi-agent cross-review for clinical-trial screen-ing. Their extraction workflow combines source-derived table standardization, iterative correction, and targeted human review. The commercial Elicit workflow proposes editable criteria and extraction fields and lets users return to earlier steps (Byun, 2025); it also provides evidence quotes, exclusion reasons, and PRISMA 2020 flow diagrams (Vard-haan and Mohanty, 2026). These workflows al-ready combine stage automation, customization, evidence access, and human oversight. To address these gaps, we develop ReviewPilot, a PRISMA-guided multi-agent system that coordi-nates literature search, screening, full-text retrieval, and information extraction. Researchers can tailor eligibility criteria and extraction schemas through dialogue, while agents generate screening guidance and per-field coding rules. Project memory retains configurations and corrections to support revision across stages (Sections 3.2 and 3.6). We evalu-ate the complete system on PERG and examine its workflows and screening agreement with human annotators in two case studies. 

## 3 ReviewPilot Development 

ReviewPilot is a conversational multi-agent system that covers five stages of a systematic literature review: search, screening, full-text retrieval, in-formation extraction, and semantic categorization (Figure 2). Researchers can configure the review through dialogue or direct editing, inspect each stage’s outputs, and can override screening deci-sions or correct extracted values. 

3.1 Architecture and Orchestration 

A Lead Agent coordinates four specialized agents and two tools through action contracts (Ap-pendix A.1). The Search Condition Agent designs the search strategy, and the Prompt Agent writes review-specific instructions (Section 3.2). The Screening Agent deduplicates and assesses records, and the Extraction Agent extracts structured in-formation. The Literature Search Tool executes queries, and the PDF Download Tool retrieves full texts. The Lead Agent categorizes values itself. The Lead Agent starts a stage only when its pre-requisites are met and the outputs it depends on are current. It reports completion only after check-ing the expected artifacts and their required fields. Agent skills are structured Markdown instructions specifying procedures for search strategy, screen-ing, prompt design, extraction, and categorization. A fixed mapping appends the matching skill to the LLM system prompts for these tasks (Appendix G). 

3.2 Review-Specific Prompt Design 

The Prompt Agent writes the review-specific parts of the screening and extraction instructions, follow-ing the prompt-design skill. After the eligibility criteria are confirmed, it writes screening guidance 

G from the review objectives, criteria, search con-cepts, and up to 200 candidate records (titles and abstract openings). This guidance defines the re-view focus, domain terms, include and exclude categories, and tie-breaking rules. After screening, it drafts an extraction schema from the objectives, the requested fields, and the abstract openings of up to three included papers. Once the schema is confirmed, it writes the coding rules C from up to 25 included papers, using their abstract openings and full-text sentences selected for each field. The guidance and the coding rules are each drafted and then revised in a second LLM pass against the skill’s checklist (Madaan et al., 2023). Reviewer decisions and reference extraction values are not among the generation inputs. Researchers can edit the guidance, schema, and rules and must confirm each before the stage that uses it runs (Ap-pendices G.3, G.4.1, and G.5.1). 

3.3 Search & Screening Search. The Search Condition Agent identifies the concepts required for eligibility and proposes alternative terms for each concept. It builds a Boolean query by joining alternatives with OR and required concept groups with AND (Ap-pendix A.2). Analytical dimensions that do not determine eligibility are omitted from the required groups. Researchers refine the concepts and query through dialogue or direct editing and review the sources, date range, and per-source limits. The Literature Search Tool then searches titles and ab-stracts in PubMed, arXiv, and OpenAlex. The saved query, settings, counts, and errors document the search as run.

3.4 Paper Retrieval & Information Extraction Paper retrieval. The PDF Download Tool tries a cascade of publisher, open-access, and preprint sources for each retained record. It checks PDF validity and compares opening-page text with the title. These heuristics do not guarantee retrieval success (Appendix A.4), so it generates a report to record the success or failure retrieval for each paper, and researchers can add missing PDFs manually. 

Information extraction. The confirmed schema 

S = {(fj , τ j , δ j )}kj=1 defines each field by its name, type, and description (Appendix A.5). The coding rules C specify how borderline values are coded. ReviewPilot places a full-text eligibility field first in the drafted schema, with options from the confirmed criteria. The model judges whether the paper remains eligible and names the criterion behind an exclusion. In a PDF assessment, an empty or unrecognized eligibility value does not exclude the paper. Excluded papers are omitted from categorization, and their exclusion reasons are recorded for PRISMA reporting. For each available PDF, the Extraction Agent sends up to the first 400,000 characters of its text, with page markers, together with the schema and coding rules to the model (Appendix G.5). For each field, the prompt requests a value vj , verbatim excerpts, and page numbers. It requires an empty or null value when the supplied text neither states nor necessarily implies a value. Responses are checked for field presence, types, and value constraints. A failed check is recorded as an extraction failure for that paper. Passing these checks does not establish that the values are correct. ReviewPilot searches the normalized PDF text for the returned excerpts. A field with at least one located excerpt is marked 

verified , and the first located excerpt is stored with 4the page on which it was located. Otherwise, the field is unverified . Excerpt location establishes textual presence, not semantic support for the value or coverage of every value in a multi-value field. For papers whose PDF was not retrieved, re-searchers can enable assessment from the abstract. When the selected model supports web search, it can seek web evidence for fields the abstract leaves open. Accepted values require located excerpts, and web pages must pass paper-identity checks. These outputs retain source labels and any source URLs without PDF page numbers and are reported separately from full-text assessments. Fields with-out evidence remain unavailable, and papers whose eligibility remains unavailable are not categorized. 

3.5 Semantic Categorization 

The Lead Agent categorizes extracted values only for papers retained after eligibility check. For a selected field, it proposes a set of categories with short descriptions (Appendices A.6 and G.6). The plan supports single-label or multiple-label assign-ment, and an Other category for values that do not fit. Researchers review and edit the plan before the Lead Agent assigns labels to each paper. Papers with no value for the field are marked unavailable. 

3.6 Memory Design 

Researchers work in a conversation panel and a stage-specific canvas. A chat request that changes criteria or the schema is saved as a draft, and confir-mation is a canvas action (Appendices A.7 and H). Project memory stores the conversation history, cur-rent configurations, confirmed configuration snap-shots, and each stage’s status and PRISMA counts. In conversation, the Lead Agent receives its task instructions, the current request, the saved project state, and the conversation history. Its instructions give saved state precedence over superseded re-quests and distinguish drafts from confirmed con-figurations. Researchers reuse a previous project’s configuration by importing it as a draft that again re-quires confirmation. The system does not retrieve memories across projects automatically or learn preferences from corrections. To override a screening decision, researchers se-lect a confirmed criterion or guidance rule and give a reason. They also give reasons when correcting extracted values. Original decisions and values re-main in review history. A change to a confirmed configuration or reviewed record marks affected downstream outputs as outdated until rerun. 

## 4 Experiments & Results 

We evaluate screening and structured information extraction separately against the expert annota-tions in PERG, a dataset released with AgentSLR (Padarha et al., 2026). Extraction uses the same expert-included papers for all methods, indepen-dently of each method’s screening predictions. 

4.1 Experiment Setup Data and reference annotations. PERG is re-leased under the CC BY 4.0 license. Its annotations originate from systematic reviews conducted by the Pathogen Epidemiology Review Group at Impe-rial College London for WHO priority pathogens (Cuomo-Dannenburg et al., 2024; Nash et al., 2024; Doohan et al., 2024; Morgenstern et al., 2025; Mc-Cain et al., 2025; Naidoo et al., 2026). Screen-ing uses 5,614 title–abstract records for Lassa, Ni-pah, SARS, and Zika, with 854 expert inclusions (15.2%). All methods apply the five inclusion and six exclusion criteria specified in AgentSLR’s PERG template (Appendix B). All records are eval-uated without date filtering or deduplication. Extraction uses 178 annotated papers (79 for Ebola, 6 for Lassa, 36 for SARS, and 57 for Zika). We evaluate five fields: model type, stochastic or deterministic status, code availability, transmission routes, and interventions (Table B.2). PERG anno-tates each transmission model in a paper. Reference values are aggregated to the paper level by taking the union across models. Code availability is true if the paper reports available code for any model. 

Models and evaluation metrics. We use gpt-6-luna through the OpenAI API, 1 and DeepSeek V4.1 Flash and GLM-5.3-Flash through Together AI. 2

## 5 Case Studies 

We apply ReviewPilot to reviews of LLM applica-tions in biomedicine and human–computer interac-tion (HCI). 

5.1 Complete Review Workflows 

Both projects used gpt-6-luna and searched PubMed, arXiv, and OpenAlex, taking up to 1,000 results per source. Searches covered publications dated 1 January 2023 to 1 October 2026. Figure 3 and Figure F.1 in Appendix F trace the workflows, outputs, and actions. 

HCI. The 2,241 records yielded 752 categorized studies (Figure 3); 153 reports were not retrieved, and full-text assessment excluded 75 of 827 reports. The researcher reinstated three excluded records, including a system evaluation of an interactive tool. The examples contrast this reversal with a rapid-review exclusion and pair GPT-4 and 43 partici-pants with source excerpts. Before categorization, the researcher regrouped the proposed application categories. Studies could receive multiple labels. 

Biomedicine. The 3,000 records yielded 1,341 categorized studies (Figure F.1). Screening re-tained 1,705 records, including four exam eval-uations reinstated by the researcher. Of these, 336 reports were not retrieved and seven not extracted. Full-text assessment excluded 21 of 1,362 reports. The examples show a survey exclusion, a reinstated exam evaluation, and extraction of GPT-4o and expert evaluation from a radiology study. The re-searcher kept the five proposed task categories. Re-viewPilot’s full-text eligibility assessments were outside the independent human audit below. 

5.2 Human Agreement and Inspection Screening. For each topic, two annotators from our research team with expertise in HCI or biomedicine independently labeled titles and ab-stracts without seeing ReviewPilot’s output (crite-ria in Appendix F). Separate searches with the same queries and date range, taking the first 30 results per source, yielded audit pools of 87 biomedical and 90 HCI records after filtering and deduplica-tion. ReviewPilot screened each pool in a separate run with gpt-6-luna. Its κ against each annotator exceeded inter-annotator agreement in biomedicine and, in HCI, fell on either side of it (Table F.1).

## 6 Discussion and Conclusion 

We present ReviewPilot, a conversational multi-agent system that supports systematic reviews from search to semantic categorization. Researchers con-firm criteria and schemas, a Prompt Agent writes review-specific guidance and coding rules for ap-plying them, and a project memory retains con-figurations and corrections. Across three LLMs, ReviewPilot achieves higher screening macro F1, pooled extraction F1, and verified-correct rates on PERG than a single-prompt LLM and AgentSLR. These gains should be read with care. PERG pools also inform ReviewPilot’s development, so the results do not establish performance on unseen reviews. A located excerpt shows that the quoted text appears in the paper, but whether it supports a decision or value still requires human judgment. The case studies show why memory design mat-ters. When researchers check flagged and sampled outputs, they reverse some screening exclusions and correct some field values, and the system keeps each change with its reason. ReviewPilot thus pairs automation with evidence that researchers can in-spect and decisions they can revise. Future work 8should measure how these features affect review ef-fort and decision quality, and extend the evaluation to reviews with other evidence types. 

## Limitations 

Broad validation across reviews, evidence types, and review teams remains incomplete. ReviewPi-lot’s screening procedure and prompt-design skill are refined using scores from the same PERG pools used for evaluation, so the reported gains do not establish performance on unseen reviews. Expert decisions and reference values are excluded from the Prompt Agent’s inputs. Quantitative extraction covers five fields from epidemiological transmis-sion models. The case-study screening audits use small, non-random pools labeled by our research team, and the selected extraction inspections pro-vide qualitative error analysis. Full-text eligibility decisions are not independently audited. We re-port one run per method and model without confi-dence intervals. These estimates do not character-ize variation across repeated runs. Macro-averaged screening metrics do not isolate include-class sen-sitivity, which matters for avoiding missed studies (Cohen et al., 2006; O’Mara-Eves et al., 2015). AgentSLR’s original high reasoning setting is re-placed with medium reasoning or provider defaults. Excerpt verification establishes textual presence, but does not assess semantic support or whether excerpts cover every value in a multi-value field (Gao et al., 2023). Search coverage is limited to PubMed, arXiv, and OpenAlex and constrained by the query and per-source result limits. Full-text extraction de-pends on successful PDF retrieval. Researchers can add PDFs manually, but the reported work-flows do not separately quantify retrieval outcomes by publication access status. The contribution of subscription barriers to unretrieved reports there-fore remains unquantified in the reported results. Access constraints may affect which studies enter extraction and categorization. Assessments based on abstracts or web sources are not separately vali-dated. These sources may lack the evidence needed to populate every field. Future evaluations should use reviews held out from method development, cover further evidence types and extraction schemas, and independently audit full-text eligibility and semantic support for extracted values. Repeated runs should report un-certainty and include-class recall. Prospective stud-ies with review teams are needed to assess reviewer effort and decision quality. Retrieval evaluations should report outcomes by access status and assess how manual PDF submission and fallback assess-ment affect evidence coverage. ReviewPilot also relies on hosted models whose behavior may change across versions (Chen et al., 2024). Its outputs require human verification, and the system is intended to support the indepen-dent review procedures recommended by Cochrane (Higgins et al., 2023).

## A ReviewPilot Implementation Details 

This appendix gives the implementation details be-hind Section 3, in the order of the main text. 

A.1 System and Orchestration 

The system uses a Starlette backend and aJavaScript interface. A project-level setting se-lects the model used for search setup, conversation, screening, and extraction. Each action contract specifies a component’s inputs and expected out-puts. Before reporting a stage as complete, the Lead Agent checks that the stage’s expected arti-facts exist and contain their required fields. Each skill is stored as a SKILL.md file in the Agent Skills format (Zhang et al., 2025). A fixed mapping as-signs the skills to the LLM tasks named in Sec-tion 3.1 and appends the selected skill to the task’s system prompt.

The Literature Search Tool applies source-specific syntax for PubMed, arXiv, and OpenAlex (Priem et al., 2022) to the query while preserving its Boolean grouping, and it records the executed query, settings, counts, and errors separately for each source. 

A.3 Screening Preprocessing 

The Screening Agent first filters records by publica-tion date. Records with missing dates, or with date intervals that overlap the search range, are retained. It then removes exact and near duplicates. Exact matching normalizes title case, punctuation, and whitespace. Near-duplicate detection compares title and author signatures with term frequency– inverse document frequency (TF-IDF) cosine simi-larity, computed with scikit-learn (Pedregosa et al., 2011), at a default threshold of 0.70. Records with distinct nonempty DOIs or PubMed identifiers are kept separate. Each removal is recorded with the relevant reason. 

A.4 Full-Text Retrieval 

The PDF Download Tool selects sources from each record’s identifiers and metadata. Routes in-clude direct links, publisher pages, DOI resolution, PubMed Central, Europe PMC, Unpaywall, arXiv, 12 bioRxiv, and medRxiv, with request throttling, re-tries, and a browser fallback that can be disabled. The identity check compares the text of the PDF’s opening page with the expected title. 

A.5 Extraction 

In the schema S, fj , τj , and δj denote a field’s name, JSON-compatible type, and description. Fields may also have value constraints. The Ex-traction Agent reads the PDF text with pypdf and inserts a page marker before the text of each page. The schema checks cover field presence, declared types, and value constraints. Proposed excerpts are matched against normalized PDF text, and a located excerpt is recorded with the page on which it is found. 

A.6 Categorization 

For a selected field fj with nonempty extracted values Vj , the Lead Agent proposes the cate-gory plan Kj = fLLM (fj , sample( Vj ), m ), where 

sample( Vj ) takes the first 150 distinct values in record order, each shortened to 300 characters, and 

m selects single-label or multiple-label assignment. It has at most five categories, fewer when the field has few distinct values, and includes an Other cat-egory within that limit when some values fit none. Returned labels are normalized when they match approved names. Multiple-label responses contain-ing other labels are rejected. Papers with no value for the field are marked as unavailable. Saved out-puts keep the field, mode, category descriptions, and per-paper assignments. 

A.7 Interface, Memory, and Revision 

The interface combines a project sidebar, a con-versation panel, and a stage-specific canvas for editing configurations and inspecting results. For example, the chat request add a field for sam-ple size edits the schema draft. Researchers can run screening or extraction on samples of one to five papers, kept separate from full-run out-puts. In conversation, the Lead Agent’s context is 

Pchat = Ptask ⊕S project ⊕H project , which concate-nates task instructions and the current request with the saved project state and the conversation history. Configurations that can be imported from a previ-ous project are its search setup, criteria, schema, and category plan. Edits submitted against an older project revision are rejected.

# Systematic Review Search Strategy 

A strategy is a list of concept blocks. Each block is one atomic concept with a canonical label, a role, an eligibility group, whether it is required for eligibility, and its equivalent query terms. The system builds the Boolean query from the blocks: terms of the concepts in one eligibility group are joined with OR, and required groups are joined with AND. 

## Frame the scope 

1. Preserve the stated research scope across its population or context, phenomenon, intervention or exposure, outcomes, and study design. 2. Identify the minimum set of distinct concepts needed to represent that scope. 3. Separate research scope from operational instructions. Database names, result limits, date controls, session names, and workflow-testing instructions are settings and stay outside concepts, query terms, and the restated research description. Publication language, 

20 document type, and other record filters are also outside the strategy; the reply tells the user that the search cannot apply them. A requested database is a setting even when ReviewPilot cannot search it (Scopus, Web of Science, IEEE Xplore); the app tells the user which requested databases it cannot search. 4. Distinguish concepts that determine study eligibility from dimensions used only to describe or analyze the included evidence. Mark analytical dimensions as not required so they stay out of the query. 5. Represent every user-facing concept as one atomic concept at the specificity the user stated, with a concise canonical label. Include a widely recognized abbreviation in the label when it appears in the request or improves interpretation. 6. Keep alternatives within one conceptual dimension as separate concepts that share one eligibility group; a record satisfies the group by matching any of them. Concepts in one group share a role. 7. Treat a list of settings, domains, populations, or interventions as shared coverage when an eligible record may address any listed member, even when the wording joins the members with "and". 8. Use distinct required groups only when every eligible record must match at least one concept from every group. Keep phenomenon, population, condition, context, intervention or exposure, outcome, and study design in distinct groups when each is required. 9. Require the concepts that titles and abstracts reliably state: usually the population or condition, the intervention, exposure, or phenomenon, and a setting the user names. Outcomes, age or sex qualifiers, and study design are often unstated there, so they are concepts that are not required, with their terms kept for screening. A population defined only by age or sex (adults, older adults, women) is such a qualifier. In an effect question ("how does X affect Y"), Y is the outcome of interest. Naming one of them in the research question describes the review's interest; it becomes required only when the user asks for the search itself to use it ("search on mortality", "restrict the search to randomized trials"). For "exercise for fatigue in adults with multiple sclerosis", multiple sclerosis and exercise are required, while fatigue and adults are not; for "how does telemedicine affect HbA1c in adults with type 2 diabetes", telemedicine and type 2 diabetes are required, while HbA1c and adults are not. 10. Retain names and entities that the research question explicitly places within scope. 11. Treat relational wording that states the review's interest as synthesis intent unless the relation itself is an eligibility requirement. 

## Choose query terms 

- Populate a concept's terms only with spelling variants, inflections, sufficiently specific abbreviations, historical names, and exact synonyms of its label, at the same specificity. - Keep an abbreviation only when it is unambiguous across the literature the sources index; a short form with other common meanings in the field (ED for emergency department also means eating disorder and erectile dysfunction) stays out, and the spelled-out term carries the concept. An abbreviation the user wrote in parentheses may appear in the label and follows the same test before it becomes a term. - Keep each term at the label's specificity. A broader umbrella (healthcare documentation for clinical documentation) or a sibling concept widens the review and belongs in scope only when the user asks for it. A term naming only one part of a compound label is such an umbrella: "clinical decision support" alone is broader than "LLM-based clinical decision support", so a compound whose parts appear as separate words in records becomes separate concepts in distinct required groups. - Retain a candidate term when a record using it would express the same concept at the same level of specificity. - Use the minimum sufficient set of equivalents; stop once spelling, inflection, abbreviation, historical naming, and exact-synonym coverage is represented. The term limit is a cap, not a target. - Broader categories, narrower instances, products, methods, applications, enabling architectures, and associated concepts are separate scope decisions; they enter retrieval only when the stated scope includes them. - Write terms as plain, source-neutral text. Source adapters apply field tags, phrase quoting, and database syntax. 

## Revise an existing strategy 

- Treat the saved concept blocks as authoritative and change only what the current message asks for. - Preserve every block, label, group, and term the message does not address. - Narrowing the scope adds a required concept or removes alternatives; broadening adds alternatives to an existing group or removes a required 

21 concept. - To cover another member of a dimension (another intervention, setting, or population), add it as a new concept in that concept's group and leave the existing concept's terms as they are. - A request about sources, limits, or dates changes settings only. - Answer questions without changing the strategy. - State exactly what changed, describing only changes that the returned strategy contains. 

## Quality checks 

- Every concept is traceable to the stated research scope. - Every term is equivalent enough to retrieve the same concept. - Alternatives remain alternatives, and jointly required concepts remain intersections. - Labels are distinct, concise, and nonredundant. - Required concepts reflect eligibility rather than plans for later analysis. </reviewpilot-agent-skill>

# Review Prompt Design 

Screening and extraction instructions combine a fixed procedure with guidance written for one review. This skill writes that guidance. The guidance interprets the confirmed criteria or schema for the records this review will actually meet; it never adds eligibility requirements or fields of its own, and it never drops the requirements the criteria state. 

## Tasks 

The Prompt Agent has two tasks, one per stage. Each request names its task and step; follow that section and the shared principles, and ignore the other sections. | Task | Step | Runs when | Inputs | Output | Section | |---|---|---|---|---|---| | Screening | Screening guidance | The criteria are confirmed | Objectives, confirmed criteria, search concepts, candidate titles and abstracts | Review focus, definitions, include and exclude categories, tie-breakers; the Screening Agent places them before the criteria in every screening prompt | Screening guidance || Extraction | 1. Schema | Included papers are available | Objectives, requested fields, sample of included papers | The fields the Extraction Agent fills, with names, types, options and descriptions | Extraction schema | | Extraction | 2. ## Shared principles 

- Ground every statement in the review's objectives and the confirmed criteria or schema. The candidate records show which 

23 kinds of work the review will meet; they are a map of the territory, and no rule targets, quotes or describes a single record. - Judge records by their own work: what the study did, studied and reports. Topics that appear only as background, motivation, an example or a citation do not decide anything. - Write categories, not keywords. Each rule names a kind of study or a kind of result, phrased so that a reader can apply it to a record they have not seen. - Read the criteria through the review's evidence setting. The criteria say what a record must be about and report; the objectives say where that evidence comes from. Every review collects its evidence from a setting the objectives imply: patients treated in routine care when the objectives describe how a drug behaves in practice; real classrooms when they describe how schooling works; working farms when they describe farm practice; evaluations of the method itself when they describe how well a method performs. A criterion phrased without a setting ("adverse event rates", "learning outcomes", "yield data") is read inside that setting. Work that produces the same kind of result outside the setting, such as animal toxicology studies for a review of reactions in patients or greenhouse trials for a review of yields on working farms, is near-miss work for the exclude list, unless an objective asks for it. Explicit criterion wording about publication types, languages and named exclusions is followed as written. - Exclusion rests on what the record's own work is, never on what its abstract leaves out. A record is excluded when its work is positively of an excluded kind (it is a literature review; it studies no drug of the class; its setting lies outside the domain). A record whose abstract omits a required feature stays plausibly eligible when its work is of a kind that normally produces that feature, such as the outcome measure of a program the authors ran. Work of a kind that does not produce the result a criterion requires does not become eligible because its abstract is silent about it. - Use plain, declarative English in short lines. Write what holds and when it holds; state exceptions next to the rule they qualify. 

## Screening guidance 

The guidance has four parts, in this order. Aim for 350 to 550 words in all: short categories with one rescue clause each are applied more consistently than long ones. **Keep the evidence threshold.** A criterion that asks for a kind of result often qualifies it: quantitative, measured, estimated, with statistical measures, from a named setting, or a named list of quantities. Every definition and include category that serves such a criterion carries the same qualifier, and none widens it to findings, descriptions, observations, evidence or relevance on the same topic. A topic the criterion names is not the result it asks for: work that studies the topic without producing the qualified result does not meet the criterion. When the criteria themselves accept records that may report a result, or accept descriptive findings, the categories say so; when they do not, the categories ask for the result itself. Before writing the categories, list for each content criterion the result it asks for and its qualifiers, and check each category against that list. 1. **Review focus.** One paragraph. First sentence: what the review collects and what it is for, taken from the review's objectives. Second sentence: when a record is relevant, stated as what the record's own work does, what kind of results it reports, and the setting those results come from ("...reports frequencies or risks of adverse reactions to the drug class, or describes such reactions in patients treated in routine care"). Use the objectives' terms for the quantities, outcomes or phenomena the review collects. 2. **Definitions.** Operational definitions for the central terms whose boundary decides many records. Define a term by what the record says or does ("counts as a biosimilar when the record calls it one or names an approved biosimilar product, for example ..."), include common variants and named examples, and say how to treat records that describe the thing without naming it, usually as plausibly eligible. Add a definition for any qualifier that must be studied rather than merely present ("the tutoring must be something the record evaluates; noting that a school offers tutoring is not enough on its own"). Two to four definitions are typical; write none when the criteria's terms are unambiguous. 3. **Include when the record's own work reports or will clearly produce at least one of:** six to ten categories that together cover every objective of the review and every kind of eligible work that recurs among the candidates. Build the categories from the candidates rather than by restating the criteria: group the records that are eligible under the focus and its setting by the concrete task, data or study type they share, and name each group with its typical forms and examples ("evaluations 

24 of a reading program on standardized test scores, grades or teacher ratings"; "estimates such as incidence rate, reporting odds ratio, time to onset ..."). Write each category as a noun phrase that completes the lead-in. Where a kind of work also exists outside the review's setting, the category names the setting ("yield measurements from working farms"; "pest counts from commercial fields"). - Cover the activities that serve the domain as well as its core tasks: training and education of the domain's professionals, studies of how practitioners or recipients use or perceive the review's subject, and research that uses it as an instrument, when they produce a result the criteria ask for and the criteria do not exclude them. - Add a category for outcome-defined work when the review asks how something changes people or practice ("effects of a feedback program on students' learning, attendance or teachers' practice"). - Include a category for eligible work whose abstract under-describes it, limited to kinds of work that normally produce the required results (for example "evaluations of instructional programs the authors ran, even when the abstract does not yet report the scores"). - When the objectives accept reviews, include reviews that cover the review's subject. - Give every quantity, outcome or kind of result that the criteria or objectives name its own category, spelled out in the forms it takes among the candidates. Broad names need their forms written out: in a review of drug reactions, severity covers serious, life-threatening or fatal reactions, hospitalisation, and the frequency or risk of such outcomes among treated patients; in a review of schooling, learning outcomes cover test scores, grades and progression. The forms stay at the criterion's level: where the criterion asks for measures or estimates, the forms are measures of the quantity, not mentions of the phenomenon. - Only when the criteria accept descriptive findings, add a category for studies of the review's subjects in their natural setting (treated patients, real classrooms, working farms) that report findings on the review's topic even without summary statistics. When a content criterion asks for quantitative, measured or estimated results, there is no such category, and work that describes the subjects without those results belongs on the exclude list. 4. **Exclude when the record's own work is:** five to eight categories of near-miss work: the kinds of records among the candidates that share the review's vocabulary but whose own work cannot supply what the review collects. The screener reads the criteria themselves, so these categories add what the criteria leave unsaid; publication language and publication type stay with the criteria. Typical near-miss kinds are: - work on mechanisms rather than on the outcomes the review collects (receptor or cell studies in a review of drug reactions), and controlled experiments outside the review's setting; - development or evaluation of a product or method (a new formulation, an assessment instrument, a crop variety) without the review's outcomes; - descriptions of practice (individual case management, lesson plans, farm-management advice) without the quantities the review collects; - surveys of attitudes or opinions, and policy or economic analyses, without the review's quantities; - analyses limited to materials outside the review's setting (reference samples, simulated data, research plots); - reviews, editorials and commentaries limited to such topics; - work in which the review's subject appears only as an example, applications outside the review's domain, and things of a different kind than the review covers. Every exclude category applies a confirmed exclusion criterion, or the focus, to a concrete kind of work; a kind of work the criteria and the focus leave eligible stays off this list, and borderline kinds are left to the tie-breakers. Write each category as a noun phrase that completes the lead-in, naming the kind of work and, where useful, examples of it, and end it with the condition that would rescue it ("..., without data from patients treated in routine care"; "..., unless it also reports reaction frequencies in a treated population"). The rescue condition names evidence from the review's setting that the excluded work by its nature lacks. Results that the excluded work itself produces, such as toxicity results from animal studies or yields from greenhouse trials, leave it excluded, so a rescue condition never lists them. Keep each rescue condition to one short clause. Then check every exclude category against every include category. A record whose own work reports a kind of result that an include category lists stays included, so each exclude category is phrased to leave such records out of its reach: name the work by what it lacks ("farm-management advice without measured yields") rather than by its topic ("farm-management studies"). Outcomes, quantities and populations that an include category names stay out of the exclude categories.

The review focus names the setting the review's evidence comes from. 2. A category for findings without summary statistics exists only when the criteria accept descriptive findings. 4. Each rescue condition is one short clause naming evidence from the review's setting that the excluded work lacks. 7. ## Extraction schema 

1. Derive fields from the review question and its intended synthesis, not from incidental wording in a few papers. The sample papers show which fields the available evidence can support. 2. Give every field a unique stable snake_case name, a precise description of what to record, a value type, and the unit or allowed values where applicable. 3. Separate raw reported values from normalized values when normalization could erase meaning. 4. Keep fields that the available evidence can support and that contribute to the intended synthesis; preserve every concept the researcher asked for. 5. ## Extraction coding rules 

Coding rules settle the borderline cases of a confirmed schema so that every paper is coded the same way. The Extraction Agent reads the schema and the rules together. A field description says what an option covers in principle; a rule says how a coder decides it from the paper, and for the cases a rule settles, the rule decides. The field excerpts from the included papers show how papers actually phrase each field; build the rules from those phrasings. The field coverage gives, for each field, the share of sample papers whose text speaks to it. Write only rules that settle a case the description leaves to judgment. A field whose description already decides every case it meets in the excerpts gets no rules, and a rule that repeats the description is left out. Eight to eighteen rules in all are typical: up to four per field, and up to six for a field with many options. Rules move values; they keep values. Every value a study supports belongs somewhere, so: - Prefer mapping rules, which say which option a phrasing belongs to ("one-to-one sessions and small-group catch-up are coded Tutoring"); they add correct values. Use a restricting rule ("only when ...") for an option only where the excerpts show a recurring confusion, at most one per option, and let it name where the other cases go ("...; other cases are coded with the option whose description fits them, or Other"). - A field with an Other option has one rule listing what goes to Other. - A field that classifies the review's central object, which every included paper has (the intervention in a review of trials, the crop in a review of yield studies), is always coded: Other when no named option fits. A field that nearly every sample paper speaks to in the field coverage is such a field. A field stays empty only when the study lacks the thing it classifies; a description's "unreported or unspecified" refers to a study that lacks it, and a study that has 

26 it is coded with the best-supported option. - For fields that collect several values, code every option the study represents; the rules sharpen the boundaries between options and leave clear cases to the description. - The preamble states the shared conventions in one or two sentences: code what the study's own work represents, and code every option it represents. **Decide first.** Before writing rules, name the central fields in the analysis: the fields that classify something every included paper has, judged from the field coverage and the objectives. The rules and the preamble then code them for every paper. For each field that needs rules, work through these questions. 1. **What do the description's examples settle?** Examples a field description lists under an option belong to that option. For methods, models or designs the description leaves unmentioned, code by the authors' presentation of their own work: an option applies when the authors use its name or a standard abbreviation of it, and work the authors name otherwise goes to the option whose description covers it, or to Other. An option that claims a design (cluster-randomized, multilevel, longitudinal) needs both the authors' name for it and the design itself ("Cluster-randomized only when the authors call the trial cluster-randomized and randomize whole schools or classes; a trial that randomizes pupils within schools is coded Randomized"). 2. **Which phrasings map to which option?** From the excerpts, list the phrasings that belong to an option without using its words ("raised transaminases and drug-induced liver injury are coded Hepatic"; "after-school catch-up and one-to-one sessions are coded Tutoring"). When an option's label contains words that papers use for another option, say where those words go. Route measures that fit no specific option to Other and list the common ones. 3. **When is a broad option too broad?** Options with broad names (support, training, technology, environment) apply only when the study has that component as a separate part ("Technology only when the program has a separate device-or software-based component"). A quantity the study only estimates, fits, adjusts for or lets vary over time is not a component it represents. 4. **What does the study itself represent?** Code what the study's own model, measurement or implementation represents, even when the authors leave it unnamed: a trial that compares the drug with an inactive pill represents a placebo comparator. What the study only mentions, cites or discusses stays uncoded. For yes/no fields, state the evidence that makes the answer yes and list the look-alikes that stay no (for a field on whether a protocol is publicly available: "available from the authors", "planned for publication", "summary only in the methods"). Say when a field stays empty (for example when the study reports no comparator). When the review spans several subjects that code differently (drug classes, age groups, crops), give a common part and a short part per subject. Keep each rule to one line. Use the field names and option labels exactly as the schema declares them. **Review checklist.** A draft of coding rules is checked against these points, one by one, and corrected where it falls short: 1. Every rule settles a case the field description leaves to judgment; rules that restate a description are removed, and fields the description fully settles have no rules. 2. Each restricting rule names where the other cases go, each option has at most one restricting rule, and every field with an Other option has a rule listing what goes to Other. 3. Fields that classify the review's central object are coded for every paper that has it, Other when no named option fits; the preamble and rules leave a field empty only when the study lacks the thing it classifies, and neither restates "use an empty value when unreported" as a general convention. 4. Examples a field description lists under an option stay with that option; other work is coded by the authors' own presentation, no rule widens an option with "or describes ..." clauses, and design options require both the name and the design. 5. Every option label that contains words papers use for another option has a rule saying where those words go. 6. Broad options name the separate component they require, and yes/no fields list the yes evidence and the look-alikes that stay no. 7. The rules come from phrasings seen in the excerpts: up to four per field, up to six for a field with many options, eight to eighteen in all. </reviewpilot-agent-skill>
