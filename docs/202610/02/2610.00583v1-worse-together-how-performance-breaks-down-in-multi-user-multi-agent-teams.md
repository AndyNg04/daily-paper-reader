## 摘要
人们正日益将任务委托给 AI 智能体，而这些智能体也越来越频繁地在代码库、日历或预算等共享资源上与他人的智能体相遇。当每个智能体代表目标各异的不同用户行事时，协调往往会失败，导致团队的结果反而不如由单个智能体代表所有人行事。我们在五种前沿模型和四类环境中的 77 个场景里，研究了这种多用户、多智能体设置：智能体共享计算预算的 API 密钥环境、共享日历的诊所环境、共享团体订单或预订的个人助理环境，以及共享发布截止时间的合并队列环境。在每个场景中，我们将服务所有用户的单个智能体（协调者），与每个智能体服务一名用户的团队进行比较，并分别考察智能体之间有无沟通渠道的情况。在所有环境中，团队的群体结果均劣于协调者：没有沟通渠道时，团队在两种环境中彻底失灵；即使有沟通渠道，协调开销仍造成显著差距。例如，在个人助理环境中，协调者满足特定用户请求的频率约为团队的两倍。我们发现了与这种糟糕的群体表现相关的多种行为，包括团队规模扩大时陷入停滞、相互推翻对方的行动，以及编造说法。我们还发现了一些有效但因环境而异的缓解措施，例如设置团队负责人、提供明确的流程指示，以及通过平台检查确保智能体在提交操作前阅读同伴的消息。我们将以 MAMUBench 的名义发布 API 密钥、诊所和个人助理环境，其中包含 74 个用于评估多用户、多智能体协调能力的场景。

## Abstract
People are increasingly delegating tasks to AI agents, and those agents are increasingly encountering other people's agents over shared resources such as a codebase, a calendar, or a budget. When each agent acts for a different user with different goals, coordination often fails, and the group ends up worse off than if a single agent had acted for everyone. We study this multi-user, multi-agent setting across five frontier models and 77 scenarios in four environments: an API key environment in which agents share a compute budget, a clinic in which they share a calendar, a personal assistant environment in which they share a group order or booking, and a merge queue in which they share a release cutoff. In each scenario, we compare a single agent that serves every user (a coordinator) to a team in which each agent serves one user, with and without a communication channel between the agents. Teams deliver worse group outcomes than the coordinator in every environment: without a channel, they completely collapse in two environments, and even with one, coordination overhead creates substantial gaps. For example, in the personal assistant environment, the coordinator fulfills a targeted user request about twice as often as teams. We identify distinct behaviors associated with this poor group-level performance, including stalling as teams grow, overriding each other's actions, and fabricating claims. We find effective but environment-specific mitigations, such as a team lead, explicit procedural instructions, and a platform check that makes an agent read its peers' messages before committing. We will release the API key, clinic, and personal assistant environments as MAMUBench, comprising 74 scenarios for evaluating multi-user, multi-agent coordination.

# 论文总结：多用户多智能体团队为何“越协作越糟”

## 1. 核心问题与整体含义

- **研究问题**：当不同用户各自委托一个 AI 智能体，而这些智能体共用预算、日历、订单或发布队列时，分别为用户争取利益，能否形成良好的群体结果？
- **研究动机**：现有多智能体研究多关注“多个智能体完成同一个目标”；现实中的智能体却可能服务于目标不同、甚至相互竞争的用户。共享资源有限时，单个智能体看似合理的行动，可能使其他人的任务落空。
- **核心含义**：增加智能体并开放通信，并不自动带来更好的协作。系统还需要解决**谁来确定优先级、信息何时真正到达决策者、谁有权修改或提交共享状态**等问题。

## 2. 方法论与关键技术

- 论文不是提出新的模型或训练算法，而是构建**多用户、多智能体协调评测框架**。同一场景下比较四种组织形式：
  1. **单人对照（solo）**：仅在适用环境中使用，一个智能体处理无其他用户竞争的任务。
  2. **单一协调者（coordinator）**：一个智能体接收并处理所有用户的请求。
  3. **静默团队（silent team）**：每名用户有自己的智能体，但智能体之间没有专门通信渠道。
  4. **点对点团队（peer-to-peer team）**：每名用户有自己的智能体，并可互发消息。
- 每个场景都设置不足以独立满足全部需求的共享资源。智能体通过环境工具采取行动，研究者从**最终资源状态与操作日志**机械地计算结果，而不只评价对话质量。
- 指标随任务而变：API 预算与合并队列采用“**实际完成价值／场景最优可行价值**”；诊所要求紧急患者及时预约、且被挪动的患者完成重新预约；个人助理则看最终提交的订单或预订是否满足某位用户的明确请求。API 任务的价值还考虑分片收益、阶段依赖和边际收益递减，最优值由预算与速率约束下的可行组合计算。
- 在结果比较之外，论文分析参与率、未完成工作上的资源消耗、对同伴任务的干预、请求是否进入提交者上下文等过程变量，再测试团队负责人、明确优先级或流程规则、提交前读取未读消息的平台约束等干预。**这些过程分析多为关联证据，不能一概视为已识别的因果机制。**

## 3. 实验设计与 Benchmark

- 共研究**四类环境、77 个场景**；计划发布的 **MAMUBench** 包含其中三个环境的 **74 个场景**，不包括合并队列：
  - **API 密钥：25 个场景**。4、8 或 16 名研究者共享不足以完成全部作业的 token 预算；衡量完成作业的总价值。
  - **合并队列：3 个场景**。4 名用户的 PR 竞争有限的 CI runner 与发布截止时间；衡量按时合并的发布价值。
  - **诊所：24 个场景**。17–52 个患者智能体共用已排满的日历；比较紧急信息一次提供与分散在多通电话中的两种条件。
  - **个人助理：25 个场景**。4、8 或 16 人共用餐食订单、预订或旅行安排，其中 9 个场景含安全相关请求。
- 最多评测五种前沿模型：Claude Opus 5、Claude Sonnet 5、GPT-5.6-sol、GPT-5.6-terra 和 Qwen3.8-max；**各环境的模型覆盖、推理设置和有效样本数并不完全相同**。
- 默认每个“场景 × 模型 × 组织形式”运行约 **20 次**，但个人助理的基线通常为每格 50 或 100 次，诊所静默团队为每格 5 次；部分干预仅运行约 5 或 10 次。论文另提供逐场景结果、置信区间及价值权重敏感性分析。

## 4. 资源与算力

- 论文报告的是**推理与评测成本**：仅让 Claude Opus 5 点对点团队在 MAMUBench 的 74 个场景各运行一次，就约处理 **34 亿 token**；串行完成所有组织形式的一轮评测约需 **370 小时、54 亿 token**。
- 文中**未明确给出 GPU 型号、GPU 数量、训练时长或训练算力**；该研究主要评测现有模型，并非训练新模型。大量智能体、消息和长时任务使复现实验的成本较高。

## 5. 实验数量、充分性与公平性

- **覆盖较广**：四种共享资源机制、77 个场景、最多五种模型，加上组织形式对照、团队规模变化、信息分散条件、多个干预与消融，足以表明协调问题并非单一案例。
- **对照有价值，但不完全等能力**：协调者从一开始就集中接收多名用户的信息；团队成员则各有独立上下文，还须传递消息。这正是论文要检验的现实差异，却意味着性能差距不能单独解释为“多智能体的推理能力更差”。
- **干预比较需谨慎**：例如，合并队列的某些改进方案直接向团队提供发布经理的优先级，而基线协调者没有得到同等明确的排序；因此“干预团队超过协调者”不宜直接理解为团队结构本身更优。部分干预样本较小，提供商错误导致的排除也使有效样本不均衡。
- **稳健性有所检验**：API 与合并队列改变任务价值权重后，逐场景胜负格局大体稳定；但行为标签依赖未经人工判定验证的 LLM 裁判，仍需独立复核。

## 6. 主要结论与发现

- **总体结果**：在四类环境的汇总结果中，各自服务一名用户的团队均落后于单一协调者；静默团队在 API 预算和个人助理环境尤其容易失效。开放通信可以缓解部分问题，却不足以保证请求被及时读取或执行。
- **API 预算**：Opus 5／Sonnet 5 的点对点团队分别达到最优价值的 **30%／12%**，协调者为 **64%／32%**，静默团队仅 **7%／2%**。团队扩大时，实际采取行动的成员比例下降；部分模型还会未经事先同意停止同伴任务。设置负责统筹价值排序的团队负责人能显著改善结果。
- **合并队列**：Opus 5／Sonnet 5 团队取得最优发布价值的 **81%／78%**，协调者为 **92%／93%**。团队较少按任务价值安排合并顺序；明确优先级及放弃来不及完成的 PR 后，部分干预平均达到约 **97%**。
- **诊所**：当紧急信息分散在多通电话中时，所有受测模型的点对点团队均落后于协调者。失败并非总因事实未传到：有时智能体已掌握信息，却没有执行当天改约。对 Claude 团队加入更严格的预约、跨来电处理信息及挂断前完成预约等规则后，整体联合成功率显著提高。
- **个人助理**：协调者满足目标用户请求的频率约为点对点团队的**两倍**。请求虽然常已被发送给最终提交者，却可能在提交时尚未进入其上下文；覆盖他人操作和缺乏依据地声称用户意愿也很常见，但论文**未证明这两类行为各自直接造成性能差距**。相比单纯指定提交负责人，平台强制提交者先读取未读私信，对原本失败的案例有更明显的挽回效果。
- **跨环境启示**：有效缓解方式取决于瓶颈——资源分配需要明确优先级，诊所需要可执行的流程，团体订单则需要在提交边界落实信息读取与确认。不能把“增加通信”或“增加负责人”当作通用解法。

## 7. 优点

- **问题贴近实际部署**：关注不同用户的智能体争用同一资源，而非预设所有智能体共享目标。
- **对照与结果可解释**：同时比较协调者、可通信团队和静默团队，并尽量依据实际完成状态而非主观观感评分。
- **跨环境定位失效环节**：将参与停滞、价值排序、信息传递、行动跟进与最终提交区分开来，避免用单一“沟通不足”概括全部问题。
- **给出可操作的系统设计线索**：除提示词和角色分工外，还检验了服务端强制读取消息、逐人确认等平台层约束。

## 8. 不足与局限

- **场景与评分仍有构造性**：作业或 PR 的价值由研究者赋予，个人助理重点检查一名目标用户的请求；这些指标未完整覆盖真实场景中的公平、隐私、长期关系及所有用户福利。
- **外推范围有限**：四个环境、所选模型和特定工具／调度机制不能代表所有自主智能体系统；尤其个人助理中消息送达时序直接影响结果。
- **基线存在信息结构差异**：协调者天然集中掌握用户请求；部分缓解实验又向团队额外提供更明确的优先级，比较时应区分组织形式效应与信息、指令效应。
- **部分机制证据偏探索性**：参与率、消息入上下文与成功率的关联有解释力，但覆盖操作、编造说法等行为的因果贡献尚未确定；后两类中的判断还依赖未经人工验证的 LLM 裁判。
- **成本与稳定性限制复现**：评测耗费大量 token 和时间，部分运行遭遇提供商错误或有效样本减少；论文目前为**审阅中的预印本**，MAMUBench 在文中表述为计划发布。
