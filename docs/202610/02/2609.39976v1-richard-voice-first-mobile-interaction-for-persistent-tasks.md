## 摘要
移动终端需要在提供应用与网络服务的同时，支持用户自主掌控注意力。我们探索一种围绕请求与委派任务组织的语音优先交互方式，使用户能够离开对话，并在之后查看、修改和获取任务成果。我们介绍了 Richard，这是一种系统原型，将语音会话、任务执行和结果交付分别进行管理，并通过持久化请求记录将它们关联起来。对话视图和任务视图提供可视化反馈，后端则协调即时响应、专用服务操作和智能体任务。请求修改、执行状态和通知均与相应任务保持关联。我们通过 Android 功能记录、受控生命周期验证，以及一项真实编程请求的执行记录来考察这一设计。受控验证复现了请求修改、确认后执行和结果留存；已部署服务的记录则显示，即使客户端断开连接，后端仍可继续推进任务并反馈失败信息。这些观察为移动语音交互中的任务连续性、用户控制和服务集成设计提供了参考，并为支持用户间歇性参与的个人计算设备提供了实现基础。

## Abstract
Mobile terminals need to provide application and network services while supporting users' control over their attention. We explore voice-first interaction organized around requests and delegated tasks, allowing users to leave a conversation and later inspect, revise, and retrieve the work. We present Richard, a system prototype that manages voice sessions, task execution, and result delivery separately, linking them through persistent request records. Conversation and task views provide visual feedback, while the backend coordinates immediate responses, dedicated service operations, and agent tasks. Request revisions, execution states, and notifications remain associated with the relevant task. We examine this design through Android functional records, controlled lifecycle verification, and execution records of a real programming request. Controlled verification reproduces revision, execution after confirmation, and result retention; deployed-service records show backend progress and failure feedback after client disconnection. These observations inform the design of task continuity, user control, and service integration in mobile voice interaction, providing an implementation basis for personal computing devices that accommodate intermittent user participation.

## 1. 核心问题与研究动机

- **核心问题**：用户向移动设备提出目标后，能否结束语音对话、暂时离开设备，而任务继续执行；待用户返回时，仍能理解进展、修改要求并取回结果？
- 传统以应用为中心的交互往往要求用户持续操作、等待或反复查看，容易增加注意力负担。仅让智能体具备执行能力还不够：如果会话中断后任务状态、修改记录或结果交付状态无法接续，用户仍需持续关注设备。
- Richard 的整体思路是将移动交互从“持续操作应用”转向“**提出请求—委派执行—按需介入和检查**”。论文关注的是支持这种间歇性参与的系统组织方式，而非证明该原型已经降低了用户的实际手机使用时间或注意力负担。

## 2. 方法论与关键技术

- **核心设计：分离三种生命周期，并用持久化记录关联。**
  - *语音会话*决定用户当前是否连接和交谈；结束会话不等于取消任务。
  - *任务执行*独立于语音连接运行，具有排队、运行、等待输入、完成、失败、取消、中断等状态。
  - *结果交付*独立于执行完成：结果可以先保存，待用户返回后查询或播放。
- **按能力选择执行路径**：一般解释可即时回答；Dida 服务的常规查询和修改使用专用工具；文件、编程或复杂分析交由 Hermes 后台执行。Android 客户端同时提供对话视图和任务视图，便于用户在不翻阅完整对话的情况下检查工作。
- **请求修订采用版本和执行轮次管理**：任务开始一次执行时固定其所依据的请求版本；运行中新增的要求先被记录，不宣称已作用于当前执行。该轮次结束后，如发现版本变化，任务等待用户确认，再依据更新后的要求启动下一轮。这牺牲了部分即时性，但使“记录了修改”与“实际执行了修改”可以区分。
- **控制与服务一致性**：结束会话、静音通知、取消任务分别作用于不同对象；取消不会撤销已经发生的外部写入。共享执行器为不同入口的 Dida 操作提供写入串行化、请求去重、操作回执及提交前版本检查。不过，版本检查与云端写入之间仍存在竞态窗口。
- 论文**没有提出数学公式或新的模型训练算法**；主要贡献是任务状态、请求版本、执行轮次与交付记录的系统流程设计。

- 从论文叙述看，主要证据是 **1 组受控修订测试、1 个编程请求及其两次任务运行**，辅以单设备移动端和服务集成功能记录；没有多数据集评测、消融实验或跨系统性能比较。

## 6. 主要结论与发现

- 受控验证表明，请求修改可以被记录而不混同于当前执行版本；确认后能够再次执行，同一任务的结果可以持久保存，执行完成与交付进度也可以分别表示。
- 部署记录表明，**客户端断开不必终止后端任务**，且系统可以保留进展与失败信息；但它也表明，连接独立性并不能保证外部模型服务可靠，更不能保证任务最终成功。
- 论文因此提出一项可复用的设计原则：用持久化任务连接用户的多次交互，并明确区分连接状态、执行状态和交付状态。

## 7. 优点

- 将“离开与返回”作为核心交互场景，而非仅优化单次语音对话或智能体执行。
- 请求版本、执行轮次和确认机制提高了修订生效范围的可追溯性，避免将尚未执行的新要求呈现为已落实。
- 区分结束对话、静音和取消任务，并将执行结果与语音播放分开记录，有助于减少控制语义的歧义。
- 同时报告受控成功案例和真实部署中的失败案例，清楚划定了机制验证与任务成功之间的界限。

## 8. 不足与局限

- **缺少用户研究**：尚未测量注意力负担、实际使用体验、任务状态理解程度或长期使用行为。
- **任务成功证据有限**：真实编程案例没有产出文件，因此未验证生成程序的正确性，也未展示完整的“语音委派—成品交付”体验。
- **端到端集成尚未完成**：播放确认机制已在后端和 Web 参考客户端验证，但 Android 端的播放确认集成仍是后续工作。
- **推广性与可靠性有限**：单设备、少量场景和项目发起者的功能记录难以代表多用户、多设备及复杂真实任务；外部模型服务故障会阻碍执行。
- **外部写入仍有边界风险**：取消不能回滚既有写入；提交前版本检查也不能消除与云端写入之间的竞态，最终一致性依赖外部服务能力。
