Abstract 

Computer-using agents are increasingly capable of performing complex tasks in the digital world. However, high-quality interaction trajectories remain scarce for specialized desktop applications, where limited application knowledge, cumbersome GUI workflows, and incomplete exploration hinder auto-mated collection. We introduce OS-Wizard, an automated trajectory collection framework. It combines tutorial-guided exploration with a hybrid GUI–Code action space, providing application-specific knowl-edge and simplifying GUI workflows through direct execution of application-native commands. The framework also checkpoints and revisits pivotal states during tree exploration to explore alternative workflows, complementing linear rollouts for broader coverage. We collect 10.9K trajectories com-prising 54.9K state–action samples. Fine-tuning open-source base models on this corpus yields a best-performing model that improves performance on a benchmark of specialized desktop workflows by 58.2 percentage points to 64.1%, surpassing reported human performance of 59.8% and establishing a new state of the art. The fine-tuned model also improves performance on general desktop workflows using GUI actions only, suggesting that the collected supervision benefits general desktop tasks as well. Comparative experiments and ablations demonstrate the e ffi ciency of trajectory collection and the importance of code actions. 

# 1 Introduction 

Computer-using agents (CUAs) extend foundation models from understanding multimodal infor-mation to directly interacting with computers, enabling them to complete tasks through graphical user interfaces (GUIs) across web and desktop environments (Deng et al., 2023; Zhou et al., 2024; Xie et al., 2024; Yuan et al., 2026). Given a task instruction and observations such as screenshots, a CUA repeatedly reasons about the current state and executes actions such as mouse clicks or keyboard input (Hong et al., 2024; Zheng et al., 2024a; Agashe et al., 2025). As these agents are increasingly expected to handle longer and more complex workflows, their capabilities depend critically on diverse and high-quality interaction trajectories that provide supervision for both interface grounding and multi-step decision making. However, computer-using trajectories remain substantially more di ffi cult to obtain than conventional text or vision data, and existing datasets still rely heavily on costly human demonstrations (Wang et al., 2026; Liu et al., 2026; Qin et al., 2025). Recent work has begun to automate trajectory synthesis through model-driven exploration and task generation (Xu et al., 2025; Sun et al., 2025; Wei et al., 2026), but collecting useful data for specialized desktop applications faces three challenges. First, the scarcity of application-specific interaction data leaves general-purpose models with limited knowledge of how to use these applications correctly, hindering e ff ective exploration. Third, collection through independent linear rollouts leaves functional coverage largely to chance: unguided sampling can miss important capabilities, while valuable intermediate states are not systematically revisited to explore alternative workflows. To address these challenges, we introduce OS-Wizard , an automated trajectory collection framework for specialized desktop applications. OS-Wizard augments GUI interactions with domain-specific code actions that directly submit application-native commands, including DSL expressions, reducing the interface interactions required to execute expert operations. In Figure 1, this abstraction reduces a multi-step hydrogen-bond visualization workflow to a single code action. To equip the collector with the knowledge needed to use this action space, we retrieve application documentation and tutorials that explain application workflows and command usage, guiding exploration and task execution in unfamiliar software. Beyond independent linear rollouts, we introduce tree exploration organized around pivotal states —states expected to o ff er valuable branching opportunities. By identifying and checkpointing these states, the collector can repeatedly restore them and explore di ff erent continuations, reusing shared workflow prefixes to broaden functional coverage. Both collection strategies combine execution checks with stage-specific verification. We evaluate OS-Wizard on ScienceBoard (Sun et al., 2026), a benchmark of specialized scientific applications, and OSWorld (Xie et al., 2024), a general desktop benchmark. On ScienceBoard, fine-tuning Qwen3.5-27B on our collected trajectories improves overall task success from 5.9% to 64.1%, surpassing the reported overall human performance of 59.8% and establishing a new state of the art. Under a matched 10K-sample training budget, OS-Wizard achieves 36.5% success compared with 13.0% and 18.9% for the Task-driven and Branch-driven collection baselines, demonstrating 2that our collection framework produces more e ff ective supervision per sample. On OSWorld, the fine-tuned model improves success from 39.1% to 42.9% using GUI actions only, which shows that the collected supervision supports substantial gains on specialized applications while also improving general desktop task performance. Our main contributions are: • We introduce OS-Wizard, an automated trajectory collection framework for specialized desk-top applications, using tutorials to mitigate knowledge gaps and revisiting pivotal states to explore alternative workflows beyond independent linear rollouts. • We develop a validatable hybrid GUI–Code action space that reduces the interface interactions needed to execute application-native commands, with ablations supporting the value of code supervision. • We collect 10,919 trajectories comprising 54,938 state–action samples, improving performance on ScienceBoard and OSWorld and outperforming alternative collection strategies under a matched training-data budget. 

# 2 Related Works 

Computer-using Agents. Existing computer-using agents primarily emulate human computer use through GUI interactions. Cradle (Tan et al., 2024), CogAgent (Hong et al., 2024), SeeClick (Cheng et al., 2024), Agent S (Agashe et al., 2025), UFO (Zhang et al., 2025c), and UI-TARS (Qin et al., 2025) use mouse and keyboard actions to perform tasks from visual observations. Recent work extends this paradigm with programmatic interfaces: CoAct-1 (Song et al., 2025) and ActionEngine (Zhong et al., 2026) introduces coding actions for executable Python or Bash programs; UltraCUA (Yang et al., 2025), UFO 2 (Zhang et al., 2025b), and Axis (Lu et al., 2025) incorporate high-level tools or native application APIs; and ToolCUA (Hu et al., 2026) and EE-MCP (He et al., 2026) study hybrid GUI–tool interaction and orchestration through MCP-based interfaces. These systems focus on general-purpose computer use, with limited dedicated support for the domain-specific knowledge and operations required by specialized desktop applications. 

Data Synthesis for GUI Agents. The scarcity of high-quality interaction trajectories has motivated scalable data generation for GUI agents. Tutorial-based methods such as AgentTrek (Xu et al., 2025), TongUI (Zhang et al., 2025a), and Video2GUI (Xiong et al., 2026) convert web tutorials into executable trajectories, while task-driven approaches, including AgentSynth (Xie et al., 2026) and Insta (Trabucco et al., 2025), synthesize task intents and execute them with capable agents. Exploration-driven methods such as OS-Genesis (Sun et al., 2025), GUI-ReWalk (Lin et al., 2025), and AutoPlay (Ramrakhya et al., 2026) instead derive tasks or workflows from environment interaction. Recent systems further improve structure and scalability: ANCHOR (Wei et al., 2026) expands verified demonstrations from meaningful branch states, and SEE (Fan et al., 2026) models GUI state transitions for long-horizon synthesis. However, dedicated mechanisms for exploring domain-specific operations and collecting verified trajectories in specialized desktop applications remain underexplored. 

Advancing GUI Agents with External Knowledge. Agentic retrieval augments conventional RAG with iterative planning, query refinement, and tool-based retrieval, allowing agents to adapt the retrieval process to the task (Zhang et al., 2024; Jin et al., 2025; Singh et al., 2025; Du et al., 2026; Suresh et al., 2026). Domain- and document-grounded agents apply these mechanisms to specialized knowledge, with PaperQA (Lála et al., 2023), RAGentA (Besrour et al., 2025a) and SQuAI (Besrour et al., 2025b) combining multi-agent retrieval and evidence verification for attributed and scientific QA, while LongAgent (Zhao et al., 2024), M3DocAgent (Cho et al., 2024), RAG-Anything (Guo et al., 2025), VisRAG (Yu et al., 2025), and Patho-AgenticRAG (Zhang et al., 2026) ground multimodal and long-document reasoning in external references. # 3 OS-Wizard 

OS-Wizard is an automated framework for collecting computer-using agent trajectories in special-ized applications. Its key insight is to explore professional software through a hybrid GUI–Code action space, capturing both graphical interactions and domain-specific operations. To scale data col-lection over this action space, OS-Wizard combines structured tree exploration with complementary linear rollouts. Figure 2 illustrates both collection strategies: tree exploration builds on cold-start navigation and pivotal-state checkpointing to support tutorial-guided parallel exploration, while linear rollouts collect independent task-oriented trajectories. Both strategies combine execution checks with stage-specific verification. We model desktop GUI exploration as a rooted exploration tree T = ( V , E ) with maximum depth D,where each node v = ( s, x, t ) ∈ V represents a distinct visited state instance, consisting of a screenshot 

s, accessibility information x, and a textual state description t. Each edge e = ( v, a, v ′ ) ∈ E records an action a ∈ A executed from node v that non-deterministically produces a new child state instance v′ .Linear rollouts arise as a special case of this formulation: when every non-root node is restricted to have at most one child, the exploration tree becomes a collection of independent linear trajectories sharing the same initial root state. 

## 3.1 Pivotal State Identification 

Naively expanding GUI state trees incurs space complexity of O(N D ) for branching factor N , while repeatedly recovering successive states along a d-step trajectory via action replay under BFS incurs 4a cumulative cost of O(d2). Since GUI states di ff er substantially in their downstream exploration value, we define a sparse set of pivotal states as states expected to serve as high-value branching points for subsequent exploration. OS-Wizard allocates more exploration budget to such states and stores VM snapshots for them, reducing both redundant branching and recovery overhead. Given adjustable weights λd , λu and λp and candidate set of states C, we score each state v ∈ C by 

S(v) = λd Sd (v) + λu Su (v) + λpSp(v), (1) where each term is min–max normalized before aggregation. Sd (v) is a depth prior favoring shallow states, which expose broader functional regions and are shared by more trajectories. Specifically, the root is always treated as a pivot. Su (v) measures the magnitude of the preceding state transition based on changes in both the screenshot and the textual state description. Larger transitions such as page-level changes are more likely to introduce useful branching contexts. Sp(v) optionally incorporates empirical action success rate from v when such statistics are available, favoring states with reliable interactions. In practice, we select the top ⌈0.2|C|⌉ states in C by S(v) as pivots. 

## 3.2 Two-stage Tree Exploration 

The tree exploration component of OS-Wizard proceeds in two stages: Cold-start Navigation and 

Tutorial-guided Parallel Exploration , as is shown in Algorithm 1. Exploration follows a depth-dependent branching function f (d) = max {N − 3d, 1}, where N = 10 denotes the root branching factor. We truncate exploration beyond the maximum depth D = 16. The motivation and design of this branching schedule are discussed in §5.3. 

Cold-start Navigation. Starting from the root state, a single worker performs open-ended ex-ploration, where an LLM sampler proposes diverse and non-redundant actions from the current screenshot and exploration history. The worker expands f (0) = N first-level states and oversamples each of them to N second-level states. Pivotal states are then identified using the scores in §3.1: each first-level state forms a singleton candidate set and is thus retained as a pivot, while each group of ten second-level siblings forms a candidate set from which 2 pivots are selected and checkpointed. For every second-level state, we additionally retrieve the top-P relevant tutorials with P = 5. 

Tutorial-guided Parallel Exploration. Each worker receives the same cold-start tree but inde-pendently sparsifies and expands it. Within each group of second-level siblings, we randomly drop M = N − f (1) nodes while always preserving pivots, reducing the e ff ective branching factor to 

f (1). The remaining nodes are inserted into a BFS queue and expanded according to f (d). For a pivotal state, sampling continues until obtaining up to f (d) valid children, whereas a non-pivotal state is attempted at most f (d) times and may therefore yield fewer children. At branching states with f (d) > 1, we use the same open-ended action sampling as in cold-start navigation to diversify action-level expansions. Once f (d) decreases to 1, the retrieved tutorials and 5–10 OOD exemplar instructions guide the synthesis of a task instruction encompassing both the exploration prefix and the subsequent rollout. With tutorials as context, the worker follows the instruction until completion or the maximum depth is reached. The single branch is executed continuously without BFS recovery between intermediate states. Independent dropout and action sampling lead workers toward di ff erent branches, improving trajectory diversity and depth. Newly generated transitions are validated according to their action types before being added to the tree as described in §3.3.

Domain-specific code actions do not expose privileged functionality, but abstract commands that could otherwise be entered and executed through the GUI. They may be provided directly by the application or benchmark, or realized by automatically entering the corresponding commands through the GUI based on accessibility information. See §A for code actions supported by each application and additional implementation details. Quality control is integrated into action generation and post-execution verification. Each sampled action must be grounded in the current screenshot and accessibility information and, when an instruction is present, remain consistent with the task objective. At branching states, previously sampled sibling actions are provided as negative references, and duplicate or semantically redundant actions are rejected to promote intent-level diversity. Recent execution history is also included to suppress local action loops. All actions must execute without errors. Without a task instruction, GUI actions additionally require reward-model validation of transition validity, whereas code actions are accepted if the application reports no execution error. With an instruction, both action types undergo execution checks, and the reward model judges only task completion: success terminates the rollout; otherwise, execution continues until completion or the depth limit D. Trajectories terminated solely by this limit are excluded. Lean reference-proof replay uses pre-collection compilation checks and a separate completion procedure (§D).

# 4 Experiments 

## 4.1 Experimental Settings 

Benchmarks. We conduct experiments on ScienceBoard (Sun et al., 2026) and OSWorld (Xie et al., 2024). Both benchmarks are adapted to the Qwen3 tool-call format (Bai et al., 2025), where ScienceBoard uses the hybrid GUI–Code action space described in §3.3 for all applications except Celestia, which lacks a programmatic control interface comparable to the command-line or DSL available in other applications, while OSWorld uses GUI actions only. 

Data Collection. To balance collection quality and cost, we use GPT-5.6-Sol (OpenAI, 2026b), GPT-5.5 (OpenAI, 2026a), and Kimi-K2.5 (Team et al., 2026) as instruction proposers and action samplers, GPT-5.6-Sol as the reward model for transition and completion verification, and Qwen3-Embedding-8B (Zhang et al., 2025d) for tutorial retrieval. We collect data using both OS-Wizard tree exploration and linear rollouts. The resulting corpus contains 10,919 trajectories and 54,938 state–action training samples, averaging 5.03 steps per trajectory, including terminal steps. Tree exploration contributes 32,250 samples, while linear rollouts contribute 22,688 samples. Of the full corpus, 17,442 samples (31.75%) come from general-purpose applications, while the remaining 37,496 samples come from specialized applications. Lean uses only linear rollouts with an application-specific collection procedure. Detailed collection statistics and the Lean-specific procedure are provided in §C and §D. 

Baselines. For ScienceBoard, we compare against (1) base models, (2) proprietary models, (3) some related results from other open-source models, and (4) SFT models trained on human-collected, 

Task-driven , and Branch-driven trajectories. We implement the latter two following OS-Genesis (Sun et al., 2025) and ANCHOR (Wei et al., 2026). For OSWorld, where our goal is to assess whether OS-Wizard training preserves and improves general desktop capability, we primarily compare against the corresponding Qwen3.5-27B base model. 

Training Setup. We perform full-parameter supervised fine-tuning of Qwen3-VL-8B (Bai et al., 2025) and Qwen3.5-27B (Qwen Team, 2026a) on the collected trajectories using Qwen3-style tool-call conversations. Training configurations, conversation construction, and evaluation details are provided in §E.

## 5.2 Data and Model Size Scaling 

Data Scaling. We first vary the number of state–action training samples while holding the back-bone fixed. Figure 5(a) shows that additional data generally improves ScienceBoard success rates, with substantial gains at small data scales and diminishing returns toward the full corpus. All three backbones improve markedly over their base models with the initial subset of training data, indicating that even limited OS-Wizard supervision is useful for adapting to specialized applications. The benefits also extend beyond this initial adaptation: for Qwen3.5-27B, expanding the training set from 10K samples to the full corpus yields a 27.6 percentage-point improvement. The returns to additional data nevertheless vary across backbones: performance continues to improve for the 9B and 27B models, while the 4B model largely plateaus at the upper end of the explored range. Thus, the results support expanding the collected corpus, while suggesting that the marginal benefit should be assessed for the target backbone. 

Model Scaling. We next compare backbone sizes under the same training-data budget. Although the base models do not exhibit a monotonic ordering by size, larger backbones consistently achieve higher success rates at every non-zero data budget in Figure 5(a). This change in ordering suggests that base-model performance alone does not fully reflect the benefits of model scale after application-specific fine-tuning. With the full corpus, scaling from 4B to 9B and from 9B to 27B improves the success rate by 6.5 and 13.8 percentage points respectively. Since these comparisons hold the amount of training data fixed, they identify backbone size as another e ff ective axis for improving the trained agent. ## 5.3 Complexity Control 

The depth-dependent branching function f (d) = max {N − γd, 1} balances exploration breadth and trajectory depth while controlling tree growth. Since shallow states are shared by more downstream trajectories and often expose broader functional regions, we allocate more branching budget near the root and gradually reduce it with depth. Under N = 10, γ = 3, and D = 16, the branching factors decrease as 10 → 7 → 4 → 1. With an action validation rate of 53.8% estimated from a pilot run, approximately 187.6 branches per worker are expected to reach the single-branch instruction-following stage, preserving broad early coverage without continued combinatorial growth. OS-Wizard reduces state-recovery overhead through pivotal checkpoints and continuous single-branch execution. In our data-collection runs, standard BFS requires replaying 15.7 actions on average, while recovering from pivotal checkpoints reduces this to 14.2. Once f (d) = 1, branches are executed continuously without intermediate BFS recovery, further reducing the observed average to 2.7 replays. Together, these mechanisms control tree growth and the overhead of extending deep branches. 

# 6 Conclusion 

We introduced OS-Wizard, an automated trajectory collection framework for specialized desktop applications. OS-Wizard combines a validatable hybrid GUI–Code action space with tutorial-guided exploration and complementary tree-based and linear collection to generate diverse and useful interaction trajectories. Experiments on ScienceBoard and OSWorld show that training on the resulting data consistently improves computer-using agents, with particularly strong gains on specialized professional applications. These results demonstrate the potential of automated trajectory collection and richer action abstractions for scaling supervision beyond common GUI workflows. Future work may further strengthen trajectory quality control and explore more e ffi cient collection architectures that better balance long-horizon exploration with state-storage and recovery costs. # B Implementation of VM 

Each environment runs QEMU (Bellard et al., 2005) ( qemu-system-x86_64 ) inside an Ubuntu 22.04 Docker container with access to the host’s /dev/kvm for hardware acceleration. The guest also uses Ubuntu 22.04, installed with legacy BIOS boot. The default configuration allocates four virtual CPUs and 8 GiB of RAM, with a 64 GiB virtual disk in qcow2 format. QEMU uses the  

> pc-q35-4.2

machine type, the host CPU model, and VirtIO disk and network interfaces. The container entrypoint launches QEMU under tini ; mounted directories /storage and /qmp hold disk images and the QEMU Machine Protocol (QMP) socket, respectively. The controller uses QMP to manage VM execution and checkpointing. The guest-side interaction server is accessible through forwarded port 5000, while port 5900 provides remote desktop access. QXL with SPICE is available for initial configuration and debugging. For trajectory collection and state recovery, we launch QEMU with -display none -vga none , since QXL graphics state could not be reliably restored in our snapshot workflow. Inside the guest, Xvfb provides an X11 display at  

> :1

with a resolution of 1920 × 1080 and 24-bit color depth. GNOME Flashback with the Metacity window manager runs on this display, and x11vnc exposes it on port 5900. The desktop session is enabled through the xtop user service. This configuration places the virtual framebu ff er and desktop processes in guest memory, allowing them to be captured together with application state without relying on QXL restoration. We enable toolkit accessibility and configure the guest for unattended interaction by disabling screen blanking, screen locking, and automatic sleep. A checkpoint is a pair C = ( Q, M ): Q is a preserved qcow2 disk image, including its backing chain, and M is a QEMU migration stream containing guest memory and execution state, including CPU and device state. Thus, the runtime snapshot is stored in a separate migration file. By default, disk writes use a copy-on-write overlay over a base image. Once an image becomes part of a checkpoint, subsequent execution writes to a new child overlay, preserving the checkpoint’s disk state. Awritable overlay belongs to a single running VM, while preserved backing images can be reused across restorations. The launcher also supports direct writes and temporary QEMU snapshot mode, but our checkpoint workflow uses explicit qcow2 overlays paired with migration files. The VM lifecycle implements the state recovery in §3.4 as follows: 1. Initial launch. Create a writable overlay backed by the base qcow2 image, boot the guest using this overlay, and establish the QMP connection. 2. Save. Pause the guest with QMP stop and export its runtime state to migration file M. After the export completes, terminate the current QEMU process and close the QMP connection. Preserve the current disk state as Q by retaining its overlay and backing chain, producing checkpoint ( Q, M ). Create a new writable overlay O backed by Q, restart QEMU with O, and import M to continue from the saved state. 3. Load. Terminate the current VM and close its QMP connection, then discard its working overlay. For the requested checkpoint ( Q, M ), create a fresh overlay O′ backed by Q and start QEMU with the matching migration file M. The launcher imports this file through QEMU’s  

> -incoming

option. Subsequent execution modifies only O′, allowing repeated exploration 

> 2https://www.texstudio.org/

17 from the same checkpoint. 4. Final exit. Terminate the VM, close the QMP connection, and discard its remaining working overlay. Retain saved checkpoint images, their backing chains, and migration files for later restoration. Pairing the preserved disk image with its corresponding migration file ensures that restored memory and disk state refer to the same checkpoint. After loading the nearest pivotal checkpoint, the collector replays the remaining actions and verifies recovered screenshots as described in §3.4. Whenever a new VM is loaded, the controller registers cleanup handlers for normal program exit and termination signals such as SIGINT . A background polling loop additionally detects abandoned containers. Every ACTIVE_TIME interval, it updates the current timestamp in /var/log/heartbeat 

inside the containers it manages and checks this file in containers matching the os-aks naming convention. Containers whose heartbeat age exceeds INACTIVE_TIME are forcibly stopped. This complements exit handlers when a collector terminates without completing normal cleanup.

# D Trajectories Collection for Lean 4 

Lean 4 poses additional challenges for automatic trajectory collection. Limited familiarity with Lean 4 syntax, tactics, and library conventions makes correct proof generation di ffi cult for the collection models, and entering and editing proofs through a GUI adds further interaction overhead. Generating theorem statements from scratch also provides no assurance that the resulting tasks admit proofs within the available interaction budget. To e ffi ciently build supervision for automated theorem proving (ATP), we therefore construct desktop interaction trajectories from existing Lean proofs. We obtain 1,608 problems with proof code from the Formal Math Autoformalization Dataset (Commons, 2026) and use their proofs to guide deterministic linear rollouts. Before collection, we compile each theorem together with its reference proof and retain only those that pass compilation. For each retained problem, we preserve the imports, declarations, and target theorem statement, and replace the proof body with an indented sorry placeholder. The theorem statement with this unfinished proof serves as the task instruction. The collector launches a VM with VS Code open on the Lean project and stages the problem in /home/user/sci/Sci/Basic.lean ,recording the initial screenshot. This setup fixes both the task and its reference solution before collection, while the recorded trajectory shows how to construct that solution through the same file-editing code interface used during evaluation. As a concrete example, the following shows a reference proof retained for replay after preprocessing: 

Lean 4 Reference Proof                                                                        

> import Mathlib theorem div_add_div_pos_ge_two (a b:R)(ha :0<a) (hb :0<b) :a/b+b/a≥2:= by rw [ge_iff_le, ←sub_nonneg] have hab :(0 :R)<a*b:= mul_pos ha hb have key :a/b+b/a-2=(a -b) ^2/(a *b) := by field_simp ring rw [key] exact div_nonneg (sq_nonneg _) hab.le

The collector replays the nonempty proof lines in order. For the example above, its first action is CODE replace <path> sorry <first-line> ; subsequent actions use CODE insert <path> <index> <line> at the corresponding 1-based line positions. Subsequent lines retain their indentation, including nested tactic blocks. In the example above, the first action replaces sorry with rw [ge_iff_le, ← sub_nonneg] . Later actions insert the positivity fact, the auxiliary algebraic identity and its nested proof, and the concluding tactics. Each action adds one source line, which 19 need not constitute a complete tactic block or a complete proof on its own. After each edit, the collector waits four seconds for the editor to update, saves a screenshot, and records the command and waiting time as a transition. This captures intermediate desktop states throughout proof construction rather than only the completed source file. After replay, we compile the resulting Lean file; only trajectories that pass compilation are marked complete and retained. Intermediate edits may leave proofs incomplete, so compilation is not required at every step. The retained paths are converted into Qwen-format training conversations using the procedure in §E. For Lean, the converter also reconstructs the source file after each edit and includes its current contents in the corresponding observation, allowing the model to condition on both the screenshot and the partially constructed proof. The proof recorder leaves action descriptions and reasoning fields empty, so these demonstrations primarily supervise the file-editing tool calls. After compilation checks, replay, and trajectory filtering, the final dataset contains 1,486 proof trajectories and 7,546 step-level training samples, including terminal steps, from the original 1,608 problems.
