## 摘要
尽管命令行界面（CLI）任务取得了快速进展，近期基于大语言模型（LLM）的智能体在通过图形用户界面（GUI）可靠执行任务方面仍面临困难。一项关键挑战是有限视口内可见内容有限，尤其是在移动设备上，许多与任务相关的目标处于隐藏状态，只有通过滑动交互才能显现。因此，尽管大多数 GUI 智能体都支持将滑动作为一种基本操作，但由于无法看到目标，它们难以判断何时、何处以及如何滑动以显示隐藏内容。我们的定量研究进一步表明，在需要通过滑动进行探索的情形中，GUI 智能体有 47.8% 的情况错误地选择了点击操作。为弥合这一差距，本文提出为 GUI 智能体配备可滚动区域感知能力，使其能够在选择操作前探索隐藏区域。为此，我们基于人工收集的 667 个 UI 屏幕数据集 Hagasu，训练了首个用于可滚动区域感知的多模态模型。实验结果显示，该模型能够正确识别 78.5% 的可滚动区域；在九种 GUI 智能体上进行的实验表明，在依赖探索的任务中，集成 Hagasu 可将端到端平均完成率从 64.8% 提高至 82.7%。为促进后续研究，我们公开了滑动数据集及 Hagasu 的源代码。

## Abstract
Despite rapid progress in command-line interface (CLI) tasks, recent LLM-based agents still struggle with reliable task execution through graphical user interfaces (GUIs). A key challenge is the limited content visible within a bounded viewport, especially on mobile devices, where many task-relevant targets remain hidden and can only be revealed through swipe interactions. Therefore, although most GUI agents support swipe as an action primitive, the lack of target visibility makes it difficult for them to decide when, where, and how to swipe to reveal the hidden content. Our quantitative study further shows that GUI agents incorrectly choose a click action in 47.8% of cases that require swipe exploration. To bridge this gap, this paper proposes equipping GUI agents with scrollable-region perception to support hidden-area exploration before action selection. To this end, we trained the first multimodal model for scrollable-region perception on a manually collected dataset of 667 UI screens, called Hagasu. By correctly identifying 78.5% of scrollable regions, experiments across nine GUI agents show that integrating Hagasu improves the mean end-to-end completion rate from 64.8% to 82.7% on explore-dependent tasks. To facilitate follow-up research, we release the swipe dataset and the source code of Hagasu.

## 1. 核心问题与整体含义

### 研究动机与背景
- GUI 智能体通常根据**当前截图、任务指令和操作历史**选择下一步动作，但截图只覆盖有限视口。移动应用中的列表、轮播图和嵌套容器，往往将任务目标隐藏在屏幕之外。
- 因而，GUI 操作不仅是“找到并点击可见目标”，还需要判断：**是否应该探索、应该滑动哪个区域，以及采用什么方向**。
- 现有智能体虽然普遍支持滑动动作，却容易选择一个“看起来最相关”的可见元素，而不是先探索隐藏内容。论文将这种偏向称为面向可见候选项的“贪心交互”。

### 初步研究证据
作者对 **7 个模型、55 个应用中的 218 个交互案例**进行测试，其中包含 192 个滑动案例和 26 个点击案例：
- 点击规划平均成功率为 **90.1%**，滑动规划仅为 **42.9%**，相差约 **47.3 个百分点**。
- 在失败的滑动案例中，**83.73%**表现为错误点击可见目标。
- 垂直滑动明显比水平滑动容易：成功率分别为 **57.4%**和 **25.3%**。

### 整体含义
论文提出，GUI 智能体的瓶颈不只是可见元素定位能力，还包括对**“哪里存在进一步获取信息的交互机会”**的感知。

其核心思路是：不直接预测隐藏目标的位置，而是先识别能够揭示隐藏内容的可滚动区域，为后续规划提供依据。这可以理解为针对 GUI **部分可观测性**的一种轻量补偿机制。

## 2. 方法论：Hagasu 的核心思想与技术流程

### 2.1 总体设计
Hagasu 是一个独立的可滚动区域感知模块，流程为：

> 当前截图 → 预测可滚动区域 → 在截图上绘制区域框并补充提示 → 原有 GUI 智能体选择动作 → 执行并更新历史。

- Hagasu 提供感知线索，**不替代原智能体的动作策略**。
- 推理时只需要截图，不依赖无障碍 XML，也不需要事先知道目标元素。
- 因此，它不是完整的滑动规划器：滑动时机、区域选择、方向和距离等，仍主要由基础智能体决定。

### 2.2 数据构建与监督形式
作者从 **49 个 Android 应用**收集了 **667 张含可滚动区域的截图**：
- 33 个中文应用、16 个英文应用。
- 364 张截图包含单一区域，303 张包含多个区域。
- 随机划分为 **540 张训练、60 张验证、67 张测试**。

标注流程包括：
1. 通过 ADB 获取截图和无障碍 XML。
2. 根据 XML 中的 `scrollable=true` 和边界信息生成候选区域，保留面积超过屏幕 **4%**的有效候选框，并结合图像候选区域。
3. 两名作者独立核验、删除误框和补充漏框，第三名作者裁决分歧。
4. 标注所有可滚动区域，包括全页容器、局部列表和轮播图，并记录滑动方向。

**XML 只用于辅助标注，并不是部署依赖。**

模型学习的映射是：给定截图和固定指令，输出该截图中全部可滚动区域的 JSON 边界框列表；每个框采用左上角和右下角坐标表示。

### 2.3 多区域过采样
为减少局部区域漏检，作者提高多区域截图的训练权重：
- 每张截图每轮重复次数等于其标注区域数量，最多重复 **5 次**。
- 540 张训练截图因此形成每轮 **964 条训练条目**，但没有增加独立截图数量。

这一设计偏重提升召回率，代价是可能增加误检。

### 2.4 两阶段 LoRA 微调
Hagasu 以 **Qwen3.5-9B**为骨干模型：

- **第一阶段：视觉适配**
  - 训练视觉组件中的 LoRA 适配器。
  - 冻结原始视觉权重、视觉—语言连接模块和语言模型。
  - 目标是加强对 UI 外观与空间结构的识别。

- **第二阶段：语言侧适配**
  - 将第一阶段视觉适配器合并至骨干模型。
  - 冻结适配后的视觉组件和原始语言模型权重。
  - 训练新的语言侧 LoRA 适配器及全部连接模块参数。
  - 目标是将视觉特征与可滚动区域语义、结构化输出关联起来。

两个阶段均采用 **LoRA rank 16、α=32、dropout 0.1**。

### 2.5 智能体集成与缓存
每个决策步骤中：
1. 获取截图。
2. 调用 Hagasu，或复用缓存中的区域预测。
3. 绘制带编号的区域框，补充“编号框表示预测可滚动区域”的提示。
4. 基础智能体结合任务和历史决定点击、滑动或结束。
5. 执行动作，比较前后截图并更新记忆，直至完成或耗尽动作预算。

在线实验采用截图缓存：若当前截图与同尺寸缓存截图的 **SSIM≥0.90**，则复用最相似截图的区域框，以降低重复推理成本。

## 3. 实验设计、Benchmark 与对比方法

论文没有直接以通用公共 benchmark 为主，而是构建了三个层次的专项评测。

### 3.1 RQ1：可滚动区域检测
- **测试集**：自建数据集中的 67 张截图。
- **对比配置共 8 个**：
  1. Qwen3-VL-8B；
  2. Qwen3.5-9B；
  3. Qwen3.5-9B + XML 候选提示；
  4. Qwen3.5-9B + 单阶段 SFT；
  5. Qwen3.5-9B + 两阶段 SFT；
  6. Qwen3-VL-8B + 两阶段 SFT；
  7. 完整 Hagasu；
  8. Hagasu + GRPO。

**评价指标：**
- 使用匈牙利算法进行预测框与标注框的一对一匹配，以 **IoU≥0.5**判定检测正确。
- 报告微平均 Precision、Recall、F1。
- Exact Match 衡量整张截图的区域集合是否完整正确、无多框和漏框。
- 集合级 mIoU 同时惩罚漏检和多检。

### 3.2 RQ2：离线滑动决策
- **Benchmark**：60 个由人工录制成功轨迹的移动任务，平均每个任务 4.1 个动作。
- 共 **245 个步骤**：99 个滑动，其中垂直 39 个、水平 60 个；另有 146 个点击。
- 测试 **9 个 VLM**，包括 GPT-6-Luna、GPT-5.6-Luna、Seed-2.1-Pro、Seed-Evolving、Qwen3.8-27B、Qwen3.7-Plus、Qwen3.5-9B、DeepSeek-V4-Flash-Vision 和 GUI-OWL-7B。

每个模型比较三种输入：
- **V**：原始截图；
- **H**：Hagasu 预测区域标注；
- **G**：人工真实区域标注。

指标包括：
- 参考滑动步骤被预测为滑动的比例；
- 参考点击步骤被预测为点击的比例；
- 点击步骤被错误预测为滑动的比例。

**注意：这里的主要指标衡量动作类型选择，并不等价于滑动区域、方向、距离全部正确。**

### 3.3 RQ3：在线端到端任务
- 从同一任务池随机选择 **18 个依赖滑动探索的任务**，涉及 **16 个 Android 应用**。
- 场景覆盖内容发现、媒体播放、商品搜索和旅行信息检索。
- 选择 RQ2 中表现较好的 **3 个模型**：Qwen3.8-27B、Qwen3.7-Plus、GPT-6-Luna。
- 每个模型比较原始设置与 Hagasu 设置，每项任务重复 **3 次**。
- 在小米 13、Android 16、2400×1080 分辨率设备上执行，人工恢复初始状态并判断成功。

报告成功率、轮次间波动、操作步数、执行时间和 token 消耗。

## 6. 主要结论与发现

### 6.1 区域感知显著提升，但完整识别仍困难

| 方法 | Precision | Recall | F1 | mIoU | Exact Match |
|---|---:|---:|---:|---:|---:|
| 原始 Qwen3.5-9B | 58.46% | 29.23% | 38.97% | 31.63% | 23.88% |
| 两阶段 SFT，无过采样 | 73.68% | 64.62% | 68.85% | 56.24% | 44.78% |
| Hagasu | 68.46% | **78.46%** | **73.12%** | **60.20%** | 43.28% |

- Hagasu 的 **78.46%是区域召回率**，不是通用意义上的准确率。
- 多区域过采样显著减少漏检，但降低精确率和整屏 Exact Match。
- GRPO 没有带来额外收益，F1 降至 **71.13%**；作者对其收敛困难的解释属于推测，未被独立验证。

### 6.2 滑动决策改善，伴随一定副作用
- 九模型平均滑动召回率：**46.02% → 53.87%**，约增加 **7.85 个百分点**，相对提高约 **17.1%**。
- 点击召回率：**95.21% → 93.53%**。
- 点击误判为滑动的比例：**2.05% → 3.88%**。

说明区域提示能够缓解“只点击可见目标”的偏向，但存在过度滑动风险，部分模型的副作用更明显。

### 6.3 端到端任务成功率提高

| 模型 | 原始成功率 | 接入 Hagasu |
|---|---:|---:|
| Qwen3.8-27B | 70.37% | 88.89% |
| Qwen3.7-Plus | 74.07% | 88.89% |
| GPT-6-Luna | 50.00% | 70.37% |
| 平均 | 64.81% | 82.72% |

平均增加约 **17.90 个百分点**，相对提高约 **27.6%**，但付出了明显时间开销。

### 6.4 更准确的区域标注不必然带来更好的规划
真实标注条件的平均滑动召回率为 **52.64%**，低于 Hagasu 条件的 **53.87%**。

这表明规划能力仍是瓶颈；也可能涉及标注呈现、区域数量或决策随机性，**不能据此认定预测区域优于真实区域**。

### 6.5 需要纠正的表述口径
- 摘要和元数据容易让人理解为“9 个智能体均完成端到端测试”；正文实际上是：**9 个模型参与离线评测，3 个模型参与在线评测**。
- 摘要的 **47.8%错误点击率**，与正文的“滑动失败案例中 83.73%错误点击”大致相容，但后者具有不同分母，不应混用。

## 7. 优点与亮点

- **问题定位具体且实用**：区分“具备滑动动作”与“知道何时、何处探索”，揭示了可见元素定位之外的重要瓶颈。
- **模块化、侵入性低**：只增强截图和提示，无需重训整个智能体或改变动作接口。
- **推理不依赖 XML**：结构信息仅用于标注，部署时采用截图输入。
- **小数据训练设计有针对性**：两阶段 LoRA 和多区域过采样分别对应视觉适配与局部区域漏检问题。
- **评估层次完整**：同时检验感知质量、动作类型选择和实际任务成功率。
- **结果披露较平衡**：报告负面消融、点击性能损失、时间开销及区域提示误导规划的案例，而非只展示成功结果。

## 8. 不足与局限

### 8.1 数据覆盖和泛化风险
- 数据只有 667 张截图，且均为含可滚动区域的页面，缺少明确的无滚动区域负样本覆盖。
- 采用截图级随机划分，未报告按应用隔离的划分；相似页面或同应用模板可能同时出现在训练和测试中，跨应用泛化能力仍待验证。
- 尚未验证桌面、网页、iOS、多分辨率及更多语言环境。

### 8.2 标注与可观测性限制
- 静态截图未必能确定区域是否真的可滚动、是否已到边界，部分属性需要实际交互验证。
- 标注由作者完成，虽有交叉核验，但未报告标注一致性统计或系统性的交互验证协议。
- 标注提及方向、示例也使用方向配色，但核心输出定义和 RQ1 主要围绕边界框，**方向预测的训练与评测说明不够充分**。

### 8.3 因果解释仍不完整
- 缺少“仅文字提示”“随机区域框”等对照，难以完全分离准确区域感知、视觉显著性增强和一般探索提醒各自的贡献。
- 缺少区域置信度、框精度与下游收益之间的系统分析。
- 初步研究中点击案例明显少于滑动案例，动作难度和样本结构并未完全控制。

### 8.4 提示可能形成新的探索偏差
- 框选区域可能被智能体过度信任，未标注区域则被忽视。
- TrainPal 失败案例中，模型反复探索被标出的水平轮播图，却没有滚动漏标的页面区域，最终错过“View more”入口。
- 这说明“保留动作自主权”不等于“不会受错误感知误导”。

### 8.5 部署效率与复现限制
- 每任务增加约 49 秒，对实时个人助理或严格时限场景并不轻微。
- SSIM 缓存可能在整体相似但局部布局改变时复用过时框，论文未单独量化这一风险。
- 训练硬件和完整超参数披露不足，限制成本评估与复现。

**总体评价：**Hagasu 提供了一个有实证支持、易于接入的 GUI 探索增强方案，证明显式感知可滚动区域具有价值。但其贡献更适合界定为**移动端滑动依赖任务中的有效辅助模块**，而不是已经解决通用隐藏目标搜索或完整探索规划。
