Despite rapid progress in command-line interface (CLI) tasks, recent LLM-based agents still struggle with
reliable task execution through graphical user interfaces (GUIs). A key challenge is the limited content visible
within a bounded viewport, especially on mobile devices, where many task-relevant targets remain hidden
and can only be revealed through swipe interactions. Therefore, although most GUI agents support swipe as
an action primitive, the lack of target visibility makes it difficult for them to decide when, where, and how to
swipe to reveal the hidden content. Our quantitative study further shows that GUI agents incorrectly choose a
click action in 47.8% of cases that require swipe exploration. To bridge this gap, this paper proposes equipping
GUI agents with scrollable-region perception to support hidden-area exploration before action selection. To
this end, we trained the first multimodal model for scrollable-region perception on a manually collected
dataset of 667 UI screens, called Hagasu. By correctly identifying 78.5% of scrollable regions, experiments
across nine GUI agents show that integrating Hagasu improves the mean end-to-end completion rate from
64.8% to 82.7% on explore-dependent tasks. To facilitate follow-up research, we release the swipe dataset and
the source code of Hagasu.

Introduction
Although large language models (LLMs) have made surprising progress on command-line interface
(CLI) tasks [48, 49], reliable task execution through graphical user interfaces (GUIs) remains chal-
lenging [20, 46]. Beyond the well-known challenge of interpreting visual semantics, the limited
content visible within a bounded viewport constitutes a key bottleneck for GUI agents. Specifi-
cally, to preserve visual appeal, UI designs constrain element density and thereby prevent visual
clutter [34]. Modern UIs therefore widely use scrollable containers, such as lists and carousels, to
accommodate additional functionality and content beyond the current view, requiring scrolling to
reveal them [29]. At every step, GUI agents are thus forced to decide under uncertainty whether to
pick a visible target or explore hidden areas.
This dilemma is particularly acute in mobile GUIs. Limited screen size leaves many UI elements
outside the current viewport, accessible only through swipe interactions. Although most GUI
agents already support swipe as an action primitive [25, 30, 33, 41, 54], recent research shows that
reliably completing mobile tasks remains challenging [20, 32]. To quantify this difficulty, this paper
conducts a study of 7 GUI agents across 218 tasks and finds that the rate of correctly planned swipe
actions is 47.3 percentage points lower than that of click actions. Further analysis of 83.73% failed

Therefore, this paper focuses on equipping GUI agents with scrollable-region perception, provid-

Background
This section explains the decision pattern underlying ordinary click interactions and why hidden
targets require a different course of action. We first describe greedy interaction as selecting a
task-relevant component from the current viewport. We then explain why agents need swipe-
based exploration when the correct target is hidden outside that viewport. Finally, we present a
preliminary study comparing click and swipe planning across different interaction scenarios.
2.1
Greedy Interaction Patterns for Visible Targets
GUI agents commonly follow an observation, decision, and execution loop, selecting actions based
on the current interface, task instruction, and interaction history [32, 41, 51, 54]. For a click action,
this decision involves selecting an element in the current viewport and clicking it. We describe this
pattern as greedy interaction: choosing the visible element that appears most likely to advance the

This strategy works when the current viewport contains the correct target, reducing click
planning to semantic matching and coordinate grounding. For example, an agent can fulfill a
request to open Settings by identifying and clicking the visible Settings button. Existing GUI
grounding methods support this process by mapping task descriptions to visible UI elements and
their locations [14, 16, 36, 44, 53].
However, as shown in Figure 1, when the correct target is hidden, even the most relevant visible
element may be an incorrect choice. An agent that continues to select among visible candidates
may therefore force a wrong click instead of reaching the required target, as shown in Figure 1.
The decision must then extend beyond which element to click to whether exploration is needed to
reveal the hidden target.
2.2
Hidden Area Exploration via Swipe Interaction
As mobile apps offer more functionality, their increasingly dense interfaces often contain more
content than the screen can display at once. Task-relevant targets may be partially clipped or
completely hidden within full-page or local scrollable regions, such as lists and carousels [32, 33, 47].
When the target lies beyond the visible content, the agent must swipe to reveal it and then reassess
the available interaction targets.
Planning this exploration requires the agent to decide when, where, and how to swipe before
the target becomes visible. For example, finding a category hidden in a horizontal carousel requires
swiping that carousel rather than clicking another visible category. The agent must infer the
region’s function and relevance to the task, locate its boundaries, and choose a suitable swipe
direction and extent. Multiple or nested scrollable regions complicate this decision, as swiping the
wrong region may reveal content unrelated to the task.
Existing GUI agents already support swipe as an action primitive [30, 41, 54]. However, this
support alone does not ensure that an agent can recognize when exploration is necessary or select

click planning with visible targets and swipe planning for hidden-area exploration.
2.3
Preliminary Study of Scrollable Perception
To examine the difficulty of hidden-area exploration compared with visible-target selection, we
conduct a preliminary interaction study. The study compares click and swipe planning by prompting
GUI agents to locate a specific UI element, either visible or hidden, and assessing whether they
select the correct next interaction based on the current screenshot.
2.3.1
Study setup. Both general-purpose VLM GUI agents and specialized GUI models are selected
for this study. Specifically, general-purpose VLM GUI agents include Qwen3-VL [15] and GPT-
5.4 [6]. As for the specialized GUI models, we include GUI-Owl [52], UI-TARS [30], GUI-G2 [38],
UI-Venus 1.5 [39] and MAI-UI [55]. To control for differences in input, all agents receive the same
current screenshot and target element description.
2.3.2
Task configuration. Using an Android phone connected through ADB, we manually collected
218 UI interactions from 55 applications, including 36 Chinese-language and 19 English-language
applications. These interactions include 192 swipe cases requiring exploration to reveal or reach
the target component and 26 click cases with visible targets as the reference condition.
Since scrollable regions vary in appearance, we categorize these swipe interactions by direction
(vertical or horizontal), scope (full-screen or local), and target visibility (partially visible or com-
pletely invisible). Specifically, full-screen scrolling refers to scrollable regions occupying more than
75% of the screen, while all remaining cases are classified as local swiping. As for visibility, we
classify a target as completely invisible when less than 25% of its area is visible, and as partially
visible when 25% to 75% is visible. The upper bound reflects the likelihood that targets with more
than 75% of their area visible can already be interacted with directly.
2.3.3
Evaluation metrics. Instead of running each agent end-to-end on complete tasks, we focus on
whether it can produce the correct next interaction to facilitate comparison across agents. Although
swipe actions involve multiple parameters, including position, direction, and distance [33], this study
focuses on position and direction, since the remaining parameters are less relevant to scrollable
perception. We then report the proportion of correctly planned interactions in each task category
to compare click and swipe planning.
2.3.4
Results and Implications. Table 1 shows a substantial gap between visible-target clicking and
hidden-area exploration. Weighting the eight swipe categories by their actual sample counts and
averaging across the evaluated agents, the mean success rate is 90.1% for click cases and 42.9% for
swipe cases, a decrease of 47.3 percentage points. Moreover, agents’ strong click capabilities do
not translate into reliable swipe planning. For example, GUI-Owl, UI-Venus 1.5, and MAI-UI each
achieve 100% on click cases, but their sample-weighted swipe success rates are only 42.2%, 35.4%,
and 40.6%, respectively.
Direction is the clearest source of variation: performance averages 57.4% for vertical swipes but
only 25.3% for horizontal swipes. This pattern is consistent with the vertical scrolling convention
used for UI lists [7]. Moreover, target visibility is associated with a substantial difference in planning
accuracy: completely invisible targets achieve a higher weighted average than partially visible
targets (47.2% versus 36.8%). The gap between full-screen and local swiping is the smallest (44.6%
versus 41.3%), suggesting that region size is not the primary bottleneck in current agents’ GUI
understanding.
Further analysis reveals a dominant failure mode: in 83.73% of failed swipe tasks, agents decided
to click on an incorrect visible target instead of exploring the correct but hidden region. Only

3
Method
This section presents Hagasu, a scrollable-region perception module that supports hidden-area
exploration through non-intrusive augmentation of GUI agents’ screenshots and prompts.
3.1
Overview
As shown in Figure 2, the Hagasu workflow consists of dataset construction, model fine-tuning,
and agent integration. First, we collect Android screenshots and accessibility XML through ADB
and manually verify and refine XML-derived region candidates to construct screenshot–region
pairs. Second, we build on Qwen3.5-9B’s UI understanding capabilities through two-stage LoRA
fine-tuning, enabling it to predict all scrollable regions as a JSON list of bounding boxes. Third,
when integrated into a GUI agent, Hagasu marks its predicted regions on the screenshot at each
step and supplements the agent’s prompt with cues for swipe-based exploration. The base agent
combines these cues with the task and interaction history to plan its next action, retaining control
over whether and how to click or swipe.
3.2
Dataset Construction
3.2.1
Data Acquisition and Scrollable-Region Annotation. Although public GUI interaction datasets
such as Android in the Wild (AITW) [33] and GUIOdyssey [27] provide screenshots and action
trajectories, they lack complete bounding-box annotations of all scrollable regions in each screen-
shot. As shown in Table 2, even existing first-tier models struggle to identify scrollable regions
accurately, making automatic annotation infeasible. We therefore manually collect and annotate UI
screenshots to provide reliable supervision for scrollable-region perception training.

49 apps are selected from Google Play’s popular app rankings [2], including 33 Chinese- and
16 English-language apps. For each app, we manually navigate its interface and save screenshots
containing scrollable regions. To reduce annotation effort, we also capture the corresponding
accessibility XML for each screenshot through Android Debug Bridge (ADB) [1], since the UI
component attributes in the XML can support preliminary region annotation [13]. Specifically, we
parse each XML node’s bounds attribute into a screen-coordinate rectangle, retain nodes whose
scrollable attribute is set to true and valid bounds cover more than 4% of the screen, deduplicate
and clip these boxes, and combine them with image-based proposals to form the candidate set for
manual verification. Note that the XML serves only as an annotation aid and is not required by
Hagasu at inference time.
Finally, three authors of this paper manually annotate the scrollable regions using these candidates
as a starting point. Specifically, two authors independently inspect each screenshot, retain valid
candidates, remove incorrect ones, and draw boxes for missed regions. The third author resolves
disagreements to finalize the annotations. The annotations include each region’s bounding box and
swipe direction. In particular, for screenshots with multiple scrollable regions, we annotate every
region, including full-page containers and local components such as lists and carousels.

3.3.1
Multi-Region Sampling. During annotation, we found that many UI screens contain multiple
scrollable regions. Identifying the complete region set on these screens is substantially more chal-
lenging than detecting a single region, as local scrollable regions can easily be missed. Specifically,
303 of the 667 screenshots contain multiple scrollable regions, accounting for 45.4% of the we
selected screenshots. Thus, these screens reflect a common pattern in practical mobile interfaces,
where a full-page container may coexist with local lists, carousels, or other scrollable components.
All scrollable regions on these screens must be identified, since the task-relevant component may
be located in any one of them.
To address low recall on screens with multiple scrollable regions, we therefore oversample
training screenshots according to the number of annotated regions. Specifically, the number of
repetitions per epoch for each training screenshot is equal to its number of annotated scrollable
regions, capped at five. Table 2 in the following Section 5 shows that this reweighting effectively
improves the model’s recall by increasing its exposure to multi-region examples during training.
3.3.2
Two-Stage LoRA SFT. Scrollable regions lack clear visual indicators, making it difficult for
models to recognize them and associate their visual appearance with swipe interaction semantics.
Given the limited size of our manually collected dataset, we adopt LoRA [19] to adapt the model
through a small number of trainable parameters instead of full-parameter fine-tuning. To address
this challenge while making effective use of the limited data, we organize LoRA fine-tuning into
two stages. The first stage strengthens visual perception of UI images, focusing on the appearance
and spatial structure of UI regions. The second stage fine-tunes the language model to connect
swipe interaction semantics with the visual features learned in the first stage.
Following prior work on Qwen-based GUI models [16, 25], we select Qwen3.5-9B as the backbone
of Hagasu. Specifically, the first stage trains LoRA adapters in the visual component while keeping
the original visual weights, the merger, and the language model frozen. The trained visual adapters
are then merged into the backbone to initialize the second stage. In the second stage, we train newly
introduced language LoRA adapters and all merger parameters while keeping the adapted visual
component and the original language-model weights frozen. Both stages use LoRA with rank 16,
𝛼= 32, and dropout 0.1, with supervision provided by screenshots paired with JSON annotations
and training samples drawn using the multi-region oversampling strategy described above.
The 667 screenshots are randomly divided into 540 training, 60 validation, and 67 test samples.
After oversampling, the 540 training screenshots yield 964 training entries per epoch, while the
validation and test sets remain unchanged. The validation set is used for model selection, and the
test set is reserved for evaluation in Section 5.
3.4
Agent Integration
3.4.1
Screenshot Annotation and Interaction Loop. We make minimal modifications to integrate
Hagasu into various GUI agents as a non-intrusive plug-in, providing supplementary visual and
textual cues for the model’s automated exploration.
At each interaction step, agent captures a screenshot and passes it to Hagasu, which returns a
JSON list of bounding boxes for the predicted scrollable regions. As shown in Figure 4, we annotate
the screenshot with numbered boxes and add the following cue 𝑐to the agent’s prompt: “The
screenshot has numbered boxes marking predicted scrollable regions.” Using the task instruction,
annotated screenshot, and interaction history, the agent generates its next action, executes it on the
device, and captures a new screenshot for subsequent planning. Algorithm 1 provides a pseudocode
summary of our agent loop.

modifies the screenshot and prompt, these modifications serve only as supplementary information

3.4.2
Memory Management. Although this paper simplifies most GUI-agent components, such
as reflection, to highlight the effect of Hagasu on planning, memory remains essential for multi-
step interaction tasks. We therefore provide a simplified memory management module to support
subsequent evaluation. Specifically, two memory management strategies are designed for offline and
online experiments. In offline experiments, the history briefly describes the screenshots and actions
from preceding steps. Since the preceding steps are deterministic, we prepared a predetermined
interaction history for each step. At each step, the model receives the interaction history of all
preceding steps in that task. In online experiments, the agents will generate their own interaction
history after each step while performing the task. In addition to screenshot and action descriptions
in the same format as in offline experiments, the agent also retains the previous screenshot and
compares it with the current one to determine whether the action changed the page, helping reduce
the risk of entering an infinite loop.

4
Experiment Design
Experiments are conducted to evaluate Hagasu’s swipe perception capability, its support for swipe
planning, and its impact on end-to-end task completion when integrated into GUI agents. The
three research questions are as follows.
• RQ1: Scrollable Region Perception. How accurately can Hagasu detect and localize scrollable
regions in mobile UIs?
• RQ2: Swipe-aware Planning. How effectively does scrollable-region perception help GUI
agents make correct swipe decisions?
• RQ3: Agent Integration. How much does Hagasu affect GUI agents’ end-to-end task completion
on swipe-dependent tasks, and what overhead does it introduce?
4.1
Datasets
For RQ1, we evaluate whether Hagasu can correctly identify all scrollable regions in a UI screenshot
and accurately localize their boundaries. We use the dataset described in Section 3, containing 67
mobile UI screenshots. Each screenshot is annotated with all scrollable regions and their boundaries.
Note that a screenshot may contain multiple scrollable regions. Therefore, we compare the predicted
region set with the complete ground-truth set.
For RQ2, we construct an offline benchmark from human-recorded successful trajectories of
60 mobile GUI interaction tasks, with each trajectory containing an average of 4.1 actions and at
least one swipe. Specifically, this benchmark contains 245 interaction steps, including 99 swipes
(39 vertical and 60 horizontal) and 146 clicks. It evaluates whether agents can correctly decide
between acting on visible content and exploring off-screen content when prompted with Hagasu’s
scrollable-region predictions.

4.2
Baselines
For RQ1, we compare Hagasu with both untuned base models and several training variants to
understand where the improvement in scrollable-region perception comes from. Specifically, we first
evaluate two untuned baselines, Qwen3-VL-8B [15] and Qwen3.5-9B [8]. We also include Qwen3.5-9B
+ XML, where scrollable-region candidates extracted from XML are provided to the model for visual
refinement. This comparison examines whether explicit structural cues can compensate for the
lack of task-specific fine-tuning.
We then construct several variants of Hagasu to study its training design. Qwen3.5-9B + one-stage
SFT directly fine-tunes the merger and language-model layers while keeping the visual encoder
frozen. Qwen3.5-9B + two-stage SFT further introduces the visual fine-tuning stage described in
Section 3. Besides, to examine the effect of the base model, we apply the same two-stage SFT
procedure to Qwen3-VL-8B, yielding Qwen3-VL-8B + two-stage SFT. Our full Hagasu configuration
further applies multi-region oversampling on top of Qwen3.5-9B with two-stage SFT. Finally, we
append a GRPO stage to the full configuration to examine whether reinforcement learning provides
additional gains. The relationship among these configurations is summarized in Figure 5.
For RQ2, we evaluate nine VLMs with different model scales and GUI capabilities: GPT-6-Luna [5],
GPT-5.6-Luna [4], Seed-2.1-Pro [12], Seed-Evolving [11], Qwen3.8-27B [10], Qwen3.7-Plus [9],
Qwen3.5-9B [8], DeepSeek-V4-Flash-Vision [3], and GUI-OWL-7B [52].
Each model is evaluated under three conditions: V stands for Vanilla, which uses the original
screenshot as input. +Hagasu is abbreviated as H, scrollable regions predicted by Hagasu are

4.3
Metrics
For RQ1, we evaluate two aspects of scrollable-region perception: whether Hagasu identifies the
correct set of regions and how accurately it localizes their boundaries.
To evaluate region detection capability, we report Precision, Recall, F1, and Exact Match. Predicted
and ground-truth regions are matched one-to-one within each screenshot using the Hungarian
algorithm [21], with IoU ≥0.5 as the matching threshold. Matched predictions are counted as true
positives, while unmatched predictions and ground-truth regions are counted as false positives
and false negatives, respectively. Precision, Recall, and F1 are micro-averaged over the entire test
set. Exact Match measures the percentage of screenshots for which the complete set of scrollable
regions is correctly detected, with neither missing nor extra regions.
As for localization accuracy, we report set-level mIoU. For each screenshot, we perform one-
to-one matching between predicted and ground-truth regions to maximize their total IoU. The
summed IoU is normalized by the larger number of predicted or ground-truth regions, such that
both missing and extra regions are penalized. We then average the resulting scores across all
screenshots.
For RQ2, we report three metrics to evaluate both the benefit and potential side effects of
scrollable-region cues. Swipe Prediction Recall is the percentage of the 99 reference swipe steps
correctly predicted as swipes, measuring the agent’s ability to identify when exploration is needed.
Click Prediction Recall is the percentage of the 146 reference click steps correctly predicted as clicks,
measuring whether region cues preserve normal click decisions. Finally, Click→Swipe Rate is the
percentage of reference click steps incorrectly predicted as swipes, specifically measuring whether
the cues cause agents to over-select swipe actions.
For RQ3, we report task success rate (SR) and 𝜎(SR) to assess task completion and stability,
with 𝜎(SR) denoting the population standard deviation of the three round-level success rates. We
compare the average number of interaction steps across all runs and across successful runs in
each setting to evaluate interaction efficiency. We also report average execution time (Avg. Time)
and input/output token usage (Avg. I Token and Avg. O Token) per run to measure execution
cost. Token usage covers reported agent-model decision and memory generation calls and Hagasu
region-annotation inference, with each component’s mean rounded down to an integer.
4.4
Implementation
We collect mobile UI screens from Android devices through ADB [1], recording both the screenshot
and its accessibility XML for each UI state. During annotation, XML- and image-based proposals are
used only as candidate regions to reduce manual effort. Two annotators independently verify these
candidates, remove invalid regions, and add missed regions, while disagreements are resolved by a
third annotator. The final annotation contains the complete set of manually verified scrollable-region
bounding boxes for each screenshot.
Hagasu is fine-tuned from a vision-language backbone using screenshot–region supervision.
Given a screenshot, the model outputs the bounding boxes of all detected scrollable regions in
JSON format.

Evaluation Result and Analysis
5.1
RQ1: Scrollable-Region Detection
Overall performance. Hagasu substantially outperforms the untuned vision-language models in
scrollable-region perception. As shown in Table 2, Hagasu achieves 78.46% Recall and 73.12% F1,
improving over untuned Qwen3.5-9B by 49.23 and 34.15 percentage points, respectively. Providing
Qwen3.5-9B with XML-derived candidate regions improves F1 from 38.97% to 56.72%, confirming
that structural cues are useful. Nevertheless, Hagasu further improves F1 to 73.12%, showing that
task-specific fine-tuning is substantially more effective than directly relying on XML candidates.
Effect of training designs. Multi-region oversampling primarily improves region coverage. Re-
moving it reduces Recall from 78.46% to 64.62% and F1 from 73.12% to 68.85%, while increasing
Precision from 68.46% to 73.68%. This trade-off is consistent with the goal of oversampling: reducing
missed regions at the cost of some additional false positives. The two-stage SFT schedule provides
a smaller but consistent improvement over one-stage SFT, higher Recall, mIoU, and Exact Match.
These results support the use of both visual fine-tuning and multi-region oversampling in Hagasu.
Other design choices. Appending GRPO to Hagasu provides no additional benefit, reducing F1
from 73.12% to 71.13% and Exact Match from 43.28% to 38.81%. This suggests that predicting floating-
point coordinates for multiple regions creates a large search space that may hinder reinforcement
learning convergence with limited training data. Despite the substantial improvement in region
coverage, complete region-set recovery remains challenging, with Hagasu achieving an Exact Match
of 43.28%.

recall decreases by only 1.68 points, from 95.21% to 93.53%. Meanwhile, the Click→Swipe rate
increases modestly from 2.05% to 3.88% (+1.83 points). These results show that Hagasu makes

swipe unnecessarily.

RQ3: Plug-in Effectiveness, Overhead, and Side Effects
RQ3 evaluates how Hagasu affects the end-to-end task automation performance of GUI agents.
This experiment examines whether scrollable-region perception can lead to higher end-to-end
task success and assesses the additional execution cost. The three VLMs with the highest swipe
prediction recall in RQ2’s +Hagasu setting are selected for end-to-end evaluation. GUI agents
powered by these VLMs are then evaluated under Vanilla and +Hagasu on the 18 swipe-dependent
tasks, with each task run three times per agent and setting and success assessed manually for each
run. Table 4 reports task success rate (SR) and its standard deviation across rounds (𝜎(SR)), average

Task completion and consistency. All three agents achieve higher task success rates under +Hagasu
on swipe-dependent tasks, with the mean rising from 64.81% to 82.72% (+17.90 percentage points).

embedded in complete task trajectories. GPT-6-Luna shows the largest gain in task success rate,
rising from 50.00% to 70.37%, while both Qwen agents reach 88.89%, showing that scrollable-region
perception benefits even agents with stronger baseline performance.
Moreover, Hagasu reduces the standard deviation of task success rates across evaluation rounds
for Qwen3.8-27B and GPT-6-Luna, particularly the latter with its lower baseline success rate,
indicating more consistent task completion across repeated runs. Nevertheless, we acknowledge
that Hagasu’s prediction errors can contribute to task failures. A representative case is discussed in
Section 6.1.

complete more tasks with fewer interactions, whereas GPT-6-Luna follows longer trajectories.

6
Discussion
This section first uses a case study to show that, although scrollable-region perception has proven
valuable for GUI agents, integrating it through supplementary cues has inevitable limitations. The
case illustrates how Hagasu can degrade an agent’s task performance. It then considers threats to
validity arising from manual annotation and variations in agent performance.
6.1
Case Study: Towards Integrated Perception and Planning
In RQ3, we observe that although Hagasu is designed to preserve agents’ decision-making autonomy,
its predictions can still misguide their exploration. To better understand this phenomenon, we
analyze a failed execution run on TrainPal’s homepage. The task requires locating KORAIL PASS
through the Global Pass section on TrainPal’s homepage. In a +Hagasu run, the Qwen3.8-27B-based
agent fails to locate KORAIL PASS, illustrating how incomplete region cues can interfere with its
exploration.

and ultimately returns finish on the homepage without locating the requested pass.
This case indicates that preserving an agent’s decision-making autonomy does not fully prevent
incomplete perception from misleading its planning. Although Hagasu only provides supplementary
guidance without enforcing any action, the agent may still rely too heavily on these cues and fail
to revise its search strategy after repeated unsuccessful interactions. This suggests future research
on internalizing scrollable-region perception into GUI agents through large-scale joint training
with task planning, so that agents can systematically learn when to explore, where to explore, and
when to stop exploring.
6.2
Threats to Validity
Annotation subjectivity. Since scrollable regions may lack clear visual boundaries, manual an-
notations are susceptible to omissions and errors. Local or nested regions can be overlooked, and
annotators may disagree on their boundaries, affecting both training supervision and the reference
annotations used in RQ1. Although XML-derived candidates provide an initial set of regions for
inspection, the candidate set may omit scrollable regions or include non-scrollable ones. To mitigate
this threat, two authors independently inspect each screenshot, remove invalid candidates, and add
missed regions. A third author resolves disagreements to finalize the annotations. Although some
annotation noise may remain, candidate-assisted inspection helps identify potential regions, while
independent checks and disagreement resolution reduce reliance on individual judgments.
Stability of effectiveness. Changes in UI states and variations in agent behavior may affect the
observed performance gains from Hagasu. The same task may encounter different interface states
or action sequences across executions, so a single run may overestimate or underestimate the
benefit of the plug-in. We acknowledge this threat and seek to mitigate it by evaluating diverse
test tasks with multiple agents. This broader evaluation reduces dependence on a particular task
or agent’s decision patterns. In RQ3, Hagasu improves the task success rate of all three evaluated
agents. Moreover, each task in RQ3 is executed three times, and we report the mean within-agent
population standard deviation of round-level task success rates (5.33 percentage points under
+Hagasu, obtained by averaging the three agents’ unrounded standard deviations over the three
evaluation rounds; Table 4). These repeated runs allow us to assess whether the observed gains
persist across executions and quantify the remaining variation.

Related Work
Interactive region perception. Identifying and localizing interactive regions is fundamental to GUI
task automation. Structured approaches use UI hierarchies and element attributes to expose interac-
tion targets [17, 42], while visual approaches ground actions directly in screenshots. ScreenAI [14]
studies screen understanding and UI element annotation, and SeeClick [16] develops GUI ground-
ing through visual pretraining. Building on visual localization, ShowUI [25], OS-Atlas [45], and
UIPro [22] further connect grounding with GUI action prediction. ScreenSpot-Pro [23] evaluates
these localization capabilities in high-resolution professional interfaces.
Beyond locating interaction targets, existing work also investigates what interactions UI re-
gions support. Schoop et al. [35] predict whether users perceive UI elements as tappable, while
Ferret-UI [53] supports UI function inference and goal-oriented interaction conversations. Omni-
Parser [28] combines interactable-element detection with functional descriptions to support action
grounding. Complementing such perception methods, Set-of-Mark prompting [50] overlays marks
on image regions so that a multimodal model can refer to them explicitly. These methods improve
the localization, functional understanding, and explicit referencing of visible interaction targets.
However, none specifically focuses on identifying scrollable containers that can reveal content
beyond the current viewport.
GUI exploration and planning. Existing work guides GUI exploration to improve testing efficiency.
Stoat [37] uses heuristic exploration strategies and GUI models to guide test generation. LLM-
Droid [40] uses general-purpose LLMs to direct existing testing tools toward additional functionality
when coverage growth slows. Guardian [31] uses runtime action constraints and replanning to
guide exploration toward UI states relevant to testing objectives. These approaches focus on select-
ing and adjusting exploration actions to improve testing efficiency, rather than explicitly learning
the interaction semantics that determine which UI regions support scrolling.
Recent GUI agents also improve planning through interaction history, reflection, and proactive
exploration [24, 26, 43]. In particular, MobileUse [24] combines hierarchical reflection with self-
planned exploration to build knowledge of unfamiliar environments. These mechanisms address
how agents accumulate and use experience to guide subsequent actions. However, for complex
apps, building such knowledge can require extensive preliminary exploration without guaranteeing
useful guidance for a given task. Hagasu instead provides scrollable-region cues directly from the
current screenshot and is shown to be effective with modest overhead.
8
Conclusion
Motivated by the huge gap between agents’ GUI and CLI task performance, this paper identifies
invisible content as a key bottleneck for GUI tasks. When the correct target is hidden, agents
often click an incorrect visible target instead of exploring. Built on a manually annotated dataset,
Hagasu provides non-intrusive scrollable-region cues that support hidden-area exploration while
preserving GUI agents’ decision-making autonomy. Experiments demonstrate that such scrollable-
region prompts improve swipe selection accuracy by 17.1% and result in a 27.6% increase in the
end-to-end task completion rate. These findings suggest that making exploration opportunities
explicit is a practical direction for improving GUI agent harnesses under partial observability.
