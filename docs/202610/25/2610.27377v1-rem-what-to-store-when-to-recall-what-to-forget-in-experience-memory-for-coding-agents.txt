## Abstract 

Large language model (LLM) agents now autonomously complete long-horizon tasks, such as repository-level coding, through hundreds of think-act steps, yet the experience each run produces is rarely reused on the next. Prior memory systems concentrate on retrieval, finding the most relevant past trajectory. Retrieval cannot observe the running agent, so it cannot decide whether the agent needs an experience, at which point, or for how long. We introduce REM (Reusable Experience Memory), a framework that manages the memory lifecycle from inside the agent’s think-act loop through three explicit decisions. What to store: each completed trajectory is consolidated into a phase-structured document, two orders of magnitude smaller than the trajectory. When to recall: the document is injected at the start of the task; the costlier implementation record is withheld until an in-loop gate detects the agent struggling. What to forget: the record is evicted after a single exposure. On repository-level bug fixing (SWE-ContextBench Lite), REM retrieves the related trajectory more accurately than every state-of-the-art memory system (68.7% vs. 55.6% match@1) and improves, in every replicate, end-task resolution (27.6% vs. 24.9%) at 17% lower cost. Injecting the same experience as a summary or raw trajectory, even when oracle-retrieved, does not. Ablating any of the three decisions reduces resolution. Altogether, these results demonstrate that the bottleneck in experience reuse is not retrieval fidelity but how experience is stored and governed across its lifecycle, opening a control-theoretic perspective on agent memory. 

## 1 Introduction 

LLM agents now run unattended for hours, solving exploratory tasks such as repository-level coding [Jimenez et al., 2024] and text-to-SQL [Yu et al., 2018] through hundreds of think-act steps. Each run produces a detailed trace of exploration, dead ends, and an eventual solution, and a growing ecosystem of memory layers [Chhikara et al., 2025, Zhu et al., 2026] and experience-reuse frameworks [Shinn et al., 2023, Zhao et al., 2024, Wang et al., 2024, 2023] promises to make that experience compound. In practice it rarely does. Most work targets the middle of the lifecycle: retrieving the most relevant past trajectory. This is most consequential where an agent runs repeatedly against an evolving codebase, its accumulated experience a standing asset whose compounding is the long-run aim of continual learning for agents [Hu et al., 2026]. We take one step toward that aim, reusing a fixed pool of past runs within a single new run, and find the state of the receiving agent decisive: naively recalled memories leave resolution unchanged even when an oracle supplies the correct experience, and the same memory that helps mid-capability agents costs the strongest ones (§5.5), while agents reference only about a quarter of the identifiers in a raw trajectory and half of those in a prose summary (§5.3). This work presents the following main contributions. • From which to when . The value of a recalled experience depends on the state of the receiving agent, which makes agent memory a control problem, not a lookup problem. • REM. A framework that governs the full memory lifecycle from inside the agent’s loop—phased consolidation, a two-tier read path, struggle-gated recall, and one-shot eviction—with an automati-cally discovered extraction schema, its only domain-specific artifact (§3). • State-of-the-art retrieval; improved resolution at lower cost. ## 2 Related work 

Agent memory and experience reuse. Self-improvement frameworks store verbal reflections, distilled insights, workflows, or skill libraries and read them back on later tasks [Shinn et al., 2023, Zhao et al., 2024, Wang et al., 2024, 2023], while production memory layers shred histories into factual items or chunks behind a search interface [Chhikara et al., 2025]. How well experience transfers depends on how it is stored, with abstract procedural memories transferring more reliably than detailed trajectories [Hu et al., 2026]. These stored units sit at the extremes of granularity, either isolated facts that lose connective structure or whole trajectories that bury the identifying tokens, and their recall is eager, delivered at the start of the next task. Structured representations of experience have also been proposed, as distilled reasoning strategies [Ouyang et al., 2026], context-aware guidelines selected for the agent’s current state [Fu et al., 2024], and subtask-level memories aligned with software-engineering workflows [Shen et al., 2026]. Deciding when to retrieve and what to keep. Adaptive retrieval learns whether a query needs retrieval at all [Asai et al., 2024], and context-curation policies learn to insert and delete material from an agent’s working context under a budget [Zhang et al., 2026]. Concurrent work casts memory operations as a learned control policy over when to retrieve, inject, and forget [Jiang et al., 2026]. The machinery for deciding whether to retrieve is well developed; what happens to retrieved experience after it enters a long-running loop is not. REM addresses that second half, the handling of experience after injection, with the simplest sufficient mechanism, an in-loop gate that withholds costly detail until the run shows struggle and evicts it after one exposure, and reports what each decision is worth in end-task resolution and cost. 

Context sensitivity and evaluation. Language models are degraded by irrelevant input and use long contexts unevenly by position [Shi et al., 2023, Liu et al., 2024], so injected experience is not free. Agentic-coding benchmarks have moved from patch correctness [Jimenez et al., 2024] toward measuring reuse, and SWE-ContextBench reports that correctly selected summaries help while unfiltered context does not, concluding that agents must interpret what they receive [Zhu et al., 2026]. We take that as the starting point and quantify uptake directly, measuring which injected identifiers a run references and whether that predicts resolution. 

## 3 An experience memory for coding agents 

3.1 Why a store needs a lifecycle policy 

Reusing a trajectory is not mainly about finding it. One repository-level run produces tens of thousands of tokens, most recording abandoned paths. Stored raw, a trajectory fails twice: as a retrieval unit its few identifying tokens are diluted by exploration noise, and as injected context its size displaces the new agent’s own reasoning. Shattering it into factoids removes the noise but also the structure that makes a trajectory a solution. The first decision, what to store , is therefore the choice of a form that keeps the structure of a solution while discarding the search that produced it. 3The other two decisions cannot be made by the store. Whether injected context helps depends on the state of the receiving agent: one that has already localized the defect gains little and can be derailed, whereas one that has exhausted its hypotheses stands to gain. That state is invisible at retrieval time and changes as the run proceeds, so injection must be decided while the agent works, by a component inside the loop, the second decision, when to recall . Once injected, context left in place biases every later turn toward another run’s solution, so the policy must also say when to remove it, the third decision, what to forget .

3.2 Framework overview 

REM wraps the loop with one stage per decision (Figure 1, Algorithm 1 in Appendix A): the write path consolidates finished trajectories into phased documents, the read path retrieves the document most related to a new task, and the in-loop node decides when the implementation record is injected and removed. The pipeline is designed for any domain whose work follows localize , understand , fix ,and verify , such as debugging code, text-to-SQL repair, or incident response; the domain enters only through a swappable module of extraction fields (§3.3). 

Write path. Each stored trajectory is a transcript of 55K–170K tokens. We flatten it to text, keeping user text, assistant text, and tool-call inputs while dropping tool results, which shrinks it roughly fifteenfold with no truncation. One LLM call extracts a schema of typed fields (for coding: files, functions, root cause, fix approach, tests), and a deterministic renderer lays them out as a four-phase document averaging 270 tokens, more than two orders of magnitude smaller than the transcript. In memory terms this is consolidation from an episodic trace into a semantic one: the solution’s structure survives while the exploration noise does not. 

Read path. We embed the pool and the new task’s problem statement with an off-the-shelf text-embedding model, pass the five nearest documents by cosine similarity to one LLM rerank call, and inject the selected document. The reranker never abstains; an unparseable reply falls back to the nearest document by cosine similarity. The stage is deliberately simple: our hypothesis is that structuring what is stored matters more than how it is searched. 

Recall node: two tiers, a struggle gate, eviction. The 270-token document is injected at the start of the run to orient the agent. The implementation record , the raw edits and verifications from the same trajectory capped at 12K characters, is injected only on demand, the first time the agent fails a validation , our simplest observable evidence that its own approach is not working (edits to test files are filtered so self-written tests do not count as struggle). After one exposure the record is evicted and does not persist in the cached prefix; the phased document, by contrast, stays in context for the whole run. §5.4 ablates both halves, comparing eager against gated injection and eviction against persistence. 

3.3 Automated schema discovery and measurement 

The extraction schema is the memory’s only domain-specific artifact, and a meta-loop learns it from a few example trajectories (nine trajectories from the experience pool, none of them an evaluation task): an LLM writes a candidate prompt, an LLM judge scores each extraction from 1 to 5 on coverage, specificity, discriminability, conciseness, and structural consistency, and weak dimensions are revised for up to five iterations. Porting to a new domain therefore needs example trajectories, not prompt engineering, and the discovered schema matches or exceeds the hand-written one (§5.2; Appendix G). 

Measurement. To test whether agents engage with what they receive, an offline probe extracts 

identifiers (file paths and CamelCase or snake_case names of at least four characters, minus a stoplist) from the exact injected text and records which appear in the agent’s own text or tool-call inputs, excluding tool results and discounting identifiers the paired no-memory run already surfaced. We report coverage , the share of injected identifiers a run references; substring matching establishes presence rather than causal use, so we read it as mechanism evidence. Resolution contrasts are paired by task and tested with the two-sided exact McNemar test, pooled over replicates; a per-task Wilcoxon signed-rank test on resolve counts leads to the same conclusions (Appendix E); utilization measures use Cohen’s d and the two-sided Mann-Whitney test. ## 4 Experimental setup 

Benchmark and agent. SWE-ContextBench Lite [Zhu et al., 2026] supplies 99 repository-level bug-fixing tasks, a pool of 300 solved trajectories, and a label marking the trajectory related to each task, which separates retrieval quality from the effect of the retrieved trajectory. A run is resolved 

when the benchmark’s held-out tests pass on its patch. Every condition runs the same agent on all 99 tasks, built on the Strands framework with six tools ( bash , read , write , edit , grep , glob ) in a per-task Docker container, capped at 100 turns and a wall-clock limit. Conversation history is never truncated, so injected-context effects are not confounded with history eviction. Claude Sonnet 4.5 is the agent unless stated; §5.5 varies it across five models. 

Outcome measures. Resolution is intention-to-treat over all 99 tasks, so a run ending without an applicable patch counts as unresolved. Match@1 is the fraction of tasks whose top-ranked trajectory is the labeled one, comparable to the benchmark’s reported top-1 rate [Zhu et al., 2026]. Treating the label as uniquely correct understates retrieval quality, so resolution is primary and match@1 secondary. 

Conditions. A condition is one memory configuration; all share the agent and differ only in what enters context and when. No memory supplies the problem statement alone. Start-of-run conditions inject once: Wrong summary (an unrelated summary), Free summary /Free trajectory (the agent browses and selects), and Oracle summary /Oracle trajectory (the labeled trajectory as summary or raw transcript). Holding the labeled trajectory fixed, Oracle phased document varies its stored form, with the same fields as REM’s document plus cautionary guidance and test commands ( ∼540 tokens). REM injects the retrieved document (hand-written schema; the discovered schema is compared on retrieval in §5.2) and applies the recall policy of §3.2; its ablations inject the record eagerly, on struggle, or never, and evict or pin it. REM, no-memory, and the recall ablations were run three times on Sonnet 4.5 (pooled 297 task-runs, exact McNemar); other conditions were run once and read as directional. Tasks are treated as independent, which is imperfect when several share a repository. ## 5 Results 

5.1 REM resolves more tasks at lower cost Start-of-run summaries and trajectories do not move resolution. The five summary and trajec-tory conditions resolve 22–24 of 99 tasks against 23 for no memory in the same replicate (24.9% over three; Figure 2), including the oracle conditions that receive the labeled trajectory, so relevance alone does not help. The benchmark’s oracle-summary gain (34.3% vs. 26.3%; Zhu et al., 2026) does not reproduce under our agent (23.2% vs. 23.2%). The phased form is the exception: the same oracle trajectory rendered as a phased document resolves 26 in a single run (Figure 2; Table 7), consistent with the stored form, not relevance, driving the gain (§5.2–5.4). Cost still moves: a raw oracle transcript raises cost-weighted tokens per task from 452K to 768K and shortens runs from 70 to 50 turns, with unappliable patches up from 7 to 11, so the agent trades its own exploration for the transcript without resolving more. 

REM improves resolution and cost at once. It resolves 27.6% against 24.9% without memory (+2.7 points, +11% relative), with per-replicate counts of 27, 29, 26 exceeding no-memory’s 23, 26, 25 in every replicate; against the strongest summary or trajectory condition the margin is 3.4 points. Of 297 paired task-runs, 20 resolve under REM that fail without memory and 12 the reverse. At 99 tasks this paired difference is not significant (exact McNemar p = 0 .22 ), so we rest the resolution claim on its consistency across every replicate rather than on a single contrast, and treat the robust wins as the retrieval margin (§5.2), which far exceeds the few-point run-to-run noise, and the cost reduction. Cost falls 17%, from 452K to 374K tokens per task, with six fewer turns, mean wall-clock time down from 11.9 to 8.8 minutes, and unappliable patches down from 7 to 4 (Appendix C). Every retrieved phased-document configuration matches or improves on no memory in both respects, and the document alone already resolves 26.9% at essentially REM’s cost (Figure 2; §5.4). Correct content injected at the start as a summary or trajectory does not raise resolution, whereas the phased document yields both, with or without the recall policy: what converts experience into resolved tasks is the form in which it is stored and the management of its lifecycle, not the relevance of what is retrieved.

5.3 Agents read the phased document more completely than any other stored form 

To explain REM’s advantage we test whether it comes from more complete use of the injected context, holding the labeled trajectory fixed and varying its stored form (Table 2). Uptake separates the forms sharply. The unrelated summary is nearly ignored at 3.4%, confirming the probe tracks use rather than coincidence. The raw trajectory is referenced least (26.7–27.2%), prose summaries reach 45.7–52.5%, and the phased document reaches 64.7% from an oracle and 69.1% under REM. Two comparisons locate the cause: REM’s phased document is smaller than the oracle summary ( ∼270 vs. 390 tokens) yet read 1.5 × as completely (69.1% vs. 45.7%), so organization, not volume , drives uptake; and the oracle trajectory offers 5.5 times as many identifiers as the oracle phased document at about 200 times the tokens yet returns only 2.3 times as many referenced. Coverage also tracks success: among the four start-of-run forms, resolved runs reference more of what they were given than unresolved runs ( d = +0 .20 , p = 0 .03 ), an association carried by how much of the context a run takes up rather than how much it was given; under REM’s recall policies, which all inject the same phased document, coverage does not separate outcomes ( d = −0.06 , p = 0 .34 ) (Appendix F). Uptake is thus what the write path should maximize, and the phased document maximizes it. 

5.4 Gating on struggle and evicting after use each pay off 

Holding the retrieved document fixed, we vary only the policy for the implementation record (Table 3; Figure 2). Gating beats eager injection : eager resolves 25.3% against 27.6% for REM, a 2.3-point gap that never reverses across replicates (the two tie in the third); the policies disagree on 19 of 297 task-runs and gating resolves 13 of them, while injecting the record in 58% of runs rather than all lowers cost from 423K to 374K tokens. 5.5 Memory helps agents in a capability band and costs the strongest ones 

Repeating the comparison across five models spanning 20–53% unaided resolution, with memory and policy fixed, the effect’s sign depends on the recipient (Figure 3). The three models at or below 31.3% never lose resolution from the phased document, gaining 4.0, 4.1, and 1.0 points (Sonnet 4.5: first replicate, like the other single runs; 2.0 points over three), whereas the two above 47% lose under every memory condition, by 2.0–9.1 points, with Opus 4.8 falling from 47.5% to 39.4%. Substituting the oracle document preserves the pattern, so the reversal is a property of the recipient, not a retrieval failure: content that orients a mid-capability agent displaces the reasoning of one that would have localized the defect unaided. Within the band, Haiku 4.5 gains 4.0 points from the document alone but only 1.0 with the record added, suggesting a record of another run’s edits is usable only by an agent able to adapt rather than transcribe it. The sweep is one replicate per model, so the claim rests on the sign pattern; an experience memory is an intervention whose sign depends on the recipient, and whether to attach memory should condition on the agent as much as on the memory. 

## 6 Discussion and limitations 

Coding agents produce far more experience than they reuse, and the field’s response has been to build better stores and retrievers, on the assumption that reuse fails because the right run is hard to find. Our results point elsewhere: once an agent is running, what matters is the form its experience was written in, whether it needs that experience now, and how long it should stay in view. Two insights carry beyond REM. First, the stored form determines how much experience is used: the same run, at the same token cost, is read far more completely when organized by the phases of the work, and what separates a successful run from a failed one is how much of what it received it takes up. Second, more memory is not better memory: the gains from delaying and withdrawing costly context came from avoiding harm, and the same content that helped mid-capability agents cost the strongest ones several points. Because REM treats memory as a set of swappable policy slots rather than a fixed store, its lessons are not tied to our implementation. The stored form is decoupled from the search algorithm, so a phased document can front existing retrievers; the recall and eviction decisions are model-agnostic and apply to any agent with an observable think-act loop; and because the extraction schema is discovered rather than hand-written, the pipeline extends to other diagnostic domains, such as text-to-SQL repair or incident response, from example trajectories rather than new engineering. Cast as a control policy over three decisions, an experience memory becomes something one can measure, price, and improve one decision at a time. These three decisions are exactly the operations a continually learning agent must eventually automate over its own growing experience—what to consolidate, when to surface it, and what to retire—so a mechanism that measures each in isolation is a prerequisite for memory that safely compounds. In practice, REM cuts cost-weighted tokens by 17%, mean wall-clock time from 11.9 to 8.8 minutes per task, and unappliable patches from 7.0 to 4.0 (Table 4). Limitations. REM sets a new state of the art for experience reuse on SWE-ContextBench Lite, improving both retrieval and end-task resolution while lowering cost, and it does so with deliberately simple components, which leaves several promising directions open. REM performs single-pass 

reuse from a fixed pool; letting an agent’s own completed runs re-enter the store, with staleness and contradiction handled, is the natural path toward memory that compounds over time and, ultimately, toward continual learning for agents [Hu et al., 2026]. The struggle signal is a single hand-written observable, so a calibrated trigger drawing on richer signals, such as repeated failed edits or lack of progress, that spends a bounded budget of disturbance on runs that would have succeeded unaided is a clear next step. Eviction removes the record itself, but the agent’s own response to it remains in the history, so a stricter variant could also prune that response. The utilization probe establishes presence by substring match rather than causal use, inviting richer attribution. Most conditions beyond REM and its ablations were run once, so several secondary contrasts are directional and invite further replication. Retrieval numbers for existing systems are those reported by the benchmark under each system’s own configuration, so a re-run through a shared embedder and reranker would further isolate the stored unit. Every task’s labeled trajectory comes from the same repository as the task (99 of 99), and we did not measure how closely its patch resembles the gold fix, nor how stored fixes age as a codebase evolves. And while we evaluate end-to-end on repository-level coding, the automatically discovered schema already ports to text-to-SQL (Appendix G), so validating the full pipeline in a second domain is an immediate opportunity. 

## 7 Conclusion 

We recast experience memory for long-running agents as a control problem rather than a lookup problem: a policy over three decisions—what to store, when to recall, and what to forget—each of which can be measured, priced, and replaced independently, and each of which we show is worth something on its own. REM realizes this view with a single phase-structured store, a struggle-gated recall, and one-shot eviction, and attains state-of-the-art retrieval and improved end-task resolution at lower cost on a public benchmark. 9Acknowledgments and Disclosure of Funding

## B Injection mechanics 

The retrieved phased document is placed in a file that the task prompt instructs the agent to read first; the agent reads it as its first action in every run, and it remains in the history thereafter. The implementation record (raw edits and verifications from the related trajectory) is capped at 12,000 characters. The struggle trigger fires on the run’s first genuinely failed validation, a test or check whose result carries a failure, with edits to test files filtered so the agent’s own test-writing does not count. In the default (evicting) policy the record appears once, in the turn after the trigger, and is absent afterward; the persistent variant pins it for the rest of the run, and the eager variant attaches it at the first source edit.

## G Schema discovery details 

The meta-loop runs four steps per iteration: an LLM writes or revises a structuring prompt (six to ten named fields with types, rules requiring exact names, and a JSON template), the candidate runs over a validation set, an LLM judge scores each extraction from 1 to 5 on coverage, specificity, discriminability, conciseness, and structural consistency, and the loop stops when every dimension reaches a mean of 4.0 or after five iterations. Bootstrap, revision, and judging use Claude Sonnet 4, and trajectories are truncated to 15K characters for the meta-prompt. For repository-level coding the loop converged on its first iteration, with means over eight extractions of 4.12 (coverage), 4.00 (specificity), 4.75 (discriminability), 4.38 (conciseness), and 4.50 (structural consistency); the prompt is ∼1.7K characters and defines eight fields. Discriminability, scored highest, matters most for a store whose documents must be told apart at retrieval time, and the discovered schema has the higher match@1 and better rerank conversion (Appendix D). Table 14 sets the discovered fields against the hand-written ones: three coincide, the discovered schema consolidates the code-structure and test fields, drops files merely read and the catch-all identifier list, and adds three fields describing the problem, spending fewer fields on where the fix landed and more on what the failure looked like. Running the same loop unchanged on text-to-SQL trajectories converged on the first iteration (means of 5.0 for coverage, specificity, discriminability, and structural consistency, 4.8 for conciseness) and produced a ten-field schema covering the database, schemas and tables, columns, SQL errors and data-quality problems, analytical approach, answer, query patterns, and business context.
