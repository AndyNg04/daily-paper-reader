## Abstract 

Contextual security defenses prevent AI agents from tak-ing rogue actions by synthesizing a task-specific policy and enforcing it on the agent’s tool calls. In multi-step tasks, however, which actions are valid often depends on what the agent has already done and learned. We present Sapien, a policy engine for enforcing stateful contextual policies. A Sapien policy specifies permitted tool-call sequences using a regular expression extended with stateful predicates, de-ferred policy generation, and scoped semantic checks. We show that Sapien stays within a few percent of an uncon-strained agent’s utility. Even if the agent is fully hijacked, Sapien’s policies rule out 93–95% of attacks on AgentDojo and 62–85% on Toolathlon (twice as many as tool allowlists on long-horizon tasks). 

## 1 Introduction 

AI agents use large language models (LLMs) to autonomously plan and carry out natural-language tasks by calling exter-nal tools [15, 17, 39]. Unlike traditional programs governed by hard-coded control flow, agents rely on the LLM’s rea-soning to interpret tool outputs and dynamically plan their next steps, allowing them to tackle complex, long-horizon tasks. Increasingly, developers aim for general-purpose agents ,equipping AI models with a broad suite of tools to handle open-ended tasks across domains on behalf of a user—for example, managing online accounts, organizing meetings and notes, or coordinating travel. Yet delegating tool invocation to an LLM makes agents inherently unreliable and prone to rogue actions —tool calls that diverge from the user’s intent. As trajectories span more steps, agents are more likely to encounter untrusted content that hijacks them via prompt injection [19, 64], or to spon-taneously drift from their goal, misinterpret a tool output, or improvise an unintended workaround [25]. In practice, agents have already emptied user inboxes [6], deleted pro-duction databases [37], attacked external infrastructure [42], and executed attacker-controlled commands [27], making this lack of reliability a primary obstacle to deploying agents in production [46, §7]. In classical systems, a common defense against rogue ac-tions interposes a reference monitor that checks each action against a policy [49, 50]. Such policies are typically static : if a program’s purpose is known ahead of time, its appropriate

For a general-purpose agent, however, whether an action is legitimate depends on the user’s task [57]: invoking the send_money tool is appro-priate when the user asks to “refund the person who sent me money last week” , but is a rogue action when the user asks to “summarize my inbox.” A static policy must either permit send_money and leave the inbox summary vulnerable to theft, or forbid it and break legitimate refunds. Because agents’ appropriate actions vary by task, a mean-ingful policy must be tailored to the task at hand. We there-fore adopt the framework of contextual agent security [57]: for each request, a policy generator synthesizes a just-in-time, task-specific policy from the user’s prompt, and a ref-erence monitor enforces it over the agent’s tool calls (§2.2). Although synthesizing a policy from natural language also requires an LLM, the policy generator operates solely on the user’s prompt and tool documentation—isolated from untrusted runtime data and multi-step execution—to most reliably produce a policy that reflects user intent. Ideally, a task’s policy should admit appropriate trajec-tories that accomplish the task and reject all others. How closely a policy can approach this ideal is bounded by the expressiveness of the policy language, and we argue that tightly bounding an agent requires a stateful policy language (§2.3), in which what the agent may do next depends on the actions it has already taken and the data it has observed. This paper presents Sapien , a policy engine for AI agents based on a stateful policy language. Following the contextual agent security framework described above, Sapien synthe-sizes a policy in this language from the user’s task prompt and tool documentation ahead of execution, and interposes on the agent’s tool calls to enforce it (§3). A Sapien pol-icy specifies permitted sequences of tool calls using reg-ular expressions—sequencing, choice, and repetition—and extends them with three mechanisms to incorporate runtime context (§4): 1. Predicates over prior tool-call results : Policies can bind return values of completed tool calls to variables, and constrain arguments against these variables via predicates (e.g., requiring send_money to use a sender and amount from the read transaction history, §4.2). 2. Deferred policy generation : When a prompt dele-gates a sub-task to an external source (e.g., “complete the items on my TODO list” ), Sapien places a hole in the policy and expands that hole only after the agent

Enforcing such a policy over an agent’s trajectory requires tracking the agent’s progress while leaving it free to choose among valid execution paths. Sapien compiles a policy into an augmented nondeterministic finite automaton (§5): each state marks a point of progress through the policy, and tran-sitions check argument predicates, bind tool results to vari-ables, and expand deferred holes. As the agent executes, Sapien tracks the set of active configurations —automaton states paired with variable bindings—and denies any tool call that no active configuration permits. Sapien’s enforce-ment only uses potentially untrusted data retrieved by the agent during execution in ways prescribed by the policy, which is derived to reflect user intent by design (§3.2). We implemented Sapien in Python for Google’s Agent Development Kit and evaluated it on the AgentDojo [13] and Toolathlon [31] benchmarks (§6). Across four models, Sapien stays within a few percent of an unconstrained agent’s task success rate. Even in the worst case of a fully hijacked agent, Sapien’s policies rule out 93–95% of attacks on AgentDojo and 62–85% on Toolathlon (doubling the defense rate of tool allowlists for the latter). This paper makes the following contributions: 1. A stateful policy language targeting autonomous AI agents performing long-horizon tasks (§4); 2. Sapien, an automaton-based engine that synthesizes policies from trusted user prompts and enforces them over tool calls with actionable recovery feedback (§5); and 3. An evaluation of Sapien’s effect on utility and worst-case security, the latter using an analytical methodol-ogy that checks whether a policy admits any attack trajectory by a fully hijacked agent (§6). While prior systems [9, 45, 62] also express dependencies across tool calls, they rely on static policies derived ahead of time (manually or with offline LLM assistance) from fixed domain rules (§8). 1 This suits single-purpose agents, but not general-purpose agents whose appropriate actions may vary with every user request. Beyond the design of Sapien’s language and enforcement engine, our work suggests that today’s LLMs can synthesize expressive, fine-grained policies from natural language, providing strong protection across diverse tasks without humans writing or auditing policies.

## 2 Background and Motivation 

An AI agent pairs a large language model (LLM) with tools :functions that gather information (e.g., read an email) or cause side effects (e.g., execute a bank transfer). Users provide agents with natural-language task prompts (e.g., “execute the bank transfer that I emailed Alice about” ); the agent carries out tasks through an execution loop managed by a runtime control program (the harness ). At each step of the loop, the harness supplies the LLM with its current context—e.g., the task prompt and the history of tool calls and their return values—and the LLM emits the next tool call to invoke or decides the task is complete. This paper focuses on general-purpose AI agents designed to handle a wide range of tasks on a user’s behalf. Examples include commercial personal assistants such as Muse [35] and Gemini Spark [68], as well as open-source solutions like OpenClaw [44] and Hermes [38]. These agents are highly ver-satile , aimed to handle “everyday tasks to personal goals” [35] with simple natural language prompts. 

2.1 Rogue actions 

An AI agent can execute rogue actions —inappropriate tool calls diverging from the user’s intent. These rogue actions can be triggered by adversarial manipulation or arise spon-taneously during benign operation. In adversarial settings, the primary threat vector is prompt injection (PI). An at-tacker who controls content the agent ingests—a web page, an email, a calendar invite—can embed instructions that hi-jack the LLM’s trajectory. State-of-the-art safeguards remain vulnerable [36, 60], leaving PI a persistent source of rogue actions. Rogue actions can also occur without any adver-sary. During long-horizon tasks, an agent may drift from its objective, misinterpret tool outputs, or improvise unin-tended workarounds. For instance, upon encountering “not found” during a search, an overly persistent web-browsing agent scraped a site owner’s contact information and sent unsolicited emails [25]; and a “misaligned” agent performed inappropriate actions to fulfill a benign goal [42, 43]. 

2.2 The need for contextual policies 

Keeping a program’s behaviors within intended bounds is a classic problem in systems: like an AI agent, a traditional pro-gram can be hijacked [1] or have bugs that cause damage [58]. A standard defense interposes a reference monitor that en-forces an explicit policy over the program’s actions [49, 50], such as syscall filters [16, 48, 55] or path confinement [4]. Such static policies are derived from the program’s fixed purpose—traditionally known at development time. Unfortunately, static policies fail to bound general-purpose AI agents due to these agents’ versatility. Because they are meant to handle diverse tasks, the appropriateness of a given tool call depends on the task at hand [57]: send_money is appropriate when “refunding the person who sent me money

2.3 The need for a stateful policy language 

If we think of policy as a predicate over trajectories —the se-quence of tool calls and return values—an ideal policy would admit every appropriate trajectory that an agent could take to fulfill the user’s task—and deny all others. ## 3 System Overview 

Sapien aims to prevent rogue actions by automatically deny-ing tool calls that clearly fall outside the user’s intent. To achieve this, Sapien interposes on the agent’s harness to mediate between the agent and its tools. Sapien operates in two phases: ahead-of-time policy gen-eration and runtime enforcement (Figure 2). Generation runs once per task before the agent begins work: given the task prompt and tool documentation, Sapien invokes a generator LLM that synthesizes a policy scoped to that task. Each pol-icy governs a single task. Enforcement runs on every tool call the agent proposes. The enforcer checks the call against the policy, executing it only if the policy admits the call. Rather than escalating blocked calls to the user—which shifts the burden of enforcement onto the human—Sapien returns the denial to the agent so the agent can correct itself.

3.1 Threat Model and Assumptions 

We assume an adversary who can compromise the agent LLM—whether indirectly via prompt injections in tool out-puts, or directly via memory poisoning or modifying its weights—and thereby force it to propose arbitrary tool calls. By contrast, we assume the policy-generator LLM is properly trained and uncompromised: it faithfully follows Sapien’s in-structions so long as its inputs contain no malicious data. We 

do not assume that the generator can resist prompt injection; this is why Sapien isolates it from untrusted content. We make three further assumptions about the agent’s environment. First, the user’s session is uncompromised, so the task prompt genuinely originates from the user. Second, the tools available to the agent behave as specified by their documentation, which grounds policy generation. Third, the harness and Sapien’s interposition cannot be bypassed and mediate every proposed tool call. 

3.2 The Policy Integrity “Invariant” 

Policy generation is the stage at which user intent enters the system, and Sapien rests on an (informal) policy integrity “in-variant”: the generated policy reflects user intent . The require-ment is what makes enforcement meaningful: an adversary-controlled policy is equivalent to no policy at all. Because LLMs cannot reliably resist prompt injection, Sapien guards this invariant by design: the generator LLM sees only the user’s task prompt and tool documentation. With adversarial inputs excluded, upholding the invariant only requires the policy LLM to accurately translate user intent. Crucially, this isolation applies to policy generation , not policy enforcement . A stateful policy inherently decides whether to admit a tool call based on data the agent has observed dur-ing execution—e.g., verifying that a send_money call matches a prior transaction record—even though that data may con-tain adversarial content. Evaluating such data during en-forcement does not violate our invariant, because the data is merely input to a fixed policy check: even if an adversary can inject data at runtime, they cannot alter the criteria un-der which actions are judged, leaving the rules that allow or deny actions anchored to the user’s intent. 

3.3 Non-Goals Sapien does not vet or second-guess the task prompt. 

Sapien aims to align the agent’s actions and the user’s task prompt; it does not judge whether the prompt itself is benign or accurately states the user’s thoughts. If a user asks for something harmful (e.g., drafting a scam email), blocking that request falls to safety alignment and content moderation, which are orthogonal to Sapien. If a user mis-states their intent—e.g., asking to delete the wrong file—then the deletion falls within the scope of the task prompt, and Sapien has no reason to deny it. Finally, if a user provides a vague or ambiguous prompt Sapien will generate a wide policy that might permit harmful calls. Catching user errors requires a separate mechanism that asks the user to double-check anomalous or high-risk actions even when they are in scope. Furthermore, whether an in-scope action—such as execut-ing a large wire transfer or deleting a repository at the user’s request—warrants human confirmation depends on its irre-versibility and the user’s risk tolerance, factors that cannot be inferred from the task prompt alone. Deployments requir-ing human-in-the-loop approval for high-stakes operations can place a confirmation policy downstream of Sapien. Because Sapien mediates tool calls, it provides safety (pre-venting unauthorized tool calls) but not liveness : a prompt injection that convinces the agent to stop working or refuse the task produces no unauthorized tool call, and Sapien does not intervene. Finally, a compromised agent could still leak information through side channels , e.g., timing channels or the ordering of permitted calls because a policy regulates only which tool calls are permitted, but not when they occur or which path the agent takes among allowed options. 

## 4 The Sapien Policy Language 

A Sapien policy specifies allowable sequences of tool calls that an agent may execute to complete a task. At runtime, a tool call is permitted only if the extended trajectory—the historical tool-call sequence appended with the candidate call—is a valid prefix of a sequence admitted by the policy. To express these temporal and data constraints, Sapien builds on regular expressions—a compact, widely adopted formalism in runtime verification [2, 8, 21] that has also been used to express privacy policies in prior work [5]. Because tool calls are not bare symbols but carry structured argu-ments and return values, we draw on a variant of regular expressions for data words [32], which allows policies to bind, carry, and compare data values across execution steps. Figure 3 gives the grammar of the Sapien policy language, which combines four primitives: 1. Sequential ordering (§4.1): regular operators augmented with “shuffle” [7, 33] to describe interleaving; 2. Variable binding and predicates (§4.2): state-tracking mechanisms to check arguments against runtime data; 3. Deferred holes (§4.3): placeholders that expand into generated sub-policies during execution; and 4. Semantic predicates (§4.4): natural-language guards delegated to a scoped LLM classifier. We next explain these primitives using a running example of an assistant agent.

4.2 Binding and predicates 

While regular operators govern the order of tool calls, call patterns govern tool calls’ arguments. Each argument in a pattern matches against either a fixed literal or a predicate 

(PREDICATE(p) ), where p takes the proposed argument value and returns a boolean. To express data dependencies across steps, a pattern may bind the call’s arguments and return value to a variable using @x ; x can be used as a Python vari-able for subsequent predicates. Unlike formalisms designed for static analysis, which restrict data guards to simple equal-ity checks for decidability [32], Sapien evaluates predicates only at runtime against concrete arguments and variable bindings. Predicates can therefore be written as Python func-tions, allowing the policy LLM to synthesize both the policy expression and predicate logic using its coding ability. Consider a policy for the prompt “Pay my Acme invoice” :            

> list_invoices@invoices .pay_invoice(vendor="Acme", amount=PREDICATE(matches_invoice)) def matches_invoice(amt): return any(inv.vendor == "Acme" and inv.amount == amt for inv in invoices.result)

4.3 Deferred policy generation 

Some tasks reveal what the agent must do only as it exe-cutes. Consider the prompt “Do the tasks on my TODO list at todo.io/bob” . While the agent’s first step should clearly fetch that URL, any following tool calls depend entirely on the content of the page. With the language features introduced so far, Sapien would have no choice but to allow arbitrary tool calls after the fetch—which is the tightest policy that admits all appropriate trajectories, since any tool may be appropriate for whatever tasks the page lists. Sapien addresses this limitation by introducing the defer 

operator, which places a hole in the policy to be expanded at runtime once relevant data is available:        

> get_page(url="todo.io/bob")@todo .defer(gen_todo) def gen_todo(): return f"Do these tasks: {todo.result}"

Syntactically, defer(g) names a generator g: a Python func-tion supplied alongside the policy expression, which takes no arguments and returns a policy-generation instruction string. At runtime, a defer-hole does not match a tool call; encountering defer obliges the agent to call a resolve action naming the generator, at which point Sapien calls g. This reads the bound variables in scope (here, todo.result ), com-poses the sub-task instruction, invokes the policy generator on it (§5.3), and splices the generated sub-policy into the hole (retaining any policy following the hole). The agent then resumes under the expanded policy. 

Deferral and the policy integrity invariant. Deriving a sub-policy from a fetched webpage might seem at odds with isolating policy generation (§3.2), which kept runtime data out of the policy generator. But recall that isolation exists only to uphold the policy integrity invariant: that the enforced policy reflects user intent. When the user asks the agent to carry out tasks listed on a webpage, they delegate 

> 5

the specification of those tasks to the page as if the page had been written directly into the task prompt. If the page contains prompt injection, the sub-policy will be wrong for the same reason a tampered task prompt yields the wrong initial policy. (Indeed, an attacker who can edit the user’s TODO list does not need to prompt inject the model, and can simply write malicious tasks directly!) Using defer thus helps to uphold the invariant: a policy that expands to admit only the tasks on the page reflects user intent more closely than one that permits arbitrary actions after the fetch. 

4.4 Semantic predicates 

Not every constraint can be expressed as a deterministic check over structured data. Consider the task prompt “Sum-marize notes.md and email it to Alice.” Verifying that the outgoing email faithfully summarizes the document requires semantic judgment over unstructured text. For such cases, a predicate may call verify_with_ai , a helper provided by the Sapien runtime that poses a yes/no question to an LLM:             

> read_doc(name="notes.md")@notes .send_email(to="alice@corp.com", body=PREDICATE(is_summary)) def is_summary(body): return verify_with_ai( f"Is '{body}' afaithful summary of "f"'{notes.result}', with nothing extra?")

Such scoped checks differ from using an LLM judge to vet agent behavior wholesale [9, 10, 14, 23, 26, 30, 40, 52] in two key ways. First, a check is narrow and local; here, it compares two specific strings rather than asking an open-ended question about whether an action is intended or safe. Second, the judge only receives inputs needed to answer that question (here, the source document and the proposed email), rather than the agent’s full execution trace, reducing exposure to prompt injection. The judge may still fall for prompt injection because it may inspect untrusted text. However, a semantic predicate can only narrow the actions permitted by a policy: even if a judge is tricked into returning True , the surrounding determinis-tic policy (reading notes.md and sending a single email to 

> alice@corp.com

) remains strictly enforced. Semantic predi-cates thus enable enforcing additional semantic properties that cannot be checked in Python code alone.

The spliced sub-policy joins the two subtasks with shuffle (||), allowing the agent to interleave their individual steps while preserving each subtask’s internal read-before-write ordering. The policy admits at most two mutating calls,

and send_email , with recipients fixed by literals and payloads constrained by data-dependent and semantic predicates on bound variables. 

## 5 The Sapien Policy Engine 

This section describes Sapien’s runtime engine: how it inte-grates with an agent harness (§5.1), how it compiles a policy into an automaton and enforces it across tool calls (§5.2), and how our prototype is implemented (§5.3). 

5.1 Integrating with an Agent Harness 

Sapien is agnostic to both the agent framework and the underlying LLM. At the core of Sapien is a stateful enforcer interface with three methods: 

• init(u) : generates and installs a policy from task prompt 𝑢 .

• can_advance(a, p) → ( 𝑜𝑘, 𝑟𝑒𝑎𝑠𝑜𝑛 ): checks whether a proposed call to tool 𝑎 with arguments p is permitted given the execution trace so far, without modifying enforcer state; if not, provides feedback. 

• advance(r) : records the completion of the allowed tool call with return value 𝑟 , advancing the enforcer state. Integrating Sapien into an agent harness requires calling  

> init(u)

when a user request arrives, calling can_advance( a, p) before executing each proposed tool call, and calling  

> advance(r)

once an allowed call returns 𝑟 . Beyond these three hooks, Sapien requires only that the harness regis-ter Sapien’s defer-resolution tool (§4.3) and allow Sapien to append instructions to the agent’s context. 

Exposing the policy to the agent. After generating a policy—both in init and when expanding defer —Sapien appends the policy expression, the predicate definitions, and the generator’s rationale to the agent’s context. Seeing the active policy helps the agent plan tool calls that satisfy the constraints and informs it when it must resolve a defer hole. 

> 6

Denial feedback. When can_advance rejects a tool call, it returns a diagnostic message identifying which argument failed which predicate along with that predicate’s source code. This feedback may help the agent recover in two situa-tions: when a generated policy is imperfect and blocks some legitimate trajectories for the task while permitting others, or when the agent is misled by a prompt injection and the denial prompts it to resume the user’s original task. 

5.2 Enforcing a Policy 

This section gives a high-level overview of how the enforcer compiles a policy into a nondeterministic finite automaton (NFA) and steps it as the run proceeds. Sapien uses a standard syntax-directed translation over the policy AST following Thompson’s construction [56], mapping each sub-expression to an NFA with a single entry state and a single exit state. A base call pattern compiles to two states connected by a single transition carrying the tool name, parameter constraints, and optional variable binding. Composite operators combine the sub-automata of their operands: concatenation ( ·), choice (+), and iteration ( *, +) connect entry and exit states with 

𝜀 -transitions, while shuffle (||) takes the Cartesian product of its two operands’ state sets [7, 33]. 

Tracking configurations. Unlike a classical NFA, where two paths at the same state admit the same future actions, transitions in Sapien bind completed call records to vari-ables that later predicates may depend on. Thus, two paths reaching the same state with different variable bindings can permit different future calls. To handle this, the enforcer tracks active configurations (𝑞, 𝜌 ), each pairing an automa-ton state 𝑞 with a valuation 𝜌 of the variables bound along that path. On can_advance(a, p) , the enforcer checks if any active configuration can (after 𝜀 -transitions) take a transi-tion for tool 𝑎 whose parameter constraints hold under 𝜌 .If no configuration matches, the call is denied. Otherwise, once the call returns 𝑟 , advance(r) steps every matching configuration to its target state, extends its valuation 𝜌 if the transition binds a variable, and discards non-matching configurations. Resolving a defer. A defer(g) hole compiles to a single transition for the defer-resolution tool (§4.3). When the agent takes this transition, each matching configuration evaluates  

> g()

5.3 Prototype Implementation 

We implemented a prototype of Sapien as a Python library and integrated it with Google’s Agent Development Kit (ADK), as well as the AgentDojo [13] and Toolathlon [31] benchmark eval harnesses (§6). All model calls are via the Gemini Enterprise Agent Platform [18]. 

Generating policies. The policy generator invokes an off-the-shelf LLM with a fixed system prompt that defines the policy language, gives worked examples, and instructs it to prefer deterministic predicates, reserving verify_with_ai 

for properties that code cannot check. For each task, Sapien 

> 7

supplies the user’s prompt and tool schemas, including re-turn types so predicates can access output fields. Generation takes two LLM calls: the model drafts a rationale and candi-date policy, and then a self-correction call critiques the draft against a checklist (e.g., valid syntax, necessary read-only tools are permitted) and emits the final policy and Python block. Generating a deferred sub-policy works the same way, with the generator’s instruction string replacing the user’s prompt and the parent policy as added context. 

Evaluating predicates and generators. Predicates and  

> defer

generators are Python functions that reference bound policy variables (e.g., inv , bob ) as free variables, yet each configuration (𝑞, 𝜌 ) has its own valuation 𝜌 . To support this without recompiling functions per configuration, the en-forcer exec s the policy’s Python block once in a custom globals dictionary, where Python resolves free variables at call time. To evaluate a function under (𝑞, 𝜌 ), the enforcer fills this dictionary with the call records in 𝜌 , calls the func-tion, and then clears the bindings. 

Expanding holes. Instead of the general per-configuration hole expansion from §5.2, our prototype uses a simplified AST-level substitution that suffices for all tasks in our evalu-ation: it substitutes the generated sub-policy into the policy AST, recompiles the automaton, and replays the recorded call trace to reconstruct the active configurations. This sim-plification requires (and enforces at runtime) that each hole is resolved at most once and that its generator produces the same instruction string across all configurations at the hole. 

## 6 Evaluation 

Our evaluation measures the advantages of Sapien’s ap-proach to balance utility-security tradeoffs and its practi-cality: 1. Utility : Does Sapien impact the agent’s task success rate? 2. Security : Can attackers achieve their goals (caused e.g., by prompt injections) in the presence of Sapien policies? 3. Efficiency : What latency and overheads does Sapien add to agent execution, and why? 

Baselines. We compare three agents that differ in what governs their tool calls: no policy (“NoPolicy”), a Sapien policy, and a per-task allow-list of tool names generated from the task prompt in the style of Conseca [57] (“AllowList”). AllowList stands in for coarse-grained, stateless contextual policies: it allows or denies each tool for the whole task, regardless of arguments or execution state, and is generated in a single LLM call (without Sapien’s self-correction pass, §5.3). 

Benchmarks. We evaluate Sapien on AgentDojo [13] and Toolathlon [31]. AgentDojo comprises 97 short tasks (most within five turns) set in synthetic environments across four suites—workspace, Slack, travel, and banking—each exposing a small set of 11–28 tools. Toolathlon features 108 longer-horizon tasks (dozens of turns) situated in a realistic en-vironment with a local file/shell workspace and 32 soft-ware applications—including GitHub, Notion, and Google Workspace—that together expose over 600 tools via MCP. To prevent Toolathlon from granting agents blanket, un-limited capabilities via a handful of “almighty tools” like 

> local_python_execute

, all agents upfront deny access to  

> local_python_execute

(impacting a handful of tasks that would otherwise use it for arbitrary computation), and we require Sapien to specify command predicates (e.g., the com-mand must be grep ) for terminal_run_command .

Models. We evaluate Sapien using four models: Gemini 3.8 Flash, Gemini 3.1 Pro, Claude Sonnet 5, and Claude Opus 5. Each run uses the same model for agent execution and policy generation (Sapien or AllowList). On AgentDojo, we run all 97 tasks (949 attack instances) on all four models. For Toolathlon, we run all 108 tasks (212 attack instances) with Gemini 3.8 Flash and, due to cost, a random subset of 20 tasks (40 attack instances) with the other three models. 

Utility. Utility is the fraction of tasks the agent completes in a benign environment, measured using each benchmark’s native completion criteria. AgentDojo compares the final environment state or tool-call trajectory against a per-task specification. Toolathlon runs a per-task verification script comparing the agent’s workspace against a ground-truth workspace and querying modified external services. 

Analytical security. In standard agent security evalua-tions, one plants prompt injections in tool outputs and mea-sures how often the agent executes them, conflating policy enforcement with the model’s built-in injection resistance. However, Sapien is designed as a second line of defense even when the model itself is compromised. We therefore evalu-ate security analytically : assuming an attacker has already hijacked the agent, does the policy admit any sequence of tool calls that achieves the attacker’s goal? Concretely, each attack instance pairs a user task and en-vironment with an attacker goal and programmatic attack-success check. For AgentDojo, we pair every user task in a suite with every “injection task” in that suite, yielding 949 attack instances. 4 For Toolathlon, which defines no attacker goals, we craft 1–2 plausible goals per user task that target the task’s own tools and data, yielding 212 attack instances. 5

We then evaluate each attack instance under conserva-tive assumptions, in which only two kinds of LLM calls be-have faithfully: ( i) initial policy generation, and ( ii ) defer 

resolutions on inputs untainted by attacker-controlled data.

6.1 Utility 

Any policy enforcement risks reducing utility: the policy generator may not anticipate every valid way to solve a task, so it may produce an overly tight policy. On AgentDojo (Figure 5), this cost is small: across all mod-els, Sapien completes 1–5 fewer of the 97 tasks than NoPolicy, and AllowList completes 0–2 fewer. On Toolathlon (Figure 6), Sapien comes within 4% of NoPolicy’s task success rate on the full Toolathlon suite (with Gemini 3.8 Flash); on the 20-task subset across all four models, Sapien succeeds on 43 of the 80 task runs, while NoPolicy succeeds on 45. Sapien fails at most 2 additional tasks on the Toolathlon 20-task benchmark regardless of model. Sapien achieves par-ity with Gemini 3.1 Pro; exceeds NoPolicy task success on Claude Sonnet, and fails an additional 1 and 2 tasks with Gem-ini 3.8 Flash and Claude Opus 5 respectively. AllowList per-forms worse than Sapien and NoPolicy regardless of model (with parity on Opus 5). Sapien’s improved utility with Son-net occurs on a task in which NoPolicy reaches the maximum number of turns; Sapien’s policy helps the agent remain on the correct trajectory to solve the task (also see §6.3). 

When Sapien policies hurt utility. Sapien policies of-ten prevent task completion because the policy generator does not see the runtime environment, and makes incor-rect assumptions about the data or workflow. For exam-ple, its Python predicates may expect the wrong data for-mat or value (e.g., matching "London Luxury Hotel" from the prompt when the database stores "London Luxury" ). Its  

> verify_with_ai

checks may read the prompt too literally (e.g., rejecting an update to a rent “standing order” that the environment stores as a one-time payment). Finally, it may restrict the workflow too tightly by omitting a needed read tool. 

Why Sapien can have higher utility than AllowList. 

One might expect a coarse policy language like AllowList to yield more permissive contextual policies (§2.3)—and thus higher utility—than Sapien’s fine-grained constraints. But Sapien has higher utility than AllowList on Toolathlon and on two of the four runs in AgentDojo, for two main reasons. First, the AllowList generator must decide “all-or-nothing” upfront tool permissions: allowing a sensitive tool (e.g., send_ email ) permits it with arbitrary arguments for the entire task, so the generator often withholds the tool when the prompt does not explicitly require it. Sapien avoids this dilemma: ar-gument predicates (e.g., bounding file writes to /workspace /result.md ) and defer holes let the generator permit sensi-tive tools while tightly bounding their use. 6

Second, unlike a flat allow-list, Sapien’s staged policy structure gives the agent implicit guidance on the expected sequence of steps (consistent with Sapien’s lower average inferences per task on Toolathlon in §6.3). 

6.2 Security 

Under our analytical model, a hijacked agent can issue any sequence of tool calls admitted by the policy, so NoPolicy blocks 0% of attacks. 6.4 Takeaways 

Sapien achieves utility parity with baselines across both benchmarks and all four models, staying within a few tasks of an unconstrained agent. On long-horizon tasks, Sapien beats a tool allow-list because argument predicates and defer 

holes let it permit sensitive tools under tight bounds rather than deny them. The same constraints deliver strong security against a hijacked agent. Under our conservative analytical evaluation, Sapien blocks over 90% of attacks on AgentDojo. On Toolathlon, where attacks abuse tools the task itself needs, it blocks roughly twice as many as an allow-list. Most remain-ing attacks exploit the semantics of data the agent ingests or produces, which deterministic predicates cannot judge. The price we pay is latency, almost all from policy gener-ation: on short tasks, it can dominate runtime, but on longer tasks, it is amortized over many steps and partly offset as Sapien’s staged policies guide the agent to fewer planning inferences. §7 discusses future directions to lower this over-head.

## 7 Discussion 

Sapien policies face several limitations. First, when an under-specified user prompt admits multiple valid actions, Sapien does not add precision and permits all of them. For example, a request may be broad (e.g., “handle my inbox” ) or one where multiple targets match the user’s description (e.g., an inbox contains two different Bob emails and the user asks to “reply to Bob” ). This allows unexpected outcomes and adversarial steering (e.g., replying to attacker-controlled “Bob” instead of the correct Bob). As promising future work, Sapien could detect such under-specification [72] and prompt the user for disambiguation before generating a policy. The generator can also get the policy wrong . Because enforcement holds relative to the generated policy, Sapien ultimately relies on the policy-generator LLM, which can err in either direction. A policy that is too broad sacrifices secu-rity; a policy that is too tight reduces utility. While the agent can often adjust after a denial, tasks can fail when an unex-pected obstacle (e.g., a broken tool) requires a workaround the policy LLM did not foresee. Nevertheless, our results and others’ [12, 51] demonstrate that LLMs already can generate relatively accurate policies, and Sapien will transparently benefit from underlying model advances, whether through general capability gains or targeted fine-tuning. Furthermore, unlike deterministic checks, LLMs evalu-ating semantic predicates may be deceived by prompt injection . However, the impact of fooling a judge is bounded: an attacker can satisfy only that specific semantic predicate, while the surrounding structural constraints—which tools may be called, in what order, and with what arguments— remain deterministically enforced. AI judges thus only fur-ther restrict actions where deterministic checks fall short. Finally, policy tightness depends on tool granularity .For a focused tool like send_money(recipient, amount) ,the effect of a call is explicit in its arguments and easy to constrain. By contrast, for a general-purpose execution tool like run_python(source) , verifying whether the arbitrary source string matches user intent requires program anal-ysis beyond the reach of argument predicates. Like other reference monitors, Sapien is most effective when agents are given narrow, well-scoped tools. The tested benchmarks have no (AgentDojo) or few (Toolathlon) coarse-grained tools, which we constrain appropriately in Sapien (§6.1); a future direction can look into deriving granular tools from coarse ones. 

Improving latency and scalability. To reduce Sapien’s latency overheads, which are mostly caused by generating policies and evaluating semantic predicates, Sapien could bet-ter utilize caching : prefix KV-caching of (static) tool schemas would eliminate redundant prefill cost, and Sapien could reuse cached parameterized policy templates for similar tasks. Sapien could also leverage model routing based on com-plexity: routing simple tasks and semantic checks to light-weight classifiers rather than frontier models can reduce these inferences’ latencies from seconds to tens of millisec-onds. For large tool sets, retrieving only the top-k task-relevant tools via a lightweight semantic search prior to synthesis will reduce both context length and reasoning complexity. Sapien policies also define exact set of transitions permitted at the current configuration; thus, the harness could prune the agent input tool schemas to only currently allowed tools. Finally, Sapien could parallelize policy generation and agent execution . Agents could begin executing actions for a task as soon as Sapien generates the initial phase of the policy, so long as policy generation remains at least one stage ahead. 

## 8 Related Work 

Policy-based defenses. Prior works [12, 20, 29, 34, 41, 45, 47, 51, 54, 57, 59, 62] also defend against agents compromised by prompt injection, model poisoning, or malicious system prompts. Like Sapien, they do so by checking agent actions against a (static or contextual) policy. Sapien contributes a stateful policy language whose fine-grained constraints can incorporate context discovered at runtime. Works like Conseca [57], CaMeL [12], and others [9, 29, 69] use LLMs for policy generation and follow the dual-LLM pat-tern [67] to ensure the security monitor is itself not compro-mised by untrusted inputs; Sapien similarly isolates the pol-icy generation (§3.2). CaMeL [12] policies are fixed control-flow graphs, supporting only single-turn tasks where the policy itself must execute the task, whereas Sapien policies permit many trajectories. CaMeL’s IFC-based data disclosure policies are orthogonal and could complement Sapien. Progent’s [51] policies—predicated allow/deny rules with fallback clauses and predefined modifications when certain conditions match—are either static per agent, or generated from user instructions and regenerated after a tool call if an LLM deems it necessary. Sapien only ever makes policy decisions off of trusted relevant context, and does not require an LLM call to check for updates at every tool call. FORGE [45] supports manual, static Datalog policies con-straining causal relationships across agent executions (pred-icates on a DAG of actions). Sapien policies are dynamic and can constrain action sequences of concurrent agents via shuffle; Sapien can be extended with causal predicates. IsolateGPT [70] proposes an architecture to prevent cross-LLM-application compromises by allowing only structured, user-approved communication across app boundaries. Sapien is orthogonal and can help generate and enforce constraints both across and within applications. 

Defenses against compromised inputs. IFC-based sys-tems [11, 28, 53, 73] prevent untrusted inputs from influ-encing agent behavior but assume agents otherwise behave 

> 12

correctly and auto-approve any untainted action; they do not defend against agents spontaneously taking malicious or erroneous actions. These systems also require manually specified trust labels for data sources; Sapien does not rely on such labels, though they could help inform its predicates. 

Model-based security techniques. Probabilistic defenses aim to use AI models to detect attacks [3, 23, 24, 65], or to distinguish untrusted from trusted inputs [22, 61, 66, 71]. Others rely on an LLM to identify threats [9, 10, 14, 23, 26, 30, 40, 52]. However, these remain susceptible to attacks introduced by untrusted context [36, 60]. By contrast, Sapien isolates policy generation from sources of prompt injection. 

## 9 Conclusion 

General-purpose agents need task-specific policies that track what the agent has done and learned. Sapien provides a state-ful policy language and an engine that enforces such policies over tool calls. Our evaluation shows that Sapien preserves utility while tightly constraining even a fully hijacked agent, making stateful contextual policies a promising path toward safely deploying autonomous agents.
