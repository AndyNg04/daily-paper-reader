## 摘要
智能体式 AI 系统结合了模型决策、可变状态、工具调用以及向外部智能体的委派。对这类系统进行监控，需要从不同的执行边界获取观测；而要实现预防，则必须在某项操作产生效果之前进行控制。我们提出 AgenticRV，一种运行时验证架构，将这些边界与监控形式主义分离。适配器生成规范化事件；每个监控器接收各自的投影与抽象；决策策略则利用规范化的判定结果，选择相应适配器所支持的响应。我们形式化了观测何时足以支持验证、替换监控器如何保持决策不变，以及阻止操作如何避免不安全效果。我们还区分了被拒绝的尝试与已完成的效果，从而避免假设被阻止的请求必然使所有监控器永久处于违规状态。Python 实现支持 LangGraph、MCP 和 A2A。我们开展了一项受控的 LangGraph 实验，结合外部 Reelay 时序监控器与程序化报告监控器；消融实验表明，对所选要求而言，两者缺一不可。差分检查与跨适配器测试进一步提供了集成方面的证据。一个由 LLM 驱动的事件响应示例展示了相同的执行路径，而已有的微基准测试则分离考察了框架开销。结果表明，在明确控制边界下可以复用监控方法，但需满足文中所述的观测与部署假设。

## Abstract
Agentic AI systems combine model decisions, mutable state, tool calls, and delegation to external agents. Monitoring them requires observations from different execution boundaries, while prevention requires control before an operation produces its effect. We present AgenticRV, a runtime-verification architecture that separates these boundaries from the monitoring formalism. Adapters emit canonical events; each monitor receives its own projection and abstraction; and a decision policy uses normalised verdicts to select a reaction supported by the responsible adapter. We formalise when observations suffice, monitor replacement preserves decisions, and blocking prevents unsafe effects. We also distinguish rejected attempts from completed effects, avoiding the assumption that a blocked request must leave every monitor in a permanent violation state. The Python implementation supports LangGraph, MCP, and A2A. A controlled LangGraph experiment combines an external Reelay temporal monitor with a programmatic report monitor; ablations show why both are needed for the selected requirements. Differential checks and cross-adapter tests provide further integration evidence. An LLM-driven incident-response example illustrates the same enforcement path, while existing microbenchmarks isolate framework costs. The results support reuse of monitoring methods at explicit control boundaries, subject to the stated observation and deployment assumptions.

## 1. 核心问题与整体含义

### 研究背景与动机
智能体式 AI 的行为不局限于模型生成的文本，还包括状态更新、工具调用、工作流分支和向外部智能体委派任务。风险因此分布在多个执行边界：

- **观测需求不同**：时序规则需要审批、检查点等历史；内容规则可能需要报告原文和目标地址。
- **可观测不等于可控制**：收到工具完成事件，通常已经无法阻止其副作用；看到远程任务状态，也不意味着能够控制远程智能体。
- **不同监控方法难以直接组合**：监控器可能采用不同输入、内部状态、形式语言和判定词汇。

论文要解决的核心问题是：**如何让不同监控方法复用同一套智能体执行基础设施，同时明确它们看到了什么、如何形成联合决策，以及在哪些边界上真正能够阻止危险操作。**

### 整体定位
作者提出 **AgenticRV**，将“执行边界的适配与控制”和“具体监控形式”解耦。

其贡献主要是**运行时接口、集成架构及其条件性保证**，而不是：

- 新的时序逻辑或监控算法；
- 对模型内部推理正确性的验证；
- 对任意智能体行为的全面安全保证。

## 2. 方法论：架构、技术细节与形式化条件

### 2.1 核心架构

系统按照以下流程运行：

1. **源适配器获取事件**
   - 支持 LangGraph、MCP、A2A。
   - 将框架或协议活动转换为规范事件，包括事件标识、来源、类型、时间戳和数据。
   - 统一的是事件外层结构，并不要求所有来源具有相同载荷。

2. **每个监控器独立获取自己的观测**
   - **订阅**：选择关注哪些事件。
   - **投影**：选择、删除或脱敏字段。
   - **抽象**：把字段转换为监控器所需的输入，例如布尔命题或结构化数据。
   - 不相关事件可被丢弃。

3. **监控器更新状态并返回原生判定**
   - 可接入时序监控器、Python 程序或 HTTP 监控服务。
   - 不要求它们使用同一种输入域、状态模型或判定词汇。

4. **归一化判定并仲裁**
   - 将原生结果映射为 `permit`、`reject`、`inconclusive`、`error` 等公共结果。
   - 结合强制参与、优先级、超时状态和授权反应，执行拒绝优先、全体一致或优先级策略。

5. **适配器实施干预**
   - 例如允许调用，或在转发前阻断工具请求。
   - 干预及其结果也会进入审计事件流。

### 2.2 明确区分“观察”与“拦截”

论文将事件分为两类：

- **观察事件**：只报告活动，不保留待执行操作。
- **决策事件**：适配器暂扣操作，等待同步监控和仲裁后再释放。

关键点是：**事件标记为“执行前”并不自动意味着可以阻断**。适配器必须实际安装在可拦截边界，并处于拦截模式。

实现中，可控边界包括代理图调用、显式状态更新、受保护原生工具，以及拦截模式下的 MCP/A2A 请求；节点输出、许多内部状态传播和远程返回事件主要仍是被动观测。

### 2.3 三个核心形式化条件

#### （1）观测充分性

每个监控器实际看到的内容为：

\[
obs_m=\alpha_m\circ\pi_m
\]

其中，\(\pi_m\) 表示投影，\(\alpha_m\) 表示抽象。

论文要求：对于部署允许的两个执行前缀，如果监控器看到的观测完全相同，那么目标属性的语义答案也必须相同：

\[
obs_m(\tau)=obs_m(\tau')
\Rightarrow b(\tau)=b(\tau')
\]

其含义是：

- 如果删掉事件后，安全与不安全历史变得不可区分，就不可能仅凭该视图实现精确判断。
- 删除任务标识可能使任务 A 的批准被错误用于任务 B。
- 删除事件也可能改变“最近六步”之类时序规则的含义，因此过滤不仅是性能优化。

这是一个**信息是否足够的条件**，不是自动生成正确监控器的方法。

#### （2）监控器替换保持决策

策略只应依赖：

- 公共判定；
- 超时、错误等响应状态；
- 优先级、强制参与和授权信息；
- 显式替换提议等控制数据。

因此，在事件、适配器能力和策略不变时，如果替换监控器后这些控制信息完全相同，最终反应也相同。

这并不意味着不同监控器天然等价；即便成功判定一致，超时行为不同，也可能改变决策。

#### （3）有条件的不安全效果预防

对于一个前缀封闭的安全语言，如果：

1. 所有效果都经过已安装的决策边界；
2. 检查与效果执行被串行化，检查的是实际已完成历史；
3. 所有不安全候选都被强制同步监控器拒绝；
4. 拒绝或失败确实阻止释放，且适配器忠实执行阻断；

那么可以保证所有已完成效果前缀都满足安全要求。

**该保证不覆盖绕过包装器的调用、失效的干预、未经论证的并发执行或不可控的远程内部操作。**

### 2.4 区分“被拒尝试”和“已完成效果”

- 不安全请求即使被阻止，也仍是审计历史中的一次违规尝试。
- 但它没有产生对应的外部效果。
- 审计监控器可以永久记录违规；可恢复的安全门则可以拒绝当前请求，同时允许后续合法请求。

论文反对用“每次拒绝后重置监控器”作为通用修复，因为这可能丢失仍然必要的批准、撤销或时序历史。

## 3. 实验设计、场景与对比方法

### 3.1 Benchmark 的性质

论文**没有使用大型公开智能体安全数据集，也没有开展标准化端到端安全排行榜评测**。

其 benchmark 主要是：

- 人工构造的事件响应工作流；
- 可确定复现的动作序列与效果账本；
- 有限轨迹差分检查；
- 框架与协议集成测试；
- 分离测量框架成本的微基准。

主要任务是验证**接口能否正确组合和执行监控决策**，而非统计真实智能体的安全率。

### 3.2 双监控器消融实验

在真实编译的 LangGraph 上，使用确定性动作驱动器，不使用 LLM 选动作：

- **Reelay 时序监控器**
  - 修复前需要最近六个监控步内的批准、最近三个监控步内的检查点。
  - 根据可信布尔分类检查报告是否含秘密。
  - “步”是抽象后的事件步，不是物理时间。

- **程序化报告监控器**
  - 检查 HTTPS 主机名白名单。
  - 检查报告原文是否包含字面量 `INTERNAL_API_KEY=`。
  - 该规则只是受控内容检测示例，不是通用秘密检测器。

构造七条路径，覆盖安全流程、缺少批准、批准过期、非法目的地、秘密报告、错误布尔分类及拒绝后恢复。每种配置共 **34 次工具决策：6 次不安全、28 次安全**。

| 配置 | 不安全请求实际执行 | 安全请求被阻断 |
|---|---:|---:|
| 无监控器 | 6/6 | 0/28 |
| 仅 Reelay | 2/6 | 0/28 |
| 仅报告监控器 | 2/6 | 0/28 |
| 两者联合 | 0/6 | 0/28 |

两种单独监控器遗漏的是不同风险，联合后覆盖所选需求。

### 3.3 LangGraph–MCP 跨边界实验

- 本地 LangGraph 完成批准，MCP 工具发送报告。
- 要求报告获得**同一事件/任务范围**的批准。
- 七条路径，每种配置含八次报告请求：六次不安全、两次安全。
- 三种配置共 **21 次路径执行、24 次报告决策**。

| 时序观测配置 | 不安全请求执行 | 安全请求被阻断 |
|---|---:|---:|
| LangGraph + MCP，按事件范围分状态 | 0/6 | 0/2 |
| 相同事件但删除范围信息 | 1/6 | 0/2 |
| 仅 MCP 事件，按范围分状态 | 0/6 | 2/2 |

这直接展示了两种信息损失：**删掉范围可能误放行，丢掉批准证据可能误阻断。**

### 3.4 差分检查、集成测试与 LLM 示例

- **时序差分检查**
  - 六符号字母表，枚举长度不超过四的全部 **1,554 条非空轨迹**。
  - 与独立 Python 求值器进行 **5,910 次逐步比较**，无不一致。
  - 另有 **35 个时序边界案例**，覆盖批准与检查点的精确有效范围。

- **运行时与适配器测试**
  - 选定测试集 **179 项全部通过**。
  - 覆盖投影、策略、有序交付、超时、迟到响应、回放及协议适配等。
  - MCP 使用真实进程内客户端/服务器；A2A 使用真实 SDK 和受控传输，并非生产远程智能体。

- **LLM 驱动示例**
  - 使用 `llama3.2:3b`，构造安全、缺少批准、批准过期、秘密报告四个场景。
  - 每个场景一次运行，均出现预期放行或阻断。
  - 这些是执行见证，不是具有统计意义的模型安全评测。

### 3.5 性能对比

五类独立微基准比较：

1. 原生 LangGraph 与代理、代理加监控器；
2. 0、1、2、4、8 个即时监控器；
3. 不同字段投影与哈希处理；
4. 关闭审计、缓冲记录、逐条刷新；
5. 允许与阻断。

未与 AgentSpec、NeMo Guardrails 等外部安全框架做直接性能或安全效果对比。

## 6. 主要结论与发现

- **异构监控方法可以共享执行基础设施**，不必将监控语义写入工作流适配器。
- **所选需求需要互补观测**：时序历史不能代替报告原文检查，内容检查也不能代替批准与检查点历史。
- **投影和订阅属于安全配置**：它们会影响信息充分性、任务关联及逻辑时钟。
- **拒绝不必导致永久停机**：区分审计尝试和已完成效果后，可以保留违规记录并允许后续合法恢复。
- **预防保证是条件性的**：同步检查、完整覆盖、正确范围、可靠阻断和检查—释放原子性缺一不可。

主要性能结果：

- 单节点图从原生约 **0.223 ms** 增至代理约 **0.919 ms**；加入一个即时监控器后约 **1.333 ms**。
- 受保护工具从零到八个即时监控器，增加约 **0.869 ms**。
- JSONL 审计增加约 **76–86 μs**。
- 阻断路径更快，是因为省略了工具执行及完成事件，不代表阻断机制本身具有性能优势。

这些是框架固定成本，**不包含 Reelay 等实质监控算法成本，也不能直接外推到网络或模型主导的工作负载**。

## 7. 优点

- **抽象边界清晰**：将观测、判定、仲裁和干预分离，避免“看到了就能控制”的错误假设。
- **形式化条件实用**：把信息丢失、超时、授权及并发等工程问题纳入保证前提。
- **恢复语义处理细致**：区分违规尝试与实际效果，避免简单重置或永久拒绝。
- **实验与论点对应紧密**：消融验证互补性，跨协议实验验证范围关联，边界检查验证时序解释。
- **证据呈现较克制**：明确区分已实现功能、可执行测试、实际测量和未来工作。
- **具有一定复现基础**：提供代码、提交标识、依赖快照、测试脚本及逐请求结果。

## 8. 不足与局限

### 适用范围与信任假设
- 只能控制已安装并正确使用的包装边界；未包装客户端、远程内部行为和部分状态合并不受保护。
- 批准真实性、任务范围绑定、内容分类和监控器正确性仍依赖应用开发者。
- 同进程 Python 监控代码没有被安全隔离；字段投影不构成对恶意监控器的沙箱。

### 人工配置成本
- 自然语言需求不能自动转化为可靠部署。
- 仍需手工设计可信命题、字段投影、抽象函数、判定映射、失败策略和恢复机制。
- 论文列出部分代码规模，但没有量化开发时间、学习成本或配置错误率。

### 并发与分布式限制
- 形式模型采用中央事件层和交付顺序，不提供全局因果重建或时钟同步。
- 主要案例采用每工作流独立状态与串行效果请求。
- 有序日志不能自动保证并发安全，仍需原子检查—释放或属性专门证明。

### 实验与泛化限制
- 仅实证组合一个外部时序监控器和一个程序化监控器，不能据此证明与任意形式体系兼容。
- 内容检测和动作空间较简单，缺少复杂提示注入、秘密混淆、动态委派及长程任务。
- 逻辑步数的新鲜度不等价于真实时间新鲜度。
- 微基准不覆盖远程监控器、真实 MCP/A2A 网络延迟、高并发及完整监控算法成本。
- 缺少与现有 guardrail 系统的直接比较，因此无法判断其综合效果或成本是否更优。

**总体评价：这是一篇以接口契约和工程集成为核心的研究。它较有说服力地证明了异构监控器能够在明确边界上联合工作，但尚不足以证明面向开放、并发、分布式真实智能体任务的普遍安全性。**
