# One Monitor Does Not Fit All: Formalism-Agnostic Runtime Verification for Agentic AI 

Angelo Ferrando 

University of Modena and Reggio Emilia, Modena, Italy 

angelo.ferrando@unimore.it 

Abstract 

Agentic AI systems combine model decisions, mutable state, tool calls, and delegation to external agents. Monitoring them requires observations from different execution boundaries, while preven-tion requires control before an operation produces its effect. We present AgenticRV, a runtime-verification architecture that separates these boundaries from the monitoring formalism. Adapters emit canonical events; each monitor receives its own projection and abstraction; and a decision policy uses normalised verdicts to select a reaction supported by the responsible adapter. We formalise when observations suffice, monitor replacement preserves decisions, and blocking prevents unsafe effects. We also distinguish rejected attempts from completed effects, avoiding the assumption that a blocked request must leave every monitor in a permanent violation state. The Python implementation supports LangGraph, MCP, and A2A. A controlled LangGraph experiment combines an external Reelay temporal monitor with a programmatic report monitor; ablations show why both are needed for the selected requirements. Differential checks and cross-adapter tests provide further integration evidence. An LLM-driven incident-response example illustrates the same enforcement path, while existing microbenchmarks isolate framework costs. The results support reuse of monitoring methods at explicit control boundaries, subject to the stated observation and deployment assumptions. 

Keywords: Runtime verification; Agentic AI; Runtime enforcement; Monitor interoperability. 

# 1 Introduction 

Agentic AI systems combine language models with stateful workflows, external tools, and other agents. Their behaviour cannot be assessed only from the text produced by a model. A tool request may change an external system, a state update may affect later decisions, and a delegated task may continue outside the local runtime. Relevant observations are spread across model calls, workflow execution, tools, and communication boundaries such as the Model Context Protocol (MCP) and Agent2Agent (A2A) [2, 10]. Runtime Verification (RV) checks an execution against a specification [9]. Earlier work has separated instrumentation from the monitoring formalism, including ROSMonitoring [5] and RV4Chatbot [6]. Runtime enforcement for LLM agents is also already supported by approaches such as AgentSpec [14]. We build on these ideas. Our problem is how to connect different monitoring methods to the same agent execution while making their observation, state, and control assumptions explicit. Consider an incident-response agent that collects diagnostics, creates a checkpoint, applies remedi-ation, and sends an external report. A temporal monitor can require approval and a recent checkpoint before remediation. A separate programmatic monitor can inspect the report destination and content. They need different inputs and need not use the same verdict vocabulary. The runtime must combine their decisions without embedding either monitor’s semantics in the workflow. It must also distinguish an attempted remediation from a completed one: rejecting a request prevents its effect, but the attempt still belongs to the audit history. The underlying issues also occur in conventional software. A model’s statement that an action is approved is not approval evidence. Observing a node’s output does not by itself provide control over its propagation. Receiving a remote task update does not imply control over the remote agent. A reusable interface must expose these differences rather than give every event the same enforcement meaning. This paper presents AgenticRV, a formalism-agnostic architecture for this interface. Source adapters produce canonical events. Monitor-specific projections and abstractions produce the input expected by each monitor, and normalisation maps native verdicts to a common domain. At a boundary that can retain an operation, a decision manager selects a supported reaction before the operation is released. A prior vision paper identified RV constraining LLM-driven systems as one direction in the relation between RV and LLMs [4]; here we give a concrete architecture and examine the conditions under which that direction provides useful guarantees. We make three contributions. First, we define an observation and control contract: we characterise property-sufficient observations, establish a normalised-response condition for monitor replacement, and give a conditional prevention argument. Second, we implement the interface for LangGraph, MCP, and A2A, identifying which boundaries support observation and which support interposition. We also describe the application-specific configuration work. Third, we evaluate joint monitoring with an external temporal monitor and a programmatic monitor, including cross-adapter control, ablations, temporal differential checks, and protocol-adapter tests. An LLM-driven example illustrates integration, while microbenchmarks measure the framework costs separately from monitor algorithms. The contribution is a runtime interface and its contracts, rather than a new specification language or a verification method for model reasoning. The guarantees concern visible operations at installed boundaries. They depend on the observation function, monitor, policy, and faithful adapter enforcement. 

# 2 Architecture 

We use agentic AI system for an application in which model-driven components select actions, update state, invoke tools, or delegate tasks. Figure 1 separates the source adapters, canonical event layer, monitors, and decision manager. An adapter understands its source but contains no property-specific logic. A monitor understands its input domain but need not understand LangGraph, MCP, or A2A. 

Instrumentation and events. Adapters either observe an execution or interpose on an operation. An 

observation event reports activity without retaining the operation. A decision event is emitted before a controlled operation and retains it while synchronous monitors are consulted. Event kind and lifecycle phase do not alone establish control: an MCP request with phase before is still passive if the adapter is configured for observation only. Canonicalisation standardises the event envelope, not every payload. The envelope identifies the source, kind, timestamp, lifecycle phase, and available execution scope. Its payload records the data 2exposed by that source. For example, a summarising node can produce start and completion events containing its input and returned summary. The next node’s input can expose the propagated value. This does not require a separate event for a value moving along an edge. Route metadata, when available, supplies a further observation of the selected branch. The framework adapter covers local execution. The MCP adapter covers wrapped tool and resource requests. The A2A adapter covers wrapped discovery, messages, task operations, status updates, artefacts, and cancellation. Protocol identifiers can relate these observations to the local task. This correlation does not reconstruct a global causal order or expose remote internals. 

Monitor-facing information. Each monitor registration specifies subscriptions, projection, abstrac-tion, verdict normalisation, synchronous or asynchronous execution, and a decision deadline. Subscrip-tions select event kinds. Projection selects or redacts fields; abstraction maps the resulting view to the monitor input. An LTL monitor may receive Boolean valuations, while a programmatic oracle receives structured fields. Either stage may discard an irrelevant event. These choices are part of the property configuration, since filtering can remove evidence or change an event-counting clock. 

Decisions and interventions. The decision manager combines normalised verdicts under a deployment policy. A backend-neutral reaction is a decision such as allow or block whose meaning does not name a framework API. An intervention is its concrete implementation: blocking a native tool suppresses the callable; blocking an MCP request suppresses forwarding. The adapter advertises the reactions supported at each boundary, and records the selected intervention and outcome as another canonical event. The abstract interface also admits pausing, replacing, requesting approval, escalating, aborting, and compensating. An adapter need not support all of them. In particular, a passive callback cannot retroactively block its originating operation. Later escalation or compensation has a different guarantee. Arbitration handles multiple monitors and configured failures, including timeouts and inconclusive results. Fail-open permits an operation without a usable mandatory verdict; fail-closed selects a preventive fallback when the boundary and monitor authorisations support it. 

Trust and scope. We assume correct adapters, event delivery, policy, and property-specific monitoring code. Projection limits the observation passed through the interface; it does not isolate malicious Python code running in the same process. Guarantees are limited to the instrumented boundaries and their available interventions. Ordinary node execution, internal state merges, unwrapped clients, and remote-agent internals do not become controllable simply because related events are available.

3.4 Attempts, Effects, and Prevention 

An attempt and its effect are different observations. A rejected request belongs to the canonical audit trace but not to the sequence of completed effects. Suppose a monitor checks G¬unapprovedRequest on an attempt trace and enters an absorbing violation state when an unapproved request is made. Blocking the request does not erase that attempt, so this monitor correctly remains violated. Under a policy that blocks every violation, it will also reject later requests. This is fail-stop behaviour, not evidence that those later requests are unsafe. A recoverable gate instead answers whether the current request is permitted from the relevant history. It can reject an unapproved attempt, retain the evidence that actually occurred, and permit a later valid request. An audit monitor may still retain the historical violation. Another option is to scope a fail-stop monitor to a task that is intentionally aborted. Resetting a monitor after each rejection is not a general repair: it can remove approval, revocation, or other history still needed for safety. Let 𝑢 ∈ B ∗ be the completed-effect prefix and 𝑥 ∈ B the pending effect. For an allow/block gate, define the intended query by 𝑢𝑥 ∈ 𝐿 , where 𝐿 ⊆ B ∗ is a prefix-closed safety language with 𝜀 ∈ 𝐿 . A 5monitor may implement this query from the full audit history, provided its state represents the relevant completed effects and current attempt correctly. The interface does not assume transactional rollback of arbitrary monitor state. If a requirement depends on time or other observations, these must also be represented in the safety model; erasing rejected attempts does not by itself preserve that requirement. 

Proposition 3 (Conditional prevention) . Assume that: (i) every effect passes through an installed decision boundary; (ii) decisions and effects are serialised, so the gate checks the actual completed prefix 𝑢 ; (iii) every candidate 𝑢𝑥 ∉ 𝐿 is rejected by a mandatory synchronous gate; and (iv) rejection or failure blocks release, with authorised and supported blocking faithfully applied by the adapter. Then every completed-effect prefix belongs to 𝐿 .Proof. Initially 𝑢 = 𝜀 ∈ 𝐿 . A blocked request leaves 𝑢 unchanged. If 𝑥 is released, condition (iii), together with (iv), excludes 𝑢𝑥 ∉ 𝐿 , so 𝑢𝑥 ∈ 𝐿 . Induction over completed effects proves the claim. □

These assumptions identify the assurance boundary. A subscription miss, an unsound abstraction, fail-open behaviour, an unsupported preventive reaction, an unwrapped call, or a failed intervention can invalidate the argument. Concurrent operations additionally need an atomic check-and-release discipline or a property-specific concurrency argument; an ordered event log alone does not establish it. Replacement requires checking the substituted effect, and is not covered by this allow/block result. Each adapter implements a reaction through 𝛾 𝑎,𝑒 : 𝐶 𝑎 (𝑒 ) → I 𝑎 , where I𝑎 is its set of interventions. Prevention requires this intervention to succeed while the operation is held. Events emitted after dispatch, asynchronous verdicts, and late responses can support later reactions but cannot prevent that occurrence. 

# 4 Implementation and Instantiation 

AgenticRV is a Python package whose core depends on neither an agent framework nor a monitoring library. LangGraph, MCP, and A2A are optional integrations. The inspected implementation is version 0.1.0. We distinguish implemented operations, executable integration tests, and measured performance coverage below; support for an operation is not evidence of an experiment using it. 

4.1 Runtime, Monitor Interface, and Adapter Coverage 

Immutable CanonicalEvent objects implement the formal envelope. A private asynchronous loop assigns an increasing sequence number, orders delivery, and maintains one serial queue per monitor. Matching precedes field projection and redaction; user abstraction receives only the projected view. Python callables, stateful objects, and JSON-over-HTTP monitor services share the same request inter-face. Native verdicts are stored alongside their normalised values. The built-in policies use common verdicts, status, priority, authorisation, and explicit replacement proposals, rather than the native verdict or diagnostics. The runtime supports deny-overrides, unanimous, and priority arbitration. Failures, missing verdicts, and deadlines enter the configured failure policy. An asynchronous or late contribution cannot change a finalised decision. A delivery gap marks the affected monitor desynchronised rather than silently using stale state. Recording and replay support fresh offline analysis with the same observation functions; replay does not invoke live interventions. Table 1 identifies the control boundaries. 4.2 What Is Manual, and What Is Reused? 

Instantiation has three layers. The adapter supplies framework and protocol event kinds and supported reactions. The monitor integration supplies its input domain, transition function, and native-verdict normalisation. The application supplies requirements, trusted evidence, relevant scopes, field projection, abstraction, and deployment policy. The architecture reuses the first two layers where possible; it does not automatically derive the third from natural-language requirements. For the incident-response application, the existing LangGraph adapter is installed once and six effect functions are guarded. Application code validates approval and classifies report contents. The Reelay registration subscribes to langgraph.tool , includes 17 field paths, explicitly excludes four raw fields, and maps two native verdicts. One abstraction uses the tool name, lifecycle phase, and five trusted Boolean fields to produce a total valuation. Approval and checkpoint are true on successful completion; remediation and reporting are true on held attempts. The supplied abstraction spans 57 source lines, with a 15-line classification helper; the stateful Reelay facade spans 76 lines, including lifecycle hooks and evidence recording. These are source inventories including comments and blank lines, not development-time estimates. The distinction matters in reuse. Adding a property over existing fields requires a specification or monitor and its registration. Adding a genuinely new observation may require application instrumentation or an adapter change. Replacing Reelay requires another facade and normaliser, but not modifications to the LangGraph wrapper. A content monitor may legitimately need raw report text that the temporal monitor must not receive. Projection declarations are therefore reviewed per property rather than copied indiscriminately. Subscriptions and field projection are declarative; abstraction and trusted classification may require Python code. Native verdict mappings can be declared as a table, while numerical verdicts can use configured thresholds. Validation checks deployment structure and callable interfaces, not semantic sufficiency. The condition in Section 3.2 supplies the corresponding review obligation. Time bounds, task scoping, failure policy, and monitor recovery remain explicit engineering choices. The case study and controlled experiments use one monitor instance per logical workflow and serial effect requests. No automatic isolation of arbitrary interleaved tasks is claimed. A deployment with concurrent tasks must introduce suitable per-task monitor state and preserve the scope information needed by its requirements. 75 Evaluation 

We separate four questions: (Q1) can monitors with different inputs and native verdicts jointly control the same workflow? (Q2) does the temporal integration preserve the selected specification, including its boundaries and recovery? (Q3) which implemented adapter and runtime behaviours have executable validation? (Q4) what are the costs of instrumentation and dispatch apart from non-trivial monitor computation? The first three questions use controlled validation, while the fourth uses microbenchmarks. The validation and timing sets use different environments and are not pooled.

Observing MCP alone loses approval evidence and blocks both legitimate reports. With the full view, a public report is permitted after secret-report rejection without resetting approval history. Trustworthy scope and approval remain application obligations; this is controlled integration, not automatic task isolation or remote-service evaluation. 

5.3 Differential Checks and Adapter Validation 

We compare the fixed Reelay monitor with an independent Python evaluator of 𝜒 𝑖 . The alphabet contains six symbols: completed approval, completed checkpoint, a neutral step, remediation attempt, public-report attempt, and secret-report attempt. We enumerate all 1,554 non-empty words of length at most four. Comparing every step of every word gives 5,910 verdict comparisons with no mismatch. This finite enumeration checks the chosen alphabet and short histories; it is not a proof for unbounded traces. Short prefixes do not cross every freshness bound. We separately vary approval age from one to eight and checkpoint age from one to five at a remediation request. Excluding equal ages, which cannot represent two distinct observations in this alphabet, gives 35 cases. Reelay permits exactly when the approval age is at most six and the checkpoint age at most three. The checks include rejection followed by a permissible observation, confirming the non-absorbing interpretation of the current guard. We also change the native-verdict payload while retaining each of the four common verdicts and the same control metadata. The built-in policy selects the same reaction in all four pairs, exercising Equation (2). This is a regression check of that interface condition, not an independent proof of the complete implementation. The selected repository test set contains 179 passing cases, with no skips or failures. It covers adapters, projection, policy, ordered runtime delivery, timeouts and late responses, trace handling, and selected executable examples. The protocol examples use a real in-process MCP client/server session and a real A2A SDK client with a controlled JSON-RPC transport. The MCP example executes echo 

but blocks delete_records before the server function is reached. The A2A example forwards one permitted message and blocks the rejected message before transport dispatch. Other adapter tests check passive mode, replacement, lifecycle events, errors, cancellation, and scope. These are integration checks, not experiments with deployed remote agents. The controlled validation uses CPython 3.11.16 on Linux, LangGraph 1.2.14, LangChain Core 1.6.7, MCP 1.30.0, A2A SDK 1.2.2, and Reelay 25.0.0. The supplement records the dependency snapshot, scripts, specification checksum, test report, and per-request outcomes. These versions are separate from the performance environment below.

5.5 Framework Costs 

The microbenchmarks isolate instrumentation, dispatch, projection, auditing, and intervention. Their monitors return immediately in the same process. They measure framework overhead, not the cost or diversity of substantive monitor algorithms. Reelay is not part of this timing campaign. The timing measurements use an Apple M3 Pro with 18 GiB of memory, Python 3.14.6, AgenticRV 0.1.0, and LangGraph 1.2.9. Each condition runs in 20 fresh processes with three warm-up and five measured batches of approximately 200 ms. Settled time includes work queued by an operation and drained within its batch, excluding construction, warm-up, validation, and shutdown. # 6 Related Work 

Runtime verification separates the observation of an execution from the analysis of its trace [9]. Runtime enforcement additionally controls whether an operation is released. Surveys of correct-by-construction enforcement in AI distinguish the guarantees of such mechanisms from checks of an AI component’s output alone [8]. Our prevention argument is conditional on the installed boundary and monitor contract; it does not construct a shield from a model of the environment. 

Monitoring infrastructures. ROSMonitoring separates ROS instrumentation from monitoring back-ends and does not prescribe a specification formalism [5]. ROSMonitoring 2.0 extends that setting to services and ordered topics [12]. RV4Chatbot follows the same design direction for chatbot interaction protocols, instantiated for Rasa and Dialogflow [6]. These are direct architectural precedents. Formalism agnosticism and adapter-based observation are therefore not new contributions of AgenticRV. We extend this separation to a shared interface for local graph events and tool/delegation boundaries, with per-monitor observation and normalisation, explicit boundary capabilities, and a distinction between attempted actions and effects. The observation-sufficiency condition states which property information a view must retain. The replacement and prevention propositions state the limits of the resulting control contract. These mechanisms are applicable beyond agentic AI; the agentic contribution is their instantiation across the identified sources and trust boundaries, together with executable joint-monitor evidence. 

Agent guardrails and enforcement. NeMo Guardrails provides programmable rails for LLM ap-plications [11]. AgentSpec provides a DSL combining triggers, predicates, and enforcement actions, 12 and evaluates runtime constraints on several kinds of LLM agents [14]. It already supports modular runtime enforcement and adaptation to agent frameworks. The distinction is not that AgenticRV intro-duces enforcement or reusable instrumentation, but that its core interface leaves the monitor input, state, formalism, and native verdict domain to separately registered implementations. ProbGuard learns a probabilistic execution model and predicts safety risks to trigger proactive intervention [15]; RvLLM uses its own formal-specification approach to constrain LLM behaviour [16]. These methods have their own guarantees and evaluation scopes. They are possible sources of monitoring components for an interoperability layer, subject to appropriate observation and response bindings. We have not integrated them, and the two-monitor experiment does not establish compatibility with their implementations. 

Specifications and monitor generation. Operational and declarative monitoring approaches can be combined for data-rich traces, as in TP-DejaVu [7]. NL2TL translates natural-language requirements into temporal logic [3]. Such work can help obtain a monitor or specification, while AgenticRV addresses its connection to execution boundaries. It does not remove the need to establish trusted propositions, review information loss, or select a failure policy. AgentHarm evaluates harmful multi-step agent behaviour [1]. It motivates evaluation over full executions, but our controlled paths are not a substitute for such benchmarks. The present results concern interface integration and conditional enforcement, rather than comparative end-to-end agent safety. 

# 7 Conclusion 

AgenticRV connects agent execution boundaries to monitors with different input and verdict domains. Its contract separates sufficient observation, normalised arbitration, and supported intervention, while distinguishing a rejected attempt from a completed effect. LangGraph, MCP, and A2A adapters im-plement the interface at explicit boundaries. Controlled ablations show joint enforcement by Reelay and a programmatic report monitor, including permitted recovery after rejection. A LangGraph–MCP workflow also tests approval correlation across incident scopes. Differential checks and adapter tests add reproducible integration evidence; the microbenchmarks isolate framework costs. The next evalua-tion steps are broader agent workloads, monitor configuration effort, substantive remote monitors, and concurrent check-and-release behaviour. Distributed trace reconstruction and stronger event-integrity guarantees also require work beyond the centralised model studied here.
