## 摘要
编码智能体的任务是生成复杂的交互式应用，例如网站、桌面应用和游戏。人类会通过交互来评估这些应用，而当前自动化 LLM 评估主要关注代码分析和单元测试。这种不匹配可能导致 LLM 评判器忽略人类用户一眼就能发现的问题。我们研究了“交互即评判”（Interaction-as-a-Judge）这一评估范式：计算机使用智能体（CUA）直接与应用进行交互。我们证明，“交互即评判”能够同时改进交互式应用的评估与生成。为此，我们收集并发布了两个互补的数据集：6,858 对带有人类偏好标注及相应智能体交互轨迹的应用，以及 222 个带有人类核验需求标签的应用。与标准的非交互式方法相比，“交互即评判”在预测人类偏好（65.6% → 69.1%）和需求验证（77.0% → 81.6%）方面均提升了评估效果。我们还观察到规模效应：无论在人类偏好对齐还是需求验证方面，更高质量的交互都能提升性能。最后，通过推理阶段和训练阶段的实验，我们证明“交互即评判”也能提高生成产物的质量。在推理阶段，“交互即评判”在五次尝试内修复了 75.5% 的失效需求，而仅基于代码的自反馈修复率为 55.4%。在训练阶段，将“交互即评判”用作奖励信号，相较于基础模型，胜率提高了 6.7 个百分点；与仅基于代码的奖励信号相比，生成代码长度减少了 35.7%，构建失败率降低了 7.2 个百分点。

## Abstract
Coding agents are tasked with producing sophisticated interactive applications such as websites, desktop applications, and games. While humans assess these applications interactively, current automated LLM evaluations primarily focus on code analysis and unit tests. This mismatch can cause LLM judges to miss failures that are immediately apparent to human users. We study Interaction-as-a-Judge, an evaluation paradigm where computer-use agents (CUAs) directly interact with an application. We demonstrate that Interaction-as-a-Judge can improve both evaluation and generation of interactive applications. To this end, we collect and release two complementary datasets: $6,858$ pairs of applications with human preferences and corresponding agent traces, and $222$ applications with human-verified requirement labels. Relative to standard non-interactive approaches, we find that Interaction-as-a-Judge improves evaluation in terms of predicting human preferences ($65.6\% \to 69.1\%$) and requirement verification ($77.0\% \to 81.6\%$). We also observe scaling benefits: across both preference alignment and requirement verification, higher-quality interactions improve performance. Finally, through both inference- and training-time experiments, we demonstrate that Interaction-as-a-Judge can also improve the quality of generated artifacts. At inference time, Interaction-as-a-Judge repairs $75.5\%$ of broken requirements within five attempts, compared to $55.4\%$ for code-only self-feedback. At training time, using Interaction-as-a-Judge as a reward signal improves win-rate over the base model by $6.7$pp while reducing both generated code length by $35.7\%$ and build failure rates by $7.2$pp compared to a code-only reward signal.

## 1. 核心问题与整体含义：为什么评估应用需要“实际操作”？

- **研究背景**：编码智能体已经能够生成网站、工具和游戏等复杂应用，但现有自动评估往往依赖源代码、单元测试或初始页面截图。这些证据不足以反映实际使用质量：
  - 能编译不代表功能正确；
  - 页面美观不代表按钮、表单或状态切换正常；
  - 游戏逻辑看似合理，也可能在操作中出现碰撞异常、动画错误或场景卡死。
- **核心问题**：让计算机使用智能体（Computer-Use Agent，CUA）实际操作应用，再根据交互过程中观察到的行为进行评判，能否更准确地预测人类偏好、验证功能，并进一步改善应用生成？
- **整体含义**：论文将评估依据从“静态产物”扩展为“运行时行为证据”，建立以下闭环：

  **生成应用 → 智能体交互 → 根据轨迹评判 → 用作修复反馈或训练奖励。**

- 需要注意：论文的实验主要覆盖 **React 网页应用和浏览器游戏**，并未直接验证其在所有桌面软件或复杂生产系统中的效果。

## 2. 方法论：核心思想、关键技术与算法流程

### 2.1 两阶段架构：交互与评判解耦

Interaction-as-a-Judge 包含两个组件：

1. **交互组件**：操作应用，收集截图、动作及可选的动作理由。
2. **评判组件**：利用这些轨迹，结合用户请求及可选源代码，判断应用质量。

二者可以由同一模型完成，也可以采用不同组合，例如：
- 强 CUA + 通用 LLM 评判器；
- 无模型的交互启发式 + 训练后的奖励模型；
- 仅使用交互轨迹、不读取代码的奖励模型。

论文将交互建模为部分可观测决策过程。轨迹可以理解为按时间排列的“**观察—动作理由—动作**”序列；评判器看到的是应用被操作后的实际表现，而不只是初始截图。

### 2.2 三种交互策略

| 策略 | 执行方式 | 优势 | 主要限制 |
|---|---|---|---|
| **迭代式交互** | 每一步观察结果，再决定下一步 | 能根据应用状态调整策略，通常效果最好 | 每一步需要模型推理，成本较高 |
| **一次性规划交互** | 根据初始截图及可用代码，一次生成整个动作序列 | 只需一次规划调用，成本较低 | 无法根据执行结果修正计划 |
| **启发式交互** | 从候选控件或动作中随机采样 | 无动作规划模型调用成本 | 难以探索复杂流程，尤其不擅长游戏 |

- 非游戏应用的启发式策略会借助 DOM 找到可见、可操作的按钮、链接、输入框等，因此**不是纯粹的随机像素点击**。
- 主要偏好实验每个候选应用最多执行 **30 次工具调用**；一次调用可以包含多个底层键盘或鼠标事件。
- 对游戏采用时间控制机制，在动作之间暂停游戏，以减少模型响应延迟对游戏运行的干扰。

### 2.3 两类评判器

**通用 LLM 评判器**
- 偏好任务：读取用户请求、两个应用的证据，预测人类更喜欢哪一个。
- 为减轻位置偏差，每对应用交换顺序评判两次，取平均一致率。
- 需求验证：将需求标为“正常、损坏、无法验证”。
- 需求发现：不给需求列表，要求模型自行发现待修复的问题。

**训练式奖励模型**
- 在 Qwen3.5-9B 上增加标量奖励头。
- 使用 Bradley–Terry 成对偏好损失：提高人类偏好获胜应用相对于失败应用的奖励分数。
- 训练语言主干及奖励头，冻结视觉编码器。
- 可以输入代码与交互轨迹，也可以完全不输入代码。

### 2.4 如何用于生成改进

- **推理阶段**：修复已知故障需求 → 自行验证 → 根据反馈继续修复，最多五轮。
- **训练阶段**：用交互轨迹奖励模型给生成应用打分，再通过 DAPO 风格强化学习更新生成模型。
- 强化学习同时加入构建、渲染失败惩罚；因此训练收益并非仅来自交互奖励本身。

## 6. 主要结论与发现

### 6.1 交互能改善评估，但收益依赖模型和场景

| 实验 | 基线 | 交互方法 | 变化 |
|---|---:|---:|---:|
| Gemini 3 Flash 偏好一致率 | 仅代码 65.6% | 69.1% | +3.5 个百分点 |
| Gemini 3 Flash 偏好一致率 | 代码 + 截图 67.6% | 69.1% | +1.5 个百分点 |
| 完整代码奖励模型 | 69.7% | 70.8% | +1.1 个百分点 |
| 仅 `App.tsx` 奖励模型 | 68.2% | 70.2% | +2.0 个百分点 |
| Sol 需求验证 | 77.0% | 81.6% | +4.6 个百分点 |
| 五轮累计修复率 | 55.4% | 75.5% | +20.1 个百分点 |

- **重要例外**：GPT 5.6 Luna 的偏好一致率从仅代码的 68.3% 变为迭代交互的 67.9%，没有显著改善。因此不能概括为“所有评判器加入交互都会提升”。

### 6.2 正确性收益主要来自识别损坏需求

以 Sol 为例：
- 损坏需求识别：63.0% → 71.1%；
- 正常需求识别：91.0% → 92.1%。

77.0% → 81.6% 是这两类表现的**非加权平均**，不是直接按全部需求数量计算的总体准确率。不给需求列表时的问题发现仍较困难，最佳损坏需求召回率约为 28%。

### 6.3 更好的交互证据通常更有帮助

- 迭代式交互整体最好；模拟和游戏的收益尤其明显。
- 低质量轨迹训练的奖励模型，有时可以通过高质量测试轨迹提升表现。
- 附加游戏实验中，视频带来主要收益，加入动作与理由文本的平均增益接近于零。
- 轨迹变长通常提高准确率，但后期边际收益减小；单纯提高静态截图分辨率无法弥补差距。

### 6.4 交互奖励可改善生成过程

相较代码奖励模型：
- 生成代码长度减少 **35.7%**；
- 构建成功率由 **81.3% 升至 88.5%**；
- 构建失败率下降 **7.2 个百分点**。

相较基础模型，交互奖励训练后的自动评判胜率增益为 **6.72 个百分点**。该质量比较仅针对成功构建、成功渲染的样本，且不是直接的人类投票结果。论文支持交互奖励改善构建稳定性和代码长度，但**没有证明其生成质量显著优于代码奖励训练**。

## 7. 优点与亮点

- **问题定位准确**：针对“静态代码正确不等于实际使用正确”的关键缺口。
- **框架通用且可组合**：交互策略、评判器和代码可用性可以独立选择。
- **形成完整证据链**：从评估准确性延伸到修复反馈和强化学习训练。
- **数据具有真实用户基础**：同时涵盖真实偏好与人工核验故障需求。
- **消融较系统**：不仅证明交互有效，还分析了交互质量、轨迹长度、视觉分辨率及文本证据的作用。
- **无代码奖励模型具有应用价值**：能够评估只能访问运行界面、无法获得源代码的应用。
- **结果呈现相对克制**：披露模型例外、类别退化及需求发现能力不足。

## 8. 不足与局限

- **场景外推有限**：主要验证 React 网站和浏览器游戏；没有覆盖复杂后端、跨设备流程、长期状态或真实桌面应用。
- **有限交互不等于充分测试**：30 步难以覆盖深层流程、罕见故障和长时行为，未观察到错误不能证明应用正确。
- **CUA 错误可能污染判断**：操作失败可能来自智能体，而非应用；质量评估与交互能力存在耦合。
- **高质量轨迹的归因不完全独立**：正确性实验同时更换交互与评判模型，难以严格拆分两部分贡献。
- **数据选择偏差**：
  - 偏好集排除了构建失败和平局；
  - 存在地区筛选和用户群体限制；
  - 正确性集偏向已被用户投诉的问题，且类别不平衡。
- **生成评估仍依赖模型**：修复结果由更强模型验证，强化学习质量由内部自动评判器衡量，缺少全面独立的人工终评。
- **关键训练数据私有**：虽提供评测数据和配置，但偏好训练集及强化学习提示集并未完全公开，限制复现。
- **成本与部署效率不清晰**：缺少总延迟、API 成本和 GPU 小时比较，尚不能确认何种收益值得额外交互成本。
- **奖励漏洞并未消失**：不读取代码可减轻代码长度偏差，但模型仍可能优化容易被短轨迹展示的表面行为，而非真正完善所有功能。

**总体评价**：论文较有说服力地证明，运行时交互证据可以补充静态代码和截图，尤其有助于发现行为故障并改善迭代修复。它更适合被理解为对现有评测体系的重要扩展，而不是替代单元测试、静态分析或完整软件测试的通用方案。
