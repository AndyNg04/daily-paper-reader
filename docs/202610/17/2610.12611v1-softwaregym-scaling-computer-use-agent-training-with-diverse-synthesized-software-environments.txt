ABSTRACT
Computer-use agents (CUAs) are rapidly improving, yet synthesizing diverse and
reliable software environments at scale remains challenging. Native application
environments require substantial construction and integration effort, which lim-
its application coverage and increases the risk of application-specific overfitting.
Browser-hosted environments provide limited interaction depth and workflow
complexity. These limitations motivate SoftwareGym, an automated pipeline for
synthesizing GUI software environments with diverse interfaces, executable func-
tionality, and runtime-verified behavior. It generates structurally diverse designs,
realizes them as runnable applications, and uses GUI evaluation with iterative
repair to ensure functional reliability. Using SoftwareGym, we synthesize 182
applications across twelve categories and achieve a mean GUI task pass rate of
91.5%. We construct SoftwareGym-Bench, a 120-task evaluation suite spanning
the same twelve categories, and use trajectories collected from these environ-
ments for CUA training. The resulting model improves Pass@3 from 41.39% to
56.97% on the strictly out-of-domain OSWorld benchmark and achieves 40.0%
on SoftwareGym-Bench. These results demonstrate the potential of synthesized
software environments as scalable and transferable supervision for CUA training.

INTRODUCTION
Training capable computer-use agents (CUAs) requires interaction data from executable software
environments (Qin et al., 2025). To support generalization, these environments must provide diverse,
realistic, and reliable trajectories. Constructing such environments at scale has therefore become a
central bottleneck for CUA training.
Current data synthesis either generates tasks and trajectories within existing desktop and mobile
applications (Sun et al., 2025; Xie et al., 2026; Jung et al., 2026) or constructs browser-hosted
software environments (Cao et al., 2026; Liu et al., 2026). Native applications preserve realistic states
and complex workflows, but the cost of integrating them into reproducible training environments
limits application coverage and increases the risk of application-specific overfitting. Browser-hosted
environments support scalable deployment and state control, but their shared substrate limits interac-
tion depth and workflow complexity. Existing approaches do not jointly satisfy three requirements
for CUA training: interface and interaction diversity to support generalization, functional reliability
to produce valid, complex trajectories, and scalability to expand the environment pool with limited
engineering effort. Achieving these three requirements introduces three corresponding challenges:
interface and interaction diversity is difficult because unconstrained generation within the same soft-
ware category often converges toward similar layouts and interaction patterns; functional reliability

requires these diversity controls and reliability checks to be applied across a large software pool,
creating a verification burden that manual development cannot sustain.
To address these challenges, we design SoftwareGym, an automated multi-agent pipeline for GUI
software synthesis. For diversity, SoftwareGym creates category-level functional specifications and
variant-specific interface and interaction designs. For reliability, it combines source-level verification
with checkpoint-based GUI evaluation and repair; only applications that complete both source-level
and GUI verification enter the software library. For scalability, it automates the complete process
with minimal human input, enabling applications to be generated in batches with substantially lower
time and monetary costs than manual development. To realize these goals, synthesis proceeds in
three stages. The design stage expands minimal human input into a detailed functional specification,
diverse UI blueprints, and corresponding interaction schemes. The implementation stage converts
each design package into an executable application and verifies its source-level functionality. The
evaluation stage executes checkpoint-based GUI tests and guides iterative implementation repair.
These stages enable SoftwareGym to produce diverse and functionally reliable software environments
with realistic multi-step workflows at scale.
Using this pipeline, we construct a large, diverse, and functionally reliable software library in
substantially less time and at lower monetary cost than manual development. We synthesize 182
runnable applications across twelve categories, with a mean GUI task pass rate of 91.5%. Figure 1
illustrates their functional depth across representative software categories. We use trajectories
collected from these applications to train a model. Without using any OSWorld applications, tasks, or
trajectories for training, it improves Pass@3 from 41.39% to 56.97% on OSWorld, demonstrating
strong out-of-domain generalization. For complementary evaluation, we evaluate the model on
SoftwareGym-Bench, a dedicated 120-task test set spanning the same twelve categories; it achieves
40.0% Pass@3 and outperforms several larger specialized computer-use agents. Our contributions
are threefold:
(1) We introduce SoftwareGym, an automated environment-synthesis pipeline that produces func-
tionally reliable and structurally diverse software at scale, with substantially lower development
time and monetary cost than comparable manually developed applications.
(2) We release 182 runnable applications across twelve categories and construct SoftwareGym-
Bench, a dedicated 120-task test set spanning the same twelve categories.
(3) Through extensive evaluations and ablations, we validate the pipeline’s key components and
show that the model trained only on SoftwareGym trajectories improves OSWorld Pass@3 by
15.58 points to 56.97%.

RELATED WORK
Data Synthesis in Existing Software.
Benchmarks such as OSWorld, Windows Agent Arena,
and AndroidWorld first make real desktop and mobile applications reproducibly accessible for CUA
evaluation (Xie et al., 2024; Bonatti et al., 2024; Rawles et al., 2025). Subsequent work synthesizes
tasks and trajectories within existing desktop and mobile applications (Sun et al., 2025; Xie et al.,
2026; Jung et al., 2026; Yang et al., 2026; Xue et al., 2026). CUA-Universe and Gym-Anything further
adapt and configure existing software as reproducible agent environments (Shi et al., 2026; Aggarwal
et al., 2026). Complementary systems refine online traces, collect human demonstrations, or train
over decentralized CUA data (Qin et al., 2025; Wang et al., 2025b;a). Although these approaches
preserve authentic software states and complex workflows, their coverage remains constrained by the
availability and integration cost of existing applications. Repeated training on this fixed software pool
may also encourage application-specific overfitting. SoftwareGym instead synthesizes new executable
applications with controllable functions, interfaces, and interaction logic, directly expanding the
software distribution.
Synthesis of Browser-Hosted Software Environments.
InfiniteWeb and AutoWebWorld first
establish scalable browser-hosted environments through multi-page websites and state-machine-
generated Web worlds (Zhang et al., 2026; Wu et al., 2026). GUI-GENESIS and ScaleWoB further
extend this approach toward software interaction by reconstructing real applications or synthesizing
software interfaces as backend-free webpages (Cao et al., 2026; Liu et al., 2026). Although these
approaches simplify deployment and state control, their shared browser/HTML/DOM substrate limits
native application structure and persistent workflows. SoftwareGym instead synthesizes standalone
desktop applications.
3
METHOD
Figure 2 summarizes software synthesis in SoftwareGym. Software Design (§3.1) specifies appli-
cation functions and interfaces. Software Implementation and Evaluation (§3.2) then realizes each
application and iteratively repairs it using failures observed through GUI interaction. Applications
that complete this verification loop enter the software library. Task Synthesis (§3.3; Figure 3) converts
their verified functions into executable GUI tasks.
3.1
SOFTWARE DESIGN
The design stage produces rich, realistic functional specifications and specifies diverse GUI structures
and interaction patterns for each software variant. Given a software type and supporting resources, it
produces a shared Software Specification and multiple style-specific Verified Design Packages. Each
package contains the Software Specification, a UI Blueprint, and SVG Assets.
Function Design.
Function design specifies the purpose of an application and the detailed functions
it should provide. Given the Software Type and Resources, FUNCTIONDESIGNER expands the initial
description through a four-step workflow. First, it establishes the functional baseline of a mature
product by identifying its target users, core objects, and expected operations, such as creating, opening,
editing, organizing, searching, recovering, and saving content. Second, it extends each module with
domain-specific professional functions, including multi-condition retrieval, batch operations, history
management, persistent view settings, and input validation. Third, it connects these functions into
complete user workflows, from creating or opening content to editing, organization, retrieval, and
final save or export. The workflows also cover cross-module state changes, dependent operations,
failure handling, and recovery. Finally, it records each function in the Software Specification as an
implementation and evaluation contract. The contract specifies the user entry, user action, expected
state update, visible GUI response, and acceptance checkpoint. These steps provide functional
breadth and operational depth while making every function implementable and directly verifiable
through GUI interaction.

stage generates multiple diverse, implementation-ready Avalonia UI blueprints. These blueprints real-

Icon and SVG Asset Generation.
ICONDESIGNER derives a style-independent Icon Candidate
Manifest from the Software Specification, covering application, action, navigation, status, content-
type, entity, avatar, and illustration icons. For each interface variant, SUBSTYLEDESIGNER assigns
icon candidates to GUI slots, and SUBICONDESIGNER renders them as style-specific SVG assets.
Icons with the same semantic role across variants are required to differ structurally rather than only by
color. A platform-side validator checks asset completeness, SVG validity, and safety constraints. The
resulting icon assets and slot mappings are included in the Verified Design Package. Together, these
constraints preserve functional consistency while introducing visual diversity across synthesized
software variants.
3.2
SOFTWARE IMPLEMENTATION AND EVALUATION
Software Implementation and Evaluation turns each Verified Design Package into a runnable applica-
tion and verifies that it satisfies the specified functional and interface requirements. For each software
variant, we implement the application, evaluate its GUI behavior, and use observed failures to guide
iterative repair.
Application Implementation and Source-Code Verification.
CODER uses the Verified Design
Package as the implementation specification and realizes the complete Avalonia application, including
its structure, visual system, icons, and functionality. Each specified function is implemented as a
complete GUI workflow, covering user entry points, command bindings, state updates, persistence,
and visible feedback. CODER also records each function and its acceptance check in a functional
manual. DEVCODER then audits the implementation against this manual. It checks command

GUI Test Generation and Evaluation.
Source-code verification alone cannot confirm how an
application behaves under direct interaction. Evaluation therefore tests the running application
independently, covering both functional GUI behavior and visual fidelity to the design package.
EVALTASKGENERATEAGENT generates cases from the source-verified functional manual produced
during implementation. The cases cover control reachability, navigation, object creation and editing,
persistence, retrieval, settings, dialogs, and file workflows. Each case begins from an explicit state,
uses only documented functions, and defines visible checkpoints. The case set is fixed after the first
implementation and reused across repair rounds. GUIAGENT executes the cases with mouse and
keyboard actions and records the interaction trace, checkpoint evidence, final state, failure location,
and repair suggestion. Functional pass rate is Pfunc = Npass/Nall, where Npass is the number
of passed tasks and Nall is the total number of generated cases. The evaluation report and failed
trajectories are returned to implementation for the next repair round. Evaluation stops when all cases
pass or the version budget is exhausted. This process grounds implementation repair in reproducible
GUI failures and progressively improves functional reliability.
Design Fidelity.
Functional success alone does not guarantee that a repaired application retains
its intended interface. Design fidelity therefore ensures that implementation and source-code repair
preserve the interface identity of each software variant. After each GUI-evaluation round, Softwar-
eGym computes a normalized visual-fidelity score between the implemented application and its
UI blueprint; its calculation is defined in Appendix B. When the score falls below a pre-calibrated
threshold, the evaluator provides targeted feedback for repair. Structural checks also compare the
implemented layout and interface elements with the blueprint. This ensures that implementation
repair improves functionality without deviating from the intended interface structure or visual design.
3.3
TASK SYNTHESIS
Task synthesis constructs GUI tasks using only application capabilities verified through GUI evalua-
tion. As shown in Figure 3, it consists of three steps: function analysis, difficulty leveling, and task
generation.
Function Analysis.
Function analysis identifies the application capabilities that have been verified
through GUI interaction and can be used for task synthesis. It constructs an evidence-grounded
function tree for each retained software variant. To build this tree, the pipeline extracts a functional
manual produced during implementation. It then uses the GUI evaluation report to determine which
functions are supported. Each leaf records a task-level capability, its support status, GUI entry points,

constraints, observable state, and evaluation evidence. A capability is marked supported only when it
cites a passed case, checkpoint, or interaction step. Untested functions, failed functions, and blocked
paths are excluded. This evidence gate prevents task generation from relying on functions that have
not been demonstrated in the running application.
Difficulty Leveling.
Difficulty leveling controls task complexity through dependencies among
verified capabilities. Tasks are assigned to three difficulty levels: easy, normal, and hard. Supported
capabilities are selected according to the assigned difficulty. An easy task has one primary goal
with limited functional composition. A normal task combines related objects or operations with a
necessary dependency between them. A hard task forms a multi-stage workflow in which each stage
establishes state required by the next stage. Each difficulty level contains two task types. A file-based
task starts with an existing input file. A blank-state task starts without an input file and operates from
the application’s default GUI state. All operations in a task must contribute to the same user goal;
unrelated or repeated actions cannot be added merely to increase difficulty. These constraints produce
comparable difficulty levels while preserving natural, goal-directed workflows.
Task Generation.
Finally, task generation converts each planned workflow into a natural user re-
quest and an executable evaluation specification. It checks the selected capabilities against the manual,
passed GUI evidence, entry points, state dependencies, persistence behavior, and completion feedback.
The request describes one user goal and the constraints required for evaluation. The user-facing
request does not expose coordinates, detailed operation paths, capability identifiers, or evaluation
mechanisms. The internal task specification records the initial state, outcome criteria, process criteria,
and expected final state. Deterministic validation rejects unsupported capabilities, inconsistent initial
states, incompatible assets, and unreachable final states. This stage produces natural-language tasks
whose requirements remain feasible, observable, and deterministically verifiable.

EXPERIMENTS
4.1
EXPERIMENTAL SETUP
Software Synthesis.
We synthesize applications across twelve categories using Codex CLI agents
with GPT-5.5 for design, implementation, and evaluation-case generation. Each application is refined
for up to three versions (v1–v3), with the v1 GUI test suite held fixed across rounds and early stopping
when all cases pass. Seed 2.1 Pro evaluates each version through mouse-and-keyboard interaction for
up to 50 steps per case in isolated virtual machines running Ubuntu 22.04.3 LTS (x86 64).
Training.
After constructing the software library, we perform multimodal SFT on Qwen3.5-
9B (Team, 2026) using trajectories collected only from SoftwareGym applications. Appendix E
describes trajectory scoring and filtering, and Appendix C.3 provides the full training configuration.
SoftwareGym-Bench.
SoftwareGym-Bench is a dedicated evaluation suite built on the Software-
Gym application library. We select one application from each of twelve software categories and ten
manually verified tasks per application, yielding 120 tasks in total. Each task is constructed to ensure
that its target state is reachable and programmatically verifiable. Tasks also include state-grounded
distractors and protected objects, requiring agents to reason about which objects to modify, ignore, or
preserve rather than simply follow a fixed sequence of operations. Further construction details are
provided in Appendix A.
Evaluation and Baselines.
We evaluate the trained model and baselines on OSWorld and
SoftwareGym-Bench.

SoftwareGym-Bench contains the 120 tasks described above. We evaluate GPT-5.5 (OpenAI, 2026b),

Software Synthesis Analysis.
SoftwareGym scales the software library while preserving broad,
runtime-verified functionality. Its 182 runnable applications span twelve categories (Figure 4(a)).
Among 121 applications from eight categories represented in OSWorld, GUI evaluations cover all 49
major functional modules and 78.8% of concrete functions on average (Figure 4(b)). Appendix B
defines the evidence criterion. This coverage demonstrates that SoftwareGym expands software
breadth while retaining substantial verified functionality. We further characterize synthesis cost by
sampling 20 applications. Each application requires 237.3 minutes, 14.8 million tokens, 1,718 model
calls, and an estimated $70.76 on average. Figure 5 decomposes these resources across pipeline
stages, showing that automated synthesis substantially reduces the cost of constructing software
environments at scale. Finally, iterative evaluation and repair improve software reliability across the
library. The mean GUI task pass rate increases from 54.9% at v1 to 81.1% at v2 and 91.5% at v3, with
consistent gains across categories (Figure 6). This improvement demonstrates that evaluation-guided
repair progressively enhances implementation reliability.

4.3
ABLATION STUDIES
We next examine the contribution of three key components: structured style design, GUI-guided
implementation repair, and the source of training trajectories.
Style Design.
We compare Full Design with a simplified baseline under the same functional
requirements and measure structural diversity using normalized tree-edit distance. Full Design
improves the macro-average diversity score from 4.9 to 83.6 and achieves higher diversity across all
categories (Figure 7(a)). This result shows that explicit style control prevents independently generated
designs from collapsing to similar interface structures. Appendix C.1 provides details.
Evaluation-Guided Implementation Repair.
We compare GUI-guided repair with source-only
repair under the same repair process. Starting from the same initial pass rate of 50.4%, GUI-
guided repair reaches 83.1%, whereas source-only repair ends at 48.8% (Figure 7(b)). This result
demonstrates that GUI feedback provides essential runtime evidence for reliable implementation
repair. Appendix C.2 provides details.
Training Software Source.
We compare models trained with trajectories collected from Softwar-
eGym applications, OSWorld applications, and their combination, while keeping the model and
evaluation protocol fixed. The model trained only on SoftwareGym trajectories achieves 56.97%
on OSWorld and 40.0% on SoftwareGym-Bench, while combining SoftwareGym and OSWorld
trajectories further improves SoftwareGym-Bench performance to 47.5% (Table 3). These results
show that synthesized software provides transferable supervision and complements native-software
data. Appendix C.3 provides details.

CONCLUSION
We introduced SoftwareGym, an automated design–implementation–evaluation pipeline that syn-
thesizes diverse and functionally reliable desktop applications at scale. Its library contains 182
applications across twelve categories and achieves a mean GUI task pass rate of 91.5%; ablations
show the value of structured design and evaluation-guided repair. Trajectories collected from these
environments provide transferable supervision beyond synthesized software. Without any OSWorld
application data for training, it improves Pass@3 from 41.39% to 56.97% on OSWorld and reaches

SOFTWAREGYM-BENCH: CONSTRUCTION AND TASK EXAMPLES
A.1
BENCHMARK CONSTRUCTION
Outcome-Driven Task Construction.
We construct each task backward from a desired final state.
We first define the target outcome and then identify the key semantic steps required to reach it. The
initial state is built to support these steps and their dependencies. This construction ensures that every
task has a reachable solution path and a well-defined terminal state.
State-Grounded Task Difficulty.
We introduce distractors and protected objects into the initial
state to make task completion require state-grounded decisions. Some objects must be modified,
some ignored, and some preserved. The correct action therefore depends on the current application
state rather than on a fixed sequence of interface operations. This design increases task difficulty
while preserving a coherent user goal.
Programmatic Evaluation.
Each task is paired with a reproducible initializer and a programmatic
evaluator. The initializer restores the task to the same initial state before each attempt. The evaluator
checks the resulting application state and any produced artifacts against the target outcome. This
makes task success deterministically verifiable and results comparable across models and runs.
To make the benchmark and its evaluation protocol concrete, we present representative successful
trajectories across software categories.

Layout-archetype distance quantifies how differently two style vari-

Visual Fidelity.
Visual fidelity measures whether an implemented application preserves the design
tokens specified by its UI blueprint during iterative repair. Let Cb and Ca denote the sets of color
values extracted from the UI blueprint and implemented application, and let Rb and Ra denote their
corner-radius sets. We use the Jaccard similarity J(A, B) = |A ∩B|/|A ∪B|, with J(∅, ∅) = 1, and
define Fpal = J(Cb, Ca) and Frad = J(Rb, Ra). Fpri and Ffont are binary indicators of whether the
blueprint’s primary color and main font are retained in the application. Fbind = Nres/(Nres+Ninline),
where Nres counts resource-based visual references and Ninline counts inline color values; the ratio
is set to 1 when its denominator is zero. The primary-color, corner-radius, and font components are
set to 1 when the corresponding blueprint property is unspecified. The overall score is
Fvis = 0.40Fpal + 0.15Fpri + 0.20Frad + 0.10Ffont + 0.15Fbind.
This is a design-token implementation gate, not a perceptual image-similarity measure. We use a
pre-calibrated threshold of 0.80, so the gate passes when Fvis ≥0.80 and the primary color is retained.
When an implementation does not satisfy this gate, the evaluator identifies the visual tokens that
deviate from the blueprint and returns those mismatches as concrete repair targets. Subsequent repair
can therefore correct functional issues without altering the application’s intended visual identity.

ABLATION PROTOCOLS AND COMPLETE RESULTS
This section separately examines the style-design procedure, the use of GUI feedback during imple-
mentation repair, and the software source used to collect training trajectories. Appendix B defines
the reported metrics, while Appendix E details the trajectory filtering used by the training-source
ablation. Selections and outputs are frozen in versioned manifests.
C.1
STYLE-DESIGN ABLATION
The comparison covers Browser, Chat, Code Editor, Forum, Mail, PDF, Rich-text Editor, Image
Editor, Slides, Spreadsheet, Music Player, and Video Player. Each method generates one set of ten
blueprints per category, yielding 120 Full Design blueprints and 120 Simple Design blueprints (240
total). Both methods receive the same frozen functional requirements and icon inventories.
Full Design generates distinct directions and assigns each to an independent designer. It enforces
variation in information architecture, layout, visual system, interaction model, and product identity,
and rejects structurally redundant designs. Simple Design receives none of these style-control
instructions; it is told only that the ten final layouts should differ. Both methods use the same artifact
schema and final validators.
For each category and method, we average the normalized tree-edit distance over the 45 pairs formed
by its ten blueprints, using the same corpus-level structural representation as the production diversity
gate. The overall score is the macro-average of the twelve category scores; Appendix B defines the
tree representation and distance. Full Design produces more diverse blueprint structures in every
category and raises the macro-average score from 4.9 to 83.6. Although all Simple blueprints differ
at the file level, each category contains at least one pair with the same normalized layout tree, and
none of the twelve Simple sets passes the production diversity gate.

EVALUATION-GUIDED IMPLEMENTATION-REPAIR ABLATION
The implementation-repair comparison uses a category-balanced paired set of three applications from
each of the twelve categories (n = 36), all with complete artifacts from the shared starting checkpoint
through both repair rounds.
Both branches start from the same v1 source package and use the same two implementation-repair
rounds. We run the same GUI evaluation after every round for both branches. In the GUI-guided
branch, the resulting report is passed to the Coder for the next repair round; in the source-only branch,
the report is recorded but withheld, so the next repair uses source-code evidence alone.
Scores average GUI task pass rates over the 36 applications while giving each of the twelve categories
equal weight. GUI feedback is decisive: from the shared 50.4% starting score, evaluation-guided
repair reaches 70.5% at v2 and 83.1% at v3, while source-only repair reaches 50.5% and then falls
below the shared starting score to 48.8%. This regression shows that source-level self-correction
alone is insufficient and can even degrade runtime functionality, making feedback from direct GUI
testing essential for reliable repair. The final 34.3-point advantage is large and consistent (95% CI:
28.2–41.0); GUI-guided repair wins on all 36 applications.

C.3
TRAINING-SOFTWARE-SOURCE ABLATION
Finally, we train three Qwen3.5-9B models: one on trajectories collected only from synthesized
SoftwareGym applications, one only from native OSWorld applications, and one on both sources.
Before length filtering, the SoftwareGym-only and OSWorld-only datasets are each matched to
3,715 trajectories and 55,263 serialized examples, with identical train/validation/test sizes. Both
datasets use the same 0.8 outcome and process thresholds and message-conversion protocol; their
post-threshold selection is source-specific, as specified in Appendix E.
For the model trained on both sources, we concatenate the complete frozen SoftwareGym-only and
OSWorld-only datasets. Because the two datasets are size-matched, each source contributes equally.
We preserve their source-prefixed semantic identifiers and original splits, without additional attempt
sampling or rewriting.
All three models are initialized from Qwen3.5-9B Base and use full-parameter SFT of the language
model for one epoch; the visual encoder and merger are frozen. The SoftwareGym-only model is
trained with 16 A800 GPUs. The OSWorld-only model and the model trained on both sources are
each trained with 8 A800 GPUs. We use bf16, FlashAttention, ZeRO-2, gradient checkpointing,
learning rate 5 × 10−6, 3% warmup, cosine decay, sequence length 16,384, and micro-batch size
1. Gradient accumulation is 2 for the SoftwareGym-only model and 4 for the OSWorld-only model
and the model trained on both sources, keeping the global batch size at 32. Overlength examples are
removed rather than truncated, leaving 49,445 examples for SoftwareGym-only training, 49,496 for
OSWorld-only training, and 98,941 for training on both sources. Evaluation fixes the context and tool
protocol, temperature 1, top-p 0.95, output limit 8,192, 100 interaction steps, and three independent
rollouts per task.
Tables 6 and 7 give the complete run-level results, while Table 3 summarizes Pass@3 in the main text.
Synthesized-software supervision transfers strongly to unseen native applications and complements
native-software data. On OSWorld, the SoftwareGym-only model obtains 56.97% Pass@3 without
any OSWorld application, task, or trajectory in training, compared with 61.48% for the OSWorld-
only model. On SoftwareGym-Bench, the SoftwareGym-only model obtains 40.0%, whereas the
OSWorld-only model obtains 33.3%. The model trained on both sources further demonstrates their
complementarity, reaching 47.5% on SoftwareGym-Bench while retaining 58.61% on OSWorld.
Matching the base model, pre-tokenization corpus size, effective batch size, core optimization settings,
and evaluation makes the source of the training trajectories the principal difference between the
SoftwareGym-only and OSWorld-only models.

TRAJECTORY SCORING AND FILTERING
Our trajectory-selection procedure asks two complementary questions: whether the agent reaches the
requested final state and whether it follows a reliable interaction process. After a structural audit, two
independent GPT-5.5 judges score each candidate. Qualified trajectories are converted to Qwen3.5
multimodal format, validated, source-specifically selected, and group-split.
E.1
TWO-STAGE TRAJECTORY SCORING
The outcome and process judges use the following prompts. The user request is the only task
specification; generated metadata is not ground truth. Outcome scoring uses up to the final five full
assistant messages and their step-aligned post-action screenshots; process scoring uses every full
assistant message and up to ten evenly sampled, step-aligned screenshots. We retain an attempt only
when both scores are at least 0.8.
Prompt for Outcome Scoring
System:
You are the OUTCOME judge for a GUI task. Determine whether the agent truly completed the user’s
request. The user request is the only task specification; ignore any generated planning or explana-
tion metadata. You will receive up to the final five chronological assistant messages. Each message
includes the complete available reasoning and assistant content, followed immediately by that exact
step’s paired post-action screenshot when available. Use message text as context for what the agent
attempted, but treat it as an unverified claim; the paired screenshot is the primary evidence of what
actually happened. Check the final evidence against every material requirement in the user request. Do
not reward an agent merely for declaring success or attempting the right action. Do not evaluate general
path efficiency here except where the final messages reveal that the requested result was not actually
completed. Score 1.0 for clearly complete evidence, 0.7–0.9 for completion with only a minor deviation,
0.4–0.6 for substantial partial completion, 0.1–0.3 for little verified progress, and 0.0 for no relevant
verified result. Return only JSON: {"score":
<0.0-1.0>, "reason":
"<assessment
of actual completion against the user request>"}
User:
# User Request
{user request}
# Final Five Assistant Messages (chronological; paired screenshots follow their exact messages)
{evidence}

E.2
MESSAGE CONVERSION, SELECTION, AND SPLITTING
Data from OSWorld and SoftwareGym undergo source-specific selection. For OSWorld, we retain the
highest-scoring qualified attempt from each task directory; all score-qualified SoftwareGym attempts
proceed to conversion. Selected trajectories from both sources are converted from the teacher schema
to Qwen3.5 multimodal format. Attempts failing strict message-format or consistency validation are
excluded.
After conversion, SoftwareGym caps each frozen semantic group at two trajectories; OSWorld
balances eight domains and difficulty to match corpus and split sizes. Both use approximately 90/5/5
group-constrained splits without frozen-group overlap, a guarantee relative to the pipeline’s grouping
definition.
