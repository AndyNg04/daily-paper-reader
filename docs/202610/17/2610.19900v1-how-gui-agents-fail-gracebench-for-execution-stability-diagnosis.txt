# How GUI Agents Fail: GraceBench for Execution Stability Diagnosis 

Ridong Zhang, Shuxian Liang †, Chaoqun Wan, Zhen Huang, Xian-Sheng Hua 

Institute of AI for Engineering, Tongji University Project page: https://iaie-physicalai.github.io/GraceBench 

Abstract 

As GUI agents are increasingly deployed for mobile task automation, their reli-ability depends not only on final task outcomes, but also on whether they reach these outcomes through stable interaction trajectories. Whether in daily automa-tion scenarios or testing workflows, unnecessary actions, detours, and execution errors can add noise to collected data, introduce irreversible side effects, or un-dermine trust, even when the agent eventually completes the task. It is therefore important to systematically diagnose the execution stability, including whether an agent deviates from a feasible path, enters a loop, becomes stagnant, or recov-ers from unstable actions. Existing benchmarks, however, primarily assess final task success or a small set of intermediate milestones, leaving step-level execu-tion behavior unclear. To bridge this gap, we introduce G RACE BENCH , an online evaluation framework that represents the reachable interaction space of mobile applications as UI Transition Graphs (UTGs), providing a structural reference for step-level execution diagnosis. To support reliable alignment between dynamic UI observations and graph states, GraceBench uses video-grounded trajectory eval-uation over this graph-aligned representation, assessing process stability beyond final success by measuring metrics such as deviation rate, loop burden rate, and recovery ability. GraceBench contains 169 tasks spanning 10 applications and constructs 10 UTGs with 2,909 canonical GUI states and 3,116 observed tran-sitions. Across 3,718 trajectories, GraceBench shows that outcome scores hide execution instability: GPT-5.6 Sol achieves the highest success rate (SR) but the lowest recovery ability, 51.24% of successful runs still contain a deviation or loop, and trajectories with the same success rate (SR) and completion rate (CR) can dif-fer substantially in recovery behavior. Code will be made publicly available. 

1 Introduction 

Graphical user interface (GUI) agents are increasingly expected to operate real software environ-ments on behalf of users (Zhang et al., 2025), from completing routine mobile tasks (Rawles et al., 2025) to supporting software-testing data collection workflows. In such settings, an agent’s capa-bility is not determined solely by whether it eventually reaches a target state; the execution process itself is equally important. This is especially true in GUI-based automated testing, where system performance, logs, resource usage, and behavioral signals are often collected along the execution trajectory. If an agent gets off track, repeats actions, or fails to recover, these path-dependent mea-surements become noisy and difficult to interpret, reproduce, and trust (Dong et al., 2021). Exe-cution stability is therefore a key requirement for reliable GUI-agent deployment in real interactive environments. Existing GUI-agent benchmarks primarily evaluate task completion, usually by checking whether the final state satisfies a goal condition (Rawles et al., 2025). Although terminal success is useful, it offers little visibility into the stability of the execution process. Some recent work introduces intermediate milestones, such as essential states or subtasks, to measure staged progress (Chai et al., 2026a; Chen et al., 2025), but such evaluation remains coarse-grained: it implicitly treats

Without step-level diagnostic signals, it is difficult to systematically understand execution instability in real GUI interactions. To address this gap, we introduce G RACE BENCH , a benchmark for diagnosing the execution sta-bility of GUI agents in real mobile applications. GraceBench uses UTGs to represent the finite reachable interaction space of an application as a graph. In a UTG, nodes correspond to GUI states and edges correspond to executable action transitions between states (Yang et al., 2015; Wen et al., 2024). This graph serves as a coordinate system for evaluating execution: nodes indicate where the agent is, edges indicate where the agent is moving, and the surrounding graph reveals what alter-native interactions are available. GraceBench defines each task on a task-specific UTG subgraph and maps the recorded execution trajectory back onto this graph for step-level diagnosis. Because dynamic mobile UIs can change during and after an action, GraceBench uses synchronized video evidence to align observations with graph states and diagnose what happened between consecutive decisions. Based on this UTG representation, GraceBench evaluates GUI agents beyond final success. It con-tains 169 tasks across 10 applications and multiple domains, built on 10 UTGs with 2,909 canon-ical GUI states; each task’s matched states and their one-hop neighborhood cover 41.09 canonical GUI states on average, providing a local structural reference for step-level diagnosis. Each task is paired with concise and detailed instruction variants, allowing us to evaluate stability under both au-tonomous path planning and step-level execution guidance. Beyond success and completion rates, GraceBench reports deviation rate, loop burden rate, and recovery ability to evaluate the execution stability of GUI agents. We evaluate eleven models, including two GUI-specific models and nine general-purpose models, on all 169 tasks under two instruction conditions, yielding 3,718 trajectories. 2 Related Work 

2.1 Mobile GUI Agent Benchmarks 

Early GUI agent benchmarks mainly rely on offline evaluation, where predicted actions are matched against a single golden trajectory step by step (Rawles et al., 2023; Li et al., 2024). While scal-able, such protocols reduce GUI control to trajectory imitation, ignoring multiple valid paths and the agent’s ability to recover from deviations. Recent online benchmarks, represented by Android-World (Rawles et al., 2025), allow agents to interact with executable environments and evaluate task completion from the final UI state. However, final-success metrics remain coarse: they reveal whether a task is completed, but not how reliably it is executed. Process-aware benchmarks fur-ther introduce intermediate supervision. A3 (Chai et al., 2026a) evaluates the completion ratio of essential semantic states, SPA-Bench (Chen et al., 2025) verifies predefined app-level subtasks, and ProBench (Yang et al., 2025) captures process information to check key-step completion. These works move beyond outcome-only evaluation, but their signals are still mostly defined over mile-stones or semantic checkpoints. Consequently, they provide limited visibility into failures occurring between milestones, and cannot distinguish merely successful executions from stable executions. Our work focuses on this missing layer by evaluating GUI agents at the granularity of execution states and action transitions. 

2.2 Graph-Structured Representations for GUI Agents 

Graph structures have been widely used to model GUI interaction as transitions over discrete inter-face states. Existing works use such representations for app exploration and knowledge construc-tion (Sun et al., 2025; Chai et al., 2026b), task generation and pretraining (Ye et al., 2025; Wu et al., 2024), and runtime planning or recovery (Yu et al., 2026; Guo et al., 2025; Zhong et al., 2026). These methods demonstrate that graphs provide a natural abstraction for multi-step, multi-path GUI interaction. 3 GraceBench 

To operationalize the graph-based diagnosis motivated above, GraceBench uses task-specific UTGs as a shared reference throughout benchmark construction and evaluation. We first build application-level UTGs and curate 169 long-horizon tasks across 10 multi-functional mobile applications, each with concise and detailed instructions. Agents then execute these tasks on physical devices while GraceBench records synchronized actions, observations, and video evidence. Figure 2 provides an overview of the resulting GraceBench pipeline: panel (a) illustrates agent-driven UTG construction, panel (b) summarizes task curation, and panel (c) shows video-grounded trajectory evaluation. We describe these components in order below.

3.2 Online Execution Environment 

Following ProBench (Yang et al., 2025), GraceBench evaluates agents on physical Android devices in an online loop. At each step, the agent receives the current screenshot, task instruction, and inter-action history, and its textual action is parsed into ADB commands for execution until completion or budget exhaustion. 3.3 Video-Grounded Trajectory Evaluation 

GraceBench evaluates each execution trace by aligning observed agent behavior with the task sub-graph. The evaluation pipeline contains four stages. First, the episode-level video is segmented into step-level clips based on action timestamps. These clips provide visual evidence for what happened before, during, and after each action. Second, GraceBench retrieves the task-specific subgraph from the full application UTG. The subgraph contains the task initial state, target state, required transi-tions, and alternative valid paths, serving as the reference structure for judging whether an observed action advances the task. Third, a video-based evaluator analyzes each local transition (ot, a t, o t+1 )

using the corresponding step-level video clip and executed action. The evaluator maps the pre-action and post-action observations to graph states. For each observation, the matched graph state is defined as

3.4 Evaluation Metrics Task evaluation metrics. At the task level, we report task success and graph-aligned execution quality. (1) SR measures the fraction of trajectories marked successful in the per-trajectory evalu-ation summaries; these labels are preserved in all reported analyses. (2) CR measures how much of the task-required subgraph has been completed, providing a finer-grained view of progress when the final task fails. (3) Deviation rate (DR) measures how often the agent moves outside the task subgraph, capturing path instability. (4) Loop burden rate (LBR) measures how much execution is consumed by repeated no-progress behavior once looping occurs. (5) Recovery success rate (RSR) 

measures whether the agent can return to the task subgraph after a deviation. (6) Average recovery latency (ARL) measures how many steps successful recovery takes. (7) Recovery ability (RA) com-bines recovery success and recovery speed into a single robustness score. 4 Experiments 

Our experiments address three questions: How do GUI agents fail? Do task outcomes adequately characterize execution stability? Finally, Do stability metrics capture reproducible agent differ-ences across tasks? After the setup, each subsection answers one question using outcome-stratified statistics, outcome-controlled comparisons, or cross-task replication. Table 2 summarizes the main experimental results across agents, instruction conditions, and stability metrics. 

4.1 Experimental Setup Baseline agents. We evaluate representative screenshot-only GUI agents, including GUI-specific models and general-purpose models from the DeepSeek, Gemini, GPT, Qwen, and GLM families, using each model’s official prompting and tool-calling setup when available. Each model is tested under detailed subgraph-derived instructions and concise user-level goals, with temperature set to 0 and a maximum budget of 15 actions. Table 2 contains 3,718 trajectories from eleven completed models, two instruction conditions, and 169 tasks. All trajectory-level analyses use this full eleven-model dataset; paired instruction analyses contain 1,859 model–task pairs. The two GUI-specific models use 8-bit MLX checkpoints (Apple, 2026) and were collected on a separate host; their evalu-ated records are included in every applicable analysis. In addition to SR and CR, we report DR, LBR, RSR, ARL, and RA to evaluate GUI-agent execution stability; detailed definitions and aggregation rules are provided in Appendix B.

Equivalent task performance masks substantial stability differences. Success is only the coarsest form of outcome equivalence. We therefore compare models executing the same task under the same instruction condition, with identical SR and equal stored CR. 4.4 Stability Metrics Capture Consistent Agent Differences Model behavior profiles persist across tasks. We test whether process metrics capture repro-ducible model behavior by repeatedly splitting the 169 tasks into stratified halves, ranking all eleven models by each metric on each half, and measuring rank agreement with Spearman ρ. The strongest consistency appears for DR and LBR: detailed-instruction rankings reach ρ = 0 .9516 and 0.9284 ,while concise-instruction rankings remain high at ρ = 0 .9228 and 0.8381 . RSR is also stable across splits ( ρ = 0 .8100 detailed; 0.8269 concise), whereas ARL is weaker ( ρ ≈ 0.58 ) and RA is condition-dependent. All metric–condition correlations remain significant after Bonferroni correc-tion ( p < 0.05 ); the full table and permutation details are reported in Appendix Table 9. 

5 Conclusion 

We introduced G RACE BENCH , which aligns video-recorded trajectories with task-specific UI Tran-sition Graphs to diagnose deviation, looping, and recovery during real mobile execution. Across eleven models and 3,718 trajectories, GraceBench reveals execution weaknesses hidden by SR and CR: lower-performing agents deviate and loop more often, while even the highest-SR model exhibits limited recovery on observed recovery opportunities. Successful trajectories, as well as trajectories with identical SR and CR, can still differ substantially in DR, LBR, and RA, showing that reliable GUI automation requires more than task completion alone. By providing graph-aligned evidence and process-level diagnostics, GraceBench supports future work on stronger state tracking, loop detection, and recovery policies for GUI agents. 9Preprint 

AI use statement 

In this work, we used generative AI tools to assist benchmark construction, including drafting can-didate task instructions, expanding parameterized task variants, and producing auxiliary transition annotations for GUI trajectory diagnosis. All AI-assisted outputs were treated as candidate arti-facts rather than ground truth. The authors manually reviewed the retained UTGs, task definitions, task instructions, and screenshots to ensure state validity, transition executability, task feasibility, and consistency with the benchmark protocol. For step-level diagnostic labels, expert-agent outputs were not assumed to be fully human-labeled; instead, we conducted a preregistered, stratified au-dit in which sampled transition labels were validated against blinded human expert judgments, as described in Appendix E. The reported quantitative results are computed from the documented eval-uation records and metric definitions, and generative AI tools were not used to make final scientific claims without author verification. The authors take full responsibility for the final content of this work, including text, claims, data, and artifacts produced with the aid of generative AI. 

Ethics statement 

GraceBench is designed to diagnose GUI-agent execution stability in controlled mobile environ-ments. The benchmark does not involve human-subject experiments. Because GUI agents may interact with real applications, we constrain tasks to avoid irreversible or high-risk operations such as payment, order submission, purchases, account changes, or authorization changes. During UTG construction and evaluation, such operations are treated as boundary states and are not executed. Screenshots, videos, and traces are collected from controlled devices and benchmark accounts, and released artifacts will be reviewed to remove or anonymize sensitive information where necessary. The benchmark is intended for reliability diagnosis and safety-oriented analysis rather than for en-abling harmful automation. 

Reproducibility statement 

To support reproducibility, we will release the benchmark task definitions, instruction variants, UTG metadata, evaluation code, metric definitions, and trace/evaluation schemas, with detailed metric calculation rules provided in the appendix. For each evaluated run, GraceBench stores action traces, pre-action and post-action screenshots, action metadata, timing information, and synchronized video evidence, and we document the evaluation environment so that trajectory judgments can be audited despite changes in mobile applications, app versions, accounts, devices, and online content. The current analysis package contains per-trajectory evaluation records for all eleven models; the two GUI-specific models were collected on a separate host, and their video and screenshot files are not included in this package.

Among the resulting 1,035 trajectories over 134 tasks, the weighted SR is 0.2591 for a return within three decisions and 0.1275 without one, a difference of 0.1316 with a 95% task-cluster interval of [0.0800, 0.1829]. 

Adjusted association and sensitivity. On all 2,230 eligible trajectories, a linear probability anal-ysis controlling task–condition and model fixed effects, onset bin, and prior-progress bin estimates an SR difference of 0.1021 [0.0604, 0.1438]. Interpretation boundary. Return is neither sufficient for task success nor an isolated validation of the RA latency weighting: among 1,301 trajectories that recovered from every observed off_path 

opportunity, only 408 eventually succeeded (SR=0.3136). After controlling whether a return oc-curred, a 0.1 increase in the local reciprocal-latency score is associated with an SR difference of 0.0047 [-0.0039, 0.0133]. The experiment therefore supports the outcome relevance of timely re-turn, but not a causal effect, an optimal latency function, or a common-error-start ranking of general recovery competence.

D Automatic UTG Exploration Details 

Agent–harness decomposition. Our explorer is not a fixed-path crawler. It separates semantic decisions from deterministic device operations: an agent identifies the current GUI state, selects business-relevant actions, and assigns stable state names, while an external harness performs ev-idence capture, action execution, graph serialization, risk gating, and consistency checks. This design allows the same execution protocol to cover heterogeneous applications without encoding app-specific navigation paths in the runtime. Before exploration, we perform a short reconnaissance pass and define an application-specific value spine, such as search–product–cart for shopping, feed– playback–comments for media, or book detail–reader–table of contents for reading applications. Low-value settings branches are expanded only after the value spine has been covered. 

Observation and evidence capture. The default observation waits 2 seconds for the interface to stabilize and then records three synchronized evidence sources through ADB (Android Developers, 2026): (i) a lossless PNG screenshot using exec-out screencap -p ; (ii) the focused package and Activity from dumpsys window ; and (iii) a UI hierarchy from uiautomator dump , with a compressed-dump fallback. For asynchronous transitions such as opening a reader or a media detail page, the agent requests a second observation with an extended wait rather than treating an intermediate loading frame as a state. Each observation is stored as a JSON record together with its screenshot and XML paths, timestamp, visible text, candidate controls, scrollable regions, and hashes. The files are indexed as step_XXXX_<label> so every graph update can be traced to the original evidence. 

State signatures and matching. The XML parser removes invalid regions smaller than 6 × 6

pixels and deduplicates controls by label and center coordinates quantized to eight-pixel cells. At most 60 tap candidates, 24 stable controls, and 12 scrollable regions are retained per observation. Personalized strings containing long numbers, prices, popularity counts, usernames, or other volatile values are excluded from the stable-control set. The harness computes a 16-hex-character screenshot hash from the PNG and a structural hash from 

(Activity , node count , clickable count , first 18 stable controls ).

These SHA-1-based hashes are deterministic identity hints, not security primitives. The agent first supplies a stable semantic state name; when several nodes share that normalized name, the harness resolves the anchor using exact screenshot hash ( +160 ), exact structural hash ( +120 ), matching Activity ( +100 ), pending status ( +80 ), and existing evidence/children. Before a pending edge enters the normal queue, a lightweight mount guard checks the current parent, proposed action, target state, and sibling context. For example, player-only actions such as comments or episode selection cannot be mounted directly under a search/ranking list, and closing one overlay should not transition directly to an unrelated overlay. A failed check writes mount_check.status=needs_review , sets blocked=true , marks the target needs_reobserve=true , and removes it from the normal pending queue. This lo-cal guard runs online; a full-tree audit is reserved for completed value-spine milestones and final delivery. 

Safety and termination. The execution gate uses both explicit metadata and lexical redline cat-egories covering payment, order submission, recharge, withdrawal, authentication, authorization, external sharing, publishing, and account-asset mutations. A risky entry may be represented as a boundary edge with risk=true and status=defer , but the side-effecting confirmation is not executed. Search submission and filter application are explicitly treated as safe exceptions. After each verified transition, reconciliation marks an action done only when every non-risk target has evidence or explored children; blocked, risky, and deferred edges remain unresolved by design. Ex-ploration stops when the application value spine has been covered and the remaining queue contains only risky, blocked, duplicate, or low-value branches. Finally, we manually review state names and evidence, deduplicate equivalent states, verify return transitions, and synchronize the canonical graph with its visualization copy.

E Human Expert Audit of Generated Transition Labels 

Transition sampling and review protocol. We froze a visual-validation population of 3,042 trajectories containing 34,767 transitions with locally verified MP4 evidence. The 676 imported aggregate-only records without media bytes were excluded. With seed 20260926, we sampled by execution model, instruction condition, and scenario, retaining at least one trajectory per nonempty stratum. The resulting 313 trajectories contain 3,487 transitions, or 0.1003 of the eligible tran-sition population. Reviewers saw the task, expert path, primitive action, and a five-frame ordered action-aligned storyboard (pre-action, onset, post-action, response, and settled frames), while model identity, condition, automatic labels, and terminal outcomes remained hidden. Expert agents generated the initial diagnostic labels for exact expert-edge state matches and Devia-tion, Recovery, and Loop events. Human experts then independently reviewed the sampled transi-tion storyboards under blinded conditions and produced reference binary labels for each diagnostic field. After the primary reviews were frozen, a human expert adjudicated field-level disagreements; all 3,487 transitions were resolved. Human experts served as auditors and annotators rather than experimental subjects, so this audit is not a human-subject experiment. Cohen’s κ is computed between the expert-agent generated binary labels and the human-adjudicated reference labels. For each diagnostic field, the expert-agent output and the human-adjudicated ref-erence each provide a binary label for every one of the 3,487 sampled transitions.
