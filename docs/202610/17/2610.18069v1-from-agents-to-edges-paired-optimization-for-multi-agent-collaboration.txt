# ABSTRACT 

Strong individual agents do not guarantee effective collaboration. Communica-tion must align what one agent conveys with how another interprets and uses it. This dependency makes the communication edge a natural unit of optimization. We introduce Paired Automated Communication Optimization (PACO), which jointly optimizes the instructions at both ends of each edge and their shared com-munication convention in systems built on black-box language models. PACO keeps model weights, agent roles, and workflow topology fixed. A state-aware discounted bandit selects edges for refinement, while execution feedback guides paired revisions evaluated through staged end-to-end execution. The optimized instructions integrate into existing agent prompts without additional model calls at deployment. On a four-agent workflow evaluated across diverse multi-agent benchmarks, PACO consistently outperforms leading prompt-optimization and communication baselines. Configurations learned on HotpotQA retain their advan-tage in cross-dataset transfer without target-specific optimization. These results demonstrate that optimizing how agents communicate can substantially improve collaboration within an otherwise fixed system. 

# 1 INTRODUCTION 

Multi-agent systems (MAS) built on large language models (LLMs) distribute complex tasks across specialized agents, with applications in software development (Qian et al., 2024), GPU kernel optimization (Luo et al., 2026), web automation (Fourney et al., 2024), and scientific discovery (Swanson et al., 2025). Their effectiveness depends on more than the quality of individual agents: each handoff determines the context available for subsequent reasoning. When agents have different information access or responsibilities, a correct intermediate result may still be insufficient if its evidence, constraints, or uncertainty are omitted or misinterpreted downstream (Cemri et al., 2025). Such failures can undermine the benefit of specialization even when the underlying models are capable. We study how to improve these handoffs within a fixed workflow by optimizing the instructions that govern context construction and use. To illustrate this problem, consider a simple distributed averaging task, following the classical distinction between local aggregates and the intermediate information needed to combine them (Gray et al., 1997). An upstream agent observes two values, 10 and 10 , and correctly reports a local mean of 10 . A downstream agent holds another value, 100 , and must compute the mean across all three observations. If the message contains only the local mean, the downstream agent lacks the sample count needed to weight it correctly. Even if that count is provided, averaging the two means without weighting yields 55 instead of the correct result, 40 . The relevant dependency spans two agents: the upstream agent must provide the information required by the aggregation rule, and the downstream agent must apply that rule consistently. This motivates grouping the instructions governing a handoff into one optimization unit. Existing approaches improve collaboration through workflow search (Zhang et al., 2025c;a), commu-nication protocols and message representations (Huang et al., 2026; Gupta et al., 2026), and agent or component prompt optimization (Agrawal et al., 2026; Wang et al., 2026; Hong et al., 2026). Several already account explicitly for interactions: MAPRO models compatibility between agent prompts (Zhang et al., 2026), MASPOB supports block-coordinate updates of adjacent agents (Hong et al., 2026), and AgentAsk introduces edge-level clarification during execution (Lin et al., 2026). We introduce Paired Automated Communication Optimization (PACO), an edge-centric framework that automates communication-instruction refinement in multi-agent systems built on black-box LLMs. As illustrated in Figure 1, PACO jointly refines the upstream instructions for constructing task context, the downstream instructions for interpreting and using it, and their shared communication convention. A state-aware discounted bandit selects edges using configuration-specific search histories. Execution feedback guides two rounds of paired revision, allowing proposals to be refined after their effects are observed. Staged end-to-end evaluations screen candidates on small batches before evaluating selected candidates on the internal validation set. Throughout optimization, model weights, agent roles, topology, and information access remain fixed. The learned packages are incorporated into existing agent prompts, so deployment requires no additional message-rewriting or clarification calls. Experiments on a four-agent workflow across three question-answering benchmarks (Yang et al., 2018; Dua et al., 2019; Trivedi et al., 2022) demonstrate the value of optimizing communication. PACO consistently outperforms leading prompt-optimization and communication baselines, improving HotpotQA Joint F1 by over 30 points relative to the unoptimized workflow. Configurations learned on HotpotQA retain their advantage under cross-dataset transfer without target-specific optimization, with a gain of nearly 6 Answer F1 points over GEPA on DROP, the strongest evaluated baseline. Controlled ablations support the value of paired refinement and assess the search components, while execution analyses characterize changes in reference preservation and downstream interpretation. Our main contributions are: • From agents to edges. We parameterize each handoff as a package of upstream instructions, downstream instructions, and a shared communication convention, aligning the optimization unit with the dependency between context construction and use. • Automated paired refinement. We introduce PACO, combining state-aware edge selection, execution-guided two-round revision, and staged end-to-end evaluation to optimize these packages under a token budget. • Strong performance and cross-dataset transfer. PACO outperforms leading evaluated baselines while keeping model weights and the workflow fixed, and retains its advantage under transfer without target-specific optimization. Ablations and execution analyses provide complementary evidence for the effectiveness of paired communication optimization. 2Preprint

Inspired by GEPA’s candidate-pool design (Agrawal et al., 2026), PACO maintains a pool P of complete communication configurations, each comprising the packages of all edges. The pool starts with the initial configuration Θ0 and retains evaluated configurations with complementary performance on the internal validation set H drawn from the optimization data. This preserves multiple starting points for refinement, including configurations that excel on different examples. Among configurations satisfying the pool’s quality and uniqueness criteria, each example in H credits those attaining its best score. Redundant configurations are pruned while preserving coverage, and PACO samples a configuration Θ ∈ P in proportion to its credits. The selected configuration serves as the parent for the next refinement step. The evaluation procedure is described in Section 3.5, with detailed pool admission and pruning rules provided in Appendix A. 3.3 STATE -A WARE EDGE SCHEDULING

After selecting an edge e, PACO refines its communication package in two rounds. Feedback from the parent alone cannot reveal how proposed instructions will interact during execution. The second round therefore uses first-round execution feedback to address remaining or newly introduced mismatches in context construction and use. Each round may revise any subset of the package’s endpoint instructions, shared convention, and message representation, while proposing and evaluating the package as a unit. For an ordinary step, edits are restricted to e, and the parent Θ remains the evaluation reference throughout. The parent first executes on a small pilot batch Dp. An LLM-based proposer uses the current package, fixed runtime constraints, and execution feedback to generate K1 candidate configurations

The generation base and evaluation reference serve different purposes. Invalid, duplicate, or unchanged candidates are filtered out, so the evaluated set may contain fewer than K1 + K2 candidates. If no first-round candidate is scorable, the second round is skipped. Feedback includes agent-visible inputs, exchanged messages, outcome categories, and eligible earlier execution cases. Reference answers, hidden reasoning, and per-example numerical verifier scores are excluded from proposer feedback. Within each refinement step, promotion evaluations occur after proposal generation and guide candidate selection. Their executions may inform later steps through historical search-set feedback, whereas evaluations on H are never used as proposal examples. We use K1 = K2 = 2 in our experiments. 3.5 STAGED END -TO -E ND EVALUATION

Disjoint pilot and promotion batches are drawn from search data separate from the internal validation set H. The pilot batch Dp screens candidates from both rounds against a positive-gain threshold. Configurations with complete evaluations on H are archived and used to refresh the candidate pool (Section 3.2). Near-best configurations with complementary coverage may be retained even when 5Preprint their mean score is lower than their parent’s. Since H guides search and configuration selection, it belongs to the optimization data and remains separate from the final test set. Each ordinary refinement step supplies at most one reward to the selected configuration’s edge bandit (Section 3.3), computed from the deepest valid evaluation stage. Evaluation settings and implementation details are provided in Appendix A. 3.6 COOPERATIVE REFINEMENT 

Improving one edge may enable further coordination across the workflow. When an ordinary single-edge step achieves a new best mean score on the full internal validation set H, PACO triggers one cooperative refinement step, using the improved configuration as its parent. This step may revise multiple edge packages, following the same two-round refinement, staged evaluation, and pool admission rules. It neither updates the single-edge bandit nor triggers further cooperative refinement. The overall search operates under a shared optimization-token budget. At its stopping boundary, PACO completes ongoing steps and freezes the configuration with the highest mean score on the full validation set H for testing. Algorithm 1 in Appendix A summarizes the complete procedure. 

# 4 EXPERIMENTS 

4.1 EXPERIMENTAL SETUP 

Tasks and data. We evaluate on HotpotQA (Yang et al., 2018) and MuSiQue-Ans (Trivedi et al., 2022) for multi-hop reasoning, and DROP (Dua et al., 2019) for discrete reasoning over text. Opti-mization uses 500 HotpotQA examples: 400 for sampling pilot and promotion batches ( Dp, D m) and 100 for internal validation ( H). After optimization, the best configuration on H is frozen for evalua-tion on 800 HotpotQA questions and 400 questions per transfer dataset, without further optimization. Appendix C details data construction. 

Workflow and initialization. We use a fixed four-agent chain: Scout → Resolver → Integrator 

→ Verifier. All agents receive the question, but only the first two receive separate evidence shards. Messages are accessible only to the direct successor, making downstream reasoning dependent on context preserved across handoffs. PACO starts from the unoptimized (vanilla) workflow, with simple, generic instructions for context construction and use and basic edge-specific conventions suggesting typed records with soft formatting requirements. Role instructions and information access remain fixed throughout optimization. Appendix D provides the complete configuration. 

Models and optimization. Workflow agents and the LLM-based proposer use gpt-5.6-luna 

with low and high reasoning effort, respectively. PACO uses a 25M-token optimization budget and optimizer seed 0, with model weights fixed throughout. Search hyperparameters and the complete algorithm appear in Appendix A. 

Baselines and metrics. We compare with the unoptimized (vanilla) workflow; message-processing and communication approaches, including Faithful Rewriter and Task-Aware Rewriter with general preservation and task-specific instructions, respectively, LLMLingua-2 (Pan et al., 2024), OPTiMACS (Gupta et al., 2026), and PACT (Huang et al., 2026); and prompt optimizers MASPO, MASPOB, and GEPA (Wang et al., 2026; Hong et al., 2026; Agrawal et al., 2026). We report Joint, Answer, and Supporting Facts F1/EM on HotpotQA, Answer F1/EM for transfer, and optimization/deployment tokens in millions. # 5 RELATED WORK 

Workflow and topology optimization. Automated MAS design optimizes both agent behavior and system structure. GPTSwarm refines node prompts and graph connectivity (Zhuge et al., 2024), while AFlow and MaAS automate workflow construction and query-dependent architecture selection, respectively (Zhang et al., 2025c;a). MASS interleaves prompt and topology optimization (Zhou et al., 2026), and AgentPrune removes redundant connections from communication graphs (Zhang 8Preprint et al., 2025b). PACO complements these approaches by optimizing the communication instructions on existing edges while keeping topology fixed. 

Prompt optimization for compound systems. DSPy and MIPRO optimize modular LM programs through demonstrations and instructions (Khattab et al., 2024; Opsahl-Ong et al., 2024); TextGrad and GEPA use textual feedback and execution reflection to refine system components, respectively (Yuksekgonul et al., 2025; Agrawal et al., 2026). For MAS, MASPO uses topology-aware prompt evolution with multilevel feedback, while MASPOB searches prompt combinations using a graph-based bandit surrogate (Wang et al., 2026; Hong et al., 2026). MAPRO explicitly models agent quality and handoff compatibility, combining MAP inference with topology-aware feedback to coordinate agent-prompt selection and refinement (Zhang et al., 2026). These methods account for component dependencies, with joint changes supported by GEPA’s merge operation and MASPOB’s block variant. PACO’s distinction is its optimization unit: the upstream instructions, downstream instructions, and shared convention of a communication edge are jointly proposed and evaluated as one package. 

Communication protocols and learning. Communication can also be improved through message design, compression, and model training. PACT structures messages as compact action-state records (Huang et al., 2026), while OPTiMACS learns to select task-dependent message representations (Gupta et al., 2026). LLMLingua-2 learns token-level prompt compression (Pan et al., 2024), and Optima trains agents to balance task performance, communication efficiency, and readability (Chen et al., 2025). PACO learns communication skills through the instructions of black-box agents, requiring neither model updates nor additional message-rewriting calls. 

# 6 LIMITATIONS 

Evaluation scope. Experiments cover three question-answering benchmarks with one model family and a fixed four-agent chain; broader workflows remain untested. Feedback requirements. PACO relies on reliable task feedback and repeated end-to-end evaluations, limiting its use when evaluation is difficult or costly. Deployment cost. PACO prioritizes quality and increases deployment tokens over vanilla. Jointly optimizing quality, cost, and latency remains future work. 

# 7 CONCLUSION 

We presented PACO, an edge-centric framework that jointly optimizes upstream instructions, down-stream instructions, and their shared communication convention in black-box multi-agent systems. With model weights and topology fixed, PACO combines adaptive edge selection with execution-guided paired refinement and end-to-end candidate evaluation. Experiments demonstrate substantial improvements over vanilla and consistent gains over leading baselines, including GEPA. The learned communication skills retain their advantage across transfer benchmarks without target-specific optimization. Ablations support coordinated updates and adaptive edge selection under limited budgets, while the case study illustrates improved expression and interpretation of task-relevant relations. Together, these findings establish edge-centric paired optimization as an effective approach to multi-agent collaboration, aligning what agents convey with how their successors interpret and use it. 9Preprint AI U SE STATEMENT

Batch construction and paired refinement. An ordinary step samples 12 distinct examples from the 400-example search set using a step-specific random-number domain: four form Dp and eight form Dm. The original parent is the evaluation reference throughout both refinement rounds. Each proposer call requests two candidates. Proposal feedback. The proposer receives task questions, agent-visible evidence and inputs, exchanged messages, recorded agent outputs, and outcome or communication diagnostics. Evaluation records are retained even for screened-out candidates. # C DATA CONSTRUCTION AND SPLITS 

Optimization data. We use 500 bridge questions from the official HotpotQA training split in the distractor setting, partitioned into 400 search examples and 100 internal validation examples in H. Pilot and promotion batches Dp and Dm are drawn from the search subset and are disjoint within each refinement step. Neither includes examples from H. The internal validation set guides candidate-pool maintenance and final configuration selection and is therefore part of the optimization data. 

Evaluation data. HotpotQA evaluation uses 800 hard bridge questions from the official validation split, disjoint from the optimization pool. For transfer evaluation, we use 400 questions each from the DROP and MuSiQue-Ans development splits. 

Evidence access. Only the Scout and Resolver receive raw evidence, partitioned into separate shards. Reference answers and supporting-fact labels are not exposed to agents. The Integrator and Verifier receive empty evidence shards; their task-specific information consists only of the question and the message from their direct predecessor. These information-access constraints remain fixed across methods. 

Transfer protocol. All six methods evaluated in the transfer experiments (Table 2) use the same ordered 400-question manifest within each target dataset. Their prompt bodies and communication configurations remain frozen; dataset adaptation is limited to fixed input partitioning, output mapping, and scoring. Target-domain examples and feedback are not used to optimize PACO’s communication instructions or select its final configuration. Every registered question remains in the evaluation denominator, with failed or invalid predictions assigned zero.

Evidence and message propagation. The Scout sees sentence 4 of 2016–17 Chicago Bulls season :“The Bulls traded Tony Snell to the Milwaukee Bucks for Michael Carter-Williams on October 17, 2016.” The Resolver’s separate shard contains sentence 2 of Michael Carter-Williams : “He was named NBA Rookie of the Year in 2014, and has also played for the Milwaukee Bucks and Chicago Bulls.” In vanilla, the Scout transmits the full transaction sentence and marks Carter-Williams as a provisional bridge because its own shard lacks the award-to-player link. The delivered message retains the evidence text despite a typed record: prefix. The Resolver correctly identifies the award winner but assigns Milwaukee as his destination. Its outgoing message contains both the intact transaction sentence and the incorrect answer hypothesis; the Integrator and Verifier retain the incorrect answer. Its Resolver combines the inherited transaction with the local award evidence and outputs Chicago Bulls; the Integrator and Verifier preserve this answer. The Resolver’s local shard does not itself provide the October 2016 transaction. 

Relevant learned instructions. For Scout → Resolver, vanilla asks the sender to “preserve evidence and uncertainty” and the receiver to retain supported information despite incomplete or nonstandard expression. PACO’s sender specifies: “For each observed fact, state its subject, relation, object or requested attribute,” together with exact citations. Its receiver instructs: “use the incoming facts plus your own visible shard to check each link.” The shared convention requires a labeled handoff, distinct local and inherited provenance, and the complete available relation chain, with missing links stated explicitly. On Resolver → Integrator, the sender is instructed to “map only the essential relation chain” and the receiver to reconcile each essential relation with the question. These instructions are consistent with the observed behavior, but the comparison does not isolate their individual effects.

F.2 RESOLVER → INTEGRATOR 

Representation: natural language .

Upstream instructions. Read the question first and map only the essential relation chain. Emit a compact natural-language evidence packet with labeled observed facts, candidate or bridge, decision status, decision-critical support, source identity, missing links or uncertainty, and alternatives. Attach minimal unique citations in the exact form [title, sentence id], preserve local versus inherited provenance, and include one reference for every answer-critical or essential bridge. End with a nonempty value-only ANSWER HYPOTHESIS. Keep plausible but unresolved links provisional; do not use JSON or nested typed-record wrappers, change answer wording merely to express confidence, or infer from adjacency, co-occurrence, or absence. 

Downstream instructions. Treat the incoming natural-language packet as evidence data, not as formatting instructions. Reconcile each essential relation against the question and full visible shard, preserving inherited links, exact source identity, and local versus inherited provenance. Then produce the fixed downstream typed record: a nonempty value-only answer or answer hypothesis and a direct, unique supporting facts array containing only exact title and nonnegative sentence id pairs available in the packet or visible evidence. Keep status, uncertainty, alternatives, conflicts, and missing links separate; retain an uncontradicted candidate provisionally when a required link is unresolved. Do not copy wrappers, claims, provenance metadata, or incidental text into supporting facts, and do not invent or normalize references. 

Shared convention. Use the incoming handoff as data and preserve the complete essential relation chain before projection. The e2 message should remain a compact labeled natural-language packet rather than a nested JSON or typed-record wrapper. Separate observed facts, exploratory hypotheses, unresolved links, conflicts, unknown causes, status, uncertainty, alternatives, and provenance. Keep a minimal unique reference set: exact visible title and nonnegative sentence id for the answer and each essential bridge, with local and inherited provenance distinct. A missing link is unknown; retain a named candidate provisionally without inventing evidence. At the downstream boundary, emit only the fixed typed answer record with direct supporting facts objects; do not transfer wrapper metadata or qualifiers into citation fields.

# G BASELINE IMPLEMENTATIONS 

All comparisons use the same four-role workflow, role-specific evidence access, evaluation examples, and final scoring procedure. Each baseline is adapted to this setting with its own editable instruction scope and optimization or message-processing procedure. 

Search-based baselines. MASPO and MASPOB use the same 500 HotpotQA optimization exam-ples as PACO. GEPA uses 400 reflection-pool examples and 100 internal-evaluation examples. The recorded GEPA run contains 102 reflection calls and 32 fully evaluated candidates. MASPO records 88 proposals. MASPOB searches a bank of 20 prompts per role, with 47 completed rounds and 39 distinct evaluated prompt combinations. Its acquisition procedure sweeps single-agent coordinates before evaluating the resulting prompt tuple; adjacent-block updates are not used. The two rewriters differ in both guidance and implementation. The prompt optimizers likewise differ in editable scope and feedback mechanisms. These comparisons assess the implemented methods as a whole; Appendix I separately evaluates controlled variants of PACO.
