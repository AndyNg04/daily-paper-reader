Abstract: Proactive robots should anticipate user needs and provide assistance before being explicitly asked. A straightforward approach is to infer human in-tentions from commonsense knowledge, but the same observed behavior can im-ply different needs across users, potentially leading to unwanted assistance. We observe that everyday routines in the real world exhibit recurring patterns, so learning these patterns can reduce ambiguity in proactive decisions. Based on this, we propose a memory-based agentic framework in which a VLM task pre-dictor reads a Procedural Assistance Memory (PAM) alongside the current ob-servation to decide when to assist and what task to perform, and a VLA ex-ecutor performs the predicted task. PAM is structured as a finite-state machine over activity phases, per-state assistance rules, and event-driven transitions; a re-flection VLM revises PAM from each day’s interaction trace without weight up-dates or retraining. In our 5-day desk-assistance evaluation, memory-free base-lines remain conservative, with limited recall on proactive tasks. Our system im-proves consistently with accumulated experience, achieving the highest preci-sion, recall, and F1 and reducing first-fire delay from approximately 5 seconds on Day 1 to 1 second by Day 5. Our approach also adapts to changes in the user’s routine through continued memory reflection, recovering from memory– routine misalignment after a single memory update. The project page is available at https://DAVIAN-Robotics.github.io/PAM .

Keywords: Proactive Robot, Agentic Framework, Self-Evolving Memory 

## 1 Introduction 

A truly useful assistant in everyday life does not only respond to requests, but also anticipates when help would be valuable. This may involve handing over an object at the right moment, putting away an item after it has been used, or preparing something that will be needed in the next step. By contrast, robot assistants are still commonly evaluated as systems that execute explicit user com-mands [1, 2]. For robots to play the role of capable assistants in household, and home-office settings, they must move beyond waiting for instructions and learn to recognize when intervention would be helpful. This has motivated growing interest in proactive robot assistance : robots that infer when help may be useful and act in advance of explicit commands. One line of work in proactive robot assistance predicts task progress in structured sequential tasks [3–5]. However, these approaches are largely confined to robots that perform a single task by following a fixed protocol (e.g., chair assembly), and are ill-suited to generalist robots tasked with open-ended housekeeping. Recently emerging generalist Vision-Language-Action models (VLAs) [1, 2, 6, 7] may appear to offer an alternative, but robotics datasets remain scarce across the diverse scenarios such settings demand. In response, recent work has adopted a System 1–2 design [8] that explicitly separates a high-level reasoning module from a VLA that executes atomic tasks [9–12]. This separation simplifies learning, since the VLM decides when and what to help with while the VLA need only carry out the prescribed action. We adopt this structure, which in turn places the burden of proactivity squarely on the high-level VLM. The central challenge, then, is accurately predicting human intention at the high level [13], and recent approaches leverage pretrained, large-scale VLMs to do so in open-ended settings [14–16]. Yet zero-shot prediction remains unreliable when the same observable behavior corresponds to different desired outcomes across users: one person setting out a mug wants coffee, another wants hot water for tea (Fig. 1). A fixed, pretrained predictor cannot resolve such ambiguity, because the missing information is not in the scene but in the individual user’s habits. Crucially, this missing information can be learned during deployment. In housekeeping settings, an individual’s behavior is highly repetitive, so even a handful of past interactions reveal stable prefer-ences, and corrective feedback gathered once can be reused whenever a similar situation recurs. This suggests that a proactive robot should not treat each deployment as zero-shot, but should accumulate experience about its specific user over time. We therefore investigate a test-time learning approach for the high-level VLM, building a robot that personalizes quickly from few interactions, continues adapting after deployment, and carries user feedback forward into future behavior. To this end, we introduce Procedural Assistance Memory (PAM), a continually updated deployment-time memory that records when assistance is needed and what assistive task should be issued for a particular user. PAM structures this memory as a finite-state machine over the user’s activity, where states represent activity phases, transitions represent progress between phases, and per-state assis-tance entries store the assistive opportunities associated with each phase. In our five-day scenario, the user repeatedly performs a daily activity; PAM is updated across these days so that the robot can provide increasingly appropriate assistance. Our contributions are threefold: 1. We propose a memory-based agentic framework for proactive robot assistance. By condition-ing the high-level VLM on user-specific routine context, it decides both when to assist and what 

task to issue without explicit user requests. 2. We propose Procedural Assistance Memory (PAM), a memory following a finite-state-machine structure with activity phases, transitions, and per-state assistance entries. It uses user and activity context to reduce ambiguity in assistance needs. 3. We develop a self-evolving memory loop whose reflector revises PAM offline after each day using observed behavior and user feedback. 2.1 Vision-Language-Action Models 

Robot manipulation has advanced through visuomotor imitation-learning policies [17, 18] and gen-eralist VLAs [1, 2, 6, 7], with subsequent work exploring chain-of-thought reasoning [19–21], spa-tial grounding [22, 23], and world-model predictions [24–26]. However, jointly optimizing action execution and high-level reasoning in a single network causes the two objectives to compete under limited robot data. In response, recent work adopts a System 1–2 design [8] that explicitly separates a slow reasoning module from a fast action executor [6, 9–12]. The reasoning module interprets the scene and reasons about how to solve the task, while the executor generates low-level actions for robot control conditioned on the high-level outputs. We build on this division of roles, using a VLM to predict proactive tasks and a VLA to execute the selected atomic skills. 

2.2 Proactive Assistance in Embodied HRI 

A prominent line of work on proactive robots studies assistance in structured sequential tasks, where the human activity is already organized into known subtasks. In these settings, robots estimate task progress or subtask completion to provide help at the right moment [4, 5], such as handovers in assembly [3] or ingredient delivery in cooking [27]. This direction is especially effective when the task sequence, progress measure, and assistance opportunities are known in advance. Another line of work models object usage patterns in daily environments to anticipate future assistance needs [28– 30]. These methods move beyond single structured tasks, but they typically require substantial in-teraction logs or curated observations for training, limiting their flexibility across diverse everyday routines and rapidly changing user behavior. With the recent progress of foundation models, proactive assistance has begun to move toward more general intent inference. Some systems rely on non-verbal cues such as visual scene changes [14], human-object interactions [31, 32], or gaze [33, 34] to infer assistive intent, while others draw on verbal cues such as indirect instructions [16], speech [15], or dialogue [35, 36]. However, intent in-ference from momentary cues alone remains ambiguous: the same cue can imply different assistance needs depending on the user, context, and activity history. We address this by conditioning the proac-tive decision on a user-specific memory accumulated across days, so that assistance is grounded not only in the current cue but also in how this user has typically acted and been assisted. 

2.3 Evolving Memory for Test-Time Adaptation 

Recent LLM-agent systems use external memory to support test-time adaptation without weight updates, allowing an agent to accumulate and reuse experience across episodes. These works span verbal self-reflection [37], reusable skill libraries [38], workflow or experience extraction [39, 40], and long-term memory [41, 42]. However, their memories are generally designed for text-centric agents, games, or instruction-following tasks, rather than for deciding when a robot should proac-tively assist during an evolving human activity. PAM organizes assistive opportunities into activity phases, per-state assistance entries, and transitions, preserving the context in which each opportunity arises. The task predictor uses this context to decide when assistance is needed and what assistive task should be issued given the user’s current activity and learned routine. 

## 3 Method 

Our goal is to learn and store a user’s routine in memory, then use it to decide when to assist and what task to perform in real time. The system should also adapt quickly to routine changes without retraining. To this end, we design a proactive assistance system built around Procedural Assistance Memory (PAM) (Fig. 2). A VLM task predictor uses observations and PAM to predict whether assistance is needed and, if so, selects a task for the VLA executor to perform. 3.1 Real-Time Task Prediction and Execution via System 1–2 Architecture 

Our task predictor serves as System 2, selecting assistive tasks without task-specific user instruc-tions. At each 1-Hz step, it receives the latest W video frames, PAM as text, and the fixed instruc-tion, “Proactively help the user before they ask.” It uses the routine stored in PAM to interpret the observations and outputs either a task expressed in natural language or NO_ACT . Explicit thinking mode is disabled for real-time inference. The predicted task is passed to the VLA executor, which serves as System 1 and generates low-level robot actions. For example, the predictor selects “bring milk” as the user pours cereal. The executor then carries out this task by picking up the milk and placing it next to the user.

The simple solution is a flat list of trigger–action pairs, but this provides limited context for interpreting cues within the user’s routine. For example, an empty bowl on the desk may indicate that the robot should bring cereal when the user is about to eat or put the bowl away when they have finished eating. To reduce this ambiguity, we orga-nize PAM using a finite-state-machine (FSM) structure: states describe activity phases, per-state trigger–action pairs link cues to assistive tasks, and transitions specify the events that connect phases (Fig. 3). Transitions cap-ture observable changes in the activity; for instance, pick-ing up a spoon indicates the shift from meal preparation to eating. A trigger should occur before the user begins an action that the robot can perform for them. For example, when the user sits down holding an empty bowl, the robot brings cereal before the user fetches it. PAM is serialized as structured text (e.g., JSON) in the predictor’s prompt. The memory provides routine con-text, while the VLM selects assistive tasks. The VLM reads all state descriptions, trigger–action pairs, and transitions alongside recent observations. The predictor uses PAM as contextual guidance to assess whether assistance is appropriate given the current observations. It selects a task only if it is immediately executable. 3.3 Offline Memory Reflection and Update 

At the end of each day, a memory reflector updates PAM offline with reasoning enabled. It receives sampled frames from the day’s video, the previous PAM as text, a summary of the day’s action history, and user feedback when available. As illustrated in Fig. 2(b), the recording includes actions that the user performed without robot as-sistance. The reflector examines these segments to identify missed opportunities and infer recurring patterns. For example, seeing the user bring out an empty bowl and then pour cereal can lead it to infer that the robot should bring cereal when the user brings out an empty bowl. It adds the re-sulting assistance rule to PAM and revises existing states, rules, or transitions when observations or feedback indicate a change in the routine. The reflector returns the updated PAM for use on the following day. PAM remains fixed during each day; adaptation occurs through these daily revisions. The prompts used for the task predictor and memory reflector are provided in Appendices E and F. 

## 4 Experiments 

In the following sections, we aim to resolve the following research questions: 

RQ1. Does PAM improve proactive task prediction over memory-free baselines? (Section 4.2) 

RQ2. Does structuring memory as an FSM yield greater improvements across days than a flat list of rules? (Section 4.2) 

RQ3. Does continued reflection enable adaptation to changes in the user’s routine? (Section 4.3) 

RQ4. Does the System 1–2 decomposition improve task execution success compared to monolithic VLAs? (Section 4.4) 

4.1 Experimental Setup Tasks. We evaluate proactive assistance in a morning desk routine (Fig. 4). The user arrives at the desk carrying an empty bowl, sits down, pours cereal and then milk into the bowl, and eats breakfast. After eating, the user sets the empty bowl aside and starts working on a laptop, then wipes their mouth with a wet wipe, leaves the used wipe on the desk, and eventually leaves the desk. To assist the user throughout this routine, the robot must perform six proactive tasks, namely (T1) deliver cereal (Cereal →Person), (T2) carry over milk (Milk →Person), (T3) place back cereal (Cereal →Storage), (T4) place back milk (Milk →Storage), (T5) place back the empty bowl (Bowl →Storage), and (T6) throw away the used wet wipe (Used wet wipe →Trash). The tasks include both preparing items for the user’s next activity and clearing items after use. Thus, the same objects can require different robot actions as the routine progresses, making the timing of assistance part of the task. We sample frames from the recorded routine videos at 1 fps and label each frame with the task that the robot should perform to assist the user. We use another scenario to evaluate adaptation to routine changes in Section 4.3, with details of this scenario provided in Appendix D.1. 5Figure 5: Multi-day proactive task prediction (Days 1–5). Memory-free baselines show limited T1–T6 recall overall, while Ours (FSM Memory) consistently improves across days, achieving the highest F1 and reducing first-fire delay from ∼5 s on Day 1 to ∼1 s by Day 5. 

Evaluation protocol. We formalize proactive task prediction as a per-frame classification prob-lem. Importantly, the label set comprises not only the six tasks above but also a NO_ACT class indicat-ing that no assistance is needed. We report precision, recall, and F1 score per class (the six proactive tasks and NO_ACT ) along with their macro averages. We also report the first-fire delay, measured from the time at which proactive assistance should be provided until the model first predicts the corresponding task. If the model does not predict a task, we instead measure the delay from the time assistance should be provided until the user completes the task without robot assistance. Together, these metrics measure whether assistance is appropriate and whether it is predicted early enough to be useful. To assess the effectiveness of our PAM, we conduct a multi-day evaluation over 5 days (Fig. 9), in which the PAM persists across days and is updated from feedback from previous days. 

Implementation details. We use Qwen 3.5 [43] as the VLM for both the task predictor and the reflector. The reflector runs once at the end of each day with thinking mode enabled to reason over the day’s observations and revise PAM for use on the following day. The task predictor runs with thinking mode disabled to support timely assistance. At each prediction step, it predicts a task or 

NO_ACT from a window of W =5 frames sampled at stride 2 from the 1 fps stream. Each reflector call takes approximately 1 minute, while each task predictor call takes approximately 1 second. For the executor, we collect 10 demonstrations per task and use them to finetune π0.5 [2]. Generation hyperparameters are fixed across all conditions and reported in Appendix A.2. 

Baselines. For the proactive task prediction baseline, we provide following: • LIT [27]. Builds a task graph over detected objects and estimates the current progress along the graph to predict the next task. This represents structured, progress-tracking proactivity. • Event-driven VLM [14]. Predicts the next task only when a scene change is detected via optical flow, by comparing the pre- and post-change frames. This represents reactive, change-triggered proactivity without any cross-day memory. • Zero-shot VLM . A state-of-the-art VLM that predicts the next proactive task directly from the current observation, without any adaptation. This isolates the benefit of our test-time memory against a strong but static predictor. • Ours w/ List Memory . A variant of our framework that replaces the FSM-structured memory with a flat list of trigger-action pairs accumulated over deployment, while keeping the rest of the pipeline identical. 4.2 Proactive Prediction across Memory Designs Effectiveness of Memory. As shown in Fig. 5, baselines without memory (LIT [27], Event-Driven [14], Zero-shot VLM [43]) predict conservatively: lacking prior knowledge of the user’s routine, they default to NO_ACT whenever the observation is ambiguous, which inflates NO_ACT re-call but suppresses proactiveness on T1–T6. LIT and Event-Driven rarely fire any proactive task, yielding near-zero recall, and the Zero-shot VLM plateaus from Day 2 onward with no mechanism to internalize recurring patterns. All three remain essentially flat across the five days, confirming that without memory there is no path from repeated exposure to better proactive behavior. In contrast, our memory-based variants (Ours w/ List, Ours w/ FSM) leverage repeated exposure to improve over the five days, though to different degrees, as we analyze next. 

Ablation of Memory Design. Among the two memory designs, Ours w/ List Memory saturates early, since the flat list offers no abstraction over recurring states as it grows. In contrast, Ours w/ FSM Memory consistently improves across days, achieving the highest precision, recall, and F1 on T1–T6 while reducing first-fire delay from roughly 5 seconds on Day 1 to about 1 second by Day 5. This shows that the gains come from the FSM structure itself, not simply from adding memory. The trade-off is that FSM Memory’s eagerness to act lowers its NO_ACT recall relative to the conservative baselines, although a correspondingly higher NO_ACT precision keeps its NO_ACT F1 on par with the others. 4.3 Memory Adaptation and Evolution Adaptation to Routine Changes. When a user’s routine changes, previously learned assistance rules may become inappropriate, making rapid adaptation important. Our method addresses this by updating PAM through reflection without retraining the models. We refer to the cereal routine shown in Figure 4 as Scenario A. Scenario B involves a different routine (Figure 20). For example, the user takes vitamins instead of eating cereal. We evaluate how effectively and quickly PAM adapts over five target days when a user who has followed Scenario A suddenly switches to Scenario B. Both A-Frozen and A-Evolving begin with Scenario A’s Day 5 memory. A-Frozen keeps this mem-ory unchanged, whereas A-Evolving updates it through reflection at the end of each day in Scenario B. Figure 6 compares these conditions with Scratch-Evolving, which builds memory from scratch in Scenario B, and the Zero-shot VLM, which uses no memory. On Day 1, A-Evolving has lower task recall and F1 than the Zero-shot VLM, suggesting that memory from the previous routine can initially cause confusion in predicting proactive tasks in the new scenario. After a single reflection at the end of Day 1, however, its recall and F1 reach levels comparable to Scratch-Evolving on Day 2. They remain close over the subsequent days, while A-Frozen stays below the Zero-shot VLM. First-fire delay also decreases with continued reflection. These results show that PAM can quickly adapt an existing memory to a different routine, recovering from the initial mismatch after one memory update. Results for the reverse B →A experiment are provided in Appendix D.2. 

Qualitative Memory Evolution. We qualitatively investigate the FSM-based Procedural Assis-tance Memory (PAM) in Fig. 7, which highlights both the efficiency and flexibility of our memory structure. Comparing Day 3 and Day 5, the FSM-based PAM becomes increasingly accurate: trigger-action pairs that were missing on Day 3 are recovered on Day 5, with each state capturing its full set of triggers and actions ( e.g ., the pair “person pours cereal” → “milk to person” is added). Our FSM-based PAM also adapts dynamically when the user’s routine changes. For instance, even when the user sits down with a bowl as before, taking vitamins before eating the cereal that the robot has just delivered causes the transition “person sits down” → “cereal to person” to be revised, after reflection, to “person sits down” → “vitamin to person”.

## 5 Conclusion 

We introduced Procedural Assistance Memory (PAM), an FSM-based memory that personalizes proactive robot assistance through daily reflection without weight updates. Across five evaluation days, PAM improves proactive prediction and response timing, while its structured memory adapts to changes in the user’s routine. Ablations demonstrate the benefits of FSM structure and contin-ued reflection, and the System 1–2 decomposition improves task execution over monolithic VLAs. These results support structured, evolving memory as a practical approach to longitudinal robot personalization. We hope this work encourages further research on proactive robot assistance. 

Limitation. Two failure modes recur in our analysis. First, FSM Memory occasionally fires when the user briefly handles a learned trigger object without committing to that step, which lowers its 

NO_ACT recall (Fig. 5); in such genuinely ambiguous situations the right behavior is often to ask the user rather than to act, but soliciting clarification lies outside our current framework. Second, due to the limited capacity of current open-source VLAs, our evaluation is restricted to seen scenarios rather than novel objects, layouts, or users; recent advances in generalist VLAs [44–50] suggest that scaling to broader scenarios is an increasingly feasible next step. 9Acknowledgments

## A Detailed Experimental Setup 

A.1 Evaluation Dataset and Annotation 

To examine how proactive-task prediction performance evolves with repeated exposure to a user’s routine, we record five days of video of a single user performing the same canonical desk routine (Fig. 9). Each day follows the same high-level sequence: the user arrives at the desk with a bowl, pours cereal and then milk into the bowl, eats the meal, sets the empty bowl aside while switching to laptop work, wipes their mouth with a wet wipe and leaves it on the desk, and finally leaves the desk. The timing of individual actions and the visible desk state vary naturally across days. These recordings allow us to evaluate whether repeated exposure to the same routine improves task prediction and enables earlier assistance. 

Per-frame annotation. We treat proactive-task prediction as a per-frame classification problem and therefore label every evaluation frame. Each day’s recording lasts roughly 3.5 to 4.5 minutes; we uniformly sample at 1 fps and obtain 197 to 270 frames per day after excluding deleted frames, for a total of 1,146 annotated frames across the five days (Tab. 2). The authors manually assign one label per sampled frame from the following seven categories: the six proactive tasks T1–T6 (deliv-ering cereal, delivering milk, putting away cereal, putting away milk, putting away the empty bowl, throwing away the used wet wipe), and NO_ACT for frames where no intervention is appropriate. A frame receives a task label when, given the current scene and the user’s ongoing behavior, that task is the most natural proactive intervention; all other frames are labeled NO_ACT . The resulting labels provide the ground truth for the proactive task prediction experiments on this routine, and we will release the annotation tool together with the dataset.

A.3 Training and Deployment for VLAs 

All three VLA variants in our study are fine-tuned from the same π0.5 backbone but differ in what they have to learn. In the cereal routine, we consider six proactive tasks: (T1) Pick up the cereal and place it next to the person. , (T2) Pick up the milk and place it next to the person. , (T3) Pick up the cereal and place it in the designated storage area. , (T4) Pick up the milk and place it in the designated storage area. , (T5) Pick up the bowl and place it in the designated storage area. , and (T6) Pick up the used wet wipe and place it in the trash can. All teleoperation demonstrations are recorded on the Franka arm at 20 fps with three RGB streams (two back-facing cameras and one wrist camera; Fig. 10). Unlike the VLM stack, all three VLA variants receive all three views as input, including the wrist camera that provides close-up grasp context. 

π0.5 (executor). Our executor executes one task at a time, as instructed by the task predictor. We therefore collect 10 teleoperation episodes per task and fine-tune π0.5 on this set, conditioning each episode on its corresponding instruction taken verbatim from T1–T6. At deployment, the executor is conditioned on the task instruction provided by the task predictor. 

π0.5 (monolithic). The monolithic baseline has no external task predictor and must therefore learn both when to act and what to do inside a single model. To match this requirement, we collect 10 end-to-end teleoperation episodes of the full scenario, in which the user arrives at the desk and proceeds through the routine, and the robot, controlled by an expert teleoperator, performs every proactive task at the appropriate moment without any external instruction. Training and deployment settings. All three VLA variants share the same training and deploy-ment recipe. We fine-tune π0.5 for 50 ,000 optimizer steps with AdamW [52] (betas (0 .9, 0.95) ,

The learning rate is linearly warmed up from 0 to 1 × 10 −4 over the first 1,000 steps and then cosine-decayed over the remaining training steps to a minimum of 2.5 × 10 −6. Training uses NVIDIA B200 GPUs with an effective batch size of 64 and no gradient accumulation. The action head predicts chunks of 50 steps, and at deployment we execute the full predicted chunk before requesting a new one, with 10 denoising steps per chunk. 

A.4 Hardware Setup Robot. We use a Franka Research 3 (FR3) 7-DoF manipulator equipped with the built-in parallel-jaw gripper. Low-level control is provided by the Deoxys real-time controller, which exposes operational-space control of the end-effector. The control loop runs at 20 Hz during teleoperation and deployment. 

Cameras. Three Intel RealSense cameras are used for both data collection and deployment, all streaming RGB at 30 fps and time-aligned to the 20 Hz control loop. Two cameras ( left_back and 

right_back ) are statically mounted behind the robot at table height, framing the desk and the seated user from two angles, while the third camera is rigidly attached to the wrist and looks down toward the gripper. The two back-facing streams are horizontally concatenated to form the input given to the VLM stack, whereas the VLA variants additionally consume the wrist stream as a third image channel. 

Teleoperation interface. Teleoperation demonstrations are collected with TactAR [53], a Meta Quest 3-based VR teleoperation interface. ## B Per-task Results of VLM Proactiveness 

Memory-augmented variants improve on average across days. Both memory variants improve their average F1 across T1–T6 from Day 1 to Day 5, although gains vary by task (Fig. 11). Memory-free baselines (LIT [27], Event-driven [14], and Zero-shot VLM [43]) achieve more limited perfor-mance overall. 

Memory helps disambiguate assistance. Memory is particularly helpful on T2 (Milk →Person) and T3 (Cereal →Storage), where assistance depends on the user’s habitual pairing or the routine’s progression. For example, observing cereal being poured does not by itself establish that this user needs milk next. The gap is smaller on T1 and T6, whose immediate cues are more informative. 

FSM structure helps most on storage actions. FSM Memory provides substantial gains over List Memory on storage tasks T3–T5. Organizing rules by activity phase helps distinguish simi-lar cues and select the appropriate moment to put items away. This context is less explicit in List Memory, where routine information must be encoded in individual trigger strings. FSM Memory has lower NO_ACT recall but higher NO_ACT precision than List Memory, resulting in comparable F1 and reflecting the trade-off discussed in Section 4.2.

## C Detailed Analysis of Memory Update 

C.1 Effectiveness of Memory Evolution 

This experiment isolates the contribution of the self-evolving update itself. All three conditions share the same inference module and differ only in how the memory changes over time: Self-Evolving (Ours) refines the memory with the reflector at the end of each day, Frozen @ Day1 builds the memory once and applies that Day-1 snapshot unchanged thereafter, and Zero-shot VLM carries no memory at all. 

Continued reflection is what sustains improvement. On metrics averaged over T1–T6, self-evolving memory improves overall from Day 1 to Day 5 (Fig. 12). Frozen memory also improves prediction over the Zero-shot VLM once the initial memory is available, but receives no further updates. Its performance varies across days without incorporating new experience. Continued re-flection yields larger gains and higher final precision, recall, and F1 than either frozen memory or the memory-free baseline, supporting the benefit of updating memory rather than only building it once. 

Faster and better-timed assistance. The same trend appears in first-fire delay: our self-evolving memory reduces the delay from roughly 5 seconds on Day 1 to about 1 second by Day 5, while the frozen memory plateaus near 2 seconds and the zero-shot VLM stays high and erratic. As the reflec-tor adds and refines triggers, the predictor identifies assistance opportunities earlier in the routine. The conditions maintain comparable NO_ACT F1, although the self-evolving variant’s lower NO_ACT 

recall reflects a trade-off between proactiveness and false alarms. 

Qualitative Analysis of Memory Update Fig. 13 traces the FSM memory after each day’s reflec-tion for one run, culminating in the instance shown in Fig. 14. Day 1 installs the skeleton: four states (meal_preparation → eating → working → leaving ) with two core pairs, bring-cereal and bowl-storage. Day 2 adds the bring-milk pair to meal_preparation and broadens the bring-cereal trigger with an or -clause. Day 3 adds the put-cereal-back and put-milk-back pairs to the same state, and broadens the bring-milk and bowl-storage triggers. Day 4 introduces a new cleaning_break 

state with the wet-wipe pair and a working ↔cleaning_break loop, and further broadens both put-away triggers. Day 5 introduces no new pairs or states; the reflector only finishes broadening the 22 remaining triggers, so the trigger lines grow while the actions and FSM topology stay fixed, yielding the final memory in Fig. 14. 

C.2 Reasoning Trace of Memory Update 

As shown in Figure 2(b), the reflector reviews the day’s video and current FSM memory at the end of each day to propose updates. To illustrate the reflector’s reasoning, we present three trace excerpts showing three types of memory update: ( i) the introduction of a new (trigger, action) pair, ( ii )the extension of an existing trigger to fire earlier, and ( iii ) the introduction of a new state. 

Introducing a new (trigger, action) pair. Figure 15 shows the reflector building the initial memory from the first day’s video. After laying out the meal-preparation rules, the reflector wants to add a rule for putting the cereal bag back into storage but recognizes that the robot must not handle the bag while the person is still holding it. The reflector therefore searches for an indirect cue and selects “Person reaches for the milk bottle”: the person is reaching for the milk, suggesting an opportunity for the robot to put away the cereal bag. The reflector explains the intended assistance (“You are getting the next ingredient (milk), so I will tidy up the previous one (cereal)”) and adds the new pair to the meal_preparation state. 

Extending an existing trigger. Figure 16 shows the same memory three days later, after the re-flector has watched another video in which the human put the cereal bag away themselves. The cereal-storage (trigger, action) pair already exists in meal_preparation . The reflector notes that the desk-placement cue was absent because the human put the bag directly into storage without first setting it on the desk. It then inspects the timeline and identifies “Person finishes pouring ce-real” as an earlier candidate cue to append with or . The existing trigger is extended; no new pair is created. 

Introducing a new state. The reflector occasionally restructures the FSM topology itself. Fig-ure 17 shows the reflector debating whether to keep wet-wipe disposal inside the working state or to introduce a separate phase. It first considers folding the wiping action into working but rejects this because the routine instruction asks for a new state when the video reveals a distinct phase. It then considers a loop connecting working and cleaning_break and checks that the state IDs remain unique. The resulting layout places the wet-wipe (trigger, action) pair in the cleaning phase, helping the predictor distinguish typing after cleaning from typing at other times and limit mistimed disposal. These examples show how the reflector adds assistance rules, broadens triggers, and revises activity phases while preserving their routine context. Why the FSM structure helps. FSM Memory orga-nizes (trigger, action) pairs into activity phases connected by transitions (Figure 14). At inference, the predictor uses this structure as context to interpret the current scene and anticipate how the routine may progress. List Memory contains no explicit phase struc-ture, so the predictor must infer routine context from the trigger descriptions and current observations. 

Phase-dependent interpretation of the same cue. 

An illustrative example of this appears during the eat-ing phase (Figure 21). Throughout the meal the predic-tor sees the user sitting at the desk eating cereal with a spoon, with the cereal bag and milk bottle already re-turned to the storage area earlier in the routine. Both predictors describe the scene correctly as “person hold-ing a bowl and a spoon, eating cereal, with milk and ce-real already in storage.” The FSM predictor, reading the memory shown in Figures 14 and 18, uses the eating 

phase, which contains no Milk → Person rule, as con-text and outputs NO_ACT . The predictor reading the List Memory in Figure 19 instead matches the cue “Person holds the bowl” to the Milk → Person ac-tion, whose trigger has been broadened during reflection to “Person pours cereal or finishes pouring cereal or holds the bowl.” It then outputs T2 (Milk → Person) repeatedly, even though the human has already poured the milk and is now eating. The cue “holds the bowl” is insufficient on its own to justify milk delivery. Its interpretation depends on the activity phase and surrounding observations; during eating, it does not indicate that more milk is needed. 

How the over-broadened trigger entered the memory. The reflector’s thinking trace illustrates how the trigger was broadened. After observing that the human had fetched the milk without robot assistance, the List reflector considered additional cues and appended “Person holds the bowl” to the Milk → Person trigger. The trace checks that the trigger and action concern different objects (“trigger object (bowl) ̸ = action object (milk), valid”), but does not explicitly distinguish meal preparation from eating. Associating the milk-delivery rule with meal_preparation gives the FSM predictor context for distinguishing preparation from eating. This context can help limit repeated milk delivery after the meal has begun, although it does not strictly prevent execution outside the assigned phase.
