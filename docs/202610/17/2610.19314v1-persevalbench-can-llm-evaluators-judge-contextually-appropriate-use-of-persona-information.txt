## Abstract 

Large language model (LLM) evaluators are increasingly used to assess personalized as-sistants, yet whether they can reliably judge personalization has rarely been tested. We in-troduce P ERS EVAL BENCH , a benchmark test-ing whether an evaluator can recognize ap-propriate and inappropriate uses of user his-tory. It contains 403 multi-episode scenar-ios where user information should persist, transfer, or cease to apply. The benchmark covers nine controlled error subtypes across three families: under-personalization, over-personalization, and misapplied-state errors. Human audits confirm that generated errors match their intended types and that the pre-scribed uses of user information are reasonable. Across five LLM evaluators, recognition of con-trolled personalization errors remains limited even with the full dialogue history. On the human-evaluated subset, under-personalization shows the largest gap: humans recognize 94.4% of these errors, compared with 63.9% for the strongest reported evaluator. Evaluators often recognize that a response is problematic but reverse the error direction, mistaking failure to follow an applicable preference (UNDER) for use of an inapplicable preference (OVER). Easier evidence access offers little help: high-lighting the relevant history turns raises error recognition only slightly, suggesting that the remaining difficulty lies in judging what role that information should play in the response.

## 2 Related Work 

Personalization and long-term memory bench-marks. Assistant-side personalization bench-marks primarily ask whether models can retain and follow user information across interactions. This includes persona-grounded dialogue (Zhang et al., 2018), personalized generation (Salemi et al., 2024), long-term conversational memory (Maha-rana et al., 2024), preference following over long contexts (Zhao et al., 2025a), long-horizon pref-erence following (Guo et al., 2026), alignment on real dialogues (Xiao et al., 2026), task-oriented personalization (Zhao et al., 2025b), and dynamic or evolving user states (Jiang et al., 2025; Li et al., 2026). A complementary line examines whether models use stored information selectively, including over-personalization (Hu et al., 2026), rational preference utilization (Feng et al., 2026), context-aware preference selectivity (Yoon et al., 2026), and contextually appropriate memory use (Mireshghallah et al., 2025), in the spirit of contex-tual integrity (Nissenbaum, 2004). These bench-marks evaluate the responding assistant, while the competence of the LLM judge used to assess it is generally assumed. 

LLM-as-judge and meta-evaluation. LLM evaluators are widely used for open-ended assess-ment (Zheng et al., 2023; Liu et al., 2023), with dedicated judge models trained for pairwise or fine-grained evaluation (Wang et al., 2024b; Kim et al., 2024a,b; Zhu et al., 2025). Meta-evaluations test whether these judges agree with human assess-ments or recover controlled labels in instruction following (Zeng et al., 2024), reward modeling (Lambert et al., 2025), and knowledge and rea-soning tasks (Tan et al., 2025). This line of work also documents systematic judge biases, includ-ing position and verbosity effects (Zheng et al., 2023; Wang et al., 2024a) and a preference for a judge’s own generations (Panickssery et al., 2024). The matched pairs in P ERS EVAL BENCH are con-strained to comparable factual correctness, task relevance, completeness, specificity, and style (Sec-tion 3.3), leaving these surface preferences little room to determine verdicts: what differs within a pair is the use of persona information. The most closely related evaluator-side work, Personalized Judge (Dong et al., 2024), tests whether an LLM can infer user preferences from persona descrip-tions. PERS EVAL BENCH instead tests whether an evaluator can judge a fixed response’s use of information from a multi-episode history, using matched pairs that isolate under-personalization, over-personalization, and misapplied-state errors. ## 3 PERS EVAL BENCH 

Figure 2 summarizes the benchmark structure: multi-episode histories establish how prior user in-formation should apply, matched responses realize controlled personalization errors, and evaluators judge each candidate response from the dialogue history. We first define the evaluation task and con-trolled scenario specification, then describe how benchmark instances are constructed and human-verified. 

3.1 Task Definition 

As shown in Figure 2 (3), each benchmark instance consists of a multi-episode dialogue history H, a target user request q, and a candidate assistant re-sponse r. Given (H, q, r ), the evaluator assigns one of three verdicts based on how the response uses information from the user history: R IGHT ,UNDER , or O VER . R IGHT uses applicable informa-tion appropriately while avoiding information that should not affect the response. U NDER omits or gives too little influence to applicable information, whereas O VER uses information that should not apply or gives it too much influence. For an error verdict, the evaluator also identifies one primary error subtype. 

3.2 Controlled Scenario Specification 

To make evaluator judgments controlled and inter-pretable, we determine the intended use of user his-tory before generating the dialogue. Each specifica-tion fixes how prior information should affect the target response, what the correct response should do, and one controlled error to introduce. This sep-arates the underlying personalization decision from its natural-language realization. Figure 1 illustrates a re-entry scenario in which an earlier online-only constraint is superseded by an updated hybrid pref-erence. 

Scenario relations. Figure 2 (1) illustrates the three history–target relations. We organize scenar-ios around the three broad ways prior information can relate to a target request in our task-oriented setting: it can remain applicable, transfer to a re-lated task, or cease to apply. Accordingly, re-entry 

tests whether an earlier state remains current, cross-domain transfer whether it carries over and with what priority, and out-of-scope whether seemingly relevant history should instead be ignored. To-gether, these relations cover the core applicability decisions of persistence, transfer, and exclusion. 

Intended use of user information. We then make the intended influence of each user state ex-plicit. Each state is assigned one of three roles for the target response: I GNORE , S UPPORT , or D OMI -

> NATE

The assignment depends on its holder, scope, temporal status, strength, and transferability to the target task. Error interventions. Figure 2 (2) summarizes the response patterns. Given the prescribed role of each user state, a response can depart from correct personalization in three basic ways: give applicable information too little influence, use in-formation that should not apply, or assign influ-ence to the wrong state or at the wrong level. These correspond to under-personalization , over-personalization , and misapplied-state errors, re-spectively, and cover the core deviations from pre-scribed persona use in our setting. The taxonomy is also grounded in prior work on preference follow-ing (Zhao et al., 2025a), selective personalization (Hu et al., 2026; Yoon et al., 2026; Feng et al., 2026), and evolving user states (Jiang et al., 2025; Li et al., 2026). To isolate each failure, every error response dif-fers from its matched R IGHT response by exactly one intervention. Under-personalization includes complete omission (CO), partial omission (PO), and explicit violation (EV); over-personalization includes irrelevant use (IU), scope leakage (SL), and unsupported inference (UI); and misapplied-state errors include stale or superseded use (SS), over-dominance (OD), and underweighting (UW). Misapplied-state errors can support either er-ror direction because they may simultaneously un-deruse one state and overuse another. We there-fore count either U NDER or O VER as recognition for this family. A human-authored compatibility matrix restricts interventions to scenario relations where they form natural violations, with subtype precedence defined in Appendix B.1; Appendix E provides worked examples. 

Evidence realization. Finally, we vary how eas-ily the relevant user information can be recovered without changing the intended personalization de-cision. Holding the scenario relation, state roles, and error intervention fixed, we vary its evidence along two dimensions: form and distance. Evi-dence is explicit when directly stated, implicit when recoverable from a choice, rejection, or compari-son, and accumulated when distributed across mul-tiple turns. 3.3 Benchmark Realization 

We next turn each accepted specification into a natural dialogue and matched response pair, while preserving its predefined personalization logic. 

Planning and verification. To obtain diverse but structured tasks, we expand the 20 domains and service schemas in the Schema-Guided Dialogue dataset (Rastogi et al., 2020) into 48 task types and a pool of 480 concrete task seeds. From this pool, an LLM planner instantiates 456 scenario specifi-cations, each defining the episode goals, states A

and B, target request, candidate options, correct de-cision, error intervention, and evidence placement (Prompts 1 and 2). Before dialogue generation, a verifier checks that each specification realizes the intended history– target relation, makes state applicability recover-able from the history, contains exactly one error intervention, and keeps the matched options com-parable apart from persona use. Specifications that fail these checks are revised and re-evaluated, then discarded if they still do not satisfy the criteria (Prompts 3 and 4). 

Dialogue synthesis. To separate scenario logic from its linguistic realization, a separate generator converts each accepted specification into a natu-ral multi-episode dialogue without changing the predefined states, evidence, or target decision. The dialogue ends with the target request, and we record episode boundaries, the target turn, and evidence turns for each user state as benchmark metadata. These annotations support verification and the con-trolled context conditions in Section 4, but are hid-den from evaluators (Prompts 5 and 6). 

Matched response generation. To isolate the assigned personalization error, we generate a matched response pair from each specification: one R IGHT response and one error response. The RIGHT response follows the prescribed state roles, while the error response receives only the infor-mation needed to realize its assigned interven-tion. Complete omission uses the target request alone, whereas other interventions receive subtype-specific restricted views of the relevant states. The two responses are constrained to remain compara-ble in factual correctness, task relevance, complete-ness, specificity, and style (Prompts 7 and 8). To make each intervention observable, scope leakage and unsupported inference must affect the recommendation, while underweighting must visi-bly reduce the influence of an applicable state. An automated validator checks observability, interven-tion fidelity, and pair comparability, regenerating failed responses with targeted feedback for up to three attempts (Prompt 9). Section 3.4 reports an in-dependent human audit of the resulting responses. 

Coverage. We prioritize coverage of factors that determine contextual applicability rather than ex-haustively crossing all design variables. Each valid relation–intervention combination is instantiated across multiple task types, goals, state configura-tions, and response decisions, with varied evidence form and distance. 3.4 Human Verification 

We conduct three complementary human studies on the same stratified sample of 100 scenarios. They test whether the generated errors realize their in-tended interventions, whether the prescribed use of user information is reasonable, and how well humans perform under the same information avail-able to evaluators. Study 1 uses one annotator pair, while Studies 2 and 3 use a second, disjoint pair. 

Intervention fidelity. Annotators independently judge whether each raw error response realizes its assigned intervention, followed by adjudication. The raw pipeline achieves 88% subtype fidelity. We revise the 12 flagged responses while preserv-ing the dialogue history and matched R IGHT re-sponse, then re-verify them before inclusion in the benchmark. All subsequent human and model eval-uations use this corrected benchmark. 

State-role validation. To validate the prescribed use of user information independently of the con-struction pipeline, annotators assign each user state an I GNORE , S UPPORT , or D OMINATE role without seeing the benchmark assignments. ## 4 Experimental Setup 

Benchmark. Table 2 summarizes the scale and composition of P ERS EVAL BENCH . Each retained scenario pairs one R IGHT response with one con-trolled error response. Of the 456 instantiated sce-nario specifications, 403 were retained after ver-ification and quality control. The construction pipeline uses Claude Sonnet 4.6 (Anthropic, 2026b) for planning, specification verification, dialogue synthesis, response generation, and automated vali-dation. Appendices B.1 and B.3 provide additional benchmark statistics and construction details. 

Evaluators. We evaluate Claude Opus 4.6 (An-thropic, 2026a), Kimi K2.5 (Kimi Team, 2026), GLM-5 (GLM-5 Team, 2026), DeepSeek-V3.2 (DeepSeek-AI, 2025), and Qwen3-32B (Yang et al., 2025). 1

Evaluation settings. We vary three aspects of evaluation. Context: Target Only , Recent , and 

Full provide the target request alone, the preced-ing six turns, and the complete history up to the target, respectively; Full + Gold Highlights marks the annotated evidence turns within the full his-tory, while Gold Evidence Only provides only those turns and the target request in chronological order. 

Formulation: End-to-end directly predicts the ver-dict and, when applicable, the subtype; Evidence-first identifies relevant user states and evidence be-fore predicting the verdict; and State-table first assesses state applicability in a structured table. Unless otherwise stated, we use Full with End-to-end (Prompts 10–12). Protocol: we additionally evaluate pointwise scoring and direct pairwise com-parison over matched responses (Appendix C.5). 

> 1Evaluator-specific results are partially omitted from the public version due to release restrictions.

Metrics. We compute Error Recognition Rate (ERR) over error responses and False Alarm Rate (FAR) over their matched R IGHT responses. An error response counts as recognized when an under-personalization error is assigned U NDER , an over-personalization error is assigned O VER , or a misapplied-state error is assigned either error ver-dict. The last case accepts both directions because the response underuses one state while overusing another. FAR is the percentage of R IGHT responses incorrectly assigned U NDER or O VER . Both met-rics score the three-way verdict only; the elicited subtype label is not scored. We report both metrics because ERR alone can be inflated by an evaluator that predicts an error indiscriminately. For analyses over matched responses, we additionally report pair accuracy, which requires the evaluator to accept the RIGHT response and correctly recognize its paired error response.

Graded applicability. The applicability-type breakdown identifies a second source of difficulty. Evaluators reach lower ERR on graded decisions involving strength or transferability than on cate-gorical boundaries involving holder, scope, or tem-poral status. Beyond finding relevant information, evaluators struggle to determine how strongly and how broadly it should apply. 

5.3 Structured Prompting Changes Verdict Tendencies, Not Judgment Quality 

To test whether structured reasoning improves ap-plicability judgment or merely changes how read-ily evaluators issue error verdicts, we compare three formulations under the same Full context. Evidence-first prompting raises ERR, but also raises FAR. The state-table formulation lowers ERR and generally lowers FAR, shifting evalua-tors toward more conservative predictions. Nei-ther formulation improves error recognition while preserving correct acceptance of R IGHT responses (Table 10). 

5.4 Independent Judgment Remains Difficult Without an Explicit Contrast 

Alternative protocols clarify where the difficulty lies. Pointwise scoring separates R IGHT from error responses in only 63.0% of matched pairs, with 35.9% ties. Direct pairwise comparison reaches 89.0% accuracy with 90.5% order consistency (Ap-pendix C.5), but this setting exposes the two re-sponses side by side and therefore provides an ex-plicit contrast that is absent from the benchmark’s target setting. The high pairwise accuracy thus does not imply that evaluators can reliably judge a response on its own. Moreover, neither protocol identifies the error direction, so neither addresses the U NDER →OVER confusion observed in inde-pendent judgments. These results reinforce that the difficult part is independently determining whether and how a response misuses user history. 

## 6 Conclusion 

PERS EVAL BENCH tests whether evaluators can judge how user history should influence a response. Across 403 scenarios, five LLM evaluators remain unreliable even with full history. The clearest failure is under-personalization: evaluators often detect a problem but reverse its direction, while humans perform substantially better. Easier evi-dence access and structured prompting yield lim-ited gains, whereas pairwise comparison is much easier than independent judgment. These results suggest that reliable personalization evaluation re-quires not only retrieving relevant history, but cor-rectly interpreting its role in the current response. 

## Limitations 

Construction. The benchmark uses LLM-generated dialogues and responses, which may dif-fer from organic interactions or contain residual generation artifacts despite structured verification and human auditing. Restricted-context generation may introduce detectable differences from R IGHT 

responses, and upstream construction still relies on Claude, so broader construction-family effects cannot be excluded. Appendix C.6 provides an additional response-generation robustness check using Mistral Large 3 (Mistral AI, 2025). 

Evaluation scope. Each benchmark response targets one controlled error, although generation can introduce secondary cues and real responses may contain multiple interacting errors. We au-dit secondary O VER cues in under-personalization cases and report robustness analyses after exclud-ing such items (Appendix C.3). Compound errors, however, remain outside the benchmark’s intended scope. We also report ERR and FAR at each re-ported model’s observed operating point and leave confidence calibration to future work. 

Generalizability. The benchmark is English-only and grounded in SGD-derived task seeds, so results may not generalize fully across domains, interaction styles, languages, or cultural norms of personalization.

## C Additional Analyses 

C.1 Evaluation Formulation 

All formulations are zero-shot with no hyperparam-eter search or model selection. Table 10 reports results for the reported evaluators under the three elicitation formulations of Section 5.3. 

C.2 Underweighting Verdict Split 

Evaluator rationales show the two readings behind the direction split on underweighting errors (Fig-ure 3b). Under the deficit reading, the evaluator anchors on the applicable state and observes that the response acknowledges the constraint but then downplays it, yielding U NDER . Under the excess 

reading, the evaluator anchors on the response con-tent and objects to what filled the vacated space: the weakened restatement of the preference no longer matches what the user actually said (read as an un-supported, fabricated preference), or a secondary consideration now dominates the decision (read as over-application of the wrong state), yielding OVER .

C.3 UNDER →OVER Robustness 

We test whether the UNDER →OVER rate re-flects responses that contain a secondary over-personalization error in addition to the intended one. The two Study 3 annotators (Appendix D) in-dependently audited all 130 under-personalization responses, judging for each whether the intended UNDER error is present and whether a secondary OVER error is also present. Excluding every item that either annotator flagged with a secondary OVER error lowers the rate from 26.6% to 21.1%; further requiring both annotators to confirm the in-tended U NDER error leaves 19.5%. The residual confusion is lowest for complete omission (14.3%) and highest for explicit violation (26.4%). A man-ual audit of all 173 main-setting judgments in which an under-personalization error was judged OVER further shows that every rationale cites gen-uine history evidence and errs in judging its applica-bility, scope, or weight; none argues from response wording alone, and none invents a user state. Sec-ondary errors therefore amplify, but do not explain, the direction confusion reported in Section 5.1.

C.5 Alternative Judging Protocols 

Section 5.4 compares the three-way verdict with two common judging protocols, both run on all 403 matched pairs under Full context with the same five evaluators. Pointwise scoring rates each response independently from 1 to 5 for how appropriately it uses the user’s history; the rubric does not men-tion under- or over-personalization and excludes overall response quality. A pair counts as correct only when the R IGHT response receives a strictly higher score than its matched error response; tied scores are reported separately. Pairwise compar-ison shows the two matched responses together and asks which uses the history more appropriately. Each pair is presented in both orders; accuracy is averaged over the two orders, and consistency is the percentage of pairs for which the same response is chosen in both orders. Pointwise scoring separates the matched re-sponses in 63.0% of pairs, with 35.9% of pairs receiving tied scores; ties rise to 50.5% for misapplied-state errors. Pairwise comparison reaches 89.0% accuracy with 90.5% order consis-tency. Neither protocol assigns an error direction, so neither can expose the U NDER →OVER confu-sion measured by the three-way verdict.

## D Human Validation 

Protocols. We conduct three human studies on the same stratified sample of 100 scenarios: in-tervention fidelity (Study 1), state-role valida-tion (Study 2), and a human evaluator reference (Study 3). Study 1 was conducted by one pair of graduate-student annotators, and Studies 2 and 3 by a second, disjoint pair; none was involved in benchmark construction. In Study 1, annotators viewed the dialogue, the error response, and the intended subtype definition, judged whether the response committed the assigned error, and consol-idated differences through joint adjudication. In Study 3, annotators performed the evaluator task itself before any exposure to the benchmark pol-icy: they independently assigned R IGHT , U NDER ,or O VER to 200 shuffled single-response instances comprising the sample’s matched R IGHT and error responses, using only the dialogue and candidate response. Their labels are reported without adjudi-cation. Misapplied-state instances were labeled in a separate round, so annotators could infer the er-ror family represented in that pool; they remained blind to which responses were erroneous and to the direction of each error, but performance on the misapplied-state portion may benefit from the nar-rower judgment space. Scoring follows Section 4. 

Study 1: Intervention fidelity. Table 12 reports per-subtype consensus confirmation rates. The con-sensus confirms the intended error in 88% of raw pipeline generations, with the lowest rates for ex-plicit violation (67%) and scope leakage (70%), the two subtypes whose boundary definitions leave the most room for judgment. The 12 intervention-realization mismatches were revised and re-verified as described in Section 3.4; the final benchmark, Studies 2 and 3, and all model evaluations use the revised versions.

For the human-reference study (Study 3), anno-tators received the following instructions: 

> Read the complete dialogue history, the target user request, and one candidate assistant response. Based only on the information shown, assign ex-actly one verdict: RIGHT : The response uses applicable information from the user history with the appropriate influ-ence and does not use information that should be ignored.

UNDER : The response omits, violates, or gives insufficient influence to applicable information from the user history. OVER : The response uses information that should not apply or gives user information more influence than warranted. Judge the response’s use of persona information rather than its general fluency or writing style.

Example 1 Re-entry × stale/superseded use Relation: the user leaves a school search, handles an unrelated task, and later returns to the school decision 

State A (applicable): updated availability: work sched-ule now predictable; hybrid programs acceptable 

State B (superseded): the original online-only constraint, stated emphatically before the update 

Dialogue (abridged) — the superseded value is stated more forcefully than its replacement 

U [B] : It has to be fully online, that’s non-negotiable for me. I can’t relocate, and my job has really unpredictable hours — I can’t commit to being physically somewhere at a set time every week. Online only. 

[ . . . an intervening episode on an unrelated planning task . . . ] 

U [A] : So my store just moved me to a consistent evening shift, which means my hours are actually predictable now. I’m free most mornings and early afternoons pretty reliably. 

A [A] : So to make sure I’ve got this right: you’re no longer restricted to 100% online — you’re open to hybrid programs? 

U [A] : Exactly — hybrid is fine now, especially if it means a stronger program or better networking. I want to come back to the college decision later. 

U [target]: So given all of that — what programs would you actually recommend for me at this point? I want strong job placement, reasonable cost, and something that fits my schedule. 

Matched responses (excerpts) — both are fluent and well-structured; only the state they apply differs 

RIGHT : “With your schedule stabilized and hybrid on the table, your options have genuinely expanded. The local university is worth putting at the top of the list . . . ” 

Error : “Since you’ve been clear that the program must be fully online (given your unpredictable work schedule), I’ve filtered everything through that requirement first . . . ” 

Why it is hard — the superseded constraint was stated with maximal emphasis (“non-negotiable”), while its re-placement was agreed to conversationally; an evaluator anchoring on emphasis rather than recency accepts the error response. 

Example 2 Cross-domain × underweighting Relation: states established while designing a work-productivity system must transfer to an urgent personal-logistics problem 

State A (applicable): a hard 5:30 pm daycare pickup, plus a stated inability to work on parallel tasks (accumu-lated over several turns) 

State B (competing): a visual, color-coded task-board preference from the same episode 

Dialogue (abridged) — State A is assembled from scat-tered signals, never one sentence 

U [A] : Even when I can see what needs attention, I end up jumping between projects and then I’m basically useless. I’ve tried multitasking — it doesn’t work for me. 

U [A] : The other constraint — and this is a hard wall for me — is 5:30. I pick up my daughter, and if I’m even five minutes late the daycare charges a penalty. It’s happened twice. 

[ . . . the system is designed; a new episode begins with a car breakdown . . . ] 

U [target]: It’s 4:15. And oh god — yes, I have to pick up my daughter at 5:30. I cannot be late. 

Matched responses (excerpts) —

RIGHT : “Stop — you don’t have time to troubleshoot this yourself. You have 75 minutes, and you know better than anyone that 5:30 is not negotiable. Call roadside assistance immediately . . . ” 

Error : “I know you mentioned the 5:30 hard stop for day-care pickup. Here’s what I’d suggest: use this window to tackle two or three things in parallel rather than finishing one completely . . . ” 

Why it is hard — the error acknowledges the constraint and then gives it no force — the signature underweight-ing shape. Evaluators that flag it split between the deficit reading (the hard stop was downplayed) and the excess reading (work-context habits were misapplied to an emer-gency); see Appendix C.2.

State B (out of scope): the user’s own cancellation policy as a vacation-rental host 

Dialogue (abridged) — State B is genuine, recent, and emphatically held — but belongs to the host role 

U [B] : My philosophy is: if you book a peak holiday slot, you’re locking it in. No exceptions. I’ve lost $3,000 in one holiday season to cancellations. 

U [B] : Non-refundable for holidays, firm 30 days for the rest. That’s my policy going forward. 

[ . . . the user then plans a family dinner: dairy allergy and seating for a hearing-impaired guest are discussed . . . ] 

U [target]: When I confirm the reservation, should I ask about their cancellation policy for Christmas Eve? I want to know what I’m getting into as a diner. 

Matched responses (excerpts) —

RIGHT : “Yes, absolutely ask. High-end restaurants on Christmas Eve commonly require a card at booking and charge a per-head cancellation fee, so ask directly what happens if a guest cancels . . . ” 

Error : “Yes — but given your experience as a vacation rental host with a strict non-refundable holiday policy of your own, you already know how high the stakes are on the restaurant’s side. That context should shape how you approach this conversation . . . ” 

Why it is hard — every keyword matches, and the im-ported state is real and vivid; the only thing wrong is the boundary — the user’s host-side policy has no bearing on her question as a customer. 

Example 4 Under-personalization subtypes in brief Coverage: the full under-personalization family: com-plete omission, partial omission, explicit violation 

Complete omission — the applicable state leaves no trace in the response 

History: while choosing a gym, the user repeatedly stressed that her daughter has a severe peanut allergy and must avoid any environment where nuts are present. 

Target: “They apparently have a nutrition station — is that something my daughter could use?” 

Error: “The nutrition station is actually a solid option for kids, and it can work really well when you’re bringing your daughter along . . . ” 

Why it is hard — fluent and helpful, written as if the al-lergy had never been mentioned; nothing in the response signals that anything is missing. 

Partial omission — one of two jointly applicable require-ments is silently dropped 

History: two hard requirements for a gift: total budget under $80, and Android compatibility (the household owns no Apple devices). 

Target: the best options for a non-tech-savvy father. 

Error: recommends well-reviewed, Android-compatible devices priced at $129–$249. 

Why it is hard — the visible personalization (Android, ease of use) makes the response look complete, hiding the dropped budget ceiling. 

Explicit violation — the recommendation directly con-tradicts an active constraint 

History: the user is a nurse on an irregular rotating sched-ule and cannot commit to fixed-time programs. 

Target: “If my schedule ever stabilizes, should I just upgrade then?” 

Error: “Honestly, I wouldn’t wait — now is actually the perfect time to commit to a structured program . . . ” 

Why it is hard — unlike underweighting, the constraint is never acknowledged: the response simply recommends the opposite of what the user can do. 

Example 5 Over-personalization and misapplied-state subtypes in brief Coverage: irrelevant use and unsupported inference (over-personalization); over-dominance (misapplied-state); scope leakage appears in Example 3, stale/super-seded use and underweighting in Examples 1 and 2 

Irrelevant use — a genuine but unrelated state is im-ported as personalization 

History: in a concert-planning episode, the user said they only attend original artists and refuse tribute acts. The current task is choosing a restaurant for their parents’ anniversary. 

Error: “Stick with the original Osteria Barolo — hon-estly, this is a bit like your original-artists-only rule for concerts.” 

Why it is hard — the imported rule is real and the analogy sounds thoughtful, but it plays no legitimate role in the restaurant decision. 

Unsupported inference — a preference is asserted from an adjacent fact the user never endorsed 

History: planning a child’s birthday, the user explicitly says budget is not a concern (“I just want the kids to have a blast”). In an earlier episode they skipped an expensive Las Vegas trip. 

Error: “Based on your earlier decision to skip the Vegas trip in favor of saving money, I’ve focused on keeping this low-cost . . . ” 

Why it is hard — the inference is derived from a real event yet contradicts what the user actually said at the target. 

Over-dominance — a soft preference is promoted to the primary decision filter 

History: the user’s binding constraint is private one-on-one sessions only (severe social anxiety); she once added that she prefers female practitioners “if possible.” The target is an urgent dermatologist search. 

Error: “Since you mentioned you feel more comfortable with female practitioners, I want to make sure that’s front and center in how we approach finding you the right dermatologist . . . ” 

Why it is hard — a nice-to-have is elevated above both the medical urgency and the actual binding constraint; every fact used is true, only the weights are wrong. 

## F Prompt System 

This appendix documents the complete prompt sys-tem as a set of cards. Prompts 1–9 drive benchmark construction in pipeline order, while Prompts 10– 12 elicit evaluator judgments. Each card specifies the prompt’s purpose, input, and output contract. All benchmark-construction calls use Claude Sonnet 4.6 with temperature 0.7 and provider-default values for other sampling parameters. 

F.1 Generation Pipeline 

Prompt 1 Scenario planner — system prompt Purpose: instantiate a structured scenario specification for one sampled design cell; fixes the label before any dialogue text exists 

Input: the instantiation template of Prompt 2 

Output: a single JSON specification (contract below) 

Role framing — establishes the designer role and the diagnosticity requirement 

You are an expert benchmark designer for PersEvalBench, a personalization-evaluator benchmark. Scenarios must be diagnostic: the correct label must be recoverable only by reasoning about which user state applies at the target and with what weight – never from surface cues, response quality, or wording artifacts. 

Sources of difficulty — the controlled factors that make the applicability judgment non-trivial 

Incorporate these difficulty factors deliberately: 1. Implicit or accumulated preference expression (the state is not spelled out in one place) 2. States A and B competing on the same attribute dimension 3. Weighting errors in which the response acknowledges the constraint yet fails it 4. Evidence located episodes before the target 5. Causal chains that make B look plausibly transferable to the target 6. A neutral distractor option that prevents elimination by binary contrast 

Factorized state design — the specification core: two states and the single dimension separating them 

Every scenario must specify: - State A: the currently applicable preference or constraint (with holder, scope, time, strength, transferability) - State B: a decoy state that is not applicable but looks similar - The A–B relation dimensions: holder, scope, time, status, strength, transferability, evidence form, evidence distance - The single dimension that makes B inapplicable 

Response design rules — fixes the generation mecha-nism of the trap 

For withhold-A subtypes (complete_omission, partial_omission, underweighting, explicit_violation): the ERROR response does not properly use A and must not actively apply B – the trap is realized by withholding or weakening A. For apply-B subtypes (irrelevant_use, scope_leakage, stale_superseded, over_dominance, unsupported_inference): the ERROR response actively applies B to the current context – the trap is realized by inserting inapplicable information. 

Subtype constraints — operational admissibility tests for eight of the nine subtypes; over-dominance is gov-erned by the family rules above and the verifier 

complete_omission: the target request must not mention or implicitly lock to State A’s content. Test: a helpful assistant can give a complete, high-quality answer without knowing State A; otherwise redesign the target request. partial_omission: State A contains at least two clearly separable, independently verifiable, equally critical requirements; the ERROR response clearly satisfies one and clearly fails the other. underweighting: State A is an unambiguous hard constraint, stated with binding language ("dealbreaker", "must", "non-negotiable") and a concrete satisfaction check; the ERROR response’s top recommendation clearly fails it. explicit_violation: RIGHT and ERROR differ only in whether A is respected. Do not frame this as using old information (that is stale_superseded). The target request does not restate A. scope_leakage: the ERROR must make the out-of-scope state materially affect the current recommendation, so that the crossed scope boundary is independently verifiable. Express this naturally and do not use a fixed attribution template. irrelevant_use: State B comes from a genuinely different domain with no temporal, logistical, or scheduling relationship to the target task. Test: if a reasonable person could argue B is relevant here, choose a different B. stale_superseded: the conversation contains an explicit update event in which the user changes the preference; the old and new values produce different recommendations; the ERROR uses the old value. unsupported_inference: the ERROR must explicitly connect an observed fact to a preference or constraint that the user never expressed. The inference must be identifiable, but its wording should vary naturally. why_tricky: give a specific, non-trivial reason the error is easy to miss; vague answers are rejected. 

Output contract — the JSON fields that later stages consume and may not alter 

Return a single JSON object with fields: scene_type, primary_error, preference_relation, episode_1_state, episode_2_state_or_change, target_episode, applicable_state_A, decoy_or_non_applicable_state_B, A_B_relation, scope_or_status_difference, A_B_distinguishing_dimension, target_options {right, trap, neutral_distractor}, right_choice_logic, error_choice_logic, why_tricky, single_error_check, preference_expression, evidence_distance_category, causal_chain_logic. No text outside the JSON.

Prompt 3 Specification verifier Purpose: reject or repair specifications whose label logic is unsound, before any dialogue is generated 

Input: one scenario specification 

Output: {passes, failures[ ]} 

Role and stakes — sets the acceptance bar 

You are a strict quality verifier for PersEvalBench benchmark scenarios. Check whether a specification passes all of the following rules. Be rigorous – a pass means the scenario will become part of the final benchmark. 

Label-soundness rules (1–3) — apply to every scenario 

Rule 1 (RIGHT satisfies State A and the main task): the RIGHT option must correctly apply the currently applicable State A and fulfill the user’s main task requirement. Rule 2 (trap is not obviously worse): the TRAP option must match RIGHT in quality, price level, completeness, and length – a plausible good response that simply applies the wrong state. Rule 3 (single error): the scenario must have exactly one primary error mechanism; if the trap could be explained by multiple distinct error types, it fails. 

Family rules (4–7) — checks specific to error families 

Rule 4 (omission errors depend on A): for complete_omission, partial_omission, underweighting, and explicit_violation, the RIGHT option must genuinely depend on State A; if a generic response would also satisfy the task, the scenario fails. Rule 5 (over-use errors depend on B): for irrelevant_use and over_dominance, the trap must be favored only if the wrong state is applied, not because it is generically bad. Rule 6 (stale errors change the choice): for stale_superseded, the old and new preference values must produce genuinely different choices. Rule 7 (scope leakage is scope-only): for scope_leakage, the only differentiator between RIGHT and TRAP must be scope applicability, not factual errors or quality issues. 

Structural rules (8–11) — relation typing and subtype separability 

Rule 8 (A–B relation structure): the A–B relation must match the declared state-relation type (same attribute for a different holder; same attribute in a different scope; same attribute at a different time; an old value superseded by a new one; a hard constraint versus a soft preference; two simultaneously applicable states; a cross-domain-transferable state versus a domain-specific one; an adjacent fact that is not an actual preference). Rule 9 (why_tricky is substantive): the explanation must give a specific, non-trivial reason a model would choose the trap. Rule 10 (complete-omission request independence): for complete_omission only, the target request must not mention or implicitly lock to State A’s content; an assistant that has never seen State A must be able to give a complete, high-quality answer. Rule 11 (partial-omission separability): for partial_omission only, State A must contain at least two clearly separable requirements, and the error logic must name which requirement is satisfied and which is omitted; the requirements must be independently verifiable. 

Output contract and calibration — machine-readable verdict with per-rule feedback 

Return a JSON object: {"passes": true/false, "failures": [{"rule_number": <int>, "rule_name": "...", "explanation": "why it fails this rule", "suggestion": "how to fix it"}]} If passes is true, failures must be an empty array. Be strict but fair: fail only rules that are genuinely violated.

F.2 Evaluation Formulations 

Subtype identifiers in the evaluation prompts carry generation-time direction prefixes ( under. /over. ); scoring follows the three error families of Sec-tion 3.2, and the elicited subtype is not scored. 

Prompt 10 End-to-end evaluation Purpose: single-pass verdict, subtype, and evidence elic-itation 

Input: context under the active visibility condition, target request, candidate response 

Output: {verdict, subtypes, confidence, reasoning} 

Inputs — the three task elements 

Given the conversation context below, evaluate whether the assistant response correctly uses the user’s preferences, constraints, and expressed states. Conversation context: {context} User request: {user_request} Assistant response: {response} 

Decision procedure — identify applicable states, check the response, then classify 

Step 1: Identify applicable user preferences/constraints from the context; list which are relevant to this specific request. Step 2: Check the response against each applicable preference. Step 3: Classify using the decision tree below. 

Verdict taxonomy — the three-way decision tree with subtype anchors 

OVER_PERSONALIZED (the response actively uses wrong information): - uses a preference that belongs to a different person - uses a stale/outdated preference (superseded by newer information) - uses a preference from a different scope (e.g., business constraints applied to a personal trip) - uses information that is irrelevant to this specific request - acts on a preference the user never stated (unsupported inference) - lets a soft preference dominate over the primary task requirement UNDER_PERSONALIZED (the response fails to use correct information): - gives a generic response ignoring a clearly applicable preference (complete omission) - uses some preferences but misses a critical one (partial omission) - acknowledges a constraint but treats it as optional/soft (underweighting) - directly contradicts a stated preference without acknowledging it (explicit violation; if the response contradicts a newer preference by using stale information, that is OVER, not UNDER) RIGHT: the response correctly applies all relevant current preferences without over- or under-applying them. 

Disambiguation rule — resolves mixed cases by the primary mechanism 

- Generic response referencing no user-specific information -> UNDER - Actively applies wrong or inapplicable information -> OVER - If both occur, classify by the primary mechanism: substitution of B for A -> OVER; simply not using A -> UNDER 

Output contract — canonical subtype labels; JSON only 

Respond with a JSON object containing: - "verdict": one of "RIGHT", "OVER_PERSONALIZED", "UNDER_PERSONALIZED" - "subtypes": the primary error subtype if applicable, drawn from: under.complete_omission, under.partial_omission, under.underweighting, under.explicit_violation, over.irrelevant_use, over.scope_leakage, over.stale_or_superseded, over.unsupported_inference, over.over_dominance; an empty list if RIGHT - "confidence": float 0.0–1.0 - "reasoning": brief explanation citing which preference was mishandled and how Respond only with the JSON object, no other text.

Input: target request, candidate response, searchable dia-logue history 

Output: {state_table, verdict, subtypes, confidence, reasoning} 

Role and inputs — frames evaluation as systematic state reconstruction 

You are a persona-use evaluator. You systematically search the dialogue history, build a structured state table, and then judge the response. Target query: {user_request} Candidate response: {response} Searchable multi-episode dialogue history: {context}

Step 2: For each candidate state, search the dialogue (at most 6 searches) for supporting evidence, later updates or exceptions, conflicting evidence, and holder/scope boundaries (does it belong to this user, for this task, at this time?). 

State-table schema — the explicit applicability record per state 

Step 3: For each confirmed state, record: State | Holder | Scope | Status | Strength | Evidence Turns | Policy, where - Holder: user / spouse / parent / colleague / other - Scope: global / specific domain / specific task / specific time - Status: active / updated / superseded / expired / one-time exception - Strength: hard (dealbreaker) / strong (important) / soft (nice-to-have) - Evidence Turns: the turn numbers that support it - Policy: IGNORE (not applicable here) / SUPPORT (should inform but not dominate) / DOMINATE (must be satisfied)
