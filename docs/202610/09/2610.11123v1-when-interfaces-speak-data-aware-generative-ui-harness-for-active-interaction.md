## 摘要
如今，大多数人机交互仍以文本为主。在复杂任务中，自然语言可能带来认知负担、歧义、信息混乱以及输入缓慢等问题；而临时生成的 UI 能够呈现结构化信息，并引导用户完成任务。我们提出 GenUI-Harness，这是一种多智能体框架，由负责信息检索与任务执行的工具智能体（Tool Agent）和负责识别歧义、生成结构化界面前端代码的 GUI 编码智能体（GUI Coder Agent）组成。通过强化学习训练编码智能体颇具挑战：交互式 UI 生成的可验证奖励需要耗费大量资源执行，而基于 LLM-as-a-Judge 的奖励则容易受到奖励投机的影响。针对第一个挑战，我们设计了 Dynamic UX，这是一个轻量级软件包，可在单个沙箱中实现动态交互与奖励收集；针对第二个挑战，我们提出 Reward Auditor，这是一种元奖励机制，可监控奖励分布，并将诊断模式提炼为共享的评估准则与评分规范。我们还推出 UI-TAU Bench，这是一个通过生成的 UI 代码开展主动人机交互的基准。该基准基于 Tau-Bench 的工具使用设置，涵盖从公开数据源构建的 10 个真实领域数据库，并分为 Lite（300 项任务）和 Full（1,000 项任务）两个子集。在 Lite 子集上，GenUI-Harness 的平均 Pass@3 比 smolagents 高出 4.48 个百分点。使用 GenUI-Harness 进行训练后，4B 主干模型的 Pass@3 从 9.33% 提升至 58.00%，超过了 Claude Opus 5（46.67%）等规模更大的前沿模型。在模糊与非模糊查询上，GenUI-Harness 也表现出稳健性。在一项比较不同沟通渠道的评审者调查中，生成式 UI 将平均对话轮数从 3.4 轮降至 1.2 轮。这些结果表明，在所评估的数据库支持型工作流中，面向数据的生成式界面有助于有效完成任务并减少对话轮数。

## Abstract
Most human-agent interaction today remains text-based. Natural language can impose cognitive overload, ambiguity, information chaos, and slow input for complex tasks; ephemeral generative UIs can present structured information and guide users toward task completion. We propose GenUI-Harness, a multi-agent harness pairing a Tool Agent for information retrieval and task execution with a GUI Coder Agent that identifies ambiguities and generates front-end code for structured interfaces. Training the coder with reinforcement learning is challenging: verifiable rewards for interactive UI generation require costly execution, while LLM-as-a-Judge rewards are prone to reward hacking. We address the first challenge with Dynamic UX, a lightweight package for dynamic interaction and reward collection in a single sandbox, and the second with Reward Auditor, a meta-reward mechanism that monitors reward distributions and distills diagnostic patterns into a shared rubric and scoring specification. We introduce UI-TAU Bench, a benchmark for active human-agent interaction through generated UI code, built on 10 real-world domain databases constructed from public data sources and based on Tau-Bench tool-use settings, with Lite (300 tasks) and Full (1,000 tasks) splits. GenUI-Harness achieves an average Pass@3 gain of 4.48 percentage points over smolagents on Lite. Training with GenUI-Harness improves a 4B backbone from 9.33% to 58.00% Pass@3, outperforming larger frontier models such as Claude Opus 5 (46.67%). GenUI-Harness also remains robust on ambiguous and non-ambiguous queries. In a reviewer survey comparing communication channels, generated UIs reduce average dialogue rounds from 3.4 to 1.2. These results show that data-aware generative interfaces can support effective task completion and reduce dialogue rounds in evaluated database-backed workflows.

## 2. 方法论：角色分工、执行反馈与奖励审计

### 2.1 GenUI-Harness：三阶段、多角色协作

框架包含两个分别训练的角色：

1. **前置探索：Tool Agent**
   - 根据用户请求和工具参数结构识别目标操作。
   - 使用 ReAct 风格循环，最多进行 **5 轮只读查询**。
   - 获取用户资料、相关记录、候选资源以及尚未解决的参数。
2. **界面生成：GUI Coder Agent**
   - 读取请求及完整探索历史，区分：
     - 已由数据库确定的信息；
     - 可以从候选记录中选择的信息；
     - 必须由用户提供的偏好。
   - 生成单文件 **React/TypeScript、Material UI** 组件。
   - 显示可读的候选标签和决策相关属性，避免让用户直接处理数据库结构或内部标识。
   - 通过 `submitData` 提交 JSON，将界面输入转成下游工具可用的数据。
3. **后置执行：Tool Agent**
   - 结合检索历史和用户提交结果，最多再进行 **5 轮查询**。
   - 验证选择、补齐数据库相关参数，执行 **一个终结动作**，更新数据库。

**关键思想**：将工具推理与界面生成分离，使 GUI Coder 可以独立优化，并迁移到其他工具推理模型。

### 2.2 训练流程：先监督学习，再只优化界面生成器

- 两个角色分别从 **Qwen3.5-4B** 初始化。
- 首先进行角色专用的监督微调（SFT），学习检索、执行及界面输出格式。
- 随后固定 SFT Tool Agent，仅对 GUI Coder 使用 **GRPO** 强化学习：
  - 每个提示生成一组候选界面；
  - 按组内相对奖励计算优势；
  - 使用裁剪策略目标更新模型，不使用独立价值模型；
  - 文中设置 **KL 系数为 0**。
- Direct RL、第一次审计奖励、第二次审计奖励对应的策略，均从同一个 SFT 检查点**独立训练**，并非连续接着训练。因此，其比较更有利于识别奖励设计的贡献。

### 2.3 Dynamic UX：降低界面执行成本

- 在一个沙箱内共享服务器、组件库和 Chromium 浏览器进程。
- 为每次 rollout 创建独立浏览器上下文及唯一会话，隔离页面状态。
- 返回编译、运行结果及初始 **ARIA 可访问性树快照**，供奖励评估使用。
- 其改进重点是减少浏览器反复启动的开销，**并不意味着每个在线训练样本都执行完整的人机交互与数据库动作**。

### 2.4 Reward Auditor：用真实任务结果修正代理奖励

**初始奖励**

- LLM 裁判从四个维度给出 0–5 分：
  - 功能等价性：权重 35%；
  - 功能完整性：35%；
  - 实现正确性：15%；
  - 任务一致性：15%。
- 加权后除以 5，得到归一化质量分。
- 代码提取、结构、渲染或裁判响应检查失败时，初始奖励统一为 0。

**初始奖励的问题**

- 界面看似完整、能够渲染，但控件可能无法提交正确值。
- 不同失败阶段都得到 0，导致 GRPO 缺少组内学习信号。
- 初始 ARIA 快照不能证明后续交互和提交逻辑正确。

**审计流程**

1. 从内部训练 rollout 中抽样，运行用户模拟器、后置 Tool Agent 和终态评估。
2. 将最终数据库精确匹配作为真实成功标签，并与“奖励是否不低于 0.5”的预测比较。
3. 使用 Claude Opus 5 分析误报、漏报、奖励分布及完整轨迹。
4. 自动修改裁判准则与确定性评分规则。
5. 在固定的历史界面输出上重放候选奖励，避免把策略变化误当成奖励改进。
6. 经两轮修订，形成跨任务共享、在对应 RL 训练期间固定的奖励规范。

**最终奖励**

- 对格式错误、代码不完整、不可用图标、渲染失败和过短 ARIA 等阶段分配不同低奖励。
- 正常界面使用“**0.20 + 0.80 × 质量分 × 可访问性系数**”。
- 可访问性系数为 0.5–1，依据标签形式、标签长度及选择控件标签关联等缺陷计算。

因此，该方法是**以抽样真实执行结果校准低成本代理奖励**，而不是直接以每个 rollout 的最终任务成功作为在线奖励。

## 3. 实验设计：数据、基准与对比方法

### 3.1 UI-TAU Bench

- 基于 Tau-Bench 的工具使用设置构建，但把主要用户交互渠道改为动态生成的 UI。
- 覆盖 **10 个领域**：航班、酒店、银行账户、餐厅、电商、电影票、活动票务、医疗预约、零售、租车。
- 数据来自 OpenFlights、Hotel Booking Demand、Olist、MovieLens、Ticketmaster 等公开来源，经过规范化、规则定义及工具构建形成任务环境。
  - 更准确地说，它们是**基于公开领域数据构建的受控数据库**，不是直接接入真实生产服务。
  - 全部评估数据库合计 **786 条记录**，规模较小。
- 两个任务集合：
  - **Lite：300 项任务**，每个领域 30 项；
  - **Full：1,000 项任务**，每个领域 100 项。
- 通过隐藏内部标识及部分动作参数制造歧义：
  - 中等歧义额外隐藏 2–3 个参数；
  - 高歧义额外隐藏 4–5 个参数。
- 工具与任务经过执行验证及双人复核；任务标注一致率约 **94%**。

### 3.2 训练数据

- Claude Sonnet 4.6 合成 **40 个训练数据库**，与评估领域分离。
- DeepSeek V4 Flash 生成轨迹，仅保留终态正确、界面可渲染且具有有效 ARIA 的轨迹。
- 数据划分：
  - **25 个 SFT 数据库**：12,376 个训练任务，32,409 条 Tool Agent 样本，12,376 条 GUI Coder 样本；
  - **15 个 RL 数据库**：8,116 个训练任务。
- 实际报告的 GRPO 训练使用其中 **1,500 个训练提示、41 个验证提示**。
- 作者检查任务文本、参考动作及工具名称序列的精确重叠，未发现训练—评估重复。

### 3.3 评估指标与用户模拟

- 成功要求动作执行成功，且**整个最终数据库状态与参考状态完全一致**。
- Lite 每个任务评估三次：
  - **Pass@3**：三次中至少一次成功的任务比例；
  - **Avg@3**：全部三次执行的平均成功率，更能反映单次可靠性。
- Full 因成本限制，仅评估一次，报告 **Pass@1**。
- 固定用户模拟器为 DeepSeek V4 Flash：
  - UI 条件下读取源码、ARIA 和隐藏目标，生成 Playwright 操作；
  - 文本条件下通过自然语言回答；
  - 无权直接调用任务动作或修改数据库。

### 3.4 对比方法

- 四种完整智能体框架：
  - GenUI-Harness；
  - smolagents；
  - mini-swe-agent；
  - Pi。
- Lite 在 **9 个共同主干模型**上比较，包括 Qwen 系列、gpt-oss-120b、DeepSeek V4 Flash、GPT-5.4、Claude Sonnet 4.6 和 Claude Opus 5。

- 另有训练奖励消融、GUI Coder 跨模型替换、无歧义任务、渲染系统测试及人工沟通渠道调查。

## 6. 主要结论与发现

### 6.1 完整系统表现改善，但并非所有模型都受益

- Lite 上，GenUI-Harness 对 smolagents 的跨模型平均提升：
  - Pass@3：**4.48 个百分点**，95% CI 为 **[2.37, 6.59]**；
  - Avg@3：**3.56 个百分点**。
- 相对 mini-swe-agent、Pi 的平均 Pass@3 提升分别为 **5.81、7.15 个百分点**。
- GenUI-Harness 在 9 个主干中有 **7 个取得最高 Pass@3**。
- 原始 Qwen3.5-4B 在 GenUI-Harness 下反而弱于三个文本基线，说明**仅添加生成式界面并不足够，模型能力与专门训练很重要**。

### 6.2 专门训练使紧凑模型显著提升

| 阶段 | Lite Avg@3 |
|---|---:|
| 原始 Qwen3.5-4B + GenUI-Harness | 3.22% |
| SFT | 27.67% |
| Direct RL | 30.67% |
| 第一轮审计奖励 | 32.67% |
| 第二轮审计奖励 | **36.00%** |

- 最终模型 Pass@3 从 **9.33% 提升至 58.00%**，增加 **48.67 个百分点**。
- 最终奖励比 Direct RL 的 Avg@3 高 **5.33 个百分点**，支持奖励审计的增量作用。
- Full 单次成功率为 **40.90%**。
- 该系统在本文设置中超过所评估的大模型配置，但这不是对通用能力的全面比较。

### 6.3 效率、迁移与适用性

- 在成功会话中，智能体轮数减少 **36%–43%**。
- 人工调查中，对话轮数由 **3.4 降至 1.2**，约减少 65%；85% 的筛选任务被多数 UI 评审者认为延迟可接受。
- GUI Coder 替换使 5 个其他模型的 Avg@3 均提高，增幅为 **2.44–8.77 个百分点**。
- 无歧义条件下，GenUI-4B 的 Avg@3 从 **36.0% 提高到 38.7%**，说明 UI 也可能帮助信息审阅与动作确认。

### 6.4 系统优化与失败瓶颈

- Dynamic UX 平均吞吐量增加 **18.2%**，中位延迟降低 **15.3%**，峰值内存降低 **35.2%**。
- 800 个失败会话中：
  - 无有效 UI 交互：**52.0%**；
  - 参数或最终状态不匹配：**44.5%**；
  - 执行被拒绝：**3.5%**。
- 关键瓶颈是**控件能否表达意图，以及提交值能否忠实映射到动作参数**，而不只是界面能否渲染。
- “无有效交互”是失败阶段分类，不能全部直接归因为界面代码错误，也可能涉及模拟器。

## 7. 优点与亮点

- **目标定义清晰**：将 UI 生成嵌入真实状态转换任务，避免只用代码相似度或审美评分衡量成功。
- **数据 grounding 与用户控制结合**：候选值来自检索结果，减少凭空生成选项；用户只处理未解决的决策。
- **模块化设计有效**：工具角色与界面角色独立训练，且展示了跨模型接口生成器迁移。
- **奖励审计具有方法价值**：利用有限真实执行预算发现代理奖励漏洞，再把诊断转成共享规则。
- **固定输出重放较严谨**：能够区分“评分规则变了”和“模型生成更好了”。
- **兼顾系统工程**：浏览器上下文隔离解决训练吞吐和资源开销问题，并进行了会话泄漏测试。
- **报告较透明**：提供训练配置、重试规则、奖励细节、错误轨迹与人工调查筛选条件，并明确承认主要局限。

## 8. 不足与局限

### 8.1 真实用户外推有限

- 模拟器知道隐藏目标，还能读取 UI 源码，比普通用户拥有更多信息。
- 人工调查只有 6 名评审者，且仅筛选稳定可交互的 100 个任务，排除了最影响真实体验的失败情况。
- 对话轮数减少不等于总操作时间或认知负荷减少：一次 UI 提交可能包含大量点击和字段编辑。

### 8.2 场景与数据规模受限

- 评估数据库总共只有 786 条记录，尚未验证海量候选、复杂分页、实时变化和生产级业务约束。
- 基准请求及规则高度受控，未充分覆盖需求中途改变、用户犹豫、信息冲突和异常恢复。
- 基准主要采用一次界面交互、一个终结动作，不适合直接代表长期、多步骤事务协作。

### 8.3 奖励仍存在代理偏差

- 最终奖励依然依赖 LLM 裁判、参考界面和静态检查，奖励审计只能缓解，不能证明消除奖励投机。
- ARIA 长度及标签长度等启发式规则，可能偏好某类实现，而不一定准确对应用户体验。
- 初始 ARIA 和源码分析不能充分检测布局重叠、视觉混乱、后续状态变化及全部动态交互问题。
- 教师、模拟器与在线裁判部分使用同一模型家族，可能存在相关性偏差。

### 8.4 评价与比较仍有局限

- Pass@3 的 58% 不代表一次使用就有 58% 成功率；Avg@3 的 **36%** 表明单次可靠性仍有较大提升空间。
- 严格数据库精确匹配可能把标识、排序或自由文本不同但语义等价的结果算作失败。
- 主比较缺少“相同智能体循环、只切换交互渠道”的全量控制实验。
- 闭源 API 使用非固定日期别名，可能影响长期复现。
- Full 表中，1,000 项单次二元评估对应的百分比通常应以 0.1 为步长，但原始 4B 的一项结果为 **4.11%**，其分母或统计口径需要进一步说明。

### 8.5 部署成本与安全尚不完整

- 未报告完整任务的生成延迟、交互时间、GPU 小时和费用，无法判断性能收益是否抵消生成与执行成本。
- 浏览器上下文隔离测试证明了所测会话的状态隔离，但不等于针对任意生成代码的完整安全验证。
- 涉及银行或医疗等领域时，还需额外验证权限、隐私、代码安全和高风险操作确认机制。

**总体评价**：本文最有价值的贡献，是把数据驱动界面生成、用户意图收集、工具执行和奖励校准连成可验证的闭环。实验支持其在受控服务任务中的有效性，但真实用户可靠性、成本优势和生产环境适用性仍需进一步研究。
