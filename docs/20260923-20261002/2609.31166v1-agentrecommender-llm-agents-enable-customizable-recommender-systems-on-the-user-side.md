## 摘要
传统上，推荐系统由平台开发。然而，这也催生了许多现象：它们或许有利于平台锁定用户，却给用户带来困扰，例如标题党、过滤气泡以及假新闻传播。近期，用户侧推荐系统作为一种解决这一问题的新范式被提出。如果用户部署自己的推荐系统，就不必再受平台利益的摆布。然而，构建用户侧推荐系统并非易事；尤其是，要为个人量身定制系统，还需要额外的数据。我们提出 AgentRecommender，这是一种利用 LLM 智能体的调查能力与内部知识、无需额外数据即可灵活构建用户侧推荐系统的方法。AgentRecommender 使用户能够轻松创建符合自身偏好的推荐系统。

## Abstract
Recommender systems have traditionally been developed for platforms. However, this has given rise to many phenomena that may be advantageous for platform lock-in but are a nuisance to users, such as clickbait, filter bubbles, and the spread of fake news. Recently, user-side recommender systems have been proposed as a new paradigm for solving this problem. If users deploy their own recommender systems, they are no longer at the mercy of the platform's interests. However, building a user-side recommender system is not trivial; in particular, customizing one for oneself requires additional data. We propose AgentRecommender, a method that leverages the investigation capability and internal knowledge of LLM agents to flexibly build user-side recommender systems without additional data. AgentRecommender allows users to easily create recommender systems tailored to their own preferences.

## 1. 核心问题与整体含义：让推荐目标更多由用户决定

### 研究背景与动机
- 传统推荐系统由平台开发，通常优化购买概率、观看时长、广告收益等平台目标。这些目标不一定与用户利益一致，可能带来标题党、信息茧房、内容偏见和曝光不公平等问题。
- **用户侧推荐系统**试图在不要求平台改造的情况下，由用户自行调整推荐结果，例如：
  - 平衡不同政治立场的新闻；
  - 增加冷门但相关的内容；
  - 同时展示不同年代、类型或价格区间的商品与内容。
- 但普通用户无法直接访问平台数据库、其他用户的交互日志或内部推荐模型。已有用户侧方法虽然能利用平台的公开推荐结果，却通常仍需物品属性标签，例如类别、年代、热度或政治倾向。
- 当平台不公开这些标签时，用户需要额外标注数据或训练分类器，部署门槛较高。

### 论文要解决的问题
**能否只依靠平台推荐接口、物品名称和用户自然语言要求，在没有额外属性标签的条件下，构建符合用户约束的推荐列表？**

论文提出 AgentRecommender，用 LLM 的知识与推理能力替代人工标签准备，并通过主动探索平台的推荐网络，发现初始列表之外的候选物品。

**整体意义**在于：它不是重新训练一个平台推荐模型，而是在现有平台上增加由用户控制的推荐层，将“平台允许用户调节”推进为“用户可以自行调节”。

## 2. 方法论：LLM 引导的推荐网络探索与最终筛选

### 2.1 问题设定
- 平台提供物品到物品的推荐接口：访问物品 \(i\)，可得到 \(K\) 个相关物品 \(P_{\mathrm{prov}}(i)\)。
- 每个物品具有隐藏属性 \(a_i\)，例如电影年代、音乐类型或商品价格档位。
- 用户通过自然语言指定属性划分和推荐约束，例如：
  - 新、旧电影各推荐五部；
  - 尽可能覆盖更多类型；
  - 高、低价格商品各占一半。
- 用户侧系统构建时**不能读取真实属性标签**；真实标签只在实验评估时使用。
- 系统需要在有限的平台查询预算 \(B\) 内，输出长度为 \(K\) 的推荐列表。

### 2.2 核心思想
方法结合了两个能力：

1. **LLM 隐式属性推断**：根据物品名称与内部知识，判断其可能的年代、类型或价格档位；必要时原则上可调用搜索等工具。
2. **主动扩展候选集合**：不只重排平台已经展示的物品，而是选择有希望补足用户约束的物品，进一步获取其相关推荐。

例如，当前电影候选以动作片为主，LLM 可以选择一部恐怖片展开，利用其相关推荐增加恐怖片候选。

### 2.3 算法流程
1. **初始化**
   - 用户访问物品 \(i\)。
   - 从页面 DOM 或 HTTP 请求读取平台推荐，形成初始候选池：
     \[
     L=P_{\mathrm{prov}}(i)
     \]

2. **重复探索**
   - 将未展开候选的名称和用户要求交给 LLM。
   - LLM 选择一个值得探索的物品 \(j\)。
   - 后台获取 \(P_{\mathrm{prov}}(j)\)，将其加入候选池。
   - 重复这一过程，正文实验使用 \(B\) 次扩展。

3. **最终筛选**
   - 将累积候选和用户约束交给 LLM。
   - 从候选池中选择 \(K\) 个不同物品，作为最终推荐结果。

### 2.4 技术实现与约束
- 实验使用 JSON Schema 结构化输出：
  - 扩展阶段用枚举约束 LLM 只能选择合法候选 ID；
  - 最终阶段要求选择 \(K\) 个不同候选。
- LLM 只接收物品名称，不直接读取真实属性。
- 可通过提示词加入“与原始物品足够相关”的要求，但这只是软性控制，并非相关性保证。
- 论文提出使用浏览器本地缓存保存日常访问中获得的推荐结果，减少在线查询、延迟和平台负担；**本文没有给出缓存方案的实测结果**。
- 方法可扩展到用户到物品推荐，但实验主要验证物品到物品场景。

**需要注意的定义细节**：问题设定称最多查询平台 \(B\) 次，而算法描述是先取得初始列表，再进行 \(B\) 次扩展。若初始列表不是免费读取或已缓存，则总查询次数可能为 \(B+1\)，预算口径需要进一步明确。

## 3. 实验设计：数据集、benchmark 与对比方法

### 3.1 实验平台与统一设置
- 平台推荐器由 **BPR（Bayesian Personalized Ranking）** 学习物品嵌入，再推荐嵌入相近的物品。
- 用户侧方法只能黑盒访问推荐结果，不能利用嵌入或 BPR 模型内部信息。
- 每个数据集随机选择 **100 名用户**，以用户最后交互的物品作为推荐起点。
- 默认推荐数量 \(K=10\)，扩展预算 \(B=8\)。
- 报告跨用户的均值和标准差。

这里的 benchmark 是**公开数据集上模拟的平台推荐环境**，不是对 Amazon、YouTube 等真实在线平台的直接评测。

### 3.2 数据集与评价任务

| 数据集 | 规模或预处理 | 任务与指标 |
|---|---|---|
| MovieLens 1M | 3,883 部电影 | 类型覆盖：10 个推荐中包含的不同类型数 |
| MovieLens 1M | 去除展示给 LLM 的片名年份后缀 | 年代平衡：1989 年及以前、1990 年及以后电影是否各有 5 部 |
| LastFM | 删除交互用户少于 15 人的艺术家，剩余 1,052 位 | 音乐类型覆盖：推荐艺术家包含的不同类型数 |
| Amazon Home and Kitchens | 从 5-core 子集筛选有标题、价格至少 1 美元、有相应子类别的商品；剩余 23,927 件 | 价格平衡：低于 19.99 美元和不低于该价格的商品是否各有 5 件 |

- **平衡成功率**：是否完全满足两类各五个的要求，再计算用户平均成功率。
- **类型覆盖数**：推荐列表覆盖的不同类型数量。电影可以具有多个类型，因此不等同于推荐了多少种互斥类别。
- 年代和价格阈值是具体实验设定，不代表用户实际偏好的普遍标准。

### 3.3 对比方法
- **Provider**：直接使用平台推荐。
- **iAgent**：对平台提供的候选进行重排，不扩展候选集合。
- **AgentRecommender**：LLM 主动探索推荐网络，再筛选最终列表。

**关键解释**：在论文所采用的“固定十个物品，只改变顺序”的设定下，类型覆盖数和类别计数都不受排列影响。因此 iAgent 与 Provider 的指标相同是预期结果，不代表 iAgent 在所有推荐质量指标上都没有价值。

### 6.1 主实验结果

### 6.2 预算与属性推断的发现
- 作者报告：即使只有一次扩展，方法在四个任务中仍明显优于 Provider 和 iAgent。
- 增大预算通常继续改善结果。
- Amazon 的成功率在约 0.6 附近趋于饱和。作者认为，从商品名称估计价格较困难，扩大候选池不能完全解决属性误判。

### 6.3 结论的证据边界
论文支持：**在这三个数据集的模拟环境中，不直接提供属性标签，也能显著改善用户指定的覆盖或平衡目标。**

但没有直接证明：
- 能减少真实新闻中的虚假信息或政治极化；
- 能改善长期用户福利；
- 能同时保持推荐相关性；
- 能支持任意复杂的自然语言约束。

这些属于研究动机或潜在应用，而非已验证结果。

## 7. 优点与亮点

- **用户控制权定位明确**：不依赖平台主动支持可控推荐，突出用户侧实现的价值。
- **降低标签准备负担**：利用 LLM 知识替代额外标注和分类器训练，尤其适合公开属性不足的场景。
- **突破单纯重排的上限**：主动发现初始列表之外的物品，能改变候选组成。
- **利用平台已有推荐能力**：通过推荐网络寻找相关候选，无需重建完整数据库或协同过滤系统。
- **实现流程简洁**：初始化、扩展、最终选择三个阶段清晰，结构化输出减少非法选择。
- **跨领域结果一致**：电影、音乐与商品任务均有提升，说明思路不局限于单一内容类型。
- **关注查询负担**：预算实验和缓存构想体现了对实际访问成本的考虑。

## 8. 不足与局限

### 8.1 方法局限
- **属性推断不可靠**：名称歧义、冷门内容、知识过时及动态价格都可能造成误判。
- **约束没有硬保证**：系统依据 LLM 估计筛选，无法确保真实标签满足要求；主实验成功率也未达到 100%。
- **受推荐图可达性限制**：如果目标类别不在有限预算可访问的区域内，方法无法发现它。
- **图距离不保证相关性**：多跳推荐可能逐渐偏离原始物品；论文没有量化相关性损失。
- **复杂约束尚未验证**：多属性同时平衡、连续属性、多目标冲突和不可满足要求等情况没有系统评估。

### 8.2 实验与偏差风险
- 缺少同查询预算探索基线和关键模块消融，难以准确归因。
- 公开数据集中的知名电影、艺术家可能更容易被 LLM 记忆，不能据此推断对新发布或长尾物品同样有效。
- 类别平衡和多样性不等于完整意义上的公平，也不自动意味着用户更满意。
- 政治立场等敏感属性可能受 LLM 训练偏差影响；用户甚至可能用同一机制强化自身信息茧房。
- 论文没有给出独立属性预测准确率，因此难以区分“探索失败”和“分类错误”。

### 8.3 实际应用限制
- 商业平台可能限制自动访问，页面结构变化也可能破坏 DOM 或请求解析。
- 用户侧控制不等于本地私密计算：向外部 LLM 提交物品和要求可能泄露兴趣信息。
- 成本、延迟、缓存效果与普通用户部署难度没有实测。
- 如果接入页面文本或搜索结果，还需要处理不可信内容和提示注入风险。
- 缓存可减少查询，但也可能造成推荐陈旧或候选覆盖不足。

**综合评价**：AgentRecommender 的主要贡献是将“无额外属性标签”和“主动扩展候选”结合到用户侧推荐中，提供了清晰、可行的概念验证。其约束满足结果具有说服力，但推荐质量、成本效率、探索策略的独立贡献以及真实平台适用性，仍需要更强的基线、消融实验和用户研究验证。
