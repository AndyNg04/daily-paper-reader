## 摘要
随着AI助手每天服务数百万用户，评估超越通用模型能力的用户体验（UX）变得日益重要。我们提出UXBench，这是首个基于真实用户反馈信号、以用户为中心的基准测试，用于评估偏好对齐和对话生成。该基准测试包含三个相互关联的任务：UX评判、UX评估和UX恢复，从主流中文AI助手的超过7万条交互日志中提取了7400个测试实例。该数据集紧密反映真实用户分布，涵盖8个场景、83个领域以及多种构成严峻挑战的失败模式。在26个前沿语言模型上的大量实验提供了新颖见解，揭示了模型如何感知用户体验以及模型能力的改进如何促进更好的对话参与度。通过对模型行为和性能差距的全面分析，我们表明用户反馈预测是一种可学习的能力，从野外反馈信号训练的奖励模型可以实现良好校准的准确性。我们进一步记录了LLM-as-a-judge评估协议的系统偏差，并比较了直接影响用户体验的典型响应策略。UXBench建立了新的评估格局，并呼吁更多关注定制的UX优化，为塑造AI助手成功的以用户为中心的扩展定律做出贡献。

## Abstract
As AI assistants serve millions of users daily, evaluating user experience (UX) beyond general model capability has become increasingly important. We present UXBench, the first user-centric benchmark grounded in real user feedback signals for evaluating preference alignment and dialogue generation. The benchmark consists of three interconnected tasks, UX Judge, UX Eval, and UX Recovery, with 7,400 test instances extracted from over 70K interaction logs of a mainstream Chinese AI assistant. The dataset closely reflects real user distributions, covering 8 scenarios, 83 domains, and diverse failure patterns that pose severe challenges. Extensive experiments on 26 frontier language models provide novel insights into how well models perceive user experience and how improvements in model capability contribute to better dialogue engagement. Through comprehensive analysis of model behavior and performance gaps, we show that user feedback prediction is a learnable capability, where a reward model trained from in-the-wild feedback signals can achieve well-calibrated accuracy. We further document the systematic biases of LLM-as-a-judge evaluation protocols and compare typical response strategies that directly affect user experience. UXBench establishes a new evaluation landscape and calls for greater attention to tailored UX optimization, contributing to a user-centric scaling law that shapes the success of AI assistants.

### 1. 论文的核心问题与整体含义（研究动机和背景）

- **核心问题**：现有大语言模型（LLM）基准（如 MT-Bench、AlpacaEval、Arena-Hard）主要评估模型在推理、知识、指令遵循等通用能力上的表现，**忽略了真实用户在使用 AI 助手时的主观体验（UX）**。模型在传统基准上的提升未必转化为更好的用户满意度，尤其当用户主要进行日常信息搜索或闲聊时。
- **研究背景**：AI 助手的长期成功依赖于用户留存和正向体验，但传统 UX 评估依赖人工参与（HCI 方法）或预定义维度，难以规模化且不能直接反映用户的即时反馈。现有 arena 式基准依赖 LLM 作为裁判，存在位置偏差和自我偏好等问题。
- **本文目标**：提出 **UXBench**，第一个基于真实用户反馈信号的自动化用户体验基准，用于评估 LLM 在用户反馈预测、对话生成和失败恢复方面的表现，从而推动模型开发更关注用户感知的效用。

### 2. 论文提出的方法论

- **核心思想**：将用户在真实交互中产生的显式（点赞/点踩）和隐式（重复提问、掠过、抱怨）反馈信号作为 **ground-truth 标签**，构建一个端到端的数据管线，自动从超过 70,000 条交互日志中提取测试用例。
- **关键技术细节**：
  - **数据管线**：原始对话日志 → 脱敏与清洗 → 行为信号提取（包括显式 dislike/like 和六种隐式负反馈信号，如重复、重述、掠过等）→ 多智能体系统（Miner 模型提出候选用例，Judge 模型打分）→ LLM 质量保证 + 人类专家验证。
  - **三个任务**：
    1. **UX Judge**：给定对话历史 + 当前轮 AI 回答，**二分类**预测用户是否满意（满意=1，不满意=0）。输出 JSON 格式 `{"verdict": 1}` 或 `{"verdict": -1}`。
    2. **UX Eval**：给定失败的用户查询（原始回答获负反馈），由待测模型**生成新回答**，然后用奖励模型评估该回答好（Good）的百分比。
    3. **UX Recovery**：在用户明确表达抱怨的场景下，模型需**生成恢复性回答**，恢复用户满意度；评估方式同 UX Eval。
  - **奖励模型（GRM）**：基于 Hunyuan-3（MoE 20B 活跃参数）训练一个点对点生成式奖励模型，输入为对话历史 + 用户查询 + 回答，输出自然语言评判和二元决策。训练数据来自同一 AI 助手（与测试集时间窗口不重叠）的约 17,000 条显式反馈实例。
  - 隐式负反馈检测公式（掠过模式）：  
    `gap_ratio_t = ∆τ_{t+1} / |r_{at}|`  
    其中 ∆τ_{t+1} 是用户下一轮输入与当前轮 AI 回答完成的时间差，|r_{at}| 是回答长度。

### 3. 实验设计

- **数据集与场景**：UXBench 包含 **7,400 个测试实例**（3 个任务：Task1 2000 条，Task2 4900 条，Task3 500 条），来自 **70,000+ 条真实交互日志**（主流中文 AI 助手）。覆盖 **8 个场景**（信息查询、知识、创意生成、日常、产品咨询、情感支持、工作等）和 **83 个领域**。平均对话轮次 5.29，大部分为多轮交互。负样本包含 10 种失败类型（冗余、任务未完成、意图误解等），正样本包含 8 种成功类型（准确回答、知识深度等）。
- **基准对比**：与三个英文对话生成基准 **Arena-Hard**、**WildBench**、**AlpacaEval** 进行跨基准泛化对比，使用相同的 GRM 评估器。
- **对比方法**：26 个前沿 LLM，涵盖 **Gemini**（2.5 Flash/Pro、3.0 Flash、3.1 Pro）、**OpenAI GPT**（5 mini/5/5.1/5.2/5.5）、**Anthropic Claude**（Sonnet 4.5、Opus 4.5/4.6/4.7）、**DeepSeek**（R1、V3、V3.2、V4 Pro）、**ByteDance Doubao**（Seed 1.6/2.0 Lite/2.0 Pro）、**Others**（Hunyuan 3、GLM-5/5.1、Kimi K2.5/K2.6、Qwen3.6-Plus）。另外还有自己训练的 **GRM**（Hunyuan-3 微调）。
- **人类验证**：5 名人类专家进行盲评（Task1 的 50 个示例标注，以及 Task2/3 的 30 对配对比较），验证 GRM 与人类的一致性。

### 4. 资源与算力

- **训练 GRM**：使用 **128 块 NVIDIA H20 GPU**，模型并行配置（上下文并行 8、流水线并行 8、虚拟流水线并行 5，MoE 路由器偏置开启）。学习率 4×10⁻⁶ → 最小 4×10⁻⁷，warmup 0.05，全局 batch size 128，训练 **1 个 epoch**（约 8500/类），每 50 步验证，每 100 步 checkpoint。
- **推理**：所有 LLM 通过 LiteLLM 兼容 API 调用，使用 deterministic 或低温度设置，输出 token 上限 20,000。未提及具体 GPU 时长或成本。

### 5. 实验数量与充分性

- **实验数量**：论文报告了 **大量实验**：三个任务上 26 个模型的完整结果（表 3）；多个消融实验（prompt 策略：用户建模、CoT、few-shot；推理努力高低；二元 vs 三类分类；不同 judge 模型（GPT-5.2、Gemini、Claude）的偏好偏差；五个模型在 7 个场景上的分解结果；6 个恢复策略统计分布）。
- **充分性**：实验设计系统，覆盖了性能、偏差、策略等多个维度。对比基线全面，包括最新和最知名的模型家族。消融实验针对关键因素（prompt、推理、分类粒度）。人类验证虽只有 30 对，但设计合理（同族、跨族、好坏）。**客观性**良好，但评估主要依赖自动 GRM，可能引入新偏差；人类验证样本量较小。实验均为中文场景，英文泛化性用三个英文基准做了初步验证。

### 6. 论文的主要结论与发现

1. **系统性正偏好偏差**：所有 26 个未微调模型在 UX Judge 中严重偏向预测“好”，召回“坏”的能力差（最佳模型 Claude Opus 4.7 坏准确率仅 61.5%，弱模型低至 11.6%）。
2. **二元分类优于三类分类**：引入“中性”类别后模型倾向于将难分的“坏”实例归类为中性，反而降低性能。
3. **用户建模提示有效**：明确推理用户画像（认知水平、情感状态等）可显著提高坏准确率（平均 +4.54pp），而通用 CoT 或 few-shot 效果有限。
4. **点对点 GRM 与真实验信号强对齐**：训练后的 GRM（Hunyuan-3 基座）在零样本下超越所有前沿模型，整体准确率 77.2%，坏准确率 72.4%。说明 UX 判断是可学习的能力。
5. **用户体验随模型进化呈弱增长**：更新模型通常优于旧版本（如 Gemini 3.1 Pro 比 2.5 Pro 高 6.3pp），但绝对增益有限；最佳模型在 UX Eval 仅 57.1% 好率，表明模型能力提升与用户感知满意度之间并非强相关。
6. **LLM-as-a-judge 存在严重自我偏好偏差**：点对点和配对评估均显示模型偏好自家产出，如 GPT-5.2 给 GPT 家族 80%+ 胜率，Gemini 给自家 75%+，而 Claude 反而低估自家。
7. **恢复策略影响显著**：大部分模型倾向道歉（45.98%）或同意（28.64%），较少直接修正（3.63%）。表现好的模型（如 Claude）更多使用幽默或轻松语气；差的模型（DeepSeek-V3）过度依赖澄清，导致用户流失。
8. **推理努力收益有限**：在做判断任务时有帮助（Task1 坏准确率提升 4-11pp），但在生成任务（Task2/3）上增益微弱。

### 7. 优点

- **数据真实**：基于大规模真实用户反馈（70K+ 日志），标签直接来源于用户行为，避免人工标注的偏差。
- **任务设计全面**：从判断（感知质量）到生成（响应质量）再到恢复（容错能力），覆盖用户体验完整的生命周期。
- **自动化数据管线**：支持动态更新，降低污染风险，可快速适应新话题和失败模式。
- **GRM 训练简洁有效**：仅使用原始反馈（无人工精选），在较小模型上达到高级别性能，展示了利用在线反馈进行模型对齐的潜力。
- **深入揭露偏差**：系统量化了 LLM 裁判的正偏好、自我偏好和家族偏好，为后续研究提供重要警示。
- **跨基准泛化验证**：虽然 UXBench 中文为主，但在英文基准上做了对比，发现排名有差异但趋势一致，说明基准的针对性。

### 8. 不足与局限

- **语言局限**：数据全部来自一个中文 AI 助手，测试实例为中文。结论对其他语言（如英语）的通用性需进一步验证。
- **评估依赖单一 GRM**：虽然 GRM 与人类有较高一致性，但自动化评估本身可能带有新的偏差，且人类验证样本仅 30 对，代表性有限。
- **恢复任务表现极低**（最高 12.8%），说明当前模型在该场景下几乎无用，基准难度可能过高，或者 GRM 对恢复响应用户满意度的判断标准与真实用户有差异。
- **计算开销**：训练 GRM 需要 128 块 H20 GPU，对一般研究组门槛较高。
- **数据采集伦理依赖 opt-in 用户**：参与体验计划的用户群体可能与普通用户存在差异，影响代表性。
- **未深入分析模型间差异原因**：虽然列举了失败和成功维度，但未对每个模型进行细粒度缺陷诊断（例如为什么某些模型在情感支持场景表现差）。
- **基准更新机制**：虽然宣称动态更新，但未展示随时间变化的迁移或难度曲线，更新频率和一致性未详细说明。
