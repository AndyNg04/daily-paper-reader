## 摘要
对非专家而言，编程机器人仍然具有挑战性，因为传统方法需要专业知识，即使是基于块的界面也常常缺乏灵活性。最近的研究探索了使用大语言模型（LLMs）从自然语言自动生成机器人程序，但这些系统仍然受到透明度不足、缺乏确保与用户意图一致的机制以及很少支持复用的限制。我们提出了APPROVE（基于可视化终端用户反馈的AI驱动的机器人编程），这是一个基于LLM的多模态终端用户编程框架，它将自然语言输入与基于块的界面以及明确的用户确认步骤集成在一起。生成的程序使用Blockly中的基于块的界面进行可视化，允许用户在执行前确认、修改或拒绝它们。确认的功能存储在库中以供复用，逐步构建一组可靠的程序组件。我们的方法为基于LLM的机器人编程贡献了一种以人为中心的设计，强调用户信任、意图一致性和可重用性。

## Abstract
Programming robots remains challenging for non-experts, as traditional methods require expert knowledge and even block-based interfaces often lack flexibility. Recent work has explored Large Language Models (LLMs) to automatically generate robot programs from natural language, but these systems remain limited by a lack of transparency, missing mechanisms to ensure alignment with user intent, and little support for reuse. We present APPROVE (AI-Powered Programming for Robots with Visual End-User Feedback), an LLM-based multi-modal end-user programming framework that integrates natural language input with a block-based interface and an explicit user confirmation step. Generated programs are visualized using a block-based interface in Blockly, allowing users to confirm, modify, or reject them before execution. Confirmed functions are stored in a library for reuse, gradually building a set of reliable program components. Our approach contributes a human-centered design for LLM-based robot programming that emphasizes user trust, intent alignment, and reusability.

- **核心问题**：机器人编程对非专家而言门槛过高。传统文本型编程需要专家知识，而现有的块状界面（如 Blockly）虽然降低了门槛，但灵活性不足，难以表达复杂逻辑。

### 2. 方法论：核心思想、关键技术细节、算法流程

#### 核心思想

> 将 **LLM 的生成能力** 与 **显式用户控制环节** 结合，构建一个"人机共同负责"的编程流程，让用户在可视化界面中检查、修改、确认或拒绝 LLM 生成的程序，在保证灵活性的同时提供透明度与可信度。

#### 系统架构与工作流程

系统命名为 **APPROVE**（AI-Powered Programming for Robots with Visual End-User Feedback），整体流程如下：

1. **自然语言输入**：用户通过文字描述任务意图。
2. **LLM 代码生成**：使用 OpenAI GPT-5 API 将自然语言直接映射为 Python 代码。选择 Python 而非直接生成块状代码的理由：
   - LLM 在 Python 语料上训练更充分，生成质量更高；
   - 新的原始功能（primitive）可轻松集成；
   - 支持通过 BlockMirror 同时以文本形式展示代码，兼顾偏好文本的用户。
3. **Blockly 可视化**：生成的 Python 代码通过 BlockMirror 自动转换为 Blockly 块状界面，用户可"一览无余"地审查程序逻辑（顶层函数优先展示）。
4. **三维仿真**：提供一个 3D 机器人仿真环境，用户可在执行前直观查看程序效果。
5. **三层用户操作选项**：
   - **确认（Confirm）**：采用**自底向上**的确认机制——高层函数只有在所依赖的子函数均被确认后方可被确认。确认后的函数被标记并在 UI 中存入函数库。
   - **手动编辑（Manually edit）**：用户可直接在 Blockly 中拖拽、重排、修改参数或从库中插入已有块。
   - **请求修改（Request edit）**：用户对当前代码状态（包括手动修改）附上文字指令，LLM 据此返回更新版本，然后再次进入用户检查循环。
6. **函数库积累**：被确认的函数携带名称、描述、参数签名及用户确认记录（用户身份 + 时间戳），存入库中，逐步积累可信赖的组件集合。
7. **约束生成空间**：代码生成被限制在预定义的可调用函数白名单和允许的 Python 内建函数范围内，从而限定可执行动作空间，保障安全性和可执行性。

#### 分层技能结构（Skill-Based Programming）

系统按技能式机器人编程的分层组织程序结构：

| 层级 | 名称 | 含义 | 示例 |
|------|------|------|------|
| 第 1 层 | Primitives | 设备级基本动作 | `move_to(pose, speed, frame)`、`get_current_pose()`、`open_gripper()`、`close_gripper(force)` |
| 第 2 层 | Services | 硬件无关的基础操作 | `get_object_pose(label)`（基于 Grounding DINO 的视觉目标检测与 3D 位姿估计） |
| 第 3 层 | Skills | 可复用的语义动作块 | pick、place、move、inspect |
| 第 4 层 | Tasks | 顶层任务编排，组合多个 skills | 完整"拾取-放置"流程 |

> 各层使用统一的数据表示，因此复杂任务本身也可被复用为更大行为中的子任务，支持模块化与可扩展性。

#### 关键设计要点：为什么确认环节交给用户而非系统？

- LLM 只能检查程序自身的逻辑一致性，但**无法验证程序是否匹配用户的主观意图**；
- 显式用户确认可以补偿 prompt 中可能存在的歧义与不精确；
- 让用户掌握最终控制权有助于建立信任（trust），体现了"正式工作协议"（formal work agreement）的理念——即使信任有限，明确的责任划分也能保障有效协作。

- **理论立场**：显式用户确认 + 以人为中心的设计，可同时促进透明度、可预测性和用户信任，是连接 LLM 生成能力与现实应用的可行桥梁。

### 7. 优点（方法/设计的亮点）

1. **针对真实工业痛点**：精准对接高混合低批量生产环境中非专家编程难的需求，应用场景明确、价值突出。
2. **以人为中心的设计理念**：
   - 将"最终确认权"显式交给用户，而非让系统自行判断，既能补偿 prompt 歧义，也符合信任机制设计的理论框架（引用了 Lee & See 2004、Castelfranchi & Falcone 2000、de Visser et al. 2020 等）。
   - 采用自底向上的逐级确认规则，逻辑严谨，确保高层函数的可靠性建立在已确认子函数之上。
3. **分层技能结构（4 层抽象）**：从 primitives 到 tasks 的统一表示，使不同粒度代码均可复用，符合工业界对模块化和标准化的需求。
4. **函数库 + 确认元数据**：每条确认记录含用户与时间戳，支持责任追踪，强化可追溯性；库作为 LLM 上下文的一部分还可引导模型复用已验证函数，降低出错概率。
5. **受限生成空间（白名单）**：限制 LLM 可调用的函数集合，在预留灵活性的同时框定安全边界，是面向实际部署的务实设计。
6. **灵活的修正途径**：同时支持 Blockly 手动编辑和自然语言请求修改，适配不同用户偏好。
7. **技术选型务实**：选择 Python 为 LLM 生成中间语言（而非直接输出 Blockly JSON），充分利用 LLM 在 Python 上的优势，再经 BlockMirror 转换为块状可视化，工程实现上简洁可靠。

### 8. 不足与局限

#### 实验与方法验证层面

- **验证规模极小**：3 名参与者的试点无法支撑关于"信任提升""意图对齐""效率改善"等核心主张的实证结论；
- **缺乏方法对比**：未与纯 LLM 方案（无确认环节）、纯块状编程、CAPIRCI 等已有系统进行受控比较，无法量化 APPROVE 的相对优势；
- **无用户专业背景分层**：未区分有/无编程经验的参与者，"对非专家友好"的声称缺乏分层数据的支持；
- **无纵向研究**：函数库随时间增长的实际收益（累计效应）仅是参与者主观感受，无客观数据验证。

#### 系统与应用层面

- **依赖商业闭源 API**：核心生成能力依赖 OpenAI GPT-5，存在成本、延迟、数据隐私和可用性风险（尤其对工业部署场景敏感）；
- **仅限仿真验证**：未在物理机器人上测试，程序从仿真到硬件的迁移可靠性是未知数；
- **基础原语集较小**：目前仅提供运动、夹爪和 3D 视觉感知等少量原语，覆盖面有限，作者也承认需扩展；
- **自然语言歧义处理不足**：系统目前按"直接生成"而非"主动澄清"的方式处理模糊指令，用户建议的澄清机制尚未实现；
- **无失败处理机制**：当用户确认了一个有缺陷的程序（或因疏忽、或因理解偏差），系统缺乏在仿真阶段自动提示异常的能力。

#### 学术规范性层面

- 未说明 pilot 研究的具体任务细节（如物品数量、障碍物等）、完成时间、操作次数等量度数据；
- 未报告参与者对系统可用性量表（如 SUS）的结果，只有描述性反馈。
