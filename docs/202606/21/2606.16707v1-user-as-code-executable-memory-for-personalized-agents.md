## 摘要
个性化AI智能体需要用户记忆：一个关于用户是谁的持久模型，通过多次对话构建并在每次新对话中参考。目前，这种记忆几乎总是以非结构化文本、知识图谱或扁平事实存储的形式存在，并通过检索——获取与当前请求最相似的条目——来参考。这种“事实袋”记忆能很好地回忆单个事实，但由于存储事实和据此行动是分离的步骤，它在解决矛盾、汇总多条记录或强制执行规则方面存在困难。我们认为用户记忆应该是可执行的。我们提出“用户即代码”（UaC）范式，其中智能体对用户的模型是一个活的软件项目：类型化的Python对象保存用户状态，普通Python函数编码管理状态的规则，因此在同一个媒介中表示和推理用户，解释器可以运行。其实现机制是一个两阶段流水线：一个只追加的日志永不丢弃事实，定期检查点化为类型化代码。这改变了记忆的能力。在标准的长对话基准测试中，UaC在召回率上既匹配全上下文上限，也匹配最强先前的记忆系统（LOCOMO上为78.8%）。其优势在表示至关重要的地方显现。在关于用户历史的聚合问题上——“我去年出国旅行了几次？”——基于检索的记忆崩溃（6-43%），而UaC保持近乎完美（99%），因为答案是对类型化状态的一行计算，而不是对文本的搜索。而且由于它的规则在状态变化时确定性执行，UaC能够发出未经请求的、安全关键的警报——例如新开的药物与几个月前记录的过敏相冲突——这是查询驱动记忆无法提供的功能。

## Abstract
A personalized AI agent needs a user memory: a persistent model of who the user is, built across many conversations and consulted on each new one. Today this memory is almost always stored as unstructured text, a knowledge graph, or a flat store of facts, and consulted by retrieval -- fetching the entries most similar to the current request. Such "bag-of-facts" memory recalls individual facts well, but because storing a fact and acting on it are separate steps, it struggles to resolve contradictions, aggregate over many records, or enforce rules. We argue that user memory should instead be executable. We introduce User as Code (UaC), a paradigm in which an agent's model of a user is a living software project: typed Python objects hold the user's state and ordinary Python functions encode the rules that govern it, so representing and reasoning about the user happen in one medium an interpreter can run. The enabling mechanism is a two-phase pipeline: an append-only log that never discards a fact, periodically checkpointed into typed code.   This changes what memory can do. On standard long-term conversation benchmarks, UaC matches both a full-context upper bound and the strongest prior memory systems on recall (78.8% on LOCOMO). Its advantage emerges where representation matters most. On aggregate questions over a user's history -- "how many international trips did I take last year?" -- retrieval-based memory collapses (6-43%) while UaC stays near-perfect (99%), because the answer is a one-line computation over typed state rather than a search over text. And because its rules execute deterministically whenever the state changes, UaC can surface unsolicited, safety-critical alerts -- such as a newly prescribed drug that conflicts with an allergy recorded months earlier -- a capability query-driven memory cannot provide.

**核心洞见**：用户记忆应改为“可执行的”。作者提出 **“用户即代码”（User as Code, UaC）范式**，将用户模型编码为一个活的软件项目：类型化Python对象保存状态，Python函数编码规则，使**表示与推理在同一可解释媒介中完成**。从而统一了存储、验证和计算。

**整体含义**：这项研究不仅改进了记忆系统的性能，更从根本上改变了记忆的**可表示性**——使记忆能够支持检索无法支持的聚合推理和主动服务（如跨会话药物冲突预警）。

## 2. 论文提出的方法论：核心思想、关键技术细节、算法流程

**核心思想**：两阶段流水线（Figure 1）。

- **第一阶段：记忆（Memorize）——追加式事实提取**  
  每个会话由LLM（Gemini 3 Flash）提取单个事实为扁平字符串，解析相对日期为绝对日期，**追加到列表中永不重写**。额外索引到ChromaDB。每会话约50-75个事实。

- **第二阶段：结构化（Structure）——定期生成类型化Python代码**  
  LLM从完整事实语料重新生成整个结构化的Python代码：使用 `date()` 表示日期，`list[T]` 表示集合，`notes: list[str]` 保存难以类型化的事实。代码是**从全部事实新鲜生成**，而非增量编辑，避免信息丢失。生成为 `state.py`、约束函数（`constraints/`）和概览清单（manifest）。

**检索策略**：多策略三通道组合：
1. **结构代码状态（[STATE]）**：当前域的 `state.py` 直接嵌入prompt（最多6000字符）。
2. **事实向量检索（[FACTS]）**：从事实列表的ChromaDB集合中查top-20。
3. **原始存档检索（[ARCHIVE]）**：从原始对话分块集合查top-10。

**主动服务循环**：生成-验证-审查循环。LLM编写约束函数 → 沙箱执行 → 结果审核 → 持久化。告警出现在清单的 `ACTIVE_ALERTS` 中，每次对话开始时自动加载（约200-300 tokens）。

**设计原则**：
- 分离结构与数据（schema vs instance）
- 统一表示与验证（代码同时承载存储和推理）
- 模块化按生活领域分区（travel/, health/, finance/ 等）
- 渐进披露（compact manifest + 按需加载）
- 代理原生文件系统（用户项目即目录）

- **模块化与渐进披露**：支持按域加载、紧凑概览，适合大规模用户状态。
- **实验充分且透明**：大量基准、消融、成本分析、跨LLM验证、跨家族裁判重判，统计严谨。开源代码为可复现性提供基础。

- **开发成本低**：不依赖自定义训练，直接使用现有LLM API。

## 8. 不足与局限

- **写入开销**：两阶段LLM调用增加初期成本（结构化一次性约7-102 m$/case）。虽然查询时摊销，但对少查询用户可能不划算。
- **结构化状态对纯召回中性**：通道消融显示结构化代码贡献仅－1.3pp（p=0.67），其主要价值在于聚合和约束。若只需单跳召回，UaC的结构化步骤不是必需的。
- **主动服务依赖流水线**：无预计算告警时UaC降至52.5%，说明约束生成和执行机制是主动服务的决定性因素，而非表示本身。
- **困难场景统计不足**：20个困难场景下UaC对live Mem0的统计差异不显著（p=0.69），需要更大样本量（约200）才能确认5pp效果。这是一个统计效能问题。
- **实验数据合成性**：分析推理基准是合成数据，整齐干净。真实用户数据噪声更大会影响解析和结构化质量。作者期望该情景更有利UaC，但未验证。
- **可扩展性上限**：当前Phase 2是全局新鲜生成，受限于LLM上下文窗口（约500K tokens，对应约100个会话）。超过需要层级结构化，论文仅提及未来工作。
- **重实现偏差**：同行骨干重实现使用了简化基础设施（ChromaDB代替MongoDB+Elasticsearch+Milvus等），可能低估原系统潜力。作者承认此点，但焦点是隔离表示变量。
- **跨LLM覆盖有限**：仅测试了Gemini 3 Flash和GPT-5.4。更小模型（如7B）可能生成低质量代码，鲁棒性未验证。
- **沙箱安全风险**：存储可执行代码需要严格沙箱和隔离，以防注入或泄漏。论文仅简要提及。
- **缺乏真人评估**：所有评估基于LLM Judge，尽管有跨家族验证，仍可能与人类判断存在偏差。
