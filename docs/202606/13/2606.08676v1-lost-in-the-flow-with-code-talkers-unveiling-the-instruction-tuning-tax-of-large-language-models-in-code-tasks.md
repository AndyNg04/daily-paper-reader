## 摘要
AI编码助手通过自动建议与用户意图一致的代码，显著提高了开发者的生产力，许多此类工具现已直接集成到集成开发环境（IDE）中。开发者以两种不同的认知模式与代码交互：心流模式和命令模式。尽管在心流模式下，开发者需要能够直接在不完整程序中补全或填充代码的工具，他们也同样需要能够理解以自然语言指令表达的意图并将其转化为可执行代码的命令模式工具。尽管经过指令微调的大语言模型（LLM）因其推断和实现开发者意图的能力而在许多应用场景中占据主导地位，但尚不清楚同样的范式是否同样适用于不同代码相关任务。因此，有必要理解指令微调如何影响CodeLLM作为编码助手的可行性。为了填补这一空白，我们进行了首次实证研究，揭示了指令微调在编程模式间引起的关键权衡，我们称之为指令微调代价。我们的结果表明，指令微调并非免费的午餐：尽管经过指令微调的模型更擅长遵循指令和利用结构化指导，但这些增益往往以削弱填充性能为代价。我们进一步通过定性和定量分析扩展了研究，包括人工失败分类、捕捉生成保真度的行为度量以及微调过程中的中间检查点评估。将我们的结果总结为七条发现和四点启示，我们的研究为AI驱动的编码工具开发提供了新视角，并强调了在指令遵循能力与有效代码生成辅助之间谨慎平衡的必要性。

## Abstract
AI coding assistants have significantly improved developer productivity by automatically suggesting code that aligns with user intent, and many of these tools are now integrated directly into Integrated Development Environments (IDEs). Developers interact with code in two distinct cognitive modes: Flow and Command. While developers require tools that directly complete or infill code in unfinished programs during Flow mode, they also need tools that can comprehend intentions expressed as natural-language instructions and convert them into executable code in Command mode. Although instruction-tuned Large Language Models (LLMs) dominate many application scenarios due to their abilities to infer and fulfill developers' intents, it remains unclear whether the same paradigm is equally suitable for different code-related tasks. Therefore, it is necessary to understand how instruction tuning affects the feasibility of CodeLLMs as coding assistants. To fill this gap, we conduct the first empirical study that uncovers a key trade-off caused by instruction tuning across programming modes, which we term the Instruction-Tuning Tax. Our results show that instruction tuning is not a free lunch: although instruction-tuned models are more capable of following instructions and leveraging structured guidance, these gains often come at the cost of weaker infilling performance. We further extend our study through both qualitative and quantitative analyses, including manual failure categorization, behavioral metrics that capture generation fidelity, and intermediate-checkpoint evaluation throughout the tuning process. Summarizing our results into seven findings and four implications, our study offers a new perspective on the development of AI-powered coding tools and highlights the need to carefully balance instruction-following ability with effective code generation assistance.

- **核心问题**：开发者与代码交互存在两种认知模式——**心流模式（Flow）**（需要代码补全/填充）和**命令模式（Command）**（需要理解自然语言指令生成代码）。当前指令微调（Instruction Tuning）的LLM在命令模式表现出色，但该范式是否同样适合心流模式的代码任务尚不清楚。论文旨在揭示指令微调对不同编程任务适用性的潜在权衡，即**指令微调代价（Instruction-Tuning Tax）**。
- **整体含义**：指令微调并非免费午餐：虽然提升指令遵循能力，但可能损害代码填充（infilling）等心流模式下的基础能力。这是首次系统实证研究该权衡，为AI编码工具开发提供新视角。

### 论文提出的方法论
- **核心思想**：通过对比基础模型（Base）与指令微调模型（Instruct）在多种代码任务上的表现，量化指令微调带来的性能权衡。结合定性（手动失败分类）和定量（行为度量）分析，并追踪微调过程中性能的演化。
- **关键技术细节**：
  - **任务形式化**：
    - 代码填充（Fill-in-the-Middle, FIM）：给定前缀和后缀，预测中间缺失片段，使用特殊标记（如 `<fim_prefix>`, `<fim_suffix>`, `<fim_middle>`）。
    - 指令遵循（Instruction Following）：使用聊天模板（如 `<INST>`, `<RESPONSE>`）将自然语言指令和代码上下文作为输入。
    - 代码补全（Code Completion）：给定上下文代码和注释/docstring，左到右预测后续代码。
  - **统计分析**：使用**McNemar检验**评估Base与Instruct模型在个体实例上的差异显著性。
  - **行为度量**：设计三个规则指标：
    - **代码-令牌比率（CTR）**：代码类令牌数占总令牌数的比例。
    - **自然语言率（NL）**：包含特定话语标记或高字母/低代码标点符号的样本比例。
    - **额外函数/类声明率（Def/Cls）**：包含多余 `def` 或 `class` 定义的样本比例。
  - **中间检查点分析**：采用Magicoder管道，将Qwen2.5-Coder-7B分为两个阶段（OSS-Instruct-75K和Evol-Instruct-110K），每个阶段取多个数据比例（5%, 10%, 20%, …, 100%）得到共12个检查点，评估性能演化。

### 论文的主要结论与发现
- **发现1**：指令微调代价在大多数情况下存在，但幅度因模型家族而异。
- **发现2**：Instruct模型擅长利用结构化自然语言指导，但代价是infilling能力下降。
- **发现3**：增加模型规模不一定能消除指令微调代价，其效果因模型家族不同。
- **发现4**：Base和Instruct模型正确解重叠较多，但各自专长不同：Base模型独占解决更多FIM问题，Instruct模型独占解决更多补全问题。
- **发现5**：手动失败分析表明，指令微调使失败模式向冗余代码和无关自然语言偏移（verbosity）。
- **发现6**：行为度量证明verbosity趋势是系统性的：Instruct模型在补全任务中更易产生额外自然语言和函数/类定义；FIM任务受结构约束，输出更聚焦。
- **发现7**：指令微调对能力的影响非单调且因任务而异：指令遵循能力持续提升，infilling整体下降，补全在aggregate上仍有增益但后期减弱。不同补全benchmark表现不同（ClassEval-Completion提升，BigCodeBench-Complete下降）。

### 优点
- **首次系统揭示指令微调代价**，填补领域空白。
- **多维度分析**：结合定量评估、统计检验、手动失败分类、行为度量、中间检查点演化。
- **手动分类具有较高可靠性**（Cohen's κ=0.8234）。
- **设计行为度量**（CTR, NL, Def/Cls）用于大规模捕捉生成保真度，实用性强。
- **提供实践启示**：针对研究人员（探索模型特定因素、设计更鲁棒训练策略）和从业者（根据失败模式设计部署防护、考虑任务路由架构）。

### 不足与局限
- **数据泄露威胁**：使用公共benchmark，无法排除模型训练时见过部分数据。
- **模型选择有限**：仅研究Qwen2.5-Coder和DeepSeek-Coder两大家族，可能不代表所有CodeLLM。
- **指令微调设置规模有限**：RQ3仅复现Magicoder管道，与厂商完整后训练流程有差距，结论不可直接泛化。
- **任务范围偏向函数级**：未覆盖仓库级、多文件编辑等更复杂场景（如vibe coding）。
- **部署上下文为离线**：未考虑真实用户迭代交互可能放大或削弱权衡。
- **行为度量本身有近似性**：CTR基于词法分词器，不能完美区分代码与自然语言。
