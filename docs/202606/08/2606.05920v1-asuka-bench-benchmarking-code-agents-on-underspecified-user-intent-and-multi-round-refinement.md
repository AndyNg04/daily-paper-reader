## 摘要
现有的代码生成基准测试只评测从完整提示到一次性输出的单一映射。然而，实际网页开发并非如此。用户很少在开始时写出完整规格；许多需求只有在看到中间结果并对其作出反应后才变得清晰。我们提出Asuka-Bench，一个将未明确用户意图与多轮迭代优化相结合的基准测试，基于浏览器渲染的行为。每个任务通过一个闭环解决：代码智能体生成网页项目，UI智能体在部署的站点上执行测试用例，用户大语言模型将评估结果转换为下一轮的自然语言反馈。该基准测试包含50个网页任务，784条评估标准和2402个预期结果。我们在2个智能体框架上对8个大语言模型进行了基准测试。结果清楚地区分了模型：加权任务通过率相差38个百分点，模型在从反馈中修复的能力上也显著不同。Asuka-Bench也远未饱和：即使是最强的模型，经过三轮后也只完成了52%的项目。

## Abstract
Existing code-generation benchmarks score a single mapping from a complete prompt to a one-shot output. However, real web development is different. Users seldom write a full spec at the start; many requirements only become clear once they look at an intermediate result and react to it. We present Asuka-Bench, a benchmark that pairs underspecified user intent with multi-round refinement, grounded in browser-rendered behavior. Each task is resolved through a closed loop: a Code Agent generates a web project, a UI Agent executes test cases on the deployed site, and a User LLM turns evaluation outcomes into natural-language feedback for the next round. The benchmark comprises 50 web tasks with 784 evaluation criteria and 2402 expected outcomes. We benchmark 8 LLMs across 2 agent frameworks. The results separate models clearly: weighted Task Pass Rate varies by 38 percentage points and models also differ substantially in their ability to repair from feedback. Asuka-Bench is also far from saturated: even the strongest model completes only 52% of projects after three rounds.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **现有基准的局限**：当前代码生成基准（如 HumanEval、SWE-Bench、WebGen-Bench 等）普遍采用 **“完整提示→单次输出”** 的静态测评范式。它们假设用户一开始就提供明确的、完整的规格说明，并且只评估模型一次性生成的正确性。
- **真实世界的不匹配**：实际网页开发中，用户往往只给出**模糊的初始需求**，随着看到中间结果和直观反馈，需求才逐步明确和细化。因此，真正重要的能力不是一次性命中完整规格，而是在**多轮交互反馈中不断收敛**。
- **目标**：提出第一个系统评估代码智能体在**未明确用户意图 + 多轮交互优化**场景下表现的基准——**Asuka-Bench**，专注于**浏览器渲染行为**层面的功能验证，而非仅看源码静态分析。

## 2. 论文提出的方法论：核心思想、关键技术细节

### 2.1 整体框架（闭环流程）

每个任务通过一个闭环系统解决，包含四个角色：

1. **任务规格生成**：从多个来源采集原始查询，经LLM改写为“清晰的产品需求文档（Clarified PRD）”，再从PRD中抽象出**故意模糊的初始查询**（仅包含高层意图，无实现细节），同时生成**模拟测试数据**和**评估标准集合**。
2. **代码智能体（Code Agent）**：基于大语言模型（如GPT-5.4、Claude-4.6-Sonnet等）和智能体框架（OpenHands 或 Claude Code），接收模糊查询，生成或迭代修改一个完整的Web前端项目（HTML/CSS/JS，无后端依赖）。
3. **UI智能体（UI Agent）**：在部署的浏览器环境中执行预定义的评估标准，模拟用户交互（点击、输入、导航等），返回每个标准的 **Pass/Fail** 结果，失败时附带解释。基于 **GPT-5.4** 视觉能力驱动。
4. **用户大语言模型（User LLM）**：将UI智能体的结果综合为结构化自然语言反馈，返回给代码智能体进行下一轮迭代。

闭环重复直到所有标准通过或达到预设轮数（论文默认3轮，扩展实验可达8轮）。

### 2.2 关键设计：DAG感知的评估协议

- 每个PRD的评估任务组织成**有向无环图（DAG）**，节点代表任务（Presence/Functionality/Robustness三类），边表示**前置依赖**（例如：只有确认UI元素存在后，才能测试交互功能）。
- 评估时按拓扑顺序执行：只有所有前置任务通过（或达到**软满足阈值 T=0.5**，即50%子标准通过），当前任务才执行；否则跳过。这避免了下游任务因上游缺陷而被无效浪费地执行，聚焦于根因。
- 使用**软满足阈值** 避免了过于严格（T=1.0）导致的过度阻塞。实验表明，软阈值下DAG阻断造成的分数偏差仅0.6 pp（严格版为6.0 pp），且将评估token消耗降低23-26%。

### 2.3 数据集构建

- **查询来源**：三种互补来源（在线用户真实请求、GitHub开源仓库、现有知名网站），经过脱敏、过滤、形式化。
- **规模**：50个Web开发任务，涵盖6个应用类别（实用工具38%、数据可视化22%、管理系统20%、电商8%、营销展示6%、社交6%）。共包含784个评估任务、2402个预期结果，平均每个任务15.7个评估子项。
- **任务类型权重**：功能型任务占62.8%，鲁棒性任务20.8%，存在性任务16.5%，平均难度权重2.96。DAG平均深度4.4层（最大9层）。

## 6. 论文的主要结论与发现

1. **模型区分度高**：加权任务通过率三轮后从 51.8% 到 90.1%，相差38个百分点；项目完成率从 8% 到 52%，顶级模型远未饱和。
2. **修复能力与初始生成能力解耦**：例如 Kimi-K2.6 首轮仅 44.3%，但通过良好反馈利用升至 86.6%，修复能力比首轮生成能力更强。单轮评估会混淆两个维度。
3. **三轮迭代显著提升**：多数增益在第二轮（~25 pp），第三轮增益约7-13 pp。即使最强模型，三轮后项目完成率仅 46-52%，说明基准远未饱和。
4. **模糊查询+多轮可以超越一次完整PRD**：所有模型在三轮模糊查询下的最终通过率，都超过了直接用完整PRD单轮生成的效果（净增益8.7-26.6 pp）。
5. **DAG协议高效且聚焦**：相比Flat评估，DAG协议减少23-26% token消耗，修复率更高（最高61.8% vs 45.9%）。
6. **鲁棒性任务最难**：存在性任务通过率最高（68-98%），功能性次之（53-90%），鲁棒性最低（42-88%）。模型差距在鲁棒性上最大。
7. **框架差异**：OpenHands项目完成率略高（5模型均值 29.2% vs 25.6%），但Claude Code更高效（1.8倍速度），且失败模式不同（Claude Code多为“接近成功”项目，OpenHands更多进程管理死锁）。

## 7. 优点：方法或实验设计上的亮点

- **开创性设定**：首次系统研究代码智能体在**模糊意图+多轮交互反馈**下的表现，填补了现有单轮静态基准的空白。
- **闭环生态真实模拟**：复用真实的代码生成-部署-测试-反馈流程，且反馈基于浏览器渲染行为而非源码静态检查，更贴近用户实际体验。
- **DAG感知评估**：通过依赖拓扑避免无效测试和冗余反馈，同时保证评估聚焦根因，效率高且结果解释性强。
- **人类对齐验证**：用专家标注验证自动化评估的可靠性，表明方法可靠。
- **饱和分析**：延长至8轮确认任务均可达，排除了任务不可解或反馈引入噪声的质疑。

## 8. 不足与局限

### 8.1 领域覆盖有限
- 仅包含6类Web应用（50任务），且均为**自包含前端项目+模拟数据**。3D场景、实时协作应用、真实后端依赖场景未覆盖。未来需扩展数据管道和部署基础设施。

### 8.2 评估器依赖
- UI Agent和User LLM均固定使用**GPT-5.4**。虽然人工验证准确率高，但更换评估骨干模型（如使用开源模型）可能会影响绝对分数。单标注者也有潜在偏差（论文仅单人标注，未做多标注者一致性检验）。

### 8.3 静态基准易受污染
- 与所有静态基准一样，Asuka-Bench的模糊查询和评估DAG可能在后续训练中被模型记忆。长期抗污染需定期更新任务池（作者将其作为未来方向）。

### 8.4 计算开销与可复现性
- 每任务运行一次，缺乏多次随机种子重复（如温度、搜索策略的随机性）。置信区间基于正态近似，对接近0/1的PCR指标可能不理想。
- 未报告具体训练/推理算力，影响复现成本估算。

### 8.5 反馈机制局限性
- 反馈由User LLM（GPT-5.4）统一生成，可能不符合所有用户的表达风格。反馈质量高度依赖于评估智能体的判断准确性；若评估错误（如误判Pass/Fail），可能导致修复方向错误。但人类验证表明错误率约5-6%。
