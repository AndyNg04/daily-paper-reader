## 摘要
自主软件代理有望提高开发人员生产力，但会犯错并表现出新的故障模式，使得人类监督成为成功人机协作的核心。现有关于代理监督的研究大多是概念性的；存在规范性框架，但用户实际如何监督代理却知之甚少。在本文中，我们通过为代理监督的理论讨论提供早期经验锚点来弥合这一差距。基于对17位经验丰富的开发人员的访谈，我们进行了一项探索性调查，考察开发人员执行的监督工作的形式、时间及方式。我们还记录了开发人员面临的监督挑战以及他们开始使用的应对策略。我们发现至少四种新兴的监督工作形式：先验控制、协同规划、实时监控和事后审查。我们表明监督工作不仅是现有研究中所描绘的反应性和回顾性的，而且也是预防性和主动性的。我们描述了情境化的监督挑战（例如，难以审查代理生成的代码）并概述了开发人员为解决此类挑战而采用的启发式方法（例如，使用测试结果作为代码正确性的保证）。最后，我们总结了高层次启示、未来研究方向、对以人为中心的软件代理设计及软件工程实践的意义，以及本研究的局限性。

## Abstract
Autonomous software agents hold promise to increase developer productivity but make mistakes and exhibit novel failure modes, making human oversight central to successful human-agent collaboration. Existing research on agent oversight is largely conceptual; normative frameworks exist, but how users actually oversee agents is less known. In this paper, we bridge this gap by providing early empirical anchors for the theoretical discourse on agent oversight. Drawing on interviews with 17 experienced developers, we conduct an exploratory inquiry examining what forms of emergent oversight work developers perform, when, and how. We also document the oversight challenges developers face and the strategies they have started using to address them. We found at least four forms of emergent oversight work: a priori control, co-planning, real-time monitoring, and post hoc review. We show that oversight work is not only reactive and retrospective, as portrayed in existing research, but also preventative and proactive. We describe situated oversight challenges (e.g., difficulty reviewing agent-generated code) and outline heuristics developers adopt to address such challenges (e.g., using test results as guarantees for code correctness). We conclude with high-level takeaways, future research directions, implications for the human-centered design of software agents and for software engineering practice, and limitations of our research.

#### 6. 论文的主要结论与发现

- **监督工作的四种形式**：
    1.  **先验控制**：在任务开始前对代理进行预防性配置和约束（如设置自定义指令、限制文件访问）。这是主动的、预防性的监督。
    2.  **协同规划**：在执行前与代理共同制定计划、分解任务、提供部分代码示例以引导其方向。这是主动的、引导性的监督。
    3.  **实时监控**：在代理执行过程中观察其行为和推理过程，并在必要时进行干预（如暂停、重定向）。实践中开发者很少进行细致的监控。
    4.  **事后审查**：在代理工作完成后，审查其生成的代码、测试结果和变更日志。这是反应性的、评估性的监督，也是研究中最常被讨论的形式。
- **监督不仅是反应性，更是预防性和主动性的**：研究挑战了现有文献将监督主要视为事后检查和反应式干预的观点。开发者的监督工作始于**配置和规划阶段**。
- **重要启发式策略**：开发者面对过于复杂和不可预测的代理系统，并非追求“完美的监督”，而是发展出**高效、满意即可（satisficing）** 的启发式策略：
    1.  **计划即工作代理**：将代理生成的计划视为其实际执行的可靠替代品，通过审查计划来替代部分代码审查。
    2.  **测试结果即正确性证明**：依赖测试套件的结果来判断代码正确性，如果所有测试通过，则信任代理的代码。
    3.  **扫视式检查**：通过对变化摘要、差异（diff）工具的“扫视”来快速定位问题，而非逐行审查。
    4.  **信任新信息**：当面对不熟悉的库或技术时，开发者倾向于默认信任代理的判断。
- **“开发者-管理者”角色转型**：软件工程实践正从传统的“工匠”模式，向“开发者-管理者”角色转变，其核心技能从编码转向架构设计、指导和审查。

- **发现富有洞察力**：指出监督的“预防性”和“主动性”维度，以及开发者采用的“满意化”启发式，这些发现深刻挑战并丰富了现有理论。揭示了理想化的治理要求与复杂的实践现实之间的张力。

#### 8. 不足与局限

- **样本偏差**：大部分参与者（12/17）来自同一家财力雄厚的大型科技公司，这意味着他们的实践可能受到特定工具、资源（如无限访问顶级模型）、企业文化（如安全规范、文档要求）和计算成本的严重影响，结果难以推广到中小型企业或资源受限的团队。

- **任务范围局限**：参与者在生产中只将**小型、边界明确的任务**委托给代理，这简化了事后审查的难度，并使得“实时监控”显得不那么重要。研究未能涵盖代理处理大型、长期、复杂任务时可能出现的全新监督挑战。
- **探索性质**：作为探索性研究，其发现的模式（监督形式、启发式）虽然具有启发性，但**无法验证其普适性或统计显著性**。结论是假设性的，需要后续更大规模、更多样化的研究来证实和细化。
