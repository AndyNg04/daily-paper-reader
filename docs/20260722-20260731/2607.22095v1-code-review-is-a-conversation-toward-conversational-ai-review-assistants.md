## 摘要
基于AI的代码评审工具日益承诺帮助开发者检查拉取请求、识别缺陷并提高代码质量。然而，当前大多数方法将代码评审框定为一次性评论任务：给定一个差异（diff），系统产生警告或建议。这种框定忽视了现代代码评审的一个核心属性：评审是一场对话。人类评审者不仅对代码发表评论；他们还会提出问题、解释期望、协商设计权衡、要求提供证据、传递项目知识、记录决策理由，并共同决定某个更改是否足够好以被整合。在这篇愿景论文中，我们主张构建对话式AI评审助手：这类系统作为交互式伙伴而非静态评论生成器参与代码评审。此类助手应能识别何时需要对话、提出有根据的问题、回应开发者的解释、总结未解决的问题、帮助捕获决策理由，并知道何时应放弃或升级给人类评审者。这种范式转变还需要新颖的评估方法论。我们概述了一个研究议程，用于研究评审对话、设计对话式AI评审能力，并评估其对软件演化和维护的影响。我们的愿景将AI代码评审从自动化评论重新定义为整合前的人机协同理解。

## Abstract
AI-based code review tools increasingly promise to help developers inspect pull requests, identify defects, and improve code quality. Yet most current approaches frame code review as a one-shot commenting task: given a diff, the system produces warnings or suggestions. This framing overlooks a central property of modern code review: review is a conversation. Human reviewers do not merely comment on code; they ask questions, explain expectations, negotiate design trade-offs, request evidence, transfer project knowledge, document rationale, and collectively decide whether a change is good enough to integrate. In this vision paper, we argue for conversational AI review assistants: systems that participate in code review as interactive partners rather than static comment generators. Such assistants should identify when conversation is needed, ask grounded questions, respond to developer explanations, summarize unresolved issues, help capture rationale, and know when to abstain or escalate to human reviewers. Such a paradigm shift requires novel evaluation methodologies as well. We outline a research agenda for studying review conversations, designing conversational AI review capabilities, and evaluating their impact on software evolution and maintenance. Our vision reframes AI code review from automated commenting to human-AI sensemaking before integration.

### 2. 方法论：核心思想与技术路径

- **范式批判**：
  - 当前数据集构造方式（将评审简化为 `代码变更→评审评论` 或 `代码→评论→修订` 三元组）会大量滤除不含代码修改的对话式交互（如提问、解释、协商、延期决策等），导致模型学习到的评审行为是“被剥离对话本质的残渣”。
  - 当前评审基准大多以“是否发现缺陷”或“反馈是否有用”为评估核心，仍未将对话性互动（澄清意图、比较方案、记录理由、放弃干预等）纳入主要评估目标。
- **核心框架——对话行为空间**：作者提出**评审应围绕对话行为而非评论生成进行设计**，具体包括8种典型对话行为（表II亦有真实PR示例）：

| 行为 | 目的与示例 |
|---|---|
| 提问（Ask） | 揭示隐藏假设或未说出的前提（如：这是否是兼容性处理的一种预期行为？） |
| 请求证据（Request evidence） | 将判断或决定可验证化（如：建议补充回归测试或基准数据） |
| 解释（Explain） | 传递项目约定与历史决策背景（如：本项目惯例是…） |
| 比较（Compare） | 支持设计权衡讨论（如：对比两种实现方案的维护代价） |
| 总结（Summarize） | 保留讨论状态，明确已解决和未解决事项 |
| 升级（Escalate） | 承认人类权威，将架构性决策交由维护者确认 |
| 弃权（Abstain） | 对微弱、重复或超出能力范围的关切保持沉默，避免噪音负担 |
- **操作化——状态型循环（五阶段模型）**：
  1. **观察**（Observe）：读取当前评审状态——现有评论、作者回复、新提交、测试结果、关联issue等；
  2. **估计**（Estimate）：判断干预是否可能改进评审进程，或仅增加噪音；
  3. **选择**（Select）：从上述行为空间中选择行为（提问、请求证据、解释、比较、总结、升级、弃权等）；
  4. **更新**（Update）：将作者回复、新提交、测试结果等融合回评审状态表征；
  5. **闭合**（Close）：临近合入时，帮助团队记录已做决定、依据证据以及被有意延迟或拒绝的关切。
- **评估维度**（核心主张）：不以评论相似度为评估标准，而应从“对评审状态与决策的影响”出发：不确定性是否减少、证据是否产出、理由是否被捕获、开发者负担如何、干预校准是否良好、维护成效（如返工率、回滚率）如何。

### 6. 主要结论与发现

- **主要发现**：当前AI评审从数据构造、系统设计到评估都系统性地剥离了评审的对话本质，这使得AI评审工具即便技术上强大也可能在真实工作流中低效甚至起反效果。
- **核心结论**：下一代AI代码评审不应仅追求生成更多“更好的评论”，而应追求支持评审过程中的协作理解——“重新框定为整合前的人机协同意义建构（human-AI sensemaking before integration）”。
- **价值转移**：评审的核心价值不仅是最终被合入的补丁，而是评审过程中产生的知识（意图澄清、证据、权衡比较、决策理由），AI应帮助捕获和保存这些知识以促进软件长期可维护性。
