## Abstract
Context: Conversational Large Language Models (CLLMs) can automatically generate code by collaborating with users through natural language. However, poor collaboration can lead to poor quality output.   Objective: This exploratory study aims to investigate how humans and CLLMs can collaborate as peers through vibe coding, an approach that integrates principles from prompt engineering, agile design, and human-AI co-creation to enhance collaboration.   Method: We designed four interaction models representing different collaboration patterns in the software development process: the solo model (human-only development), the collaborative model (human-CLLM collaboration), the fully automated model (development autonomously performed by a CLLM), and the agentic model (development autonomously performed by the MetaGPT~X platform). Based on these models, we implemented corresponding Test-Driven Development (TDD) workflows using structured prompts and Python scripts. We then conducted a controlled pre-experimental study with TDD professionals to compare the solo and collaborative workflows. **作者**：Moritz Mock, Barbara Russo（博尔扎诺自由大学）

- **核心问题**：人类与 CLLMs 如何以对等（peer）身份进行高质量协作？在不同的自动化程度（从 vibe coding 到 agentic coding）下，哪种交互模式更适合何种开发目标？

## 方法论

### 核心思想

提出四层方法论：①设计人类与 CLLM 交互模型；②定义支撑交互的提示（prompts）；③将开发流程建模为工作流；④评估产物质量与流程效率。核心创新在于将 TDD 这一迭代开发流程与人机协作模式结合，通过结构化提示（structured prompts）和 Python 脚本自动化驱动 CLLM，实现不同自动化程度的开发流程。

### 四种交互模型

1. **solo-coding（单独模型）**：纯人类开发，仅人类编写生产代码和测试代码，遵循 TDD 实践（如 Assertion First），无 CLLM 参与。
2. **collaborative（协作模型）**：人类与 CLLM 以预定义角色协作（人类编写测试，CLLM 生成生产代码），遵循 TDD 实践，通过脚本支持自动化交互，属于"vibe coding"。
3. **fully-automated（全自动模型）**：单个 CLLM 同时编写测试和生产代码，整个 TDD 流程通过脚本全自动执行，人类仅触发初始步骤。
4. **agentic（代理模型）**：整个开发流程完全委托给代理平台（如 MetaGPT X），平台通过多个具有专业角色的 AI 代理按标准操作流程（SOP）自主规划、执行、测试和迭代，人类仅触发初始目标设定。

### 关键技术细节

- **提示设计**：从 White 等人的提示模式目录中选取组合了 Game Play、Persona、Template、Context Manager、Question Refinement 五种模式，分别设计测试代码和生成代码的提示；提示包含参数化占位符（如 `<error trace>`、`<test code>`、`<existing test code>`），参数值随 TDD 迭代阶段变化；首轮与后续轮次使用不同的提示模板（首轮无既有代码，后续轮次纳入全部既有测试与生产代码）；每次迭代作为新的交互会话执行，防止 CLLM 被先前迭代所偏置。
- **工作流实现**：通过自动化工具箱实现——AI Handler 负责 API 交互（GPT-3.5 Turbo）、Collaborative Runner 处理协作模式、Fully Automated Runner 处理全自动模式、Tester Handler 模拟测试者角色、Developer Handler 模拟开发者角色、Log Collector 收集错误追踪；同一测试不通过时最多自动重试五次（repetitions），超过则中断并交回人工处理（协作模式）或由 CLLM 自主重构（全自动模式）。
- **评估框架**：三维度——生产代码质量（语法相似性 LCS/LED、功能正确性 TPR、结构复杂度 MCC 及基线测试的语句/分支覆盖率 SCB/BCB）、测试代码质量（结构复杂度 TAM/TM、对代码的覆盖率 SC/BC）、流程效率（迭代次数、完成时间）；基线测试套件采用 category-partition testing（类别划分测试）设计。
- **统计方法**：先用 Kruskal-Wallis H 检验检测组间差异，再用 Mann-Whitney U 检验做两两比较，采用 Holm-Bonferroni（HB）多重比较校正控制错误率，报告 Cliff's delta 效应量。

## 主要结论与发现

- **生产代码质量（RQ1）**：agentic 工作流的功能正确性（TPR 94.58%）显著高于其他工作流，且与其他流程有显著差异，但代码结构复杂度（MCC）也显著更高，基线测试的覆盖率（BCB）反而更低——代理引入了规范未要求的额外实现决策，形成未测试的决策点；人类参与的流程 TPR 变异性大，但个别参与者（如 P13）能达到与 agentic 相当的 100% 正确率。
- **测试代码质量（RQ2）**：人类参与的工作流（solo 和 collaborative）产出组织更接近基线测试套件的测试代码；solo-coding 的语句/分支覆盖率显著高于 agentic 工作流；fully-automated 的测试最少且最不完整（固定 3 个测试方法、每方法 1 条断言）。
- **流程效率（RQ3）**：agentic 最快（平均 75 秒），fully-automated 次之（约 800 秒），均显著快于人类参与的流程；collaborative 虽比 solo 迭代次数少，但经常需要重写断言（平均 12.1 次迭代中 5.6 次涉及断言返工），反映了额外的协调成本。
- **总体判断**：交互模型的选择应取决于开发目标——追求快速且功能正确的生产代码选 agentic；追求高质量、组织良好的测试套件选人类参与的流程；collaborative 是在自动化与人类专长之间的折中，但需要更好的交互机制来降低协调开销。
- **更深层发现**：精确复现软件开发过程工作流仍是一个开放问题，即使用新的 agentic 技术亦如此——现有代理平台（如 MetaGPT X 的 SOP）无法完整捕捉 TDD 这类迭代增量式开发流程。

## 不足与局限

- **样本量有限**：人工实验仅 16 名专业人员，统计效力受限；论文自认属于探索性研究，结论不宜过度泛化。
- **模型选择偏旧**：人工协作与全自动流程使用 GPT-3.5 Turbo（相对较旧的模型），仅代理流程使用较先进模型（GPT-5/Claude Sonnet 4），不同流程之间的模型能力差异可能对结果有干扰。
- **提示未做优化**：论文明确表示"不试图优化提示以获得最大模型性能"，提示设计本身可能不是最优的，限制了结论对提示工程的普适性。
- **任务代表性有限**：仅两个简单的字符串居中函数，不涉及复杂 API、类结构或跨模块依赖，对真实工业级开发场景的推广性存疑。
- **评估环境不一致**：人类参与的流程在受控实验环境（限时 40 分钟、屏幕共享监控）中评估，而自动化流程在不受限的脚本执行中评估，两者的"时间"度量含义不同（自报 vs 运行时采集），可能影响公平性。
- **迭代数据缺失**：代理工作流因 MetaGPT X 的 SOP 机制无法记录 TDD 迭代次数，导致 RQ3 中 agentic 的迭代指标为空，降低了该维度比较的完整性。
- **未披露算力资源**：没有报告 GPU 型号、数量、推理时长等算力信息，不利于其他研究者评估资源需求。
- **外部效度受限**：参与者的 TDD/Python 经验不一，且实验任务简单，对经验差异不敏感；测试基线本身不测试 setter 方法，与多数人类参与者的测试选择不一致，可能扭曲 TPR 的比较基准。
- **定性反馈有限**：采纳了参与者对实验难易的主观判断，但部分表现不佳的参与者仍将任务评为"简单"，说明主观反馈与客观指标之间的偏差未被深度解析。
