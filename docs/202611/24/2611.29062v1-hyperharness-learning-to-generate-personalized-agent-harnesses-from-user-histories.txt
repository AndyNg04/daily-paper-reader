## Abstract 

Personalized LLM agents rely on an agent harness , the surrounding memory and control code, to con-nect user history with downstream decisions. Existing methods typically employ either a single shared memory workflow across all users, which is efficient to deploy but cannot adapt how evidence is retrieved and interpreted across diverse histories, or per-user harness optimization, which customizes behavior for each user but requires costly repeated candidate evaluation at deployment and suffers from sparse, noisy supervision in raw logs. To address this trade-off, we present H YPER HARNESS , a framework that learns a shared history-to-harness generator to synthesize executable, user-specific retrieval and answer-guidance code directly from user histories. Given a user’s permitted history, H YPER HARNESS prompts a construction LLM to write personalized retrieval and guidance functions, while downstream task scores across training users supervise iterative refinements to the shared generator without reference harnesses or answering-model updates. At deployment, the frozen generator constructs a harness for each unseen user in a single pass from history alone, eliminating per-user task-scored search. Across three benchmarks (Person-aMemv3, Mem-PAL, and MemoryCD) and three answering models ( Qwen3.5-9B , Qwen3.8-27B , and 

GPT-5.6-Luna ), H YPER HARNESS achieves the highest aggregate score in seven of nine settings and ranks second in the remaining two, improving over the strongest baselines by up to 5.95 points while cutting matched answer-time tokens by 90.32% over long-context prompting. Analyses show that optimization tailors context allocation to each executor, transfers to unseen user clusters, and amortizes adaptation costs.

Personalization is a core component of user-facing AI systems because it connects raw user behavior with downstream decisions about what content, recommendations, or responses should be presented to each individual (Tan and Jiang, 2023; Kirk et al., 2024; Salemi et al., 2024a; Tan et al., 2024a). As large language models (LLMs) evolve from static text generators into interactive agents, adapting to a user involves not only what the model says, but also the execution procedure used to reach an answer: which historical records to consult, how to reconcile conflicting or noisy evidence, and when to restrain personal context (Chen et al., 2024; Cai et al., 2025; Yin et al., 2026). In agentic systems, this decision process is governed by an agent harness , the surrounding executable code and instructions that control how memory is stored, retrieved, and applied (Packer et al., 2023; Xu et al., 2025). A central design choice in agent personalization is how to construct the harness that connects a user’s interaction history to runtime execution. Existing approaches mainly follow two paradigms: shared memory workflows and per-user harness optimization. In practice, shared workflows, such as long-context prompting, fixed top-k retrieval, or uniform rolling summaries (Salemi et al., 2024a,b; Richardson et al., 2023), are the dominant choice because they can be deployed immediately to any user without per-user search. However, applying a single fixed procedure to every user overlooks substantial heterogeneity in how users express preferences and how their histories are structured. A compact summary may suffice for stable tastes, whereas shifting or multi-faceted interests require 1arXiv:2611.29062v1 [cs.CL] 21 Nov 2026 targeted multi-query retrieval and explicit disambiguation; simply packing more raw history into the prompt is token-intensive and frequently distracts the answering model with irrelevant records (Shi et al., 2023). In contrast, automated agent and harness optimization methods (Hu et al., 2025; Zhang et al., 2025a; Robeyns et al., 2025; Zhang et al., 2025b; Agrawal et al., 2026; Lee et al., 2026a; Yang et al., 2026) offer the flexibility to customize prompts or executable workflows through evaluation feedback. However, running task-scored search separately for each user faces two key challenges. First, repeated candidate generation and evaluation incur heavy token and latency overhead before the agent can serve a new user, often exceeding context budgets as histories grow. More importantly, an individual user’s raw interaction log provides sparse and indirect supervision by mixing enduring preferences, temporary intent, and incidental exposure (Tan et al., 2025a; Jiang et al., 2025; Tan et al., 2025b), and there is no ground-truth reference harness specifying how that user’s evidence should be retrieved or applied. This exposes a clear trade-off between deployment efficiency and user-specific procedural adaptation: shared workflows are lightweight to deploy but rigid across users, whereas per-user search is expressive but costly and difficult to supervise at deployment. We resolve this trade-off by shifting optimization from individual users’ harnesses to a shared construction procedure. We propose H YPER HARNESS , a framework that learns a reusable history-to-harness generator capable of synthesizing executable, user-specific retrieval and answer-guidance code directly from a user’s history (Figure 1). Inspired by hypernetworks that generate target network weights (Ha et al., 2017) and generation-based parameter adaptation (Phang et al., 2023; Ivison et al., 2023; Tan et al., 2026a), HYPER HARNESS extends amortized generation from static profiles or adapter weights to executable procedures that govern both which personal evidence is recalled and how it guides the answering model (Appendix C.5). Specifically, given a user’s permitted construction history, H YPER HARNESS organizes the historical records into structured evidence and prompts a frozen construction LLM to write user-specific code for memory retrieval and answer guidance under bounded host validity checks. During training, we keep both the construction and answering models frozen and optimize the shared generator’s code and prompts across training users using downstream task scores. Much as textual user profiles can be optimized through downstream utility without ground-truth summaries (Gao et al., 2025; Tan et al., 2026b), supervising the generator via downstream task performance eliminates the need for reference harnesses while allowing the generator to discover which historical patterns call for which retrieval and guidance designs. At deployment, the selected generator is frozen and constructs a personalized harness for an unseen user in a single pass from history alone, requiring no task-scored per-user search and amortizing optimization cost across the user population. We evaluate H YPER HARNESS on PersonaMemv3 (Jiang et al., 2026), Mem-PAL (Huang et al., 2026a), and MemoryCD (Zhang et al., 2026a) across three frozen answering models ( Qwen3.5-9B , Qwen3.8-27B , and 

GPT-5.6-Luna ). Our results show that H YPER HARNESS achieves the highest reported aggregate score in seven of nine configurations and ranks second in the remaining two, outperforming strong history, persistent memory, tool-using agent, and prompt/harness optimization baselines. With Qwen3.5-9B , H YPER HARNESS improves over the strongest baseline by 5.95 points on PersonaMemv3 (54.51 versus 48.56) and 3.39 points on Mem-PAL (32.77 versus 29.38). In a matched execution comparison on MemoryCD, generated harnesses reduce mean answer-time tokens by 90.32% relative to L ONG CONTEXT (3,147.28 versus 32,512.22 tokens per query) while preserving task performance, and amortize shared training costs to cross below per-user optimization baselines (GEPA and META -H ARNESS ) after a few dozen users. Extensive analyses further show that cross-user optimization adapts retrieval budgets and guidance structure to each answering model (e.g., gaining 7.96 points on PersonaMemv3 with Qwen3.5-9B while using 17.4% fewer input tokens), transfers to unseen clusters on PersonaMemv3 and Mem-PAL, and remains competitive under sparse or noisy histories. To summarize, our contributions are twofold. First, we propose H YPER HARNESS , a cross-user learning framework that trains a shared history-to-harness generator from downstream task feedback, showing that user-specific retrieval and answer-guidance code can be synthesized directly from history at deployment without ground-truth reference harnesses, model weight updates, or per-user task-scored search. Second, through extensive experiments across assistant, preference-selection, and cross-domain recommendation benchmarks, we demonstrate that H YPER HARNESS achieves strong personalization quality and a favorable efficiency frontier, while analyzing how learned harnesses adapt context allocation, generalize across user clusters, and respond to history perturbations. 

## 2 Methodology 

We aim to bridge rigid shared memory workflows and costly per-user harness search by learning a reusable construction procedure across users. Instead of treating harness generation as an isolated optimization problem solved separately for each user at deployment, we model it as a shared history-to-code generator that maps a user’s behavioral history to executable retrieval and answer-guidance functions. The key idea is to use the downstream task utility of the generated harnesses as supervision: rather than matching ground-truth reference programs, the shared generator is optimized so that the harnesses it constructs improve downstream answers with a frozen answering model. Editing Boundaries and Runtime Interface. To keep optimization modular and safe, H YPER HARNESS enforces a strict three-layer separation between the host, the shared generator, and each user’s personalized harness. First, the host runtime is fixed and non-editable: it owns data boundaries, official scoring, execution budgets, and a restricted Python AST sandbox (plain functions without imports, classes, while loops, I/O, or intermediate model calls), interacting with construction through bounded propose-and-check turns and invoking harnesses solely via the top-level recall and apply entry points. Second, the shared generator GS is the only layer edited by cross-user optimization; it bundles history digestion code, the construction prompt and call budgets, and a shared runtime backbone that implements common retrieval, packing, and dispatch logic around a single personal-section insertion slot. Third, once GS is frozen, that shared backbone becomes read-only to the per-user constructor, and host AST validation restricts each personalized harness hu to defining a user-state dictionary ( USER_MODEL )and standard hook functions: user_route (retrieval triggers, queries, and per-request depth), user_keep 

(record filtering), user_guidance (answer conditioning), and optional dispatch-gated overrides ( u_recall ,

u_apply ). Personal sections cannot redefine shared entry points, read shared global state, or relax host constraints, cleanly separating cross-user design edits from per-user specialization (full templates, neutral hook signatures, and generated code examples appear in Appendix E).

## 3 Experimental Settings 

3.1 Models and Datasets 

We instantiate H YPER HARNESS using gpt-6-sol (OpenAI, 2026a) for harness construction and generator opti-mization, and evaluate generated harnesses with three frozen answering models: Qwen3.5-9B , Qwen3.8-27B ,and GPT-5.6-Luna (Qwen Team, 2026a,b; OpenAI, 2026b). We conduct experiments on three benchmarks covering complementary personalization tasks with strictly disjoint training and test users. PersonaMemv3 (Jiang et al., 2026) evaluates personalized assistant interactions across recommendations, evolving preferences, restraint, and proactive actions (25 training and 75 test users). Mem-PAL (Huang et al., 2026a) evaluates preference-based solution selection on 50 training and 50 test users (408 test questions). MemoryCD (Zhang et al., 2026a) evaluates cross-domain transfer from Books, Electronics, and Beauty histories to held-out Home tasks spanning item ranking, rating prediction, and review generation (100 training and 223 test users; 2,676 test instances). During construction, the generator accesses only the permitted historical prefix or source-domain history and never observes test queries, reference answers, or test scores. Table 2 summarizes the experimental splits. 

3.2 Baselines and Evaluation History and Memory Baselines. We first compare against direct history-access and persistent memory methods, with N O HISTORY as a reference. L ONG CONTEXT packs the most recent history events within the input budget, and BM25 retrieves the top ten relevant records per request (Robertson and Zaragoza, 2009). For persistent memory, ROLLING MEMORY maintains a summary updated every 20 events, and M EM 0 WITH RAG constructs memories with the answering model and retrieves ten entries via MiniLM (Chhikara et al., 2025; Wang et al., 2020). These baselines test whether generated harnesses improve over shared retrieval and memory-compression workflows. 

Agent and Optimization Baselines. We further compare against C ODEX CLI, which runs the answering model as a tool-using agent (OpenAI, 2026c), GEPA for reflective prompt optimization (Agrawal et al., 2026), and META -H ARNESS for trace-guided executable harness optimization (Lee et al., 2026a). These methods test whether single-pass harness generation remains competitive with multi-step agent execution and task-scored search. 

Evaluation. For each benchmark, we compute official task metrics per user and average equally across users: rule-based and gpt-5.5 scores on PersonaMemv3, signed hit-rate score on Mem-PAL, and the equal average of ranking NDCG@5, normalized rating accuracy, and review ROUGE-L on MemoryCD (Järvelin and Kekäläinen, 2002; Lin, 2004). We also report deployment token usage Tdeploy in thousands of tokens per scheduled query, combining per-user setup and online execution while excluding judging and shared generator training. Full metric definitions, execution budgets, and implementation details are provided in Appendix A. 

## 4 Results 

Table 1 compares H YPER HARNESS against history, persistent memory, agent, and optimization baselines across three benchmarks and three answering models. H YPER HARNESS achieves the highest aggregate score in seven of nine configurations and ranks second in the remaining two. We highlight three main observations below. 

Executable personalization outperforms shared history and memory workflows. Across benchmarks, generat-ing user-specific retrieval and guidance code is consistently more effective than applying a uniform context workflow to every user. Packing raw history in L ONG CONTEXT exposes the answering model to irrelevant interactions that dilute task-critical signals, whereas fixed lexical retrieval in BM25 struggles when preferences span multiple topics or require implicit reasoning. Meanwhile, persistent memory methods (R OLLING MEMORY and M EM 0 WITH 

RAG) perform well only when paired with a strong backbone capable of maintaining faithful summaries (such as ROLLING MEMORY with GPT-5.6-Luna ), but degrade sharply on smaller models where iterative compression discards fine-grained evidence. By synthesizing tailored retrieval and guidance logic for each user, H YPER HARNESS 

adapts evidence selection to the structure of the user’s history and achieves the best score across all three benchmarks with both Qwen3.5-9B and GPT-5.6-Luna .

Amortized generation matches or exceeds per-user search by regulating preference use. Despite constructing harnesses in a single pass without test-time search, H YPER HARNESS outperforms the multi-step C ODEX CLI agent and matches or surpasses the reflective optimizers GEPA and M ETA -H ARNESS . Unconstrained agent exploration in CODEX CLI often struggles to extract stable preference signals from noisy logs even with multiple calls per query. ## 5 Analysis 

5.1 Model-Dependent Harnesses 

Figure 3 tracks how cross-user optimization alters model input, packed history, answer guidance, and static evidence use across all nine runs. Across seven of nine configurations, optimization shrinks total model input while raising task accuracy; on PersonaMemv3 with Qwen3.5-9B , it delivers a +7 .96 -point gain while cutting packed history by nearly a third. Filtering distracting interactions therefore matters more than supplying longer prompts. Equally striking, the learned context allocation depends strongly on the answering model itself. Even when Qwen3.8-27B 

and GPT-5.6-Luna receive identical retrieved history on MemoryCD, optimization steers Qwen3.8-27B toward richer, evidence-conditioned guidance while shifting GPT-5.6-Luna toward concise, largely static preference cues. A similar split appears on PersonaMemv3 and Mem-PAL, where stronger models tolerate aggressive history compression while smaller models rely more heavily on explicit historical context. Effective harnesses thus co-adapt to the reasoning habits of each executor rather than following a single model-agnostic design (Appendix C.1, Table 3; trajectories in Appendix C.3).

5.4 Efficiency Analysis 

Practical personalization requires improving downstream quality without imposing prohibitive inference prompts or repeated per-user search costs. H YPER HARNESS achieves this by structurally decoupling one-time cross-user training, single-pass per-user harness construction, and lightweight online execution (Table 1). In a matched MemoryCD comparison on Qwen3.5-9B across all 223 users and 2,676 requests, generated retrieval cuts mean answer-time tokens by 90.32% relative to L ONG CONTEXT (3.15k versus 32.51k per query) while matching its task score. While this comparison isolates runtime execution from training cost, it shows that most raw history supplied to long-context models is redundant at query time and can be filtered programmatically before invoking the answering model. To examine multi-user scaling, Figure 6 compares cumulative adaptation tokens under a 200-record history cap, scaling per-user optimization costs for GEPA and M ETA -H ARNESS to the 200-record budget alongside H YPER HARNESS ’s shared training and per-user construction costs. Per-user search methods (GEPA and M ETA -H ARNESS ) accumulate steep marginal costs with every new user and frequently exceed the 32K input budget on GEPA. By contrast, H YPER HARNESS pays a fixed training cost followed by lightweight per-user construction, crossing below both baselines after roughly 9–35 users for scalable deployment. 

5.5 Case Study 

To understand how a single frozen generator adapts execution logic to heterogeneous users, Figure 7 traces initial and optimized H YPER HARNESS programs built for two unseen PersonaMemv3 users with the lowest and highest shares of short-term preference labels, both executed by Qwen3.5-9B . From the same construction pipeline, the optimized generator synthesizes distinct control flows matched to each user’s history instead of applying a uniform template: for User 52, whose log reflects concentrated tastes (Spanish family comedy and dance alongside dislikes of fight promotions), the optimized generator replaces the initial harness’s skipped retrieval with a ranking-triggered preference search that supplies three records and preference guidance; for User 93, whose log spans diverse interests (music, Amharic practice, and home repairs), the same generator instead matches candidate cues such as 

#LatinMusic to trigger a targeted music search (Courtney Hadwin and classic soul) with five records and topic guidance. Across all 70 TEST requests per user, these tailored procedures lift overall scores by about six points (50.29 to 56.30 and 45.84 to 52.03) and nearly double mean recommendation NDCG@5 (14.50 to 30.50 and 11.80 to 21.20). On the two illustrated slates, however, NDCG@5 remains zero under both versions because the first search exhausts the history budget and hard negatives remain in the top five. These traces show that cross-user optimization improves personalization mainly by turning user history into tailored retrieval triggers, queries, and guidance logic rather than expanding raw context, while single-shot retrieval budgets remain a limiting factor when candidate slates contain closely competing distractors. 

## 6 Related Work 

LLM personalization. Existing LLM personalization methods adapt context, model parameters, alignment objectives, or agent behavior (Zhang et al., 2025c; Liu et al., 2025; Guan et al., 2025). Prompt- and context-based approaches incorporate user data directly into the input context, including raw user history as few-shot examples (Dai 9et al., 2023; Wang et al., 2024; Kang et al., 2023; Kim and Yang, 2025), history retrieval to handle long logs (Salemi et al., 2024a; Mysore et al., 2024; Salemi et al., 2024b), and summarized textual user profiles (Richardson et al., 2023; Sun et al., 2025; Dong et al., 2024; Tan et al., 2025b; Zhang, 2024); subsequent work enhances these pipelines with planning, reasoning, and utility-driven profile optimization (Salemi and Zamani, 2025; Salemi et al., 2025; Gao et al., 2025; Tan et al., 2026b). Parameter-based approaches embed user preferences in lightweight model components, spanning per-user PEFT adapters (Tan et al., 2024a), collaborative parameter sharing (Tan et al., 2024b), group-level adaptation (Zhang et al., 2025d), generated user adapters (Tan et al., 2026a), and learned user embeddings (Ning et al., 2025). A complementary line targets personalized alignment via post-hoc parameter merging (Jang et al., 2023), personalized RLHF (Li et al., 2024; Park et al., 2024), customized or factorized reward models (Cheng et al., 2023; Bose et al., 2025; Shenfeld et al., 2025), black-box model factorization (Zhuang et al., 2024), and interactive conversational settings (Zhao et al., 2025; Wu et al., 2025). More recently, agent personalization has extended adaptation to memory, planning, tool use, preference-aware skills, and harness evolution (Zhang et al., 2026b; Mazzolenis and Zhang, 2025; Bose et al., 2026; Liang et al., 2026; Gan et al., 2026a; Jin et al., 2026; Gan et al., 2026b). Rather than updating executor weights or relying on a fixed retrieval-and-prompting template, HYPER HARNESS learns a shared generator of executable user-specific procedures so history shapes both retrieved evidence and the code that applies it. 

Automated agent and harness design. Automatic optimization has progressed from prompts and agent workflows (Khattab et al., 2024; Agrawal et al., 2026; Hu et al., 2025; Zhang et al., 2025a) to evolving memories and skills (Ouyang et al., 2026a,b; Wei et al., 2026; Xu et al., 2026a). Another line improves agent code and meta-level modification procedures recursively, including STOP, SICA, the Darwin Gödel Machine, Hyperagents, MetaSkill-Evolve, and MCE (Zelikman et al., 2024; Robeyns et al., 2025; Zhang et al., 2025b, 2026c; Wang et al., 2026a; Ye et al., 2026). Recent work extends automated search directly to end-to-end executable harnesses: offline methods evolve harnesses with execution feedback, observability signals, or research knowledge (Lee et al., 2026a; Yang et al., 2026; Lin et al., 2026; Chen et al., 2026; Zhang et al., 2026d,e), while related systems train harness editors and generators from rewards or diagnostic search experience (Shao et al., 2026; Zhang et al., 2026f; Huang et al., 2026b). Online and test-time approaches further refine harnesses across deployment streams and continual episodes (Lee et al., 2026b; Wang et al., 2026b; Nie et al., 2026; Liu et al., 2026; Karten et al., 2026; Kang et al., 2026; Zhou, 2026; Xu et al., 2026b). H YPER HARNESS applies harness optimization to a shared construction procedure across users: task-scored search happens during cross-user training, so the frozen generator synthesizes each new user’s harness directly from history without per-user scored search at deployment. 

## 7 Conclusion 

We introduced H YPER HARNESS , a framework for learning to generate personalized agent harnesses from user his-tories. By optimizing a shared construction procedure with downstream feedback, it produces user-specific retrieval and guidance code without per-user task-scored search at deployment. Experiments show competitive performance across three benchmarks and reveal that useful adaptation can come from changing how context is selected and interpreted. The findings support executable harness generation as a practical direction for personalization, with transfer and history sensitivity remaining important considerations. 

## Limitations 

Our experiments cover three benchmarks under bounded retrieval-and-guidance interfaces and do not test unrestricted agent workflows. Several cross-method comparisons span slightly different evaluation subsets or task masks, and the robustness study evaluates 12 users per dataset with a single perturbation seed. Both harness optimization and construction are stochastic, and our case studies examine end-to-end traces without ablating individual code rules. Finally, cost comparisons reflect different workload scopes, and deploying generated programs in practice requires strict access controls, validation, and privacy safeguards over user histories.

Models and optimization. We use gpt-6-sol for harness construction and generator optimization, and 

Qwen3.5-9B , Qwen3.8-27B , or GPT-5.6-Luna for answer execution. Each run evaluates an initial gen-erator and up to ten optimization rounds, then freezes a TRAIN-selected version for TEST. Construction and optimization use medium reasoning effort by default, with low construction effort for the Qwen3.5-9B Memo-ryCD configuration and task-aware initialization on Mem-PAL. Independent Qwen replications start from fresh initial programs and reference scaffolds and are reported separately. 

Candidate selection. A candidate is normally adopted when it improves the equal-user mean on the TRAIN panel. The optimizer receives the current specification, generated user programs, task scores, and diagnostic cases showing gains and regressions relative to the incumbent. Candidate evaluation generates new personal programs, so the measured change includes construction variability as well as changes to the shared procedure. Construction checks test interface compliance and executable validity with permitted history and synthetic requests; their repair feedback is separate from task-quality feedback. For GPT-5.6-Luna on MemoryCD, candidate acceptance additionally requires gains in at least three of five fixed TRAIN groups and a per-task regression check against the initial generator. 

Execution and baselines. The input cap is 32,768 tokens. Output caps are 512 for Mem-PAL and 4,096 for MemoryCD; PersonaMemv3 uses its official task-specific limits. Mem-PAL and MemoryCD harnesses use a single final-answer call per request. Qwen disables implicit thinking and uses local structured decoding, while 

GPT-5.6-Luna uses hosted decoding with reasoning effort none . L ONG CONTEXT packs recent complete events; BM25 retrieves ten records per query; R OLLING MEMORY updates every 20 events with a 512-token memory cap; and M EM 0 WITH RAG uses the corresponding executor for updates and MiniLM top-10 retrieval without reranking. C ODEX CLI permits at most 12 model calls and 600 seconds per answer. We also compare GEPA (Agrawal et al., 2026) and M ETA -H ARNESS (Lee et al., 2026a); N O HISTORY is the non-personalized reference. Methods retain their reported budgets, so equal input caps do not imply equal end-to-end compute. Appendix E gives the prompt templates and the executed code examples. 

Evaluation metrics and deployment cost. We compute each user’s benchmark score and average equally across users. PersonaMemv3 uses the official rule-based and gpt-5.5 evaluators with lifecycle-pair aggregation (0–100 scale), following each user’s designated later-half query split. Mem-PAL uses 50 × (positive hits − negative hits )

on its English machine-translated solution-selection subset ( −100 to 100 scale). MemoryCD equally weights NDCG@5 for item ranking, normalized rating accuracy 1 − MAE /4, and ROUGE-L for review titles and review text (0–100 scale). Chronological evaluations admit later observations only when the task protocol makes them available, whereas MemoryCD uses fixed source-domain history. Deployment tokens Tdeploy are the equal-user mean of (Tsetup ,u + Texec ,u )/Q u in thousands per scheduled query, where setup includes memory or harness construction and execution includes answer calls and subsequent memory updates; judging and shared generator training are excluded. Because methods can cover slightly different evaluation subsets, GPT-5.6-Luna uses filtered task masks on MemoryCD and Mem-PAL, and H YPER HARNESS deployment tokens on Mem-PAL with 

Qwen3.5-9B are measured from a separate replication.

Aggregation. We use a single fixed random seed across all 11 perturbation conditions and four methods. Full-history controls are shared across settings. We use each benchmark’s scoring procedure to aggregate scores within users, then average equally across users. Each condition constructs a fresh harness, so differences can reflect both history sensitivity and construction variability. 

C.5 Connection to Hypernetworks 

HYPER HARNESS is conceptually inspired by neural hypernetworks (Ha et al., 2017) and hypernetwork-based parameter adaptation for LLMs (Phang et al., 2023; Ivison et al., 2023; Tan et al., 2026a). Below we summarize the shared design principles and key differences between the two paradigms (Table 6). 21 Shared principles. Both neural hypernetworks and H YPER HARNESS address the tension between per-user specialization and deployment cost through amortized conditional generation . Rather than running iterative fine-tuning or search separately for each unseen user at test time, both learn a single shared meta-generator across a training population and condition it on user-specific inputs to synthesize a personalized artifact in a single pass. Both also avoid ground-truth target artifacts: hypernetworks do not need supervised reference adapters when trained end-to-end on downstream task loss, and H YPER HARNESS similarly avoids ground-truth reference harnesses by optimizing the shared generator GS directly against downstream answering quality across training users. 

Key differences and complementarity. Despite this shared formulation, the two paradigms differ along four main axes. First, in output space and parameterization , neural hypernetworks are differentiable models that map conditioning vectors into continuous parameter deltas ( ∆θu), whereas H YPER HARNESS parameterizes its generator with discrete prompts, code, and supporting specifications S and generates executable programs hu via a frozen construction LLM. Second, in optimization , neural hypernetworks rely on gradient backpropagation through generated weights, whereas H YPER HARNESS uses derivative-free cross-user optimization driven by task scores and diagnostic execution traces. Third, in executor compatibility , parameter-generating hypernetworks require white-box access to open-weight checkpoints and are coupled to a fixed model architecture, whereas H YPER HARNESS keeps the answering model completely frozen and works uniformly across open-weight and hosted black-box models (such as GPT-5.6-Luna ). Fourth, in adaptation mechanism and inspectability , weight generation steers internal model representations with minimal extra input tokens at inference time, while harness generation adapts external control flow, query formulation, and evidence filtering in human-readable code that can be inspected, sandboxed, and validated by the host (Section 5.5). Consequently, the two approaches are complementary: H YPER HARNESS is especially suited to long-horizon episodic memory selection and black-box deployment, whereas parameter-space hypernetworks could be combined with generated harnesses to jointly adapt both external context selection and internal model weights when open checkpoints are available.
