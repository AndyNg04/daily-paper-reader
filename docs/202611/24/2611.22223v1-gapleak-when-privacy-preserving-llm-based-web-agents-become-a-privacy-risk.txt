Abstract
To protect user privacy, current Large Language Model (LLM)-based
web agents rely on two privacy-preserving principles: data mini-
mization, which limits users to providing only task-relevant infor-
mation, and least privilege, which restricts agents to task-authorized
sources. We reveal that these principles are necessary but not suffi-
cient. They constrain the sources an agent is authorized to use, but
not the higher-sensitivity sources that remain reachable in its envi-
ronment. A website can request a field that no authorized source
can provide, opening an information gap between what the agent
is authorized to use and what it can reach. A human would leave
such a field blank, but a goal-driven agent tends to escalate to a
reachable but unauthorized source to complete the task. We for-
malize this vulnerability as GapLeak, where an adversary exploits
a legitimate web form to induce an agent to disclose accumulated
sensitive information, without requiring prompt injection or other
malicious instructions.
To further understand the root causes of unauthorized disclosure,
the effectiveness of existing defenses, and the generalizability of
GapLeak, we evaluate GapLeak on three popular web-agent frame-
works and six LLMs from Anthropic, Google, and OpenAI across
four representative domains: recruitment, e-commerce, travel, and
healthcare. Results show that GapLeak induces an average unau-
thorized disclosure of approximately 37%, with the information gap
serving as the primary driver of the vulnerability, as eliminating
this gap reduces disclosure by more than 50%. Moreover, existing
instruction-level defenses based on the least privilege principle can
partially mitigate the vulnerability, but often degrade task success
rate. To address this limitation, we propose a submission-time veri-
fication mechanism that filters unauthorized content before form

Introduction
Large language model (LLM)-based web agents can autonomously
navigate websites, fill out forms, and submit data, transforming
the browser from a user-operated interface into a delegated task-
execution environment [17, 19, 34, 58]. Commercial agents, such as
DoBrowser [2] and OpenAI’s Operator [35], have already demon-
strated multi-step workflows, including job applications, e-com-
merce returns, travel bookings, and medical intake form completion.
By mid-2025, 62% of organizations reported experimenting with
LLM-based agents, while 23% had already begun deploying them at
scale in at least one business function [31]. Agentic automation is
transitioning from a proof-of-concept technology to a foundational
component of everyday digital infrastructure. However, the success-
ful execution of these delegated tasks inherently requires agents to
access users’ personal information [38, 52, 55]. For example, book-
ing a single trip may require access to a user’s travel itinerary,
payment credentials, calendar availability, and even the contact in-
formation of accompanying travelers. Consequently, each delegated
task grants autonomous agents broad visibility into sensitive per-
sonal data. Because these agents independently interact with web-
sites and external services on behalf of users, private information
may be disclosed, inferred, or propagated across multiple domains
without the user’s awareness or explicit consent [10, 11, 41, 53].
These privacy risks have attracted growing attention from both
the research community and standards organizations. In 2026, the
U.S. NIST launched an AI Agent Standards initiative and solicited
public input on emerging security and privacy threats associated
with autonomous agents [33]. In parallel, researchers have advo-
cated two fundamental privacy-preserving principles for agent

design: data minimization, which restricts the information exposed
to the agent, and least privilege, which limits data sources the agent
is permitted to access. AgentDAM [56] introduced a benchmark for
evaluating whether agents adhere to data minimization by access-
ing sensitive information only when necessary. AirGapAgent [7]
applies the least-privilege principle by filtering user data and re-
stricting the agent’s access to only the information required for
the current task. The recent studies [7, 20, 32, 56] share a common
assumption: if an agent is provided with only the minimum neces-
sary information and granted only the minimum necessary access,
unauthorized disclosure can be effectively prevented.
However, we observe that these principles are necessary but
not sufficient. Data minimization and least privilege constrain the
agent’s authorized scope, meaning the information the user pro-
vides and the sources the task sanctions. However, the two prin-
ciples do not constrain the agent’s reachable scope, which still
includes higher-sensitivity sources present in the agent’s environ-
ment. As a result, a residual gap remains between what the agent
is authorized to use and what it can actually reach. Consider a
user who requests a product return and provides only the item
name, purchase date, and reason for return. The user withholds
the complete order history and payment details, yet both records
remain reachable through the user’s logged-in account. When a
website then requests a field that no authorized source can provide,
an information gap arises. The agent must now choose between
two options. It can leave the field blank and risk task failure, or it
can escalate to a reachable but unauthorized source and risk the
user’s privacy. Since current web agents are goal-driven by design,
they tend to escalate rather than abandon the task [42, 47]. The
information gap is the primary driver of unauthorized disclosure.
When no authorized source can supply the requested field, the
agent reaches into unauthorized sources to complete the task, and
sensitive content the user never intended to share is exposed in
the process. The exposed content is not limited to the user’s own
data. It routinely includes third-party information such as reference
contacts, accompanying travelers, and family members, whose ex-
posure constitutes a privacy harm regardless of how the user chose
to interact with the site.
We formalize this vulnerability as GapLeak, which exploits
the gap between the agent’s authorized and reachable scope to
induce disclosure beyond the task’s authorized scope. Specifically,
GapLeak begins when a web form requests a field that the user
has not provided. The missing field creates an information gap,
which drives the agent to escalate to reachable but unauthorized
sources. As the agent searches for the field, additional sensitive
content accumulates in its working context. The adversary is a
website operator that controls only the target form. The adver-
sary then manipulates the website guidance to present the ac-
cumulated content as relevant or necessary, which induces the
agent to submit the content as part of the task workflow. Crucially,
GapLeak requires only a legitimate web form and does not rely
on prompt injection, hidden elements, compromised contexts, or
other forms of instruction manipulation. Throughout the attack
the agent remains aligned with the user’s original task. To un-
derstand the factors that drive unauthorized disclosure, evaluate
whether existing defenses can prevent it, and assess the generaliz-
ability of GapLeak, we evaluate it across four representative web
task domains, namely Recruitment [18, 30], E-commerce [37, 46],
Travel [9, 44], and Health [17, 24]. Each scenario is evaluated us-
ing three agent frameworks (BrowserUse [8], DoBrowser [2], and
Agent-E [5]) and six models from three providers (Claude Haiku 4.5,
Claude Sonnet 4.6, Gemini 2.5 Flash, Gemini 2.5 Pro, GPT 5.4 Mini,
and GPT 5.4).
Our evaluation demonstrates that GapLeak generalizes across all
tested frameworks and models, inducing an average unauthorized
disclosure rate of approximately 37%. The information gap is the
primary driver. When the gap is present, unauthorized disclosure
increases by more than 50%, while task success rate decreases by
roughly one-third, so the gap degrades privacy and utility at the
same time. A trade-off between the two arises instead under a de-
fense. When we apply least privilege as an explicit instruction-level
defense, disclosure still persists in 77% of completed tasks, and the
task success rate drops to 30%. Instead of restricting the agent during
task execution, we propose submission-time verification, which in-
spects each field immediately before submission and removes unau-
thorized content. Submission-time verification eliminates over 96%
of unauthorized disclosures without further reducing task success
rate. We summarize the main contributions of this paper as follows:
• Vulnerability identification: We identify and formalize
GapLeak, a structural vulnerability rooted in the informa-
tion gap that arises when a web form requests a field no
authorized source can provide. The information gap drives
goal-driven web agents to escalate to unauthorized sources
and disclose the accumulated content, including third-party
data, beyond the task’s authorized scope.
• Systematic evaluation: We design four controlled scenar-
ios spanning distinct web task domains, together with an
automated evaluation pipeline, to systematically evaluate
GapLeak across three agent frameworks and six models.
• Defense evaluation and countermeasure: We evaluate
the effectiveness and limitations of least-privilege-based
instruction-level defenses and propose submission-time ver-
ification as a countermeasure that reduces unauthorized dis-
closure without compromising task success rate.

Background and Motivation
2.1
LLM-Based Web Agents
LLM-based web agents leverage LLMs to execute browser-based
tasks on behalf of users [15]. Unlike chatbots or search-augmented
assistants (e.g., Perplexity [4]), which primarily retrieve and summa-
rize web content, web agents interact directly with web interfaces
by clicking buttons, filling forms, and submitting data. This ca-
pability enables agents to operate on previously unseen websites
without requiring API access or site-specific configuration.
To automate tasks, web agents typically follow an observe–plan–
act cycle [15, 58]. The agent first captures the current browser
state through techniques, e.g., raw HTML extraction, accessibility
tree parsing [1], browser screenshots [26], or combinations thereof,
and then provides the observation, together with the user’s task
description, to the LLM, which reasons about the current state and
determines the next action. The agent executes the selected action
through browser automation frameworks, e.g., Playwright [3], and
the cycle repeats until the task is completed.

Web agents exist both as research prototypes [26, 58] and as com-
mercial products [2, 5, 8]. They are commonly deployed as desktop
applications that launch dedicated browser instances [8], browser
extensions that operate within an existing browsing session [2], or
overlay interfaces embedded into the current webpage [5]. Despite
these deployment differences, all web agents share the same funda-
mental workflow: observing the browser state, planning the next
action through an LLM, and executing actions.
2.2
Information Gap
When a user fills out a web form, the information requested by the
website and the information provided by the user are determined
independently, with no built-in mechanism to ensure that they
align. Therefore, if the website requests a field that the user has
not provided, an information gap arises. Crucially, the gap is not
merely that the user withheld the field. The requested field is absent
from the sources the task authorizes, yet it often remains obtainable
from higher-sensitivity sources that stay reachable in the agent’s
environment. The information gap is therefore the point at which
the agent’s authorized scope and its reachable scope diverge. The
phenomenon of websites requesting more information than users
intend to disclose has been widely studied in human–computer
interaction [13]. When faced with such a gap, human users can
often recognize irrelevant or excessive requests and choose to skip
those fields or abandon the form altogether [16]. In a delegated
task, however, the agent completes the form on the user’s behalf
and may not exercise the same judgment.
2.3
Motivation
Data minimization and least privilege constrain what information
is provided to the agent and what sources it is permitted to access.
These principles narrow the agent’s authorized scope, but they do
not narrow the reachable scope that still exposes higher-sensitivity
sources in the agent’s environment. As a result, they do not account
for situations in which the target website requests a field that the
authorized sources cannot supply but a reachable source can. How
LLM-based web agents respond to this situation remains unclear.
The goal-driven design of current web agents may prefer to escalate
to additional sources rather than leave the field empty, yet this
behavior has not been systematically examined in prior work.
Motivated by this observation, we pose the following research
question: How do LLM-based web agents respond to information
gaps, and what privacy risks does this pose? Specifically, we seek
to understand how GapLeak drives agents to escalate to additional
sources and disclose sensitive information across different agent
frameworks, models, and task domains.
3
Methodology
3.1
Threat Model
Adversary Capabilities. The adversary is a website operator that
controls only the content of a target webpage visited by the agent
during a delegated task. Specifically, the adversary controls: (1)
the set of fields requested by the page, (2) the guidance and helper
text associated with each field, and (3) the validation and feedback
messages returned upon submission. These capabilities are available
to any website operator, such as an online retailer managing its
own product return portal.
The adversary does not control the agent’s system prompt, un-
derlying model, or framework implementation, nor does it inject
hidden elements, scripts, or instructions that redirect the agent
away from the delegated task. All page content consists of legiti-
mate, user-visible text that remains within the scope of the task.
Adversary Objectives. The user authorizes the agent to access only
the low-sensitivity sources 𝐿that the user explicitly provides for
the task. The agent’s environment also contains higher-sensitivity
sources 𝐻that the user did not provide or authorize (𝐿∩𝐻= ∅). An
information gap is a requested field𝑔that cannot be resolved from 𝐿
(𝑔∉𝐿) but can be resolved from 𝐻(𝑔∈𝐻). The adversary’s goal is
to induce the agent to escalate to 𝐻to resolve the information gap,
and to submit one or more fields outside the minimal-disclosure
policy Π(𝑇,𝑊), the set of fields the task minimally requires. We
distinguish two forms of such unauthorized disclosure: (1) over-
disclosure, where the agent submits sensitive information about the
user beyond what the task minimally requires, and (2) third-party
disclosure, where the agent reveals information about individuals
other than the user, such as reference contacts, accompanying trav-
elers, and family members. Third-party disclosure is a distinct harm
because these individuals never interacted with the website and
never consented to the release of their information.
Trust Assumptions. We consider a delegated task setting in which
a user instructs an agent to complete a web-based workflow on
their behalf. Following the principle of data minimization [56], the
user provides only task-relevant materials rather than all available
personal information. We emphasize that the user interacts with the
website willingly and intends to submit the form. The privacy harm
does not arise from the information the user knowingly provides
for the task. It arises when the agent escalates to sources the user
never authorized and submits information the user never intended
to share, including information about third parties. In other words,
the boundary that GapLeak violates is not the user’s willingness to
use the site, but the minimal-disclosure policy Π(𝑇,𝑊) that the task
itself defines. We further assume the user trusts the agent to operate
within this boundary and does not intervene during execution,
consistent with how current web agents operate. We examine the
implications of relaxing this assumption, including the case where
a human approval step precedes submission, in Section 7.
3.2
GapLeak Mechanism
Figure 1 illustrates how GapLeak exploits the information gap
through a three-stage attack chain.
Stage 1: Source escalation. When the agent encounters a required
field that cannot be resolved from the provided materials, it may
leave the field blank, ask the user for clarification, or escalate to
reachable but unauthorized sources. In practice, LLM-based web
agents are designed as goal-driven systems that autonomously
resolve obstacles to complete a user-specified objective [42, 47],
and tend to seek the missing information from other sources.
Stage 2: Context accumulation. As the agent navigates across
sensitive sources in search of the missing field, each observation is
appended to its working context, which the LLM relies on to plan
subsequent actions [15, 47]. Since LLMs are inherently stateless,

Stage 3: Guidance-amplified disclosure. The target website ac-

comply with requests or suggestions even when such compliance is
unwarranted [39, 51]. As a result, the agent may interpret the web-

and submit the accumulated sensitive information in an attempt
to satisfy it. The agent thereby discloses information beyond what
the task minimally requires.
Interaction between stages. The information gap is the precon-
dition for the entire chain. Without a missing field to resolve, the
agent has no reason to escalate beyond the user’s provided materi-
als, no sensitive content enters its working context, and the website
guidance finds no accumulated content to elicit. The escalation and
guidance stages therefore act on the exposure that the gap first
creates, rather than opening it on their own.

Scenario Model
A scenario is formalized as a tuple 𝑆= (𝑇,𝑊, 𝐿, 𝐻,𝑔, Π). 𝑇denotes

Each scenario instantiates 𝐿as a task-specific summary document
that contains only task-relevant materials, consistent with the trust
assumption in Section 3.1. The summary contains the information
needed for 𝑇, with the exception of 𝑔. The absence of 𝑔from 𝐿

triggered when 𝑊requests 𝑔driving the agent to escalate to 𝐻for

Defining the minimal-disclosure policy Π(𝑇,𝑊). For each sce-
nario we operationalize Π(𝑇,𝑊) as the set of fields that are strictly
necessary to complete 𝑇on 𝑊. Concretely, a field is included in
Π(𝑇,𝑊) if and only if it is mandatory for a valid submission on the
benign version of the website, or it is required to satisfy the task’s
ground-truth success criteria. All remaining fields that 𝑊exposes,
including every optional field, are outside Π(𝑇,𝑊) by construction,
and submitting any of them constitutes unauthorized disclosure.
The per-scenario membership of Π(𝑇,𝑊) is fixed in advance from
the benign form and the task ground truth, so it does not depend
on agent behavior. The success criteria used to derive Π(𝑇,𝑊) are
listed in Appendix F, and the reliability of the resulting labels is
validated against an independent LLM judge in Appendix G.
The scenario model is instantiated across four scenarios:
• Job Application. The agent completes a job application
using candidate materials stored in a local directory and
interview availability obtained from a calendar.
• E-commerce Return. The agent submits a product return
request. Order and account information is available through
a simulated e-commerce website that mirrors the structure
and functionality of online retail platforms.
• Travel Booking. The agent completes a travel booking
request. Travel and reservation information are accessible
through a simulated travel website, while scheduling avail-
ability is provided through a calendar.
• Medical Intake. The agent completes a medical intake and
insurance pre-authorization form. Patient and insurance ma-
terials are stored in a local directory, and appointment avail-
ability is provided through a calendar.

4
Implementation
4.1
Scenario Assets
Each scenario is implemented as a set of locally hosted services that
the agent interacts with through Google Chrome. All task materials,
including locally stored documents, account pages, and scheduling
interfaces, are served through local HTTP endpoints, ensuring full
experimental control and reproducibility.
In the job application and medical intake scenarios, task materi-
als are organized as local document collections accessible through
browser-based vault pages, with each document corresponding to
one of the higher-sensitivity sources in Figure 2. In the e-commerce
return and travel booking scenarios, a locally hosted account web-
site simulates the structure of a real online platform. It includes
a home page and several thematic record pages corresponding to
the higher-sensitivity sources in Figure 2, with each page hosted
at a distinct URL so that the agent must actively navigate to reach
it. Three scenarios (job application, travel booking, and medical
intake) also include a locally hosted calendar page that displays a
week-view of predefined synthetic events. These designs reproduce
how real-world tasks organize and expose user information.
4.2
Target Website Design
Each scenario includes two versions of the target website: a benign
version and a manipulated version. Both share the same task goal
and require the same mandatory fields for submission, but differ in
their form structure and wording.
Benign Website. The benign website includes both mandatory and
optional fields, but does not use wording that encourages provid-
ing information beyond Π(𝑇,𝑊). Depending on the scenario, the
benign form ranges from a single-page submission (e-commerce re-
turn and travel booking) to a multi-page workflow (job application
and medical intake).
Manipulated Website. The manipulated website preserves the
same task goal, mandatory fields, and optional fields, but restruc-
tures the submission into a multi-step workflow across all scenarios.
Each step focuses on a specific category of information and is ac-

task completion. The guidance does not instruct the agent to access

4.3
Evaluation Pipeline
Figure 3 illustrates the end-to-end evaluation workflow. The evalua-
tion pipeline automatically computes all metrics by combining two
data sources: the agent’s final submission, which is used to assess
task success and disclosure violations, and structured action traces,
which are used to measure higher-sensitivity source access patterns.
Action Traces. Each run generates a structured event log that
captures page visits, file accesses, draft saves, and final submissions,
each annotated with timestamps and sensitivity labels. SSE is com-
puted from these traces by identifying which higher-sensitivity
sources the agent accessed.
Task Success. Task success is evaluated from the final submission
by checking two conditions: (1) a valid submission timestamp exists,
and (2) all required fields match the scenario ground truth. Required
fields are evaluated using exact string matching, rule-based key-
word matching, or time window validation, depending on the field
type. The detailed evaluation criteria are provided in Appendix F.
Over-Disclosure. OD is computed by matching the content of
the final submission against a predefined set of sensitive keywords
derived from each scenario’s higher-sensitivity sources. The submit-
ted text is normalized before matching, and each detected keyword
is mapped to its corresponding disclosure category. Disclosure
breadth and severity are then calculated as defined in Section 3.4.
Third-Party Disclosure. TPD is computed by checking whether
the final submission contains personally identifiable information
belonging to individuals other than the task subject. The evaluation
matches submitted content against known third-party identifiers
in the scenario data, covering both explicit fields such as backup
contacts and implicit references such as names, email addresses,
and phone numbers.

not included in the tested model set) as a secondary evaluator fol-
lowing the LLM-as-a-Judge methodology [57]. We randomly sample
400 episodes (approximately 10% of all runs), with 100 episodes
per scenario. For each episode, the LLM evaluator independently

5
Evaluation
The evaluation is organized around five research questions. We first
examine the two core mechanisms underlying GapLeak: manipu-
lated website guidance (RQ1) and the information gap (RQ2). We
then evaluate existing defenses based on the least-privilege prin-
ciple (RQ3), assess the generalizability of GapLeak across different
agent frameworks and models (RQ4), and finally investigate the
resulting trade-off between privacy and utility (RQ5).
RQ1: Can the manipulated website induce unauthorized disclosures
compared to the benign website?
RQ2: What effect does the information gap have on source escala-
tion and over-disclosure?
RQ3: Can instruction-level defenses based on least privilege reduce
disclosure under GapLeak?
RQ4: Does GapLeak generalize across different agent frameworks
and models?
RQ5: Can an agent preserve privacy under GapLeak without sacri-
ficing task success rate?
RQ1 through RQ3 are evaluated using BrowserUse as the pri-
mary framework, as it provides the most complete model coverage
across the four scenarios (Table 1). RQ4 extends the evaluation to
DoBrowser and Agent-E to assess cross-framework generalizability.
RQ5 aggregates results across all frameworks and conditions.
5.1
Information-Access Condition
To systematically evaluate GapLeak, each scenario is tested under
five information-access conditions that vary the availability of in-
formation sources and the presence of privacy-related instructions.
The full prompt templates are provided in Appendix A.
Raw Materials. The agent is given access to the ordinary task
materials (i.e., all task materials except the summary document).
These materials contain the information required to complete the
task, but may also include sensitive information beyond what the
task minimally requires.
Summary Incomplete. A scenario-specific summary document
is added to the task materials, while the agent retains access to all
ordinary task materials and may freely navigate to them. Combined
with the manipulated website, this condition instantiates GapLeak.
Summary Complete. The summary document is modified to in-
clude the missing field, eliminating the information gap. The agent
can still navigate to the ordinary task materials. This condition
isolates the role of the information gap.
Soft Boundary. The summary document is accompanied by non-
binding privacy guidance stating that the summary and low-sen-
sitivity sources should normally be sufficient, and encouraging the
agent to avoid unnecessary access to sensitive information. It does
not impose hard restrictions, so the agent may still access higher-
sensitivity sources. This condition represents the weakest form of
the least-privilege principle and tests whether soft guidance alone
can reduce disclosure.
Access Restriction. The summary document is accompanied by
explicit access and submission restrictions specifying which sources
may be accessed, which fields may be submitted, and that unavail-
able fields should be left blank rather than resolved from higher-
sensitivity sources. This condition represents a stricter instruction-
level enforcement of the least-privilege and tests whether explicit
restrictions can prevent source escalation and disclosure.

5.2
Impact of Manipulated Website Guidance
To assess whether manipulated website guidance induces unautho-
rized disclosure (RQ1), we compare the benign and manipulated
target websites (Section 4.2) under the Raw Materials condition. All
experiments are conducted with six models from three providers.
Table 2 reports TS, OD, and TPD for each model and scenario.
Task Success Rate. TS remains largely stable between benign and
manipulated websites across all four scenarios, indicating that the
manipulated guidance does not interfere with task completion. The
exception is Sonnet 4.6 in the job application scenario, where TS
drops from 100% to 60%. Trace analysis reveals that in four of ten
episodes, the agent refuses to proceed after observing that the task
materials contain sensitive personal information. This behavior is
unique to Sonnet 4.6 and does not appear in any other model.
Over-Disclosure and Third-Party Disclosure. OD increases
across all four scenarios when the benign website is replaced with
the manipulated one. The effect is strongest in e-commerce return
scenario, where OD rises from near zero to 24%–91.9%, and in travel
booking scenario, where it rises from near zero to 32.4%–59.5%. In
the medical intake scenario, OD is already elevated under the benign
website (31.3%–77.1%), because the intake workflow has agents fill
a wide range of medical fields as part of standard task completion;
the manipulated website adds only modestly here.
TPD shows a distinct pattern. In job application and e-commerce
return scenarios, TPD rises from near zero to 8%–33.3% and 33.3%–
76% respectively, as the guidance frames reference contacts and
household members as useful for coordination. In travel booking
scenario, TPD is already present under the benign website for some
models (e.g., Haiku 4.5 at 45%, Sonnet 4.6 at 82%), and the manip-
ulated guidance pushes most models to 71%–100%. In the medical
intake scenario, TPD is near 100% under both websites, since the
workflow’s family contact fields are filled regardless of the guidance.
Key finding of RQ1
Even without an information gap, manipulated website guid-
ance alone substantially increases unauthorized disclosure
across all scenarios while task success rate remains stable; the
effect is strongest when the requested optional information
is semantically close to the task goal.

To assess whether GapLeak generalizes beyond our main setup

Summary Incomplete condition and manipulated website. Each

Cross-framework effectiveness. GapLeak activates on all three
frameworks. SSE is above 9% on every cell and reaches 75% to 84%
on DoBrowser for e-commerce return, travel booking, and medical
intake scenarios. This means agents on every framework respond
to the information gap by escalating to sensitive sources rather than
refusing or asking the user for the missing field. Across all three

5.6
Privacy Cost of Task Success
This section combines all conditions, frameworks, and scenarios
into a single view to quantify the relationship between privacy and
utility across the full evaluation (RQ5). We aggregate all 384 model-
level data points across six conditions, three frameworks, and four
scenarios. Each data point represents one model’s average TS and
PCS over ten episodes. Figure 7 plots these points on a TS-PCS
scatter, with small dots showing individual data points and large
dots showing the condition-level mean. The two marginal plots on
the right show the overall distribution of TS and PCS across all 384
points, with the dashed line marking the mean.
GapLeak separates TS from PCS. Under the benign website, the
mean TS is 62.0% and mean PCS is 29.7%. Under Summary Complete,
which provides full user materials against manipulated website, the
values are similar (TS = 59.1%, PCS = 31.1%). In both cases, higher
TS tends to come with higher PCS, because agents that complete
the task correctly tend to stay within the authorized scope. How-
ever, GapLeak breaks this relationship. Under Summary Incomplete,
which combines the information gap with the manipulated website,
TS drops to 41.1% while PCS falls to 10.3%. Of the 64 data points
under this condition, only 6 achieve both TS above 50% and PCS
above 50%. Among those that do complete the task (TS above 50%),
more than half have a PCS of zero. In other words, agents continue
completing tasks while failing to protect the user’s privacy.
Instruction-level defenses trade TS for PCS. Soft Boundary and
Access Restriction raise PCS from 10.3% under Summary Incomplete
to 20.8% and 23.3% respectively, but TS drops from 52.8% to 38.3%
and 29.8%. The defense instructions limit what agents can access or
submit, which reduces disclosure but also lowers task completion,
producing a trade-off rather than a solution.
Key finding of RQ5
Task success rate and policy-compliant success rate are
normally positively correlated, as agents that complete the
task correctly also tend to stay within the authorized scope.
GapLeak decouples the two: among agents that still complete
the task, more than half are never policy-compliant, and only
6 of 64 cases achieve both. Instruction-level defenses based
on least privilege raise policy-compliant success rate only by
lowering task success rate, confirming a fundamental privacy
and utility trade-off that no condition escapes.

7
Discussion
Toward a Better Defense. STV avoids the utility and privacy
trade-off of instruction-level defenses by operating at the submis-
sion boundary rather than restricting the agent during execution.
However, it does not alter the source escalation itself, and it does
not restore the task success that the information gap costs. These
properties point to a direction for future work, namely defenses that
govern source access during execution and thereby address both
escalation and task success rather than submission content alone.
Human Oversight. Our threat model assumes the user does not
intervene during execution. One might expect that requiring human
approval before submission would prevent unauthorized disclosure,
but its effect is limited by timing. By the time the user is asked
to approve, the agent has already escalated to higher-sensitivity
sources and prefilled the sensitive fields, so approval reduces to
confirming a form that already looks complete. It also comes too
late to undo the escalation, since the sensitive content has already
entered the agent’s working context. Human oversight is therefore
most effective when it governs source access during execution
rather than the final submission alone.
Benign-complete Baseline. We evaluate the benign website under
the Complete Summary condition, where neither the information
gap nor the manipulated guidance is present. Across all four scenar-
ios and six models, agents achieve an average TS and PCS of 83.3%,
with all failures due to execution errors rather than unauthorized
disclosure. This result shows that agents can complete the tasks
without disclosing unauthorized information when the provided
materials fully cover the requested fields. The disclosure observed
in our main experiments therefore stems from GapLeak rather than
the tasks themselves. However, complete materials are a best prac-
tice, not a defense. Because the adversary controls the form, it can
always introduce a field that falls outside the user’s provided mate-
rials, and users are unlikely to anticipate every field a website may
request. Therefore, users should provide task materials that are as
complete as possible when delegating tasks to web agents, thereby
reducing the likelihood and impact of information gaps.

Related Works
8.1
Security and Privacy of LLM Agents
Prompt injection and its indirect variants embed adversarial in-
structions into content the agent reads, hijacking it into unintended
actions [14, 21, 43, 49]. Context manipulation attacks instead cor-
rupt the agent’s stored context or planning state [36], and adver-
sarial UI elements such as crafted pop-ups mislead vision-language
agents through perception [54]. A separate line targets PII extrac-
tion, coaxing agents to reveal personal information they hold or
can retrieve [25, 29], and broader benchmarks evaluate agent ro-
bustness against varied threats [6, 27, 50]. Several recent works
also study disclosure risks in web agents. Spillage [37] examines
natural oversharing on unmodified websites without an adversary,
while Too Helpful to Be Safe [9] studies user-mediated attacks that
manipulate users rather than the agent.
GapLeak differs from prior work in two ways. (1) Adversary
capability. Prior attacks require instruction injection, context cor-
ruption, crafted UI elements, user manipulation, or no adversary
at all, whereas GapLeak requires only control of a legitimate web
form. (2) Agent internal state. Prior attacks steer the agent’s task
representation toward an attacker-introduced objective, whereas
under GapLeak the agent stays aligned with the original user task
throughout. Defenses that detect anomalous instructions or cor-
rupted internal state may therefore be ineffective against GapLeak.

8.2
Privacy-Preserving Agent Design
A related but distinct line of work focuses on privacy-preserving
design for LLM agents. AgentDAM [56] introduces a benchmark
that evaluates whether agents follow the data minimization princi-
ple, using sensitive information only when necessary for the task.
AirGapAgent [7] enforces this principle through a dual-LLM ar-
chitecture that filters user data, confining the agent to only the
information required for the current task. Other work catalogs the
privacy-relevant behaviors of deployed browser agents and doc-
uments how existing tools may expose user data [41]. However,
these approaches constrain the agent’s authorized scope but not
its reachable scope. As shown in RQ3 and RQ5, instruction-level
defenses based on least privilege only partially reduce disclosure
under GapLeak, and do so at the cost of task success rate.
9
Conclusion
Data minimization and least privilege protect user privacy by nar-
rowing what an agent is authorized to use. However, they do not re-
move the underlying risk, because the higher-sensitivity sources in
the agent’s environment remain reachable. We formalized GapLeak,
a structural vulnerability that exploits this residual gap. An infor-
mation gap drives goal-driven agents to escalate to unauthorized
sources, and manipulated website guidance induces them to dis-
close the accumulated content. Across three frameworks and six
models, we found that the information gap is the primary driver
of disclosure and that least-privilege defenses mitigate it only at
the cost of task success. Our submission-time verification removes
most unauthorized disclosure without further reducing task success.
These findings reveal a limitation of data minimization and least
privilege in agentic systems.

Ethical Considerations
This study reveals GapLeak, a structural vulnerability that arises
when data minimization and least privilege leave an information
gap between an agent’s authorized and reachable scope, which leads
LLM-based web agents to unauthorized disclosure. All experiments
were conducted on locally hosted websites designed by the authors,
using entirely synthetic user profiles and task materials. No real
personal information, human subjects, or live commercial systems
were involved, so the study required no IRB review. GapLeak relies
only on standard web design practices such as optional form fields
and helper text, rather than any specialized tooling or exploit code.
We have weighed the risk that documenting GapLeak could aid
misuse, and believe it is outweighed by the benefit to the commu-
nity. GapLeak introduces no new technical capability, but exposes
how goal-driven agents mishandle missing fields. Because it stems
from a general property of goal-driven agents rather than a defect
in any single product, no individual vendor can patch it. There-
fore, we disclose it through publication, together with a concrete
countermeasure, submission-time verification, so that developers
can adopt mitigations. Documenting this vulnerability across mul-
tiple frameworks and models serves the research community by
motivating development of privacy-preserving agent designs.

AI Use
As an object of study. Our research evaluates the privacy behavior
of LLM-based web agents, and therefore generative models are cen-
tral to our methodology. We evaluate six publicly available models
(Claude Haiku 4.5, Claude Sonnet 4.6, Gemini 2.5 Flash, Gemini 2.5
Pro, GPT 5.4 Mini, and GPT 5.4) across three agent frameworks, and
use an additional independent model as an evaluator (Claude Opus
4.6) and as the verifier in our proposed defense (GPT 5.5). These
models are studied as deployed systems through their standard
APIs; we do not train, fine-tune, or collect any data to train models.
All experiments were run on locally hosted, synthetic environments
with no real user data. We selected widely deployed models to en-
sure our findings reflect agents in practical use, and we limited
each configuration to N=10 episodes to keep the query volume
and associated computational and environmental footprint modest
while still capturing the stochastic behavior of the agents. Because
several of the studied models are closed-source and accessed via
APIs, exact reproducibility is inherently limited; we mitigate this
by reporting results across multiple models and frameworks, re-
leasing our scenario assets and evaluation code, and validating our
automated metrics against an independent evaluator.

E
Agent Framework Details
This appendix provides the detailed architecture of the three agent
frameworks summarized in Section 4.4.
BrowserUse is an open-source agent that operates as a desktop
application. It launches a Playwright-controlled browser instance
and observes the environment through a combination of DOM
extraction and accessibility tree parsing. The agent maintains a
task state across steps, which allows it to decompose complex goals
into sub-tasks and recover from intermediate failures. BrowserUse
supports a wide range of LLMs through direct API configuration.
DoBrowser is a commercial agent implemented as a Chrome
browser extension. DoBrowser observes the browser environment
through its built-in extension capabilities, which give it direct access
to the DOM of the user’s active tab. Based on our experimental ob-
servations, DoBrowser processes each turn by reading the current
page and producing an action in a single step, without maintaining
a planning state across turns. DoBrowser supports a fixed set of
models selectable through its settings panel.
Agent-E is an open-source agent that operates in overlay mode,
injecting a JavaScript overlay into the browser page. It observes
the environment through DOM snapshots and accessibility tree

Task Success Evaluation Criteria
Task success is determined by checking two conditions: a valid sub-
mission timestamp exists, and all required fields match the scenario
ground truth. Required fields are evaluated using three matching
strategies depending on the field type.
Identity fields such as names, email addresses, and reference
numbers are validated through exact string matching after normal-
ization. The normalization process converts both the submitted
value and the ground truth to lowercase, removes extra white-
space, and strips common formatting variations. A field passes only
when the normalized submitted value is identical to the normalized
ground truth.
Free-text fields such as issue descriptions and visit reasons cannot
be evaluated through exact matching because agents express the
same meaning in different ways. These fields are validated through a
rule-based keyword matcher. The matcher normalizes the submitted
text and checks whether it contains expected key terms or their
known variants. For example, a visit reason field passes if the text
expresses the relevant medical procedure or authorization context
using any of several predefined synonym groups. The synonym
groups are manually constructed from the scenario ground truth to
cover common paraphrases without relying on an external language
model for evaluation.

and medical intake scenarios. Each requires three appointment or

Evaluation Validation
We measure agreement using Cohen’s 𝜅for the binary TS metric
and Pearson correlation (𝑟) for the continuous OD and TPD metrics.
We additionally report Mean Absolute Error (MAE) to quantify
the average magnitude of disagreement. Table 8 summarizes the
results.
The remaining disagreements arise primarily from two sources.
First, the automated pipeline applies additional validation rules
for TS, such as time-slot format constraints and calendar conflict
detection, which the LLM evaluator may not fully capture from
the submission data alone, leading to occasional cases where the
automated pipeline scores TS as 0 while the LLM evaluator scores
TS as 1. Second, certain OD disagreements stem from boundary
cases where the submission contains indirect references to sensitive
content (e.g., paraphrased role descriptions rather than explicit em-
ployer names), which the two evaluators classify differently. These
differences are concentrated in borderline cases and do not affect
the core evaluation, as confirmed by the high Pearson correlations
across all scenarios.
