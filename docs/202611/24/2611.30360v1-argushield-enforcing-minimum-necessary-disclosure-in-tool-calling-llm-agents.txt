## Abstract 

Large language model agents increasingly use third-party tools to complete user tasks. Even without malicious intent, they may fill broad or weakly constrained fields with private information that is unnecessary or inappropriate for the receiving tool. Such calls can satisfy the tool schema and complete the task, yet still violate minimum-necessary disclosure. We introduce ArguShield, a mediation layer that intercepts proposed tool calls before execution. It evaluates each candidate value using three signals: Value Provenance, Task Relevance, and Disclosure Boundary. ArguShield releases justified values, defers values that need user confirmation, and withholds those outside the permitted scope. We evaluate ArguShield with four tool-calling models on ArgPrivBench, a benchmark of 120 tasks across Travel, Shopping, and Healthcare. Unprotected agents frequently over-disclose private information despite high task success. Prompt-only protection reduces unauthorized disclosure but substantially lowers task success. ArguShield reduces unauthorized silent release to 9% on Standard tasks and 6% on High-risk tasks while preserving recoverable task success under simulated user confirmation. 

Keywords: Tool-calling agents; agent privacy; minimum-necessary disclosure; argument-level mediation; data minimization 

## 1. Introduction 

Recent AI agents increasingly complete user tasks through third-party tools. Locally de-ployable agents with persistent memory and external application access, such as Open-Claw (Wang et al., 2026), expand the boundary at which private context may leave the system: a value in memory, profile, or context becomes an external disclosure once copied into a tool call. This disclosure is not always caused by malicious intent or incorrect tool choice. Third-party schemas may expose broad, optional, or weakly constrained fields; 36.9% of 2,344 Action/API specifications in the OpenAI GPT ecosystem expose at least one weakly con-strained free-text parameter such as query , notes , or context (Shayesteh and Wilson, 2026). Such fields make over-disclosure easy to express as a schema-valid call that com-pletes the task while still transmitting values the receiver does not need. Figure 1 illustrates this failure for hotel reservation: operational fields can be mixed with profile-derived name, phone, passport, and address values, some requiring confirmation and others falling outside the task disclosure boundary. We study this as a violation of minimum-necessary disclosure : a value should be released only when the current task and receiving tool justify it. ## 2. Related Work 

Tool-use and agent evaluation. Tool use has become a central interface for extending language models from text generation to external action. Early work studies reasoning with actions, self-supervised tool-use learning, and generalization across large API collections (Yao et al., 2023; Schick et al., 2023; Qin et al., 2024). Subsequent work addresses API-call generation and function-calling evaluation (Patil et al., 2024, 2025), as well as verified function-calling dataset construction (Liu et al., 2024). More recent agent environments move from isolated API calls to stateful interaction, multi-turn workflows, and tool-agent-user settings (Wang et al., 2025; Lu et al., 2025; Yao et al., 2025). Broader web, app, desktop, and workplace benchmarks further expand the evaluation of agents in realistic interfaces (Trivedi et al., 2024; Zhou et al., 2024; Xie et al., 2024). These studies establish the importance of tool calling and action execution, but they primarily measure whether agents can complete tasks. Our work studies a complementary property: whether the values released to a third-party tool are minimally necessary for the current task and receiver. 

Agentic disclosure and purpose-bound privacy. Privacy risks in tool-calling agents arise not only from model behavior, but also from the interfaces agents are asked to pop-ulate. Third-party tool schemas can expose broad, optional, or weakly constrained fields, leaving disclosure decisions to the agent at runtime (Shayesteh and Wilson, 2026). Agent-DAM evaluates privacy leakage in autonomous web agents, while SPILLage studies agentic oversharing on the web (Zharmagambetov et al., 2025; Roh et al., 2026). Prompt-injection attacks can induce leakage of personal data observed by agents (Alizadeh et al., 2025), whereas PrivacyAsst proposes a privacy-protection method for tool-using agents (Zhang et al., 2024). Other work frames privacy in terms of contextual integrity, purpose, recipient, and situation rather than sensitivity alone (Bagdasarian et al., 2024; Mireshghallah et al., 2024; Li et al., 2025). ToolPrivacyBench formalizes a closely related purpose-bound privacy problem: successful tool execution does not imply appropriate disclosure, because private information may be routed to tools or downstream sinks that do not require it (Hu et al., 2026). ArguShield targets this failure at the point where it becomes executable: before a proposed invocation releases candidate values to a third-party API. 

Tool-boundary mediation and enforcement granularity. Existing defenses differ in their intervention points, policy representations, and enforcement granularity. Kan et al. (2023) sanitize sensitive inputs before remote model access, whereas Wen et al. (2026) gen-erate context-specific privacy guidance during agent execution. PrivacyLens (Shao et al., 2024) provides a complementary framework for evaluating privacy violations in agents’ ac-tions. Mobile-agent systems use visual interface context to plan and execute actions (Wang et al., 2024; Zhang et al., 2025). Privacy-focused evaluation further reveals limitations in smartphone agents’ recognition of privacy-sensitive situations (Lin et al., 2026). For Fu Fu 

tool-calling agents, however, the receiving tool may observe private values before any final response exists. Tool-risk and agent-security studies show that tool use can cause pri-vacy leakage, unsafe execution, prompt-injection vulnerabilities, speculative-call exposure, or multi-tool leakage channels (Ruan et al., 2024; Debenedetti et al., 2024; Mohammadi et al., 2026; Qiao et al., 2026). System-level defenses such as CaMeL and FIDES separate control/data flow or enforce information-flow policies to secure agents against untrusted inputs (Debenedetti et al., 2025; Costa et al., 2025). PACT makes a related granularity observation: risks can arise when untrusted information determines an authority-bearing argument, so provenance must be tracked below the whole-invocation level (Fan et al., 2026). ArguShield applies this argument-level perspective to privacy at the tool-execution boundary. 

## 3. ArguShield: Enforcing Minimum-Necessary Disclosure at the Tool Boundary 

ArguShield is a pre-execution release mediation layer for tool-calling agents. Rather than executing a model-proposed tool call directly, ArguShield treats it as an executable draft whose values must be justified before crossing the third-party tool boundary. The enforce-ment goal is minimum-necessary disclosure : a value is released only when it is grounded in an appropriate source, warranted by the current task, and appropriate for the receiving tool. A schema-valid invocation may mix values with different disclosure status. Some values are required for task completion, some may be useful but require user confirmation, and others are outside the permitted disclosure boundary. ArguShield therefore preserves the tool-level intent whenever possible while mediating which candidate values are allowed to leave the agent. Figure 2 summarizes the pipeline.

3.2. Disclosure Justification 

For each candidate value, ArguShield constructs a disclosure justification record from three evidence signals. Value Provenance asks where the value comes from. Values explicitly provided in the current request are treated differently from values copied from user profile, prior tool outputs, retrieved content, or model inference. This distinction prevents the agent from treating contextual availability as permission to disclose. For example, a home address stored in profile may be available to the agent, but it should not be silently copied into a hotel reservation unless the task and receiver justify that release. 

Task Relevance asks whether the current task warrants the value. A value can be required for task success, useful but not strictly necessary, unsupported by the request, or conflicting with the task state. This signal prevents optional schema fields from becoming automatic disclosure channels. A field such as notes , context , or special instructions 

may be schema-valid, but schema compatibility alone does not make every available personal value task-relevant. 

Disclosure Boundary asks whether the receiving tool is an appropriate recipient under the current purpose. Some values are justified for silent release, some may support task completion but require confirmation, and others should be withheld for the current receiver. This receiver-aware signal captures the fact that sensitivity alone is insufficient: the same Fu Fu 

phone number, address, or medical note can be appropriate for one tool, confirmation-needed for another, and unjustified for a different third-party service. At inference time, ArguShield does not use gold release labels. It estimates the three evidence signals from the runtime state and then applies a fixed release monitor. For Value Provenance, it performs normalized matching against the current request, profile fields, prior tool outputs, and retrieved content. Exact matches, normalized string matches, and typed matches for dates, names, addresses, identifiers, prices, and contact fields are assigned to their supporting source; unmatched or fabricated values are marked as inferred or unknown. For Task Relevance, it combines the user intent, tool schema, argument path, value type, and task-success criteria to determine whether the value is required, useful, unsupported, or conflicting. For Disclosure Boundary, it uses the receiver identity, tool purpose, argument path, value type, and authorization status to decide whether the value is permitted for silent release, requires confirmation, or is outside the receiver boundary. Ambiguous evidence is handled conservatively and cannot justify silent release. 

3.3. Release Policy and Execution 

After evidence extraction, ArguShield applies a deterministic release monitor to each can-didate value. The final action is fixed given the evidence record, making release behavior auditable and reproducible rather than delegated to another model judgment. The mon-itor follows a priority order. Hide has highest priority and is assigned when a value is unsupported, conflicting, inferred without reliable grounding, or outside the receiving tool’s disclosure boundary. This rule blocks values that are schema-valid but not justified for release. 

Keep is assigned only when all three disclosure conditions are satisfied: the value is source-supported, warranted by the task, and permitted for silent release to the current receiver. This covers operational arguments explicitly provided by the user for the current task or values otherwise grounded and necessary for execution. Ask is assigned when a value may support the task but lacks sufficient authorization for silent release, such as profile-derived or previously observed values whose transmission to the current receiver should be confirmed by the user. Thus, Ask is not a weaker form of Keep ; it is a local withholding action that prevents the value from crossing the tool boundary until approval. After assigning actions, ArguShield reconstructs the outgoing invocation: ˜c = ( t, ˜A), Q = {ℓi | ai = Ask }.

Values assigned Keep remain in ˜A and are sent to the tool. Values assigned Ask are removed from the outgoing call and placed in Q until approved. Values assigned Hide 

are removed and are not offered for release. The audit log G records each argument path, the resolved evidence labels, and the final action, enabling post-hoc inspection and error analysis. ArguShield is intended to complement, rather than replace, the underlying tool-calling model. The model still selects the tool and drafts the invocation, but release control is moved to the execution boundary where structured values can be checked before they leave the system. This separation allows task execution to proceed with the minimum set of justified values while keeping confirmation-needed and unjustified values local. ArguShield: Minimum-Necessary Disclosure 

## 4. Experiments 

We evaluate whether tool-calling agents satisfy minimum-necessary disclosure when private context becomes executable tool input. Each instance provides a user request, visible con-text, and target tool schema. The model proposes a structured invocation, and we evaluate which values would be released to the third-party receiver. The evaluation is offline, but it preserves the failure studied in this paper: a call may be schema-valid and task-completing while still releasing values that the current task or receiver does not justify. 

4.1. Experimental Setup Benchmark. ArgPrivBench contains 120 synthetic tasks across Travel, Shopping, and Healthcare, with 20 Standard and 20 High-risk tasks per domain. The domains cover common third-party tool interactions: Travel includes hotel booking, itinerary planning, and appointment scheduling; Shopping includes checkout, delivery, return, and coupon-related tools; Healthcare includes clinic booking, pharmacy, insurance, and patient-intake tools. Each task specifies a user intent, visible user/context state, target tool schema, task-specific success criteria, and a set of candidate values that may be copied into the invocation. Candidate values include operational fields needed by the tool, profile-derived values, prior-context values, and receiver-sensitive values. They are annotated as Keep 

when silent release is justified, Ask when the value may support completion but requires user confirmation, and Hide when it is outside the task need or disclosure boundary. Standard tasks contain everyday personal values and optional arguments where over-disclosure is plausible. High-risk tasks do not necessarily have higher violation frequency; instead, they involve stricter receiver, purpose, or value-type constraints, so an unjustified release is more severe. 

Models, methods, and metrics. We evaluate DeepSeek-V4-Flash, GLM-5.1, Kimi-K2.7-Code, and Qwen3.7-Plus. We select these models because they support structured tool calls or schema-constrained argument generation, span four distinct model providers and families, and were available through commercial APIs during the evaluation period. All four models are evaluated with the same tasks, tool schemas, prompts, mediator con-figuration, and temperature of 0.0; only endpoint-specific tool-call formatting differs where necessary. No model is selected or excluded based on its performance with ArguShield. No-Protection executes the generated call directly. Prompt-Only Guard adds a privacy instruction but does not inspect the structured call after generation. ArguShield mediates the proposed call before execution. APVR measures unauthorized silent release, namely gold Ask /Hide values released as Keep ; it does not measure disclosure following simulated approval. TLR is the fraction of tasks with at least one unauthorized silent release. TSR measures task success. In the main protection comparison, we report TSR approve-all , where task-required values routed to Ask are treated as recoverable after simulated approval; for NoProtection , the same column reports ordinary task success without confirmation. ADF1 is macro-F1 over Keep , Ask , and Hide . ASKR measures the fraction of values routed to Ask on completed tasks, and is reported only as confirmation overhead. 4.2. Over-Disclosure in Unprotected Calls 

Under direct execution, agents often select plausible tools and satisfy the user request, yet still copy optional profile, delivery, payment-adjacent, insurance, or medical-note values into the call (Table 1). Averaged over all entries, unprotected execution yields 0.81 APVR on Standard tasks, 0.77 on High-risk tasks, and 0.96 TSR overall. The gap between high TSR and high APVR shows that task success alone does not imply appropriate information release. 

4.3. Effectiveness of ArguShield 

Release mediation substantially reduces unauthorized silent release while preserving recov-erable task success under simulated user confirmation (Table 2). Averaged over four models, Standard APVR drops from 0.84 under NoProtection to 0.09 with ArguShield, and High-risk APVR drops from 0.76 to 0.06. TSR approve-all remains 0.97 on both splits, and ADF1 improves consistently, indicating closer alignment with the intended Keep /Ask /Hide pol-icy. Prompt-only guidance achieves lower or equal APVR across the evaluated settings, but substantially reduces task success and yields lower ADF1. In contrast, ArguShield retains task-needed values and blocks or defers disclosures without sufficient task or receiver justification.

4.5. Ablation of Disclosure-Justification Signals 

The ablation removes one disclosure-justification signal at a time and reports changes rel-ative to full ArguShield, macro-averaged over models and splits (Figure 3). We focus on APVR for unauthorized silent release, ASKR for confirmation behavior, and ADF1 for action-level alignment. Removing the provenance signal sharply increases APVR and lowers ADF1, show-ing that source grounding is a core privacy signal; the lower ASKR indicates that some confirmation-needed values become silent releases. Removing Task Relevance produces lit-tle APVR change but increases ASKR and lowers ADF1, suggesting weaker precision in distinguishing task-needed from merely plausible values. Removing Disclosure Boundary yields the largest APVR increase and ADF1 drop, confirming that receiver-specific restric-tions are essential. Overall, provenance and boundary checks mainly prevent unauthorized silent release, while Task Relevance improves Keep /Ask /Hide assignment.

## 5. Limitations 

ArguShield mediates release at the third-party tool boundary before execution and cannot retract information after release. Final responses, shared memory, inter-agent messages, and multi-tool orchestration are outside ArguShield’s current scope. Related work iden-tifies privacy risks from speculative tool dispatch (Mohammadi et al., 2026) and sensitive inferences formed by combining tool outputs (Qiao et al., 2026). ArguShield is therefore one enforceable layer for structured tool inputs, not a complete privacy architecture. Release decisions also depend on evidence quality. Ambiguous intent, underspecified schemas, incomplete context, or domain-specific norms can still produce conservative de-ferral or incorrect release despite auditable checks over Value Provenance, Task Relevance, and Disclosure Boundary. ArgPrivBench is similarly diagnostic: its controlled values and stable schemas make over-disclosure measurable, but do not capture the diversity of de-ployment traces, organizational policies, or legal regimes (Zharmagambetov et al., 2025; Mireshghallah et al., 2024; Li et al., 2025). Finally, we evaluate recoverability under simulated confirmation for Ask values rather than live human-in-the-loop interaction. Real users may reject or misunderstand confirma-tion requests, and excessive prompting can add interaction cost. Future work should study confirmation design and adaptive policies that preserve minimum-necessary disclosure with lower overhead. 

## 6. Conclusion 

Tool-calling agents can complete user tasks while still exposing values that the current task or receiving tool does not justify. We formalize this failure as tool-argument over-disclosure ,a violation of minimum-necessary disclosure at the third-party tool boundary. ArguShield addresses this risk through pre-execution release mediation. It treats a model-proposed invocation as an executable draft, evaluates candidate values using Value Provenance, Task Relevance, and Disclosure Boundary, and assigns each value to Keep ,

Ask , or Hide before execution. We evaluate ArguShield on ArgPrivBench, a 120-task benchmark across Travel, Shop-ping, and Healthcare. Experiments show that unprotected agents frequently release un-necessary private values despite high task success, while prompt-only protection reduces ArguShield: Minimum-Necessary Disclosure 

unauthorized disclosure at a substantial cost to task success. ArguShield substantially re-duces unauthorized silent release on both Standard and High-risk tasks while preserving recoverable task success under simulated user confirmation. These results support value-level mediation as a complementary enforcement layer at the tool-execution boundary.
