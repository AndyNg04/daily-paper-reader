# Subverting Tool Arguments: Defense-Evading Metadata Poisoning in LLM Agents 

Shih-Chieh Dai, Xinyu Sun, Haichuan Zhang, Zhiyuan Zhong, Guanhong Tao 

Kahlert School of Computing University of Utah Salt Lake City, UT 

{shihchieh.dai, xinyu.s, hc.zhang, zhiyuan.zhong, guanhong.tao }@utah.edu 

Abstract —Conventional indirect prompt injection (IPI) attacks hijack an LLM agent’s workflow through malicious instruc-tions embedded in retrieved external content. The growing adoption of the Model Context Protocol (MCP) exposes another attack surface: tool descriptions supplied by third-party MCP servers. Attackers can manipulate this metadata to induce malicious argument generation during tool calls. The challenge is to ensure that the modified descriptions still appear benign to both LLMs and users. Existing IPI attacks, however, struggle to achieve both high attack success and low detectability in this setting. To address this challenge, we propose GRAFT , an LLM-based optimization method for crafting adversarial tool descriptions. Specifically, GRAFT uses a masking mechanism to identify argument-relevant token positions for targeted injection. It then iteratively refines candidate descriptions using dynamic mutation strategies proposed by an LLM, guided by the agent’s tool choices and generated arguments. We evaluate GRAFT on three public datasets against several attack baselines. The results show that GRAFT achieves higher attack success while maintaining low detection rates across five filter-based defenses. It also bypasses several existing IPI defenses. Even under an adaptive defense trained on GRAFT -generated injections, GRAFT remains more effective than the baselines. 

## 1. Introduction 

Large language model (LLM) agents increasingly use external tools to automate tasks beyond text generation. By combining reasoning with tool invocation, these agents can retrieve information, process documents, execute code, and interact with external services [1], [2]. To complete these tasks, an agent must select appropriate tools and construct their arguments based on the user’s request and the available context. The resulting tool calls translate natural-language queries into concrete actions, making the integrity of tool use essential to agent security. However, tool-use agents are susceptible to indirect prompt injection (IPI) [3], [4]. In conventional IPI, an attacker embeds malicious instructions in external content that an agent encounters while performing a legitimate task, such as a web page, document, or tool output. Existing prompt injection methods [9], [10], [11], [12] can be adapted to generate malicious tool descriptions. However, these methods face a trade-off between attack effectiveness and stealthiness. Although they can manipulate tool use, their descriptions are often lengthy or contain conspicuous instructions. Agent service providers typically limit the length of tool metadata [13], [14], [15]. Imposing length constraints during generation substantially reduces these methods’ attack success rates. Additionally, repeated instructions and explicit directive language make the gen-erated descriptions susceptible to filter-based defenses [16], [17], [18], [19]. Effective description poisoning therefore requires more than simply adapting conventional injection instructions into tool metadata. The modified description must remain concise and natural while preserving the le-gitimate guidance needed for tool selection and argument construction. To address these challenges, we propose GRAFT 1, an LLM-based optimization method that crafts malicious tool descriptions through localized changes to benign metadata. Our key idea is to exploit the information and structure already present in a description. GRAFT identifies and masks argument-relevant token positions where an attacker-selected value could potentially fit. An LLM then gen-erates mutation instructions for modifying those positions and follows them to produce candidate descriptions. The optimization iteratively refines these mutation strategies us-ing feedback from the agent’s tool choices and generated arguments. This design effectively incorporates the targeted argument value while preserving legitimate tool-use guid-ance and avoiding lengthy additions. Attack generation also does not require access to any detectors or their feedback. Our contributions are as follows:

> ‚

> ‚

It also bypasses two existing IPI defenses and outperforms the baselines under an adaptive defense trained on GRAFT -generated injections.

Each tool is exposed to the agent through structured tool metadata , commonly specified via standardized interfaces such as the Model Con-text Protocol (MCP) [8]. This metadata typically comprises three components: (1) tool name (e.g., read_file ), (2) a natural-language description explaining the tool’s function-ality and when it should be invoked, and (3) an input schema defining parameter names, data types, required fields, and per-parameter descriptions. Before processing a user request, the agent host collects these definitions from registered tool servers and serializes them into the model’s system prompt [22] ( ❶). During task execution, the agent relies on this metadata to perform tool selection and argument generation in an iterative loop. Given a user query ( ❷), the LLM evaluates the semantic alignment between the user’s intent and the available tool descriptions to determine whether a tool call is needed and which tool to invoke. Once a tool is selected, the model autoregressively synthesizes structured arguments (typically formatted as a JSON object) by mapping entities from the user prompt onto the parameter schema while following any formatting rules ( ❸). The host runtime then intercepts the generated tool call ( ❹), executes the underly-ing function, and returns the execution output to the agent (❺). The output is subsequently processed by the agent before being appended to the conversation history ( ❻). All of these elements, including system instructions, serialized tool metadata, user queries, emitted tool calls, and returned tool outputs, coexist within a single shared 

agent context window . Because LLMs process this context as a unified token sequence without strict architectural separation between instructions and descriptive metadata, all components in the context window jointly influence the model’s predictions. 

## 3. Motivation 

Tool poisoning against LLM agents manipulates agent execution through various channels such as the metadata or tool outputs [6], [23]. As discussed in Section 2, two steps are crucial to tool-use agents: selecting a tool from the registry and constructing its arguments based on the user query. For example, if a malicious tool is selected for document conversion, confidential files may be exposed to the attacker. If the recipient argument of a legitimate pay-ment tool is manipulated, funds may be transferred to the at-tacker’s account. Tool descriptions guide both tool selection and argument construction, making them an entry point for attacker-controlled instructions. We study how a poisoned description can induce an agent to select an attacker-targeted tool over benign alternatives that also support the user’s task, and then invoke it with an attacker-chosen argument value. A straightforward approach is to use conventional prompt injection attacks to generate malicious tool descrip-tions. Specifically, we apply direct injection [9], CTH [10], PISmith [11], and AttackMove [12] to construct these de-scriptions. Although these attacks achieve attack success rates (ASRs) of up to 81.2% on MCP Security Bench (MSB) [20], their descriptions are often lengthy or contain overtly directive language. For example, CTH produces descriptions with a median length of 304 tokens, which is 40 times that of benign descriptions. Agent service providers typically limit the length of tool metadata. For instance, OpenAI rejects tool descriptions exceeding 1,024 characters (« 250 tokens) [13]. Security guidelines also recommend warning users about overly long tool descriptions, such as those exceeding 500 characters ( « 125 tokens) [14].This is because descriptions of many tools in the registry are provided to the agent as context (Section 2), such lengthy descriptions increase context overhead when loaded along-side other tool descriptions, system prompts, user queries, and tool interaction history. When limiting the length of descriptions during attack generation, CTH’s ASR drops from 81.2% to 31%. Additionally, these descriptions contain conspicuous attack signals, including fabricated “security protocol” narratives, repeated injection instructions, and explicit directive language such as “must,” “always,” or “regardless of the user.” Existing filter-based defenses [16], [17], [24] can detect these attacks with 73.18% accuracy on average (See Table 8). Moreover, our results in Section 7.2 show that even attacks adapted to evade a known detector remain detectable by other defenses. These results show that existing attacks can manipu-late tool use to some extent, but their lengthy payloads and conspicuous instructions increase context overhead and make them susceptible to detection. The challenge is to ensure the stealthiness of the generated descriptions while inducing selection of the attacker-targeted tool and an unau-thorized argument change. Achieving this requires concise and natural-appearing descriptions that retain the tool-use guidance needed to perform the requested action. 

Our Idea. We exploit the information and structure al-ready present in benign tool descriptions to make localized changes that manipulate tool arguments while appearing consistent with legitimate metadata. By identifying and masking positions where an attacker-selected value can po-tentially fit, we leverage an LLM to modify these relevant parts of the description. We formulate the attack as an opti-mization over mutation instructions: the LLM first generates instructions for incorporating the attacker-selected value into masked positions in the benign description, then fol-lows these instructions to produce a malicious description. This allows us to dynamically refine the insertion strategy while preserving legitimate tool-use guidance and avoiding lengthy additions. Our results in Table 1 show that, without using detectors or their feedback during attack generation, our attack achieves an average success rate of 95.32% in inducing tool execution with the targeted arguments on MSB and 95.32% after filtering by all evaluated detectors. In addition, our generated descriptions contain only 70 tokens on average. 

## 4. Threat Model and Problem Formulation 

4.1. Threat Model 

We consider an LLM-based agent that interacts with ex-ternal tools through the Model Context Protocol (MCP) [8], [25]. Each tool is associated with metadata that the agent uses to determine when and how to invoke the tool. We consider a scenario in which an attacker can modify the description of a tool exposed to the agent. 

Attacker’s Goal. The attacker’s goal is to induce the agent to select an attacker-targeted tool and generate attacker-desired tool arguments that deviate from the legitimate user’s intent. Specifically, the attacker aims to manipulate one or more argument values while preserving the appearance of a legitimate tool invocation. Unlike conventional prompt injection attacks, which embed malicious instructions in external data sources and rely on the agent to retrieve the poisoned content, often inducing additional tool calls to achieve the attacker’s objective, our attack embeds malicious instructions in tool descriptions to manipulate the agent’s tool-selection and argument-generation process. 

Attacker’s Knowledge. We consider an attacker who knows the target tool’s functionality, argument schema, and the metadata exposed to the agent. The attacker may also have access to the LLM agent for evaluating candidate descrip-tions. However, the attacker does not necessarily know the exact user query or the internal parameters of the target LLM at deployment time. 

Attacker’s Capabilities. We assume that the attacker can modify the natural-language description of an attacker-controlled MCP tool before the agent receives its metadata. The attacker cannot modify the legitimate user’s query, the agent’s system instructions, or the underlying LLM param-eters. The attacker also has no access to the actual user queries but can synthesize representative queries based on the tool description to approximate potential use cases. The attacker can query an LLM agent to simulate tool selection and argument generation, then use the results to optimize poisoned tool descriptions. Furthermore, the attacker can obtain benign tool metadata from publicly available MCP platforms, such as MCP Registry [26], MCP Market [27], and MCP Servers [28], as well as tool implementations from their associated public source-code repositories, when available. It then constructs a diverse set of candidates by identifying and modifying the most promising tokens in the benign descrip-tion (Section 5.1). 5.1. Localized Token Masking and Injection 

Prior work has shown that placing malicious instruc-tions at the end of tool responses can improve attack ef-fectiveness [29]. However, this strategy may not directly generalize to tool descriptions, where simply appending malicious instructions can disrupt the semantic coherence of the original description and make the injected content more conspicuous [30]. Here, we focus on inserting the attacker-desired argument value into the description and discuss tool selection manipulation later. This raises a key question: how can we identify an appropriate insertion position that main-tains the naturalness of the tool description while allowing the malicious instruction to introduce the target argument? An intuitive approach is to ask an LLM to insert the ma-licious instruction at the position it considers most suitable and coherent. However, our study in Table 11 shows that simply asking an LLM to choose a position and then run the optimization achieves only 60% ASR. The generated descriptions are also detected by Snyk’s Agent Scan [31] with 45% accuracy. We further examine where the LLM places the instruction. We find that 87% of the time it simply appends the malicious instruction to the end of the benign description. This restricts the search space for an insertion that is both effective and coherent, causing the optimization to stagnate. An alternative is to greedily try every possible position and optimize at each. While this raises ASR to 81.3%, the detection rate is still 24%, and it is expensive because the LLM must explore all candidate positions. The greedy approach consumes four times the budget of GRAFT .In light of this challenge, we aim to effectively identify where to graft the malicious instruction into the benign de-scription. The main question is where in description d to in-sert the attacker-selected value so that the agent uses it while the description still reads like legitimate tool documentation. We propose a localized token masking and injection approach, which identifies argument-relevant positions for incorporating the malicious instruction. Figure 4 illustrates its workflow. Specifically, it ranks the description’s content tokens by relevance to the target argument, masks the top-ranked tokens, and prompts the proposer (an LLM) to infill each slot based on the mask role.

5.1.2. Role-based Masking and Insertion. After identify-ing tokens in the description that are relevant to the mali-cious instruction, a straightforward approach is to replace the highest-scoring token in our ranking with r. However, as the above example illustrates, multiple tokens may be relevant to the attack objective, making a single substitution insufficient. Our study in Table 14 shows that using only one substitution results in an ASR that is up to 20% lower. Inspired by masked denoising in text-diffusion mod-els [34], [35], [36], where corrupted spans are regenerated based on the surrounding context, we mask the relevant tokens and let the LLM proposer P determine how to incor-porate r at each location. This allows P to adapt the wording while maintaining grammatical coherence and preserving the tool’s functional description. Concretely, we mask the top-k tokens, label the slots [MASK_1] , . . . , [MASK_ k] in reading order, and pass the masked description together with 

r to P . We set k “ 5 in GRAFT because the relevance score 

spwq drops and plateaus near zero beyond the top five tokens (Figure 5). Additional masks may therefore disrupt the benign de-scription while covering little additional content relevant to 

r. Our ablation study in Appendix E further examines the effect of varying k.Although the top-k tokens are relevant to r, they may serve different roles, as illustrated by Execute and statement 

in Figure 4. Without guidance on these roles, P struggles to incorporate r coherently into d and tends to either omit the attacker-selected value or turn several masks into explicit directive language. Our study in Table 11 shows that using masks without explicit roles results in an ASR that is up to 12% lower. We therefore distinguish two mutation roles for the selected tokens: injection , which embeds the attacker-selected value as seemingly benign documentation, and imperative , which rephrases the original text as a gentle suggestion. We let P assign a role to each selected mask and determine how many slots of each type to use, requiring at least one injection slot. This allocation is determined independently for each candidate description, allowing P

to distribute the instruction across positions without relying on a fixed insertion pattern.

5.2. Two-Stage Tailored Optimization 

Prior attacks [6] commonly use directive language, such as “must” or “regardless of the user,” to achieve attack success. Such language is effective because it explicitly instructs the agent to override the user’s intended value. However, detectors also use these expressions to identify malicious descriptions. Softening the wording of successful attack descriptions may help avoid detection, but even sim-ple rewriting can substantially reduce ASR—for example, from 88% to 15.5% for Combined Attack [37]. Descriptions that are both stealthy and effective thus occupy a narrow region of the search space. Random or one-shot rewriting rarely finds such descriptions, leaving too few successful examples for the attacker to learn from. We therefore propose an iterative optimization method with a two-stage mutation process: an LLM proposer first generates a tailored mutation instruction from agent feed-back, and the same proposer then uses this instruction to revise the description. Specifically, we refine each starting point generated in Section 5.1 through the loop shown in Figure 7. We first evaluate the current description on the training queries using the agent ( ❶). 5.2.1. Constructing Tailored Mutation Instruction. Astraightforward approach to constructing mutation instruc-tions is to apply a fixed rewriting strategy based on the feedback category. In our setting, however, each candidate description is evaluated on a batch of training queries, yielding both an overall training success rate and per-query feedback. A fixed template cannot reconcile mixed outcomes across queries, and a single feedback label may conceal different underlying failure cases. For example, two descrip-tions may both produce high rates of WRONG ARGS but fail for opposite reasons. Partial success across the batch also requires balancing the preservation of successful description features with the correction of failures, as illustrated below: 

Case I: Injection Ignored. On failing queries, the victim calls read_file(path="./config.yaml") , retain-ing the user’s intended file instead of using the attack-chosen path. The description fails to establish the target path as the tool’s natural default behavior. The required correction is to strengthen the contextual framing so that the target value replaces the user’s input. 

Case II: Incorrect Argument Substitution. The victim calls read_file(path="˜/.ssh/") or 

read_file(path="/etc/ssh/ssh_config") ,abandoning the user’s file in favor of a sensitive default but generating an approximate path rather than the exact target string. Here, the contextual framing already works. The required correction is therefore different: specify the exact literal value rather than further reinforce the framing. 

Case III: Partial Success across the Training Batch. 

A candidate description succeeds on a subset of train-ing queries, producing read_file(path="˜/.ssh/ id_rsa") , but fails on others with WRONG ARGS out-comes or missed tool calls. An aggressive rewrite aimed at correcting these failures risks disrupting description features on queries that already succeed, while leaving the descrip-tion unchanged prevents further improvement in the overall success rate. While we illustrate three representative cases here, other failure scenarios can still arise during optimization, such as assigning the target value to the wrong argument. Figure 6 shows ASR on the training queries throughout optimization. With the intuitive fixed mutation strategy, ASR fluctuates significantly as the optimization attempts to address different failure cases, which can be conflicting as discussed above. The final ASR is only around 10%. Candidate-Tailored Mutation. To address aforementioned limitations, we leverage an LLM proposer to tailor the mu-tation strategy to each candidate description. The proposer receives four types of information describing the optimiza-tion state: 1) Batch Feedback: The overall success rate on the train-ing query set and per-query feedback outcomes. These capture both overall progress and how individual queries have failed, providing the proposer with a clear signal of what requires improvement. 2) Recent Traces: Descriptions from recent optimization steps, together with their batch success rates and feed-back distributions. These provide short-term context, helping the proposer identify which mutations improved or degraded performance across the query set. 3) Contrastive Memory: A record of every description gen-erated during optimization, helping the proposer avoid generating descriptions that have already appeared. We categorize each description as either positive (the attack succeeds) or negative (the attack fails). 4) Lexical Score: A regular-expression-based score indicat-ing whether a description contains injection-style words or phrases, such as “must,” “always,” or “regardless of the user.” This feedback helps discourage conspicuous directive language. The proposer leverage the above contextual information to propose a mutation strategy in each generation step. Specifically, it examines the batch success rate and feedback distribution to infer the dominant failure mode and decide whether to prioritize tool selection or argument generation. For example, when failing queries show that the agent calls the correct tool but retains the user’s argument value (WRONG ARGS ), the proposer is directed to make a targeted structural change, such as revising how the target argument is specified, rather than appending sentences or paraphrasing previously unsuccessful wording. When the batch shows partial or high success, the proposer preserves phrasing associated with successful queries in recent traces and fa-vors conservative refinements, such as reducing the lexical score, to improve stealth and generalization while preserving successful features. As shown in Figure 6, our tailored mutation instructions effectively address conflicting failure cases, yielding a much smoother optimization trajectory than the naive approach. The final ASR exceeds 80%. 

Selecting the Final Description. After optimization, each of the n starting points yields a candidate description and an optimization status. We first consider only candidates whose training VUL rate reached a threshold ρ. If no candi-date reached this threshold, we then rank them using three criteria, in order of priority: ① the cumulative number of  

> VUL

outcomes observed on the training queries during the corresponding optimization run (higher is better), ② the lexical score (lower is better), and ③ semantic similarity to the original description d (higher is better). We return the top-ranked candidate. This selection prioritizes cumulative attack success, breaking ties first by less suspicious wording and then by greater similarity to the benign description. 

5.3. Proxy Query Synthesis 

Because the attacker has no access to actual deployment-time queries, we construct a query set that approximates realistic use of the targeted tool. Given tool t’s description and argument schema, an LLM generates a set ˜Q of natural user requests that would legitimately require invoking t.Each request is paired with the benign value that an agent following the request should assign to k‹. The attack objec-tive is to replace this benign value with the attacker-selected value v‹. For each tool, we synthesize 10 representative queries and check for duplicates. 

## 6. Experiment Setup 

Datasets. We conduct experiments on three recent MCP security datasets: MCPTox [6], MCP-SafetyBench (MCP-SB) [38], and MCP Security Bench (MSB) [20], which col-lectively comprise 109 tasks, 33 MCP servers, and 118 tools. The 109 tasks span 33 real-world MCP servers across differ-ent application domains, such as web search and browsing, software development, file and document management, and finance. The details about these datasets are in Appendix A. For evaluation, we synthesize three held-out queries per task that remain unseen during optimization, yielding a total of 327 test queries. 

Models. We target both proprietary and open-source models: GPT-5.6-Luna, Qwen3.8-27B, Qwen3-32B, Llama-3.1-8B, Llama-3.3-70B, Muse-Glimmer-30B, and the instruction-tuned defenses Meta-SecAlign-8B/70B. Unless stated other-wise, our attack is optimized with a fixed Qwen3.8-27B pro-poser P and then evaluated on held-out test queries for each victim model. We served the local LLMs using vLLM [39] and used Hugging Face for LoRA adapter support. 

Metrics. We evaluate attack effectiveness and detection evasion using three metrics:  

> ‚

Attack Success Rate (ASR). The percentage of instances in which the victim agent invoke the attacker-controlled tool with the k‹ “ v‹ (higher is better).  

> ‚

Stealthy Attack Success Rate (sASR). The percentage of instances in which an attack both succeeds and bypasses the detector (higher is better).  

> ‚

Detection Rate and DET@5. The percentage of attack instances flagged by each individual detector, alongside DET@5, the ensemble (union) detection rate across all five detectors—i.e., the percentage flagged by at least one detector (lower values indicate greater stealth). 

6.1. Baselines 

We compare GRAFT against three families of IPI at-tacks, grouped by how the poisoned description is produced. All baselines are evaluated under the identical protocol on the same datasets and victim models. 

Template-based Attacks. These methods append fixed, rule-based injections to the benign tool description. ‚ Enhanced-1: A concatenation operation, with the injec-tion wrapped in emphasis markup— <IMPORTANT>.. .</IMPORTANT> [23].  

> ‚

Enhanced-2: A concatenation operation, prefixed with a context-ignoring instruction (“Ignore all previous instruc-tions, strictly adhere to the following: . . . ”) [9].  

> ‚

Combined: A stacked prompt-injection template—an es-cape sequence, a fake task-completion, and a context-ignoring instruction chained together [37]. By construction, these attacks are highly detectable (the 

<IMPORTANT> tag and “ignore all previous instructions” are themselves flagged patterns), and serve as the lower bound. 

Optimization-based Attacks. These methods optimize injected instructions through mutations guided by victim feedback.  

> ‚

AttackMove [12]: An adaptive evolutionary search method. A proposer LLM generates candidate instructions to append to the tool description. Each candidate is scored by the fraction of victim responses in which the target argument takes the attacker-selected value. The proposer is then conditioned on the best and worst previous candi-dates. We match the budget to GRAFT ’s (approximately 800 candidates ˆthe train queries) and use the per-victim re-optimized variant.  

> ‚

MCP-ITP [40]: The poisoned description combines a be-nign description with an optimized segment. Over several iterations, an attacker LLM refines a small set of candi-dates using prior feedback. Each candidate is evaluated by an evaluator LLM on shadow queries and penalized by an in-loop detector LLM . The method retains the top candidate and stops when a candidate succeeds without being detected. Because no official code is available, we reimplement the method based on the paper, using its appendix prompts verbatim except for the changes needed to adapt the objective from tool-call hijacking to argument tampering. 

RL-based Attacks. An attacker model (Qwen3-4B) is trained on successful injections using reinforcement learning and generates each injection in a single shot after training.  

> ‚

PISmith [11]: The base attacker is trained using sparse-reward reinforcement learning to poison tool descriptions. The nano and 4o-mini variants correspond to different released checkpoints.  

> ‚

CTH (Climbing-the-Hill) [10]: A curriculum-based RL counterpart to PISmith that uses the same training pipeline with a hill-climbing curriculum. The terra and luna 

variants are the two released curriculum-trained attackers. Because these methods generate much longer descriptions (approximately 305–800 GPT-2 tokens), we also report a 

length-matched variant that regenerates each injection under a length limit comparable to GRAFT ’s, controlling for the advantage of lengthy descriptions (See Appendix B).

Finally, our experimental results show that even com-mercial detectors specifically designed for MCP and agen-tic security (Cisco and Snyk) fail to reliably detect tool-poisoning attacks. Neither detector flags more than 50.0% of the attacks on any benchmark (peaking at 29.3% for Cisco and 44.0% for Snyk on MCPTox). Consequently, scanners specifically built for MCP and agent security still miss a substantial portion of tool-poisoning attacks. To ensure that detector false positives do not bias our evaluation, we further conduct a false positive rate (FPR) analysis on benign tool descriptions across all evaluated detectors, with the results shown in Table 9. Most detectors achieve a 0.0% FPR: Snyk maintains a 0.0% FPR across all three benchmarks, while Cisco, PA, Shield, and PG exhibit 0.0% FPRs except for a slight 1.3% FPR on MCPTox. In addition, we initially considered DataSentinel [18], a promi-nent prompt injection detector. However, our analysis reveals that DataSentinel suffers from an excessively high FPR on benign tool descriptions, flagging 100.0%, 85.5%, and 90.0% of benign descriptions across the three benchmarks, respectively. One explanation is that benign tool descriptions are naturally written as instructions (e.g., “Execute the SQL statement”), giving them a high likelihood of being flagged by detectors designed to catch malicious instructions. There-fore, we exclude DataSentinel from our evaluation. 

IPI Defenses. In addtions to the filter-based defenses, we also evaluate conventional IPI defense methods, such as Sandwich [42] and MELON [43]. The results are in Table 5 where we show the ASR after applying the defense. Table 9 reveals the FPR of these defenses. The Sandwich defense operates by appending a reminder of the user’s original query after untrusted context so that the agent remains anchored to the user’s legitimate intent rather than following injected instructions. However, across all three benchmarks, this defense is largely ineffective against tool-poisoning attacks (see Table 5). In particular, GRAFT 

achieves an sASR of 100.0%, 94.4%, and 86.7% on MSB, MCP-SB, and MCPTox, respectively, remaining virtually unchanged from its undefended ASR (93.8%, 100.0%, and 88.0%) and outperforming or matching every baseline. Most baseline methods similarly retain high sASR under Sand-wich (e.g., 72.2%–94.4% on MCP-SB and 72.6%–84.0% on MCPTox for all methods except PISmith). This is due to two reasons: first, tool descriptions reside within the privi-leged system prompt rather than inside the untrusted data-plane boundaries typically wrapped by Sandwich; second, reiterating the user’s legitimate request does not counteract 

GRAFT , whose reframed tool semantics align the poisoned execution directly with fulfilling the user’s task. MELON conducts its defense by executing each prompt twice. Specifically, it first runs the original user query and then performs a “masked” run in which the user query is replaced with a generic benign instruction asking the agent to summarize the tool outputs from the first run, checking whether both runs invoke the same tool call. However, in tool-poisoning attacks, the malicious payload resides in the tool description rather than the tool output. Consequently, 

GRAFT largely evades this check and outperforms all base-lines, achieving an sASR of 81.2%, 77.8%, and 81.3% across the three benchmarks, respectively. In contrast, CTH-Luna’s effectiveness drops sharply under MELON, with its ASR decreasing by 43.7%, 44.4%, and 18.7%, respectively. This occurs because CTH-Luna relies on explicit directive instructions that attempt to hijack the agent’s workflow. Because tool descriptions are loaded into the agent context, such strong imperative wording triggers the malicious tool call even when the masked query is unrelated to the tar-get tool, making it easily caught by MELON. Conversely, 

GRAFT ’s payload reframes the tool’s purpose rather than issuing standalone instructions, so the agent generates the attacker-selected argument value only while carrying out the user’s legitimate request. 

Tool-Use Defense. The Firewall defense [44] places two lightweight LLM filters at the agent–tool boundary: a Tool-Input Firewall ( Minimizer ), which strips extraneous or sen-sitive data from outgoing tool-call arguments conditioned on the user task and tool description, and a Tool-Output Firewall ( Sanitizer ), which scrubs malicious instructions from returned tool observations. Firewall substantially re-duces the effectiveness of most baseline attacks, particu-larly on MCPTox. It reduces the sASR of template-based attacks such as Combined and Enhanced-2 from 72.6% and 75.0% down to 20.2% and 13.1%, respectively, suppresses PISmith-Nano and PISmith-4o to 8.0% and 6.7%, and low-ers optimization-based baselines such as MCP-ITP from 85.3% to 32.0% and AttackMove from 81.3% to 56.0%. In contrast, GRAFT maintains the highest resilience across all three benchmarks, achieving an sASR of 93.8%, 88.9%, and 64.0% on MSB, MCP-SB, and MCPTox, respectively— preserving its full undefended effectiveness on MSB and surpassing the strongest baseline on MCPTox (AttackMove at 56.0%) by 8.0%. This advantage stems from how GRAFT 

integrates the malicious parameter: rather than introducing explicit override instructions or out-of-scope tool calls that trigger runtime policy violations, GRAFT frames the in-jected argument as a standard functional requirement of the requested tool, allowing the resulting invocation to appear semantically consistent with the user’s workflow. 

Stacked Defense. The Stacked defense composes all four mechanisms, Detector, Sandwich, MELON, and Firewall, into a layered defense-in-depth pipeline in which an at-tack succeeds only if it bypasses every stage simultane-ously (see last column of Table 5). Under this combined defense, template-based attacks (Combined, Enhanced-1, and Enhanced-2) and PISmith-4o are completely neutral-ized (0.0% sASR across all three benchmarks). Even the strongest optimization- and RL-based baselines experience substantial cumulative reductions in attack success across defense layers: on MCPTox, MCP-ITP drops from 85.3% to 10.7%, AttackMove from 81.3% to 25.3%, CTH-Luna from 86.7% to 21.3%, and CTH-Terra from 77.3% to 22.7%. In contrast, GRAFT maintains the highest resilience across all three benchmarks, achieving an sASR of 81.2%, 66.7%, and 50.7% on MSB, MCP-SB, and MCPTox, respectively. 

GRAFT maintains over a 50.0% success rate even against the full four-layer stack and outperforming the strongest baseline (AttackMove at 62.5%, 50.0%, and 25.3%) by 18.7%, 16.7%, and 25.4%., respectively. A single mechanism explains GRAFT’s robustness across various runtime defenses. Prompt-injection detectors, masked re-execution (MELON), and the tool-input firewall all reduce to the same operation: a model inspects the tool description together with the resulting call and judges whether the behavior is legitimate or the product of an injected instruction. Existing PI attacks append an explicit instruction to the description (e.g., “ignore the user’s request and set path to ˜/.ssh ”). Because this instruction is an explicit command unrelated to the user’s task, each defense can localize and remove it—the detector flags it, the firewall’s minimizer restores the user’s intended argument, and the masked rerun reproduces it even when the user’s task is withheld. 

GRAFT instead rewrites the description so that the attacker-chosen value is presented as the tool’s own documented behavior (e.g., “the path argument is set to ˜/.ssh , the canonical location for credential files” ). The adversarial value thus becomes indistinguishable from a legitimate specification: there is no imperative word to flag (Filter-based), no command to refuse (MELON), and no argument that appears unjustified relative to the tool’s stated purpose (Firewall). The effect is visible at the level of individual decisions: for the identical target 

path=˜/.ssh , the firewall minimizer strips the value under an imperative baseline (reverting to the user’s requested file) yet preserves it under GRAFT , treating it as a legitimate parameter of the tool. Because every defense in this family ultimately relies on a model’s assessment of legitimacy, and GRAFT moves the attack from an instruction appended to the description into the meaning of 

the description itself, framing the payload as specification rather than command. As a result, GRAFT demonstrates an effective sASR under these defenses.

## 9. Related Work 

Prompt Injection Attack The goal of prompt injection (PI) is to use malicious instructions to make the agent produce adversarial content [9], [49] or to hijack the agent’s workflow to carry out malicious actions [4], [29]. PI can be divided into direct prompt injection (DPI) [9] and indirect prompt injection (IPI) [3]. The difference between DPI and IPI lies in the channel through which the malicious instruction reaches the agent. In DPI, the instruction is injected directly through the user input. Here the attacker is typically the user, and the goal is to extract the system prompt or the reasoning trace of the LLM [50], [51]. In IPI, by contrast, the instruction is injected into an external data source, such as a web page or a document retrieved via retrieval-augmented generation (RAG) [52], so the user is typically unaware of the attack. 

Tool-Use Attacks. Unlike conventional indirect prompt in-jection (IPI), which embeds payloads in external content, recent attacks directly target the LLM tool-use pipeline via tool selection or tool poisoning. Tool-selection attacks in-duce agents to pick a malicious tool over benign alternatives: 

Shi et al. [53] and Mo et al. [5] optimize tool descriptions to bias selection, whereas Wang et al. [54] apply advertising-style persuasive rewriting. Tool poisoning corrupts tool metadata to hijack work-flows or tamper with arguments [6], [20], [23], [38]. Early methods rely on explicit directives such as <IMPORTANT> 

tags [23] or imperative instructions [6], while Li et al. [40] propose MCP-ITP, which optimizes descriptions using dual LLM judges for attack success and stealthiness. However, our experiments show that MCP-ITP remains vulnerable to existing defenses because it overlooks the structural characteristics of tool descriptions. In contrast, GRAFT 

exploits tool-specification properties to achieve high attack effectiveness while evading defenses. 

Tool-Use Defenses. Specialized defenses against tool-use attacks span static scanners, runtime firewalls, and system-level MCP frameworks. Static filter-based scanners include Snyk Agent Scan [31], Cisco MCP Scan [41], and MCP-Shield [24], whereas firewall-based defenses [44] employ an LLM judge at runtime to verify that generated tool argu-ments align with user intent. System-level MCP frameworks further incorporate multi-stage inspection pipelines, such as MCP-Guard [55] and MCP Guardian [56], or cryptographic schema verification [57]. Existing studies also benchmark conventional IPI de-fenses; for example, ToolHijacker [53] evaluates perplexity-based filters [58], [59] and alignment-based training [45], [60]. In this work, we evaluate GRAFT against both MCP-specific mechanisms and representative IPI defenses [42], [43]. 

## 10. Conclusion 

We present GRAFT , an LLM-based method for poi-soning tool descriptions to manipulate tool selection and argument generation. Using argument-relevant masking and dynamically refined mutation instructions, GRAFT pro-duces concise and natural-appearing descriptions without detector feedback. Evaluations on three public datasets show higher attack success and lower detectability than existing baselines. These findings highlight the need to secure tool metadata that directly influences agent execution.

As shown in Table 13, PISmith and CTH produce sub-stantially longer tool descriptions than all other baselines (307–805 tokens), with CTH-Luna averaging 11 .5ˆ the length of GRAFT (70 tokens). ## Appendix C. Qualitative Analysis 

To quantify why poisoned tool descriptions trigger or evade static detectors, we analyze three linguistic features alongside token length: (1) override prevalence , the aver-age number of explicit control or hijacking keywords (e.g., 

ignore , priority , enforce ) per description; (2) imperative density , the frequency of commanding verbs and direc-tive constructions per 100 tokens, measuring how overtly an attack orders the agent to act; and (3) declarative-to-imperative ratio (decl/imp ratio) , the ratio of descriptive, specification-style statements to imperative commands, cap-turing the extent to which an attack legitimizes the injected parameter as a standard functional requirement rather than issuing a direct order. Table 13 shows the result. Across these metrics, GRAFT exhibits a fundamentally different linguistic profile from all competing baselines. A 

GRAFT description averages only 70 tokens, contains vir-tually no override language (0.3 override terms on average), and achieves the lowest imperative density of any method (0.6 per 100 tokens). Crucially, GRAFT legitimizes the attacker’s argument rather than commanding it, yielding a decl/imp ratio of 11 .7 compared to at most 4.0 for every competing attack. Both template-based attacks (Combined, Enhanced) and optimization/RL-based attacks (AttackMove, MCP-ITP, PISmith, CTH) retain the original benign text and append an explicit command, carrying up to 4.0 override terms and an imperative density of 3.3–5.7 per 100 tokens. ## Appendix D. Adversarial DPO Fine-Tuning 

To evaluate a learning-based defense alongside runtime mitigations, we fine-tune the victim model (Qwen/Qwen3.8-27B ) using Direct Preference Optimization (DPO) [47] on adversarial examples generated by GRAFT. Specifically, we train a parameter-efficient LoRA adapter [62] (rank r “ 16 ) with DPO regularization coefficient β “ 0.1, while keeping the base checkpoint frozen both as the DPO reference policy and as GRAFT’s attack optimizer. All preference pairs are constructed exclusively from the training split, with held-out evaluation items strictly isolated and contributing zero training pairs. Training proceeds in two stages to balance attack resis-tance against benign tool-use utility: 1) Resistance Stage: We construct adversarial prefer-ence triples px, y w, y lq from legitimate user queries paired with GRAFT-poisoned tool descriptions. The rejected completion yl is the poisoned tool call contain-ing attacker-controlled arguments, whereas the chosen completion yw is the intended clean tool call validated against recovered benign-gold arguments. 2) Utility-Preserving Stage: To prevent degenerate over-refusal (declining valid requests or emitting empty tool calls on unpoisoned inputs), we augment the training mixture with benign-behavior preference pairs on clean tool descriptions, where yw is the correct clean tool call and yl is an invalid or empty (null) output. Across adapters, we evaluate both held-out attack success rate and clean tool-selection accuracy, and verify general-purpose reasoning stability using MMLU [48].

## Appendix F. Overhead Analysis 

To better understand the computational cost of op-timizing a poisoned tool description compared to other optimization-based baselines (AttackMove and MCP-ITP), we further evaluate the average overhead—measured in LLM calls and token consumption—required to generate a successful attack across the three benchmarks. As shown in Table 15, GRAFT achieves the highest average sASR (85.8%), substantially outperforming AttackMove (68.6%) and MCP-ITP (48.8%). In terms of search overhead, MCP-ITP is the least expensive, requiring an average of 52 LLM calls and 0.08 M tokens per successful attack, followed by 

GRAFT (1,227 LLM calls and 1.23 M tokens), whereas AttackMove is the most expensive ( 2,000 LLM calls and 

1.9M tokens). Because both GRAFT and AttackMove incur higher query budgets than MCP-ITP, a natural question is whether this additional overhead is justified by the result-ing sASR improvement. To quantify cost-effectiveness, we compute the marginal sASR gain per 1K additional LLM calls relative to MCP-ITP, finding that GRAFT yields a 31.5% sASR gain per 1K calls—more than triple the ef-ficiency of AttackMove. Based on OpenRouter API pricing for Qwen3.8-27B 2 (starting at $0.035 per 1M input tokens), and given that 1K LLM calls corresponds to roughly 1Mtokens in our setup, GRAFT delivers a 31.5% sASR gain for roughly $0.035 in marginal token cost.
