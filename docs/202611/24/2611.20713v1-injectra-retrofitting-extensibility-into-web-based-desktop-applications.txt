# Injectra: Retrofitting Extensibility into Web-Based Desktop Applications 

## Qin Sun 

# kingsun22515@gmail.com 

Abstract 

Large language models can generate code based on natural language prompts, opening up new possibilities for users to customize software and extend its functionality. However, applying gen-erated code to existing desktop software that users rely on daily still poses engineering challenges, such as integrating with heterogeneous host systems, adapting to runtime environments, and deploy-ing enhanced features. Existing research has implemented various forms of software modification through specific interface toolkits, browser extensions, dedicated application architectures, and exter-nal overlay interfaces; however, their integration requirements and scope of applicability vary, and there remains a lack of a universal, cross-application extension solution for existing desktop clients. This paper proposes and implements Injectra, a general-purpose code injection and feature en-hancement system for existing desktop clients, suitable for applications whose user interfaces are built using embedded browser engines (such as Electron) or system WebViews (such as Tauri). In-jectra decouples the host integration logic from the upper-layer enhancement code. Combining both runtime integration and pre-launch bootstrap mechanisms, it injects JavaScript, HTML, and CSS into the application’s internal Web runtime environment through a unified execution channel, thereby enabling modifications to interface rendering, adjustments to interactive behaviors, and client-side functionality extensions. The system uses a command-line interface (CLI) as a unified entry point, allowing external tools, AI agents, and MCP integration layers to reuse its injection and enhancement capabilities. We tested 38 desktop applications already installed on our macOS machine; code injection was successfully completed for all of them. We demonstrated the system’s capability to extend functional-ity through various enhanced use cases and also successfully validated the Windows version. Based on Injectra, we further developed an LLM-powered enhancement tool driven by selection and annotation: users select interface objects within the original application and describe their modification require-ments; the large language model then generates the enhancement code, which is injected, executed, and rendered by Injectra. Experimental results demonstrate that Injectra possesses generalized, cross-application integra-tion capabilities within typical desktop applications, and that various upper-layer enhancement tools can reuse its unified execution infrastructure. Injectra provides a unified in-application execution foundation for both manually written and AI-generated enhancement code, driving the evolution of existing desktop software from a closed model—which only provides predefined functions and cus-tomization options—toward a user-extensible software environment. The system’s source code has now been released as open source: https://github.com/sqmw/injectra .

# 1 Introduction 

Users’ actual needs are often more specific than what a software’s preset features can cover, and they constantly evolve depending on the task and usage context. Within the same application, some users may want to hide controls unrelated to the current task, others may need to reorganize interface information, and still others may wish to add annotation, filtering, or auxiliary processing functions alongside existing content. At the same time, users have accumulated data, operational habits, and workflows through their daily use of software. Redeveloping an application or migrating to other tools to meet these needs entails significant costs; in contrast, directly supplementing the required capabilities within the user’s familiar 1arXiv:2611.20713v1 [cs.SE] 16 Nov 2026 software environment offers more immediate practical value. This is precisely the focus of software plasticity and end-user extension: enabling software to continuously adapt to specific usage contexts, rather than being limited to the configuration options provided in advance by developers [14, 12]. Large language models offer new technical opportunities for achieving this goal. Users can describe their modification intentions using natural language, with the model assisting in generating or adjusting implementation code, followed by iterative feedback based on the interface results. Stylette explores an interactive approach for expressing web styling goals through natural language, while DirectGPT com-bines direct manipulation with large language models, demonstrating the value of pointing to specific objects and making modification requests [10, 15]. These studies indicate that a more direct connection can be established between users expressing their needs and modifying software. However, generating enhanced code is only one step in the process: the code must also be integrated into the application the user is currently using, executed within the correct interface context, and work in tandem with existing functionality. This deployment challenge is particularly pronounced in existing desktop applications. Desktop clients typically organize their interfaces and functionality around their own product goals; whether and how external code can enter the application depends on the extension interfaces, debugging capabilities, and runtime environment provided by the host. Even if both clients use Web technologies to build their interfaces, their page discovery methods, launch processes, and code execution entry points may differ. If every enhancement tool must handle these differences anew, integration with the host would become cou-pled with specific functional implementations, and cross-application reuse would be limited. Therefore, a common integration and execution layer—one that can be reused by different enhancement tools—is needed to bridge the gap between natural language requirements and in-application functional extensions. Research on software transformation has explored various implementation paths. For example, Jelly generates interfaces mediated by a task-driven data model and transforms users’ natural language com-mands and direct manipulations into modifications to this model, enabling the interface and data to con-tinuously evolve according to task requirements [2]; DOMSteer directly modifies the DOM in real-time web pages via browser extensions to provide users with in-situ assistance [8]; Interface Quilt, meanwhile, combines a computer operation agent with generative interfaces to overlay interface patches on existing ap-plications, altering their presentation, interaction, and usability [16]. These approaches demonstrate that existing software can gain new interactions and functionalities at different levels, but they correspond to different integration prerequisites: altering the data model within generative systems, modifying pages within the browser, and overlaying new interfaces externally—each acting on distinct software layers. This paper further focuses on the internal execution environment of existing Web UI desktop clients, in-vestigating how to organize their integration capabilities into a reusable, general-purpose infrastructure. Web UI desktop applications provide a common technical foundation for researching this issue. The mainstream architectures of such applications can be divided into two categories based on the source of the rendering engine: those that bundle a browser kernel within the application (such as Electron) and those that call the operating system’s WebView component (such as Tauri). Although they differ in how they integrate with the desktop host and platform, their Web interfaces share execution and rendering mechanisms based on JavaScript, HTML, and CSS. This commonality implies that the host-related inte-gration process can be separated from the upper-layer enhancement logic: the former is responsible for establishing an execution channel for the target application and pages, while the latter utilizes the inter-face environment to implement the required functionality. Based on this observation, this paper proposes a research question: How can a universal code integration and enhancement execution layer be estab-lished for existing Web UI desktop applications, enabling both manually written and model-generated enhancement code to be deployed and executed within the original application, and reused by different upper-layer tools? 

Answering this question requires addressing challenges at both the integration and reuse levels. At the integration level, it is necessary to connect the execution entry points of different hosts to specific application pages, while accommodating both applications that are already running and those that require entry points to be prepared before startup. At the reuse level, upper-layer tools must be able to submit 2enhanced code, update enhanced content, and obtain execution results in a consistent manner, without having to implement integration processes for various hosts themselves. The universality here is reflected in the reuse of integration mechanisms and execution capabilities; object selection and business logic dependent on the semantics of specific pages are handled by the corresponding enhancement tools. This paper proposes and implements Injectra, a general-purpose code injection and functionality enhancement system for existing Web UI desktop applications. Injectra decouples host integration logic from the enhancement execution mechanism and combines two paths—runtime integration and pre-launch initialization—to inject JavaScript, HTML, and CSS into the target application’s Web interface environment. On top of a shared execution mechanism, enhancement code can alter interface presentation, adjust interactive behavior, or extend client-side functionality. The system provides a unified command-line interface (CLI) and a reusable library layer, enabling enhancement payloads and external tools to share the underlying integration capabilities. This organizational approach allows Injectra to support enhancements from various sources, including scripts written by developers and code generated by large language models. The following sections first review relevant research and define the system’s scope and design objec-tives, then introduce Injectra’s architecture and implementation, and subsequently demonstrate its capabil-ities through reference enhancement examples and system validation. Finally, we discuss its applicability limits and future research directions. 

# 2 Background and Related Work 

## 2.1 Background 

2.1.1 Web UI Desktop Applications 

A Web UI desktop application refers to a desktop client whose user interface is built, in whole or in part, using Web technologies. Such applications typically consist of two components: a native layer and a Web interface environment. The native layer handles window management, process organization, and calls to operating system capabilities, while the Web interface environment is responsible for executing and rendering documents, scripts, and styles. In terms of how the rendering engine is deployed, Electron integrates Chromium and Node.js into its application framework and distinguishes between the main process and the rendering process: the main process manages application windows, while the rendering process hosts the web pages within those windows [7]. Tauri, on the other hand, uses the WebView provided by the operating system to render the front end and connects the front end to native capabilities through a communication mechanism between the Rust core and the WebView [18]. A single desktop application can contain multiple windows or WebViews, and a single window can also contain multiple documents and execution contexts. The environments of the native layer and page scripts are not identical. For example, in Electron, the main process, preload scripts, and page scripts have different responsibilities, and context isolation can be applied between preload scripts and web pages [7]. Whether a page can access files, window management, or other native capabilities depends on the interfaces exposed by the native layer to that environment. Therefore, when describing where code is executed within an application, it is necessary to distinguish between the application process, the WebView, and the specific page context. 

2.1.2 Web Documents and Execution Contexts 

HTML describes the document structure, CSS describes style rules, and JavaScript executes logic, handles events, and manipulates the document through interfaces provided by the runtime environment. The 4Document Object Model (DOM) represents a document as a node tree and defines nodes, events, and their operation interfaces [19]. Modifications to nodes or styles can alter the page’s rendering, while event-handling code links user actions to page behavior. Desktop windows, DOM nodes, and internal business objects within an application belong to different levels of representation: the nodes and properties accessible to a page are not directly equivalent to the host’s entire internal state. The execution context specifies the global objects and variable environment visible to the script at runtime. A single page can have mutually isolated scripting environments: for example, content scripts in Chrome extensions are by default in an isolated environment, where their JavaScript variables are separated from the page’s scripts, yet they can still manipulate the corresponding document [4]. The debugging interface also organizes code execution through target and context identifiers; the Runtime domain of the Chrome DevTools Protocol (CDP) provides protocol operations related to expression eval-uation and execution contexts [3]. Therefore, sending code to a JavaScript engine and executing a piece of code within a specific application page that can access the target document are two distinct operations that require separate descriptions. 

2.1.3 Code Injection and Enhancement Payloads 

This paper refers to the client that hosts the original interface and functionality as the host application 

, and refers to external code and resources that add rendering, interaction, or client-side logic to it as 

enhancement payloads . connecting to refers to establishing a communication channel directed at the target host and its pages, while injecting refers to loading the payload into the target execution environ-ment through that channel. In a web interface, an enhanced payload can include JavaScript, HTML, and CSS; HTML and CSS are used as document and style resources, respectively, while associated scripts are responsible for assembling them into the page and implementing the corresponding behavior. The payload may originate from manually written files or code generated by other tools. To describe the timing of establishing an access point, this paper uses the terms “runtime access” and 

“pre-launch bootstrap” . Runtime access targets applications that are already running and establishes a page execution channel through available debugging interfaces or host bridges. Pre-launch bootstrapping, on the other hand, first prepares a bootstrap code segment that is loaded when the application starts; this bootstrap code then connects to an external control endpoint and loads subsequent enhancement payloads. Both describe the timing and method of entry point establishment; the enhancement code subsequently runs within the execution environment of the corresponding application. Entry point establishment, pay-load generation, and payload updates are distinct stages in this process. 

2.1.4 End-User Extension and LLM-Assisted Modification 

End-user programming emphasizes programming activities that serve the user’s own tasks; it is defined by the purpose of the activity rather than the participant’s professional status or programming proficiency. End-user development also involves modifying and extending software during use [12]. Software plas-ticity focuses on the modifiability of software during use, such as when users continuously adjust its pre-sentation, interaction, or functionality [11]. In the LLM-assisted modification process, natural language descriptions, the selection of interface objects, or direct manipulation can serve as inputs for modification intent, with the model generating or adjusting the corresponding implementation [10, 15]. Requirement expression, implementation generation, and code execution correspond to different responsibilities in this process; it should be noted that LLM-based augmentation tools do not necessarily adopt an agent architec-ture: their code generation can be organized as a fixed request–generation–execution workflow without the need to introduce autonomous planning or multi-step decision-making mechanisms. 52.2 Related Work 

2.2.1 Malleable Software Environments 

One line of research incorporates plasticity into the organization of documents, data, and applications by designing software environments that support sustainable modification. Webstrates treats web pages as shareable dynamic media; through DOM synchronization between the server and client, it enables collaborative modification of document content, interfaces, and code [11]. Its plasticity is built upon Webstrates’ hosted and shared environment; applications or documents gain the corresponding modifica-tion capabilities upon joining this environment. Jelly, on the other hand, generates interfaces mediated by a task-driven data model and translates natural-language requests and direct manipulations into modifica-tions to the data model, causing the interface and data to update continuously[2]. It organizes continuous customization as an evolutionary process of the data model and interface within the generation system. These works provide environments and representation methods for building plastic software, but their modification mechanisms rely on corresponding shared foundations or generative models. When the re-search subject is a third-party client that has already been deployed but was not built using these en-vironments, the question of how to integrate into its existing execution environment requires separate consideration. Injectra focuses on this integration layer: while preserving the existing application as the execution environment, it establishes reusable execution channels for external enhancement code. This objective complements the redesign of malleable software environments and does not require the uniform conversion of existing business data into the data model of any specific generative system. 

2.2.2 Browser-Based Automation and Web Augmentation 

Research on web automation and user scripts has demonstrated that clients can continue to modify the content and behavior of web pages after they have been rendered. Chickenfoot embeds a programming environment within Firefox and, by utilizing operations such as keyword matching targeting visible page components, supports web automation, customization, and cross-site integration [1]. Therefore, adding functionality to existing pages via scripts is not limited to visual adjustments, nor does it require access to the website’s server-side source code. In recent years, DOMSteer has further integrated user requests, real-time interface context, and LLM processing to perform DOM insertion, modification, and reorganization via a Chrome extension, providing supplementary information and interactive support to the original webpage [8]. Its implementation reuses the page access and execution infrastructure provided by browser extensions. The prerequisite for this approach is that the corresponding browser can load and run an extension or scripting environment; page matching, script loading, and permission management are also organized by this environment [4]. Although Web UI desktop clients also have a Web execution environment, their processes, windows, and code entry points are managed by their respective hosts; therefore, one cannot assume that they share the same extension loading mechanism merely because they share a DOM. Injectra therefore separates the integration of heterogeneous desktop hosts from upper-layer enhancements and investigates how to provide an execution foundation for browser page enhancement approaches tailored to existing desktop clients. This difference at the system level shifts the focus of this paper to the reuse of integration mechanisms across desktop hosts, whereas DOMSteer focuses on the auxiliary generation and delivery based on real-time web page contexts. 

2.2.3 Runtime Modification of Existing Desktop Applications 

There are also direct research precedents for runtime modification of existing desktop software. Scotty, through runtime toolkit overrides, enables developers to modify the interactions and behavior of existing Cocoa applications without accessing the original application’s source code [6]. The team’s report de-scribes hooks for altering control rendering, event funnels for modifying event handling, glass sheets for overlaying interactions, as well as abstractions such as dynamic code loading and object delegation [9]. 6It should be noted that this capability is not universally available in arbitrary desktop software but is closely tied to the runtime characteristics of Cocoa. The dynamic code loading, object delegation, and event interception relied upon by Scotty are built upon the dynamic object model and message dispatch mechanisms of the Cocoa and Objective-C runtimes; the host framework itself provides the ability to query and replace classes, methods, and event-handling behaviors at runtime. For native applications lacking such dynamic mechanisms, similar runtime modifications typically require binary instrumentation or reverse engineering techniques (such as dynamic instrumentation tools like Frida), which significantly increase compatibility, stability, and maintenance costs, thereby limiting the development and widespread adoption of unified abstraction frameworks. Therefore, what Scotty demonstrates is that, provided the host offers sufficient dynamic runtime support, interaction and functional extensions can be achieved without source code; this does not imply that runtime integration is equally feasible for any desktop software. This environmental boundary constitutes a key condition for comparison in this paper: modification abstractions built upon the object models, event dispatching, and runtime mechanisms of specific native toolkits are difficult to directly migrate to hosts that lack these mechanisms. Injectra targets Web UI desk-top applications. By leveraging the standardized execution foundation of shared page scripts, documents, and styles, it uses integration and adaptation to handle host differences, enabling upper-layer enhance-ments to reuse common Web execution capabilities. Building on this foundation, it combines runtime integration with pre-launch guidance to organize reusable enhancement capabilities. This paper further investigates precisely this cross-host Web execution layer and its reuse mechanisms. 

2.2.4 Natural Language and Direct Manipulation for Modification 

Another class of research focuses on the expression of modification intent and the transformation from user intent to specific modifications. Stylette converts users’ natural-language styling goals for web page components into suggested CSS properties and values, and supports iterative adjustments through a candi-date panel [10]. DirectGPT introduces interaction principles such as object selection, direct manipulation, reusable prompt operations, and undo into the LLM interface, supporting modifications to text, code, and vector graphics within its editing environment [15]. These systems contribute to the interpretation of styling intent and the organization of human-computer interaction, respectively, rather than focusing on the unified integration of heterogeneous desktop hosts. These interaction mechanisms can provide a means of inputting requirements for enhanced tools, but the specific generation process does not automatically provide a code deployment channel for third-party desktop applications. The selection-and-annotation tool presented in this paper inherits the interactive approach of pointing to objects and expressing intent, serving as a reference application built on top of a generic injection layer. Accordingly, Injectra’s contribution lies in the foundation of integration and execution that can be shared by various higher-level tools, while the selection-and-annotation example demonstrates how this layered approach connects the expression of requirements with in-application aug-mentation. 

2.2.5 External Interface Patches and Pixel-Based Access 

Unlike entering an application’s internal execution environment, the external overlay approach alters how users interact with existing software by superimposing a new interaction layer on top of the target appli-cation. Research on this approach predates the emergence of generative tools. User Interface Façades enables the adjustment, reorganization, and recombination of existing graphical interfaces through direct manipulation [17]. Prefab, on the other hand, identifies interface components based on pixels, providing a foundation for implementing new interactive behaviors in existing interfaces [5]. These approaches, which start from interface fragments and visible pixels, respectively, demonstrate that modifying existing software is not limited to accessing internal application document objects. Interface Quilt uses a computer-operated agent to explore the interface, after which a generative tool constructs interface patches that overlay the original application; a runtime control layer is responsible for transmitting interface states and input operations between the patches and the target application [16]. This approach does not rely 7on the target application’s source code, DOM, or pre-provided business APIs, enabling modifications to applications that employ different interface technologies. At the same time, this external overlay approach introduces a series of additional costs. First, interface exploration and patch generation rely on multiple rounds of perception, reasoning, and manipulation by the agent, resulting in relatively high computational and interactive overhead. Second, the patch itself constitutes an independent overlay interface; its design requires reorganizing controls and interaction flows and is predicated on an understanding of the target application’s interface structure and task logic— this places an additional interface design burden on users or generative tools. Third, user operations do not act directly on the original application; instead, they are first received by the patch layer, then simulated and forwarded to the target application, while the original application’s state must be fed back to the patch layer to maintain synchronization. While this intermediate layer provides integration capabilities, it also increases the complexity of input consistency, interaction latency, and state synchronization; the original paper also lists patch construction, interaction verification, and state synchronization as major limitations [16]. Injectra utilizes the application’s internal Web execution environment as the enhancement vehicle, allowing direct access to the page’s DOM interface and JavaScript execution capabilities. The enhanced interface is embedded within the original page; users continue to interact within the original application, and input events are handled by the page’s own event mechanism. This eliminates the need for simulation and forwarding via an external patch layer, as well as the need to maintain state synchronization between two sets of interfaces. The trade-off of this design is the necessity of establishing a usable internal access channel, and its applicability is constrained by the target application’s Web execution environment. Con-sequently, the two approaches use visible interfaces and internal execution environments, respectively, as their primary access points, and carry out new interactions and functions externally and internally within the application: the former requires rebuilding the interface and forwarding input to support different in-terface technologies, while the latter relies on internal access to directly extend the interface and behavior within the original application. 

2.2.6 Positioning of This Work 

The aforementioned studies have established software extension capabilities at various levels, includ-ing malleable environments, web scripts, native toolkits, interaction modification, and external interface patching. Cross-application reuse, decoupling of code from the host, and AI-assisted modification con-stitute the common research threads among these works. Following this thread, this paper focuses its research question specifically on —specifically, the integration of generic code and enhanced execution 

within existing Web UI desktop clients: by adapting to the host to handle different entry points, we con-nect runtime integration with pre-launch guidance to a shared page execution capability, which is then reused by various higher-level enhancements. The key to this approach lies in extracting the host in-tegration work—previously scattered across specific enhancements—into an independent infrastructure, enabling page-level extensions to enter different clients through the same execution layer. Subsequent architectural explanations and real-world application validation will focus on the reuse of integration mechanisms, shared execution capabilities, and the boundaries of page semantic adaptation. # 3 Scope and Design Goals 

The central research question of this paper is: How can reusable code integration and enhanced execution capabilities be provided for existing Web UI desktop applications? This question involves both the exe-cution entry points in different hosts and how upper-layer enhancements can reuse these capabilities once integration is established. This chapter first defines the research subjects, scope of capabilities, and sys-tem responsibilities, and then proposes design objectives to guide architectural division and technology selection. 

## 3.1 Research Scope 

3.1.1 Target Applications and Execution Layer 

The research subjects are existing desktop clients that have been deployed and whose user interfaces are built using an embedded browser engine or the system’s WebView. Enhancements are applied to the Web pages within the application and their execution environments, extending their presentation and behavior through JavaScript, HTML, and CSS. For hybrid applications that contain both native controls and Web-Views, this paper discusses only the Web interface portion; native windows or controls are not considered targets for enhancement simply because they belong to the same process as the WebView. Server-side 9implementation modifications, general native interface refactoring, and arbitrary process memory modi-fications are outside the scope of this paper. Access channels can be established through various mechanisms, such as debugging protocols or host bridging, and may involve calls to the host’s native layer when necessary. The underlying mechanisms used to establish the channel and the level at which the enhancement code ultimately operates must be described separately. This paper organizes enhancement capabilities around a shared Web execution en-vironment and does not require all hosts to adopt the same underlying access mechanism. In terms of platforms, the implementation and verification in this paper focus on macOS (Apple Silicon) and Win-dows; support for Linux is reserved for future work. Specific host versions and runtime conditions are detailed in the Implementation and Evaluation sections. 

3.1.2 Enhancement Capabilities and Access Paths 

The scope of functionality covers three levels: interface presentation, interactive behavior, and client-side logic. Presentation enhancements include adjustments to styling, layout, and information organization; interaction enhancements include adding operation entry points, modifying local interaction methods, and integrating new event-handling logic; client-side logic enhancements can involve adding annotation, filtering, or auxiliary processing functions to the content accessible on the page. These capabilities enter the original application via external enhancement payloads, which can be written by developers or gen-erated by LLM-driven upper-layer tools. The DOM, page state, and interfaces accessible to the payload still depend on the execution environment actually provided by the target page and the host application. This paper also incorporates two approaches: runtime integration and pre-launch initialization. Run-time integration targets an already running application, establishing a page execution channel through available entry points; pre-launch initialization first prepares an initialization entry point in a derived copy of the application, then loads and updates the external enhancements. Once the initialization entry point is prepared, page enhancements can be iterated independently of the application package, without requiring the application to be repackaged after each modification to the payload. The common goal of both approaches is to provide page execution capabilities to upper layers; the entry conditions and preparation processes are handled by the corresponding host application adapters. 

3.1.3 System and Enhancement Responsibilities 

Injectra is responsible for establishing page execution channels for the target application, accounting for differences in process discovery and application launch methods across operating system platforms such as macOS and Windows, as well as variations in debugging interfaces, WebView organization, and launch entry points among different host applications. Once the channel is established, Injectra takes full responsibility for identifying and selecting the target page, injecting and managing the execution of the enhancement payload, and providing feedback on execution results; the payload code itself continues to run within the target page’s Web execution environment. The enhancement author or upper-layer tool is responsible for the specific functional content, includ-ing selecting which UI elements to target, interpreting page semantics, meeting user needs, and handling the business logic of the enhancement itself. Therefore, generality is reflected in the fact that the integra-tion mechanism and execution capabilities can be reused across multiple applications and enhancements, without requiring that the same segment of code—which depends on specific page semantics—remain unchanged across all applications. Annotation-driven LLM tools sit above this execution layer, responsible for capturing modification intent, organizing context, and generating enhancement code. Their role is to demonstrate the types of upper-level workflows that general injection capabilities can support; Model selection, prompt design, and agent orchestration are not part of the core responsibilities of injection. Similarly, the completion of page execution and the generation of code that satisfies the user’s intent are two distinct criteria: the former is supported by execution feedback and page effect verification, while the latter requires evaluation specific to the enhancement task. 10 3.1.4 Operational Boundaries and Non-Goals 

Injectra executes enhancement code only within target applications explicitly specified and actively ini-tiated by the user; the scope of this research does not include providing a secure sandbox for arbitrarily generated code. Scripts within a page possess the permissions allowed by their respective execution environments; selecting a specific area does not imply that the scope of the injected script’s impact will automatically be restricted to that area. Operations such as the removal of managed nodes and the cleanup of registered payloads only handle resources registered by Injectra; this does not imply that persistent data written by the script or its impact on the external environment will also be revoked. This document focuses on targeted integration, execution, and enhancement updates. Automatic re-injection following page navigation, automatic cross-window enhancement recovery, or automatic adap-tation of enhancements after application updates are not considered part of the current capability require-ments. Page object targeting is implemented by specific enhancement payloads, while long-term adapta-tion following changes to the application or page is the responsibility of the enhancement payload author or higher-level tools. A complete workspace, built-in editor, plugin marketplace, and generic agent plat-form are also not included as component objectives of this system; existing editors, external tools, and model services may participate in the enhancement process by calling APIs. This boundary allows the research to focus on generic integration and execution reuse in real-world applications, while reserving research on long-term maintenance, code generation, and user interaction as composable higher-level problems. 

## 3.2 Design Goals 

Within the scope described above, the system design adheres to the following five objectives. These objectives provide a common basis for subsequent module division, integration paths, and interaction workflows, and are validated through corresponding system behaviors. 

3.2.1 G1: Cross-Host Generality 

The system should leverage the common execution foundation of Web UI applications and converge differ-ences among operating system platforms, host applications, and integration mechanisms into adaptation implementations with clearly defined boundaries. This objective is adopted because if every new appli-cation required the complete reimplementation of the injection process, it would be difficult to establish a reusable infrastructure for integration. Therefore, new applications with identical technical conditions should prioritize reusing existing integration implementations; only when there are genuinely different host mechanisms or version requirements should corresponding adaptation be performed. Generic appli-cability is supported by clear, common interfaces and their reuse across multiple real-world hosts, rather than by writing application-specific branches within the core process. 

3.2.2 G2: Separation of Access and Enhancement Logic 

Host integration and upper-layer enhancements should have distinct responsibilities, so that enhancement authors do not need to reimplement low-level connections and execution entry points for each feature. Ac-cordingly, the adaptation layer is responsible for handling differences between operating system platforms and specific host applications, and for establishing an execution channel to the target page; the shared execution layer is responsible for injecting enhancement payloads through this channel and managing their execution; while the page element targeting and business logic required for specific enhancements remain within the enhancement payload. This requires different integration routes to reuse a common enhancement execution mechanism, thereby avoiding the need to repeatedly implement the same payload processing logic for different operating system platforms and preventing the intermingling of specific application interface rules into the general integration process. This separation provides a common exe-cution foundation for manual scripts, reusable enhancement packages, and model-generated code. 11 3.2.3 G3: In-Application Iteration with Explicit Resource Ownership 

Enhancements should be rendered and validated within the user’s original application, ensuring that mod-ification feedback corresponds to the actual page and usage context. The system must therefore support the deployment, updating, and cleanup of managed resources associated with enhancement payloads, and ensure that these managed resources have identifiable ownership so that subsequent operations can locate their targets. For pre-launch onboarding routes, one-time setup should be separated from subsequent pay-load iterations, allowing users to modify external enhancements via existing editors and view the results in the live application. This objective emphasizes the iteration and resource management of enhancements within the original working environment; the resource attribution mechanism is used solely to identify and clean up enhancement resources registered with Injectra and does not imply that script behavior is isolated or that all of its effects can be rolled back. 

3.2.4 G4: Composable Access for External Tools 

General-purpose injection capabilities should be usable by multiple callers without being tied to specific editors, models, agent frameworks, or integration protocols. Therefore, the system must provide a sta-ble entry point for programmatic calls, organizing target selection, payload submission, and execution feedback into operations that external tools can compose. The CLI and reusable library layers serve this purpose; access layers such as natural language interaction, box-selection annotations, and MCP can or-ganize their respective workflows on top of them. The responsibility of the external interface is to expose callable injection and enhancement capabilities, while the specific methods by which callers generate code and schedule tasks remain independent. 

3.2.5 G5: Explicit Targets and Execution Outcomes 

Augmentation operations should target specific application instances and pages, avoiding the assumption that the correct execution environment has been obtained based solely on the application name or the exis-tence of a process. Access capabilities, page identity, and session state must be verifiable conditions prior to execution; when targets change or capabilities are insufficient, recognizable results should be provided to the caller. Execution feedback must also distinguish between three scenarios: not executed, executed, and undetermined results. Notably, “executed” does not equate to “successful execution”; it may still be accompanied by script exceptions or produce only partial effects. For operations with uncertain outcomes, automatic retries should not be used to mask this uncertainty, as repeated execution may introduce new side effects. This objective provides upper-layer tools with interpretable execution boundaries, enabling them to determine subsequent interactions and verifications based on actual feedback. The above objectives constrain different levels of subsequent design: G1 and G2 guide the division of the host adaptation and shared execution layers; G3 guides enhancement updates and resource manage-ment; G4 guides external invocation methods; and G5 guides target binding and result feedback. Corre-sponding verification requires observing whether integration implementations are reused, whether differ-ent enhancements can use a common channel, whether updates produce effects on the correct pages, and whether exceptions and target changes are clearly expressed. These observable conditions will link the subsequent architectural descriptions with the evaluation content; specific mechanisms and verification results are elaborated in the corresponding sections. # 4 Injectra Architecture 

Section 3 proposes design goals for cross-host access, enhanced execution, and the separation and reuse of upper-layer functions. Based on these goals, Injectra encapsulates host-related entry mechanisms as access adapters, organizes the invocation methods of target pages into a common contract, and executes external enhancement payloads through a shared runtime. This section explains this architecture in terms of component responsibilities, target representation, access paths, payload lifecycle, and tool composition; specific platform mechanisms and implementation requirements will be discussed in the next section. 

## 4.1 Architecture Overview 

Figure 2 illustrates the system’s logical organization. The components in the figure represent their re-spective responsibilities, and the lines indicate the primary interaction relationships between components rather than dependencies between source code modules; solid lines denote runtime calls and result feed-back, while dashed lines denote pre-launch initialization or optional external integration. The overall structure distinguishes between the control end and the target application: the control end accepts calls, assembles payloads, and organizes integration, while the web pages within the target application host the shared runtime and specific enhancement code. The control end submits programs and receives return values or errors, whereas the page end generates actual effects through its own DOM, styles, and event mechanisms. Therefore, the fact that the control end can initiate execution does not imply that the payload logic runs on the control end. The external invocation entry point consists of the CLI and a reusable library layer. The CLI handles parameter parsing, specific backend assembly, and result output; the library layer provides use cases such as target discovery, application enhancement, enhancement removal, and page execution, enabling external programs to invoke these same capabilities within their own workflows. These use cases rely on an abstract Web execution contract rather than directly depending on any specific debugging protocol 13 or host bridging implementation. Specific adaptation can be handled by the CLI or provided by external programs. Regardless of the approach, use cases follow the same processing flow: first, verify target ownership and page execution capabilities; then, submit the program to be executed to the selected page— without needing to alter their own implementation based on changes in the underlying access mechanism. The integration adapter is responsible for mapping the execution entry points actually provided by the host to this contract. Platform differences, host mechanisms, and page functionality are thus handled at different levels: the platform and host adapters handle the application environment and execution entry points; the shared layer handles payload execution; and the enhanced code handles page semantics and specific business logic. Injectra’s core layer uniformly defines only three types of information: the iden-tification method for target pages, the description method for session capabilities, and the meanings of different error types. Whether the target page provides a DOM, how scripts are executed within the page, and what transmission protocol is used between the control end and the page are not within the scope of the core layer’s specifications; instead, they are handled separately by the Web Execution Contract and the specific integration adapter. This division clarifies the boundary between the core layer and Web exe-cution capabilities, preventing any host-specific internal mechanism from being treated as a prerequisite that all integration implementations must satisfy. 14 4.2 Targets, Sessions, and Capabilities 

Cross-host enhancement first requires ensuring that code is delivered to the page actually specified by the caller, rather than simply sent to an application or process with the same name. The existence of an application name or process can only be used to discover candidate targets; it cannot uniquely identify a page within a window or its execution environment. Injectra therefore uniformly represents connectable pages as Web targets, separating page identity from the implementation details of specific hosts, enabling upper-layer use cases to specify operation targets in a consistent manner. Each Web target contains a target reference to the associated backend, as well as metadata such as the title, URL, and page context. A target reference consists of the backend instance’s identity and the target key interpreted by that instance; even if two backends return the same local target key, they cannot be regarded as the same target. This reference is valid only within the current controlling process and the backend instance; it is not a universal object handle that can be persistently stored across processes. This design preserves the host information needed to locate a page while preventing the misuse of local identifiers across different backends. Building upon the unified target representation, the Web Execution Contract further separates target discovery, session establishment, and page evaluation. Backends list targets, adapters verify the cor-responding entry conditions, and sessions are established for selected targets; sessions preserve bound targets, declare the operations they support, and provide an interface for page evaluation. Use cases ver-ify the backend ownership of a target before establishing a connection, re-verify the target bound to the session after connection, and check whether the session possesses the page execution capabilities required for the current operation. Consequently, target selection, host access, and capability checks form a ver-ifiable execution path, preventing target keys from other connections from being passed to the current backend or code from being submitted when the session lacks the necessary capabilities. The common contract also unifies the semantics of page evaluation: code must be evaluated in an execution environment capable of accessing the target page’s DOM, wait for the returned Promise, pass the result back to the control end as a JSON value, and treat script exceptions as execution errors. The fact that a host can run JavaScript is not sufficient proof that it satisfies this contract; for example, code running in an isolated script engine may not be able to access the target page’s DOM. For Injectra, these constraints are key to enhancing cross-host reusability: higher-level tools deal with consistent page exe-cution semantics, rather than having to handle execution locations, asynchronous results, and exception representations separately for each host. The current common goal is based on the main page context and does not automatically treat arbitrary frames, workers, or other isolated environments as execution objects with the same semantics. A capability declaration describes the operational capabilities that an adapter confirms when estab-lishing a session, allowing use cases to verify them before execution. It does not guarantee that the target page will always be available after the session is established; page destruction or connection failure may still cause subsequent execution to fail, which must be expressed through execution feedback. Capabil-ity declarations also do not restrict a script’s actual permissions within the page and therefore do not constitute a security sandbox. Through the three layers of target, session, and capability declaration, Injectra translates “which page to operate on, through which connection to execute, and what can currently be executed” into explicit checks within a generic workflow. This allows different higher-level tools to reuse the same set of target binding and pre-execution verification mechanisms without needing to understand the page identifiers and connection details of each host, thereby laying the foundation for cross-host reuse in G1, the separation of integration and enhancement in G2, and the clear definition of targets and execution results in G5. 

## 4.3 Access Paths and Host Adaptation 

Injectra separates the establishment of the entry point from the subsequent execution of enhancements, supporting two paths: runtime integration and pre-launch initialization. The two paths have different prerequisites, but once page execution capability is obtained, both utilize Web contracts to support the 15 same enhancement use cases and share the same runtime. While the two paths share the semantics of target operations and enhancement execution, this does not imply that all hosts employ the same underlying technology. Runtime integration targets applications that are already running and have an available entry point. Adapters are responsible for discovering specific pages, establishing connections, and routing evaluation requests to the corresponding execution environment. Existing implementations include CDP-based page integration and host bridging for Electron and WKWebView. These approaches vary in their reliance on debugging endpoints, host interfaces, or native runtime conditions; some bridges require passing through the host’s native layer to obtain execution capabilities for Web pages. The enhancements ultimately act upon the Web page, which is distinct from the underlying methods used to establish the channel. Pre-launch bootstrapping is intended for hosts that require entry points to be prepared in advance. The preparer identifies the entry point layout, injects a small amount of bootstrap code into a derived copy of the application, and retains the preparation information needed for subsequent connections. After the application launches, the bootstrap code establishes an authenticated communication channel with the local control endpoint and, upon discovering a page, implements a shared Web contract through the bootstrap backend. One-time entry point preparation is thus separated from subsequent payload iterations: after modifying external enhancement files, new content can be submitted to the established page channel without having to rebuild the application package every time an enhancement is modified. This process reuses the preparation mechanism based on the local Web entry point, rather than application-specific custom logic; as long as the entry point resources can be located and modified, and the derived copy can launch normally, subsequent enhancements can reuse the same execution process. When the entry point is protected by integrity checks, or when the interface is loaded entirely from a remote source, separate adaptation or alternative access paths are required. Adaptation is categorized based on reusable protocols, host mechanisms, and resource formats, rather than application names. Applications with identical technical conditions should prioritize reusing exist-ing implementations; corresponding strategies are introduced only when differences in the entry point or host require independent maintenance. Specific adaptation is assembled by the system at the call bound-ary; use case and payload processing logic are not reimplemented across application brands. Therefore, cross-application extensions primarily involve adding target configurations, applicable conditions, and compatibility evidence; when new code is absolutely necessary, its dependencies are also restricted to the corresponding adaptation. Figure 3 outlines two access paths step by step: runtime access uses existing entry points, while pre-launch guidance first prepares and launches a derived instance; after completing page discovery and session binding, both paths enter a common payload application and result feedback process. This tem-poral perspective complements the component division of labor shown in Figure 2; there is no automatic fallback relationship between the two paths. 

## 4.4 Enhancement Bundles and Shared Execution 

Enhanced payloads are organized into Bundles, whose versioned manifests declare enhancement iden-tifiers and optional JavaScript, HTML, and CSS resources; resource paths are resolved relative to the manifest directory. After the control end reads and validates these resources, it assembles them into a program ready for execution. Bundles describe only the deployment content; page selectors and busi-ness logic are implemented by the payload, while the host access method is determined by lower-layer adaptation. All backends reuse the same Web runtime to assemble the program, avoiding the need to implement DOM creation and update logic separately. The runtime adds CSS to the page, inserts HTML into the created root container, and executes the payload script, while providing the script with a reference to the root container and a registration entry point for cleanup callbacks. If no HTML is provided, the root container may be empty, and the payload may directly manipulate the original page. The shared runtime stores created nodes and cleanup callbacks in the page based on enhancement identifiers. ## 4.5 Iteration and Execution Feedback 

During the dev process that boots the route before launch, the control end listens for changes to the Bundle manifest file and its declared resource files, and organizes the read content into versions and computes a digest identifier. If a file changes again during the reading process, that candidate version is discarded; stable versions are executed sequentially, and identical digests are not submitted repeatedly due to duplicate listening events. The target page is bound to the session; when the page is destroyed, rebuilt, or the connection fails, the current update cycle stops and does not automatically transfer to another page. Execution feedback not only distinguishes between error types but also indicates at which stage the failure occurred and whether the code has already been executed. Specifically, NotExecuted indicates that the operation was rejected before submission, or there is clear evidence that it was not executed; 

Executed indicates that execution was confirmed to have been initiated on the target, but success of all statements is not guaranteed; Unknown indicates that the request may have been executed, but the result cannot be confirmed at this time. Script exceptions and return code failures are classified as post-execution errors; timeouts or disconnections cannot be used to determine that execution did not occur. A normal acknowledgment indicates that the program has completed evaluation; it does not imply that the 17 enhanced functionality meets user requirements, and the caller must still perform subsequent acceptance testing based on the execution results. To prevent repeated execution when the result is unknown, the dev process records the request iden-tifier, content version, and target before submission, and saves the acknowledgment upon receiving a definitive result. When the result is Unknown , the system retains the pending confirmation status and stops automatic updates; after an abnormal termination of the control process, these unconfirmed records also prevent the system from automatically resubmitting the same request upon restart. The caller must verify the target status and explicitly confirm it before initiating a new execution. A single runtime call returns a result or an error directly, and the caller decides on subsequent handling. 

## 4.6 Composition with External Tools 

Injectra separates the generation of enhanced code from its execution within the page, enabling different external tools to reuse the same set of integration and execution capabilities. Developers can use existing editors to write Bundles; external programs can use the CLI or library layer to select targets, generate code, and update the enhancement, without needing to reimplement the host connection. Page semantics and specific business logic are still handled by the enhancement payload. Integration layers such as MCP can also be layered on top of the CLI or library layer to provide the same capabilities to other tools without modifying the page runtime. Annotation-driven LLM tools that operate on selected text are examples of this approach. The require-ment capture component records the selected area and annotations on the original page; the control end then organizes the context based on this information, invokes the model to generate or modify the enhance-ment code, and applies the candidate payload to the same page via Injectra. Since the capture component and the modified enhancements use different identifiers, annotation entry points are not removed when updates are applied, allowing users to continue proposing the next round of modifications. The tool is re-sponsible for model selection, context organization, and ensuring that the generated results align with the user’s intent, while Injectra provides page integration, execution, and result feedback. The entire process can run according to fixed steps without requiring autonomous planning or agent orchestration within the injection core. At this point, host adaptation, shared execution, resource management, a unified invocation entry point, and execution feedback have respectively implemented the aforementioned G1–G5. Subsequent implementation details and system evaluation will revolve around these mechanisms. 

# 5 Implementation 

This section describes the specific implementation of the architecture described in Section 4 within the current system. The implementation follows the component division shown in Figure 2 and the two access paths shown in Figure 3, focusing on how the host entry point is transformed into page execution capabilities, how enhanced payloads are assembled, and how page changes and exceptions are identified. Application coverage, enhancement instances, and evaluation results are reported in the next section. 

## 5.1 Software Organization and Interfaces 

The control plane of Injectra is implemented in Rust and is divided into four layers: common contracts, Web execution, application use cases, and specific backends. Upper-layer use cases depend only on the 

WebBackend and WebSession interfaces and do not directly reference specific protocol implemen-tations; therefore, they can run on different access backends. Target binding and capability checks are unified at the library layer, allowing both the CLI and external programs that directly call the library to reuse the same execution workflow. The CLI provides commands for target discovery, application enhancement, removal of enhancements, and prepare /dev , among others. It selects and initializes the appropriate backend based on command 18 parameters, then passes it to the library-layer use case for execution. Successful results of ordinary one-time operations are output as JSON; continuous development workflows output JSON events line by line; and fatal errors are written to the standard error stream, making it easy for external programs to distinguish between state changes, execution receipts, and command failures. Backends are selected based on call parameters; in the event of failure, the integration path is not automatically switched. Model invocation, interface object selection, and specific functional payloads are maintained by external tools or enhancement authors and are not the responsibility of the CLI integration use case. The shared page runtime is implemented in JavaScript; it executes enhancement code within the target page and manages related resources. Host bridging and pre-launch preparation are implemented via auxiliary Python and JavaScript programs, which are uniformly invoked by the Rust control end. 

## 5.2 Runtime Access Backends 

5.2.1 CDP Page Access 

The CDP backend retrieves a list of debuggable pages from a specified loopback port and treats pages that provide a WebSocket endpoint for page debugging as candidate targets. Before establishing a connection, the backend verifies the endpoint’s address, port, and debug path to ensure it uses the local page endpoint specified by the caller. When establishing a connection, the backend precisely matches the target based on the page identifier, rather than selecting candidate pages based on window titles. The session executes code within the page via Runtime.evaluate , waits for the Promise to complete, and returns the result by value. Script exceptions and execution results that cannot be converted to JSON values are both recorded as post-execution errors; if a disconnection, timeout, or unparseable response occurs after submission, the result is marked as unknown, and the request is not automatically retried. 

5.2.2 Electron Gadget Bridge 

For Electron hosts that meet the loading criteria but do not provide a page entry point via CDP, the system offers optional Gadget bridging. The Rust backend connects to authenticated Frida Gadget sessions via a Python helper, verifying the target device, process instance, and host configuration—rather than relying solely on a PID for access. The target-side helper script uses the host’s libuv scheduling mechanism to route requests into its native V8/Node.js execution environment; after obtaining the Electron main process interface, it then discovers webContents and calls its page execution interface. Therefore, script scheduling in the native bridge and the subsequent execution of the enhancement program within the page are two sequential steps. The page identifier includes the target scope and verifies the current page by combining the 

webContents identity, URL, and main frame information. The Node.js-side acknowledgment carries the request ID and process information; the assistant reads from the log starting point of this request and matches it against the acknowledgment to avoid mistaking historical output for the current result. Native asynchronous handles and callbacks retain their references during use; script resources are released only after a close operation obtains the corresponding acknowledgment. This bridging relies on available host output symbols and a matching ABI; if these conditions are not met, it returns “not supported.” 

5.2.3 WKWebView Bridge 

The WKWebView backend reuses Frida session communication, but page discovery and evaluation uti-lize WebKit’s native interfaces. The macOS host adaptation traverses the window view tree on the main thread, selects the WKWebView within it, and organizes the target based on the view identity and URL; it re-locates and verifies the corresponding view with each execution. Page code runs in the main frame’s page content environment via callAsyncJavaScript , and return values and exceptions are en-capsulated within the page before being passed back via native completion. 19 WKWebView’s execution relies on the main thread and asynchronous callbacks; therefore, a timeout on the control end does not necessarily mean the operation has been canceled. Tasks that have not yet begun are discarded; tasks that have already begun are marked as having an unknown result, and the necessary callback and resource information is retained to prevent false positives indicating that cleanup has been completed. The CDP approach is intended for macOS and Windows hosts with corresponding page endpoints, while the Gadget and WKWebView bridging described in this section currently uses a macOS target configuration. Therefore, the fact that the control end can be built or use CDP on another platform does not imply that all host bridging has been ported. Specific entry points and version requirements for each application are reported separately in the evaluation section; experimental probes or interface declarations are not considered formal backend capabilities. 

## 5.3 Preparing a Derived Application 

The previous section described the implementation of runtime integration; this section explains the im-plementation of pre-launch bootstrapping. prepare The process reads the host’s package layout and main entry point, creates a copy of the derived application with a distinct identity, and installs Bootstrap within that copy, while leaving the original application unchanged. The current implementation covers common Electron CommonJS packaging formats on macOS Apple Silicon, including directories, ASAR files, and nested ASAR entry points within directories. These packaging formats share the same prepara-tion process, eliminating the need to write separate injection logic for each application; for entry points that cannot be recognized or are unsupported, the preparer will stop and report the reason. The preparation process employs two strategies based on the entry point format. For CommonJS text entry points that can be parsed directly, a syntax parser is used to determine the positions of the file header and directive preamble, after which the bootstrap loading statement is inserted. The insertion position preserves the original file header and directives such as strict mode, avoiding the simple placement of the bootstrap statement at the beginning of the file that would alter the original entry point’s semantics. Modifications are limited to the entry point and necessary bootstrap resources within the derived copy; subsequent enhancements are not written to this entry point. For entries nested within archives or handled by a host loader, the preparer employs a main module delegation strategy. The new entry file first loads Bootstrap, then initiates the original entry via Node.js’s main module loading mechanism. This strategy requires no modification to the original entry’s content and is therefore also suitable for entries where direct text insertion is not possible. This differs from the simple require call: the original entry point still runs as the main module, and its relative dependencies are resolved according to their original locations. Upon completion of preparation, the preparer generates a preparation record that stores the derived instance identifier, entry point strategy, control-end address, and the status of key resources at the time of preparation completion for subsequent verification. The authentication materials and runtime logs required for Bootstrap communication are stored in the derived instance directory outside the repository. Subsequently, the macOS helper script updates the integrity records of relevant resources in the copy and signs the copy locally; finally, a pre-check confirms that Bootstrap can be loaded. The pre-check exits immediately after outputting a confirmation marker and does not continue executing the original business entry point; therefore, it is used solely to verify the preparation chain. Subsequent dev processes launch or connect to the corresponding derived instance based on the preparation record, and there is no need to re-execute the preparation process when updating the enhanced payload. 

## 5.4 Bootstrap Support for In-Application Iteration 

Bootstrap launches alongside the derived application and, after completing instance authentication, pro-vides the local control end with a channel for page discovery and enhancement execution. The application entry point only needs to be prepared once; subsequent modifications can be submitted to the selected 20 page through this channel, allowing users to view the results within the original application without having to re-prepare the application package. To apply modifications to the document currently visible to the user, the bootstrap code uses Elec-tron’s webContents to discover the page and binds the target to the current connection session, page, and document generation to distinguish between different document loads within the same page. When the document is ready, the system writes a random marker into the page; this binding becomes invalid immediately after main page navigation, a change in the rendering process, or page destruction. Before executing each enhancement, the page first verifies this marker and then runs the payload, preventing erroneous execution caused by document changes occurring between the time the control end selects a page and the time the enhancement is actually executed. Both requests and acknowledgments carry content version and target information; the control end ac-cepts only results that match the current request. Connection restoration or the resending of an acknowl-edgment does not cause the original payload to be re-executed; when the result cannot be confirmed, the system retains an “unknown” status, and the caller decides the next action after verifying the page’s behavior. Version logging and diagnostic methods are described in Section 5.6. 

## 5.5 Bundle Loading and Page Execution 

A bundle uses a versioned JSON manifest to declare the enhanced identifier, as well as the relative paths to JavaScript, HTML, and CSS resources. After the server reads and validates the manifest and resources, it assembles the payload into a program executable within the page. Input validation is used solely to ensure the format and paths are valid; it does not guarantee that the payload code is secure. The program generator reuses the same Web runtime, serializing the enhanced identifier, HTML, and CSS into data, and assembling JavaScript into asynchronous function bodies. All backends share this runtime, eliminating the need to implement DOM assembly and update logic separately. The page runtime creates style nodes and an optional HTML root container, providing the payload with a reference to the root container and onCleanup a cleanup registration interface; if no HTML is present, the root container remains empty, and the payload can directly manipulate the original page. The runtime registers nodes and cleanup callbacks based on the enhancement identifier. During up-dates, it first cleans up the old instance before executing the new payload and rejects overlapping opera-tions on the same identifier. Cleanup affects only registered resources; even if a cleanup callback fails, the system continues processing the remaining resources and reports the error at the end. This mechanism supports replacing or removing individual enhancements without refreshing the page. 

## 5.6 Revision Management and Execution Feedback 

The dev workflow uses the manifest and resource content digests as version identifiers to map a single file modification to a subsequent page execution. If a file changes or becomes temporarily invalid during reading, the system reports a source error and does not submit the payload; once a stable candidate is obtained, it is applied to the selected page in sequence. Within the same dev run, versions that have already been attempted will not be executed again due to repeated file events. This mechanism prevents mixed content from being submitted to the page during the saving process, but does not guarantee that updates to multiple files will be completed simultaneously. Each submission records the request number, content version, and target, and saves the pending status before execution. Upon receiving a definitive result, the control end saves the corresponding acknowledg-ment; if the result is unknown, it retains the record and halts automatic updates. Even if the control end restarts, the user must verify the page status and explicitly confirm it before a new request can be initi-ated; the system will not automatically re-execute the original program. Thus, the caller can distinguish between a file that has been modified, a program that has been executed, and an execution result that is unknown. Execution feedback is also used to guide subsequent modifications. In the Bootstrap path, the control end converts matching error stacks—based on the request, version, and the user script’s position within 21 the generated program—into row and column numbers in the enhanced source file and associates them with the corresponding console logs; if no match is found, the original error is retained. Source errors, execution failures, and unknown results are reported separately, allowing the caller to correct the payload, verify the page, or end the current iteration. Stopping ‘dev‘ only terminates file monitoring and the communication connection; it does not close the application, undo the current page effects, or save this enhancement as a feature that automatically loads when the application starts. 

# 6 Reference Enhancements and Evaluation 

This section examines, through real-world host verification and reference-enhanced examples, whether Injectra can establish page execution channels in different applications, reuse enhanced execution mecha-nisms, and support in-application modification workflows. The evaluation combines system verification with example demonstrations, focusing on the capabilities actually provided by the system and their appli-cable conditions—a approach consistent with toolkit research, which selects evaluation evidence based on research questions [13]. 

## 6.1 Evaluation Questions and Evidence Scope 

The evaluation centers on three questions: Can the same set of page execution capabilities be reused across different hosts and access paths? Can these capabilities support presentation adjustments, interaction modifications, and enhanced instances generated by large language models? Do updates, cleanup, and execution failures have verifiable boundaries? These three questions correspond to access reuse, the scope of enhanced expression, and iterative control, respectively, and are not intended to estimate Injectra’s overall compatibility with all desktop software. The evaluation data is derived from validation records retained during system development and de-ployment, primarily on macOS Apple Silicon, with supplementary validation conducted concurrently on Windows. Software versions, entry conditions, and validation objectives varied across different batches; some attempts also included method refinements and follow-up re-validation. Therefore, this section re-ports results based on original batches and specific combinations and should not be regarded as a random-ized sampling experiment with a predetermined protocol. The basic unit of observation is the combination of application version, platform, access path, and selected page; repeated requests, other versions of the same application, and independent test hosts are not counted as new third-party applications. Page execution verification uses custom payloads to check DOM mounting, style calculations, JavaScript interactions, updates under the same identifier, and resource cleanup. In the official CLI route, auxiliary tools are responsible for asserting page behavior, while payloads are still submitted by Injectra. Enhanced references are separately examined for the scope of their layout, control, or text modifications. The former verifies the execution channel, while the latter verifies the localized effects of specific enhancements; these two types of evidence are not interchangeable.

## 6.5 Summary of Findings 

The above validations lead to three main conclusions. First, Injectra’s unified page execution contract and shared runtime can be reused across operating systems, host frameworks, and integration paths, validating the feasibility of a generic integration architecture. Second, the same execution foundation can deploy 26 both theme and layout enhancements written by developers and support local modifications generated by LLMs, indicating that upper-layer enhancements do not need to reimplement host integration, and that page semantic adaptation can remain separate from the generic execution mechanism. Finally, identifier-based updates, managed resource cleanup, and execution feedback constitute a verifiable in-application iterative process, enabling enhancements not only to be injected but also to be continuously modified and verified within the original application. These results demonstrate that Injectra integrates cross-application integration, enhancement execu-tion, and iterative feedback into reusable infrastructure, providing a unified implementation pathway for LLM-generated code to enter real-world desktop software. 

# 7 Discussion 

## 7.1 Retrofitting Malleability into Existing Software 

The enhanced example demonstrates that Injectra can perform software modifications directly within ap-plications that users already rely on, without the need to rebuild replacement applications or migrate exist-ing data, usage habits, or workflows. Theme adjustments, layout reorganization, and localized functional modifications act on interface presentation, interaction organization, and client-side logic, respectively, while continuing to reuse the original application’s document processing, input responses, and business components. Injectra thus provides a unified foundation for code integration and execution while preserv-ing the flexibility of enhancements in terms of functional form and page adaptation. This approach incrementally introduces software plasticity into existing Web UI clients: enhance-ments can be loaded, replaced, and cleared based on identifiers, allowing users to continuously view the results within the original application and initiate the next round of modifications. Compared to redesign-ing the software environment to be malleable, this approach does not require the application to migrate to a new data model or runtime environment; compared to external interface overrides, it directly utilizes the page’s internal DOM, styles, and event mechanisms, eliminating the need to maintain an overlay inter-face or input forwarding layer. Consequently, Injectra provides a transformation path for existing software that preserves the original runtime environment, supports multiple forms of enhancement, and enables sustainable iteration. 

## 7.2 Access Infrastructure and Enhancement Reuse 

The value of separating integration from enhancement lies in centralizing recurring host differences within a shared infrastructure. A single page integration can execute both handwritten payloads and support reading plugins or LLM modification tools, eliminating the need for the caller to implement protocol connections and page execution separately. Existing plugin libraries and independent control endpoints exemplify this approach to reuse: the latter uses existing library interfaces to handle requirement collec-tion, code generation, and page updates, without needing to replicate the injection runtime. This reuse does not imply that application semantics will automatically align. The same styles or scripts may correspond to different object selectors across different applications, and the content within a ‘Canvas‘ cannot be used to derive internal object semantics solely through the DOM interface. Therefore, it is necessary to evaluate separately whether the integration mechanism is reused, whether the enhance-ment payload requires adaptation, and whether the final functionality is correct. Current records support the feasibility of shared integration and execution, but have not yet quantified the integration costs, learn-ing curve, or long-term maintenance workload for independent developers. 

## 7.3 Roles of Users and Language Models 

The selection and annotation tool demonstrates a clear division of labor between the LLM and Injectra: the model is responsible for converting user requirements into candidate enhancement code, while Injectra is responsible for applying the code to the original application page and providing execution feedback; 27 the injection core does not need to handle requirement understanding or autonomous planning. Users specify the objects to be modified and their intent through selection and annotation, and the actual page results serve as the basis for subsequent verification and modification. Models, prompts, and interaction tools can be replaced independently, and both handwritten and generated payloads can share the same set of update, cleanup, and feedback mechanisms. Clear information regarding requests, objectives, and results keeps this process controllable and ver-ifiable. Successful execution indicates that the code has run on the target page, but whether it meets the requirements must still be determined by evaluating the page’s actual behavior; the selected area is used to express the intent of the modification and does not constitute a security boundary that restricts script be-havior. By distinguishing between code generation, payload submission, and execution verification—and by preserving context information in the event of exceptions or unknown outcomes—Injectra provides a reliable foundation for human-in-the-loop iterative development within applications. As model capabili-ties and interaction methods evolve, this division of labor also offers a viable path for non-programmers to continuously refine everyday software using natural language. 

## 7.4 Deployment Trade-offs and Future Interfaces 

Runtime integration reduces the preparation steps for entry points but relies on the target already pro-viding or allowing the establishment of corresponding channels; pre-launch guidance through derived copies supports subsequent iterations while introducing conditions such as package layout, signatures, and application launch. A unified interface cannot eliminate these differences. Preparing copies may also be affected by account data paths, shared containers, and software update methods; even if a specific page passes verification, this does not mean that a derived copy can unconditionally replace the original application as a daily usage environment. These experiences suggest that if future hosts can provide clear extension entry points, page identity, and lifecycle covenants, they can reduce the uncertainty external tools face when adapting to existing software. The current implementation provides a set of reference abstractions and implementation meth-ods, rather than an established cross-vendor standard. If interoperability is to be further standardized, independent clients or implementations must validate the common contract; if long-term personalized functionality is to be sustained, evidence of cross-application updates and long-term usability is required. Therefore, this study regards unified execution capabilities as a composable foundation layer, reserving generation methods, specific interactions, and long-term maintenance as separate research topics. 

# 8 Limitations and Conclusion 

## 8.1 Limitations 

The current evaluation is primarily based on test samples obtained during the development and deploy-ment process. The page results obtained so far do not yet cover all windows, business functions, or sub-sequent versions of the same application. Nevertheless, validation results across various hosts, platforms, and integration paths indicate that Injectra’s integration and execution mechanisms offer capabilities that can be reused across applications; however, additional adaptation may still be required for applications with protected entry points, unique page structures, or special runtime environments. Whether the system can be integrated and what content it can modify depends on the entry points and page environment provided by the host. Current enhancements are primarily implemented through DOM, CSS, and JavaScript; therefore, they do not directly affect native controls, other frames, hidden views, or objects within Canvas. Linux and other hardware and host configurations have not yet been verified, and their usability cannot be inferred from the existing results. For hosts where an entry point cannot be established, resources are protected, or the required APIs are missing, corresponding integration mechanisms or adaptation implementations must be supplemented. The payload runs as trusted code within the target page environment; the current system does not provide a security sandbox for arbitrary JavaScript. Cleaning nodes and registering callbacks can only 28 handle registered resources and cannot undo persistence, network, or other external side effects; derived copies and isolated directories also cannot guarantee that account or system side effects have been com-pletely isolated. The box-selection annotation tool, used as a verification reference example, relies on a user-configured external model service to process the UI context and generate code. The model may misinterpret user requirements, and the context may contain sensitive UI information; Injectra’s execu-tion receipt can only confirm whether the code was executed, but cannot guarantee the correctness of the generated results nor eliminate the risk of information exposure. The current workflow primarily supports loading for specific targets and iterations during the develop-ment phase. After the control end is stopped, the current page state can be retained; however, after a page refresh, window reconstruction, or application restart, the target must be reconfirmed, and the enhance-ment must be loaded according to the corresponding process. The system does not yet provide one-click consolidation and distribution of final enhancements, automatic uninstallation of Bootstrap, or automatic repair after application upgrades, nor does it guarantee indefinite operation or automatic recovery under any failure. Existing evaluations have verified the actual effectiveness of the enhancement features by examining page states, user interactions, and control preservation in real-world applications, providing direct evi-dence of the system’s feasibility. These technical validations primarily address whether the features can be implemented and do not equate to improvements in user experience or work efficiency. Model ser-vices and page structures change over time; subsequent reproduction requires verification of the actual code, materials, services, and host versions. In the future, user studies and paired tasks can be further conducted on this basis to evaluate Injectra’s impact on development costs, user burden, and long-term usage benefits. 

## 8.2 Conclusion 

This paper proposes and implements Injectra, a general-purpose code injection and functionality enhance-ment system for existing Web UI desktop applications. The system decouples host integration from upper-layer enhancements, providing unified page execution capabilities through runtime integration and pre-launch guidance, and supports the enhancement, replacement, and inspection of applications via a shared runtime, explicit target binding, and execution feedback. Validation across multiple real-world hosts, along with LLM tools for theme customization, reading layout reorganization, and box-selection annotation, demonstrates the ability to reuse the same execution foundation across applications. Against the backdrop of large language models capable of generating code based on natural language, Injectra further addresses the challenge of how generated code can be integrated into and executed within the software the user is currently using. It enables model-generated enhancements and developer-written payloads to share the same in-application execution foundation, while also providing a composable, uni-fied entry point for various interactive tools and agents. Consequently, existing desktop software is no longer limited to relying solely on predefined features and settings set by developers but now has the foun-dation to evolve into a software environment that can be continuously extended for users. Future work can focus on broader host adaptation, enhanced long-term maintenance, and natural language interaction experiences to drive the implementation of this foundation in more real-world workflows.
