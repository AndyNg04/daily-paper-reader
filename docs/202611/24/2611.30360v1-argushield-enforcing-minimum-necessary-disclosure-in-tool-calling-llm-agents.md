## 摘要
大语言模型智能体日益依赖第三方工具来完成用户任务。即使没有恶意意图，它们也可能在宽泛或约束不足的字段中填入私人信息，而这些信息对于接收工具而言并非必要，甚至并不合适。此类调用可能符合工具的模式要求并完成任务，却仍违反最少必要披露原则。我们提出 ArguShield，这是一种在工具调用执行前拦截其提议的中介层。它依据三项信号评估每个候选值：值的来源、任务相关性和披露边界。ArguShield 会放行有充分依据的值，将需要用户确认的值暂缓处理，并拒绝披露超出许可范围的值。我们使用四种工具调用模型，在 ArgPrivBench 上评估 ArguShield。ArgPrivBench 是一个包含 120 项任务、涵盖旅行、购物和医疗保健领域的基准。未受保护的智能体即使任务成功率很高，也经常过度披露私人信息。仅依靠提示词进行保护虽能减少未经授权的披露，却会显著降低任务成功率。在模拟用户确认的情况下，ArguShield 将标准任务和高风险任务中的未经授权静默披露率分别降至 9% 和 6%，同时保留了可通过确认挽回的任务成功率。

## Abstract
Large language model agents increasingly use third-party tools to complete user tasks. Even without malicious intent, they may fill broad or weakly constrained fields with private information that is unnecessary or inappropriate for the receiving tool. Such calls can satisfy the tool schema and complete the task, yet still violate minimum-necessary disclosure. We introduce ArguShield, a mediation layer that intercepts proposed tool calls before execution. It evaluates each candidate value using three signals: Value Provenance, Task Relevance, and Disclosure Boundary. ArguShield releases justified values, defers values that need user confirmation, and withholds those outside the permitted scope. We evaluate ArguShield with four tool-calling models on ArgPrivBench, a benchmark of 120 tasks across Travel, Shopping, and Healthcare. Unprotected agents frequently over-disclose private information despite high task success. Prompt-only protection reduces unauthorized disclosure but substantially lowers task success. ArguShield reduces unauthorized silent release to 9% on Standard tasks and 6% on High-risk tasks while preserving recoverable task success under simulated user confirmation.

# ArguShield 论文总结

## 1. 核心问题与研究动机

- **工具调用合法、任务完成，不代表信息披露合理。** 智能体可以把用户档案、历史上下文或先前工具输出中的个人信息填入 `notes`、`context` 等宽泛字段。即使参数符合 API 规范、调用也成功了，接收方仍可能获得完成任务并不需要的信息。这类过度披露不需要恶意工具或攻击者就会发生。
- **论文将问题定义为“工具参数过度披露”。** 最少必要披露不是简单地屏蔽所有敏感值，而是判断某个值是否有可靠来源、是否为当前任务所需，以及当前接收方是否有权获得它。例如，电话号码可能是配送所需的信息，却不应被自动填入酒店预订的备注。
- **整体思路**是把“模型想调用什么工具”与“系统允许向该工具发送什么数据”分开：模型负责起草调用，执行层负责逐值授权。

## 2. 方法论：执行前的逐值披露控制

ArguShield 在调用发往第三方之前拦截请求，把嵌套参数对象展平为一组“**参数路径—候选值**”，再对每个叶子值独立判断，而不是批准或拒绝整次调用。

| 判断信号 | 核心问题 | 文中描述的实现 |
|---|---|---|
| **值的来源（Value Provenance）** | 这个值从哪里来？ | 在当前请求、用户档案、历史工具输出和检索内容中进行精确、归一化或类型匹配；无可靠匹配的值标为推断或未知。 |
| **任务相关性（Task Relevance）** | 当前任务是否需要这个值？ | 结合用户意图、工具模式、参数路径、值类型和任务成功条件，区分必需、有用但非必需、缺乏支持及与任务冲突。 |
| **披露边界（Disclosure Boundary）** | 当前接收方在此用途下能否获得这个值？ | 根据接收方身份、工具用途、参数路径、值类型和授权状态，区分可直接披露、须确认和超出边界。 |

- **Hide（拦截）优先**：缺乏任务支持、与任务冲突、没有可靠来源或超出接收方边界的值被移除，不进入确认队列。
- **Keep（放行）**：只有在来源、任务需要和接收方授权均有充分依据时，才直接发送。模糊证据不能作为静默放行的依据。
- **Ask（待确认）**：可能有助于任务、但尚未获准直接发送的值先留在本地，只有确认后才可发送。
- 系统据此生成清理后的调用、本地确认队列和审计日志。**给定证据记录后，决策规则是确定性的；证据本身仍可能估计错误。** 推理时不使用基准的人工标注作为决策输入。

## 3. 实验设计：基准、对照与指标

- **主基准 ArgPrivBench**：120 项合成任务，涵盖旅行、购物和医疗；每个领域有 20 项标准任务和 20 项高风险任务。每项任务提供用户意图、可见上下文、目标工具模式、成功标准，以及标注为 Keep、Ask 或 Hide 的候选值。高风险表示接收方、用途或值类型受到更严格的约束，并不意味着违规更频繁。主评测为离线评估。
- **模型与对照**：评估 DeepSeek-V4-Flash、GLM-5.1、Kimi-K2.7-Code 和 Qwen3.7-Plus。比较 **NoProtection**（直接执行）、**Prompt-Only Guard**（只加隐私提示）和 **ArguShield**（执行前审核）。模型使用相同任务和工具模式，温度均为 0.0，仅在必要时适配端点格式。
- **外部验证**：一组使用来自 **26 个公开 MCP 服务器**的工具模式，构造隐私场景并检查本地服务器实际收到的参数；另一组使用 **123 项 AgentDAM 任务**，覆盖购物、GitLab 和 Reddit，通过执行边界适配器把网页动作表示为结构化参数。两组均未重训或修改发布策略。
- **指标**：APVR 衡量本应 Ask 或 Hide 的值被直接放行的比例；TLR 衡量至少发生一次此类披露的任务比例；TSR 衡量任务成功率；ADF1 是三类动作的宏平均 F1；ASKR 衡量已完成任务中的确认开销。**APVR 不计入确认后发生的披露**，因此不能当作总披露率。

## 4. 资源与算力

- 论文说明四个模型通过商业 API 调用，MCP 验证通过本地 `stdio` 服务器执行。实验重点是推理时的参数审核，外部验证没有重训。
- 文中未报告 GPU 型号或数量、训练时长，也未给出总 token 用量、API 成本、硬件配置或中介层延迟。因此，无法据此估算端到端部署开销。

## 5. 实验数量与证据充分性

- **实验规模**：主对照为 **4 个模型 × 3 种方法 × 2 个风险划分，共 24 个汇报单元**，复用同一批任务，并非 24 组独立数据集。另有两组外部验证、三项单信号消融、三种模拟确认策略，以及按领域、值类型、错误类型和披露后果分层的诊断。
- **公平性**：统一任务、模式和模型设置，有助于隔离执行前审核的作用；同时报告隐私与任务指标，也避免把“少发送参数”直接等同于“防护更好”。不过，无保护组的 TSR 是普通任务成功率，主表中 ArguShield 的 TSR 则计入模拟批准后可恢复的成功，两者不是完全相同的交互条件。
- **充分性**：这些实验足以支持“在所测场景中，逐值审核可以降低未授权静默披露”。但基线较少，未报告置信区间、重复运行波动或真实用户研究，尚不足以证明方法优于其他执行层防护，或能在部署中稳定复现同等收益。

## 6. 主要结论与发现

- **无保护时，高成功率与高过度披露并存。** 按主保护对照表（表 2）的四模型平均结果，无保护组在标准和高风险任务上的 APVR 分别约为 **84% 和 76%**；ArguShield 将其降至 **9% 和 6%**。在全部模拟批准的设定下，两组任务的 TSR 均约为 **97%**。
- **仅靠提示词可以更保守，但任务代价更大。** 提示词组各设置的 APVR 低于或等于 ArguShield，但平均 TSR 在标准和高风险任务中分别约为 **75% 和 69%**，动作分类 F1 也更低。因此，ArguShield 的主要优势是**兼顾任务完成与披露控制**，而不是获得最低 APVR。
- **接收方边界与来源检查是降低静默披露的主要信号。** 移除披露边界或来源信号，APVR 分别上升约 **73 和 54 个百分点**；移除任务相关性仅使 APVR 小幅变化，却明显增加确认并降低动作分类 F1。
- **任务成功并不完全依赖“全部批准”。** 最多批准首个待确认值时，批准的 Ask 值约少 **41%**，任务成功率不变；全部拒绝时，标准和高风险任务的 TSR 分别为 **92.9% 和 93.3%**。这些结果来自固定模拟策略，不代表真实用户行为。
- **外部验证显示一定迁移性。** MCP 场景的 APVR 从 **84.2% 降至 3.1%**，TSR 保持 **100%**；AgentDAM 的 APVR 从 **74.6% 降至 12.8%**，TSR 从 **96.7% 降至 93.5%**。后果分层还显示，两种任务划分中的高后果值残余违规率均低于低后果值；**风险等级不能仅凭整体 APVR 高低判断**。

## 7. 优点

- **干预位置和粒度恰当**：在数据离开系统之前执行控制，能单独移除不必要的值，而不必拒绝整次调用。
- **把可见性、必要性与授权分开**：系统可访问某个值，不代表任务需要它；任务需要它，也不代表当前接收方可以直接获得它。
- **设计可审计，实验能解释误差来源**：记录逐值证据与动作，并用消融、确认策略和后果分层分析区分误放行、过度扣留与不必要确认，而非只汇报一个总体泄露率。

## 8. 不足与局限

- **真实场景覆盖有限**：主基准是三个领域中的合成、离线任务；MCP 验证虽采用真实工具模式，但隐私场景是围绕这些模式构造的。AgentDAM 补充了网页交互证据，但仍不能代表长期运行、多轮工作流或组织内部的复杂政策。
- **证据提取决定防护上限**：来源匹配不等同于完整的数据流追踪；嵌在自由文本中的信息、改写过的值、含糊的用户意图和说明不足的工具模式都可能引起误判。任务相关性判断还使用任务成功条件，而实际部署中未必有同样明确的条件；文中对相关性和边界判定的实现细节也不足以独立复现全部决策。
- **确认机制缺少真人验证**：真实用户可能误解、拒绝或习惯性批准确认请求。诊断显示，残余动作错误中 **43% 是过度扣留，39% 是不必要确认**，说明降低过度披露仍可能带来交互摩擦。
- **不构成端到端隐私保证**：系统不能撤回已发送的信息，也不覆盖最终回复、共享记忆、智能体间通信和多工具输出组合导致的敏感推断。结论应限定为：**在所测条件下，ArguShield 减少了执行前未获确认的参数披露，而非消除了整个智能体系统的隐私风险。**
