## 摘要
个人智能手机上的移动智能体可能影响私人数据、支付、设置和前台屏幕。我们提出 MATE（Mobile Agent Trustworthy Execution，移动智能体可信执行），这是一种执行层系统，可在不修改底层模型的情况下，对智能体的动作提议与设备实际操作之间的边界进行控制。MATE 将每个 UI 原语表示为结构化动作记录，其中包含指令、目标应用、屏幕上下文、原语和动作字段。运行时护栏（Runtime Guardrail，RG）根据该记录作出允许、阻止或请求用户批准的决策；预定义任务路由（Predefined Task Routing，PTR）通过经过验证的路由处理重复请求，并在执行后检查屏幕；浮动界面则以紧凑的叠加层呈现执行过程。在 MobileSafetyBench 上，MATE 将 GPT-4o 的高风险操作拦截率从 29.7% 提升至 97.0%。在 AndroidWorld 上，MATE 将 LLM 调用次数最多减少 6 倍，并将重复使用场景下的任务成功率提高至 95.7%。

## Abstract
Mobile agents on personal smartphones can affect private data, payments, settings, and the foreground screen. We present MATE (Mobile Agent Trustworthy Execution), an execution-layer system that controls the boundary between agent action proposals and device effects without modifying the underlying model. MATE represents each UI primitive as a structured action record that combines the instruction, target app, screen context, primitive, and action fields. Runtime Guardrail (RG) maps this record to an allow, block, or user-approval decision; Predefined Task Routing (PTR) serves recurring requests through verified routes with post-execution screen checks; and a floating interface keeps execution in a compact overlay. On MobileSafetyBench, MATE raises high-risk blocking from 29.7% to 97.0% under GPT-4o. On AndroidWorld, it reduces LLM calls by up to 6x and raises recurring-use task success to 95.7%.

## 1. 核心问题与研究动机

- **模型提出的动作，不应直接等同于用户授权的设备操作。** 手机智能体通常逐步观察屏幕、生成点击或输入动作，再交给操作系统执行。但同一个“点击”可能只是打开页面，也可能确认付款。仅检查用户指令或模型输出文本，难以判断动作在当前界面上会产生什么后果。
- **个人手机上的安全、效率和交互问题相互关联。** 手机集中存放账户、消息、照片和支付信息；重复调用多模态模型会累积开销；长时间全屏操作又会占用用户正在使用的前台界面。
- **论文的核心主张**是把控制点放在“动作已提出、但尚未在设备上生效”的位置。MATE 不重新训练或替换底层模型，而是在执行层决定哪些动作可以放行、哪些需要审批，以及哪些常用流程可以直接复用。

## 2. 方法论与算法流程

### 2.1 运行时护栏（RG）：判断待执行动作的风险

- MATE 将候选动作表示为五元组 \(x=(u,p,s,a,m)\)：**用户指令、目标应用、屏幕上下文、动作原语和结构化字段**。字段包括目标控件、输入值或坐标，使护栏能区分形式相同、后果不同的动作。
- RG 结合两类检查：一类由语义守护模型判断越狱意图、禁止主题和金融或凭据相关意图；另一类通过确定性规则检查应用包名、坐标范围、动作格式和确认信号。论文实验统一使用 **GPT-4o-mini** 作为语义守护模型。
- 判定顺序是**拒绝优先，其次审批，否则放行**。命中禁止或受限规则时终止；属于敏感但可确认的动作时，先发起用户审批，而不是直接执行。例如，论文演示了阻止凭据输入，并将符合规则的转账动作交由用户确认。

### 2.2 预定义任务路由（PTR）：复用已验证的常用流程

- 部署前，系统在有限深度内探索已安装应用的界面，将常见入口和操作序列保存为应用专属路由。AndroidWorld 的静态路由在评测前冻结，不使用评测轨迹构建；另一种持续更新模式则在成功交互后积累已验证的路由。
- 运行时，应用适配器用关键词或正则将指令映射到路由 ID，再用“**应用标识 + 路由 ID**”检索。命中后确定性执行预设步骤，并检查结果屏幕是否符合目标；未命中、执行失败或校验失败时，回退到视觉智能体逐步决策。
- 公式（3）的核心含义是：**只有路由命中且成功通过校验，才能省下该任务的逐步策略调用**。在论文的简化估计中，剩余调用量约为基线调用量乘以 \(1-\text{命中率}\times\text{命中后校验成功率}\)。这估计的是逐步控制器调用，不等同于完整端到端成本。
- 附录还区分了**直接执行**和**路由提示**：前者跳过逐步规划，后者只向模型提供导航线索，具体点哪里仍由模型根据当前屏幕决定。按算法 1，逐动作 RG 检查明确位于模型回退分支；论文对直接执行分支的安全约束主要依赖预验证与路由范围限制，并说明支付相关应用不纳入直接路由构建。

### 2.3 浮动执行界面：保留用户观察和接管能力

- 浮动模式将执行过程呈现在紧凑叠加层中，用户可保留底层应用的视野，并在登录或确认环节接管，再让智能体继续。浮动界面改变的是呈现和交互方式，本身不是安全隔离机制。

## 5. 实验数量与证据充分性

- **规模上**，论文包含两个主基准、一个补充安全基准，以及多组部署和开销分析。主要对照包括安全侧的 **7 个骨干开关对比**、**2 个骨干各 5 种护栏配置**，任务侧的 **7 个骨干各 3 种 PTR 配置**，另有 **5 轮重复使用实验**、**4 档探索深度**和两种界面模式对比。这些配置有复用，不宜相加当作独立实验数。论文称，除另有说明外，AndroidWorld 的 MATE 消融取三次独立运行的平均值。
- **最有说服力的是同系统对照。** 固定骨干与执行协议再切换 RG 或 PTR，比横向比较不同移动智能体更能归因到执行层本身。静态路由不使用评测轨迹，也降低了直接复用测试答案的风险。
- **证据足以支持基准内收益，但不足以证明真实部署可靠性。** 跨系统比较没有覆盖最新的端到端 GUI 模型；固定守护模型提高了 RG 开关比较的一致性，却不能说明换用其他守护模型后仍有相同收益。关键表格也缺少充分的方差或置信区间，较小的差异不宜过度解读。

## 6. 主要结论与发现

- **RG 显著提高高风险任务阻止率，但存在误拦截。** GPT-4o 从 **29.67% 提升至 97.03%**，低风险误拦截率为 **4.10%**；Qwen2.5-VL 从 **9.68% 提升至 90.17%**，误拦截率为 **14.90%**。GPT-5.5 的补充结果为 **36.66% → 98.60%**，误拦截率 **3.00%**。两个主骨干在该基准的间接提示注入子集上均达到 100% 阻止率，但这不代表能阻止所有真实攻击。
- **护栏对不同骨干的作用机制不同。** Qwen2.5-VL 的大部分阻止率提升来自主题检查；GPT-4o 加入应用包名、坐标等结构检查后仍有明显增益。AndroidWorld 的独立开销对照中，RG 未降低报告的任务成功率，但增加了守护检查和重试开销，且 Qwen2.5-VL 的增幅更明显。
- **静态 PTR 同时改善成功率和成本。** 在 GPT-4o 的 AndroidWorld 受控对照中，\(D=6\) 相比无 PTR，将成功率从 **41.4% 提升至 67.2%**，平均调用从 **14.2 次降至 6.8 次**，端到端延迟从 **47.1 秒降至 14.1 秒**。七个受测骨干均有提升，成功率增益为 **27.5–38.0 个百分点**。
- **接近 6 倍的调用差距来自重复使用实验，不是通用基准的平均加速。** 五轮中，路由命中率从 **4.8% 升至 62.7%**，总调用从 **1,711 次降至 280 次**，末轮成功率达到 **95.7%**。浮动与全屏模式在禁用 PTR 时均取得 **41.4%** 的成功率；该结果支持浮动模式未降低此设置下的任务完成率，但不能替代用户体验评测。

## 7. 优点与亮点

- **控制对象贴合 GUI 风险。** 用带有上下文的待执行动作做决策，比只过滤指令或输出文字更接近真实设备后果。拒绝与审批分开，也保留了合法敏感操作的用户授权途径。
- **路由复用有明确的校验和回退机制。** 系统既不要求模型重复推理稳定的导航流程，也不把已存路由视为永远有效。论文同时报告探索成本、存储和深度饱和情况，有助于判断何时值得构建路由库。
- **同时报告收益与代价。** 安全实验给出低风险误拦截率，效率实验区分静态路由与重复使用场景，消融展示了骨干和规则组合如何影响结果。与 OS-Sentinel 的比较也如实呈现了准确率和 F1 不总是同步改善。

## 8. 不足与局限

- **执行后校验不能防止已发生的副作用。** 算法 1 的直接路由分支先执行、后验证，未展示与回退分支等价的逐动作护栏。若路由过时或匹配错误，事后发现结果不符也不代表中间操作可以撤销。因此，不能把 RG 的高风险阻止率直接视为整套系统所有执行路径的安全保证。
- **泛化依赖已知应用、稳定布局和有限的动作词表。** 跨应用交接、复杂手势、事件触发、硬件交互和认证流程多需回退。新应用、界面改版或语义不清晰的控件都可能降低命中率或风险识别率。路由未使用评测轨迹，不等于验证了对未见应用的泛化。
- **安全评估和交互评估覆盖有限。** 任务拒绝／阻止率合并了模型拒绝和执行层拦截，不能单独刻画不可逆副作用或用户误批风险。论文没有独立的自适应对抗评测，也没有真实用户研究来测量审批疲劳、接管体验或长期信任。
- **不能从调用下降直接推出省电或隐私改善。** 虽然路由库可以本地存储，实验中的骨干推理仍在设备外完成，屏幕观测可能经网络发送。实际部署还需评估敏感画面处理、网络波动、端到端能耗，以及不同设备上的兼容性。
