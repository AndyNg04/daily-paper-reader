## 摘要
AI 编程智能体日益负责管理跨会话和项目延续的上下文，但开发者对智能体存储、检索和应用的内容了解有限。这种不透明性造成了元记忆问题：开发者对哪些内容应当被记住所作的元层级判断，与智能体在对象层级执行的记忆操作相互分离，妨碍了维持二者一致的监控与控制。我们对 12 名开发者开展了一项形成性研究，明确了他们希望从智能体记忆使用的四个维度进行监控和控制的内容。基于这些发现，我们设计了 MemoSync，这是一种协同管理系统，将智能体记忆视为一种可共同操作的共享表征：智能体提出候选记忆并报告其使用的内容，开发者则对其进行审核、编辑并设定适用范围。在一项与两个基线系统进行比较的被试间研究中（N=132），MemoSync 组参与者的任务表现显著更高，开发者与智能体之间的记忆一致性平均值也最高。探索性中介分析显示，一致性优势主要源于监控准确性的提升。尽管参与者执行的监控和控制操作显著增多，他们报告的感知工作负荷并未增加。一项为期一周、涉及九名开发者的部署研究表明，记忆监控与控制能够融入日常开发工作。MemoSync 已开源：https://github.com/SLEEPYBQ/MemoSync。

## Abstract
AI coding agents increasingly manage what context carries across sessions and projects, but developers have limited visibility into what these agents store, retrieve, and apply. This opacity creates a metamemory problem: the developer's meta-level judgments about what should be remembered are separated from the agent's object-level memory operations, disrupting the monitoring and control that keep the two levels aligned. We conducted a formative study with 12 developers and identified what they want to monitor and control across four dimensions of agent memory use. Based on these findings, we designed MemoSync, a co-management system that treats agent memory as a shared, operable representation: the agent proposes memory candidates and reports which items it uses, and the developer reviews, edits, and scopes them. In a between-subjects study (N=132) against two baselines, MemoSync participants achieved significantly higher task performance and the highest mean developer-agent memory alignment. In an exploratory mediation analysis, the alignment advantage was primarily driven by improved monitoring accuracy. Despite performing substantially more monitoring and control actions, participants reported no increase in perceived workload. A week-long deployment with nine developers showed that memory monitoring and control fit into everyday development work. MemoSync is open-sourced at https://github.com/SLEEPYBQ/MemoSync.

# MemoSync：跨上下文协同管理开发者与智能体的元记忆

**作者：** Baiqiao Zhang 等｜[论文预印本](https://arxiv.org/pdf/2611.24165v1)｜[开源代码](https://github.com/SLEEPYBQ/MemoSync)

## 1. 核心问题与研究动机

- **问题不只是智能体会不会记住，而是开发者能否知道它记住了什么、在哪些场景使用，以及能否及时纠正。** 跨会话、跨项目开发时，智能体可能遗忘已有约定，把项目规则带到无关代码库，或继续沿用已废弃的要求。开发者通常要等到输出出错，才察觉记忆与预期不一致。
- 论文用**元记忆（metamemory）**解释这一问题：在人类认知中，元层负责判断该记什么，对象层负责存储和检索，两者通过“监控—控制”形成闭环。在开发者与智能体的协作中，这两个层级分属双方：**开发者判断什么值得保留、适用范围是什么；智能体负责存储、选择并将记忆用于任务。** 一旦这些操作不可见，开发者即使能够发出纠正指令，也很难知道何时、针对哪一条介入。
- 现有做法各有缺口：手动重述上下文难以长期维持；静态 Markdown 文件可编辑，却不说明智能体这一轮用了哪些规则；自动记忆提取减轻记录负担，但写入和迁移往往缺乏直接监督。论文因此依次研究：**开发者需要监控和控制什么、怎样设计协同管理界面、这种设计是否改善记忆对齐与任务表现。**

## 2. 方法论：把记忆变成双方可共同操作的对象

- **记忆表征。** 将记忆建模为条目 \(M_i=(c_i,s_i)\)，其中 \(c_i\) 是内容，\(s_i\) 是**个人、项目或会话**范围。条目提供简短摘要、按需展开的详情和修改历史。记忆面板支持编辑、调整范围、归档与恢复，并可与 Markdown 文件同步；逐轮记忆记录保存在智能体上下文窗口之外，会话压缩后仍可查询。
- **每轮任务围绕四个环节组织：**

  | 环节 | 智能体做什么 | 开发者能做什么 |
  |---|---|---|
  | **演化：更新长期记忆** | 从对话提取可复用的偏好、约束、决策理由和经验；标记冲突、重复或疑似过时的条目 | 审核、编辑、合并、拒绝或调整范围；提议的变更经批准后才写入 |
  | **选择：组装本轮工作记忆** | 推荐本轮条目，并逐条说明预计用途 | 增删条目或用自然语言要求重新选择；确认后才将条目作为记忆块注入主会话 |
  | **执行：追踪与纠正** | 在生成回复中实时引用记忆条目 | 查看被引用的内容与范围，发现偏差时中断，并提交纠正指令以继续执行 |
  | **影响：事后审计** | 用独立于执行分支的会话检查记录，区分条目影响了输出、被违反、不适用或无可见影响，并标明是执行自报还是审计发现 | 跳转到相关证据，将条目标记为下轮必须纳入；反复违规则可触发修改提议 |

- **跨项目迁移采用“源条目 → 通用原则 → 目标项目规则”。** 先去除源项目特有的实现细节，再根据目标代码库、现有记忆和当前任务重写。界面并列展示三种形式和建议范围，由开发者决定是否迁移，而不是整份复制旧项目配置。
- **实现与指标。** 系统基于 Kanna，使用 TypeScript、React、Bun 和 SQLite，支持 Claude Agent SDK 与 Codex CLI。候选提取、迁移建议和冲突检查在共享上下文前缀的分支中并行准备，以复用提示缓存，并避免把分析过程写入主会话。实验中，**记忆对齐**比较“用户希望保存什么”与“系统实际保存什么”；**监控准确率**比较“用户以为系统保存什么”与实际存储；**控制准确率**则衡量用户希望保留的要求是否落实到最终产物。内容评分归一化到 \([0,1]\)，范围匹配记为 0 或 1，联合指标为两者乘积。

## 3. 实验设计：场景、基准与对比方法

- **形成性研究：12 名开发者。** 通过约一小时的访谈和材料走查，共同查看真实项目的对话、配置文件及智能体记忆，归纳对记忆表征及四个使用环节的需求。
- **受控实验：132 人，三组各 44 人。** 每人完成两个 FullStack-Bench 项目——**公寓租赁**和**汽车租赁**。两者均使用 Next.js、NestJS 和 PostgreSQL，业务与数据模型不同，但应用结构相近。每个项目包含两场连续会话，第二场沿用第一场代码；项目顺序在参与者之间平衡。四场提交分别冻结，使用基准的前端、后端和数据库评分规则，总分 30 分。
  - **Auto：自动记忆。** 成功执行后自动更新，最多保留 50 条；逐轮注入当前项目的全部活跃记忆，切换项目时复制一次旧项目记忆。参与者可看摘要并用自然语言要求修改，但不能直接编辑条目。
  - **Static：静态配置。** 开发者与智能体共同编辑 `MEMORY.md`，每轮注入完整文件。
  - **MemoSync：协同管理。** 使用结构化条目、逐轮选择、执行引用与事后审计等完整机制。
- 三组使用相同工作台、任务材料和编码智能体。除任务评分外，研究还比较了记忆对齐、监控与控制准确率、记忆应用感知偏差、交互次数、主观负荷、可用性以及活跃任务时间。
- **真实项目部署：9 名开发者试用一周。** 参与者在自己的项目上使用系统，研究者结合操作日志与结束访谈，观察记忆维护、跨项目复用和并行会话交接。

## 5. 实验数量与证据充分性

- **总体是三项用户研究，加一项智能体单独运行的任务校准。** 主实验有三种条件、两个项目、四个会话位置，共 **528 个参与者会话**，但组间比较的参与者样本为 **132 人**，并非 528 个独立样本。校准将四种会话任务各运行 10 次，共 40 次；无累积记忆时平均得分约为满分的 50%。校准为单次运行且无人参与，只能作描述性参照。
- **整体系统比较较扎实。** 主实验有事前功效分析、等组样本、项目顺序平衡、统一智能体与评分流程；成对比较按各指标和比较位置做 Holm 校正，主观工作负荷还进行了等效性检验。记忆应用评估在 200 个随机条目上与人工裁决结果的一致率为 **97.5%**。
- **证据足以比较这三种具体实现，不足以确定哪个模块最有效。** 论文没有对迁移、逐轮选择、实时引用或审计分别做消融。Auto 的条目上限和摘要机制、Static 的全文注入、MemoSync 的选择性注入同时改变了智能体得到的上下文，因此结果不能单独归因于“增加了人工审核”，也不能推广为对所有自动记忆系统的比较。

## 6. 主要结论与发现

| 指标 | MemoSync | Auto | Static | 结果解读 |
|---|---:|---:|---:|---|
| 总体任务得分 | **59.8%** | 47.7% | 51.1% | MemoSync 显著高于两组；Static 也显著高于 Auto |
| 记忆内容对齐 | **88.0%** | 77.6% | 66.2% | MemoSync 显著高于两组，且四个会话位置均有内容对齐优势 |
| 内容监控准确率 | **93.6%** | 87.1% | 76.2% | MemoSync 显著高于两组 |
| 记忆应用绝对感知偏差（1–5 分量表） | **0.19** | 0.42 | 0.38 | MemoSync 显著缩小主观感知与产物评估之间的差距 |

- **对齐收益主要体现在内容，不应概括为所有维度均显著胜出。** “内容＋范围”的对齐得分在 MemoSync 中均值最高（69.0%），但仅显著高于 Static（50.0%），与 Auto 的差异未达显著；单看范围也是如此。MemoSync 的控制准确率在三个维度上都显著高于两组，但各组均已处于较高水平。
- **监控准确性可能是关键机制。** 探索性中介分析中，经监控准确率的间接效应相较 Static 和 Auto 分别约为 **+20.2** 和 **+11.0 个百分点**；经控制准确率的间接效应未达显著。这为“先看清记忆状态，才能有效纠正”提供了支持，但不能确立因果机制。
- **操作明显增加，未检测到主观负荷或耗时上升。** MemoSync 组四场会话平均执行 **70.3 次监控、25.3 次控制**；对照组平均监控约 7–9 次，控制不足 1 次。主观负荷在预设的中等效应界值内通过等效性检验；系统可用性和活跃任务时间未检出组间差异。
- **部署中，记忆记录让开发者不必全程盯着执行。** 部分参与者委派任务后再通过记录和审计恢复监督，也有人利用记忆在项目或并行会话之间交接要求。同时，参与者希望对简单指令、明确偏好和可直接修复的错误减少重复确认。

## 7. 优点

- **把“存了什么”与“用了什么”分开设计。** 除了展示记忆库，还把每轮的选择、执行引用、输出证据和纠正入口连起来，比单纯增加一个可编辑面板更能帮助开发者定位偏差。
- **允许按需监督，而不是要求持续盯守。** 开发者可以在执行前修改选择、执行中打断，也可以完成后只检查被标记的条目。摘要与详情分层，兼顾人的阅读负担和智能体对实现细节的需要。
- **证据相互补充。** 需求研究解释为何设计这些功能，受控实验量化整体效果，真实项目部署则揭示使用方式与确认摩擦。论文还区分了组间显著差异、负荷等效性和探索性机制分析。

## 8. 不足与局限

- **外部效度有限。** 两个基准项目共享技术栈、业务结构相近，尚未充分检验系统能否在高度异质的项目间阻止不当迁移。一周、9 人的部署也无法判断长期维护成本、持续使用率或多人团队的记忆治理效果。
- **完整系统优势不能拆解到单个机制。** MemoSync 在首场会话已表现出任务优势，说明收益并非只能来自跨项目迁移，也可能来自第一轮的候选提取与上下文选择。未来需要分阶段消融和更强的替代基线。
- **可见性不是模型行为的因果证明。** 实时引用依赖智能体自报；审计虽在单独分支执行，仍依赖模型判断。逐轮“强制”主要保证条目被纳入工作记忆，并不保证生成代码一定遵守。模型也会影响用户看到哪些条目，造成对遗漏项的盲区。
- **测量和统计有边界。** 问卷围绕已存储条目展开，对“本该记住却从未被提取”的内容覆盖有限。监控准确率与记忆对齐又使用同一批条目和同一问卷，解读中介结果时需留意共享测量来源。另有 9 人因缺少可评估的期望内容，未纳入控制准确率、应用偏差及中介分析；成对比较虽经校正，但未对所有指标和会话位置做全局校正。
- **实际部署仍有确认与治理成本。** 每轮审核可能对简单任务造成不必要的中断。若扩展到生产或团队环境，还需检验何时可以自动处理、何时必须人工批准，以及跨项目或跨成员共享时如何限制访问、追踪来源并明确责任。
