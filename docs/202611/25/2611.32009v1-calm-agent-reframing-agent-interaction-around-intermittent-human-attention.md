## 摘要
当用户专注于其他工作时，AI 智能体可以执行辅助任务。然而，用户仍需了解任务状态、进行调整，并在需要帮助时作出响应。我们认为，持续执行辅助任务的智能体应围绕人类间歇性注意力进行设计：任务应在交互间隙继续执行，用户也应能轻松返回，以了解和控制任务。我们将这一理念发展为 Calm Agent。它通过持久化的任务表征，连接三种按需交互模式：委派（Delegate）、调整（Adjust）和查看（Check）。生成式交互为开放式目标提供适用的控制方式与反馈，而现有控件则支持常规操作。我们通过 Orvlet 展示这些原则。Orvlet 是一款用于后台执行和紧凑型任务界面的桌面原型。我们指出了若干挑战：在保持连续性的同时调整界面、协调不同任务间的注意力、提供响应及时的交互，以及随着时间推移学习用户习惯。其目标是在支持持续任务控制的同时，保护用户的注意力，使其能够专注于主要工作。

## Abstract
AI agents can carry out auxiliary tasks while users focus on other work. Yet users still need to understand task state, make changes, and respond when help is required. We argue that agents for ongoing auxiliary tasks should be designed around intermittent human attention: tasks should continue between interactions, and users should be able to return with little effort to understand and control them. We develop this position as Calm Agent. It connects three on-demand interaction modes: Delegate, Adjust, and Check, through a persistent task representation. Generative interaction provides controls and feedback suited to open-ended goals, while existing controls support routine actions. We illustrate these principles with Orvlet, a desktop prototype for background execution and compact task interfaces. We identify challenges in adapting interfaces while preserving continuity, coordinating attention across tasks, providing responsive interaction, and learning user habits over time. The aim is to support continuing task control while protecting attention for primary work.

# Calm Agent：围绕间歇性人类注意力设计智能体交互

**论文定位：**这是一篇提出设计立场与交互框架的论文。作者用桌面原型 Orvlet 展示框架如何实现，但没有通过用户实验验证它能否降低注意力负担。

## 1. 核心问题与研究动机

- **把任务交给智能体，不等于把注意力成本也交了出去。** 当智能体在后台播放音乐、计时或查询信息时，用户仍需确认当前状态、调整任务，并在执行受阻时作出决定。如果每次回访都要打开聊天窗口、翻阅历史或重新组织提示词，辅助任务仍会打断主工作。
- **任务持续时间与用户参与时间并不匹配。** 辅助任务可能运行数分钟乃至数小时，而用户每次只愿意投入几秒钟。论文因此将设计重点从“如何发出一条指令”转向“如何让用户离开后再回来，仍能迅速理解和控制同一个任务”。
- **与平静技术（Calm Technology）的关系：**论文沿用技术可在注意力中心与边缘之间移动的理念，并指出开放式委托带来的额外问题：随着目标和执行环境变化，系统还要判断哪些状态值得展示、哪些动作仍可用，以及何时确实需要用户介入。

## 2. 方法论：三种交互模式与持久任务表征

### 2.1 三条设计原则

1. **交互之间维持任务。** 界面收起后，任务仍应在授权范围内继续执行并更新状态；如果缺少必要输入，则保留任务和待处理请求，而不是要求用户维持对话。
2. **让短时交互与意图匹配。** 开放式目标用语言表达，明确的局部修改用直接控件完成，只想了解进度时则直接查看状态。常规操作不应反复触发界面生成。
3. **回访时既看得懂，也能采取行动。** 用户应能直接看到已观测的状态、当前可执行的操作以及是否需要输入；如果系统无法确认执行状态，应明确显示不确定性。

### 2.2 三种按需模式

| 模式 | 用户目的 | 对任务的作用 |
|---|---|---|
| **Delegate（委托）** | 用自然语言建立目标，或表达现有控件无法覆盖的修改 | 建立或修订目标与约束，必要时重新规划或调整界面 |
| **Adjust（调整）** | 使用已有控件执行明确操作，如暂停播放或修改计时 | 直接调用当前任务绑定的动作，不必重新写提示词 |
| **Check（查看）** | 确认任务在运行、等待输入还是已经完成 | 读取当前状态，必要时展开详情，不下达新指令 |

三种模式不是固定流程，用户可以按需切换。**智能体主动请求注意不是第四种模式**：它描述交互如何发起，用户随后可以查看问题、用语言补充信息，或通过已有控件作出选择。

### 2.3 任务表征与执行流程

- 每个任务表示为 \(T_i=\langle G,C,S,A,H\rangle\)：\(G\) 是目标，\(C\) 是用户与环境约束，\(S\) 是可观测状态，\(A\) 是可用动作及其处理逻辑，\(H\) 是执行历史。这个表征是界面和后台执行共享的任务模型，而不是训练目标或优化公式。
- 对于新目标或目标修订，系统结合任务上下文进行解释和规划，通过网页、应用或工具执行，并检查结果、更新状态和历史。对于已验证的控件，系统可以复用动作绑定；如果只是运行数值发生变化，则只更新显示。
- **界面随交互需求变化，而不是随每次状态变化重建。** 例如，把音乐改为纯器乐爵士可能改变选曲标准，但播放和音量控件仍可保留。若某项动作已不可用，界面应明确标示，而不是让同一个控件悄悄改变含义。

## 6. 主要结论与发现

- **核心结论是设计主张，而不是实证发现：**持续性辅助任务应能在用户离开后继续运行，或在等待输入时保留上下文；用户回访时，应能直接看到可信状态并采取行动，而不必从对话中重建任务。
- **原型展示了两种访问路径可以共存：**用户可主动检查或调整，也可在智能体确实需要澄清或决策时，从同一任务入口回应。
- 论文归纳了四项开放挑战：**界面适配与控件连续性、多任务注意力请求的协调、界面生成与执行的响应速度，以及长期用户习惯学习。**

## 7. 优点

- **研究问题具体。** 论文将注意力成本落实到可观察的步骤：定位任务、理解状态、选择操作、回到主工作，为后续用户研究提供了清晰的测量方向。
- **区分了需要生成的交互与应保持稳定的操作。** 自然语言用于表达开放式目标，直接控件用于明确调整，状态显示用于快速确认；论文没有把生成界面当作每次交互的默认方案。
- **强调界面必须与真实执行一致。** 控件不仅要位置稳定，还要语义稳定；状态反馈应有执行依据，不能把尚未验证的结果呈现为已经完成。相比单纯缩小窗口，这更直接关系到用户能否安全、有效地恢复控制。
