CANDID: Candidate-Driven Intervention for Disciplined Execution in
Local Computer-Use Agents
Woongkyu Lee
Jungwook Choi*
Hanyang University
{lwghanyang, choij}@hanyang.ac.kr
Abstract
We present CANDID (Candidate-Driven In-
tervention for Disciplined Execution), an
execution-control framework designed to en-
hance the reliability of local computer-use
agents (CUAs) in resource-constrained settings.
While local CUAs feature robust baseline pro-
ficiency in single-step action prediction, they
frequently fail at critical junctions due to rigid
action loops or premature DONE decisions.
Rather than imposing imprecise cognitive loads
through textual reflection, CANDID repurposes
parallel test-time scaling into a disciplined,
execution-level intervention at sparse, failure-
prone points. We introduce a loop-recovery
mechanism to filter candidates away from re-
peated behaviors and a conservative, unani-
mous DONE gating policy that requires abso-
lute consensus to terminate. Experiments on
OSWorld demonstrate that CANDID’s struc-
tural control significantly improves success
rates, outperforming feedback-based alterna-
tives with minimal execution overhead.

Introduction
Computer-use
agents
(CUAs)
have
recently
emerged as a promising paradigm for autonomous
interaction with graphical user interfaces (GUIs),
enabling multimodal agents to execute real-world
desktop and web tasks by understanding screen-
shots and executing GUI actions. Recent advances
in multimodal foundation models (Qin et al., 2025;
Wang et al., 2025; Xue et al., 2026; Xu et al., 2025;
Lin et al., 2024) and agentic frameworks (Agashe
et al., 2024, 2025; Gonzalez-Pumariega et al., 2026;
Yang et al., 2025) have significantly improved long-
horizon GUI interaction capabilities across increas-
ingly realistic environments (Xie et al., 2024; Zhou
et al., 2024; Bonatti et al., 2024; Deng et al., 2023).
In particular, modern CUA systems leverage hi-
erarchical planning (Agashe et al., 2024), mem-

ory retrieval (Liu et al., 2025), and test-time scal-
ing (Yang et al., 2025) strategies to improve execu-
tion robustness and task success rates.
Deploying
CUAs
under
local,
resource-
constrained settings is practically important,
and small language model (SLM)-based agen-
tic systems have been increasingly proposed
toward this goal (Belcak et al., 2025). Yet such
deployment remains highly challenging: unlike
large cloud-based systems that rely on expensive
multi-agent orchestration (Song et al., 2026; Yang
et al., 2026; Han et al., 2026) or proprietary
reasoning models (Anthropic, 2026a; Singh et al.,
2026), local CUAs operate with limited model
sizes and weaker multimodal reasoning. Under
these conditions, simply increasing execution
horizons or enlarging multimodal histories often
fails to reliably improve performance. The central
obstacle is that local agents fail in two coupled
ways: they fall into repetitive action loops, or
terminate prematurely before completing the task.
Moreover, naively scaling the step budget or
contextual history merely shifts the failure pattern
between the two, rather than resolving both.
Prior methods for recovering failed agent trajec-
tories primarily rely on textual reflection or verifier
feedback (Shinn et al., 2023; Han et al., 2026),
where the agent inspects its own recent trajectory,
generates natural-language feedback, and incorpo-
rates it before revising its next action. However, we
argue that such feedback-based approaches provide
limited benefit for lightweight local CUAs, whose
reasoning capabilities are often insufficient either
to generate meaningful textual feedback about the
failure or to convert given feedback into distinct,
executable GUI actions. These limitations prevent
agents from escaping repetitive action loops or im-
proving termination decisions under ambiguous
completion states, often causing the model to still
repeat its failed behavior under a restated rationale.
To overcome these limitations, we instead build

complementary failure modes, and that sparse inter-
vention is more effective than applying candidate

Background and Motivation
2.1
Computer-Use Agents
Computer-use agents (CUAs) autonomously op-
erate graphical user interfaces (GUIs) in real OS
environments, observing screenshots and gener-
ating executable actions such as clicking, typing,
scrolling, or keyboard inputs. As illustrated in
Fig. 1, at each step the agent receives a task in-
struction, the current screenshot, and a multimodal
history of previous screenshot–response pairs, and
predicts the next action in a structured format (e.g.,
click(x,y) or typewrite(‘Tesla’)). The ac-
tion is executed in the environment, after which the
updated screenshot is observed. This interaction
continues until the agent emits a termination signal
such as DONE or reaches the step budget s, while
the history length h controls the number of past
screenshot–response pairs retained as context.

Limitations of Textual Feedback
Prior autonomous-agent frameworks often use
prompt-level verification or self-reflection to miti-
gate execution failures (Han et al., 2026; Pan et al.,
2024; Shinn et al., 2023). These methods work
well with proprietary, large-scale reasoning models,
whose stronger language understanding lets verbal
feedback translate into corrective actions. Inspired
by VLAA-GUI (Han et al., 2026), we implement
two representative self-feedback mechanisms: a

a rejected DONE prediction, the agent regenerates
DONE or repeats a recent target, again resulting in
failure. These results highlight the limited effec-
tiveness of textual feedback for local CUAs.

Method
We propose CANDID, a sparse, candidate-based
execution-control framework for local CUAs that
intervenes at failure-prone steps to address two
coupled failure modes: repetitive action loops and
premature DONE decisions. Our key intuition is
that local CUAs can often generate multiple plau-
sible candidates from the same interface state but
fail by committing to a single one under uncertain
execution states. Instead of sampling throughout
execution, CANDID generates a small set of can-
didates only at these high-risk points, recovering
from loops by selecting an alternative candidate
and preventing premature termination by requiring
unanimous agreement before accepting DONE.
3.1
Loop-Recovery Candidate Selection
Fig. 4(a) illustrates CANDID’s loop-recovery
pipeline. At each step, the agent predicts its next
action from the current screenshot and recent his-
tory. When the proposed action is identified as a
potential repetitive loop and confirmed as stagnant,
CANDID samples alternative candidates, filters out
those matching the detected loop pattern, and exe-
cutes one of the remaining candidates.
Loop detection.
Judging whether the agent is
stuck in a loop is itself unreliable: the local CUA
often cannot assess its own progress, while pure
rule-based heuristics risk flagging legitimate rep-
etition as a loop. We therefore use a two-stage
gate that separates cheap detection from reliable
confirmation.
A lightweight rule-based detec-
tor first compares the proposed action against a
sliding window of recent actions (governed by
a window size, a minimum repeat count, and a
target-coordinate tolerance) and flags repetitive pat-
terns—for example, repeated scrolling is flagged as
repeated_targetless_action_type. Only for
flagged cases does the local model then confirm
whether the trajectory is genuinely stuck in a loop.
This confines the model’s harder judgment to the
rare cases where it is needed, while leaving the
initial action untouched otherwise. Further details
and sensitivity analysis are in Appendix A.1 and
Appendix B.2, respectively.
Recovery candidate generation.
Simply re-
questing a single new action from the same context
after a loop is confirmed often reproduces the same
failed action. Instead, once a loop is confirmed, the
local agent samples a small set of executable can-
didates (a hyperparameter set to four in our main
experiments) from the current environment state,
leveraging its demonstrated ability to produce di-
verse actions under repeated sampling. These can-
4


didates may include both repeated and alternative
actions, and are passed to the filtering stage.
Filtering and selection.
Before the agent selects
among candidates, CANDID first narrows the pool
to reduce selection overhead: malformed or non-
executable actions are removed, DONE is disallowed
during loop recovery, candidates matching the de-
tected loop pattern are excluded, and duplicates are
merged. If no valid candidate remains, CANDID
falls back to the original proposal; if exactly one re-
mains, it is executed directly; otherwise, the agent
selects among the filtered candidates based on the
task instruction and recent trajectory.
3.2
Unanimous DONE Gating
Local CUAs frequently misjudge task completion,
often terminating prematurely (Section 2.2), moti-
vating a conservative approach to accepting DONE.
Fig. 4(b) illustrates CANDID’s unanimous DONE
gating module, which is triggered only when the
agent proposes DONE. Rather than accepting a sin-
gle termination prediction, CANDID samples ad-
ditional candidates from the same context and ac-
cepts DONE only when all valid candidates agree
(Case 1); even a single continuation candidate, such
as WAIT or click, is treated as evidence that the
task may still be unfinished, in which case termina-
tion is rejected and all DONE candidates are removed
(Case 2). This conservative policy uses the agent’s
own candidate diversity to challenge unsupported
DONE decisions without relying on an external veri-
fier. We further show in Section 4.3 that this unani-
mous policy more effectively suppresses premature
completions than a majority voting.
Candidate selection.
Once DONE candidates are
removed, the remaining continuation candidates
are processed for execution. In Case 2, for ex-
ample, the sampled set contains DONE, WAIT, and
click; after filtering, only WAIT and click remain
as continuation candidates, and exact duplicates
are merged. If a single continuation candidate re-
mains, it is executed directly; otherwise, the local
agent selects one from the remaining continuation
candidates based on the task instruction, current
screenshot, and recent trajectory. The selector is
restricted to choosing among the generated candi-
dates and cannot introduce a new action.

Candidate sampling configuration.
For both

Inference-Time Control Baselines.
We com-
pare CANDID against several inference-time con-
trol baselines. For test-time scaling, we apply GTA-
1 (Yang et al., 2025), using the local CUAs as
the planner while retaining the original GTA-1-7B
grounding model and sampling four plans. We fol-
low the publicly released GTA-1 implementation,
including its available prompting and inference
procedure, without modifying the disclosed com-
ponents other than replacing the planner with the
evaluated local CUA. We also implement step-wise
Self-Guidance, which generates compact progress
feedback after each step and appends it to the next
action-generation prompt. Finally, we implement
VLAA-GUI-style (Han et al., 2026) Loop Breaker
and Verifier modules by adapting their core inter-
vention concepts for local CUA evaluation, rather
than reproducing the full multi-agent architecture.

Complementary effects of control modules.

distinct failure modes. Loop-only substantially re-

only suppresses premature false success at the cost
of increased execution exhaustion. Combining both
modules mitigates this trade-off and achieves the
highest average score of 38.8%, demonstrating that
loop recovery and conservative termination control
are most effective when applied jointly.

Related Work
Models and Frameworks.
Recent progress in
multimodal GUI agents has been driven by real-
istic computer-use benchmarks (Xie et al., 2024;
Deng et al., 2023; Rawles et al., 2025) and CUA-
specialized models that improve GUI ground-
ing, action prediction, and long-horizon interac-
tion (Wang et al., 2025; Qin et al., 2025; Xue et al.,
2026; Lin et al., 2024; Xu et al., 2025). Agen-
tic frameworks further improve reliability through
multi-agent coordination (Song et al., 2026; Yang
et al., 2026), hierarchical planning (Agashe et al.,
2025), and test-time scaling (Yang et al., 2025;
Gonzalez-Pumariega et al., 2026). However, these
approaches often rely on proprietary models or sub-
stantial inference-time computation, leaving effi-
cient execution control for local CUAs compara-
tively underexplored.
Inference-Time
Exploration
and
Selection.
Reasoning-oriented LLM studies use parallel
inference-time scaling through candidate sampling
and branching search (Wang et al., 2023; Yao et al.,
2023; Zhu et al., 2025; Lee et al., 2026), and re-
lated CUA frameworks adopt trajectory reranking
or parallel exploration (Yang et al., 2025; Gonzalez-
Pumariega et al., 2026). While related in spirit, our
approach applies candidate diversification only at
failure-prone points to recover in local CUAs.
Execution Reliability and Recovery.
Agent reli-
ability has been enhanced via feedback, reflection,
and trajectory refinement (Madaan et al., 2023;
Shinn et al., 2023; Lin et al., 2026; Han et al., 2026).
While VLAA-GUI improves automation using ver-
ifier and loop-breaker (Han et al., 2026), it de-
pends on proprietary models (Anthropic, 2026a,b;
Google, 2026; Singh et al., 2026) and multi-agent
systems. Conversely, CANDID improves reliabil-
ity using only the local agent’s own action candi-
dates, without auxiliary agents or verifiers.
6
Conclusion
We
presented
CANDID,
a
candidate-based
execution-control framework for local computer-
use agents that addresses two coupled failure
modes:
repetitive action loops and premature
DONE decisions, both of which persist under naive
execution scaling and textual feedback. By lever-
aging alternative actions generated by the local
agent and intervening only at failure-prone de-
cision points, CANDID recovers from repetitive
behavior and challenges unsupported termination.
Experiments on OSWorld demonstrate consistent
improvements across multiple local CUAs over
feedback-based alternatives, with minimal execu-
tion overhead. These results suggest that selectively
allocating inference-time computation to high-risk
execution states can be more effective than uni-
formly scaling computation throughout the trajec-
tory.

Limitations
Our framework focuses on lightweight execution-
time control for local computer-use agents and is
evaluated primarily on OSWorld desktop environ-
ments. While the proposed mechanisms consis-
tently improve robustness across multiple local
CUAs, the current study does not explore broader
settings such as mobile environments, large-scale
cloud agents, or long-horizon multi-agent orches-
tration. CANDID also depends on the base agent
producing sufficiently diverse and useful candi-
dates; when sampled candidates collapse to the
same failed behavior, candidate-based recovery pro-
vides limited benefit. Moreover, the current loop
detector targets relatively local repetitive patterns
and may miss longer-range or irregular failure cy-
cles. Our candidate selection strategy relies on
lightweight heuristic filtering and local reranking,
and we do not yet integrate CANDID with higher-
level planning or memory modules. Extending the
framework with adaptive triggering, stronger veri-
fication, and higher-level agentic signals remains
an important direction for future work.

CANDID Implementation
A.1
Loop Detection Details
This section details the loop detection procedure
used by the loop-recovery module in Section 3.1.
The implementation follows a two-stage detection.
First, a deterministic rule detector checks whether
the newly proposed action would extend a recent
repetitive pattern. Second, the local model con-
firms that the trajectory is stagnant before recovery
candidates are generated.
Action signatures.
For each proposed action, the
detector constructs a coarse signature consisting
of an action type, an optional target coordinate,
and a normalized action string. Action types are
extracted from parsed PyAutoGUI calls when avail-
able: click-like calls are mapped to click vari-
ants, typewrite/write to type, hotkey/press
to key, scroll/hscroll to scroll, moveTo to
mouse_move, and dragTo to drag. If the parsed
code is unavailable, the detector falls back to coarse
markers in the natural language action string. Tar-
get coordinates are extracted from the first (x, y)
pair when present.
Rule-based trigger.
Let at be the action pro-
posed for the current step. If the parsed action
is empty or is a termination action, loop recov-
ery is not triggered. Otherwise, the detector com-
pares at against the last w executed actions, where
w = loop_recovery_window. The detector re-
quires at least r −1 historical actions before testing
repetition, because the current proposal itself sup-
plies the r-th repeated item. The concrete trigger
conditions are listed in Table 8.
For cyclic patterns, the detector uses a slightly
longer window, max(w, 8), appends the current
proposal, and converts each action into a compact
sequence item. Coordinate-based actions are buck-
eted by the target tolerance τ; type and key actions
retain their normalized full action string; all other
actions use only the coarse action type. The detec-
tor then checks whether the sequence suffix repeats
with a pattern length from 2 to 4. This catches cases
such as alternating between two nearby clicks or
repeatedly cycling through scroll and click opera-
tions.
Model confirmation gate.
The rule detector is
intentionally high-recall: it identifies points where
repetition is plausible, but it does not independently
decide that the trajectory is unproductive. A model
confirmation call therefore follows a positive rule
trigger. The confirmation prompt contains the task,
current screenshot, recent trajectory, and the cur-
rent proposed action, and asks the same local model
to return a JSON object with progress_signal,
loop_detected, loop_evidence, strategy_signal,
avoid_actions, and escape_direction. Recovery pro-
ceeds only when either loop_detected=true or
strategy_signal=SWITCH. Otherwise, the origi-
nal action is left unchanged and candidate genera-
tion is skipped.
Candidate blocking after detection.
The de-
tected rule also defines what recovery candidates
are forbidden to repeat. Malformed candidates are
removed, and DONE termination is disallowed dur-
ing loop recovery. If a candidate has a different
action type from the blocked action type, it re-
mains eligible. If it has the same action type, it
is blocked when it lacks a distinguishable target or
when its target lies within the same tolerance τ of
the blocked target. This ensures that recovery does
not simply reselect the same local operation under
a different surface form.

B.3.2
Termination-Gate Evaluation
We further compare Unanimous DONE Gating
with the VLAA-GUI-style Verifier as termination
gates. In this analysis, TP denotes an accepted
DONE decision followed by task success, FP denotes
an accepted DONE decision followed by task failure,
TN denotes a rejected DONE decision followed by
task failure, and FN denotes a rejected DONE de-
cision followed by task success. Table 12 reports
the corresponding decision counts, and Table 13
presents the derived precision, recall, specificity,
and accuracy.
Both methods achieve high recall, indicating that
tasks that ultimately succeed are rarely prevented
from terminating.
However, precision remains
modest for both gates, meaning that a substantial
fraction of accepted DONE decisions still occur in
trajectories that fail according to the OSWorld eval-
uator. This limitation reflects the difficulty of in-
ferring semantic task completion from the local
model’s own observations and predictions.
The main difference appears in specificity. Unan-
imous DONE Gating achieves higher specificity
than the VLAA-GUI Verifier (26.3% vs. 15.2%),
indicating that it rejects a larger fraction of pre-
mature termination proposals. This improvement
also leads to higher task-level decision accuracy
(62.5% vs. 56.8%). Overall, these results suggest
that the unanimous policy provides a more effective
sampling-based check against unsupported termi-
nation than textual verification.
B.4
Generalization to WindowsAgentArena
We further evaluate CANDID on 154 Win-
dowsAgentArena tasks to assess cross-benchmark
generalization. As shown in Table 14, CANDID
improves overall task accuracy from 21.47% to
24.71% for Qwen3-VL-30B-A3B and from 10.39%
to 11.69% for Qwen3-VL-8B. For Qwen3-VL-30B-
A3B, the largest gains occur in Windows System
and Media & Video, although performance varies
across domains. As the results are based on a sin-
gle run, they provide preliminary evidence of cross-
benchmark generalization.

This section describes three feedback-style base-
lines implemented for the comparison.
Self-
Guidance is our own lightweight prompt-based
intervention. The Loop Breaker and Verifier are
VLAA-GUI-style implementations: they are in-
spired by the STOP and RECOVER components
described in VLAA-GUI, but they are adapted to
our PyAutoGUI action space and local-model set-
ting rather than reproduced exactly.
C.1
Self-Guidance
Self-Guidance runs a separate diagnostic prompt
before normal action generation and injects the
resulting text into the next action prompt as
Guidance. The guidance model discusses progress,
local loops, what to avoid, the next direction, and
whether task completion looks unsafe.
Prompt skeleton.
The system prompt asks the
model to diagnose the desktop trajectory:
System Prompt
You are diagnosing progress in a desktop-computer task.

free-form guidance for the next action. Be concrete.
Mention if the agent appears stuck in a local loop.
Mention what should not be repeated. Mention whether
task completion looks unsafe and should be avoided. Do
not output tool calls, XML tags, code, or executable UI
actions.
The user message contains the task instruction, re-

Requested Output Format
- progress so far
- suspected issue
- avoid repeating
- next direction
- completion note
Output use.

<free-form guidance text>

C.2
VLAA-GUI-Style Loop Breaker
The VLAA-GUI-style Loop Breaker is a reflection
module that runs before action generation when
previous responses exist. It follows the RECOVER
idea from VLAA-GUI: inspect recent trajectory
evidence, decide whether the agent is stuck in
repetitive no-progress behavior, and emit a strategy-
change signal. In our implementation, the module
does not directly choose an action. Instead, when
it returns a loop signal, it writes a textual loop-
recovery constraint into the next action prompt.
Prompt skeleton.
The system prompt is:
System Prompt
You are a reflection agent for a desktop automation task.
Analyze the recent trajectory and current screenshot for
repetitive no-progress behavior. Focus only on loop
recovery. Do not judge whether the whole task is
complete. Return only a valid JSON object.
At each step, the user message includes the latest
assistant response, the parsed action, and optionally
the current screenshot. The requested schema is:
Requested Output Schema
{"progress_signal": "what visibly changed, or
no visible progress",
"loop_detected": true/false,
"loop_evidence": "short evidence",
"strategy_signal": "KEEP or SWITCH",
"avoid_actions": ["short action/target
patterns to avoid"],
"escape_direction": "short direction for
changing approach"}
Output
use.
If
loop_detected=true
or
strategy_signal=SWITCH, the module formats
the result into a constraint block:
Control Block Appended to the User Prompt
Loop recovery constraint:
- strategy_signal: SWITCH
- loop_evidence: <evidence>
- avoid_actions: <patterns>
- escape_direction: <direction>
The next action must change approach and must
not match avoid_actions.
This block is injected into the next action-
generation prompt.
The enforcement mode is
prompt-only: unlike our candidate-based loop re-
covery, the VLAA-GUI-style Loop Breaker does
not sample multiple executable candidates or re-
move repeated actions through a hard filter.
C.3
VLAA-GUI-Style Completion Verifier
The VLAA-GUI-style Verifier is activated only
when the normal action model proposes DONE. It fol-
lows the STOP idea from VLAA-GUI: accept task
termination only when the current screenshot or re-
cent trajectory provides direct evidence that every
task requirement is satisfied. Our implementation
is intentionally conservative and rejects ambiguous
completion claims.
Prompt skeleton.
The system prompt is:
System Prompt
You are an extremely strict task completion verifier for
desktop automation. Decide whether the task is already
fully completed right now. Mark completion only if
every requirement has direct, unambiguous evidence in
the current screenshot or recent trajectory text. Do not
assume hidden state or intent. For side effects such as
saving, exporting, sending, creating, deleting, or
changing settings, require visible or trajectory evidence
that the side effect was committed. Prefer false negatives
over false positives. Return only a valid JSON object.
The user message includes the task instruction, re-
cent trajectory text, the candidate final response,
and the parsed termination action. The requested
schema is:
Requested Output Schema
{"complete": true/false,
"reason": "short evidence-based reason",
"missing_steps": "what evidence/action is
still needed, or empty if complete"}
