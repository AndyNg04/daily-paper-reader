ABSTRACT
As catalogs of models, tools, and reusable skills expand, determining which re-
sources an agent should use becomes increasingly challenging. The value of a
resource depends on the backbone and the other resources it is combined with, and
it is known only after execution. Existing methods address parts of this problem.
Token-based tool generators tie each tool to a learned token, so they select only
from the training catalog. Retrievers and routers score each tool or backbone on its
own and miss complementary resources, and bundle reuse and agent recommen-
dation return configurations built for other tasks. How to compose heterogeneous
resources for a new task remains underexplored. We formulate Task-Conditioned
Agent Resource Composition (AgentComposition): jointly selecting a backbone
model and composing a tool–skill bundle that maximize end-to-end execution
utility. We propose Retrieval-Grounded Bundle-Aware Agent Generation. It re-
trieves candidate resources and past configurations of similar tasks, and a fine-tuned
generator that reads each resource from its description recombines them by con-
strained beam search, so new resources need no retraining. A bundle-aware critic
ranks the complete configurations. It learns from two proxies for real execution, an
LLM teacher and historically successful configurations, and adapts to end-to-end
execution feedback when it is available. We evaluate by reference recovery, offline
execution with judged and native rewards, and online recommendation with real
execution, and we build AgentSelect-Exec with 5,060 executed configurations for
this purpose. Our method recovers the complete reference configuration within ten
candidates for 67.73% of AgentSelect queries, nearly twice the strongest baseline,
and leads all baselines on SkillsBench. The proxy-trained critic already raises the
execution score of the top-ranked agent from 7.58 to 8.37 out of 10, and execution
feedback lifts it to 8.78, above the strongest baselines. Four target-domain queries
suffice to adapt the generator to SkillsBench, and agents recommended online
execute better than those of the strongest baselines under both an LLM judge and
native verifiers. These results establish resource composition as a learnable and
transferable capability, shifting the focus from individual resource relevance to
joint task suitability, toward agents that adapt to changing resource ecosystems and
evolve through accumulated task experience.

INTRODUCTION
Large language models (LLMs) have grown from text completion Radford et al. (2019); Brown et al.
(2020) into agents that reason, call functions, and act in environments Yao et al. (2023); Schick
et al. (2023); Qin et al. (2024b). The Model Context Protocol (MCP) Anthropic (2024) and Agent
Skills Anthropic (2025b); Xu & Yan (2026) expose growing catalogs of tools, data, and reusable
skills, and agent harnesses organize them around a backbone model Microsoft (2026); OpenAI
(2026); Anthropic (2025a). Choosing these resources well makes agents more adaptive Cheng et al.
(2025); Hao et al. (2025), keeps the tool context small Liu et al. (2026), and lets agents keep up with
changing ecosystems Wu et al. (2026b). Each new task therefore raises a practical question: which
backbone and which resources should an agent use together?

Existing work answers parts of this question. Tool learning and tool retrieval select tools for a
fixed backbone Qin et al. (2024a); Hao et al. (2023); Wang et al. (2025); Du et al. (2024); Qu et al.
(2024); Yuan et al. (2024), model routing chooses a backbone without tools Ong et al. (2025), and
AgentSelect recommends predefined configurations Shi et al. (2026). Composing a configuration
for a new task is harder, for four reasons. First, the value of a resource depends on the resources it
is combined with. A seven-day, pet-friendly road trip under a fixed budget needs accommodation
search, pet-policy checks, route planning, and cost calculation. Accommodation tools alone leave
needs unmet, and a past road-trip configuration may miss the pet constraint. Selecting resources
one by one misses such bundle effects (Appendix N). Second, the number of configurations grows
combinatorially with the catalog. Third, the catalog keeps changing, so methods tied to a fixed set of
resources must be retrained. Fourth, a configuration’s quality is known only after a costly execution.
We formulate Task-Conditioned Agent Resource Composition (AgentComposition): given a
task and its context, select a backbone and compose a tool–skill bundle that maximize end-to-end
execution utility. Agent architecture search such as AgentSquare Shang et al. (2025) optimizes how
an agent plans, reasons, and remembers. AgentComposition chooses the resources an agent uses. We
propose Retrieval-Grounded Bundle-Aware Agent Generation, whose components address these
challenges. Retrieval narrows the search to relevant resources and supplies past configurations of
similar tasks. A fine-tuned generator composes configurations by constrained beam search, choosing
each tool given the backbone and the tools already chosen. It reads each resource from its description,
so a new resource is usable as soon as it is indexed. A bundle-level critic estimates execution
quality from proxy signals, adapts to execution feedback when available, and reranks the completed
configurations.
We evaluate on AgentSelect Shi et al. (2026) and SkillsBench Li et al. (2026) and on three datasets
with execution outcomes: BFCL Patil et al. (2025), SWE-Skills-Bench Han et al. (2026), and
AgentSelect-Exec, which we build from 5,060 executed configurations. Four findings emerge. (i) Our
method recovers complete configurations best, while historical bundles, tool retrievers and model
routers, token-based tool generators, bundle generators, and retrieval-augmented LLMs each fall
short in ways their designs predict. (ii) Execution feedback makes the critic’s rankings agree with
execution. The critic then selects better-executing configurations than all proxy-trained variants and
the strongest baselines, and it works best as a final reranker. (iii) The learned composition transfers
to new domains. Four target queries are enough to adapt the generator to SkillsBench, and Stage 3
adapts the critic when executed candidates are available. (iv) Agents recommended online execute
better than those of the strongest baselines, under both an LLM judge and native verifiers, and within
our lists, higher-ranked recommendations execute better.
Our contributions are as follows. ❶We formulate AgentComposition, which composes a backbone
and a tool–skill bundle for each task to maximize execution utility, and we identify its bundle-level
challenges. ❷We propose a retrieval-grounded, bundle-aware framework that composes valid
configurations from a changing catalog and ranks them with a critic that adapts to execution feedback.
❸We build AgentSelect-Exec and evaluate by reference recovery, offline execution, transfer to new
domains, and online execution1.

RELATED WORK
Agent Construction and Resource Composition. Agent construction decides what an agent can
do and how it does it. AgentSquare searches over planning, reasoning, tool-use, and memory
modules Shang et al. (2025). ADAS repeatedly writes and tests agent programs Hu et al. (2025b).
SkillWeaver discovers and refines reusable skill APIs Zheng et al. (2025), and PSEC combines
skill-specific LoRA modules in parameter space Liu et al. (2025). These methods change the agent’s
design or build new capabilities. We compose existing catalog resources for a task, choosing a
backbone and a tool–skill bundle together. Model routing chooses between a strong and a weak LLM
without tools Ong et al. (2025).
Agent Resource Retrieval and Selection. Existing retrieval typically ranks individual resources by
their relevance to a query Shi et al. (2025); Moon et al. (2024). PORTS aligns a dense tool retriever
with LLM preferences over tool selection Molfetta et al. (2025), and AnyTool collects APIs for a

fixed LLM through hierarchical LLM agents Du et al. (2024). Scoring tools one at a time finds useful
tools but ignores how they work together, so the top-ranked tools form bundles with many extra tools.
Generative methods such as ToolkenGPT, ToolGen, and ToolWeaver let a fixed backbone select tools
by generating them Hao et al. (2023); Wang et al. (2025); Fang et al. (2026). ToolWeaver encodes

skips the current call Yakovlev et al. (2024). It improves individual tool calls during generation. Our
method treats resource selection as composition. It selects a backbone and a bundle together and
generates configurations from retrieved resources and their descriptions, so a new resource can be
used as soon as it is indexed.
Bundle Recommendation and Agent Discovery. Bundle recommendation ranks existing bundles
or constructs new ones Sun et al. (2026). BGCN models user–item, user–bundle, and bundle–item
interactions through graph convolutions Chang et al. (2020). CrossCBR aligns item- and bundle-level
representations Ma et al. (2022). Construction methods include query-conditioned Text2Bundle Hu
et al. (2025a), LLM-based adaptive in-context learning Sun et al. (2024), and discrete-diffusion
generation of unordered bundles Tu et al. (2026). In agent discovery, AgentSearchBench and
AgentSelect retrieve or rank predefined agents or configurations from an existing catalog Wu et al.
(2026a); Shi et al. (2026). We treat agent resources as parts of a bundle and generate a new
configuration for each task.

Method overview. Our framework has three steps (Figure 1). Retrieval finds task-relevant resources
and the past configurations of similar tasks. A fine-tuned generator then recombines these resources
into candidate configurations through constrained beam search. Finally, a bundle-aware critic ranks
the completed configurations. The critic stands in for execution. It learns from proxy signals and can
adapt to execution feedback when it is available. Algorithm 1 in Appendix C gives the procedure.

retrieved tools, and evidence, which includes resource profiles, normalized scores, provenance, and
complete historical bundles when available. Semantic retrieval is the default, and a collaborative-
signal retriever is added when query–agent interaction histories exist (Appendix B).

3.4
BUNDLE-AWARE CONSTRAINED GENERATION
Search composes a configuration step by step over the retrieved resources. It selects a backbone first
and then adds one tool at a time, so each tool is chosen given the backbone and the tools already in
the bundle. Two quantities control the search. The proposal budget P is the maximum number of
proposals kept at each expansion, and the pruning width W(η) is the number of paths kept from η
candidates (Eq. (6)).
Constrained decoding. Each hypothesis h holds a backbone Mh ∈Mr(Q), a prefix ρh = ⟨Mh,
τsep, t1, . . . , tℓ⟩, and a tool set Bh. A legal action adds an unused tool from Tr(Q) \ Bh or terminates
the bundle with τend, or with τ∅, τend for an empty bundle. A path also ends when |Bh| = Lmax.
Prefix tries over the identifiers restrict decoding to legal actions, so every output is a valid configuration
of retrieved resources.

EXPERIMENTS
4.1
DATASETS
AgentSelect Shi et al. (2026) pairs queries with agent configurations over 231 LLMs and 12,099
tools. SkillsBench Li et al. (2026) runs agents with and without skills on tasks checked by hidden
tests. From its successful runs, we build queries over 19 LLMs, 155 skills, and 20 tools and split them
by task. We use it as a new resource domain (Section 5.2). Three further datasets record the execution
outcome of each configuration. AgentSelect-Exec executes the ten top-ranked configurations of each
AgentSelect query and scores each run with an LLM judge. We use it for Stage 3 training and the
execution analysis (Section 5.1). BFCL Patil et al. (2025) and SWE-Skills-Bench Han et al. (2026)
provide native rewards for transfer to new domains (Section 5.2). Table 1 summarizes the splits, and
Appendix D.1 details their construction.
4.2
IMPLEMENTATION DETAILS
The generator is Meta-Llama-3-8B fine-tuned with LoRA on AgentSelect. The critic starts from
AgentEmbedding Chen et al. (2026), is trained by Stages 1 and 2 on AgentSelect, and is adapted by
Stage 3 on the AgentSelect-Exec training split. Search uses adaptive beam bounds (bmin, bmax) =
(1, 2), retain ratio rkeep = 0.4, proposal budget P = 5, Lmax = 6, and K = 10. The critic reranks
completed configurations without guiding search. Appendix D.2 gives all training and search settings,
and Appendix K reports the parameter grid.
4.3
BASELINES
We compare five baseline families (Appendix H). (i) Retrieval-based composition pairs a retrieved
LLM with independently retrieved tools (Component-Ret) or with a historical bundle (Bundle-Ret).
(ii) Tool retrieval and model routing covers PORTS Molfetta et al. (2025) (a tool retriever aligned
with LLM preferences), AnyTool Du et al. (2024) (API retrieval by hierarchical LLM agents), and
RouteLLM Ong et al. (2025) (routing queries between LLMs). (iii) Token-based tool generation
covers ToolGen Wang et al. (2025) and ToolWeaver Fang et al. (2026), which generate learned tool
tokens or codes. (iv) Bundle generation adapts sequential Text2Bundle Hu et al. (2025a) and discrete-
diffusion DDBC-Adapt Tu et al. (2026). (v) Retrieval-augmented LLMs generate configurations
from the same retrieved evidence as ours, using RAG-Llama, GPT-5.6-Sol/Terra/Luna, DeepSeek-
V4-Pro, Qwen3.8-27B, and Kimi-K2.6. Families (ii) and (iii) select either tools or a backbone, so we
complete each configuration with the other module of Component-Ret (Appendix H.4).
4.4
EVALUATION METRICS
Each method returns 10 configurations, and metrics are averaged over queries on a 0–100 scale. Our
primary metric, Rank-Discounted Component Recall (RDCR@10), discounts component recall by
rank, rewarding partial recovery near the top. RDCP@10 similarly discounts component precision
and penalizes components absent from the matched reference. ToolR@1 is the share of required
tools covered at rank 1, and CompR@1 also counts the reference LLM. Tool-Hit@10 asks whether
any candidate covers all required tools. CR-Hit@1, CR-Hit@10, and CR-MRR@10 additionally
require the reference LLM, with MRR rewarding earlier first hits. Appendix I defines all metrics, and
Table 2 reports them.

4.5
OVERALL RECOMMENDATION PERFORMANCE
This section tests whether composing a configuration as a whole recovers complete configurations
better than reusing, retrieving, or generating resources one at a time. Table 2 shows that it does. The
two variants of ours rank first and second in RDCR@10 and RDCP@10, and each baseline family
falls short in ways its design predicts.
Historical bundles hold the right resources, but not the right configuration. Bundle-Ret reaches
the highest Tool-Hit@10 (97.62%), so the bundles of similar past queries contain most required tools.
Reused as they are, they rarely match the whole configuration of a new task (12.40% CR-Hit@10),
so we recompose the retrieved resources.
Selecting resources one by one does not compose them. Retrievers and routers score each com-
ponent on its own. PORTS finds relevant tools but adds many that the task does not need (26.01%
RDCP@10), and token-based generators such as ToolGen and ToolWeaver, which tie each tool to
a learned token, recover even less. RAG-LLMs read the same evidence as ours and select relevant
resources, with high ToolR@1 and CompR@1, but they rarely recover the backbone and all tools
together (at most 36.73% CR-Hit@10).
Bundle generators fix the backbone or the vocabulary. Text2Bundle builds a bundle for a fixed
CF-selected LLM and rarely recovers the whole configuration (3.82% CR-Hit@10). DDBC-Adapt
generates the backbone and the tools together from the components of its training vocabulary and
reaches 32.43%, about half of ours.
Joint composition recovers complete configurations. Our generator chooses each tool given the
backbone and the tools already chosen. It recovers the complete configuration within ten candidates
on 67.73% of queries, nearly twice the best baseline. Constrained decoding keeps every output valid,
whereas 3% of free outputs name unknown components (Appendix L).
Reference recovery does not measure execution. Critic reranking slightly lowers recovery, e.g.,
RDCP@10 from 65.28% to 62.71%. The critic estimates execution quality, and a configuration
that departs from the reference can still execute well. Section 5.1 therefore evaluates rankings by
execution.

FURTHER ANALYSIS
5.1
FROM REFERENCE CONFIGURATIONS TO EXECUTION SIGNALS
Our critic is meant to estimate execution quality, which reference recovery does not capture. On
AgentSelect-Exec, we ask which supervision lets the critic predict execution quality, where in the
pipeline it should act, and whether its full ranking agrees with execution. Execution feedback (Stage 3)
lets the critic pick the best-executing configurations and order the rest as execution does, and the
critic works best as a final reranker.
Figure 2a–b compares six rankers on the 200 test queries. A ranks candidates by generator scores (G).
B, C, and D rerank them with critics trained on Stage 1, Stage 2, and both stages. E adds Stage 3, and
F also applies the Stage 3 critic during beam search. A–E rerank the same ten executed configurations
per query (Appendix F), and F ranks the pool of its own search.
Each signal brings the critic closer to execution. Both proxy signals improve the top choice over
generator scores, and together they help more (D, 8.37 versus 7.58 for A). Execution feedback helps
most. E reaches 8.78 and cuts the share of queries scoring below 5 from 15.5% to 3.5%. Reference
recovery stays flat across A–E (60.7%–61.3% RDCR@10), so it misses these gains. Even the
proxy-trained critic D selects better configurations than Bundle-Ret (7.36) and RAG-Qwen3.8-27B
(7.99).
The critic belongs at the end of search. Guiding beam search with the Stage 3 critic (F) lowers the
top choice to 8.57. The critic is trained on complete configurations, so it misjudges partial ones and
prunes good branches early. We therefore apply it only after search.

The adapted critic orders all candidates as execution does. Beyond the top choice (Figure 2c–e),
execution quality falls steadily with the Stage 3 critic’s rank, from 8.73 at rank 1 to 4.03 at rank 10,
so configurations that fail in execution sink to the bottom. The Stage 1+2 critic and the generator
spread such failures across their lists. Within queries, the Stage 3 critic orders 68.0% of configuration
pairs correctly, against 55.8% for the Stage 1+2 critic and 43.1% for the generator. On pairs whose
execution scores differ by at least 6 points, it is correct 90.2% of the time (Figure 2e).

5.3
ONLINE RECOMMENDATION AND EXECUTION
Beyond reranking recorded executions, we ask whether the agents our pipeline recommends online
also execute better. We run the full pipeline on held-out queries and score each executed recommen-
dation with an LLM judge and, on SkillsBench, with native verifiers (Appendix M). On SkillsBench,
our recommendations execute better than those of RAG-Qwen3.8-27B under both the native verifier
and the LLM judge (Figure 4a–b). They also pass more verifiers when every method runs on the
same fixed backbone, so the gain comes from the selected skills. On AgentSelect, every rank of
our top-10 lists executes better than the top-1 agents of both baselines (Figure 4c). Within the lists,
higher ranks execute better. The score falls from 8.67 at ranks 1–3 to 8.45 at ranks 8–10, and ranks
1–3 outscore ranks 8–10 on 15 of 25 queries and trail on 6 (Figure 4c–d). Appendix M.4 also ranks
official SkillsBench runs offline.
6
CONCLUSION AND FUTURE WORK
We formulate AgentComposition, which composes a backbone and a tool–skill bundle for each task to
maximize execution utility, and propose a retrieval-grounded, bundle-aware framework for it. Across
reference recovery, offline execution, new domains, and online execution, composing a configuration
as a whole outperforms selecting resources one by one, and a critic adapted to execution feedback
ranks configurations as execution does. Because the generator reads resources from their descriptions,
the learned composition transfers to new domains with a few target queries. Our method is limited by
retrieval recall, and its critic relies on proxy signals when no execution feedback is available. Future
work will use the adapted critic as a reinforcement-learning reward for the generator.

BASELINE ADAPTATIONS AND OUTPUT PROTOCOLS
H.1
RETRIEVAL-BASED COMPOSITION
Component-Ret. We independently retrieve LLMs via CF and tools via semantic retrieval. The
top-10 LLMs are paired with the same six highest-ranked tools, forming ten configurations ranked by
LLM CF score.
Bundle-Ret. Separate CF models retrieve one top-ranked LLM and ten historical tool bundles. Each
intact bundle is paired with that LLM and ranked by bundle CF score.

H.2
TEXT2BUNDLE
We adapt Text2Bundle Hu et al. (2025a) by mapping items to tools and using the query as the
request. We omit user-ID embeddings and personalization rewards. Queries and tool descriptions
use AgentEmbedding Chen et al. (2026), an EasyRec Ren & Huang (2025) model tuned for agent-
resource retrieval. We retain the Transformer state encoder, action-relation modeling, and learned
termination action.
Pairwise bundle-completion pretraining precedes Double-DQN training with experience replay. The
action pool deduplicates tools from retrieved historical bundles and semantic retrieval. Missing target
tools are added to the pool during training, and validation and inference use the retrieved candidates.
The CF-selected LLM stays fixed while beam search extends the single-output policy to Top-K
tool sets. Paths are ranked by negative cumulative action regret: each increment is the chosen
action’s Q-value minus the highest valid-action Q-value. The greedy path scores zero and comes first.
Duplicate tool sets keep their best path, and a size cap ends search.
H.3
DDBC-ADAPT
We adapt DDBC Tu et al. (2026), which uses masked discrete diffusion and residual quantization.
DDBC-Adapt operates over a component vocabulary built from the training split. Frozen MPNet
embeddings of LLM and tool descriptions, PCA, and residual k-means replace its representation
learner and quantizer. An extra code separates components with identical quantized codes.
A query-conditioned denoiser jointly generates one LLM and a tool set with typed boundaries.
Training masks component codes, preserves structural tokens, and randomizes tool order. Decoding
retains absorbing masks, enforces code compatibility, and excludes duplicate tools, so it can generate
new combinations of the components in its training vocabulary.
Task-trained semantic adapters estimate query–component relevance over the training vocabulary.
Relevance probabilities are summed over legal components sharing each code value, and the resulting
log masses augment denoiser logits. Distinct valid configurations are ranked by LLM and summed
tool relevance, weighted by the predicted probability of their tool count.
H.4
ADAPTED TOOL RETRIEVAL AND LLM ROUTING
ToolGen Wang et al. (2025), ToolWeaver Fang et al. (2026), PORTS Molfetta et al. (2025), Any-
Tool Du et al. (2024), and RouteLLM Ong et al. (2025) each address one part of agent resource use
and do not output a complete configuration. ToolGen selects the next tool for a fixed backbone within
its agent loop, ToolWeaver generates tools as hierarchical code sequences that capture tool co-usage,
PORTS aligns a dense tool retriever with LLM preferences over tool selection, AnyTool collects
individual APIs through hierarchical LLM agents, and RouteLLM routes a query between a strong
and a weak LLM without tools. We adapt each method to produce configurations while keeping its
core mechanism, and pair its output with the remaining module of Component-Ret.
ToolGen. Following ToolGen, we first train tool-token memorization on 47,800 document-to-token
examples, one per tool in our catalog. We then fine-tune the model to generate the complete tool
sequence of each training configuration. Beam search produces candidate tool sets, each paired with
the CF backbone ranking, and the fusion weight of tool and backbone scores is selected on 616
validation queries.
ToolWeaver. We encode each tool document with a frozen MPNet encoder and quantize it with
a residual-quantized autoencoder into two code levels of 1,024 entries each. A graph term in the
quantizer pulls together tools that co-occur in training configurations, so co-usage shapes the codes,
and every catalog tool keeps a unique two-token code. The language model starts from the ToolGen
memorization checkpoint, and each new code token is initialized from the memorized tokens of the
tools it covers. With LoRA, we first align queries with the codes of single tools from the training
configurations and then fine-tune the model to generate the codes of complete training bundles.
Beam search over valid codes produces bundles of one to six tools, which are combined with the CF
backbone ranking as in ToolGen, with weights selected on validation queries.

Preprint
PORTS. We split each training configuration into query–tool positives, and a frozen Meta-Llama-3-
8B scores the identifier of the positive tool when conditioned on each candidate tool document. A
BGE-base encoder, shared by queries and tool documents, learns to match this preference distribution
over the positive and three hard negatives, together with an odds-ratio preference term that ranks
the positive above each negative. Hard negatives are the encoder’s nearest non-positive tools and
are refreshed during training. At test time, the top two retrieved tools form the bundle, and its size
and the checkpoint are selected by tool F1 on validation queries. The bundle is paired with the CF
backbone ranking.
AnyTool. We keep AnyTool’s category–service–API navigation and solvability check, use the
collected APIs as the tool set, and pair it with the CF backbone ranking.
RouteLLM. We replace the backbone ranking of Component-Ret with RouteLLM’s matrix-
factorization (MF) router, trained on backbone positives with TF-IDF query features, and keep
the six semantically retrieved tools.

positive weights, RDCR@10 varies by at most 1.1 points per beam setting, and at (1, 2) it spans

on par with αc = 0.5. Generator scores therefore add little once the critic ranks the candidates, and
our final ranking uses the critic alone (Section 3.4).

M.2
EXECUTION AND SCORING
Of the 66 APIs, 11 call public services or a local adapter, and the other 55 are simulated by GPT-5.6-
Luna following MirrorAPI Guo et al. (2025). The simulator sees the endpoint description, schema,
and arguments, and is blind to the recommendation rank, score, and backbone. Each configuration
runs at temperature zero within the budgets of Table 11.
On SkillsBench, the selected skills are mounted in network-isolated containers, and the original
hidden tests check the exported artifacts. On AgentSelect, the selected skills are given to the backbone
as textual instructions.
GPT-5.6-Terra judges each run from the user request, the outputs, the tool observations, and any
verifier results, blind to the rank, scores, and backbone. It assigns 0–4 points for task completion, 0–4
for correctness, and 0–2 for constraint satisfaction.

Figure 8: Bundle effects.
We examine a query from the end-to-end evaluation to illustrate how
tool value depends on its companion resources. The user requests a
domain-similarity check, NS records, and a nameserver IP. We fix
DeepSeek-V4-Pro and the similarity tool S, then vary DNS Lookup
D and NS Lookup N. Tool contributions depend on the bundle.
The raw critic scores for S, S+D, S+N, and S+D+N are −5.56,
0.11, 1.42, and 3.14 (Figure 8). Adding D to S yields a 5.67 gain, but
only 1.72 when N is already present, indicating diminishing returns
from overlapping lookup capabilities. An additive extrapolation
would predict 7.09 for the full bundle rather than the observed 3.14,
showing a clear non-additive interaction. Critic ranking agrees
with execution quality. The end-to-end judge scores of S, S+D,
S+N, and S+D+N are 6.5, 9, 10, and 9.5. The critic ranks the two
bundles with N first and S alone last, as execution does. The three-tool agent does not call N, and
S+N achieves the best execution with fewer tools. This case illustrates both context-dependent tool
value and the agreement between the critic’s ranking and observed execution quality.
