GUARD: Stabilizing Recursive
Self-Improvement with Regret Guidance
Minghe Zhang1,*, Xuetao Kang1,*, Yifei Ming1, Yanfei Chen1, Han Yu1, Yufan Zhuang1 and Chen-Yu Lee1
1Google Cloud, *Equal contribution
Autonomous AI agents pair a frozen base model with an editable harness of prompts, skills, tool rules, and
memory. Recursive self-improvement (RSI) adapts this harness from experience without weight updates,
yet self-editing without external graders often backfires: reflection and scalar scores conflate what an
edit newly broke with what remains unsolved, causing local regressions, skill forgetting, and memory
bloat. We introduce GUARD (Grader-free Unsupervised Environment Design [UED] with Adaptive Rule
Distillation), a closed-loop framework for reference-free continual harness evolution. Our key insight is
to decompose each task into pre-execution self-checks and guide harness updates via directional regret.
Each round grades trajectories against these checks, pinning mastered rules while prioritizing newly
broken behaviors, and selects among parallel candidate edits by critic-free group-relative fitness. A
Soft-HURT gate then promotes an edit only when gains outweigh regressions, scoping specialized fixes
to prevent over-triggering and guaranteeing non-regression on its gated buffer. At test time, one frozen
harness runs in a single pass. Across benchmarks on memory, skill evolution, continual task streams,
and domain reasoning, GUARD consistently improves performance without catastrophic forgetting or
memory pollution while substantially cutting deployment token usage.
1. Introduction
Modern language model agents combine a frozen
base model with a surrounding harness of
prompts, reusable skills, tool interfaces, memory,
and control logic [31, 42, 20, 45]. In practice, this
harness decides whether the same model checks
the right state before acting, calls tools with valid
arguments, recovers from failed commands, and
carries useful rules across sessions [52, 40]. Much
recent progress in deployed agents comes from
harness engineering, yet tuning harnesses by hand
scales poorly: engineers can inspect only a small
slice of failed runs, and fixed designs quickly
go stale as tools, schemas, and user workflows
change [5, 49]. Recursive self-improvement (RSI)
aims to automate this loop by turning past expe-
rience into persistent edits that improve future
runs [54, 38, 44, 26]. Because frontier models of-
ten sit behind black-box APIs with frozen weights
and open-world tasks rarely provide ground-truth
rewards for weight-space reinforcement learning
[60, 62, 13, 46], treating the editable harness
as a non-parametric policy around the frozen
model offers a practical, inspectable way to im-
prove agents after deployment [23, 36].

probe per-task harnesses online while saving

rule written for recent failures breaks tasks that
already worked; catastrophic forgetting, where
shifts in workflow, topic, or domain overwrite
earlier skills [5]; and memory pollution, where
unverified additions accumulate stale or conflict-
ing rules that bloat the prompt. Over multiple
rounds, self-editing can leave an agent worse than
its starting point (Figure 1).
Central Question. How can an autonomous
agent continually improve its persistent har-
ness in a reference-free setting without inter-
fering with or catastrophically forgetting pre-
viously learned skills?
We address this challenge by casting harness
adaptation around a frozen model as gradient-
free policy optimization in text space, guided by
two ideas from reinforcement learning: curricu-
lum regret from unsupervised environment de-
sign (UED) [7, 14, 15, 35] and critic-free group-
relative scoring from Group Relative Policy Opti-
mization (GRPO) [37, 3]. We never update the
model weights or train a value critic: the harness
is the only part of the policy that changes (§2).
We implement this approach in GUARD (Grader-
free UED with Adaptive Rule Distillation; Figure 2,
§4). Before executing a task, GUARD compiles the
task prompt and tool schema into a fixed check-
list of atomic binary checks (§4.1) and grades
completed runs with a two-layer (sandbox execu-
tion plus semantic trace) self-reviewer, because
checking one requirement on a finished trace is
simpler than satisfying every constraint during
generation. Across rounds, Analyze (§4.2) pins

What reference-free does and does not mean.
Throughout this paper, reference-free (and grader-
free) is an operational constraint on the adapta-
tion loop E: neither the solver, the self-reviewer,
nor the distiller ever accesses held-out reference
answers, test cases, hidden verifiers 𝑉★, oracle
skills, or official grading rubrics.
It does not
mean learning from zero supervision. Specifically,
adaptation draws on four observable sources of
structure: (i) benchmark-authored training task
prompt distributions, (ii) public tool declarations
and environment schemas, (iii) the agent’s own
interaction trajectories and observable sandbox
states (with no human expert demonstrations),
and (iv) structured criterion-level judgments from
the language-model self-reviewer (§4.1).

Verbal reflection, memories, and playbooks.
Reflexion [38], ExpeL [59], ReasoningBank

Bench [50], EvoHarnessBench [17], and
Drift Gauntlet [5]. Accepting an update only
when prior behavior does not degrade echoes
regression-free model updates [47] and gradient-
constrained continual learning [21], which rely

7. Conclusion
Continually adapting an agent’s harness around a
frozen backbone model without external graders
requires preventing local overfitting, catastrophic
forgetting, and memory pollution. Drawing on
curriculum regret from UED and group-relative
scoring from reinforcement learning (GRPO),
GUARD (Grader-free UED with Adaptive Rule
Distillation) treats the text harness as a non-
parametric policy component and updates it from
task-derived checklists: Analyze separates edit-
induced regressions (Δhurt) from unresolved gaps
(Δgap) while pinning mastered criteria, Propose
selects among parallel candidate edits via critic-
free group-standardized fitness and contrasts the
best and worst candidates to rewrite proposal
prompts, and Gate (Soft-HURT) promotes only
net-positive updates with formal non-regression
guarantees on the self-review objective (Theo-
rems 1–2, Proposition 1). At test time, it deploys
a single frozen harness in one pass. Across four
benchmark settings, GUARD improves upon or
matches 𝑊0 in held-out accuracy, achieves 19/19
non-regressive execution-gated promotions, and
sustains monotonic pass@1 gains with zero post-
block forgetting under hidden stream drift while
cutting hosted tokens per task by 54.5%.

learnings:
• Trigger scope decides the outcome. The winner attached every rule to a concrete tool call or a literal request
phrase, such as ‘calling create_new_hr_case’ or ‘creating it if necessary’. The loser opened with a broad
‘request names people, groups, services. . . ’ trigger and an unconditional ‘[always, at final response]’ rule.
Those fire on nearly every task and hurt tasks the champion already solved.
• Unconditional end-of-task rules that tell the agent to take more actions are dangerous. ‘If a required write is still
pending, perform it before replying’ can cause spurious or duplicate writes. Final-response guidance should
only interpret results, never trigger new actions.
• Precision in field formats matters. The winner said ‘numeric service id, not the name’ and ‘leave the default
unless the request states a status’. The loser said ‘resolved service id’ and invented a draft-or-work_in_progress
rule with extra synonyms. Vague wording leaves the agent guessing, and invented defaults override correct
behavior.
• Complete the data chain each rule needs. The winner told the agent to resolve each matched profile to a user’s
first and last name before writing, because the write field needs a name. The loser listed the matches but never
said how to get the field value.
• Order conditional lookups explicitly: look up the service first, and fetch topic details only if it is not found.
Ambiguous order invites wasted or duplicate calls.
• Error-recovery wording should be narrow (‘fix only the named field’s format and retry’), not generic.
• Notification rules should name the payload (affected case numbers and outcome) and require that the send call
actually succeeded.
