## Abstract 

LLM agents increasingly perform consequential actions through external tools, yet their proposed actions are often executed without independent verification of policy compliance or task completion. We introduce JevAct , a runtime verifica-tion framework that intercepts selected agent actions before execution and enables feedback-driven correction. JevAct compiles domain policies into executable state checks and structured questions evaluated by a prefill-only decision model, which produces probability-based judgments without relying on LLM generation. By combining deterministic verification of tool-state facts with probabilistic assess-ment of conversational context, the framework identifies potentially invalid ac-tions and premature task termination, providing targeted feedback for bounded revision. JevAct operates independently of the underlying agent model and re-quires no modifications to its parameters or tools. We evaluate JevAct across eleven LLM agents on τ 2-bench Airline and Telecom tasks and BFCL. Results show improvements in agent reliability across multiple models and benchmarks, with particularly consistent gains on Telecom and BFCL, while performance on Airline is more mixed. ## 1 Introduction 

Language-model agents increasingly use tools to change records, make bookings, and guide users through multi-step procedures. A mistaken answer can sometimes be corrected in a later turn; an unauthorized write or a premature hand-off may be harder to undo. Yet many agent loops execute a proposed tool call as soon as the model produces it. This leaves a gap between generating an action and checking that it is appropriate to carry out. ReAct agents interleave reasoning with tool use, while reflection methods such as Self-Refine and Reflexion add critique and feedback to improve later proposals or trials (Yao et al., 2022; Madaan et al., 2023; Shinn et al., 2023). These methods can improve agent behavior, but they do not by themselves verify a particular action against a domain policy immediately before execution. Run-time constraints and learned tool-call checks address this separate problem (Wang et al., 2026; Chen et al., 2025; Mou et al., 2026; Kang et al., 2026a). A separate generative LLM could review each proposal and explain its concerns, as in LLM-as-a-judge methods (Zheng et al., 2023; Liu et al., 2023). But free-form explanations must still be interpreted before a gate can act on them, and the cost of making this decision with a frontier model is high. Decision models instead return choices and probabilities for fixed questions, making threshold-based checks straightforward. Their probabilities are not guaranteed to be calibrated or correct, so their value has to be tested in the agent loop rather than assumed (TypeSafe AI, 2026; Deußer et al., 2026). We present JevAct, a harness that checks selected proposals before execution. Offline, a compiler turns a domain policy into questions, rules, executable checks over tool state, and where needed, a hand-off checklist. At runtime, code checks facts available in tool records and Kev (an open sourced Jev-like (TypeSafe AI, 2026) decision model) answers questions that depend on the con-versation. A passing proposal proceeds; a flagged proposal is returned to the agent with targeted feedback and a bounded chance to revise. The agent still proposes actions; Kev does not choose them. This separates JevAct from decision-centric runtimes that delegate action selection to a deci-sion model (ZJUNLP, 2026). Our central question in this is work is whether a decision model can serve as a probability-thresholded verifier alongside executable tool-state checks. We compare JevAct with a ReAct har-ness using the same agent LLM in both arms, across Airline and Telecom tasks in τ 2-bench and multi-turn function-calling tasks in BFCL (Barres et al., 2025; Patil et al., 2025). On Telecom, all eight agents improve both at-least-once success and success across all three runs. On BFCL, all nine improve in three-run success, but at-least-once results are mixed. Airline effects are smaller and vary by agent (see Figure 1). Because JevAct adds compiled checks and revision opportunities, these comparisons evaluate the full harness, not the judge in isolation. Our contributions in this work are threefold: • We introduce JevAct, which combines executable checks over tool state with thresholded decision-model judgments of conversational context before selected actions are executed. • We lay the foundation for a workflow that compiles domain policies into questions, decision rules, executable state checks, and hand-off checklists for a decision-model gate. • We evaluate the harness against same-model ReAct baselines across three benchmark set-tings, with component and judge ablations alongside task-success, repeatability, and esti-mated judge-cost results. 

## 2 Related Work 

2.1 LLM Agents and Test-Time Feedback 

ReAct interleaves model reasoning with environment actions (Yao et al., 2022). Self-Refine and Reflexion add test-time critique or feedback to improve later proposals and trials without updating 2model weights (Madaan et al., 2023; Shinn et al., 2023). These methods motivate giving an agent a chance to revise, but do not by themselves check whether a consequential tool call satisfies a domain policy before execution. 

2.2 Runtime Policy Enforcement 

Several systems place explicit controls around agent execution. GuardAgent uses a separate agent to generate and execute verification code from user-defined guard requirements (Xiang et al., 2024). Zwerdling et al. compile company policies into executable guards that check compliance before tool actions (Zwerdling et al., 2025). AgentSpec represents runtime constraints as triggers, pred-icates, and enforcement actions; ShieldAgent derives verifiable rules from policy documents; and CUGA applies governance interventions across an execution graph (Wang et al., 2026; Chen et al., 2025; Shlomov et al., 2026). ToolSafe uses a learned guardrail to assess proposed tool calls and return feedback, while PolicyGuard and PolicyGuide use model-based verifiers for policy adher-ence and workflow guidance (Mou et al., 2026; Kang et al., 2026a,b). Related approaches include verifier-grounded runtime mediation, which uses executable procedural checks to select interven-tions (Yabusaki, 2026), and ToolFence, which combines deterministic authorization with judge-based capability grants (Li et al., 2026a). CaMeL instead enforces security through separation of trusted control flow and untrusted data (Debenedetti et al., 2026). JevLoop assigns action and con-trol decisions to a decision model; JevAct leaves proposals to the ReAct LLM and places Kev, an open-source Jev-type decision model, in a separate verification step before selected actions com-mit (ZJUNLP, 2026). We focus on probability-thresholded verification using a fixed-choice decision model, combined with executable checks of tool-state facts and feedback-driven revision. 

2.3 LLM Judges and Decision Models 

LLM-as-a-judge methods use generative models to compare responses, as in MT-Bench, or apply explicit rubrics, as in G-Eval; such judgments can also be sensitive to response order (Zheng et al., 2023; Liu et al., 2023; Wang et al., 2024). Jev introduced decision models that return typed choices, scores, and probabilities rather than generated text (TypeSafe AI, 2026). Initial evaluations study its closed-label decisions and rubric-based scoring (Deußer et al., 2026). Two recent preprints evaluate Jev as a judge: Li et al. report competitive results on preference and evidence-grounded factuality but weaker performance when derivation is required, while Rao and Callison-Burch report mixed rubric results and overlapping errors with LLM judges (Li et al., 2026b; Rao and Callison-Burch, 2026). Those studies judge completed outputs. JevAct instead uses Kev, an open-source Jev-type model, online before selected actions execute, combining its fixed-choice judgments with programmatic state checks and feedback for revision (Palmer, 2026). 

## 3 Method 

In this work we introduce JevAct, which augments the harness of a ReAct agent (Yao et al., 2022) by inserting a selective checking stage between message proposal and execution. The checks can defer execution and request a revised proposal from the LLM with temporary feedback, subject to a fixed revision budget. The agent’s LLM, base prompt, and tools remain unchanged. 

3.1 Overview Setting. At each step t, an LLM reads the conversation history and proposes a message, which may contain user-facing text, tool calls, or both. The harness normally executes the proposal and adds it and any tool results to the history. In policy-governed tasks, JevAct checks selected proposals before execution because some mistakes are hard to undo. A write call changes the environment, for example by booking, cancelling, or changing a setting. A hand-off ends the agent’s attempt, either by transferring the user to a human or by telling the user that nothing more can be done. The same runtime design can also apply generic checks when no written policy is available.

(2) Compiler : Offline, an LLM turns each domain’s policy into yes/no questions, rules that combine their answers, code that computes facts from tool results, and (where needed) a hand-off checklist. Although the components rely on each other, each is modular and can be independently replaced or improved in future work. 

3.2 Decision loop 

At step t, the agent goes through four stages: 1. Propose. The LLM proposes a message m ∼ π(· | ht) given the history ht.2. Trigger. If m contains a write call, the write gate applies. If m hands off, the hand-off check applies. Any other message is committed directly. 3. Check. The check returns pass or flag . A flag comes with a feedback text f that names the problem. 4. Commit or revise. A passed message is executed and added to the history, as in ReAct. Aflagged message is discarded: it is never executed and never stored. The LLM then proposes again with the feedback appended for this one call, m′ ∼ π(· | ht, f ).Each check has a revision budget: R = 2 for the write gate and R = 1 for the hand-off check. While budget remains, a flagged proposal is discarded and the agent gets another chance to respond to the feedback. Once the budget is exhausted, the next proposal is committed without another check. Thus, a check cannot block the agent indefinitely, and it adds at most R extra LLM calls. Feedback is temporary and is not added to the conversation history, so critiques of earlier steps do not accumulate in the context. 

3.3 Compiler 

The compiler runs offline for each domain. It uses the policy and tool schemas to build the checks; code generation and repair also use example tool outputs and calls from development logs. For each write tool, it produces: 4• yes/no questions about policy requirements, the source of call arguments, user intent, and any required prior steps or confirmations; • a Boolean rule that combines the answers and specifies when the call is allowed; and • a Python function that computes policy-relevant facts available in tool records (such as dates, amounts, and counts) and returns any violations those records establish. For hand-offs, it also produces the problem types covered by the policy and the steps the agent should try for each problem before giving up. Each step has a settled question: was it tried, verified, or ruled out? One instruction in the compile prompt matters most: a condition that was never discussed is not ruled out . Without it, “enable roaming” compiles to “. . . or the user is not traveling”, which looks settled even though nobody asked. With it, the checklist gets its own step: ask whether the user is traveling. For write gates, the compiler gets one repair pass using logged calls without outcome labels. Next, questions that the judge answers with a confident violation on more than 10% of a tool’s development calls are dropped; this filters questions that are hard to answer from the available evidence. The hand-off checklist has a separate filter: steps flagged on more than 5% of hand-offs in solved training episodes are dropped. The prompts and examples are in Section A.1. 

3.4 Judge 

For the judge in this work, we use Kev (Palmer, 2026), an open-source Jev-like decision model. Given a prompt and questions with fixed answer options, it returns a probability for each option in one forward pass, without generating text. Questions about the same prompt share that pass. We use Kev-27B, a fine-tune of Qwen3.8-27B, without further training for our setup. Its probabilities let the checks act only on confident answers, and the cost of a check does not grow with the number of questions. Because Kev is separate from the agent LLM, the agent does not judge its own proposals. The checks divide the work by evidence source: code calculates facts available in tool records, while Kev answers focused questions that require interpreting the conversation, such as whether the user requested an action or whether a step was tried. This asks the judge to assess specific candidate items rather than diagnose an entire problem from scratch. Other models that answer the same questions can take Kev’s place. We chose Kev as open source model. 

3.5 Checks Write gate. The write gate runs before each write call, in three steps: 1. Code: the compiled function reads the proposed call’s arguments and earlier tool results, then returns any violations established by those records. 2. Judge: Kev answers the questions for that tool using the policy, conversation, tool results (with dates annotated and list values ranked), and proposed call. An answer counts as no only when Kev is confident, meaning P (yes ) ≤ 0.05 ; otherwise it counts as yes .3. Rule: the call is flagged if the code finds a violation or the Boolean rule is not satisfied by the question answers. Feedback lists the established violations and failed questions, then asks the agent to correct the call, ask the user for missing information, or explain why the request cannot be fulfilled. If the agent believes the call is already correct, it may submit it again. After a second flag, the feedback directs the agent to respond to the user rather than call the tool again. 

Hand-off check. The hand-off check runs before a transfer call and before a message that gives up in words. A keyword filter first identifies possible give-up messages, which the judge then confirms. From the conversation, Kev identifies the user’s problem, whether the user says it is fixed, and whether each checklist step is settled. A step is open when the probability that the user’s problem requires it is at least 0.5 and the probability that it is settled is at most 0.5. If the problem is not fixed and at least one required step is open, the check flags the hand-off and returns the open steps as feedback. The hand-off check allows one revision; after that budget is used, the next proposal is committed without another check. 5Function calling without a policy. BFCL multi-turn (Patil et al., 2025) has no written policy, and its user turns are fixed, so we use two generic checks. The end-of-turn check runs when the agent ends its turn while a tool error stating a requirement (for example, “needs to” or “must”) remains unresolved. Kev selects the tool that meets the requirement from the tool list, or selects none. If the probability of a tool being the right one is at least 0.6, feedback directs the agent to call it rather than ask the user. The requested-action gate runs before each state-changing call and asks whether the user requested it or a tool error requires it. If Kev assigns at most 0.05 probability to “yes,” the gate flags the call as unrequested and directs the agent to do only what was asked or required. 

## 4 Experimental Setup 

4.1 Benchmarks 

τ 2-bench (Barres et al., 2025): an agent serves a simulated user under a domain policy and calls tools that read and write a database. We use two domains. Airline (50 tasks) tests policy-compliant write calls (book, cancel, change). Telecom (the 114-task base split) tests troubleshooting, in which the agent also guides the user through actions on their own device; here the main failure is giving up too early. The user simulator is GPT-4.1, as in τ 2-bench. Scoring is τ 2-bench’s own: the final database state and the required communication. 

BFCL multi-turn (Patil et al., 2025): 800 entries, 200 in each of four categories (base, missing function, missing parameter, long context). The user turns are fixed, so there is no user simulator. We follow BFCL’s function-calling loop (no system prompt, up to 20 steps per user turn) and score with its own multi-turn checker: an entry is solved only if every turn’s end state and response match the ground truth. BFCL has no written policy, so JevAct uses its two generic checks here, the end-of-turn check and the requested-action gate (Section 3.5). 

4.2 Agent LLMs 

We evaluate eleven agent LLMs. GPT-4.1, Claude Opus 4.6, gpt-oss-20b, gpt-oss-120b, Qwen3.8-27B, and DeepSeek-V4-Pro are tested on all three benchmark settings. Claude Haiku 4.5 and Claude Opus 5.5 are tested on Telecom only; Llama 3.3 70B, Mistral Small 3.2 24B, and Gemma 4 31B are tested on BFCL only (Table 2). Within each comparison, the ReAct and JevAct arms use the same agent model. Agent calls use temperature 0 and a maximum of 4,096 output tokens; the GPT-4.1 user simulator on τ 2-bench also runs at temperature 0. 

4.3 Judge and Compiler 

Unless stated otherwise, every JevAct result uses the same configuration. The judge is Kev-27B, used as is, for every agent LLM and benchmark. Claude Opus 4.6 compiles the checks offline for policy-governed tasks (Section 3.3). The write gate counts an answer as no only when P (yes ) ≤

5.1 Ablations 

We examine three aspects of JevAct: the contribution of its verification components, the trade-off between decision models and generative LLM judges, and the effect of judge size. 

Write-gate components. Table 3 examines the contribution of different write-gate components using a single-trial Airline evaluation with GPT-4.1 as the agent. The full gate improves success from 50.0% to 72.0%, while executable checks alone achieve 68.0%. In contrast, Kev-27B questions alone reach 57.1%, suggesting that programmatic verification accounts for much of the improvement in this setting. Replacing Kev-27B with the smaller Kev-9B reduces success to 58.0%, indicating that judge choice can substantially affect performance. Reducing the revision budget from two to one has a relatively small effect (68.0%). Importantly, flagging every write call once without checking its validity gives no improvement over ReAct (50.0%), with three runs per task and a gpt-oss-120b user simulator, an unconditional re-check of every write leaves GPT-4.1’s passˆ3 unchanged (26.0% to 28.0%) while the full gate raises it to 40.0% (paired 95% CI of the gain over ReAct: +2 .0

to +26 .0 points); for gpt-oss-120b as the agent, the same re-check, or random flags at the gate’s rate, raise passˆ3 as much as the full gate (32.0% to 42.0%), so whether the judge’s verdicts matter beyond the revision opportunity depends on the agent. The flag rates further show that the full gate intervenes on fewer than half of write calls, while achieving the highest success rate among the tested configurations. As these results are based on a single trial, differences between configurations should be interpreted cautiously. 

Judge choice and cost. Table 4 compares Kev with open-weight and API-based generative LLM judges. All judged configurations improve passˆ1 over their corresponding ReAct baselines by 9.4– 18.7 percentage points, suggesting that the verification framework is not dependent on a particu-lar judge architecture. Kev-27B achieves competitive performance: with GPT-4.1 as the agent, it reaches 70.0% success, compared with 67.3–72.0% for generative judges; with Haiku 4.5, it reaches 68.0%, compared with 64.7–66.0%. The main advantage of Kev is efficiency. Its estimated judge cost ranges from $0.0003 to $0.0017 per task, compared with $0.0020–$0.0040 for open-weight LLM judges and $0.0127–$0.0231 for API judges. Judge size. Table 5 evaluates whether increasing the decision model’s size improves verification. Surprisingly, larger judges do not consistently yield better downstream task performance. On Air-line, Kev-27B performs best for GPT-4.1 (65.3% passˆ1, compared with 59.3% for Kev-9B and 58.0% for Kev-0.8B), but the remaining agents show no consistent preference for larger models. On Telecom, smaller judges frequently match or outperform Kev-27B, indicating that increased model capacity does not necessarily translate into more successful agent interactions. Moreover, in a re-play of 609 identical hand-off states, Kev-9B agrees with Kev-27B on 97.0% of decisions, while Kev-0.8B agrees on 90.6% (Section A.2). This suggests that substantially smaller decision models can often reproduce the decisions of a larger judge. One factor affecting judge size is input length. On Airline, 41% of write-check inputs exceed 8,192 tokens, beyond the smaller judges’ validated context length. Offline analysis shows that Kev-9B misses more invalid calls on long inputs, while threshold recalibration reduces the gap on shorter inputs. Kev-0.8B remains weaker even on short inputs (Section A.3, and A.4). Together, these findings suggest that effective judge selection depends not only on model capacity, but also on context length, decision thresholds, and the type of verification required. Since downstream success also depends on the agent’s response to feedback, these results should not be interpreted as direct rankings of judge accuracy. 

Overall findings. The ablations highlight three observations. First, executable state checks pro-vide a substantial part of the measured benefit on Airline, and selective verification beats indis-criminate revision for GPT-4.1 but not for gpt-oss-120b, for which a re-check alone gives the same gain. Second, prefill-only decision models offer a competitive and comparatively inexpensive alter-native to generative LLM judges, reducing cost with small drop in performance. Third, larger judges are not uniformly better: smaller models can be effective when their context capacity and decision thresholds are appropriate for the verification task. ## 6 Conclusion 

We introduced JevAct, a runtime gate that checks selected agent proposals before execution, com-bines executable checks over tool state with probability-based judgments of conversational context, and returns feedback for bounded revision. Compared with same-model ReAct baselines, the full harness shows its clearest gains on Telecom: all eight agents improve both at-least-once success and success across all three runs. On BFCL, all nine improve in three-run success, while at-least-once results are mixed. Airline results are smaller and mixed across agents. These findings support further study of decision-model gates, but do not establish uniform gains or isolate the judge’s contribution. Two caveats apply: with a gpt-oss-120b user simulator the Telecom gain does not appear (passˆ3 changes by −1.8 points, 95% CI −7.9 to +4 .4), and on 260 labelled development write calls 42 of the 101 incorrect calls break no compiled question, because the questions encode the policy rather than the user’s request. 

Future work. The next step is to make the gate work across agent architectures rather than tying it to one ReAct loop. A common interface to proposed actions, tool state, and execution outcomes could support different action formats and orchestration frameworks. We also aim to automate more of the setup: deriving candidate checks from policies and tool schemas, generating and validating executable checks, and selecting thresholds and revision budgets on held-out traces. Such automa-tion should account for both missed violations and unnecessary interventions, while retaining human escalation for uncertain or high-impact decisions.
