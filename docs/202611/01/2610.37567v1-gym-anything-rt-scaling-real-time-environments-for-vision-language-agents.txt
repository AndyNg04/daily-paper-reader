## ABSTRACT 

AI agents have made substantial progress in domains where they have a non-trivial amount of time to deliberate between actions, such as mathematics, software engineering, and performing tasks on desktop applications. It is less clear how such models fare in settings that demand real-time interaction , such as playing a video game or operating a physical device. In these settings, the environment state may evolve as the agent is reasoning, or even as the underlying model is performing a forward pass. To gain insight into the real-time interaction capabilities of vision-language agents, we introduce G YM -A NYTHING -RT. Our key idea is to construct 

visual minigames that demand a portfolio of capabilities required for interactive real-time settings. G YM -A NYTHING -RT uses an agentic pipeline to automatically generate such environments based on a taxonomy of six capabilities required for real-time interaction, including the ability to perceive the environment and act under an evolving environment state. A key feature of G YM -A NYTHING -RT is that it allows for controlled comparison of real-time interaction capabilities: we can run the same minigame in real time, or pause or slow down the environment to relax the requirement for real-time actions. We use G YM -A NYTHING -RT to construct 100 real-time minigames and evaluate AI agents on them. We find large capability gaps in real-time interaction. For example, GPT-6 Astra (xHigh) achieves a pass rate of only 9.0% on the real-time minigames, which rises to 75.0% when the environment is paused. We also identify intriguing behaviors by the most powerful frontier agents: for instance, when given the ability to write code, these agents write code that bypasses the need to perceive and act in real time. We publicly release GYM -A NYTHING -RT and the generated minigames to spur further research on AI agents in real-time interactive settings. 1

## 1 INTRODUCTION 

AI agents have made substantial progress in domains where they have time to deliberate between actions, such as mathematics (DeepSeek-AI, 2025), software engineering (Jimenez et al., 2024), and performing tasks on desktop applications (Yuan et al., 2026; Aggarwal et al., 2026; Jang et al., 2026). However, these agents have a key limitation: they are slow, often taking more than ten seconds to choose a single action. This is acceptable when the environment waits for the agent, but not in settings that demand real-time interaction , such as playing a video game or operating a physical device (Zhang et al., 2026; Black et al., 2025). There, the environment keeps changing while the agent reasons, or even while the model performs a forward pass. By the time an action executes, it may no longer be valid, and the agent cannot react to what happened in the meantime. Existing evaluations shed little light on this limitation. Computer-use benchmarks wait for the agent between actions, so they never test acting under an evolving state (Xie et al., 2024; Yuan et al., 2026; Aggarwal et al., 2026). Video game benchmarks do run in real time. However, frontier models make little progress on them (Zhang et al., 2026; Ying et al., 2026; Ouyang et al., 2026). Furthermore, each game combines many capabilities, such as 3D spatial understanding, temporal reasoning, and learning unfamiliar controls, in a single fixed task. Separating these two causes requires controlled comparisons that vary how much time an agent has to respond on the same task. To address these challenges, we introduce G YM -A NYTHING -RT, a framework for creating envi-ronments for studying the real-time interaction capabilities of vision-language agents. Our key idea is to construct visual minigames that demand a portfolio of capabilities required for interactive real-time settings, while avoiding the complexity of complete games. For instance, in Rotating On-Screen Keyboard (Figure 1), the agent must enter a code by clicking keys that keep moving in three-dimensional space between its observation and its action. Furthermore, we build an evaluation stack that controls the clock of each minigame, so we can run the same task live at its natural speed, slow it down to give the agent more time to respond, or pause it between observation and action to remove the need for real-time actions. Since each minigame is a program, we can also modify it, for instance, to remove its temporal dynamics or to increase its difficulty. By comparing an agent’s performance on these variants of the same task, we can tell whether it fails because it cannot act in time as the environment changes, or because the task is hard for other reasons. Building such minigames by hand is laborious, since each needs its own visuals, dynamics, controls, and verifier. We therefore build an agentic pipeline that generates the minigames automatically. We first survey prior work on embodied agents (Savva et al., 2019; Srivastava et al., 2021; Yang et al., 2025c), video games (Zhang et al., 2026), and computer use (Cheng et al., 2024; Xie et al., 2024) to identify six capabilities required for real-time interaction, such as 3D visual understanding, temporal reasoning, and acting under an evolving environment state, and select minigames that cover the capabilities. We then build on the creator-auditor procedure of Gym-Anything (Aggarwal et al., 2026), in which one coding agent builds an environment and an independent agent audits it. In our setting, a creator agent implements each minigame as a program, and additionally writes an oracle solution that uses the program’s internal state to show that the task is solvable. Independent audit agents then test the minigame and report problems to the creator agent, which fixes them until the minigame behaves as intended. Finally, review agents label the capabilities that each minigame requires. Each program also defines four easier difficulty levels and a simplified interaction mode, which let us evaluate weaker models and study what makes a task hard. Using this pipeline, we construct a benchmark of 100 real-time minigames and their non-real-time counterparts, and use it to evaluate frontier and open-weight models. We find that current agents perform poorly in real time. GPT-6 Astra (xHigh) solves only 9.0% of the real-time tasks, while it solves 66.0% of their non-real-time counterparts, which we obtain by modifying each program so that it no longer requires real-time interaction. Other models perform even worse: Claude Opus 5.5 (xHigh) and GPT-6 Luna (xHigh) solve only 5.0% and 1.0% of the real-time tasks, and the 2Preprint open-weight Qwen3.8-27B and Qwen3.5-9B solve only 1.0% and 0.0%, respectively. In addition, we find that for frontier models, the primary bottleneck is speed. On the same real-time tasks, slowing the environment by 64 × raises Astra’s pass rate from 9.0% to 57.0%, and pausing it raises the pass rate to 75.0%. Since we also control difficulty and the interaction interface, we further identify temporal reasoning and exploration of unfamiliar interfaces as additional sources of difficulty. Interestingly, we also find that frontier agents can partially offset their poor real-time capabilities through their strong coding and reasoning capabilities . Specifically, when we allow Astra to run code, it writes scripts that perceive and act on its behalf between its own responses. For instance, in Rotating On-Screen Keyboard, it locates the moving keys using image template matching and clicks them within 200 ms. As a result, its real-time pass rate rises from 9.0% to 31.0%. In summary, our contributions are three-fold. First, we introduce G YM -A NYTHING -RT, a framework that uses coding agents to automatically generate real-time visual minigames as programs, with oracle solutions and controlled difficulty and interaction. Its evaluation stack runs each minigame live, slowed down, or paused. Second, using G YM -A NYTHING -RT, we construct a benchmark of 100 real-time minigames and their non-real-time counterparts for studying the real-time interaction capabilities of vision-language agents. Third, through extensive evaluations, we show that current agents perform poorly in real time, that speed is the primary bottleneck for frontier models, and that frontier agents can partially offset their slow responses by writing code. 

## 2 METHODOLOGY 

Our goal is to develop a suite of minigames that test the real-time interaction capabilities of vision-language agents in a controllable way. In particular, we construct minigames in which the time available to respond can be controlled while the underlying task stays the same. Formally, each minigame is an executable environment E whose program defines its internal state, controls, and clock. At each step, the agent observes a screenshot ot and issues mouse and keyboard actions at,while the environment keeps evolving as the agent chooses at. We say that a task requires real-time interaction when the agent must use recent visual evidence to choose an action for the state in which it will execute, so that changes during the delay between observation and action can reduce that action’s value (Appendix H). Each minigame has ten configurations Ed,i , where d ∈ { 1, . . . , 5} specifies the difficulty and i ∈{simplified , full } specifies the interaction mode. Each configuration can be run with a slowdown s:live execution at its natural speed ( s = 1 ), slowed execution ( s > 1), in which the clock advances at 1/s of its normal rate, and paused execution, in which the environment freezes until the agent acts. In addition, each real-time minigame has a non-real-time counterpart ¯E, obtained through a minimal change to its timing (Section 2.3). Since a broken or unsolvable minigame would be counted as an agent failure, every configuration must also be solvable and objectively gradable. We construct these minigames with coding agents, that is, LLM agents that can write and run code and inspect screenshots in a sandbox. All agents are instances of GPT-6 Astra run through the Codex CLI. Each agent takes on one of four roles: survey agents collect candidate minigames, creator agents implement real-time versions of them, audit agents verify them, and review agents calibrate difficulty and annotate capabilities. Figure 2 summarizes this procedure. 2.1 TASK DISCOVERY AND SELECTION 

We prompt survey agents to search prior work, public demonstrations, visual puzzles, online videos, and social media for challenges that satisfy four criteria: they can be formulated as self-contained minigames, require visual understanding and grounding, require actions through a visual interface, and have objectively verifiable outcomes. These include tasks that involve moving objects, hidden information, physical manipulation, or changes that occur between actions. For every source, the survey agent records its provenance, objective, visual structure, required interactions, temporal behavior, failure and recovery process, and information needed to verify success. We manually review the first 15 minigames and use them as quality standards for subsequent agent iterations. We select candidates with a traceable source, distinct visual and interaction requirements, an objectively gradable outcome, and meaningful mouse or keyboard actions. To construct a real-time minigame E from a source P , we build upon the creator-auditor procedure from Gym-Anything (Aggarwal et al., 2026), in which a creator agent builds each environment and independent audit agents verify it. In our setting, the creator agent writes a program that implements the minigame and exposes a common interface for screenshot observations as well as mouse and keyboard actions. Crucially, we ask the creator agent to turn the task posed by the source into one that requires real-time interaction, as defined above, whether or not the source itself does. Adding decorative motion, a countdown, or faster animation is not sufficient. For example, Rotating On-Screen Keyboard requires the agent to click keys that keep moving between observation and action. The creator agent implements the generator, interface, dynamics, action handling, and grader of E. It also constructs an oracle solver that uses the privileged state of the environment to determine a valid solution and executes it through the same action space available to the agent. A successful oracle execution therefore demonstrates that the task is solvable and that its action and grading paths agree. The creator agent records the implementation, oracle trajectory, and visual and temporal evidence for these claims (Appendix B.1). Each implementation is then audited by a fresh audit agent that cannot modify the program. The audit agent inspects the code and evidence, runs the environment when necessary, and checks generation, solvability, rendering, action handling, grading, and recovery from failure. It also checks the real-time requirement itself, searching for shortcuts that would let an agent avoid acting in real time, such as a brake that halts the moving parts or periodic motion that permits a precomputed solution. The audit agent returns issues to the creator agent for revision, and the loop repeats until an audit passes. 2.3 NON -R EAL -T IME COUNTERPARTS 

A low pass rate on a real-time minigame does not by itself show that real-time interaction is the cause, since the underlying task may also be hard. We therefore construct, for each real-time minigame 

E, a non-real-time counterpart ¯E that poses the same task without requiring real-time interaction. The creator agent makes a minimal change to the timing of E, while preserving its goal, controls, difficulty, and the information available to the agent. An independent audit agent then checks across all ten configurations that the two versions differ only in their timing. Comparing an agent on E and ¯E

thus lets us separate the effect of the real-time requirement from the difficulty of the underlying task. 4Preprint 2.4 CONTROLLED TASK VARIATIONS 

To also evaluate weaker models and study what makes a task hard, we construct easier variants of each minigame. We vary the difficulty d and the interaction mode i while holding the other and the random seed fixed, for both E and its counterpart. A difficulty-review agent first reads the generator, visible interface, grader, verifier, and oracle solver to determine what the original minigame requires. It compares this configuration with an approved set of reference minigames and assigns it to one of five levels. The creator agent preserves the original configuration at that level and constructs the remaining levels around it by changing the amount of information, number of dependencies, speed, precision, dynamics, or simultaneous control required for success. A difficulty-review agent then checks each adjacent pair and rejects any spurious difficulty increase, such as requesting repeated actions or adding ambiguity. The agent also ensures that the same types of perception, memory, decisions, and control are required across difficulty levels. For example, the levels of Rotating On-Screen Keyboard (Figure 3) vary the code length, the number and size of keys, and the keyboard motion. The creator agent also implements simplified and full interaction for every difficulty level. Simplified interaction exposes proxy controls, while full interaction requires the direct mouse or keyboard manipulation appropriate to the minigame. For example, in Rotating On-Screen Keyboard, simplified interaction lets the agent type the code directly with keyboard actions, while full interaction requires clicking the rotating keys. For a fixed seed and difficulty, the audit agent verifies that both modes generate the same minigame and differ only in the controls used to act on it. Appendices B.2 and B.3 give examples of both variations. 2.5 CONTROLLING TIME 

To control how much time an agent has to respond, we build an evaluation stack on top of Gym-Anything (Aggarwal et al., 2026) that controls the clock of each minigame. During live execution, the task continues to change from observation through action execution at its natural speed. In Rotating On-Screen Keyboard, for example, a key can move between observation and action, so the agent must account for its position when the click executes. Since any delay between an action and its effect counts against the agent, we also build a direct connection protocol. A central server still launches and manages many sandboxes in parallel, but each agent exchanges actions and screenshots over a direct connection to its own sandbox, bypassing the server. This keeps the median time from sending an action to receiving the resulting screenshot below 50 ms in our timing tests (Appendix E.1). For slowed execution, the stack scales every clock of the minigame, including its timers, animations, and server-side clocks, so that a slowdown of s advances the game by one second during s seconds of real time. Action delivery and screenshot capture still run in real time, so the slowdown changes the time available to respond while the agent’s interaction stays the same. During paused execution, the task advances through an observation window and then freezes on the final frame until the action is executed. All settings use the same minigame, seed, difficulty, interaction mode, and verifier. Appendix E describes the evaluation protocol. 2.6 CAPABILITY REVIEW 

To relate agent failures to the capabilities a minigame requires, a capability-review agent labels each configuration of both the real-time minigames and their counterparts for 3D visual understanding, temporal reasoning, reasoning and planning, and exploration and interface understanding (see Ap-pendix D for definitions). It reviews the game’s program, interface, verifier, oracle solution, and recorded behavior to identify what a solution using screenshots and mouse or keyboard actions requires. Each label is supported by code or behavioral evidence. A real-time review agent checks the real-time requirement separately for each configuration, using the implementation and recorded behavior (Appendix H).

Since frontier models are strong coding agents, we next examine whether they can use code to compensate for their slow responses. We allow models to run code in an isolated sandbox, where they can request screenshots and execute the same mouse and keyboard actions through an API (Appendix F.5). The action space is unchanged, but models can now write scripts that observe and act without waiting for the model’s next response. Table 2 reports results at the highest difficulty with full interaction in the live setting. Coding raises the pass rate of Astra (xHigh) on real-time tasks from 9.0% to 31.0%, a 3.4-fold increase, compared with a gain of only 8.0 points on their non-real-time counterparts, from 66.0% to 74.0%. The gain also grows with model capability: Astra (Low) improves from 8.0% to 14.0%, and Luna only from 1.0% to 5.0%. To understand this gain, we inspect Astra’s trajectories. Astra writes image-processing scripts that perceive and act between its own responses. For instance, in Rotating On-Screen Keyboard, it locates the moving keys using image template matching and clicks them within 200 ms. In Clockwork Clutch Safe, where moving gears must be aligned, it tracks gear markers and times clutch releases using estimates of their motion (Appendix G). In effect, the model moves the real-time part of the task into code, and reasons only about what the code should do. This suggests that similar scripts could help slow models act in other real-time domains, such as video games and physical interfaces. Nonetheless, coding still leaves Astra far below its paused performance of 75.0%, and such scripts are difficult to write when the relevant visual information cannot be extracted reliably or prepared for in advance. 4.5 MODELS ARE SLOW AND EXPENSIVE

4.8 PROVIDING INTERFACE RULES IMPROVES PERFORMANCE 

Many minigames require the agent to learn how an unfamiliar interface behaves before it can solve the task. To isolate this demand, we append an environment-specific rulebook describing the controls, action effects, and world rules to Luna’s task prompt (Appendix F.6), and evaluate with full interaction in the live setting on minigames requiring exploration and interface understanding. Figure 8 shows that providing these rules raises Luna’s pass rate from 11.3% to 16.2% across the five difficulty levels. The model must still solve the same minigame and carry out its solution through the same controls, so this gain comes from knowing the rules in advance. This identifies interface exploration as a further source of difficulty: Luna can use interface knowledge that it struggles to acquire through interaction. 4.9 PERFORMANCE DECREASES WITH DIFFICULTY AND IMPROVES WITH SIMPLIFIED

Finally, we turn to the easier difficulty levels and simplified interaction. Table 4 reports Luna’s pass rates in the live setting with full interaction across all five difficulty levels. While Luna solves only 1.0% of the real-time tasks at the highest difficulty, it solves 15.0% at difficulty 1, so the easier levels leave room to measure progress for weaker models. On their non-real-time counterparts, its pass rate falls from 35.0% to 17.0%. The gap between the two stays between 14.0 and 27.0 points at every difficulty, so acting in real time is a major source of failure even on the easiest tasks. To study difficulty without this effect, Figure 9 reports Luna’s pass rate on real-time tasks across the five difficulty levels under paused execution. Averaged across both interaction modes, pass rate decreases from 53.0% at difficulty 1 to 15.5% at difficulty 5, showing that the difficulty levels provide a controlled range of challenge. Simplified interaction raises the overall pass rate from 29.8% to 33.2%, with larger gains at higher difficulty. Since both modes realize the same minigame, this gain shows that some failures arise from operating the full controls rather than from solving the task. However, the decline with difficulty persists under simplified interaction, showing that the challenges introduced at higher difficulty levels are not only about the controls. 

## 5 RELATED WORK 

Real-time interaction. Acting in a changing environment requires accounting for the delay between observing it and acting on it. Robotics methods handle this delay through asynchronous execution or by predicting the state at execution time (Black et al., 2025; Shukor et al., 2025; Tang et al., 2025), and reinforcement learning studies decision making under action and observation delays (Ramstedt & Pal, 2019; Derman et al., 2021). For computer-use agents, OSWorld-Human measures latency and finds that agents take 2.7 to 4.3 times more steps than necessary (Abhyankar et al., 2026). Game benchmarks either pause the game during inference (Ouyang et al., 2026) or compare paused and real-time play (Zhang et al., 2026; Park et al., 2025), and Real-Time Reasoning Gym adds time pressure to text-based games (Wen et al., 2026). However, these comparisons cover only a few visual games or text-based environments. G YM -A NYTHING -RT pairs each of 100 real-time minigames with a non-real-time counterpart and controls the clock of each minigame, so that we can vary how much time an agent has to respond on the same task. 

Benchmarks for interactive visual agents. Benchmarks for vision-language agents cover websites (Zhou et al., 2024; Koh et al., 2024), desktop and mobile applications (Xie et al., 2024; Bonatti et al., 2024; Yuan et al., 2026; Rawles et al., 2024), professional software (Aggarwal & Welleck, 2025; 10 Preprint Aggarwal et al., 2026), games (Zhang et al., 2026; Paglieri et al., 2025; Hu et al., 2025a; Zheng et al., 2025a; Ying et al., 2026; Ouyang et al., 2026; ARC Prize Foundation, 2026), and embodied simulators (Savva et al., 2019; Shridhar et al., 2020; Srivastava et al., 2021; Yang et al., 2025c). However, most of these environments wait for the agent between actions, and each task requires many capabilities at once, so low performance does not reveal which capability limits the agent. Prior works address the latter by mapping tasks to capabilities (Wu et al., 2023), evaluating perception, reasoning, and decision making separately (Wang et al., 2025c; Xu et al., 2026; Li et al., 2024), or varying one condition of a task, such as difficulty, the initial state, or the interface (Davydova et al., 2025; Zheng et al., 2025b; Zhao et al., 2025; Liu et al., 2026). G YM -A NYTHING -RT instead varies the real-time requirement, difficulty, and interaction interface of the same minigame. 

Capability-specific evaluation of VLMs. Many benchmarks test individual capabilities of VLMs through questions about images or videos, such as 3D spatial understanding (Yang et al., 2025a; Wang et al., 2025b; Ma et al., 2024; Jia et al., 2025), temporal reasoning (Liu et al., 2024; Shangguan et al., 2024; Zhang et al., 2024), GUI grounding (Cheng et al., 2024; Li et al., 2025), and abstract reasoning (Chia et al., 2024; Ghosal et al., 2024; Song et al., 2025). However, the model answers a question about a fixed input, without acting on what it perceives. iVISPAR and VisGym evaluate visual reasoning through interaction (Mayer et al., 2025; Wang et al., 2026b). G YM -A NYTHING -RT further requires agents to perceive and act while the minigame keeps changing. 

Automated environment construction. Recent works use coding agents and LLMs to construct computer-use environments (Aggarwal et al., 2026; Wang et al., 2026a; Cao et al., 2026), text-based environments (Zhang et al., 2025), and environments with tasks of varying difficulty (Hu et al., 2025b; Faldor et al., 2024), while procedural generators vary the complexity of task instances (Cobbe et al., 2019; Samvelyan et al., 2021; Chevalier-Boisvert et al., 2019; Stojanovski et al., 2025; Chen et al., 2025). However, none of these produce visual minigames whose timing, difficulty, and interaction interface can be varied while preserving the underlying task. We extend the creator and audit agents of Gym-Anything (Aggarwal et al., 2026) to construct such minigames, each with a non-real-time counterpart and an oracle solution. Appendix I provides a more detailed related work. 

## 6 CONCLUSION 

In this work, we introduced G YM -A NYTHING -RT, a scalable framework for creating environments for studying the real-time interaction capabilities of vision-language agents. In G YM -A NYTHING -RT, coding agents implement and audit each environment as a visual minigame program with an oracle solution, and our evaluation stack controls the clock of each minigame. As a result, we can vary how much time an agent has to respond, whether the task requires real-time interaction, its difficulty, and its interaction interface on the same minigame. Using G YM -A NYTHING -RT, we constructed a benchmark of 100 real-time minigames and showed that current agents perform poorly in real time, with the strongest agent, GPT-6 Astra (xHigh), solving only 9.0% of the real-time tasks compared with 66.0% of their non-real-time counterparts. We further showed that speed is the primary bottleneck for frontier models, and that temporal reasoning and exploration of unfamiliar interfaces are additional sources of difficulty. Interestingly, we also find that frontier agents can partially offset their poor real-time capabilities by writing code that perceives and acts on their behalf. More broadly, our results suggest that progress in real-time interaction requires agents that are not only capable but also fast. We hope that G YM -A NYTHING -RT and the released minigames provide a foundation for future work on real-time agents, including faster models, agents that move the time-critical parts of a task into code, and training on real-time environments.

## A LIMITATIONS 

We focus on evaluating existing agents, although our programmatic task generators and automatic verifiers also provide a basis for training. Studying whether training on these minigames improves real-time interaction is an important direction for future work. Our minigames capture specific demands of real-time environments to enable controlled comparisons across capabilities, difficulty, and interaction. Whether improvements on these tasks transfer to complete games and physical interfaces remains an open question. 18 Preprint Finally, G YM -A NYTHING -RT covers a selected set of capabilities and task mechanics. Our creation– audit framework provides a way to extend this coverage with additional minigames and capability combinations. 

## B MINIGAME CONSTRUCTION 

This appendix details the construction procedure summarized in Section 2. All agents in the construc-tion pipeline use GPT-6 Astra. B.1 CREATOR AND AUDIT AGENTS 

The creator agent receives one selected minigame together with its survey records and source links. It also inspects previously approved minigames as working examples of the environment structure. The creator implements the environment specification, task, generator, browser interface, server grader, exported verifier, oracle solver, difficulty and interaction controls, real-time settings, and tests. It may create or edit only the files of its own minigame and cannot modify the shared runtime, evaluator, or clock. The creator runs all ten difficulty and interaction configurations in the browser in the live and paused settings and checks generation, grading, result export, verification, failure, and retry. It records screenshots, recordings, and command outputs as evidence, together with a solution video in which the oracle solver completes the task in the browser. A fresh audit agent then inspects the environment and its evidence without modifying any files. It checks the following items and ends its report with a verdict of PASS or REVISION REQUIRED .(a) Difficulty baseline. The generated task is assigned to the appropriate level by comparison with approved reference minigames, without relying on the environment name or the creator’s description. (b) Difficulty variations. Levels 1 to 5 increase in what the agent must perceive, decide, remember, or control. Adding repetitive steps is not sufficient. (c) Interaction. For the same seed and difficulty, simplified and full interaction use the same minigame, information, goal, timing, physics, tolerances, and success condition. Full interaction requires the intended mouse or keyboard operations on the minigame. (d) Real time. In live execution, the environment continues while the model produces an action. In paused execution, it remains frozen until the action arrives, and the action then executes with the intended behavior. The real-time configurations satisfy the definition in Appendix H, and no mechanism lets the agent avoid acting in real time, such as a brake that halts moving parts or repeating motion that permits a precomputed solution. (e) End-to-end behavior. All configurations load, remain playable, produce the correct grading result, export the result, handle failure, and allow another attempt. (f) Evidence. The audit agent ignores comments and written claims that the running environ-ment does not support. Screenshots, recordings, frame sequences, exported results, and browser behavior serve as evidence, and missing visual evidence is a severe issue. The audit agent also checks that the creator changed only files within its permitted scope. The creator revises the implementation in response to the report, and a new audit agent repeats the audit. ## D CAPABILITY ANNOTATION CRITERIA 

GYM -A NYTHING -RT studies six capabilities. Review agents annotate the four capabilities below. The remaining two, interaction and real-time interaction, are varied through the interaction mode and the real-time setting. Appendix H defines when a configuration requires real-time interaction. The authors define the following criteria for capability annotation. Review agents apply them to the requirements of a solution using screenshots and visible mouse or keyboard controls. 

Visual understanding. We classify visual understanding as 2D or 3D according to the spatial understanding required to solve the task. Decorative perspective alone is insufficient for a 3D label. 

Temporal reasoning. A configuration requires this capability when every general screenshot-only solution must interpret change, motion, order, or duration, remember relevant earlier state that is no longer visible, or control when and for how long an action remains active. The temporal relationship must affect action choice or execution. A simple visible sequence, idle animation, or automatic transition to a static result does not establish this requirement. 

Reasoning and planning. Solving requires inferring constraints or choosing actions whose conse-quences affect later decisions. The annotation identifies the relevant inference or action dependency. Basic visual recognition alone does not establish this requirement. 

Exploration and interface understanding. The agent must interact to reveal relevant information or learn how the interface behaves before solving the task. Routine feedback, an automatic transition that supplies the next required information, or following explicit controls does not establish this requirement. Review agents inspect the implementation and recorded behavior for each difficulty and interaction mode. Each annotation is supported by code or behavioral evidence. 

## E REAL -T IME EVALUATION PROTOCOL 

The shared runtime controls the execution schedule, and the task clock begins when the environment starts. In live execution, an observation request returns a current frame while the task clock continues. Paused execution advances the task through an observation window and returns a chronological sequence of frames. The clock then stops on the final frame until the action executes and resumes for the next observation window. The observation window and number of frames are set per minigame and are the same for its non-real-time counterpart. The window ranges from 80 to 800 ms with three to six frames. E.1 ACTION AND SCREENSHOT LATENCY 

Direct connection protocol. Our action and screenshot path builds on a fast input and output path that we previously developed for a single agent controlling a single sandbox. That design assumes a one-to-one pairing between agent and sandbox. Gym-Anything (Aggarwal et al., 2026), in contrast, runs many sandboxes behind a central server that launches them and forwards requests to them, and forwarding every action and screenshot through this server adds latency. We therefore separate the two roles. The central server still allocates sandboxes and manages their lifecycle, but actions and screenshots bypass it. The agent’s client runs on the same machine as its sandbox and keeps a persistent direct HTTP connection to an input service inside the sandbox, which executes each action and returns its acknowledgement over this connection. ## I EXTENDED RELATED WORK 

This appendix expands on the related work discussion in Section 5. 

Benchmarks for interactive visual agents. Existing benchmarks for vision-language agents span web, desktop, mobile, game, and embodied environments. Web benchmarks such as WebArena and VisualWebArena provide self-hosted websites with realistic tasks (Zhou et al., 2024; Koh et al., 2024), while desktop benchmarks such as OSWorld and Windows Agent Arena evaluate open-ended tasks across operating system applications (Xie et al., 2024; Bonatti et al., 2024). OSWorld 2.0 further extends this setting to 108 long-horizon workflows, where the best agent completes only 20.6% of tasks (Yuan et al., 2026). On mobile, AndroidWorld provides tasks across 20 Android apps (Rawles et al., 2024), and Programming with Pixels and Gym-Anything extend computer-use evaluation to software engineering and to 200 professional software applications (Aggarwal & Welleck, 2025; Aggarwal et al., 2026). Game benchmarks evaluate the same models on complete games, ranging 32 Preprint from classic video games (Zhang et al., 2026) and reinforcement learning environments such as NetHack (Paglieri et al., 2025) to platformers, puzzle games, and browser games (Hu et al., 2025a; Zheng et al., 2025a; Ying et al., 2026; Ouyang et al., 2026). ARC-AGI-3 evaluates exploration and goal inference in turn-based abstract games, where humans solve all environments while frontier models solve less than 1% (ARC Prize Foundation, 2026). Embodied benchmarks similarly evaluate agents in simulated homes and physical environments (Savva et al., 2019; Shridhar et al., 2020; Srivastava et al., 2021; Yang et al., 2025c). However, since each task in these benchmarks requires many capabilities at once, low performance does not identify which capability limits the agent. Several works attempt to attribute performance to individual capabilities. SmartPlay maps each of its six games to a subset of nine agent capabilities (Wu et al., 2023), LVLM-Playground evaluates perception, question answering, rule following, and end-to-end play separately on the same board games (Wang et al., 2025c), and Embodied Agent Interface decomposes embodied decision making into separate modules, arguing that final success rates cannot pinpoint which ability is missing (Li et al., 2024). VS-Bench similarly reports perception, strategic reasoning, and decision making separately (Xu et al., 2026). Other benchmarks vary conditions of the same task, such as difficulty tiers (Davydova et al., 2025; Zheng et al., 2025b), initial states (Zhao et al., 2025), or interface changes between actions (Liu et al., 2026). However, these works either operate through text or turn-based interfaces, or vary a single condition without controlling the capabilities a task requires. In contrast, G YM -A NYTHING -RT annotates the capabilities required by each configuration, and varies difficulty, interaction interface, and real-time setting on the same minigame. 

Capability-specific evaluation of VLMs. A large body of work evaluates individual capabilities of VLMs through question answering. For 3D spatial understanding, VSI-Bench, MindCube, 3DSR-Bench, and OmniSpatial evaluate spatial relations, viewpoint changes, and mental models of scenes (Yang et al., 2025a; Wang et al., 2025b; Ma et al., 2024; Jia et al., 2025), while BLINK shows that perception tasks that humans solve easily remain difficult for multimodal models (Fu et al., 2024). For temporal reasoning, TempCompass, TOMATO, and Vinoground evaluate speed, direction, and event order in videos (Liu et al., 2024; Shangguan et al., 2024; Zhang et al., 2024), with TOMATO showing that many questions in earlier video benchmarks can be answered from a single frame. For GUI grounding, SeeClick and ScreenSpot-Pro evaluate whether models can locate screen elements from instructions (Cheng et al., 2024; Li et al., 2025). Finally, PuzzleVQA, AlgoPuzzleVQA, and VisualPuzzles evaluate abstract and algorithmic reasoning over images (Chia et al., 2024; Ghosal et al., 2024; Song et al., 2025), and MMMU and MMMU-Pro evaluate multidisciplinary reasoning over images and text (Yue et al., 2024; 2025). However, in all of these benchmarks the model answers a question about a static input, without having to act on its understanding. Closer to our work, iVISPAR evaluates the spatial reasoning of VLM agents on a sliding-tile puzzle presented in 3D, 2D, and text (Mayer et al., 2025), and VisGym provides 17 interactive environments with configurable difficulty and input representation (Wang et al., 2026b). G YM -A NYTHING -RT complements these works by covering temporal reasoning, exploration and interface understanding, and real-time interaction, and by annotating the capabilities required by each configuration. 

Real-time interaction. Acting in dynamic environments requires accounting for the delay between observing the environment and executing an action. In robotics, real-time action chunking and asynchronous inference execute previously planned actions while the next chunk is computed (Black et al., 2025; Shukor et al., 2025), and VLASH conditions the policy on the state predicted at execution time (Tang et al., 2025). Reinforcement learning has similarly studied decision making under action and observation delays (Ramstedt & Pal, 2019; Derman et al., 2021). For computer-use agents, OSWorld-Human measures end-to-end latency and finds that agents take 2.7 to 4.3 times more steps than necessary (Abhyankar et al., 2026). Game benchmarks have taken different approaches to latency. GameWorld pauses the game during inference and reports a separate real-time study with two models (Ouyang et al., 2026), VideoGameBench runs games in real time and additionally provides a Lite version that pauses the emulator while the agent is thinking (Zhang et al., 2026), and Orak compares paused and real-time play on StarCraft II (Park et al., 2025). Real-Time Reasoning Gym advances text-based games after a fixed number of generated tokens, comparing reactive and planning agents under increasing time pressure (Wen et al., 2026). Our work complements these efforts by evaluating the same minigame and seed in the live, slowed, and paused settings, and by pairing each real-time minigame with a non-real-time counterpart. 33 Preprint 

Automated environment construction. A growing body of work uses coding agents and LLMs to construct environments for agents. Gym-Anything uses a creation agent and an independent audit agent to convert 200 software applications into computer-use environments (Aggarwal et al., 2026). CUA-Gym separates an agent that constructs environment states from one that writes reward functions (Wang et al., 2026a), and GUI-GENESIS converts real applications into lightweight web environments with executable rewards (Cao et al., 2026). AutoEnv generates 36 text-based environments with 358 levels (Zhang et al., 2025), while AgentGen and OMNI-EPIC generate environments together with tasks of varying difficulty (Hu et al., 2025b; Faldor et al., 2024). Similar pipelines construct software engineering tasks from code repositories (Pan et al., 2025; Yang et al., 2025b) and 3D scenes for embodied agents (Yang et al., 2024). Procedural generation further provides task instances with adjustable complexity, including Procgen games (Cobbe et al., 2019), MiniHack and BabyAI (Samvelyan et al., 2021; Chevalier-Boisvert et al., 2019), and verifiable reasoning problems in Reasoning Gym and Enigmata (Stojanovski et al., 2025; Chen et al., 2025). However, these approaches construct software, text, or game environments, and do not produce interactive visual minigames whose difficulty and interaction interface can be varied while preserving the underlying task. We extend the creator-auditor approach to such minigames, where each minigame has a non-real-time counterpart, five difficulty levels, two interaction modes, and an oracle solution. 

CAPTCHAs and visual puzzles. Many of the seed minigames in G YM -A NYTHING -RT are derived from CAPTCHAs and puzzle games. CAPTCHA research has studied whether automated solvers can pass challenges designed to distinguish humans from bots. Recent works solve reasoning and visual CAPTCHAs with LLMs and VLMs (Deng et al., 2024; Teoh et al., 2025), analyze which types of challenges remain difficult for these models (Wang et al., 2025a; Wu et al., 2025), and train GUI agents on interactive CAPTCHAs (Chen et al., 2026). Open CaptchaWorld evaluates web agents on 20 types of interactive CAPTCHAs, where the best agent achieves 40.0% compared to 93.3% for humans (Luo et al., 2025). Beyond CAPTCHAs, KORGym, DiG-bench, and VGRP-Bench evaluate multi-turn reasoning in text, game, and grid puzzles (Shi et al., 2025; Battleday et al., 2026; Ren et al., 2025). However, these works primarily target security or reasoning in isolation.
