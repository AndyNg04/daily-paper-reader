## Abstract 

Large language model (LLM) agents that serve users across many sessions must choose, for every request, the few stored memories that enter a limited context window. This choice largely decides whether the agent answers correctly, and it runs on every request at Web scale. This selection faces three challenges: a large and grow-ing store, a per-request cost budget, and multi-session questions that need all of their evidence. Many memory systems build notes or graphs with hundreds to thousands of LLM calls per history, and each is designed on its own, so it is unclear which component yields the accuracy. These challenges mirror the properties of rec-ommendation, so we formalize agent memory as budgeted slate recommendation, with the request as the user, stored memories as items and the context window as a slate. The formalization places memory systems in one design space of recommender cascades and factorizes accuracy into the completeness that each stage controls. Guided by it, we propose AgentMemRec, which adapts candidate generation, learning to rank and slate construction from recom-mender systems and selects memories without any LLM call. On multi-session questions of LongMemEval, AgentMemRec outper-forms memory and context-selection methods, including A-Mem, HippoRAG 2, DynamicRAG and T-Mem, by 10 to 31 points of ac-curacy. It matches an LLM reranker that makes 64 calls per query at 3.2 times lower serving cost, and on LoCoMo it outperforms Mem0 and Zep without any LLM call at write time. The factoriza-tion attributes the gains to slates that more often hold all of the evidence, so recommender-system design offers an effective and efficient foundation for the long-term memory of LLM agents. 

## 1 Introduction 

Web-based chat assistants keep a long-term memory of each user’s past sessions [40], so for every request their large language model (LLM) agent must decide which stored memories enter its limited context (Figure 1). This decision largely determines whether the agent answers correctly, since a context that misses an evidence turn loses 37 to 64 points of accuracy with Qwen for every turn-level design we compare. The decision also runs on every request, so its latency and cost grow with Web traffic, as they do for Web recommenders, and production memory layers are judged by these costs [8]. Three properties make the decision hard. The store is large and keeps growing: in LongMemEval-M, the history of one question holds about 500 sessions and 1.5M tokens [40], while the answering model in our setting reads at most 2,700 tokens. The budget is per request, so scoring the store with an LLM costs calls in proportion to its size and to traffic. Recommender systems choose a few items from a large catalogue for every request under a latency budget, and they judge the shown set as a whole [10, 18]. ## 2 Related Work 

Long-term memory for LLM agents. LoCoMo [26] and Long-MemEval [40] evaluate assistants on long multi-session histories. Most memory systems decide at write time what to store and how to index it, as linked notes [42], consolidated facts [8], temporal knowledge graphs [31] or fact graphs searched by personalized PageRank [17]. Others build hypergraphs, temporal hierarchies, boundary-guided segments or antecedent links [23, 38, 46, 47], and verbatim chunks have been reported to outperform extracted ar-tifacts on long conversations [1]. In the recommender view, these designs are item side-information or recall structure, and most of them spend LLM calls at write time. AgentMemRec works at read time over raw turns with no LLM call, so its cost per request stays flat as stores grow, and it can use a memory builder’s units as a recall channel. 

Context selection under a budget. Adaptive-k cuts a ranked list at the largest gap in its similarity scores [37], and DynamicRAG trains a reranker that chooses both the order and the number of passages [36]. SetR replaces ranking with set selection by an LLM [21], which lies outside a budget of no LLM calls, and ranked-list truncation learns where to cut a list [3, 27]. High-scoring passages that do not answer the question hurt [11], as do retrieved hard negatives [19] and input length alone [14]. Like these selectors, AgentMemRec orders candidates and fills a budget. It keeps the budget fixed because a fill dominates every cutoff of a ranking when the reward does not fall as the fill extends it. We add a label-controlled contrast of ranked and random filler and a noise-floor control for the per-question headroom that cutoff methods assume. 

Recommender techniques and memory. Industrial recommenders split candidate generation from ranking [10] and treat the shown set as the unit of decision [18], and industrial search arranges rankers of increasing cost in cascades [25]. Set-aware stages re-rank with attention over the list [29] or select diverse subsets with determinan-tal point processes [6]. LambdaRank with gradient-boosted trees is a standard learned ranker [4, 20, 41], reciprocal rank fusion merges channels [9], and LLM rankers can be distilled into cross-encoders [34]. The probability ranking principle orders documents by rel-evance when each is judged on its own [33]. For agent memory, RMM trains a reranker online from the citations of the answering model [39], and recent work studies learned memory rerankers [15, 22, 28], pipelines without LLM calls [30] and small-model con-text construction [44]. MemRec builds agentic recommenders on a collaborative memory [7], and RecMem consolidates agent mem-ory by recurrence [12]. We formalize agent memory as budgeted slate recommendation, extend the probability ranking principle to complete evidence sets, and derive and measure which stages of the design space carry accuracy. Unlike RMM, AgentMemRec needs no feedback from the answering model at use time, which our frozen protocol could not provide, and we did not run these rerankers. MemRec applies memory to recommendation and RecMem decides when to consolidate, whereas we select a context.

## 4 AgentMemRec 

AgentMemRec instantiates the design problem of Equation (2) with an LLM budget of zero (Figure 2). Candidate generation raises 

𝑟 pool , learning to rank raises 𝑟 rank , the pool size is chosen by their product, and the slate fills the budget instead of cutting the ranking. No stage calls an LLM at selection time. 

## 4.1 Candidate generation: raising 𝑟 pool 

In Equation (2), 𝑟 pool bounds the product, so the pool must be wide, and with 𝐿 = 0 it must be cheap to build. Like a recommender, AgentMemRec narrows the catalogue with cheap retrieval chan-nels. The lexical channel ranks all turns by BM25 [32] over lower-cased word tokens. The dense channel ranks them by the cosine similarity of bge-m3 embeddings [5]. Reciprocal rank fusion [RRF; 9] with 𝑘 = 60 merges the two lists, and the pool P ( 𝑞 ) is the top 𝑁 = 128 fused turns. The pool size was chosen on develop-ment questions by slate completeness after ranking, the product 

𝑟 pool 𝑟 rank , where 128 turns led with 0.912 against 0.879 for 64 turns, in-sample for a ranker trained on 64-turn pools. 

## 4.2 Learning to rank: raising 𝑟 rank 

When evidence units are independent, the set-level objective re-duces to ranking units by their probability of being evidence. The ranker therefore learns item relevance from gold labels, and with 

𝐿 = 0 it uses cheap features, as recommender cascades do. Agent-MemRec uses a LightGBM model [20] trained with the LambdaRank objective [4, 41]. Each (question, pooled turn) pair has ten features. Five are cheap relevance signals: the bge-m3 cosine, the logarithms of the global dense and BM25 ranks, the position in the fused pool and the bge-reranker-v2-m3 cross-encoder score. Five describe the turn: whether its role is user, its relative position in its session, the logarithms of its age in days and of its length, and the spaCy keys it shares with the question. The labels are the gold annota-tions of the 152 development questions, with pools from both their LongMemEval-S and LongMemEval-M histories, 19,456 pairs in total. 

## 4.3 Slate construction: the fill 

The slate stage fills the budget 𝐵 from the ranked pool. It walks the pool in rank order and adds each turn whose rendered cost still fits. The rendered cost of a turn is the increase in the token count of the rendered slate when the turn is added, including its session header if no earlier turn of that session was selected. A turn that does not fit is skipped, and the walk continues. The rendering groups the selected turns by session, orders sessions by date and uses the official LongMemEval history format (Appendix A). The budget is fixed at 𝐵 = 2,700 tokens, a value set in our first experiment before any system was compared, and the evaluation perturbs it to 2,400 to 2,700. There is no per-question cutoff, because the fill contains every prefix that fits, so a cutoff can only help where a lower-ranked turn lowers the value of the slate. On the ranking of AgentMemRec, choosing the best of three budgets per question gains no more than decode noise. ## 4.4 Optional write-time records 

This optional extension adds item side-information at write time to raise 𝑟 pool and 𝑎 c, with no LLM call at selection time. An LLM (Qwen3-32B) reads each session once and writes typed records with a date, entities and the turns they cite. A record channel adds to the 128-turn pool the turns cited by the records most similar to the question, up to 32 new turns, and the frozen ranker orders the union. Relative-time tags attach the dates of citing records to turns that contain a relative time expression, keeping only dates up to the reference date of the question. 

## 5 Experimental Setup 

Benchmarks and splits. Like most memory papers, we evaluate on LongMemEval-S [40] and LoCoMo [26]. LongMemEval-S (cleaned release) has 500 questions over histories of about 50 sessions and 100k tokens. LongMemEval-M shares its questions over histories of about 500 sessions and 1.5M tokens, and serves as a harder third setting. We exclude the 30 questions of the unanswerable type and compute 𝜅 over the other 470. A split fixed before any method run assigns 152 of the 500 questions of both variants to development and 348 to test, of which 328 are answerable. The primary stratum is 𝜅 ≥ 2 on test, with 𝑛 = 209, and we also report 𝜅 ≥ 3 (49 test questions). Label-only and oracle measurements have no learned component and use all 300 questions with 𝜅 ≥ 2. LoCoMo has 1,540 scored questions in 10 conversations. As the field does, we report all of them, and we add paired comparisons on test conversations 3 to 9, with conversations 0 to 2 for development. 

Answering and judging. On LongMemEval, two answering mod-els read every slate: Qwen3-32B [43] with FP8 weights under vLLM, and DeepSeek V4.1 Flash [13] through one pinned FP8 provider. Both decode at temperature 0 with reasoning disabled and the of-ficial step-by-step answer prompt of LongMemEval. Final labels come from the official GPT-4o judge with its per-type prompts. A Qwen3-32B judge with the same prompts agrees with GPT-4o on 94% to 98% of answers and changes one primary label. On LoCoMo, we use the answering model, prompt and judge of T-Mem: GPT-4o-mini answers, and the GPT-4o-mini judge is run three times per answer. Appendix A gives the serving and judging details. 

Implementation details. Single decodes are unstable: changing only the lowest-ranked 100 to 300 tokens of a 2,700-token slate changes the judged answer on 91 of 300 multi-session questions for Qwen and 43 for DeepSeek. The variation comes from the answer-ing model, because re-judging identical answers agrees on 99.9% of them. We therefore build 𝐾 = 4 slates per question and system, with budgets 𝐵 ∈ { 2,400 , 2,500 , 2,600 , 2,700 } in the system’s own order, and report the mean judge label. Identical prompts are answered once, so Adaptive-k and DynamicRAG, whose slates often stop short of the budget, reuse one decode for all four budgets on 86% and 52% of questions. T-Mem assembles one context per question and uses one decode. Systems are compared by a paired percentile bootstrap over questions with 10,000 draws at the 5% level. Labels are fixed before each run, and a difference is a gain when it is sig-nificantly above zero and a loss when it is significantly below zero. It is at parity when it is not significant and is significantly above −3points in a one-sided test at the 2.5% level, and underpowered other-wise. Parity is therefore non-inferiority at a 3-point margin with no significant difference. In Table 1, every margin of AgentMemRec over a memory or context-selection method is a gain, and every comparison with Ref is parity except a gain on LongMemEval-M with DeepSeek. The 3-point margin is the spread of one system’s accuracy across four near-identical budgets on one backend, 2.6 and 3.3 points. On LongMemEval-M, this averaged protocol replicates a single-decode test (Appendix E). All systems in the headline tables are answered on one backend per answering model. 

Compared systems. We compare against three families at the shared budget: context selectors, LLM-built memories and an LLM reranker. The context selectors are Adaptive-k [37], which applies its official largest-gap rule to bge-m3 similarities over the whole his-tory, and DynamicRAG [36], whose 8B selector chooses among the top 40 fused turns. The LLM-built memories are the LongMemEval memory design [40], HippoRAG 2 [17], A-Mem [42] and T-Mem [16]. They run with Qwen3-32B as the builder LLM, so the com-parison is between memory designs under a shared builder. The LongMemEval design was run on LongMemEval-M only. T-Mem, the strongest system we found on LoCoMo, is the main compari-son, reproduced on LoCoMo and built by us on LongMemEval-S. The LLM reranker ( Ref ) scores each turn of the 64-turn fused pool from 0 to 10 with Qwen3-8B and fills the budget in score order. Appendix D lists every deviation from the official settings, and the appendix documents all implementation details, including seed selection. 

## 6 Results 

The experiments test the recommender formulation through three research questions. RQ1 asks whether selecting memories the way a recommender selects items outperforms memory systems that build structure with LLM calls. RQ2 asks which terms of the stage factorization carry the gain, and RQ3 asks what the formulation costs.

## 6.3 RQ3: Cost 

We count a generation by a decoder language model as an LLM call, so AgentMemRec makes none at selection time, and its cross-encoder pass is part of its measured serving cost. On LongMemEval-M, its median selection latency is 329 ms against 955 ms for Ref, and on LongMemEval-S its 90th-percentile latency is 321 ms against 1,156 ms (Table 8). At saturation on one A100, selection takes 280 GPU-milliseconds per request for AgentMemRec against 891 for Ref, 3.2 times less, or $69 against $220 per million requests at a list price of $0.89 per A100-hour. Adding the shared pool construction to both keeps the ratio at 3.0 in GPU time and, with a persistent per-history index, 2.7 in median latency at LongMemEval-M size. At write time, the default pipeline makes no LLM call, whereas HippoRAG 2, A-Mem and T-Mem make about 440 to 2,270 per history, a cost that a deployed memory spreads over the requests of each user. On LongMemEval-M, the LongMemEval design and HippoRAG 2 make 251,622 and about 512,000 write-time calls in total. ## 7 When Item-Wise Ranking Suffices 

The reduction to item-wise ranking and the advantage of the fill over cutoffs rest on two conditions on the reward. Accuracy on complete and on incomplete slates must not depend on their com-position, and adding a unit must not lower the value of a slate. This section tests both conditions on the evaluated slates and on label-controlled slates. 

Complementarity. Every system loses 37 to 64 points of accuracy with Qwen when its slate misses a gold turn, and 37 to 68 with DeepSeek, and this gap 𝑎 c −𝑎 i scales each stage gain of the factoriza-tion. Completeness falls with the number of evidence sessions, from 0.940 at 𝜅 ≥ 2 to 0.832 at 𝜅 ≥ 3 for AgentMemRec. A slate thus succeeds when it holds all of the evidence, which is the regime in which the item-wise reduction makes completeness the objective. 

Composition. Across the compared systems, accuracy on jointly complete slates differs by at most 2.8 points at 𝜅 ≥ 2. Accuracy on incomplete slates varies more, from 22% to 47%, and tracks how much of the gold an incomplete slate still holds. The first condition thus holds for complete slates and only approximately for incomplete ones, and it begins to fail at 𝜅 ≥ 3. There, the jointly complete slates of AgentMemRec score 8.7 points below those of the cross-encoder order for Qwen and 6.5 points below for DeepSeek. They hold 23 units against 11, most of them turns that the cross-encoder ranks low. Label-controlled slates that fill the budget around the gold turns show the effect directly (LongMemEval-M, one decode, Qwen judge). Ranked near-miss filler (Appendix E) costs 17.7 points for Qwen and 4.7 points for DeepSeek against the gold turns alone, and 39.4 and 14.1 points at 𝜅 ≥ 3. Random filler of the same length costs 7.0 points for Qwen and nothing measurable for DeepSeek ( −2.3). Adding units can therefore lower the reward, by an amount that depends on the answering model. These costs do not show that the reward is non-additive, since negative item values would produce them too.

## 8 Conclusion 

This paper asked how an LLM agent should choose, for every re-quest, the stored memories that enter its bounded context. We showed that this choice is budgeted slate recommendation and placed memory systems in one design space of recommender cas-cades. Its factorization reduces memory design to raising the com-pleteness of each stage within an LLM budget. Following this prin-ciple, AgentMemRec selects memories without any LLM call. On LongMemEval, it outperforms LLM-built memories and context selectors, and it matches or exceeds an LLM reranker at a fraction of the cost. On LoCoMo, it outperforms production memory layers. Its gains come from slates that more often hold all of the evidence, which suggests that recommender-system principles offer an effec-tive and efficient foundation for agent memory. Set-level objectives, models of user state and learning from use are natural next steps.

## A Data, Rendering and Judging 

LongMemEval data. We use the cleaned LongMemEval release of 2025-09, so our numbers are not comparable with those of the original paper. LongMemEval-M and LongMemEval-S hold about 4,894 and 490 turns per question and share their 500 question iden-tifiers. The frozen split has 51, 69, 22 and 10 development questions and 119, 160, 49 and 20 test questions with 𝜅 = 1, 𝜅 = 2, 𝜅 ≥ 3 and unanswerable. Every answerable question has a gold turn. 

LoCoMo data. LoCoMo has 10 conversations of 369 to 689 turns and 1,540 scored questions (332 with 𝜅 ≥ 2), 385 in development conversations 0 to 2 and 1,155 in test conversations 3 to 9. 

Rendering and budget. On LongMemEval, selected turns are grouped by session, sessions are ordered by date, and each ses-sion block follows the official template with the session date and the turns as JSON. Token counts use the o200k tokenizer, and, un-like the official turn-level retriever, we group the selected turns of one session into one chunk for every system. On LoCoMo, the slate starts with a fixed header and lists the selected turns under session headers with dates, as speaker and text with image captions. 

Answering and judging. Answers are limited to 600 tokens, and Qwen3-32B runs with FP8 weights under vLLM with thinking dis-abled. DeepSeek V4.1 Flash runs through OpenRouter with one pinned FP8 provider, no fallback and reasoning disabled. Every sys-tem of the LongMemEval comparisons was answered on DeepInfra. The GPT-4o judge uses the official per-type prompts at temperature 0, on the test split only, with duplicate judge prompts scored once. 

Decoding variability. Re-answering identical slates on a second machine agrees per question on 85.6% for Qwen and 95.7% for DeepSeek, while re-judging identical answers agrees on 99.9% (Co-hen’s 𝜅 0.997). These observations agree with reports that hosted LLM inference is not deterministic at temperature 0 [2], that batch size and hardware change outputs [45], and that prompt format-ting changes accuracy [35]. Averaging over four perturbed slates changed no primary label. 

Noise across budgets. On one backend, the accuracy of the LLM-ranked reference across four near-identical budgets of 2,400 to 2,700 tokens on LongMemEval-M spans 2.6 points for Qwen and 3.3 for DeepSeek, the noise scale behind the 3-point margin. 

Qwen judge calibration. On 2,000 LongMemEval-S answers by GPT-4o-mini, the Qwen3-32B judge agrees with GPT-4o on 97.3% (Cohen’s kappa 0.904). Under the Qwen judge, every primary label of both LongMemEval variants is the same as under GPT-4o except AgentMemRec against Ref with DeepSeek on LongMemEval-M, which is parity ( +3.6) instead of a gain ( +5.1).

## C Case Studies 

Table 6 follows three test questions whose evidence the cheap rankings and the memory systems miss. 

Ordering events. The five evidence turns of the concerts question open five sessions, and each mentions a concert in passing while asking for something else. In the 128-turn pool, the recall order ranks them 1, 14, 38, 61 and 67 and the cross-encoder 11, 16, 23, 36 and 47, so their slates keep one and two of them, and Ref’s 64-turn pool misses one. The ranker of AgentMemRec moves them to ranks 1, 2, 3, 6 and 7, in line with the weight of the turn-context features in Table 4, and only its slate keeps all five. 

Counting events. The festivals question asks for a count, which needs every mention, and its six evidence turns lie in three sessions. The recall order ranks them 4 to 51, and AgentMemRec ranks all six within the first 14 and keeps them in its slate, as Ref does with 64 LLM calls. Every selector that drops a mention gives a wrong count, except A-Mem on two of four slates. 

Resolving time. The investment question refers to an event four weeks before the question date. Its one evidence turn, from that day, reads “I actually got my own set of sculpting tools . . . today” without naming the competition. The recall order ranks it 89 and the cross-encoder 65, Ref’s 64-turn pool misses it, and even LLM rankers that score all 128 turns with Qwen3-8B or Qwen3-32B leave it out of their slates. AgentMemRec ranks it 14 and keeps it, and it is the only system that answers correctly. 

Ordering three events. A fourth question asks for the order of three sports events in one month, each mentioned in the opening turn of a session. The recall order ranks the three turns 17, 29 and 86, and Ref’s 64-turn pool misses the last, so Ref answers wrongly on every slate. AgentMemRec ranks them 1, 2 and 10 and answers correctly on every slate, while Adaptive-k, DynamicRAG, HippoRAG 2 and A-Mem keep at most one of them. 

What the cases share. In all four questions, the recall order ranks some evidence turns too low for the budget, and the slates of the memory and context-selection methods miss evidence. The learned ranker lifts every evidence turn into the slate, the completeness term that carries the margins of Section 6.2. It does so with no LLM call, where Ref spends 64 per question and still misses evidence in three of the four questions. 

## D Baselines and Deviations 

Adaptive-k. We follow the official code and settings: the rule keeps the turns up to the largest gap in the sorted bge-m3 similari-ties of the whole history, ignoring the extreme 10% tail, and then five more turns. The kept turns fill the slate in similarity order up to the budget cap, which binds for 4% of questions. 

DynamicRAG. We run the released DynamicRAG-8B with the official template and prompt on the top 40 fused turns, each with its session date and role and truncated to 600 characters in the selector input, sampling at temperature 0.4. The selected turns are rendered in full in the returned order up to the budget, and every output was non-empty on the 209 LongMemEval-S test questions. 

LongMemEval memory design. Values are rounds, keys are user turns expanded with user facts, and the ranking is dense. The ex-tractor is Qwen3-32B instead of Llama-3.1-8B, with one call per unique user message, and a bge-m3 arm was chosen on develop-ment data over the official Stella encoder. Slates hold whole rounds at the shared budgets, where the paper uses ten uncapped rounds (run here as a reference arm), and time-aware query expansion was not run. 

HippoRAG 2. We use one passage per round and one index per history, with the official retrieval, recognition filter and personalized PageRank. Qwen3-32B replaces Llama-3.3-70B, bge-m3 replaces NV-Embed-v2, and the filter prompt tuned for Llama is used verbatim. ## E Results on LongMemEval-M 

Under GPT-4o with four slates (Table 7), AgentMemRec is at par-ity with Ref for Qwen ( +3.3) and exceeds it for DeepSeek ( +5.1), which the Qwen judge labels parity. It exceeds the other systems by 10.6 to 33.3 points, all gains, and the LongMemEval design and HippoRAG 2 reach slate completeness 0.495 and 0.342 against 0.861. At write time, these two make 251,622 and about 512,000 LLM calls on LongMemEval-M, and AgentMemRec makes none. 

Single-decode primary test. The single-decode runs (Qwen judge) were the primary test, with the averaged protocol as their replica-tion: AgentMemRec scores 68.9 and 79.9 against 65.6 and 76.1 for Ref ( +3.3 and +3.8), parity for both models. Label-controlled slates on LongMemEval-M ( 𝜅 ≥ 2, all 300 ques-tions, Qwen3-32B judge, one decode, 𝐵 = 2,700) give slate com-pleteness and Qwen and DeepSeek accuracy of 0.823, 0.690 and 0.780 for the LLM ranker, and 0.850, 0.727 and 0.807 for gold in pool then cross-encoder order. With all gold first, they are 0.773 and 0.883 with cross-encoder order, 0.720 and 0.857 with LLM-ranked filler, and 0.827 and 0.927 with random filler. The gold turns alone (238 tokens) give 0.897 and 0.903. With the gold turns fixed, ranked near-miss filler thus costs more than random filler of the same length for both answering models.
