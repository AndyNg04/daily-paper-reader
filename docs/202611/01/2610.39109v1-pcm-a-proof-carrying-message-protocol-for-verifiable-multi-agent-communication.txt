Abstract 

When one AI agent tells another that “the tests passed” or “a person approved this refund” , the receiver has only the sender’s word. A2A and MCP authenticate the channel, but the sender is the party in doubt. A prompt-injected agent can launder fabricated facts and authority through a multi-agent system. We present Proof-Carrying Messages (PCM) , a protocol in which each claim carries evidence : records from an append-only Merkle log that the agent cannot write, with inclusion proofs, signed by an attesting signer the agent cannot control. Receivers check messages offline and give each claim a three-valued result: proven , unproven or failed . A claim that rests only on the agent’s own report is never proven . Authority travels as grant chains rooted in a recorded human approval, and the chains can only narrow. We specify four claim types, a typed caveat algebra, replay rules that survive restarts, and “strict readings” that make independent verifiers agree, and we prove the resulting security properties. On a pre-specified benchmark of 926 messages from real runs, 712 of them lies in 16 classes, PCM accepts 10 lies, all of them stale evidence (1.4%, 95% CI 0.8–2.6%). ## 1 Introduction 

Large language model (LLM) agents increasingly work in teams. A planning agent delegates to a coding agent, a customer-service agent asks a payments agent to issue a refund, and a research agent hands results to a writing agent. Protocols such as Google’s Agent2Agent (A2A) [1] and Anthropic’s Model Context Protocol (MCP) [2] have standardised how such messages are framed, addressed and transported. What they leave open is the question every receiving agent faces: 

should I believe what this message says happened? 

Consider agent A asking agent B to refund $120 on order 81. Alongside the request, A asserts three facts: (i) “alice approved refunds up to $200 for this order”; (ii) “the refund tests passed”; and (iii) “I fetched the order from api.example.com ”. 

B has only A’s word for each. If A was prompt-injected [20, 29], if a hallucination turned a failed tool call into a reported success, or if another process sends the message in A’s name, B pays out anyway. Authenticating the channel does not help: TLS, mTLS, a signed A2A Agent Card or an RFC 9421 HTTP signature [4] all prove who sent the message, and the sender is the very party whose claims are in doubt. A lying agent that signs with its own key signs its own lie. The problem is sharper for LLM agents than for conventional services, for three reasons. First, an agent’s behaviour is driven by untrusted text, so any agent that reads a web page, an email or a tool result may be steered by an adversary [14, 20, 38]. Second, LLMs are known to report tool outcomes that did not occur [5], so even an uncompromised agent’s self-report is weak evidence. Third, multi-agent pipelines compose: a single false claim accepted at one hop becomes a premise for every agent downstream, and authority granted to one agent is easily re-presented by another [24, 32]. What is missing is not a better transport but a way for the content of a message to carry its own justification. 

Our approach. We take our cue from proof-carrying code [26, 27]. There the producer of untrusted code ships a proof of a safety property, and the consumer checks it with a small checker instead of trusting the producer. Proof-Carrying Messages (PCM) apply the same shape to agent communication. The “proof” is not a formal derivation but cryptographic evidence that an event was recorded by a party other than the agent :1. The agent’s tool calls go through an attesting signer , a service the agent cannot control. It holds every key, decides policy, and records each call in an append-only Merkle log that the agent cannot write. Calls that matter run through an attesting gateway or executor, which records the result itself. 2. When the agent sends a message, the signer signs it as the calling run , and the message carries the log records that back each claim, with RFC 9162 inclusion proofs [23] under a signed checkpoint. 3. The receiver checks the signature, the proofs and the records offline , against keys it pins, and gives each claim one of three results: proven , unproven or failed .Authority is handled in the same spirit. A request travels with a grant chain whose root exists only because a named person approved its exact terms, and each later link can only narrow its parent under a fixed, typed implication table. No agent ever holds a signing key. The signer checks each

Headline results. PCM accepts 10 of 712 lies (1.4%; 95% CI 0.8–2.6%), and all 10 are of one kind, stale evidence: a suite passed, the code changed and the suite failed, and the sender cites the pass. Every other lie, 702 of 712, is either rejected (626) or explicitly flagged accept-unproven (76), across the claim, evidence, authority, delivery, encoding and message scopes. The deployed protocols we model accept 70.8–100% of the same lies; stacking AP2, SCITT and RFC 9421 still accepts 51.3%. What PCM does not do. PCM does not make a compromised agent honest: a prompt-injected agent can still ask for anything its grants allow, and the grant, not the agent, sets the limit. PCM authenticates the signer’s records , so the signer is the trusted computing base. A claim says that something happened , not that it still holds. We state these limits precisely in Sections 3 and 13 and show that they explain every remaining error in the evaluation.

## 2 Background 

Agent protocols. A2A [1] defines how agents discover each other (through an Agent Card , which A2A 1.0 lets the card’s owner sign as a JWS), exchange messages made of typed parts , and manage long-running tasks. MCP [2] connects a model to tools and resources. Both carry content and can run over authenticated transports. Neither defines a way for the receiver of a message to check, independently of the sender, a statement about what the sender did. ANP signs requests with RFC 9421 HTTP Message Signatures [4] under the sender’s DID key, adds a time window and a nonce cache, and states explicitly that authentication alone does not imply business authority. In the payments domain, AP2 [3] and Mastercard’s Verifiable Intent [25] carry signed mandates :SD-JWT credentials that record who authorised a purchase, under which constraints and until when. 

Transparency logs. Certificate Transparency (CT) [22, 23] introduced append-only Merkle logs whose operators sign a checkpoint (a tree size and root hash). Any party can verify that a leaf is in the tree with an inclusion proof of ⌈log 2 n⌉ hashes. Leaves are hashed as SHA256 (0x00 ∥ ℓ) and interior nodes as SHA256 (0x01 ∥ a ∥ b), which separates the two domains. The C2SP specifications fix a text format for signed notes [12], for checkpoints [10] and for witness cosignatures [11]. A 

witness cosigns a checkpoint only if it is consistent with every checkpoint the witness saw before, which makes a log that shows different histories to different parties detectable. SCITT (RFC 9943, with COSE Receipts, RFC 9942) [7, 33] generalises this to signed statements about supply-chain artefacts.

Canonical JSON. The JSON Canonicalization Scheme (JCS, RFC 8785) [30] maps a JSON value to a unique byte string: object members sorted by UTF-16 code units, numbers in the ECMAScript shortest round-trip form, and minimal string escaping. PCM hashes and signs only JCS bytes, so two implementations that parse the same value sign and verify the same bytes. 

Capability tokens. Macaroons [6], Biscuit [8] and UCAN [36] are bearer or holder-of-key creden-tials that a holder can attenuate offline by adding caveats. Biscuit expresses caveats and policies in Datalog. In all three, the delegating party holds the key that attenuates. 

Proof-carrying code and provenance. Proof-carrying code [26, 27] ships a machine-checkable proof with untrusted code, so that a small trusted checker replaces trust in the producer. Supply-chain provenance frameworks such as in-toto [34] and SLSA [28] sign statements about build steps. SLSA in particular holds that provenance should be generated by the build platform , not by the build’s own (possibly compromised) steps. PCM’s T1/T2 distinction (Section 5) is the per-claim analogue of that principle. 

Running example. Throughout, agent A (identity uid:990101 ) sends agent B (uid:990102 ) the intent refund.request with arguments {"amount": 12000, "order": 81} (amounts are integer cents). The message carries a root grant that alice ( uid:990001 ) approved, amount <= 20000 and

## 3 System and Threat Model 

3.1 Parties 

Table 1 lists the parties. An agent is any program that calls tools and sends messages; PCM never trusts it. A run is one session of an agent within a log. It has an identifier and a tenant (an isolation unit within one log), and the signer binds it to the transport identity that registered it, written 

> scheme:subject

, for example uid:990101 or an mTLS SPIFFE ID. The attesting signer is a service the agent reaches over an authenticated channel. It keeps the run’s events in an append-only Merkle log and signs, with its log key , the log’s checkpoints, PCM messages and PCM grants. The receiver 

pins the log keys it trusts in a trust document and keeps replay state. 

3.2 Adversary 

We consider an adversary that fully controls the sending agent . It may be a prompt-injected LLM, a hallucinating LLM, malicious code in the agent’s process, or another process that holds the agent’s credential. The adversary • composes arbitrary message bodies, claims, evidence selections and grant chains, and may submit any body to the signer for signing; • reports arbitrary T1 tool results, chooses the identifiers ( tool_use_id ) of its own calls, and names tools as it likes; • writes any file the agent can write, including test-runner configuration in its working directory; • records, replays, reorders, drops and redirects messages on the network, and sends messages to any receiver;

3.3 Goals 

G1 Origin. A receiver accepts a message only if an honest signer signed that exact body, as the run that appears in from .

G2 Evidence soundness. A claim is proven only if the sender’s run contains signer-appended records, written by a party other than the agent, that establish exactly what the claim states. 

G3 No self-attestation. No combination of the agent’s own reports (T1) makes a claim proven .

G4 Attenuated authority. Any authority a message presents is no wider than what a configured person approved: never widened at a delegation step, never past its expiry, and never moved to another tenant or log. 

G5 Freshness of delivery. A receiver acts on each message at most once, including across restarts and replicas, and only if the message is addressed to it. 

G6 Determinism. Any two conforming verifiers return the same verdict, claim results and conformance fields on the same inputs.

G7 Honest progress. Honest senders who follow the specification get their claims proven and their messages accepted. 

3.4 Non-goals 

PCM does not (N1) make the agent’s intentions trustworthy, since a compromised agent may send any request its grants allow; (N2) prove that a state is current , since a claim is existential, “a call happened”, and a later event can undo it; (N3) prove absence , since the sender chooses which records to disclose; (N4) provide confidentiality, which TLS does; or (N5) protect against a compromised signer or a leaked log key (Section 9.6). 

3.5 Assumptions 

Assumption 1 (Cryptography) . Ed25519 with the strict verification rules of Section 8.1 is exis-tentially unforgeable under chosen-message attack (EUF-CMA). SHA-256 is collision-resistant. HMAC-SHA256 is a binding commitment when keyed by a uniformly random 32-byte salt. 

Assumption 2 (Honest signer) . The signer for each pinned log (i) signs a message only as the calling run, and sets id , ts and nonce itself; (ii) assigns each record’s seq and ts as it appends it; (iii) sets a record’s top-level source /tier to gateway /T2 only for results reported by an authenticated attesting gateway or executor; (iv) writes approval and approval.request 

records only from authenticated answers and its own requests, and effect.observed only from observer reports; (v) issues a root grant only under Section 7.3’s conditions and a child only under Section 7.4’s; and (vi) never lets an agent read its keys or write its log. 

Assumption 3 (Honest attesting parties) . An attesting gateway or executor records a call under a tool name that the frozen placement table maps to class k only if the tool it ran is of class k, and records ok only if the call succeeded. 

Assumption 4 (Clocks and receivers) . The clocks of signer and receiver agree within the receiver’s replay window. A receiver keeps one replay state per identity, shared by all replicas that answer for that identity. Assumption 2 makes the signer the trusted computing base, much as a CT log operator, a SLSA build platform or a hardware root of trust is trusted in its own setting. Section 9.6 analyses what follows if it fails. We note that the assumption is operational : a deployment satisfies it by running the signer as a different user, on a different host or in a different trust domain from the agents it records.

4.3 Claims, evidence and grants at a glance 

A claim is a typed statement about the sender’s own run: tests_passed{suite} , approved_by{person, call, covers?} , reached_host{host} or file_written{path, digest} . Its optional evidence is a C2SP checkpoint note signed by the log key together with 1–16 records of the sender’s run, each with its hash and RFC 9162 inclusion proof. A record of a policy.decision may also carry an 

opening , a salt and the arguments, which opens the HMAC commitment to the call’s arguments that the signer stored instead of the arguments themselves (Section 5.3). A grant states that a subject may send an intent within typed caveats until a time. The chain is root first, and the root’s issuer is a person (Section 7). 

4.4 Outcomes 

The verifier returns a structured result (Algorithm 2): signature, replay, schema and grant sub-results, one result per claim, and a verdict. A accept means that everything required is proven. A 

accept-unproven means that nothing failed but something rests on the sender’s word, and a receiver 

should treat it as testimony. A reject must never be acted on. The result also names any checks the caller skipped (no replay state, no receiver identity); a non-empty skipped marks an audit result that must not drive action.

7.3 Root grants come from a person 

A caveat-free grant is the widest grant, so the root of authority must be human. The signer issues a root grant ( parent: null ) only if all of the following hold: an approvals configuration names who may answer; the agent made a tool call pcm.grant whose args are exactly the grant’s subject, intent, caveats, expiry and delegability, and that call was approved and the approval consumed with exactly those args; the approver is a person mapped to a name, not an agent approver, not the run’s own agent or its person (self-approval), and not the grant’s subject; expires_at is in the future and at most 24 hours away; the call has no result yet (one grant per approval); and the run is not held or quarantined. The issuer then becomes {kind: person, id, person, run, tenant, approval_id} . A policy that never asks a person about pcm.grant leaves nothing to consume, so no root grant can exist: the design fails closed. 

7.4 Delegation 

The subject of a delegable grant may ask the signer for a child. The signer refuses unless the parent verifies under its own log key, belongs to the caller’s tenant, names the caller as subject, is delegable and unexpired, and the child expires no later than the parent and narrows it. The child is issued by {kind: agent, id: caller} , for the parent’s intent, with parent = H(parent ).A child needs no further approval, since by Theorem 4 it grants nothing new.

## 10 Determinism by Construction 

A verification protocol is only as strong as its weakest conforming verifier . If two verifiers can disagree on a message, an adversary can probe for the more permissive one, and a sender cannot know whether its honest message will be accepted. Determinism (G6) is therefore a security property, not a convenience. It is also hard to achieve: PCM’s verdicts depend on parsing JSON, base64, URLs, IP addresses, shell command lines, file paths and regular expressions, and widely used libraries disagree on every one of them.

Where the field is one the sender cannot simply rewrite (a host in a URL that was really fetched, the path of a call that really ran), a claim whose decisive field reads as ⊥ is unproven ,never proven and never failed . 1. Closed, strictly parsed objects. Every JSON object in PCM is closed and every pattern matches the whole value with ASCII classes. Parsing refuses duplicate names, lone surrogates, numbers outside the double range and integers past 2 53 , so every verifier works from the same parsed value, and JCS gives that value the same bytes everywhere. 2. Notes name the standard-library functions that behave as a step does (so a Python verifier can call urlsplit after applying the bracket rule itself), but the step, not the library, is the rule. 3. Protocol data, frozen and hashed. The tool placement table (54 names) and the runner list (42 sequences) are part of the protocol and shipped with every verifier (the table is also identified by its SHA-256), never taken from a message or an operator. 4. Conformance fields. The result fields that receivers act on ( verdict , sub-results, each claim’s result, approved , skipped ) are compared on every vector, while human-readable strings are not. ## 11 Implementation 

Reference implementation. Tracekit 1.5.0 [19] (signer RPC contract 20) implements every part of PCM 0.1 marked Implemented in the specification. Its attesting signer serves four PCM calls: 

pcm_sign signs a message body as the calling run, pcm_grant issues a root grant from a consumed person approval, pcm_delegate issues a narrowing child, and pcm_evidence returns records of the caller’s own run with inclusion proofs. The signer assigns every record’s ts from its own clock when it appends the record. It writes a checkpoint at most once per second on request (and every 10 s while the log grows), so an honest sender has evidence about one second after a call. It records an ext record for every message and grant it signs. Its executor runs tool calls under the signer’s custody protocol (decide, ask a person, consume the approval, complete as the executor’s identity) and reports T2 results. A log may also pin a hybrid SLH-DSA-SHA2-128s key (FIPS 205) under the log’s name, in which case every checkpoint needs a valid post-quantum signature line as well. Known gaps of the reference implementation. The specification records where Tracekit does less than it asks. Replay state is per process, so a deployment with several replicas per receiver identity must route each sender to one replica. And until a pcm.grant call has its result, repeated grant requests on one consumed approval can mint grants that differ only in ts , which the specification permits but discourages. Transport bindings are drafts: Tracekit ’s A2A gateway forwards a PCM part without verifying it. 

## 12 Evaluation: PCM-Lies 

We ask how often a receiving agent accepts a false claim from a sending agent, and at what cost to honest senders. The evaluation addresses six research questions: 

RQ1 (Safety). How many lies does a PCM receiver accept, and of which kinds? 

RQ2 (Honest progress). Are honest claims backed by attested evidence proven? 

RQ3 (No self-attestation). Are claims backed only by the agent’s own reports ever proven? 

RQ4 (Determinism). Do independent verifiers agree? 

RQ5 (Comparison). What do existing agent protocols let a receiver catch, and why? 

RQ6 (Cost). How large are PCM messages, and how long does verification take? 

12.1 Methodology 

Pre-specified design. Before the first benchmark run, we wrote down the threat model, a taxonomy of 16 lie classes, four hypotheses with pass bars, the two baselines, and the cost metrics: • H1 : no lie is accepted (0 false accepts); • H2 : at least 99% of honest claims backed by T2 or signer records are proven ;• H3 : every claim backed only by T1 is unproven ;• H4 : the two verifiers give the same verdict and reason class on every message. The design was a dated planning note written before the first benchmark commit. It has no independent public timestamp, so we present it as a pre-specified design rather than a registered one, and list every departure from it in Section 12.8. The six real-protocol receivers were added after the results and are covered by no hypothesis. 

Ground truth from real runs. Every message comes from runs of a real Tracekit 1.5.0 signer, and all T2 calls go through the executor’s own custody code. The tools really run. pytest runs 12 suites that pass, 12 that fail, 5 that pass and then fail after a code change, and 10 look-alike test files, all in a temporary project. HTTP fetches go to a local server on 127.0.0.1 and ::1 . Files are written in a temporary directory. Refunds and read_file calls are answered by person identities (alice, carol, erin), by an unmapped approver (dave) and by an agent approver. Root grants come from a person’s approval of pcm.grant , and delegations from pcm_delegate . Egress-observer records are included. Each message is labelled true , false or unknowable (the only evidence is T1 ) at construction time, from what happened , never by a verifier. For tests, the label is the exit code of the suite’s latest run. For hosts, it is the connection’s destination as the machine’s resolver gives it. For files, it is the inode and the digest at send time. For approvals, it is who answered what. A lie

12.2 RQ1: Safety 

Table 9 reports the pre-specified hypotheses, and Figure 7 shows PCM’s verdict on every lie class. H1 fails, and it fails in exactly one way. All 10 false accepts are L10.T.06 –10 and L10.F.06 –10 . In the first five, a suite passed, the code changed and the suite failed, and the sender cites the pass under the checkpoint from before the failure. In the other five, a file was written twice and the sender cites the first write. In both cases the claim is genuinely proven : the call happened, through an attesting executor, and the claim type asserts that a call happened, not that nothing happened since. This is the existential semantics of PCM 0.1 (non-goal N2), stated in the specification before 

the benchmark (S14.13). The pre-specified taxonomy nonetheless labels these messages as lies, and we keep that label. Section 13 discusses the receiver-side mitigations and the design for fresh evidence. 

Every other lie, 702 of 712, is not accepted : 626 are rejected and 76 are flagged accept-unproven .The flagged ones are the 36 T1 -only lies of L4 (correct by H3), and 40 lies whose claim the verifier cannot decide (for instance, a fabricated claim with no evidence, or a host that will not parse). A receiver that follows the specification treats these as testimony and does not act on them as fact.

12.4 RQ4: Determinism 

H4 passes. On all 926 messages, Tracekit ’s verifier and the standalone verifier agree on the verdict, the reason class and every conformance field, including messages sent as raw text through each verifier’s own strict loader. The benchmark had already earned its keep here: the run before the fixes found five disagreements, all caused by 1e400 (F5). Median verification time is 1.22 ms for

12.5 RQ5: What existing protocols catch 

Figures 1 and 8 and Table 10 compare the receivers. Three patterns stand out. 

Authenticating the sender does not authenticate the content. The signed Agent Card catches nothing, because it authenticates a sender who is the liar and leaves messages unsigned. The uAgents envelope catches the 10 replays addressed to another receiver. It has no nonce cache, and it reads 

expires as a reply timeout, so the other 40 replays pass. RFC 9421 with replay checks catches 30 of 50 replays (same nonce, another receiver, outside the window). It misses the 10 replays after a receiver restart, because its cache lives in memory, and the 10 below the floor, because it keeps no per-sender floor. It also misses every content lie, which the sender simply re-signs. 

Transparency without semantics catches forged evidence, not false claims. SCITT receipts catch 162 lies, all at the evidence layer: proofs for another tree (all 48 of L9), edited records (45 of 66 in L5), forged checkpoint signatures, unpinned logs, and claims without records. They miss true records cited for false claims (L1–L3), because SCITT has no rule that ties a claim to a record. They also miss the agent’s own reports (L4), because SCITT has no tiers; records of another run or tenant; every replay; and every grant lie.

12.6 Findings: what the benchmark changed 

A benchmark is only useful if it can find bugs, and PCM-Lies found three (Table 11). F1 is a platform-dependent attack. The executor fetched http://0127.0.0.1/ and macOS connected to 

127.0.0.1 , but the specification read the host as inet_aton does, so a claim of 87.0.0.1 , an address never contacted, was proven . F3 showed that leaving the comparison of approved with the intent to receivers fails in practice: a receiver acting on the verdict alone accepted a $5 approval for a $50 request. It motivated covers . F5 was a determinism bug. Each was fixed in the specification and both verifiers and pinned by vectors. The dataset grew by 47 messages to exercise the fixes, and the benchmark was re-run. Across the 875 messages the two datasets share, the only verdict changes are accept → accept-unproven (26 messages), and the only reason-class change is F5’s.

12.8 Threats to validity 

Departures from the pre-specified design. The design called for an improve loop that would repeat “until H1–H4 pass”. We stopped with H1 and H2 failing because their causes, F2 and F4, are properties of the 0.1 claim semantics and evidence profile. Fixing them requires format changes, which we specify for a later draft rather than fold into this evaluation. The dataset grew after the first run (47 messages for the fixes). Four honest fetches with numeric host spellings were moved to L16, so that H2 measures a sender that follows the specification. L11 gained two replay kinds (outside the window and below the floor). The sender-signature baseline checks the PCM signer’s key, which the sender cannot use, so it catches forged and stripped signatures and accepts 643 of the lies rather than all of them. H2 was first counted per message and is now counted per claim, as specified. One message ( L15.G.13 ) was relabelled before the final run of dataset 1. The design note has no public timestamp prior to the results. 

Internal validity. Labels come from the generator’s record of what happened, never from a verifier. Dataset 1 was generated three times and gave the same counts in every cell, apart from the relabel. Dataset 2 was generated once. Ids, nonces, timestamps and signatures change between generations, while the seed (20261028) fixes keys and choices. 

External validity. All runs used one machine (macOS 26.3, arm64, Python 3.11.15). F1 depended on the platform: glibc reads leading-zero octets as octal, so a Linux-generated dataset labels some L16 messages differently. The signer and executor ran in-process, the executor was Tracekit ’s custody code with an in-process client rather than the HTTP executor service, and host names were served by the local server without real DNS. The six protocol receivers are models built from specifications, not runs of their SDKs. They omit transport security (which authenticates the liar too) and VI’s suggested mandate lifetimes. By our reading of their specifications, MCP, IBM ACP, LangChain Agent Protocol, Agora, Coral and FIPA-ACL reduce to plain A2A on these claims, and Visa TAP and the OpenAI/Stripe Agentic Commerce Protocol to RFC 9421 with replay checks at best; we did not measure them. Finally, the lie taxonomy is ours. Lies outside it (for example, an

## 13 Discussion and Limitations 

13.1 Evidence is not freshness 

Every PCM 0.1 claim type is existential: “a call ran and succeeded”. The sender chooses which records to disclose, so evidence can show that something happened, but never that nothing happened since. This explains all 10 false accepts in Section 12. Within 0.1, a receiver that acts on current state applies three checks. First, an age bound : it refuses evidence whose oldest record is older than a per-intent bound (seconds or minutes) relative to the message ts . It uses the oldest record because a sender can always add newer ones, and it compares only times set by the log, so the receiver’s clock plays no part. Second, an after-last-change bound : when the receiver knows when the thing it acts on last changed (the commit to merge was pushed, or it sent the request), it refuses older evidence. Third, for files, a digest check over the bytes it holds, which is the one check that rules out a later change outright. Both verifiers print the evidence age to support the first check. For a later draft we have designed two mechanisms (Section C). The run since the call adds a signer-set head to the envelope, naming the last record of the sender’s run at signing time, and an evidence form that carries every record of the run from the claimed call up to head . These records are chained by the per-run run_prev_hash that the log already maintains, so no record in between can be omitted, and a later failure of the same suite or a later write of the same path becomes visible. Bound claims have the executor record what a call ran on: the git tree id of a fresh checkout for tests_passed , and the path and digest it read back for file_written . A receiver then compares the tree with the commit it will merge. Together they would close the L10 class at a cost of roughly 1 KB per later record. 

13.2 A response is not a failure 

An HTTP 404 proves that the host was reached, but the 0.1 evidence profile records only whether a result was ok , and the executor records a status of 400 or more as not ok . Honest claims of this kind are therefore failed , which is the cause of both H2 misses. An egress observer’s record proves the connection whatever the answer. PCM 0.2 can record the protocol status, so that reached_host 

rests on any response. 

13.3 Trust in the signer and in executors 

PCM moves trust from the agent to the signer, but does not remove it. A compromised signer, or a caller who can make it sign as another identity, can mint anything (Section 9.6). A second, subtler dependency is on executors. A verifier places a T2 call by its tool name, so an executor that runs operator-named HTTP actions could record one under the name Bash , and an HTTP request that succeeded would then prove tests_passed . The specification forbids logs that offer the evidence profile from recording a tool under a name of another class. A future trust member would let receivers pin which attesting parties may attest each tool class. 

13.4 What a proof does not say 

A proven tests_passed proves that a specific command line exited 0 through an executor. It does not prove that the tests that matter ran: runner flags and configuration files in the working  

> 38 PCM: Proof-Carrying Messages for Multi-Agent Communication Cygnux Labs

directory can make a suite vacuous. Receivers therefore compare suite with the suites they accept. A proven drive-path file_written assumes a Windows executor. A proven approved_by without  

> covers

says what alice approved, and that may not be what is now being requested; that is why requiring schemas accept only covering approvals. PCM 0.1 also cannot prove absence (“no other call happened”). These limits are stated in the specification so that receivers do not read more into proven than the record supports. 

13.5 Privacy 

A receiver learns the sender’s identity, run and tenant, the intent and its args, the payload, and every grant in the chain, including the approving person’s identity and name. From evidence it learns the disclosed records in full (types, times, tool names, call ids, approvers, policy outcomes, observed hosts), the log’s size at the checkpoint, and the args of opened decisions. It does not learn records that were not sent, or the args of unopened decisions. Commitments hide those args, but an opening is permanent and, because the message is signed, attributable. A salt also exposes low-entropy args to brute force, which is why the signer hands salts only to the run’s own agent. Senders should disclose the minimum each claim needs. 

13.6 Implications for LLM agent systems 

PCM is complementary to defences that harden a single agent against prompt injection, such as instruction hierarchies, dual-LLM and capability-based designs [15, 37], and benchmarks such as AgentDojo [14]. Those defences reduce the chance that an agent is subverted. PCM bounds what a subverted agent can make others believe and do. Three integration patterns follow. • Verifier as a gate. The receiving framework verifies each PCM part before the model sees it and drops reject parts. The model then sees each claim annotated with its result (proven, or “the sender says”), so the planner reasons over structured provenance rather than free text. • Authority outside the model. Grants and their caveats are checked by code, so a prompt-injected sender cannot talk a receiver into exceeding them: the grant, not the model, sets the limit. • Auditable pipelines. When the signer records every message signed and every grant issued, as the specification recommends and Tracekit does, a multi-agent run leaves a verifiable, append-only trail of who asserted what, on which evidence, under whose authority. Agents increasingly exchange model state as well as text, for example by fusing one model’s KV cache into another’s (cache-to-cache transfer) [17]. A draft extension in the specification records such transfers (sender and receiver model ids, modality, projector, size and digest) as a signer-decided call, so that a receiver can at least check that the bytes it received are the bytes the sender declared to its signer before the transfer. Nothing in that record proves what the state means.

Transparency logs. PCM’s evidence format is that of Certificate Transparency [22, 23], with C2SP notes, checkpoints and witness cosignatures [10–12]. CT logs certificates for public audit, whereas PCM hands a receiver the handful of records of one run that back one claim, from a log that may be private to a deployment. SCITT [7, 33] checks that a signed statement is in a transparency log. Individual drafts profile it for agent actions, but SCITT itself has no rule that ties a claim to a record, no T1/T2 distinction, no replay rule and no grants. Our benchmark shows the consequence: true records cited for false claims pass (Section 12). PCM adds exactly these semantics over the same kind of evidence. 

Capability-based authorisation. Macaroons [6], Biscuit [8] and UCAN [36] support offline attenuation by the holder. PCM grants also only narrow, but no agent holds a key: the signer signs each step after checking it. A root exists only after a person’s recorded approval of its exact terms, and caveats are typed by the intent’s schema and compared with a fixed table (Table 3) rather than a general logic such as Biscuit’s Datalog. The table is deliberately incomplete (bounds never imply equality), which trades expressiveness for verdicts that are identical across implementations. South et al. [32] extend OAuth 2.0 and OpenID Connect with agent credentials and scoped delegation, which answers on whose behalf an agent acts. PCM is complementary: it adds claims about what the agent did, and grants that a receiver checks offline. 

Agent payment mandates. AP2 [3], now stewarded by the FIDO Alliance, checks a chain of SD-JWT mandates for a purchase: who authorised it, within which constraints, until when, bound to the agent’s key. Mastercard’s Verifiable Intent [25] adds an issuer-certified user key. Both answer “was this purchase authorised?”, not “did the agent do what it says?”, and AP2 0.2 excludes agent-to-agent delegation. Our models of both catch most authority lies and none of the lies about tests, hosts or files. Proof-Gated Signing [18] guards a different point of the same pipeline: before a wallet-controlling agent signs a transaction, an SMT solver checks its value and permission policy over the whole range of oracle-price uncertainty, and the result is compiled into on-chain post-conditions that the wallet enforces atomically. It constrains what an agent may do ; PCM

constrains what other agents will believe about what it did. 

Agent receipts and provenance. Tracekit [19], PCM’s reference implementation, records each coding-agent session’s requests, stated reasoning and executed actions in a hash-chained, exter-nally anchorable ledger for audit. PCM builds on its attesting signer and Merkle log, and turns the audit trail into evidence that a receiving agent checks per claim. Notarized Agents [16] has the called service sign a receipt of each action, encrypt it to the agent’s owner and publish it to a witnessed log, so the owner can audit the agent. PCM needs no cooperation from the service. The sender’s attesting signer and executor record the call, and any receiver checks the records offline. NabaOS [5] cross-checks a model’s claims against HMAC-signed tool-execution receipts to detect hallucinated tool results. An HMAC can be checked only with the key that made it, whereas PCM’s records are signed with public keys that any receiver can check, and PCM adds authority and delivery rules. In software supply chains, in-toto [34] signs statements about steps, and SLSA [28] requires that provenance come from the build platform rather than the build’s own steps. PCM applies the SLSA principle per claim, inside a message, and adds a third outcome for what cannot be checked. 

Security of agent protocols. A2ABreak [24] extracts a 37-state machine from the A2A specification and finds 11 vulnerabilities, among them context injection through unprotected context identifiers and identity loss across multi-hop delegation. PCM signs its whole message and makes each delegation step a signed grant that names its issuer and subject, although parts of an A2A message outside the PCM part remain unsigned. Prompt-injection attacks on agents [20, 29, 38] and benchmarks such as AgentDojo [14] motivate PCM’s threat model. Design-level defences such as CaMeL [15] constrain what a single agent may do with untrusted data, while PCM constrains what other agents will believe. 

Cross-implementation disagreement. Parser differentials are a classic source of vulnerabilities: in X.509 and TLS stacks [21], in URL parsers [35], in Ed25519 verification [13] and in JSON parsers [31]. PCM treats differential-freeness as a design requirement. Wherever readers differ it specifies a strict reading, maps divergence to unproven , and pins the outcome with vectors produced by a real signer (Section 10). 

## 15 Conclusion 

Multi-agent systems built on LLMs pass each other claims about what happened and about who allowed what, and today a receiver can do no better than trust the sender. PCM lets each claim carry evidence written by someone other than the agent, lets authority travel as person-rooted chains that only narrow, and has every receiver check both offline, in about a millisecond, with the same answer whatever its implementation. Its three-valued semantics keeps doubt apart from falsity, so a claim the verifier cannot decide costs the sender the proof rather than the message, and a liar cannot turn its own report into proof. On 712 lies built from real runs, PCM accepts only the 10 that its specification already says it cannot catch, while models of today’s deployed protocols accept between 504 and 712. Closing that last class, evidence that a state is still current, is the main work for the next draft, together with a dedicated message key, key rotation, Unicode hosts, and verified transport bindings for A2A and MCP. ## C Design for Fresh Evidence 

This appendix summarises the design that the specification proposes for closing the stale-evidence class (L10) in a later draft. 

The run since the call. The evidence profile already chains each run: every record carries run_seq ,its position in its run, and run_prev_hash , the hash of the run’s previous record. The design adds a signer-set envelope member head = {run_seq : n, hash : digest }, the last record of the sender’s  

> 47 PCM: Proof-Carrying Messages for Multi-Agent Communication Cygnux Labs

run when the signer took the message to sign. It is set like ts , so the agent cannot choose it. The design also adds an evidence item marked "since": true , whose records are the claim’s records followed by every record of the run after the first of them, up to head . The verifier checks that consecutive records have consecutive run_seq values and linked run_prev_hash values, and that the last record matches head . Because the run chain binds each record to the next and the message signature binds head , no record between the call and the message can be omitted. The checkers then read the later records: • tests_passed : a later shell call of the same suite whose result is not ok fails the claim (“the suite failed after it passed”). A later unopened shell call with no result or a failed one makes the claim unproven until the sender opens it. • file_written : a later write of the claimed path with other content fails the claim. A later write whose path is not shown makes it unproven . This requires the table to separate writing from reading tools within fs .The cost is about 1 KB per later record, and a cap bounds how long after the call a sender can claim. The design does not cover runs of the suite in other runs, writes by other processes (the receiver’s digest check covers those), or earlier flaky runs. 

Bound claims. The executor records what a call ran on. For tests_passed{suite, tree} , the agent names a git commit, and the executor checks out its tree into a fresh directory the agent cannot write, runs the suite there and records the tree id. The receiver compares that id with the commit it will merge ( git rev-parse Cˆ{tree} ). Hashing the agent’s working directory instead would not do, because an ignored conftest.py changes the result without changing the id. For file_written ,the executor reads the file back after writing and records the absolute path and the digest of the bytes on disk. That record alone then proves the claim without opening the decision, at the cost of the path appearing in clear in the log. 

Responses with an error status. For reached_host , the evidence profile would record whether the call got a response, for example its protocol status, so that a 404 proves the host was reached.
