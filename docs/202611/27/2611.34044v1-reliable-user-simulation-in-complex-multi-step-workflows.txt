## Abstract 

LLM-based user simulators are increasingly used to evaluate conversational assis-tants. Yet, these simulators can drift from their assigned goals or fail to exhaustively explore all specified options, causing evaluation errors incorrectly attributed to the assistant. Prior work has examined goal alignment in single-task settings, but many practical scenarios require simulators to execute multi-step workflows with sequential tasks, fallback logic, and cross-task dependencies, where simulator fidelity has not been measured. To close this gap, we introduce a benchmark of 500 workflows represented using the Hierarchical Task Network (HTN) abstraction. Our experiments reveal that the simulator’s fidelity degrades sharply with work-flow complexity, and that goal drift accounts for the majority of failures. Fidelity also depends on the assistant’s response style, with the same simulator scoring substantially better or worse across styles. To address this, we propose ReUST (Reasoning + User State Tracking), a simple prompting strategy to maintain state information across dialogue turns. ReUST improves goal success rate by more than 12 points for mid-sized and large models, and reduces simulator sensitivity to the assistant’s response style.

LLM-based user simulators are increasingly used to evaluate tool-augmented conversational assistants at scale [Yao et al., 2024, Barres et al., 2025]. An LLM plays the role of a user, talk-ing to an assistant to test whether it can book a hotel, schedule an appointment, or handle a cus-tomer service request. These frameworks rest on the assumption that the simulator faithfully follows its assigned goal. When it does not, and instead drifts from the goal, omits required in-formation, or invents constraints, its mistakes appear as assistant errors. The failure also re-duces coverage; a simulator that abandons a goal before trying the remaining options never steers the conversation to the edge cases the evaluation was designed to check. These approaches evaluate simulators only on single-domain dialogues with a single overall goal. Many practical applications require simulators to execute multi-step workflows, which are structured sequences of tasks with fallback logic, retry behavior, and cross-task dependencies. For example, to test a travel booking workflow, user simulator might require completing hotel reservation, then train booking (with taxi as fallback if trains are unavailable), then restaurant reservation—where the restaurant booking time depends on the train arrival time. No existing benchmark systematically evaluates whether simulators can maintain goal alignment across such complex workflows. We address this gap with two contributions. First, we introduce a 500-workflow evaluation set represented using the Hierarchical Task Network (HTN) abstraction [Nau et al., 2003]. Workflows vary along two axes of difficulty: path length , the number of steps the simulator must attempt before the workflow completes, and fallback depth , the number of tasks whose preferred method fails outright and forces a switch to an alternative. Second, we propose ReUST (Reasoning + User State Tracking), a task-agnostic prompting strategy that requires the simulator to maintain a structured reasoning state across dialogue turns, tracking which options it has tried, what the previous turn returned, and what to do next. We isolate the contribution of each component by ablation (§6.2). We measure Goal Success Rate (GSR), which is the fraction of workflows a simulator completes as prescribed in the goal. Our first finding is that GSR is not a property of the simulator alone: holding the simulator fixed and changing only how the assistant words its replies changes GSR from 62.8% to 92.8%, making the assistant’s response style a substantial confounder for measuring fidelity (§6.1). Our proposed ReUST prompt improves GSR across assistant style making it a practical tool for faithful workflow following user simulators. 

## 2 Related Work 

User Simulators. LLM-based user simulators are now central to scalable dialogue evaluation [Davidson et al., 2023, Ni et al., 2026]. DuetSim [Luo et al., 2024] adds a verifier LLM to catch simulator errors and hallucinations, DAUS [Sekuli´ c et al., 2024] fine-tunes on real dialogue data to improve goal adherence, and UGST [Mehri et al., 2025], closest to our work, decomposes user goals into profile, policy, and task components tracked across turns to prevent goal drift, while ChatChecker [Mayr et al., 2025] probes robustness through non-cooperative user simulation. These methods evaluate single-task scenarios. We extend the question to multi-task workflows that require sequential execution, fallback logic, and cross-task argument propagation. 

Dialogue State Tracking and Reasoning. ReUST’s per-turn state block is closely related to Dialogue State Tracking (DST), which maintains user goals and slot values across turns in task-oriented dialogue. Recent work recasts DST as an LLM task: driving it directly with LLMs [Feng et al., 2023], framing it as zero-shot function calling [Li et al., 2024], and showing zero-shot LLMs performing state tracking and API calls, though still short of specialized models [Hudeˇ cek and Dušek, 2023]. ReUST differs in role and direction: rather than tracking the assistant’s belief state to satisfy a user goal, the simulator tracks its own progress through an assigned workflow. Its structured Thought block follows the reasoning-and-acting lineage of ReAct [Yao et al., 2023], externalizing working memory so the model need not reconstruct it from the transcript at each turn. 

Benchmarks and Datasets. Earlier task-oriented dialogue corpora are static: MultiWOZ [Budzianowski et al., 2020] covers hotel, train, taxi, restaurant, and attraction bookings, and the Schema-Guided Dialogue dataset [Rastogi et al., 2020] extends this to 20 domains with explicit schemas, but both consist of pre-recorded conversations. Interactive benchmarks followed. τ -Bench [Yao et al., 2024] measures task success and consistency across repeated trials under domain policies, and τ 2-Bench [Barres et al., 2025] extends it to a dual-control setting in which the simulated user also executes tools on the shared environment state. ToolSandbox [Lu et al., 2025] adds stateful tool execution and a built-in user simulator for on-policy conversational evaluation. CONFETTI [Alkhouli et al., 2025] evaluates function calling turn by turn. Static or interactive, all of these measure assistant 

capability while assuming faithful user simulation. We turn the measurement on the simulator, asking whether it executes its assigned workflow at all, on dynamic workflows with systematic variation in path length, fallback depth, and cross-task dependencies. Our finding that fidelity degrades with 2workflow complexity matches work on long-horizon tasks [Kwa et al., 2025], where reliability falls as task duration grows.

We represent workflows using the Hierarchical Task Network (HTN) abstraction [Nau et al., 2003, Langley, 2025, Siddiqui et al., 2024]. HTNs allow arbitrary nesting, but we fix a three-level hierarchy of tasks, methods, and steps, which is enough to capture the sequential execution, fallback logic, and retry behavior of real workflows. Each workflow is serialized into deterministic natural-language instructions, and the simulator must decide at each turn whether to retry with the next step, fall back to another method, or advance to the next task. 

3.1 Workflow Structure 

A workflow is a sequence of tasks that must be completed in order (Figure 2). A task is a major unit of work such as Hotel Booking or Inter-city Travel, and the simulator cannot move to the next task until the current one succeeds. Each task can be completed by one or more methods , attempted in sequence: Inter-city Travel might first try Train and fall back to Taxi once every train option fails. Methods correspond to the tools available to the assistant. Each method is an ordered list of steps 

tried one at a time until one succeeds, where a step is a single action with concrete parameter values, such as booking a 7 AM train and then 8 AM if that fails. The entities in a step correspond to tool arguments. 

3.2 Execution Path 

The simulator receives the workflow as a goal and must navigate it through conversation. At each step it makes a request, the assistant executes a tool call, and the simulator learns the outcome only from the assistant’s response. It must then decide whether to advance to the next task, retry with the next step, or switch to a fallback method because the current one is exhausted. The execution path 

is the sequence of steps attempted from start to successful completion. 3.3 Cross-Task Dependencies 

Workflows also contain cross-task dependencies , where the outcome of one task fixes the parameters of a later one. These take three forms: direct propagation , reusing a value from a completed task (“book a taxi on the same day the hotel was reserved”); computed derivation , calculating a value from a prior outcome (“book a taxi 1 hour after the train arrival time”); and conditional branching ,where which value applies depends on how an earlier task resolved (“if the train was booked, book sightseeing 1 hour after train arrival; if the taxi was used instead, 2 hours after taxi arrival”). Handling them requires the simulator to keep a coherent internal state and transform information across task boundaries. Appendix G shows a full simulator goal.

We construct an evaluation set of 500 workflows and ex-ecution paths, stratified evenly across fallback depths (Ta-ble 1). Workflow complexity varies along two dimensions: 

path length , the total number of steps attempted from start to successful completion, and fallback depth , the number of tasks whose primary method fails completely and forces a switch. We build the workflow tasks on the MultiWOZ domains [Budzianowski et al., 2020]—hotel, train, taxi, restaurant, and attraction—each of which supplies realistic booking scenarios with natural constraints such as time slots and availability. We extend beyond single-domain dialogues to workflows whose tasks must be completed in sequence under cross-task dependencies. Each goal is a fixed template of nested conditional instructions, so the simulator must work through the branch structure to successfully achieve the goal. 43.5 Data Generation Pipeline 

Generation runs in three stages. First, we define HTN workflows by sampling tasks and their hierarchy, specifying primary and fallback methods with ordered steps, and sample an execution path from each. Second, for each path we generate the expected behavior at every step: the exact tool call, the argument values, and the correct decision (retry, fallback, or advance). Third, we convert the workflow structure into natural-language instructions covering the task sequence, available methods, ordered steps, and cross-task dependencies. This conversion is rule-based and deterministic, so the same workflow always produces the same goal text. The simulator sees only this text, never the underlying HTN or the sampled path. 

3.6 Controlled Conversation Loop 

The loop runs between the simulator, a conversational assistant, and a scripted environment (Figure 3): the simulator generates natural-language requests, the assistant parses them and executes tool calls, and the environment returns scripted success or failure responses based on the chosen evaluation path. Because the environment fully determines which steps succeed, deviations from ground truth originate almost entirely with the simulator, through incorrect arguments, wrong task selection, bad ordering, or premature fallback switches. The assistant can also err, but a reference-free LLM judge found assistant argument error below 0.4% (§7). 

## 4 Evaluation Metrics 

A simulator can fail in several ways: calling the wrong tool, supplying incorrect arguments, or departing from the prescribed order of steps. Tool Accuracy is the fraction of steps where the correct tool was selected, and Argument Accuracy the fraction where every argument matches ground truth; together they separate navigation errors from argument errors. Survival Rate is the fraction of the workflow completed before the first error, which distinguishes early cascading failures from near-successes. Our primary metric, Goal Success Rate (GSR) [Davidson et al., 2023], asks whether the simulator executed the whole workflow exactly as prescribed: every expected call, in order, with correct arguments. Formal definitions are in Appendix A. 

## 5 Experiments 

We evaluate user simulator performance on our 500-workflow stratified evaluation set (125 workflows at each fallback depth 0–3) along two axes: the simulator’s prompting strategy and the assistant’s persona. We focus on open-weight models, which are cost-effective at scale and can be self-hosted. Frontier models would likely score higher but are expensive to run. Our aim is to understand the failure modes of accessible models and to find mitigations that make simulation with them practical. We set temperature to zero for both the user simulator and the assistant, and retry only on transient infrastructure failures (Appendix D).

5.1.3 Prompting Strategies 

Completing a workflow requires the simulator to remember which options it has already tried and which task it is on. We therefore evaluate five strategies that differ in what the simulator is asked to track across turns, from nothing at all to structured state with reasoning over it. 1. Baseline gives the workflow goal as natural-language instructions and asks the simulator to generate user utterances turn by turn, with no reasoning or state-tracking support. 2. Goal Reminder repeats the full goal at the end of each turn’s prompt, testing whether restating it without any structure is enough. 3. Summary asks the simulator to maintain three fields across turns: a cumulative free-text summary of every task attempted so far and its outcome, the current task, and the next action. 4. State Tracking Only replaces the summary with a structured JSON record (current task, fixed parameters, variable options, tried and remaining options), testing whether enumerating the option space suffices without reasoning over it. 5. ReUST (Reasoning + User State Tracking) reasons over that state. At each turn the simulator receives the goal, the conversation so far, and the previous turn’s state, then emits a JSON block recording the current task, which steps it has attempted and how they turned out, and the next action to take. It generates its utterance from that block. The instructions are task-agnostic; the Baseline and ReUST prompts, and an example of the state ReUST produces, are shown in Appendix E. 

## 6 Results 

6.1 Assistant Persona as a Confounder 

We ran the same simulator against all five assistant personas under identical experimental settings. When the assistant uses the Tool-only persona, which replies with only whether the task succeeded or failed, the simulator completes only 62.8% of workflows correctly. However, when the assistant uses Echo , which restates the details of the attempt it just made, the same simulator completes 92.8% of workflows (Table 2, right). The assistant’s reply acts as an external memory, so the simulator no longer has to track what it has already tried, and it achieves higher GSR as a result (Figure 4). User simulator fidelity should therefore be established by testing against several assistant response styles. For the remaining experiments we use the Terse assistant unless we say otherwise. We then ask whether ReUST removes that dependence. Under ReUST, the standard deviation of GSR across personas falls from 12.4 pt to 2.0 pt (Table 2, right). 6.2 State Tracking Improves Fidelity 

ReUST improves GSR from 81.0% to 93.6% on the Medium models and from 84.6% to 97.4% on the Large model (Table 3). The increase comes primarily from argument accuracy on the Medium models (91.1% to 97.6%) in the taxi, restaurant, and attraction bookings, where the arguments have to be derived from the outcome of an earlier task (Appendix C). We also compare ReUST with three simpler prompting strategies defined in §5.1.3 namely, repeating the goal every turn, summarizing the conversation in free text, and tracking state without reasoning. ReUST outperforms all three, reaching 93.2% GSR (Table 2, left). Each task in a workflow comes with a list of options to try in order, such as five car models for a taxi, and the task is finished as soon as one of them succeeds. State Tracking Only stores which options the simulator has tried and which are left, but not whether the last attempt succeeded. In half the runs (252 of 500), the simulator books the taxi and then carries on down the list, asking for the remaining car models. These extra calls violate strict goal following, which is why the strategy scores 35.0%, below the 72.6% of Baseline. 

6.3 Fidelity Degrades with Workflow Length 

We use path length, the number of steps a workflow requires, as our measure of complexity. Longer paths ask the simulator for more values and give it more chances to lose track of what it has already done. GSR degrades with path length under both strategies, by a similar amount for each (Figure 5). ## 7 Error Analysis 

To understand why simulators fail, we use an LLM judge to label every deviation from the workflow goal in the failed conversations. We analyze the Qwen3 235B runs under the default Terse assistant, 137 and 34 failed workflows out of 500 for Baseline and ReUST respectively, using Claude Opus 4.5 [Anthropic, 2025] at temperature zero as the judge. The judge sees the goal and the full transcript, and assigns each deviation one of six failure modes, defined with examples in Appendix B. Table 4 counts occurrences rather than conversations, since one conversation can show several modes. Under Baseline, half of all failures are goal drift: the simulator skips a step, switches to a fallback too early, or attempts tasks out of order. ReUST reduces goal drift by 85.5% in total, and also per failed conversation ( p < 0.001 for both). Early termination is flagged in almost every failed conversation under both strategies, and its reduction follows the overall reduction in failures rather than being an independent effect. Using the same judge model and sub-sampled dataset, we find the assistant’s tool selection accuracy and argument accuracy are 99.98% and 99.67% respectively, so the assistant is not a meaningful source of the GSR differences we report. 

## 8 Conclusion 

We introduced a 500-workflow HTN-based evaluation set for LLM-based user simulators, combining sequential execution, fallback logic, and cross-task dependencies. Our main finding is that user simulator fidelity depends on the assistant, so the assessment has to be done across several assistant response styles. Further, our proposed ReUST prompting strategy improves simulator fidelity across assistant personas for sufficiently capable models, making it a practical method. We also observe that, fidelity declines as workflows grow longer, so simulating long workflows faithfully is still a challenging problem. 

## Limitations 

The evaluation set covers five booking domains (hotel, train, taxi, restaurant, and attraction) within a single travel setting, so we cannot say how these results transfer to other task families. Our error 8analysis relies on LLM-as-a-Judge throughout, and we did not validate its labels against human annotation, so a judge that systematically mislabels a mode would bias the taxonomy in a direction we cannot detect. Our workflows are strictly forward-only—a completed task is never revisited and methods run in fixed order—whereas real users backtrack, so GSR measures fidelity to a prescribed policy rather than human-likeness. 9References

A.3 Survival Rate 

Survival Rate measures how far into the workflow the simulator progresses before making its first error. Unlike Argument Accuracy which averages over all steps, Survival Rate captures whether errors occur early (causing cascading failures) or late (indicating near-success). For example, a simulator that correctly executes 8 of 10 steps before failing has Survival Rate 0.8, while one that fails on step 2 has Survival Rate 0.2. Let N be the total steps and k be the number of correct steps before the first error. Then: Survival Rate = kN

A perfect trajectory yields 1.0; early failures yield proportionally lower scores. 

A.4 Goal Success Rate 

Goal Success Rate is our primary metric, measuring whether the simulator completed the entire workflow correctly. ## B Definition of Errors 

Goal Drift The user simulator deviates from the specified workflow sequence. This includes: (1) skipping intermediate steps within a task and jumping to future steps, (2) switching to a fallback method without exhausting the current method, (3) attempting tasks out of order, violating dependen-cies. Example (Intra-Task): After a booking fails for Wednesday, the user should try Thursday next, but instead skips to Friday. Example (Inter-Task): User tries to book a taxi to an attraction before booking the attraction itself. 

Inter-Task Dependency Failure The user simulator fails to maintain or correctly use information from previously completed tasks. Details from past tasks (e.g., booking reference, location name, time) are needed for future tasks but are not used or are used incorrectly. Example: User books a restaurant but then fails to use the restaurant’s location when booking a taxi to that restaurant. 

Misinterpretation of Assistant Response The user simulator fails to understand the assistant’s response and makes a wrong decision. User retries a task that was already successful, or moves on when they should retry. Example: Assistant confirms “restaurant booking successful for Thursday at 07:00 PM” but user tries to book again instead of moving to next task. 

Early Termination The user simulator ends the conversation before completing all tasks specified in the workflow goal. The conversation up to that point may be correct, but it is incomplete. 

Incomplete Arguments The user simulator omits preference arguments when making requests. Main arguments are provided but optional/preference arguments are missing. Example: For train booking, user provides departure, destination, time but omits the AC-tier class preference. 

Assistant Error The assistant makes tool calls with incorrect arguments or to wrong tools, halluci-nates tool results, or provides information not returned by the tool.

## D Retry Policy 

The retry mechanism operates at two levels: (1) API-level retries (up to 10 attempts with exponential backoff, capped at 30 seconds) handle transient infrastructure failures such as rate limiting and API timeouts; (2) conversation-level retries (up to 5 attempts) restart the entire conversation if all API retries are exhausted. Under deterministic decoding, successful API calls produce identical outputs, so retries do not affect semantic behavior. The retry configuration is identical across all prompting strategies.
