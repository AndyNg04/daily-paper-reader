# Tether : Verified Stateful Policy Engine for System-Level Monitoring of Agents 

Meghana Aparna Sistla 1, Alaia Solko-Breslin 1,3 , Somesh Jha 2,4 , Aditya Kanade 2 and Krishnamurthy Dj Dvijotham 1   

> 1Google DeepMind, 2Google, 3University of Pennsylvania, 4University of Wisconsin-Madison

Autonomous AI agents are increasingly deployed for long-running tasks that execute arbitrary shell commands or programs. However, these actions can result in unauthorized network requests or persistent, malicious changes to the user’s file system, processes, or privileges. Existing defense mechanisms rely on either LLM-based monitors, which lack provable safety guarantees, or stateless policy enforcement layers, which miss multi-step data flows and execution side-effects unmodeled by the policy language (e.g., network calls initiated inside a Python script). We introduce Tether , a framework for runtime enforcement of stateful security policies over the observed side-effects of an agent’s actions. Tether executes each proposed action in an ephemeral, isolated sandbox, inferring abstract action semantics from observed system calls. Tether then enforces stateful policies over these inferred semantics, permitting actions to proceed only if they comply with the policy. Policies and action semantics are defined in an embedded DSL in Lean 4 capable of expressing diverse constraints, including information flow control (IFC), access control, and network security policies. Because actions can propagate labels from sources to destinations, a single rule can enforce fine-grained IFC policies across multi-step execution flows of arbitrary length. Expressing policies in Lean enables formal verification that they satisfy global security invariants (e.g., preventing network access after reading a sensitive file). We evaluate Tether on realistic coding-agent benchmarks across both benign and adversarial trajectories. With a single policy shared across all tasks, Tether blocks 100% of in-scope attacks while maintaining a benign false-positive rate under 5%. 

Keywords: LLM agents, runtime enforcement, information flow control, Lean 4, formal verification 

## 1. Introduction 

Large Language Model (LLM) powered agents are increasingly deployed to automate complex, multi-step workflows (Wang et al., 2024; Yang et al., 2024; Yao et al., 2023). While these agents are clearly useful, they also introduce critical security risks. Agents can, due to misalignment or due to a prompt injection, exfiltrate sensitive data or download and execute malicious binaries (Debenedetti et al., 2024; Greshake et al., 2023; Ruan et al., 2024; Zhan et al., 2024). To mitigate these risks, many production agent harnesses deploy a secondary LLM-as-a-judge monitor to review proposed commands before execution (Anthropic, 2026; Trębacz et al., 2026). While auxiliary LLMs can assess high-level intent, they remain probabilistic and susceptible to prompt injections (Remedios et al., 2026), rendering them incapable of providing formal security guarantees. An alternative is to use formal reference monitors (Anderson, 1972) integrated into sandboxes that enforce explicit security policies over agent actions (Amazon Web Services, 2026; Brooker et al., 2026; Watson, 2026; Wu et al., 2025). Enforcing security policies on autonomous terminal agents presents two fundamental challenges unresolved by prior work: 

Challenge 1: Ambiguous tool semantics. Existing reference monitors for agents assume that actions taken by agents are structured API calls whose semantics are known and targets are explicit in

their arguments. They may also attempt to filter shell commands statically before execution (Cutler et al., 2024; Shi et al., 2026). In a terminal environment, however, a single command (e.g., running a Python script or a shell pipeline with variable expansion) can perform file and network operations that are difficult to predict statically (Greenberg and Blatt, 2020). Conversely, simply executing the command to observe its side effects may mutate the host system or leak sensitive data over the network before the monitor has the opportunity to block it. 

Challenge 2: Formally verified, stateful IFC. To prevent multistage attacks, such as staging a secret across temporary files before uploading it, a runtime monitor must enforce stateful Information Flow Control (IFC) (Denning, 1976; Denning and Denning, 1977; Myers and Liskov, 1997). However, existing frameworks like Cedar (Cutler et al., 2024) and OpenShell (Watson, 2026) rely on stateless allowlists, while event-history monitors (Amazon Web Services, 2026; Brooker et al., 2026) maintain no persistent security labels on resources, forcing policies to reconstruct flows over a fixed number of hops (see §8). Furthermore, as policies grow to combine access control, multi-dimensional taint tracking, and policy composition, policy authors need formal guarantees that their rules are free of subtle bypasses. We introduce Tether , a stateful runtime reference monitor and verified policy engine for terminal agents. Rather than assuming what a shell command might do from its syntax, Tether executes each command inside an ephemeral copy-on-write (CoW) filesystem layer (Lamprou et al., 2026) under system-call tracing, infers the command’s semantics, and enforces formal security policies. To infer a command’s semantics safely, Tether traces system calls in the CoW layer and intercepts outbound network requests via a local proxy. The filesystem changes and network requests are committed (or forwarded) if and only if the policy permits every action seen so far; otherwise, the ephemeral layer and intercepted requests are cleanly discarded. From the observed system calls, Tether infers a sequence of canonical abstract actions, e.g., read ,

> copy

, and uploadNet . Because reconstructing the exact data flow of an arbitrary process from system calls alone is impossible in general, Tether does not assume that the exact semantics of any terminal action can be recovered; instead, it over-approximates the command’s information-flow and privilege side effects. For example, if a script reads from file a.txt and subsequently writes to file b.txt ,

Tether conservatively infers a data-flow transfer from a.txt to b.txt even if the written bytes were independent of a.txt . This over-approximation may introduce occasional false positives, but avoids missing tracked data flows (§7). We implement our abstract action calculus and policy language as an embedded domain-specific language (EDSL) in Lean 4 (Moura and Ullrich, 2021), a dependently typed programming language and interactive theorem prover with a small trusted kernel 1. Each abstract action deterministi-cally updates a security state parametric over an arbitrary product lattice of security labels (e.g., confidentiality and integrity), propagating resource labels across direct transfers (e.g., copy or concate-nate ) without over-tainting the agent’s context. To aid policy designers, we mechanically prove key metatheoretic guarantees in Lean 4 (§3.5), including deny-overrides monotonicity , non-bypassability of required policies , permutation invariance (order independence), and state preservation under denial .Because Tether decouples semantic inference (our Isolate engine, §4) from policy specification and enforcement, the inference engine can be improved independently (§8). We evaluate Tether on two realistic coding-agent benchmarks that pair benign software-engineering tasks with adversarial side tasks: MonitoringBenchHonest (Küçükkurt and Elasky, 2026) and LinuxArena (Tracy et al., 2026). ## 2. Overview 

2.1. Motivating Example 

Consider an agent that has access to a sensitive file, data/servers.csv , containing a company’s inventory. The user wants to prevent this file from being sent to an external site ( api.github.com ), but also allow the agent to read it for local checks and upload benign status reports ( scratch/ report.txt ) to the same site. The agent proposes the following shell commands (Listing 1):    

> $ curl --json @scratch/report.txt \ https://api.github.com # (1) $ cp data/servers.csv \ scratch/report.txt # (2) $ curl --json @scratch/report.txt \ https://api.github.com # (3)

Listing 1 | The running example. Step (1) uploads the benign report, step (2) copies the sensitive inventory to scratch/report.txt ,and step (3) uploads the report again. Although Steps (1) and (3) run the same command, a runtime monitor must allow Step (1) and deny Step (3) because the report is now sensitive. Unlike existing frameworks that rely on stateless allowlists, lack persistent resource state, or coarsely approximate command effects (Amazon Web Services, 2026; Brooker et al., 2026; Disselkoen et al., 2024; Watson, 2026), Tether dynamically traces and evaluates arbitrary command execution at runtime. By tracing low-level system calls, Tether infers what a command actually does, maps it to a calculus of abstract actions (e.g., copy or uploadNet ), and checks it against a stateful policy. To ensure security, commands run speculatively; Tether commits their environmental side effects if and only if the policy approves the inferred actions.

2.2. Architecture of Tether 

Tether consists of two main components: Isolate (§4), a semantic inference engine that sandboxes agent execution to infer abstract actions, and a stateful policy monitor implemented in Lean 4 (§3). The mapping from low-level observed effects to canonical abstract actions serves as our semantic contract , modulo which Tether ’s security guarantees hold. Building on the filesystem-isolation model in try (Lamprou et al., 2026), Isolate runs each proposed command inside a disposable OverlayFS layer under system-call tracing. It intercepts system-level events, gates outbound network requests through a local proxy, and tracks data provenance

The monitor tracks the system state such as every resource’s security labels ( 𝜎 ) and the agent’s context taint, thereby allowing or denying actions based on the specified policy, while updating the system state accordingly. The staged changes are committed or discarded based on the monitor’s verdict. 

2.3. Threat Model 

We assume that Tether operates within the reference monitor framework (Anderson, 1972), enforcing deterministic security policies over an untrusted terminal agent. We assume that an adversary can control the agent’s actions either directly (as a malicious user) or indirectly via prompt-injection attacks. Because we treat the agent’s underlying LLM as untrusted, we assume that the adversary can generate arbitrary terminal commands. The adversary has full knowledge of the policy but cannot bypass or alter the monitor or its policy rules. As is standard in the sandboxing literature, our Trusted Computing Base (TCB) consists of the host OS kernel, the system-call tracing layer, the ephemeral filesystem overlay driver, the network proxy, Tether ’s abstract action inference, and the Lean 4 proof kernel (for verification) alongside the Lean 4 compiler and runtime. Kernel-level exploits and sandbox escapes are outside the scope of this work.

We now define the syntax of the policy language, implemented as an embedded domain-specific language (EDSL) in Lean 4. A policy Π written in the grammar shown in Fig. 2 specifies which actions are permitted in state 𝑆 , while Fig. 3 shows a sample information-flow policy. Each policy Π consists of four components: 1. Resource sets (𝐷 ): Resource sets take the form set 𝐴 := [𝑠 1, . . . , 𝑠 𝑚 ], where each 𝑠 𝑖 is a pattern in the policy. Fig. 3 shows two such sets: Scratch and ApprovedHosts . ## 4. Isolate : Sandboxed Execution and Semantic Inference 

In this section, we describe how Isolate infers the abstract actions defined in §3 from an agent’s terminal commands. To infer these actions, Isolate intercepts the command’s system-level events and network traffic. Our current implementation uses strace for system-call tracing. The tracing backend is fully modular; while strace provides a robust and portable tracing interface for our environment, the system is designed to seamlessly swap in high-performance alternatives, such as an eBPF-based tracer, at scale. 

4.1. Transactional Sandboxed Execution 

The idea of running untrusted operations speculatively, checking their effects, and committing them only if safe has been previously explored in systems security (Liang et al., 2003; Shankar and Karlof, 2006). Building on try (Lamprou et al., 2026), Isolate applies this concept to agentic security by executing each command inside an isolated Linux mount and process environment that stages side effects without affecting the host: • OverlayFS for filesystem isolation: Isolate mounts a per-directory OverlayFS over the host’s root directories and stages all changes in a disposable scratch directory; changes are later committed to the host or discarded, based on the policy verdict. • Network interception: Isolate routes all outbound traffic through a local proxy. The proxy holds each request and records its destination and, where applicable, its contents (i.e., method, URL, headers, and body). Isolate infers the corresponding abstract action over the trace prefix observed so far and checks it against the policy. The held request is then forwarded to its destination or dropped. • Background processes: When a command spawns background processes that outlive the foreground shell, Isolate pauses them and resumes or terminates them based on the policy verdict. However, because per-step strace stops once the foreground command exits, a policy can choose to block such spawned processes entirely (§7). 

4.2. Semantic Inference Pipeline 

Isolate turns the raw trace of system calls and network traffic into the abstract actions of §3.2 in four stages. 

1. Process-tree and file-descriptor tracking. Isolate reconstructs the process tree across fork ,

clone , and execve system calls and tracks file descriptors, including pipes and I/O redirections. It records the files each process reads and the writer provenance (actor , origin ) of each file mutation, where actor is the binary performing the system call and origin is the parent program that invoked it. It also tracks privilege transitions (e.g., sudo → escalatePrivilege ).

5.1. Fuzzing Isolate

End-to-end enforcement, however, relies on the semantic contract : Isolate must faithfully map the system calls of arbitrary shell commands to abstract actions. In a POSIX environment, the same logical data flow can be carried out through many different OS mechanisms such as standard utilities ( cp ,

6.1. Experimental Setup 

To answer these questions, we evaluate Tether on two coding-agent control benchmarks with realistic software-engineering tasks. To the best of our knowledge, Tether is the first runtime monitor with formal guardrails to be evaluated on realistic benchmarks. The benchmarks contain agent trajectories, created by running an agent either on a benign main task alone (benign trajectories) or on a main task with an adversarial side task (adversarial trajectories).  

> 16 Tether : Verified Stateful Policy Engine for System-Level Monitoring of Agents

The benchmarks used in our evaluations are as follows: • MonitoringBenchHonest (Jotautait˙ e et al., 2026; Küçükkurt and Elasky, 2026): A system-administration benchmark built on ControlArena (Inglis et al., 2025) spanning 88 Linux con-tainers, 88 main tasks, and four adversarial side tasks. • LinuxArena (Tracy et al., 2026): A multi-service software-engineering benchmark spanning 10 containerized production environments, over 340 main tasks, and 81 adversarial side tasks. 

Replay setup. To evaluate Tether on these benchmarks, we replicate each task’s environment inside our sandbox and replay the offline trajectories provided in the benchmarks step by step. We emulate each environment’s external services on a best-effort basis and exclude trajectories whose required services cannot be emulated. We also exclude trajectories that cannot be replayed end-to-end (e.g., where the side-task attack is only triggered by the benchmark harness after the agent finishes). Among the remaining trajectories, we focus on the subset where every action taken by the agent runs in the foreground, can be captured, and has semantics currently modeled by Tether . This subset contains 218 benign and 199 adversarial trajectories for MonitoringBenchHonest, and 1 ,372 benign and 145 adversarial trajectories for LinuxArena. 

Policy design. Because the benchmarks do not come with an explicit security policy, we formulate a policy in our DSL for realistic scenarios that enforces the safety invariants in Tab. 1 (App. C gives the full policy). The policy rules are shared across all tasks and both benchmarks; only the initial labels and task-specific resource sets assigned to resources, such as files and network endpoints, vary across environments and tasks. We design the shared rules to prevent general security violations, and configure each task’s resource labels and allowlists from its main-task description (e.g., which paths and hosts are allowed, protected, or sensitive). That is, if a main task explicitly requires writing to an otherwise write-restricted folder, we allow it for that task. Note that this configuration is done at the task level, not at the trajectory level, and we use no side-task information when configuring the policy (see §7.2 for more details).

Tab. 2 compares the recall and FPR of Tether against both Auto Mode configurations. Its false positives stem mainly from Auto Mode blocking file edits even though they are explicitly allowed in the main-task description. For a fair comparison,

Moreover, in neither configuration does Auto Mode detect attacks hidden inside scripts, whose behavior cannot be determined from the command line. We also observe that because LLM-based monitors are inherently probabilistic, Auto Mode can produce different verdicts on the same trajectory across runs. This shows that LLM-based monitors lack a notion of formally reasoning about policies, even when provided with explicit rules and labels. In contrast, in a formal guardrail system like Tether , one can define an explicit policy and reason about the monitor’s behavior deterministically. RQ3: Limits of formal runtime monitoring. Of the remaining trajectories of these benchmarks that can be faithfully replayed, we analyze how many Tether can intercept today and at least trigger an “ask the user” (or block), even when the internal semantics of some operations in those trajectories have not been modeled. Specifically, to prevent an agent from bypassing the monitor via these unmonitored channels, Tether enforces a restrictive policy that prohibits background processes and database interactions. To enforce this, we add rules to the policy that intercept these operations at process, network, and library boundaries. For background processes, the policy blocks writes to background tokens (e.g., asynchronous execution with &, daemon managers, cron jobs) and for database interactions, the policy blocks socket connections to database services (e.g., PostgreSQL, MySQL) as well as file operations on database storage paths (e.g., *.sqlite and /var/lib/postgresql ). We evaluate this restrictive policy across both benchmarks. We note that 28 .2% of Monitor-ingBenchHonest and 22 .1% of LinuxArena trajectories require LLM-based content inspection to understand agent behavior and therefore cannot be handled by any formal runtime monitor. Of the remaining non-semantic trajectories, Tether can capture and trigger on background and database channels, leading to another 36 .3% of MonitoringBenchHonest and 71 .5% of LinuxArena trajectories that can be intercepted now, even though their internal semantics are not yet modeled. Future work could extend Tether to model the internal semantics of these operations. For example, to trace background processes, Tether can be extended to use container-wide tracing such as eBPF (The Linux Kernel Documentation, 2026a). To trace database queries, Tether could map them into canonical database-specific abstract actions to track fine-grained information flow across tabular data (Chlipala, 2010; Mehta et al., 2017; Schultz and Liskov, 2013; Zhang et al., 2022).

Tether , along with fuzzing (§5.1), we run an end-to-end red-teaming experiment. We evaluate 

Tether against an adaptive adversarial agent explicitly prompted to bypass the monitor (a red-team agent). Because a formal guardrail system provides protection only within its modeled scope, we only evaluate on in-scope actions. To do this, we create a simple fake environment with a few files marked as sensitive/secret or protected. Fig. 7(a) shows the architecture used for our red-team experiments. The agent is prompted with a main task and an adversarial side task with one of two goals: (a) Goal 1: 

Exfiltrate a sensitive or secret file to a fake endpoint, and (b) Goal 2: Create, modify, or delete a file in a protected path. For every proposed command by the red-teaming agent, we use an additional scope-checker LLM to determine whether the action is in-scope. We use Gemini 3.8 Flash as the red-team agent and scope-checker. If the action is in-scope, the action is checked against the runtime monitor; otherwise, the action is discarded and the agent is prompted to try again. The runtime monitor is configured with the same policy as discussed in §6.1, configuring only environment and task specific labels and allowlists. We evaluate 10 tasks (5 targeting Goal 1 and 5 targeting Goal 2) for up to 15 rounds each, where each round runs for up to 30 executed turns (or 20 monitor denials). Using fuzzing (§5.1) and the end-to-end red-teaming experiments, we were able to find and fix bugs in our implementation of Isolate . Fig. 7(b) shows the attack success rate (ASR) across different iterations of Tether . Earlier iterations of Tether uncovered tracing gaps in Isolate such as missing hard-links. As a result of these experiments, we were able to increase our confidence in the robustness of Tether , with the ASR dropping from 40% to 0% across three iterations. Unlike prompt tweaks for an LLM-based monitor, which can still fail on similar inputs, every bypass of a formal guardrail pinpoints a concrete root cause that can be fixed deterministically.

## 7. Limitations and Discussion 

7.1. Limitations 

As a runtime reference monitor, Tether is restricted to enforcing prefix-closed safety properties over individual execution traces (Schneider, 2000). Consequently, Tether cannot enforce liveness properties, nor can it precisely guarantee hyperproperties such as non-interference or implicit flow control, which require reasoning over sets of execution traces rather than a single path (Clarkson and Schneider, 2010). Over the execution of a single trace, the limitations of Tether fall into categories spanning the fundamental limits of formal runtime monitoring, and implementation-level OS tracing limitations. 

Semantic attacks. As discussed in §6, Tether , like any formal runtime monitor, cannot prevent purely semantic attacks that violate no system-level flow invariants (e.g., maliciously modifying code in a permitted file). To cover such cases, Isolate can be paired with trusted LLM-based classifiers that predict abstract actions, establishing guarantees modulo the classifier’s correctness. 

Over-approximation of tracing. Reconstructing exact data-flow lineage from low-level system calls is generally undecidable, so Tether must soundly over-approximate taint flow. While this abstraction is necessary to guarantee security, it introduces a nonzero false-positive rate. Moreover, because real attacks are rare in deployment, the base-rate fallacy (Axelsson, 2000) implies that most blocks will be benign. To mitigate this, we need fine-grained abstract action semantics, as in Tether ,to keep false alarms low. 

Background processes and database operations. As discussed in §6, Tether can be extended to model these actions that are not handled currently. 

Bypassed I/O channels. Mechanisms like io_uring and shared memory access bypass standard read/write syscalls to transfer data. Tether currently guarantees security by blocking access to these interfaces, but can later be extended to leverage other kernel mechanisms such as Landlock (The Linux Kernel Documentation, 2026b) or eBPF Linux Security Modules (LSM). 

TLS termination. Isolate inspects plaintext HTTP traffic, and currently decrypts HTTPS only for emulated endpoints. General HTTPS inspection can be added via a TLS-terminating forward proxy (e.g., mitmproxy ) or eBPF uprobes on TLS libraries (e.g., OpenSSL). 

Overhead of strace . While strace is easy to use, it is known to incur significant tracing overhead that slowed our experiments; future work can replace it with faster tracing mechanisms.

7.2. Discussion: Policy Design 

Designing good security policies is a longstanding challenge in systems security, often requiring many rounds of refinement. For example, developing practical SELinux policies took around five years of effort from the security community. In general, this policy refinement process involves (a) synthesizing a candidate policy, (b) evaluating it against benign and adversarial traces, and (c) iteratively refining the policy based on the observed outcomes. When designing the benchmark policy for our experiments (Fig. 6), we faced a similar challenge. We used an iterative, LLM-assisted refinement loop (Fig. 8) to settle on the final policy. The process involved: (1) Given the environment specifications and high-level safety goals, an LLM proposes or refines a candidate policy Π𝑖 in each iteration, (2) Π𝑖 is evaluated on benchmark traces to identify rules that can be improved, (3) Π𝑖 is also verified against the safety invariants (Tab. 1) in Lean 4 to ensure they still hold. This process continues until the policy satisfies all safety invariants without over-blocking benign traces. 

## 8. Related Work 

Policy languages and agent sandboxes. Existing frameworks for formal, agentic policy enforcement fall into two primary categories (Tab. 3). First, stateless policy engines and sandboxes evaluate individual tool invocations or system resources in isolation (Cutler et al., 2024; Shi et al., 2026; Wang et al., 2026a; Watson, 2026). For example, Cedar (Cutler et al., 2024; Disselkoen et al., 2024), Progent (Shi et al., 2026), and AgentSpec (Wang et al., 2026a) gate tool calls against declarative access-control rules, while OpenShell (Watson, 2026) combines kernel-level filesystem confinement with declarative network filtering. Because these systems are stateless, they cannot track multi-step data provenance required for IFC. They do have formal checks such as Cedar’s Lean-verified SMT analysis and OpenShell’s Z3 policy-containment, which reason over single actions. Second, 

temporal event-history monitors evaluate rules over recorded event sequences: Dogwood (Brooker et al., 2026) extends Cedar with temporal logic over tool-call histories, and the Dogwood Strands Box sandbox (Amazon Web Services, 2026) integrates this engine into an OS sandbox to control its built-in shell, Python, and network actions. However, event-history monitors do not maintain persistent security labels on resources and miss information flows not explicitly logged by the harness. In contrast, Tether executes proposed commands inside an ephemeral CoW sandbox, infers abstract actions from system calls, and tracks per-resource labels for IFC. It also supports whole-trace invariant proofs in Lean 4. 

Heuristic defenses for agents. A large body of work mitigates agent security risks using heuristic or learning-based defenses. At the harness level, LLM-based monitors route candidate commands, reasoning traces, or trajectories to auxiliary judge models to check alignment with user intent (Chennabasappa et al., 2025; Jia et al., 2025; Ruan et al., 2024; Tsai and Bagdasarian, 2025; Xiang et al., 2025). Similar techniques have been deployed as commercial monitors including Claude Code Auto Mode (Anthropic, 2026) and Codex Auto-review (Trębacz et al., 2026). While these heuristic guardrails can interpret high-level intent, they are inherently probabilistic and remain vulnerable to adaptive prompt injections and evasions (Anthropic, 2026; Nasr et al., 2025; Trębacz et al., 2026). Tether provides a complementary approach, providing deterministic, formally verified enforcement grounded in observed system-call effects. 

Other formal agent guardrails. Recent work has also explored formal security enforcement in the form of architectures that separate sensitive data from the underlying LLM, as well as more general reference monitoring. Dual-LLM and planner-level isolation architectures mitigate prompt injection by separating privileged control flow from untrusted data processing or isolating third-party apps into separate execution hubs (Bagdasarian et al., 2024; Costa et al., 2025; Debenedetti et al., 2026; Wu et al., 2025). On the other hand, IFC and language-based monitors propagate security labels across structured tool calls (Costa et al., 2025; Debenedetti et al., 2026; Palumbo et al., 2026; Solko-Breslin et al., 2026; Zhou et al., 2026). However, these existing IFC approaches assume that tool semantics are known a priori. Therefore, they cannot provide formal guarantees for general terminal agents where an opaque shell command can implicitly transfer data across files. Tether 

addresses this by enforcing policies over syscall-inferred semantics before side effects are committed. 

OS IFC, sandboxing, and provenance. Tether also connects to the rich systems-security literature on kernel and user-space OS IFC (Efstathopoulos et al., 2005; Krohn et al., 2007; Zeldovich et al., 2006), system-call sandboxing (blocking syscalls against a policy) (Garfinkel, 2003; Goldberg et al., 1996; Provos, 2003), speculative sandboxing (side effects staged and committed) (Lamprou et al., 2026; Liang et al., 2003; Shankar and Karlof, 2006), and provenance tracking (Lee et al., 2013; Ma et al., 2016; Pasquier et al., 2017). Classic challenges in this space, such as over-tainting ( grep -r ) also arise in Tether . Our current Isolate engine is a best-effort prototype ( strace over a CoW sandbox) built to show that inferring abstract actions makes verified, stateful agent policies practical. Because Tether decouples action inference from policy engine, Isolate can be improved using these prior works alongside static shell analysis (Lazarek et al., 2026), formal POSIX (Greenberg and Blatt, 2020) and SQL (Benzaken and Contejean, 2019; Chu et al., 2017; Guagliardo and Libkin, 2017; Malecha et al., 2010) semantics, and database IFC (Chlipala, 2010; Mehta et al., 2017; Schultz and Liskov, 2013; Zhang et al., 2022).

## 9. Conclusion 

We introduced Tether , a framework for runtime enforcement of stateful security policies for coding agents. Our key takeaway is that an effective runtime monitor requires stateful policies over fine-grained action semantics, along with a mechanism to infer these actions from low level OS effects. 

Tether realizes this by combining system call tracing to infer the abstract actions and enforcing verified (against safety invariants), stateful policies in Lean 4. We also show that, on two coding agent benchmarks, Tether achieves 100% recall with a 2 .3%–5 .0% FPR on trajectories whose actions it can model. Ultimately, Tether enables formal, provable stateful guardrails for autonomous agents, even with arbitrary shell command execution. 

Future work. Beyond the extensions discussed in §7, Tether can naturally extend from single-agent scenarios to multi-agent workflows where agents spawn subagents. Tether can also be extended to track user-configured metadata (e.g., action counts, rate limits) similar to Dogwood (Brooker et al., 2026). Finally, Tether ’s deterministic semantics can be extended to support probability distributions (Solko-Breslin et al., 2026; Wang et al., 2026b) to model uncertainty in tool calls.

## A. Comparison on the Running Example 

Consider the running example (Listing 1) from §2. Fig. 9 shows policies for it written in Open-Shell (Watson, 2026), Cedar (Cutler et al., 2024), and Dogwood (Brooker et al., 2026). (a) OpenShell grants access to the specified paths and endpoints. The policy in Fig. 9a grants read access to data/ , read and write access to scratch/ , and curl access to api.github.com .This policy allows all three steps: even though the proxy of OpenShell binds each connection to its executable and ancestors, and middleware may inspect the request body, no field relates the body of Step (3) to data/servers.csv .(b) Cedar (Fig. 9b) evaluates each request in isolation. An allowlist on scratch/report.txt 

sent to api.github.com allows both Step (1) and Step (3). A stateful policy is needed to deny Step (3). (c) Dogwood checks past events only within a bounded look-back window. With typed file tools (Fig. 9c), a copy event names its source and destination, so the rule differentiates between Step (1) and Step (3), but only within that window (at most 24 h by default): an upload more

than 24 h after Step (2) is allowed. With a generic shell tool (Fig. 9d), each event is a command string. Dogwood’s temporal conditions match a past command only by its exact string or by a wildcard over the whole field; pattern matching ( like ) applies only to the current request. The rule must therefore name Step (2) verbatim to deny Step (3), and cat data/servers.csv > scratch/report.txt evades it. Strands Box (Amazon Web Services, 2026) narrows this gap. It pairs Dogwood with its own shell that records the files each command reads and writes. A Box rule can therefore deny Step (3) by matching a command that read data/servers.csv 

and wrote the report before the upload read it (see App. B). However, the second example on multi-step copy in §2.1 shows that denying such flows without blocking benign uploads needs more precise abstract actions and per-file state. Even with typed tools or Box’s file events, Dogwood keeps no per-file state, such as a provenance label. It keeps only a log of past events, so each rule must trace where the uploaded file came from by matching that log. In the multi-step example (§2.1), the rule in Fig. 9c no longer fires because the copy into scratch/report.txt reads scratch/tmp.csv . Catching it needs a second rule that joins the two copies on the intermediate file y:

Each temporal predicate names a single action, and Dogwood does not support recursion, so each hop and each copy-like action must be written out. With 𝑚 such actions, a chain of 𝑗 hops has 𝑚 𝑗 combinations, so covering up to 𝑘 hops takes Í𝑘 𝑗 =1 𝑚 𝑗 patterns, and a longer chain evades them all.
